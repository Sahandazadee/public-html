چرا MQTT؟ مشکل روش قدیمی (HTTP)

در درس ۴.۲ یک وب سرور روی ESP32 ساختی. آن روش یک مشکل بزرگ دارد: ESP32 فقط داخل شبکه خانه دیده می‌شود. از بیرون خانه (مثلا از اینترنت گوشی) نمی‌توانی مستقیم به آن وصل شوی، چون مودم اجازه نمی‌دهد کسی از بیرون به دستگاه‌های داخل وصل شود. این یک قابلیت امنیتی خوب است، نه ایراد.

راه حل این است که هم ESP32 و هم گوشی تو، هر دو به یک سرور وسط در اینترنت وصل شوند. هر دو اتصال «از داخل به بیرون» است و مودم با آن مشکلی ندارد. این سرور وسط در دنیای MQTT اسمش Broker (کارگزار) است.

مثال از زندگی روزمره: کانال تلگرام

یک کانال تلگرام را تصور کن به اسم «دمای اتاق علی». ESP32 مثل مدیر کانال است که هر ۱۰ ثانیه یک پست می‌گذارد: «۲۴٫۵ درجه». گوشی تو، لپ‌تاپ تو و یک داشبورد، عضو کانال هستند. مدیر کانال لازم نیست بداند چند نفر عضوند یا آن‌ها کجای دنیا هستند؛ فقط پست را به خود تلگرام می‌دهد و تلگرام به همه اعضا می‌رساند.

در MQTT: تلگرام = Broker، اسم کانال = Topic (موضوع)، پست گذاشتن = Publish (انتشار)، عضو شدن = Subscribe (اشتراک)، هر کسی که به تلگرام وصل است (چه مدیر، چه عضو) = Client (مشتری).

به یک نکته مهم دقت کن: در MQTT فرستنده و گیرنده هرگز مستقیم با هم حرف نمی‌زنند. هر دو فقط Broker را می‌شناسند. به این می‌گویند «جدا بودن» (Decoupling). ESP32 لازم نیست IP گوشی تو را بداند و گوشی هم لازم نیست بداند ESP32 کجاست.

مقایسه با HTTP: «مدام پرسیدن» در برابر «خبرم کن»

فرض کن می‌خواهی LED را از گوشی روشن کنی. با HTTP (بدون MQTT) ESP32 باید مدام از یک سرور بپرسد «فرمان جدید داری؟». به این روش Polling (پرس‌وجوی پشت سر هم) می‌گویند. با MQTT، ESP32 یک بار وصل می‌شود، اتصال را باز نگه می‌دارد و Broker هر وقت فرمانی رسید، فورا آن را روی همان اتصال باز می‌فرستد (Push).

مفهوم‌های اصلی MQTT، یکی‌یکی

۱. Topic (موضوع) و سلسله‌مراتب آن

Topic یک رشته متنی است که با / به چند «سطح» تقسیم می‌شود، درست مثل آدرس پستی یا مسیر پوشه در کامپیوتر. مثلا:

  • home/livingroom/temp دمای پذیرایی
  • home/livingroom/humidity رطوبت پذیرایی
  • home/kitchen/temp دمای آشپزخانه
  • home/kitchen/light/set فرمان چراغ آشپزخانه

لازم نیست Topic را از قبل روی Broker «بسازی». همین که اولین بار کسی روی آن Publish کند، وجود دارد. Topic به حروف بزرگ و کوچک حساس است: Home/Temp با home/temp فرق دارد.

قانون‌های نام‌گذاری Topic که بعدا نجاتت می‌دهند

۱) از کلی به جزئی برو: خانه/اتاق/دستگاه/کمیت. ۲) فقط حروف کوچک انگلیسی، عدد، خط تیره و /. فاصله و حروف فارسی از نظر پروتکل مجازند ولی دردسر می‌سازند. ۳) Topic را با / شروع نکن؛ /home/temp یک سطح اول خالی دارد و با home/temp فرق دارد. ۴) برای فرمان‌ها از پسوند /set استفاده کن تا با وضعیت (/state) قاطی نشود.

۲. Wildcard: اشتراک در چند موضوع با یک دستور

وقتی Subscribe می‌کنی (فقط موقع اشتراک، نه موقع انتشار) می‌توانی از دو علامت ویژه استفاده کنی:

۳. QoS: چقدر مطمئن باشیم پیام رسیده؟

QoS (کیفیت سرویس) عددی بین ۰ تا ۲ است که فرستنده برای هر پیام انتخاب می‌کند. هر چه بیشتر، اطمینان بیشتر ولی پیام‌های رفت‌وبرگشتی بیشتر.

مثال از زندگی روزمره: اداره پست

QoS 0 = نامه معمولی در صندوق پست می‌اندازی و می‌روی. معمولا می‌رسد، ولی اگر گم شد کسی خبردار نمی‌شود. QoS 1 = نامه سفارشی با رسید. اگر رسید برنگشت، دوباره می‌فرستی؛ ممکن است گیرنده دو نسخه بگیرد. QoS 2 = نامه سفارشی با تایید دو مرحله‌ای؛ دقیقا یک بار می‌رسد ولی کاغذبازی‌اش بیشتر است.

QoSضمانتتعداد پیام در شبکهکجا مناسب است
0حداکثر یک بار (ممکن است گم شود)۱دمای هر ۱۰ ثانیه؛ اگر یکی گم شد، ۱۰ ثانیه بعد تازه‌اش می‌رسد
1حداقل یک بار (ممکن است تکراری برسد)۲فرمان «LED روشن» یا هشدار؛ تکرار آن ضرری ندارد
2دقیقا یک بار۴شمارش پول یا دوز دارو؛ جایی که تکرار فاجعه است (در پروژه‌های ESP32 کم پیش می‌آید)
محدودیت کتابخانه PubSubClient

کتابخانه‌ای که در این درس استفاده می‌کنیم (PubSubClient) برای سبک بودن، فقط با QoS 0 منتشر می‌کند و موقع Subscribe فقط QoS 0 یا 1 را پشتیبانی می‌کند. برای پروژه‌های آموزشی و بیشتر پروژه‌های خانگی کاملا کافی است. اگر روزی QoS 2 لازم داشتی، کتابخانه‌های دیگری مثل کلاینت داخلی ESP-IDF (esp-mqtt) هست.

۴. پیام ماندگار (Retained)

معمولا Broker پیام را به مشترک‌هایی که همان لحظه وصل‌اند می‌رساند و بعد فراموشش می‌کند. حالا فرض کن گوشی‌ات را ساعت ۹ روشن می‌کنی ولی ESP32 آخرین بار ساعت ۸:۵۹ وضعیتش را فرستاده بود. گوشی تا پیام بعدی هیچ نمی‌داند.

اگر پیام را با پرچم retain بفرستی، Broker آخرین پیام آن Topic را نگه می‌دارد و به هر مشترک تازه، بلافاصله بعد از Subscribe تحویل می‌دهد. مثل «پیام سنجاق‌شده» بالای کانال تلگرام.

کی retain بزنیم، کی نه؟

برای وضعیت (online یا offline، LED روشن است یا خاموش، آخرین دما) retain خوب است. برای فرمان (مثل «در را باز کن») retain خطرناک است: هر بار ESP32 ریست شود و دوباره Subscribe کند، فرمان قدیمی را دوباره می‌گیرد و در دوباره باز می‌شود!

۵. وصیت‌نامه (Last Will and Testament)

اگر ESP32 ناگهان خاموش شود (برق برود یا Wi-Fi قطع شود)، فرصت ندارد خداحافظی کند. MQTT برای این لحظه راه حل دارد: Client موقع اتصال یک پیام «وصیت‌نامه» به Broker می‌دهد: «اگر من بی‌خبر ناپدید شدم، این پیام را روی این Topic منتشر کن.» اگر Client مودبانه (با DISCONNECT) قطع شود، وصیت‌نامه اجرا نمی‌شود.

۶. Keep-alive: «هنوز زنده‌ای؟»

Broker از کجا بفهمد ESP32 ناپدید شده؟ با Keep-alive. Client قول می‌دهد حداقل هر N ثانیه یک پیام (یا یک PINGREQ کوچک) بفرستد. اگر Broker حدود ۱٫۵ برابر این زمان هیچ چیزی نشنود، اتصال را مرده حساب می‌کند و وصیت‌نامه را منتشر می‌کند. در PubSubClient مقدار پیش‌فرض ۱۵ ثانیه است (با setKeepAlive عوضش می‌کنی).

چرا این به تو مربوط است؟

چون PING را خود کتابخانه داخل تابع mqtt.loop() می‌فرستد. اگر در loop() یک delay(30000) بگذاری، ESP32 نه PING می‌فرستد و نه پیام ورودی را می‌خواند؛ Broker بعد از حدود ۲۲ ثانیه اتصال را می‌بندد و تو خطای -3 (اتصال از دست رفت) می‌بینی. برای همین در این درس همه زمان‌بندی‌ها با millis() است، نه delay.

۷. Client ID: کارت ملی هر دستگاه

هر Client موقع اتصال یک شناسه (Client ID) می‌فرستد. قانون مهم: دو Client با یک ID نمی‌توانند هم‌زمان وصل باشند. اگر دومی وصل شود، Broker اولی را بیرون می‌اندازد. اگر هر دو برنامه «اتصال دوباره خودکار» داشته باشند، مدام همدیگر را بیرون می‌اندازند و تو قطع و وصل بی‌پایان می‌بینی. برای همین ID را از روی MAC برد و یک عدد تصادفی می‌سازیم.

بخش الف: بروکر عمومی HiveMQ (بدون ثبت‌نام)

هشدار جدی: این Broker عمومی است

هر کسی در دنیا می‌تواند روی هر Topicی Subscribe کند، حتی # (یعنی همه چیز!). پس: ۱) هیچ اطلاعات شخصی، رمز یا موقعیت مکانی نفرست. ۲) هیچ وسیله واقعی خطرناک (قفل در، بخاری، پمپ آب) را با آن کنترل نکن؛ هر کسی می‌تواند فرمان بفرستد. ۳) اسم Topic را یکتا انتخاب کن (مثلا esp32course/ali1234/...) وگرنه پیام‌های تو با پیام‌های هزاران دانشجوی دیگر که Topicی مثل test/temp دارند قاطی می‌شود. پیام‌ها رمزنگاری هم نمی‌شوند (پورت 1883 متن ساده است).

چرا GPIO13 برای سنسور؟ چون در کل دوره DHT22 همیشه روی همین پایه است (مثل درس ۳.۳)، پس سیم‌کشی بردبوردت از درسی به درس دیگر عوض نمی‌شود. تازه پایه‌ای «امن» هم هست: Strapping نیست، فقط ورودی نیست و به فلش وصل نیست. نکته: GPIO13 جزو ADC2 است و وقتی Wi-Fi روشن است آنالوگ‌خوانی روی آن کار نمی‌کند؛ ولی DHT22 دیجیتال است، پس هیچ مشکلی نیست. LED هم مثل درس ۲.۲ روی GPIO4 می‌ماند.

const char* WIFI_PASS = "";

// ---- بروکر عمومی HiveMQ ----
const char* MQTT_HOST = "broker.hivemq.com";

// پیشوند یکتا: ali1234 را با اسم و عدد دلخواه خودت عوض کن

const char* TOPIC_CLIMATE = BASE "/sensor/climate";
const char* TOPIC_CMD     = BASE "/led/set";
const char* TOPIC_STATUS  = BASE "/status";

const int LED_PIN = 4;
const int DHT_PIN = 13;

DHT dht(DHT_PIN, DHT22);
WiFiClient net;              // لوله TCP خام
PubSubClient mqtt(net);      // MQTT روی همان لوله

char clientId[40];
unsigned long lastPublish = 0;
unsigned long lastTry = 0;

// هر پیامی روی Topicهای مشترک‌شده برسد، این تابع صدا زده می‌شود
void onMessage(char* topic, byte* payload, unsigned int length) {
  char msg[32];
  unsigned int n = (length < sizeof(msg) - 1) ? length : sizeof(msg) - 1;
  memcpy(msg, payload, n);
  msg[n] = '\0';             // payload خودش '\0' ندارد!
  Serial.printf("<- [%s] %s\n", topic, msg);

  if (strcmp(topic, TOPIC_CMD) == 0) {
    if (strcmp(msg, "ON") == 0) {
      digitalWrite(LED_PIN, HIGH);
    } else if (strcmp(msg, "OFF") == 0) {
      digitalWrite(LED_PIN, LOW);
    } else {
      Serial.println("Unknown command (use ON or OFF)");
    }
  }
}

void connectWiFi() {
  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  Serial.print("WiFi");
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  Serial.print(" connected, IP: ");
  Serial.println(WiFi.localIP());
}

bool connectMqtt() {
  Serial.printf("MQTT: connecting as %s ... ", clientId);
  // وصیت‌نامه: اگر بی‌خبر قطع شدیم، Broker روی status بنویسد offline
  if (mqtt.connect(clientId, TOPIC_STATUS, 1, true, "offline")) {
    Serial.println("OK");
    mqtt.publish(TOPIC_STATUS, "online", true);   // true یعنی retained
    mqtt.subscribe(TOPIC_CMD, 1);
    return true;
  }
  Serial.printf("failed, state=%d\n", mqtt.state());
  return false;
}

void publishClimate() {
  float t = dht.readTemperature();
  float h = dht.readHumidity();
  if (isnan(t) || isnan(h)) {
    Serial.println("DHT22 read failed");
    return;
  }
  JsonDocument doc;
  doc["temp"] = serialized(String(t, 1));   // 24.3 با یک رقم اعشار
  doc["hum"] = serialized(String(h, 1));
  doc["uptime"] = millis() / 1000;
  char buf[128];
  serializeJson(doc, buf, sizeof(buf));
  bool ok = mqtt.publish(TOPIC_CLIMATE, buf);
  Serial.printf("-> %s %s\n", buf, ok ? "" : "(publish FAILED)");
}

  dht.begin();
  connectWiFi();
  // Client ID یکتا: MAC برد + یک عدد تصادفی
  String mac = WiFi.macAddress();   // مثل 24:6F:28:AB:CD:EF
  mac.replace(":", "");
  snprintf(clientId, sizeof(clientId), "esp32-%s-%04X", mac.c_str(), (unsigned)(esp_random() & 0xFFFF));
  mqtt.setServer(MQTT_HOST, MQTT_PORT);
  mqtt.setCallback(onMessage);
}

void loop() {
  if (WiFi.status() != WL_CONNECTED) {
    return;                  // Wi-Fi خودش دوباره وصل می‌شود (درس ۴.۱)
  }
  if (!mqtt.connected()) {
    if (lastTry == 0 || millis() - lastTry > 5000) {   // هر ۵ ثانیه یک تلاش
      lastTry = millis();
      connectMqtt();
    }
    return;                  // تا وصل نشده‌ایم، کار دیگری نکن
  }
  mqtt.loop();               // خواندن پیام‌های ورودی + فرستادن PING

  if (millis() - lastPublish >= 10000) {
    lastPublish = millis();
    publishClimate();
  }
}

این برنامه بلندترین برنامه‌ای است که تا حالا دیده‌ای، ولی از تکه‌های آشنا ساخته شده. روی هر کارت کلیک کن تا خط‌های مربوط پررنگ شود:

  1. چهار کتابخانه. WiFi.h برای اتصال به مودم، PubSubClient.h برای زبان MQTT، ArduinoJson.h برای ساختن متن JSON و DHT.h برای خواندن سنسور. هر کتابخانه یک کار را خوب انجام می‌دهد. PubSubClient خودش اینترنت بلد نیست؛ فقط «زبان» MQTT را روی یک اتصال TCP که ما به او می‌دهیم صحبت می‌کند. همین جدایی باعث می‌شود بعدا با عوض کردن فقط یک خط، اتصال را امن (TLS) کنیم.
  2. نام و رمز Wi-Fi. در شبیه‌ساز Wokwi شبکه مجازی Wokwi-GUEST بدون رمز است. روی برد واقعی اسم و رمز مودم خودت را بنویس. Wokwi یک مودم مجازی دارد که واقعا به اینترنت وصل است، پس ESP32 شبیه‌سازی‌شده هم می‌تواند به HiveMQ واقعی وصل شود.
  3. آدرس Broker و پورت. broker.hivemq.com روی پورت 1883، پورت استاندارد MQTT بدون رمزنگاری. هر سرویس روی یک «در» (پورت) مشخص گوش می‌دهد. 1883 برای MQTT ساده و 8883 برای MQTT امن (TLS) قرارداد جهانی است؛ بعدا هر دو را می‌بینی.
  4. ساختن اسم Topicها. #define BASE یک پیشوند مشترک می‌سازد. در C++ وقتی دو رشته ثابت کنار هم نوشته شوند (BASE "/led/set")، کامپایلر آن‌ها را به هم می‌چسباند: "esp32course/ali1234/led/set". پیشوند را فقط یک جا عوض می‌کنی و همه Topicها یکتا می‌شوند. اگر ali1234 را عوض نکنی و هم‌کلاسی‌ات هم عوض نکند، هر کدام از شما LED دیگری را هم کنترل می‌کند!
  5. سه شیء اصلی. dht سنسور است. net یک اتصال TCP خام است. mqtt کلاینت MQTT است که net را به عنوان «لوله» می‌گیرد. مثل نامه و پاکت: PubSubClient نامه (پیام MQTT) را می‌نویسد، WiFiClient آن را در پاکت TCP می‌گذارد و از طریق Wi-Fi می‌فرستد.
  6. متغیرهای سراسری. جا برای Client ID، و دو «زمان‌سنج» برای آخرین انتشار و آخرین تلاش اتصال. نوع unsigned long است چون millis() همین نوع را برمی‌گرداند؛ با int بعد از حدود ۲۴ روز سرریز و خراب می‌شد.
  7. امضای تابع Callback. PubSubClient هر وقت پیامی برسد این تابع را با سه ورودی صدا می‌زند: اسم Topic (رشته C)، آرایه بایت‌های پیام (payload) و طول آن. امضا (نوع و ترتیب ورودی‌ها) باید دقیقا همین باشد، وگرنه setCallback کامپایل نمی‌شود. به این الگو «Callback» می‌گویند: تو تابع را می‌دهی، کتابخانه هر وقت لازم شد صدایش می‌زند.
  8. مهم‌ترین تله MQTT: payload رشته نیست! بایت‌های پیام را در یک آرایه ۳۲ خانه‌ای کپی می‌کنیم (حداکثر ۳۱ بایت) و خودمان آخرش '\0' می‌گذاریم. در C++ توابع رشته‌ای مثل strcmp و printf("%s") آن‌قدر جلو می‌روند تا به بایت صفر برسند. payload این بایت صفر را ندارد؛ پس بدون این کپی، strcmp از آخر پیام رد می‌شود و آشغال حافظه را هم مقایسه می‌کند؛ نتیجه: گاهی «ON» تشخیص داده نمی‌شود یا برنامه کرش می‌کند. شرط n هم جلوی نوشتن بیرون از آرایه را می‌گیرد اگر کسی پیام خیلی بلند بفرستد.
  9. چاپ پیام ورودی. مثلا <- [esp32course/ali1234/led/set] ON. همیشه اول ببین دقیقا چه رسیده. نصف مشکلات MQTT این است که پیام با فاصله اضافه، حروف کوچک یا Topic اشتباه رسیده.
  10. تصمیم‌گیری. اگر پیام روی Topic فرمان بود: ON روشن، OFF خاموش، هر چیز دیگر پیام خطا. اول Topic را چک می‌کنیم چون بعدا ممکن است در چند Topic مشترک شویم و همه پیام‌ها به همین یک تابع می‌آیند. شاخه آخر (پیام ناشناخته) برای عیب‌یابی است: اگر on با حرف کوچک بفرستی، می‌فهمی چرا کار نکرد.
  11. اتصال Wi-Fi. همان کد درس ۴.۱: حالت Station، شروع اتصال، صبر تا وصل شود، چاپ IP. اینجا در setup منتظر ماندن با delay اشکالی ندارد، چون بدون Wi-Fi هیچ کار دیگری از دستگاه برنمی‌آید.
  12. اتصال به Broker همراه با وصیت‌نامه. ورودی‌های connect به ترتیب: Client ID، Topic وصیت‌نامه، QoS وصیت‌نامه (۱)، retain وصیت‌نامه (true)، متن آن (offline). وصیت‌نامه فقط هنگام اتصال قابل تعیین است، نه بعدا. retain بودنش یعنی هر کس بعدا Subscribe کند، فورا می‌فهمد دستگاه خاموش است.
  13. بعد از اتصال موفق. وضعیت online را با retain منتشر می‌کنیم (روی وصیت‌نامه قبلی می‌نویسد)، سپس در Topic فرمان با QoS 1 مشترک می‌شویم. Subscribe باید بعد از هر اتصال دوباره تکرار شود. ما «clean session» داریم، یعنی Broker بعد از قطع شدن، اشتراک‌های قبلی را فراموش می‌کند. برای همین subscribe داخل همین تابع است، نه در setup.
  14. اگر اتصال شکست خورد. عدد mqtt.state() را چاپ می‌کنیم. این عدد دقیقا می‌گوید مشکل کجاست (شبکه، رمز، Client ID تکراری...). جدول معنی همه عددها در بخش عیب‌یابی است.
  15. خواندن سنسور و بررسی خطا. اگر سنسور جواب ندهد، کتابخانه DHT مقدار NaN (یعنی «عدد نیست») برمی‌گرداند؛ با isnan آن را می‌گیریم و چیزی منتشر نمی‌کنیم. انتشار nan روی داشبورد یعنی نمودار خراب و گیج سردرگم. داده بد نفرستادن بهتر از فرستادن داده غلط است.
  16. ساختن JSON با ArduinoJson 7. JsonDocument doc; یک سند خالی می‌سازد و با doc["کلید"] = مقدار پر می‌شود. serialized(String(t, 1)) عدد را با دقیقا یک رقم اعشار به صورت متن خام در JSON می‌گذارد. در نسخه ۷ اندازه سند خودکار تنظیم می‌شود و دیگر لازم نیست مثل نسخه ۶ عدد ظرفیت حدس بزنی. String(t, 1) از چاپ اعدادی مثل 24.29999924 جلوگیری می‌کند (float در حافظه دقیقا 24.3 نیست). یک JSON کوتاه یعنی پیام کوچک‌تر.
  17. تبدیل به متن و انتشار. serializeJson سند را در آرایه buf می‌نویسد (با '\0' در آخر). mqtt.publish آن را روی Topic می‌فرستد و true یا false برمی‌گرداند. اگر publish مقدار false بدهد، دو علت رایج دارد: اتصال قطع است، یا پیام (Topic + متن + سربرگ) از بافر ۲۵۶ بایتی کتابخانه بزرگ‌تر شده. بافر ۱۲۸ بایتی ما هم عمدا از آن کوچک‌تر است.
  18. ساختن Client ID یکتا. MAC برد را بدون دونقطه می‌گیریم و یک عدد تصادفی ۴ رقمی هگز (از مولد اعداد تصادفی سخت‌افزاری esp_random()) به آن اضافه می‌کنیم. نتیجه چیزی مثل esp32-246F28ABCDEF-3A9C. MAC هر برد واقعی یکتاست. ولی در Wokwi ممکن است همه دانشجوها MAC یکسانی داشته باشند؛ آن عدد تصادفی جلوی بیرون انداختن همدیگر از Broker عمومی را می‌گیرد.
  19. معرفی Broker و Callback. setServer فقط آدرس را ذخیره می‌کند؛ اتصال واقعی بعدا در loop انجام می‌شود. setCallback تابع onMessage را ثبت می‌کند. اتصال را عمدا در loop گذاشتیم تا یک کد واحد هم «اولین اتصال» و هم «اتصال دوباره بعد از قطعی» را انجام دهد.
  20. اگر Wi-Fi قطع است، صبر کن. از loop برمی‌گردیم و دور بعد دوباره چک می‌کنیم. هسته ESP32 به طور پیش‌فرض خودش Wi-Fi را دوباره وصل می‌کند (درس ۴.۱). تلاش برای وصل شدن به Broker بدون Wi-Fi فقط وقت تلف می‌کند.
  21. اتصال دوباره بدون مسدود کردن (Non-blocking). اگر به Broker وصل نیستیم، حداکثر هر ۵ ثانیه یک بار تلاش می‌کنیم، و بین تلاش‌ها loop آزاد است. نسخه بد و رایج در اینترنت یک while (!mqtt.connected()) { ...; delay(5000); } است که برنامه را تا ابد گیر می‌اندازد؛ حتی دکمه‌ها و سنسورها هم کار نمی‌کنند. در روش ما اگر بخواهی دکمه‌ای هم بخوانی، بین تلاش‌ها کار می‌کند. شرط lastTry == 0 باعث می‌شود اولین تلاش بلافاصله انجام شود. یادت باشد خود connect() اگر سرور جواب ندهد تا حدود ۱۵ ثانیه (Socket timeout) صبر می‌کند.
  22. قلب برنامه: mqtt.loop(). پیام‌های رسیده را می‌خواند و onMessage را صدا می‌زند، و اگر لازم باشد PING زنده‌بودن را می‌فرستد. اگر این خط اجرا نشود، هیچ فرمانی نمی‌رسد و Broker بعد از حدود ۲۲ ثانیه اتصال را مرده حساب می‌کند. هر چیزی که loop را طولانی متوقف کند (delay بلند، حلقه while) دشمن این خط است.
  23. انتشار هر ۱۰ ثانیه با millis. اگر از آخرین انتشار ۱۰۰۰۰ میلی‌ثانیه گذشته، دوباره منتشر کن. DHT22 حداکثر هر ۲ ثانیه یک بار اندازه تازه می‌دهد، و دمای اتاق در ۱۰ ثانیه تقریبا عوض نمی‌شود. فرستادن سریع‌تر فقط ترافیک و (در سرویس‌هایی مثل Adafruit IO) سهمیه تو را هدر می‌دهد.

این پروژه کاملا در Wokwi شبیه‌سازی می‌شود، چون Wokwi یک شبکه Wi-Fi مجازی به اسم Wokwi-GUEST (بدون رمز) دارد که واقعا به اینترنت وصل است. مراحل: ۱) پروژه ESP32 خالی باز کن. ۲) diagram.json را با متن زیر عوض کن و کد را در sketch.ino بچسبان. ۳) در زبانه Library Manager (یا با ساختن فایل libraries.txt) سه کتابخانه را اضافه کن: PubSubClient، ArduinoJson و DHT sensor library. ۴) ▶ را بزن. روی سنسور DHT22 کلیک کن تا بتوانی دما را با اسلایدر عوض کنی و ببینی عدد منتشرشده عوض می‌شود.

تست از بیرون: فرستادن فرمان و دیدن داده

ESP32 کارش را می‌کند؛ حالا یک Client دیگر لازم داری که نقش «گوشی» را بازی کند. سه راه:

  1. ساده‌ترین: HiveMQ WebSocket Client در مرورگر. به hivemq.com/demos/websocket-client برو و بدون تغییر تنظیمات روی Connect بزن. این صفحه از طریق WebSocket به همان broker.hivemq.com وصل می‌شود.
  2. Subscribe کن. در بخش Subscriptions روی Add New Topic Subscription بزن و بنویس esp32course/ali1234/# (با پیشوند خودت). حالا هر ۱۰ ثانیه JSON دما را می‌بینی، و پیام online را هم که retain شده بود فورا می‌بینی.
  3. فرمان بفرست. در بخش Publish، Topic را esp32course/ali1234/led/set و Message را ON بنویس و Publish را بزن. LED باید روشن شود. بعد OFF.
  4. وصیت‌نامه را ببین. برد را از برق بکش (یا شبیه‌سازی Wokwi را متوقف کن). بعد از حدود ۲۰ ثانیه روی .../status پیام offline ظاهر می‌شود. این همان Last Will است!
ابزارهای دسکتاپ برای کار جدی‌تر

MQTTX (از شرکت EMQ، رایگان و متن‌باز، برای ویندوز، مک و لینوکس) و MQTT Explorer (رایگان، درخت Topicها را به شکل پوشه نشان می‌دهد و برای دیدن ساختار عالی است). در هر دو یک اتصال جدید با Host broker.hivemq.com و Port 1883 بساز. دقت کن MQTT Explorer به طور پیش‌فرض ممکن است روی # مشترک شود و روی Broker عمومی سیلی از پیام‌های دیگران ببینی؛ Topic را به پیشوند خودت محدود کن.

وقتی شبکه مقصر است، نه کد

بعضی شبکه‌های مدرسه، دانشگاه، اداره یا Wi-Fi عمومی (کافه، هتل) پورت‌های 1883 و 8883 را می‌بندند و فقط وب معمولی را باز می‌گذارند. اگر خطای -2 (اتصال شبکه برقرار نشد) گرفتی در حالی که Wi-Fi وصل است، اول همان برنامه را روی شبکه خانه یا هات‌اسپات گوشی امتحان کن. اگر آنجا کار کرد، مشکل از مسیر شبکه است نه کد تو. راه حرفه‌ای و مستقل از اینترنت هم این است که Broker را روی کامپیوتر خودت اجرا کنی (پایین‌تر در همین درس).

بخش ب: HiveMQ Cloud با اتصال امن TLS (پورت 8883)

بروکر عمومی برای یادگیری عالی است، ولی برای پروژه‌ای که واقعا در خانه استفاده می‌کنی، باید دو چیز داشته باشی: رمز (تا هر کسی نتواند فرمان بفرستد) و رمزنگاری (تا کسی وسط راه پیام و رمزت را نخواند). HiveMQ Cloud یک طرح رایگان (Serverless Free) دارد که هر دو را می‌دهد. در زمان نوشتن این درس، طرح رایگان تا ۱۰۰ اتصال هم‌زمان و ۱۰ گیگابایت ترافیک در ماه را پوشش می‌دهد که برای ده‌ها ESP32 خیلی زیاد است (عددها ممکن است عوض شوند؛ صفحه قیمت‌گذاری HiveMQ را ببین).

  1. ثبت‌نام. در HiveMQ Cloud روی دکمه ثبت‌نام رایگان بزن (با ایمیل یا حساب گوگل؛ کارت بانکی لازم نیست). بعد از تایید ایمیل، در کنسول یک Cluster از نوع Serverless با طرح Free بساز. ساخته شدنش چند ثانیه تا یکی دو دقیقه طول می‌کشد.
  2. آدرس Cluster را بردار. روی Manage Cluster بزن. در زبانه Overview چیزی شبیه abc123def456.s1.eu.hivemq.cloud (به اسم Cluster URL) و پورت 8883 (TLS) می‌بینی. پورت 8884 هم که آنجا نوشته برای WebSocket (مرورگر) است، نه ESP32.
  3. نام کاربری و رمز بساز. در زبانه Access Management یک Credential بساز (مثلا کاربر esp32-room با رمز بلند تصادفی) و Permission آن را روی Publish and Subscribe بگذار. بدون Credential هیچ Clientی وصل نمی‌شود. یک Credential دوم (مثلا phone) هم برای ابزار تست بساز؛ دو Client با یک کاربر مشکلی ندارند، ولی جدا بودن بعدا عیب‌یابی را راحت‌تر می‌کند.
  4. تست بدون ESP32. زبانه Web Client همان کنسول، یک کلاینت MQTT داخل مرورگر است. با Credential دوم وصل شو و روی esp32course/# مشترک شو؛ بعد از آپلود کد ESP32، پیام‌هایش باید اینجا بیاید. (صفحه عمومی websocket-client بخش الف هم با وارد کردن آدرس Cluster، پورت 8884، تیک SSL و نام کاربری و رمز کار می‌کند.)

TLS به زبان ساده

TLS همان چیزی است که قفل سبز کنار آدرس سایت‌ها در مرورگر را می‌سازد. دو کار می‌کند: ۱) رمزنگاری: پیام‌ها طوری درهم می‌شوند که کسی وسط راه (مثلا روی Wi-Fi کافه) نتواند بخواندشان. ۲) احراز هویت سرور: مطمئن می‌شوی واقعا با HiveMQ حرف می‌زنی، نه با یک سرور جعلی که خودش را جای HiveMQ جا زده.

رمزنگاری مثل گذاشتن نامه در پاکت دربسته است. ولی اگر پاکت را به آدم اشتباه بدهی، دربسته بودن فایده ندارد! احراز هویت یعنی قبل از دادن پاکت، کارت شناسایی تحویل‌گیرنده را چک کنی. «گواهی ریشه» (Root CA) مثل مهر رسمی دولت روی آن کارت است: اگر مهر اصل باشد، کارت را قبول می‌کنی.

همه رمزهای این درس در یک فایل جمع می‌شوند: secrets.h، همان الگویی که در درس ۴.۱ یاد گرفتی. در Arduino IDE روی فلش کوچک ⋯ کنار اسم تب‌ها بزن، New Tab را انتخاب کن، اسمش را secrets.h بگذار و مقادیر خودت را در آن بنویس. بخش ج هم از همین فایل استفاده می‌کند؛ پس هر چه الان داری بنویس و بقیه را بعدا.

  2. اسم و رمز Wi-Fi. همان دو خط درس ۴.۱. در Wokwi بنویس "Wokwi-GUEST" و رمز خالی "". یک فایل رمز برای کل درس: هر برنامه فقط خط‌هایی را که لازم دارد استفاده می‌کند.
  3. نام کاربری و رمز HiveMQ Cloud. همان Credential که در Access Management ساختی (مرحله ۳ بالا). این همان رمزی است که TLS در راه رسیدن به Broker از آن محافظت می‌کند؛ بدون TLS هر کسی روی همان شبکه می‌تواند بخواندش.
  4. نام کاربری و کلید Adafruit IO. برای بخش ج؛ تا به آنجا نرسیده‌ای همین مقادیر نمونه را نگه دار. کلید AIO رمز واقعی کل حساب Adafruit توست، پس جایش اینجاست، نه داخل برنامه.
رمز را در کد نگذار و آپلودش نکن

اگر کدت را روی GitHub می‌گذاری، secrets.h را در فایل .gitignore بنویس تا هیچ‌وقت آپلود نشود (درس ۴.۱). هر سال هزاران رمز و کلید API لو می‌رود فقط چون مستقیم داخل کد نوشته شده بودند. در مورد گواهی ریشه برنامه پایین نگرانی نیست؛ آن عمومی است و محرمانه نیست.

// هر پیامی روی Topicهای مشترک‌شده برسد، این تابع صدا زده می‌شود
void onMessage(char* topic, byte* payload, unsigned int length) {
  char msg[32];
  unsigned int n = (length < sizeof(msg) - 1) ? length : sizeof(msg) - 1;
  memcpy(msg, payload, n);
  msg[n] = '\0';             // payload خودش '\0' ندارد!
  Serial.printf("<- [%s] %s\n", topic, msg);

  if (strcmp(topic, TOPIC_CMD) == 0) {
    if (strcmp(msg, "ON") == 0) {
      digitalWrite(LED_PIN, HIGH);
    } else if (strcmp(msg, "OFF") == 0) {
      digitalWrite(LED_PIN, LOW);
    } else {
      Serial.println("Unknown command (use ON or OFF)");
    }
  }
}

void connectWiFi() {
  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  Serial.print("WiFi");
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  Serial.print(" connected, IP: ");
  Serial.println(WiFi.localIP());
}

bool connectMqtt() {
  Serial.printf("MQTT: connecting as %s ... ", clientId);
  // وصیت‌نامه: اگر بی‌خبر قطع شدیم، Broker روی status بنویسد offline
  if (mqtt.connect(clientId, MQTT_USER, MQTT_PASS,     // ★ + نام کاربری و رمز
                   TOPIC_STATUS, 1, true, "offline")) {
    Serial.println("OK");
    mqtt.publish(TOPIC_STATUS, "online", true);   // true یعنی retained
    mqtt.subscribe(TOPIC_CMD, 1);
    return true;
  }
  Serial.printf("failed, state=%d\n", mqtt.state());
  return false;
}

void publishClimate() {
  float t = dht.readTemperature();
  float h = dht.readHumidity();
  if (isnan(t) || isnan(h)) {
    Serial.println("DHT22 read failed");
    return;
  }
  JsonDocument doc;
  doc["temp"] = serialized(String(t, 1));   // 24.3 با یک رقم اعشار
  doc["hum"] = serialized(String(h, 1));
  doc["uptime"] = millis() / 1000;
  char buf[128];
  serializeJson(doc, buf, sizeof(buf));
  bool ok = mqtt.publish(TOPIC_CLIMATE, buf);
  Serial.printf("-> %s %s\n", buf, ok ? "" : "(publish FAILED)");
}

  mqtt.setServer(MQTT_HOST, MQTT_PORT);
  mqtt.setCallback(onMessage);
}

void loop() {
  if (WiFi.status() != WL_CONNECTED) {
    return;                  // Wi-Fi خودش دوباره وصل می‌شود (درس ۴.۱)
  }
  if (!mqtt.connected()) {
    if (lastTry == 0 || millis() - lastTry > 5000) {   // هر ۵ ثانیه یک تلاش
      lastTry = millis();
      connectMqtt();
    }
    return;                  // تا وصل نشده‌ایم، کار دیگری نکن
  }
  mqtt.loop();               // خواندن پیام‌های ورودی + فرستادن PING

  if (millis() - lastPublish >= 10000) {
    lastPublish = millis();
    publishClimate();
  }
}

اگر درست انجام داده باشی، خروجی Serial دقیقا مثل بخش الف است (فقط اتصال اول یکی دو ثانیه بیشتر طول می‌کشد، چون دست دادن TLS محاسبه سنگینی دارد). این نسخه در Wokwi هم کار می‌کند: آنجا هم یک تب secrets.h اضافه کن (درس ۴.۱ روشش را نشان داده) با "Wokwi-GUEST" و رمز خالی.

  1. چهار کتابخانه بخش الف، به‌اضافه WiFiClientSecure. WiFiClientSecure نسخه رمزنگاری‌شده WiFiClient است که داخلش کتابخانه mbedTLS کار TLS را انجام می‌دهد. چون PubSubClient فقط یک «لوله» می‌خواهد، با عوض کردن نوع لوله کل ارتباط امن می‌شود و بقیه کد MQTT دست نمی‌خورد.
  2. رمزها از secrets.h می‌آیند. #include "secrets.h" (با گیومه، یعنی «در پوشه خود همین برنامه بگرد») شش اسم را وارد می‌کند. بلوک #ifndef MQTT_USER ... #endif بررسی می‌کند که MQTT_USER وجود دارد یا نه؛ اگر هنوز secrets.h کوتاه درس ۴.۱ را داری، کامپایلر یک هشدار روشن چاپ می‌کند و با مقادیر نمونه جلو می‌رود تا برنامه باز هم کامپایل شود. هشدار روشن «MQTT_USER در secrets.h تعریف نشده» خیلی راحت‌تر از یک عالمه خطای «was not declared» فهمیده می‌شود. با رمز نمونه، Broker راهت نمی‌دهد (خطای 4 یا 5) و این یادت می‌اندازد رمز واقعی را بنویسی.
  3. آدرس Cluster خودت و پورت 8883. آدرس را از زبانه Overview همان Cluster کپی کن. روی پورت 8883، Broker انتظار دارد اول «دست دادن» TLS انجام شود. اگر اشتباهی WiFiClient ساده را به 8883 وصل کنی، اتصال با خطای -2 یا -4 شکست می‌خورد.
  4. Topicها و پایه‌ها: مثل بخش الف. همان پیشوند، همان سه Topic، LED روی GPIO4 و DHT22 روی GPIO13. روی Cluster خودت کس دیگری Topicهایت را نمی‌بیند، ولی پیشوند یکتا باز هم عادت خوبی است: روزی که پروژه را به Broker دیگری ببری، چیزی با چیز دیگری قاطی نمی‌شود.
  5. گواهی ریشه (Root CA). این متن، کلید عمومی سازمان ISRG (صادرکننده گواهی‌های Let's Encrypt) است. R"EOF( ... )EOF" یک «رشته خام» C++ است که اجازه می‌دهد متن چندخطی را بدون گذاشتن \n در آخر هر خط بنویسی. گواهی سرور HiveMQ Cloud را Let's Encrypt امضا کرده، و امضای Let's Encrypt را ISRG Root X1. ESP32 با داشتن ریشه می‌تواند کل زنجیره را بررسی کند. این گواهی تا ژوئن ۲۰۳۵ معتبر است؛ ولی اگر روزی HiveMQ صادرکننده‌اش را عوض کرد، باید گواهی را به‌روز کنی. گواهی فعلی را همیشه از مستندات HiveMQ چک کن.
  6. لوله امن. حالا net از نوع امن است و mqtt روی آن کار می‌کند. TLS حدود ۴۰ تا ۵۰ کیلوبایت RAM برای بافرها و محاسبات رمزنگاری لازم دارد. ESP32 این را راحت دارد (برای همین روی بردهای کوچک‌تر مثل آردوینو UNO این کار ممکن نیست).
  7. متغیرهای سراسری و Callback: عینا مثل بخش الف. payload را در بافر کپی کن، '\0' بگذار، Topic را چک کن، بعد ON یا OFF. TLS کاملا داخل لوله است. پیام‌هایی که از آن بیرون می‌آیند دقیقا مثل قبل‌اند، پس کدی که آن‌ها را پردازش می‌کند هیچ تغییری نمی‌کند.
  8. اتصال Wi-Fi: همان تابع. فقط حالا WIFI_SSID و WIFI_PASS از secrets.h می‌آیند. در بخش الف متغیر بودند و اینجا #define هستند. برای WiFi.begin فرقی نمی‌کند: در هر دو حالت یک متن تحویل می‌گیرد.
  9. connect با نام کاربری و رمز. ترتیب ورودی‌ها: ID، کاربر، رمز، سپس همان چهار ورودی وصیت‌نامه. خط فقط برای جا شدن در صفحه دو تکه شده است. PubSubClient چند نسخه از connect دارد (Overload)؛ کامپایلر بر اساس تعداد و نوع ورودی‌ها تشخیص می‌دهد کدام را می‌خواهی. ترتیب را جابه‌جا نکن.
  10. publishClimate: مثل بخش الف. خواندن سنسور، ساختن JSON، انتشار. رمزنگاری داده را لوله در مسیر خروج انجام می‌دهد، نه این تابع.
  11. شروع setup: مثل بخش الف. Serial، پایه LED، سنسور، Wi-Fi و Client ID یکتا. Client ID در HiveMQ Cloud هم باید یکتا باشد؛ دو برد با یک ID مدام همدیگر را بیرون می‌اندازند.
  12. setCACert در برابر setInsecure. setCACert یعنی «فقط به سروری اعتماد کن که گواهی‌اش با این ریشه امضا شده». setInsecure یعنی «رمزنگاری کن، ولی هر کسی گفت من HiveMQ هستم قبول کن». هر کدام را که انتخاب کنی، باید قبل از اولین connect صدا زده شود. حقیقت صادقانه: setInsecure جلوی کسی که فقط گوش می‌دهد را می‌گیرد، ولی جلوی کسی که خودش را جای سرور جا بزند (حمله مرد میانی) را نمی‌گیرد؛ آن وقت رمز MQTT تو را هم می‌دزدد. برای تست سریع قابل قبول است، برای دستگاهی که در خانه می‌ماند نه.
  13. معرفی Broker و loop: مثل بخش الف. اتصال دوباره بدون گیر کردن هر ۵ ثانیه، mqtt.loop() و انتشار هر ۱۰ ثانیه. تنها فرقی که حس می‌کنی: هر تلاش برای اتصال به خاطر دست دادن TLS یکی دو ثانیه بیشتر طول می‌کشد. این هم دلیل دیگری است که تلاش‌های اتصال را با فاصله انجام دهیم.
اگر اتصال TLS شکست خورد

در Serial Monitor چیزی مثل X509 - Certificate verification failed یا -2 می‌بینی. به ترتیب چک کن: ۱) آدرس Cluster دقیقا کپی شده؟ ۲) پورت 8883 است؟ ۳) گواهی کامل و بدون حذف خط کپی شده؟ ۴) برای تشخیص، یک بار با setInsecure() امتحان کن: اگر وصل شد، مشکل فقط از گواهی است.

بخش ج: داشبورد آماده با Adafruit IO

تا اینجا داده را فقط به صورت متن دیدی. Adafruit IO یک سرویس IoT است که هم Broker MQTT دارد، هم داده را ذخیره می‌کند و هم داشبورد گرافیکی (گیج، نمودار، کلید، اسلایدر) دارد؛ بدون یک خط کد وب. یعنی در ۱۵ دقیقه یک اپ کنترل از راه دور داری که روی گوشی هم باز می‌شود.

مفهوم‌های Adafruit IO

  • Feed (خوراک): یک «جوی داده» با اسم، مثل temperature یا led. هر عددی که به آن بفرستی با تاریخ و ساعت ذخیره می‌شود. هر Feed یک key دارد (اسم با حروف کوچک و خط تیره) که در Topic استفاده می‌شود.
  • Dashboard (داشبورد): صفحه‌ای که بلوک‌ها (Block) رویش می‌چینی. هر بلوک به یک Feed وصل است: گیج Feed دما را نشان می‌دهد، کلید (Toggle) روی Feed فرمان می‌نویسد.
  • AIO Key: رمز حساب تو برای دستگاه‌ها. در MQTT نام کاربری = نام کاربری Adafruit، و رمز = AIO Key.
  • قالب Topic: username/feeds/feed-key؛ مثلا ali_maker/feeds/temperature.

Adafruit IO اول روی Topic username/throttle هشدار می‌دهد و اگر ادامه بدهی، حساب را موقتا (مثلا ۳۰ ثانیه) مسدود می‌کند. یادت باشد کلیک روی کلید داشبورد هم یک داده حساب می‌شود.

  1. ثبت‌نام. در io.adafruit.com حساب رایگان بساز.
  2. سه Feed بساز. از منوی Feeds › New Feed سه Feed به اسم‌های temperature، humidity و led بساز. key هر کدام را در صفحه Feed چک کن (باید همان حروف کوچک باشد).
  3. داشبورد بساز. Dashboards › New Dashboard، اسمش را «اتاق من» بگذار و بازش کن. از آیکون چرخ‌دنده Create New Block را بزن.
  4. دو بلوک Gauge (گیج). اولی را به Feed temperature وصل کن (حداقل ۰، حداکثر ۵۰) و دومی را به Feed humidity (حداقل ۰، حداکثر ۱۰۰).
  5. بلوک Toggle (کلید). آن را به Feed led وصل کن. متن حالت روشن را ON و خاموش را OFF بگذار (معمولا پیش‌فرض همین است). این دقیقا همان متنی است که کد ما انتظار دارد.
  6. کلید AIO را بردار. روی آیکون کلید زرد (My Key یا «YOUR AIO KEY») بزن. Username و Active Key را کپی کن. این کلید مثل رمز است؛ به کسی نده.
#include <WiFi.h>
#include <PubSubClient.h>
#include <DHT.h>
#include "secrets.h"      // WIFI_SSID، WIFI_PASS، AIO_USER، AIO_KEY
#ifndef AIO_USER          // secrets.h قدیمی درس ۴.۱؟ هشدار بده
#warning "AIO_USER/AIO_KEY are not defined in secrets.h"
#define AIO_USER "your_username"
#define AIO_KEY  "aio_xxxxxxxxxxxxxxxxxxxxxxxxxxxx"
#endif

const char* MQTT_HOST = "io.adafruit.com";
const int   MQTT_PORT = 1883;

// قالب Topic در Adafruit IO: username/feeds/feed-key
const char* TOPIC_TEMP     = AIO_USER "/feeds/temperature";
const char* TOPIC_HUM      = AIO_USER "/feeds/humidity";
const char* TOPIC_LED      = AIO_USER "/feeds/led";
const char* TOPIC_LED_GET  = AIO_USER "/feeds/led/get";
const char* TOPIC_THROTTLE = AIO_USER "/throttle";
const char* TOPIC_ERRORS   = AIO_USER "/errors";

const int LED_PIN = 4;
DHT dht(13, DHT22);
WiFiClient net;
PubSubClient mqtt(net);
unsigned long lastPublish = 0, lastTry = 0;

void onMessage(char* topic, byte* payload, unsigned int length) {
  char msg[128];
  unsigned int n = (length < sizeof(msg) - 1) ? length : sizeof(msg) - 1;
  memcpy(msg, payload, n);
  msg[n] = '\0';
  Serial.printf("<- [%s] %s\n", topic, msg);
  if (strcmp(topic, TOPIC_LED) == 0) {
    digitalWrite(LED_PIN, strcmp(msg, "ON") == 0 ? HIGH : LOW);
  }
}

bool connectMqtt() {
  char id[24];
  snprintf(id, sizeof(id), "esp32-%04X", (unsigned)(esp_random() & 0xFFFF));
  if (!mqtt.connect(id, AIO_USER, AIO_KEY)) {
    Serial.printf("MQTT failed, state=%d\n", mqtt.state());
    return false;
  }
  Serial.println("Adafruit IO connected");
  mqtt.subscribe(TOPIC_LED);
  mqtt.subscribe(TOPIC_THROTTLE);
  mqtt.subscribe(TOPIC_ERRORS);
  mqtt.publish(TOPIC_LED_GET, "");   // «آخرین مقدار led را برایم بفرست»
  return true;
}

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  dht.begin();
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) delay(500);
  mqtt.setServer(MQTT_HOST, MQTT_PORT);
  mqtt.setCallback(onMessage);
}

void loop() {
  if (!mqtt.connected()) {
    if (lastTry == 0 || millis() - lastTry > 10000) {
      lastTry = millis();
      connectMqtt();
    }
    return;
  }
  mqtt.loop();
  if (millis() - lastPublish >= 10000) {       // ۲ Feed × ۶ = ۱۲ داده در دقیقه
    lastPublish = millis();
    float t = dht.readTemperature();
    float h = dht.readHumidity();
    if (!isnan(t) && !isnan(h)) {
      char buf[16];
      snprintf(buf, sizeof(buf), "%.1f", t);   // فقط عدد، نه JSON
      mqtt.publish(TOPIC_TEMP, buf);
      Serial.printf("-> temperature = %s\n", buf);
      snprintf(buf, sizeof(buf), "%.1f", h);
      mqtt.publish(TOPIC_HUM, buf);
      Serial.printf("-> humidity = %s\n", buf);
    }
  }
}
  1. نام کاربری، AIO Key و Wi-Fi از secrets.h می‌آیند. همان فایل بخش ب؛ AIO_USER و AIO_KEY دقیقا همان‌هایی هستند که از صفحه My Key کپی کردی. نام کاربری به حروف بزرگ و کوچک حساس است. محافظ #ifndef هم دقیقا مثل بخش ب کار می‌کند. در Adafruit IO نام کاربری دو نقش دارد: هم برای ورود به Broker، هم اول هر Topic. اگر در secrets.h اشتباه باشد، یا وصل نمی‌شوی (خطای 5) یا انتشارت رد می‌شود.
  2. Broker مخصوص Adafruit. io.adafruit.com پورت 1883. روی 1883 کلید AIO تو بدون رمزنگاری فرستاده می‌شود. Adafruit خودش اتصال امن روی پورت 8883 را قویا توصیه می‌کند؛ برای آن دقیقا مثل بخش ب از WiFiClientSecure استفاده کن (برای شروع با setInsecure()، و برای کار جدی با گواهی ریشه‌ای که در مثال‌های رسمی کتابخانه Adafruit MQTT هست).
  3. Topic سه Feed. AIO_USER "/feeds/temperature" در زمان کامپایل به "your_username/feeds/temperature" تبدیل می‌شود؛ humidity و led هم همین‌طور. Adafruit IO فقط Topicهایی با قالب username/feeds/key را قبول می‌کند؛ هر چیز دیگری با پیام «not a valid resource topic» روی Topic خطاها رد می‌شود. برای همین key فیدهایی که در مرحله ۲ ساختی باید حرف به حرف با همین اسم‌ها یکی باشد.
  4. Topic ویژه /get. اگر روی .../led/get یک پیام (حتی خالی) منتشر کنی، Adafruit IO آخرین مقدار Feed led را فقط برای تو می‌فرستد. Adafruit IO از پرچم retain پشتیبانی نمی‌کند. بدون این ترفند، اگر ESP32 ریست شود، تا وقتی کسی دوباره روی کلید نزند نمی‌داند LED باید روشن باشد یا خاموش.
  5. Topicهای throttle و errors. Adafruit IO هشدار سرعت زیاد و خطاهای تو (مثلا Topic اشتباه) را روی این دو Topic می‌فرستد. پیام‌های خطا ذخیره نمی‌شوند؛ اگر لحظه‌ای که رخ می‌دهند مشترک نباشی، هرگز نمی‌فهمی چرا داده‌ات روی داشبورد نیامد.
  6. Callback کوتاه‌تر. مثل قبل payload را با '\0' به رشته تبدیل می‌کنیم (این بار بافر ۱۲۸ بایت چون پیام‌های خطا بلندترند). اگر پیام از Feed led بود، ON یعنی روشن و هر چیز دیگر خاموش. عملگر سه‌تایی شرط ? HIGH : LOW یک if و else کوتاه در یک خط است. پیام‌های throttle و errors فقط چاپ می‌شوند.
  7. اتصال با نام کاربری و کلید. Client ID تصادفی می‌سازیم و با connect(id, user, key) وصل می‌شویم. در Adafruit IO هویت تو با نام کاربری و کلید مشخص می‌شود و Client ID فقط باید بین دستگاه‌های خودت تکراری نباشد. عدد تصادفی esp_random() احتمال تکرار را خیلی کم می‌کند.
  8. اشتراک در سه Topic و درخواست آخرین مقدار. بعد از Subscribe روی Feed led، پیام خالی به /get می‌فرستیم تا وضعیت فعلی کلید برسد. ترتیب مهم است: اول Subscribe، بعد get. اگر برعکس باشد، جواب قبل از اشتراک می‌رسد و گم می‌شود.
  9. اتصال Wi-Fi فشرده. همان کار connectWiFi() در برنامه اول، در دو خط، با اسم و رمز از secrets.h. برای کوتاه ماندن این مثال؛ در پروژه واقعی همان نسخه کامل با چاپ پیشرفت را بگذار.
  10. اتصال دوباره هر ۱۰ ثانیه. همان الگوی Non-blocking، این بار با فاصله ۱۰ ثانیه. Adafruit IO به تلاش‌های اتصال خیلی سریع هم حساس است و ممکن است موقتا مسدودت کند. فاصله بیشتر بین تلاش‌ها، مودبانه‌تر است.
  11. انتشار دما و رطوبت به صورت عدد خالی. اول هر دو مقدار خوانده می‌شوند؛ فقط اگر هر دو معتبر بودند، snprintf("%.1f") هر کدام را با یک رقم اعشار به متن تبدیل می‌کند (مثلا 24.5) و روی Feed خودش منتشر می‌کند. همان buf برای عدد دوم دوباره استفاده می‌شود. بلوک گیج و نمودار Adafruit IO یک عدد ساده می‌خواهند. اگر JSON بفرستی، Feed آن را به عنوان متن ذخیره می‌کند و گیج چیزی نشان نمی‌دهد. دو Feed هر ۱۰ ثانیه = ۱۲ داده در دقیقه، همان حساب کادر «حساب کن»، خیلی زیر سهمیه ۳۰ تایی.

برنامه را آپلود کن، داشبورد را روی گوشی باز کن و کلید را بزن. LED باید در کمتر از یک ثانیه واکنش نشان دهد و هر دو گیج هر ۱۰ ثانیه به‌روز شوند. 🎉

جایگزین مستقل: Broker شخصی با Mosquitto

اگر سرویس ابری از دسترس خارج شد، شبکه‌ات پورت MQTT را می‌بندد، یا نمی‌خواهی داده‌های خانه‌ات از خانه بیرون برود، می‌توانی Broker را خودت اجرا کنی. Mosquitto یک Broker رایگان و متن‌باز از بنیاد Eclipse است که روی یک کامپیوتر معمولی یا حتی Raspberry Pi راحت اجرا می‌شود. آن وقت ESP32 و گوشی تو (وقتی به Wi-Fi خانه وصل است) بدون اینترنت هم با هم کار می‌کنند.

sudo apt update
sudo apt install -y mosquitto mosquitto-clients
echo "listener 1883
allow_anonymous true" | sudo tee /etc/mosquitto/conf.d/lan.conf
sudo systemctl restart mosquitto
mosquitto_sub -h localhost -t "esp32course/#" -v
  1. نصب. بسته mosquitto خود Broker است و mosquitto-clients دو ابزار خط فرمان mosquitto_pub و mosquitto_sub برای تست. روی ویندوز هم نصب‌کننده رسمی در سایت mosquitto.org هست؛ منطق تنظیم همین است.
  2. اجازه اتصال از شبکه. یک فایل تنظیم می‌سازیم که روی پورت 1883 برای همه کارت‌های شبکه گوش بدهد و اتصال بدون رمز را قبول کند. Mosquitto از نسخه ۲ به بعد به طور پیش‌فرض فقط اتصال از خود همان کامپیوتر (localhost) را قبول می‌کند. بدون این دو خط، ESP32 خطای -2 می‌گیرد. allow_anonymous true فقط برای شبکه خانگی مورد اعتماد مناسب است؛ برای کار جدی با mosquitto_passwd کاربر و رمز بساز.
  3. راه‌اندازی دوباره و تست. mosquitto_sub روی همه Topicهای زیر esp32course مشترک می‌شود و با -v اسم Topic را هم چاپ می‌کند. در کد ESP32 فقط MQTT_HOST را به IP این کامپیوتر (مثلا "192.168.1.50") عوض کن. IP را با دستور hostname -I ببین. اگر دیوار آتش (Firewall) روشن است، پورت 1883 را باز کن.

روی ویندوز

  1. نصب. از mosquitto.org/download نصب‌کننده 64-bit ویندوز را بگیر و با تنظیمات پیش‌فرض نصب کن (در C:\Program Files\mosquitto).
  2. فایل تنظیم. Notepad را با Run as administrator باز کن، فایل C:\Program Files\mosquitto\mosquitto.conf را باز کن و در آخرش دو خط listener 1883 و allow_anonymous true را بنویس و ذخیره کن.
  3. اجرا. یک Command Prompt با Run as administrator باز کن و بنویس: cd "C:\Program Files\mosquitto" و بعد mosquitto -v -c mosquitto.conf. این پنجره را باز نگه دار؛ هر اتصال ESP32 را در آن می‌بینی (اگر خطای «Only one usage of each socket address» داد، سرویس Mosquitto قبلا در پس‌زمینه اجرا شده؛ از services.msc آن را Stop کن یا بعد از تغییر فایل Restart کن).
  4. Firewall. اولین بار ویندوز می‌پرسد «اجازه دسترسی شبکه بدهم؟»؛ تیک Private networks را بزن و Allow کن. اگر نپرسید و ESP32 خطای -2 گرفت، در Windows Defender Firewall یک قانون ورودی (Inbound Rule) برای پورت TCP 1883 بساز.
  5. IP کامپیوتر. در Command Prompt بنویس ipconfig و عدد IPv4 Address کارت Wi-Fi را (مثلا 192.168.1.50) در MQTT_HOST بگذار. برای تست، MQTTX را روی همان IP وصل کن.
Wokwi به Broker محلی تو نمی‌رسد

ESP32 شبیه‌سازی‌شده در Wokwi در اینترنت است، نه داخل شبکه خانه تو؛ پس به IP مثل 192.168.1.50 دسترسی ندارد. Broker محلی را فقط با برد واقعی تست کن.

ویدیوی کمکی

  • این ویدیو از مجموعه رسمی «MQTT Essentials» شرکت HiveMQ است؛ همان شرکتی که Broker عمومی این درس را اداره می‌کند.
  • دنبال سه نقش Publisher، Subscriber و Broker بگرد و آن‌ها را با مثال کانال تلگرام همین درس مقایسه کن.
  • دقت کن چرا می‌گوید فرستنده و گیرنده «از هم جدا» (decoupled) هستند؛ این در فضا، زمان یا هر دو یعنی چه؟
  • بعد از این ویدیو، بقیه قسمت‌های همان مجموعه (QoS، Retained، Last Will) را هم در کانال HiveMQ ببین.

پیام‌ها روی داشبورد نمی‌آید، هیچ خطایی هم نیستTopic فرستنده و گیرنده یک حرف فرق دارددر ابزار تست روی پیشوند/# مشترک شو و ببین پیام دقیقا کجا می‌رود
ESP32 بعد از ریست فرمان قدیمی را دوباره اجرا می‌کندفرمان با retain منتشر شدهفرمان‌ها را بدون retain بفرست؛ برای پاک کردن پیام ماندگار، یک پیام خالی با retain روی همان Topic بفرست
هشدار «data rate limit reached» در Adafruit IOبیش از ۳۰ داده در دقیقهفاصله انتشار را زیاد کن؛ فقط وقتی مقدار عوض شد بفرست
روی برد واقعی -2، در Wokwi سالممسیر اینترنت تو به آن سرویس بسته یا کند استبا Broker دیگر یا Mosquitto محلی امتحان کن تا مشکل کد از مشکل شبکه جدا شود
حرف مربی

در MQTT، سه بخش جدا داری: دستگاه، Broker و گیرنده. وقتی چیزی کار نمی‌کند، مثل یک کارآگاه یکی‌یکی حذفشان کن. اول با MQTTX یا صفحه HiveMQ روی پیشوند/# مشترک شو و فقط نگاه کن: آیا پیام ESP32 به Broker می‌رسد؟ اگر نه، مشکل در دستگاه است (عدد state را بخوان). اگر بله، از همان ابزار یک فرمان بفرست: آیا ESP32 آن را در Serial چاپ می‌کند؟ هرگز هم‌زمان کد ESP32 و داشبورد را عوض نکن؛ دو متغیر هم‌زمان یعنی هیچ‌وقت نمی‌فهمی کدام درستش کرد. و یک قانون آهنین: در loop هیچ delay بلندی نگذار. نود درصد قطع و وصل‌های عجیبی که دانشجوها برایم می‌فرستند، همین است.

آزمون این درس

در MQTT، ESP32 و گوشی چطور با هم ارتباط برقرار می‌کنند؟

  1. گوشی مستقیم به IP دستگاه ESP32 وصل می‌شود
  2. هر دو به یک Broker وصل می‌شوند و Broker پیام‌ها را بر اساس Topic جابه‌جا می‌کند
  3. ESP32 نقش Broker را دارد و گوشی به آن وصل می‌شود
  4. از طریق بلوتوث
Broker مثل تلگرام است: فرستنده و گیرنده فقط او را می‌شناسند، نه همدیگر را. برای همین از بیرون خانه هم کار می‌کند.

اشتراک در home/+/temp کدام پیام را نمی‌گیرد؟

  1. home/kitchen/temp
  2. home/bedroom2/temp
  3. home/floor1/kitchen/temp
  4. home/livingroom/temp
+ دقیقا یک سطح را جایگزین می‌کند. floor1/kitchen دو سطح است. برای گرفتن آن باید home/# یا home/+/+/temp بنویسی.

پیام «در را باز کن» را با retain فرستاده‌ای. چه خطری دارد؟

  1. هر بار دستگاه ریست شود و دوباره Subscribe کند، فرمان قدیمی را می‌گیرد و در دوباره باز می‌شود
  2. پیام رمزنگاری نمی‌شود
  3. پیام هرگز تحویل داده نمی‌شود
  4. حافظه Broker پر می‌شود
retain برای «وضعیت» است (online، دمای آخر)، نه برای «فرمان». فرمان ماندگار یعنی فرمانی که بارها اجرا می‌شود.

در Callback نوشته‌ای if (strcmp((char*)payload, "ON") == 0) و گاهی کار می‌کند، گاهی نه. چرا؟

  1. strcmp برای مقایسه متن مناسب نیست
  2. چون ON باید با حروف کوچک باشد
  3. چون QoS صفر است
  4. چون payload با بایت صفر تمام نمی‌شود و strcmp از آخر پیام جلوتر می‌رود
payload آرایه بایت با طول مشخص است، نه رشته C. همیشه آن را با طول length در یک بافر کپی کن و '\0' بگذار.

ESP32 تو هر حدود ۲۰ ثانیه از Broker قطع می‌شود و state() عدد -3 می‌دهد. در loop یک delay(30000) داری. ارتباط این دو چیست؟

  1. بافر ۲۵۶ بایتی پر شده
  2. در این ۳۰ ثانیه mqtt.loop() اجرا نمی‌شود، PING فرستاده نمی‌شود و Broker بعد از حدود ۱٫۵ برابر Keep-alive (۱۵ ثانیه) اتصال را مرده حساب می‌کند
  3. delay باعث قطع شدن Wi-Fi می‌شود
  4. رمز اشتباه است
زمان‌بندی را با millis() بنویس تا mqtt.loop() مدام اجرا شود.

چرا setInsecure() برای دستگاهی که همیشه در خانه کار می‌کند توصیه نمی‌شود؟

  1. چون پیام‌ها رمزنگاری نمی‌شوند
  2. چون اتصال را خیلی کند می‌کند
  3. چون هویت سرور بررسی نمی‌شود و یک سرور جعلی می‌تواند خودش را جای Broker جا بزند و رمز تو را بگیرد
  4. چون با HiveMQ Cloud کار نمی‌کند
رمزنگاری بدون احراز هویت مثل پاکت دربسته‌ای است که به هر کس گفت «من پستچی‌ام» تحویل می‌دهی. با setCACert کارت شناسایی را چک می‌کنی.

تمرین ۱: فقط وقتی عوض شد بفرست

برنامه بخش الف را طوری تغییر بده که دما را هر ۲ ثانیه بخواند، ولی فقط وقتی منتشر کند که حداقل ۰٫۳ درجه با آخرین مقدار منتشرشده فرق داشته باشد، یا ۶۰ ثانیه از آخرین انتشار گذشته باشد (تا داشبورد بداند دستگاه زنده است).

راهنمایی

یک متغیر سراسری float lastSent = -100; نگه دار. شرط انتشار: fabs(t - lastSent) >= 0.3 || millis() - lastPublish >= 60000. بعد از انتشار lastSent = t.

چه باید ببینی؟

با مدار Wokwi بخش الف (DHT22 روی همان ۲۴٫۵ درجه)، در Serial Monitor چیزی شبیه این می‌بینی. IP، Client ID و عددهای uptime تو فرق دارند:

WiFi..... connected, IP: 10.10.0.2
MQTT: connecting as esp32-240AC4000110-3A9C ... OK
(change) -> {"temp":24.5,"hum":40.0,"uptime":6}
(heartbeat) -> {"temp":24.5,"hum":40.0,"uptime":66}
(change) -> {"temp":27.0,"hum":40.0,"uptime":81}
(heartbeat) -> {"temp":27.0,"hum":40.0,"uptime":141}
  • اولین پیام بلافاصله بعد از OK می‌آید و (change) دارد، چون lastSent از ‎-100 شروع می‌شود.
  • اگر به سنسور دست نزنی، تقریبا هر ۶۰ ثانیه یک خط (heartbeat) می‌آید (uptime به اندازه ۶۰ یا ۶۱ بالا می‌رود)، نه هر ۲ یا ۱۰ ثانیه.
  • روی DHT22 کلیک کن و دما را ۰٫۵ درجه یا بیشتر جابه‌جا کن: در کمتر از ۲ ثانیه یک خط (change) می‌آید. اگر فقط ۰٫۱ یا ۰٫۲ درجه جابه‌جا کنی، چیزی منتشر نمی‌شود.
  • در MQTTX پیام‌های esp32course/ali1234/sensor/climate دقیقا همان لحظه‌هایی می‌رسند که خط‌های Serial چاپ می‌شوند.
جواب کامل با توضیح

این برنامه کامل بخش الف است؛ فقط دو متغیر سراسری تازه اضافه شده و انتهای loop() عوض شده است.

#include <WiFi.h>
#include <PubSubClient.h>
#include <ArduinoJson.h>
#include <DHT.h>

// ---- Wi-Fi (در Wokwi همین را نگه دار) ----
const char* WIFI_SSID = "Wokwi-GUEST";
const char* WIFI_PASS = "";

// ---- بروکر عمومی HiveMQ ----
const char* MQTT_HOST = "broker.hivemq.com";
const int   MQTT_PORT = 1883;

// پیشوند یکتا: ali1234 را با اسم و عدد دلخواه خودت عوض کن
#define BASE "esp32course/ali1234"
const char* TOPIC_CLIMATE = BASE "/sensor/climate";
const char* TOPIC_CMD     = BASE "/led/set";
const char* TOPIC_STATUS  = BASE "/status";

const int LED_PIN = 4;
const int DHT_PIN = 13;

DHT dht(DHT_PIN, DHT22);
WiFiClient net;              // لوله TCP خام
PubSubClient mqtt(net);      // MQTT روی همان لوله

char clientId[40];
unsigned long lastPublish = 0;
unsigned long lastTry = 0;
float lastSent = -100;       // آخرین دمای منتشرشده (-100 یعنی هنوز هیچ)
unsigned long lastRead = 0;  // آخرین بار که سنسور را خواندیم

// هر پیامی روی Topicهای مشترک‌شده برسد، این تابع صدا زده می‌شود
void onMessage(char* topic, byte* payload, unsigned int length) {
  char msg[32];
  unsigned int n = (length < sizeof(msg) - 1) ? length : sizeof(msg) - 1;
  memcpy(msg, payload, n);
  msg[n] = '\0';             // payload خودش '\0' ندارد!
  Serial.printf("<- [%s] %s\n", topic, msg);

  if (strcmp(topic, TOPIC_CMD) == 0) {
    if (strcmp(msg, "ON") == 0) {
      digitalWrite(LED_PIN, HIGH);
    } else if (strcmp(msg, "OFF") == 0) {
      digitalWrite(LED_PIN, LOW);
    } else {
      Serial.println("Unknown command (use ON or OFF)");
    }
  }
}

void connectWiFi() {
  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  Serial.print("WiFi");
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  Serial.print(" connected, IP: ");
  Serial.println(WiFi.localIP());
}

bool connectMqtt() {
  Serial.printf("MQTT: connecting as %s ... ", clientId);
  // وصیت‌نامه: اگر بی‌خبر قطع شدیم، Broker روی status بنویسد offline
  if (mqtt.connect(clientId, TOPIC_STATUS, 1, true, "offline")) {
    Serial.println("OK");
    mqtt.publish(TOPIC_STATUS, "online", true);   // true یعنی retained
    mqtt.subscribe(TOPIC_CMD, 1);
    return true;
  }
  Serial.printf("failed, state=%d\n", mqtt.state());
  return false;
}

void publishClimate() {
  float t = dht.readTemperature();
  float h = dht.readHumidity();
  if (isnan(t) || isnan(h)) {
    Serial.println("DHT22 read failed");
    return;
  }
  JsonDocument doc;
  doc["temp"] = serialized(String(t, 1));   // 24.3 با یک رقم اعشار
  doc["hum"] = serialized(String(h, 1));
  doc["uptime"] = millis() / 1000;
  char buf[128];
  serializeJson(doc, buf, sizeof(buf));
  bool ok = mqtt.publish(TOPIC_CLIMATE, buf);
  Serial.printf("-> %s %s\n", buf, ok ? "" : "(publish FAILED)");
}

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  dht.begin();
  connectWiFi();
  // Client ID یکتا: MAC برد + یک عدد تصادفی
  String mac = WiFi.macAddress();   // مثل 24:6F:28:AB:CD:EF
  mac.replace(":", "");
  snprintf(clientId, sizeof(clientId), "esp32-%s-%04X", mac.c_str(), (unsigned)(esp_random() & 0xFFFF));
  mqtt.setServer(MQTT_HOST, MQTT_PORT);
  mqtt.setCallback(onMessage);
}

void loop() {
  if (WiFi.status() != WL_CONNECTED) {
    return;                  // Wi-Fi خودش دوباره وصل می‌شود (درس ۴.۱)
  }
  if (!mqtt.connected()) {
    if (lastTry == 0 || millis() - lastTry > 5000) {   // هر ۵ ثانیه یک تلاش
      lastTry = millis();
      connectMqtt();
    }
    return;                  // تا وصل نشده‌ایم، کار دیگری نکن
  }
  mqtt.loop();               // خواندن پیام‌های ورودی + فرستادن PING

  if (millis() - lastRead >= 2000) {             // هر ۲ ثانیه بخوان
    lastRead = millis();
    float t = dht.readTemperature();
    if (isnan(t)) return;                        // خواندن ناموفق: ۲ ثانیه بعد دوباره
    bool changed = fabs(t - lastSent) >= 0.3;          // حداقل ۰٫۳ درجه عوض شده؟
    bool heartbeat = millis() - lastPublish >= 60000;  // ۶۰ ثانیه بی‌انتشار گذشته؟
    if (changed || heartbeat) {
      Serial.print(changed ? "(change) " : "(heartbeat) ");
      lastPublish = millis();
      lastSent = t;
      publishClimate();
    }
  }
}
  1. مثل بخش الف. کتابخانه‌ها، Wi-Fi، Broker، Topicها، پایه‌ها و شیءها دست نخورده‌اند. این تمرین فقط زمان انتشار را عوض می‌کند، نه محتوا یا مقصد آن را؛ پس بقیه چیزها همان می‌ماند.
  2. دو حافظه تازه. lastSent آخرین دمای منتشرشده را نگه می‌دارد و lastRead زمان آخرین خواندن سنسور را. برای تصمیم «به اندازه کافی عوض شده؟» به مقدار قبلی نیاز داریم. شروع از ‎-100 (دمایی که هیچ اتاقی ندارد) تضمین می‌کند اولین خواندن حتما «تغییر» حساب شود و فورا منتشر شود.
  3. تابع‌ها، setup()‎ و ابتدای loop()‎ بدون تغییر. publishClimate() هنوز خودش سنسور را می‌خواند و JSON را می‌سازد. سنسور دو بار خوانده می‌شود، ولی کتابخانه DHT اگر در کمتر از ۲ ثانیه دوباره بپرسی همان مقدار ذخیره‌شده را برمی‌گرداند؛ پس عدد منتشرشده همان عددی است که مقایسه کردیم.
  4. هر ۲ ثانیه یک خواندن. زمان‌بندی با millis()، مثل انتشار ۱۰ ثانیه‌ای بخش الف؛ اگر خواندن خراب شد، فقط تا دور بعد صبر می‌کنیم. DHT22 زودتر از هر ۲ ثانیه عدد تازه نمی‌دهد. با millis() به جای delay()، mqtt.loop() مدام اجرا می‌شود و فرمان‌های LED همچنان فوری می‌رسند.
  5. دو دلیل برای انتشار. changed وقتی true است که اختلاف (بدون علامت، به کمک fabs) حداقل ۰٫۳ باشد؛ heartbeat وقتی true است که ۶۰ ثانیه از آخرین انتشار گذشته باشد. fabs بالا رفتن و پایین آمدن را یکسان می‌گیرد. بدون heartbeat، اتاقی با دمای ثابت ساعت‌ها ساکت می‌ماند و داشبورد نمی‌تواند «چیزی عوض نشده» را از «دستگاه خاموش شده» تشخیص دهد.
  6. انتشار، به خاطر سپردن و گفتن دلیل. دلیل را چاپ می‌کنیم، زمان و مقدار را نگه می‌داریم و publishClimate() را صدا می‌زنیم. lastSent فقط وقتی باید عوض شود که واقعا منتشر کرده‌ایم؛ وگرنه یک تغییر آرام ۰٫۱ درجه‌ای در هر خواندن هیچ‌وقت به ۰٫۳ نمی‌رسید و گزارش نمی‌شد. دلیل چاپ‌شده کمک می‌کند منطق را در Serial Monitor وارسی کنی.

در Wokwi با مدار بخش الف امتحانش کن (همان کتابخانه‌ها: PubSubClient، ArduinoJson و DHT sensor library). روی DHT22 کلیک کن و با اسلایدر دما هر دو قانون را آزمایش کن.

تمرین ۲: گزارش وضعیت LED

بعد از هر فرمان، ESP32 وضعیت واقعی LED را روی Topic .../led/state با retain منتشر کند (ON یا OFF). چرا این Topic باید با .../led/set فرق داشته باشد؟

راهنمایی

داخل onMessage بعد از digitalWrite، mqtt.publish(TOPIC_STATE, msg, true) را صدا بزن. فکر کن اگر state و set یکی بود و ESP32 هم در آن مشترک بود، بعد از انتشار چه اتفاقی می‌افتاد.

چه باید ببینی؟

در MQTTX روی esp32course/ali1234/led/# (با پیشوند خودت) مشترک شو و به .../led/set به ترتیب ON، OFF و BLINK بفرست. در Serial Monitor این را می‌بینی (Client ID تو فرق دارد؛ خط‌های دمای هر ۱۰ ثانیه اینجا حذف شده‌اند):

MQTT: connecting as esp32-240AC4000110-3A9C ... OK
-> [esp32course/ali1234/led/state] OFF
<- [esp32course/ali1234/led/set] ON
-> [esp32course/ali1234/led/state] ON
<- [esp32course/ali1234/led/set] OFF
-> [esp32course/ali1234/led/state] OFF
<- [esp32course/ali1234/led/set] BLINK
Unknown command (use ON or OFF)
-> [esp32course/ali1234/led/state] OFF
  • بعد از هر خط <- دقیقا یک خط وضعیت -> می‌آید و LED روی GPIO4 با آن می‌خواند.
  • فرمان ناشناخته هم یک پیام وضعیت می‌سازد، با همان وضعیت قبلی.
  • MQTTX را قطع و دوباره وصل کن: آخرین وضعیت فورا با برچسب retained ظاهر می‌شود، با اینکه ESP32 چیز تازه‌ای نفرستاده.
  • ESP32 هیچ‌وقت پیام وضعیت خودش را دریافت نمی‌کند (هیچ خط <- [.../led/state] نمی‌بینی).
جواب کامل با توضیح

چرا دو Topic: اگر state و set یک Topic بودند، ESP32 (که در آن مشترک است) پیام خودش را دوباره دریافت می‌کرد، دوباره اجرا و دوباره منتشر می‌کرد: یک حلقه بی‌پایان. مشکل دوم هم هست: وضعیت retain دارد، پس یک «ON» ماندگار روی Topic فرمان، بعد از هر اتصال دوباره LED را روشن می‌کرد، حتی اگر کسی در این فاصله خاموشش کرده بود. جدا کردن «فرمان» (set، بدون retain) از «وضعیت» (state، با retain) الگوی استاندارد سیستم‌هایی مثل Home Assistant است.

// هر پیامی روی Topicهای مشترک‌شده برسد، این تابع صدا زده می‌شود
void onMessage(char* topic, byte* payload, unsigned int length) {
  char msg[32];
  unsigned int n = (length < sizeof(msg) - 1) ? length : sizeof(msg) - 1;
  memcpy(msg, payload, n);
  msg[n] = '\0';             // payload خودش '\0' ندارد!
  Serial.printf("<- [%s] %s\n", topic, msg);

  if (strcmp(topic, TOPIC_CMD) == 0) {
    if (strcmp(msg, "ON") == 0) {
      digitalWrite(LED_PIN, HIGH);
    } else if (strcmp(msg, "OFF") == 0) {
      digitalWrite(LED_PIN, LOW);
    } else {
      Serial.println("Unknown command (use ON or OFF)");
    }
    publishLedState();       // ★ بعد از هر فرمان: بگو LED واقعا چه وضعی دارد
  }
}

bool connectMqtt() {
  Serial.printf("MQTT: connecting as %s ... ", clientId);
  // وصیت‌نامه: اگر بی‌خبر قطع شدیم، Broker روی status بنویسد offline
  if (mqtt.connect(clientId, TOPIC_STATUS, 1, true, "offline")) {
    Serial.println("OK");
    mqtt.publish(TOPIC_STATUS, "online", true);   // true یعنی retained
    mqtt.subscribe(TOPIC_CMD, 1);
    publishLedState();       // ★ بلافاصله بعد از هر اتصال (دوباره) هم
    return true;
  }
  Serial.printf("failed, state=%d\n", mqtt.state());
  return false;
}

void publishClimate() {
  float t = dht.readTemperature();
  float h = dht.readHumidity();
  if (isnan(t) || isnan(h)) {
    Serial.println("DHT22 read failed");
    return;
  }
  JsonDocument doc;
  doc["temp"] = serialized(String(t, 1));   // 24.3 با یک رقم اعشار
  doc["hum"] = serialized(String(h, 1));

  serializeJson(doc, buf, sizeof(buf));
  bool ok = mqtt.publish(TOPIC_CLIMATE, buf);
  Serial.printf("-> %s %s\n", buf, ok ? "" : "(publish FAILED)");
}

void loop() {

    return;                  // Wi-Fi خودش دوباره وصل می‌شود (درس ۴.۱)
  }
  if (!mqtt.connected()) {
    if (lastTry == 0 || millis() - lastTry > 5000) {   // هر ۵ ثانیه یک تلاش
      lastTry = millis();
      connectMqtt();
    }
    return;                  // تا وصل نشده‌ایم، کار دیگری نکن
  }
  mqtt.loop();               // خواندن پیام‌های ورودی + فرستادن PING

    lastPublish = millis();
    publishClimate();
  }
}

  2. publishLedState()‎. پایه را با digitalRead دوباره می‌خواند، ON یا OFF را با retain = true منتشر می‌کند و آنچه فرستاده را چاپ می‌کند. خواندن پایه گزارش می‌دهد LED واقعا چه می‌کند، نه آنچه فکر می‌کنیم به آن گفته‌ایم. در ESP32 می‌شود پایه‌ای را که OUTPUT است دوباره خواند. retain باعث می‌شود Broker آخرین وضعیت را برای هر کسی که بعدا مشترک شود نگه دارد، مثلا داشبوردی که یک ساعت بعد باز می‌شود.
  3. گزارش بعد از هر فرمان. این فراخوانی داخل بلوک TOPIC_CMD و بعد از if/else است، پس برای فرمان ناشناخته هم اجرا می‌شود. انتشار از داخل callback اینجا بی‌خطر است، چون اول payload را در msg کپی کرده‌ایم؛ PubSubClient برای پیام ورودی و خروجی از یک بافر داخلی مشترک استفاده می‌کند.
  4. گزارش بعد از هر اتصال (دوباره). بلافاصله بعد از Subscribe، وضعیت فعلی را یک بار منتشر می‌کنیم. بعد از ریست یا قطعی، وضعیت retained روی Broker ممکن است کهنه باشد. یک پیام در لحظه اتصال، حقیقت را سر جایش برمی‌گرداند.
  5. loop()‎ بدون تغییر. اتصال دوباره، mqtt.loop() و انتشار دما هر ۱۰ ثانیه دقیقا مثل بخش الف است. گزارش وضعیت رویدادمحور است (با فرمان یا اتصال)، پس تایمر جداگانه لازم ندارد.

پروژه تمرینی: چراغ خواب از راه دور با MQTT

یک چراغ خواب برای راهرو می‌سازی که از هر جای دنیا می‌توانی وضعیتش را ببینی و کنترلش کنی. خودش مثل چراغ خواب درس ۳.۱ وقتی راهرو تاریک شود روشن می‌شود. ولی هر ۳۰ ثانیه سطح نور را هم به اینترنت گزارش می‌دهد، و از گوشی‌ات می‌توانی آن را به زور روشن (ON) یا خاموش (OFF) کنی، یا با AUTO کنترل را دوباره به سنسور نور بدهی. هر کس بعدا داشبورد را باز کند، به لطف یک پیام ماندگار (Retained) فورا وضعیت فعلی چراغ را می‌بیند.

نیازمندی‌ها

  1. همه Topicها با پیشوند خودت شروع می‌شوند (esp32course/yourname/nightlight)، و .../status دقیقا مثل درس، online یا (با وصیت‌نامه) offline را نشان می‌دهد.
  2. برد هر ۳۰ ثانیه (و یک بار بلافاصله بعد از اتصال) سطح نور را به صورت یک عدد صحیح از 0 (تاریک) تا 100 (روشن) روی .../light/level منتشر می‌کند.
  3. برد به .../led/set گوش می‌دهد: ON چراغ را روشن می‌کند و روشن نگه می‌دارد، OFF خاموش می‌کند و خاموش نگه می‌دارد، AUTO کنترل را به سنسور نور برمی‌گرداند. هر چیز دیگر (حتی on با حروف کوچک) پیام Unknown command چاپ می‌کند و هیچ چیزی را عوض نمی‌کند.
  4. در حالت AUTO، LDR هر ۲۰۰ میلی‌ثانیه با هیسترزیس بررسی می‌شود: بالای ۲۶۰۰ میلی‌ولت (تاریک) LED روشن و زیر ۲۲۰۰ میلی‌ولت (روشن) خاموش می‌شود. این کار وقتی Wi-Fi یا Broker قطع است هم ادامه دارد.
  5. هر بار که حالت یا LED عوض شود، و بعد از هر اتصال (یا اتصال دوباره)، برد یک پیام JSON ماندگار روی .../led/state منتشر می‌کند؛ مثلا {"mode":"AUTO","led":"ON"}. اگر چیزی عوض نشده باشد، آن را تکرار نمی‌کند.
  6. loop() هیچ‌جا از delay() استفاده نمی‌کند؛ همه زمان‌بندی‌ها با millis() است.

قطعه‌ها

  • ESP32 DevKitC، برد بورد و سیم جامپر
  • LDR (مدل GL5528) + مقاومت ۱۰ کیلواهم؛ همان تقسیم‌کننده ولتاژ درس ۳.۱
  • LED + مقاومت ۲۲۰ اهم روی GPIO4
  • برای تست: HiveMQ WebSocket Client در مرورگر، یا MQTTX / MQTT Explorer (از همین درس). سنسور DHT22 درس می‌تواند روی برد بورد بماند؛ این پروژه از آن استفاده نمی‌کند.

// چراغ خواب از راه دور: سطح نور روی MQTT، فرمان‌های LED: ON / OFF / AUTO
#include <WiFi.h>
#include <PubSubClient.h>

// ---- Wi-Fi (در Wokwi همین را نگه دار؛ روی برد واقعی اسم مودم خودت) ----
const char* WIFI_SSID = "Wokwi-GUEST";
const char* WIFI_PASS = "";
const char* MQTT_HOST = "broker.hivemq.com";
const int   MQTT_PORT = 1883;

// ali1234 را با اسم و عدد خودت عوض کن
#define BASE "esp32course/ali1234/nightlight"
const char* TOPIC_LEVEL  = BASE "/light/level";   // ما منتشر می‌کنیم: 0 تا 100
const char* TOPIC_SET    = BASE "/led/set";       // ما گوش می‌دهیم: ON/OFF/AUTO
const char* TOPIC_STATE  = BASE "/led/state";     // ما منتشر می‌کنیم (ماندگار)
const char* TOPIC_STATUS = BASE "/status";        // online/offline (وصیت‌نامه)

const int LED_PIN = 4;
const int LDR_PIN = 35;                 // وسط تقسیم‌کننده LDR
const uint32_t DARK_ON_MV   = 2600;     // بالاتر از این: تاریک، LED روشن
const uint32_t LIGHT_OFF_MV = 2200;     // پایین‌تر از این: روشن، LED خاموش

WiFiClient net;
PubSubClient mqtt(net);
char clientId[40];

enum Mode { MODE_AUTO, MODE_ON, MODE_OFF };
Mode mode = MODE_AUTO;
bool ledOn = false;
bool stateDirty = true;                 // true یعنی وضعیت باید منتشر شود
unsigned long lastLevel = 0, lastCheck = 0, lastTry = 0;

uint32_t readLdrMv() {                  // میانگین ۸ بار خواندن
  uint32_t sum = 0;
  for (int i = 0; i < 8; i++) sum += analogReadMilliVolts(LDR_PIN);
  return sum / 8;
}

int lightPercent(uint32_t mv) {         // 0 یعنی تاریک، 100 یعنی روشن
  if (mv > 3300) mv = 3300;
  return 100 - (int)(mv * 100 / 3300);
}

void setLed(bool on) {
  if (on == ledOn) return;              // تغییری نیست: چیزی برای گزارش نیست
  ledOn = on;
  digitalWrite(LED_PIN, on ? HIGH : LOW);
  stateDirty = true;
}

const char* modeName() {
  if (mode == MODE_ON) return "ON";
  if (mode == MODE_OFF) return "OFF";
  return "AUTO";
}

void publishState() {
  char buf[48];
  snprintf(buf, sizeof(buf), "{\"mode\":\"%s\",\"led\":\"%s\"}",
           modeName(), ledOn ? "ON" : "OFF");
  if (mqtt.publish(TOPIC_STATE, buf, true)) {   // true یعنی ماندگار (retained)
    stateDirty = false;
    Serial.printf("-> state %s\n", buf);
  }
}

void onMessage(char* topic, byte* payload, unsigned int length) {
  char msg[16];
  unsigned int n = (length < sizeof(msg) - 1) ? length : sizeof(msg) - 1;
  memcpy(msg, payload, n);
  msg[n] = '\0';                        // payload خودش '\0' ندارد
  Serial.printf("<- [%s] %s\n", topic, msg);
  if (strcmp(topic, TOPIC_SET) != 0) return;
  if (strcmp(msg, "ON") == 0) {
    mode = MODE_ON;
    setLed(true);
  } else if (strcmp(msg, "OFF") == 0) {
    mode = MODE_OFF;
    setLed(false);
  } else if (strcmp(msg, "AUTO") == 0) {
    mode = MODE_AUTO;                   // از این به بعد LDR تصمیم می‌گیرد
  } else {
    Serial.println("Unknown command (use ON, OFF or AUTO)");
    return;
  }
  stateDirty = true;                    // حالت عوض شد، گزارشش کن
}

void connectWiFi() {
  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASS);

  while (WiFi.status() != WL_CONNECTED) {

    return true;
  }
  Serial.printf("failed, state=%d\n", mqtt.state());
  return false;
}

void loop() {
  // ۱) چراغ خواب حتی وقتی شبکه قطع است کار می‌کند
  if (mode == MODE_AUTO && millis() - lastCheck >= 200) {
    lastCheck = millis();
    uint32_t mv = readLdrMv();
    if (mv > DARK_ON_MV) setLed(true);
    else if (mv < LIGHT_OFF_MV) setLed(false);
  }

  // ۲) شبکه: اتصال دوباره بدون گیر انداختن برنامه، مثل درس
  if (WiFi.status() != WL_CONNECTED) return;
  if (!mqtt.connected()) {
    if (lastTry == 0 || millis() - lastTry > 5000) {
      lastTry = millis();
      connectMqtt();
    }
    return;
  }
  mqtt.loop();

  // ۳) سطح نور هر ۳۰ ثانیه (و بلافاصله بعد از اولین اتصال)
  if (lastLevel == 0 || millis() - lastLevel >= 30000) {
    lastLevel = millis();
    char buf[8];
    snprintf(buf, sizeof(buf), "%d", lightPercent(readLdrMv()));
    mqtt.publish(TOPIC_LEVEL, buf);
    Serial.printf("-> level %s %%\n", buf);
  }

  // ۴) هر تغییر حالت یا LED یک بار و ماندگار گزارش می‌شود
  if (stateDirty) publishState();
}

در MQTT همه Clientها فقط به Broker وصل‌اند و روی Topic (با Wildcardهای + و #) Publish و Subscribe می‌کنند؛ QoS، retain و Last Will برای اتصال‌های ناپایدار ساخته شده‌اند. در PubSubClient: payload را خودت با '\0' ببند، ID یکتا بساز، بعد از هر اتصال دوباره Subscribe کن و mqtt.loop() را بدون delay مدام اجرا کن. برای امنیت از TLS روی 8883 با setCACert استفاده کن، و Adafruit IO یا Mosquitto محلی دو راه سریع برای داشبورد و استقلال هستند.
