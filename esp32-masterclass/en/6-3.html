Step zero: requirements (a small PRD)

Before writing code, professionals write a short document that says exactly what the product must do. It's called a PRD (Product Requirements Document). Without one, a project keeps growing and is never "done", because you don't know what "done" means.

An everyday example: a building plan

No builder starts laying bricks without a plan. If halfway through the owner says "Oh, by the way, I want one more floor", the columns were never designed to carry it. The PRD is your project's plan: short, but clear.

IDRequirementAcceptance criterion (how do I know it's done?)
R1Measure temperature and humidityOnce every 2 seconds; a sensor error is shown as "ERR", never as a wrong number
R2Measure ambient lightLight as a percentage from 0 to 100; it drops when you cover the sensor
R3Local displayThe OLED shows temperature, humidity, light, Wi-Fi and MQTT status, and alarm status
R4Local alarmAbove 35 degrees: the LED blinks and the buzzer beeps; the button silences the buzzer
R5No flickering (hysteresis)The alarm only turns off once the temperature drops below 33 degrees
R6Send to the cloudEvery 30 seconds, temperature, humidity and light are sent over MQTT
R7Cloud alerts without spamOne message when the alarm starts, one when it ends, and at most one reminder every 10 minutes while it lasts
R8Survives network outagesIf Wi-Fi or the server drops, the display and local alarm keep running without a pause, and the connection comes back on its own
R9 (optional)Battery modeUsing deep sleep, measure and send once every few minutes
Why is R8 so important?

The internet goes down; that's a fact, not a possibility. A device whose local alarm also stops working when the internet drops will be silent at exactly the moment you need it. The design rule: local jobs never wait for the network.

Choosing the pins (with reasons)

OLED SDA / SCLGPIO21 / GPIO22The default I2C pins in the Arduino core; every library and tutorial assumes them

LDR (analog output AO)GPIO35It's on ADC1. ADC2 pins can't be used while Wi-Fi is on; since we use Wi-Fi, only ADC1 (GPIO32 to 39) is safe. GPIO35 is input-only, which is no problem for a sensor

These are the same pins the whole course has used for these parts (the LED on 4, the button on 27, the DHT22 on 13, the LDR on 35, the buzzer on 25, I2C on 21/22), so the station grows out of the breadboard you already have.

A classic trap: the LDR on ADC2

If you put the LDR on, say, GPIO14 or GPIO26 (which are ADC2 pins), it works perfectly without Wi-Fi; but the moment Wi-Fi turns on, analogRead stops giving correct numbers. It's one of those bugs you don't see in step 1 (no Wi-Fi) that suddenly shows up in step 4. That's why we choose correctly from the start.

How we build it: small steps, each one tested

The biggest beginner mistake: connect every part, write 200 lines of code, upload, and... nothing works. So where's the problem? The sensor? The display? Wi-Fi? The code? You have no idea. We'll take six steps, and we won't move on until the previous step works:

  1. Sensors → correct numbers in the Serial Monitor
  2. Display → the same numbers on the OLED
  3. Local alarm → LED and buzzer with hysteresis, no delay
  4. Wi-Fi → connect and reconnect without blocking
  5. MQTT → a test message in an MQTT client
  6. Integration and cloud alerts → the final program with millis scheduling

Step 1: the sensors

// Step 1: sensors only; output in the Serial Monitor
#include <DHT.h>

const int PIN_DHT = 13;
const int PIN_LDR = 35;                  // ADC1: works with Wi-Fi too
DHT dht(PIN_DHT, DHT22);

void setup() {
  Serial.begin(115200);
  dht.begin();
  analogReadResolution(12);              // output 0 to 4095
}

void loop() {
  float t = dht.readTemperature();       // Celsius
  float h = dht.readHumidity();          // percent
  int raw = analogRead(PIN_LDR);
  int lightPct = map(raw, 4095, 0, 0, 100);   // more light = lower voltage
  if (isnan(t) || isnan(h)) Serial.println("DHT22 error!");
  else Serial.printf("T=%.1f C  H=%.0f %%  LDR raw=%d  light=%d %%\n", t, h, raw, lightPct);
  delay(2000);                           // delay is fine in this test step
}
  1. Pins and the sensor object. The DHT22 on GPIO13 and the LDR on GPIO35, exactly as in the pin table. We use the final pins right from step 1. If you use a temporary pin now, you've created one more place for a mistake during the final integration.
  2. ADC resolution. 12 bits means numbers from 0 to 4095. This is already the ESP32 default, but writing it out shows which range we rely on, and we use that range later in map.
  3. Reading the DHT22. Temperature in Celsius and humidity in percent. If a reading fails, it returns NaN ("Not a Number"). The DHT22 is slow: it gives fresh data at most once every 2 seconds. That's why the whole system is designed around a 2-second cycle.
  4. Light as a percentage. map(raw, 4095, 0, 0, 100) converts the range in reverse: 4095 (dark) → 0 percent, 0 (bright) → 100 percent. On common LDR modules (and the Wokwi module), the AO voltage drops as the light increases. If your module works the other way round (covering the sensor makes the percentage go up), just swap the order: map(raw, 0, 4095, 0, 100). This number is a "relative percentage", not real lux.
  5. Printing with an error check. If either value is NaN, print an error; otherwise print every value on one line. Printing raw next to the percentage helps with troubleshooting: if raw is always 0 or 4095, the problem is the LDR wiring, not the formula.
Step 1 pass test

Temperature and humidity should show sensible numbers (for example 20 to 30 degrees and 20 to 60 percent); holding the sensor in your hand should slowly raise the temperature; covering the LDR should lower the light percentage. Pull out the DATA wire: you should see "DHT22 error!". All good? On to step 2.

Step 2: the OLED display

// Step 2: show values on the OLED
#include <Wire.h>
#include <Adafruit_GFX.h>
#include <Adafruit_SSD1306.h>
#include <DHT.h>

DHT dht(4, DHT22);
Adafruit_SSD1306 oled(128, 64, &Wire, -1);   // -1: no reset pin

void setup() {
  Serial.begin(115200);
  dht.begin();
  Wire.begin(21, 22);                          // SDA, SCL
  if (!oled.begin(SSD1306_SWITCHCAPVCC, 0x3C)) {
    Serial.println("OLED not found! check wiring/address");
    while (true) delay(1000);                  // without a display, this step is pointless
  }
  oled.setTextColor(SSD1306_WHITE);
}

void loop() {
  float t = dht.readTemperature();
  float h = dht.readHumidity();
  oled.clearDisplay();
  oled.setTextSize(2);
  oled.setCursor(0, 0);
  if (isnan(t)) oled.print("T: ERR"); else { oled.print(t, 1); oled.print(" C"); }
  oled.setCursor(0, 24);
  if (isnan(h)) oled.print("H: ERR"); else { oled.print(h, 0); oled.print(" %"); }
  oled.display();                              // nothing appears on screen until this line
  delay(2000);
}
  1. Libraries. Wire for I2C (part of the core), Adafruit GFX for drawing text and shapes, Adafruit SSD1306 for the display itself. GFX is the shared "drawing language" of Adafruit displays; SSD1306 translates it for this particular display. Install both from the Library Manager.
  2. Creating the display object. Width 128, height 64, on the Wire bus, with no reset pin. Four-pin modules have no reset pin; -1 means "do the reset in software".
  3. Starting I2C and the display. The usual address is 0x3C. If begin fails, we print a message and stop. In this test step, stopping is the right call: we want to see a display problem right away. In the final program we do not do this, because a broken display must not also stop the alarm and the uploads (R8). If it isn't found, try address 0x3D, or find the address with the I2C scanner program from lesson 3.3.
  4. Drawing. Clear the buffer, set text size 2 (12×16-pixel characters), move to a position, print, and finally call display(). All drawing commands only write into a buffer in RAM; display() sends the whole buffer over I2C in one go. That's what keeps the screen from flickering. print(t, 1) means one decimal place.

Step 3: a local alarm with hysteresis (no delay)

Before the code, two key ideas:

Hysteresis: like a heater's thermostat

If you turn the alarm on at one number (35 degrees) and off at the same number, then when the temperature hovers around 35 (34.9, 35.1, 34.9...) the alarm keeps switching on and off and the buzzer drives you crazy. A heater's thermostat solves the same problem: it turns on at 20 degrees but doesn't turn off until it reaches 22. This "safety gap" is called hysteresis. We turn the alarm on above 35 and off below 33.

The second idea: timing without delay (lesson 3.1). The LED has to blink, the buzzer has to beep and the button has to be read, all at the same time, so we can't freeze the program with delay(2000). Instead, we run each job by asking "is it time yet?" (millis()).

// Step 3: local alarm with hysteresis and no delay
#include <DHT.h>

const int PIN_LED = 4, PIN_BUZ = 25, PIN_BTN = 27;
const float TEMP_HIGH = 35.0, TEMP_CLEAR = 33.0;
DHT dht(4, DHT22);

float tempC = NAN;
bool alarmOn = false, muted = false;
uint32_t tSensor = 0;

void setup() {
  Serial.begin(115200);
  dht.begin();
  pinMode(PIN_LED, OUTPUT);
  pinMode(PIN_BTN, INPUT_PULLUP);
  ledcAttach(PIN_BUZ, 2000, 8);           // core 3.x API
}

void loop() {
  if (millis() - tSensor >= 2000) {       // every 2 seconds, without stopping the program
    tSensor = millis();
    float t = dht.readTemperature();
    if (!isnan(t)) tempC = t;
    if (!alarmOn && tempC > TEMP_HIGH) { alarmOn = true;  muted = false; Serial.println("ALARM ON"); }
    if (alarmOn && tempC < TEMP_CLEAR) { alarmOn = false; Serial.println("ALARM OFF"); }
  }
  if (alarmOn && digitalRead(PIN_BTN) == LOW) muted = true;   // button = mute

  bool blink = (millis() / 250) % 2;      // flips between 0 and 1 every 250 ms
  digitalWrite(PIN_LED, alarmOn && blink);
  static bool buzzing = false;
  bool wantBuzz = alarmOn && !muted && blink;
  if (wantBuzz != buzzing) {              // only touch LEDC when something changes
    ledcWriteTone(PIN_BUZ, wantBuzz ? 2000 : 0);
    buzzing = wantBuzz;
  }
}
  1. Two thresholds. 35 to turn on and 33 to turn off. A 2-degree gap is bigger than the DHT22's natural reading jitter (about half a degree) and the short swings in room temperature. Too small a gap = flickering; too large a gap = the alarm turns off late.
  2. Program state. The last valid temperature (NaN at first), whether the alarm is on, whether it's muted, and the time of the last reading. These variables are the program's "memory". Because loop runs thousands of times a second, every decision has to be based on stored state, not on waiting.
  3. ledcAttach for the buzzer. Connects pin 25 to PWM with a starting frequency of 2000 Hz and 8-bit resolution. A passive buzzer makes no sound by itself; it has to be vibrated by a square wave at an audio frequency. This is the core 3.x API; on 2.x you had to write ledcSetup and ledcAttachPin (lesson 3.2).
  4. Scheduled reading and the hysteresis logic. The temperature is read every 2 seconds and only replaces the old value if it's valid. Alarm off + temperature above 35 → on (and mute is cleared). Alarm on + temperature below 33 → off. The conditions also check the "current state", so the "ALARM ON" message is printed only once, at the moment of change. We'll use this same pattern later for cloud messages without spam. If the temperature is NaN, every comparison with it is false and the state doesn't change.
  5. The mute button. If the button is pressed during an alarm, the buzzer goes quiet; the LED keeps blinking. Muting only silences the sound, not the alarm itself; the danger is still there and must stay visible. When the next alarm starts, muted becomes false again (line 25).
  6. Blinking without delay. millis() / 250 goes up by one every 250 ms; the remainder after dividing by 2 alternates between 0 and 1. A one-line trick for blinking without any extra variables. The LED is on only when the alarm is on and blink is 1.
  7. Only change the buzzer when needed. ledcWriteTone(pin, 2000) is a 2 kHz beep, ledcWriteTone(pin, 0) is silence. But we only call it when what we want differs from the current state. loop spins thousands of times a second. Setting up PWM again on every pass is pointless and can make the buzzer sound scratchy. The static variable remembers the previous state between passes.

Step 3 pass test

In Wokwi, click the DHT22 and raise the temperature to 36: the LED should blink and the buzzer should beep. Press the button: the buzzer goes quiet, the LED keeps blinking. Bring the temperature down to 34: the alarm should not turn off (hysteresis!). Bring it to 32: off. Step 4: Wi-Fi without blocking

In lesson 4.1 you learned how to connect and reconnect. The point of this step: never wait for Wi-Fi inside loop with a while, because the local alarm doesn't work while you wait (R8).

// Step 4: non-blocking Wi-Fi
#include <WiFi.h>

const char* WIFI_SSID = "Wokwi-GUEST";         // real board: your Wi-Fi name
const char* WIFI_PASS = "";                    // real board: your Wi-Fi password
uint32_t tWifi = 0;
bool wasConnected = false;

void setup() {
  Serial.begin(115200);
  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASS);        // start connecting; we don't wait
}

void loop() {
  bool ok = (WiFi.status() == WL_CONNECTED);
  if (ok && !wasConnected) {
    Serial.print("WiFi connected, IP = ");
    Serial.println(WiFi.localIP());
  }
  if (!ok && wasConnected) Serial.println("WiFi lost!");
  if (!ok && millis() - tWifi >= 15000) {  // one retry every 15 seconds
    tWifi = millis();
    Serial.println("WiFi not connected, retrying...");
    WiFi.reconnect();
  }
  wasConnected = ok;
  // ... everything else runs here without waiting ...
}
  1. Start connecting and move on. WiFi.begin only starts the connection and returns immediately. The connection happens in the background (handled by the FreeRTOS operating system inside the ESP32). We just check the status whenever we need to.
  2. Detecting a change of state. By comparing the current state with the previous one (wasConnected), we print a message only at the moment of connecting and the moment of disconnecting. This is the same "edge" pattern you saw in the alarm: do the work at the moment of change, not on every pass of loop.
  3. Periodic retries. If we're not connected, call WiFi.reconnect() once every 15 seconds. By default the ESP32 core also tries to reconnect on its own; this manual retry is an extra layer of safety. The 15-second gap stops us from "hammering" the router with back-to-back requests.

Step 5: MQTT

The public broker broker.hivemq.com on port 1883 works without signing up (lesson 5.1). Because it's public, anyone can see your messages; so build your topic with a unique prefix (for example your name and a random number) and never send private data.

// Step 5: send a test message over MQTT
#include <WiFi.h>
#include <PubSubClient.h>

const char* MQTT_HOST = "broker.hivemq.com";
const char* BASE = "esp32fa/station-42/";      // make this unique!
WiFiClient net;
PubSubClient mqtt(net);
uint32_t tMqtt = 0, tPub = 0;

void setup() {
  Serial.begin(115200);
  WiFi.begin("Wokwi-GUEST", "");             // real board: your Wi-Fi name and password
  mqtt.setServer(MQTT_HOST, 1883);
}

void loop() {
  if (WiFi.status() != WL_CONNECTED) return;   // no Wi-Fi: do nothing
  if (!mqtt.connected()) {
    if (millis() - tMqtt < 5000) return;      // at most one attempt every 5 seconds
    tMqtt = millis();
    String id = "esp32-station-" + String((uint32_t)ESP.getEfuseMac(), HEX) + "-" + String(esp_random() & 0xFFFF, HEX);
    Serial.println(mqtt.connect(id.c_str()) ? "MQTT connected" : "MQTT failed");
    return;
  }
  mqtt.loop();                                 // keep the connection alive
  if (millis() - tPub >= 10000) {
    tPub = millis();
    String topic = String(BASE) + "test";
    String msg = String(millis() / 1000);
    mqtt.publish(topic.c_str(), msg.c_str());
    Serial.println("Published " + topic + " = " + msg);
  }
}
  1. The topic prefix. Every topic in this project starts with esp32fa/station-42/. One prefix means you can see all of the station's messages at once in a client with esp32fa/station-42/#. And if you switch to Adafruit IO, you only change this one line.
  2. Connecting with a gap between attempts. If there's no Wi-Fi, we return from loop right away. If MQTT isn't connected, we try at most once every 5 seconds. The client ID is built from the MAC address. The ID must be unique; if two devices connect with the same ID, the broker kicks out the first one and they keep knocking each other off. Note: mqtt.connect itself can take a few seconds when the server can't be reached; this is the only place where we block a little.
  3. mqtt.loop(). Must be called regularly. It sends "I'm alive" (keep-alive) messages to the broker and processes incoming messages. If loop gets stuck in a long delay, the broker decides the device is dead and drops the connection.
  4. Publishing every 10 seconds. Sends the board's uptime (in seconds) to the .../test topic. A simple test message that is always changing; if the number keeps going up in your client, the whole chain (Wi-Fi, DNS, TCP, MQTT) is healthy.
Where do I see the messages?

In an MQTT client (for example the HiveMQ web client, or the app you used in lesson 5.1), connect to broker.hivemq.com and subscribe to the topic esp32fa/station-42/# (# means "every sub-topic"). Step 5 pass test: you see a new number every 10 seconds.

Step 6: the final integrated program

Now we put all the steps together in one cleanly structured program. The structure:

  • All settings at the top; to change the behavior, you don't have to hunt through the code.
  • One function per responsibility: reading the sensors, alarm logic, outputs, display, network, uploading.
  • loop only schedules: "Is it time to read? Is it time to send?" and hands everything else to the functions.
// Environment monitoring station with cloud alerts — lesson 6.3
#include <WiFi.h>
#include <PubSubClient.h>
#include <Wire.h>
#include <Adafruit_GFX.h>
#include <Adafruit_SSD1306.h>
#include <DHT.h>

// ================== 1. Settings ==================
const char* WIFI_SSID = "Wokwi-GUEST";         // real board: your Wi-Fi name
const char* WIFI_PASS = "";                    // real board: your Wi-Fi password
const char* MQTT_HOST = "broker.hivemq.com";
const uint16_t MQTT_PORT = 1883;
const char* MQTT_USER = nullptr;               // Adafruit IO: username
const char* MQTT_KEY  = nullptr;               // Adafruit IO: AIO Key
const char* BASE      = "esp32fa/station-42/"; // unique topic prefix

const float TEMP_HIGH  = 35.0;                 // above this: alarm
const float TEMP_CLEAR = 33.0;                 // below this: alarm ends
const uint32_t SENSOR_MS  = 2000;              // read every 2 seconds
const uint32_t PUBLISH_MS = 30000;             // send every 30 seconds
const uint32_t REMIND_MS  = 600000;            // alarm reminder: at most every 10 minutes

// ================== 2. Pins ==================
const int PIN_DHT = 13;
const int PIN_LDR = 35;                        // ADC1: works with Wi-Fi
const int PIN_LED = 4;
const int PIN_BUZ = 25;
const int PIN_BTN = 27;                        // mute button

// ================== 3. Objects and state ==================
DHT dht(PIN_DHT, DHT22);
Adafruit_SSD1306 oled(128, 64, &Wire, -1);
WiFiClient net;
PubSubClient mqtt(net);

float tempC = NAN, hum = NAN;
int lightPct = 0;
bool alarmOn = false, muted = false, oledOk = false;
uint32_t tSensor = 0, tPublish = 0, tAlert = 0, tWifi = 0, tMqtt = 0;
float fakeTemp = NAN;                          // test helper: NAN = use the real sensor

// ================== 4. Sensors ==================
void readSensors() {
  float t = dht.readTemperature();
  float h = dht.readHumidity();
  if (!isnan(t) && !isnan(h)) { tempC = t; hum = h; }
  else Serial.println("DHT22 read failed, keeping last value");
  if (!isnan(fakeTemp)) tempC = fakeTemp;      // test helper (section 10)
  int raw = analogRead(PIN_LDR);               // 0..4095
  lightPct = map(raw, 4095, 0, 0, 100);        // more light = lower voltage
}

// ================== 5. Sending to the cloud ==================
void publishValue(const char* name, float v, int decimals) {
  char topic[64], payload[16];
  snprintf(topic, sizeof(topic), "%s%s", BASE, name);
  snprintf(payload, sizeof(payload), "%.*f", decimals, v);
  mqtt.publish(topic, payload);
}

void publishAll() {
  if (!mqtt.connected() || isnan(tempC)) return;
  publishValue("temp", tempC, 1);
  publishValue("hum", hum, 0);
  publishValue("light", lightPct, 0);
  Serial.println("Published to MQTT");
}

void publishAlert(const char* msg) {
  tAlert = millis();                           // restart the reminder timer
  Serial.println(msg);
  if (!mqtt.connected()) return;
  char topic[64];
  snprintf(topic, sizeof(topic), "%salert", BASE);
  mqtt.publish(topic, msg);
}

// ================== 6. Alarm logic (hysteresis + rate limiting) ==================
void updateAlarm() {
  if (isnan(tempC)) return;
  if (!alarmOn && tempC > TEMP_HIGH) {
    alarmOn = true;
    muted = false;
    publishAlert("ALERT: temperature high");
  } else if (alarmOn && tempC < TEMP_CLEAR) {
    alarmOn = false;
    publishAlert("OK: temperature back to normal");
  } else if (alarmOn && millis() - tAlert >= REMIND_MS) {
    publishAlert("ALERT: still high");         // a reminder, not spam
  }
}

void driveOutputs() {
  if (alarmOn && digitalRead(PIN_BTN) == LOW) muted = true;
  bool blink = (millis() / 250) % 2;
  digitalWrite(PIN_LED, alarmOn && blink);
  static bool buzzing = false;
  bool wantBuzz = alarmOn && !muted && blink;
  if (wantBuzz != buzzing) {
    ledcWriteTone(PIN_BUZ, wantBuzz ? 2000 : 0);
    buzzing = wantBuzz;
  }
}

// ================== 7. Display ==================
void drawDisplay() {
  if (!oledOk) return;                         // no display? everything else keeps going
  oled.clearDisplay();
  oled.setTextSize(1);
  oled.setCursor(0, 0);
  oled.print(WiFi.status() == WL_CONNECTED ? "WiFi OK  " : "WiFi --  ");
  oled.print(mqtt.connected() ? "MQTT OK" : "MQTT --");
  oled.setTextSize(2);
  oled.setCursor(0, 14);
  if (isnan(tempC)) oled.print("T: ERR");
  else { oled.print(tempC, 1); oled.print(" C"); }
  oled.setCursor(0, 34);
  if (isnan(hum)) oled.print("H: ERR");
  else { oled.print(hum, 0); oled.print(" %"); }
  oled.setTextSize(1);
  oled.setCursor(0, 56);
  oled.printf("Light %d%%  %s", lightPct, alarmOn ? (muted ? "ALARM(m)" : "ALARM!") : "normal");
  oled.display();
}

// ================== 8. Network (non-blocking) ==================
void keepWiFi() {
  if (WiFi.status() == WL_CONNECTED) return;
  if (millis() - tWifi < 15000) return;        // one attempt every 15 seconds
  tWifi = millis();
  Serial.println("WiFi: reconnecting...");
  WiFi.reconnect();
}

void keepMqtt() {
  if (WiFi.status() != WL_CONNECTED) return;
  if (mqtt.connected()) { mqtt.loop(); return; }
  if (millis() - tMqtt < 5000) return;         // one attempt every 5 seconds
  tMqtt = millis();
  String id = "esp32-station-" + String((uint32_t)ESP.getEfuseMac(), HEX) + "-" + String(esp_random() & 0xFFFF, HEX);
  String will = String(BASE) + "status";
  if (mqtt.connect(id.c_str(), MQTT_USER, MQTT_KEY, will.c_str(), 0, true, "offline")) {
    mqtt.publish(will.c_str(), "online", true);
    Serial.println("MQTT connected");
  } else {
    Serial.printf("MQTT failed, state=%d\n", mqtt.state());
  }
}

// ================== 9. setup and loop ==================
void setup() {
  Serial.begin(115200);
  pinMode(PIN_LED, OUTPUT);
  pinMode(PIN_BTN, INPUT_PULLUP);
  ledcAttach(PIN_BUZ, 2000, 8);                // core 3.x API
  analogReadResolution(12);
  dht.begin();
  Wire.begin(21, 22);
  oledOk = oled.begin(SSD1306_SWITCHCAPVCC, 0x3C);
  if (oledOk) oled.setTextColor(SSD1306_WHITE);
  else Serial.println("OLED not found, continuing without display");
  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  mqtt.setServer(MQTT_HOST, MQTT_PORT);
  net.setConnectionTimeout(1000);              // TCP: give up after 1 s (default 3 s)
  mqtt.setSocketTimeout(2);                    // broker reply: give up after 2 s (default 15 s)
  tWifi = millis();
}

void loop() {
  readSerialCommands();                        // test helper (section 10)
  uint32_t now = millis();
  if (now - tSensor >= SENSOR_MS) {
    tSensor = now;
    readSensors();
    updateAlarm();
    drawDisplay();
  }
  if (now - tPublish >= PUBLISH_MS) {
    tPublish = now;
    publishAll();
  }
  keepWiFi();
  keepMqtt();
  driveOutputs();
}

// ================== 10. Test helper: a fake temperature over Serial ==================
void readSerialCommands() {
  if (!Serial.available()) return;
  String line = Serial.readStringUntil('\n');  // e.g. "t 36" or "real"
  line.trim();
  if (line.startsWith("t ")) {
    fakeTemp = line.substring(2).toFloat();
    Serial.printf("Fake temperature: %.1f C\n", fakeTemp);
  } else if (line == "real") {
    fakeTemp = NAN;
    Serial.println("Using the real sensor again");
  }
}

Let's go through the program section by section. Click any card to highlight its lines in the code above.

  1. Section 1: settings. Network, broker, username and key (for public HiveMQ, nullptr means "none"), topic prefix, thresholds and time intervals. The two Wi-Fi lines are for Wokwi; on a real board, write your own network name and password there (or move them to secrets.h). Any number you might want to change one day should have a name and live at the top of the program. Nobody will understand a "magic number" 600000 in the middle of the code six months from now; everyone understands REMIND_MS. In a real project, move the passwords into a secrets.h file (lesson 6.2).
  2. Section 2: pins. Exactly as in the pin table and the wiring diagrams. A single source of truth: if you move a wire, this is the only place you change.
  3. Section 3: objects and state. The sensor, the display, the network client and MQTT; then the latest values, the alarm state, whether the display is working, and a "last time" for each scheduled job. The last variable, fakeTemp, belongs to the test helper in section 10. The five t... variables are five independent "clocks": each job has its own clock and never holds up the others. This is the heart of scheduling without delay.
  4. Section 4: reading the sensors. Like step 1, with one difference: if the DHT22 returns an error, the last valid value is kept. The last line only matters while testing: if you typed a fake temperature (section 10), it replaces the real one. The DHT22 occasionally misses a reading. Wiping the number on every single error would make "ERR" flash on the display and cut the cloud data. Until the first successful reading the value is NaN and the display shows ERR (R1). In exercise 2 you'll make this smarter.
  5. Section 5 (a): one function to send any number. The topic name is built with BASE, and the number is turned into text with however many decimal places you ask for (%.*f). Repeating the same code three times means three places for bugs. A small function means one. We used snprintf with a fixed-size array instead of String so we don't fragment memory; that matters in a program that stays on for months.
  6. Section 5 (b): sending all values. Nothing is sent if MQTT isn't connected or we don't have any valid temperature yet. Sending "nan" to a dashboard breaks its charts. Three separate topics (temp, hum, light) suit Adafruit IO, where each feed expects one number. With 3 values every 30 seconds, that's 6 messages a minute, which keeps us under the Adafruit IO free tier's rate limit (about 30 data points per minute).
  7. Section 5 (c): the alert message. Records the time, prints the message to Serial and, if we're connected, sends it to .../alert. tAlert is updated even if the send fails; that way a network outage doesn't cause repeated retries and a flood of messages the moment we reconnect. A deliberate weakness: if the network is down at the moment the alarm starts, the first message is lost, and the reminder 10 minutes later makes up for it (exercise 1 improves this).
  8. Section 6 (a): hysteresis and rate limiting. Three cases: the alarm starts (above 35 and previously off), the alarm ends (below 33 and previously on), a reminder (still on and 10 minutes since the last message). These three branches implement R5 and R7 exactly. Without the third branch, a user who missed the first message would never know the problem is still going on. Without the time limit, a message would arrive every 2 seconds: 1800 messages an hour! You'd end up muting your phone, and when it really mattered, you'd never see the alert.
  9. Section 6 (b): local outputs. The same logic as step 3: mute button, blinking LED, and changing the buzzer only when needed. This function runs on every pass of loop so the blinking and the button stay smooth, unlike reading the sensors, which happens only every 2 seconds. Light jobs often; heavy jobs rarely.
  10. Section 7: the display. Network status on the top line; temperature and humidity in big letters in the middle; light and alarm state at the bottom (ALARM(m) means muted). If the display wasn't found, the function returns right away. Showing the Wi-Fi and MQTT status on screen lets you troubleshoot on site without a laptop. oledOk means a display failure (a loose wire, say) doesn't stop the alarm and the uploads, unlike step 2, which stopped on purpose.
  11. Section 8 (a): keeping Wi-Fi alive. Just like step 4. If we're connected, the function returns almost instantly, so calling it on every pass of loop costs nothing.
  12. Section 8 (b): keeping MQTT alive, with a "last will" (LWT). When we connect, we tell the broker: "If I disconnect without saying goodbye, publish the message offline with retain on .../status on my behalf." Right after connecting, we send online with retain ourselves. With this trick, the dashboard always knows whether the station is alive, even if the station loses power and never gets a chance to say goodbye. Retain means anyone who subscribes later gets the latest status immediately. If the connection fails, mqtt.state() gives you an error code (for example, negative means a network problem, and 4 or 5 means a wrong username or key). Adafruit IO doesn't support the retain flag (lesson 5.1); but because every feed stores its own latest value, the dashboard still shows the last status. If you're on Adafruit IO and the connection keeps dropping and reconnecting, change true (retain) to false on lines 143 and 144 to rule this out.
    A network outage must not freeze the local alarm (R8), so we cap how long one connection attempt may take. mqtt.connect first opens a TCP connection to the broker, then waits for the broker's reply. In setup we limit the first wait to 1 second (setConnectionTimeout) and the second to 2 seconds (setSocketTimeout); the defaults are 3 and 15 seconds, and 15 seconds of silence in the middle of an alarm is a real problem. With attempts 5 seconds apart, the worst case is a hiccup of a second or two in the blinking now and then, never a frozen alarm. Test T11 checks exactly this. The fully professional approach is to put the whole network part in a separate FreeRTOS task so the local outputs are never held up at all; exactly what you learned in lesson 5.4 (optional exercise).
  13. Section 9 (a): setup. Pins, the buzzer with the core 3.x API, the ADC, the sensor, I2C and the display (without stopping if it fails), starting the Wi-Fi connection (without waiting) and setting the broker. The last two lines limit how long one MQTT connection attempt can block (see section 8 (b)). setup has no waiting loops, which means the device reaches loop in a fraction of a second and the local alarm works from the very start, even if the router is off (R8).
  14. Section 9 (b): loop, the central scheduler. Every 2 seconds: read, decide on the alarm, update the display. Every 30 seconds: send. On every pass: keep Wi-Fi and MQTT alive and drive the outputs. The first line checks for a test command from the Serial Monitor (section 10). The whole program logic fits in about 15 readable lines. If tomorrow you want a new feature (say, saving to an SD card every 5 minutes), you just add one more time variable and one more if. now - tX >= interval keeps working correctly even after millis overflows (about 49 days).
  15. Section 10: a test helper, a fake temperature over Serial. Type t 36 in the Serial Monitor and press Enter: from then on the station uses 36 °C instead of the sensor's value. Type real to go back to the real sensor. It uses the Serial input you learned in lesson 3.1; set the Serial Monitor's line ending to Newline. In Wokwi you just click the DHT22 and drag the temperature slider; on a real board you'd have to heat the sensor with a hair dryer and wait for it to cool down again. With this helper, tests T4 to T8 take minutes on a real board too. Testing hooks like this are common in real products; keep it, it costs nothing when you don't use it.

The whole station in Wokwi: in the Library Manager tab, add these libraries: DHT sensor library, Adafruit SSD1306, Adafruit GFX Library and PubSubClient. The virtual Wokwi-GUEST Wi-Fi is connected to the real internet, so the messages really do reach broker.hivemq.com and you can see them in your own MQTT client. Click the DHT22 and push the temperature above 35; click the light sensor and change its lux value. Be sure to change BASE to a prefix of your own.

Battery mode (optional): combining with lesson 6.1

The program above is always on and draws about 100 mA; on a battery it lasts only a day or two. For battery mode (R9) you have to change the design, not just add a line:

  • Do all the work in setup(): wake up, read the sensor, send a message if needed, go to sleep (say, for 5 minutes). loop stays empty.
  • Keep the alarm state and the time of the last message in RTC_DATA_ATTR; because millis() starts from zero after every wake-up, count "wake-ups" instead of time for the rate limiting.
  • The buzzer and the blinking LED don't work during sleep; the local alarm effectively becomes one short beep per wake-up. That's a trade-off you should write into the PRD.
  • Turn the OLED off before sleeping (oled.ssd1306_command(SSD1306_DISPLAYOFF)), otherwise it stays on and drains the battery.
  • Let the button on GPIO27 (an RTC pin) wake the board with EXT0 for an instant reading.

You saw the battery hardware (a protected charger, a low-power regulator, the dev board's sleep current) in 6.1 and 1.4; read those sections again. Fully implementing this mode is exercise 3.

Enclosure and placement

  • Keep the sensor away from the ESP32. The ESP32 and the board's regulator get warm, especially with Wi-Fi on. A DHT22 right next to the board reads several degrees higher than the real room temperature. Leave at least a few centimeters of space, or put the sensor outside the box on a cable.
  • Air has to flow. In a sealed box, the sensor measures the humidity and temperature of the box itself. Give the sensor ventilation holes.
  • No direct sunlight. With direct sun on it, the DHT22 measures the temperature of "the sensor itself", not the air. The LDR, on the other hand, has to go where it can see the ambient light.
  • Away from sources of heat and moisture (heaters, kettles, the kitchen), unless that's exactly what you want to monitor.
  • Outdoors you need a waterproof box and a "radiation shield" (like the stacked-plate housings on weather stations); and keep the ESP32 away from water and condensation.
  • Don't cover the Wi-Fi antenna. The antenna on the WROOM module (the wavy trace at the end of the module) shouldn't be near metal or under wires.

Lesson quiz

Why did we connect the LDR to GPIO35 and not, say, to GPIO25?

  1. GPIO25 is output-only
  2. GPIO35 is on ADC1; ADC2 (like GPIO25) doesn't work while Wi-Fi is on
  3. GPIO35 is more accurate
  4. GPIO35 is the only I2C pin
ADC2 is shared with the Wi-Fi radio. In a project that uses Wi-Fi, analog inputs go only on ADC1 (GPIO32 to 39).

The alarm is on with TEMP_HIGH=35 and TEMP_CLEAR=33. The temperature drops to 34 degrees. What happens?

  1. The alarm turns off
  2. An "OK" message is sent
  3. The alarm stays on
  4. The alarm flickers on and off quickly
This is hysteresis: between 33 and 35, the previous state is kept.

If we remove the "reminder" branch and the tAlert variable and send an alert message on every reading where the temperature is above 35, how many messages are sent during one hour of alarm?

  1. About 1800 messages (one every 2 seconds)
  2. 6 messages
  3. 120 messages
  4. 1 message
3600 ÷ 2 = 1800. Rate limiting brings this down to 1 start message + at most 6 reminders per hour.

Why doesn't the final program's setup use a while to wait for Wi-Fi to connect?

  1. Because while in setup causes a compile error
  2. Because without while, Wi-Fi never connects
  3. Because while increases power consumption
  4. Because if the router is off, the local alarm would never start working either
R8: local jobs never wait for the network. The connection happens in the background.

When is the "last will" (LWT) message with the value offline published on the status topic?

  1. Every time the device connects
  2. When the broker notices the device disconnected without saying goodbye (for example, a power cut)
  3. When the temperature goes above 35
  4. Every 30 seconds
The device hands the LWT to the broker when it connects, and the broker publishes it only if the connection drops unexpectedly.

The station reads 4 degrees higher than the wall thermometer. What's the first thing you check?

  1. The TEMP_HIGH value
  2. Switch to a different DHT library
  3. How far the sensor is from the ESP32, sources of heat, and sunlight
  4. Turn off Wi-Fi to avoid radio interference
Heat from the ESP32 itself and its regulator is the most common cause. The sensor should feel the room's free air, not the board's heat.

Exercises

Exercise 1: an alert that never gets lost

In the current program, if the network is down at the moment the alarm starts, the "ALERT" message is lost. Change the program so the alert message waits in a "pending" variable and is sent as soon as MQTT connects.

Hint

Create a variable const char* pendingAlert = nullptr;. In publishAlert, if you're not connected, store the message in it. In keepMqtt, right after a successful connection, if pendingAlert isn't empty, send it and clear it. Because the messages are constant strings, keeping a pointer to them is safe.

Exercise 2: a dead sensor

If the DHT22 gets disconnected for good, the current program shows and sends the last valid temperature forever; that's a lie. Change it so that after 5 failed readings in a row, tempC and hum go back to NaN and an "ERROR: sensor" message is sent (just once) to the alert topic.

Hint

Add a failStreak counter in readSensors: reset to zero on success, add one on failure. When it reaches exactly 5 (not greater-than-or-equal, so the message goes out only once), set the values to NaN and call publishAlert. publishAll already sends nothing when the value is NaN, and the display shows "ERR".

Answer 
// Replacement for readSensors in the final program (part of a program)
int failStreak = 0;

void readSensors() {
  float t = dht.readTemperature();
  float h = dht.readHumidity();
  if (!isnan(t) && !isnan(h)) {
    tempC = t; hum = h;
    failStreak = 0;
  } else {
    failStreak++;
    if (failStreak == 5) {                   // exactly once
      tempC = NAN; hum = NAN;
      publishAlert("ERROR: sensor");
    }
  }
  int raw = analogRead(PIN_LDR);
  lightPct = map(raw, 4095, 0, 0, 100);
}
  1. Success resets the counter. That means only failures in a row are counted; an occasional single error is normal.
  2. On the fifth failure, report the fault. The values become NaN and one error message goes out. The condition == 5 instead of >= 5 means the message goes out only once, not on every reading after that; the same "no spam" principle. Five readings means 10 seconds, which can't be mistaken for a random glitch. publishAlert must be defined before this function (as in the final program, where section 5 comes before it's used, or with a forward declaration).
Exercise 3: battery mode

Build the battery version of the station (see the "Battery mode" section): wake every 5 minutes, take a reading, show it on the OLED for 3 seconds, send a message if an alarm started or ended, send the values once every 6 wake-ups, and go back to sleep. The GPIO27 button should wake the board for an instant reading. Then use the formula from lesson 6.1 to estimate how long a 2000 mAh battery would last.

Hint

Use the variables RTC_DATA_ATTR bool alarmOn and RTC_DATA_ATTR uint32_t wakeCount. Condition for sending values: wakeCount % 6 == 0. Alarm reminder: every 2 wake-ups (10 minutes). For Wi-Fi, use connectWiFiFast() from lesson 6.1 with a timeout, and only turn Wi-Fi on when you have something to send. Before sleeping, turn the OLED off with SSD1306_DISPLAYOFF and set up EXT0 on GPIO27 with a LOW level and the RTC pull-up. When the button caused the wake-up, skip sending and just show the reading.

The lesson in three lines

Start a big project with clear requirements (a PRD), an architecture and a pin table with reasons, then build it in small tested steps: sensors, display, alarm, Wi-Fi, MQTT, integration. The final program, with separate functions and millis() scheduling, never waits for the network; the alarm doesn't flicker thanks to hysteresis and doesn't spam thanks to rate limiting. Before you say "done", pass every acceptance test and mount the sensor away from the ESP32's heat.
