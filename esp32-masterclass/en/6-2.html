AI can write a hundred lines of ESP32 code in a few seconds. The problem is that it writes that code with the same confidence whether it's right or wrong. In this lesson you learn how to use Claude, ChatGPT and similar tools like a skilled assistant, how to ask them the right questions, and, most important of all, how to review their answers before anything goes near a real board.

  • Solve a compile error with AI's help and your own reasoning
  • Ask AI to explain unfamiliar code line by line, and judge its explanation
  • Review any generated code with a 10-step checklist
  • Keep sensitive information (Wi-Fi passwords, API keys) out of your AI conversations

The philosophy: an assistant, not a replacement

You might ask: "If AI writes the code, why did we read all these chapters?" The short answer: because you have to be the judge. AI produces text that "sounds likely and correct". Most of the time it really is correct, but sometimes it invents something that doesn't exist, or that is wrong for your board, and its tone is equally confident either way. This is called hallucination.

An everyday example: a car's GPS

The navigation app on your phone is incredibly useful. But you've heard all the stories about someone who followed the GPS into a dead-end alley or onto a dirt track. A driver who can drive and read road signs puts the GPS aside when they see it's wrong. A driver who can't just goes wherever it says. This course has made you a driver; now you can use the GPS.

Why is AI so fond of the old API?

Language models learned from text on the internet. Arduino core 2.x was the standard for years, and thousands of tutorials were written for it; core 3.x is newer and there is less text about it. So the "most likely" code, from the model's point of view, is often old code. The model also can't see your board, can't see your wiring, and (unless it has special tools) doesn't run the code. All it knows is what you wrote in your prompt.

The AI workflow loop

Working well with AI isn't a single "question and answer"; it's a loop. No answer goes straight onto the board; everything passes through the filter of your understanding and review.

flowchart TD
  A["A clear need: what exactly do I want?"] --> B["Write the prompt with the template"]
  B --> C["The AI's answer"]
  C --> D{"Do I understand every line?"}
  D -- "No" --> E["Explanation prompt: what does this line do?"]
  E --> D
  D -- "Yes" --> F["Review checklist: pins, voltage, API"]
  F --> G["Compile and run in Wokwi"]
  G --> H{"Did it work?"}
  H -- "No" --> I["Troubleshooting prompt: full error + code + what I tried"]
  I --> C
  H -- "Yes" --> J["Test on a real board, step by step"]
  J --> K["Keep the code in the project and note what you learned"]
The golden rule

Never run code on a real board if there is even one line you don't understand. Ask first, understand, then run it.

A prompt template for embedded projects

The quality of an AI's answer depends directly on the quality of your prompt. In desktop programming, "write a program that adds two numbers" is almost enough. But in embedded work, the code is connected to real hardware: which board? which pin? which library version? If you don't say, the AI guesses, and its guesses are exactly the mistakes in the table above.

Save this template and fill it in every time. It's in English because the technical names, pins and code are all in English and that makes it easy to copy. If you prefer, you can write the same structure in your own language; today's models understand many languages well (Persian included). Just keep pin names, function names and error messages exactly as they are, in English.

ROLE: You are an experienced embedded engineer helping a beginner.

HARDWARE
- Board: ESP32 DevKitC V4 (ESP32-WROOM-32E module)
- Core: Arduino-ESP32 core 3.x (exact: 3.x.x) in Arduino IDE 2
- Parts and wiring:
  * DHT22: DATA -> GPIO4, VCC -> 3V3, GND -> GND (10k pull-up present)
  * OLED SSD1306 I2C 128x64: SDA -> GPIO21, SCL -> GPIO22, address 0x3C

LIBRARIES (installed)
- DHT sensor library (Adafruit) 1.4.x
- Adafruit SSD1306 2.5.x + Adafruit GFX

GOAL
Read temperature and humidity every 2 s and show them on the OLED.

CONSTRAINTS
- No delay() in loop(); use millis() scheduling.
- Use only core 3.x APIs (e.g. ledcAttach, not ledcSetup).
- If a sensor read fails (NaN), show "ERR" instead of a number.
- Do not put real Wi-Fi passwords or API keys in the code; use placeholders.

OUTPUT I WANT
1) Complete, compilable sketch with short comments.
2) A wiring table (part pin -> ESP32 pin) so I can check it.
3) A step-by-step test plan (what to test first, in isolation).
4) If you are unsure about anything, say so and state your assumption.
  1. ROLE. Tells the model what angle to answer from: an experienced engineer helping a beginner. This sentence makes the answers explain more, and stops the model from assuming you already know everything. It isn't magic, but it improves the tone and depth of the answer.
  2. The board and the core version. Write the exact board name and the exact version of the Arduino core. You can find the version under Tools › Board › Boards Manager. This is the most important line in the whole template. "ESP32" on its own covers dozens of boards and two completely different API versions. Writing "core 3.x" prevents a large share of old-API mistakes.
  3. Your actual wiring. Every part, every pin, and which ESP32 pin it goes to; plus the I2C address and the resistors. If you don't say the DHT22 is on GPIO4, the model picks a "typical" pin that may not match your wiring, or may even be an unsuitable pin. You decide the wiring, not the model.
  4. Libraries and versions. Exactly which libraries you have installed. There are several libraries with similar names for the same sensor, and their functions differ. Without this line, the model may write code for a library you don't have, and you get a "not declared" error.
  5. GOAL. One or two clear sentences: what, how often, and where it's shown. A vague goal like "build a weather station" makes the model add ten features you never asked for (a web server, Wi-Fi, an SD card), and the code gets three times bigger and riskier.
  6. CONSTRAINTS. Rules the code must follow: no delay, core 3.x APIs only, what to do when a sensor fails, no real passwords. These are the very lessons you learned in this course. By writing them down, you "inject" your own knowledge into the model. Without them, the model usually picks the simplest way, not the best one.
  7. The output you expect. Complete code, a wiring table, a test plan, and an admission of uncertainty. You want the wiring table so you can compare it with your own wiring: if the model wrote a different pin, it didn't read your prompt properly. The test plan makes you move forward step by step. The last line encourages the model to tell you where it isn't sure, instead of making a confident-sounding guess.

Example 1: generating code (bad prompt versus good prompt)

Note: these examples are made up for teaching

We wrote the texts and code in this section ourselves to show the kind of differences you'll see; they are not real transcripts of a conversation with any particular model. A real model's answer can be different every time.

Bad prompt: "write code so the esp32 reads the temperature and controls a fan"

What does this prompt leave out? Which sensor (DHT11? DHT22? DS18B20?), which pins, how the fan is connected (directly? through a transistor? a relay?), on/off control or speed control with PWM, and which core version. The model has to guess all of it. The result might look something like this:

// Made-up example: the kind of answer a vague prompt might get (it has problems!)
#include <WiFi.h>
#include "DHT.h"

#define DHTPIN 2
DHT dht(DHTPIN, DHT11);
const char* ssid = "MyHomeWiFi";
const char* password = "12345678";

void setup() {
  Serial.begin(9600);
  WiFi.begin(ssid, password);
  while (WiFi.status() != WL_CONNECTED) delay(500);
  dht.begin();
  ledcSetup(0, 25000, 8);
  ledcAttachPin(35, 0);
}

void loop() {
  float t = dht.readTemperature();
  if (t > 30) ledcWrite(0, 255);
  else ledcWrite(0, 0);
  delay(5000);
}
  1. Wi-Fi and a password nobody asked for. The model added Wi-Fi and put a sample password straight into the code. The prompt never mentioned the internet. Extra code means extra bugs. And the habit of putting passwords in code will one day make you publish your real password on GitHub or in a chat.
  2. A guessed sensor and pin. A DHT11 on GPIO2. If your sensor is a DHT22, the numbers come out wrong or NaN. GPIO2 is a strapping pin, and on many boards it also has an LED; it's not a good choice for a sensor.
  3. An unusual serial speed and endless waiting. 9600 instead of 115200; and a loop that spins forever if Wi-Fi never connects. 9600 isn't wrong, but with your Serial Monitor setting (which has always been 115200 in this course) you'll see garbled characters. A loop with no time limit means that if the router is off, the fan is never controlled either.
  4. An old API and an input-only pin. ledcSetup and ledcAttachPin don't exist in core 3.x; and GPIO35 is input-only, so it can't produce PWM at all. These two lines are two completely different mistakes: the first gives a compile error (that's good; you find out quickly). The second, even if it compiled, would never work, and would cost you hours.
  5. NaN ignored, a long delay. If the reading fails, t is NaN, and comparing it always gives false; the fan silently stays off. delay(5000) also freezes the program. Code that quietly does the wrong thing when something fails is the most dangerous kind of code. And the fan itself: you can't connect a 12 V fan straight to an ESP32 pin; you need a transistor or a MOSFET (lesson 3.4). The model didn't give any warning about the hardware!

A good prompt is the template above with these changes: "DHT22 on GPIO4; a two-wire 12 V DC fan, driven through a logic-level MOSFET whose gate is connected to GPIO25, with a flyback diode; speed control with 25 kHz PWM; off below 28 degrees, full speed above 35 degrees, linear in between; core 3.x." Now the model has nothing left to guess. In the answer to a prompt like this you should usually see the following (and if you don't, ask): ledcAttach(25, 25000, 8), ledcWrite(25, duty), an isnan check, timing with millis(), and a wiring table that matches what you said.

A trick: follow-up questions

The first answer isn't the end of the job. A few follow-up questions that are always worth asking:

  • "In which situations might this code not work correctly?"
  • "Which parts depend on the core or library version?"
  • "If the sensor gets disconnected, what exactly does this program do?"
  • "Compare the wiring again with the pins I gave you."

Example 2: troubleshooting a compile error

Say you took some code from an old tutorial on the internet, and the Arduino IDE gives you this error:

/home/me/Arduino/fan/fan.ino: In function 'void setup()':
/home/me/Arduino/fan/fan.ino:5:3: error: 'ledcSetup' was not declared in this scope
    5 |   ledcSetup(CH, 5000, 8);
      |   ^~~~~~~~~
/home/me/Arduino/fan/fan.ino:6:3: error: 'ledcAttachPin' was not declared in this scope
    6 |   ledcAttachPin(FAN_PIN, CH);
      |   ^~~~~~~~~~~~~
exit status 1
  1. Where? The error is in the setup() function. Compiler messages are read from top to bottom. The first error is the most important; later errors are sometimes just side effects of the first one.
  2. What? fan.ino:5:3 means the file fan.ino, line 5, column 3. was not declared in this scope means the compiler doesn't know anything by this name at all. "Not declared" means one of three things: you mistyped the name, the file or library that defines it isn't included, or the function doesn't exist in the version you have installed. Three cases, three different fixes.
  3. A pattern. Two functions from the same family (LEDC) are both unknown. The names are spelled correctly and they belong to the core (not a separate library), so the most likely case is the third one: these functions aren't in the version you have installed. That means you've solved half the problem yourself before even asking the AI.

A good troubleshooting prompt

To troubleshoot, give three things in full: the complete error message (not a summary), the complete code (or at least the relevant part), and what you've already tried plus your own guess.

Board: ESP32 DevKitC V4, Arduino-ESP32 core 3.x (Boards Manager shows 3.x.x).
This code is from an older tutorial. Full compiler output:
[paste the full error output here]

Full code:
[paste the code here]

What I checked: spelling is correct, it compiled for the tutorial author.
My guess: these LEDC functions changed between core 2.x and 3.x.
Please: 1) confirm or reject my guess and explain why,
2) rewrite only the LEDC part for core 3.x,
3) tell me what else in this code might be 2.x-only.
  1. The exact version. Without this line, the model might tell you to "install the ESP32 library", or even suggest the old function again.
  2. The full error and the full code. Copy the error text in full (the Arduino IDE has a Copy error messages button). Summarizing the error ("it gives some LEDC error") throws away vital information such as the line number and the exact wording.
  3. What you tried and your guess. This saves the model from useless suggestions ("check your spelling"), and, more importantly, it makes you think before you ask. If the model rejects your guess, ask it why instead of accepting it straight away.
  4. A specific request. Confirm or reject with a reason, rewrite only the relevant part, and list the other risks. "Only the LEDC part" stops it from rewriting the whole program, which could bring in new bugs. Item 3 prepares you for the next error.

The correct answer (which you should be able to confirm yourself with the official 2.x to 3.0 migration guide): in core 3.x the idea of a "channel" was removed from the main API, and everything works with the pin number. Look at the old and new code side by side:

// Core 2.x (old) — does not compile on 3.x
const int FAN_PIN = 25;
const int CH = 0;

void setup() {
  ledcSetup(CH, 5000, 8);        // channel 0, 5 kHz frequency, 8-bit resolution
  ledcAttachPin(FAN_PIN, CH);    // connect the pin to the channel
}

void loop() {
  ledcWrite(CH, 128);            // in 2.x: first number = channel
}
  1. Two steps in 2.x. First you set up a PWM channel, then you connected the pin to that channel. This approach was flexible but confusing for beginners: two numbers (channel and pin) that had to be kept in step with each other.
  2. ledcWrite with a channel. The first number was the channel. This line still compiles on 3.x, but its meaning has changed: now it means "pin 0". Since pin 0 isn't attached to LEDC, the function silently returns false and nothing happens. A silent trap; read on.
// Core 3.x (current)
const int FAN_PIN = 25;

void setup() {
  ledcAttach(FAN_PIN, 5000, 8);  // pin, frequency, resolution; the channel is picked automatically
}

void loop() {
  ledcWrite(FAN_PIN, 128);       // in 3.x: first number = pin
}
  1. ledcAttach. One line instead of two: pin, frequency and bit resolution. The core finds a free channel by itself. Fewer numbers, fewer mistakes.
  2. ledcWrite with a pin. Now the first number is the pin number. If you fix only ledcSetup but keep the old ledcWrite(0, 128), the code compiles without a single error and the fan never runs. That's why we put item 3 in the troubleshooting prompt: "what else is 2.x?"
Ask the board itself for your core version

If you're not sure which version is installed, run this small program. Put the number it prints into your prompts:

void setup() {
  Serial.begin(115200);
  delay(500);
  Serial.printf("Arduino-ESP32 core %d.%d.%d\n",
                ESP_ARDUINO_VERSION_MAJOR,
                ESP_ARDUINO_VERSION_MINOR,
                ESP_ARDUINO_VERSION_PATCH);
}

void loop() {}
  1. Version macros. ESP_ARDUINO_VERSION_MAJOR and the two macros after it hold the version number of the core the code was compiled with. This number comes from the build itself, so it's no longer a guess. With #if ESP_ARDUINO_VERSION_MAJOR >= 3 you can even write code that compiles on both versions.

Example 3: explaining unfamiliar code, line by line

One of the best uses of AI is as a "private tutor": you give it some code you found on the internet and don't understand, and ask it to explain it line by line. A suggested prompt:

I am a beginner (Arduino-ESP32 core 3.x). Explain this code line by line:
what each line does, WHY it is needed, and what would break if I removed it.
Mark clearly anything you are not sure about.
Then give me 3 small experiments to verify your explanation on a real board.

[paste code here]
  1. What, why, and what if I remove it? Three questions for every line. You can often guess the "what" yourself. The "why" and "what if I remove it" build deep understanding; it's the same structure the explanation cards in this course use.
  2. Experiments to check the answer. The AI's explanation can be wrong too. A test on the board is the final judge, not how confident the text sounds.

For example, take this pulse-counting code (for pulses from a water-flow sensor or a button, say). Below it we've written the kind of explanation you'd expect from a good answer; you can use it to judge the quality of the AI's answer:

volatile uint32_t pulses = 0;
portMUX_TYPE mux = portMUX_INITIALIZER_UNLOCKED;

void IRAM_ATTR onPulse() {
  portENTER_CRITICAL_ISR(&mux);
  pulses++;
  portEXIT_CRITICAL_ISR(&mux);
}

void setup() {
  Serial.begin(115200);
  pinMode(27, INPUT_PULLUP);
  attachInterrupt(digitalPinToInterrupt(27), onPulse, FALLING);
}

void loop() {
  static uint32_t last = 0;
  if (millis() - last >= 1000) {
    last = millis();
    portENTER_CRITICAL(&mux);
    uint32_t n = pulses;
    pulses = 0;
    portEXIT_CRITICAL(&mux);
    Serial.printf("pulses/s: %lu\n", n);
  }
}
  1. volatile. Tells the compiler this variable may be changed "from outside" (in an interrupt), so it must read it from memory every time. Without volatile, the compiler might keep the value in a register for speed, and loop would never see the changes made by the interrupt. If you remove it: sometimes it works, sometimes it doesn't; the worst kind of bug.
  2. A lock (mux). A small lock so the interrupt and loop don't touch pulses at the same time. The ESP32 has two cores, and reading a variable and then zeroing it are two separate operations. Without the lock, a pulse might arrive exactly between the read and the reset and get lost.
  3. The interrupt function (ISR). IRAM_ATTR puts the function in the fast internal RAM. It does only one short job inside: increase the counter. An interrupt must finish within a few microseconds. Serial.print or delay inside an ISR is forbidden. The _ISR in the macro names means the special version for use inside an interrupt.
  4. Setting up the interrupt. GPIO27 is an input with a pull-up; every falling edge (FALLING, meaning from HIGH to LOW) calls the onPulse function. With the internal pull-up, a button or a sensor's open-collector output between the pin and GND is all you need. A mechanical button bounces, so one press can count as several pulses; for a button you need to add debouncing.
  5. Timing without delay. Once every 1000 milliseconds. static means the value of last is kept between runs of loop, without a global variable. The subtraction millis() - last still works correctly even when millis overflows after about 49 days.
  6. Grab the count safely, then print. Under the lock, we copy the value and reset it to zero; after releasing the lock, we print. Work done under a lock must be kept to a minimum; Serial.printf is slow and must not be inside the lock. The result: the number of pulses per second.

Now try it yourself: remove volatile, or move the print inside the ISR. What happens? Did it match what the AI predicted?

One button between GPIO27 and GND. Press the button each time and see how many pulses per second are counted. You'll very likely sometimes see more than one pulse for a single press, because Wokwi simulates button bounce too; that's exactly what bouncing is.

A review checklist for any generated ESP32 code

Print this checklist and stick it by your desk. Any code an AI (or any internet tutorial) gives you must pass these ten steps before it runs on a real board:

  1. I understand every line. If not, ask first. Code you don't understand doesn't get run.
  2. Pins. Check every pin against the pinout page: no GPIO6 to 11; no outputs on 34 to 39; no ADC2 with Wi-Fi; strapping pins (0, 2, 5, 12, 15) only with care.
  3. It matches my wiring. Compare the answer's wiring table with your real circuit, wire by wire.
  4. Voltage and current. No 5 V signal goes straight into an ESP32 pin. No heavy load (motor, fan, relay, LED strip) is powered straight from a pin. A pin can supply a few tens of milliamps at most.
  5. API version. Look for signs of 2.x: ledcSetup, ledcAttachPin, the old ESP-NOW callback signature. Not sure? Check the migration guide.
  6. The libraries are real. Find every #include in the Library Manager or on GitHub. Are the functions it calls actually in that library's documentation?
  7. No endless waiting. A long delay in loop? A while with no time limit? What happens if Wi-Fi or the sensor isn't there?
  8. Error handling. A NaN from the sensor, Wi-Fi dropping, MQTT failing, a missing display: how does the code behave in each case?
  9. Security. No real password or key in the code; no public MQTT topic used to control important things at home.
  10. Wokwi first, then the board. Test the code in Wokwi first, or at least compile it in the Arduino IDE; then on the real board, one part at a time (sensor first, then the display, then the network).

Privacy and security: what you must never paste

Everything you type into an AI conversation goes to another company's servers and may be stored. So:

  • Never paste a real Wi-Fi password, an API key (such as the AIO Key in Adafruit IO), a Telegram bot token, or account passwords into a prompt.
  • Before pasting code, replace these values with placeholders such as "YOUR_WIFI_PASSWORD".
  • Keep other people's personal information (addresses, phone numbers) out of your code and logs.
  • Don't paste an employer's confidential code into public services without permission.

The best habit: keep passwords in a separate file from the very start, and never share that file. In the Arduino IDE, create a new tab called secrets.h:

// secrets.h — don't share this file with anyone and don't put it on GitHub
#pragma once
#define WIFI_SSID  "MyHome"
#define WIFI_PASS  "put-your-real-password-here"
  1. #pragma once. If this file is included more than once, it is only read once. It prevents "redefinition" errors in multi-file projects.
  2. Defining the passwords. Two macros for the network name and password. Now your main .ino file only has #include "secrets.h" and WiFi.begin(WIFI_SSID, WIFI_PASS). You can show that file to an AI or a friend without worry. If you use git, add secrets.h to .gitignore.

Coach's advice

AI makes you faster, as long as you know what you're doing. If you don't, it just helps you make mistakes faster. My rule for my students is simple: for any code you got from an AI, you must be able to explain it to someone else without looking at the answer. Can't do it? Then it isn't your code yet; it's the AI's. And one serious warning: a burned-out circuit, an overheated battery or a leaked password is your responsibility, not the AI's.

  3. 128 isn't an allowed PWM value
  4. ledcWrite was removed in 3.x
This is the silent trap: the same function name with a different meaning. A successful compile means "correct as a language", not "correct in its logic".

Which prompt is better for troubleshooting a compile error with AI?

  1. "my code doesnt work, fix it"
  2. "it gives some LEDC error"
  3. Just pasting the complete code
  4. Core version + the full error text + the code + what you've tried and your guess
The more precise the information, the more precise the answer. And making your own guess forces you to think.

An AI suggested connecting the ECHO output of an HC-SR04 sensor (which runs on 5 V) straight to GPIO18. What do you do?

  1. I don't accept it; I bring the voltage down to 3.3 V with a voltage divider or a level shifter
  2. I accept it, because the AI said so
  3. I just move it to GPIO19
  4. I enable the internal pull-up resistor
ESP32 pins are designed for 3.3 V (ways to convert levels are in lesson 1.4). This is exactly where your basic knowledge is ahead of the AI.

Which of these is the right thing to do in a conversation with an AI assistant?

  1. Paste the complete code with the real Wi-Fi password so the model can test it
  2. Paste the API key so the model can fix the connection
  3. Replace the passwords with placeholder text and keep the real ones in a separate file
  4. Give it your router's IP address and admin password to troubleshoot the network
Sensitive information never goes into a conversation. A separate secrets.h file makes that easy.

The lesson in three lines

AI is an assistant, not a replacement, because it writes right and wrong code with the same full confidence (unsuitable pins, core 2.x APIs, 5 V signals). Get better answers with the prompt template (board, core version, wiring, libraries, goal, constraints, output), and for troubleshooting give the full error and the full code. Review every piece of code with the ten-step checklist, run it in Wokwi first, and never paste a real password or key into a conversation.
