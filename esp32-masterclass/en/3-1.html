Digital and analog: two ways of "listening"

When a GPIO pin is an input, it "reads" the voltage on itself. There are two kinds of reading:

  • Digital: only two answers are possible: HIGH (high voltage, close to 3.3 V) or LOW (close to zero). Like a yes/no question: "Is the button pressed?"
  • Analog: the answer is a number in a range, for example 0 to 4095. Like a "how much?" question: "How far is the knob turned? How bright is it?"
An everyday example

The light switch in your room is digital: it's either on or off. The volume knob on a radio is analog: it can sit anywhere between zero and maximum. The first half of this lesson is about the "switch", and the second half is about the "volume knob".

How does the ESP32 decide between HIGH and LOW?

Inside the pin there's a comparator circuit. If the voltage is above roughly 75% of the supply voltage (about 2.5 V or more) it reads HIGH, and if it's below roughly 25% (about 0.8 V or less) it reads LOW. In between is a "gray zone" where the answer can't be trusted. The goal of everything you learn next is to make sure the pin never sits in the gray zone.

The 4-pin push button: what's going on inside?

Small tactile buttons have four legs but only two electrical connections. Each pair of legs that face each other along the same long side of the body is always connected. Pressing the button connects these two pairs together.

Test it with a multimeter

If you're not sure which legs are connected, set your multimeter to continuity (beep) mode. Two legs that beep without pressing are permanently connected. Two legs that beep only while you press are the switch.

The floating pin problem: our first deliberately broken experiment

The simplest idea that comes to mind is this: connect one side of the button to 3V3 and the other to GPIO27. Press the button, 3.3 V reaches the pin, and we read HIGH. Release it, and... what? The pin is connected to nothing! This is called "floating", and we're doing this experiment on purpose so you can see with your own eyes why you shouldn't do it.

// Floating pin experiment: button with no pull resistor (deliberately wrong!)
const int BUTTON_PIN = 27;

void setup() {
  Serial.begin(115200);
  pinMode(BUTTON_PIN, INPUT);          // plain input, no internal resistor
}

void loop() {
  int state = digitalRead(BUTTON_PIN); // answer: 0 or 1
  Serial.println(state);
  delay(100);
}
  1. The button's pin number. We chose GPIO27. GPIO27 is one of the safe pins (it isn't a strapping pin and isn't wired to the flash), and it can be both an input and an output.
  2. pinMode(pin, INPUT). Makes the pin a plain input; the ESP32 only "looks at" the voltage and connects no internal resistor. We chose the plain mode on purpose so you can see the floating problem. Shortly we'll fix it with a single word.
  3. digitalRead(pin). Reads the pin's voltage and returns 1 (HIGH) or 0 (LOW). We store the answer in an int variable so we can print it or make decisions with it.
  4. Print and a short pause. One number is printed every 100 milliseconds. 100 milliseconds is fast enough to see the changes and slow enough not to flood the Serial Monitor.

Put the button between 3V3 and GPIO27 (the same wiring as "method 1" a little further down, but without the 10 kΩ resistor), upload the code and open the Serial Monitor at 115200. Without pressing the button, bring your finger close to the GPIO27 wire, or touch it. You'll probably see something like this:

0 0 1 1 0 1 0 0 1

You haven't pressed the button, yet the number keeps changing! A floating pin is like a tiny antenna: the electric charge on your body, the 50 Hz mains wiring in the wall and even nearby wires all affect it. The ESP32's input has a very high resistance, so the tiniest bit of charge is enough to push its voltage up and down.

Example: a flag on a pole

A floating pin is like a flag that isn't tied to its pole: every breeze blows it in some direction. A pull resistor is like a spring that always pulls the flag toward one default side; only when your hand (the button) pulls it does it go the other way.

You won't see this experiment in Wokwi

The simulator is a perfect, noise-free world and may show a floating pin as perfectly steady. This is exactly one of the places where real hardware teaches you something the simulator can't. If you have a real board, definitely try this experiment. If you only use Wokwi, just read the output above as "what a real board would show" and move on; from the next section on, everything behaves the same in Wokwi and on real hardware.

The fix: pull-up and pull-down resistors

The fix is to "tie" the pin to a known voltage through a fairly large resistor (usually 10 kΩ):

  • Pull-down: a resistor from the pin to GND. Normal (released) state = LOW. The button sits between the pin and 3V3; pressed = HIGH.
  • Pull-up: a resistor from the pin to 3V3. Normal (released) state = HIGH. The button sits between the pin and GND; pressed = LOW.
Do the math: why 10 kΩ and not zero ohms?

In the pull-up circuit, while the button is pressed, current flows from 3V3 through the resistor to GND: I = 3.3V ÷ 10000Ω = 0.00033A = 0.33mA. Very small and harmless.

If you used a plain wire (zero ohms) instead of the resistor, pressing the button would connect 3V3 straight to GND: a short circuit! The board's regulator heats up and the ESP32 resets. And if you use a very large resistor (say 10 MΩ), the "spring" becomes so weak that noise overpowers it again. 10 kΩ is a good balance between low current and resistance to noise (anything between 4.7 kΩ and 47 kΩ works too).

Method 1: an external 10 kΩ pull-down resistor

With this wiring, run the Floating_Demo code again without changing it. Now you see only 0 until you press the button, no matter how much you touch the wire. Problem solved.

Method 2: the ESP32's internal resistors (no extra parts)

Inside almost every GPIO there are ready-made pull-up and pull-down resistors (each about 45 kΩ) that you switch on with one word in pinMode:

Mode in pinModeWhat gets connectedWhere the button goesReleased / pressed
INPUTNothing (floating)Only with an external resistorUndefined!
INPUT_PULLUPInternal resistor to 3V3Between the pin and GNDHIGH / LOW
INPUT_PULLDOWNInternal resistor to GNDBetween the pin and 3V3LOW / HIGH
GPIO34 to GPIO39 have no internal resistors

The input-only pins GPIO34, 35, 36 and 39 have no internal pull-up or pull-down at all. If you write INPUT_PULLUP for these pins, the compiler won't complain, but the pin still floats. For a button on these pins, always add an external 10 kΩ resistor. (These pins are great for analog reading; you'll see that later.)

Why do professionals prefer the pull-up?

With a pull-up, the button wire goes to GND, not to 3V3. If a GND wire accidentally touches a metal case or something else, nothing bad happens; but a 3V3 wire run outside the circuit makes a short circuit if it touches GND. On top of that, the habit dates back to older chips that had internal pull-ups but no pull-downs. So for the rest of the course we always use INPUT_PULLUP.

A button with INPUT_PULLUP and reversed logic

The main circuit for the rest of this section: a button between GPIO27 and GND (no resistor, since we use the internal pull-up) and an LED with a 220 Ω resistor on GPIO4, the same circuit as in lesson 2.2.

// Button with internal pull-up: pressed = LOW
const int BUTTON_PIN = 27;
const int LED_PIN = 4;

void setup() {
  Serial.begin(115200);
  pinMode(BUTTON_PIN, INPUT_PULLUP);   // internal ~45k resistor to 3.3V
  pinMode(LED_PIN, OUTPUT);
}

void loop() {
  bool pressed = (digitalRead(BUTTON_PIN) == LOW);   // reversed logic!
  digitalWrite(LED_PIN, pressed ? HIGH : LOW);
  Serial.println(pressed ? "pressed" : "released");
  delay(50);
}
  1. Two constants for two pins. The button on 27 and the LED on 4. The same habit as in the last lesson: a meaningful name instead of a bare number, so if you move a wire you only change one line.
  2. INPUT_PULLUP. The pin becomes an input, and the internal resistor to 3.3 V is connected too. Now the pin is always HIGH while released. One word replaces an external resistor and two wires. Fewer wires = fewer chances for mistakes.
  3. Converting to "human" logic. digitalRead(...) == LOW means "is the pin LOW?". The answer (true or false) goes into a bool variable called pressed. With a pull-up, pressed = LOW. This "reversed logic" (active low) is a common source of mistakes. By converting it on the very first line into a clear name (pressed), you don't have to think backwards anywhere else in the program.
  4. The ternary operator ? :. pressed ? HIGH : LOW means "HIGH if pressed is true, otherwise LOW". A short if/else on one line. When you're just choosing between two values, it's easier to read.
  5. Report and pause. Prints the button's state as text. The text pressed/released is easier to read than 0/1, and you no longer have to remember which number means pressed.

The result: the LED stays on while you hold the button and goes off when you release it, like a doorbell.

millis(): the clock that never stops

Before we tackle the button's next problem, we need a vital tool. In lesson 2.2 you saw that delay(1000) freezes the whole program for one second. If you press and release the button during that second, the program never notices. To build a device that does several things at once, we have to put delay aside.

millis() is a simple function: it returns the number of milliseconds that have passed since the board powered up. That's all. It doesn't stop the program; it just tells you the time.

Example: boiling an egg

The delay way: you put the egg in the water and stand motionless by the stove for 10 minutes. If the phone rings, you don't answer.

The millis way: you look at the clock (8:00) and go do other things. Every few seconds you glance at the clock and ask: "Have ten minutes passed since 8:00?" As long as the answer is no, you get on with your other jobs. When it's yes, you turn off the stove.

With numbers

Say the board powered up 5 seconds ago: millis() gives 5000. We turned the LED on at moment 5000 and saved that number in the variable lastToggle. On the following passes of loop we keep calculating millis() − lastToggle. When millis() reaches 5500, the result is 500; that means 500 milliseconds have passed and it's time to switch the LED. During those 500 milliseconds, loop may have run hundreds of thousands of times, and each time it had a chance to do something else too.

// Blink without delay: by looking at the clock
const int LED_PIN = 4;
const unsigned long INTERVAL = 500;   // every 500 milliseconds
unsigned long lastToggle = 0;         // the last time we switched the LED
bool ledOn = false;

void setup() {
  pinMode(LED_PIN, OUTPUT);
}

void loop() {
  unsigned long now = millis();
  if (now - lastToggle >= INTERVAL) {   // is it time?
    lastToggle = now;
    ledOn = !ledOn;
    digitalWrite(LED_PIN, ledOn);
  }
  // loop is free here; do whatever else you like
}
  1. The unsigned long type. A 32-bit unsigned (positive-only) whole number that goes up to about 4.3 billion. millis() returns exactly this type. If you store the time in a plain int, the number goes negative after about 24 days and the program behaves strangely. The rule: every variable that deals with time is an unsigned long.
  2. The program's memory. lastToggle holds the time of the last change, and ledOn holds the LED's current state. Since there's no delay any more, the program has to "remember" where it is by itself. These variables are global so they aren't wiped between passes of loop.
  3. Read the clock once. We store the current time in now. If you call millis in several places during one pass of loop, the answers may differ slightly. Reading it once and using that one number keeps the logic clean.
  4. The key question: "has enough time passed?" now - lastToggle is how many milliseconds have passed since the last change. If it's 500 or more, we enter the if. Always write it as "subtract and compare", not now >= lastToggle + INTERVAL. The millis counter rolls back to zero after about 49.7 days (overflow); thanks to the math of unsigned numbers, the subtraction form works correctly even at that moment, but the addition form breaks.
  5. Record the time and flip the LED. We update the time, !ledOn flips the value (true↔false), and we write it to the pin. digitalWrite treats true like HIGH and false like LOW. So you don't need a separate if.
  6. loop is free. No line stops the program. This is exactly where, in the next section, we'll add button reading without breaking the blinking.

Button bounce: when one press looks like three

When the metal contacts inside a button hit each other, they "bounce up and down" a few times before settling, like a ball dropped on the floor. This usually lasts under 10 milliseconds; to you it's an instant, but in that time the ESP32 reads the pin thousands of times and sees several zeros and ones.

Let's see the problem first. This program counts one every time the button goes from released to pressed, but it deliberately has no debouncing:

// Counting presses without debouncing (deliberately incomplete!)
const int BUTTON_PIN = 27;
int lastState = HIGH;     // previous state (released = HIGH)
int count = 0;

void setup() {
  Serial.begin(115200);
  pinMode(BUTTON_PIN, INPUT_PULLUP);
}

void loop() {
  int state = digitalRead(BUTTON_PIN);
  if (lastState == HIGH && state == LOW) {   // edge: it was just pressed
    count++;
    Serial.print("Press #");
    Serial.println(count);
  }
  lastState = state;
}
  1. Remembering the previous state. lastState holds the button's state from the previous pass of loop; count holds the number of presses. To catch "the moment of pressing", we have to compare the current state with the previous one. A single photo can't tell you something changed; two photos in a row can.
  2. Edge detection (state change detection). The condition is true only when the pin was HIGH (released) before and is LOW (pressed) now. && means "and". If we only asked "is it LOW?", the counter would go up on every pass of loop for as long as your finger is on the button; that's thousands of times a second! We want the "press event", not the "being pressed" state.
  3. Count and print. count++ adds one, and the number is printed. Printing the number lets you see the bounce with your own eyes: one press, several counts.
  4. Update the memory. The current state becomes the "previous state" for the next pass. If you forget this line, lastState stays HIGH forever and edge detection breaks.

Press the button carefully ten times. With cheap buttons you'll usually see something like this (the count sometimes jumps by two or three at a time):

Press #1 Press #2 Press #3 Press #4 Press #5 Press #6

From only three real presses! (Wokwi's button simulates bounce by default too, so you can see this there as well.)

Debouncing with millis: "only believe a change that stays put"

The idea is simple: every time the pin's raw reading changes, restart a timer from zero. Only if the reading stays unchanged for 30 milliseconds do you accept it as the button's real state. Bounces always end before 30 milliseconds, so they're never "believed". In this same program, each press toggles the LED on or off.

// Toggle the LED with each press + debouncing with millis
const int BUTTON_PIN = 27;
const int LED_PIN = 4;
const unsigned long DEBOUNCE_MS = 30;   // bounce is usually under 10ms

int stableState = HIGH;           // the button's "confirmed" state
int lastReading = HIGH;           // the last raw reading
unsigned long lastChangeTime = 0; // when the raw reading last changed
bool ledOn = false;

void setup() {
  Serial.begin(115200);
  pinMode(BUTTON_PIN, INPUT_PULLUP);
  pinMode(LED_PIN, OUTPUT);
}

void loop() {
  int reading = digitalRead(BUTTON_PIN);

  if (reading != lastReading) {        // the raw reading changed (maybe bounce)
    lastChangeTime = millis();         // restart the timer
    lastReading = reading;
  }

  if (millis() - lastChangeTime > DEBOUNCE_MS && reading != stableState) {
    stableState = reading;             // steady for 30ms: it's a real change
    if (stableState == LOW) {          // only at the moment of pressing (not releasing)
      ledOn = !ledOn;
      digitalWrite(LED_PIN, ledOn);
      Serial.println(ledOn ? "LED ON" : "LED OFF");
    }
  }
}
  1. The waiting time: 30 milliseconds. Most buttons bounce for under 10 milliseconds; 30 gives a good safety margin. On the other hand, people can't notice a delay under about 50 milliseconds, so the button doesn't feel "sluggish". If your button is really poor quality, raise it to 50.
  2. Four memory variables. stableState: the last state we "believed". lastReading: the last thing the pin said (maybe bounce). lastChangeTime: when the raw reading last changed. ledOn: the LED's state. Separating the "raw reading" from the "believed state" is the heart of debouncing. We always track the raw reading, but we only act on the believed state.
  3. The raw reading. We read the pin on every pass of loop. loop runs thousands of times a second, so no change escapes the program's notice; not even one-millisecond bounces.
  4. Every raw change resets the timer. If the reading differs from last time, we record the time. During bounce this condition keeps coming true and the timer keeps restarting. So until the bouncing is over, 30 quiet milliseconds never happen.
  5. The confirmation condition. Two things are needed together: more than 30 ms since the last raw change, and a reading that differs from the believed state. Then we believe the new state. The second condition makes us react to each real change only once, not on every pass of loop while the button stays put.
  6. Toggle only at the moment of pressing. When the believed state becomes LOW (pressed), we flip the LED and report it. Releasing the button is a "real change" too (LOW to HIGH). Without this if, the LED would turn on when you press and off when you release; that's the doorbell again!
There's hardware debouncing too

A 100 nF capacitor in parallel with the button smooths out most of the bounce. But software debouncing is free, needs no extra parts and can be adjusted. For beginner projects, software is all you need.

Several things at once: blinking + a button, without delay

Now we combine the two skills: the LED blinks using millis, and at the same time the (debounced) button pauses or restarts the blinking. If you wrote this program with delay(500), short button presses would get lost in the middle of the delay.

// Blinking + reading a button, at the same time and without delay
const int BUTTON_PIN = 27;
const int LED_PIN = 4;
const unsigned long BLINK_MS = 500;
const unsigned long DEBOUNCE_MS = 30;

bool blinking = true;             // the button turns this on/off
bool ledOn = false;
unsigned long lastBlink = 0;

int stableState = HIGH, lastReading = HIGH;
unsigned long lastChangeTime = 0;

void setup() {
  Serial.begin(115200);
  pinMode(BUTTON_PIN, INPUT_PULLUP);
  pinMode(LED_PIN, OUTPUT);
}

void loop() {
  unsigned long now = millis();

  // Job 1: the button (with debouncing)
  int reading = digitalRead(BUTTON_PIN);
  if (reading != lastReading) { lastChangeTime = now; lastReading = reading; }
  if (now - lastChangeTime > DEBOUNCE_MS && reading != stableState) {
    stableState = reading;
    if (stableState == LOW) {
      blinking = !blinking;
      Serial.println(blinking ? "Blinking ON" : "Blinking paused");
    }
  }

  // Job 2: blinking (only if enabled)
  if (blinking && now - lastBlink >= BLINK_MS) {
    lastBlink = now;
    ledOn = !ledOn;
    digitalWrite(LED_PIN, ledOn);
  }
  if (!blinking && ledOn) {         // when paused, keep the LED off
    ledOn = false;
    digitalWrite(LED_PIN, LOW);
  }
}
  1. Blinking memory. blinking says whether blinking is enabled; ledOn and lastBlink work like in Blink_NoDelay. Each "job" has its own variables. This separation lets you add a third and fourth job later without everything getting tangled.
  2. Button memory. The same debouncing variables; this time two variables of the same type are declared on one line. int a = 1, b = 2; means two int variables on one line. It's just shorter.
  3. One clock for everyone. The current time is read once, and both jobs use it. Both jobs make their decisions from the same "snapshot" of the clock; the logic becomes simpler and more predictable.
  4. Job 1: the button. Exactly the earlier debouncing logic, except it flips the blinking variable instead of the LED. Line 25 is the earlier three lines squeezed onto one line. On each pass of loop this part takes only a few microseconds and never waits; that's why no press ever gets lost.
  5. Job 2: blinking. If blinking is enabled and 500 ms have passed, flip the LED. Two completely independent jobs are written one after the other, and neither keeps the other waiting. This pattern (check a condition quickly, do a short job, move on) is the foundation of every multitasking microcontroller program.
  6. A clean pause. If blinking is paused but the LED was left on, turn it off. Without this part, if you press the button right while the LED is on, the LED gets "stuck" on. Small details are the difference between a professional product and an amateur one.

Talking back: sending commands from the Serial Monitor

Until now the Serial Monitor has been a one-way street: the ESP32 talks and you read. But the box at the top of the Serial Monitor (in Wokwi, the input line under the output) lets you type something and send it to the board. That turns the Serial Monitor into a tiny remote control: you can change a setting while the program is running, without uploading again. Later lessons use this all the time (for example, typing a target angle for a motor in lesson 3.4).

An everyday example: a mailbox

Everything you type lands in a small mailbox inside the ESP32 (the receive buffer, 256 bytes by default). The letters wait there until your program checks. Serial.available() is a glance at the mailbox: "how many letters are waiting?" Serial.readStringUntil('\n') takes letters out until it reaches the "end of message" mark. If your program never checks, the mail just piles up; nothing happens by itself.

The line-ending setting: the invisible "Enter"

When you press Enter, the Serial Monitor can add invisible characters to the end of your text. In Arduino IDE 2 you choose which ones with the drop-down next to the input box:

SettingWhat is sent when you type 250 and press EnterGood for our code?
No Line Ending250Works, but slowly: the ESP32 can't see where the message ends, so it waits 1 second (the timeout) before it gives up and uses what it has
New Line250\n✅ Best choice. \n is the "end of message" mark
Carriage Return250\rLike "No Line Ending": we look for \n, which never comes
Both NL & CR250\r\n✅ Also fine, because trim() removes the extra \r

Set it to New Line once; the IDE remembers it. Wokwi's Serial Monitor sends a \n when you press Enter, so it works there without changing anything.

Example: change the blink speed by typing a number

The circuit is just the LED on GPIO4 (you can leave the button connected; it isn't used). Type a number between 50 and 2000 and press Enter, and the LED blinks at that speed. Type stop to switch it off.

// Commands from the Serial Monitor: type a blink speed
const int LED_PIN = 4;
unsigned long interval = 500;          // 0 means "stopped"
unsigned long lastToggle = 0;
bool ledOn = false;

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  Serial.println("Type 50 to 2000 (ms) or stop, then press Enter");
}

void loop() {
  if (Serial.available() > 0) {                  // is there mail?
    String line = Serial.readStringUntil('\n');  // read up to Enter
    line.trim();                                 // remove \r and spaces
    if (line == "stop") {
      interval = 0;
      ledOn = false;
      digitalWrite(LED_PIN, LOW);
      Serial.println("Stopped");
    } else {
      long value = line.toInt();                 // "250" -> 250, "abc" -> 0
      if (value >= 50 && value <= 2000) {
        interval = value;
        Serial.printf("New interval: %ld ms\n", value);
      } else {
        Serial.println("Please type a number from 50 to 2000");
      }
    }
  }

  if (interval > 0 && millis() - lastToggle >= interval) {
    lastToggle = millis();
    ledOn = !ledOn;
    digitalWrite(LED_PIN, ledOn);
  }
}
  1. The interval is now a variable. It starts at 500 ms, and we agree that 0 means "stopped". Until now the interval was a const. A setting the user can change while the program runs has to be an ordinary variable.
  2. A short instruction for the user. Printed once at startup. A program that expects input should say what it expects. Otherwise you stare at an empty screen and don't know what to type.
  3. Serial.available(). Returns how many characters are waiting in the receive buffer. If it's 0, nobody has typed anything, and we skip the whole block. This check takes a microsecond and never waits. That's why the blinking below keeps running smoothly: we only read when something is actually there.
  4. Serial.readStringUntil('\n'). Reads characters until it reaches \n (the New Line mark) and returns them as text (a String) without the \n. It waits at most 1 second for the \n. When the line ending is set to New Line, the whole line arrives in about a millisecond, so there's no real waiting. '\n' in single quotes is one character; "stop" in double quotes is text.
  5. trim(). Removes spaces, \r and other invisible characters from both ends of the text. With "Both NL & CR", the text would be "stop\r", and "stop\r" == "stop" is false. One trim() makes the program work with every line-ending setting.
  6. A text command. If the text is exactly stop, we set the interval to 0 and switch the LED off. == works for comparing a String with text. We also switch the LED off here; otherwise it could stay on if you typed stop halfway through a blink.
  7. toInt(). Converts text into a whole number: "250" becomes 250. For decimal numbers there's toFloat(): "21.5" becomes 21.5. Both return 0 if the text isn't a number. That's why we never trust the result blindly; the next line checks it.
  8. Check the range. Only 50 to 2000 is accepted; anything else (including "abc", which became 0) gets a helpful message. The golden rule of input: never trust what a user types. A typo like 5 instead of 500 would make the LED flicker madly; a check costs two lines. %ld prints a long.
  9. The usual millis blinking. It only runs when the interval isn't 0. Reading the keyboard and blinking are two independent jobs in one loop, exactly the pattern from the previous section.

A shortcut you'll meet: Serial.parseInt() and Serial.parseFloat()

Many examples on the internet skip the text step and read a number straight from the mailbox:

if (Serial.available()) {
  float value = Serial.parseFloat();          // reads "21.5" as 21.5
  while (Serial.available()) Serial.read();   // throw away the Enter and leftovers
  Serial.println(value);
}
  1. Serial.parseFloat(). Skips anything that isn't part of a number, then reads a decimal number. Serial.parseInt() does the same for whole numbers. Handy, but it has the same weakness as toFloat(): if no number arrives within 1 second, it returns 0, and you can't tell that apart from a real 0.
  2. Empty the mailbox. Reads and throws away every character that is still waiting. parseFloat stops right after the number and leaves the \n in the buffer. Without this line, on the next pass of loop available() sees that leftover \n, parseFloat waits a second for a number that never comes, and you get a mystery 0.

Both styles work. For your own programs we recommend the readStringUntil + trim + toInt/toFloat style from the example above: it handles text commands too, and there are no leftovers to clean up.

A short introduction to interrupts

In the methods so far, the program kept asking the pin "have you been pressed?" (this is called polling). The other approach is to tell the hardware: "Whenever the pin goes from HIGH to LOW, drop whatever you're doing and run this little function." That function is called an ISR (interrupt service routine).

Example: the doorbell

Polling means walking to the front door every minute and opening it to see if anyone is there. An interrupt is the doorbell: whatever you're doing, you stop when it rings, open the door, and go back to what you were doing.

// Counting button presses with an interrupt
const int BUTTON_PIN = 27;

volatile uint32_t pressCount = 0;     // shared between the ISR and loop
volatile uint32_t lastIsrTime = 0;

void IRAM_ATTR onButton() {           // ISR: short and fast
  uint32_t now = millis();
  if (now - lastIsrTime > 200) {      // simple debouncing inside the ISR
    pressCount++;
    lastIsrTime = now;
  }
}

void setup() {
  Serial.begin(115200);
  pinMode(BUTTON_PIN, INPUT_PULLUP);
  attachInterrupt(digitalPinToInterrupt(BUTTON_PIN), onButton, FALLING);
}

void loop() {
  static uint32_t shown = 0;
  uint32_t count = pressCount;        // take a copy
  if (count != shown) {
    shown = count;
    Serial.printf("Presses: %lu\n", (unsigned long)count);
  }
  delay(1000);                        // even with a long delay, no press is lost
}
  1. The volatile keyword. Tells the compiler: "this variable can change at any moment, outside the normal flow of the program; read it from memory every time". For speed, the compiler may keep the value in a register and stop reading it from memory. Then loop would never see the change the ISR made. Every variable that both the ISR and loop work with must be volatile.
  2. IRAM_ATTR. Places the ISR in fast internal RAM (IRAM). Normal ESP32 code is read from flash memory. If an interrupt arrives right while the flash is busy (for example during a write), an ISR sitting in flash can't run and the board crashes. IRAM_ATTR removes that risk.
  3. The ISR body: counting only. If more than 200 ms have passed since the last interrupt, the counter goes up by one. Button bounce triggers the interrupt several times too, so debouncing is needed here as well. 200 ms is bigger than the earlier 30 ms because here we only see falling edges, and releasing the button can also produce falling-edge bounces.
  4. attachInterrupt. Takes three things: the pin's interrupt number (digitalPinToInterrupt), the name of the ISR function, and the kind of edge: FALLING means "from HIGH to LOW", which with a pull-up is the moment of pressing. The other options: RISING (LOW to HIGH, the moment of release) and CHANGE (both).
  5. loop only reports. It takes a copy of the counter and prints it if it has changed since the last display. static means the shown variable isn't wiped between passes of loop. Heavy work (like printing to Serial) always happens in loop, never in the ISR. Taking a copy means that if an interrupt arrives in the middle, the comparison and the print both use one fixed number.
  6. A one-second delay, on purpose. To show off the power of interrupts: even while loop is asleep for a whole second, presses get counted. The display may be up to a second late, but nothing is lost.
The strict rules of an ISR (important!)

1) An ISR must be very short: set a flag or bump a counter and return. 2) Inside an ISR, never call Serial.print, delay, Wi-Fi functions or slow sensor reads; the board may reset with a watchdog error or a Guru Meditation Error. 3) Make shared variables volatile. 4) If a shared variable is bigger than 32 bits, or you change several variables together, use a critical section (portENTER_CRITICAL) in loop; you'll see this in more advanced projects.

Coach's advice: an interrupt is not a hammer

When beginners learn about interrupts, they want to solve everything with them. For a button that a human presses, polling with millis (as in the previous section) is simpler, easier to debug and completely good enough. Save interrupts for very fast or very short events: counting pulses from a water-flow sensor, a motor encoder, or waking the board from sleep.

Analog input: the ADC takes a "ruler" reading tens of thousands of times a second

Many sensors don't give a yes/no answer; they output a voltage that changes with whatever they measure. A part of the ESP32 called the ADC (analog-to-digital converter) turns that voltage into a number.

The ESP32's ADC is 12-bit: it divides the voltage range into 212 = 4096 steps and gives you a number from 0 to 4095.

Example: a ruler with 4096 marks

Imagine a ruler that, instead of centimeters, has 4096 tiny marks. The ADC holds the voltage up against this ruler and says "it reached mark number 2048". The more marks, the finer the measurement. The Arduino Uno has a 1024-mark (10-bit) ruler; the ESP32's is four times finer.

With numbers

If we assume a range of 0 to 3.3 V, each step is roughly 3.3 ÷ 4095 ≈ 0.0008V, or 0.8 millivolts. So the number 2048 means roughly 2048 × 0.0008 ≈ 1.65V, half of 3.3 V. In practice, though, the ESP32's ADC isn't this clean; you'll see why below.

Three facts you need to know about the ESP32's ADC

1) Attenuation. Internally, the ADC can only measure voltages of about one volt directly. To read higher voltages, the ESP32 "shrinks" the input voltage before measuring it. In Arduino-ESP32 the default is ADC_11db, which gives the widest range. According to the official documentation, the measurable range on the classic ESP32 is:

AttenuationMeasurable range (classic ESP32)When to use it
ADC_0db100 to 950 mVVery small signals
ADC_2_5db100 to 1250 mVRarely used
ADC_6db150 to 1750 mVSensors with outputs up to 1.7 V
ADC_11db (default)150 to 3100 mVPotentiometers, LDRs and most jobs

You can change it with analogSetAttenuation(ADC_6db) for all pins or analogSetPinAttenuation(pin, ADC_6db) for one pin. In this lesson we leave the default alone.

2) Non-linearity at both ends of the range. The classic ESP32's ADC is "blind" near zero and near 3.3 V: voltages below roughly 0.1 to 0.15 V all read as 0, and voltages above roughly 3.1 V all read as 4095. Even in the middle of the range the relationship isn't perfectly straight.

The practical fix: use analogReadMilliVolts instead of analogRead. This function corrects the raw number using calibration data that Espressif wrote into each chip's eFuse memory at the factory, and returns millivolts directly. It's more accurate, and you don't have to do the math yourself.

3) ADC1 and ADC2; Wi-Fi is ADC2's enemy. The ESP32 has two converters. ADC2 can't be used while Wi-Fi is on, because the Wi-Fi driver itself uses it, and analogRead on ADC2 pins returns an error or a meaningless number.

ConverterPins on the DevKitCWith Wi-Fi
ADC1GPIO32, 33, 34, 35, 36, 39✅ Always works
ADC2GPIO0, 2, 4, 12, 13, 14, 15, 25, 26, 27❌ Not while Wi-Fi is on

You may notice that our button (GPIO27) and LED (GPIO4) are on the ADC2 list. That's no problem: the Wi-Fi limit only affects analog reading. digitalRead, digitalWrite and PWM work on these pins as usual, with or without Wi-Fi.

The coach's rule

Start the habit today: analog sensor = ADC1 pin (32 to 39). Even if your current project has no Wi-Fi. Three months from now you'll add Wi-Fi and spend hours wondering why your sensor suddenly broke. That's why in this lesson the potentiometer is on GPIO34 and the LDR on GPIO35.

The potentiometer: your first analog input

A potentiometer is a resistor with three legs. The two outer legs connect to the two ends of a resistive track (say 10 kΩ). The middle leg (the wiper) is a metal "brush" that slides along the track as you turn the knob. If you connect one end to 3V3 and the other to GND, the middle leg shows any voltage between 0 and 3.3 V, depending on where the knob is.

Never connect the potentiometer to 5V

If you connect an outer leg to 5V, at the end of the knob's travel 5 volts reaches GPIO34. The ESP32's pins tolerate 3.6 V at most; 5 V can permanently damage the pin or the whole chip. Always 3V3.

// Reading a potentiometer on GPIO34
const int POT_PIN = 34;       // ADC1_CH6, input only

void setup() {
  Serial.begin(115200);
  // default resolution is 12 bits (0 to 4095) and default attenuation is 11dB
}

void loop() {
  int raw = analogRead(POT_PIN);                  // 0 to 4095
  uint32_t mv = analogReadMilliVolts(POT_PIN);    // calibrated millivolts
  int percent = map(raw, 0, 4095, 0, 100);        // convert to percent

  Serial.printf("raw=%4d  mV=%4lu  percent=%3d%%\n", raw, (unsigned long)mv, percent);
  delay(200);
}
  1. GPIO34. An input-only pin from the ADC1 group. Input-only pins aren't useful for anything else; using them for analog keeps the all-purpose pins free for LEDs and buttons.
  2. setup without pinMode. We only start Serial. analogRead prepares the pin for the ADC by itself; there's no need for pinMode. The default settings (12 bits, 11 dB) are exactly what we want for 0 to 3.3 V.
  3. analogRead. Returns the raw number, 0 to 4095 (uncalibrated). For a "ratio" (for example, the knob's position as a percentage), the raw number is good enough and fast.
  4. analogReadMilliVolts. Returns the actual voltage in millivolts, using the factory calibration. When the voltage itself matters (a sensor that says "one degree per 10 millivolts", or a battery voltage), this function is more accurate. uint32_t means a positive 32-bit number, the same type the function returns.
  5. map(value, fromLow, fromHigh, toLow, toHigh). Moves a number from one range to another: 0→0, 4095→100, 2048→50. map works with whole numbers and throws away the fraction. That's fine for a percentage. Its formula is plain proportion: (raw − 0) × (100 − 0) ÷ (4095 − 0) + 0.
  6. Serial.printf. Formatted printing: %4d means a whole number in 4 character spaces, %lu means unsigned long, and %% means the % sign itself. printf prints several values neatly on one line and the columns stay lined up; that's much easier to read than several prints in a row.

Slowly turn the knob from one end to the other:

raw= 0 mV= 142 percent= 0% raw= 812 mV= 803 percent= 19% raw=2047 mV=1760 percent= 49% raw=3350 mV=2780 percent= 81% raw=4095 mV=3142 percent=100%

(Your numbers will be a little different; these are examples.) Notice that at both ends, raw gets "stuck" at 0 or 4095 while the millivolts are still above zero and below 3300. That's the non-linearity you saw above.

In Wokwi, turn the potentiometer with the mouse and watch the numbers in the Serial Monitor. (The simulator's ADC is ideal, so you won't see the non-linearity at the ends of the range there.)

Smoothing the readings (averaging)

Even if you hold the knob still, the number wobbles up and down by a few units; for example 2041, 2053, 2046. That's the ADC's natural noise. Two simple ways to calm it down:

  • Average several samples: read 16 times in a row and take the average. Random noise largely cancels itself out.
  • Exponential moving average: each time, move only 10% of the way toward the new value. Like a heavy needle on a gauge that moves slowly.
// Averaging: 16 samples, one calm number
const int POT_PIN = 34;
const int SAMPLES = 16;

int readAverage(int pin) {
  long sum = 0;
  for (int i = 0; i < SAMPLES; i++) {
    sum += analogRead(pin);
    delayMicroseconds(100);      // a short gap between samples
  }
  return sum / SAMPLES;
}

float smoothed = 0;             // for the exponential moving average

void setup() {
  Serial.begin(115200);
  smoothed = analogRead(POT_PIN);
}

void loop() {
  int avg = readAverage(POT_PIN);
  smoothed = smoothed + 0.1 * (avg - smoothed);   // 10% toward the new value
  Serial.printf("raw:%d avg:%d smooth:%.0f\n", analogRead(POT_PIN), avg, smoothed);
  delay(50);
}
  1. Our own function. int readAverage(int pin) means a function that takes a pin number and returns a whole number. We put code that's needed in several places into a function so it isn't repeated. You can use this same function for the LDR or any other analog sensor.
  2. A for loop: add up 16 times. for (int i = 0; i < 16; i++) means "start i at zero, repeat while it's less than 16, and add one each time". Each pass adds one sample to sum. sum is a long because 16 × 4095 = 65520 is bigger than the small int range on some boards; it's a good habit to use a bigger type for sums. The 100-microsecond gap makes the samples a little more independent of each other.
  3. Divide and return. The sum divided by 16 = the average. The whole function takes about 2 milliseconds; perfectly acceptable for a potentiometer or a light level.
  4. The moving average's starting value. In setup, we fill smoothed with the first reading. If it started at zero, for the first few seconds it would slowly "creep up" from zero and show a wrong number.
  5. The exponential moving average formula. Work out the gap between the new value and the smoothed value, and add 10% of it. Make 0.1 bigger (say 0.3) and it becomes faster and noisier; make it smaller (0.05) and it becomes calmer and slower. It's a tuning knob between "speed" and "calm".
  6. Comparing three numbers. Prints the raw, averaged and smoothed values side by side; for example raw:2047 avg:2051 smooth:2049. %.0f means a decimal number with no digits after the point. We chose the name:number format (with a colon, separated by spaces) on purpose, because the Serial Plotter in Arduino IDE 2 understands exactly this format. Close the Serial Monitor and open Tools › Serial Plotter to see three colored lines; the raw line is jagged and the smooth line is soft. (With = instead of :, the plotter won't recognize the numbers.)

The LDR and the voltage divider: measuring light

An LDR (light-dependent resistor) is a part whose resistance changes with light: low in bright light (say 1 kΩ) and very high in the dark (up to about one megaohm). But the ADC reads voltage, not resistance. So we have to turn the change in resistance into a change in voltage. The tool for this is the "voltage divider": we put the LDR in series with a fixed resistor.

The voltage divider formula, step by step with numbers

Current flows from 3V3 through both resistors to GND. The voltage at the middle point is the share that drops across the LDR: Vout = Vin × R_LDR ÷ (R_fixed + R_LDR).

In room light the LDR is about 10 kΩ: 3.3 × 10k ÷ (10k + 10k) = 3.3 × 0.5 = 1.65V. Right in the middle of the range.

In partial darkness the LDR is about 50 kΩ: 3.3 × 50k ÷ 60k = 2.75V. In bright light, 1 kΩ: 3.3 × 1k ÷ 11k = 0.30V.

Why a 10 kΩ fixed resistor?

A voltage divider is most sensitive when its two resistors are close in value; that's where the smallest change in the LDR makes the biggest change in voltage. A GL5528's resistance in ordinary room light is about 10 to 20 kΩ, so 10 kΩ gives the best sensitivity exactly in the range that matters for a night light (the change from room light to darkness). If the fixed resistor were 1 MΩ, Vout would stay close to zero in all normal lighting and the differences would get lost.

Want brighter = bigger number?

Swap the LDR and the fixed resistor (LDR on top to 3V3, resistor at the bottom to GND). Then the relationship is reversed. We chose this arrangement because the LDR module in the Wokwi simulator is built exactly this way too (a 10 kΩ resistor to VCC and the LDR to GND), and we want the code to behave the same in both places.

The boundary problem: why one threshold isn't enough (hysteresis)

The simplest night light: "if the voltage is above 2400 millivolts, LED on, otherwise off". The problem? At dusk, when the light sits right near the boundary, ADC noise pushes the number up and down between 2398 and 2403, and the LED flickers like a broken lamp.

The fix is "hysteresis": two separate thresholds. Turn on at 2600 millivolts, but turn off only when it drops back below 2200. The gap between the two (400 millivolts) is much bigger than the noise, so there's no more flickering.

Example: a heater's thermostat

A good thermostat turns the heater on at 19 degrees and off at 22 degrees, not both at 20 degrees. Otherwise the heater would switch on and off every few seconds and wear out quickly. Hysteresis is in every control device around you.

Project: an automatic night light

// Automatic night light with an LDR and hysteresis
const int LDR_PIN = 35;               // middle of the voltage divider (ADC1_CH7)
const int LED_PIN = 4;
const uint32_t DARK_ON_MV   = 2600;   // above this: it's dark, turn on
const uint32_t LIGHT_OFF_MV = 2200;   // below this: it's light, turn off

bool lampOn = false;

uint32_t readLdrMv() {
  uint32_t sum = 0;
  for (int i = 0; i < 8; i++) sum += analogReadMilliVolts(LDR_PIN);
  return sum / 8;                     // average of 8 samples
}

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
}

void loop() {
  uint32_t mv = readLdrMv();

  if (!lampOn && mv > DARK_ON_MV) {           // it got dark
    lampOn = true;
    digitalWrite(LED_PIN, HIGH);
  } else if (lampOn && mv < LIGHT_OFF_MV) {   // it got light enough
    lampOn = false;
    digitalWrite(LED_PIN, LOW);
  }

  Serial.printf("LDR=%lu mV  lamp=%s\n", (unsigned long)mv, lampOn ? "ON" : "OFF");
  delay(200);
}
  1. GPIO35 for the LDR. Another ADC1 pin. We chose ADC1 so nothing breaks when you add Wi-Fi (for example, to report the light level to your phone).
  2. The two hysteresis thresholds. On at 2600 and off at 2200 millivolts. With a 10 kΩ resistor, 2600 mV means the LDR is about 37 kΩ (twilight), and 2200 mV means about 20 kΩ. Tune these numbers later to the real values in your own room: first watch the Serial Monitor in the light and in the dark, then set the thresholds.
  3. Remembering the lamp's state. Hysteresis is impossible without memory: the decision depends on whether the lamp is currently on or off.
  4. A reading function with averaging. Reads the millivolts 8 times and takes the average. Here the for loop has a one-line body and doesn't need curly braces. Averaging reduces the noise and hysteresis handles the rest of the flicker. Two layers of protection. We used millivolts so the thresholds have a physical meaning and are the same on every board.
  5. The turn-on condition. Only if the lamp is off and the voltage has gone above 2600. The !lampOn condition means this branch isn't even considered while the lamp is on. Each branch is for one state only.
  6. The turn-off condition. else if: only if the lamp is on and the voltage has dropped below 2200. Between 2200 and 2600 neither branch runs, and the lamp keeps its previous state. This "dead zone" is the heart of hysteresis.
  7. Report. Prints the voltage and the lamp's state, 5 times a second. Light changes slowly; 200 milliseconds is more than fast enough for a night light. (A delay is fine here because there's nothing else to do; if you add a button, switch to millis.)
LDR=1638 mV lamp=OFF LDR=2107 mV lamp=OFF LDR=2615 mV lamp=ON LDR=2580 mV lamp=ON LDR=2390 mV lamp=ON LDR=2150 mV lamp=OFF

Notice: on lines 4 and 5 the voltage dropped below 2600, but the lamp stayed on. It only turned off once the voltage fell below 2200. That means hysteresis is working.

Wokwi has no bare LDR; instead it has a "light sensor module" that contains exactly this voltage divider (LDR + 10 kΩ resistor), with its output on the AO pin. We don't need the DO pin for now. During the simulation, click the module and use the slider to raise and lower the light level (lux). With Wokwi's default settings, the lamp turns on below about 15 lux and off above about 40 lux.

Ready-made LDR modules (with a blue potentiometer)

Cheap light sensor modules usually have four pins (VCC, GND, DO, AO) and a small blue potentiometer. AO is the voltage divider output. DO is the digital output of a built-in comparator whose threshold you set with the potentiometer on the module (with no programmable hysteresis). If you have one of these modules, connect AO to GPIO35, make sure VCC goes to 3V3 (not 5V), and don't add the external 10 kΩ resistor; the module already has it. On most of these modules "darker = bigger number" too, but some three-pin modules (for example the KY-018) are wired the other way round. So run the code first, cover the sensor with your hand and see whether the millivolts go up or down. If they go down, swap the > and < in the code and adjust the two thresholds to match the numbers you saw.

Full answer with explanation 
const int UP_PIN = 27;                  // button 1: count up
const int DOWN_PIN = 33;                // button 2: count down
const unsigned long DEBOUNCE_MS = 30;

int count = 0;

// button 1 memory
int stableState1 = HIGH, lastReading1 = HIGH;
unsigned long lastChangeTime1 = 0;
// button 2 memory
int stableState2 = HIGH, lastReading2 = HIGH;
unsigned long lastChangeTime2 = 0;

void setup() {
  Serial.begin(115200);
  pinMode(UP_PIN, INPUT_PULLUP);
  pinMode(DOWN_PIN, INPUT_PULLUP);
  Serial.println("Count: 0");
}

void loop() {
  unsigned long now = millis();

  // button 1: up
  int reading1 = digitalRead(UP_PIN);
  if (reading1 != lastReading1) { lastChangeTime1 = now; lastReading1 = reading1; }
  if (now - lastChangeTime1 > DEBOUNCE_MS && reading1 != stableState1) {
    stableState1 = reading1;
    if (stableState1 == LOW) {
      count++;
      Serial.printf("Count: %d\n", count);
    }
  }

  // button 2: down, never below zero
  int reading2 = digitalRead(DOWN_PIN);
  if (reading2 != lastReading2) { lastChangeTime2 = now; lastReading2 = reading2; }
  if (now - lastChangeTime2 > DEBOUNCE_MS && reading2 != stableState2) {
    stableState2 = reading2;
    if (stableState2 == LOW) {
      if (count > 0) count--;
      Serial.printf("Count: %d\n", count);
    }
  }
}
  1. Two buttons, two pins. Button 1 on GPIO27 (as in the whole lesson) and button 2 on GPIO33, both to GND. In the course pin plan the second button is always GPIO33, so this circuit can stay on your breadboard and you'll reuse it later.
  2. Two separate sets of variables. Each button has its own three debounce variables; only a 1 or a 2 was added to the end of the names. If both buttons shared one lastChangeTime, the bounce of one button would reset the other button's timer and presses would get lost.
  3. The starting number. The first value is printed once in setup. That way you see straight away that the program is running and counting starts from 0.
  4. Button 1, debounced. The same block as Toggle_Debounce; instead of toggling the LED it does count++ and prints. Only the moment of pressing (LOW) counts; holding the button or releasing it adds nothing.
  5. Button 2 and the zero limit. A copy of the same block with the number-2 variables; it only subtracts when the number is above zero. We print the number even when it didn't change, so you can see the press was noticed but the "don't go below zero" rule stopped it.

The green button (GPIO27) counts up and the red button (GPIO33) counts down. Click each button in the simulator and watch the Serial Monitor.

Exercise 2: blink speed from a potentiometer

Use a potentiometer on GPIO34 to set the blink speed of the LED on GPIO4, anywhere from 50 to 1000 milliseconds. Write it without delay (using millis) so it still works if you add a button later.

Hint

Calculate unsigned long interval = map(analogRead(34), 0, 4095, 50, 1000); on every pass of loop, and use it in the millis condition instead of a fixed number.

What should you see?

This program prints nothing to the Serial Monitor; watch the LED instead:

  • Knob at one end (ADC 0): a 50 ms interval, so 10 blinks per second; the LED almost looks like it is flickering.
  • Knob at the other end (4095): a 1000 ms interval; one second on, one second off. In 10 seconds it lights up exactly 5 times.
  • Knob in the middle (about 2048): map gives 525 ms, a little more than half a second.
  • In the middle of a slow blink, turn the knob toward fast: the change shows immediately; it doesn't wait for the old blink to finish.
Full answer with explanation 
const int POT_PIN = 34;
const int LED_PIN = 4;
unsigned long lastToggle = 0;
bool ledOn = false;

void setup() {
  pinMode(LED_PIN, OUTPUT);
}

void loop() {
  unsigned long interval = map(analogRead(POT_PIN), 0, 4095, 50, 1000);
  unsigned long now = millis();
  if (now - lastToggle >= interval) {
    lastToggle = now;
    ledOn = !ledOn;
    digitalWrite(LED_PIN, ledOn);
  }
}
  1. A variable interval. On every pass of loop, the potentiometer's number is mapped to the range 50 to 1000 milliseconds. Because it's recalculated on every pass, turning the knob takes effect immediately; even in the middle of a long blink.
  2. The same millis pattern. Only the variable interval replaces the INTERVAL constant. Once you've learned the millis pattern properly, the only things that ever change are "what" and "how often".

Turn the potentiometer knob in the simulator and watch the blink speed of the LED change.

Exercise 3: a night light with a manual button

Add a button (GPIO27) to the night light project that cycles through three modes in order: "automatic" → "always on" → "always off" → "automatic". Print the current mode to the Serial Monitor. The program must not contain any delay.

Hint

Create a variable int mode = 0;. On each (debounced) press: mode = (mode + 1) % 3;. The % sign is the remainder of a division, and it makes the value go back to 0 after 2. Read the LDR every 200 ms using millis.

What should you see?

A sample output (the millivolt numbers depend on your room's light): we covered the LDR with a hand, pressed the button three times, then uncovered it.

Mode: AUTO
Auto: dark (2710 mV) -> lamp ON
Mode: ALWAYS ON
Mode: ALWAYS OFF
Mode: AUTO
Auto: light (2140 mV) -> lamp OFF
  • Each button press moves the mode exactly one step: AUTO → ALWAYS ON → ALWAYS OFF → AUTO.
  • In ALWAYS ON and ALWAYS OFF, covering the LDR has no effect on the LED, and no "Auto" message is printed.
  • When you come back to AUTO, the LED matches the room's light straight away (on in the dark, off in the light).
  • The button always responds instantly, even though the LDR is only read every 200 ms. That means no delay is in the way.
Full answer with explanation 
const int LDR_PIN = 35;                 // middle of the LDR voltage divider
const int LED_PIN = 4;
const int BUTTON_PIN = 27;
const uint32_t DARK_ON_MV   = 2600;     // above this: dark
const uint32_t LIGHT_OFF_MV = 2200;     // below this: light
const unsigned long DEBOUNCE_MS = 30;

const char *MODE_NAMES[] = {"AUTO", "ALWAYS ON", "ALWAYS OFF"};
int mode = 0;                           // 0 = auto, 1 = always on, 2 = always off
bool lampOn = false;                    // the automatic (hysteresis) decision
unsigned long lastLdrRead = 0;

int stableState = HIGH, lastReading = HIGH;
unsigned long lastChangeTime = 0;

uint32_t readLdrMv() {
  uint32_t sum = 0;
  for (int i = 0; i < 8; i++) sum += analogReadMilliVolts(LDR_PIN);
  return sum / 8;
}

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  pinMode(BUTTON_PIN, INPUT_PULLUP);
  Serial.println("Mode: AUTO");
}

void loop() {
  unsigned long now = millis();

  // job 1: the button changes the mode
  int reading = digitalRead(BUTTON_PIN);
  if (reading != lastReading) { lastChangeTime = now; lastReading = reading; }
  if (now - lastChangeTime > DEBOUNCE_MS && reading != stableState) {
    stableState = reading;
    if (stableState == LOW) {
      mode = (mode + 1) % 3;
      Serial.printf("Mode: %s\n", MODE_NAMES[mode]);
    }
  }

  // job 2: read the LDR every 200 ms (hysteresis, as in Night_Light)
  if (now - lastLdrRead >= 200) {
    lastLdrRead = now;
    uint32_t mv = readLdrMv();
    if (!lampOn && mv > DARK_ON_MV) {
      lampOn = true;
      if (mode == 0) Serial.printf("Auto: dark (%lu mV) -> lamp ON\n", (unsigned long)mv);
    } else if (lampOn && mv < LIGHT_OFF_MV) {
      lampOn = false;
      if (mode == 0) Serial.printf("Auto: light (%lu mV) -> lamp OFF\n", (unsigned long)mv);
    }
  }

  // job 3: the mode decides what the LED does
  bool ledShouldBeOn;
  if (mode == 0)      ledShouldBeOn = lampOn;
  else if (mode == 1) ledShouldBeOn = true;
  else                ledShouldBeOn = false;
  digitalWrite(LED_PIN, ledShouldBeOn ? HIGH : LOW);
}
  1. Pins and thresholds. The same numbers as the Night_Light program, and the same button on GPIO27. The exercise is built on the same night-light circuit; only the button is added, so no wire moves.
  2. The mode names and the mode itself. MODE_NAMES is a list (an array) of three pieces of text; MODE_NAMES[0] is the first ("AUTO") and MODE_NAMES[2] the third. mode is the number of the current mode. With this list, printing the mode's name takes one line and you don't need three ifs for three texts. In C++ counting starts at 0.
  3. The automatic decision, separate from the output. lampOn only says "if we were in automatic mode, should the lamp be on?". It's kept up to date in every mode, so when you go back to AUTO the LED matches the room's current light straight away.
  4. Job 1: the button. Debounced as in Toggle_Debounce; each press does mode = (mode + 1) % 3 and prints the mode name. % makes the value go back to 0 after 2: 0 → 1 → 2 → 0. In printf, %s is the placeholder for a piece of text.
  5. Job 2: the LDR every 200 ms. Instead of the original program's delay(200), the millis pattern; inside it, the same night-light hysteresis. If delay(200) had stayed, short button presses could get lost. The "Auto" message is only printed in automatic mode, so the Serial Monitor stays tidy.
  6. Job 3: the final decision. In AUTO the output is just lampOn; in the other two modes it is fixed. One place decides and one place writes to the pin, so no two parts of the program fight over the LED.

The same night-light circuit plus the button on GPIO27. Click the light sensor module and use the slider to raise and lower the light (lux); change the mode with the green button.

The lesson in three lines

A digital input without a pull-up floats; INPUT_PULLUP + a button to GND + reversed logic, plus debouncing with millis, make a button reliable. millis() with the "subtract and compare" pattern instead of delay lets several jobs run at once; interrupts are only for very fast events. The 12-bit ADC (0 to 4095) with 11 dB attenuation reads about 0.15 to 3.1 V; use ADC1, analogReadMilliVolts is more accurate, and with a voltage divider and hysteresis you can turn any resistive sensor, like an LDR, into a stable decision.
