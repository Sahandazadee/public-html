Over-the-air updates (OTA), programming without a cable

You've installed your device inside a drop ceiling to control the lights. A week later you find a bug. Without OTA you have to fetch a ladder, open the ceiling, and carry your laptop up there with a USB cable. With OTA (Over-The-Air) you upload the new program from your desk, over the same Wi-Fi.

How does OTA work behind the scenes? (partitions)

The ESP32's 4 MB flash memory is divided into several "partitions", like a hard disk. You choose the map of this division in the Tools › Partition Scheme menu. The key idea behind OTA is this: for a safe update there must be two program slots (app0 and app1). The new program is written into the empty slot while the current program keeps running. Only when the download has finished completely and correctly does a small "note" (the otadata partition) change to say "boot from the other slot next time". If the power goes out in the middle of an update, the old program is still untouched.

A common trap: Huge APP and OTA

When your program grows (Wi-Fi + Bluetooth + HTTPS), you get the Sketch too big error, and many tutorials say "choose Huge APP". That fixes the error but kills OTA for good, because it has only one program slot. For a device that needs OTA, choose Minimal SPIFFS: programs up to 1.9 MB with OTA intact. The only cost is that file space shrinks to 128 KB, which is enough for a settings page. Remember that a Partition Scheme change only takes effect with a USB upload.

Method one: ArduinoOTA, uploading from the Arduino IDE itself

The ArduinoOTA library is built into the core. It "announces" the board on the network (with mDNS, as in lesson 4.2) and waits for a new program on port 3232. First, extend the secrets.h file from lesson 4.1; this version holds all the passwords for this lesson:

#pragma once
#define WIFI_SSID "MyHomeWiFi"
#define WIFI_PASS "my-strong-password"
#define OTA_PASS  "ota-pass-2026"      // password for wireless updates
#define WEB_USER  "admin"              // username for the web update page
#define WEB_PASS  "change-me-now"      // password for the web update page
#define NTFY_TOPIC "home-alert-7f3k9q" // ntfy topic name: unguessable
  1. The Wi-Fi password. The same two lines as in lesson 4.1. One secrets file for every program in lessons 5.5 and 5.6; each program only uses the lines it needs.
  2. The OTA password. Anyone who doesn't know this password can't change the board's program. OTA without a password means anyone connected to your Wi-Fi (a guest, a neighbor who knows the password, an infected phone) can put any program they like on your device.
  3. Username and password for the web update page. For method two, later in this lesson. Kept separate from the OTA password, so if one leaks the other stays safe.
  4. The ntfy topic name. For the phone-alert section in lesson 5.6. We add it now, so this one file serves both lessons. On ntfy.sh the topic name itself acts as the password, so it belongs in secrets.h too.
#include <WiFi.h>
#include <ArduinoOTA.h>
#include "secrets.h"             // WIFI_SSID, WIFI_PASS, OTA_PASS
#ifndef OTA_PASS                 // if it's missing from secrets.h, warn
#warning "OTA_PASS is not defined in secrets.h"
#define OTA_PASS "change-me"
#endif

const int LED_PIN = 4;

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) {   // kept simple; robust version in lesson 4.1
    delay(500);
    Serial.print(".");
  }
  Serial.printf("\nIP: %s\n", WiFi.localIP().toString().c_str());

  ArduinoOTA.setHostname("esp32-kitchen");  // name shown in the Port menu
  ArduinoOTA.setPassword(OTA_PASS);         // without it, anyone can flash
  ArduinoOTA
    .onStart([]() { Serial.println("OTA start"); })
    .onEnd([]() { Serial.println("\nOTA done, rebooting"); })
    .onProgress([](unsigned int done, unsigned int total) {
      Serial.printf("OTA %u%%\r", done * 100 / total);
    })
    .onError([](ota_error_t err) { Serial.printf("OTA error %u\n", err); });
  ArduinoOTA.begin();                       // from here on it waits for updates
  Serial.println("OTA ready");
}

void loop() {
  ArduinoOTA.handle();                      // every pass: "any update?"
  static unsigned long last = 0;            // blink without delay (lesson 3.1)
  static bool on = false;
  if (millis() - last >= 500) {
    last = millis();
    on = !on;
    digitalWrite(LED_PIN, on);
  }
}
  1. The ArduinoOTA library. Part of the core; nothing to install. We also need WiFi.h, because OTA works over the network.
  2. The #ifndef guard. If you haven't written the OTA_PASS line in secrets.h, the compiler shows an orange warning and the temporary password change-me is used. The program still compiles with the old secrets.h from lesson 4.1, but the warning reminds you to set a real password. Never ignore compiler warnings.
  3. Connecting to Wi-Fi. A simple version, to keep the example short. In a real device use the robust version from lesson 4.1, with a time limit and automatic reconnection. OTA doesn't work without Wi-Fi.
  4. setHostname. The board's name on the network; the name you see in the Port menu. If you don't give it a name, it gets something like esp32-a0b1c2d3e4f5 (based on the MAC address). When you have three devices at home, "esp32-kitchen" is much better. Use only lowercase English letters, digits and hyphens.
  5. setPassword. The OTA password. The Arduino IDE asks you for it when you upload. In core 3.3, OTA authentication uses SHA-256 (older versions used MD5, which is no longer considered secure). If you don't want the plain password inside the program, use setPasswordHash with the SHA-256 hash of the password.
  6. Events (callbacks). Four small functions for start, end, progress and error. []() { ... } is a "nameless function" (a lambda) in C++ (see the C++ corner in lesson 5.4). In a real project, use onStart to switch off motors and relays and close files; a few seconds later the board resets, and nothing should be left half-done.
  7. ArduinoOTA.begin. From here on the board announces itself on the network and waits for an update. It must be called after Wi-Fi has connected.
  8. ArduinoOTA.handle on every pass of loop. Checks whether anyone wants to send an update. If loop gets stuck somewhere in a long delay or a busy-wait loop, OTA doesn't answer and the IDE reports "No response from device". That's why we wrote the LED blink with millis(), not delay.

Step by step: your first wireless update

  1. The first time must be over USB. The board doesn't have the OTA code yet, so it can't receive a program over the air. Upload the program above over USB as usual. (The Partition Scheme must include OTA; Default is fine.)
  2. Check the Serial Monitor. You should see the IP address and OTA ready.
  3. Computer and board on the same network. Your laptop must be connected to the same router (not your phone's hotspot, and not the router's guest network, which isolates devices from each other).
  4. Pick the network port. Unplug the USB cable (or leave it in) and open the Tools › Port menu. Under the Network ports heading, something like esp32-kitchen at 192.168.1.50 appears. If it isn't there, wait 30 seconds and open the menu again; the IDE scans the network every few seconds.
  5. Make a small change (for example, change 500 to 100 so the LED blinks faster) and press Upload. The IDE asks for the password: your OTA_PASS.
  6. The result. You'll see the progress bar Uploading: [==== ] 45%. Then the board resets by itself and the LED blinks at the new speed. There is no network Serial Monitor; to see messages you still need the cable (or send your logs over the web or MQTT).
Important: every new program must include the OTA code too

If you send over the air a program that has no ArduinoOTA.begin and handle (or that gets stuck in setup, or has the wrong Wi-Fi details), that was your last wireless update! Next time you'll need the ladder and the cable. Make it a habit: put the OTA code in every program before anything else, and test it on a board on your desk before sending it to the device in the ceiling.

Method two: an update page in the browser (Update + WebServer)

ArduinoOTA only works from inside the Arduino IDE, on the same network. Sometimes you want to give the program file to someone else (a customer, for example) so they can update without installing the Arduino IDE. The solution: a web page on the ESP32 itself that accepts a .bin file. The Update library (built into the core) does the writing into the second partition.

Creating the .bin file

  1. In the Arduino IDE, choose Sketch › Export Compiled Binary (shortcut Alt+Ctrl+S).
  2. After compiling, a build folder appears in the project folder, and inside it a folder named after the board (for example esp32.esp32.esp32). Open it with Sketch › Show Sketch Folder.
  3. You'll see several .bin files. The right one is the file whose name is just ProjectName.ino.bin. Don't send the .bootloader.bin, .partitions.bin and .merged.bin files over OTA; those are for a full flash with the cable.
#include <WiFi.h>
#include <WebServer.h>
#include <Update.h>
#include "secrets.h"
#ifndef WEB_USER
#warning "WEB_USER/WEB_PASS are not defined in secrets.h"
#define WEB_USER "admin"
#define WEB_PASS "change-me"
#endif

WebServer server(80);

const char UPDATE_PAGE[] PROGMEM = R"HTML(
<!doctype html><meta charset="utf-8">
<h3>Firmware update</h3>
<form method="POST" action="/update" enctype="multipart/form-data">
  <input type="file" name="firmware" accept=".bin">
  <button>Upload</button>
</form>)HTML";

void handlePage() {
  if (!server.authenticate(WEB_USER, WEB_PASS)) {
    return server.requestAuthentication();          // username/password prompt
  }
  server.send(200, "text/html", UPDATE_PAGE);
}

void handleUploadDone() {                           // after the upload finishes
  if (!server.authenticate(WEB_USER, WEB_PASS)) {
    return server.requestAuthentication();
  }
  bool ok = !Update.hasError();
  server.send(200, "text/plain", ok ? "OK, rebooting..." : Update.errorString());
  if (ok) {
    delay(500);
    ESP.restart();                                  // come back up with the new program
  }
}

void handleUploadChunk() {                          // for every chunk of the file
  if (!server.authenticate(WEB_USER, WEB_PASS)) return;
  HTTPUpload &up = server.upload();
  if (up.status == UPLOAD_FILE_START) {
    Serial.printf("Update: %s\n", up.filename.c_str());
    if (!Update.begin(UPDATE_SIZE_UNKNOWN)) Update.printError(Serial);
  } else if (up.status == UPLOAD_FILE_WRITE) {
    if (Update.write(up.buf, up.currentSize) != up.currentSize) {
      Update.printError(Serial);
    }
  } else if (up.status == UPLOAD_FILE_END) {
    if (Update.end(true)) Serial.printf("Done: %u bytes\n", up.totalSize);
    else Update.printError(Serial);
  }
}

void setup() {
  Serial.begin(115200);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) delay(500);
  Serial.printf("Open http://%s/\n", WiFi.localIP().toString().c_str());
  server.on("/", HTTP_GET, handlePage);
  server.on("/update", HTTP_POST, handleUploadDone, handleUploadChunk);
  server.begin();
}

void loop() {
  server.handleClient();
}
  1. The Update library. A simple interface for writing a new program into the empty OTA partition. ArduinoOTA itself uses this same library behind the scenes. We've only changed how the file arrives (the browser instead of the IDE).
  2. An HTML page with an upload form. enctype="multipart/form-data" means "this form sends a file". R"HTML( ... )HTML" is the same raw string from lesson 4.2. Without enctype, the browser sends only the file's name, not its contents. accept=".bin" only limits the file picker to bin files (it's a convenience, not security).
  3. A password-protected main page. server.authenticate checks the username and password; if they're wrong, requestAuthentication opens the browser's login prompt. An update page without a password means anyone on the network can take over your device. This simple authentication (Basic/Digest) is not encrypted over HTTP, so use it only on a trusted home network, and never expose this page to the internet with port forwarding.
  4. server.on with two functions. For file uploads, WebServer wants two functions: handleUploadChunk, which is called for every chunk of the file, and handleUploadDone, which sends the reply to the browser after the whole upload is finished. The bin file is around one megabyte and the ESP32's free RAM is about 300 kilobytes. So you can't receive the whole file into RAM first; it has to arrive in chunks (a few kilobytes at a time) and be written to flash right away.
  5. Start: Update.begin. On the first chunk, the empty OTA partition is prepared (erased). UPDATE_SIZE_UNKNOWN means "I don't know the size; keep writing while there is room". If there is no OTA partition (Huge APP), you get an error right here, and Update.printError prints the reason on Serial.
  6. Writing each chunk. Update.write writes the chunk to flash and returns the number of bytes written. If that number doesn't match the chunk size, the write failed. Check, don't guess.
  7. Finish: Update.end(true). Checks that the file is complete and valid (the program's header and checksum), and if it is, changes otadata so the next boot uses the new program. If you sent the wrong file (say a photo, or the merged file), it is rejected right here and the previous program stays intact. That is the safety of having two partitions.
  8. Reply and reset. If there was no error, it sends "OK" to the browser, waits half a second for the message to get there, and calls ESP.restart(). The new program only runs after a reset. Without the delay, the board might reset before the reply reaches the browser, and you'd think the update had failed.

To use it: open the board's IP address in a browser, enter the username and password, pick the .ino.bin file and press Upload. About 10 to 20 seconds later you'll see "OK, rebooting...".

Shortcut: the ready-made HTTPUpdateServer library

Core 3.x also has a library called HTTPUpdateServer that adds this same page to your WebServer in two lines. We deliberately wrote the manual version so you understand what happens behind the scenes. In online tutorials you'll also see libraries such as ElegantOTA; its older versions (AsyncElegantOTA) are deprecated.

Pulling updates from a server: HTTPUpdate

Both methods above "push": you send the program to the board. With several devices, "pull" is handier: each device downloads a new .bin file from a web address when you tell it to (a button, an MQTT message, or once a day). The built-in HTTPUpdate library does it in one call. To try it, put the .ino.bin file in a folder on your computer and run python -m http.server 8000 in that folder. On success the board restarts by itself with the new program. For a real product, use HTTPS (lesson 5.6) and pass the current version as the third input of update(), so the server can answer "no update" instead of sending the same file again and again.

#include <HTTPUpdate.h>
// ... after Wi-Fi has connected:
WiFiClient client;
t_httpUpdate_return r = httpUpdate.update(client, "http://192.168.1.10:8000/firmware.bin");
if (r == HTTP_UPDATE_FAILED) {
  Serial.printf("Update failed: %s\n", httpUpdate.getLastErrorString().c_str());
}

Automatic rollback: what if the new program is broken?

Suppose the new program has a bug that stops it from connecting to Wi-Fi. Now OTA doesn't work either! ESP-IDF has "automatic rollback" for exactly this case, and it's enabled in Arduino core 3 too (CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y). The idea: after its first boot, a new program is "on probation". If it declares "I'm healthy", it stays; if it resets before that, or says "I'm broken", the bootloader goes back to the previous program.

By default the Arduino core declares the new program "healthy" immediately at startup. To make that decision yourself:

#include <WiFi.h>
#include "esp_ota_ops.h"
#include "secrets.h"

// Tell the core: "I'll confirm the new program myself"
extern "C" bool verifyRollbackLater() {
  return true;
}

void setup() {
  Serial.begin(115200);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  unsigned long t0 = millis();
  while (WiFi.status() != WL_CONNECTED && millis() - t0 < 30000) delay(500);

  if (WiFi.status() == WL_CONNECTED) {
    esp_ota_mark_app_valid_cancel_rollback();   // "this version is healthy"
    Serial.println("New firmware confirmed");
  } else {
    Serial.println("No Wi-Fi: rolling back");
    esp_ota_mark_app_invalid_rollback_and_reboot();  // go back to the previous version
  }
}

void loop() {
  delay(1000);
}
  1. verifyRollbackLater. The core defines this function as "weak", returning false. When you write your own version that returns true, yours replaces it and the core skips the automatic confirmation. The extern "C" is essential: the core's function is defined in a C file, and without it the C++ compiler changes your function's name (name mangling); the program compiles without any error, but your version is never called. This "weak function" pattern is common in the Arduino core: a way to change internal behavior without touching the core's files.
  2. Confirming. If Wi-Fi connects within 30 seconds, esp_ota_mark_app_valid_cancel_rollback() says "this version stays". Choose the health test yourself: connecting to Wi-Fi, getting an answer from the MQTT server, or whatever is needed for OTA to keep working.
  3. Rejecting. esp_ota_mark_app_invalid_rollback_and_reboot() resets the board, and the bootloader runs the previous version. If the program was uploaded over USB, there is no valid previous version and this function just returns an error; so on your desk it does nothing. This mechanism only makes sense after an OTA update.
Take OTA security seriously

OTA means "a way to replace the device's brain remotely". If that way is open, an attacker can use it too. The minimum: 1) always set a password; 2) never expose port 3232 or the update page to the internet with port forwarding; 3) for a device you sell to others, study signed OTA (the SignedOTA example in the ArduinoOTA library) and Secure Boot, so that only programs signed with your own private key are accepted.

OTA and uploading LittleFS files are not simulated in Wokwi (Wokwi puts the program straight into the simulator's memory and has no network port for the IDE). Practice these two on a real board.

LittleFS, a small flash drive inside the ESP32

In lesson 4.2 we wrote the web page as one big string inside the C++ code. It worked, but every tiny change to a button's color meant compiling and uploading the whole program again. And if you want to keep settings (such as the user's chosen city) or a log of several days, variables are wiped by every reset. LittleFS is a "file system": it gives you part of the flash memory (the spiffs partition in the figure above) as a small flash drive with folders and files. Files survive power loss, and even uploading a new program (over USB or OTA).

An everyday example

Your program is like the cook, and RAM is like the cook's worktable: fast, but wiped clean when the restaurant closes (the power goes off). LittleFS is like the notebook shelf in the kitchen: the recipes (the web page) and the account book (the log) stay there, even when the cook is replaced (a new program).

Why LittleFS and not SPIFFS?

SPIFFS is the ESP32's older file system. It has no real folders and is more easily damaged if the power fails mid-write; Espressif no longer develops it. LittleFS was designed for microcontrollers: it is power-loss resilient, and it spreads writes across the whole memory so that no single spot of the flash wears out early (wear leveling). The partition is still called "spiffs", but LittleFS uses it without any trouble.

Writing, appending, reading and listing files

#include <LittleFS.h>

void listFiles(const char *dir) {
  File root = LittleFS.open(dir);
  File f = root.openNextFile();
  while (f) {
    Serial.printf("  %-20s %6u bytes\n", f.name(), (unsigned)f.size());
    f = root.openNextFile();
  }
}

void setup() {
  Serial.begin(115200);
  delay(500);
  if (!LittleFS.begin(true)) {               // true = format it if it's broken
    Serial.println("LittleFS mount failed");
    return;
  }
  Serial.printf("FS: %u of %u bytes used\n",
                (unsigned)LittleFS.usedBytes(), (unsigned)LittleFS.totalBytes());

  File f = LittleFS.open("/note.txt", "w");  // w = create, or overwrite from the start
  f.println("Hello from ESP32!");
  f.close();                                 // closing = saved for sure

  f = LittleFS.open("/log.txt", "a");        // a = append to the end of the file
  f.printf("boot at %lu ms\n", millis());
  f.close();

  f = LittleFS.open("/log.txt", "r");        // r = read only
  Serial.println("--- log.txt ---");
  while (f.available()) {
    Serial.write(f.read());
  }
  f.close();

  Serial.println("--- files ---");
  listFiles("/");
}

void loop() {}
  1. The LittleFS library. Built into the core. No separate install needed. Don't install old libraries such as "LITTLEFS by lorol"; they were for core 1.x and conflict with core 3.
  2. LittleFS.begin(true). "Mounts" the file system. The true input means "if you can't mount it (for example the first time, when it isn't formatted yet), format it". The first time you run on a new board, the partition is empty and unformatted, and without true you always get "mount failed". But be careful: if the files really are damaged, true erases everything. For a device with valuable data, try false first and format deliberately.
  3. Total and used space. totalBytes and usedBytes. With the default Partition Scheme you'll see about 1.3 to 1.4 MB; with Minimal SPIFFS, only 128 KB. Before saving a long log, always know how much free space you have.
  4. Mode "w": write from the start. Creates the file; if it already exists, its contents are erased. Then you write into it just like Serial, with println and printf. A file name always starts with / (the full path). Don't forget close(): until the file is closed, the last piece of data may still be in RAM and be lost if the power goes out.
  5. Mode "a": append. Adds to the end of the file and keeps what was there. For logs, always use "a". Every reset adds one boot at ... line. Press the EN button a few times and watch the file grow; that proves the data survived the reset.
  6. Mode "r": read. available() says how many bytes are left, and read() returns one byte. Reading byte by byte is simple and light on memory for small files. For a big file, f.readStringUntil('\n') reads it line by line.
  7. Listing the files. We open the folder and step through it one entry at a time with openNextFile() until an empty file (false) comes back. A great debugging tool: when the web page can't be found, first check that the file really is on the board and what exactly it's called (uppercase and lowercase letters are different).

A web page from LittleFS

Now let's move the web page out of the C++ code. In the project folder (next to the .ino file), create a folder named exactly data and put these two files in it:

    ├── index.html

  <meta name="viewport" content="width=device-width,initial-scale=1">

  1. An ordinary HTML page. In English, with a separate CSS file. (For a right-to-left language such as Persian, you would add dir="rtl" to the <html> tag.) Now you can open the page on your computer with a double-click and design it in the browser, without compiling. Only its fetch gets no answer on the computer.
  2. Live data with fetch. The page itself is static, but it gets the temperature from the /api/temp address that the ESP32 program provides (the same pattern as lesson 4.2). A clean split: the "look" lives in files, the "data" lives in code. A web designer and an ESP32 programmer can work separately.
body { font-family: sans-serif; max-width: 480px; margin: 2em auto; }
h1   { color: #2f7af0; }
  1. The page's look in a separate file. The font, a maximum width of 480 pixels (for phones), and a blue heading color. The browser requests the CSS file separately (/style.css), so the ESP32 program must also answer that address; line 19 of the program below does exactly that.
#include <WiFi.h>
#include <WebServer.h>
#include <LittleFS.h>
#include "secrets.h"

WebServer server(80);

void setup() {
  Serial.begin(115200);
  if (!LittleFS.begin(true)) {
    Serial.println("LittleFS mount failed");
  }
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) delay(500);
  Serial.printf("Open http://%s/\n", WiFi.localIP().toString().c_str());

  // static files straight from LittleFS (after LittleFS.begin)
  server.serveStatic("/", LittleFS, "/index.html");
  server.serveStatic("/style.css", LittleFS, "/style.css", "max-age=3600");

  // live data from the code
  server.on("/api/temp", []() {
    float t = temperatureRead();               // chip's internal temperature (rough)
    server.send(200, "application/json", "{\"t\":" + String(t, 1) + "}");
  });
  server.onNotFound([]() { server.send(404, "text/plain", "Not found"); });
  server.begin();
}

void loop() {
  server.handleClient();
}
  1. Mount LittleFS before anything else. serveStatic checks at the moment you define it whether the path is a file or a folder; if LittleFS isn't mounted yet, it gets it wrong.
  2. serveStatic for the main page. "Whoever asks for the address /, send them the /index.html file from LittleFS". It guesses the content type (text/html) from the file extension. One line instead of a whole function. A subtle detail: if you give it a folder instead of a file (for example serveStatic("/", LittleFS, "/")), then for the address / the library looks for index.htm (without the l), not index.html. To avoid that trap, we gave the exact file path.
  3. The CSS file, with caching. The fourth input, "max-age=3600", tells the browser "don't ask for this file again for an hour". The ESP32 is a weak server; every request it doesn't have to handle means faster answers for the rest. We didn't cache index.html, so your changes show up immediately.
  4. The live-data route. temperatureRead() gives the chip's internal temperature (not accurate, just for show), and it's sent as JSON. In a real project, use the temperature from a DHT22 or any other sensor instead.

Uploading the data folder to the board (Arduino IDE 2)

To put the data folder onto LittleFS, Arduino IDE 2 needs a plugin: arduino-littlefs-upload by Earle Philhower (the author of the RP2040 core). It works with Arduino IDE 2.2.1 and later.

  1. Download. Go to the Releases page and download the latest arduino-littlefs-upload-x.y.z.vsix file (don't unzip it).
  2. The plugins folder. On Windows, go to C:\Users\YourUserName\.arduinoIDE\ and create a plugins folder if it doesn't exist. On macOS and Linux: ~/.arduinoIDE/plugins/. Note that the folder name starts with a dot (.arduinoIDE), and on Windows it may be hidden.
  3. Copy and restart. Put the vsix file in the plugins folder, then close the Arduino IDE completely and open it again.
  4. Close the Serial Monitor. If it's open, the upload fails with a "port doesn't exist" error.
  5. Run it. Press Ctrl+Shift+P (on a Mac, ⌘+Shift+P) and choose the command Upload LittleFS to Pico/ESP8266/ESP32. The plugin works out the partition's size and location from the Partition Scheme you selected, builds a LittleFS image from the data folder, and writes it to the board over the USB cable.
  6. Now upload the program (or do it before; the order doesn't matter). These two uploads are independent: uploading the program doesn't erase the files, and uploading LittleFS doesn't erase the program.
Two common traps

1) The Partition Scheme must be the same for the LittleFS upload and the program upload; if you upload the first with Default and the second with Minimal SPIFFS, the program looks for the partition in a different place and you get "mount failed" or missing files. 2) Uploading LittleFS overwrites the whole partition; logs and settings that the program had created on the board are erased. This plugin doesn't work in Wokwi; in Wokwi you have to create files from code (like the LittleFS_Basics program does).

Flash wears out too

Each flash memory cell can take about 10,000 to 100,000 erase cycles. LittleFS and NVS spread the writes around, but if you write a log line every second, within a few months you'll do damage. The rule: save only when a value has changed (not on every pass of loop), and collect frequent log entries in RAM and write them in one go, say every 10 minutes.

Coach's corner

OTA feels like magic the first time, and that's exactly when people get careless. My two rules: One, never send a program over OTA to a device you can't reach unless you've first tested that exact program on a board on your desk, including Wi-Fi dropouts and power cuts. I've seen devices that had to be brought down from the roof because of one wrong line in setup. Rollback is your safety net, not your plan. Two, treat flash like a notebook with a limited number of pages: write when something has changed, not on every pass of loop, and always know how much free space you have. Upload the LittleFS_Basics sketch today and press EN ten times: when you see ten lines in log.txt, you've understood files that survive a reset.

Lesson quiz

Your program gives "Sketch too big" and the device must have OTA. Which Partition Scheme do you choose?

  1. Huge APP (3MB No OTA/1MB SPIFFS)
  2. No OTA (2MB APP/2MB SPIFFS)
  3. Default 4MB with spiffs
  4. Minimal SPIFFS (1.9MB APP with OTA/128KB SPIFFS)
Minimal SPIFFS has two 1.9 MB program slots: a bigger program fits and OTA stays. Only the file space drops to 128 KB.

Your device is in the ceiling. After an OTA update it no longer shows up in the Port menu, and Wi-Fi isn't connected either. What could have prevented this in advance?

  1. Removing the OTA password
  2. Choosing Huge APP
  3. Testing the new program on a board on your desk, and using rollback so the new version is only confirmed after Wi-Fi connects
  4. Turning off the watchdog
With verifyRollbackLater() and manual confirmation after Wi-Fi connects, a broken version automatically goes back to the previous one. And nothing replaces testing on your desk.

On the web update page, which file from the build folder do you pick?

  1. ProjectName.ino.merged.bin
  2. ProjectName.ino.bin
  3. ProjectName.ino.partitions.bin
  4. ProjectName.ino.bootloader.bin
OTA only replaces the program itself, so it wants the plain .ino.bin file. Update.end(true) checks the file and rejects a wrong one, leaving the old program intact.

Your log file must keep every old line and add a new line at each boot. Which mode do you open it with?

  1. LittleFS.open("/log.txt", "a")
  2. LittleFS.open("/log.txt", "w")
  3. LittleFS.open("/log.txt", "r")
  4. Delete the file and create it again
"a" (append) adds to the end and keeps what was there. "w" starts from an empty file.

You uploaded the data folder with the Default Partition Scheme, then the program with Minimal SPIFFS. The program says LittleFS mount failed. Why?

  1. The LittleFS upload plugin is broken
  2. index.html is too big
  3. The two uploads used different partition maps, so the program looks for the file system in a different place
  4. You must call LittleFS.begin(false)
The LittleFS upload and the program upload must use the same Partition Scheme. Choose it once and don't change it.

Exercises

Exercise 1: a boot diary on a web page

Combine LittleFS_Basics and LittleFS_Web: at every boot, append one line to /log.txt with the boot number, and add a /log address that shows the whole file in the browser as plain text. Press EN a few times and refresh the page: the list should grow by one line each time.

Hint

To find the boot number, read the file once at startup and count its lines (every '\n' is one line), then add one. For /log, open the file with "r" and send it with server.streamFile(f, "text/plain"), then f.close(). Don't cache it, because it changes.

What should you see?

On a real board (Wokwi's free version can't open a web page from your browser). After the upload, the Serial Monitor shows (your boot number and IP differ):

This is boot #1
Open http://192.168.1.42/log

Open that address. The browser shows the file as plain text; after pressing EN twice and refreshing:

boot #1 at 312 ms
boot #2 at 309 ms
boot #3 at 311 ms
  • Each press of EN plus a refresh adds exactly one line, and the numbers go up by 1 without gaps.
  • The times are all small (a few hundred ms), because the line is written right at the start of setup, before Wi-Fi.
  • If you ran LittleFS_Basics before, its lines (boot at ... ms) are already in the file and count too, so your diary may start at #2 or #3. That's correct: the number is "lines in the file + 1".
  • The main page (/) still works if the data folder from LittleFS_Web is on the board. Troubleshooting: no log yet means the file couldn't be written; check the LittleFS mount failed line and the Partition Scheme.
Full answer with explanation

The complete program: LittleFS_Web plus a line counter, one appended line per boot and a /log address.

#include <WiFi.h>
#include <WebServer.h>
#include <LittleFS.h>
#include "secrets.h"

WebServer server(80);

int countLines(const char *path) {           // every '\n' ends one line
  File f = LittleFS.open(path, "r");
  if (!f) return 0;                          // no file yet: 0 lines
  int lines = 0;
  while (f.available()) {
    if (f.read() == '\n') lines++;
  }
  f.close();
  return lines;
}

void handleLog() {
  File f = LittleFS.open("/log.txt", "r");
  if (!f) {
    server.send(404, "text/plain", "no log yet");
    return;
  }
  server.sendHeader("Cache-Control", "no-store");   // it changes: never cache
  server.streamFile(f, "text/plain");        // sends the file piece by piece
  f.close();
}

void setup() {
  Serial.begin(115200);
  if (!LittleFS.begin(true)) {
    Serial.println("LittleFS mount failed");
  }
  int boot = countLines("/log.txt") + 1;     // lines so far + 1
  File f = LittleFS.open("/log.txt", "a");   // a = add to the end
  if (f) {
    f.printf("boot #%d at %lu ms\n", boot, millis());
    f.close();                               // closed = saved
  }
  Serial.printf("This is boot #%d\n", boot);

  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) delay(500);
  Serial.printf("Open http://%s/log\n", WiFi.localIP().toString().c_str());

  server.serveStatic("/", LittleFS, "/index.html");
  server.serveStatic("/style.css", LittleFS, "/style.css", "max-age=3600");
  server.on("/api/temp", []() {
    float t = temperatureRead();             // chip's internal temperature (rough)
    server.send(200, "application/json", "{\"t\":" + String(t, 1) + "}");
  });
  server.on("/log", HTTP_GET, handleLog);    // ★ the boot diary
  server.onNotFound([]() { server.send(404, "text/plain", "Not found"); });
  server.begin();
}

void loop() {
  server.handleClient();
}
  1. Count the lines. Read the file byte by byte and count the '\n' characters. If the file doesn't exist yet, the answer is 0. We never saved a separate counter: the file itself is the memory. Every line we write ends with \n, so "number of newlines" is "number of boots so far". Reading a few hundred bytes one at a time is fast enough for a small log.
  2. Send the file to the browser. Open it with "r"; if it's missing, answer 404; otherwise streamFile sends it as text/plain, then we close it. streamFile sends the file in pieces, so even a long log never has to fit in RAM. Cache-Control: no-store tells the browser never to keep an old copy, because the file changes at every boot; the style sheet, which never changes, gets max-age instead.
  3. One line per boot. Boot number = lines + 1; open with "a" (append) and write boot #N at T ms; close. "a" adds to the end and keeps the old lines ("w" would wipe the file). close() is the moment the data is really in flash; LittleFS is safe against power loss, so a power cut leaves either the old file or the new one, never a broken one.
  4. LittleFS_Web, unchanged. The static page, the style sheet and /api/temp. The exercise adds a feature; everything that already worked stays as it was.
  5. The new address. /log, for GET requests, handled by handleLog. It must be registered before server.begin(), like every other route.
Exercise 2: your first real wireless fix

Add ArduinoOTA to LittleFS_Web (hostname esp32-files, password from secrets.h) and upload it once over USB. Then power the board from a phone charger, away from the computer. Over OTA, change /api/temp so it also returns the uptime in seconds, and check in the browser that the page still loads. What does this prove about the LittleFS files?

Hint

Call ArduinoOTA.begin() after Wi-Fi connects, and put ArduinoOTA.handle() next to server.handleClient() in loop. Don't change the Partition Scheme between the USB upload and the OTA uploads. The JSON can become {"t":41.2,"up":1234}.

What should you see?

After the first USB upload, the Serial Monitor prints the address; in the Arduino IDE, Tools → Port now also lists a network port such as esp32-files at 192.168.1.42. During the OTA upload the IDE asks for the password and the board (if it's still connected to a Serial Monitor) prints:

OTA start
OTA done, rebooting
Open http://192.168.1.42/

After the update, http://192.168.1.42/api/temp returns something like this (your numbers differ):

{"t":47.3,"up":12}
  • The page at / still loads with its blue heading (the style sheet from LittleFS), although you never uploaded the data folder again.
  • up is small right after the update (the board restarted) and grows by 1 per second when you refresh.
  • Troubleshooting: no network port? The computer and the board must be on the same Wi-Fi network, and some guest or school networks block it. OTA error or a refused password: check OTA_PASS in secrets.h. LittleFS mount failed after the update: the Partition Scheme was changed between uploads.
Full answer with explanation

What it proves: an OTA update (like a USB upload) only rewrites the program partition. The LittleFS partition, with index.html and style.css, is a separate area of flash that nobody touched, so the files survive every new program. They are only replaced when you upload a new LittleFS image, as long as the Partition Scheme stays the same.

This is the final version, the one sent over OTA. The first USB version is the same program without line 35 and with the original /api/temp answer.

#include <WiFi.h>
#include <WebServer.h>
#include <LittleFS.h>
#include <ArduinoOTA.h>                      // ★
#include "secrets.h"                         // WIFI_SSID, WIFI_PASS, OTA_PASS
#ifndef OTA_PASS
#warning "OTA_PASS is not defined in secrets.h"
#define OTA_PASS "change-me"
#endif

WebServer server(80);

void setup() {
  Serial.begin(115200);
  if (!LittleFS.begin(true)) {
    Serial.println("LittleFS mount failed");
  }
  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) delay(500);
  Serial.printf("Open http://%s/\n", WiFi.localIP().toString().c_str());

  ArduinoOTA.setHostname("esp32-files");     // ★ name in the Port menu
  ArduinoOTA.setPassword(OTA_PASS);          // ★ without it, anyone can flash
  ArduinoOTA
    .onStart([]() { Serial.println("OTA start"); })
    .onEnd([]() { Serial.println("\nOTA done, rebooting"); })
    .onError([](ota_error_t err) { Serial.printf("OTA error %u\n", err); });
  ArduinoOTA.begin();                        // ★ after Wi-Fi is connected

  server.serveStatic("/", LittleFS, "/index.html");
  server.serveStatic("/style.css", LittleFS, "/style.css", "max-age=3600");
  server.on("/api/temp", []() {
    float t = temperatureRead();             // chip's internal temperature (rough)
    unsigned long up = millis() / 1000;      // ★ new in the OTA version: uptime in s
    server.send(200, "application/json",
                "{\"t\":" + String(t, 1) + ",\"up\":" + String(up) + "}");
  });
  server.onNotFound([]() { server.send(404, "text/plain", "Not found"); });
  server.begin();
}

void loop() {
  ArduinoOTA.handle();                       // ★ every pass: "any update?"
  server.handleClient();
}
  1. The OTA library and the password. If OTA_PASS is missing from secrets.h, the compiler warns and uses a placeholder. The password stays out of the sketch, so you can share the code without sharing the key to your board.
  2. OTA set-up, after Wi-Fi. Hostname, password, three short messages, then begin(). begin() needs a working network to announce the board under its name, so it comes after the Wi-Fi loop. The messages let you follow the update when a Serial Monitor is attached.
  3. The small fix sent over the air. /api/temp now also returns the uptime in seconds. A visible change lets you prove that the new program really arrived: the key up is only in the new version, and its small value shows the board just restarted.
  4. Both jobs in loop. ArduinoOTA.handle() next to server.handleClient(), with no delay. The board only notices an update request when handle() runs. Every future version must keep these lines, or the next update has to go over USB again.
The lesson in three lines

OTA needs two program partitions (Default or Minimal SPIFFS, never Huge APP) and a password; the first upload is always over USB, and every new program must include the OTA code again. With rollback, a new version is only kept after it proves it can reach Wi-Fi. LittleFS is a small, power-loss-resilient drive in flash for web pages, JSON settings and short logs; it survives new programs, but not a new LittleFS upload.
