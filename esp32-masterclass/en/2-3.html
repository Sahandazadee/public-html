In this lesson you write your first real program: you turn an LED on and off. It sounds simple, but almost every basic idea of microcontroller programming is packed into these few lines: pins, outputs, HIGH and LOW, setup and loop, and timing.

🎯 After this lesson you can

  • Blink the board's built-in LED
  • Wire an external LED on a breadboard with the right resistor
  • Explain what every single line of the program does
  • Use the Serial Monitor to see what your program is doing

🧰 Prerequisites and parts

  • Lesson 2.1 (installing the Arduino IDE) or 2.2 (Wokwi)
  • An ESP32 DevKitC board and a USB data cable
  • One red 5 mm LED + a 220 Ω resistor
  • A breadboard and two male-to-male jumper wires

The big idea: a pin is a light switch

Picture every GPIO pin on the ESP32 as a tiny light switch that your program flips. When you tell a pin HIGH, about 3.3 volts appear on it (switch on). When you tell it LOW, its voltage drops to zero (switch off). If an LED is connected to that pin, current flows through the LED when the "switch" is on, and it lights up.

An everyday example

Imagine there is a lamp in your room and you tell a friend: "Flip the switch on, wait one second, flip it off, wait one second, and keep doing that forever." The Blink program gives the ESP32 exactly those instructions. Your tireless friend is the loop() function.

Step 1: the built-in LED (no wiring at all)

Most ESP32 boards have a small blue LED connected to GPIO2. That means we can test our first program without connecting a single part. This has a big advantage: if something doesn't work, we know the wiring isn't the problem.

Careful: not every board has an LED on GPIO2

The official DevKitC V4 in the photo above only has a (red) power LED and no programmable LED. Most of the inexpensive boards you can buy (such as the ESP32 DOIT DevKit V1 or NodeMCU-32S) do have a blue LED on GPIO2. If your board has no blue LED, jump straight to the external LED.

// First program: blink the board's built-in LED
const int LED_PIN = 2;          // on most boards the blue LED is on GPIO2

void setup() {
  pinMode(LED_PIN, OUTPUT);     // make pin 2 an output
}

void loop() {
  digitalWrite(LED_PIN, HIGH);  // on: 3.3 V on the pin
  delay(1000);                  // wait 1000 ms = 1 second
  digitalWrite(LED_PIN, LOW);   // off: 0 V on the pin
  delay(1000);                  // wait another second
}

Now let's go through this code piece by piece. Click any card to highlight its lines in the code above:

  1. A comment. The compiler ignores everything after // up to the end of the line. The note is for humans only. Six months from now you won't remember what this program did. Good comments are a favor to your future self.
  2. A name for the pin number. const int LED_PIN = 2; means "create a whole number (int) called LED_PIN whose value is 2 and never changes (const)". If you later move the LED to pin 4, you change this one line instead of four different places in the program. const also stops you from accidentally changing the number somewhere else.
  3. The setup() function. Everything between { and } runs once: right when the board powers up or you press EN. void means the function doesn't return anything. Initial settings (like deciding what each pin does) are only needed once. Repeating them on every pass of the loop would be wasted work.
  4. pinMode(pin, mode). Tells the ESP32 that pin 2 is an output (OUTPUT): we set its voltage instead of reading it. Every GPIO can be an input or an output. Until you say so, the ESP32 doesn't know and the pin stays an input. On core 3.x, if you forget pinMode, digitalWrite does nothing at all (it only writes IO 2 is not set as GPIO to a hidden log) and the LED stays dark; on older cores the LED sometimes glowed very dimly.
  5. The loop() function. Once setup has finished, this function runs forever, over and over. When it reaches the final }, it starts again from the top. A microcontroller has no operating system for your program to "finish" and return to. Its job is endless repetition: read sensors, decide, act.
  6. digitalWrite(pin, HIGH). Sets pin 2 HIGH: about 3.3 volts. Current flows through the LED and it lights up. "Digital" means there are only two states: zero or one. That's all you need for simple on and off. (For half brightness you need PWM, which you'll learn in lesson 3.2.)
  7. delay(1000). Pauses the program completely for 1000 milliseconds (one second). During that time the pin stays HIGH. The ESP32 runs millions of instructions per second. Without delay, the on/off switching is so fast that your eye only sees a steady, half-lit LED. The downside of delay is that nothing else can happen while it waits; in lesson 3.1 you'll learn the better millis() approach.
  8. Off, then wait. Sets the pin LOW (zero volts) and waits another second. Then loop starts over. If you remove the second delay, the LED turns back on immediately after turning off and you never see it off. This is one of the most common beginner mistakes.

Uploading the program in the Arduino IDE

  1. Pick the board. In Tools › Board › esp32, choose ESP32 Dev Module. It works for almost every 30-pin and 38-pin board.
  2. Pick the port. In Tools › Port, choose the port that appeared when you plugged the board in (for example COM5 on Windows). If there is no port, see the driver section of lesson 2.1.
  3. Upload. Click the arrow (→) button at the top of the window. First the program compiles (a few seconds to a minute), then you'll see a Writing at 0x... progress bar.
  4. If Connecting........_____ goes on for a long time, hold the BOOT button on the board until a percentage appears, then let go. Some inexpensive boards don't do this automatically.
  5. See the result. After the Hard resetting via RTS pin... message, the blue LED should blink once per second. 🎉

Step 2: an external LED on a breadboard

Now we'll connect a real LED outside the board. This is the most important hardware skill in the course, because every later part (sensors, displays, motors) connects to the pins with exactly the same logic.

Why do we need a resistor? (with numbers)

An LED is like a one-way gate that has almost no resistance once it opens. Connect it straight to 3.3 volts and the current gets so high that both the LED and the ESP32 pin are damaged. The resistor works like a flow-limiting valve that keeps the current in check.

Do the math: Ohm's law

Pin voltage = 3.3 V. A red LED "uses up" about 2 V of it (this is called the forward voltage). So what's left across the resistor is 3.3 − 2.0 = 1.3V.

With a 220 Ω resistor: I = V ÷ R = 1.3 ÷ 220 ≈ 0.006A = 6mA.

6 mA is plenty to light the LED nicely and far below the limit of an ESP32 pin (about 40 mA maximum; the course's own rule is to stay under 20 mA, see lesson 1.3). So 220 Ω is both safe and bright. Any value between 100 and 1000 Ω also works; the larger it is, the dimmer the LED.

Wiring diagram

Why GPIO4 this time? Because in lesson 1.3 we saw that GPIO4 is a "safe" pin: it isn't a strapping pin, it isn't input-only and it isn't wired to the flash. GPIO2 also works, but it is a strapping pin, and it's a good habit to reach for safe pins first when you connect external parts.

  1. Unplug the USB cable first. Always wire with the board powered off; a wire that brushes the wrong pin while you move it can cause a short on a live board.
  2. Place the ESP32 on the breadboard so it straddles the center gap, with one row of pins on each side. (The DevKitC is wide; if it doesn't fit on one breadboard, put two breadboards side by side. You saw how a breadboard is connected inside in lesson 1.4.)
  3. Put the LED's long leg (anode) in a free column and the short leg (cathode) in the column next to it. Never put both LED legs in the same column; that shorts the LED and it won't light.
  4. Place the resistor so one end shares a column with the LED's anode and the other end sits in a free column.
  5. Orange wire: from the board's GPIO4 to the free end of the resistor.
  6. Black wire: from the LED's cathode to one of the board's GND pins.
  7. Before plugging in USB, trace the path once with your finger: GPIO4 → resistor → LED long leg → short leg → GND. (The full bench checklist is in lesson 1.4.) Now plug in USB and upload.
A professional habit: wire colors

Always use red for power, black for ground and other colors for signals. When a circuit gets crowded and something doesn't work, this habit saves hours of troubleshooting.

Now change just line 2 of the code above:

const int LED_PIN = 4;          // the external LED is now on GPIO4

See? Thanks to that const int LED_PIN, we changed only one number. That's the "why" we talked about earlier.

Step 3: see what your program is thinking (Serial Monitor)

The ESP32 has no screen. So how do we find out what's happening inside the program? By sending text messages to the computer over the same USB cable. This is your single most important debugging tool for the whole course.

const int LED_PIN = 4;
int counter = 0;                       // counts the blinks

void setup() {
  Serial.begin(115200);                // start serial at 115200 baud
  pinMode(LED_PIN, OUTPUT);
  Serial.println("Blink started!");
}

void loop() {
  counter = counter + 1;
  digitalWrite(LED_PIN, HIGH);
  Serial.print("LED ON  - blink #");
  Serial.println(counter);
  delay(500);
  digitalWrite(LED_PIN, LOW);
  Serial.println("LED OFF");
  delay(500);
}
  1. A variable. int counter = 0; creates a box called counter that starts at zero. This time there is no const, because it's meant to change. We declared the variable outside the functions (globally) so it keeps its value between passes of loop. Declared inside loop, it would reset to zero every time.
  2. Serial.begin(115200). Starts serial communication at 115,200 bits per second. 115200 is the ESP32's standard speed; the ESP32's own boot messages use it too. If you pick a different speed in the Serial Monitor, you'll see scrambled characters.
  3. println a start message. println sends the text and moves to a new line. Seeing this message proves that setup ran. If the board keeps resetting, you'll see it several times, which is a great clue for debugging.
  4. Increase the counter. Each pass of loop adds one to counter. (Shorter form: counter++;) A number that keeps going up shows the program isn't stuck and loop really is repeating.
  5. print and println together. print doesn't start a new line, println does. The result is one complete line such as LED ON - blink #3. Mixing fixed text with a variable's value makes the log readable. In bigger projects you'll print sensor values exactly this way.

After uploading, open Tools › Serial Monitor and set the speed in the bottom corner to 115200 baud. You should see something like this:

Blink started! LED ON - blink #1 LED OFF LED ON - blink #2 LED OFF LED ON - blink #3

Before Blink started! you may see a few lines of the ESP32's own boot messages (such as rst:0x1 (POWERON_RESET)) or some garbage characters; that's normal. If you don't see Blink started! and the count starts at, say, 5, the Serial Monitor opened after setup had already run; press EN to restart the program. If the LED blinks but you see no text at all, check the speed at the bottom of the window again.

When it doesn't work: step-by-step troubleshooting

SymptomLikely causeFix
No port in the Port menuThe USB cable is charge-only, or the CP2102 or CH340 driver isn't installedTry another cable (one you've used to copy files to a phone). Install the driver as described in lesson 2.1.
Failed to connect to ESP32: Timed out waiting for packet headerThe board didn't enter download mode automaticallyHold BOOT while Connecting... is shown.
Upload succeeded but the external LED stays darkThe LED is in backwards (an LED only works one way round)Turn the LED around. The long leg goes toward the resistor and the GPIO.
The LED is always on and never blinksThe LED is connected to 3V3 instead of GPIO4Follow the orange wire and make sure it ends at the pin labeled 4.
The Serial Monitor shows strange charactersThe Serial Monitor speed doesn't match Serial.beginSet it to 115200 baud at the bottom of the window.
Coach's advice

If the LED doesn't work, don't touch the code! First isolate the hardware with a simple test: take the wire that goes to GPIO4 and touch it straight to 3V3. If the LED lights, the hardware is fine and the problem is in the code or the pin number. If it doesn't, the problem is the LED, the resistor or the breadboard. This "cut the problem in half" method is the single most important troubleshooting skill in all of electronics.

Lesson quiz

How many times does setup() run?

  1. Once on every pass of the loop
  2. Once every second
  3. Only once, after power-up or reset
  4. Never, unless we call it
setup runs only once; that's why pinMode and Serial.begin go there.

If you delete the line pinMode(LED_PIN, OUTPUT);, what will most likely happen?

  1. The program won't compile
  2. The LED stays off or very dim because the pin isn't an output
  3. Nothing changes, the ESP32 figures it out
  4. The board burns out
Pins are normally inputs after power-up. Without OUTPUT, the pin can't supply enough current to the LED; on core 3.x, digitalWrite on such a pin is ignored completely and the LED stays off.

A red LED with a 2 V forward voltage and a 130 Ω resistor is connected to a 3.3 V pin. Roughly how much current flows?

  1. 25 mA
  2. 1 mA
  3. 15 mA
  4. 10 mA
(3.3 − 2) ÷ 130 = 0.01A = 10mA. Still safe, but 220 Ω gives a bigger safety margin.

Your external LED won't light, but the built-in LED worked with the same code (on pin 2). What is the most sensible first step?

  1. Check the LED's orientation (long leg toward the resistor and the GPIO)
  2. Reinstall the Arduino IDE
  3. Buy a new ESP32 board
  4. Make the delay longer
When the code worked on the built-in LED, the problem is almost certainly the wiring, and a reversed LED is the most common mistake.

Exercises

Exercise 1: heartbeat

Change the program so the LED blinks like a heartbeat: two quick blinks (100 ms on, 100 ms off), then 700 ms off.

Hint

Inside loop you need four digitalWrite calls and four delays. Sketch the timing on paper first.

Answer 
void loop() {
  digitalWrite(LED_PIN, HIGH); delay(100);
  digitalWrite(LED_PIN, LOW);  delay(100);
  digitalWrite(LED_PIN, HIGH); delay(100);
  digitalWrite(LED_PIN, LOW);  delay(700);
}
  1. First beat. 100 ms on, 100 ms off. Two statements on one line are only for readability; the compiler doesn't care. setup and LED_PIN stay the same as in the main program; only loop has changed.
  2. Second beat and rest. Again 100 ms on, but this time 700 ms off. The long final pause is the gap between heartbeats; without it you'd see four identical blinks in a row instead of the "ba-dum... ba-dum" rhythm.
Exercise 2: traffic light

Connect three LEDs, red, yellow and green, to GPIO25, GPIO26 and GPIO27 (each with its own 220 Ω resistor). Sequence: green for 3 seconds, yellow for 1 second, red for 3 seconds. Print the name of each color to the Serial Monitor as it lights.

Hint

Declare three const int constants and make all three OUTPUT in setup. Each LED needs its own resistor; one shared resistor for three LEDs is a mistake. Why?

Answer 
// Traffic light: green 3 s, yellow 1 s, red 3 s
const int RED_PIN    = 25;
const int YELLOW_PIN = 26;
const int GREEN_PIN  = 27;

void setup() {
  Serial.begin(115200);
  pinMode(RED_PIN, OUTPUT);
  pinMode(YELLOW_PIN, OUTPUT);
  pinMode(GREEN_PIN, OUTPUT);
}

void loop() {
  digitalWrite(GREEN_PIN, HIGH);        // green
  Serial.println("GREEN");
  delay(3000);
  digitalWrite(GREEN_PIN, LOW);

  digitalWrite(YELLOW_PIN, HIGH);       // yellow
  Serial.println("YELLOW");
  delay(1000);
  digitalWrite(YELLOW_PIN, LOW);

  digitalWrite(RED_PIN, HIGH);          // red
  Serial.println("RED");
  delay(3000);
  digitalWrite(RED_PIN, LOW);
}
  1. Three names for three pins. Each color gets its own constant. GPIO25, 26 and 27 are in the green table of lesson 1.3. With names, moving an LED only takes a one-line change.
  2. Setup. Serial and three pinMode calls. Every pin you digitalWrite to must be made OUTPUT separately; forget one and that color never lights.
  3. The green phase. On, print its name, wait 3 seconds, off. Turning each light off at the end of its phase guarantees two lights are never on at the same time.
  4. Yellow and red. The same pattern with different times; then loop starts again at green. When a pattern repeats three times, you'll later learn to put it in a function; for now the explicit version is easier to read.

Why separate resistors? In this particular program only one LED is on at a time, so a single shared resistor in the GND path would actually work. But the day you light two LEDs at once, the current splits between them, and because different colors have different forward voltages (red about 2 V, green and blue higher), the LED with the lower drop takes most of the current and the others stay dim or dark. Simple rule: every LED gets its own resistor.

Exercise 3: think (no code)

Why should you never connect an LED to GPIO6 through GPIO11? Find the answer on the pinout page.

Answer

GPIO6 through GPIO11 are wired inside the module to the flash memory, and the processor reads the program over them all the time. Any wire or command on them disrupts the flash and the board crashes or resets (lesson 1.3). On the DevKitC they are labeled CLK, SD0 to SD3 or D0 to D3, and CMD; on the DOIT board they aren't brought out at all.

The lesson in three lines

pinMode in setup decides what a pin does; digitalWrite in loop turns it on and off; delay creates the timing. An LED always goes in with a series resistor and the right way round. The Serial Monitor is your window into the program.
