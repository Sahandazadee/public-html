What is a simulator, and what doesn't it simulate?

A simulator is a program that imitates the behavior of a piece of hardware on your computer. Wokwi compiles your code with the same ESP32 compiler and runs the resulting binary on a "virtual ESP32" that imitates the processor's instructions, the pins, the timers and even Wi-Fi. So code that works in Wokwi will very likely work on a real board too.

An everyday example

A simulator is like a pilot's flight simulator. You learn the buttons, the routes and the rules without any risk, and if the plane crashes, nobody gets hurt. But no pilot gets a license from the simulator alone, because they haven't felt real wind, real turbulence or real fear. Wokwi is the same: it tests your program's logic brilliantly, but it doesn't fully reproduce the physical world.

What Wokwi does really well

  • Runs real ESP32 code (the same pinMode, Serial, WiFi functions and so on)
  • Common parts: LEDs, buttons, potentiometers, servos, OLED displays, the DHT22, the HC-SR04 and many more
  • A Serial Monitor, virtual Wi-Fi with real internet access, and a logic analyzer
  • Sharing a project with a single link (fantastic for asking other people for help)

Limits: where the simulator doesn't tell the truth

TopicIn WokwiIn the real world
Analog behavior and currentAn LED lights up even without a resistor, and nothing burns. The resistor value usually has no effect on brightness.An LED without a resistor draws far too much current, and either the LED or the ESP32 pin gets damaged (see the Ohm's law math in lesson 2.2).
Noise and interferenceSignals are clean and perfect. There are no long wires, loose connections or dirty breadboards.Long wires pick up noise, breadboards make bad contact, and motors make the voltage wobble.
PowerThere is always enough steady power. A brownout (voltage dip) almost never happens.Wi-Fi draws a high burst of current when it starts up; a poor cable causes resets.
TimingSometimes the simulation runs slower than real time (the speed percentage is shown at the top of the panel). Very timing-sensitive tasks may behave differently.Timing is exact, but real parts have delays and tolerances.
SensorsYou set a sensor's value with a slider; it's always exact and error-free.Sensors have errors and noise, and sometimes they fail; a DHT22 sometimes returns nan.
Smoke!A short circuit, 5 V on a 3.3 V pin, wiring something backwards: nothing burns.Every one of these ruins the part for good.
So why use a simulator at all?

Because most beginner mistakes are logic mistakes, not physical ones: the wrong pin number, a condition that's backwards, a forgotten delay. A simulator shows you these in seconds, with nothing to buy, no waiting for uploads and no fear. Our rule in this course: get the logic right in Wokwi, and the physics right on the bench.

Working with the diagram: parts, wires, colors, rotation

  1. Adding a part: press the blue + button and search for, say, LED. The part appears in the top-left corner of the diagram; drag it with the mouse to where you want it.
  2. Drawing a wire: click on a pin, then click on the destination pin. If you want the wire to follow a particular path, click at points along the way. To cancel a half-drawn wire: Esc or right-click. Hover the mouse over any pin to see its name.
  3. Wire color: Wokwi picks the starting color itself (black for GND wires, red for 5 V wires, green for the rest). Click a wire and choose another color, or select the wire and press a key: 0 black, 2 red, 3 orange, 6 blue, 5 green.
  4. Rotating: select a part and press R (90 degrees each time). D duplicates the part and Delete removes it.
  5. Part settings: click a part to see and change its properties (for example the LED color or the resistor value). The ? key opens the documentation for that part.
  6. Zooming: + and -, or F to fit the whole circuit on the screen.
Take wire colors seriously

In the simulator, wire color has no electrical effect at all, but you'll carry the same habit over to your real bench. The course rule: red for power, black for ground, orange for outputs, blue for inputs. A crowded circuit full of same-colored wires is a troubleshooting nightmare.

The diagram.json file: your circuit written as text

Everything you do with the mouse on the diagram actually edits a text file called diagram.json. This file is in JSON format: a standard way of writing data so that both humans and machines can read it. Why should you learn it? Because throughout this course we give you a ready-made diagram.json for every circuit, and a single copy and paste builds the whole circuit; and because editing text is sometimes much faster than using the mouse.

An everyday example

diagram.json is like the inventory list for a house move: the first section says "which things we have and where each one goes in the room" (parts), and the second says "which thing plugs into which socket with which cable" (connections). Anyone who has this list can set up the room exactly like yours.

Here is the complete diagram.json for the project we'll build together shortly: a button on GPIO27 and an LED with a resistor on GPIO4.

{
  "version": 1,
  "author": "ESP32 Persian Masterclass",
  "editor": "wokwi",
  "parts": [
    { "type": "board-esp32-devkit-c-v4", "id": "esp", "top": 0, "left": 0, "attrs": {} },
    { "type": "wokwi-pushbutton", "id": "btn1", "top": 185, "left": 190, "attrs": { "color": "green", "key": "b" } },
    { "type": "wokwi-resistor", "id": "r1", "top": 110, "left": 170, "rotate": 90, "attrs": { "value": "220" } },
    { "type": "wokwi-led", "id": "led1", "top": 30, "left": 200, "attrs": { "color": "red" } }
  ],
  "connections": [
    [ "esp:TX", "$serialMonitor:RX", "", [] ],
    [ "esp:RX", "$serialMonitor:TX", "", [] ],
    [ "esp:27", "btn1:1.l", "blue", [] ],
    [ "btn1:2.l", "esp:GND.3", "black", [] ],
    [ "esp:4", "r1:2", "orange", [] ],
    [ "r1:1", "led1:A", "orange", [] ],
    [ "led1:C", "esp:GND.2", "black", [] ]
  ],
  "dependencies": {}
}
  1. The outer curly braces. The whole file is one JSON "object" that starts with { and ends with }. Inside it are "name": value pairs separated by commas. JSON is very strict: one extra comma after the last item, or one missing quote mark, makes the whole file invalid and Wokwi shows an error. So if you edit it by hand, watch your commas.
  2. The header. version is always 1; author is the creator's name; editor is the program that made the file ("wokwi"). These three lines have no effect on how the circuit behaves. Feel free to put your own name as the author.
  3. The list of parts (parts). An array (a list) between [ and ] where each item is one part. The order of the parts doesn't matter; each part's id just has to be unique, because the wires refer to parts by that id.
  4. The ESP32 itself. type is the kind of part: board-esp32-devkit-c-v4 means the official DevKitC, version 4. id is a short name we chose (esp). top and left are the part's position on the screen in pixels. attrs holds extra properties (empty here). The short name esp keeps the wires readable: esp:27 means "pin 27 of the part called esp".
  5. The button. Type wokwi-pushbutton with two properties: color, the color of the button cap, and key, which links the B key on your keyboard to the button. With key you can hold down B while the simulation runs instead of clicking. That's much easier for repeated tests. (The diagram needs to have focus, meaning you've clicked on it once.)
  6. The resistor. value is the value in ohms ("220"). rotate: 90 turns it 90 degrees so it stands vertically. Remember (from the limits table): in the simulator the resistor value has almost no effect. We include it anyway because on a real board it is mandatory. The simulator is where you practice good habits.
  7. The LED. Type wokwi-led, colored red. Its pins are A (anode, positive) and C (cathode, negative). Watch out: in Wokwi the cathode is called C, but in our wiring diagrams (and many datasheets) it's K. They're the same thing.
  8. The list of wires (connections). Each wire is an array of four items: [from, to, color, path]. "From" and "to" are written as partId:pinName. The direction of a wire (which end is "from") makes no electrical difference.
  9. Connecting to the Serial Monitor. $serialMonitor is a special, invisible part: the Serial Monitor window itself. The empty color "" means the wire isn't drawn. Notice that the board's TX goes to the monitor's RX and the other way round: the transmitter on one side has to reach the receiver on the other, like one person's mouth to the other's ear. Without these two lines, the Serial Monitor shows nothing.
  10. The button wires. The button's 1.l pin (the left side of contact 1) goes to GPIO27, and its 2.l pin (the left side of contact 2) goes to one of the GND pins. GND.3 means the board's third GND pin. The button has four pins: 1.l and 1.r are always connected to each other (both are contact 1), and so are 2.l and 2.r. Pressing the button connects contact 1 to contact 2. If you accidentally use both pins of the same contact (for example 1.l and 1.r), the button always reads as "pressed". The board has several GND pins and it doesn't matter which one you use; Wokwi tells them apart by number.
  11. The LED wires. GPIO4 → resistor → LED anode, and LED cathode → GND. The colors follow our rule: orange for outputs, black for ground. This is exactly the external LED circuit from lesson 2.2. Whether the resistor comes before or after the LED makes no difference; what matters is that it's in series in the path.
  12. The last array of each wire: the path. An empty [] means "let Wokwi choose the path". You can write instructions such as "v10" (10 pixels vertically), "h-20" (20 pixels horizontally, to the left) and "*". When you route a wire through points along the way with the mouse, Wokwi writes these instructions here. You don't need to memorize them; just know where those odd numbers come from.
  13. dependencies. Extra dependencies; usually empty. Libraries don't go here; they live in a separate file called libraries.txt.
Going further

You can also add an optional "serialMonitor" section at the top level of the file to control how the Serial Monitor behaves (for example, always shown, or switched to plotter mode). The full details are in the diagram.json documentation.

Let's build it together: a button and an LED

Now we'll build a complete project: the LED stays on for as long as you hold the button, and every time the button's state changes, a message appears in the Serial Monitor. Before the code, there's one important idea you need to understand.

Why do we connect the button to GND? (INPUT_PULLUP)

A button is just a switch: when you press it, it connects its two ends together. We've connected one end to GND. So while the button is pressed, GPIO27 is connected straight to zero volts (LOW). But when the button is released, GPIO27 isn't connected to anything at all. This is called a floating pin: its voltage is undefined, and the slightest bit of noise (even your hand coming close) makes it jump between HIGH and LOW.

The fix: a large resistor between the pin and 3.3 V that gently "pulls" the pin up to HIGH while the button is released. This is called a pull-up resistor. The good news: the ESP32 has this resistor built in (about 45 kΩ), and you switch it on with INPUT_PULLUP.

An everyday example

Picture a door with a spring that always keeps it closed on its own (the default state = HIGH). The spring is weak (a large resistor), so when someone pushes the door (presses the button), it opens easily (LOW). Without the spring, the door would swing open and shut with every little breeze (a floating pin). The pull-up resistor is that spring.

Remember the reversed logic

With INPUT_PULLUP: pressed = LOW and released = HIGH. That's the opposite of what you'd expect, and it's the most common source of beginner bugs. Always put a comment next to it in your code.

Why not connect the button to 3.3 V so the logic isn't reversed?

You can, but then you need a pull-down resistor. The ESP32 has internal pull-downs too (INPUT_PULLDOWN), but the GND + PULLUP approach is a universal standard: it works on every microcontroller (the Arduino Uno has no internal pull-down), and you don't run an extra 3.3 V wire across your breadboard that could cause a short circuit if it accidentally lands in the wrong place.

Wiring diagram

Why GPIO27? Because in the course pin plan (lesson 1.3) it is the fixed home of "button 1", and it's one of the "safe" pins too: it isn't a strapping pin, it isn't input-only (unlike GPIO34 to 39, which have no internal pull-up resistor at all!) and it isn't wired to the flash. GPIO27 is also an ADC2 pin, but that only matters for analog readings while Wi-Fi is on (lesson 3.1); a digital button doesn't care at all. On a real board, keep this button on the breadboard next to the status LED (GPIO4); later lessons use these two parts again.

The code

// Button and LED: the LED stays on while you hold the button
const int BUTTON_PIN = 27;   // one side of the button to GPIO27, the other to GND
const int LED_PIN = 4;       // LED with a 220 ohm resistor on GPIO4

int lastState = HIGH;        // the button's previous state (starts as released)

void setup() {
  Serial.begin(115200);
  pinMode(BUTTON_PIN, INPUT_PULLUP);   // turn on the internal pull-up resistor
  pinMode(LED_PIN, OUTPUT);
  Serial.println("Ready! Press the green button (or key B).");
}

void loop() {
  int state = digitalRead(BUTTON_PIN); // HIGH = released, LOW = pressed

  if (state == LOW) {
    digitalWrite(LED_PIN, HIGH);       // button pressed: LED on
  } else {
    digitalWrite(LED_PIN, LOW);        // button released: LED off
  }

  if (state != lastState) {            // print only when the state changes
    Serial.println(state == LOW ? "Pressed" : "Released");
    lastState = state;
  }

  delay(20);                           // short pause: a simple help against button bounce
}
  1. Names for the pins. Two constants for the button and LED pin numbers. These numbers must match diagram.json exactly (esp:27 and esp:4). If you change one side and not the other, the circuit "doesn't work" without any error message.
  2. Remembering the previous state. lastState remembers what state the button was in on the previous pass of loop. It starts as HIGH because nobody is pressing the button at the start. Without this variable we can't tell when a "change" happened; we'd only know the current state. We declared it globally so it isn't wiped between passes of loop.
  3. INPUT_PULLUP. Makes the pin an input and switches on the internal pull-up resistor at the same time. If you write just INPUT, the pin floats on a real board and the LED flickers on and off at random. (You may not see this problem in the simulator; it's one of the simulator's little lies.)
  4. LED as output, and a ready message. Just like in lesson 2.2. The Ready message proves that setup has finished and the program is now waiting for the button.
  5. digitalRead. Reads the pin's current state: HIGH or LOW. On every pass of loop, which is roughly every 20 milliseconds, we read the button again. This approach is called polling ("asking over and over"). You'll see the more advanced approach (interrupts) in chapter 3.
  6. The decision: LED on or off. If the button is pressed (LOW), turn the LED on; otherwise turn it off. Here you see that "reversed logic" in action: the condition == LOW means "pressed". A shorter version of these five lines is digitalWrite(LED_PIN, state == LOW ? HIGH : LOW);, but when you're starting out, the long version is easier to read.
  7. Print only on a change. If the state is different from the previous pass, print a message and remember the new state. The expression condition ? a : b (the ternary operator) means "a if the condition is true, otherwise b". If we printed on every pass, we'd see 50 lines of "Released" every second and the important message would get lost. Printing only on a change is a professional pattern you'll use again and again.
  8. delay(20). A 20-millisecond pause between readings. When you press a real button, its metal contacts open and close several times within a fraction of a millisecond (bounce). Wokwi simulates this bounce by default too! This short pause hides most of the bounce, but it isn't a complete fix; if you sometimes see two "Pressed" in a row, that's why. You'll learn the proper method in lesson 3.1.

More Wokwi features

Virtual Wi-Fi: Wokwi-GUEST

Wokwi's virtual ESP32 can connect to a virtual Wi-Fi network called Wokwi-GUEST. The network has no password and reaches the real internet through Wokwi's server, so you can send HTTP requests or connect to an MQTT server (chapters 4 and 5).

#include <WiFi.h>

void setup() {
  Serial.begin(115200);
  WiFi.begin("Wokwi-GUEST", "", 6);    // virtual network, no password, channel 6
  Serial.print("Connecting");
  while (WiFi.status() != WL_CONNECTED) {
    delay(250);
    Serial.print(".");
  }
  Serial.println();
  Serial.print("Connected! IP: ");
  Serial.println(WiFi.localIP());
}

void loop() {
  delay(1000);
}
  1. The WiFi library. It's part of the ESP32 core; no separate install needed. This exact line is the same on a real board. Wi-Fi code you write in Wokwi works on real hardware once you change the network name and password.
  2. WiFi.begin(name, password, channel). The network name is Wokwi-GUEST, the password is empty, and the channel is 6. The third parameter (the channel) is optional. According to the Wokwi documentation, giving channel 6 skips the network scan and makes connecting about 4 seconds faster. On a real board you normally give just the name and password.
  3. Wait until connected. As long as the status isn't "connected", print a dot every 250 milliseconds. Connecting to Wi-Fi isn't instant. If you reach for the internet without waiting, it fails. (This loop waits forever; we'll write a robust version with a timeout and automatic reconnection in lesson 4.1.)
  4. Print the IP. The address the network gave the ESP32. Seeing an IP means the connection really is up. This IP is inside Wokwi's virtual network; to open an ESP32 web server in your own browser, Wokwi has a separate "IoT Gateway", explained in its Wi-Fi documentation.
  5. An empty loop. Nothing to do for now. This program is only a connection test. Chapter 4 builds on exactly this foundation.
Public and private gateway

By default, traffic goes over Wokwi's "public gateway" on the internet, which, according to Wokwi's own documentation, is slower, and connections may be monitored. So never put a real password or sensitive information in a simulator project. For more serious work there's a "private gateway" that runs on your own computer; it's one of the paid features.

The logic analyzer: seeing your signals

A logic analyzer is a tool that records the HIGH and LOW changes on one or more wires over time; think of it as a video camera for digital signals. A real one costs money; in Wokwi it's free. Wokwi has an 8-channel logic analyzer (D0 to D7). Add Logic Analyzer (8 channels) from the + button, or put these lines into diagram.json:

{ "type": "wokwi-logic-analyzer", "id": "logic1", "top": 260, "left": 180, "attrs": {} },

[ "esp:4", "logic1:D0", "green", [] ],
[ "logic1:GND", "esp:GND.1", "black", [] ],
  1. The logic analyzer part. This line goes into the "parts" list (after the other parts, with a comma). We gave it the id logic1 so the wires can refer to it.
  2. The wires. Connect channel D0 to GPIO4 (the LED pin) and the analyzer's GND to the board's GND. These two lines go into the "connections" list. A pin can be connected to several places at once; the LED keeps working and the analyzer just "listens". A shared ground is needed for any measurement, in the simulator and in real life.

Run the simulation, press the button a few times, then stop the simulation. Wokwi downloads a file called wokwi-logic.vcd, which you can open in the free PulseView or GTKWave software to see the exact waveform. This tool will come in very handy in the lessons on PWM (3.2) and communication protocols (3.3).

Libraries in Wokwi: the libraries.txt file

Built-in libraries such as WiFi.h and Wire.h are always available. For other libraries (for an OLED display, say), open the Library Manager tab, press the blue + button, search for the library's name and click it. Wokwi creates a file called libraries.txt for you:

# Wokwi Library List
Adafruit SSD1306
DHT sensor library

# a specific version with @
Adafruit GFX Library@1.11.9
  1. Comments. Lines that start with # are ignored. Use them for notes about what each library is for.
  2. One library per line. The name is exactly the one shown in the Arduino Library Manager. The latest version gets installed. This file plays the same role as lib_deps in PlatformIO: the libraries are recorded with the project, and anyone who opens the link gets the same ones.
  3. Pinning a version with @. name@version installs one exact version. When a new version of a library breaks old code, this is the only way back. You usually don't need to edit the file by hand; the Library Manager does it for you.

Saving and sharing a project

  • Saving (SAVE) needs a free account (with an email address or a Google/GitHub account). If you don't save, everything is lost when you close the page.
  • Sharing (SHARE) gives you a link of the form wokwi.com/projects/number. Anyone who opens the link sees the circuit and code, can run it, and can make their own copy with "Save a copy"; your version stays untouched.
  • When asking for help: instead of taking a screenshot or copying a piece of your code, send the Wokwi link. Whoever wants to help you sees exactly what you see.

Wokwi in VS Code (very briefly)

If you use PlatformIO (lesson 2.1, part B), the Wokwi for VS Code extension brings the simulator right into VS Code. You Build the project as usual and Wokwi runs the compiled file. All you need is two files in the project's root folder: the same diagram.json and a settings file:

[wokwi]
version = 1
firmware = '.pio/build/esp32dev/firmware.bin'
elf = '.pio/build/esp32dev/firmware.elf'
  1. The wokwi section and version. The fixed format of the file. The TOML format looks like the ini format you saw in platformio.ini.
  2. The paths to the compiled files. PlatformIO puts the output of the esp32dev environment in .pio/build/esp32dev/. firmware is the executable file, and elf (optional) helps the simulator. If your environment in [env:…] has a different name, change the folder name too. Use /, not \, even on Windows. Always Build once before you start the simulation.

To get started: install the extension, press F1 and choose Wokwi: Request a new License to get a free license, then F1 › Wokwi: Start Simulator.

From the simulator to real hardware

The day your real board arrives, follow this path. Don't skip any step:

Checklist: what the simulator didn't check

✔ItemWhy
☐Do the pin labels on your board match Wokwi?Wokwi shows a DevKitC board. Your DOIT or NodeMCU board has a different pin layout, and the labels may read D27, G27 or just 27. Go by the GPIO number, not by where the pin physically sits.
☐Is the LED resistor really there? Is its value right?It made no difference in the simulator; in real life it's mandatory. 220 Ω: red-red-brown. Don't grab a 22 k (red-red-orange) by mistake; the LED will be very dim. Not sure? Measure it with a multimeter (lesson 1.4).
☐LED orientationThe long leg (anode) goes toward the resistor/GPIO. In Wokwi you could see it at a glance; on the bench you have to pay attention.
☐Did you pick diagonal button pins?A real 4-pin button has two pairs of pins that are always connected. If you use both pins of one pair, the button is always "pressed". The safest choice: use two pins that are diagonally opposite each other.
☐Power and groundNo wire from 5V or VIN may reach a GPIO pin (the GPIOs are 3.3 V pins). Every part must share a common GND with the board.
☐BreadboardThe middle rows on the two sides of the center gap aren't connected to each other; on some long breadboards the side power rail is split in the middle. (Full reminder in lesson 1.4; make sure with your multimeter's continuity beeper.)
☐Same codeUpload the same code you tested in Wokwi, with the same pin numbers. If you used WiFi.begin("Wokwi-GUEST", "", 6) in Wokwi, put in your own network name and password.
☐LibrariesWhatever was in libraries.txt, install it in the Arduino IDE too, with the Library Manager (preferably the same version).

Coach's advice

Wokwi is a great crutch, not a leg. The big danger is staying in the simulator for months and then panicking at your first loose wire when you finally reach real hardware. My rule for you: every circuit you build in Wokwi, build it on the bench the same week, even if it's just one LED and one button. And when it doesn't work on the bench, don't blame the simulator; go through the checklist above line by line. Every time you find a difference between the simulator and reality, write it in your notebook. Those notes are worth more than any book.

In Wokwi you connected an LED straight to GPIO4 with no resistor, and it worked. What's the correct conclusion?

  3. The simulator doesn't model current; on a real board the resistor is mandatory
  4. You should use a different pin
Analog behavior and physical damage don't exist in the simulator. "It worked in Wokwi" means the logic is right, not that the circuit is safe.

  4. A random value

  2. The wire isn't connected yet
  3. The button has no extra properties
  4. No path instructions were given, so Wokwi chooses the wire's path itself
The fourth item holds path instructions (such as "v10" or "h-20"). Empty means an automatic path.

Why does our diagram.json have two lines with $serialMonitor?

  1. To connect the board's power
  2. To connect the board's TX and RX to the Serial Monitor window; without them, Serial messages don't show up
  3. To enable Wi-Fi
  4. They're just decoration and can be deleted
$serialMonitor is an invisible part. The board's TX connects to the monitor's RX, and the board's RX to the monitor's TX.

Your project works perfectly in Wokwi. On a real DOIT DevKit V1 board with the same code, the button does nothing. What's the first thing you check?

  1. Rewrite the code using an interrupt

  4. Add a 10 k resistor
The DOIT pin layout differs from the DevKitC, and a real 4-pin button has pairs of pins that are always connected. These two are the most common differences between the simulator and the bench.

Full answer with explanation 
// Two opposite LEDs: red while the button is pressed, green while it's released
const int BUTTON_PIN = 27;   // one side of the button to GPIO27, the other to GND
const int LED_PIN = 4;       // red LED with a 220 ohm resistor on GPIO4
const int LED2_PIN = 32;     // green LED with a 220 ohm resistor on GPIO32

int lastState = HIGH;        // the button's previous state (starts as released)

void setup() {
  Serial.begin(115200);
  pinMode(BUTTON_PIN, INPUT_PULLUP);   // turn on the internal pull-up resistor
  pinMode(LED_PIN, OUTPUT);
  pinMode(LED2_PIN, OUTPUT);
  Serial.println("Ready! Press the green button (or key B).");
}

void loop() {
  int state = digitalRead(BUTTON_PIN); // HIGH = released, LOW = pressed

  if (state == LOW) {
    digitalWrite(LED_PIN, HIGH);       // pressed: red on
    digitalWrite(LED2_PIN, LOW);       //          green off
  } else {
    digitalWrite(LED_PIN, LOW);        // released: red off
    digitalWrite(LED2_PIN, HIGH);      //           green on
  }

  if (state != lastState) {            // print only when the state changes
    Serial.println(state == LOW ? "Pressed" : "Released");
    lastState = state;
  }

  delay(20);                           // short pause: a simple help against button bounce
}
  1. A new pin and its role. A constant for GPIO32, and making it an OUTPUT. Every LED needs its own pin and its own resistor. GPIO32 is one of the safe pins, and one of the "swappable" pins in the course plan.
  2. The reversed logic. In each branch, the two LEDs get opposite states. Because both branches set both LEDs, they can never stay on together or off together.
  3. Printing and the pause, unchanged. The same code as the main project. Only change what the exercise asks for; the rest of the code is already tested.

The new diagram.json lines: two parts, { "type": "wokwi-led", "id": "led2", … "attrs": { "color": "green" } } and { "type": "wokwi-resistor", "id": "r2", … }, and three wires: ["esp:32","r2:2","orange",[]], ["r2:1","led2:A","orange",[]] and ["led2:C","esp:GND.1","black",[]]. The top and left numbers (where a part sits on the screen) can be anything in your circuit.

Exercise 2: a toggle button

Change the program so that every time you press and release the button, the LED switches state (like the light switch in your room). First press: on, and it stays on. Second press: off.

Hint

You need a bool ledOn variable. Flip the state only at the moment the reading changes from HIGH to LOW (the press edge): ledOn = !ledOn;. If the LED sometimes switches twice, think about button bounce.

What should you see?

LED ON
LED OFF
LED ON

  • Press and release four times: exactly four lines, alternating LED ON and LED OFF, and the LED changes together with each line.
  • Hold the button for 3 seconds: the LED changes the moment you press, and nothing happens when you let go (no new line is printed).
  • If one press gives you two lines in a row (ON and straight away OFF), button bounce got past the debounce; check the delay(50).
Full answer with explanation 
// Toggle: every press flips the LED, like the light switch in your room
const int BUTTON_PIN = 27;
const int LED_PIN = 4;

bool ledOn = false;          // the LED's current state
int lastState = HIGH;        // the button's previous state (starts as released)

void setup() {
  Serial.begin(115200);
  pinMode(BUTTON_PIN, INPUT_PULLUP);
  pinMode(LED_PIN, OUTPUT);
  Serial.println("Ready! Each press toggles the LED.");
}

void loop() {
  int state = digitalRead(BUTTON_PIN);
  if (state != lastState) {                  // the state changed (pressed or released)
    if (state == LOW) {                      // only at the moment of pressing
      ledOn = !ledOn;                        // flip it
      digitalWrite(LED_PIN, ledOn ? HIGH : LOW);
      Serial.println(ledOn ? "LED ON" : "LED OFF");
    }
    delay(50);                               // wait for the bounce (on press and on release) to settle
    lastState = state;
  }
}
  1. Remembering the LED. A bool has only two values: true or false. Now the LED's state no longer depends on the button's current state; it has to be remembered separately.
  2. Serial and a ready message. Just like the main project. By printing the LED's state, you can tell how many times the program switched it without even looking at the LED; that's exactly what you need to spot button bounce.
  3. Detecting a change. We only do something when the button's state differs from the previous pass. If you only checked state == LOW, the LED would flip dozens of times a second for as long as you held the button.
  4. The press edge: flip, apply and print. If the change was "released → pressed", ! (logical NOT) flips the LED's state, the LED is set to match the variable, and the new state is printed. Releasing the button is also a "change", but a light switch only changes when you press it; so we flip the state only in the LOW branch.
  5. Pause and update the button memory. After every change (press or release) we wait 50 milliseconds and remember the new state. A button bounces when it's released, too. If we only waited after a press, the bounce on release would create a fake "press" and the LED would sometimes switch by itself. This is the simplest possible debounce; the complete method is in lesson 3.1.

The same circuit as the main project (button on GPIO27, LED on GPIO4). Wokwi simulates button bounce too, so it's a good test for your debounce.

Exercise 3: bug hunting with diagram.json

In the project's diagram.json, deliberately change the "esp:27" wire to "esp:26" (leave the code alone) and run it. What do you see? What does the Serial Monitor say? Now put the wire back, and this time change "btn1:2.l" to "btn1:1.r". Explain the result.

Hint

In the first case, GPIO27 isn't connected to anything, but it has its PULLUP. In the second case, think about the button's internal wiring from the walk-through above: 1.l and 1.r are always connected.

What should you see?

First case ("esp:26"): however often you press the button, only this:

Ready! Press the green button (or key B).

The red LED never lights. Second case ("btn1:1.r"): straight after the start:

Ready! Press the green button (or key B).
Pressed

and the red LED is on from the very beginning and doesn't react to the button at all.

  • In neither case do you get an error message; the program compiles and runs.
  • After you put the wires back, the normal behavior (Pressed and Released with every press) should return.
Full answer with explanation

First case: with the pull-up, GPIO27 is always HIGH, so the LED never lights and only "Ready" is printed; there's no error at all. The important lesson: wrong wiring fails silently. Second case: GPIO27 is always connected to GND through 1.l–1.r, so the LED is always on and a single "Pressed" is printed at the start; the button has no effect.

Step by step: (1) the code still reads GPIO27, but in the first case the button is connected to GPIO26; GPIO27 only has its internal pull-up and stays HIGH. lastState also starts as HIGH, so no "change" ever happens and no line is printed. (2) In the second case, the 1.l leg (connected to GPIO27) and the 1.r leg (now connected to GND) are always joined inside the button; so GPIO27 is always LOW. On the first pass of loop the state differs from lastState (HIGH), so Pressed is printed once; after that nothing ever changes. Pressing the button only joins the 1 legs to the 2 legs, which are now connected to nothing.

The lesson in three lines

Wokwi runs real ESP32 code in your browser, and diagram.json (parts + connections) holds the whole circuit as text. A button between a GPIO and GND with INPUT_PULLUP: pressed = LOW, released = HIGH. The simulator tests logic, not physics; before moving to hardware, check resistors, pin labels and part orientation with the checklist.
