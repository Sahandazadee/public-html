Why MQTT? The problem with the old way (HTTP)

In lesson 4.2 you built a web server on the ESP32. That approach has one big problem: the ESP32 can only be seen inside your home network. From outside your home (say, over your phone's mobile data) you can't connect to it directly, because the router doesn't let anyone from outside connect to the devices inside. That's a good security feature, not a flaw.

The solution is for both the ESP32 and your phone to connect to the same server in the middle, on the internet. Both connections go "from inside to outside", and the router is fine with that. In the MQTT world, this server in the middle is called the Broker.

An everyday example: a Telegram channel

Imagine a Telegram channel called "Ali's room temperature". The ESP32 is like the channel admin, who posts every 10 seconds: "24.5 degrees". Your phone, your laptop and a dashboard are members of the channel. The admin doesn't need to know how many members there are or where in the world they are; the admin just hands the post to Telegram itself, and Telegram delivers it to every member.

In MQTT: Telegram = the Broker, the channel name = the Topic, posting = Publish, joining = Subscribe, and anyone connected to Telegram (admin or member) = a Client.

Notice one important point: in MQTT, the sender and the receiver never talk to each other directly. Both of them only know the Broker. This is called "Decoupling". The ESP32 doesn't need to know your phone's IP address, and the phone doesn't need to know where the ESP32 is.

Compared with HTTP: "asking over and over" vs "let me know"

Say you want to turn the LED on from your phone. With HTTP (no MQTT), the ESP32 has to keep asking a server, "Any new commands?". This approach is called Polling (asking again and again). With MQTT, the ESP32 connects once and keeps the connection open, and whenever a command arrives, the Broker sends it immediately over that open connection (Push).

Why is MQTT so lightweight?

MQTT was designed in 1999 to monitor oil pipelines over satellite links, where every byte cost money and the connection kept dropping. That's why its headers are so small, and why features like the "Last Will" and "retained messages" were built for a world of unreliable connections. It's exactly what a small sensor on ordinary Wi-Fi needs.

The main MQTT ideas, one at a time

1. Topics and their hierarchy

A Topic is a text string divided into several "levels" by /, just like a postal address or a folder path on a computer. For example:

  • home/livingroom/temp living room temperature
  • home/livingroom/humidity living room humidity
  • home/kitchen/temp kitchen temperature
  • home/kitchen/light/set kitchen light command

You don't need to "create" a Topic on the Broker in advance. As soon as someone publishes to it for the first time, it exists. Topics are case-sensitive: Home/Temp is different from home/temp.

Topic naming rules that will save you later

1) Go from general to specific: home/room/device/quantity. 2) Use only lowercase English letters, digits, dashes and /. Spaces and non-English letters are allowed by the protocol, but they cause trouble. 3) Don't start a Topic with /; /home/temp has an empty first level and is different from home/temp. 4) Use a /set suffix for commands so they don't get mixed up with state (/state).

2. Wildcards: subscribing to several topics at once

When you subscribe (only when subscribing, never when publishing), you can use two special characters:

3. QoS: how sure do we need to be that a message arrived?

QoS (Quality of Service) is a number from 0 to 2 that the sender picks for each message. The higher it is, the more certainty, but also the more back-and-forth messages.

An everyday example: the post office

QoS 0 = you drop an ordinary letter in the mailbox and walk away. It usually arrives, but if it gets lost, nobody finds out. QoS 1 = registered mail with a receipt. If the receipt doesn't come back, you send it again; the receiver might get two copies. QoS 2 = registered mail with a two-step confirmation; it arrives exactly once, but there's more paperwork.

A limit of the PubSubClient library

To stay lightweight, the library we use in this lesson (PubSubClient) only publishes with QoS 0, and when subscribing it only supports QoS 0 or 1. That's perfectly enough for learning projects and most home projects. If you ever need QoS 2, there are other libraries, such as the ESP-IDF built-in client (esp-mqtt).

4. Retained messages

Normally the Broker delivers a message to the subscribers who are connected at that moment, and then forgets it. Now imagine you switch your phone on at 9:00, but the ESP32 last sent its state at 8:59. The phone knows nothing until the next message.

If you send the message with the retain flag, the Broker keeps the last message on that Topic and hands it to every new subscriber right after they subscribe. It's like a "pinned message" at the top of a Telegram channel.

When to retain, and when not to

For state (online or offline, whether the LED is on or off, the latest temperature), retain is good. For commands (like "open the door"), retain is dangerous: every time the ESP32 resets and subscribes again, it receives the old command again and the door opens again!

5. The Last Will (Last Will and Testament)

If the ESP32 suddenly dies (a power cut or a Wi-Fi drop), it has no chance to say goodbye. MQTT has a solution for that moment: when it connects, the Client gives the Broker a "last will" message: "If I disappear without warning, publish this message on this Topic." If the Client disconnects politely (with DISCONNECT), the last will is not used.

6. Keep-alive: "Are you still there?"

How does the Broker find out the ESP32 has disappeared? With Keep-alive. The Client promises to send a message (or a small PINGREQ) at least every N seconds. If the Broker hears nothing for about 1.5 times that long, it considers the connection dead and publishes the last will. In PubSubClient the default is 15 seconds (you change it with setKeepAlive).

Why does this matter to you?

Because the library sends the PING itself, inside the mqtt.loop() function. If you put a delay(30000) in loop(), the ESP32 neither sends PINGs nor reads incoming messages; after about 22 seconds the Broker closes the connection, and you see error -3 (connection lost). That's why all timing in this lesson uses millis(), not delay.

7. Client ID: every device's ID card

Every Client sends an identifier (the Client ID) when it connects. An important rule: two Clients with the same ID can't be connected at the same time. If the second one connects, the Broker kicks the first one out. If both programs have "automatic reconnect", they keep kicking each other out and you see an endless connect/disconnect cycle. That's why we build the ID from the board's MAC address plus a random number.

Part A: the public HiveMQ broker (no sign-up)

The company HiveMQ runs a free public Broker for learning and testing: broker.hivemq.com on port 1883. No sign-up, no password. It's great for getting started.

A serious warning: this Broker is public

Anyone in the world can subscribe to any Topic, even # (that is, everything!). So: 1) Don't send any personal information, passwords or locations. 2) Don't control anything real and dangerous with it (a door lock, a heater, a water pump); anyone can send commands. 3) Pick a unique Topic name (for example esp32course/ali1234/...), otherwise your messages get mixed up with those of thousands of other students using a Topic like test/temp. The messages aren't encrypted either (port 1883 is plain text).

The complete program: publish the temperature and receive LED commands

#include <WiFi.h>
#include <PubSubClient.h>
#include <ArduinoJson.h>
#include <DHT.h>

// ---- Wi-Fi (keep this as is in Wokwi) ----
const char* WIFI_SSID = "Wokwi-GUEST";
const char* WIFI_PASS = "";

// ---- Public HiveMQ broker ----
const char* MQTT_HOST = "broker.hivemq.com";
const int   MQTT_PORT = 1883;

// Unique prefix: replace ali1234 with your own name and number
#define BASE "esp32course/ali1234"
const char* TOPIC_CLIMATE = BASE "/sensor/climate";
const char* TOPIC_CMD     = BASE "/led/set";
const char* TOPIC_STATUS  = BASE "/status";

const int LED_PIN = 4;
const int DHT_PIN = 13;

DHT dht(DHT_PIN, DHT22);
WiFiClient net;              // a raw TCP pipe
PubSubClient mqtt(net);      // MQTT over that same pipe

char clientId[40];
unsigned long lastPublish = 0;
unsigned long lastTry = 0;

// Called whenever a message arrives on a subscribed Topic
void onMessage(char* topic, byte* payload, unsigned int length) {
  char msg[32];
  unsigned int n = (length < sizeof(msg) - 1) ? length : sizeof(msg) - 1;
  memcpy(msg, payload, n);
  msg[n] = '\0';             // payload has no '\0' of its own!
  Serial.printf("<- [%s] %s\n", topic, msg);

  if (strcmp(topic, TOPIC_CMD) == 0) {
    if (strcmp(msg, "ON") == 0) {
      digitalWrite(LED_PIN, HIGH);
    } else if (strcmp(msg, "OFF") == 0) {
      digitalWrite(LED_PIN, LOW);
    } else {
      Serial.println("Unknown command (use ON or OFF)");
    }
  }
}

void connectWiFi() {
  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  Serial.print("WiFi");
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  Serial.print(" connected, IP: ");
  Serial.println(WiFi.localIP());
}

bool connectMqtt() {
  Serial.printf("MQTT: connecting as %s ... ", clientId);
  // Last will: if we drop without warning, the Broker writes offline to status
  if (mqtt.connect(clientId, TOPIC_STATUS, 1, true, "offline")) {
    Serial.println("OK");
    mqtt.publish(TOPIC_STATUS, "online", true);   // true means retained
    mqtt.subscribe(TOPIC_CMD, 1);
    return true;
  }
  Serial.printf("failed, state=%d\n", mqtt.state());
  return false;
}

void publishClimate() {
  float t = dht.readTemperature();
  float h = dht.readHumidity();
  if (isnan(t) || isnan(h)) {
    Serial.println("DHT22 read failed");
    return;
  }
  JsonDocument doc;
  doc["temp"] = serialized(String(t, 1));   // 24.3, with one decimal place
  doc["hum"] = serialized(String(h, 1));
  doc["uptime"] = millis() / 1000;
  char buf[128];
  serializeJson(doc, buf, sizeof(buf));
  bool ok = mqtt.publish(TOPIC_CLIMATE, buf);
  Serial.printf("-> %s %s\n", buf, ok ? "" : "(publish FAILED)");
}

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  dht.begin();
  connectWiFi();
  // Unique Client ID: the board's MAC + a random number
  String mac = WiFi.macAddress();   // like 24:6F:28:AB:CD:EF
  mac.replace(":", "");
  snprintf(clientId, sizeof(clientId), "esp32-%s-%04X", mac.c_str(), (unsigned)(esp_random() & 0xFFFF));
  mqtt.setServer(MQTT_HOST, MQTT_PORT);
  mqtt.setCallback(onMessage);
}

void loop() {
  if (WiFi.status() != WL_CONNECTED) {
    return;                  // Wi-Fi reconnects by itself (lesson 4.1)
  }
  if (!mqtt.connected()) {
    if (lastTry == 0 || millis() - lastTry > 5000) {   // one attempt every 5 seconds
      lastTry = millis();
      connectMqtt();
    }
    return;                  // do nothing else until we're connected
  }
  mqtt.loop();               // read incoming messages + send PINGs

  if (millis() - lastPublish >= 10000) {
    lastPublish = millis();
    publishClimate();
  }
}

This is the longest program you've seen so far, but it's built from familiar pieces. Click any card to highlight its lines:

  1. Four libraries. WiFi.h to connect to the router, PubSubClient.h for the MQTT language, ArduinoJson.h to build JSON text, and DHT.h to read the sensor. Each library does one job well. PubSubClient doesn't know anything about the internet by itself; it only speaks the MQTT "language" over a TCP connection that we hand it. This separation is what lets us make the connection secure (TLS) later by changing just one line.
  2. The Wi-Fi name and password. In the Wokwi simulator, the virtual network Wokwi-GUEST has no password. On a real board, write your own router's name and password. Wokwi has a virtual router that really is connected to the internet, so the simulated ESP32 can connect to the real HiveMQ too.
  3. The Broker address and port. broker.hivemq.com on port 1883, the standard port for unencrypted MQTT. Every service listens on a specific "door" (port). 1883 for plain MQTT and 8883 for secure MQTT (TLS) is a worldwide convention; you'll see both later.
  4. Building the Topic names. #define BASE creates a shared prefix. In C++, when two string constants are written next to each other (BASE "/led/set"), the compiler glues them together: "esp32course/ali1234/led/set". You change the prefix in one place and every Topic becomes unique. If you don't change ali1234 and your classmate doesn't either, you'll both be controlling each other's LEDs!
  5. Three main objects. dht is the sensor. net is a raw TCP connection. mqtt is the MQTT client, which takes net as its "pipe". Think of a letter and an envelope: PubSubClient writes the letter (the MQTT message), and WiFiClient puts it in a TCP envelope and sends it over Wi-Fi.
  6. Global variables. Room for the Client ID, and two "timers" for the last publish and the last connection attempt. The type is unsigned long because that's what millis() returns; with int it would overflow and break after about 24 days.
  7. The callback function's signature. Whenever a message arrives, PubSubClient calls this function with three inputs: the Topic name (a C string), the array of message bytes (payload) and its length. The signature (the types and order of the inputs) must be exactly this, or setCallback won't compile. This pattern is called a "callback": you hand over the function, and the library calls it whenever it needs to.
  8. MQTT's biggest trap: the payload is not a string! We copy the message bytes into a 32-byte array (at most 31 bytes) and add the '\0' at the end ourselves. In C++, string functions like strcmp and printf("%s") keep going until they reach a zero byte. The payload doesn't have that zero byte; so without this copy, strcmp runs past the end of the message and compares leftover memory too. The result: sometimes "ON" isn't recognized, or the program crashes. The n check also prevents writing outside the array if someone sends a very long message.
  9. Printing the incoming message. For example <- [esp32course/ali1234/led/set] ON. Always look first at exactly what arrived. Half of all MQTT problems are a message that arrived with an extra space, in lowercase, or on the wrong Topic.
  10. Making the decision. If the message is on the command Topic: ON turns the LED on, OFF turns it off, and anything else prints an error. We check the Topic first because later we may subscribe to several Topics, and all messages come to this one function. The last branch (unknown message) is for debugging: if you send on in lowercase, you'll see why it didn't work.
  11. Connecting to Wi-Fi. The same code as lesson 4.1: Station mode, start connecting, wait until connected, print the IP. Waiting here in setup with delay is fine, because without Wi-Fi the device can't do anything else anyway.
  12. Connecting to the Broker, with a last will. The inputs to connect, in order: the Client ID, the last-will Topic, the last-will QoS (1), the last-will retain flag (true) and its text (offline). The last will can only be set when connecting, not later. Making it retained means anyone who subscribes later immediately learns the device is off.
  13. After a successful connection. We publish the state online with retain (it overwrites the earlier last will), then subscribe to the command Topic with QoS 1. The subscribe must be repeated after every reconnect. We use a "clean session", which means the Broker forgets our earlier subscriptions after a disconnect. That's why subscribe lives inside this function, not in setup.
  14. If the connection failed. We print the mqtt.state() number. This number tells you exactly where the problem is (network, password, duplicate Client ID...). The table of what every number means is in the troubleshooting section.
  15. Reading the sensor and checking for errors. If the sensor doesn't answer, the DHT library returns NaN ("not a number"); we catch it with isnan and publish nothing. Publishing nan to a dashboard means a broken chart and a confused gauge. Sending no data is better than sending wrong data.
  16. Building JSON with ArduinoJson 7. JsonDocument doc; creates an empty document, which you fill with doc["key"] = value. serialized(String(t, 1)) puts the number into the JSON as raw text with exactly one decimal place. In version 7 the document size adjusts itself, so you no longer have to guess a capacity number as in version 6. String(t, 1) prevents numbers like 24.29999924 from being printed (a float in memory isn't exactly 24.3). Short JSON means a smaller message.
  17. Turning it into text and publishing. serializeJson writes the document into the buf array (with a '\0' at the end). mqtt.publish sends it to the Topic and returns true or false. If publish returns false, there are two common causes: the connection is down, or the message (Topic + text + header) is larger than the library's 256-byte buffer. Our 128-byte buffer is deliberately smaller than that.
  18. Building a unique Client ID. We take the board's MAC without the colons and add a random 4-digit hex number (from the hardware random number generator, esp_random()). The result is something like esp32-246F28ABCDEF-3A9C. Every real board's MAC is unique. But in Wokwi, all students may have the same MAC; the random number stops them from kicking each other off the public Broker.
  19. Registering the Broker and the callback. setServer only stores the address; the real connection happens later in loop. setCallback registers the onMessage function. We deliberately put the connection in loop so that a single piece of code handles both the "first connection" and "reconnecting after an outage".
  20. If Wi-Fi is down, wait. We return from loop and check again on the next pass. The ESP32 core reconnects Wi-Fi by itself by default (lesson 4.1). Trying to reach the Broker without Wi-Fi just wastes time.
  21. Non-blocking reconnection. If we're not connected to the Broker, we try at most once every 5 seconds, and loop is free between attempts. The bad, common version on the internet is a while (!mqtt.connected()) { ...; delay(5000); }, which can trap the program forever; even buttons and sensors stop working. With our approach, if you also want to read a button, it works between attempts. The lastTry == 0 condition makes the first attempt happen immediately. Keep in mind that connect() itself waits up to about 15 seconds (the socket timeout) if the server doesn't answer.
  22. The heart of the program: mqtt.loop(). It reads the messages that have arrived and calls onMessage, and sends the keep-alive PING when needed. If this line doesn't run, no command ever arrives, and after about 22 seconds the Broker considers the connection dead. Anything that stops loop for a long time (a long delay, a while loop) is this line's enemy.
  23. Publishing every 10 seconds with millis. If 10000 milliseconds have passed since the last publish, publish again. The DHT22 gives a fresh measurement at most once every 2 seconds, and room temperature barely changes in 10 seconds. Sending faster only wastes traffic and (on services like Adafruit IO) your quota.

When the network is to blame, not your code

Some school, university, office or public Wi-Fi networks (cafés, hotels) block ports 1883 and 8883 and only let ordinary web traffic through. If you get error -2 (network connection failed) while Wi-Fi is connected, first try the same program on your home network or your phone's hotspot. If it works there, the problem is the network route, not your code. The professional solution, which doesn't depend on the internet at all, is to run the Broker on your own computer (further down in this lesson).

TLS in plain words

TLS is what makes the green padlock next to a website's address in your browser. It does two jobs: 1) Encryption: messages are scrambled so that nobody along the way (say, on a café's Wi-Fi) can read them. 2) Server authentication: you make sure you really are talking to HiveMQ, not to a fake server pretending to be HiveMQ.

An everyday example: a sealed envelope and an ID card

Encryption is like putting your letter in a sealed envelope. But if you hand the envelope to the wrong person, the seal is useless! Authentication means checking the recipient's ID card before you hand over the envelope. The "root certificate" (Root CA) is like the official government stamp on that ID card: if the stamp is genuine, you accept the card.

If you put your code on GitHub, write secrets.h in your .gitignore file so it never gets uploaded (lesson 4.1). Thousands of passwords and API keys leak every year because they were written straight into the code. The root certificate in the program below is no worry; it's public, not secret.

// Called whenever a message arrives on a subscribed Topic
void onMessage(char* topic, byte* payload, unsigned int length) {
  char msg[32];
  unsigned int n = (length < sizeof(msg) - 1) ? length : sizeof(msg) - 1;
  memcpy(msg, payload, n);
  msg[n] = '\0';             // payload has no '\0' of its own!
  Serial.printf("<- [%s] %s\n", topic, msg);

  if (strcmp(topic, TOPIC_CMD) == 0) {
    if (strcmp(msg, "ON") == 0) {
      digitalWrite(LED_PIN, HIGH);
    } else if (strcmp(msg, "OFF") == 0) {
      digitalWrite(LED_PIN, LOW);
    } else {
      Serial.println("Unknown command (use ON or OFF)");
    }
  }
}

void connectWiFi() {
  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  Serial.print("WiFi");
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  Serial.print(" connected, IP: ");
  Serial.println(WiFi.localIP());
}

bool connectMqtt() {
  Serial.printf("MQTT: connecting as %s ... ", clientId);
  // Last will: if we drop without warning, the Broker writes offline to status
  if (mqtt.connect(clientId, MQTT_USER, MQTT_PASS,     // ★ + username and password
                   TOPIC_STATUS, 1, true, "offline")) {
    Serial.println("OK");
    mqtt.publish(TOPIC_STATUS, "online", true);   // true means retained
    mqtt.subscribe(TOPIC_CMD, 1);
    return true;
  }
  Serial.printf("failed, state=%d\n", mqtt.state());
  return false;
}

void publishClimate() {
  float t = dht.readTemperature();
  float h = dht.readHumidity();
  if (isnan(t) || isnan(h)) {
    Serial.println("DHT22 read failed");
    return;
  }
  JsonDocument doc;
  doc["temp"] = serialized(String(t, 1));   // 24.3, with one decimal place
  doc["hum"] = serialized(String(h, 1));
  doc["uptime"] = millis() / 1000;
  char buf[128];
  serializeJson(doc, buf, sizeof(buf));
  bool ok = mqtt.publish(TOPIC_CLIMATE, buf);
  Serial.printf("-> %s %s\n", buf, ok ? "" : "(publish FAILED)");
}

  pinMode(LED_PIN, OUTPUT);
  dht.begin();

  mac.replace(":", "");

  // net.setInsecure();        // ★ testing only: encryption without identity checks

  mqtt.setCallback(onMessage);
}

    return;                  // Wi-Fi reconnects by itself (lesson 4.1)
  }
  if (!mqtt.connected()) {
    if (lastTry == 0 || millis() - lastTry > 5000) {   // one attempt every 5 seconds
      lastTry = millis();
      connectMqtt();

    return;                  // do nothing else until we're connected
  }
  mqtt.loop();               // read incoming messages + send PINGs

  if (millis() - lastPublish >= 10000) {
    lastPublish = millis();
    publishClimate();
  }

  1. Part A's four libraries, plus WiFiClientSecure. WiFiClientSecure is the encrypted version of WiFiClient, with the mbedTLS library doing the TLS work inside it. Since PubSubClient only wants a "pipe", changing the type of pipe makes the whole connection secure and the rest of the MQTT code stays untouched.
  2. The passwords come from secrets.h. #include "secrets.h" (with quotes, meaning "look in this sketch's own folder") brings in the six names. The #ifndef MQTT_USER ... #endif block checks whether MQTT_USER exists; if you're still using the shorter secrets.h from lesson 4.1, the compiler prints a clear warning and uses placeholder values so the sketch still compiles. A clear "MQTT_USER is not defined in secrets.h" warning is much easier to understand than a pile of "was not declared" errors. With the placeholder password the Broker will refuse you (error 4 or 5), which reminds you to fill in the real one.
  3. Your Cluster address and port 8883. Copy the address from the Cluster's Overview tab. On port 8883 the Broker expects the TLS "handshake" to happen first. If you accidentally connect a plain WiFiClient to 8883, the connection fails with error -2 or -4.
  4. Topics and pins: the same as part A. The same prefix, the same three Topics, the LED on GPIO4 and the DHT22 on GPIO13. On your own Cluster, nobody else can see your Topics, but a unique prefix is still a good habit: the day you move a project to another Broker, nothing collides.
  5. The root certificate (Root CA). This text is the public key of ISRG, the organization that issues Let's Encrypt certificates. R"EOF( ... )EOF" is a C++ "raw string", which lets you write multi-line text without putting \n at the end of every line. The HiveMQ Cloud server's certificate is signed by Let's Encrypt, and Let's Encrypt's signature is signed by ISRG Root X1. With the root, the ESP32 can check the whole chain. This certificate is valid until June 2035; but if HiveMQ ever changes its certificate issuer, you'll have to update it. Always check the current certificate in HiveMQ's documentation.
  6. The secure pipe. Now net is the secure type, and mqtt runs on top of it. TLS needs about 40 to 50 KB of RAM for buffers and cryptographic calculations. The ESP32 has that easily (which is why this isn't possible on smaller boards like the Arduino UNO).
  7. The global variables and the callback: identical to part A. Copy the payload into a buffer, add '\0', check the Topic, then ON or OFF. TLS lives entirely inside the pipe. The messages that come out of it look exactly the same as before, so the code that handles them doesn't change at all.
  8. Connecting to Wi-Fi: the same function. Only now WIFI_SSID and WIFI_PASS come from secrets.h. In part A they were variables; here they're #defines. WiFi.begin doesn't care: in both cases it receives a piece of text.
  9. connect with a username and password. The order of the inputs: ID, user, password, then the same four last-will inputs. The line is split in two only so it fits on the screen. PubSubClient has several versions of connect (overloads); the compiler decides which one you want from the number and types of the inputs. Don't change the order.
  10. publishClimate: the same as part A. Read the sensor, build the JSON, publish. The data is encrypted on its way out by the pipe, not by this function.
  11. The start of setup: the same as part A. Serial, the LED pin, the sensor, Wi-Fi and the unique Client ID. Client IDs must be unique on HiveMQ Cloud too; two boards with the same ID would keep kicking each other off.
  12. setCACert vs setInsecure. setCACert means "only trust a server whose certificate was signed by this root". setInsecure means "encrypt, but believe anyone who says they're HiveMQ". Either one must be called before the first connect. The honest truth: setInsecure stops someone who is only listening, but it doesn't stop someone who pretends to be the server (a man-in-the-middle attack); that attacker would then steal your MQTT password too. It's acceptable for a quick test, but not for a device that stays in your home.
  13. Registering the Broker, and loop: the same as part A. Non-blocking reconnection every 5 seconds, mqtt.loop(), and a publish every 10 seconds. The only difference you'll notice: each connection attempt takes a second or two longer, because of the TLS handshake. That's another reason to keep reconnection attempts spaced out.
If the TLS connection fails

In the Serial Monitor you'll see something like X509 - Certificate verification failed or -2. Check, in order: 1) Was the Cluster address copied exactly? 2) Is the port 8883? 3) Was the certificate copied completely, with no missing lines? 4) To diagnose, try once with setInsecure(): if that connects, the problem is only the certificate.

Part C: a ready-made dashboard with Adafruit IO

So far you've only seen the data as text. Adafruit IO is an IoT service that has an MQTT Broker, stores your data, and has a graphical dashboard (gauges, charts, switches, sliders), without a single line of web code. That means in 15 minutes you have a remote-control app that opens on your phone too.

Adafruit IO concepts

  • Feed: a named "stream of data", such as temperature or led. Every value you send to it is stored with a date and time. Each Feed has a key (its name in lowercase letters and dashes) that is used in the Topic.
  • Dashboard: a page where you arrange blocks. Each block is linked to a Feed: a gauge shows the temperature Feed, and a switch (Toggle) writes to the command Feed.
  • AIO Key: your account's password for devices. In MQTT, the username = your Adafruit username, and the password = the AIO Key.
  • Topic format: username/feeds/feed-key; for example ali_maker/feeds/temperature.

  memcpy(msg, payload, n);

bool connectMqtt() {
  char id[24];
  snprintf(id, sizeof(id), "esp32-%04X", (unsigned)(esp_random() & 0xFFFF));
  if (!mqtt.connect(id, AIO_USER, AIO_KEY)) {
    Serial.printf("MQTT failed, state=%d\n", mqtt.state());
    return false;
  }
  Serial.println("Adafruit IO connected");
  mqtt.subscribe(TOPIC_LED);
  mqtt.subscribe(TOPIC_THROTTLE);
  mqtt.subscribe(TOPIC_ERRORS);
  mqtt.publish(TOPIC_LED_GET, "");   // "send me the latest led value"

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  dht.begin();

void loop() {

  1. The username, the AIO Key and the Wi-Fi come from secrets.h. The same file as part B; AIO_USER and AIO_KEY are exactly the ones you copied from the My Key page. The username is case-sensitive. The #ifndef guard works just like in part B. In Adafruit IO the username has two roles: it logs you in to the Broker, and it starts every Topic. If it's wrong in secrets.h, either you can't connect (error 5) or your publishes are rejected.
  2. Adafruit's own Broker. io.adafruit.com on port 1883. On 1883, your AIO key is sent without encryption. Adafruit itself strongly recommends a secure connection on port 8883; for that, use WiFiClientSecure exactly as in part B (with setInsecure() to start with, and for serious work with the root certificate found in the official examples of the Adafruit MQTT library).
  3. The three Feeds' Topics. AIO_USER "/feeds/temperature" becomes "your_username/feeds/temperature" at compile time; the same goes for humidity and led. Adafruit IO only accepts Topics in the format username/feeds/key; anything else is rejected with a "not a valid resource topic" message on the errors Topic. That's also why the Feed keys you created in step 2 must match these names letter for letter.
  4. The special /get Topic. If you publish a message (even an empty one) on .../led/get, Adafruit IO sends the latest value of the led Feed, just to you. Adafruit IO doesn't support the retain flag. Without this trick, if the ESP32 resets, it doesn't know whether the LED should be on or off until someone taps the switch again.
  5. The throttle and errors Topics. Adafruit IO sends rate-limit warnings and your errors (for example a wrong Topic) on these two Topics. Error messages aren't stored; if you aren't subscribed at the moment they happen, you'll never find out why your data didn't reach the dashboard.
  6. A shorter callback. As before, we turn the payload into a string with '\0' (a 128-byte buffer this time, because error messages are longer). If the message came from the led Feed, ON means on and anything else means off. The ternary operator condition ? HIGH : LOW is a short if/else on one line. Throttle and errors messages are just printed.
  7. Connecting with the username and key. We build a random Client ID and connect with connect(id, user, key). In Adafruit IO, your identity comes from the username and key, and the Client ID only has to be different among your own devices. A random number from esp_random() makes a clash very unlikely.
  8. Subscribing to three Topics and asking for the latest value. After subscribing to the led Feed, we send an empty message to /get so the switch's current state arrives. The order matters: subscribe first, then get. The other way round, the answer arrives before the subscription and is lost.
  9. A compact Wi-Fi connection. The same job as connectWiFi() in the first program, in two lines, with the name and password from secrets.h. This keeps the example short; in a real project, use the full version that prints its progress.
  10. Reconnecting every 10 seconds. The same non-blocking pattern, this time with a 10-second gap. Adafruit IO is also sensitive to very fast connection attempts and may block you temporarily. A longer gap between attempts is more polite.
  11. Publishing the temperature and humidity as plain numbers. Both values are read first; only if both are valid, snprintf("%.1f") turns each one into text with one decimal place (for example 24.5) and publishes it to its own Feed. The same buf is reused for the second number. Adafruit IO's gauge and chart blocks want a simple number. If you send JSON, the Feed stores it as text and the gauge shows nothing. Two Feeds every 10 seconds = 12 data points per minute, the same sum as in the "Do the math" box, well under the quota of 30.

Upload the program, open the dashboard on your phone and flip the switch. The LED should react in less than a second, and both gauges should update every 10 seconds. 🎉

Then the ESP32 and your phone (while it's on your home Wi-Fi) work together even without internet.

Coach's advice

In MQTT you have three separate parts: the device, the Broker and the receiver. When something doesn't work, rule them out one at a time, like a detective. First, subscribe to prefix/# with MQTTX or the HiveMQ page and just watch: do the ESP32's messages reach the Broker? If not, the problem is in the device (read the state number). If they do, send a command from the same tool: does the ESP32 print it in Serial? Never change the ESP32 code and the dashboard at the same time; two variables at once means you'll never know which one fixed it. And one iron rule: no long delays in loop. Ninety percent of the strange connect/disconnect problems students send me come down to exactly that.

Lesson quiz

In MQTT, how do the ESP32 and the phone communicate?

  1. The phone connects directly to the ESP32's IP address
  2. Both connect to the same Broker, and the Broker routes messages by Topic
  3. The ESP32 acts as the Broker and the phone connects to it
  4. Over Bluetooth
The Broker is like Telegram: the sender and receiver only know it, not each other. That's why it works from outside your home too.

Which message does a subscription to home/+/temp not receive?

  1. home/kitchen/temp
  2. home/bedroom2/temp
  3. home/floor1/kitchen/temp
  4. home/livingroom/temp
+ replaces exactly one level. floor1/kitchen is two levels. To catch it you'd write home/# or home/+/+/temp.

You sent the message "open the door" with retain. What's the danger?

  1. Every time the device resets and subscribes again, it receives the old command and the door opens again
  2. The message isn't encrypted
  3. The message is never delivered
  4. The Broker's memory fills up
retain is for "state" (online, the latest temperature), not for "commands". A retained command is a command that runs again and again.

In your callback you wrote if (strcmp((char*)payload, "ON") == 0), and it sometimes works and sometimes doesn't. Why?

  1. strcmp isn't suitable for comparing text
  2. Because ON should be lowercase
  3. Because QoS is zero
  4. Because the payload doesn't end with a zero byte, so strcmp runs past the end of the message
The payload is a byte array with a known length, not a C string. Always copy it into a buffer using length and add a '\0'.

Your ESP32 drops off the Broker about every 20 seconds, and state() returns -3. You have a delay(30000) in loop. How are the two connected?

  1. The 256-byte buffer is full
  2. During those 30 seconds mqtt.loop() doesn't run, no PING is sent, and after about 1.5 times the Keep-alive (15 seconds) the Broker considers the connection dead
  3. delay makes Wi-Fi disconnect
  4. The password is wrong
Write your timing with millis() so that mqtt.loop() keeps running.

Why isn't setInsecure() recommended for a device that runs at home all the time?

  1. Because messages aren't encrypted
  2. Because it makes the connection very slow
  3. Because the server's identity isn't checked, so a fake server can pretend to be the Broker and get your password
  4. Because it doesn't work with HiveMQ Cloud
Encryption without authentication is like a sealed envelope you hand to anyone who says "I'm the mail carrier". With setCACert you check their ID card.

Exercise 1: only send when it changes

Change the part A program so it reads the temperature every 2 seconds, but only publishes when it differs by at least 0.3 degrees from the last published value, or when 60 seconds have passed since the last publish (so the dashboard knows the device is alive).

Hint

Keep a global variable float lastSent = -100;. The publish condition: fabs(t - lastSent) >= 0.3 || millis() - lastPublish >= 60000. After publishing, lastSent = t.

What should you see?

With the Wokwi circuit from part A (DHT22 left at 24.5 °C), the Serial Monitor shows something like this. Your IP, Client ID and uptime numbers will differ:

Full answer with explanation

This is the complete part A program; only two new global variables and the end of loop() have changed.

#include <WiFi.h>
#include <PubSubClient.h>
#include <ArduinoJson.h>
#include <DHT.h>

// ---- Wi-Fi (keep this as is in Wokwi) ----
const char* WIFI_SSID = "Wokwi-GUEST";
const char* WIFI_PASS = "";

// ---- Public HiveMQ broker ----
const char* MQTT_HOST = "broker.hivemq.com";
const int   MQTT_PORT = 1883;

// Unique prefix: replace ali1234 with your own name and number
#define BASE "esp32course/ali1234"
const char* TOPIC_CLIMATE = BASE "/sensor/climate";
const char* TOPIC_CMD     = BASE "/led/set";
const char* TOPIC_STATUS  = BASE "/status";

const int LED_PIN = 4;
const int DHT_PIN = 13;

DHT dht(DHT_PIN, DHT22);
WiFiClient net;              // a raw TCP pipe
PubSubClient mqtt(net);      // MQTT over that same pipe

unsigned long lastTry = 0;
float lastSent = -100;       // last published temperature (-100 = nothing yet)
unsigned long lastRead = 0;  // when we last read the sensor

// Called whenever a message arrives on a subscribed Topic
void onMessage(char* topic, byte* payload, unsigned int length) {
  char msg[32];
  unsigned int n = (length < sizeof(msg) - 1) ? length : sizeof(msg) - 1;
  memcpy(msg, payload, n);
  msg[n] = '\0';             // payload has no '\0' of its own!
  Serial.printf("<- [%s] %s\n", topic, msg);

  if (strcmp(topic, TOPIC_CMD) == 0) {
    if (strcmp(msg, "ON") == 0) {
      digitalWrite(LED_PIN, HIGH);
    } else if (strcmp(msg, "OFF") == 0) {
      digitalWrite(LED_PIN, LOW);
    } else {
      Serial.println("Unknown command (use ON or OFF)");
    }
  }
}

  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  Serial.print("WiFi");
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  Serial.print(" connected, IP: ");

bool connectMqtt() {
  Serial.printf("MQTT: connecting as %s ... ", clientId);
  // Last will: if we drop without warning, the Broker writes offline to status
  if (mqtt.connect(clientId, TOPIC_STATUS, 1, true, "offline")) {
    Serial.println("OK");
    mqtt.publish(TOPIC_STATUS, "online", true);   // true means retained
    mqtt.subscribe(TOPIC_CMD, 1);
    return true;
  }
  Serial.printf("failed, state=%d\n", mqtt.state());
  return false;
}

void publishClimate() {
  float t = dht.readTemperature();
  float h = dht.readHumidity();
  if (isnan(t) || isnan(h)) {
    Serial.println("DHT22 read failed");
    return;
  }
  JsonDocument doc;
  doc["temp"] = serialized(String(t, 1));   // 24.3, with one decimal place
  doc["hum"] = serialized(String(h, 1));
  doc["uptime"] = millis() / 1000;
  char buf[128];
  serializeJson(doc, buf, sizeof(buf));
  bool ok = mqtt.publish(TOPIC_CLIMATE, buf);
  Serial.printf("-> %s %s\n", buf, ok ? "" : "(publish FAILED)");
}

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  dht.begin();
  connectWiFi();
  // Unique Client ID: the board's MAC + a random number
  String mac = WiFi.macAddress();   // like 24:6F:28:AB:CD:EF
  mac.replace(":", "");
  snprintf(clientId, sizeof(clientId), "esp32-%s-%04X", mac.c_str(), (unsigned)(esp_random() & 0xFFFF));
  mqtt.setServer(MQTT_HOST, MQTT_PORT);
  mqtt.setCallback(onMessage);
}

void loop() {
  if (WiFi.status() != WL_CONNECTED) {
    return;                  // Wi-Fi reconnects by itself (lesson 4.1)
  }
  if (!mqtt.connected()) {
    if (lastTry == 0 || millis() - lastTry > 5000) {   // one attempt every 5 seconds
      lastTry = millis();
      connectMqtt();
    }
    return;                  // do nothing else until we're connected
  }
  mqtt.loop();               // read incoming messages + send PINGs

  if (millis() - lastRead >= 2000) {             // read every 2 seconds
    lastRead = millis();
    float t = dht.readTemperature();
    if (isnan(t)) return;                        // failed read: try again in 2 s
    bool changed = fabs(t - lastSent) >= 0.3;          // moved at least 0.3 degrees?
    bool heartbeat = millis() - lastPublish >= 60000;  // 60 s without a publish?
    if (changed || heartbeat) {
      Serial.print(changed ? "(change) " : "(heartbeat) ");
      lastPublish = millis();
      lastSent = t;
      publishClimate();
    }
  }
}
  1. Same as part A. Libraries, Wi-Fi, Broker, Topics, pins and the objects are unchanged. The exercise only changes when we publish, not what or where, so everything else stays as it was.
  2. Two new memories. lastSent holds the last temperature we published, and lastRead holds the time of the last sensor reading. To decide "has it changed enough?" we need the old value. Starting at -100 (a temperature a room never has) makes sure the very first reading counts as a change and is published at once.
  3. Functions, setup() and the start of loop(), unchanged. publishClimate() still reads the sensor itself and builds the JSON. It reads the sensor a second time, but the DHT library returns its saved value if you ask again within 2 seconds, so the published number is the same one we just compared.
  4. A reading every 2 seconds. Timed with millis(), like the 10-second publish in part A; a failed reading simply waits for the next round. The DHT22 can't give a fresh value faster than every 2 seconds. With millis() instead of delay(), mqtt.loop() keeps running and LED commands still arrive at once.
  5. The two reasons to publish. changed is true when the difference (without its sign, thanks to fabs) is at least 0.3; heartbeat is true when 60 seconds have passed since the last publish. fabs catches a rise and a drop alike. Without the heartbeat, a room with a steady temperature would stay silent for hours and the dashboard couldn't tell "nothing changed" from "the device is dead".
  6. Publish, remember, and say why. We print the reason, save the time and the value, and call publishClimate(). lastSent must be updated only when we really publish; otherwise a slow drift of 0.1 degrees per reading would never add up to 0.3 and would never be reported. The printed reason lets you check the logic in the Serial Monitor.

Exercise 2: report the LED state

After every command, have the ESP32 publish the LED's real state on the Topic .../led/state with retain (ON or OFF). Why must this Topic be different from .../led/set?

Hint

Inside onMessage, after digitalWrite, call mqtt.publish(TOPIC_STATE, msg, true). Think about what would happen after publishing if state and set were the same Topic and the ESP32 were subscribed to it.

What should you see?

Full answer with explanation

Why two Topics: if state and set were the same Topic, the ESP32 (which is subscribed to it) would receive its own message again, carry it out again and publish again: an endless loop. There's a second problem too: the state is retained, so a retained "ON" on the command Topic would switch the LED on again at every reconnect, even if someone switched it off in the meantime. Keeping "commands" (set, without retain) apart from "state" (state, with retain) is the standard pattern used by systems like Home Assistant.

Exercise 3: two devices, one dashboard

If you have two ESP32s (or two Wokwi tabs), run both with the prefixes .../room1 and .../room2. In MQTTX, see the temperature of both rooms with just one Subscribe.

What should you see?

In MQTTX, one subscription to esp32course/ali1234/+/sensor/climate (with your own prefix) shows messages from both rooms, each with its full Topic, for example:

esp32course/ali1234/room1/sensor/climate  {"temp":24.5,"hum":40.0,"uptime":42}
esp32course/ali1234/room2/sensor/climate  {"temp":19.0,"hum":55.0,"uptime":37}
esp32course/ali1234/room1/sensor/climate  {"temp":24.5,"hum":40.0,"uptime":52}
esp32course/ali1234/room2/sensor/climate  {"temp":19.0,"hum":55.0,"uptime":47}
  • Each board's Serial Monitor shows only its own -> lines, one every 10 seconds.
  • Set a different temperature on each DHT22 (in Wokwi: click the sensor) so you can tell the rooms apart.
  • Both boards stay connected. If one keeps dropping and reconnecting, the two have the same Client ID; our code builds it from the MAC plus a random number, so this only happens if you typed a fixed ID.
  • Sending ON to .../room1/led/set switches on only room 1's LED.
Full answer with explanation

Put the room name into the Topic, one level below your prefix: esp32course/ali1234/room1/sensor/climate and .../room2/sensor/climate. The + wildcard matches exactly one level, so in MQTTX you subscribe to esp32course/ali1234/+/sensor/climate. (esp32course/ali1234/# would also work, but it also brings the status and LED messages.) The same program runs on both boards; only one line differs.

#include <WiFi.h>
#include <PubSubClient.h>
#include <ArduinoJson.h>
#include <DHT.h>

// ---- Wi-Fi (keep this as is in Wokwi) ----
const char* WIFI_SSID = "Wokwi-GUEST";
const char* WIFI_PASS = "";

// ---- Public HiveMQ broker ----
const char* MQTT_HOST = "broker.hivemq.com";
const int   MQTT_PORT = 1883;

// Unique prefix: replace ali1234 with your own name and number
#define BASE "esp32course/ali1234"
#define ROOM "room1"         // ★ on the second board (or tab): "room2"
const char* TOPIC_CLIMATE = BASE "/" ROOM "/sensor/climate";
const char* TOPIC_CMD     = BASE "/" ROOM "/led/set";
const char* TOPIC_STATUS  = BASE "/" ROOM "/status";

const int LED_PIN = 4;
const int DHT_PIN = 13;

DHT dht(DHT_PIN, DHT22);
WiFiClient net;              // a raw TCP pipe
PubSubClient mqtt(net);      // MQTT over that same pipe

char clientId[40];
unsigned long lastPublish = 0;
unsigned long lastTry = 0;

// Called whenever a message arrives on a subscribed Topic
void onMessage(char* topic, byte* payload, unsigned int length) {
  char msg[32];
  unsigned int n = (length < sizeof(msg) - 1) ? length : sizeof(msg) - 1;
  memcpy(msg, payload, n);
  msg[n] = '\0';             // payload has no '\0' of its own!
  Serial.printf("<- [%s] %s\n", topic, msg);

  if (strcmp(topic, TOPIC_CMD) == 0) {
    if (strcmp(msg, "ON") == 0) {
      digitalWrite(LED_PIN, HIGH);
    } else if (strcmp(msg, "OFF") == 0) {
      digitalWrite(LED_PIN, LOW);
    } else {
      Serial.println("Unknown command (use ON or OFF)");
    }
  }
}

void connectWiFi() {
  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  Serial.print("WiFi");
  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }
  Serial.print(" connected, IP: ");
  Serial.println(WiFi.localIP());
}

bool connectMqtt() {
  Serial.printf("MQTT: connecting as %s ... ", clientId);
  // Last will: if we drop without warning, the Broker writes offline to status
  if (mqtt.connect(clientId, TOPIC_STATUS, 1, true, "offline")) {
    Serial.println("OK");
    mqtt.publish(TOPIC_STATUS, "online", true);   // true means retained
    mqtt.subscribe(TOPIC_CMD, 1);
    return true;
  }
  Serial.printf("failed, state=%d\n", mqtt.state());
  return false;
}

void publishClimate() {
  float t = dht.readTemperature();
  float h = dht.readHumidity();
  if (isnan(t) || isnan(h)) {
    Serial.println("DHT22 read failed");
    return;
  }
  JsonDocument doc;
  doc["temp"] = serialized(String(t, 1));   // 24.3, with one decimal place
  doc["hum"] = serialized(String(h, 1));
  doc["uptime"] = millis() / 1000;
  char buf[128];
  serializeJson(doc, buf, sizeof(buf));
  bool ok = mqtt.publish(TOPIC_CLIMATE, buf);
  Serial.printf("-> %s %s\n", buf, ok ? "" : "(publish FAILED)");
}

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  dht.begin();
  connectWiFi();
  // Unique Client ID: the board's MAC + a random number
  String mac = WiFi.macAddress();   // like 24:6F:28:AB:CD:EF
  mac.replace(":", "");
  snprintf(clientId, sizeof(clientId), "esp32-%s-%04X", mac.c_str(), (unsigned)(esp_random() & 0xFFFF));
  mqtt.setServer(MQTT_HOST, MQTT_PORT);
  mqtt.setCallback(onMessage);
}

void loop() {
  if (WiFi.status() != WL_CONNECTED) {
    return;                  // Wi-Fi reconnects by itself (lesson 4.1)
  }
  if (!mqtt.connected()) {
    if (lastTry == 0 || millis() - lastTry > 5000) {   // one attempt every 5 seconds
      lastTry = millis();
      connectMqtt();
    }
    return;                  // do nothing else until we're connected
  }
  mqtt.loop();               // read incoming messages + send PINGs

  if (millis() - lastPublish >= 10000) {
    lastPublish = millis();
    publishClimate();
  }
}
  1. The room name. ROOM is "room1" on the first board; before uploading to the second board (or starting the second Wokwi tab), change it to "room2". A #define at the top is the one place to change, so the rest of the code stays identical on every device.
  2. Topics with the room inside. The compiler glues neighbouring strings together, so BASE "/" ROOM "/sensor/climate" becomes "esp32course/ali1234/room1/sensor/climate". The room goes in the middle so that a single + can stand in for it. The command and status Topics get the room too, so each LED listens only to its own room and each Last Will reports the right device.
  3. A unique Client ID (unchanged). MAC address plus a random number. The Broker allows only one connection per Client ID. Two boards with the same ID would kick each other off endlessly. With the MAC in the ID, two boards (or two Wokwi tabs, which get different random numbers) never collide.

The lesson in three lines

In MQTT, every Client connects only to the Broker, and they Publish and Subscribe on Topics (with the + and # wildcards); QoS, retain and the Last Will were built for unreliable connections. With PubSubClient: terminate the payload with '\0' yourself, build a unique ID, subscribe again after every reconnect, and keep mqtt.loop() running without delays. For security, use TLS on 8883 with setCACert; Adafruit IO and a local Mosquitto are two quick routes to a dashboard and to independence.
