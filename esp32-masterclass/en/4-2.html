Safety first: mains voltage can kill

A relay can switch mains power (120 V in North America, 230 V in Europe), and the modules even have 10A 250VAC printed on them. But this lesson has no mains wiring instructions, and it never will. Mains voltage can kill by passing through your heart, it causes sparks and fires on a breadboard, and cheap relay modules don't have enough insulation distance. Until you've had hands-on electrical training and an experienced person is next to you, work only with an LED or a low-voltage load (for example a 12 V LED strip or a 5 V fan with its own adapter). For real household appliances, use a standard, certified "smart plug" product.

HTTP from zero: how do a browser and a server talk?

Every time you type an address into a browser, two programs have a conversation:

  • Client: your browser. It sends a request.
  • Server: a program that waits for requests and sends back a response. Today, your ESP32 is the server.

The language of this conversation is HTTP: a simple text-based agreement that both sides understand.

An everyday example: a restaurant

You (the browser) sit down in a restaurant and tell the waiter: "A cup of tea, please." That's the request. The kitchen (the server) makes the tea, and the waiter brings it with a label: "Here you go, tea" (a response with code 200, meaning "success"). If you order something that isn't on the menu, you hear: "We don't have that" (code 404). The important part: the kitchen never comes to you on its own; you always have to order. That's exactly why our page "asks" once every second.

URL: the exact address of something

In the address http://192.168.1.37/api/state:

PartMeaning
http://The language of the conversation (the protocol). No "s", which means it isn't encrypted.
192.168.1.37The server's address on the network (the board's IP, which we printed in lesson 4.1).
:80 (invisible)The port: the building's "door" number. HTTP uses door number 80 by default, so you don't need to write it.
/api/stateThe path: which page or which action. A plain / means the home page.
?on=1 (in some addresses)A parameter (query): extra information in the form name=value.

GET and POST: two kinds of request

  • GET means "give me something". When you type an address into the browser, you always send a GET. A GET should never change anything.
  • POST means "do this / take this". We use POST to change a state (like switching the relay on).
Why switch the relay with POST and not GET?

Browsers, link previews in messaging apps and some browser extensions sometimes open addresses with GET on their own, before you click, so the page loads faster. If switching the relay on were a GET such as /relay/on, just sending the link in a chat could switch on the relay in your house! Nobody "prefetches" a POST. Simple rule: read with GET, change with POST.

Status codes: what did the server answer?

CodeNameMeaning
200OKEverything went fine; here's your answer.
400Bad RequestYour request was incomplete or wrong (for example, you didn't send a required parameter).
401UnauthorizedGive a username and password first.
404Not FoundNo such path exists.
500Internal Server ErrorThe server itself broke.

A real HTTP request and response look like this; it's just plain text:

GET /api/state HTTP/1.1
Host: 192.168.1.37
User-Agent: Mozilla/5.0 (Android)

HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 37

{"led":true,"relay":false,"pot":2048}
  1. The browser's request. First line: the type (GET), the path (/api/state) and the HTTP version. Then the headers: Host is the server's address and User-Agent says which browser this is. An empty line (line 4) marks the end of the headers. The WebServer library reads all of this for you and hands you just the path and the parameters.
  2. The ESP32's response. The first line is the status code (200 OK). Content-Type says what kind of content this is (text/html for a page, application/json for data). Content-Length is the length of the content in bytes. The browser uses Content-Type to decide whether to show the content as a page or hand it to JavaScript as data. Get it wrong and your page shows up as raw text.
  3. The response body. The content itself; here, a piece of JSON text. JSON is the standard format for exchanging data on the web: "name":value pairs inside curly braces. Humans can read it, and JavaScript converts it in a single line.

Today's whole conversation at a glance:

sequenceDiagram
  participant B as Phone browser
  participant E as ESP32 web server
  B->>E: GET /
  E-->>B: 200 OK + HTML page
  loop every 1 second
    B->>E: GET /api/state
    E-->>B: 200 OK + status JSON
  end
  Note over B: User taps the ON button
  B->>E: POST /api/led?on=1
  Note over E: digitalWrite(4, HIGH)
  E-->>B: 200 OK + new status JSON
  B->>E: GET /favicon.ico
  E-->>B: 404 Not Found

The browser sends that last request by itself to fetch the little tab icon. We don't have an icon, so we return 404; that's completely normal.

HTML in two minutes

A web page is written in a language called HTML. HTML is made of "tags": <h1> starts a heading and </h1> ends it. That's it!

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <title>My page</title>
</head>
<body>
  <h1>Hello</h1>
  <p>This is a paragraph</p>
  <button onclick="alert('Hello')">Button</button>
</body>
</html>
  1. The skeleton. <!DOCTYPE html> says "this is modern HTML". Everything goes inside <html>, and lang="en" tells the browser the page is in English. (For a right-to-left language such as Persian, you would add dir="rtl" here.) Without DOCTYPE, the browser switches into a "compatibility mode for old pages" and the page looks strange.
  2. head: behind-the-scenes information. charset="utf-8" makes non-English characters (accents, Persian, emoji) display correctly, and title is the text shown on the browser tab. If you leave out charset, such text shows up as garbled characters, for example "CafÃ©" instead of "Café".
  3. body: what the user sees. h1 is a big heading, p a paragraph, button a button. onclick says which JavaScript code runs on a click. Our project page is built with exactly these few tags, plus a little CSS for looks (color and size) and a little JavaScript for talking to the ESP32.

Save this file on your laptop as page.html and double-click it to open it in your browser. Congratulations, your first web page!

The relay module: a quick recap

You met the relay properly in lesson 3.4: a switch flipped by a small electromagnet, with COM, NO and NC screw terminals, packed on a module together with the transistor and diode that let a GPIO drive it. Three reminders for this lesson:

  • Control side: VCC, GND and IN go to the ESP32. Load side: in this lesson we connect nothing to the screw terminals (or, if you like, a low-voltage load on COM and NO).
  • Active-LOW: most modules switch on when IN is LOW. We use the same RELAY_ACTIVE_LOW constant and setRelay() function as in lesson 3.4.
  • 3.3 V compatibility: if your 5 V module never switches off, read "Why 3.3 V usually works, but not always" in lesson 3.4 (a "3.3V trigger" module, or the JD-VCC wiring).
With numbers

With an active-LOW module: digitalWrite(26, LOW) → about 0 V on IN → the small LED on the module lights, "click", COM connects to NO. digitalWrite(26, HIGH) → 3.3 V on IN → the relay is off. Our code has a constant called RELAY_ACTIVE_LOW that handles this reversal in one place, so the rest of the program only has to say "on" or "off".

Wiring diagram

Three parts: the LED on GPIO4, the relay input on GPIO26 and the potentiometer on GPIO34.

Why these three pins?

GPIO4 is our usual safe pin for the LED. GPIO26 for the relay: it isn't a strapping pin, and unlike GPIO14 and GPIO15 it doesn't output a PWM signal during boot, so the relay doesn't "click click" when the board powers up. GPIO34 for the potentiometer, because it's on ADC1. The most important hardware point in this lesson: while Wi-Fi is on, ADC2 doesn't work (the radio uses it). So in any Wi-Fi project, connect analog sensors only to ADC1 pins: GPIO32 to GPIO39. And connect the potentiometer to 3V3, not 5V; the ESP32's pins can't handle 5 volts.

The board's 5V pin passes the USB cable's 5 V straight out, and that's enough for the relay coil (about 70 mA). Because the module takes its VCC and GND from the ESP32 board, the two share a ground and there's no real isolation; that's fine for a small relay and a low-voltage load. For full isolation with a separate coil supply, use the JD-VCC wiring from lesson 3.4. If you don't have a relay module, no problem: wire a second LED with a resistor like the first one, but from 3V3 to GPIO26 (anode toward 3V3). That LED then behaves just like an active-LOW relay: it lights on LOW. That's what we did in Wokwi too.

The complete program: a tiny smart home

This program is longer than in previous lessons, but it's built from a few simple pieces. We'll go through it piece by piece.

#include <WiFi.h>
#include <WebServer.h>
#include <ESPmDNS.h>

const char* WIFI_SSID = "Wokwi-GUEST";      // your network name
const char* WIFI_PASS = "";                 // your network password

const int LED_PIN   = 4;                    // a regular LED
const int RELAY_PIN = 26;                   // the relay module's IN input
const int POT_PIN   = 34;                   // potentiometer (ADC1, works with Wi-Fi)
const bool RELAY_ACTIVE_LOW = true;         // most relay modules turn on with LOW

WebServer server(80);                       // server on port 80 (the standard HTTP port)
bool ledOn = false;
bool relayOn = false;

// the complete web page, inside a raw string literal
const char INDEX_HTML[] PROGMEM = R"rawliteral(
<!DOCTYPE html>
<html lang="en">
<head>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width, initial-scale=1">
<title>ESP32 Home</title>
<style>
  body { font-family: sans-serif; text-align: center; background: #f2f4f8; }
  .card { background: #fff; max-width: 340px; margin: 14px auto; padding: 12px; border-radius: 12px; }
  button { font-size: 20px; padding: 10px 24px; margin: 4px; border: 0; border-radius: 8px; color: #fff; }
  .on  { background: #2e9d5b; }
  .off { background: #c0392b; }
</style>
</head>
<body>
<h1>ESP32 Home Control</h1>
<div class="card">
  <h2>LED: <span id="led">?</span></h2>
  <button class="on"  onclick="send('led', 1)">ON</button>
  <button class="off" onclick="send('led', 0)">OFF</button>
</div>
<div class="card">
  <h2>Relay: <span id="relayState">?</span></h2>
  <button class="on"  onclick="send('relay', 1)">ON</button>
  <button class="off" onclick="send('relay', 0)">OFF</button>
</div>
<div class="card">
  <h2>Pot: <span id="pot">?</span></h2>
  <progress id="bar" max="4095" value="0"></progress>
</div>
<script>
function show(s) {
  document.getElementById('led').textContent   = s.led   ? 'ON' : 'OFF';
  document.getElementById('relayState').textContent = s.relay ? 'ON' : 'OFF';
  document.getElementById('pot').textContent   = s.pot;
  document.getElementById('bar').value         = s.pot;
}
function refresh() {
  fetch('/api/state')
    .then(r => r.json())
    .then(show)
    .catch(e => console.log('ESP32 unreachable', e));
}
function send(dev, val) {
  fetch('/api/' + dev + '?on=' + val, { method: 'POST' })
    .then(r => r.json())
    .then(show);
}
refresh();
setInterval(refresh, 1000);
</script>
</body>
</html>
)rawliteral";

void setRelay(bool on) {
  relayOn = on;
  if (RELAY_ACTIVE_LOW) digitalWrite(RELAY_PIN, on ? LOW : HIGH);
  else                  digitalWrite(RELAY_PIN, on ? HIGH : LOW);
}

String stateJson() {
  String json = "{\"led\":";
  json += ledOn ? "true" : "false";
  json += ",\"relay\":";
  json += relayOn ? "true" : "false";
  json += ",\"pot\":";
  json += analogRead(POT_PIN);              // a number from 0 to 4095
  json += "}";
  return json;                              // e.g. {"led":true,"relay":false,"pot":2048}
}

void handleRoot()  { server.send(200, "text/html; charset=utf-8", INDEX_HTML); }
void handleState() { server.send(200, "application/json", stateJson()); }

void handleLed() {
  if (!server.hasArg("on")) { server.send(400, "text/plain", "missing ?on=0/1"); return; }
  ledOn = (server.arg("on") == "1");
  digitalWrite(LED_PIN, ledOn ? HIGH : LOW);
  handleState();                            // send back the new state
}

void handleRelay() {
  if (!server.hasArg("on")) { server.send(400, "text/plain", "missing ?on=0/1"); return; }
  setRelay(server.arg("on") == "1");
  handleState();
}

void handleNotFound() { server.send(404, "text/plain", "404: Not Found"); }

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  pinMode(RELAY_PIN, OUTPUT);
  setRelay(false);                          // first thing: relay off
  digitalWrite(LED_PIN, LOW);

  WiFi.mode(WIFI_STA);
  WiFi.setAutoReconnect(true);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  Serial.print("Connecting");
  unsigned long start = millis();
  while (WiFi.status() != WL_CONNECTED && millis() - start < 20000) {
    delay(500);
    Serial.print(".");
  }
  if (WiFi.status() != WL_CONNECTED) {
    Serial.println("\nWiFi failed -> restart in 5 s");
    delay(5000);
    ESP.restart();
  }
  Serial.print("\nOpen http://");
  Serial.println(WiFi.localIP());

  if (MDNS.begin("esp32")) {                // the name esp32.local
    MDNS.addService("http", "tcp", 80);
    Serial.println("or   http://esp32.local");
  }

  server.on("/", HTTP_GET, handleRoot);
  server.on("/api/state", HTTP_GET, handleState);
  server.on("/api/led", HTTP_POST, handleLed);
  server.on("/api/relay", HTTP_POST, handleRelay);
  server.onNotFound(handleNotFound);
  server.begin();
  Serial.println("HTTP server started");
}

void loop() {
  server.handleClient();                    // "is anyone knocking?"
  delay(2);                                 // a little breathing room for the rest of the system
}
  1. Three built-in libraries. WiFi.h for the network, WebServer.h for the web server, ESPmDNS.h for the name esp32.local. All three come with the ESP32 package. A built-in library always matches your core version and needs no separate install; the best place to start.
  2. Settings. The network name and password (in Wokwi, that's Wokwi-GUEST), the three pins, and the fact that the relay is active-LOW. If your module is active-HIGH, just change line 11 to false. (Remember that in a real project you should move the password into secrets.h, as in lesson 4.1.)
  3. Creating the server. WebServer server(80); creates a server object that waits for guests behind "door number 80". 80 is the default HTTP port, so users don't have to type it in the address. If you choose another port such as 8080, the address becomes http://192.168.1.37:8080.
  4. Remembering the state. Two variables that remember whether the LED and the relay are on right now. The JSON response has to say what the current state is. Keeping it in a variable is simpler and more reliable than reading the pin, especially for the relay with its reversed logic.
  5. A raw string literal. R"rawliteral( starts and )rawliteral" ends a long piece of text in which anything is kept exactly as is: quotes, new lines, backslashes. In a normal C++ string you have to write every " as \" and close every line separately; for a hundred lines of HTML full of quotes, that's a nightmare. The word rawliteral is just a "label" that marks the end of the text; any word would do, but it must be one that doesn't appear together with ) and " in your HTML or JS. PROGMEM has no effect on the ESP32 (constants stay in flash anyway) and is only there for compatibility with ESP8266 and Arduino code.
  6. The page header and styling (CSS). meta viewport makes the page suitable for phones. Inside <style> we set the looks: each .card is a white card with rounded corners, the buttons are big, .on is green and .off is red. Without viewport, the page shows up tiny on a phone. Big buttons (20 pixels) are easy to tap with a finger. We put the CSS inside the page itself so only one request is needed; the ESP32 shouldn't have to answer a separate request for every small file.
  7. The page body. Three cards: LED, relay and potentiometer. Each <span id="..."> is a named "blank" that JavaScript fills in later. onclick="send('led', 1)" means "on a click, call the send function with these two inputs". <progress> is a progress bar from 0 to 4095. We deliberately wrote the page text in English so the code doesn't get scrambled in the editor (mixing Persian and English text on one line of code makes the words appear out of order). But other languages work perfectly well on the page itself, because we have charset=utf-8; if you want to write in a right-to-left language such as Persian, also add the dir="rtl" attribute to the <html> tag. The initial ? shows that no data has arrived yet. If the page shows ? forever, JavaScript couldn't talk to the ESP32: a troubleshooting clue.
  8. The show function in JavaScript. It takes a state object such as {led:true, relay:false, pot:2048} and updates the text in the three blanks and the value of the bar. document.getElementById('led') means "find the element whose id is led". The display code lives in one function because it's called from two places: after each periodic update and after a button press. One piece of code, two uses.
  9. The refresh function and fetch. fetch('/api/state') sends a GET request to the ESP32 in the background, without leaving the page. .then(r => r.json()) means "when the response arrives, turn the JSON text into an object". .then(show) means "then hand that object to show". .catch writes an error to the browser console if the ESP32 can't be reached. fetch is "asynchronous": it sends the request and returns right away, so the browser doesn't freeze. The .then chain means "when it's ready, do this"; just like the Wi-Fi events in lesson 4.1. r => r.json() is a short function: "take r and return r.json()".
  10. The send function. Builds the address from pieces, so '/api/' + 'led' + '?on=' + 1 becomes /api/led?on=1, and sends it with method: 'POST'. The ESP32 sends back the new state and show updates the page immediately. Because the button's response is the new state itself, the user sees the result right away and doesn't have to wait for the next update (up to 1 second).
  11. Start and repeat. refresh() once at the very start, and setInterval(refresh, 1000) once every 1000 milliseconds. This is "asking over and over" (polling), because the server can't come to the browser on its own (the restaurant example). One second is a good balance: almost live to the eye, and only one small request per second for the ESP32. If several phones open the page at the same time, don't go below 500.
  12. setRelay: one place for the reversed logic. If the relay is active-LOW, "on" means LOW and "off" means HIGH; otherwise the other way round. If you repeat this logic in several places, sooner or later you'll get one of them wrong. One function, one source of truth.
  13. Building the JSON. We add the JSON text piece by piece to a String with +=. \" means a real quote inside the text. analogRead(POT_PIN) adds the number from 0 to 4095 directly. For three values, building it by hand is the simplest way and needs no extra library. For larger data, the ArduinoJson library is better. Note that true and false have no quotes in JSON; if you add quotes, JavaScript treats the text "false" as "true"!
  14. Two simple handlers. server.send(code, type, content) sends the response. The home page with text/html; charset=utf-8, and the state with application/json. Each path has its own function, like each counter in an office that handles just one job. charset=utf-8 is required for non-English text (such as Persian) to display correctly.
  15. handleLed: validate, act, respond. First we check that the on parameter was sent (hasArg); if not, code 400. Then server.arg("on") gives the value as text, and we compare it with "1". At the end we send back the new state with handleState(). Never trust outside input: someone may type the address by hand and leave something out. Any value other than "1" means off, so strange input never switches anything on by mistake. The safest default for an output is off.
  16. handleRelay. The same pattern, this time with setRelay. Using the same pattern for every device means adding a third device is just copying a few lines.
  17. The 404 page. For every path we haven't defined (such as /favicon.ico). Without it, the library still sends a plain 404, but writing it is a good habit, and later you can give a better message.
  18. Pins and a safe starting state. Both pins become outputs, and right away the relay and the LED are switched off. In core 3.x, right after pinMode(OUTPUT) the pin is usually LOW; for an active-LOW relay that means "on". That's why the very next line switches it off. That gap lasts a few microseconds, and the relay's mechanical coil (which needs a few milliseconds to pull in) has no chance to react. (In core 3.x you can't write to a pin before pinMode; it only prints an error message.)
  19. Connecting with a 20-second limit. Like lesson 4.1. If it doesn't connect, instead of hanging we restart the board with ESP.restart() after 5 seconds. A web server without a network is useless, so waiting in setup makes sense here; but not forever. The automatic restart means that after a power cut, if the board comes up before the router, it sorts itself out a few minutes later. setAutoReconnect covers later dropouts.
  20. Printing the address. We print the board's IP in full, with http://. Copy it from the Serial Monitor and enter it in the browser on your phone or laptop; that device must be on the same Wi-Fi.
  21. mDNS. MDNS.begin("esp32") announces to the network "my name is esp32.local". addService adds that it has a web server on port 80. With DHCP the IP may change, but the name stays the same. The name must be unique on the network; if you have two boards, name one esp32-kitchen and the other esp32-garden.
  22. The route map (routing). server.on(path, type, function) says "if a request of this type arrives at this path, call this function". Then server.begin() opens the door. Because we set the type (HTTP_GET or HTTP_POST), if someone goes to /api/led with a GET, handleLed does not run and they get a 404; that's our "change only with POST" rule. All paths must be registered before begin.
  23. loop: just check the door. server.handleClient() checks whether a request has arrived; if so, it calls the function for that path. The small delay(2) gives the system's other tasks (such as Wi-Fi) a moment to breathe. The WebServer library is "synchronous": requests are answered only when handleClient is called. So loop must never contain a long delay or a waiting loop; otherwise the page gets slow or shows a "timed out" error. If you have other work to do (such as reading a sensor), put it next to handleClient using the millis() pattern.

mDNS: a name instead of a number

Remembering 192.168.1.37 is hard, and worse, DHCP might hand out a different number tomorrow. mDNS (Multicast DNS) solves this: the board announces on the local network, "Whoever is looking for esp32.local, that's me."

An everyday example

At a party, instead of memorizing someone's seat number, you call out their name and they raise their hand. mDNS is calling out a name on your home network. The .local ending means "look for it only on this network, not on the internet".

  • Windows 10 and 11, macOS, iPhone and Linux: http://esp32.local usually works with no setup at all.
  • Android: support depends on the Android version and the browser, and it doesn't work on many phones. On Android, use the IP.
  • A permanent fix for the IP: on the router's settings page there's an option called DHCP Reservation or Static Lease that always gives your board's MAC the same IP. This is better than hard-coding a static IP in the ESP32 code, because it avoids IP conflicts.

Security: who can switch on your lights?

The program above has no password. That means anyone connected to your home Wi-Fi (a guest, a neighbor who knows the Wi-Fi password, an infected phone) can open the page and switch the relay. For an LED that doesn't matter; for a garage door it matters a lot.

The simplest lock is Basic Authentication: the browser shows a username and password box. The WebServer library has this ready to use:

const char* WEB_USER = "admin";
const char* WEB_PASS = "Change-Me-2026";    // be sure to change this

bool checkAuth() {
  if (!server.authenticate(WEB_USER, WEB_PASS)) {
    server.requestAuthentication();         // the browser shows the username and password box
    return false;
  }
  return true;
}

void handleRoot() {
  if (!checkAuth()) return;                 // the guard at the door
  server.send(200, "text/html; charset=utf-8", INDEX_HTML);
}
// add this same first line to handleState, handleLed and handleRelay too
  1. Username and password. Put these two below the server definition in the main program. Be sure to change the password and move it into secrets.h as in lesson 4.1. A default password that's been published on the internet isn't a password.
  2. The guard function. server.authenticate(user, pass) checks whether the request carries the right password. If it doesn't, requestAuthentication() sends a 401 response so the browser shows the password box. Once you've entered the password, the browser sends it by itself with later requests (including the fetch calls), so the page's JavaScript doesn't need any changes.
  3. A guard at every door. The first line of every handler: if there's no password, go back. Forgetting even one path means leaving a back door open. The most dangerous paths (/api/led and /api/relay) matter more than the home page; someone can skip the page and send requests straight to the API.
Basic Auth is not encryption

Over plain HTTP, the username and password are only "wrapped" in Base64, not encrypted. Anyone who eavesdrops on the network traffic can unwrap them in a second. Basic Auth keeps out a curious guest, not a hacker. Real encryption (HTTPS) is possible on the ESP32, but it's heavy and advanced.

Control from outside the house? Don't use port forwarding

You might want to reach the board from work too. Online you'll find tutorials telling you to set up "port forwarding" on your router so requests that reach your home's public IP get sent on to the ESP32. Don't do it.

  • Automated bots scan every IP on the internet day and night and find an open port within a few hours.
  • The ESP32's simple WebServer isn't designed to face the internet directly, and the Basic Auth password travels unencrypted.
  • On many internet connections (especially mobile internet and some home fiber or DSL plans) you don't get your own public IP (CGNAT), so it isn't even possible.

The right way is for the ESP32 to connect out to a trusted service on the internet by itself (instead of waiting for guests). That's exactly the topic of lesson 5.1: MQTT.

An advanced option: ESPAsyncWebServer

In online tutorials you'll often see the ESPAsyncWebServer library. The main difference is that it's "asynchronous": you don't have to keep calling handleClient() in loop; requests are answered in a separate task as soon as they arrive.

Careful: which version you install

The library's original repository (me-no-dev) and its later fork (mathieucarbou) were archived in January 2025 and are no longer updated. Lesson quiz

Why does our page "ask" the ESP32 for the state every second with fetch, instead of the ESP32 announcing it by itself whenever the potentiometer changes?

  1. Because the ESP32 can't send data
  2. Because in HTTP the client (the browser) always makes the request and the server only answers
  3. Because fetch saves battery
  4. Because WebServer only sends HTML
Like a restaurant waiter: until you order, nothing arrives. For the server to send on its own, you need WebSocket or SSE (in ESPAsyncWebServer) or MQTT (chapter 5).

You connected the potentiometer to GPIO25. It worked fine without Wi-Fi, but in this project it doesn't give sensible readings. Why?

  1. GPIO25 is output-only
  2. Wi-Fi reduces the ADC resolution to 8 bits
  3. GPIO25 is on ADC2, and while Wi-Fi is on, ADC2 belongs to the radio
  4. The potentiometer must be connected to 5V
In Wi-Fi projects, use only ADC1 pins (GPIO32 to GPIO39) for analog.

Your relay module is active-LOW. What must you send to the IN pin to switch the relay on?

  1. LOW
  2. HIGH
  3. A PWM signal with 50% duty
  4. 5 volts
Active-LOW means "activated by LOW". That's why we wrote this logic only in the setRelay function.

Why did we register switching the LED on with HTTP_POST in the code, and not HTTP_GET?

  1. Because POST is faster
  2. Because POST is encrypted
  3. Because WebServer doesn't support GET
  4. Because GET should be only for reading; browsers and link previews may open a GET by themselves, without you clicking
Read with GET, change with POST. This rule prevents things from switching on unintentionally.

In R"rawliteral( ... )rawliteral", what role does the word rawliteral play?

  1. It's a special ESP32 command that compresses the HTML
  2. It's just a label that marks the start and end of the raw text, so that a )" inside the HTML or JS doesn't end the text early
  3. It stores the text in flash memory
  4. It runs the JavaScript inside the text
A C++ raw string has the form R"label( ... )label". The label is up to you; it just must not appear in the text itself.

With "Cancel" you get a blank page or a 401 error; with admin and the right password the page works as before, buttons included (the browser sends the password with the fetch requests too).
  • Test 2: the terminal output (the IP and the pot number are yours):
curl -i -X POST "http://192.168.1.37/api/led?on=1"
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Login Required"
...

curl -i -u admin:Change-Me-2026 -X POST "http://192.168.1.37/api/led?on=1"
HTTP/1.1 200 OK
Content-Type: application/json
...
{"led":true,"relay":false,"pot":1873}
  • After the first request the LED must not come on; after the second it does.
  • curl -i http://IP/api/state without a password must also give 401. If it gives 200, you forgot to lock handleState.
  • Remember that Basic Auth over plain HTTP only encodes the password with Base64 (it isn't encryption). That's enough for a home network, not for the internet.

Remember: with free Wokwi your browser can't reach the board's page (see the Wokwi box in the web server section). Use it only to check that the code compiles and connects, and look at the page on a real board.

Full answer with explanation

The complete SmartHome program with a lock on all four paths:

#include <WiFi.h>
#include <WebServer.h>
#include <ESPmDNS.h>

const char* WIFI_SSID = "Wokwi-GUEST";      // your network name
const char* WIFI_PASS = "";                 // your network password

const int LED_PIN   = 4;                    // a regular LED
const int RELAY_PIN = 26;                   // the relay module's IN input
const int POT_PIN   = 34;                   // potentiometer (ADC1, works with Wi-Fi)
const bool RELAY_ACTIVE_LOW = true;         // most relay modules turn on with LOW

WebServer server(80);                       // server on port 80 (the standard HTTP port)
bool ledOn = false;
bool relayOn = false;
const char* WEB_USER = "admin";
const char* WEB_PASS = "Change-Me-2026";    // be sure to change this

// the complete web page, inside a raw string literal
const char INDEX_HTML[] PROGMEM = R"rawliteral(
<!DOCTYPE html>
<html lang="en">
<head>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width, initial-scale=1">
<title>ESP32 Home</title>
<style>
  body { font-family: sans-serif; text-align: center; background: #f2f4f8; }
  .card { background: #fff; max-width: 340px; margin: 14px auto; padding: 12px; border-radius: 12px; }
  button { font-size: 20px; padding: 10px 24px; margin: 4px; border: 0; border-radius: 8px; color: #fff; }
  .on  { background: #2e9d5b; }
  .off { background: #c0392b; }
</style>
</head>
<body>
<h1>ESP32 Home Control</h1>
<div class="card">
  <h2>LED: <span id="led">?</span></h2>
  <button class="on"  onclick="send('led', 1)">ON</button>
  <button class="off" onclick="send('led', 0)">OFF</button>
</div>
<div class="card">
  <h2>Relay: <span id="relayState">?</span></h2>
  <button class="on"  onclick="send('relay', 1)">ON</button>
  <button class="off" onclick="send('relay', 0)">OFF</button>
</div>
<div class="card">
  <h2>Pot: <span id="pot">?</span></h2>
  <progress id="bar" max="4095" value="0"></progress>
</div>

  document.getElementById('led').textContent   = s.led   ? 'ON' : 'OFF';
  document.getElementById('relayState').textContent = s.relay ? 'ON' : 'OFF';
  document.getElementById('pot').textContent   = s.pot;
  document.getElementById('bar').value         = s.pot;
}
function refresh() {
  fetch('/api/state')
    .then(r => r.json())
    .then(show)
    .catch(e => console.log('ESP32 unreachable', e));
}
function send(dev, val) {
  fetch('/api/' + dev + '?on=' + val, { method: 'POST' })
    .then(r => r.json())
    .then(show);
}
refresh();
setInterval(refresh, 1000);
</script>
</body>
</html>
)rawliteral";

void setRelay(bool on) {
  relayOn = on;
  if (RELAY_ACTIVE_LOW) digitalWrite(RELAY_PIN, on ? LOW : HIGH);
  else                  digitalWrite(RELAY_PIN, on ? HIGH : LOW);
}

bool checkAuth() {
  if (!server.authenticate(WEB_USER, WEB_PASS)) {
    server.requestAuthentication();         // 401 + "please log in"
    return false;
  }
  return true;
}
String stateJson() {
  String json = "{\"led\":";
  json += ledOn ? "true" : "false";
  json += ",\"relay\":";
  json += relayOn ? "true" : "false";
  json += ",\"pot\":";
  json += analogRead(POT_PIN);              // a number from 0 to 4095
  json += "}";
  return json;                              // e.g. {"led":true,"relay":false,"pot":2048}
}

void handleRoot() {
  if (!checkAuth()) return;                 // the guard at the door
  server.send(200, "text/html; charset=utf-8", INDEX_HTML);
}

void handleState() {
  if (!checkAuth()) return;
  server.send(200, "application/json", stateJson());
}

void handleLed() {
  if (!checkAuth()) return;
  if (!server.hasArg("on")) { server.send(400, "text/plain", "missing ?on=0/1"); return; }
  ledOn = (server.arg("on") == "1");
  digitalWrite(LED_PIN, ledOn ? HIGH : LOW);
  handleState();                            // send back the new state
}

void handleRelay() {
  if (!checkAuth()) return;
  if (!server.hasArg("on")) { server.send(400, "text/plain", "missing ?on=0/1"); return; }
  setRelay(server.arg("on") == "1");
  handleState();
}

void handleNotFound() { server.send(404, "text/plain", "404: Not Found"); }

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  pinMode(RELAY_PIN, OUTPUT);
  setRelay(false);                          // first thing: relay off
  digitalWrite(LED_PIN, LOW);

  WiFi.mode(WIFI_STA);
  WiFi.setAutoReconnect(true);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  Serial.print("Connecting");
  unsigned long start = millis();
  while (WiFi.status() != WL_CONNECTED && millis() - start < 20000) {
    delay(500);
    Serial.print(".");
  }
  if (WiFi.status() != WL_CONNECTED) {
    Serial.println("\nWiFi failed -> restart in 5 s");
    delay(5000);
    ESP.restart();
  }
  Serial.print("\nOpen http://");
  Serial.println(WiFi.localIP());

  if (MDNS.begin("esp32")) {                // the name esp32.local
    MDNS.addService("http", "tcp", 80);
    Serial.println("or   http://esp32.local");
  }

  server.on("/", HTTP_GET, handleRoot);
  server.on("/api/state", HTTP_GET, handleState);
  server.on("/api/led", HTTP_POST, handleLed);
  server.on("/api/relay", HTTP_POST, handleRelay);
  server.onNotFound(handleNotFound);
  server.begin();
  Serial.println("HTTP server started");
}

void loop() {
  server.handleClient();                    // "is anyone knocking?"
  delay(2);                                 // a little breathing room for the rest of the system
}
  1. The page username and password. Separate from the Wi-Fi password. Be sure to change the default password; anyone who has read this lesson knows it.
  2. The lesson's checkAuth. If the browser didn't send the right name and password, a 401 reply asking for a login goes back, and it returns false. Keeping this logic in one function means each handler needs just one line, and if you change the login method later you change it in one place.
  3. Page and state, locked. handleRoot and handleState, which used to be one-liners, now call checkAuth first. Without locking handleState, anyone on your network can use /api/state to see whether the relay and LED are on (a hint that someone is home, for example). Reading information is a privacy matter too.
  4. LED, locked. The first line of the handler. This is the most important lock: without it anyone could switch things on.
  5. Relay, locked. The same line. handleLed and handleRelay end by calling handleState, which checks the password again; that's fine, because the browser sends it with every request. The 404 path isn't locked because it reveals nothing.
The lesson in three lines

In HTTP the browser makes requests (GET to read, POST to change) and the ESP32 answers with a status code and content; the WebServer library connects each path to a function with server.on, and loop just calls handleClient(). The HTML page sits in a raw string R"rawliteral(...)rawliteral" and updates itself every second with fetch and JSON. Analog sensors only on ADC1, an active-LOW relay that starts switched off, a password with Basic Auth, and never port forwarding; for access from outside, MQTT in chapter 5.
