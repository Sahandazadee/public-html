Calling internet APIs (HTTPS and JSON)

Until now the ESP32 was the server (others asked it for things). Now it's the other way round: the ESP32 becomes a client and asks an internet service for something. An address that a service has set up to answer programs (not people) is called an API. The answer is usually JSON, the same format you saw in lesson 5.1.

An everyday example

An API is like the order window of a bakery. You don't need to know what goes on inside the bakery; you only need to know how to order ("two baguettes, please"), and the baker hands the answer back in a fixed form (a bag of bread). The URL is your order and the JSON is the bag of bread.

The weather in your city from Open-Meteo

Open-Meteo is a free weather service that needs no key (API key) and no sign-up for non-commercial use. Before writing any code, open the address below in your computer's browser to see what the answer looks like; that's a professional habit:

https://api.open-meteo.com/v1/forecast?latitude=43.65&longitude=-79.38&current=temperature_2m,wind_speed_10m

The address has three parts: latitude and longitude (here the geographic coordinates of Toronto; to find your own, right-click your city in Google Maps or OpenStreetMap: the first number shown is the latitude and the second the longitude; west and south are negative), and current (which "right now" values you want: the temperature 2 meters above the ground and the wind speed at a height of 10 meters). The answer looks something like this (shortened):

{
  "latitude": 43.64,
  "longitude": -79.38,
  "timezone": "GMT",
  "current_units": { "time": "iso8601", "interval": "seconds",
                     "temperature_2m": "°C", "wind_speed_10m": "km/h" },
  "current": {
    "time": "2026-09-23T10:15",
    "interval": 900,
    "temperature_2m": 21.3,
    "wind_speed_10m": 14.8
  }
}

We only want two numbers: current.temperature_2m and current.wind_speed_10m. The rest is extra and wastes RAM.

The library you need: ArduinoJson 7

  1. Arduino IDE → Tools › Manage Libraries (the book icon).
  2. Search for ArduinoJson and install ArduinoJson by Benoit Blanchon; make sure it's version 7.x. It has no dependencies.
#include <WiFi.h>
#include <WiFiClientSecure.h>
#include <HTTPClient.h>
#include <ArduinoJson.h>
#include "secrets.h"

const char *URL =
  "https://api.open-meteo.com/v1/forecast"
  "?latitude=43.65&longitude=-79.38"
  "&current=temperature_2m,wind_speed_10m";

bool fetchWeather(float &temp, float &wind) {
  WiFiClientSecure client;
  client.setInsecure();              // for learning only! see the right way below
  HTTPClient http;
  http.setConnectTimeout(5000);      // at most 5 seconds to connect
  http.setTimeout(5000);             // at most 5 seconds for the answer
  http.useHTTP10(true);              // no chunking, so we can read the stream
  if (!http.begin(client, URL)) return false;

  int code = http.GET();
  if (code != HTTP_CODE_OK) {
    Serial.printf("HTTP error: %d %s\n", code, http.errorToString(code).c_str());
    http.end();
    return false;
  }

  JsonDocument filter;               // keep only these two numbers
  filter["current"]["temperature_2m"] = true;
  filter["current"]["wind_speed_10m"] = true;

  JsonDocument doc;
  DeserializationError err = deserializeJson(doc, http.getStream(),
                               DeserializationOption::Filter(filter));
  http.end();
  if (err) {
    Serial.printf("JSON error: %s\n", err.c_str());
    return false;
  }
  temp = doc["current"]["temperature_2m"] | NAN;   // if missing: NAN
  wind = doc["current"]["wind_speed_10m"] | NAN;
  return !isnan(temp);
}

void setup() {
  Serial.begin(115200);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) delay(500);
  Serial.println("Wi-Fi OK");
}

void loop() {
  float t, w;
  if (fetchWeather(t, w)) {
    Serial.printf("Now: %.1f C, wind %.1f km/h\n", t, w);
  }
  delay(10UL * 60 * 1000);           // every 10 minutes, not every second
}
  1. Three libraries. WiFiClientSecure for the encrypted connection (HTTPS), HTTPClient for building the request and reading the HTTP answer, and ArduinoJson for parsing the JSON. In core 3.x the real class name is NetworkClientSecure, and WiFiClientSecure is a backward-compatible alias; both are the same thing. We kept the more familiar name.
  2. The API address. In C++, strings placed side by side are joined automatically; we split the address over three lines for readability. Separate the parameters with & and don't put in any spaces. One wrong letter (for example temperature_2) gets you a 400 error answer.
  3. setInsecure: encryption without identity checking. The connection is encrypted, but the ESP32 doesn't check that the other side really is open-meteo.com. The honest truth (as in lesson 5.1): for fetching a public temperature that isn't secret, the risk is small; the worst case is that someone feeds you a fake temperature. But for anything that carries passwords or commands, never use setInsecure. You'll see the right way (useBuiltinCACertBundle) in the next example.
  4. Time limits. setConnectTimeout for connecting and setTimeout for waiting for the answer, both in milliseconds. Without a time limit, if the internet is slow or the server is busy, the program may wait a long time. A real device should never wait forever for anything.
  5. useHTTP10. Sends the request using HTTP version 1.0. In HTTP/1.1 the server may send the answer in "chunks" (chunked encoding), with size numbers between the chunks. Because we hand the answer straight from the network stream (getStream) to ArduinoJson, those numbers would corrupt the JSON. HTTP/1.0 has no chunking. This is the official recommendation of the ArduinoJson documentation.
  6. GET and checking the response code. HTTP_CODE_OK means 200. A negative number means we never reached the server at all; errorToString turns it into text (for example connection refused or read Timeout). The important codes: 200 success, 400 bad address, 429 "too many requests" (rate limit), 5xx server error. Always check the code before reading the answer, and don't forget http.end() on every path, so memory is freed.
  7. A JSON filter. A small document whose shape says "from the answer, keep only these two fields". The full answer is a few hundred bytes, and with other APIs (for example a 7-day hourly forecast) it can be tens of kilobytes. With a filter, ArduinoJson throws the rest away while reading, and very little RAM is used.
  8. deserializeJson straight from the network. The answer is read directly from the network stream, without storing it in a big String first. If the JSON is incomplete or broken, err is set and err.c_str() gives the reason (for example IncompleteInput or NoMemory). Version 7 has only JsonDocument, which sizes itself. In version 6 you had to write StaticJsonDocument<512> or DynamicJsonDocument with a hand-picked size; old code from the internet gives warnings or errors with version 7.
  9. The | operator for a default value. "If this field exists, give me its value; otherwise NAN (not a number)". If the service renames the field one day, you get NAN instead of a fake zero (which looks like a real temperature!), and you know something is wrong.
  10. Every 10 minutes. 10UL * 60 * 1000 milliseconds; UL means a big unsigned number, so the multiplication doesn't overflow. Open-Meteo itself only updates the "current" data about every 15 minutes (the interval: 900 field); asking every second just bothers the server and may get your IP limited. Under Open-Meteo's terms, free use is for non-commercial purposes only, with a limit of fewer than 10,000 requests per day (and 600 per minute), and the data is licensed CC BY 4.0 (if you publish it somewhere, credit Open-Meteo). Every 10 minutes means 144 requests per day.

An alert to your phone: POST with JSON to ntfy

Now the other direction: the ESP32 sends news. ntfy.sh is a free notification service with no sign-up: you install the ntfy app on your phone (Android or iOS), subscribe to a "topic" with any name you like, and every message sent to that topic appears as a notification on your phone.

The topic name is the password

ntfy.sh has no accounts, so anyone who knows your topic name can read your messages and send you fake ones. Don't pick a name like test or ali; use a long random name like home-alert-7f3k9q and keep it in secrets.h (the file from lesson 5.5 already has the line #define NTFY_TOPIC "..."; if yours doesn't, add it). The limits of free ntfy.sh: about 250 messages per day, and at most 4096 bytes per message.

The circuit: one push button between GPIO27 and GND (we turn on the internal pull-up resistor; lesson 3.1).

#include <WiFi.h>
#include <WiFiClientSecure.h>
#include <HTTPClient.h>
#include <ArduinoJson.h>
#include "secrets.h"
#ifndef NTFY_TOPIC
#warning "NTFY_TOPIC is not defined in secrets.h"
#define NTFY_TOPIC "change-me-to-a-random-name"
#endif

const int BUTTON_PIN = 27;          // button between GPIO27 and GND

bool sendAlert(const char *title, const char *message) {
  WiFiClientSecure client;
  client.useBuiltinCACertBundle();  // really checks the server's identity
  HTTPClient http;
  http.setTimeout(5000);
  if (!http.begin(client, "https://ntfy.sh/")) return false;
  http.addHeader("Content-Type", "application/json");

  JsonDocument msg;                 // {"topic":..,"title":..,"message":..}
  msg["topic"] = NTFY_TOPIC;
  msg["title"] = title;
  msg["message"] = message;
  msg["priority"] = 4;              // 1 to 5; 4 means "high"
  msg["tags"].add("warning");
  String body;
  serializeJson(msg, body);

  int code = http.POST(body);
  http.end();
  Serial.printf("ntfy -> %d\n", code);
  return code == 200;
}

void setup() {
  Serial.begin(115200);
  pinMode(BUTTON_PIN, INPUT_PULLUP);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) delay(500);
  Serial.println("Press the button to send an alert");
}

void loop() {
  static unsigned long lastSent = 0;
  if (digitalRead(BUTTON_PIN) == LOW && millis() - lastSent > 30000) {
    lastSent = millis();            // at most one alert every 30 seconds
    sendAlert("Door", "Front door opened!");
  }
  delay(20);
}
  1. useBuiltinCACertBundle. This time the identity of the ntfy.sh server really is checked. This message goes to your phone, and one day it might say "the door opened" or "gas leak"; you don't want anyone changing it on the way.
  2. The root address and the content type. To send JSON you must POST to the root address https://ntfy.sh/ (not https://ntfy.sh/topic) and say that the body is JSON. According to the ntfy documentation, JSON is only accepted at the root address, and the topic name goes inside the JSON itself. There is also a simpler way: POST plain text to https://ntfy.sh/your-topic-name, and the whole text becomes the message.
  3. Building the JSON. This time it's the reverse of deserialize: we fill the document, and serializeJson turns it into text. msg["tags"].add("warning") creates an array, which ntfy turns into the ⚠️ emoji. Never build JSON by hand by gluing strings together ("{\"title\":\"" + ...); if the message text contains a ", the JSON breaks. ArduinoJson takes care of special characters for you.
  4. Priority 1 to 5. 3 is the default, 4 is "high" with a long vibration, 5 is "urgent". Use 4 or 5 for a real alert; use 2 for a daily report, which sits silently in the notification list. If everything is urgent, nothing is urgent anymore.
  5. POST and the response code. On success, ntfy returns 200. If you see 429, you've gone over the request limit; if it's a negative number, the problem is the network or the certificate.
  6. A sending limit. After each alert, no other alert is sent for 30 seconds, even if the button is held down. Without this, holding the button for 2 seconds means dozens of requests and dozens of notifications, and a few minutes later the service blocks you. Every device that sends messages to an outside service needs "brakes" (rate limiting).

A checklist for a device that stays on for months

A program that works on your desk for 10 minutes is different from a program that works for 6 months without anyone touching it. Problems you never see in 10 minutes: memory that slowly breaks into fragments, Wi-Fi that drops at 3 a.m., power that goes out in the middle of writing a file. The engineering rule: assume that anything that can go wrong eventually will, and the device must pick itself back up.

An everyday example: an airplane's black box

After every incident, an airplane can tell what happened, because it has a black box. Your device needs a "black box" too: every time it powers up, it should say why it reset and how many times it has crashed so far. Without that, troubleshooting a device in the ceiling is just guessing.

#include <Preferences.h>
#include "esp_system.h"
#include "esp_task_wdt.h"

Preferences prefs;

const char *resetReasonText(esp_reset_reason_t r) {
  switch (r) {
    case ESP_RST_POWERON:   return "power on";
    case ESP_RST_SW:        return "software (ESP.restart)";
    case ESP_RST_PANIC:     return "PANIC (crash / Guru Meditation)";
    case ESP_RST_INT_WDT:   return "interrupt watchdog";
    case ESP_RST_TASK_WDT:  return "TASK WATCHDOG";
    case ESP_RST_WDT:       return "other watchdog";
    case ESP_RST_DEEPSLEEP: return "wake from deep sleep";
    case ESP_RST_BROWNOUT:  return "BROWNOUT (weak power)";
    default:                return "other/unknown";
  }
}

void workerTask(void *param) {
  esp_task_wdt_add(NULL);                      // register this task with the watchdog
  for (;;) {
    // ... the task's real work goes here ...
    esp_task_wdt_reset();                      // "I'm alive"
    vTaskDelay(pdMS_TO_TICKS(1000));
  }
}

void setup() {
  Serial.begin(115200);
  delay(500);
  esp_reset_reason_t why = esp_reset_reason();

  prefs.begin("sys", false);                   // "sys" namespace in NVS
  uint32_t boots = prefs.getUInt("boots", 0) + 1;
  prefs.putUInt("boots", boots);
  if (why == ESP_RST_PANIC || why == ESP_RST_TASK_WDT || why == ESP_RST_BROWNOUT) {
    prefs.putUInt("crashes", prefs.getUInt("crashes", 0) + 1);
  }
  Serial.printf("Boot #%lu, reason: %s, crashes so far: %lu\n",
                (unsigned long)boots, resetReasonText(why),
                (unsigned long)prefs.getUInt("crashes", 0));
  prefs.end();

  enableLoopWDT();                             // if loop is stuck over 5 s: reset
  xTaskCreatePinnedToCore(workerTask, "worker", 3072, NULL, 1, NULL, 1);
}

String line;                                   // global, reserved once

void loop() {
  line.reserve(64);                            // does nothing after the first time
  line = "uptime=";
  line += millis() / 1000;
  line += "s heap=";
  line += ESP.getFreeHeap();
  Serial.println(line);
  delay(2000);                                 // change this to 6000 and the WDT resets
}
  1. Turning the reset reason into text. esp_reset_reason() returns a number of type esp_reset_reason_t, and we turn the most important ones into readable text. Three reasons that should always worry you: PANIC (a crash, such as a Guru Meditation or a stack overflow), TASK_WDT (a task got stuck), and BROWNOUT (weak power). POWERON means power was connected, and SW means the program itself called ESP.restart() (after an OTA update, for example). Note: pressing the EN button on the ESP32 is usually reported as POWERON.
  2. Registering a task with the watchdog. esp_task_wdt_add(NULL) means "watch the current task", and esp_task_wdt_reset() means "I'm alive". From this moment, if this task doesn't reset the watchdog for more than 5 seconds, the board resets. Put the reset where it runs only when the work is really making progress, not in a separate task that is always alive (then you'd be fooling the watchdog). Add a task that does long jobs such as HTTPS with care, because one slow request can take more than 5 seconds.
  3. Counters in Preferences. The total number of boots and the number of "bad" resets are stored in NVS and aren't lost when the power goes off. If after a week you see crashes is 40, you know something is wrong, even if the device "seems to work". We only write at boot, not in loop, so the flash doesn't wear out. In a real project, report these numbers on the web page or over MQTT.
  4. enableLoopWDT. A ready-made core function that registers loopTask with the watchdog. The core itself resets the watchdog before every pass of loop(). So if one pass of loop takes more than 5 seconds (for example it gets stuck in a while waiting for a sensor that has been disconnected), the board resets itself and starts over. A reset is better than freezing forever.
  5. A String with reserve. The global variable line grabs 64 bytes once, and every pass refills that same space. Every time a String grows, it may take a new spot in the heap and leave the old one empty. After thousands of times, the heap becomes full of holes, like Swiss cheese: the total free space is large, but no big continuous piece is left (and HTTPS needs a continuous piece of several tens of kilobytes). reserve takes the space once, up front. For fixed-size strings, char buf[64] with snprintf is the safest. To see the problem, print ESP.getMaxAllocHeap() (the largest free block) as well as ESP.getFreeHeap().
  6. Testing the watchdog. If you change the delay to 6000, each pass of loop takes more than 5 seconds and the board resets; after the reset you'll see the message reason: TASK WATCHDOG. Trigger every safety mechanism on purpose once, to make sure it really works. A watchdog that has never been tested isn't a watchdog.

Writing safely in case of power loss

Suppose you're rewriting config.json and the power goes out right in the middle. Mode "w" had already emptied the old file; now you have neither the old settings nor the new ones. The right pattern (you'll see it in the project below): 1) write to config.tmp, 2) close it, 3) delete the old file and rename the tmp file to config.json. Renaming in LittleFS is almost instant. And in any case, when the settings file is missing or broken, the program must come up with default values, not crash. For small values, Preferences already has this safety built in.

Now let's put everything together. A device that:

  • serves its settings page from LittleFS and stores the city's coordinates in a JSON file;

Config cfg = {43.65, -79.38};      // default: Toronto

// ---------- LittleFS: reading and safely saving the settings ----------
void loadConfig() {
  File f = LittleFS.open("/config.json", "r");
  if (!f) return;                                  // not saved yet
  JsonDocument doc;
  if (!deserializeJson(doc, f)) {
    cfg.lat = doc["lat"] | cfg.lat;
    cfg.lon = doc["lon"] | cfg.lon;
  }
  f.close();
}

bool saveConfig(const Config &c) {
  JsonDocument doc;
  doc["lat"] = c.lat;
  doc["lon"] = c.lon;
  File f = LittleFS.open("/config.tmp", "w");      // temporary file first
  if (!f) return false;
  bool ok = serializeJson(doc, f) > 0;
  f.close();
  if (!ok) return false;
  LittleFS.remove("/config.json");
  return LittleFS.rename("/config.tmp", "/config.json");  // then swap it in
}

// ---------- Weather task: every 10 minutes, or when the settings change ----------
bool fetchWeather(float lat, float lon, Weather &w) {
  char url[160];
  snprintf(url, sizeof(url),
           "https://api.open-meteo.com/v1/forecast?latitude=%.2f&longitude=%.2f"
           "&current=temperature_2m,wind_speed_10m", lat, lon);
  WiFiClientSecure client;
  client.useBuiltinCACertBundle();
  HTTPClient http;
  http.setConnectTimeout(5000);
  http.setTimeout(5000);
  http.useHTTP10(true);
  if (!http.begin(client, url)) return false;
  int code = http.GET();
  bool ok = false;
  if (code == HTTP_CODE_OK) {
    JsonDocument filter;
    filter["current"]["temperature_2m"] = true;
    filter["current"]["wind_speed_10m"] = true;
    JsonDocument doc;
    if (!deserializeJson(doc, http.getStream(), DeserializationOption::Filter(filter))) {
      w.temp = doc["current"]["temperature_2m"] | NAN;
      w.wind = doc["current"]["wind_speed_10m"] | NAN;
      w.at = millis();
      ok = !isnan(w.temp);
    }
  }
  http.end();
  return ok;
}

void weatherTask(void *param) {
  for (;;) {
    if (WiFi.status() == WL_CONNECTED) {
      xSemaphoreTake(cfgMutex, portMAX_DELAY);
      Config c = cfg;                              // copy, then give the lock back
      xSemaphoreGive(cfgMutex);
      Weather w;
      if (fetchWeather(c.lat, c.lon, w)) {
        xQueueOverwrite(weatherBox, &w);           // replaces the previous value
      }
    }
    // sleep 10 minutes, unless someone wakes us up sooner
    ulTaskNotifyTake(pdTRUE, pdMS_TO_TICKS(10UL * 60 * 1000));
  }
}

// ---------- Display task: latest weather on the OLED every 2 seconds ----------
void displayTask(void *param) {
  Weather w;
  for (;;) {
    display.clearDisplay();
    display.setCursor(0, 0);
    display.println(WiFi.localIP());
    if (xQueuePeek(weatherBox, &w, 0) == pdPASS) {  // look, don't take
      display.setTextSize(2);
      display.printf("%.1f C\n", w.temp);
      display.setTextSize(1);
      display.printf("wind %.1f km/h\n", w.wind);
      display.printf("%lu min ago", (millis() - w.at) / 60000);
    } else {
      display.println("waiting for data...");
    }
    display.display();
    vTaskDelay(pdMS_TO_TICKS(2000));
  }
}

// ---------- Web: page from LittleFS, data from code ----------
void handleState() {
  Weather w = {NAN, NAN, 0};
  xQueuePeek(weatherBox, &w, 0);
  JsonDocument doc;
  xSemaphoreTake(cfgMutex, portMAX_DELAY);
  doc["lat"] = cfg.lat;
  doc["lon"] = cfg.lon;
  xSemaphoreGive(cfgMutex);
  doc["temp"] = w.temp;
  doc["wind"] = w.wind;
  String out;
  serializeJson(doc, out);
  server.send(200, "application/json", out);
}

void handleSave() {
  Config c = {server.arg("lat").toFloat(), server.arg("lon").toFloat()};
  if (c.lat < -90 || c.lat > 90 || c.lon < -180 || c.lon > 180) {
    return server.send(400, "text/plain", "bad lat/lon");
  }
  xSemaphoreTake(cfgMutex, portMAX_DELAY);
  cfg = c;
  xSemaphoreGive(cfgMutex);
  saveConfig(c);
  xTaskNotifyGive(weatherHandle);                  // "fetch again right now"
  server.sendHeader("Location", "/");
  server.send(303);
}

void setup() {
  Serial.begin(115200);
  LittleFS.begin(true);
  loadConfig();
  weatherBox = xQueueCreate(1, sizeof(Weather));
  cfgMutex = xSemaphoreCreateMutex();

  Wire.begin(21, 22);
  display.begin(SSD1306_SWITCHCAPVCC, 0x3C);
  display.setTextColor(SSD1306_WHITE);

  WiFi.mode(WIFI_STA);
  WiFi.setAutoReconnect(true);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  unsigned long t0 = millis();
  while (WiFi.status() != WL_CONNECTED && millis() - t0 < 20000) delay(250);

  ArduinoOTA.setPassword(OTA_PASS);
  ArduinoOTA.begin();

  server.serveStatic("/", LittleFS, "/index.html");
  server.on("/api/state", HTTP_GET, handleState);
  server.on("/api/config", HTTP_POST, handleSave);
  server.begin();

  xTaskCreatePinnedToCore(weatherTask, "weather", 12288, NULL, 1, &weatherHandle, 1);
  xTaskCreatePinnedToCore(displayTask, "display", 4096, NULL, 1, NULL, 1);
}

void loop() {
  ArduinoOTA.handle();
  server.handleClient();
  delay(2);
}
  1. Two structs. Weather is a package of temperature, wind and the time it was fetched; Config holds the coordinates. Packing related data into one struct lets a single xQueueOverwrite move it all together, in one piece; a new temperature never gets mixed up with an old time.
  2. A one-slot queue as a "mailbox". A queue of length 1 that is filled with xQueueOverwrite and read with xQueuePeek. In the ordinary queue (lesson 5.4), each piece of data was read and removed once. Here we have two readers (the OLED and the web page), and both just want "the latest weather"; Peek looks without removing, and Overwrite always replaces the previous value and never finds the queue "full".
  3. Reading the settings at boot. If the file doesn't exist or the JSON is broken, the Toronto default (line 25) stays. The same principle as the reliability checklist: the device must always boot, even with incomplete settings.
  4. Saving safely. First config.tmp, then delete the old file and rename. If the power goes out in the middle of serializeJson, the previous config.json is still intact. serializeJson(doc, f) writes straight into the file and returns the number of bytes; zero means failure.
  5. fetchWeather. The same code as the weather example earlier in this lesson, with two differences: the address is built from the coordinates with snprintf, and this time we use useBuiltinCACertBundle. snprintf writes into a fixed 160-byte array and never runs past its end; no temporary String is created on the heap. This task runs every 10 minutes for months, so this is exactly where heap fragmentation matters.
  6. weatherTask. It copies the settings under the lock, gives the lock back right away, then does the slow HTTPS request and puts the result in the mailbox. Never hold a lock during a slow job (several seconds of HTTPS), or the web page, which also needs cfg, has to wait just as long. "Copy, release, then work".
  7. ulTaskNotifyTake with a 10-minute limit. The task sleeps until either 10 minutes pass or someone wakes it with xTaskNotifyGive. A task notification is FreeRTOS's lightest tool for "hey, wake up". With a plain vTaskDelay, after changing the city you'd have to wait up to 10 minutes for the new weather.
  8. displayTask. Every 2 seconds it redraws the screen: the IP address, the temperature in large text, the wind, and how many minutes ago the data was fetched. Only this task touches the OLED (and I2C), so the display doesn't need a mutex. A rule simpler than locks: every piece of hardware has one owner. Showing "minutes ago" matters: if the internet is down for a day, the user won't mistake yesterday's temperature for today's.
  9. /api/state. Peeks the latest weather from the mailbox, reads the settings under the lock, and returns everything as JSON. This function runs in loopTask (inside server.handleClient), while weatherTask may be reading cfg at the same moment, or waiting for it to change; that's why the lock is needed.
  10. /api/config. It validates the input, saves it in cfg and in the file, wakes up weatherTask, and sends the browser back to the main page with code 303. Never trust user input: toFloat() returns zero for invalid text, and a latitude of 500 makes no sense. The 303 makes sure that refreshing the page doesn't resend the form.
  11. setup in the right order. LittleFS and the settings, then the queue and the lock (before any task), the OLED, Wi-Fi with a 20-second limit, OTA, the web server, and finally the tasks. If Wi-Fi doesn't connect within 20 seconds, the device doesn't stop: setAutoReconnect connects it later, and weatherTask simply waits until then. weatherTask's stack is deliberately 12 KB because HTTPS is heavy; after a few days, measure the real value with uxTaskGetStackHighWaterMark.
  12. A tiny loop. Only OTA and the web server, with a delay(2). Because the slow work lives in a separate task, loop always comes round in a few milliseconds, and OTA and the web page always answer quickly, even in the middle of a slow HTTPS request. That's exactly the problem lesson 5.4 started with.

Coach's corner

Two rules to take away. One, a device that doesn't record the cause of its resets isn't a professional device. From today on, in every project that stays on for more than a day, include the "black box" code from the reliability checklist. Once the crash counter has stayed at zero for a week, then you can say "it works". Two, be a polite guest on other people's servers: a sensible interval, time limits on every request, and brakes on every alert. A device that hammers an API every second gets blocked, and then it doesn't work at all.

Lesson quiz

In the weather example, why did we put http.useHTTP10(true) before deserializeJson(doc, http.getStream(), ...)?

  1. Because HTTP 1.0 is faster
  2. So the server doesn't send the answer chunked (in pieces with size numbers), which would corrupt the JSON read from the stream
  3. Because HTTPS only works with HTTP 1.0
  4. So the server's certificate isn't checked
When you read straight from getStream(), HTTPClient doesn't stitch the chunks back together. HTTP/1.0 removes the problem at its root.

Your device sends a "door opened" alert to your phone through ntfy. Which connection setting is right?

  1. setInsecure(), because it's simpler
  2. Plain http:// with no encryption
  3. It doesn't matter for a notification
  4. useBuiltinCACertBundle()
For anything that carries commands, passwords or important alerts, check the server's identity. The built-in bundle does it without you having to copy a certificate.

After a week, your device's page shows "crashes: 40" and the last reset reason is TASK WATCHDOG. What does that tell you?

  1. A task (or loop) got stuck for more than 5 seconds, again and again; find out which one
  2. The power supply is too weak
  3. Everything is fine; the watchdog is just strict
  4. Someone pressed the EN button 40 times
The watchdog kept the device alive by resetting it, but the bug is still there. The CPU 0: ... line in the watchdog message names the culprit.

In the weather station, why does weatherTask copy the settings under the lock and give the lock back before the HTTPS request?

  1. To save RAM
  2. Because HTTPS doesn't work while a mutex is held
  3. So the web page, which also needs the settings, doesn't have to wait seconds for a slow request
  4. Because a mutex expires after one second
"Copy, release, then work": hold a lock only for the moment you touch the shared data, never during a slow job.

Full answer with explanation

The complete program: fetchWeather from WeatherNow, sendAlert from the ntfy program, and a small checkHeat that decides. It runs in Wokwi as well, with the same secrets.h trick as WeatherNow (plus a #define NTFY_TOPIC line).

#include <WiFi.h>
#include <WiFiClientSecure.h>
#include <HTTPClient.h>
#include <ArduinoJson.h>
#include <Preferences.h>
#include "secrets.h"
#ifndef NTFY_TOPIC
#warning "NTFY_TOPIC is not defined in secrets.h"
#define NTFY_TOPIC "change-me-to-a-random-name"
#endif

const char *URL =
  "https://api.open-meteo.com/v1/forecast"
  "?latitude=43.65&longitude=-79.38"
  "&current=temperature_2m,wind_speed_10m";
const float ALERT_ABOVE = 30.0;          // alert when it gets hotter than this
const float REARM_BELOW = 28.0;          // ready again once it's cooler than this
const unsigned long CHECK_MS = 10UL * 60 * 1000;   // every 10 minutes

Preferences prefs;

bool fetchWeather(float &temp, float &wind) {
  WiFiClientSecure client;
  client.useBuiltinCACertBundle();       // check the server's identity
  HTTPClient http;
  http.setConnectTimeout(5000);
  http.setTimeout(5000);
  http.useHTTP10(true);
  if (!http.begin(client, URL)) return false;
  int code = http.GET();
  if (code != HTTP_CODE_OK) {
    Serial.printf("HTTP error: %d %s\n", code, http.errorToString(code).c_str());
    http.end();
    return false;
  }
  JsonDocument filter;
  filter["current"]["temperature_2m"] = true;
  filter["current"]["wind_speed_10m"] = true;
  JsonDocument doc;
  DeserializationError err = deserializeJson(doc, http.getStream(),
                               DeserializationOption::Filter(filter));
  http.end();
  if (err) {
    Serial.printf("JSON error: %s\n", err.c_str());
    return false;
  }
  temp = doc["current"]["temperature_2m"] | NAN;
  wind = doc["current"]["wind_speed_10m"] | NAN;
  return !isnan(temp);
}

bool sendAlert(const char *title, const char *message) {
  WiFiClientSecure client;
  client.useBuiltinCACertBundle();
  HTTPClient http;
  http.setTimeout(5000);
  if (!http.begin(client, "https://ntfy.sh/")) return false;
  http.addHeader("Content-Type", "application/json");
  JsonDocument msg;
  msg["topic"] = NTFY_TOPIC;
  msg["title"] = title;
  msg["message"] = message;
  msg["priority"] = 4;
  msg["tags"].add("warning");
  String body;
  serializeJson(msg, body);
  int code = http.POST(body);
  http.end();
  Serial.printf("ntfy -> %d\n", code);
  return code == 200;
}

void checkHeat(float t) {
  prefs.begin("alert", false);
  bool sent = prefs.getBool("sent", false);     // survives resets
  if (!sent && t > ALERT_ABOVE) {
    char text[48];
    snprintf(text, sizeof(text), "It is %.1f C outside", t);
    if (sendAlert("Heat", text)) {
      prefs.putBool("sent", true);              // only once it was really sent
      Serial.printf("Alert sent; next one after it drops below %.1f C\n", REARM_BELOW);
    }
  } else if (sent && t < REARM_BELOW) {
    prefs.putBool("sent", false);               // ready for the next alert
    Serial.println("Cooled down: ready for the next alert");
  }
  prefs.end();
}

void setup() {
  Serial.begin(115200);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) delay(500);
  prefs.begin("alert", false);                  // false = read/write (creates it once)
  Serial.printf("Wi-Fi OK, alert already sent: %s\n", prefs.getBool("sent", false) ? "yes" : "no");
  prefs.end();
}

void loop() {
  float t, w;
  if (fetchWeather(t, w)) {
    Serial.printf("Now: %.1f C, wind %.1f km/h\n", t, w);
    checkHeat(t);
  }
  delay(CHECK_MS);                              // the weather changes slowly
}
  1. The two limits and the interval. Alert above 30, re-arm below 28, check every 10 minutes. The gap between 30 and 28 is the hysteresis: a temperature wobbling around 30 (30.1, 29.9, 30.2...) can't create dozens of alerts, because after an alert it has to drop a full 2 degrees first. Named constants make testing easy.
  2. Fetching the weather, as in WeatherNow. One difference: useBuiltinCACertBundle() instead of setInsecure(). This program acts on the data (it alerts you), so it's worth checking that the answer really comes from Open-Meteo. The bundle is already there for ntfy anyway.
  3. Sending, as in the ntfy program. Returns true only when the server answered 200. The caller needs to know if the alert really went out, so that "sent" is only stored after success.
  4. The memory that survives resets. The "sent" flag lives in Preferences, in the alert namespace. A normal variable goes back to false at every reset, and a board that restarts during a heat wave would alert again and again. A bool in NVS is enough.
  5. Hot and not yet sent: alert. Build the text with the real temperature and send it; only on success store sent = true. If the internet is down for a moment, the flag stays false and the next check tries again: no alert is lost.
  6. Cool again: re-arm. Only when sent is true and the temperature is below 28. Flash is written only when the value changes, not every 10 minutes; flash cells survive a limited number of writes, so pointless writes are worth avoiding.
  7. Show the stored state at start-up. It lets you check the "remembered after a reset" part of the exercise directly.
  8. A simple loop. Fetch, print, decide, wait 10 minutes. The program has nothing else to do, so a long delay is fine here; the weather service updates about every 15 minutes, so asking more often gains nothing.

#include <ArduinoOTA.h>

#include <ArduinoJson.h>
#include <Wire.h>

#define OTA_PASS "change-me"

struct Weather { float temp; float wind; unsigned long at; };
struct Config  { float lat; float lon; };

WebServer server(80);
Adafruit_SSD1306 display(128, 64, &Wire, -1);

const char *resetReasonText(esp_reset_reason_t r) {
  switch (r) {
    case ESP_RST_POWERON:   return "power on";
    case ESP_RST_SW:        return "software (ESP.restart)";
    case ESP_RST_PANIC:     return "PANIC (crash / Guru Meditation)";
    case ESP_RST_INT_WDT:   return "interrupt watchdog";
    case ESP_RST_TASK_WDT:  return "TASK WATCHDOG";
    case ESP_RST_WDT:       return "other watchdog";
    case ESP_RST_DEEPSLEEP: return "wake from deep sleep";
    case ESP_RST_BROWNOUT:  return "BROWNOUT (weak power)";
    default:                return "other/unknown";
  }
}

void recordBoot() {                 // ★ once, at the start of setup
  esp_reset_reason_t why = esp_reset_reason();
  resetText = resetReasonText(why);
  Preferences prefs;
  prefs.begin("sys", false);
  bootCount = prefs.getUInt("boots", 0) + 1;
  prefs.putUInt("boots", bootCount);
  crashCount = prefs.getUInt("crashes", 0);
  if (why == ESP_RST_PANIC || why == ESP_RST_TASK_WDT || why == ESP_RST_BROWNOUT) {
    crashCount++;
    prefs.putUInt("crashes", crashCount);
  }
  prefs.end();
  Serial.printf("Boot #%lu, reason: %s, crashes: %lu\n", (unsigned long)bootCount,
                resetText, (unsigned long)crashCount);
}

// ---------- LittleFS: reading and safely saving the settings ----------
void loadConfig() {
  File f = LittleFS.open("/config.json", "r");
  if (!f) return;                                  // not saved yet
  JsonDocument doc;
  if (!deserializeJson(doc, f)) {
    cfg.lat = doc["lat"] | cfg.lat;
    cfg.lon = doc["lon"] | cfg.lon;
  }
  f.close();
}

bool saveConfig(const Config &c) {
  JsonDocument doc;
  doc["lat"] = c.lat;
  doc["lon"] = c.lon;
  File f = LittleFS.open("/config.tmp", "w");      // temporary file first
  if (!f) return false;
  bool ok = serializeJson(doc, f) > 0;
  f.close();
  if (!ok) return false;
  LittleFS.remove("/config.json");
  return LittleFS.rename("/config.tmp", "/config.json");  // then swap it in
}

  2. A switch for the experiment. CRASH_TEST 1 builds the broken version, 0 the fixed one. One number decides whether the bug is compiled in (#if removes the code completely), so the fixed version is the same program, not a copy you might forget to update.
  3. The black box in RAM. The reason text and both counters as globals. They are read once in setup and then only sent. handleState runs in loop, so it can read them without a lock.
  4. Reason code to text. Copied from RobustBoot. The page should say "TASK WATCHDOG", not "6".

A power-on, a software restart (OTA) or a wake from sleep is normal; only real failures should count as crashes. The counter is written only when it changes.
  6. Three more fields in /api/state. The page already fetches this JSON, so the black box needs no new address; the page only has to show the new keys.

  8. Feed the watchdog during OTA. onProgress is called after every received chunk; feedLoopWDT() tells the watchdog "loop is alive". Without these lines, the fixed version could never arrive over the air: the watchdog would cut every upload after 5 seconds. Feeding (rather than switching the watchdog off) keeps the protection: a real hang during the upload still resets.
  9. Switch on the loop watchdog. From now on, if loop doesn't finish a pass within 5 seconds, the board resets. It comes at the end of setup, because the Wi-Fi wait above can take up to 20 seconds.
  10. The deliberate bug. After one minute, loop gets stuck in an endless while. During the first minute ArduinoOTA.handle() still runs, so the fix can still arrive over OTA; after that, the watchdog resets the board about 5 seconds later, and the next minute begins.

Practice project: a morning briefing on your desk

Before you leave the house, a glance at a little screen tells you today's temperature, the high, and the chance of rain. If rain or a heat wave is coming, your phone buzzes once with a reminder, but only once per day, not every half hour. The device refreshes itself, lets you force a refresh with a button, and quietly survives Wi-Fi drops. It's a small version of the "runs for months on its own" device from this lesson.

Requirements

  1. The board fetches, over HTTPS with the built-in certificate bundle and 5-second time limits, from Open-Meteo for your coordinates: the current temperature, today's highest temperature, today's highest chance of rain, and today's local date. It uses a JSON filter and keeps only those four values.
  2. It fetches right after connecting, then every 30 minutes, and immediately when the button on GPIO27 is pressed. After a failed fetch it tries again after 1 minute instead of 30.
  3. The OLED shows the date (or Wi-Fi: reconnecting), the current temperature in large text, the high, the rain chance, and how many minutes ago the data was fetched, with OLD! added from 90 minutes on. It redraws once a second.
  4. If the rain chance is at least 60 % or the high is at least 30 °C, it sends one ntfy alert for that date. A failed send is retried on the next fetch; a date that was alerted successfully is never alerted again.
  5. loop() never waits for Wi-Fi. The Serial Monitor shows Wi-Fi lost, reconnecting... and Wi-Fi connected once per change, and fetching resumes by itself when the network returns.

Parts

  • ESP32 DevKitC, breadboard, jumper wires
  • 0.96-inch SSD1306 OLED (I2C) on SDA 21 / SCL 22
  • Push button on GPIO27
  • The ntfy app on your phone, subscribed to your own topic name (from secrets.h)

void loop() {
  // 1) report Wi-Fi changes once (never wait for Wi-Fi here)
  bool online = (WiFi.status() == WL_CONNECTED);
  if (online != wasOnline) {
    wasOnline = online;
    Serial.println(online ? "Wi-Fi connected" : "Wi-Fi lost, reconnecting...");
  }

  // 2) button: fetch again now (debounced)
  int reading = digitalRead(BUTTON_PIN);
  if (reading != lastReading) { lastChange = millis(); lastReading = reading; }
  if (millis() - lastChange > 30 && reading != stableState) {
    stableState = reading;
    if (stableState == LOW) fetchNow = true;
  }

  // 3) fetch on schedule, on request, and only when online
  if (online && (fetchNow || millis() - lastFetch >= waitMs)) {
    fetchNow = false;
    lastFetch = millis();
    Serial.println("Fetching the forecast...");
    Briefing nb;
    if (fetchBriefing(nb)) {
      b = nb;
      haveData = true;
      waitMs = REFRESH_MS;
      Serial.printf("%s: now %.1f C, max %.1f C, rain %d %%\n", b.date, b.now, b.maxT, b.rain);
      checkAlert();
    } else {
      waitMs = RETRY_MS;                        // try again sooner
      Serial.println("Fetch failed: next try in 1 minute");
    }
  }

  // 4) redraw once a second
  if (millis() - lastDraw >= 1000) {
    lastDraw = millis();
    drawScreen();
  }

  2. Everything you might want to change, at the top. Coordinates, the two alert thresholds, the two intervals and the button pin. 30UL * 60 * 1000 uses UL so the multiplication happens in unsigned long and can't overflow.
  3. One struct for one forecast. Plus the state: whether we have data, the alerted date, the timers and the debounce variables. char date[11] holds "YYYY-MM-DD" (10 characters) plus the closing '\0'. A fixed array instead of a String avoids heap fragmentation in a device that runs for months.
  4. The address. snprintf inserts the coordinates with two decimals; daily= asks for the two daily values, timezone=auto makes "today" the city's own day, and forecast_days=1 limits the arrays to one element. Without timezone=auto, days are counted in GMT, and in Toronto "today" would switch at 8 p.m.
  5. The HTTPS request. The certificate bundle, both time limits, HTTP 1.0 for a plain stream, and a clear message for any code other than 200. This is the lesson's recipe. The time limits guarantee that one bad request can never block loop for more than a few seconds.
  6. Filter and parse. Four fields are kept; everything else in the answer is skipped while reading. The full answer also contains units and metadata. The filter keeps the JsonDocument tiny, whatever Open-Meteo adds in the future.
  7. Reading the arrays. [0] takes the first (and only) day; | supplies defaults; strlcpy copies the date safely into the 11-byte array.   8. sendAlert. The lesson's JSON POST to ntfy, with a fixed title and an umbrella tag. It returns true only on HTTP 200, so the caller knows whether the alert really went out.
  9. checkAlert: once per date. Already alerted for this date: return. Neither rainy nor hot: return. Otherwise build a short message and, only if it was sent, remember the date. Remembering the date only after a successful send means a temporary ntfy failure is retried at the next fetch. When the date changes at midnight, the comparison fails again and a new day can be alerted.
  10. drawScreen. The first line shows Wi-Fi trouble if there is any, otherwise the date; then the big temperature, the high, the rain chance and the age of the data.   11. setup doesn't wait for Wi-Fi. Button, OLED, then WiFi.begin with automatic reconnection. The screen appears at once ("waiting for data..."), and loop starts working even if the router is off.
  12. Reporting Wi-Fi changes once. wasOnline remembers the previous state; a line is printed only when it differs. Printing "offline" hundreds of times per second would drown every other message.
  13. The button only raises a flag. The debounce from lesson 5.2; a press sets fetchNow. The fetch itself happens in one place below, with the same checks (online or not) for every reason to fetch.
  14. One fetch decision. Online and (asked for, or the wait is over): fetch into a temporary struct. On success, copy it, schedule the next in 30 minutes, print and check the alert; on failure, keep the old data and retry in 1 minute. Fetching into nb first means a failed or half-read answer never overwrites good data. A short retry after a failure brings the display back quickly after an outage without hammering the server.
  15. Redraw once a second. The "min ago" counter and the Wi-Fi line stay current without redrawing thousands of times per second.

Chapter 5 capstone: a two-room climate hub

This project uses everything from chapter 5. A small node in the bedroom measures temperature and humidity and sends them over ESP-NOW, with no router involved. A hub in the living room receives them, adds its own room's reading, and does the "smart home" part: it runs its work in FreeRTOS tasks, publishes both rooms over MQTT, serves a live web page from LittleFS, warns you with an LED when the bedroom goes silent, and can be updated over the air.

Requirements

  1. Node: every 10 seconds (and right after boot) it reads the DHT22 and sends a 16-byte ClimateMsg (type 1, room 2, a growing seq, temperature, humidity) to the hub's MAC, on the hub's router channel. It prints each reading with delivered or NOT delivered, and flashes its LED for 50 ms on delivery, without delay().
  2. Hub: joins Wi-Fi (at most 20 seconds of waiting) and prints its MAC, channel and IP. Its ESP-NOW receive callback only checks length, type and room, and copies the message into a FreeRTOS queue without waiting.
  3. Hub: a localTask reads the potentiometer every 10 seconds as room 1's temperature (10 to 35 °C, humidity unknown) and puts it into the same queue.
  4. Hub: loop() empties the queue, stores the latest reading of each room under a mutex, logs it, and publishes {"t":…,"h":…,"seq":…} on …/room1/climate or …/room2/climate (null for unknown values). …/hub/status is online, or offline via the Last Will.
  5. Hub: a watchTask checks every 2 seconds whether room 2 has been silent for more than 35 seconds. When that changes, it switches the LED on GPIO4 on or off and logs one line.
  6. Hub: / serves index.html from LittleFS, and /api/rooms returns both rooms as JSON with temperature, humidity, age in seconds and count, read under the mutex.
  7. Hub: ArduinoOTA runs with the hostname climate-hub; loop() never blocks for longer than its delay(2), and every Serial line goes through the mutex-protected logf().

Parts

  • Two ESP32 DevKitC boards with two USB cables; a USB charger lets the node sit in another room (optional)
  • Node: DHT22 (+ 10 kΩ pull-up if it's the bare 4-pin sensor) and LED + 220 Ω
  • Hub: 10 kΩ potentiometer (stand-in for a second thermometer) and LED + 220 Ω
  • A 2.4 GHz Wi-Fi network; the HiveMQ web client or MQTTX to watch the messages

  1. Where to send, and on which channel. The hub's MAC and its router's channel, both copied from the hub's first log line; the room number and the interval. The node never joins the router, so it can't discover the channel by itself (lesson 5.2). With a wrong channel, every send reports NOT delivered.
  2. The message. Type, room, number, temperature, humidity: 1 + 1 + 2 padding + 4 + 4 + 4 = 16 bytes. The type and room bytes let the hub reject anything else on the channel, and seq shows you at a glance whether readings were lost.
  3. The send callback only stores the result. volatile int with −1 meaning "nothing new". The callback runs in the Wi-Fi task; printing belongs in loop. volatile makes loop reread the value every time.
  4. Radio on, then to the router's channel. setChannel only works once the radio is running and must happen before esp_now_init.
  5. Callback and peer. peer.channel = 0 means "the current channel", which is now the router's. Only unicast to a registered peer gets a MAC-level acknowledgment, which is what makes delivered meaningful.
  6. Every 10 seconds: read and send. The line is printed without a newline; the result finishes it. A failed DHT22 read gives NAN, which is still sent: the hub then shows null, which is more honest than skipping the reading.
  7. Report and flash. When the callback has stored a result, print it; on delivery, switch the LED on and off again 50 ms later with millis(). A brief flash every 10 seconds tells you, without a computer, that the node and hub are talking.
// Climate hub: ESP-NOW in, FreeRTOS tasks, MQTT out, LittleFS page, OTA
#include <WiFi.h>
#include <esp_now.h>
#include <PubSubClient.h>
#include <WebServer.h>
#include <ArduinoOTA.h>
#include <LittleFS.h>
#include <ArduinoJson.h>
#if __has_include("secrets.h")
#include "secrets.h"                  // real board: WIFI_SSID, WIFI_PASS, OTA_PASS
#endif
#ifndef WIFI_SSID                     // no secrets.h (Wokwi): Wokwi's network
#define WIFI_SSID "Wokwi-GUEST"
#define WIFI_PASS ""
#endif
#ifndef OTA_PASS
#define OTA_PASS "change-me"
#endif

#define BASE "esp32course/ali1234/home"     // your own prefix, as in 5.1
const char *MQTT_HOST = "broker.hivemq.com";
const int MQTT_PORT = 1883;
const char *TOPIC_STATUS = BASE "/hub/status";
const int LED_PIN = 4;                // on = room 2 has gone silent
const int POT_PIN = 34;               // stand-in for room 1's thermometer
const unsigned long STALE_MS = 35000; // 3 missed readings = silent

typedef struct {
  uint8_t type;
  uint8_t room;
  uint32_t seq;
  float tempC;
  float hum;
} ClimateMsg;                         // exact copy of the node's layout

struct Room { float tempC; float hum; unsigned long at; uint32_t count; };

QueueHandle_t readings;               // ESP-NOW + local task -> loop
SemaphoreHandle_t roomsMutex;         // protects rooms[]
SemaphoreHandle_t logMutex;           // protects Serial
Room rooms[3];                        // we use [1] and [2]
WiFiClient net;
PubSubClient mqtt(net);
WebServer server(80);
char clientId[40];
unsigned long lastTry = 0;

void logf(const char *fmt, ...) {
  char buf[112];
  va_list args;
  va_start(args, fmt);
  vsnprintf(buf, sizeof(buf), fmt, args);
  va_end(args);
  if (xSemaphoreTake(logMutex, pdMS_TO_TICKS(100)) == pdTRUE) {
    Serial.printf("[%6lu] %s\n", millis(), buf);
    xSemaphoreGive(logMutex);
  }
}

// runs in the Wi-Fi task: check, copy into the queue, never wait
void onRecv(const esp_now_recv_info_t *info, const uint8_t *data, int len) {
  if (len != sizeof(ClimateMsg)) return;
  ClimateMsg m;
  memcpy(&m, data, sizeof(m));
  if (m.type != 1 || m.room != 2) return;
  xQueueSend(readings, &m, 0);
}

// room 1: the potentiometer pretends to be a thermometer (10..35 C)
void localTask(void *param) {
  uint32_t seq = 0;
  for (;;) {
    uint32_t raw = 0;
    for (int i = 0; i < 8; i++) raw += analogRead(POT_PIN);
    raw /= 8;
    ClimateMsg m = {1, 1, ++seq, 10.0f + raw * 25.0f / 4095.0f, NAN};
    xQueueSend(readings, &m, pdMS_TO_TICKS(100));
    vTaskDelay(pdMS_TO_TICKS(10000));
  }
}

// watches room 2: LED on (and one log line) when it goes silent
void watchTask(void *param) {
  bool silent = false;
  for (;;) {
    xSemaphoreTake(roomsMutex, portMAX_DELAY);
    unsigned long at = rooms[2].at;
    xSemaphoreGive(roomsMutex);
    unsigned long quietFor = (at == 0) ? millis() : millis() - at;
    bool nowSilent = quietFor > STALE_MS;
    if (nowSilent != silent) {
      silent = nowSilent;
      digitalWrite(LED_PIN, silent ? HIGH : LOW);
      logf(silent ? "!! room 2 silent for over 35 s" : "room 2 is back");
    }
    vTaskDelay(pdMS_TO_TICKS(2000));
  }
}

void publishRoom(const ClimateMsg &m) {
  JsonDocument doc;
  if (isnan(m.tempC)) doc["t"] = nullptr;    // JSON has no NaN: send null
  else doc["t"] = serialized(String(m.tempC, 1));
  if (isnan(m.hum)) doc["h"] = nullptr;
  else doc["h"] = serialized(String(m.hum, 1));
  doc["seq"] = m.seq;
  char topic[64], buf[96];
  snprintf(topic, sizeof(topic), BASE "/room%u/climate", m.room);
  serializeJson(doc, buf, sizeof(buf));
  mqtt.publish(topic, buf);
}

bool connectMqtt() {
  if (!mqtt.connect(clientId, TOPIC_STATUS, 1, true, "offline")) {
    logf("MQTT failed, state=%d", mqtt.state());
    return false;
  }
  mqtt.publish(TOPIC_STATUS, "online", true);
  logf("MQTT connected");
  return true;
}

void handleRooms() {
  JsonDocument doc;
  xSemaphoreTake(roomsMutex, portMAX_DELAY);
  for (int r = 1; r <= 2; r++) {
    JsonObject o = doc["room" + String(r)].to<JsonObject>();
    o["t"] = round(rooms[r].tempC * 10.0) / 10.0;   // 1 decimal; NAN -> null
    o["h"] = round(rooms[r].hum * 10.0) / 10.0;
    if (rooms[r].at == 0) o["age"] = nullptr;
    else o["age"] = (millis() - rooms[r].at) / 1000;
    o["count"] = rooms[r].count;
  }
  xSemaphoreGive(roomsMutex);
  String out;
  serializeJson(doc, out);
  server.send(200, "application/json", out);
}

void setup() {
  Serial.begin(115200);
  delay(300);
  readings = xQueueCreate(10, sizeof(ClimateMsg));
  roomsMutex = xSemaphoreCreateMutex();
  logMutex = xSemaphoreCreateMutex();
  for (int r = 0; r < 3; r++) rooms[r] = {NAN, NAN, 0, 0};
  pinMode(LED_PIN, OUTPUT);
  if (!LittleFS.begin(true)) Serial.println("LittleFS mount failed");

  WiFi.mode(WIFI_STA);
  WiFi.setAutoReconnect(true);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  unsigned long t0 = millis();
  while (WiFi.status() != WL_CONNECTED && millis() - t0 < 20000) delay(250);
  WiFi.setSleep(false);               // keep the radio awake for ESP-NOW
  logf("Hub MAC %s, channel %d, IP %s", WiFi.macAddress().c_str(), WiFi.channel(),
       WiFi.localIP().toString().c_str());

  if (esp_now_init() == ESP_OK) esp_now_register_recv_cb(onRecv);
  else logf("ESP-NOW init failed");

  String mac = WiFi.macAddress();
  mac.replace(":", "");
  snprintf(clientId, sizeof(clientId), "hub-%s-%04X", mac.c_str(), (unsigned)(esp_random() & 0xFFFF));
  mqtt.setServer(MQTT_HOST, MQTT_PORT);

  ArduinoOTA.setHostname("climate-hub");
  ArduinoOTA.setPassword(OTA_PASS);
  ArduinoOTA.begin();

  server.serveStatic("/", LittleFS, "/index.html");
  server.on("/api/rooms", HTTP_GET, handleRooms);
  server.begin();

  xTaskCreatePinnedToCore(localTask, "local", 3072, NULL, 1, NULL, 1);
  xTaskCreatePinnedToCore(watchTask, "watch", 3072, NULL, 1, NULL, 1);
}

void loop() {
  ArduinoOTA.handle();
  server.handleClient();

  ClimateMsg m;
  while (xQueueReceive(readings, &m, 0) == pdPASS) {    // empty the queue
    xSemaphoreTake(roomsMutex, portMAX_DELAY);
    rooms[m.room].tempC = m.tempC;
    rooms[m.room].hum = m.hum;
    rooms[m.room].at = millis();
    rooms[m.room].count++;
    xSemaphoreGive(roomsMutex);
    logf("room%u #%lu: %.1f C, %.1f %%", m.room, (unsigned long)m.seq, m.tempC, m.hum);
    if (mqtt.connected()) publishRoom(m);
  }

  if (WiFi.status() == WL_CONNECTED) {
    if (mqtt.connected()) {
      mqtt.loop();
    } else if (lastTry == 0 || millis() - lastTry > 5000) {
      lastTry = millis();
      connectMqtt();
    }
  }
  delay(2);
}
  1. Secrets with Wokwi fallbacks. The same pattern as the 5.5 and 5.6 projects. One sketch that compiles on your board with real passwords and in Wokwi without any.
  2. Settings. Your topic prefix, the broker, the status topic, the two pins and the silence limit. 35 seconds is three missed readings plus a margin, so one lost packet doesn't trigger a false alarm.
  3. The message and the room record. ClimateMsg is an exact copy of the node's; Room keeps the latest values, when they arrived and how many have arrived. Storing millis() at arrival, not a time from the node, means the hub's clock alone decides what "silent" means.
  4. Shared objects. One queue into loop, a mutex for rooms[], a mutex for Serial, and the network objects. rooms[3] is indexed by room number, so rooms[m.room] needs no translation; index 0 is simply unused.
  5. logf. Format first, then print one whole line under the lock. Three tasks print; without the lock their lines could interleave.
  6. The ESP-NOW callback. Check the length, copy, accept only type 1 from room 2, and xQueueSend with a wait of 0. This runs inside the Wi-Fi task: it must never block. If the queue is ever full, the reading is dropped, which is better than stalling the radio.
  7. localTask. Average 8 potentiometer readings, map 0 to 4095 onto 10 to 35 °C, send a room 1 message with unknown humidity, sleep 10 seconds. By sending the same message type into the same queue as the node, the rest of the hub doesn't care where a reading came from. Swap in a real sensor later and nothing else changes.
  8. watchTask. Copy room 2's arrival time under the lock, compute how long it has been quiet (since boot if it never reported), and act only when the silent/not-silent state changes. Copy-then-release keeps the lock time tiny. Acting only on changes gives exactly one log line per event instead of one every 2 seconds. This task is the LED's only owner.
  9. publishRoom. Build {"t":…,"h":…,"seq":…} with one decimal (or null), put the room number into the topic, publish. Standard JSON has no NaN, so unknown values must be null, or dashboards reject the message. serialized(String(x, 1)) is the lesson 5.1 trick for exactly one decimal.
  10. connectMqtt. Connect with a Last Will, then publish online retained. The hub doesn't subscribe to anything, so there's nothing to re-subscribe after reconnecting.
  11. /api/rooms. Build both room objects under the lock, rounding to one decimal, with null age for a room that never reported; release; send. This runs in loop while watchTask may be reading the same data, hence the lock. Rounding in double keeps the JSON short (23.8, not 23.79999924); a NAN stays NaN and becomes null.
  12. Shared objects before anything that uses them. Queue, mutexes, empty room records, the LED pin and LittleFS. The ESP-NOW callback and the tasks start later in setup; by then everything they touch exists.
  13. Wi-Fi first, then report the channel. Up to 20 seconds; setSleep(false) keeps the radio listening for ESP-NOW between router beacons. The router decides the channel, so it's only known after connecting. The log line gives you exactly what the node needs.
  14. ESP-NOW and MQTT set up. ESP-NOW starts on the router's channel; the MQTT client ID uses the MAC plus a random number. The hub doesn't add the node as a peer: receiving unencrypted unicast needs no peer (lesson 5.2).
  15. OTA and the web server. The page comes from LittleFS; the data comes from /api/rooms. Separating the page (a file) from the data (code) means you can restyle the page with a LittleFS upload, without touching the program.
  16. Two small tasks on core 1. 3072 bytes each, priority 1. Neither does anything heavy (no HTTPS), so a small stack is enough; check it later with uxTaskGetStackHighWaterMark as in lesson 5.4.
  17. loop: OTA, web, then empty the queue. Each reading is stored under the lock, logged, and published if MQTT is up. loop is the single owner of the MQTT connection; PubSubClient isn't made for being called from several tasks at once. %% prints a percent sign; a NAN humidity prints as nan.
  18. Keep MQTT alive, and rest 2 ms. The lesson 5.1 non-blocking reconnection. One honest limit: while connect() itself is trying, it can take up to about 15 seconds. The readings then wait in the queue (10 slots, one every few seconds), and the web page answers a bit late, but nothing is lost.

The lesson in three lines

Call APIs with HTTPS, time limits, a JSON filter and a sensible interval, and check the server's identity with the built-in CA bundle whenever something important travels. A device that runs for months records why it reset, counts its crashes, lets the watchdog restart it when it gets stuck, avoids heap fragmentation and saves files safely. The weather station puts it all together: slow work in its own task, data in a one-slot mailbox, settings in LittleFS and updates over OTA.
