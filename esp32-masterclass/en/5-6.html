Calling internet APIs (HTTPS and JSON)

Until now the ESP32 was the server (others asked it for things). Now it's the other way round: the ESP32 becomes a client and asks an internet service for something. An address that a service has set up to answer programs (not people) is called an API. The answer is usually JSON, the same format you saw in lesson 5.1.

An everyday example

An API is like the order window of a bakery. You don't need to know what goes on inside the bakery; you only need to know how to order ("two baguettes, please"), and the baker hands the answer back in a fixed form (a bag of bread). The URL is your order and the JSON is the bag of bread.

The weather in your city from Open-Meteo

Open-Meteo is a free weather service that needs no key (API key) and no sign-up for non-commercial use. Before writing any code, open the address below in your computer's browser to see what the answer looks like; that's a professional habit:

https://api.open-meteo.com/v1/forecast?latitude=43.65&longitude=-79.38&current=temperature_2m,wind_speed_10m

The address has three parts: latitude and longitude (here the geographic coordinates of Toronto; to find your own, right-click your city in Google Maps or OpenStreetMap: the first number shown is the latitude and the second the longitude; west and south are negative), and current (which "right now" values you want: the temperature 2 meters above the ground and the wind speed at a height of 10 meters). The answer looks something like this (shortened):

{
  "latitude": 43.64,
  "longitude": -79.38,
  "timezone": "GMT",
  "current_units": { "time": "iso8601", "interval": "seconds",
                     "temperature_2m": "°C", "wind_speed_10m": "km/h" },
  "current": {
    "time": "2026-09-23T10:15",
    "interval": 900,
    "temperature_2m": 21.3,
    "wind_speed_10m": 14.8
  }
}

We only want two numbers: current.temperature_2m and current.wind_speed_10m. The rest is extra and wastes RAM.

The library you need: ArduinoJson 7

  1. Arduino IDE → Tools › Manage Libraries (the book icon).
  2. Search for ArduinoJson and install ArduinoJson by Benoit Blanchon; make sure it's version 7.x. It has no dependencies.
#include <WiFi.h>
#include <WiFiClientSecure.h>
#include <HTTPClient.h>
#include <ArduinoJson.h>
#include "secrets.h"

const char *URL =
  "https://api.open-meteo.com/v1/forecast"
  "?latitude=43.65&longitude=-79.38"
  "&current=temperature_2m,wind_speed_10m";

bool fetchWeather(float &temp, float &wind) {
  WiFiClientSecure client;
  client.setInsecure();              // for learning only! see the right way below
  HTTPClient http;
  http.setConnectTimeout(5000);      // at most 5 seconds to connect
  http.setTimeout(5000);             // at most 5 seconds for the answer
  http.useHTTP10(true);              // no chunking, so we can read the stream
  if (!http.begin(client, URL)) return false;

  int code = http.GET();
  if (code != HTTP_CODE_OK) {
    Serial.printf("HTTP error: %d %s\n", code, http.errorToString(code).c_str());
    http.end();
    return false;
  }

  JsonDocument filter;               // keep only these two numbers
  filter["current"]["temperature_2m"] = true;
  filter["current"]["wind_speed_10m"] = true;

  JsonDocument doc;
  DeserializationError err = deserializeJson(doc, http.getStream(),
                               DeserializationOption::Filter(filter));
  http.end();
  if (err) {
    Serial.printf("JSON error: %s\n", err.c_str());
    return false;
  }
  temp = doc["current"]["temperature_2m"] | NAN;   // if missing: NAN
  wind = doc["current"]["wind_speed_10m"] | NAN;
  return !isnan(temp);
}

void setup() {
  Serial.begin(115200);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) delay(500);
  Serial.println("Wi-Fi OK");
}

void loop() {
  float t, w;
  if (fetchWeather(t, w)) {
    Serial.printf("Now: %.1f C, wind %.1f km/h\n", t, w);
  }
  delay(10UL * 60 * 1000);           // every 10 minutes, not every second
}
  1. Three libraries. WiFiClientSecure for the encrypted connection (HTTPS), HTTPClient for building the request and reading the HTTP answer, and ArduinoJson for parsing the JSON. In core 3.x the real class name is NetworkClientSecure, and WiFiClientSecure is a backward-compatible alias; both are the same thing. We kept the more familiar name.
  2. The API address. In C++, strings placed side by side are joined automatically; we split the address over three lines for readability. Separate the parameters with & and don't put in any spaces. One wrong letter (for example temperature_2) gets you a 400 error answer.
  3. setInsecure: encryption without identity checking. The connection is encrypted, but the ESP32 doesn't check that the other side really is open-meteo.com. The honest truth (as in lesson 5.1): for fetching a public temperature that isn't secret, the risk is small; the worst case is that someone feeds you a fake temperature. But for anything that carries passwords or commands, never use setInsecure. You'll see the right way (useBuiltinCACertBundle) in the next example.
  4. Time limits. setConnectTimeout for connecting and setTimeout for waiting for the answer, both in milliseconds. Without a time limit, if the internet is slow or the server is busy, the program may wait a long time. A real device should never wait forever for anything.
  5. useHTTP10. Sends the request using HTTP version 1.0. In HTTP/1.1 the server may send the answer in "chunks" (chunked encoding), with size numbers between the chunks. Because we hand the answer straight from the network stream (getStream) to ArduinoJson, those numbers would corrupt the JSON. HTTP/1.0 has no chunking. This is the official recommendation of the ArduinoJson documentation.
  6. GET and checking the response code. HTTP_CODE_OK means 200. A negative number means we never reached the server at all; errorToString turns it into text (for example connection refused or read Timeout). The important codes: 200 success, 400 bad address, 429 "too many requests" (rate limit), 5xx server error. Always check the code before reading the answer, and don't forget http.end() on every path, so memory is freed.
  7. A JSON filter. A small document whose shape says "from the answer, keep only these two fields". The full answer is a few hundred bytes, and with other APIs (for example a 7-day hourly forecast) it can be tens of kilobytes. With a filter, ArduinoJson throws the rest away while reading, and very little RAM is used.
  8. deserializeJson straight from the network. The answer is read directly from the network stream, without storing it in a big String first. If the JSON is incomplete or broken, err is set and err.c_str() gives the reason (for example IncompleteInput or NoMemory). Version 7 has only JsonDocument, which sizes itself. In version 6 you had to write StaticJsonDocument<512> or DynamicJsonDocument with a hand-picked size; old code from the internet gives warnings or errors with version 7.
  9. The | operator for a default value. "If this field exists, give me its value; otherwise NAN (not a number)". If the service renames the field one day, you get NAN instead of a fake zero (which looks like a real temperature!), and you know something is wrong.
  10. Every 10 minutes. 10UL * 60 * 1000 milliseconds; UL means a big unsigned number, so the multiplication doesn't overflow. Open-Meteo itself only updates the "current" data about every 15 minutes (the interval: 900 field); asking every second just bothers the server and may get your IP limited. Under Open-Meteo's terms, free use is for non-commercial purposes only, with a limit of fewer than 10,000 requests per day (and 600 per minute), and the data is licensed CC BY 4.0 (if you publish it somewhere, credit Open-Meteo). Every 10 minutes means 144 requests per day.

An alert to your phone: POST with JSON to ntfy

Now the other direction: the ESP32 sends news. ntfy.sh is a free notification service with no sign-up: you install the ntfy app on your phone (Android or iOS), subscribe to a "topic" with any name you like, and every message sent to that topic appears as a notification on your phone.

The topic name is the password

ntfy.sh has no accounts, so anyone who knows your topic name can read your messages and send you fake ones. Don't pick a name like test or ali; use a long random name like home-alert-7f3k9q and keep it in secrets.h (the file from lesson 5.5 already has the line #define NTFY_TOPIC "..."; if yours doesn't, add it). The limits of free ntfy.sh: about 250 messages per day, and at most 4096 bytes per message.

The circuit: one push button between GPIO27 and GND (we turn on the internal pull-up resistor; lesson 3.1).

#include <WiFi.h>
#include <WiFiClientSecure.h>
#include <HTTPClient.h>
#include <ArduinoJson.h>
#include "secrets.h"
#ifndef NTFY_TOPIC
#warning "NTFY_TOPIC is not defined in secrets.h"
#define NTFY_TOPIC "change-me-to-a-random-name"
#endif

const int BUTTON_PIN = 27;          // button between GPIO27 and GND

bool sendAlert(const char *title, const char *message) {
  WiFiClientSecure client;
  client.useBuiltinCACertBundle();  // really checks the server's identity
  HTTPClient http;
  http.setTimeout(5000);
  if (!http.begin(client, "https://ntfy.sh/")) return false;
  http.addHeader("Content-Type", "application/json");

  JsonDocument msg;                 // {"topic":..,"title":..,"message":..}
  msg["topic"] = NTFY_TOPIC;
  msg["title"] = title;
  msg["message"] = message;
  msg["priority"] = 4;              // 1 to 5; 4 means "high"
  msg["tags"].add("warning");
  String body;
  serializeJson(msg, body);

  int code = http.POST(body);
  http.end();
  Serial.printf("ntfy -> %d\n", code);
  return code == 200;
}

void setup() {
  Serial.begin(115200);
  pinMode(BUTTON_PIN, INPUT_PULLUP);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) delay(500);
  Serial.println("Press the button to send an alert");
}

void loop() {
  static unsigned long lastSent = 0;
  if (digitalRead(BUTTON_PIN) == LOW && millis() - lastSent > 30000) {
    lastSent = millis();            // at most one alert every 30 seconds
    sendAlert("Door", "Front door opened!");
  }
  delay(20);
}
  1. useBuiltinCACertBundle. This time the identity of the ntfy.sh server really is checked. This message goes to your phone, and one day it might say "the door opened" or "gas leak"; you don't want anyone changing it on the way.
  2. The root address and the content type. To send JSON you must POST to the root address https://ntfy.sh/ (not https://ntfy.sh/topic) and say that the body is JSON. According to the ntfy documentation, JSON is only accepted at the root address, and the topic name goes inside the JSON itself. There is also a simpler way: POST plain text to https://ntfy.sh/your-topic-name, and the whole text becomes the message.
  3. Building the JSON. This time it's the reverse of deserialize: we fill the document, and serializeJson turns it into text. msg["tags"].add("warning") creates an array, which ntfy turns into the ⚠️ emoji. Never build JSON by hand by gluing strings together ("{\"title\":\"" + ...); if the message text contains a ", the JSON breaks. ArduinoJson takes care of special characters for you.
  4. Priority 1 to 5. 3 is the default, 4 is "high" with a long vibration, 5 is "urgent". Use 4 or 5 for a real alert; use 2 for a daily report, which sits silently in the notification list. If everything is urgent, nothing is urgent anymore.
  5. POST and the response code. On success, ntfy returns 200. If you see 429, you've gone over the request limit; if it's a negative number, the problem is the network or the certificate.
  6. A sending limit. After each alert, no other alert is sent for 30 seconds, even if the button is held down. Without this, holding the button for 2 seconds means dozens of requests and dozens of notifications, and a few minutes later the service blocks you. Every device that sends messages to an outside service needs "brakes" (rate limiting).

A checklist for a device that stays on for months

A program that works on your desk for 10 minutes is different from a program that works for 6 months without anyone touching it. Problems you never see in 10 minutes: memory that slowly breaks into fragments, Wi-Fi that drops at 3 a.m., power that goes out in the middle of writing a file. The engineering rule: assume that anything that can go wrong eventually will, and the device must pick itself back up.

RiskSymptomCure
The program gets stuck in a loop or a waitThe device is "alive" but doesn't respondWatchdog: register loop and the important tasks with the watchdog, so the board resets if they get stuck
Wi-Fi or internet dropsAfter the router goes down, it never sends data againAutomatic reconnection with events and a millis watchdog (lesson 4.1); every network operation needs a time limit
Heap fragmentationA crash or a NoMemory error after a few days, even though "free memory" looks plentifulIn long-running code, avoid constantly creating and destroying Strings; use reserve(), or use char[] with snprintf
Weak power (brownout)Resets when Wi-Fi or a relay switches onA 5 V, 1 A supply, a short cable, a 100 to 470 µF capacitor (lesson 4.1); never turn off the brownout detector
Power cut in the middle of writing a fileA half-written settings file; the device boots with broken settingsWrite to a temporary file first, then rename it; always have default values
Not knowing why resets happen"Sometimes it resets by itself", with no clue whyRead esp_reset_reason() at startup, print it, and keep a counter in Preferences
An everyday example: an airplane's black box

After every incident, an airplane can tell what happened, because it has a black box. Your device needs a "black box" too: every time it powers up, it should say why it reset and how many times it has crashed so far. Without that, troubleshooting a device in the ceiling is just guessing.

#include <Preferences.h>
#include "esp_system.h"
#include "esp_task_wdt.h"

Preferences prefs;

const char *resetReasonText(esp_reset_reason_t r) {
  switch (r) {
    case ESP_RST_POWERON:   return "power on";
    case ESP_RST_SW:        return "software (ESP.restart)";
    case ESP_RST_PANIC:     return "PANIC (crash / Guru Meditation)";
    case ESP_RST_INT_WDT:   return "interrupt watchdog";
    case ESP_RST_TASK_WDT:  return "TASK WATCHDOG";
    case ESP_RST_WDT:       return "other watchdog";
    case ESP_RST_DEEPSLEEP: return "wake from deep sleep";
    case ESP_RST_BROWNOUT:  return "BROWNOUT (weak power)";
    default:                return "other/unknown";
  }
}

void workerTask(void *param) {
  esp_task_wdt_add(NULL);                      // register this task with the watchdog
  for (;;) {
    // ... the task's real work goes here ...
    esp_task_wdt_reset();                      // "I'm alive"
    vTaskDelay(pdMS_TO_TICKS(1000));
  }
}

void setup() {
  Serial.begin(115200);
  delay(500);
  esp_reset_reason_t why = esp_reset_reason();

  prefs.begin("sys", false);                   // "sys" namespace in NVS
  uint32_t boots = prefs.getUInt("boots", 0) + 1;
  prefs.putUInt("boots", boots);
  if (why == ESP_RST_PANIC || why == ESP_RST_TASK_WDT || why == ESP_RST_BROWNOUT) {
    prefs.putUInt("crashes", prefs.getUInt("crashes", 0) + 1);
  }
  Serial.printf("Boot #%lu, reason: %s, crashes so far: %lu\n",
                (unsigned long)boots, resetReasonText(why),
                (unsigned long)prefs.getUInt("crashes", 0));
  prefs.end();

  enableLoopWDT();                             // if loop is stuck over 5 s: reset
  xTaskCreatePinnedToCore(workerTask, "worker", 3072, NULL, 1, NULL, 1);
}

String line;                                   // global, reserved once

void loop() {
  line.reserve(64);                            // does nothing after the first time
  line = "uptime=";
  line += millis() / 1000;
  line += "s heap=";
  line += ESP.getFreeHeap();
  Serial.println(line);
  delay(2000);                                 // change this to 6000 and the WDT resets
}
  1. Turning the reset reason into text. esp_reset_reason() returns a number of type esp_reset_reason_t, and we turn the most important ones into readable text. Three reasons that should always worry you: PANIC (a crash, such as a Guru Meditation or a stack overflow), TASK_WDT (a task got stuck), and BROWNOUT (weak power). POWERON means power was connected, and SW means the program itself called ESP.restart() (after an OTA update, for example). Note: pressing the EN button on the ESP32 is usually reported as POWERON.
  2. Registering a task with the watchdog. esp_task_wdt_add(NULL) means "watch the current task", and esp_task_wdt_reset() means "I'm alive". From this moment, if this task doesn't reset the watchdog for more than 5 seconds, the board resets. Put the reset where it runs only when the work is really making progress, not in a separate task that is always alive (then you'd be fooling the watchdog). Add a task that does long jobs such as HTTPS with care, because one slow request can take more than 5 seconds.
  3. Counters in Preferences. The total number of boots and the number of "bad" resets are stored in NVS and aren't lost when the power goes off. If after a week you see crashes is 40, you know something is wrong, even if the device "seems to work". We only write at boot, not in loop, so the flash doesn't wear out. In a real project, report these numbers on the web page or over MQTT.
  4. enableLoopWDT. A ready-made core function that registers loopTask with the watchdog. The core itself resets the watchdog before every pass of loop(). So if one pass of loop takes more than 5 seconds (for example it gets stuck in a while waiting for a sensor that has been disconnected), the board resets itself and starts over. A reset is better than freezing forever.
  5. A String with reserve. The global variable line grabs 64 bytes once, and every pass refills that same space. Every time a String grows, it may take a new spot in the heap and leave the old one empty. After thousands of times, the heap becomes full of holes, like Swiss cheese: the total free space is large, but no big continuous piece is left (and HTTPS needs a continuous piece of several tens of kilobytes). reserve takes the space once, up front. For fixed-size strings, char buf[64] with snprintf is the safest. To see the problem, print ESP.getMaxAllocHeap() (the largest free block) as well as ESP.getFreeHeap().
  6. Testing the watchdog. If you change the delay to 6000, each pass of loop takes more than 5 seconds and the board resets; after the reset you'll see the message reason: TASK WATCHDOG. Trigger every safety mechanism on purpose once, to make sure it really works. A watchdog that has never been tested isn't a watchdog.

Writing safely in case of power loss

Suppose you're rewriting config.json and the power goes out right in the middle. Mode "w" had already emptied the old file; now you have neither the old settings nor the new ones. The right pattern (you'll see it in the project below): 1) write to config.tmp, 2) close it, 3) delete the old file and rename the tmp file to config.json. Renaming in LittleFS is almost instant. And in any case, when the settings file is missing or broken, the program must come up with default values, not crash. For small values, Preferences already has this safety built in.

Config cfg = {43.65, -79.38};      // default: Toronto

// ---------- LittleFS: reading and safely saving the settings ----------
void loadConfig() {
  File f = LittleFS.open("/config.json", "r");
  if (!f) return;                                  // not saved yet
  JsonDocument doc;
  if (!deserializeJson(doc, f)) {
    cfg.lat = doc["lat"] | cfg.lat;
    cfg.lon = doc["lon"] | cfg.lon;
  }
  f.close();
}

bool saveConfig(const Config &c) {
  JsonDocument doc;
  doc["lat"] = c.lat;
  doc["lon"] = c.lon;
  File f = LittleFS.open("/config.tmp", "w");      // temporary file first
  if (!f) return false;
  bool ok = serializeJson(doc, f) > 0;
  f.close();
  if (!ok) return false;
  LittleFS.remove("/config.json");
  return LittleFS.rename("/config.tmp", "/config.json");  // then swap it in
}

// ---------- Weather task: every 10 minutes, or when the settings change ----------
bool fetchWeather(float lat, float lon, Weather &w) {
  char url[160];
  snprintf(url, sizeof(url),
           "https://api.open-meteo.com/v1/forecast?latitude=%.2f&longitude=%.2f"
           "&current=temperature_2m,wind_speed_10m", lat, lon);
  WiFiClientSecure client;
  client.useBuiltinCACertBundle();
  HTTPClient http;
  http.setConnectTimeout(5000);
  http.setTimeout(5000);
  http.useHTTP10(true);
  if (!http.begin(client, url)) return false;
  int code = http.GET();
  bool ok = false;
  if (code == HTTP_CODE_OK) {
    JsonDocument filter;
    filter["current"]["temperature_2m"] = true;
    filter["current"]["wind_speed_10m"] = true;
    JsonDocument doc;
    if (!deserializeJson(doc, http.getStream(), DeserializationOption::Filter(filter))) {
      w.temp = doc["current"]["temperature_2m"] | NAN;
      w.wind = doc["current"]["wind_speed_10m"] | NAN;
      w.at = millis();
      ok = !isnan(w.temp);
    }
  }
  http.end();
  return ok;
}

void weatherTask(void *param) {
  for (;;) {
    if (WiFi.status() == WL_CONNECTED) {
      xSemaphoreTake(cfgMutex, portMAX_DELAY);
      Config c = cfg;                              // copy, then give the lock back
      xSemaphoreGive(cfgMutex);
      Weather w;
      if (fetchWeather(c.lat, c.lon, w)) {
        xQueueOverwrite(weatherBox, &w);           // replaces the previous value
      }
    }
    // sleep 10 minutes, unless someone wakes us up sooner
    ulTaskNotifyTake(pdTRUE, pdMS_TO_TICKS(10UL * 60 * 1000));
  }
}

// ---------- Display task: latest weather on the OLED every 2 seconds ----------
void displayTask(void *param) {
  Weather w;
  for (;;) {
    display.clearDisplay();
    display.setCursor(0, 0);
    display.println(WiFi.localIP());
    if (xQueuePeek(weatherBox, &w, 0) == pdPASS) {  // look, don't take
      display.setTextSize(2);
      display.printf("%.1f C\n", w.temp);
      display.setTextSize(1);
      display.printf("wind %.1f km/h\n", w.wind);
      display.printf("%lu min ago", (millis() - w.at) / 60000);
    } else {
      display.println("waiting for data...");
    }
    display.display();
    vTaskDelay(pdMS_TO_TICKS(2000));
  }
}

// ---------- Web: page from LittleFS, data from code ----------
void handleState() {
  Weather w = {NAN, NAN, 0};
  xQueuePeek(weatherBox, &w, 0);
  JsonDocument doc;
  xSemaphoreTake(cfgMutex, portMAX_DELAY);
  doc["lat"] = cfg.lat;
  doc["lon"] = cfg.lon;
  xSemaphoreGive(cfgMutex);
  doc["temp"] = w.temp;
  doc["wind"] = w.wind;
  String out;
  serializeJson(doc, out);
  server.send(200, "application/json", out);
}

void handleSave() {
  Config c = {server.arg("lat").toFloat(), server.arg("lon").toFloat()};
  if (c.lat < -90 || c.lat > 90 || c.lon < -180 || c.lon > 180) {
    return server.send(400, "text/plain", "bad lat/lon");
  }
  xSemaphoreTake(cfgMutex, portMAX_DELAY);
  cfg = c;
  xSemaphoreGive(cfgMutex);
  saveConfig(c);
  xTaskNotifyGive(weatherHandle);                  // "fetch again right now"
  server.sendHeader("Location", "/");
  server.send(303);
}

void setup() {
  Serial.begin(115200);
  LittleFS.begin(true);
  loadConfig();
  weatherBox = xQueueCreate(1, sizeof(Weather));
  cfgMutex = xSemaphoreCreateMutex();

  Wire.begin(21, 22);
  display.begin(SSD1306_SWITCHCAPVCC, 0x3C);
  display.setTextColor(SSD1306_WHITE);

  WiFi.mode(WIFI_STA);
  WiFi.setAutoReconnect(true);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  unsigned long t0 = millis();
  while (WiFi.status() != WL_CONNECTED && millis() - t0 < 20000) delay(250);

  ArduinoOTA.setHostname("weather-station");
  ArduinoOTA.setPassword(OTA_PASS);
  ArduinoOTA.begin();

  server.serveStatic("/", LittleFS, "/index.html");
  server.on("/api/state", HTTP_GET, handleState);
  server.on("/api/config", HTTP_POST, handleSave);
  server.begin();

  xTaskCreatePinnedToCore(weatherTask, "weather", 12288, NULL, 1, &weatherHandle, 1);
  xTaskCreatePinnedToCore(displayTask, "display", 4096, NULL, 1, NULL, 1);
}

void loop() {
  ArduinoOTA.handle();
  server.handleClient();
  delay(2);
}
  1. Two structs. Weather is a package of temperature, wind and the time it was fetched; Config holds the coordinates. Packing related data into one struct lets a single xQueueOverwrite move it all together, in one piece; a new temperature never gets mixed up with an old time.
  2. A one-slot queue as a "mailbox". A queue of length 1 that is filled with xQueueOverwrite and read with xQueuePeek. In the ordinary queue (lesson 5.4), each piece of data was read and removed once. Here we have two readers (the OLED and the web page), and both just want "the latest weather"; Peek looks without removing, and Overwrite always replaces the previous value and never finds the queue "full".
  3. Reading the settings at boot. If the file doesn't exist or the JSON is broken, the Toronto default (line 25) stays. The same principle as the reliability checklist: the device must always boot, even with incomplete settings.
  4. Saving safely. First config.tmp, then delete the old file and rename. If the power goes out in the middle of serializeJson, the previous config.json is still intact. serializeJson(doc, f) writes straight into the file and returns the number of bytes; zero means failure.
  5. fetchWeather. The same code as the weather example earlier in this lesson, with two differences: the address is built from the coordinates with snprintf, and this time we use useBuiltinCACertBundle. snprintf writes into a fixed 160-byte array and never runs past its end; no temporary String is created on the heap. This task runs every 10 minutes for months, so this is exactly where heap fragmentation matters.
  6. weatherTask. It copies the settings under the lock, gives the lock back right away, then does the slow HTTPS request and puts the result in the mailbox. Never hold a lock during a slow job (several seconds of HTTPS), or the web page, which also needs cfg, has to wait just as long. "Copy, release, then work".
  7. ulTaskNotifyTake with a 10-minute limit. The task sleeps until either 10 minutes pass or someone wakes it with xTaskNotifyGive. A task notification is FreeRTOS's lightest tool for "hey, wake up". With a plain vTaskDelay, after changing the city you'd have to wait up to 10 minutes for the new weather.
  8. displayTask. Every 2 seconds it redraws the screen: the IP address, the temperature in large text, the wind, and how many minutes ago the data was fetched. Only this task touches the OLED (and I2C), so the display doesn't need a mutex. A rule simpler than locks: every piece of hardware has one owner. Showing "minutes ago" matters: if the internet is down for a day, the user won't mistake yesterday's temperature for today's.
  9. /api/state. Peeks the latest weather from the mailbox, reads the settings under the lock, and returns everything as JSON. This function runs in loopTask (inside server.handleClient), while weatherTask may be reading cfg at the same moment, or waiting for it to change; that's why the lock is needed.
  10. /api/config. It validates the input, saves it in cfg and in the file, wakes up weatherTask, and sends the browser back to the main page with code 303. Never trust user input: toFloat() returns zero for invalid text, and a latitude of 500 makes no sense. The 303 makes sure that refreshing the page doesn't resend the form.
  11. setup in the right order. LittleFS and the settings, then the queue and the lock (before any task), the OLED, Wi-Fi with a 20-second limit, OTA, the web server, and finally the tasks. If Wi-Fi doesn't connect within 20 seconds, the device doesn't stop: setAutoReconnect connects it later, and weatherTask simply waits until then. weatherTask's stack is deliberately 12 KB because HTTPS is heavy; after a few days, measure the real value with uxTaskGetStackHighWaterMark.
  12. A tiny loop. Only OTA and the web server, with a delay(2). Because the slow work lives in a separate task, loop always comes round in a few milliseconds, and OTA and the web page always answer quickly, even in the middle of a slow HTTPS request. That's exactly the problem lesson 5.4 started with.

Coach's corner

Two rules to take away. One, a device that doesn't record the cause of its resets isn't a professional device. From today on, in every project that stays on for more than a day, include the "black box" code from the reliability checklist. Once the crash counter has stayed at zero for a week, then you can say "it works". Two, be a polite guest on other people's servers: a sensible interval, time limits on every request, and brakes on every alert. A device that hammers an API every second gets blocked, and then it doesn't work at all.

Lesson quiz

In the weather example, why did we put http.useHTTP10(true) before deserializeJson(doc, http.getStream(), ...)?

  1. Because HTTP 1.0 is faster
  2. So the server doesn't send the answer chunked (in pieces with size numbers), which would corrupt the JSON read from the stream
  3. Because HTTPS only works with HTTP 1.0
  4. So the server's certificate isn't checked
When you read straight from getStream(), HTTPClient doesn't stitch the chunks back together. HTTP/1.0 removes the problem at its root.

Your device sends a "door opened" alert to your phone through ntfy. Which connection setting is right?

  1. setInsecure(), because it's simpler
  2. Plain http:// with no encryption
  3. It doesn't matter for a notification
  4. useBuiltinCACertBundle()
For anything that carries commands, passwords or important alerts, check the server's identity. The built-in bundle does it without you having to copy a certificate.

After a week, your device's page shows "crashes: 40" and the last reset reason is TASK WATCHDOG. What does that tell you?

  1. A task (or loop) got stuck for more than 5 seconds, again and again; find out which one
  2. The power supply is too weak
  3. Everything is fine; the watchdog is just strict
  4. Someone pressed the EN button 40 times
The watchdog kept the device alive by resetting it, but the bug is still there. The CPU 0: ... line in the watchdog message names the culprit.

In the weather station, why does weatherTask copy the settings under the lock and give the lock back before the HTTPS request?

  1. To save RAM
  2. Because HTTPS doesn't work while a mutex is held
  3. So the web page, which also needs the settings, doesn't have to wait seconds for a slow request
  4. Because a mutex expires after one second
"Copy, release, then work": hold a lock only for the moment you touch the shared data, never during a slow job.

Exercises

Exercise 1: heat alert

Combine the weather program and the ntfy program: if the temperature in your city goes above 30 degrees, send an ntfy alert, but only once, until the temperature drops back below 28 degrees. The "alert already sent" state must be remembered even after a reset.

Hint

The gap between 30 and 28 is "hysteresis", so that temperatures of 30 and 29.9 one after another don't create dozens of alerts. To remember across resets, a bool in Preferences is enough; write it only when its value changes.

Answer (the key part) 
prefs.begin("alert", false);
bool sent = prefs.getBool("sent", false);
if (!sent && t > 30.0) {
  if (sendAlert("Heat", "Above 30 C")) {
    prefs.putBool("sent", true);   // only once it was really sent
  }
} else if (sent && t < 28.0) {
  prefs.putBool("sent", false);    // ready for the next alert
}
prefs.end();
Exercise 2: the black box on the web page

Add the "black box" from the reliability checklist to the weather-station project: return the reason for the last reset, the number of boots and the number of crashes in /api/state, and show them in index.html. Then make a deliberate change (for example, an endless loop in loop after 1 minute, with enableLoopWDT) to trigger a watchdog reset, and check that it gets recorded on the page. Finally, send the fixed version over OTA.

Hint

Read the reset reason once in setup and keep it in a global const char * variable; in handleState just put it into the JSON. For the OTA test, make sure the broken version still calls ArduinoOTA.handle() during that first minute, or you'll have to fix it with the cable. (This very experience will make the coach's OTA advice in lesson 5.5 real for you.)

The lesson in three lines

Call APIs with HTTPS, time limits, a JSON filter and a sensible interval, and check the server's identity with the built-in CA bundle whenever something important travels. A device that runs for months records why it reset, counts its crashes, lets the watchdog restart it when it gets stuck, avoids heap fragmentation and saves files safely. The weather station puts it all together: slow work in its own task, data in a one-slot mailbox, settings in LittleFS and updates over OTA.

That's the end of chapter 5. In lesson 6.1 you learn to make a device like this last for months on a battery, with deep sleep and light sleep.
