Wi-Fi is great for connecting to a router and the internet. But what if there is no router? In a car, on a mountain, or when you just want to control something in the same room with the phone in your hand. That's where Bluetooth comes in. The ESP32 has two kinds of Bluetooth, and in this lesson you build with both: first a "wireless serial cable" with Bluetooth Classic, then a proper BLE device that talks to your phone the way a smartwatch does.

Bluetooth from scratch: two different languages with one name

"Bluetooth" is really the name of two technologies. Both work on the same 2.4 GHz band (like Wi-Fi), but they speak completely different languages and can't talk to each other directly:

  • Bluetooth Classic (also called BR/EDR): the older version, made for a continuous stream of data. Headphones, speakers, car hands-free kits, and file transfer between older phones.
  • Bluetooth Low Energy (BLE): since 2010 (Bluetooth 4.0). Made for small packets of data at very low power. Smartwatches and fitness bands, smart scales, temperature sensors, key finders.
An everyday example: a phone call vs a text message

Bluetooth Classic is like a phone call: the line stays open and both sides keep talking. Great for audio, but it eats the battery. BLE is like texting: it's quiet most of the time and sends a short message every now and then. The coin cell in a BLE sensor can last for months, even years.

With numbers: ESP32 power use

Note that "low energy" describes the protocol. The ESP32 itself draws about 100 mA or more while its radio is on, whether it's Classic or BLE. The difference is that with BLE you can keep the radio off most of the time (for example, on for a few milliseconds every 1 second). You'll see this in full in lesson 6.1, deep sleep.

Part A: Bluetooth Classic, a wireless serial cable

The built-in BluetoothSerial library makes the ESP32 look like a "serial port" to your phone: the same idea as the Serial Monitor, just without the cable. Whatever the phone sends, the ESP32 reads with SerialBT.read(), and whatever the ESP32 writes with SerialBT.println() shows up on the phone's screen. The profile that does this is called SPP (Serial Port Profile).

The iPhone can't do this part

iOS doesn't let apps use SPP to connect to Bluetooth Classic devices that lack Apple's special certification (MFi). So you won't find an iPhone app for this part. If you have an iPhone, read this part to learn the idea, and do the hands-on test in the BLE part; BLE works perfectly on the iPhone.

#include <BluetoothSerial.h>

// If your board is a C3 or S3, this stops the compile (they have no Classic)
#if !defined(CONFIG_BT_SPP_ENABLED)
#error "Bluetooth Classic (SPP) is only available on the original ESP32"
#endif

BluetoothSerial SerialBT;           // the "wireless serial port"
const int LED_PIN = 4;
bool ledOn = false;
String line = "";                   // incoming characters collect here

void handleCommand(String cmd) {
  cmd.trim();                       // remove extra spaces, \r and \n
  cmd.toLowerCase();                // so "ON" and "On" are accepted too
  if (cmd.length() == 0) return;    // ignore empty lines

  Serial.printf("Command: [%s]\n", cmd.c_str());
  if (cmd == "on") {
    ledOn = true;
    SerialBT.println("OK: LED is ON");
  } else if (cmd == "off") {
    ledOn = false;
    SerialBT.println("OK: LED is OFF");
  } else if (cmd == "status") {
    SerialBT.println(ledOn ? "LED is ON" : "LED is OFF");
  } else {
    SerialBT.println("Unknown command. Use: on / off / status");
  }
  digitalWrite(LED_PIN, ledOn ? HIGH : LOW);
}

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  if (!SerialBT.begin("ESP32-LED")) {           // the name the phone sees
    Serial.println("Bluetooth init failed!");
    while (true) delay(1000);                   // no point going on without Bluetooth
  }
  Serial.println("Bluetooth ready. Pair your phone with 'ESP32-LED'");
}

void loop() {
  while (SerialBT.available()) {                // as long as new characters are waiting
    char c = SerialBT.read();
    if (c == '\n' || c == '\r') {               // end of a command
      handleCommand(line);
      line = "";
    } else if (line.length() < 32) {            // length cap, to keep memory safe
      line += c;
    }
  }
}
  1. The BluetoothSerial library. It comes installed with the ESP32 package. This library hides all the complexity of the Bluetooth stack (Bluedroid) and gives you an interface that works exactly like Serial; everything you know about Serial works here too.
  2. A compile-time guard. #if !defined(CONFIG_BT_SPP_ENABLED) means "if SPP support is not turned on for this board". In that case #error stops the compile with a clear message. It's better to learn at compile time, in one plain sentence, that the board you picked (a C3, say) has no Bluetooth Classic, than to face dozens of cryptic errors. These lines start with # and are checked before compiling, not on the board.
  3. The Bluetooth object and the variables. SerialBT is our wireless serial port. ledOn remembers the LED state, and line collects incoming characters until "Enter" arrives. Bluetooth data arrives character by character, sometimes in pieces, not all at once. It's like someone spelling out a word letter by letter: you shouldn't decide anything until the sentence is finished.
  4. Cleaning up the command. trim() removes spaces and the invisible \r and \n characters from both ends of the text. toLowerCase() makes every letter lowercase. We ignore empty text. Apps usually send \r\n (two characters) at the end of each message, and users sometimes type "On " with a space, or "ON". Without these two lines, "on\r" == "on" is false, and a beginner can spend hours thinking Bluetooth is broken. This is called robust input handling. Both functions change the text itself and return nothing.
  5. A log line in the Serial Monitor. We print the cleaned-up command between [ ]. The brackets show whether an invisible character or a space is left over: [on] is correct, [on ] means something is wrong with trim.
  6. Decide and reply. Three commands: on, off and status. Each one sends a reply to the phone with SerialBT.println. An unknown command gets a help message. At the end, we bring the LED in line with ledOn. Replying to every command lets the user on the phone know the command arrived and was carried out. One digitalWrite at the end, instead of several in the branches, means the LED always matches the stored state exactly.
  7. Turning Bluetooth on. SerialBT.begin("ESP32-LED") starts Bluetooth with this name and returns false if it fails. In that case we print an error and stop the program. This is the name you'll see in your phone's Bluetooth list; pick a distinctive one so it doesn't get mixed up with other devices. Stopping with while (true) is deliberate here: a program whose only job is Bluetooth has nothing to do without it. (In a program that also does other things, we would just set an error flag instead of stopping.)
  8. loop: collecting characters. As long as a character is waiting (available()), read it. If it's \n or \r, the command is finished: run it and empty line. Otherwise add the character to line, as long as it doesn't go over 32 characters. There's no delay or waiting in loop; it only takes the characters that are ready. The 32-character cap stops someone from filling the ESP32's memory by sending endless text; never trust the length of outside input. Because \r\n calls handleCommand twice, the second call gets empty text, which is ignored on line 16.

Part B: BLE and the idea of GATT

In BLE there is no "continuous pipe" any more. Instead, every BLE device has a neat table of values that the phone can read, write or subscribe to. This structure is called GATT (Generic Attribute Profile). Before the code, you need to know these few names as well as your friends' names.

An everyday example: an office filing cabinet

The ESP32 is a cabinet in an office hallway (the Server). The cabinet has several shelves, each for one topic (a Service, say "the lights shelf"). Each shelf holds several drawers, each with its own unique label stuck on it (a Characteristic with a UUID), and inside each drawer is a value, for example "on". Each drawer also says what you're allowed to do with it (its Properties): "look only" (Read), "you may leave a note" (Write), or "I'll text you whenever the contents change" (Notify). The phone (the Client) is the office worker who comes to the cabinet.

Why is a UUID so long?

The Bluetooth organization has defined short 16-bit UUIDs for standard services; for example 0x180F means "Battery Service" and 0x2A19 means "Battery Level". Every phone in the world knows these. For something you invented yourself (like our LED), you must make a random 128-bit UUID. The number of possible values is so huge (about 10 to the power of 38) that the chance of anyone else in the world making the same one is practically zero. To make your own UUIDs, use a site like uuidgenerator.net. Never use the standard UUIDs for your own things, or the phone will think your device is, say, a heart-rate monitor.

Notify, with numbers

Without Notify, the phone has to "read" (Read) every time it wants the latest value; that's polling, as in lesson 4.2. With Notify, the ESP32 sends the new value by itself every 2 seconds. In one hour that's 1,800 small messages, instead of the phone asking "anything new?" every 200 milliseconds, say (18,000 times an hour). Ten times fewer messages means less battery for both sides.

A five-minute C++ primer for the code below

The BLE library is written in "real" C++, so the next program uses a few words you haven't needed yet. Think of building houses:

  • class: a blueprint. BLEServer is the blueprint of "a BLE server"; it describes what one has and what it can do, but it isn't a server yet.
  • object: an actual house built from the blueprint. WebServer server(80); in lesson 4.2 built one object called server. You can build many houses from one blueprint.
  • pointer (*): a note with a house's street address on it, not the house itself. BLEServer* pServer is such a note; the library builds the house and hands you only its address. nullptr is an empty note: "no address yet". And &x means "write down the address of x", as in getLocalTime(&t) in lesson 4.1.
  • ->: "go to the address on this note and use what's there". pServer->setCallbacks(...) calls a function of the object the pointer points to. With a plain object you use a dot instead: server.begin().
  • new: build a new house now and give me its address. new LedCallbacks() makes an object that stays alive for the whole program (it isn't thrown away at the end of setup).
  • inheritance and override: class LedCallbacks : public BLECharacteristicCallbacks means "my blueprint is the library's blueprint plus my changes". The library's version is like a standard form with empty lines (onWrite does nothing); override says "I'm filling in exactly this line", and the compiler complains if the line's name or shape doesn't match.
  • ::: "belongs to the blueprint itself", not to one particular house. BLEDevice::init(...) is like calling the company's main office rather than a single employee; there's only one BLE radio, so no object is needed.

You don't need to write classes yourself yet. It's enough to read the program below and recognize these pieces.

The BLE server program

#include <BLEDevice.h>
#include <BLEServer.h>
#include <BLEUtils.h>
#include <BLE2902.h>

// Our own unique IDs (UUIDs), made with a random UUID generator
#define SERVICE_UUID       "0582d484-de7b-45b7-b730-09a9fae5cbf4"
#define LED_CHAR_UUID      "851c0eca-a1b1-4b1e-9a56-9f9f546e7ab6"
#define COUNTER_CHAR_UUID  "e8f00efd-6510-4206-8140-d2feea0d4aa7"

const int LED_PIN = 4;
BLEServer* pServer = nullptr;
BLECharacteristic* pLedChar = nullptr;
BLECharacteristic* pCounterChar = nullptr;
volatile bool deviceConnected = false;
bool wasConnected = false;
uint32_t counter = 0;
unsigned long lastNotify = 0;

// 1) When the phone connects or disconnects
class ServerCallbacks : public BLEServerCallbacks {
  void onConnect(BLEServer* s) override {
    deviceConnected = true;
    Serial.println("Phone connected");
  }
  void onDisconnect(BLEServer* s) override {
    deviceConnected = false;
    Serial.println("Phone disconnected");
  }
};

// 2) When the phone writes something to the LED characteristic
class LedCallbacks : public BLECharacteristicCallbacks {
  void onWrite(BLECharacteristic* c) override {
    String v = c->getValue();               // in core 3.x its type is String
    v.trim();
    v.toLowerCase();
    Serial.printf("LED write: [%s]\n", v.c_str());
    if (v == "on" || v == "1") {
      digitalWrite(LED_PIN, HIGH);
      c->setValue("on");
    } else if (v == "off" || v == "0") {
      digitalWrite(LED_PIN, LOW);
      c->setValue("off");
    }
  }
};

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);

  BLEDevice::init("ESP32-BLE-LED");                 // the name in the scan list
  pServer = BLEDevice::createServer();
  pServer->setCallbacks(new ServerCallbacks());

  BLEService* service = pServer->createService(SERVICE_UUID);

  pLedChar = service->createCharacteristic(
      LED_CHAR_UUID,
      BLECharacteristic::PROPERTY_READ | BLECharacteristic::PROPERTY_WRITE);
  pLedChar->setCallbacks(new LedCallbacks());
  pLedChar->setValue("off");

  pCounterChar = service->createCharacteristic(
      COUNTER_CHAR_UUID,
      BLECharacteristic::PROPERTY_READ | BLECharacteristic::PROPERTY_NOTIFY);
  pCounterChar->addDescriptor(new BLE2902());       // the phone's on/off switch for notify

  service->start();

  BLEAdvertising* adv = BLEDevice::getAdvertising();
  adv->addServiceUUID(SERVICE_UUID);
  adv->setScanResponse(true);
  BLEDevice::startAdvertising();
  Serial.println("Advertising as ESP32-BLE-LED ...");
}

void loop() {
  unsigned long now = millis();

  // 3) Every 2 seconds, send the phone a new number
  if (deviceConnected && now - lastNotify >= 2000) {
    lastNotify = now;
    counter++;
    String msg = "count=" + String(counter);
    pCounterChar->setValue(msg);
    pCounterChar->notify();
    Serial.println("notify: " + msg);
  }

  // 4) Phone gone? Advertise again so others can find us
  if (!deviceConnected && wasConnected) {
    delay(500);                                     // give the Bluetooth stack a moment
    pServer->startAdvertising();
    Serial.println("Advertising again");
    wasConnected = false;
  }
  if (deviceConnected && !wasConnected) {
    wasConnected = true;
  }
}
  1. Four built-in BLE library files. BLEDevice (the device itself), BLEServer (the GATT server), BLEUtils (utilities) and BLE2902 (the special descriptor for notify). All of these are part of the BLE library built into the ESP32 package; there's nothing extra to install. The same code works on the ESP32, C3, S3 and C6.
  2. Three UUIDs. One for the service and two for the two characteristics. #define substitutes the text. The UUIDs must be the same on the ESP32 and in the phone app; keeping them at the top of the program makes them easy to find and compare.
  3. Global variables. Pointers to the server and the two characteristics, so we can reach them in loop too. deviceConnected is volatile because it's changed from the Bluetooth task. counter is the number we send every 2 seconds. The * means "the address of an object", not the object itself; the BLE library creates the objects on its own and only hands us their addresses. nullptr means "doesn't point anywhere yet". The reason for volatile is the same one you saw for Wi-Fi events in lesson 4.1.
  4. The server callback class. A class that inherits from BLEServerCallbacks and overrides its two functions, onConnect and onDisconnect (override). The library calls them when the phone connects and disconnects. This is the same "doorbell" idea from lesson 4.1, just in the shape of a C++ class. override tells the compiler "make sure I really am replacing a function of the parent class"; if you misspell the name or the parameters, you get a compile error instead of silent failure. Just like with Wi-Fi events, we only change a variable here and leave the heavy work to loop.
  5. The write callback: onWrite. This function is called every time the phone writes something to the LED characteristic. c->getValue() gives you the written value. The -> sign means "call this function through this pointer". In core 3.x, getValue() returns an Arduino String (you'll read about the difference from 2.x further down).
  6. Clean up and act. trim and toLowerCase again. If the value is "on" or "1", the LED goes on; if it's "off" or "0", it goes off. Then c->setValue sets the characteristic's value to the standard form ("on" or "off"). Accepting "1" and "0" makes life easier for apps that send numbers. Updating the value means that if the phone "reads" this characteristic later, it sees the LED's real state, not whatever the user typed. Unknown input does nothing at all: the safest default.
  7. Starting the device and the server. BLEDevice::init starts the BLE stack with a name. createServer creates the GATT server, and setCallbacks hands it our doorbell class. :: means "a function that belongs to the class itself, not to one particular object", because we only have one BLE device. new creates a callback object that stays alive for the whole life of the program.
  8. Creating the service. Our "shelf", with its own UUID. Every characteristic has to live inside a service; there is no such thing as a characteristic without a service.
  9. The LED characteristic. Created with the permissions PROPERTY_READ | PROPERTY_WRITE; the | sign means "both". The write callback is attached to it, and its starting value is "off". Only grant the permissions you need: this drawer has no notify because the LED never changes by itself; only we change it. The starting value means that if the phone reads before anything has been written, it still gets a correct answer.
  10. The counter characteristic and descriptor 0x2902. Permissions READ | NOTIFY. Then addDescriptor(new BLE2902()) adds the standard CCCD descriptor. By the Bluetooth standard, the phone turns notify on by writing to this very descriptor (that's what happens when you tap the triple-arrow icon in nRF Connect). In the Bluedroid stack (the default for the original ESP32 in Arduino), if you don't add it, the phone can't subscribe and no notification ever arrives. In the NimBLE stack it's added automatically, but writing the line does no harm.
  11. service->start(). Activates the service. Until it's started, the phone won't see it in the list, even after connecting. All characteristics must be created before this line.
  12. Advertising. We add the service UUID to the advertisement, turn on the scan response, and start advertising. A BLE advertising packet is tiny (31 bytes). A 128-bit UUID takes 16 of them; the Scan Response is a second packet where the device name fits. The result: the phone sees the name and can also filter by service.
  13. Notify every 2 seconds, without delay. If the phone is connected and 2000 milliseconds have passed, increase the counter, build a text such as count=7, put it in the characteristic with setValue and send it with notify(). We send text instead of a raw binary number because nRF Connect shows text directly, so you can read it without converting from hex. In a real project you'd send a sensor value instead of a counter (for example, the temperature from a DHT22). When nobody is connected, we don't notify; sending to nobody just wastes energy.
  14. Advertising again after a disconnect. If we're not connected now but we were before, the phone has just left: wait 500 milliseconds, then call startAdvertising(). This is the biggest BLE trap for beginners: in this library, advertising stops when the phone connects, and after the phone disconnects it does not restart by itself. Without this part, the ESP32 becomes invisible forever after the first disconnect, until you reset it. (Core 3.x also has a shortcut: pServer->advertiseOnDisconnect(true); in setup; it's off by default. We wrote the manual version so you can see what happens behind the scenes.) The 500 milliseconds give the Bluetooth stack time to fully close the old connection. This short delay only happens once after each disconnect.
  15. Remembering the moment of connection. When we've just connected, set wasConnected to true. Together these two variables detect an "edge": the moment of change from disconnected to connected or back. It's the same idea as detecting the moment a button is pressed in lesson 3.1.
How much fits in one notification? 20 bytes by default

A BLE connection starts with an MTU (the maximum packet size) of 23 bytes, and 3 of those are overhead, so one notify or read carries 20 bytes of data by default. count=1800 (10 bytes) fits easily; temperature=23.5 humidity=41.2 (32 bytes) does not: the library cuts it to the first 20 bytes and prints a warning. Many phones ask for a bigger MTU after connecting (nRF Connect on Android has a "Request MTU" menu item), but you can't count on it. The simple rule: keep each value short (a number, or a few letters), or give each value its own characteristic.

Careful: BLE differences between core 3.x and 2.x

In core 2.x, getValue() returns a std::string (the standard C++ string), and almost every older tutorial has this line: std::string value = pCharacteristic->getValue();. In core 3.x the function returns an Arduino String, and that line no longer compiles (you get an error like conversion from 'String' to non-scalar type 'std::string' requested). The fix: write String value = .... If you really need a std::string: std::string v = c->getValue().c_str();. In core 3.x, setValue also accepts a String. Details are in the 2.x to 3.0 migration guide.

A lighter alternative: NimBLE-Arduino

The built-in BLE library is built on the Bluedroid stack, which takes a lot of flash and RAM. The NimBLE-Arduino library (from the Library Manager) does the same job with much less memory and is popular in projects that use Wi-Fi and BLE together. The class names are similar (NimBLEDevice, NimBLEServer…), but some callback signatures are different; so don't copy code over line by line, look at the library's own examples.

Security: who can connect?

Both programs in this lesson are unlocked. In part A, the ESP32 uses the "Just Works" method: any phone within about 10 meters can pair without a PIN. In part B, anyone with nRF Connect can connect and write to the LED characteristic. That's fine for a learning LED; for a door lock, never.

  • Secure pairing (Pairing / Bonding): BLE can encrypt the connection and ask for a 6-digit code (a Passkey) before the first connection. The BLE library has the BLESecurity class for this (look at the "Secure" or "Passkey" examples in the ESP32 and NimBLE libraries). Even a fixed code in your program is better than nothing.
  • A safe default rule: as in lesson 4.2, an unclear command should do nothing, and a dangerous output should default to off.
  • When you're done: in part A, if you don't want the device to be pairable all the time, turn Bluetooth off with SerialBT.end() when you've finished.

Coach's advice

BLE is confusing at first because you don't see any "messages", only a table of values. A common mistake is for a beginner to keep picturing "sending messages" and, when it doesn't work, to mix code from five different tutorials. Don't do that. First, with nRF Connect and none of your own apps, prove the server is right: the service is visible, writing works, notifications arrive. Only after that, move on to building an app or connecting a sensor. In any system with two sides, always test one side with a tool you know is correct. And remember: a phone disconnecting is a normal event, not an exception; a program that goes invisible after the first disconnect is broken.

Lesson quiz

Your friend has an ESP32-C3 and uploads the BluetoothSerial program. What happens?

  1. It works, but only with Android
  2. It works, but more slowly
  3. It doesn't compile, because the ESP32-C3 only has BLE and no Bluetooth Classic (SPP)
  4. It compiles, but nothing happens because the C3 has no Bluetooth at all
Only the original ESP32 has Bluetooth Classic. The C3, S3 and C6 only have BLE, and the S2 has no Bluetooth at all.

In nRF Connect, on the counter characteristic, the value never changes unless you tap the subscribe icon. Why?

  1. Because notifications are only sent to a phone that has subscribed by writing to descriptor 0x2902
  2. Because the ESP32 only counts while the app is open
  3. Because the READ permission isn't enough and WRITE must be added too
  4. Because Android doesn't support notify
Subscribing means the phone tells the ESP32 "from now on, send me the changes". This is done with the CCCD (that same 0x2902).

If you delete the line pServer->startAdvertising(); from loop, what happens?

  1. The ESP32 can never be found
  2. Notify stops working
  3. The LED won't light
  4. You can connect the first time, but after disconnecting, the ESP32 no longer shows up in scans until it's reset
Advertising stops when a phone connects and doesn't restart by itself after the disconnect. You have to restart advertising yourself.

The old line std::string value = c->getValue(); doesn't compile on core 3.x. What is the most correct change?

  1. Downgrade the core to 2.x
  2. String value = c->getValue();
  3. char value = c->getValue();
  4. int value = c->getValue();
In core 3.x, getValue returns an Arduino String. The trim and toLowerCase methods work on that String too.

In part A, why do we call trim() before comparing the command?

  1. To make capital letters lowercase
  2. To shorten long commands
  3. Because apps send invisible \r and \n characters or spaces at the end of a message, and without trim, "on\r" isn't equal to "on"
  4. To keep the ESP32's memory from filling up
Always clean up user input before comparing it. This is the simplest form of "robust input handling".

Exercise 1: a blink command

Add a blink command to the Bluetooth Classic program that blinks the LED 5 times (200 ms on and 200 ms off each time) and then returns it to its previous state. Also add a help command that sends a list of all the commands.

Hint

The simplest version is a for loop with delay inside handleCommand (2 seconds). The professional version (no delay): set a variable blinksLeft = 10, and in loop use the millis() pattern to flip the LED every 200 milliseconds and subtract one from blinksLeft. Which one did you choose, and why?

What should you see?

Wokwi doesn't simulate Bluetooth; try this on a real board with the Serial Bluetooth Terminal app on an Android phone. In the app (it shows the lines you sent in another color):

  • After blink you see exactly 5 blinks, and the whole thing takes 2 seconds (time it with your phone's stopwatch).
  • If the LED was on before, it stays on after the blinks; if it was off, it stays off.
  • Send status in the middle of a blink: the reply comes at once, before "Blink done". That proves the program didn't wait (no delay).
  • The Serial Monitor on the computer also shows each command, for example Command: [blink].

If it doesn't work:

Full answer with explanation

The complete BT_Classic_LED program with the blink and help commands (the professional version, with no delay):

#include <BluetoothSerial.h>

// If your board is a C3 or S3, this stops the compile (they have no Classic)
#if !defined(CONFIG_BT_SPP_ENABLED)
#error "Bluetooth Classic (SPP) is only available on the original ESP32"
#endif

BluetoothSerial SerialBT;           // the "wireless serial port"
const int LED_PIN = 4;
bool ledOn = false;
String line = "";                   // incoming characters collect here
bool blinking = false;              // is a blink sequence running?
int blinkStep = 0;                  // 0..9 = the ten on/off halves, 10 = restore
unsigned long lastBlinkStep = 0;

void handleCommand(String cmd) {
  cmd.trim();                       // remove extra spaces, \r and \n
  cmd.toLowerCase();                // so "ON" and "On" are accepted too
  if (cmd.length() == 0) return;    // ignore empty lines

  Serial.printf("Command: [%s]\n", cmd.c_str());
  if (cmd == "on") {
    ledOn = true;
    SerialBT.println("OK: LED is ON");
  } else if (cmd == "off") {
    ledOn = false;
    SerialBT.println("OK: LED is OFF");
  } else if (cmd == "status") {
    SerialBT.println(ledOn ? "LED is ON" : "LED is OFF");
  } else if (cmd == "blink") {
    blinking = true;                // loop does the actual blinking
    blinkStep = 0;
    lastBlinkStep = millis() - 200; // so the first step happens right away
    SerialBT.println("OK: blinking 5 times");
  } else if (cmd == "help") {
    SerialBT.println("Commands: on / off / status / blink / help");
  } else {
    SerialBT.println("Unknown command. Type help");
  }
  if (!blinking) digitalWrite(LED_PIN, ledOn ? HIGH : LOW);
}

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  if (!SerialBT.begin("ESP32-LED")) {           // the name the phone sees
    Serial.println("Bluetooth init failed!");
    while (true) delay(1000);                   // no point going on without Bluetooth
  }
  Serial.println("Bluetooth ready. Pair your phone with 'ESP32-LED'");
}

void loop() {
  while (SerialBT.available()) {                // as long as new characters are waiting
    char c = SerialBT.read();
    if (c == '\n' || c == '\r') {               // end of a command
      handleCommand(line);
      line = "";
    } else if (line.length() < 32) {            // length cap, to keep memory safe
      line += c;
    }
  }

  // blinking without delay: one step every 200 ms
  if (blinking && millis() - lastBlinkStep >= 200) {
    lastBlinkStep = millis();
    if (blinkStep < 10) {
      digitalWrite(LED_PIN, blinkStep % 2 == 0 ? HIGH : LOW);   // even = on, odd = off
      blinkStep++;
    } else {
      blinking = false;                         // done: back to the previous state
      digitalWrite(LED_PIN, ledOn ? HIGH : LOW);
      SerialBT.println(ledOn ? "Blink done, LED is ON" : "Blink done, LED is OFF");
    }
  }
}
  1. The blink memory. blinking says a blink sequence is running, blinkStep is the step number (0 to 10) and lastBlinkStep is the time of the last step. 5 blinks = 10 halves (on, off, on...) plus one final step that restores the previous state. It is the same idea as blinksLeft in the hint, just counting up.
  2. The blink command: just start it. handleCommand doesn't blink by itself; it only sets the state and replies at once. millis() - 200 means "pretend 200 ms have passed since the last step", so the first flash starts without a pause. ledOn is untouched, so the previous state is remembered automatically.
  3. help, and the unknown message. help sends a list of all the commands, and the "unknown" message now points to help. A help command means the user doesn't need to read the code to find out what the device can do.
  4. During a blink, loop owns the LED. If you send on or off mid-blink, only ledOn changes. That way two parts of the program don't fight over the LED; the new state is applied when the blink ends.
  5. Blinking in loop, with no delay. One step every 200 ms: even steps on, odd steps off. At step 10 the LED goes back to ledOn and a "done" message is sent. The timing: 0 on, 200 off, ... 1600 on, 1800 off, 2000 restore; exactly 5 full blinks in 2 seconds. We chose the no-delay version: with delay inside handleCommand the board would be deaf for 2 seconds and wouldn't answer status or any other command.
Exercise 2: notify a potentiometer

In the BLE program, instead of the counter, notify the value of a potentiometer on GPIO34 (as in lesson 4.2) every 500 milliseconds, but only when the value has changed by more than 20 units.

Hint

Keep a variable int lastSent = -100;. In loop: int v = analogRead(34); if (abs(v - lastSent) > 20) { ... notify ...; lastSent = v; }. Why the 20-unit condition? Because the ADC is a bit noisy, and without it messages would keep going out even when you aren't touching the potentiometer.

What should you see?

Wokwi has no Bluetooth, so test with a real board and the nRF Connect app. In nRF Connect, connect, open the service 0582d484-... and tap the triple-arrow (subscribe) button on the characteristic e8f00efd-.... If you see no value, tap the read button (down arrow) once to fetch the current value; the first notify may have gone out before you subscribed. In the Serial Monitor (the numbers are yours):

Advertising as ESP32-BLE-LED ...
Phone connected
notify: pot=2047
notify: pot=2311
notify: pot=2894
notify: pot=4095
  • While you don't touch the knob, no new messages arrive (neither on the phone nor on Serial). If the number keeps changing by small amounts, the 20-unit condition isn't working.
  • Turn the knob quickly from one end to the other: only a few messages arrive, at most two per second.
  • Turn the knob very slowly: you still get a message each time the total change passes 20.
  • Disconnect and reconnect: once reconnected, the current value is sent without touching the knob.
Full answer with explanation

The complete BLE_LED_Counter program, notifying the potentiometer instead of the counter:

#include <BLEDevice.h>
#include <BLEServer.h>
#include <BLEUtils.h>
#include <BLE2902.h>

// Our own unique IDs (UUIDs), made with a random UUID generator
#define SERVICE_UUID       "0582d484-de7b-45b7-b730-09a9fae5cbf4"
#define LED_CHAR_UUID      "851c0eca-a1b1-4b1e-9a56-9f9f546e7ab6"
#define COUNTER_CHAR_UUID  "e8f00efd-6510-4206-8140-d2feea0d4aa7"

const int LED_PIN = 4;
BLEServer* pServer = nullptr;
BLECharacteristic* pLedChar = nullptr;
BLECharacteristic* pCounterChar = nullptr;
volatile bool deviceConnected = false;
bool wasConnected = false;
const int POT_PIN = 34;                     // potentiometer (ADC1)
int lastSent = -100;                        // far from any ADC value: the first reading is always sent
unsigned long lastNotify = 0;

// 1) When the phone connects or disconnects
class ServerCallbacks : public BLEServerCallbacks {
  void onConnect(BLEServer* s) override {
    deviceConnected = true;
    Serial.println("Phone connected");
  }
  void onDisconnect(BLEServer* s) override {
    deviceConnected = false;
    Serial.println("Phone disconnected");
  }
};

// 2) When the phone writes something to the LED characteristic
class LedCallbacks : public BLECharacteristicCallbacks {
  void onWrite(BLECharacteristic* c) override {
    String v = c->getValue();               // in core 3.x its type is String
    v.trim();
    v.toLowerCase();
    Serial.printf("LED write: [%s]\n", v.c_str());
    if (v == "on" || v == "1") {
      digitalWrite(LED_PIN, HIGH);
      c->setValue("on");
    } else if (v == "off" || v == "0") {
      digitalWrite(LED_PIN, LOW);
      c->setValue("off");
    }
  }
};

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);

  BLEDevice::init("ESP32-BLE-LED");                 // the name in the scan list
  pServer = BLEDevice::createServer();
  pServer->setCallbacks(new ServerCallbacks());

  BLEService* service = pServer->createService(SERVICE_UUID);

  pLedChar = service->createCharacteristic(
      LED_CHAR_UUID,
      BLECharacteristic::PROPERTY_READ | BLECharacteristic::PROPERTY_WRITE);
  pLedChar->setCallbacks(new LedCallbacks());
  pLedChar->setValue("off");

  pCounterChar = service->createCharacteristic(
      COUNTER_CHAR_UUID,
      BLECharacteristic::PROPERTY_READ | BLECharacteristic::PROPERTY_NOTIFY);
  pCounterChar->addDescriptor(new BLE2902());       // the phone's on/off switch for notify

  service->start();

  BLEAdvertising* adv = BLEDevice::getAdvertising();
  adv->addServiceUUID(SERVICE_UUID);
  adv->setScanResponse(true);
  BLEDevice::startAdvertising();
  Serial.println("Advertising as ESP32-BLE-LED ...");
}

void loop() {
  unsigned long now = millis();

  // 3) Every 500 ms: send the pot value, but only if it really changed
  if (deviceConnected && now - lastNotify >= 500) {
    lastNotify = now;
    int v = analogRead(POT_PIN);            // 0 to 4095
    if (abs(v - lastSent) > 20) {           // only real changes, not noise
      String msg = "pot=" + String(v);
      pCounterChar->setValue(msg);
      pCounterChar->notify();
      lastSent = v;
      Serial.println("notify: " + msg);
    }
  }

  // 4) Phone gone? Advertise again so others can find us
  if (!deviceConnected && wasConnected) {
    delay(500);                                     // give the Bluetooth stack a moment
    pServer->startAdvertising();
    Serial.println("Advertising again");
    wasConnected = false;
  }
  if (deviceConnected && !wasConnected) {
    wasConnected = true;
    lastSent = -100;                              // a new phone: send the current value right away
  }
}
  1. The pin and the last value sent. They replace the counter variable. -100 is deliberately far from every possible ADC value. The distance from -100 to any number from 0 to 4095 is more than 20, so the first reading is always sent and the phone has the real value from the start.
  2. The time guard. The same millis pattern as the main program, this time every 500 ms; we only read the potentiometer while a phone is connected. At most two messages per second: good for the battery, and it doesn't flood the phone.
  3. Only real changes. If the difference from the last value sent is more than 20, notify the text pot=... and update lastSent. Comparing with the "last value sent" (not the last value read) means slow changes also add up and eventually get sent; it's the same deadband as in lesson 3.2. We reused the counter characteristic so no new UUID is needed.
  4. A new phone, a fresh value. When a new phone connects, lastSent goes back to −100. Without this line, if the knob hasn't moved since the previous connection, the new phone would get no message at all. The "advertise again" part above this line is unchanged.
Exercise 3: think (no code)

You want to build a battery-powered temperature sensor for a room so you can see its temperature on your phone. Bluetooth Classic, BLE, or Wi-Fi with a web server (lesson 4.2)? Write one advantage and one drawback for each, and explain your choice with a reason. If you also want to see the temperature from work, does your answer change?

What should you see?

Your answer is good if it has these four things:

  • At least one correct advantage and one drawback for each of the three options (see the table in the full answer).
  • The choice for the room: BLE, with battery use as the reason. (Wi-Fi is acceptable only if you said the device is plugged in or spends most of its time in deep sleep.)
  • For viewing from work: your answer changes, because BLE only reaches about 10 m and lesson 4.2's web server can only be seen inside your home network.
  • The remote solution: the data has to go to the internet (a cloud service, for example MQTT in lesson 5.1), rather than the phone connecting straight to the ESP32.
Full answer with explanation
OptionAdvantageDrawback
Bluetooth ClassicSimple: it works like a wireless Serial, and a terminal app is enough.High power use (not for batteries); doesn't work with the iPhone; only the original ESP32 has it.
BLEVery low power: with sleep between measurements it runs for months on a battery; works with iPhone and Android.Short range (about 10 m, a room or two); you need an app such as nRF Connect or your own; UUIDs and characteristics are more complex.

The choice for the room: BLE. The device runs on a battery and the phone is usually in the same home; BLE uses the least power and works with every phone. (With lesson 6.1's deep sleep, the battery lasts even longer.)

From work: the answer changes. At work your phone is out of BLE range, and the ESP32's web server has a private address inside your home (for example 192.168.1.37) that can't be seen from the internet; opening a port on the router is a serious security risk. The right way: the sensor wakes every few minutes, sends the temperature over Wi-Fi to a cloud service (MQTT in lesson 5.1) and goes back to sleep (lesson 6.1); your phone reads the temperature from that cloud service. Another way: keep the BLE sensor, and let an always-on ESP32 at home act as a "gateway" that passes the data from BLE to the internet.

The lesson in three lines

Bluetooth Classic is a continuous pipe (with BluetoothSerial it's a wireless Serial, only on the original ESP32 and only with Android), while BLE is a low-power table of values that works on the ESP32, C3, S3 and C6, and with the iPhone too. In BLE, a server has services, which hold characteristics with UUIDs and Read/Write/Notify permissions; notifications don't arrive without descriptor 0x2902 and a subscription from the phone, and after every disconnect you must restart advertising. Clean up input with trim and toLowerCase; in core 3.x getValue() is a String; and without pairing, anyone in range can connect.
