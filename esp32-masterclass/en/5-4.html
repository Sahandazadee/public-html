Part 1: FreeRTOS, doing several jobs at once without a mess

The problem: a single loop() gets crowded fast

Imagine you want a device that blinks one LED every 250 milliseconds, blinks another LED every 1 second, reads a potentiometer every 200 milliseconds, fetches the weather in Tehran from the internet every 10 minutes, and always answers a web page. With delay() this is impossible, because every delay stops everything else. With millis() (lesson 3.1) it can be done, but loop fills up with if (millis() - lastX >= ...) checks. Worst of all: fetching the weather can take 2 to 5 seconds, and during that time the LEDs and the web page are stuck waiting too.

The professional solution is to write each job separately, as if each one had its own little program, and let a "manager" decide whose turn it is at every moment. That manager is FreeRTOS: a small real-time operating system (RTOS) that is always running on the ESP32, even when you don't know it.

An everyday example: a restaurant kitchen

Picture a restaurant. If it has only one cook (that's the lone loop), the cook has to put the rice on, run to flip the kebabs, run to make the salad, and if they get stuck on the phone taking orders, the kebabs burn. A real restaurant has several cooks (each one is a task): one handles the rice, one the kebabs, one the salad. The head chef (the FreeRTOS scheduler) decides who gets to use the stove. The ESP32 has two stoves (two cores), so two cooks can cook at exactly the same time.

The cooks don't talk over each other and mess up each other's work; they put orders on the counter (that's a queue). And there is only one big knife: whoever picks it up, everyone else waits until it's put back (that's a mutex).

The secret: loop() is itself a task

When you write a program in the Arduino IDE, before anything else the Arduino core creates a task called loopTask, which calls setup() once and then loop() forever. Here are this task's settings in core 3.3.12 (from the core's own main.cpp and sdkconfig files):

So you have been using FreeRTOS since day one. Now you are just learning to hire a second and a third cook. (Wi-Fi itself also runs several high-priority tasks on core 0; that's why Wi-Fi works "behind the scenes".)

The first tasks: two LEDs at two speeds

The circuit: two LEDs, each with its own 220 Ω resistor, on GPIO4 and GPIO5. Also connect the potentiometer to GPIO34 now, because you'll need it in the next example.

Careful: GPIO5 is a strapping pin

GPIO5 plays a small role in the boot configuration at power-up. An LED with a 220 Ω resistor won't cause trouble, but if your board behaves strangely at power-up, move the second LED to GPIO18 and change the number in the code (lesson 1.3).

// Two LEDs at two different speeds, each in its own task
const int LED_FAST = 4;   // fast LED
const int LED_SLOW = 5;   // slow LED

void blinkFast(void *param) {          // first task function
  pinMode(LED_FAST, OUTPUT);
  bool on = false;
  for (;;) {                           // a task must never end
    on = !on;
    digitalWrite(LED_FAST, on);
    vTaskDelay(pdMS_TO_TICKS(250));    // step aside for 250 ms
  }
}

void blinkSlow(void *param) {          // second task function
  pinMode(LED_SLOW, OUTPUT);
  bool on = false;
  for (;;) {
    on = !on;
    digitalWrite(LED_SLOW, on);
    vTaskDelay(pdMS_TO_TICKS(1000));   // 1 second
  }
}

void setup() {
  Serial.begin(115200);
  xTaskCreatePinnedToCore(
    blinkFast,     // which function
    "blinkFast",   // task name (only for debugging)
    2048,          // stack size in BYTES
    NULL,          // input parameter (none)
    1,             // priority
    NULL,          // task handle (not needed)
    1);            // core 1
  xTaskCreatePinnedToCore(blinkSlow, "blinkSlow", 2048, NULL, 1, NULL, 1);
  Serial.printf("setup() runs on core %d\n", xPortGetCoreID());
}

void loop() {                          // loop is a task too
  Serial.printf("loop() alive on core %d, millis=%lu\n",
                xPortGetCoreID(), millis());
  delay(2000);
}
  1. The task function. Every task is an ordinary function with exactly this shape: void name(void *param). The param input is a "pointer to anything" that you can hand to the task when you create it. FreeRTOS wants one fixed shape for all tasks so it can treat them all the same way. If the function's shape is different, the compiler gives an error.
  2. One-time work at the start of the task. Like a small setup just for this task: it makes the pin an output and creates a local variable for the LED state. The variable on is inside the task, so it lives on this task's stack. Every task has its own separate stack, so two tasks with variables of the same name never get mixed up.
  3. The endless loop for (;;). A task must stay in a loop forever. This plays the same role as loop(). If the task function reaches its final } and returns, the ESP32 resets with an error (abort). If a task's work really is finished, it must delete itself with vTaskDelete(NULL);.
  4. vTaskDelay and pdMS_TO_TICKS. vTaskDelay tells the scheduler "I have nothing to do right now, give the stove to someone else". Its unit is the "tick"; pdMS_TO_TICKS(250) converts milliseconds to ticks. On the Arduino ESP32 one tick is 1 millisecond (CONFIG_FREERTOS_HZ=1000), so the conversion doesn't change the number. But if you ever move the code to a system with a 10 ms tick, all your times would be 10 times longer without this macro. Build the right habit from the start.
  5. The second task. Exactly the same pattern, just with a different pin and time. See how simple it became: each task only thinks about its own job. No tangled if (millis() - last ...) checks.
  6. xTaskCreatePinnedToCore with seven inputs. In order: function, name, stack size, parameter, priority, handle, core number. "PinnedToCore" means "pin it to this core". If you don't choose a core (the xTaskCreate function), the task can run on either core; when you're starting out, pinning makes the behavior more predictable.
  7. 2048 means 2048 bytes. This is the single most important ESP32 detail: in the ESP-IDF version of FreeRTOS, stack size is given in bytes. In standard FreeRTOS (on an STM32, for example) the same number is in "words", and each word is four bytes; so 2048 there would be 8 KB. If you copy code from the internet that sets the stack to 512, on the ESP32 you get only 512 bytes and the board will probably crash. Use 2048 for a simple task, about 3000 to 4096 for a task that uses Serial.printf, and at least 8 to 12 KB for a task that uses HTTPS.
  8. Priority. A number from 0 to 24; bigger means more important. When two tasks are ready to run, the scheduler always picks the one with higher priority. Tasks with equal priority take turns (every tick). 1 is the same priority as loop. To start, give everything 1 or 2. Give high priority to a task that must respond quickly and works briefly; a long-running task with high priority starves everyone else.
  9. The second task in one line. The same seven inputs, without comments. After this line we have three tasks on core 1: loopTask and the two blinkers, plus the system's own tasks on core 0.
  10. loop keeps doing its own job. It prints a message every 2 seconds; xPortGetCoreID() returns the number of the current core. Important detail: on the Arduino ESP32, delay() is really just vTaskDelay (the core defines it as vTaskDelay(ms / portTICK_PERIOD_MS)), so a delay in loop also hands the CPU to other tasks and the blinking never stops. But delayMicroseconds() and empty loops such as while(...) {} really do lock up the CPU.
setup() runs on core 1 loop() alive on core 1, millis=312 loop() alive on core 1, millis=2312 loop() alive on core 1, millis=4312

And on the board: the red LED blinks twice per second and the green LED blinks once every 2 seconds (1 second on, 1 second off), completely independently of each other.

So how is vTaskDelay different from delay?

On the Arduino ESP32, in behavior, almost not at all: both put the current task to sleep and free the CPU. The difference is the unit: delay(ms) takes milliseconds and vTaskDelay(ticks) takes ticks. Inside tasks we use vTaskDelay(pdMS_TO_TICKS(...)) because it is FreeRTOS's own language and works correctly on any system. If you want something to repeat exactly every 100 milliseconds (without the time the job itself takes being added on), use vTaskDelayUntil.

Moving data safely: the queue

Now a real problem: one task reads a sensor and another task has to display the value. The first idea: "I'll use a global variable; one task writes it and the other reads it". For a simple int this usually works, but for bigger data (say a struct with temperature, humidity and time) the display task might read it halfway through a write: new temperature with old humidity! This bug is called a "race condition", and it's the worst kind of bug, because it happens once in a thousand times.

A queue is FreeRTOS's official solution. A queue is a pipe with a fixed number of slots: one task puts a copy of the data in at one end, and the other task takes it out at the other end, in the same order (first in, first out). FreeRTOS guarantees that data is never moved halfway.

// Sensor task → queue → display task, plus a lock for Serial
const int POT_PIN = 34;          // potentiometer (ADC1, input only)
const int LED_PIN = 4;           // LED with variable brightness (PWM)

QueueHandle_t potQueue;          // queue between the two tasks
SemaphoreHandle_t serialMutex;   // lock for the Serial Monitor
TaskHandle_t sensorHandle = NULL;
TaskHandle_t displayHandle = NULL;

void sensorTask(void *param) {
  for (;;) {
    int raw = analogRead(POT_PIN);                  // 0 to 4095
    if (xQueueSend(potQueue, &raw, 0) != pdPASS) {  // don't wait
      // queue is full: throw this sample away
    }
    vTaskDelay(pdMS_TO_TICKS(200));                 // 5 times per second
  }
}

void displayTask(void *param) {
  int value;
  for (;;) {
    // wait up to 1 second for data; the CPU is free meanwhile
    if (xQueueReceive(potQueue, &value, pdMS_TO_TICKS(1000)) == pdPASS) {
      ledcWrite(LED_PIN, value / 16);               // 0..4095 → 0..255
      if (xSemaphoreTake(serialMutex, pdMS_TO_TICKS(100)) == pdTRUE) {
        Serial.printf("pot=%4d  led=%3d\n", value, value / 16);
        xSemaphoreGive(serialMutex);                // give the lock back
      }
    }
  }
}

void setup() {
  Serial.begin(115200);
  ledcAttach(LED_PIN, 5000, 8);                     // 5 kHz, 8 bits
  potQueue = xQueueCreate(10, sizeof(int));         // 10 slots, one int each
  serialMutex = xSemaphoreCreateMutex();
  if (potQueue == NULL || serialMutex == NULL) {
    Serial.println("Out of memory!");
    while (true) delay(1000);
  }
  xTaskCreatePinnedToCore(sensorTask, "sensor", 3072, NULL, 2, &sensorHandle, 1);
  xTaskCreatePinnedToCore(displayTask, "display", 4096, NULL, 1, &displayHandle, 1);
}

void loop() {
  delay(5000);
  if (xSemaphoreTake(serialMutex, portMAX_DELAY) == pdTRUE) {
    Serial.printf("[stack] sensor free=%u B, display free=%u B, heap=%u B\n",
                  (unsigned)uxTaskGetStackHighWaterMark(sensorHandle),
                  (unsigned)uxTaskGetStackHighWaterMark(displayHandle),
                  (unsigned)ESP.getFreeHeap());
    xSemaphoreGive(serialMutex);
  }
}
  1. Handles. QueueHandle_t, SemaphoreHandle_t and TaskHandle_t are like the "phone numbers" of the queue, the lock and the tasks; FreeRTOS builds the object itself in memory and we only keep its number. They are global so every task can reach them. A handle never changes after it is created, so making it global is safe.
  2. Read and send. xQueueSend(queue, address of data, wait time) copies the contents of raw and puts it in the queue. The & sign means "the address of this variable". Because it's a copy, raw can change after this line without damaging the data inside the queue. A wait time of 0 means "if the queue is full, don't wait"; the sensor task shouldn't fall behind just because the display is slow.
  3. If the queue is full. xQueueSend returns errQUEUE_FULL, and we deliberately do nothing: this sample is thrown away. In a real device you have to decide: "is new data more important, or old data?". For a display, the newest data matters; for a log, all of it does. Make this decision on purpose, not by accident.
  4. xQueueReceive with a wait time. The display task waits up to 1 second for something to arrive in the queue. During that time it really sleeps and uses zero percent of the CPU. This is the most beautiful part of a queue: the display task doesn't need vTaskDelay, because waiting on the queue already frees the CPU. As soon as data arrives, FreeRTOS wakes it up.
  5. LED brightness. The 12-bit ADC number (0 to 4095) divided by 16 becomes 0 to 255, the range of 8-bit PWM. This is the same ledcWrite from lesson 3.2, with the version 3 API. In core 2.x you had to use ledcSetup and ledcAttachPin with a channel number.
  6. A mutex around Serial. xSemaphoreTake picks up the knife (waiting up to 100 milliseconds if someone else has it), prints, and xSemaphoreGive puts it back. Without the lock, if loop and the display task print at the same time, their lines get jumbled together: pot=12[stack] sens34 led=.... Protect every shared resource (Serial, I2C, a file, a big variable) that more than one task uses with a mutex. Golden rule: every Take has a Give, or everyone else waits forever.
  7. Creating the queue and the lock, and checking they worked. xQueueCreate(10, sizeof(int)) creates a queue with 10 slots, each the size of one int (4 bytes). The queue and the lock take memory from the heap. If memory has run out, you get NULL back, and using NULL means a crash. Always check. The queue and the lock must be created before the tasks, because the tasks start using them immediately.
  8. Priorities and handles. The sensor task has priority 2 and the display task 1. This time we keep the handle (&sensorHandle). Reading the sensor is short and time-sensitive, so it gets the higher priority. We need the handle so we can later ask about the task from outside (for example, how much stack it has used).
  9. uxTaskGetStackHighWaterMark. The "high-water mark" is the smallest amount of free stack this task has ever had, given in bytes in ESP-IDF. This number is your stack-tuning tool: if you gave a task 4096 bytes and this number is 2800, then at most about 1300 bytes were used; you can shrink the stack and free up RAM. If it drops below 500 bytes, make the stack bigger. ESP.getFreeHeap shows the total free RAM.
pot=2048 led=128 pot=2051 led=128 pot=4095 led=255 [stack] sensor free=1964 B, display free=2312 B, heap=289140 B pot=4095 led=255

(The stack and heap numbers will be a little different on your board; what matters is that you know how to read them.)

Try it in Wokwi: turn the potentiometer and watch the LED brightness and the numbers in the Serial Monitor change. FreeRTOS is fully simulated in Wokwi, so the tasks, the queue and the mutex behave exactly as they do on a real board. No extra library is needed.

When the stack runs out (stack overflow)

Every task has a box of memory of the size you asked for. Local variables, arrays and every function you call fit into this box. Serial.printf alone needs a few hundred bytes, and an HTTPS connection needs several kilobytes. If the box overflows, data spills onto the neighboring memory. Luckily the ESP32 is watching, and before everything is ruined it prints this and resets the board:

***ERROR*** A stack overflow in task display has been detected. Backtrace: 0x40081f2e:0x3ffb5f40 0x40086d15:0x3ffb5f60 ... Rebooting...

Common signs of a too-small stack: this very message, or Guru Meditation Error: Core 1 panic'ed (LoadProhibited), or random resets when a task does something heavier (for example, its first HTTPS connection). The cure: double the stack number in xTaskCreatePinnedToCore, then use uxTaskGetStackHighWaterMark to see how much is really needed. And don't declare a big array (such as char buf[4000]) as a local inside a task; make it global or static so it moves off the stack.

The task watchdog: why does the board reset by itself?

The ESP32 has a "watchdog" that checks every so often that the important tasks are still alive. In the Arduino core this watchdog watches core 0's idle task (IDLE0), with a timeout of 5 seconds (CONFIG_ESP_TASK_WDT_TIMEOUT_S=5). The idle task only runs when no other task on that core has anything to do. So if a task on core 0 works for five seconds without a break, IDLE0 never gets a turn, the watchdog concludes "the system is frozen", and it resets the board.

An everyday example

A building's night guard has to press a button in the lobby every hour so the system knows they're awake. If someone blocks the lobby with an endless job and the guard can't reach the button, the alarm goes off. vTaskDelay is how you "let the guard through".

// ❌ Deliberately wrong: a greedy task on core 0 that never rests
volatile unsigned long counter = 0;

void greedyTask(void *param) {
  for (;;) {
    counter++;              // works nonstop and never steps aside
    // vTaskDelay(1);       // ✅ the cure: uncomment this line
  }
}

void setup() {
  Serial.begin(115200);
  xTaskCreatePinnedToCore(greedyTask, "greedy", 2048, NULL, 1, NULL, 0);
}

void loop() {
  Serial.println(counter);
  delay(1000);
}
  1. The greedy task. An endless loop that only increments a number and never calls vTaskDelay. This task is always ready to run and its priority (1) is higher than IDLE0's (0); so the scheduler always picks it and IDLE0 starves.
  2. On core 0. The last input is 0. If you put the same task on core 1, the default settings won't reset the board (IDLE1 isn't watched), but loop and the equal-priority tasks on core 1 slow down. "It doesn't reset" means "the problem is hidden", not "it's correct".
  3. The cure. One vTaskDelay(1) (even 1 millisecond) in the loop is enough to give IDLE0 a turn. The rule: every endless loop in every task must sleep or wait for something somewhere (vTaskDelay, xQueueReceive, xSemaphoreTake with a wait time). Busy-wait loops such as while (!ready) {} are enemy number one.

About 5 seconds after power-up you'll see something like this, and the board resets:

E (5316) task_wdt: Task watchdog got triggered. The following tasks/users did not reset the watchdog in time: E (5316) task_wdt: - IDLE0 (CPU 0) E (5316) task_wdt: Tasks currently running: E (5316) task_wdt: CPU 0: greedy E (5316) task_wdt: CPU 1: IDLE1 E (5316) task_wdt: Aborting. abort() was called at PC 0x400d8c5f on core 0 ... Rebooting...

The line CPU 0: greedy gives away the culprit: the name you gave the task. That's why you should choose meaningful task names.

The wrong way: turning off the watchdog

On forums you'll see code like disableCore0WDT(). It silences the message, but the problem is still there: the system tasks on core 0 (such as Wi-Fi) starve, and the network connection drops in strange ways. The watchdog isn't your enemy; it's a friend telling you your code is stuck somewhere.

Task or millis()? Which should I choose?

For two or three light, quick jobs, millis() in loop is simpler and has no concurrency bugs. Bring in a task when: 1) you have a slow, blocking job (HTTPS, a slow sensor read, writing to an SD card) that shouldn't make everything else wait; 2) the jobs have completely different timing; 3) you want to use the second core. Every new task means a separate stack, and every piece of shared data means a queue or a mutex. Don't create tasks without a reason.

Part 2: Over-the-air updates (OTA), programming without a cable

You've installed your device inside a drop ceiling to control the lights. A week later you find a bug. Without OTA you have to fetch a ladder, open the ceiling, and carry your laptop up there with a USB cable. With OTA (Over-The-Air) you upload the new program from your desk, over the same Wi-Fi.

How does OTA work behind the scenes? (partitions)

The ESP32's 4 MB flash memory is divided into several "partitions", like a hard disk. You choose the map of this division in the Tools › Partition Scheme menu. The key idea behind OTA is this: for a safe update there must be two program slots (app0 and app1). The new program is written into the empty slot while the current program keeps running. Only when the download has finished completely and correctly does a small "note" (the otadata partition) change to say "boot from the other slot next time". If the power goes out in the middle of an update, the old program is still untouched.

A common trap: Huge APP and OTA

When your program grows (Wi-Fi + Bluetooth + HTTPS), you get the Sketch too big error, and many tutorials say "choose Huge APP". That fixes the error but kills OTA for good, because it has only one program slot. For a device that needs OTA, choose Minimal SPIFFS: programs up to 1.9 MB with OTA intact. The only cost is that file space shrinks to 128 KB, which is enough for a settings page. Remember that a Partition Scheme change only takes effect with a USB upload.

Method one: ArduinoOTA, uploading from the Arduino IDE itself

The ArduinoOTA library is built into the core. It "announces" the board on the network (with mDNS, as in lesson 4.2) and waits for a new program on port 3232. First, extend the secrets.h file from lesson 4.1; this version holds all the passwords for this lesson:

#pragma once
#define WIFI_SSID "MyHomeWiFi"
#define WIFI_PASS "my-strong-password"
#define OTA_PASS  "ota-pass-2026"      // password for wireless updates
#define WEB_USER  "admin"              // username for the web update page
#define WEB_PASS  "change-me-now"      // password for the web update page
#define NTFY_TOPIC "home-alert-7f3k9q" // ntfy topic name: unguessable
  1. The Wi-Fi password. The same two lines as in lesson 4.1. One secrets file for every program in this lesson; each program only uses the lines it needs.
  2. The OTA password. Anyone who doesn't know this password can't change the board's program. OTA without a password means anyone connected to your Wi-Fi (a guest, a neighbor who knows the password, an infected phone) can put any program they like on your device.
  3. Username and password for the web update page. For method two in this same part. Kept separate from the OTA password, so if one leaks the other stays safe.
  4. The ntfy topic name. For the phone-alert section (Part 4). On ntfy.sh the topic name itself acts as the password, so it belongs in secrets.h too.
#include <WiFi.h>
#include <ArduinoOTA.h>
#include "secrets.h"             // WIFI_SSID, WIFI_PASS, OTA_PASS
#ifndef OTA_PASS                 // if it's missing from secrets.h, warn
#warning "OTA_PASS is not defined in secrets.h"
#define OTA_PASS "change-me"
#endif

const int LED_PIN = 4;

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) {   // kept simple; robust version in lesson 4.1
    delay(500);
    Serial.print(".");
  }
  Serial.printf("\nIP: %s\n", WiFi.localIP().toString().c_str());

  ArduinoOTA.setHostname("esp32-kitchen");  // name shown in the Port menu
  ArduinoOTA.setPassword(OTA_PASS);         // without it, anyone can flash
  ArduinoOTA
    .onStart([]() { Serial.println("OTA start"); })
    .onEnd([]() { Serial.println("\nOTA done, rebooting"); })
    .onProgress([](unsigned int done, unsigned int total) {
      Serial.printf("OTA %u%%\r", done * 100 / total);
    })
    .onError([](ota_error_t err) { Serial.printf("OTA error %u\n", err); });
  ArduinoOTA.begin();                       // from here on it waits for updates
  Serial.println("OTA ready");
}

void loop() {
  ArduinoOTA.handle();                      // every pass: "any update?"
  static unsigned long last = 0;            // blink without delay (lesson 3.1)
  static bool on = false;
  if (millis() - last >= 500) {
    last = millis();
    on = !on;
    digitalWrite(LED_PIN, on);
  }
}
  1. The ArduinoOTA library. Part of the core; nothing to install. We also need WiFi.h, because OTA works over the network.
  2. The #ifndef guard. If you haven't written the OTA_PASS line in secrets.h, the compiler shows an orange warning and the temporary password change-me is used. The program still compiles with the old secrets.h from lesson 4.1, but the warning reminds you to set a real password. Never ignore compiler warnings.
  3. Connecting to Wi-Fi. A simple version, to keep the example short. In a real device use the robust version from lesson 4.1, with a time limit and automatic reconnection. OTA doesn't work without Wi-Fi.
  4. setHostname. The board's name on the network; the name you see in the Port menu. If you don't give it a name, it gets something like esp32-a0b1c2d3e4f5 (based on the MAC address). When you have three devices at home, "esp32-kitchen" is much better. Use only lowercase English letters, digits and hyphens.
  5. setPassword. The OTA password. The Arduino IDE asks you for it when you upload. In core 3.3, OTA authentication uses SHA-256 (older versions used MD5, which is no longer considered secure). If you don't want the plain password inside the program, use setPasswordHash with the SHA-256 hash of the password.
  6. Events (callbacks). Four small functions for start, end, progress and error. []() { ... } is a "nameless function" (a lambda) in C++. In a real project, use onStart to switch off motors and relays and close files; a few seconds later the board resets, and nothing should be left half-done.
  7. ArduinoOTA.begin. From here on the board announces itself on the network and waits for an update. It must be called after Wi-Fi has connected.
  8. ArduinoOTA.handle on every pass of loop. Checks whether anyone wants to send an update. If loop gets stuck somewhere in a long delay or a busy-wait loop, OTA doesn't answer and the IDE reports "No response from device". That's why we wrote the LED blink with millis(), not delay.

Step by step: your first wireless update

  1. The first time must be over USB. The board doesn't have the OTA code yet, so it can't receive a program over the air. Upload the program above over USB as usual. (The Partition Scheme must include OTA; Default is fine.)
  2. Check the Serial Monitor. You should see the IP address and OTA ready.
  3. Computer and board on the same network. Your laptop must be connected to the same router (not your phone's hotspot, and not the router's guest network, which isolates devices from each other).
  4. Pick the network port. Unplug the USB cable (or leave it in) and open the Tools › Port menu. Under the Network ports heading, something like esp32-kitchen at 192.168.1.50 appears. If it isn't there, wait 30 seconds and open the menu again; the IDE scans the network every few seconds.
  5. Make a small change (for example, change 500 to 100 so the LED blinks faster) and press Upload. The IDE asks for the password: your OTA_PASS.
  6. The result. You'll see the progress bar Uploading: [==== ] 45%. Then the board resets by itself and the LED blinks at the new speed. There is no network Serial Monitor; to see messages you still need the cable (or send your logs over the web or MQTT).
Important: every new program must include the OTA code too

If you send over the air a program that has no ArduinoOTA.begin and handle (or that gets stuck in setup, or has the wrong Wi-Fi details), that was your last wireless update! Next time you'll need the ladder and the cable. Make it a habit: put the OTA code in every program before anything else, and test it on a board on your desk before sending it to the device in the ceiling.

Method two: an update page in the browser (Update + WebServer)

ArduinoOTA only works from inside the Arduino IDE, on the same network. Sometimes you want to give the program file to someone else (a customer, for example) so they can update without installing the Arduino IDE. The solution: a web page on the ESP32 itself that accepts a .bin file. The Update library (built into the core) does the writing into the second partition.

Creating the .bin file

  1. In the Arduino IDE, choose Sketch › Export Compiled Binary (shortcut Alt+Ctrl+S).
  2. After compiling, a build folder appears in the project folder, and inside it a folder named after the board (for example esp32.esp32.esp32). Open it with Sketch › Show Sketch Folder.
  3. You'll see several .bin files. The right one is the file whose name is just ProjectName.ino.bin. Don't send the .bootloader.bin, .partitions.bin and .merged.bin files over OTA; those are for a full flash with the cable.
#include <WiFi.h>
#include <WebServer.h>
#include <Update.h>
#include "secrets.h"
#ifndef WEB_USER
#warning "WEB_USER/WEB_PASS are not defined in secrets.h"
#define WEB_USER "admin"
#define WEB_PASS "change-me"
#endif

WebServer server(80);

const char UPDATE_PAGE[] PROGMEM = R"HTML(
<!doctype html><meta charset="utf-8">
<h3>Firmware update</h3>
<form method="POST" action="/update" enctype="multipart/form-data">
  <input type="file" name="firmware" accept=".bin">
  <button>Upload</button>
</form>)HTML";

void handlePage() {
  if (!server.authenticate(WEB_USER, WEB_PASS)) {
    return server.requestAuthentication();          // username/password prompt
  }
  server.send(200, "text/html", UPDATE_PAGE);
}

void handleUploadDone() {                           // after the upload finishes
  if (!server.authenticate(WEB_USER, WEB_PASS)) {
    return server.requestAuthentication();
  }
  bool ok = !Update.hasError();
  server.send(200, "text/plain", ok ? "OK, rebooting..." : Update.errorString());
  if (ok) {
    delay(500);
    ESP.restart();                                  // come back up with the new program
  }
}

void handleUploadChunk() {                          // for every chunk of the file
  if (!server.authenticate(WEB_USER, WEB_PASS)) return;
  HTTPUpload &up = server.upload();
  if (up.status == UPLOAD_FILE_START) {
    Serial.printf("Update: %s\n", up.filename.c_str());
    if (!Update.begin(UPDATE_SIZE_UNKNOWN)) Update.printError(Serial);
  } else if (up.status == UPLOAD_FILE_WRITE) {
    if (Update.write(up.buf, up.currentSize) != up.currentSize) {
      Update.printError(Serial);
    }
  } else if (up.status == UPLOAD_FILE_END) {
    if (Update.end(true)) Serial.printf("Done: %u bytes\n", up.totalSize);
    else Update.printError(Serial);
  }
}

void setup() {
  Serial.begin(115200);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) delay(500);
  Serial.printf("Open http://%s/\n", WiFi.localIP().toString().c_str());
  server.on("/", HTTP_GET, handlePage);
  server.on("/update", HTTP_POST, handleUploadDone, handleUploadChunk);
  server.begin();
}

void loop() {
  server.handleClient();
}
  1. The Update library. A simple interface for writing a new program into the empty OTA partition. ArduinoOTA itself uses this same library behind the scenes. We've only changed how the file arrives (the browser instead of the IDE).
  2. An HTML page with an upload form. enctype="multipart/form-data" means "this form sends a file". R"HTML( ... )HTML" is the same raw string from lesson 4.2. Without enctype, the browser sends only the file's name, not its contents. accept=".bin" only limits the file picker to bin files (it's a convenience, not security).
  3. A password-protected main page. server.authenticate checks the username and password; if they're wrong, requestAuthentication opens the browser's login prompt. An update page without a password means anyone on the network can take over your device. This simple authentication (Basic/Digest) is not encrypted over HTTP, so use it only on a trusted home network, and never expose this page to the internet with port forwarding.
  4. server.on with two functions. For file uploads, WebServer wants two functions: handleUploadChunk, which is called for every chunk of the file, and handleUploadDone, which sends the reply to the browser after the whole upload is finished. The bin file is around one megabyte and the ESP32's free RAM is about 300 kilobytes. So you can't receive the whole file into RAM first; it has to arrive in chunks (a few kilobytes at a time) and be written to flash right away.
  5. Start: Update.begin. On the first chunk, the empty OTA partition is prepared (erased). UPDATE_SIZE_UNKNOWN means "I don't know the size; keep writing while there is room". If there is no OTA partition (Huge APP), you get an error right here, and Update.printError prints the reason on Serial.
  6. Writing each chunk. Update.write writes the chunk to flash and returns the number of bytes written. If that number doesn't match the chunk size, the write failed. Check, don't guess.
  7. Finish: Update.end(true). Checks that the file is complete and valid (the program's header and checksum), and if it is, changes otadata so the next boot uses the new program. If you sent the wrong file (say a photo, or the merged file), it is rejected right here and the previous program stays intact. That is the safety of having two partitions.
  8. Reply and reset. If there was no error, it sends "OK" to the browser, waits half a second for the message to get there, and calls ESP.restart(). The new program only runs after a reset. Without the delay, the board might reset before the reply reaches the browser, and you'd think the update had failed.

To use it: open the board's IP address in a browser, enter the username and password, pick the .ino.bin file and press Upload. About 10 to 20 seconds later you'll see "OK, rebooting...".

Shortcut: the ready-made HTTPUpdateServer library

Core 3.x also has a library called HTTPUpdateServer that adds this same page to your WebServer in two lines. We deliberately wrote the manual version so you understand what happens behind the scenes. In online tutorials you'll also see libraries such as ElegantOTA; its older versions (AsyncElegantOTA) are deprecated.

Automatic rollback: what if the new program is broken?

Suppose the new program has a bug that stops it from connecting to Wi-Fi. Now OTA doesn't work either! ESP-IDF has "automatic rollback" for exactly this case, and it's enabled in Arduino core 3 too (CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y). The idea: after its first boot, a new program is "on probation". If it declares "I'm healthy", it stays; if it resets before that, or says "I'm broken", the bootloader goes back to the previous program.

By default the Arduino core declares the new program "healthy" immediately at startup. To make that decision yourself:

#include <WiFi.h>
#include "esp_ota_ops.h"
#include "secrets.h"

// Tell the core: "I'll confirm the new program myself"
extern "C" bool verifyRollbackLater() {
  return true;
}

void setup() {
  Serial.begin(115200);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  unsigned long t0 = millis();
  while (WiFi.status() != WL_CONNECTED && millis() - t0 < 30000) delay(500);

  if (WiFi.status() == WL_CONNECTED) {
    esp_ota_mark_app_valid_cancel_rollback();   // "this version is healthy"
    Serial.println("New firmware confirmed");
  } else {
    Serial.println("No Wi-Fi: rolling back");
    esp_ota_mark_app_invalid_rollback_and_reboot();  // go back to the previous version
  }
}

void loop() {
  delay(1000);
}
  1. verifyRollbackLater. The core defines this function as "weak", returning false. When you write your own version that returns true, yours replaces it and the core skips the automatic confirmation. The extern "C" is essential: the core's function is defined in a C file, and without it the C++ compiler changes your function's name (name mangling); the program compiles without any error, but your version is never called. This "weak function" pattern is common in the Arduino core: a way to change internal behavior without touching the core's files.
  2. Confirming. If Wi-Fi connects within 30 seconds, esp_ota_mark_app_valid_cancel_rollback() says "this version stays". Choose the health test yourself: connecting to Wi-Fi, getting an answer from the MQTT server, or whatever is needed for OTA to keep working.
  3. Rejecting. esp_ota_mark_app_invalid_rollback_and_reboot() resets the board, and the bootloader runs the previous version. If the program was uploaded over USB, there is no valid previous version and this function just returns an error; so on your desk it does nothing. This mechanism only makes sense after an OTA update.
Take OTA security seriously

OTA means "a way to replace the device's brain remotely". If that way is open, an attacker can use it too. The minimum: 1) always set a password; 2) never expose port 3232 or the update page to the internet with port forwarding; 3) for a device you sell to others, study signed OTA (the SignedOTA example in the ArduinoOTA library) and Secure Boot, so that only programs signed with your own private key are accepted.

OTA and uploading LittleFS files are not simulated in Wokwi (Wokwi puts the program straight into the simulator's memory and has no network port for the IDE). Practice these two on a real board.

Part 3: LittleFS, a small flash drive inside the ESP32

In lesson 4.2 we wrote the web page as one big string inside the C++ code. It worked, but every tiny change to a button's color meant compiling and uploading the whole program again. And if you want to keep settings (such as the user's chosen city) or a log of several days, variables are wiped by every reset. LittleFS is a "file system": it gives you part of the flash memory (the spiffs partition in the figure above) as a small flash drive with folders and files. Files survive power loss, and even uploading a new program (over USB or OTA).

An everyday example

Your program is like the cook, and RAM is like the cook's worktable: fast, but wiped clean when the restaurant closes (the power goes off). LittleFS is like the notebook shelf in the kitchen: the recipes (the web page) and the account book (the log) stay there, even when the cook is replaced (a new program).

Why LittleFS and not SPIFFS?

SPIFFS is the ESP32's older file system. It has no real folders and is more easily damaged if the power fails mid-write; Espressif no longer develops it. LittleFS was designed for microcontrollers: it is power-loss resilient, and it spreads writes across the whole memory so that no single spot of the flash wears out early (wear leveling). The partition is still called "spiffs", but LittleFS uses it without any trouble.

Writing, appending, reading and listing files

#include <LittleFS.h>

void listFiles(const char *dir) {
  File root = LittleFS.open(dir);
  File f = root.openNextFile();
  while (f) {
    Serial.printf("  %-20s %6u bytes\n", f.name(), (unsigned)f.size());
    f = root.openNextFile();
  }
}

void setup() {
  Serial.begin(115200);
  delay(500);
  if (!LittleFS.begin(true)) {               // true = format it if it's broken
    Serial.println("LittleFS mount failed");
    return;
  }
  Serial.printf("FS: %u of %u bytes used\n",
                (unsigned)LittleFS.usedBytes(), (unsigned)LittleFS.totalBytes());

  File f = LittleFS.open("/note.txt", "w");  // w = create, or overwrite from the start
  f.println("Hello from ESP32!");
  f.close();                                 // closing = saved for sure

  f = LittleFS.open("/log.txt", "a");        // a = append to the end of the file
  f.printf("boot at %lu ms\n", millis());
  f.close();

  f = LittleFS.open("/log.txt", "r");        // r = read only
  Serial.println("--- log.txt ---");
  while (f.available()) {
    Serial.write(f.read());
  }
  f.close();

  Serial.println("--- files ---");
  listFiles("/");
}

void loop() {}
  1. The LittleFS library. Built into the core. No separate install needed. Don't install old libraries such as "LITTLEFS by lorol"; they were for core 1.x and conflict with core 3.
  2. LittleFS.begin(true). "Mounts" the file system. The true input means "if you can't mount it (for example the first time, when it isn't formatted yet), format it". The first time you run on a new board, the partition is empty and unformatted, and without true you always get "mount failed". But be careful: if the files really are damaged, true erases everything. For a device with valuable data, try false first and format deliberately.
  3. Total and used space. totalBytes and usedBytes. With the default Partition Scheme you'll see about 1.3 to 1.4 MB; with Minimal SPIFFS, only 128 KB. Before saving a long log, always know how much free space you have.
  4. Mode "w": write from the start. Creates the file; if it already exists, its contents are erased. Then you write into it just like Serial, with println and printf. A file name always starts with / (the full path). Don't forget close(): until the file is closed, the last piece of data may still be in RAM and be lost if the power goes out.
  5. Mode "a": append. Adds to the end of the file and keeps what was there. For logs, always use "a". Every reset adds one boot at ... line. Press the EN button a few times and watch the file grow; that proves the data survived the reset.
  6. Mode "r": read. available() says how many bytes are left, and read() returns one byte. Reading byte by byte is simple and light on memory for small files. For a big file, f.readStringUntil('\n') reads it line by line.
  7. Listing the files. We open the folder and step through it one entry at a time with openNextFile() until an empty file (false) comes back. A great debugging tool: when the web page can't be found, first check that the file really is on the board and what exactly it's called (uppercase and lowercase letters are different).

body { font-family: sans-serif; max-width: 480px; margin: 2em auto; }

  1. The page's look in a separate file. The font, a maximum width of 480 pixels (for phones), and a blue heading color. The browser requests the CSS file separately (/style.css), so the ESP32 program must also answer that address; line 19 of the program below does exactly that.
#include <WiFi.h>
#include <WebServer.h>
#include <LittleFS.h>
#include "secrets.h"

WebServer server(80);

void setup() {
  Serial.begin(115200);
  if (!LittleFS.begin(true)) {
    Serial.println("LittleFS mount failed");
  }
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) delay(500);
  Serial.printf("Open http://%s/\n", WiFi.localIP().toString().c_str());

  // static files straight from LittleFS (after LittleFS.begin)
  server.serveStatic("/", LittleFS, "/index.html");
  server.serveStatic("/style.css", LittleFS, "/style.css", "max-age=3600");

  // live data from the code
  server.on("/api/temp", []() {
    float t = temperatureRead();               // chip's internal temperature (rough)
    server.send(200, "application/json", "{\"t\":" + String(t, 1) + "}");
  });
  server.onNotFound([]() { server.send(404, "text/plain", "Not found"); });
  server.begin();
}

void loop() {
  server.handleClient();
}
  1. Mount LittleFS before anything else. serveStatic checks at the moment you define it whether the path is a file or a folder; if LittleFS isn't mounted yet, it gets it wrong.
  2. serveStatic for the main page. "Whoever asks for the address /, send them the /index.html file from LittleFS". It guesses the content type (text/html) from the file extension. One line instead of a whole function. A subtle detail: if you give it a folder instead of a file (for example serveStatic("/", LittleFS, "/")), then for the address / the library looks for index.htm (without the l), not index.html. To avoid that trap, we gave the exact file path.
  3. The CSS file, with caching. The fourth input, "max-age=3600", tells the browser "don't ask for this file again for an hour". The ESP32 is a weak server; every request it doesn't have to handle means faster answers for the rest. We didn't cache index.html, so your changes show up immediately.
  4. The live-data route. temperatureRead() gives the chip's internal temperature (not accurate, just for show), and it's sent as JSON. In a real project, use the temperature from a DHT22 or any other sensor instead.

Uploading the data folder to the board (Arduino IDE 2)

To put the data folder onto LittleFS, Arduino IDE 2 needs a plugin: arduino-littlefs-upload by Earle Philhower (the author of the RP2040 core). It works with Arduino IDE 2.2.1 and later.

  1. Download. Go to the Releases page and download the latest arduino-littlefs-upload-x.y.z.vsix file (don't unzip it).
  2. The plugins folder. On Windows, go to C:\Users\YourUserName\.arduinoIDE\ and create a plugins folder if it doesn't exist. On macOS and Linux: ~/.arduinoIDE/plugins/. Note that the folder name starts with a dot (.arduinoIDE), and on Windows it may be hidden.
  3. Copy and restart. Put the vsix file in the plugins folder, then close the Arduino IDE completely and open it again.
  4. Close the Serial Monitor. If it's open, the upload fails with a "port doesn't exist" error.
  5. Run it. Press Ctrl+Shift+P (on a Mac, ⌘+Shift+P) and choose the command Upload LittleFS to Pico/ESP8266/ESP32. The plugin works out the partition's size and location from the Partition Scheme you selected, builds a LittleFS image from the data folder, and writes it to the board over the USB cable.

Two common traps

1) The Partition Scheme must be the same for the LittleFS upload and the program upload; if you upload the first with Default and the second with Minimal SPIFFS, the program looks for the partition in a different place and you get "mount failed" or missing files. 2) Uploading LittleFS overwrites the whole partition; logs and settings that the program had created on the board are erased. This plugin doesn't work in Wokwi; in Wokwi you have to create files from code (like the LittleFS_Basics program does).

Part 4: Calling internet APIs (HTTPS and JSON)

Until now the ESP32 was the server (others asked it for things). Now it's the other way round: the ESP32 becomes a client and asks an internet service for something. An address that a service has set up to answer programs (not people) is called an API. The answer is usually JSON, the same format you saw in lesson 5.1.

An everyday example

An API is like the order window of a bakery. You don't need to know what goes on inside the bakery; you only need to know how to order ("two baguettes, please"), and the baker hands the answer back in a fixed form (a bag of bread). The URL is your order and the JSON is the bag of bread.

The weather in Tehran from Open-Meteo

Open-Meteo is a free weather service that needs no key (API key) and no sign-up for non-commercial use. Before writing any code, open the address below in your computer's browser to see what the answer looks like; that's a professional habit:

https://api.open-meteo.com/v1/forecast?latitude=35.69&longitude=51.39&current=temperature_2m,wind_speed_10m

The address has three parts: latitude and longitude (Tehran's geographic coordinates), and current (which "right now" values you want: the temperature 2 meters above the ground and the wind speed at a height of 10 meters). The answer looks something like this (shortened):

{
  "latitude": 35.7,
  "longitude": 51.4,
  "timezone": "GMT",
  "current_units": { "time": "iso8601", "interval": "seconds",
                     "temperature_2m": "°C", "wind_speed_10m": "km/h" },
  "current": {
    "time": "2026-09-23T10:15",
    "interval": 900,
    "temperature_2m": 27.4,
    "wind_speed_10m": 11.2
  }
}

We only want two numbers: current.temperature_2m and current.wind_speed_10m. The rest is extra and wastes RAM.

The library you need: ArduinoJson 7

  1. Arduino IDE → Tools › Manage Libraries (the book icon).
  2. Search for ArduinoJson and install ArduinoJson by Benoit Blanchon; make sure it's version 7.x. It has no dependencies.
#include <WiFi.h>
#include <WiFiClientSecure.h>
#include <HTTPClient.h>
#include <ArduinoJson.h>
#include "secrets.h"

const char *URL =
  "https://api.open-meteo.com/v1/forecast"
  "?latitude=35.69&longitude=51.39"
  "&current=temperature_2m,wind_speed_10m";

bool fetchWeather(float &temp, float &wind) {
  WiFiClientSecure client;
  client.setInsecure();              // for learning only! see the right way below
  HTTPClient http;
  http.setConnectTimeout(5000);      // at most 5 seconds to connect
  http.setTimeout(5000);             // at most 5 seconds for the answer
  http.useHTTP10(true);              // no chunking, so we can read the stream
  if (!http.begin(client, URL)) return false;

  int code = http.GET();
  if (code != HTTP_CODE_OK) {
    Serial.printf("HTTP error: %d %s\n", code, http.errorToString(code).c_str());
    http.end();
    return false;
  }

  JsonDocument filter;               // keep only these two numbers
  filter["current"]["temperature_2m"] = true;
  filter["current"]["wind_speed_10m"] = true;

  JsonDocument doc;
  DeserializationError err = deserializeJson(doc, http.getStream(),
                               DeserializationOption::Filter(filter));
  http.end();
  if (err) {
    Serial.printf("JSON error: %s\n", err.c_str());
    return false;
  }
  temp = doc["current"]["temperature_2m"] | NAN;   // if missing: NAN
  wind = doc["current"]["wind_speed_10m"] | NAN;
  return !isnan(temp);
}

void setup() {
  Serial.begin(115200);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) delay(500);
  Serial.println("Wi-Fi OK");
}

void loop() {
  float t, w;
  if (fetchWeather(t, w)) {
    Serial.printf("Tehran: %.1f C, wind %.1f km/h\n", t, w);
  }
  delay(10UL * 60 * 1000);           // every 10 minutes, not every second
}
  1. Three libraries. WiFiClientSecure for the encrypted connection (HTTPS), HTTPClient for building the request and reading the HTTP answer, and ArduinoJson for parsing the JSON. In core 3.x the real class name is NetworkClientSecure, and WiFiClientSecure is a backward-compatible alias; both are the same thing. We kept the more familiar name.
  2. The API address. In C++, strings placed side by side are joined automatically; we split the address over three lines for readability. Separate the parameters with & and don't put in any spaces. One wrong letter (for example temperature_2) gets you a 400 error answer.
  3. setInsecure: encryption without identity checking. The connection is encrypted, but the ESP32 doesn't check that the other side really is open-meteo.com. The honest truth (as in lesson 5.1): for fetching a public temperature that isn't secret, the risk is small; the worst case is that someone feeds you a fake temperature. But for anything that carries passwords or commands, never use setInsecure. You'll see the right way (useBuiltinCACertBundle) in the next example.
  4. Time limits. setConnectTimeout for connecting and setTimeout for waiting for the answer, both in milliseconds. Without a time limit, if the internet is slow or the server is busy, the program may wait a long time. A real device should never wait forever for anything.
  5. useHTTP10. Sends the request using HTTP version 1.0. In HTTP/1.1 the server may send the answer in "chunks" (chunked encoding), with size numbers between the chunks. Because we hand the answer straight from the network stream (getStream) to ArduinoJson, those numbers would corrupt the JSON. HTTP/1.0 has no chunking. This is the official recommendation of the ArduinoJson documentation.
  6. GET and checking the response code. HTTP_CODE_OK means 200. A negative number means we never reached the server at all; errorToString turns it into text (for example connection refused or read Timeout). The important codes: 200 success, 400 bad address, 429 "too many requests" (rate limit), 5xx server error. Always check the code before reading the answer, and don't forget http.end() on every path, so memory is freed.
  7. A JSON filter. A small document whose shape says "from the answer, keep only these two fields". The full answer is a few hundred bytes, and with other APIs (for example a 7-day hourly forecast) it can be tens of kilobytes. With a filter, ArduinoJson throws the rest away while reading, and very little RAM is used.
  8. deserializeJson straight from the network. The answer is read directly from the network stream, without storing it in a big String first. If the JSON is incomplete or broken, err is set and err.c_str() gives the reason (for example IncompleteInput or NoMemory). Version 7 has only JsonDocument, which sizes itself. In version 6 you had to write StaticJsonDocument<512> or DynamicJsonDocument with a hand-picked size; old code from the internet gives warnings or errors with version 7.
  9. The | operator for a default value. "If this field exists, give me its value; otherwise NAN (not a number)". If the service renames the field one day, you get NAN instead of a fake zero (which looks like a real temperature!), and you know something is wrong.
  10. Every 10 minutes. 10UL * 60 * 1000 milliseconds; UL means a big unsigned number, so the multiplication doesn't overflow. Open-Meteo itself only updates the "current" data about every 15 minutes (the interval: 900 field); asking every second just bothers the server and may get your IP limited. Under Open-Meteo's terms, free use is for non-commercial purposes only, with a limit of fewer than 10,000 requests per day (and 600 per minute), and the data is licensed CC BY 4.0 (if you publish it somewhere, credit Open-Meteo). Every 10 minutes means 144 requests per day.

An alert to your phone: POST with JSON to ntfy

Now the other direction: the ESP32 sends news. ntfy.sh is a free notification service with no sign-up: you install the ntfy app on your phone (Android or iOS), subscribe to a "topic" with any name you like, and every message sent to that topic appears as a notification on your phone.

The topic name is the password

ntfy.sh has no accounts, so anyone who knows your topic name can read your messages and send you fake ones. Don't pick a name like test or ali; use a long random name like home-alert-7f3k9q and keep it in secrets.h. The limits of free ntfy.sh: about 250 messages per day, and at most 4096 bytes per message.

The circuit: one push button between GPIO15 and GND (we turn on the internal pull-up resistor; lesson 3.1).

#include <WiFi.h>
#include <WiFiClientSecure.h>
#include <HTTPClient.h>
#include <ArduinoJson.h>
#include "secrets.h"
#ifndef NTFY_TOPIC
#warning "NTFY_TOPIC is not defined in secrets.h"
#define NTFY_TOPIC "change-me-to-a-random-name"
#endif

const int BUTTON_PIN = 15;          // button between GPIO15 and GND

bool sendAlert(const char *title, const char *message) {
  WiFiClientSecure client;
  client.useBuiltinCACertBundle();  // really checks the server's identity
  HTTPClient http;
  http.setTimeout(5000);
  if (!http.begin(client, "https://ntfy.sh/")) return false;
  http.addHeader("Content-Type", "application/json");

  JsonDocument msg;                 // {"topic":..,"title":..,"message":..}
  msg["topic"] = NTFY_TOPIC;
  msg["title"] = title;
  msg["message"] = message;
  msg["priority"] = 4;              // 1 to 5; 4 means "high"
  msg["tags"].add("warning");
  String body;
  serializeJson(msg, body);

  int code = http.POST(body);
  http.end();
  Serial.printf("ntfy -> %d\n", code);
  return code == 200;
}

void setup() {
  Serial.begin(115200);
  pinMode(BUTTON_PIN, INPUT_PULLUP);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) delay(500);
  Serial.println("Press the button to send an alert");
}

void loop() {
  static unsigned long lastSent = 0;
  if (digitalRead(BUTTON_PIN) == LOW && millis() - lastSent > 30000) {
    lastSent = millis();            // at most one alert every 30 seconds
    sendAlert("Door", "Front door opened!");
  }
  delay(20);
}
  1. useBuiltinCACertBundle. This time the identity of the ntfy.sh server really is checked. This message goes to your phone, and one day it might say "the door opened" or "gas leak"; you don't want anyone changing it on the way.
  2. The root address and the content type. To send JSON you must POST to the root address https://ntfy.sh/ (not https://ntfy.sh/topic) and say that the body is JSON. According to the ntfy documentation, JSON is only accepted at the root address, and the topic name goes inside the JSON itself. There is also a simpler way: POST plain text to https://ntfy.sh/your-topic-name, and the whole text becomes the message.
  3. Building the JSON. This time it's the reverse of deserialize: we fill the document, and serializeJson turns it into text. msg["tags"].add("warning") creates an array, which ntfy turns into the ⚠️ emoji. Never build JSON by hand by gluing strings together ("{\"title\":\"" + ...); if the message text contains a ", the JSON breaks. ArduinoJson takes care of special characters for you.
  4. Priority 1 to 5. 3 is the default, 4 is "high" with a long vibration, 5 is "urgent". Use 4 or 5 for a real alert; use 2 for a daily report, which sits silently in the notification list. If everything is urgent, nothing is urgent anymore.
  5. POST and the response code. On success, ntfy returns 200. If you see 429, you've gone over the request limit; if it's a negative number, the problem is the network or the certificate.
  6. A sending limit. After each alert, no other alert is sent for 30 seconds, even if the button is held down. Without this, holding the button for 2 seconds means dozens of requests and dozens of notifications, and a few minutes later the service blocks you. Every device that sends messages to an outside service needs "brakes" (rate limiting).
Telegram, and a fact about Iran

The UniversalTelegramBot library (by Brian Lough) lets you build a Telegram bot with the ESP32, so you can switch a relay on and off by messaging the bot. But Telegram's servers (api.telegram.org), and sometimes other services such as ntfy.sh, may not be reachable from inside Iran without a VPN, and the ESP32 can't easily use a VPN. More dependable alternatives: MQTT on your own server (lesson 5.1), or running ntfy on your own server (ntfy is open source).

Part 5: A checklist for a device that stays on for months

A program that works on your desk for 10 minutes is different from a program that works for 6 months without anyone touching it. Problems you never see in 10 minutes: memory that slowly breaks into fragments, Wi-Fi that drops at 3 a.m., power that goes out in the middle of writing a file. The engineering rule: assume that anything that can go wrong eventually will, and the device must pick itself back up.

An everyday example: an airplane's black box

After every incident, an airplane can tell what happened, because it has a black box. Your device needs a "black box" too: every time it powers up, it should say why it reset and how many times it has crashed so far. Without that, troubleshooting a device in the ceiling is just guessing.

#include <Preferences.h>
#include "esp_system.h"
#include "esp_task_wdt.h"

Preferences prefs;

const char *resetReasonText(esp_reset_reason_t r) {
  switch (r) {
    case ESP_RST_POWERON:   return "power on";
    case ESP_RST_SW:        return "software (ESP.restart)";
    case ESP_RST_PANIC:     return "PANIC (crash / Guru Meditation)";
    case ESP_RST_INT_WDT:   return "interrupt watchdog";
    case ESP_RST_TASK_WDT:  return "TASK WATCHDOG";
    case ESP_RST_WDT:       return "other watchdog";
    case ESP_RST_DEEPSLEEP: return "wake from deep sleep";
    case ESP_RST_BROWNOUT:  return "BROWNOUT (weak power)";
    default:                return "other/unknown";
  }
}

void workerTask(void *param) {
  esp_task_wdt_add(NULL);                      // register this task with the watchdog
  for (;;) {
    // ... the task's real work goes here ...
    esp_task_wdt_reset();                      // "I'm alive"
    vTaskDelay(pdMS_TO_TICKS(1000));
  }
}

void setup() {
  Serial.begin(115200);
  delay(500);
  esp_reset_reason_t why = esp_reset_reason();

  prefs.begin("sys", false);                   // "sys" namespace in NVS
  uint32_t boots = prefs.getUInt("boots", 0) + 1;
  prefs.putUInt("boots", boots);
  if (why == ESP_RST_PANIC || why == ESP_RST_TASK_WDT || why == ESP_RST_BROWNOUT) {
    prefs.putUInt("crashes", prefs.getUInt("crashes", 0) + 1);
  }
  Serial.printf("Boot #%lu, reason: %s, crashes so far: %lu\n",
                (unsigned long)boots, resetReasonText(why),
                (unsigned long)prefs.getUInt("crashes", 0));
  prefs.end();

  enableLoopWDT();                             // if loop is stuck over 5 s: reset
  xTaskCreatePinnedToCore(workerTask, "worker", 3072, NULL, 1, NULL, 1);
}

String line;                                   // global, reserved once

void loop() {
  line.reserve(64);                            // does nothing after the first time
  line = "uptime=";
  line += millis() / 1000;
  line += "s heap=";
  line += ESP.getFreeHeap();
  Serial.println(line);
  delay(2000);                                 // change this to 6000 and the WDT resets
}
  1. Turning the reset reason into text. esp_reset_reason() returns a number of type esp_reset_reason_t, and we turn the most important ones into readable text. Three reasons that should always worry you: PANIC (a crash, such as a Guru Meditation or a stack overflow), TASK_WDT (a task got stuck), and BROWNOUT (weak power). POWERON means power was connected, and SW means the program itself called ESP.restart() (after an OTA update, for example). Note: pressing the EN button on the ESP32 is usually reported as POWERON.
  2. Registering a task with the watchdog. esp_task_wdt_add(NULL) means "watch the current task", and esp_task_wdt_reset() means "I'm alive". From this moment, if this task doesn't reset the watchdog for more than 5 seconds, the board resets. Put the reset where it runs only when the work is really making progress, not in a separate task that is always alive (then you'd be fooling the watchdog). Add a task that does long jobs such as HTTPS with care, because one slow request can take more than 5 seconds.
  3. Counters in Preferences. The total number of boots and the number of "bad" resets are stored in NVS and aren't lost when the power goes off. If after a week you see crashes is 40, you know something is wrong, even if the device "seems to work". We only write at boot, not in loop, so the flash doesn't wear out. In a real project, report these numbers on the web page or over MQTT.
  4. enableLoopWDT. A ready-made core function that registers loopTask with the watchdog. The core itself resets the watchdog before every pass of loop(). So if one pass of loop takes more than 5 seconds (for example it gets stuck in a while waiting for a sensor that has been disconnected), the board resets itself and starts over. A reset is better than freezing forever.
  5. A String with reserve. The global variable line grabs 64 bytes once, and every pass refills that same space. Every time a String grows, it may take a new spot in the heap and leave the old one empty. After thousands of times, the heap becomes full of holes, like Swiss cheese: the total free space is large, but no big continuous piece is left (and HTTPS needs a continuous piece of several tens of kilobytes). reserve takes the space once, up front. For fixed-size strings, char buf[64] with snprintf is the safest. To see the problem, print ESP.getMaxAllocHeap() (the largest free block) as well as ESP.getFreeHeap().
  6. Testing the watchdog. If you change the delay to 6000, each pass of loop takes more than 5 seconds and the board resets; after the reset you'll see the message reason: TASK WATCHDOG. Trigger every safety mechanism on purpose once, to make sure it really works. A watchdog that has never been tested isn't a watchdog.

Writing safely in case of power loss

Suppose you're rewriting config.json and the power goes out right in the middle. Mode "w" had already emptied the old file; now you have neither the old settings nor the new ones. The right pattern (you'll see it in the project below): 1) write to config.tmp, 2) close it, 3) delete the old file and rename the tmp file to config.json. Renaming in LittleFS is almost instant. And in any case, when the settings file is missing or broken, the program must come up with default values, not crash. For small values, Preferences already has this safety built in.

#include <WiFi.h>
#include <WebServer.h>
#include <ArduinoOTA.h>
#include <LittleFS.h>
#include <WiFiClientSecure.h>
#include <HTTPClient.h>
#include <ArduinoJson.h>
#include <Wire.h>
#include <Adafruit_GFX.h>
#include <Adafruit_SSD1306.h>
#include "secrets.h"
#ifndef OTA_PASS
#warning "OTA_PASS is not defined in secrets.h"
#define OTA_PASS "change-me"
#endif

struct Weather { float temp; float wind; unsigned long at; };
struct Config  { float lat; float lon; };

WebServer server(80);
Adafruit_SSD1306 display(128, 64, &Wire, -1);
QueueHandle_t weatherBox;          // one-slot mailbox: always the latest weather
SemaphoreHandle_t cfgMutex;        // lock for the shared settings
TaskHandle_t weatherHandle = NULL;
Config cfg = {35.69, 51.39};       // default: Tehran

// ---------- LittleFS: reading and safely saving the settings ----------
void loadConfig() {
  File f = LittleFS.open("/config.json", "r");
  if (!f) return;                                  // not saved yet
  JsonDocument doc;
  if (!deserializeJson(doc, f)) {
    cfg.lat = doc["lat"] | cfg.lat;
    cfg.lon = doc["lon"] | cfg.lon;
  }
  f.close();
}

bool saveConfig(const Config &c) {
  JsonDocument doc;
  doc["lat"] = c.lat;
  doc["lon"] = c.lon;
  File f = LittleFS.open("/config.tmp", "w");      // temporary file first
  if (!f) return false;
  bool ok = serializeJson(doc, f) > 0;
  f.close();
  if (!ok) return false;
  LittleFS.remove("/config.json");
  return LittleFS.rename("/config.tmp", "/config.json");  // then swap it in
}

// ---------- Weather task: every 10 minutes, or when the settings change ----------
bool fetchWeather(float lat, float lon, Weather &w) {
  char url[160];
  snprintf(url, sizeof(url),
           "https://api.open-meteo.com/v1/forecast?latitude=%.2f&longitude=%.2f"
           "&current=temperature_2m,wind_speed_10m", lat, lon);
  WiFiClientSecure client;
  client.useBuiltinCACertBundle();
  HTTPClient http;
  http.setConnectTimeout(5000);
  http.setTimeout(5000);
  http.useHTTP10(true);
  if (!http.begin(client, url)) return false;
  int code = http.GET();
  bool ok = false;
  if (code == HTTP_CODE_OK) {
    JsonDocument filter;
    filter["current"]["temperature_2m"] = true;
    filter["current"]["wind_speed_10m"] = true;
    JsonDocument doc;
    if (!deserializeJson(doc, http.getStream(), DeserializationOption::Filter(filter))) {
      w.temp = doc["current"]["temperature_2m"] | NAN;
      w.wind = doc["current"]["wind_speed_10m"] | NAN;
      w.at = millis();
      ok = !isnan(w.temp);
    }
  }
  http.end();
  return ok;
}

void weatherTask(void *param) {
  for (;;) {
    if (WiFi.status() == WL_CONNECTED) {
      xSemaphoreTake(cfgMutex, portMAX_DELAY);
      Config c = cfg;                              // copy, then give the lock back
      xSemaphoreGive(cfgMutex);
      Weather w;
      if (fetchWeather(c.lat, c.lon, w)) {
        xQueueOverwrite(weatherBox, &w);           // replaces the previous value
      }
    }
    // sleep 10 minutes, unless someone wakes us up sooner
    ulTaskNotifyTake(pdTRUE, pdMS_TO_TICKS(10UL * 60 * 1000));
  }
}

// ---------- Display task: latest weather on the OLED every 2 seconds ----------
void displayTask(void *param) {
  Weather w;
  for (;;) {
    display.clearDisplay();
    display.setCursor(0, 0);
    display.println(WiFi.localIP());
    if (xQueuePeek(weatherBox, &w, 0) == pdPASS) {  // look, don't take
      display.setTextSize(2);
      display.printf("%.1f C\n", w.temp);
      display.setTextSize(1);
      display.printf("wind %.1f km/h\n", w.wind);
      display.printf("%lu min ago", (millis() - w.at) / 60000);
    } else {
      display.println("waiting for data...");
    }
    display.display();
    vTaskDelay(pdMS_TO_TICKS(2000));
  }
}

// ---------- Web: page from LittleFS, data from code ----------
void handleState() {
  Weather w = {NAN, NAN, 0};
  xQueuePeek(weatherBox, &w, 0);
  JsonDocument doc;
  xSemaphoreTake(cfgMutex, portMAX_DELAY);
  doc["lat"] = cfg.lat;
  doc["lon"] = cfg.lon;
  xSemaphoreGive(cfgMutex);
  doc["temp"] = w.temp;
  doc["wind"] = w.wind;
  String out;
  serializeJson(doc, out);
  server.send(200, "application/json", out);
}

void handleSave() {
  Config c = {server.arg("lat").toFloat(), server.arg("lon").toFloat()};
  if (c.lat < -90 || c.lat > 90 || c.lon < -180 || c.lon > 180) {
    return server.send(400, "text/plain", "bad lat/lon");
  }
  xSemaphoreTake(cfgMutex, portMAX_DELAY);
  cfg = c;
  xSemaphoreGive(cfgMutex);
  saveConfig(c);
  xTaskNotifyGive(weatherHandle);                  // "fetch again right now"
  server.sendHeader("Location", "/");
  server.send(303);
}

void setup() {
  Serial.begin(115200);
  LittleFS.begin(true);
  loadConfig();
  weatherBox = xQueueCreate(1, sizeof(Weather));
  cfgMutex = xSemaphoreCreateMutex();

  Wire.begin(21, 22);
  display.begin(SSD1306_SWITCHCAPVCC, 0x3C);
  display.setTextColor(SSD1306_WHITE);

  WiFi.mode(WIFI_STA);
  WiFi.setAutoReconnect(true);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  unsigned long t0 = millis();
  while (WiFi.status() != WL_CONNECTED && millis() - t0 < 20000) delay(250);

  ArduinoOTA.setHostname("weather-station");
  ArduinoOTA.setPassword(OTA_PASS);
  ArduinoOTA.begin();

  server.serveStatic("/", LittleFS, "/index.html");
  server.on("/api/state", HTTP_GET, handleState);
  server.on("/api/config", HTTP_POST, handleSave);
  server.begin();

  xTaskCreatePinnedToCore(weatherTask, "weather", 12288, NULL, 1, &weatherHandle, 1);
  xTaskCreatePinnedToCore(displayTask, "display", 4096, NULL, 1, NULL, 1);
}

  ArduinoOTA.handle();
  server.handleClient();

}
  1. Two structs. Weather is a package of temperature, wind and the time it was fetched; Config holds the coordinates. Packing related data into one struct lets a single xQueueOverwrite move it all together, in one piece; a new temperature never gets mixed up with an old time.
  2. A one-slot queue as a "mailbox". A queue of length 1 that is filled with xQueueOverwrite and read with xQueuePeek. In the ordinary queue (Part 1), each piece of data was read and removed once. Here we have two readers (the OLED and the web page), and both just want "the latest weather"; Peek looks without removing, and Overwrite always replaces the previous value and never finds the queue "full".
  3. Reading the settings at boot. If the file doesn't exist or the JSON is broken, the Tehran default (line 25) stays. The same principle as Part 5: the device must always boot, even with incomplete settings.
  4. Saving safely. First config.tmp, then delete the old file and rename. If the power goes out in the middle of serializeJson, the previous config.json is still intact. serializeJson(doc, f) writes straight into the file and returns the number of bytes; zero means failure.
  5. fetchWeather. The same code as Part 4, with two differences: the address is built from the coordinates with snprintf, and this time we use useBuiltinCACertBundle. snprintf writes into a fixed 160-byte array and never runs past its end; no temporary String is created on the heap. This task runs every 10 minutes for months, so this is exactly where heap fragmentation matters.
  6. weatherTask. It copies the settings under the lock, gives the lock back right away, then does the slow HTTPS request and puts the result in the mailbox. Never hold a lock during a slow job (several seconds of HTTPS), or the web page, which also needs cfg, has to wait just as long. "Copy, release, then work".
  7. ulTaskNotifyTake with a 10-minute limit. The task sleeps until either 10 minutes pass or someone wakes it with xTaskNotifyGive. A task notification is FreeRTOS's lightest tool for "hey, wake up". With a plain vTaskDelay, after changing the city you'd have to wait up to 10 minutes for the new weather.
  8. displayTask. Every 2 seconds it redraws the screen: the IP address, the temperature in large text, the wind, and how many minutes ago the data was fetched. Only this task touches the OLED (and I2C), so the display doesn't need a mutex. A rule simpler than locks: every piece of hardware has one owner. Showing "minutes ago" matters: if the internet is down for a day, the user won't mistake yesterday's temperature for today's.
  9. /api/state. Peeks the latest weather from the mailbox, reads the settings under the lock, and returns everything as JSON. This function runs in loopTask (inside server.handleClient), while weatherTask may be reading cfg at the same moment, or waiting for it to change; that's why the lock is needed.
  10. /api/config. It validates the input, saves it in cfg and in the file, wakes up weatherTask, and sends the browser back to the main page with code 303. Never trust user input: toFloat() returns zero for invalid text, and a latitude of 500 makes no sense. The 303 makes sure that refreshing the page doesn't resend the form.
  11. setup in the right order. LittleFS and the settings, then the queue and the lock (before any task), the OLED, Wi-Fi with a 20-second limit, OTA, the web server, and finally the tasks. If Wi-Fi doesn't connect within 20 seconds, the device doesn't stop: setAutoReconnect connects it later, and weatherTask simply waits until then. weatherTask's stack is deliberately 12 KB because HTTPS is heavy; after a few days, measure the real value with uxTaskGetStackHighWaterMark.
  12. A tiny loop. Only OTA and the web server, with a delay(2). Because the slow work lives in a separate task, loop always comes round in a few milliseconds, and OTA and the web page always answer quickly, even in the middle of a slow HTTPS request. That's exactly the problem we started this lesson with.

Coach's corner

This lesson gave you powerful tools, and power is dangerous. My three rules: One, every new task, queue and lock needs a reason; if you can't say in one sentence why this job needs its own task, it doesn't. Two, never send a program over OTA to a device you can't reach unless you've first tested that exact program on a board on your desk, including Wi-Fi dropouts and power cuts. I've seen devices that had to be brought down from the roof because of one wrong line in setup. Three, a device that doesn't record the cause of its resets isn't a professional device. From today on, in every project that stays on for more than a day, include the "black box" code from Part 5. Once the crash counter has stayed at zero for a week, then you can say "it works".

Lesson quiz

On the ESP32, how much stack does the line xTaskCreatePinnedToCore(f, "t", 2048, NULL, 1, NULL, 1); give the task?

  1. 2048 words, which is 8 KB
  2. 2048 bytes, which is 2 KB
  3. Always 8 KB, like loopTask
  4. It depends on the priority
In ESP-IDF's FreeRTOS, stack size is in bytes. Code copied from other platforms with a small number such as 512 crashes on the ESP32.

You have a task on core 0 that increments a number in a for(;;) loop without any vTaskDelay. What happens after about 5 seconds?

  1. Nothing happens
  2. A stack overflow happens
  3. The task watchdog fires because IDLE0 never got a turn to run, and the board resets
  4. The brownout detector resets the board
In the Arduino core, the task watchdog watches IDLE0 with a 5-second timeout. The cure: a short vTaskDelay in the loop.

A sensor task reads a number every 200 milliseconds and a display task has to show it. What's the safest and cleanest way to pass it over?

  1. A queue with xQueueSend and xQueueReceive
  2. An ordinary global variable
  3. Just a mutex, with no variable
  4. Writing to Serial and reading from it
A queue copies the data, never moves it halfway, and puts the receiving task to sleep until data arrives.

Your program gives "Sketch too big" and the device must have OTA. Which Partition Scheme do you choose?

  1. Huge APP (3MB No OTA/1MB SPIFFS)
  2. No OTA (2MB APP/2MB SPIFFS)
  3. Default 4MB with spiffs
  4. Minimal SPIFFS (1.9MB APP with OTA/128KB SPIFFS)
Minimal SPIFFS has two 1.9 MB program slots: a bigger program fits and OTA stays. Only the file space drops to 128 KB.

In the weather example, why did we put http.useHTTP10(true) before deserializeJson(doc, http.getStream(), ...)?

  1. Because HTTP 1.0 is faster
  2. So the server doesn't send the answer chunked (in pieces with size numbers), which would corrupt the JSON read from the stream
  3. Because HTTPS only works with HTTP 1.0
  4. So the server's certificate isn't checked
When you read straight from getStream(), HTTPClient doesn't stitch the chunks back together. HTTP/1.0 removes the problem at its root.

Your device is in the ceiling. After an OTA update it no longer shows up in the Port menu, and Wi-Fi isn't connected either. What could have prevented this in advance?

  1. Removing the OTA password
  2. Choosing Huge APP
  3. Testing the new program on a board on your desk, and using rollback so the new version is only confirmed after Wi-Fi connects
  4. Turning off the watchdog
With verifyRollbackLater() and manual confirmation after Wi-Fi connects, a broken version automatically goes back to the previous one. And nothing replaces testing on your desk.

Exercises

Exercise 1: three cooks

Extend the queue program (potentiometer and LED): create a third task that blinks the second LED on GPIO5, with a blink speed that depends on the potentiometer value (0 means every 1000 milliseconds and 4095 means every 100 milliseconds). The display task must also send the value on to the third task. Print the stack of all three tasks every 5 seconds, and shrink the stacks as far as you can while keeping at least 500 bytes of margin.

Hint

Create a second queue. The blinking task can ask "got a new number?" without waiting, using xQueueReceive(q2, &v, 0), and carry on with the previous number if there isn't one. To convert the number, use map(v, 0, 4095, 1000, 100).

Exercise 2: heat alert

Combine the weather program and the ntfy program: if the temperature in Tehran goes above 35 degrees, send an ntfy alert, but only once, until the temperature drops back below 33 degrees. The "alert already sent" state must be remembered even after a reset.

Hint

The gap between 35 and 33 is "hysteresis", so that temperatures of 35 and 34.9 one after another don't create dozens of alerts. To remember across resets, a bool in Preferences is enough; write it only when its value changes.

Answer (the key part) 
prefs.begin("alert", false);
bool sent = prefs.getBool("sent", false);
if (!sent && t > 35.0) {
  if (sendAlert("Heat", "Tehran above 35 C")) {
    prefs.putBool("sent", true);   // only once it was really sent
  }
} else if (sent && t < 33.0) {
  prefs.putBool("sent", false);    // ready for the next alert
}
prefs.end();
Exercise 3: the black box on the web page

Add the Part 5 "black box" to the weather-station project: return the reason for the last reset, the number of boots and the number of crashes in /api/state, and show them in index.html. Then make a deliberate change (for example, an endless loop in loop after 1 minute, with enableLoopWDT) to trigger a watchdog reset, and check that it gets recorded on the page. Finally, send the fixed version over OTA.

Hint

Read the reset reason once in setup and keep it in a global const char * variable; in handleState just put it into the JSON. For the OTA test, make sure the broken version still calls ArduinoOTA.handle() during that first minute, or you'll have to fix it with the cable. (This very experience will make the coach's advice real for you.)

The lesson in three lines

FreeRTOS runs slow jobs in separate tasks; pass data with a queue and protect shared resources with a mutex, give stack sizes in bytes, and make every loop sleep somewhere so the watchdog doesn't reset the board. OTA, with two program partitions (Default or Minimal SPIFFS) and a password, keeps the device up to date remotely, and LittleFS keeps files and settings separate from the program. Call APIs with HTTPS, time limits, a JSON filter and a sensible interval, and with reset-reason logging, a watchdog and safe saving, build a device that works for months without you.
