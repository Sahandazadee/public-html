FreeRTOS: doing several jobs at once without a mess

The problem: a single loop() gets crowded fast

Imagine you want a device that blinks one LED every 250 milliseconds, blinks another LED every 1 second, reads a potentiometer every 200 milliseconds, fetches the weather from the internet every 10 minutes, and always answers a web page. With delay() this is impossible, because every delay stops everything else. With millis() (lesson 3.1) it can be done, but loop fills up with if (millis() - lastX >= ...) checks. Worst of all: fetching the weather can take 2 to 5 seconds, and during that time the LEDs and the web page are stuck waiting too.

The professional solution is to write each job separately, as if each one had its own little program, and let a "manager" decide whose turn it is at every moment. That manager is FreeRTOS: a small real-time operating system (RTOS) that is always running on the ESP32, even when you don't know it.

An everyday example: a restaurant kitchen

Picture a restaurant. If it has only one cook (that's the lone loop), the cook has to put the rice on, run to flip the kebabs, run to make the salad, and if they get stuck on the phone taking orders, the kebabs burn. A real restaurant has several cooks (each one is a task): one handles the rice, one the kebabs, one the salad. The head chef (the FreeRTOS scheduler) decides who gets to use the stove. The ESP32 has two stoves (two cores), so two cooks can cook at exactly the same time.

The cooks don't talk over each other and mess up each other's work; they put orders on the counter (that's a queue). And there is only one big knife: whoever picks it up, everyone else waits until it's put back (that's a mutex).

The secret: loop() is itself a task

When you write a program in the Arduino IDE, before anything else the Arduino core creates a task called loopTask, which calls setup() once and then loop() forever. Here are this task's settings in core 3.3.12 (from the core's own main.cpp and sdkconfig files):

So you have been using FreeRTOS since day one. Now you are just learning to hire a second and a third cook. (Wi-Fi itself also runs several high-priority tasks on core 0; that's why Wi-Fi works "behind the scenes".)

The first tasks: two LEDs at two speeds

The circuit: two LEDs, each with its own 220 Ω resistor, on GPIO4 and GPIO26. Also connect the potentiometer to GPIO34 now, because you'll need it in the next example.

// Two LEDs at two different speeds, each in its own task
const int LED_FAST = 4;   // fast LED
const int LED_SLOW = 26;  // slow LED

void blinkFast(void *param) {          // first task function
  pinMode(LED_FAST, OUTPUT);
  bool on = false;
  for (;;) {                           // a task must never end
    on = !on;
    digitalWrite(LED_FAST, on);
    vTaskDelay(pdMS_TO_TICKS(250));    // step aside for 250 ms
  }
}

void blinkSlow(void *param) {          // second task function
  pinMode(LED_SLOW, OUTPUT);
  bool on = false;
  for (;;) {
    on = !on;
    digitalWrite(LED_SLOW, on);
    vTaskDelay(pdMS_TO_TICKS(1000));   // 1 second
  }
}

void setup() {
  Serial.begin(115200);
  xTaskCreatePinnedToCore(
    blinkFast,     // which function
    "blinkFast",   // task name (only for debugging)
    2048,          // stack size in BYTES
    NULL,          // input parameter (none)
    1,             // priority
    NULL,          // task handle (not needed)
    1);            // core 1
  xTaskCreatePinnedToCore(blinkSlow, "blinkSlow", 2048, NULL, 1, NULL, 1);
  Serial.printf("setup() runs on core %d\n", xPortGetCoreID());
}

void loop() {                          // loop is a task too
  Serial.printf("loop() alive on core %d, millis=%lu\n",
                xPortGetCoreID(), millis());
  delay(2000);
}
  1. The task function. Every task is an ordinary function with exactly this shape: void name(void *param). The param input is a "pointer to anything" that you can hand to the task when you create it. FreeRTOS wants one fixed shape for all tasks so it can treat them all the same way. If the function's shape is different, the compiler gives an error.
  2. One-time work at the start of the task. Like a small setup just for this task: it makes the pin an output and creates a local variable for the LED state. The variable on is inside the task, so it lives on this task's stack. Every task has its own separate stack, so two tasks with variables of the same name never get mixed up.
  3. The endless loop for (;;). A task must stay in a loop forever. This plays the same role as loop(). If the task function reaches its final } and returns, the ESP32 resets with an error (abort). If a task's work really is finished, it must delete itself with vTaskDelete(NULL);.
  4. vTaskDelay and pdMS_TO_TICKS. vTaskDelay tells the scheduler "I have nothing to do right now, give the stove to someone else". Its unit is the "tick"; pdMS_TO_TICKS(250) converts milliseconds to ticks. On the Arduino ESP32 one tick is 1 millisecond (CONFIG_FREERTOS_HZ=1000), so the conversion doesn't change the number. But if you ever move the code to a system with a 10 ms tick, all your times would be 10 times longer without this macro. Build the right habit from the start.
  5. The second task. Exactly the same pattern, just with a different pin and time. See how simple it became: each task only thinks about its own job. No tangled if (millis() - last ...) checks.
  6. xTaskCreatePinnedToCore with seven inputs. In order: function, name, stack size, parameter, priority, handle, core number. "PinnedToCore" means "pin it to this core". If you don't choose a core (the xTaskCreate function), the task can run on either core; when you're starting out, pinning makes the behavior more predictable.
  7. 2048 means 2048 bytes. This is the single most important ESP32 detail: in the ESP-IDF version of FreeRTOS, stack size is given in bytes. In standard FreeRTOS (on an STM32, for example) the same number is in "words", and each word is four bytes; so 2048 there would be 8 KB. If you copy code from the internet that sets the stack to 512, on the ESP32 you get only 512 bytes and the board will probably crash. Use 2048 for a simple task, about 3000 to 4096 for a task that uses Serial.printf, and at least 8 to 12 KB for a task that uses HTTPS.
  8. Priority. A number from 0 to 24; bigger means more important. When two tasks are ready to run, the scheduler always picks the one with higher priority. Tasks with equal priority take turns (every tick). 1 is the same priority as loop. To start, give everything 1 or 2. Give high priority to a task that must respond quickly and works briefly; a long-running task with high priority starves everyone else.
  9. The second task in one line. The same seven inputs, without comments. After this line we have three tasks on core 1: loopTask and the two blinkers, plus the system's own tasks on core 0.
  10. loop keeps doing its own job. It prints a message every 2 seconds; xPortGetCoreID() returns the number of the current core. Important detail: on the Arduino ESP32, delay() is really just vTaskDelay (the core defines it as vTaskDelay(ms / portTICK_PERIOD_MS)), so a delay in loop also hands the CPU to other tasks and the blinking never stops. But delayMicroseconds() and empty loops such as while(...) {} really do lock up the CPU.
setup() runs on core 1 loop() alive on core 1, millis=312 loop() alive on core 1, millis=2312 loop() alive on core 1, millis=4312

And on the board: the red LED blinks twice per second and the green LED blinks once every 2 seconds (1 second on, 1 second off), completely independently of each other.

So how is vTaskDelay different from delay?

On the Arduino ESP32, in behavior, almost not at all: both put the current task to sleep and free the CPU. The difference is the unit: delay(ms) takes milliseconds and vTaskDelay(ticks) takes ticks. Inside tasks we use vTaskDelay(pdMS_TO_TICKS(...)) because it is FreeRTOS's own language and works correctly on any system. If you want something to repeat exactly every 100 milliseconds (without the time the job itself takes being added on), use vTaskDelayUntil.

C++ corner: void *, & and lambdas

FreeRTOS code (and the ESP32 libraries in lessons 5.5 and 5.6) is full of three C++ signs that look scary at first. Each one is a simple idea:

An everyday example: parcels, addresses and nicknames

A pointer (*) is a home address written on a note: the note isn't the house, but with it you can find the house. void * is an address note with no label saying what kind of building it is; whoever receives it must know. A reference (& in a parameter) is a nickname: "Sam" and "Samuel" are the same person, so if you give Sam a haircut, Samuel has short hair too. A lambda is a note with instructions written on the spot and handed over directly, instead of a named recipe in a cookbook.

All three in one small sketch (the same circuit: LEDs on GPIO4 and GPIO26):

// void*, & and a lambda: the three C++ signs of FreeRTOS code
int fastPin = 4;                             // global: lives as long as the program
int slowPin = 26;

void blinkTask(void *param) {                // one function, used by two tasks
  int pin = *(int *)param;                   // void* back to int*, then read the int
  int ms = (pin == fastPin) ? 250 : 1000;
  pinMode(pin, OUTPUT);
  bool on = false;
  for (;;) {
    on = !on;
    digitalWrite(pin, on);
    vTaskDelay(pdMS_TO_TICKS(ms));
  }
}

void addOne(int &n) {                        // & in a parameter: a reference
  n = n + 1;                                 // changes the caller's own variable
}

void setup() {
  Serial.begin(115200);
  xTaskCreatePinnedToCore(blinkTask, "fast", 2048, &fastPin, 1, NULL, 1);
  xTaskCreatePinnedToCore(blinkTask, "slow", 2048, &slowPin, 1, NULL, 1);
  xTaskCreatePinnedToCore(                   // a task written as a lambda
    [](void *param) {
      int count = 0;
      for (;;) {
        addOne(count);                       // count really grows by one
        Serial.printf("lambda task: count = %d\n", count);
        vTaskDelay(pdMS_TO_TICKS(1000));
      }
    },
    "counter", 3072, NULL, 1, NULL, 1);
}

void loop() {
  delay(1000);                               // loop has nothing to do here
}
  1. & in front of a variable: "the address of". &fastPin is not the number 4; it's the address in memory where the number 4 is kept. That address is what reaches the task as its param. One function can now serve two tasks, each with its own pin. The variables are global on purpose: a local variable in setup() disappears when setup ends, and the task would then read an address that holds garbage.
  2. void *: "a pointer to anything". FreeRTOS doesn't know what you'll pass, so the parameter has no type. (int *)param says "this address points to an int", and the * in front reads the int that lives there. This is the one fixed shape FreeRTOS demands for every task function. You'll see (void *param) in every task in this course, usually unused (NULL is passed).
  3. & in a parameter: a reference. int &n means "n is just another name for the caller's variable". addOne(count) really changes count. Without the &, the function would get a copy and change only the copy. In lesson 5.6, fetchWeather(float &temp, float &wind) uses exactly this to "return" two numbers at once.
  4. A lambda: a function with no name. [](void *param) { ... } is written right where it's needed. The empty [] means it uses no local variables from around it. You'll meet lambdas everywhere as "callbacks", small functions you hand to a library to call later: ArduinoOTA.onStart([]() { ... }) and server.on("/api/temp", []() { ... }) in lesson 5.5. For a task longer than a few lines, a normal named function is easier to read.

Moving data safely: the queue

Now a real problem: one task reads a sensor and another task has to display the value. The first idea: "I'll use a global variable; one task writes it and the other reads it". For a simple int this usually works, but for bigger data (say a struct with temperature, humidity and time) the display task might read it halfway through a write: new temperature with old humidity! This bug is called a "race condition", and it's the worst kind of bug, because it happens once in a thousand times.

A queue is FreeRTOS's official solution. A queue is a pipe with a fixed number of slots: one task puts a copy of the data in at one end, and the other task takes it out at the other end, in the same order (first in, first out). FreeRTOS guarantees that data is never moved halfway.

// Sensor task → queue → display task, plus a lock for Serial
const int POT_PIN = 34;          // potentiometer (ADC1, input only)
const int LED_PIN = 4;           // LED with variable brightness (PWM)

QueueHandle_t potQueue;          // queue between the two tasks
SemaphoreHandle_t serialMutex;   // lock for the Serial Monitor
TaskHandle_t sensorHandle = NULL;
TaskHandle_t displayHandle = NULL;

void sensorTask(void *param) {
  for (;;) {
    int raw = analogRead(POT_PIN);                  // 0 to 4095
    if (xQueueSend(potQueue, &raw, 0) != pdPASS) {  // don't wait
      // queue is full: throw this sample away
    }
    vTaskDelay(pdMS_TO_TICKS(200));                 // 5 times per second
  }
}

void displayTask(void *param) {
  int value;
  for (;;) {
    // wait up to 1 second for data; the CPU is free meanwhile
    if (xQueueReceive(potQueue, &value, pdMS_TO_TICKS(1000)) == pdPASS) {
      ledcWrite(LED_PIN, value / 16);               // 0..4095 → 0..255
      if (xSemaphoreTake(serialMutex, pdMS_TO_TICKS(100)) == pdTRUE) {
        Serial.printf("pot=%4d  led=%3d\n", value, value / 16);
        xSemaphoreGive(serialMutex);                // give the lock back
      }
    }
  }
}

void setup() {
  Serial.begin(115200);
  ledcAttach(LED_PIN, 5000, 8);                     // 5 kHz, 8 bits
  potQueue = xQueueCreate(10, sizeof(int));         // 10 slots, one int each
  serialMutex = xSemaphoreCreateMutex();
  if (potQueue == NULL || serialMutex == NULL) {
    Serial.println("Out of memory!");
    while (true) delay(1000);
  }
  xTaskCreatePinnedToCore(sensorTask, "sensor", 3072, NULL, 2, &sensorHandle, 1);
  xTaskCreatePinnedToCore(displayTask, "display", 4096, NULL, 1, &displayHandle, 1);
}

void loop() {
  delay(5000);
  if (xSemaphoreTake(serialMutex, portMAX_DELAY) == pdTRUE) {
    Serial.printf("[stack] sensor free=%u B, display free=%u B, heap=%u B\n",
                  (unsigned)uxTaskGetStackHighWaterMark(sensorHandle),
                  (unsigned)uxTaskGetStackHighWaterMark(displayHandle),
                  (unsigned)ESP.getFreeHeap());
    xSemaphoreGive(serialMutex);
  }
}
  1. Handles. QueueHandle_t, SemaphoreHandle_t and TaskHandle_t are like the "phone numbers" of the queue, the lock and the tasks; FreeRTOS builds the object itself in memory and we only keep its number. They are global so every task can reach them. A handle never changes after it is created, so making it global is safe.
  2. Read and send. xQueueSend(queue, address of data, wait time) copies the contents of raw and puts it in the queue. The & sign means "the address of this variable". Because it's a copy, raw can change after this line without damaging the data inside the queue. A wait time of 0 means "if the queue is full, don't wait"; the sensor task shouldn't fall behind just because the display is slow.
  3. If the queue is full. xQueueSend returns errQUEUE_FULL, and we deliberately do nothing: this sample is thrown away. In a real device you have to decide: "is new data more important, or old data?". For a display, the newest data matters; for a log, all of it does. Make this decision on purpose, not by accident.
  4. xQueueReceive with a wait time. The display task waits up to 1 second for something to arrive in the queue. During that time it really sleeps and uses zero percent of the CPU. This is the most beautiful part of a queue: the display task doesn't need vTaskDelay, because waiting on the queue already frees the CPU. As soon as data arrives, FreeRTOS wakes it up.
  5. LED brightness. The 12-bit ADC number (0 to 4095) divided by 16 becomes 0 to 255, the range of 8-bit PWM. This is the same ledcWrite from lesson 3.2, with the version 3 API. In core 2.x you had to use ledcSetup and ledcAttachPin with a channel number.
  6. A mutex around Serial. xSemaphoreTake picks up the knife (waiting up to 100 milliseconds if someone else has it), prints, and xSemaphoreGive puts it back. Without the lock, if loop and the display task print at the same time, their lines get jumbled together: pot=12[stack] sens34 led=.... Protect every shared resource (Serial, I2C, a file, a big variable) that more than one task uses with a mutex. Golden rule: every Take has a Give, or everyone else waits forever.
  7. Creating the queue and the lock, and checking they worked. xQueueCreate(10, sizeof(int)) creates a queue with 10 slots, each the size of one int (4 bytes). The queue and the lock take memory from the heap. If memory has run out, you get NULL back, and using NULL means a crash. Always check. The queue and the lock must be created before the tasks, because the tasks start using them immediately.
  8. Priorities and handles. The sensor task has priority 2 and the display task 1. This time we keep the handle (&sensorHandle). Reading the sensor is short and time-sensitive, so it gets the higher priority. We need the handle so we can later ask about the task from outside (for example, how much stack it has used).
  9. uxTaskGetStackHighWaterMark. The "high-water mark" is the smallest amount of free stack this task has ever had, given in bytes in ESP-IDF. This number is your stack-tuning tool: if you gave a task 4096 bytes and this number is 2800, then at most about 1300 bytes were used; you can shrink the stack and free up RAM. If it drops below 500 bytes, make the stack bigger. ESP.getFreeHeap shows the total free RAM.
pot=2048 led=128 pot=2051 led=128 pot=4095 led=255 [stack] sensor free=1964 B, display free=2312 B, heap=289140 B pot=4095 led=255

(The stack and heap numbers will be a little different on your board; what matters is that you know how to read them.)

Try it in Wokwi: turn the potentiometer and watch the LED brightness and the numbers in the Serial Monitor change. FreeRTOS is fully simulated in Wokwi, so the tasks, the queue and the mutex behave exactly as they do on a real board. No extra library is needed.

Task notifications: the lightest doorbell

A queue carries data. Sometimes there's no data to send at all, only a message: "wake up, there's work". For that, every FreeRTOS task has a built-in doorbell called a task notification. One task (or loop) rings it with xTaskNotifyGive(handle); the waiting task sleeps in ulTaskNotifyTake(...) until the bell rings or its time limit runs out. You don't create anything, it uses almost no memory, and it's faster than a queue.

An everyday example: the kitchen bell

In our restaurant, the queue is the counter where plates of food are put down. A notification is the little bell on the counter: "ding" carries no food, it just means "come now". The cook who hears it knows what to do.

The circuit: keep the LED on GPIO4 and add a push button between GPIO27 and GND, exactly as in lesson 3.1 (we use the internal pull-up).

// A report task: wakes every 10 s, or at once when the button is pressed
const int BUTTON_PIN = 27;           // button between GPIO27 and GND
const int LED_PIN = 4;               // status LED

TaskHandle_t reportHandle = NULL;    // the report task's "phone number"

void reportTask(void *param) {
  pinMode(LED_PIN, OUTPUT);
  for (;;) {
    // sleep until the bell rings, or for at most 10 seconds
    uint32_t rings = ulTaskNotifyTake(pdTRUE, pdMS_TO_TICKS(10000));
    if (rings > 0) {
      Serial.printf("Woken by the button (rings: %lu)\n", (unsigned long)rings);
    } else {
      Serial.println("10 s passed: routine report");
    }
    digitalWrite(LED_PIN, HIGH);     // short flash: "I did my job"
    vTaskDelay(pdMS_TO_TICKS(100));
    digitalWrite(LED_PIN, LOW);
  }
}

void setup() {
  Serial.begin(115200);
  pinMode(BUTTON_PIN, INPUT_PULLUP);
  xTaskCreatePinnedToCore(reportTask, "report", 3072, NULL, 1, &reportHandle, 1);
}

void loop() {
  static bool wasPressed = false;
  bool pressed = (digitalRead(BUTTON_PIN) == LOW);
  if (pressed && !wasPressed) {      // only the moment of pressing (the edge)
    xTaskNotifyGive(reportHandle);   // ring the bell
  }
  wasPressed = pressed;
  delay(30);                         // simple debounce, and a rest for the CPU
}
  1. The task handle. To ring a task's bell you need its "phone number", so this time we pass &reportHandle to xTaskCreatePinnedToCore and it fills the handle in. If you forget it, the handle stays NULL, and xTaskNotifyGive(NULL) crashes the board. Create the task before anyone tries to notify it.
  2. ulTaskNotifyTake: wait for the bell. The task sleeps (zero CPU) until someone calls xTaskNotifyGive, or until 10 seconds have passed. pdTRUE means "after waking, reset the ring count to zero". One line gives you two things at once: a regular timer (every 10 seconds) and an instant wake-up. With a plain vTaskDelay(10000), a button press would have to wait up to 10 seconds. With pdFALSE instead, each call takes only one ring off the count, which is handy for counting events one by one.
  3. Why did I wake up? The return value is the number of rings that were waiting. Zero means the time limit ran out. If you press twice while the task is busy flashing the LED, the rings add up, and the next call returns 2. Nothing is lost, and the task still wakes only once.
  4. Ringing the bell on the press. loop notices the moment the button goes from "not pressed" to "pressed" (the edge, as in lesson 3.1) and calls xTaskNotifyGive. Holding the button down rings only once. Notice that loop never prints anything: only the report task uses Serial, so there's no need for a mutex. "One owner per resource" is often simpler than a lock.
  5. delay(30). Checking the button about 30 times per second is plenty, and it filters out contact bounce. This delay also hands the CPU to other tasks. A loop with no delay at all would spin nonstop and waste power.
10 s passed: routine report Woken by the button (rings: 1) Woken by the button (rings: 1) 10 s passed: routine report

Notice that after a button wake-up, the 10-second count starts again from zero, because every ulTaskNotifyTake call starts a new wait. The weather-station project in lesson 5.6 uses exactly this pattern: "fetch every 10 minutes, or right now if the settings change".

Try it in Wokwi: wait 10 seconds for the routine report, then click the green button and watch the report arrive at once, with a short flash of the LED.

From an interrupt to a task: xQueueSendFromISR

In lesson 3.1 you met interrupts: with attachInterrupt, a tiny function (the ISR) runs the instant a pin changes, like a doorbell. An ISR must be very short: no Serial, no delay, no waiting of any kind. The ordinary FreeRTOS functions such as xQueueSend and xTaskNotifyGive are not allowed inside an ISR, because they may wait or switch tasks in a way an interrupt can't handle. Each of them has an ISR twin with FromISR at the end of its name. The professional pattern: the ISR only notes the event and hands it to a task; the task does the slow work.

An everyday example

The doorbell only rings; it doesn't open the door or make tea for the guest. Someone inside the house (the task) hears the ring and does the real work. If the bell itself tried to make tea, the whole house would stop while it did.

// Button interrupt → queue → task: the ISR only records the time
const int BUTTON_PIN = 27;                 // button between GPIO27 and GND

QueueHandle_t pressQueue;                  // press times, from the ISR to the task

void IRAM_ATTR onPress() {                 // the ISR: tiny and fast
  uint32_t now = millis();
  BaseType_t wokeHigher = pdFALSE;
  xQueueSendFromISR(pressQueue, &now, &wokeHigher);
  portYIELD_FROM_ISR(wokeHigher);          // switch to the woken task right away
}

void pressTask(void *param) {
  uint32_t t;
  int count = 0;
  for (;;) {
    xQueueReceive(pressQueue, &t, portMAX_DELAY);  // sleep until an edge arrives
    vTaskDelay(pdMS_TO_TICKS(30));         // let the contact bounce die down
    xQueueReset(pressQueue);               // throw away the bounce edges
    if (digitalRead(BUTTON_PIN) != LOW) continue;  // not held: it was a release
    count++;
    Serial.printf("Press #%d at %lu ms\n", count, (unsigned long)t);
  }
}

void setup() {
  Serial.begin(115200);
  pinMode(BUTTON_PIN, INPUT_PULLUP);
  pressQueue = xQueueCreate(20, sizeof(uint32_t));
  if (pressQueue == NULL) {
    Serial.println("Out of memory!");
    while (true) delay(1000);
  }
  xTaskCreatePinnedToCore(pressTask, "press", 3072, NULL, 2, NULL, 1);
  attachInterrupt(digitalPinToInterrupt(BUTTON_PIN), onPress, FALLING);
}

void loop() {
  delay(1000);                             // loop has nothing to do here
}
  1. The ISR with IRAM_ATTR. The same kind of function as in lesson 3.1: it runs on every falling edge (HIGH to LOW) of GPIO27. IRAM_ATTR keeps the ISR in fast internal RAM, so it can run even while the flash memory is busy. Without it, an interrupt at the wrong moment can crash the board.
  2. xQueueSendFromISR. Puts a copy of the press time into the queue, without ever waiting. If the queue is full, the press is simply dropped. The third input, &wokeHigher, is a small report back: "did this wake a task more important than the one that was interrupted?" This is the interrupt-safe twin of xQueueSend. The rule is simple: inside an ISR, only call FreeRTOS functions whose name ends in FromISR. Others you'll meet: vTaskNotifyGiveFromISR and xSemaphoreGiveFromISR.
  3. portYIELD_FROM_ISR. If wokeHigher became true, the scheduler switches to that task the moment the ISR ends, instead of at the next tick. Here pressTask has priority 2, higher than loop's 1, so the press gets handled within microseconds. Without this line it still works, just up to 1 ms later.
  4. The task waits forever for a press. portMAX_DELAY means "no time limit". Between presses the task uses zero CPU. This is the same queue you used for the potentiometer; only the sender changed. That's the beauty of a queue: the receiver doesn't care who sent the data.
  5. Debouncing in the task, not in the ISR. A mechanical button "bounces" and produces several edges per press. The task waits 30 ms, throws away the extra edges with xQueueReset, then checks that the button is really still held down. Waiting is forbidden in an ISR but perfectly fine in a task. The last check also filters out the bounce when you release the button, which can create a falling edge too.
  6. The slow work: printing. Serial runs in the task, never in the ISR. Serial.printf can take milliseconds and uses locks inside; in an ISR it can freeze or crash the board. The ISR finishes in a few microseconds, and the task does the rest calmly.
  7. The right order in setup. First the queue, then the task, and only then attachInterrupt. If the interrupt were switched on first, one press (or a bounce at power-up) could call the ISR while pressQueue is still NULL, and the board would crash.
Press #1 at 2315 ms Press #2 at 3870 ms Press #3 at 4102 ms

Also good to know: software timers

For "run this small job every 500 ms", FreeRTOS also has software timers: you give it a function and a period, and a built-in timer task calls your function on time. The function must be short and must never wait (no delay, no long HTTPS request), because all timers share that one task. For anything slow, a timer can simply notify a task.

void onTick(TimerHandle_t t) {           // runs in the timer task: keep it short
  static bool on = false;
  on = !on;
  digitalWrite(4, on);                   // the status LED blinks by itself
}

// in setup(), after pinMode(4, OUTPUT):
TimerHandle_t tick = xTimerCreate("tick", pdMS_TO_TICKS(500), pdTRUE, NULL, onTick);
xTimerStart(tick, 0);                    // pdTRUE above = repeat forever

When the stack runs out (stack overflow)

Every task has a box of memory of the size you asked for. Local variables, arrays and every function you call fit into this box. Serial.printf alone needs a few hundred bytes, and an HTTPS connection needs several kilobytes. If the box overflows, data spills onto the neighboring memory. Luckily the ESP32 is watching, and before everything is ruined it prints this and resets the board:

***ERROR*** A stack overflow in task display has been detected. Backtrace: 0x40081f2e:0x3ffb5f40 0x40086d15:0x3ffb5f60 ... Rebooting...

Common signs of a too-small stack: this very message, or Guru Meditation Error: Core 1 panic'ed (LoadProhibited), or random resets when a task does something heavier (for example, its first HTTPS connection). The cure: double the stack number in xTaskCreatePinnedToCore, then use uxTaskGetStackHighWaterMark to see how much is really needed. And don't declare a big array (such as char buf[4000]) as a local inside a task; make it global or static so it moves off the stack.

The task watchdog: why does the board reset by itself?

The ESP32 has a "watchdog" that checks every so often that the important tasks are still alive. In the Arduino core this watchdog watches core 0's idle task (IDLE0), with a timeout of 5 seconds (CONFIG_ESP_TASK_WDT_TIMEOUT_S=5). The idle task only runs when no other task on that core has anything to do. So if a task on core 0 works for five seconds without a break, IDLE0 never gets a turn, the watchdog concludes "the system is frozen", and it resets the board.

An everyday example

A building's night guard has to press a button in the lobby every hour so the system knows they're awake. If someone blocks the lobby with an endless job and the guard can't reach the button, the alarm goes off. vTaskDelay is how you "let the guard through".

// ❌ Deliberately wrong: a greedy task on core 0 that never rests
volatile unsigned long counter = 0;

void greedyTask(void *param) {
  for (;;) {
    counter++;              // works nonstop and never steps aside
    // vTaskDelay(1);       // ✅ the cure: uncomment this line
  }
}

void setup() {
  Serial.begin(115200);
  xTaskCreatePinnedToCore(greedyTask, "greedy", 2048, NULL, 1, NULL, 0);
}

void loop() {
  Serial.println(counter);
  delay(1000);
}
  1. The greedy task. An endless loop that only increments a number and never calls vTaskDelay. This task is always ready to run and its priority (1) is higher than IDLE0's (0); so the scheduler always picks it and IDLE0 starves.
  2. On core 0. The last input is 0. If you put the same task on core 1, the default settings won't reset the board (IDLE1 isn't watched), but loop and the equal-priority tasks on core 1 slow down. "It doesn't reset" means "the problem is hidden", not "it's correct".
  3. The cure. One vTaskDelay(1) (even 1 millisecond) in the loop is enough to give IDLE0 a turn. The rule: every endless loop in every task must sleep or wait for something somewhere (vTaskDelay, xQueueReceive, xSemaphoreTake with a wait time). Busy-wait loops such as while (!ready) {} are enemy number one.

About 5 seconds after power-up you'll see something like this, and the board resets:

E (5316) task_wdt: Task watchdog got triggered. The following tasks/users did not reset the watchdog in time: E (5316) task_wdt: - IDLE0 (CPU 0) E (5316) task_wdt: Tasks currently running: E (5316) task_wdt: CPU 0: greedy E (5316) task_wdt: CPU 1: IDLE1 E (5316) task_wdt: Aborting. abort() was called at PC 0x400d8c5f on core 0 ... Rebooting...

The line CPU 0: greedy gives away the culprit: the name you gave the task. That's why you should choose meaningful task names.

The wrong way: turning off the watchdog

On forums you'll see code like disableCore0WDT(). It silences the message, but the problem is still there: the system tasks on core 0 (such as Wi-Fi) starve, and the network connection drops in strange ways. The watchdog isn't your enemy; it's a friend telling you your code is stuck somewhere.

Task or millis()? Which should I choose?

For two or three light, quick jobs, millis() in loop is simpler and has no concurrency bugs. Bring in a task when: 1) you have a slow, blocking job (HTTPS, a slow sensor read, writing to an SD card) that shouldn't make everything else wait; 2) the jobs have completely different timing; 3) you want to use the second core. Every new task means a separate stack, and every piece of shared data means a queue or a mutex. Don't create tasks without a reason.

Coach's corner

FreeRTOS is a powerful tool, and power is dangerous. My three rules: One, every new task, queue and lock needs a reason; if you can't say in one sentence why this job needs its own task, it doesn't. Two, every endless loop in every task must wait somewhere; the moment you type for (;;), your very next thought should be "where does this sleep?". Three, keep interrupts tiny: an ISR that prints or waits will crash sooner or later, usually at the worst possible moment. Before you move on, explain to a friend, without looking, the difference between a queue, a mutex and a notification. If you can, you're ready for lesson 5.5.

Lesson quiz

On the ESP32, how much stack does the line xTaskCreatePinnedToCore(f, "t", 2048, NULL, 1, NULL, 1); give the task?

  1. 2048 words, which is 8 KB
  2. 2048 bytes, which is 2 KB
  3. Always 8 KB, like loopTask
  4. It depends on the priority
In ESP-IDF's FreeRTOS, stack size is in bytes. Code copied from other platforms with a small number such as 512 crashes on the ESP32.

You have a task on core 0 that increments a number in a for(;;) loop without any vTaskDelay. What happens after about 5 seconds?

  1. Nothing happens
  2. A stack overflow happens
  3. The task watchdog fires because IDLE0 never got a turn to run, and the board resets
  4. The brownout detector resets the board
In the Arduino core, the task watchdog watches IDLE0 with a 5-second timeout. The cure: a short vTaskDelay in the loop.

A sensor task reads a number every 200 milliseconds and a display task has to show it. What's the safest and cleanest way to pass it over?

  1. A queue with xQueueSend and xQueueReceive
  2. An ordinary global variable
  3. Just a mutex, with no variable
  4. Writing to Serial and reading from it
A queue copies the data, never moves it halfway, and puts the receiving task to sleep until data arrives.

Inside an interrupt function (ISR) you want to send the time of a button press to a task through a queue. Which line is correct?

  1. xQueueSend(q, &t, portMAX_DELAY);
  2. xQueueSendFromISR(q, &t, &wokeHigher);
  3. Serial.println(t); and let the task read Serial
  4. delay(50); then xQueueSend(q, &t, 0);
Inside an ISR only the FromISR functions are allowed; they never wait. wokeHigher tells you whether to switch to the woken task right away with portYIELD_FROM_ISR.

A task sleeps for 10 minutes between two jobs. When the user presses a button, you want it to do its job right away. No data needs to be sent. What's the lightest tool?

  1. A mutex
  2. Delete the task and create it again
  3. A task notification: xTaskNotifyGive on one side, ulTaskNotifyTake with a 10-minute time limit on the other
  4. Change the 10 minutes to vTaskDelay(1)
A notification is FreeRTOS's built-in doorbell: nothing to create, almost no memory, and the waiting task wakes either when the bell rings or when its time limit runs out.

Exercises

Exercise 1: three cooks

Extend the queue program (potentiometer and LED): create a third task that blinks the second LED on GPIO26, with a blink speed that depends on the potentiometer value (0 means every 1000 milliseconds and 4095 means every 100 milliseconds). The display task must also send the value on to the third task. Print the stack of all three tasks every 5 seconds, and shrink the stacks as far as you can while keeping at least 500 bytes of margin.

Hint

Create a second queue. The blinking task can ask "got a new number?" without waiting, using xQueueReceive(q2, &v, 0), and carry on with the previous number if there isn't one. To convert the number, use map(v, 0, 4095, 1000, 100).

What should you see?

Five pot= lines per second, and every 5 seconds one stack report. The stack and heap numbers below are an example; yours will be a little different:

pot=   0  led=  0
pot=   0  led=  0
pot=2048  led=128
pot=4095  led=255
[stack free] sensor=940 B, display=1290 B, blink=1310 B, heap=288900 B
  • Pot at 0: the green LED on GPIO26 is on for 1 second, off for 1 second. Pot in the middle (about 2048): it changes every 550 ms. Pot at the end (4095): every 100 ms, a fast flicker.
  • After you turn the pot, the new speed starts at the next change of the LED (at most 1 second later), and the red LED on GPIO4 changes its brightness at the same time.
  • Every stack number in the report is at least 500. If one is below 500, make that task's stack bigger; if one is far above (over 1500), you can make it smaller.
  • No line is ever jumbled with another: the mutex still protects the Serial Monitor.
Full answer with explanation

The complete program: the queue example from this lesson plus a second queue and a third task.

// Three cooks: sensor -> queue -> display -> queue -> blinker
const int POT_PIN = 34;          // potentiometer (ADC1, input only)
const int LED_PIN = 4;           // LED with variable brightness (PWM)
const int LED2_PIN = 26;         // ★ second LED: blink speed follows the pot

QueueHandle_t potQueue;          // sensor -> display
QueueHandle_t blinkQueue;        // ★ display -> blinker
SemaphoreHandle_t serialMutex;   // lock for the Serial Monitor
TaskHandle_t sensorHandle = NULL;
TaskHandle_t displayHandle = NULL;
TaskHandle_t blinkHandle = NULL;

void sensorTask(void *param) {
  for (;;) {
    int raw = analogRead(POT_PIN);                  // 0 to 4095
    xQueueSend(potQueue, &raw, 0);                  // queue full? drop this sample
    vTaskDelay(pdMS_TO_TICKS(200));                 // 5 times per second
  }
}

void displayTask(void *param) {
  int value;
  for (;;) {
    if (xQueueReceive(potQueue, &value, pdMS_TO_TICKS(1000)) == pdPASS) {
      ledcWrite(LED_PIN, value / 16);               // 0..4095 -> 0..255
      xQueueSend(blinkQueue, &value, 0);            // ★ pass it on, never wait
      if (xSemaphoreTake(serialMutex, pdMS_TO_TICKS(100)) == pdTRUE) {
        Serial.printf("pot=%4d  led=%3d\n", value, value / 16);
        xSemaphoreGive(serialMutex);
      }
    }
  }
}

void blinkTask(void *param) {                       // ★ the third cook
  pinMode(LED2_PIN, OUTPUT);
  int period = 1000;                                // until the first number arrives
  int v;
  bool on = false;
  for (;;) {
    while (xQueueReceive(blinkQueue, &v, 0) == pdPASS) {  // empty the queue, no waiting
      period = map(v, 0, 4095, 1000, 100);               // the newest number wins
    }
    on = !on;
    digitalWrite(LED2_PIN, on);
    vTaskDelay(pdMS_TO_TICKS(period));
  }
}

void setup() {
  Serial.begin(115200);
  ledcAttach(LED_PIN, 5000, 8);                     // 5 kHz, 8 bits
  potQueue = xQueueCreate(10, sizeof(int));
  blinkQueue = xQueueCreate(10, sizeof(int));
  serialMutex = xSemaphoreCreateMutex();
  if (potQueue == NULL || blinkQueue == NULL || serialMutex == NULL) {
    Serial.println("Out of memory!");
    while (true) delay(1000);
  }
  // stacks shrunk after measuring (were 3072 and 4096)
  xTaskCreatePinnedToCore(sensorTask, "sensor", 2048, NULL, 2, &sensorHandle, 1);
  xTaskCreatePinnedToCore(displayTask, "display", 3072, NULL, 1, &displayHandle, 1);
  xTaskCreatePinnedToCore(blinkTask, "blink", 2048, NULL, 1, &blinkHandle, 1);
}

void loop() {
  delay(5000);
  if (xSemaphoreTake(serialMutex, portMAX_DELAY) == pdTRUE) {
    Serial.printf("[stack free] sensor=%u B, display=%u B, blink=%u B, heap=%u B\n",
                  (unsigned)uxTaskGetStackHighWaterMark(sensorHandle),
                  (unsigned)uxTaskGetStackHighWaterMark(displayHandle),
                  (unsigned)uxTaskGetStackHighWaterMark(blinkHandle),
                  (unsigned)ESP.getFreeHeap());
    xSemaphoreGive(serialMutex);
  }
}
  1. One more pin, queue and handle. GPIO26 for the second LED, blinkQueue between the display and the blink task, and blinkHandle for the stack report. Each pair of cooks gets its own queue. A queue has exactly one job (carry numbers from A to B), which keeps the program easy to follow.
  2. The sensor task, unchanged. Reads the pot 5 times per second and drops the sample if the queue is full. Its job hasn't changed; only its stack is smaller now (see setup).
  3. The display task passes the value on. Right after setting the red LED, it puts the same number into blinkQueue, with a waiting time of 0. The display task must never get stuck because the blinker is slow. With 0, if the queue were ever full, the number is simply dropped; a newer one follows 200 ms later.
  4. Empty the queue without waiting. The while takes every number that has arrived; only the last one (the newest) sets period. If nothing has arrived, the old period stays. About 5 numbers arrive per second, but at the slow speed the task only looks once per second. Taking just one number per round would leave it working through old values, several seconds behind the knob. map turns 0..4095 into 1000..100: map(2048, 0, 4095, 1000, 100) = 550.
  5. Blink, then sleep. Toggle the LED and wait period milliseconds with vTaskDelay. vTaskDelay frees the CPU for the other tasks during the wait. This is also why a new speed starts only after the current wait ends.
  6. Create the second queue and check it. All three objects are checked for NULL before any task starts. A task that uses a queue that was never created crashes the board. Creating everything first, then the tasks, avoids that.
  7. Smaller stacks. The lesson measured about 1964 bytes free out of 3072 for the sensor task (so about 1100 used), and 2312 free out of 4096 for the display task (about 1800 used). So 2048 leaves about 940 and 3072 about 1290 free, both above the 500-byte margin. The blink task does even less and gets 2048. Stack size = what the task really uses + a safety margin. Don't cut it to exactly 500: a rare path (an error message, a longer printf) can use more than you ever measured.
  8. A report for three tasks. One uxTaskGetStackHighWaterMark per handle, inside the mutex. The high-water mark is the smallest free stack ever seen, so let the program run a while and turn the knob before you trust the numbers.

Try it in Wokwi: turn the potentiometer from one end to the other and watch the green LED's speed and the red LED's brightness change together. No extra library is needed.

Exercise 2: a press counter with a heartbeat

Combine the last two examples. The ISR sends presses to pressTask through the queue, as in ButtonISR. After every 5 presses, pressTask notifies a second task, which blinks the LED on GPIO26 five times quickly. The blinking task must also blink the LED once every 10 seconds on its own, as a "heartbeat", even if nobody presses anything.

Hint

In the blinking task use ulTaskNotifyTake(pdTRUE, pdMS_TO_TICKS(10000)): a return value of 0 means the 10 seconds ran out (heartbeat: one blink), and more than 0 means the bell rang (five blinks). Keep the blinking task's handle in a global variable, and create both tasks before attachInterrupt.

What should you see?

Press the button a few times. Your millisecond numbers will differ:

  5 presses: ringing blinkTask
  • Without pressing anything, the LED on GPIO26 gives one short flash (0.1 s) about every 10 seconds: the heartbeat.
  • Presses 1 to 4 make no blink. The 5th press gives five quick blinks (one second in total), and so does the 10th, the 15th...
  • Each press is counted exactly once, whether you press fast or slowly (the numbers go up by 1, never jump by 2 or 3).
  • After the five blinks, the next heartbeat comes about 10 seconds later, because the wait starts again.
Full answer with explanation

The complete program: ButtonISR plus a blinking task that waits for a notification, like the report task in NotifyDemo.

// Button ISR -> queue -> pressTask -> every 5 presses -> blinkTask
const int BUTTON_PIN = 27;                 // button between GPIO27 and GND
const int LED2_PIN = 26;                   // second LED (+220 Ω)

QueueHandle_t pressQueue;                  // press times, from the ISR to pressTask
TaskHandle_t blinkHandle = NULL;           // blinkTask's "phone number"

void IRAM_ATTR onPress() {                 // the ISR: tiny and fast
  uint32_t now = millis();
  BaseType_t wokeHigher = pdFALSE;
  xQueueSendFromISR(pressQueue, &now, &wokeHigher);
  portYIELD_FROM_ISR(wokeHigher);
}

void blink(int times, int ms) {            // on and off, `times` times
  for (int i = 0; i < times; i++) {
    digitalWrite(LED2_PIN, HIGH);
    vTaskDelay(pdMS_TO_TICKS(ms));
    digitalWrite(LED2_PIN, LOW);
    vTaskDelay(pdMS_TO_TICKS(ms));
  }
}

void blinkTask(void *param) {
  pinMode(LED2_PIN, OUTPUT);
  for (;;) {
    // sleep until the bell rings, or for at most 10 seconds
    uint32_t rings = ulTaskNotifyTake(pdTRUE, pdMS_TO_TICKS(10000));
    if (rings > 0) {
      blink(5, 100);                       // 5 presses: five quick blinks
    } else {
      blink(1, 100);                       // 10 s of quiet: one heartbeat
    }
  }
}

void pressTask(void *param) {
  uint32_t t;
  int count = 0;
  for (;;) {
    xQueueReceive(pressQueue, &t, portMAX_DELAY);  // sleep until an edge arrives
    vTaskDelay(pdMS_TO_TICKS(30));         // let the contact bounce die down
    xQueueReset(pressQueue);               // throw away the bounce edges
    if (digitalRead(BUTTON_PIN) != LOW) continue;  // not held: it was a release
    count++;
    Serial.printf("Press #%d at %lu ms\n", count, (unsigned long)t);
    if (count % 5 == 0) {                  // every 5th press
      Serial.println("  5 presses: ringing blinkTask");
      xTaskNotifyGive(blinkHandle);        // ring the bell
    }
  }
}

void setup() {
  Serial.begin(115200);
  pinMode(BUTTON_PIN, INPUT_PULLUP);
  pressQueue = xQueueCreate(20, sizeof(uint32_t));
  if (pressQueue == NULL) {
    Serial.println("Out of memory!");
    while (true) delay(1000);
  }
  xTaskCreatePinnedToCore(blinkTask, "blink", 2048, NULL, 1, &blinkHandle, 1);
  xTaskCreatePinnedToCore(pressTask, "press", 3072, NULL, 2, NULL, 1);
  attachInterrupt(digitalPinToInterrupt(BUTTON_PIN), onPress, FALLING);  // last!
}

void loop() {
  delay(1000);                             // loop has nothing to do here
}
  1. A queue and a handle. The queue carries press times from the ISR to pressTask; the global handle lets pressTask ring blinkTask. Data (a time) goes through a queue; a plain "wake up" goes through a notification, which needs nothing but the handle.
  2. The ISR, unchanged. It only records the time and hands it to the queue with the FromISR function. An ISR must be tiny; the counting and the blinking are work for tasks.
  3. A small blink helper. On and off, as many times as asked, with vTaskDelay for the waits. One function serves both the heartbeat and the celebration. vTaskDelay (not a busy wait) lets the press task keep counting while the LED blinks.
  4. One wait, two meanings. ulTaskNotifyTake sleeps until the bell rings or 10 seconds pass. 0 means "time ran out": one heartbeat; more than 0 means "the bell rang": five quick blinks. The return value tells the two cases apart, so a single task handles both jobs with no timer and no extra variable. pdTRUE clears the count, so several rings during the blinking lead to one more round, not a pile-up.
  5. Counting, as in ButtonISR. Wait for an edge, let the bounce settle, empty the queue, check that the button is still held, count. This is what makes every press count exactly once, so "every 5th press" really means five presses.
  6. Every 5th press rings the bell. count % 5 == 0 is true at 5, 10, 15... % gives the remainder of the division; it's 0 exactly on multiples of 5, so there's no second counter to reset.
  7. Tasks first, interrupt last. blinkTask is created first, so blinkHandle is set before anyone can ring it; attachInterrupt comes at the very end. A press during setup must not reach a queue or a handle that doesn't exist yet. pressTask has the higher priority (2) so a press is handled at once, even in the middle of a blink.

Try it in Wokwi: wait for a heartbeat, then click the green button five times. No extra library is needed.

The lesson in three lines

FreeRTOS runs each job in its own task: give the stack size in bytes, choose priorities sensibly, and make every loop sleep or wait somewhere so the watchdog doesn't reset the board. Pass data with a queue, protect shared resources with a mutex, wake a task with a notification, and from an interrupt use only the FromISR functions. Bring in a task only when there's a reason: a slow, blocking job or completely different timing.
