What is ESP-NOW?

ESP-NOW uses the same 2.4 GHz Wi-Fi radio that is built into the ESP32, but it skips all the Wi-Fi formalities (joining a router, getting an IP address, TCP, handshakes and so on). Each message is a small packet sent straight to the "MAC address" of the target board. It's like handing a letter to your neighbor through the window instead of going to the post office.

An everyday example: walkie-talkie vs telephone

Wi-Fi and MQTT are like a phone call: you dial a number, the telephone exchange (the router and the broker) connects you, and then you talk. It works from anywhere in the world, but without the exchange, nothing works. ESP-NOW is like a walkie-talkie: you press the button and your voice goes straight to the other handset. It's fast and needs no exchange, but it only reaches as far as the signal carries, and messages have to be short.

A few official numbers (from the ESP-IDF documentation)

Each board's address book holds at most 20 peers; by default up to 7 of them can be encrypted (ESP-IDF settings can raise that to 17). In ESP-NOW v1 the data length is at most 250 bytes. Newer cores (based on ESP-IDF 5.4 and later) have ESP-NOW v2, which sends up to 1470 bytes; but a v1 device either truncates or drops any message longer than 250 bytes. This lesson's advice: until you are sure every board has v2, keep messages under 250 bytes. (In this lesson we only send 8 and 12 bytes!)

Step 1: find your board's MAC address

A MAC address is a 6-byte number the factory writes into every ESP32 chip, such as 24:6F:28:AB:CD:EF. Think of it as a house number: ESP-NOW delivers the letter to that exact address. Each two-digit group is one byte in base 16 (hexadecimal).

#include <WiFi.h>

void setup() {
  Serial.begin(115200);
  delay(1000);
  Serial.print("Before WiFi.mode: ");
  Serial.println(WiFi.macAddress());   // probably 00:00:00:00:00:00

  WiFi.mode(WIFI_STA);                 // the Wi-Fi radio switches on
  while (!WiFi.STA.started()) {
    delay(10);
  }
  Serial.print("STA MAC: ");
  Serial.println(WiFi.macAddress());
}

void loop() {}
  1. Reading the MAC before Wi-Fi is on. On purpose, we print the MAC once before WiFi.mode. In Arduino core 3, WiFi.macAddress() reads the address from the "network interface", and that interface doesn't exist until Wi-Fi starts. That's why you get 00:00:00:00:00:00. Lots of students copy exactly these zeros into their sender code and then spend hours hunting for the problem.
  2. WiFi.mode(WIFI_STA). Switches the radio on in station mode. It doesn't need to connect to any router. ESP-NOW works on the STA or the AP interface, and we always pick STA. Each interface has its own MAC (the AP MAC is usually one higher), so take the MAC of the interface ESP-NOW actually uses.
  3. Wait until the STA interface has really started. WiFi.STA.started() becomes true once the radio has finished starting up. Wi-Fi starts up in a separate task and takes a few milliseconds. Espressif's official ESP-NOW examples use exactly this waiting loop too.
  4. The real MAC. Now the correct address is printed. Write it on a piece of masking tape and stick it on the board! From here on you have two boards, and their MACs look alike. Labeling them stops you from mixing up board A and board B.
Before WiFi.mode: 00:00:00:00:00:00 STA MAC: 24:6F:28:AB:CD:EF

Upload this program to board B (the receiver) and write down its MAC. To use it in code, put 0x in front of each part: 24:6F:28:AB:CD:EF becomes {0x24, 0x6F, 0x28, 0xAB, 0xCD, 0xEF}.

The message layout: struct, sizeof and memcpy

ESP-NOW just sends "a handful of bytes" and has no idea what they mean. We have to agree that bytes one to four are the message number, byte five means on or off, and so on. In C++ we write that agreement down as a struct (structure).

An everyday example: a printed form

A struct is like a printed paper form: box one is "number", box two is "status". The sender fills in the form and sends it. The receiver must have exactly the same form to know what each box means. If the receiver has an old version of the form with the boxes in different places, it will read the temperature as the message number!

Do the math: what is sizeof really?

Our command layout: uint32_t seq (4 bytes) + bool ledOn (1 byte). Total = 5 bytes? No! On the ESP32, sizeof(CommandMsg) is 8. The compiler adds three empty bytes (padding) after the bool so the total size is a multiple of 4, because a 32-bit processor reads 4-byte numbers faster from addresses that are multiples of 4. The reply layout: 4 + 1 + 3 (empty) + a 4-byte float = 12 bytes.

In practice: if one side is an ESP32 and the other side is a different chip or compiler (say, an ESP8266), the padding may differ. Between two ESP32s on the same core there's no problem. To be completely sure, you can write __attribute__((packed)) after struct to remove the padding.

  • sizeof(x) gives the number of bytes in x, at compile time. Always use it; never type the number by hand.
  • memcpy(destination, source, count) copies a number of bytes exactly as they are from one place in memory to another. We use it to pour the received bytes into our own struct variable.
  • (uint8_t *)&cmd means "look at the address of the variable cmd as an array of bytes". & gives the address and (uint8_t *) changes the type without changing any data.

Before any radio code, let's see all of this with our own eyes. The program below uses one board and no radio at all: it prints the sizes, shows the actual bytes of a message, and "receives" them again with memcpy, exactly as board B will. Run it on any ESP32, or in Wokwi (an empty ESP32 project; paste it into sketch.ino and press ▶).

typedef struct {
  uint32_t seq;     // message number
  bool ledOn;       // should the LED be on?
} CommandMsg;

typedef struct {
  uint32_t seq;
  bool ledOn;
  float tempC;
} ReplyMsg;

CommandMsg cmd;     // global, so every byte (padding too) starts at 0

void printBytes(const char *label, const uint8_t *p, size_t n) {
  Serial.printf("%s (%u bytes):", label, (unsigned)n);
  for (size_t i = 0; i < n; i++) Serial.printf(" %02X", p[i]);
  Serial.println();
}

void setup() {
  Serial.begin(115200);
  delay(1000);
  Serial.printf("sizeof(CommandMsg) = %u\n", (unsigned)sizeof(CommandMsg));
  Serial.printf("sizeof(ReplyMsg)   = %u\n", (unsigned)sizeof(ReplyMsg));

  cmd.seq = 258;                        // 258 = 0x00000102
  cmd.ledOn = true;
  printBytes("cmd", (uint8_t *)&cmd, sizeof(cmd));

  uint8_t air[sizeof(cmd)];             // pretend these bytes flew over the air
  memcpy(air, &cmd, sizeof(cmd));       // sender: struct -> bytes
  CommandMsg got;
  memcpy(&got, air, sizeof(got));       // receiver: bytes -> struct
  Serial.printf("got.seq = %lu, got.ledOn = %d\n", (unsigned long)got.seq, got.ledOn);
}

void loop() {}
  1. The two message layouts. The same two structs this lesson sends over the radio: a command (A to B) and a reply (B to A). Seeing them in a tiny program first means that later, when the radio is involved, you already trust this part.
  2. A global message variable. A global variable starts with every byte at zero, including the padding bytes. A local variable's padding bytes can hold leftover values from memory, and the printout would show random numbers in those three places. That would be harmless, but confusing.
  3. printBytes: show any memory as bytes. It takes an address and a length and prints every byte in hexadecimal (%02X means "two hex digits"). This is how you look at a message the way the radio sees it: just a row of bytes, with no names and no types.
  4. Printing the sizes. You should see 8 and 12, not 5 and 9. That's the padding from the box above, measured instead of calculated. sizeof always tells the truth, which is why the radio code uses it for every length.
  5. Filling in the form and looking at its bytes. seq = 258 and ledOn = true. The output is 02 01 00 00 01 00 00 00. 258 is 0x00000102 in hex. The ESP32 stores the smallest byte first (this is called "little-endian"), so you see 02 01 00 00. Then comes the bool (01) and three padding bytes (00 00 00). You don't have to memorize the order; both ESP32s use the same one, and that's all that matters.
  6. A pretend radio trip. The first memcpy turns the struct into a plain byte array (what esp_now_send does), and the second pours the bytes into a fresh struct (what the receive callback does). If got.seq comes out as 258 and got.ledOn as 1, the "form" survived the trip. In the real project, the only difference is that the byte array travels through the air between the two memcpys.
sizeof(CommandMsg) = 8 sizeof(ReplyMsg) = 12 cmd (8 bytes): 02 01 00 00 01 00 00 00 got.seq = 258, got.ledOn = 1

Code for board A (sender)

#include <WiFi.h>
#include <esp_now.h>

// Put board B's MAC here (from the GetMac program)
uint8_t receiverMac[] = {0x24, 0x6F, 0x28, 0xAB, 0xCD, 0xEF};

const int BUTTON_PIN = 27;

// Message layout: must be exactly the same on sender and receiver
typedef struct {
  uint32_t seq;     // message number
  bool ledOn;       // should the LED be on?
} CommandMsg;

CommandMsg cmd = {0, false};
int lastReading = HIGH;
int stableState = HIGH;
unsigned long lastChange = 0;

// Core 3.3 and later: the first parameter is a wifi_tx_info_t
void onSent(const wifi_tx_info_t *info, esp_now_send_status_t status) {
  Serial.println(status == ESP_NOW_SEND_SUCCESS ? "  delivered" : "  delivery FAILED");
}

void setup() {
  Serial.begin(115200);
  pinMode(BUTTON_PIN, INPUT_PULLUP);

  WiFi.mode(WIFI_STA);
  while (!WiFi.STA.started()) delay(10);

  if (esp_now_init() != ESP_OK) {
    Serial.println("ESP-NOW init failed");
    while (true) delay(1000);
  }
  esp_now_register_send_cb(onSent);

  esp_now_peer_info_t peer = {};
  memcpy(peer.peer_addr, receiverMac, 6);
  peer.channel = 0;          // 0 means the channel we are on right now
  peer.encrypt = false;
  if (esp_now_add_peer(&peer) != ESP_OK) {
    Serial.println("Failed to add peer");
    while (true) delay(1000);
  }
  Serial.println("Sender ready. Press the button.");
}

void loop() {
  int reading = digitalRead(BUTTON_PIN);
  if (reading != lastReading) {        // new change: restart the bounce timer
    lastChange = millis();
    lastReading = reading;
  }
  if (millis() - lastChange > 30 && reading != stableState) {
    stableState = reading;
    if (stableState == LOW) {          // the button really was pressed
      cmd.seq++;
      cmd.ledOn = !cmd.ledOn;
      esp_err_t r = esp_now_send(receiverMac, (uint8_t *)&cmd, sizeof(cmd));
      Serial.printf("Sent #%lu ledOn=%d (%s)\n", (unsigned long)cmd.seq, cmd.ledOn, r == ESP_OK ? "queued" : esp_err_to_name(r));
    }
  }
}
  1. Two libraries. WiFi.h to switch the radio on, and esp_now.h, which is the main ESP-NOW API from ESP-IDF. ESP-NOW needs the Wi-Fi radio even if you never connect to a router. Both libraries come with the ESP32 core, so there's nothing to install.
  2. The receiver's address. A 6-byte array holding board B's MAC. Get even one digit wrong and the message reaches nobody, and the send callback says "FAILED". This is the most common ESP-NOW mistake.
  3. Defining the message layout. typedef struct {...} CommandMsg; creates a new data type called CommandMsg with two boxes. uint32_t means an unsigned whole number of exactly 32 bits. Unlike int, its size is the same on every chip, which matters when you send data between devices. The message number (seq) helps us notice when a message was lost or arrived twice.
  4. Global variables. The message itself with a starting value, and three variables for debouncing the button. Their values must survive between passes of loop, so they are global. The debounce logic is the same as in lesson 3.1.
  5. The send callback. After every send, ESP-NOW calls this function with the result: ESP_NOW_SEND_SUCCESS or ESP_NOW_SEND_FAIL. Success means board B's radio received and acknowledged the packet at the MAC layer; it does not mean B's program has handled it. If B is off or the MAC is wrong, you get FAIL. This function's signature has changed between versions; be sure to read the yellow box below.
  6. Switching the radio on. STA mode, then wait until it has fully started. esp_now_init must be called after Wi-Fi is on; otherwise it returns an error.
  7. Starting ESP-NOW and registering the callback. If esp_now_init fails, we hold the program in an endless loop. Carrying on without ESP-NOW only produces confusing errors later. "Fail early and loudly" (fail fast) is a good habit.
  8. Adding a peer. We zero an esp_now_peer_info_t structure (= {}), copy the MAC into it, set the channel to 0, leave encryption off, and add it to the address book with esp_now_add_peer. ESP-NOW only sends one-to-one (unicast) messages to MACs that are in the address book. Channel 0 means "the radio's current channel"; by default both boards start on the same channel (usually 1). Zeroing the structure matters: without it, the fields we didn't set would hold garbage values.
  9. Catching every raw change of the button. Whenever the input differs from the previous reading, we record the time. When you press a button, its contact "bounces" for a few milliseconds and flips between 0 and 1 several times. Without debouncing, one press might send two commands and the LED would switch on and immediately off again.
  10. The stable state. If nothing has changed for 30 milliseconds and the state differs from the previous stable state, we accept it; only the "pressed" edge (LOW) sends a command. This way, the bounce when you release the button doesn't create an extra command either.
  11. Building and sending the message. The number goes up by one and the state flips. esp_now_send(destination, bytes, length) puts the message in the send queue and returns immediately. ESP_OK only means "queued"; the real result arrives a few milliseconds later in onSent. esp_err_to_name turns an error code into a readable name (for example, ESP_ERR_ESPNOW_NOT_FOUND means the peer was never added).
Callback signatures in different versions (read online tutorials carefully)

Receive callback: in core 3.x the signature is void onRecv(const esp_now_recv_info_t *info, const uint8_t *data, int len), and the sender's MAC is in info->src_addr. In core 2.x it was void onRecv(const uint8_t *mac, const uint8_t *data, int len). Most tutorials online (even this lesson's video) use the 2.x version, and on core 3 they fail to compile with an invalid conversion error.

Send callback: in core 2.x and 3.0 to 3.2 the signature was void onSent(const uint8_t *mac_addr, esp_now_send_status_t status). Starting with core 3.3.0 (based on ESP-IDF 5.5) it became void onSent(const wifi_tx_info_t *info, esp_now_send_status_t status), and the destination MAC is in info->des_addr. If you get the error invalid conversion from 'void (*)(const uint8_t*, esp_now_send_status_t)', you are compiling old code on a new core. Check your core version in Tools › Board › Boards Manager. If your code has to work on both:

#if ESP_ARDUINO_VERSION >= ESP_ARDUINO_VERSION_VAL(3, 3, 0)
void onSent(const wifi_tx_info_t *info, esp_now_send_status_t status) {
#else
void onSent(const uint8_t *mac_addr, esp_now_send_status_t status) {
#endif
  Serial.println(status == ESP_NOW_SEND_SUCCESS ? "delivered" : "FAILED");
}
  1. Picking the signature at compile time. #if is a preprocessor directive: before compiling, only one of the two opening lines of the function is kept, based on the core version. The core itself defines the ESP_ARDUINO_VERSION macros. The function body is shared because we don't use the first parameter.
  2. The shared body. It only prints the status. If you need the MAC, read it from info->des_addr in the new branch and from mac_addr in the old one.

Code for board B (receiver)

#include <WiFi.h>
#include <esp_now.h>

const int LED_PIN = 4;

typedef struct {
  uint32_t seq;
  bool ledOn;
} CommandMsg;

CommandMsg incoming;
volatile bool gotMsg = false;

// Core 3.x signature: sender info + data + length
void onRecv(const esp_now_recv_info_t *info, const uint8_t *data, int len) {
  if (len != sizeof(CommandMsg)) return;   // wrong size? ignore it
  memcpy(&incoming, data, sizeof(incoming));
  gotMsg = true;                          // loop does the real work
}

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  WiFi.mode(WIFI_STA);
  while (!WiFi.STA.started()) delay(10);
  Serial.print("Receiver MAC: ");
  Serial.println(WiFi.macAddress());

  if (esp_now_init() != ESP_OK) {
    Serial.println("ESP-NOW init failed");
    while (true) delay(1000);
  }
  esp_now_register_recv_cb(onRecv);
}

void loop() {
  if (gotMsg) {
    gotMsg = false;
    digitalWrite(LED_PIN, incoming.ledOn ? HIGH : LOW);
    Serial.printf("Got #%lu -> LED %s\n", (unsigned long)incoming.seq, incoming.ledOn ? "ON" : "OFF");
  }
}
  1. The same message layout. An exact copy of the sender's struct, with the same order and the same types. If you swap the order of seq and ledOn in the sender but not here, the bytes are read in the wrong places and you get no error at all, just strange behavior. In big projects this struct lives in a shared .h file.
  2. A place for the message and a flag. incoming holds the latest message and gotMsg signals that a new one has arrived. volatile tells the compiler "this variable may be changed from somewhere else; read it from memory every time". The callback runs in another task (the Wi-Fi radio's task), not in loop. Without volatile, the compiler might cache the value and loop would never see it change.
  3. The receive callback. First we check the length, then copy the bytes into incoming and raise the flag. info carries details such as the sender's MAC (info->src_addr) and the signal strength (info->rx_ctrl->rssi). The length check keeps out incomplete messages and messages from other programs. Don't do heavy work (printing, digitalWrite, reading sensors) in the callback: Espressif's documentation says it runs in the high-priority Wi-Fi task, and making it slow disrupts the messages that come next. Stick to the pattern "set a flag in the callback, do the work in loop".
  4. Switching the radio on and printing the MAC. The same as the GetMac program. Printing the MAC from the receiver itself means that whenever you swap boards, you see the new address without any hassle.
  5. Starting ESP-NOW and registering the receive callback. The receiver doesn't need to add the sender as a peer. According to the documentation, unencrypted unicast messages and broadcast messages are received even without a peer. A peer is only needed for sending (and for receiving encrypted messages).
  6. Carrying out the command in loop. If the flag is up, we lower it, set the LED and print the result. An honest note: if two messages arrive very close together, the second one might be written into incoming while the first is still being read. For a hand-held remote this practically never happens; for fast data, people use a FreeRTOS queue (xQueueSend), which you learn in lesson 5.4.

Project 2: two-way messaging with acknowledgment and temperature

In project 1, board A only knew that B's radio had received the packet. But did the LED actually turn on? In project 2, after carrying out the command, B sends back a reply: the number of that same command, the real state of the LED, and its own room temperature. If A gets no reply within 500 milliseconds, it reports an error. This "request, reply, deadline" pattern (request/response + timeout) is the foundation of every reliable protocol.

#include <WiFi.h>
#include <esp_now.h>

uint8_t boardB[] = {0x24, 0x6F, 0x28, 0xAB, 0xCD, 0xEF};   // board B's MAC
const int BUTTON_PIN = 27;
const int STATUS_LED = 4;      // the course's status LED (+220 Ω)

typedef struct {
  uint32_t seq;
  bool ledOn;
} CommandMsg;

typedef struct {
  uint32_t seq;      // number of the command this reply belongs to
  bool ledOn;        // the real LED state on B
  float tempC;       // B's temperature (or NAN if the sensor failed)
} ReplyMsg;

CommandMsg cmd = {0, false};
ReplyMsg reply;
volatile bool gotReply = false;
bool waiting = false;
unsigned long sentAt = 0;
int lastReading = HIGH, stableState = HIGH;
unsigned long lastChange = 0;

void onSent(const wifi_tx_info_t *info, esp_now_send_status_t status) {
  if (status != ESP_NOW_SEND_SUCCESS) Serial.println("  radio: not delivered");
}

void onRecv(const esp_now_recv_info_t *info, const uint8_t *data, int len) {
  if (len != sizeof(ReplyMsg)) return;
  if (memcmp(info->src_addr, boardB, 6) != 0) return;   // only accept from B
  memcpy(&reply, data, sizeof(reply));
  gotReply = true;
}

void setup() {
  Serial.begin(115200);
  pinMode(BUTTON_PIN, INPUT_PULLUP);
  pinMode(STATUS_LED, OUTPUT);
  WiFi.mode(WIFI_STA);
  while (!WiFi.STA.started()) delay(10);
  if (esp_now_init() != ESP_OK) {
    Serial.println("ESP-NOW init failed");
    while (true) delay(1000);
  }
  esp_now_register_send_cb(onSent);
  esp_now_register_recv_cb(onRecv);
  esp_now_peer_info_t peer = {};
  memcpy(peer.peer_addr, boardB, 6);
  peer.channel = 0;
  peer.encrypt = false;
  esp_now_add_peer(&peer);
}

void sendCommand() {
  cmd.seq++;
  cmd.ledOn = !cmd.ledOn;
  digitalWrite(STATUS_LED, LOW);            // off until the ack arrives
  esp_now_send(boardB, (uint8_t *)&cmd, sizeof(cmd));
  Serial.printf("-> #%lu ledOn=%d\n", (unsigned long)cmd.seq, cmd.ledOn);
  waiting = true;
  sentAt = millis();
}

void loop() {
  int reading = digitalRead(BUTTON_PIN);
  if (reading != lastReading) { lastChange = millis(); lastReading = reading; }
  if (millis() - lastChange > 30 && reading != stableState) {
    stableState = reading;
    if (stableState == LOW) sendCommand();
  }

  if (gotReply) {
    gotReply = false;
    if (waiting && reply.seq == cmd.seq) {
      waiting = false;
      digitalWrite(STATUS_LED, HIGH);         // ack received
      Serial.printf("<- ack #%lu, LED on B is %s, temp %.1f C (%lu ms)\n",
                    (unsigned long)reply.seq, reply.ledOn ? "ON" : "OFF",
                    reply.tempC, millis() - sentAt);
    }
  }
  if (waiting && millis() - sentAt > 500) {   // half a second to reply
    waiting = false;
    Serial.println("!! no reply from B within 500 ms");
  }
}
  1. Board B's MAC and two pins. The button is on GPIO27 and the status LED is on GPIO4, the course's usual pins. The status LED is the same external LED + 220 Ω resistor you've used since lesson 2.2, so it works on every board. (Some boards also have a built-in LED on GPIO2, but the ESP32-DevKitC doesn't.)
  2. Two message layouts. CommandMsg (8 bytes) goes from A to B and ReplyMsg (12 bytes) goes from B to A. Because the two layouts have different sizes, the receiver can tell them apart from len. Bigger projects put a "message type" byte first.
  3. Program state. waiting means "I'm waiting for a reply", and sentAt is the send time, used to work out the deadline and the delay. These variables form a tiny "state machine": either we are waiting or we aren't. Without it, there's no way to know which command an incoming reply belongs to or when the deadline has passed.
  4. The send callback (core 3.3+). It only reports radio failures. Here our real acknowledgment is the reply from B's program, not the radio's ack, so we don't print successes and keep the Serial Monitor tidy.
  5. A receive callback that filters by sender. memcmp compares the six bytes of the sender's MAC with board B's MAC (0 means they match). Any other ESP32 nearby that sends ESP-NOW on this channel reaches this function too. Only trust messages from B.
  6. Registering both callbacks and the peer. A both sends and receives. One board can be a sender and a receiver at the same time; the radio switches between the two jobs automatically.
  7. sendCommand. Builds a new command, switches the status LED off, sends it, and starts the waiting clock. Putting this in its own function keeps loop readable, and later you can call it from somewhere else too (a timer, for example).
  8. Compact debounce. The same logic as project 1, this time with several statements on one line. The logic is identical; it's just written compactly to save space.
  9. Handling the reply. If we were waiting and the reply's seq matches the latest command, we accept the acknowledgment, switch the status LED on, and print the temperature and the round-trip time. Comparing seq stops us from accepting a late reply to an old command. The round-trip time is usually a few to a few tens of milliseconds (mostly the time it takes to read the DHT22 on B), and it shows how fast ESP-NOW is.
  10. The timeout. If 500 milliseconds pass with no reply, we stop waiting and report an error. In the wireless world, "no reply" is a normal situation (B is off, too far away, or the message got lost). A good program has a plan for it; in exercise 2, for example, you add retries yourself.

void loop() {
  if (!gotMsg) return;
  gotMsg = false;
  digitalWrite(LED_PIN, incoming.ledOn ? HIGH : LOW);

  if (!esp_now_is_peer_exist(senderMac)) {   // first time? add A to the address book

    memcpy(peer.peer_addr, senderMac, 6);
    peer.channel = 0;
    peer.encrypt = false;
    esp_now_add_peer(&peer);

  reply.seq = incoming.seq;
  reply.ledOn = incoming.ledOn;

  1. The DHT22 sensor on GPIO13. The same Adafruit library as in lesson 3.3. GPIO13 is the course's usual DHT22 pin and a safe one, and because the DHT22 is digital, it has no trouble running alongside the radio (which ties up ADC2).
  2. Two layouts, an exact copy of board A's. The order and types of the boxes must match A. If you write double instead of float on B, the size becomes 16 bytes and A (which expects 12 bytes) throws the message away because of its length check. Luckily, that's better than reading a wrong number!
  3. Saving the sender's MAC. Besides the message, we copy the sender's address from info->src_addr. This way B doesn't need to know board A's MAC in advance; it replies to whoever sent the command. (For more security, add a MAC filter like the one on A.)
  4. Carrying out the command. If no message has arrived, we return from loop; otherwise we set the LED. An early return avoids deeply nested ifs and makes the code easier to read.
  5. Adding A to the address book, the first time only. esp_now_is_peer_exist checks whether this MAC has already been added. To send the reply, A has to be a peer. Adding it twice gives the error ESP_ERR_ESPNOW_EXIST; this check prevents that. We do this in loop, not in the callback, so the callback stays short.
  6. Building and sending the reply. We put the command's seq, the LED state and the temperature in a ReplyMsg and send it to A. Echoing back the same seq lets A match the reply to the right command. If the sensor doesn't respond, NAN is sent and A prints nan, so the error isn't hidden.

Broadcasting

If you want one message to reach every ESP32 nearby (for example, "all lights off"), send it to the special address FF:FF:FF:FF:FF:FF. This address must also be added with esp_now_add_peer, like any other peer. Two important differences from one-to-one messages:

  • A broadcast message has no radio acknowledgment. The send callback usually reports success even if no receiver is switched on. So if confirmation matters, the receivers have to reply (as in project 2).
  • A broadcast message is not encrypted. Every ESP32 nearby receives it.
A new C++ library in core 3: ESP32_NOW.h

Besides the classic esp_now.h API (the one you learned in this lesson), Arduino core 3 has an object-oriented library called ESP_NOW (file ESP32_NOW.h). It has a global object ESP_NOW (ESP_NOW.begin(), ESP_NOW.getMaxDataLen() and so on), and for each peer you inherit from the ESP_NOW_Peer class and override its onReceive and onSent functions. Ready-made examples are in File › Examples › ESP_NOW (such as ESP_NOW_Broadcast_Master and ESP_NOW_Serial). We taught the classic API because 90% of the code online and the ESP-IDF documentation use it; once you understand it, you can learn the new library in an hour.

ESP-NOW and Wi-Fi together: the shared-channel rule

The ESP32 has only one radio, and at any moment it works on one channel (1 to 13 in Europe and most of the world, 1 to 11 in North America). When board B connects to a router (to send data to MQTT, for example), its radio has to move to the router's channel, say channel 6. Now if board A is still on channel 1, its messages never reach B.

An everyday example: radio frequencies

Two people are talking on walkie-talkies. If one of them switches to channel 6 to stay in touch with the base (the router) as well, the other one has to switch to channel 6 too, or they can't hear each other.

  2. Printing the channel. WiFi.channel() returns the radio's current channel, for example 6. You need this number for board A.
  3. ESP-NOW on the same channel. Now ESP-NOW works at the same time as Wi-Fi, on the router's channel. Wi-Fi and ESP-NOW share the radio; on the same channel they work together without any trouble.
const uint8_t ROUTER_CHANNEL = 6;   // the number board B printed

  1. The router's channel. The same number B printed. A isn't connected to the router, so it can't find out the channel by itself; we tell it.
  2. Switching the radio on and changing the channel. WiFi.setChannel (available in core 3) moves the radio to the channel you choose. Changing the channel only works while the radio is running; right after the waiting loop is the safest place for it.
  3. The rest as before. Because peer.channel = 0, the current channel (6) is used. If you put any number other than zero in the peer, it must exactly match the radio's current channel; otherwise sending fails with an error.
Trap: the router changes its channel

Many routers are set to "Auto Channel" and switch channels after a restart or when the airwaves get crowded. Then the ESP-NOW link suddenly drops. Two ways out: 1) Fix the channel in the router's settings (say, 6). 2) The more professional way: board A finds the router's network in setup with WiFi.scanNetworks() and reads its channel with WiFi.channel(i); you do this in exercise 3.

Coach's advice

With ESP-NOW you have two programs on two boards, and when it doesn't work you're tempted to change both at once. Don't. Always make sure first that the MAC is correct (from the receiver's own Serial output, not from memory), then prove the link works with the simplest possible program (project 1), and only then make it more complex. Label each board A or B, and mark each Serial Monitor window with the board it belongs to. And remember: "delivered" means the radio received it, not that the program acted on it. Wherever carrying out a command matters (a lock, a pump, a motor), ask for a reply from the program with a seq. That's the difference between a toy and a reliable system.

This is the complete receiver from project 1 (Receiver_OneWay.ino) with three small additions.

  if (len != sizeof(CommandMsg)) return;   // wrong size? ignore it
  memcpy(&incoming, data, sizeof(incoming));
  lastRssi = info->rx_ctrl->rssi;        // ★ negative; closer to 0 = stronger
  gotMsg = true;                          // loop does the real work

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  WiFi.mode(WIFI_STA);

    Serial.printf("Got #%lu -> LED %s, RSSI %d dBm\n", (unsigned long)incoming.seq,

  1. A shared variable for the RSSI. A global volatile int. The callback writes it and loop reads it. volatile tells the compiler that the value can change "behind its back" (in the Wi-Fi task), so it must really read it from memory every time.
  2. Read the signal strength of this packet. info->rx_ctrl holds the radio details of the received packet, and rssi is its strength in dBm. We only copy one number, so the callback stays short. The RSSI belongs to this packet, which is why it must be read here and not later in loop.
  3. Print it next to the message. The number, the LED state and the RSSI on one line. With the message number on the same line, you can spot gaps (lost messages) and the signal strength at the same moment.

A dBm scale is logarithmic: every 10 dB less is ten times less power. That's why the step from -60 to -90 dBm (a thousand times weaker) is where the links fall apart.

Full answer with explanation

Why seq must stay the same: if the first message did arrive and only its reply got lost, B must be able to tell it's the same command as before, so it doesn't carry it out a second time. In our project the command carries the absolute state ("LED on"), so repeating it happens to be harmless; but a command like "toggle" or "ring the bell once" would run twice. A command that does no harm when repeated is called "idempotent"; it's the same problem QoS 2 solves in MQTT. So B remembers the last seq it carried out; if the same seq comes again, it skips the action but still sends the reply, because the reply is probably what got lost.

Board A (project 2, with retries):

#include <WiFi.h>
#include <esp_now.h>

uint8_t boardB[] = {0x24, 0x6F, 0x28, 0xAB, 0xCD, 0xEF};   // board B's MAC
const int BUTTON_PIN = 27;
const int STATUS_LED = 4;      // the course's status LED (+220 Ω)

typedef struct {
  uint32_t seq;
  bool ledOn;
} CommandMsg;

typedef struct {
  uint32_t seq;      // number of the command this reply belongs to
  bool ledOn;        // the real LED state on B
  float tempC;       // B's temperature (or NAN if the sensor failed)
} ReplyMsg;

CommandMsg cmd = {0, false};
ReplyMsg reply;
volatile bool gotReply = false;
bool waiting = false;
unsigned long sentAt = 0;
int lastReading = HIGH, stableState = HIGH;
unsigned long lastChange = 0;
int tries = 0;                 // ★ how many times this command was re-sent

void onSent(const wifi_tx_info_t *info, esp_now_send_status_t status) {
  if (status != ESP_NOW_SEND_SUCCESS) Serial.println("  radio: not delivered");
}

void onRecv(const esp_now_recv_info_t *info, const uint8_t *data, int len) {
  if (len != sizeof(ReplyMsg)) return;
  if (memcmp(info->src_addr, boardB, 6) != 0) return;   // only accept from B
  memcpy(&reply, data, sizeof(reply));
  gotReply = true;
}

void setup() {
  Serial.begin(115200);
  pinMode(BUTTON_PIN, INPUT_PULLUP);
  pinMode(STATUS_LED, OUTPUT);
  WiFi.mode(WIFI_STA);
  while (!WiFi.STA.started()) delay(10);
  if (esp_now_init() != ESP_OK) {
    Serial.println("ESP-NOW init failed");
    while (true) delay(1000);
  }
  esp_now_register_send_cb(onSent);
  esp_now_register_recv_cb(onRecv);
  esp_now_peer_info_t peer = {};
  memcpy(peer.peer_addr, boardB, 6);
  peer.channel = 0;
  peer.encrypt = false;
  esp_now_add_peer(&peer);
}

void sendCommand() {
  cmd.seq++;
  cmd.ledOn = !cmd.ledOn;
  digitalWrite(STATUS_LED, LOW);            // off until the ack arrives
  esp_now_send(boardB, (uint8_t *)&cmd, sizeof(cmd));
  Serial.printf("-> #%lu ledOn=%d\n", (unsigned long)cmd.seq, cmd.ledOn);
  waiting = true;
  sentAt = millis();
  tries = 0;                                // ★ a new command: no retries yet
}

void loop() {
  int reading = digitalRead(BUTTON_PIN);
  if (reading != lastReading) { lastChange = millis(); lastReading = reading; }
  if (millis() - lastChange > 30 && reading != stableState) {
    stableState = reading;
    if (stableState == LOW) sendCommand();
  }

  if (gotReply) {
    gotReply = false;
    if (waiting && reply.seq == cmd.seq) {
      waiting = false;
      digitalWrite(STATUS_LED, HIGH);         // ack received
      Serial.printf("<- ack #%lu, LED on B is %s, temp %.1f C (%lu ms)\n",
                    (unsigned long)reply.seq, reply.ledOn ? "ON" : "OFF",
                    reply.tempC, millis() - sentAt);
    }
  }
  if (waiting && millis() - sentAt > 500) {   // half a second to reply
    if (tries < 3) {                          // ★ send the SAME cmd again (same seq)
      tries++;
      esp_now_send(boardB, (uint8_t *)&cmd, sizeof(cmd));
      Serial.printf("-> #%lu again (retry %d of 3)\n", (unsigned long)cmd.seq, tries);
      sentAt = millis();                      // a fresh 500 ms for this try
    } else {
      waiting = false;
      Serial.println("!! no reply from B after 3 retries");
    }
  }
}
  1. A retry counter. tries counts how many times the current command has been re-sent. It must be global, because the retries happen across many passes of loop, not in one go.
  2. A new command resets the counter. sendCommand() works as before and now also sets tries = 0. Only a real button press makes a new seq. Retries never call sendCommand(), because that would increase seq and flip ledOn.
  3. Time is up: try again. If fewer than 3 retries have been made, send the very same cmd bytes again and start a fresh 500 ms window. Same bytes means same seq and same ledOn. Restarting sentAt gives each try its own half second, so the whole attempt takes at most 4 × 500 ms = 2 seconds, and loop stays free (no delay), so the button still works.
  4. Only now report an error. After the third retry has also timed out, stop waiting and print the error once. A single lost packet is normal in radio; the user should only hear about it when something is really wrong.
  5. The ack check is unchanged. A reply is accepted only if its seq matches cmd.seq. A late reply to an old command can't be mistaken for a reply to the current one. The time shown is measured from the last try.

Practice project: a doorbell that knows it was heard

A wireless doorbell has one job: when someone presses the button at the door, the chime inside must ring. Cheap doorbells just send and hope. Yours will be smarter: the chime answers "I heard you", the button retries if the answer doesn't come, and if the chime is really unreachable, the button blinks an error so the visitor knows to knock. Along the way you solve a classic wireless puzzle: how to retry without ringing twice.

Requirements

  1. Board A (button): every debounced press sends a RING message with a new number (seq) to board B and prints it. Presses while A is still waiting for an answer are ignored (with a note).
  2. Board B (chime): every RING it receives is answered with an ACK carrying the same number, even if it has seen that number before.
  3. Board B: the chime (880 Hz for 300 ms, then 660 Hz for 400 ms, LED on while it sounds) plays only once per ring number. A repeat of the same number within 5 seconds is a retry: B prints a note and doesn't chime again.
  4. Board A: it waits 300 ms for the ACK. If none arrives, it resends the same number, up to 3 more times (4 sends in total). On an ACK it prints the try number and the total time and lights the LED solid for 1 second; after the fourth failed try it prints an error and blinks the LED 5 times quickly.
  5. Both boards use only millis() for their timing: no delay() in either loop().

Parts

  • Two ESP32 DevKitC boards with two USB cables (the pair from this lesson)
  • Board A: push button + LED with a 220 Ω resistor
  • Board B: passive buzzer; the LED + 220 Ω on GPIO4 is optional but makes testing easier

  2. A typed message. enum : uint8_t makes the two type values exactly one byte. With the 3 padding bytes, BellMsg is 8 bytes. The same layout serves both directions, and the receiver checks type after the length. B must have an identical copy.
  3. The radio's report. Only failures are printed. "Not delivered" tells you the radio got no MAC-level acknowledgment at all (B is off or out of range). Our real acknowledgment is B's ACK message.
  4. Receiving the ACK. Length, sender and type are checked; then the number is stored and the flag raised. The callback runs in the Wi-Fi task, so it stays short and leaves the thinking to loop.
  5. sendRing sends the current ring, unchanged. It counts the try and restarts the 300 ms clock. A retry must be byte-for-byte the same message, above all the same seq. That's what lets B recognize it.
  6. startRing: a new ring, a new number. If we're still waiting, the press is ignored. Otherwise the number goes up, the counters reset and the first send goes out. Ignoring presses while waiting keeps one ring "in flight" at a time, so an ACK always matches exactly one ring. Switching the LED off here cancels any leftover feedback from the previous ring.
  7. The debounced press. Identical to the lesson. Without it, one press could start a ring and a second "bounce" press would be ignored with a confusing message.
  8. The ACK arrived. Only an ACK for the ring we're waiting for counts. We print the try number and the total time, and light the LED for 1 second. A late ACK for an older ring (for example, one that arrived just after we gave up) is simply ignored because waiting is false or the number is different.
  9. Timeout: retry or give up. While tries is at most 3, send again (tries 2, 3 and 4); after that, stop waiting, print the error and schedule 10 blink steps.   10. LED feedback with millis. The solid light switches off after 1 second. The blink counter goes down every 100 ms; odd numbers mean on, even numbers mean off, so 10 steps are 5 blinks. unsigned long lastRingAt = 0;
int chimeStep = 0;                       // 0 = quiet, 1 = "ding", 2 = "dong"
unsigned long chimeAt = 0;

void onRecv(const esp_now_recv_info_t *info, const uint8_t *data, int len) {
  if (len != sizeof(BellMsg)) return;
  BellMsg m;
  memcpy(&m, data, sizeof(m));
  if (m.type != MSG_RING) return;
  incoming = m;
  memcpy(senderMac, info->src_addr, 6);  // reply to whoever rang
  gotRing = true;
}

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  ledcAttach(BUZZER_PIN, 2000, 8);       // LEDC drives the buzzer (lesson 3.2)
  WiFi.mode(WIFI_STA);
  while (!WiFi.STA.started()) delay(10);
  Serial.print("Chime MAC: ");
  Serial.println(WiFi.macAddress());
  if (esp_now_init() != ESP_OK) {
    Serial.println("ESP-NOW init failed");
    while (true) delay(1000);
  }
  esp_now_register_recv_cb(onRecv);
}

void loop() {
  if (gotRing) {
    gotRing = false;
    if (!esp_now_is_peer_exist(senderMac)) {   // first time: add A as a peer
      esp_now_peer_info_t peer = {};
      memcpy(peer.peer_addr, senderMac, 6);
      peer.channel = 0;
      peer.encrypt = false;
      esp_now_add_peer(&peer);
    }
    BellMsg ack = {MSG_ACK, incoming.seq};
    esp_now_send(senderMac, (uint8_t *)&ack, sizeof(ack));   // ALWAYS reply

    bool repeat = (incoming.seq == lastSeq) && (millis() - lastRingAt < 5000);
    if (repeat) {
      Serial.printf("RING #%lu again (a retry): ACK sent, no second chime\n",
                    (unsigned long)incoming.seq);
    } else {
      lastSeq = incoming.seq;
      lastRingAt = millis();
      Serial.printf("RING #%lu: ding-dong, ACK sent\n", (unsigned long)incoming.seq);
      ledcWriteTone(BUZZER_PIN, 880);    // "ding"
      digitalWrite(LED_PIN, HIGH);
      chimeStep = 1;
      chimeAt = millis();
    }
  }

  // the two-note chime, without delay()
  if (chimeStep == 1 && millis() - chimeAt >= 300) {
    ledcWriteTone(BUZZER_PIN, 660);      // "dong"
    chimeStep = 2;
    chimeAt = millis();
  } else if (chimeStep == 2 && millis() - chimeAt >= 400) {
    ledcWriteTone(BUZZER_PIN, 0);        // silence
    digitalWrite(LED_PIN, LOW);
    chimeStep = 0;
  }
}
  1. Buzzer and LED pins. GPIO25 for the passive buzzer (lesson 3.2) and GPIO4 for the LED. A passive buzzer can play two different notes, which makes the "ding-dong" possible; an active buzzer could only beep.
  2. The same layout as A. Same enum, same struct, same order. If the two copies ever differ, the length or type check quietly throws every message away.
  3. Memory for duplicates and for the chime. lastSeq and lastRingAt remember the last ring we chimed for; chimeStep and chimeAt drive the two notes. Remembering the last number is the whole trick for "retry without ringing twice".
  4. Receiving a RING. Checks, a copy of the message and of the sender's MAC, and a flag. B doesn't need to know A's MAC in advance; it answers whoever rang.
  5. ledcAttach for the buzzer. The same PWM hardware as lesson 3.2. ledcWriteTone does nothing on a pin that isn't attached.
  6. Always answer. Add A as a peer the first time, then send the ACK with the received number, before anything else. If the previous ACK was lost, A is asking again precisely because it didn't hear us. Staying silent for a repeat would make A give up although the bell rang.
  7. New ring or retry? Same number within 5 seconds means retry: print a note. Otherwise remember the number and time and start the first note. This makes the chime idempotent: doing the same request twice has the same effect as doing it once. The time window protects against A being reset and starting again at 1.
  8. The two notes with millis. After 300 ms switch to 660 Hz; after 400 ms more, silence and LED off. If the chime used delay(700), a retry arriving during the chime would wait, and A might time out and send yet another retry.
The lesson in three lines

ESP-NOW moves short messages (up to 250 bytes in v1) between ESP32s by MAC address, with no router, in a few milliseconds; read the MAC after Wi-Fi is on, and add the peer before sending. The message layout is an identical struct on both sides, sent and read with sizeof and memcpy; keep callbacks short and use the core 3 signatures (esp_now_recv_info_t, and from 3.3 on wifi_tx_info_t). "Delivered" is only the radio's confirmation; for certainty, build a reply with a seq and a timeout, and if one side is connected to a router, put everyone on the router's channel.
