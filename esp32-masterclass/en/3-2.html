A digital pin has only two states: 0 or 3.3 V. So how do you make an LED glow at "half brightness", or tell a motor "go to exactly 73 degrees"? The answer is a clever trick called PWM: switch the pin on and off so fast that the outside world only feels the "average". In this lesson you'll understand PWM from the ground up, work with the ESP32's dedicated PWM hardware (LEDC), and control a servo motor precisely.

🎯 After this lesson you can

  • Explain duty cycle, frequency and resolution with real numbers
  • Fade an LED smoothly up and down with ledcAttach and ledcWrite (core 3)
  • Recognize old core 2 code (ledcSetup) in online tutorials and translate it
  • Power an SG90 servo correctly and control it both with the ESP32Servo library and without it
  • Make sounds and melodies with a buzzer

What is PWM? On and off, very fast

PWM stands for Pulse Width Modulation. The name sounds scary, but the idea is simple: we switch the pin on and off thousands of times per second and only change the ratio of on-time to the total time. That ratio is called the duty cycle.

An example: a tap and a glass

Imagine a tap that has only two settings: fully open or fully closed. If you want a glass to fill "slowly", you open the tap for one second, close it for three seconds, and repeat. Overall, the glass fills at a quarter of the speed. That's exactly what PWM does, just with voltage and thousands of times per second.

With numbers: the average voltage

Average voltage = on-voltage × duty cycle.

25% duty: 3.3 × 0.25 ≈ 0.83V · 50% duty: 3.3 × 0.50 = 1.65V · 75% duty: 3.3 × 0.75 ≈ 2.48V.

If you put a multimeter on a PWM pin, it shows roughly these numbers, because a multimeter is slow too and takes an average. But remember: at any single instant the pin really is either 0 or 3.3 V.

Why does the LED look dimmer?

Unlike an incandescent bulb, an LED turns on and off extremely fast (in nanoseconds). So at 25% PWM, the LED really is fully lit for 25% of the time and completely off for the other 75%. The dimming happens in your eyes and brain: the human eye can't separate changes faster than about 50 to 100 per second, so it averages the light. It's the same effect that turns 24 still pictures per second into a "moving picture" at the cinema.

Why 5 kHz for an LED?

Below about 100 Hz you can see flicker, especially out of the corner of your eye or when you move your head. A phone camera records dark bands even at a few hundred hertz. 5000 Hz is high enough that neither your eye nor a camera notices anything, and still low enough to give good resolution (next section).

Frequency and resolution: a trade-off

Two numbers define a PWM signal:

  • Frequency: how many on/off periods happen every second (for example, 5000 Hz means each period lasts 0.2 ms).
  • Resolution: how many steps each period is divided into. 8 bits means 28 = 256 steps (duty from 0 to 255); 12 bits means 4096 steps (0 to 4095).

The LEDC hardware counts those steps with an internal clock. On the classic ESP32 that clock runs at 80 MHz, so every period needs 2bits clock ticks. The golden rule:

The frequency × steps rule

frequency × 2resolution ≤ 80,000,000 (for the classic ESP32 with its 80 MHz clock)

An example: a ruler and speed

Imagine you have only 80 million "ticks" to spend every second. If you split each period into 256 parts, you can fit a lot of periods into a second (high frequency). If you want each period to have 65,536 tiny parts, fewer periods fit. More resolution = lower frequency; always.

There's a lower frequency limit too

The LEDC clock divider has a limited range, so each resolution also has a minimum frequency. For example, a very low frequency combined with a very low resolution may be rejected. According to the documentation, if you need a low frequency, increase the resolution, not decrease it. For the jobs in this lesson (5 kHz and 50 Hz) there's nothing to worry about.

LEDC: the PWM factory inside the ESP32

The ESP32 doesn't use the CPU to generate PWM; it has a separate hardware block called LEDC (LED Control). Once you set the duty, LEDC produces the wave on its own and the CPU is free to do anything else. Despite its name, LEDC is also used for motors, servos and buzzers.

  • The classic ESP32 has 16 channels (two groups of 8, each group with 4 timers). That means up to 16 independent PWM pins at the same time. (The ESP32-S2 and ESP32-S3 have eight channels and the ESP32-C3 has six.)
  • Any GPIO that can be an output can do PWM. So GPIO34 to 39 (input-only) can't.
  • Channels with the same frequency and resolution share one timer. So if you have 5 LEDs at 5 kHz and 8 bits, they all use a single timer.

The core 3 API: just two main functions

Most tutorials written before 2024 use the core 2 API, which worked with channel numbers. If you copy that code, you'll get the error 'ledcSetup' was not declared in this scope. Here's the translation:

The biggest trap: both versions have a function called ledcWrite, but in the old version the first number was the channel and in the new one it's the pin. If you want to pick the channel yourself, core 3 has ledcAttachChannel(pin, freq, res, channel). Check your core version in the Arduino IDE under Tools › Board › Boards Manager (esp32 by Espressif Systems, version 3.x).

Project 1: a breathing LED

The same LED circuit as lesson 2.2: GPIO4 → 220 Ω resistor → LED → GND. No hardware changes are needed; we simply use PWM instead of digitalWrite.

// Breathing LED with LEDC
const int LED_PIN = 4;
const int PWM_FREQ = 5000;      // 5kHz: far above what the eye can notice
const int PWM_RES  = 8;         // 8 bits: duty from 0 to 255

void setup() {
  Serial.begin(115200);
  if (!ledcAttach(LED_PIN, PWM_FREQ, PWM_RES)) {
    Serial.println("ledcAttach failed!");
  }
}

void loop() {
  for (int duty = 0; duty <= 255; duty++) {   // slowly brighter
    ledcWrite(LED_PIN, duty);
    delay(8);
  }
  for (int duty = 255; duty >= 0; duty--) {   // slowly dimmer
    ledcWrite(LED_PIN, duty);
    delay(8);
  }
}
  1. Two PWM constants. A frequency of 5000 Hz and a resolution of 8 bits. 5000 × 256 = 1.28MHz is far below the 80 MHz limit. 256 steps are plenty for the eye, and giving these numbers names makes them easy to change later when you experiment.
  2. ledcAttach with error checking. Connects pin 4 to an LEDC channel with the settings above. If that fails (for example, the frequency and resolution combination is impossible), it returns false and we print a message. ! means "not". Checking the return value is a good habit: if one day you set PWM_RES to 14, you get a clear message instead of a dark LED and a lot of confusion. Notice that pinMode is no longer needed; ledcAttach makes the pin an output by itself.
  3. The brightening loop. Duty goes from 0 to 255, 8 milliseconds per step. 256 steps × 8 ms ≈ 2 seconds to reach full brightness; a slow pace that looks like breathing. Make the 8 smaller and it breathes faster.
  4. ledcWrite(pin, duty). Sets the duty in the hardware. From that moment LEDC produces the wave by itself until the next command. In core 3 the first number is the pin, not the channel. Don't mix this up with old code.
  5. The dimming loop. The reverse: from 255 down to 0. duty-- means "subtract one". The condition duty >= 0 (not > 0) makes the LED really reach zero and go completely dark.
Why does the first half of the breath look faster?

The human eye is much more sensitive to dim light than to bright light (its response is roughly logarithmic). So a change in duty from 10 to 20 is far more visible than from 210 to 220. For a more "natural" breath, use the square of the duty instead of the duty itself: ledcWrite(LED_PIN, duty * duty / 255);. This correction is called "gamma correction".

The hardware version: ledcFade

In the code above the CPU changes the duty step by step and is stuck in the delays. LEDC can do this job by itself:

const int LED_PIN = 4;

void setup() {
  ledcAttach(LED_PIN, 5000, 8);
}

void loop() {
  ledcFade(LED_PIN, 0, 255, 1500);   // the hardware fades up over 1.5 seconds
  delay(2000);                       // the CPU is free here; delay only keeps the example simple
  ledcFade(LED_PIN, 255, 0, 1500);   // and fades down over 1.5 seconds
  delay(2000);
}
  1. ledcFade(pin, start, end, milliseconds). Tells LEDC to raise the duty smoothly from 0 to 255 over 1500 milliseconds, and returns immediately. This function doesn't wait for the fade to finish. So in a real program, instead of delay you could read a button or answer Wi-Fi requests while the LED changes smoothly on its own.
  2. A delay longer than the fade. Wait 2000 ms so the fade (1500 ms) can finish and the LED stays at full brightness for half a second. If you start the next fade before the previous one has finished, the previous one is cut short. More advanced versions (ledcFadeWithInterrupt) can call a function of yours when the fade is done.

There's analogWrite too; how does it relate to LEDC?

On the Arduino Uno you use analogWrite(pin, 0..255) for PWM. The ESP32's core 3 has this function too, so Arduino code runs easily. Behind the scenes, the first time you call analogWrite it calls ledcAttach(pin, 1000, 8) by itself (default: 1000 Hz, 8 bits) and then calls ledcWrite. You can change these settings with analogWriteFrequency(pin, freq) and analogWriteResolution(pin, bits).

Which one should I use?

For quick, Arduino-compatible code: analogWrite. For full control over frequency and resolution, plus error checking: ledcAttach + ledcWrite. Just don't mix the two on the same pin. (Note: the name analogWrite is misleading; it isn't a true analog output, it's plain PWM. The real analog outputs are the DAC on GPIO25 and 26.)

Project 2: a potentiometer sets the LED brightness

The potentiometer goes on GPIO34 (as in lesson 3.1) and the LED on GPIO4. Here's a neat trick: the ADC gives a 12-bit number (0 to 4095), so if we set the PWM to 12 bits as well, we can hand that number to the LED directly, with no map.

// A potentiometer sets the LED brightness
const int POT_PIN = 34;
const int LED_PIN = 4;

void setup() {
  Serial.begin(115200);
  ledcAttach(LED_PIN, 5000, 12);      // 12 bits: 0 to 4095, same range as the ADC
}

void loop() {
  int raw = analogRead(POT_PIN);      // 0 to 4095
  ledcWrite(LED_PIN, raw);            // the same number, straight into PWM
  Serial.printf("raw=%d  duty=%d%%\n", raw, raw * 100 / 4095);
  delay(20);
}
  1. 12-bit PWM. 5 kHz with 4096 steps. 5000 × 4096 = 20.48MHz is under the 80 MHz limit. When the ADC and PWM have the same range, no conversion is needed and no resolution is thrown away.
  2. Read and write directly. The potentiometer's number becomes the duty. If you had set the PWM to 8 bits, you'd have to write map(raw, 0, 4095, 0, 255) or raw >> 4 (divide by 16). Writing 4095 to an 8-bit PWM is a common mistake: any number above 255 means "fully on", so the knob only does something in the first 6% of its travel.
  3. Show the percentage. raw * 100 / 4095 calculates the duty as a percentage. %% prints the % sign itself. Multiply first, then divide: if you divided first (raw / 4095 * 100), integer division would always give 0 (except at the very end of the range).
  4. A 20 ms pause. 50 updates per second are enough to feel "instant", and they don't flood the Serial Monitor.

Turn the potentiometer and watch the LED dim and brighten smoothly. You can try the Breathing_LED code on this same circuit too.

Servo motors: PWM for "angle"

A servo motor (like the small blue SG90) is a small DC motor, a gearbox, a built-in potentiometer and a control circuit, all packed into one case. You don't tell it "spin"; you tell it "go to 90 degrees and stay there". The internal circuit reads the current angle from its own potentiometer and turns the motor until it reaches the angle you asked for.

An example: a car with a self-driving steering wheel

You only say "steering wheel 30 degrees to the right". The driver (the internal circuit) looks at where the wheel is now, turns it, and stops when it gets there. If someone tries to force the wheel around, the driver pushes back. That's "feedback".

The servo's language: pulse width, not duty

A servo expects one pulse every 20 milliseconds (that's 50 times per second, 50 Hz). The width of that pulse sets the angle. For an SG90 in practice:

Datasheet numbers differ from reality

SG90 datasheets usually quote 1 to 2 milliseconds for full travel, but in practice that range only moves the arm about 90 degrees. Most makers and libraries use 0.5 to 2.4 milliseconds for 0 to 180 degrees. Every servo is a little different; if your servo "buzzes" at one of the two ends, the pulse has gone past its mechanical limit and you should narrow the range a little (see troubleshooting below).

Powering the servo: the most important part of this lesson

SG90 spec (approximate)Value
Operating voltage4.8 to 6 V (5 V is ideal)
TorqueAbout 1.8 kg·cm at 4.8 V
Current at restA few mA up to a few tens of mA

WiresBrown = GND · Red = +5 V · Orange = signal (on some servos: black = GND, red = +, white or yellow = signal)

The ESP32's 3.3 V signal is enough to command an SG90. But the servo's power must never come from the 3V3 pin or from a GPIO. There are two ways to do it:

Method 1 (only for one small servo and for testing): the board's 5V pin

The DevKitC's 5V pin is connected almost directly (through a diode on some boards) to the USB 5 V. On 30-pin boards (such as the DOIT DevKit V1) the same pin is labeled VIN; wherever you see 5V in this course, use VIN on those boards. A computer's USB port usually supplies 500 mA, and the ESP32 itself uses 100 to 250 mA (with Wi-Fi). One unloaded SG90 usually fits within that, but the current spike when it starts moving makes the voltage dip. (You saw the complete power path from USB to the pins, and the current budget, in lesson 1.4; lesson 3.4 shows with numbers why you can't power a power-hungry load straight from the board.)

Method 2 (the right, reliable way): a separate supply + a common ground

For more than one servo, a servo under load, or any serious project, power the servo from a separate 5 V supply (a 5 V 2 A adapter, or a power bank). The supply's ground and the ESP32's ground must be connected together.

Why is a common ground essential?

A voltage is always measured "relative to some point". The ESP32's 3.3 V signal means "3.3 V above the ESP32's own GND". If the servo's GND isn't connected to the ESP32's GND, the servo has no reference point to measure that 3.3 V against, and the signal means nothing to it. It's like saying "three floors up" without saying which building.

Brownout: when the servo resets your board

If the ESP32 resets every time the servo moves and the Serial Monitor shows Brownout detector was triggered, the servo's current spike has pulled the voltage so low that the ESP32's built-in protection reset the chip to prevent unpredictable behavior. The fix: method 2 (a separate supply), plus a 470 to 1000 µF electrolytic capacitor (rated 10 V or more) between the servo's + and −, close to the servo itself (the capacitor's negative leg to GND). Like a small reservoir, the capacitor supplies the short current bursts.

The ESP32Servo library

Arduino's well-known Servo library doesn't work on the ESP32. Instead we use ESP32Servo, which has the same commands and uses LEDC behind the scenes.

  1. Install: in the Arduino IDE, open Sketch › Include Library › Manage Libraries…, search for ESP32Servo and install the library with exactly that name, ESP32Servo by Kevin Harrington, John K. Bennett (version 3.x or newer, which works with core 3; versions 1.x and 0.x give compile errors on core 3). This library has no other dependencies. Don't install other libraries with similar names (such as ServoESP32); their commands are different.
  2. In Wokwi: open the Library Manager tab, click + and add ESP32Servo. (Wokwi saves this in a file called libraries.txt.)
#include <ESP32Servo.h>

Servo myServo;                  // one servo object
const int SERVO_PIN = 32;

void setup() {
  Serial.begin(115200);
  myServo.setPeriodHertz(50);             // standard servo: 50Hz
  myServo.attach(SERVO_PIN, 500, 2400);   // pulse 0.5ms to 2.4ms
}

void loop() {
  for (int angle = 0; angle <= 180; angle++) {
    myServo.write(angle);
    delay(15);                  // give the servo time to move
  }
  for (int angle = 180; angle >= 0; angle--) {
    myServo.write(angle);
    delay(15);
  }
}
  1. include. Adds the library's code to the program. <...> means "look in the libraries folder". If you see a No such file or directory error, the library isn't installed.
  2. Creating an object. Servo myServo; creates a "virtual servo" called myServo. Every real servo needs its own object. For two servos: Servo s1, s2;. An object is like a TV remote that is paired with only one TV.
  3. setPeriodHertz(50). A frequency of 50 Hz (a 20 ms period). The library's default is 50 anyway, but writing it out makes the code clearer. Some digital servos also accept higher frequencies (for example 330 Hz).
  4. attach(pin, min, max). Connects the servo to GPIO32 and says that 0 degrees = 500 microseconds and 180 degrees = 2400 microseconds. The library's default is 544 to 2400. We wrote the SG90 range out explicitly so that if you have a different servo, you know where to change it. GPIO32 is a safe, general-purpose output, and in this course it's the fixed pin for a servo (or a NeoPixel data line), so the button, LED and potentiometer can stay where they are.
  5. Sweep from 0 to 180. write(angle) takes the angle in degrees and the library converts it into a pulse width. 15 ms between degrees gives the servo time to move; 181 steps × 15 ms ≈ 2.7 seconds for half a turn. The SG90's top speed is about 0.1 seconds per 60 degrees, so don't make it faster for no reason.
  6. Back from 180 to 0. The same loop in reverse. A smooth back-and-forth movement causes the smallest current spikes. Jumping suddenly from 0 to 180 draws the most current and is the most likely to cause a brownout.

Without a library: a servo is just PWM (demystified)

The library isn't magic. Let's do the math ourselves. At 50 Hz with 16-bit resolution, one period is 20,000 microseconds and it's divided into 65,536 steps:

Working out the duty for a servo

duty = pulse width (µs) × 65536 ÷ 20000

0 degrees: 500 × 65536 ÷ 20000 ≈ 1638 · 90 degrees: 1450 × 65536 ÷ 20000 ≈ 4751 · 180 degrees: 2400 × 65536 ÷ 20000 ≈ 7864.

(90 degrees is halfway between 500 and 2400, which is 1450 microseconds, close to the standard 1.5 ms.) So even in the extreme case the servo only sees about 12% duty; the rest of the period is LOW.

// A servo without a library: just LEDC and a little math
const int SERVO_PIN = 32;
const int FREQ = 50;            // 50Hz = one pulse every 20ms
const int RES  = 16;            // 16 bits: 0 to 65535
const int MIN_US = 500;         // pulse for 0 degrees
const int MAX_US = 2400;        // pulse for 180 degrees

uint32_t usToDuty(int us) {
  return (uint32_t)us * 65536UL / 20000UL;   // the pulse's share of 20000 microseconds
}

void writeAngle(int angle) {
  angle = constrain(angle, 0, 180);
  int us = map(angle, 0, 180, MIN_US, MAX_US);
  ledcWrite(SERVO_PIN, usToDuty(us));
  Serial.printf("angle=%3d  pulse=%4dus  duty=%lu\n", angle, us, (unsigned long)usToDuty(us));
}

void setup() {
  Serial.begin(115200);
  ledcAttach(SERVO_PIN, FREQ, RES);
}

void loop() {
  const int angles[] = {0, 90, 180, 90};
  for (int i = 0; i < 4; i++) {
    writeAngle(angles[i]);
    delay(1000);
  }
}
  1. Servo parameters. 50 Hz, 16 bits and the pulse range. 50 × 65536 ≈ 3.3MHz, far below the limit. 16-bit resolution means each step is about 0.3 microseconds; with 8 bits each step would be 78 microseconds and we'd have only about 24 steps between 0 and 180 degrees (jerky, step-by-step movement).
  2. Converting microseconds to duty. The same formula as above. (uint32_t) makes the number 32-bit before the multiplication, and UL means "an unsigned long constant". 2400 × 65536 = 157,286,400 doesn't fit in the 16-bit int that some boards use. Make it a habit to do large multiplications explicitly in a big enough type. Multiply first, then divide, so you don't lose precision.
  3. constrain(value, low, high). Keeps the angle between 0 and 180. If you pass 250 by mistake, without this line the pulse goes out of the allowed range, the servo pushes against its mechanical end stop, draws a lot of current and might strip its gears.
  4. Angle → microseconds → duty → hardware. map turns the angle into a pulse width and usToDuty turns that into a duty. This is exactly what myServo.write() does behind the scenes.
  5. ledcAttach at 50 Hz and 16 bits. The same function we used for the LED, just with different numbers. PWM is one tool; the LED and the servo are simply two ways of using it.
  6. A list of angles. An array of four values that are played in order, one second each. An array is several values of the same type stored one after another; angles[0] is the first one. This is cleaner than writing writeAngle four times.
angle= 0 pulse= 500us duty=1638 angle= 90 pulse=1450us duty=4751 angle=180 pulse=2400us duty=7864 angle= 90 pulse=1450us duty=4751

Project 3: a potentiometer sets the servo angle

The circuit: the same "method 1" diagram above (servo on GPIO32, potentiometer on GPIO34). Turn the knob and the servo arm turns with it; like a simple robot arm.

#include <ESP32Servo.h>

const int POT_PIN = 34;
const int SERVO_PIN = 32;
Servo myServo;
int lastAngle = -1;             // no angle written yet

void setup() {
  Serial.begin(115200);
  myServo.setPeriodHertz(50);
  myServo.attach(SERVO_PIN, 500, 2400);
}

void loop() {
  long sum = 0;
  for (int i = 0; i < 16; i++) sum += analogRead(POT_PIN);   // average of 16 samples
  int raw = sum / 16;
  int angle = map(raw, 0, 4095, 0, 180);

  if (abs(angle - lastAngle) >= 2) {    // deadband: ignore 1-degree jitter
    myServo.write(angle);
    lastAngle = angle;
    Serial.printf("raw=%d  angle=%d\n", raw, angle);
  }
  delay(20);
}
  1. Remembering the last angle, starting at −1. −1 is never a real angle, so on the first pass of loop the condition is guaranteed to be true and the servo moves to where the knob is.
  2. An average of 16 samples. The same technique as lesson 3.1, this time in three lines. Without averaging, ADC noise keeps changing the angle by ±1 degree and the servo "jitters" and buzzes.
  3. Convert to an angle. 0 to 4095 → 0 to 180.
  4. A deadband. Only move the servo when the angle has changed by at least 2 degrees. abs is the absolute value (it turns a negative number positive). Even with averaging, the number sometimes flips between two neighboring angles. A deadband is a close cousin of the hysteresis from the previous lesson: ignore tiny, meaningless changes. A bonus: the Serial Monitor only prints when something has really changed.
  5. A 20 ms pause. The servo only sees a new pulse every 20 ms; updating faster is pointless.

Before you run it, add the ESP32Servo library from Wokwi's Library Manager tab, or you'll get a compile error. In the simulator the servo is powered straight from 5V and there's no current problem; that problem only exists in the real world, so take the power section seriously. Try the Servo_Sweep and Servo_Raw_LEDC code on this same circuit too.

Bonus: sound with a buzzer and ledcWriteTone

There are two kinds of buzzer: active (it has a built-in oscillator and beeps at one fixed pitch when you apply a steady voltage) and passive (it's like a tiny speaker, and it only makes sound when you feed it a square wave). To play different notes you need a passive buzzer. The PWM frequency is the pitch (the note): 440 Hz = the note A.

If you have an active buzzer

An active buzzer needs no PWM at all: digitalWrite(pin, HIGH) makes it beep and LOW makes it stop, always at the same pitch, like a microwave's beep. That makes it perfect for simple alarms. Two cautions: many active buzzers are rated for 5 V and draw about 30 mA, which is more than a GPIO should supply, so use a 3.3 V type or drive it through a transistor (lesson 3.4); and ledcWriteTone on an active buzzer only gives a rough crackle. How to tell them apart: an active buzzer usually has a sealed black bottom and a sticker on top, and it beeps when you connect it straight to 3.3 V; a passive one only clicks.

// C major scale on a passive buzzer
const int BUZZER_PIN = 25;
const int notes[] = {262, 294, 330, 349, 392, 440, 494, 523};  // C D E F G A B C

void setup() {
  ledcAttach(BUZZER_PIN, 2000, 10);   // attach the pin to LEDC first
}

void loop() {
  for (int i = 0; i < 8; i++) {
    ledcWriteTone(BUZZER_PIN, notes[i]);   // 50% square wave at this frequency
    delay(250);
  }
  ledcWriteTone(BUZZER_PIN, 0);            // zero frequency = silence
  delay(2000);
}
  1. An array of note frequencies. The eight notes of the C major scale in hertz (rounded). Every note has a specific frequency. The high C (523) is almost exactly twice the low C (262); one octave means doubling the frequency.
  2. Attach before playing a tone. In core 3, ledcWriteTone does nothing on a pin that isn't attached and returns zero. The initial frequency and resolution don't matter; ledcWriteTone changes them itself for every note.
  3. Play each note for 250 ms. ledcWriteTone produces a 50% square wave at the note's frequency. Here the duty stays fixed at 50% and the frequency changes; the opposite of the LED, where the frequency was fixed and the duty changed.
  4. Zero frequency = silence. According to the documentation, a frequency of zero sets the duty to zero. Without this line the buzzer would play the last note forever.
A shortcut: tone()

Core 3 also has Arduino's familiar tone(pin, freq, duration) and noTone(pin). They're enough for simple beeps. We learned ledcWriteTone so you can see that a buzzer is just another use of LEDC.

Coach's advice

Most of the "broken servos" my students bring me are perfectly fine; the problem is power. Before you change a single line of code, ask three questions: Where does the servo's power come from? Are the grounds shared? How far does the 5V drop while it moves (check with a multimeter)? And one more rule: never copy PWM code from the internet without first checking whether it contains ledcSetup. Core 3 means ledcAttach. These two habits will save you weeks.

PWM with 8-bit resolution and a duty of 64 on a 3.3 V pin. Roughly what is the average voltage?

  2. 1.65 V

  4. 3.3 V
64 ÷ 256 = 25% and 3.3 × 0.25 ≈ 0.83V.

  2. 5 kHz with 12 bits
  3. 50 Hz with 16 bits
  4. 20 kHz with 10 bits

  2. digitalWrite(4, 128);
  3. ledcWrite(4, 128);
  4. ledcAttach(4, 5000, 8); ledcWrite(4, 128);
In core 3, first ledcAttach(pin, freq, res) and then ledcWrite(pin, duty); both use the pin number.

  1. 0.5 milliseconds
  2. About 1.45 milliseconds
  3. 2.4 milliseconds
  4. 20 milliseconds
The middle of the range: (500 + 2400) ÷ 2 = 1450µs, close to the standard 1.5 ms.

You've powered the servo from a separate 5 V adapter and the signal wire goes to GPIO32, but the servo doesn't move at all. What's the most likely problem?

Exercise 1: breathing without delay

Rewrite the breathing LED program with millis and no delay at all: every 8 milliseconds the duty changes by one in the current direction, and the direction reverses at 0 and 255. Then add the button from lesson 3.1 (GPIO27) to pause and resume the breathing.

Hint

You need two variables: int duty = 0; and int step = 1;. Each time it's time for a step: duty += step; if (duty <= 0 || duty >= 255) step = -step;. || means "or".

What should you see?

This program prints nothing; watch the LED:

  • The LED fades up smoothly in about 2 seconds and down in about 2 seconds: 255 steps × 8 ms ≈ 2.04 s each way, so each "breath" takes about 4.1 s. In 20 seconds you see roughly 5 full breaths.
  • Press the button (GPIO27) mid-breath: the light freezes at its current brightness (it doesn't go off, and it doesn't go to full).
  • Press again: breathing carries on from the same point in the same direction, with no jump.
  • Each press acts only once. If one press makes the breathing stop for a moment and then start again, the debouncing isn't right.
Full answer with explanation 
const int LED_PIN = 4;
const int BUTTON_PIN = 27;
int duty = 0, step = 1;
unsigned long lastStep = 0;
bool paused = false;
int stableState = HIGH, lastReading = HIGH;
unsigned long lastChangeTime = 0;

void setup() {
  pinMode(BUTTON_PIN, INPUT_PULLUP);
  ledcAttach(LED_PIN, 5000, 8);
}

void loop() {
  unsigned long now = millis();

  // the button (debounced), as in lesson 3.1
  int reading = digitalRead(BUTTON_PIN);
  if (reading != lastReading) { lastChangeTime = now; lastReading = reading; }
  if (now - lastChangeTime > 30 && reading != stableState) {
    stableState = reading;
    if (stableState == LOW) paused = !paused;
  }

  // breathing: one step every 8 ms, unless paused
  if (!paused && now - lastStep >= 8) {
    lastStep = now;
    duty += step;
    if (duty <= 0 || duty >= 255) step = -step;
    ledcWrite(LED_PIN, duty);
  }
}
  1. The breathing state. duty is the current brightness and step is the direction (+1 up, −1 down). Instead of two for loops, we have a small "state machine" that takes just one step on each pass of loop.
  2. Pause and button memory. paused says whether breathing is on hold; the other three are the debouncing variables from lesson 3.1. The button and the breathing are two separate jobs, each with its own variables.
  3. The button, debounced. The same logic as Toggle_Debounce in lesson 3.1, but each confirmed press flips paused. We toggle only on the press (LOW), not on the release, so one press = one pause or resume.
  4. One step every 8 ms, unless paused. The duty moves by one and the direction reverses at both ends. Exactly the millis pattern from lesson 3.1; loop never waits, so no button press is lost. While paused, the LED simply keeps its current brightness.

Click the green button in the simulator to pause the breathing and resume it.

Exercise 2: a light meter needle

Combine the night-light circuit from lesson 3.1 (LDR on GPIO35) with the servo on GPIO32. Make the servo act like the needle of a light meter, showing the light level between 0 (dark) and 180 (bright).

Hint

In our circuit, dark = high voltage. So write the map the other way round: map(mv, 300, 3100, 180, 0), then constrain. Don't forget the 2-degree deadband.

What should you see?

A sample output (the millivolt numbers depend on your room's light, but the link between millivolts and angle must be exactly this):

LDR=1700 mV  angle=90
LDR=2400 mV  angle=45
LDR=2950 mV  angle=10
LDR=650 mV  angle=158
  • Check the maths: 1700 mV must give 90 degrees, 2400 mV must give 45 and 2950 mV must give 10. If your numbers don't follow this rule, the map is wrong.
  • Cover the LDR with your hand: the needle moves toward 0. Shine your phone's flashlight on it: toward 180.
  • While the light is steady, no new lines are printed and the servo is quiet (the deadband is working).
  • The angle never goes below 0 or above 180, even in total darkness or very strong light.
Full answer with explanation 
#include <ESP32Servo.h>

const int LDR_PIN = 35;                 // middle of the LDR divider (lesson 3.1)
const int SERVO_PIN = 32;
Servo needle;                           // the servo is our "needle"
int lastAngle = -1;                     // no angle written yet

uint32_t readLdrMv() {
  uint32_t sum = 0;
  for (int i = 0; i < 8; i++) sum += analogReadMilliVolts(LDR_PIN);
  return sum / 8;                       // average of 8 samples
}

void setup() {
  Serial.begin(115200);
  needle.setPeriodHertz(50);
  needle.attach(SERVO_PIN, 500, 2400);
}

void loop() {
  uint32_t mv = readLdrMv();
  int angle = map(mv, 300, 3100, 180, 0);   // dark = high voltage = 0 degrees
  angle = constrain(angle, 0, 180);

  if (abs(angle - lastAngle) >= 2) {        // 2-degree deadband
    needle.write(angle);
    lastAngle = angle;
    Serial.printf("LDR=%lu mV  angle=%d\n", (unsigned long)mv, angle);
  }
  delay(50);
}
  1. Two familiar parts. The LDR on GPIO35 from lesson 3.1 and the servo on GPIO32 from this lesson. lastAngle = -1 means "nothing written yet". Every angle from 1 to 180 is at least 2 away from −1, so the first reading is written straight away. The only exception is 0 (very dark at start-up); then the servo simply stays where it was.
  2. An average of 8 samples. Exactly the function from the night light. A shaky needle is hard to read; averaging reduces the ADC noise before it reaches the servo.
  3. A reversed map, then constrain. 300 mV (bright) → 180 degrees and 3100 mV (dark) → 0 degrees. For example, 1700 mV gives exactly 90 degrees. In our circuit darkness raises the voltage, so we swapped 180 and 0. map doesn't limit its output (100 mV, for example, becomes 192), so constrain is needed to keep impossible commands away from the servo.
  4. A 2-degree deadband. The servo only moves, and a line is only printed, when the angle changes by at least 2 degrees. The same trick as Pot_Servo: without it the servo keeps twitching one degree back and forth and buzzing.

Exercise 3: a siren

Use the buzzer to build a siren whose frequency glides smoothly from 600 to 1200 Hz in 1 second and back again. Then think: why couldn't you do this by changing the duty?

Hint

One for loop from 600 to 1200 in steps of 10 with delay(8), and one loop in reverse. Pitch depends on frequency; the duty only changes the loudness and the "color" of the sound a little.

What should you see?

You hear a police-style siren ("wee-oo, wee-oo"), about once per second. In the Serial Monitor:

One cycle: 961 ms
One cycle: 961 ms
One cycle: 960 ms
  • The number should be close to 960 (120 steps × 8 ms); a millisecond or two more is normal, because ledcWriteTone itself takes a little time.
  • The sound glides up and down smoothly, with no audible steps and no pause at either end.
  • If all you hear is a click, your buzzer is active, not passive (see the active buzzer box in this lesson).

The answer to the thinking question: pitch (how high or low a sound is) is how many times per second the buzzer's disc moves back and forth; that is the frequency. Duty only changes the width of each pulse at the same fixed frequency. The number of pulses per second stays the same, so the note stays the same; only the loudness and the "color" of the sound change a little (50% duty gives the loudest sound).

Full answer with explanation 
// Siren: 600 -> 1200 Hz and back, about once a second
const int BUZZER_PIN = 25;

void setup() {
  Serial.begin(115200);
  ledcAttach(BUZZER_PIN, 2000, 10);
}

void loop() {
  unsigned long start = millis();
  for (int f = 600; f < 1200; f += 10) {    // up: 600, 610 ... 1190 (60 steps)
    ledcWriteTone(BUZZER_PIN, f);
    delay(8);
  }
  for (int f = 1200; f > 600; f -= 10) {    // down: 1200, 1190 ... 610 (60 steps)
    ledcWriteTone(BUZZER_PIN, f);
    delay(8);
  }
  Serial.printf("One cycle: %lu ms\n", millis() - start);
}
  1. The same buzzer set-up. A passive buzzer on GPIO25 and ledcAttach, as in the melody program. The pin must be attached to LEDC before ledcWriteTone.
  2. Going up. The frequency goes from 600 to 1190 in 10 Hz steps, 8 ms each: 60 steps × 8 ms = 480 ms. A 10 Hz step is small enough that your ear doesn't hear the stairs; the sound glides.
  3. Coming back, and measuring. From 1200 down to 610: again 60 steps and 480 ms. At the end, the time for one full cycle is printed. We wrote the conditions with < and > (not ≤ and ≥) so 600 and 1200 aren't played twice in a row. In total 120 steps × 8 ms = 960 ms, about one second; printing the time is how you prove it yourself.

The lesson in three lines

PWM means switching on and off fast with a variable duty; average voltage = 3.3 × duty, and the classic ESP32 rule is frequency × 2bits ≤ 80MHz. In core 3 you only need ledcAttach(pin, freq, res) and ledcWrite(pin, duty); ledcSetup code belongs to core 2. A servo wants a 50 Hz pulse about 0.5 to 2.4 ms wide (ESP32Servo or the 16-bit math by hand), and its power must come from a 5 V supply that can deliver enough current, with a common ground, never from 3V3.
