Wi-Fi برای وصل شدن به مودم و اینترنت عالی است؛ ولی اگر مودمی در کار نباشد چه؟ در ماشین، در کوه، یا وقتی فقط می‌خواهی با گوشی که در دستت است، یک وسیله را در همان اتاق کنترل کنی. اینجا نوبت بلوتوث است. ESP32 دو نوع بلوتوث دارد و در این درس هر دو را می‌سازی: اول یک «سیم سریال بی‌سیم» با بلوتوث کلاسیک، بعد یک دستگاه BLE حرفه‌ای که مثل ساعت‌های هوشمند با گوشی حرف می‌زند.

🎯 بعد از این درس می‌توانی

  • فرق بلوتوث کلاسیک و BLE را با عدد توضیح بدهی و بدانی کدام برد کدام را دارد
  • با BluetoothSerial از گوشی اندرویدی فرمان متنی بفرستی و LED را کنترل کنی
  • مفاهیم GATT (سرور، سرویس، characteristic، UUID، read/write/notify) را بفهمی
  • یک سرور BLE با characteristic نوشتنی و notify بسازی و با nRF Connect آزمایشش کنی

🧰 پیش‌نیاز و وسایل

  • درس ۲.۳ (LED) و درس ۴.۱ (رویدادها و millis)
  • برد ESP32 معمولی (DevKitC یا مشابه). برای بخش الف، ESP32-C3 یا S3 کار نمی‌کند
  • یک LED و مقاومت ۲۲۰ اهم
  • گوشی اندرویدی با اپ رایگان Serial Bluetooth Terminal (نوشته Kai Morich) و اپ رایگان nRF Connect (شرکت Nordic، برای اندروید و آیفون)

شبیه‌ساز Wokwi رادیوی بلوتوث را شبیه‌سازی نمی‌کند (نه Classic و نه BLE؛ این قابلیت در فهرست درخواست‌های Wokwi هنوز باز است). کد ممکن است آنجا کامپایل شود ولی هیچ گوشی‌ای نمی‌تواند به آن وصل شود. پس این درس Wokwi ندارد و به برد واقعی و گوشی نیاز داری.

بلوتوث از صفر: دو زبان متفاوت با یک اسم

«بلوتوث» در واقع اسم دو فناوری است که هر دو روی همان فرکانس ۲٫۴ گیگاهرتز (مثل Wi-Fi) کار می‌کنند، ولی زبانشان کاملا فرق دارد و مستقیم با هم حرف نمی‌زنند:

  • بلوتوث کلاسیک (Bluetooth Classic یا BR/EDR): نسخه قدیمی‌تر، برای جریان پیوسته داده. هدفون، اسپیکر، هندزفری ماشین و انتقال فایل بین گوشی‌های قدیمی.
  • بلوتوث کم‌مصرف (Bluetooth Low Energy یا BLE): از سال ۲۰۱۰ (بلوتوث ۴٫۰). برای بسته‌های کوچک داده با مصرف خیلی کم. ساعت و دستبند هوشمند، ترازوی هوشمند، سنسور دما، ردیاب کلید.
مثال از زندگی روزمره: تماس تلفنی در برابر پیامک

بلوتوث کلاسیک مثل تماس تلفنی است: خط باز می‌ماند و دو طرف پیوسته حرف می‌زنند؛ برای صدا عالی است ولی باتری را می‌خورد. BLE مثل پیامک است: بیشتر وقت‌ها ساکت است و هر چند وقت یک پیام کوتاه می‌فرستد؛ باتری سکه‌ای یک سنسور BLE ممکن است ماه‌ها و حتی سال‌ها دوام بیاورد.

بخش الف: بلوتوث کلاسیک، سیم سریال بی‌سیم

کتابخانه داخلی BluetoothSerial کاری می‌کند که ESP32 برای گوشی مثل یک «پورت سریال» دیده شود؛ همان Serial Monitor، ولی بدون سیم. هر چه گوشی بفرستد، ESP32 با SerialBT.read() می‌خواند و هر چه ESP32 با SerialBT.println() بنویسد، روی صفحه گوشی ظاهر می‌شود. پروفایلی که این کار را انجام می‌دهد SPP (Serial Port Profile) نام دارد.

آیفون این بخش را پشتیبانی نمی‌کند

iOS به اپ‌ها اجازه نمی‌دهد با پروفایل SPP به دستگاه‌های بلوتوث کلاسیکی که تأییدیه ویژه اپل (MFi) ندارند وصل شوند. پس با آیفون اپی برای این بخش پیدا نمی‌کنی. اگر آیفون داری، این بخش را بخوان تا مفهوم را یاد بگیری و آزمایش عملی را در بخش BLE انجام بده؛ BLE روی آیفون کاملا کار می‌کند.

#include <BluetoothSerial.h>

// اگر برد تو C3 یا S3 است، این خط جلوی کامپایل را می‌گیرد (Classic ندارند)
#if !defined(CONFIG_BT_SPP_ENABLED)
#error "Bluetooth Classic (SPP) is only available on the original ESP32"
#endif

BluetoothSerial SerialBT;           // «پورت سریال بی‌سیم»
const int LED_PIN = 4;
bool ledOn = false;
String line = "";                   // حروف رسیده را اینجا جمع می‌کنیم

void handleCommand(String cmd) {
  cmd.trim();                       // فاصله و \r و \n اضافه را پاک کن
  cmd.toLowerCase();                // "ON" و "On" هم قبول شود
  if (cmd.length() == 0) return;    // خط خالی را نادیده بگیر

  Serial.printf("Command: [%s]\n", cmd.c_str());
  if (cmd == "on") {
    ledOn = true;
    SerialBT.println("OK: LED is ON");
  } else if (cmd == "off") {
    ledOn = false;
    SerialBT.println("OK: LED is OFF");
  } else if (cmd == "status") {
    SerialBT.println(ledOn ? "LED is ON" : "LED is OFF");
  } else {
    SerialBT.println("Unknown command. Use: on / off / status");
  }
  digitalWrite(LED_PIN, ledOn ? HIGH : LOW);
}

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  if (!SerialBT.begin("ESP32-LED")) {           // اسمی که گوشی می‌بیند
    Serial.println("Bluetooth init failed!");
    while (true) delay(1000);                   // بدون بلوتوث ادامه نمی‌دهیم
  }
  Serial.println("Bluetooth ready. Pair your phone with 'ESP32-LED'");
}

void loop() {
  while (SerialBT.available()) {                // تا وقتی حرف تازه رسیده
    char c = SerialBT.read();
    if (c == '\n' || c == '\r') {               // پایان یک فرمان
      handleCommand(line);
      line = "";
    } else if (line.length() < 32) {            // سقف طول، برای امنیت حافظه
      line += c;
    }
  }
}
  1. کتابخانه BluetoothSerial. همراه پکیج ESP32 نصب شده است. این کتابخانه همه پیچیدگی پشته بلوتوث (Bluedroid) را پنهان می‌کند و رابطی دقیقا مثل Serial به تو می‌دهد؛ هر چه درباره Serial بلدی، اینجا هم کار می‌کند.
  2. نگهبان زمان کامپایل. #if !defined(CONFIG_BT_SPP_ENABLED) یعنی «اگر پشتیبانی SPP در این برد روشن نیست». در آن صورت #error کامپایل را با یک پیام روشن متوقف می‌کند. بهتر است همان موقع کامپایل با یک جمله واضح بفهمی برد انتخابی‌ات (مثلا C3) بلوتوث کلاسیک ندارد، تا این که با ده‌ها خطای نامفهوم روبه‌رو شوی. این خطوط با # شروع می‌شوند و قبل از کامپایل بررسی می‌شوند، نه روی برد.
  3. شیء بلوتوث و متغیرها. SerialBT پورت سریال بی‌سیم ماست. ledOn وضعیت LED را نگه می‌دارد و line حروف رسیده را تا رسیدن «Enter» جمع می‌کند. داده بلوتوث حرف به حرف و گاهی تکه‌تکه می‌رسد، نه یک‌جا. مثل وقتی کسی کلمه‌ای را حرف به حرف هجی می‌کند؛ تا جمله تمام نشده، نباید تصمیم بگیری.
  4. تمیز کردن فرمان. trim() فاصله‌ها و کاراکترهای نامرئی \r و \n را از دو سر متن پاک می‌کند. toLowerCase() همه حروف را کوچک می‌کند. متن خالی را نادیده می‌گیریم. اپ‌ها در پایان هر پیام معمولا \r\n (دو کاراکتر) می‌فرستند و کاربرها گاهی «On » با فاصله یا «ON» تایپ می‌کنند. بدون این دو خط، "on\r" == "on" غلط است و مبتدی ساعت‌ها فکر می‌کند بلوتوث کار نمی‌کند. به این می‌گویند پردازش مقاوم (Robust) ورودی. هر دو تابع خود متن را تغییر می‌دهند و چیزی برنمی‌گردانند.
  5. لاگ در Serial Monitor. فرمان تمیزشده را بین [ ] چاپ می‌کنیم. براکت‌ها نشان می‌دهند آیا کاراکتر نامرئی یا فاصله‌ای مانده یا نه: [on] درست است، [on ] یعنی مشکلی در trim هست.
  6. تصمیم‌گیری و پاسخ. سه فرمان on، off و status. هر فرمان پاسخی با SerialBT.println به گوشی می‌فرستد. فرمان ناشناخته هم پیام راهنما می‌گیرد. در پایان LED را با ledOn هماهنگ می‌کنیم. پاسخ دادن به هر فرمان یعنی کاربر روی گوشی مطمئن می‌شود فرمانش رسیده و اجرا شده. یک digitalWrite در انتها به جای چند تا در شاخه‌ها، یعنی LED همیشه دقیقا با وضعیت ذخیره‌شده یکی است.
  7. روشن کردن بلوتوث. SerialBT.begin("ESP32-LED") بلوتوث را با این اسم روشن می‌کند و اگر شکست بخورد false برمی‌گرداند. در آن صورت پیام خطا می‌دهیم و برنامه را متوقف می‌کنیم. این اسمی است که در لیست بلوتوث گوشی می‌بینی؛ اسم مشخص بده تا با وسایل دیگر قاطی نشود. توقف با while (true) اینجا عمدی است: برنامه‌ای که هدفش فقط بلوتوث است، بدون بلوتوث کاری ندارد. (در برنامه‌ای که کارهای دیگر هم دارد، به جای توقف فقط یک متغیر خطا را روشن می‌کردیم.)
  8. loop: جمع کردن حروف. تا وقتی حرفی رسیده (available())، آن را بخوان. اگر \n یا \r بود، یعنی پایان فرمان: آن را اجرا کن و line را خالی کن. وگرنه حرف را به line اضافه کن، به شرطی که از ۳۲ حرف بیشتر نشود. هیچ delay یا انتظاری در loop نیست؛ فقط حروفی را که آماده‌اند برمی‌دارد. سقف ۳۲ حرف جلوی این را می‌گیرد که کسی با فرستادن متن طولانی بی‌پایان، حافظه ESP32 را پر کند؛ هرگز به طول ورودی بیرونی اعتماد نکن. چون \r\n دو بار handleCommand را صدا می‌زند، بار دوم با متن خالی است که در خط ۱۶ نادیده گرفته می‌شود.

آزمایش با گوشی اندرویدی

  1. آپلود کن و Serial Monitor را روی 115200 باز کن. باید Bluetooth ready. Pair your phone with 'ESP32-LED' را ببینی.
  2. جفت کردن (Pair): در گوشی به Settings › Bluetooth برو، دستگاه‌های جدید را جستجو کن و روی ESP32-LED بزن. معمولا بدون رمز جفت می‌شود (اگر رمز خواست، تأیید کن یا 1234 را امتحان کن).
  3. اپ Serial Bluetooth Terminal را باز کن. از منوی ☰ گزینه Devices و بعد تب Bluetooth Classic را بزن و ESP32-LED را انتخاب کن.
  4. وصل شو: به صفحه ترمینال برگرد و آیکون اتصال (دو شاخه) بالای صفحه را بزن. پیام Connected را می‌بینی.
  5. فرمان بده: on را تایپ کن و ارسال کن. LED روشن می‌شود و پاسخ OK: LED is ON روی گوشی می‌آید. OFF، Status و hello را هم امتحان کن.

دکمه‌های آماده در اپ

در Serial Bluetooth Terminal ردیف دکمه‌های M1، M2… پایین صفحه را نگه دار تا ویرایش شوند؛ یکی را با متن on و دیگری را با off تنظیم کن. حالا یک کنترل از راه دور دو دکمه‌ای داری، بدون نوشتن حتی یک خط برنامه اندروید.

بخش ب: BLE و مفهوم GATT

در BLE دیگر «لوله پیوسته» وجود ندارد. به جایش هر دستگاه BLE یک جدول مرتب از مقدارها دارد که گوشی می‌تواند آن‌ها را بخواند، بنویسد یا مشترکشان شود. به این ساختار GATT (Generic Attribute Profile) می‌گویند. قبل از کد، این چند اسم را باید مثل اسم دوستانت بشناسی.

مثال از زندگی روزمره: کمد کشودار اداره

ESP32 یک کمد در راهروی یک اداره است (Server). کمد چند قفسه دارد و هر قفسه به یک موضوع اختصاص دارد (Service، مثلا «قفسه چراغ‌ها»). در هر قفسه چند کشو است که روی هر کدام یک برچسب یکتا چسبیده (Characteristic با UUID) و داخلش یک مقدار است، مثلا «on». روی هر کشو هم نوشته چه کارهایی مجاز است (Properties): «فقط نگاه کن» (Read)، «می‌توانی یادداشت بگذاری» (Write)، یا «هر وقت محتوا عوض شد، به تو پیامک می‌زنم» (Notify). گوشی (Client) کارمندی است که سراغ کمد می‌آید.

چرا UUID این‌قدر طولانی است؟

سازمان بلوتوث برای سرویس‌های استاندارد، UUIDهای کوتاه ۱۶ بیتی تعریف کرده؛ مثلا 0x180F یعنی «سرویس باتری» و 0x2A19 یعنی «درصد باتری». هر گوشی دنیا این‌ها را می‌شناسد. برای چیزی که خودت اختراع کرده‌ای (مثل چراغ ما) باید یک UUID ۱۲۸ بیتی تصادفی بسازی. تعداد حالت‌های ممکن آن‌قدر زیاد است (حدود ۱۰ به توان ۳۸) که احتمال این که کس دیگری در دنیا همان را بسازد عملا صفر است. برای ساختن UUID خودت از سایتی مثل uuidgenerator.net استفاده کن. هرگز UUIDهای استاندارد را برای کار خودت استفاده نکن، چون گوشی فکر می‌کند دستگاه تو مثلا یک ضربان‌سنج است.

Notify با عدد

بدون Notify، گوشی برای دیدن مقدار تازه باید هر بار «بخواند» (Read)؛ مثل Polling در درس ۴.۲. با Notify، ESP32 هر ۲ ثانیه مقدار جدید را خودش می‌فرستد. در یک ساعت یعنی ۱۸۰۰ پیام کوچک، به جای این که گوشی مثلا هر ۲۰۰ میلی‌ثانیه (۱۸۰۰۰ بار در ساعت) بپرسد «چیز تازه‌ای هست؟». ده برابر پیام کمتر، یعنی باتری کمتر برای هر دو طرف.

برنامه سرور BLE

#include <BLEDevice.h>
#include <BLEServer.h>
#include <BLEUtils.h>
#include <BLE2902.h>

// شناسه‌های یکتای (UUID) خودمان — با یک مولد UUID تصادفی ساخته شده‌اند
#define SERVICE_UUID       "0582d484-de7b-45b7-b730-09a9fae5cbf4"
#define LED_CHAR_UUID      "851c0eca-a1b1-4b1e-9a56-9f9f546e7ab6"
#define COUNTER_CHAR_UUID  "e8f00efd-6510-4206-8140-d2feea0d4aa7"

const int LED_PIN = 4;
BLEServer* pServer = nullptr;
BLECharacteristic* pLedChar = nullptr;
BLECharacteristic* pCounterChar = nullptr;
volatile bool deviceConnected = false;
bool wasConnected = false;
uint32_t counter = 0;
unsigned long lastNotify = 0;

// ۱) وقتی گوشی وصل یا قطع می‌شود
class ServerCallbacks : public BLEServerCallbacks {
  void onConnect(BLEServer* s) override {
    deviceConnected = true;
    Serial.println("Phone connected");
  }
  void onDisconnect(BLEServer* s) override {
    deviceConnected = false;
    Serial.println("Phone disconnected");
  }
};

// ۲) وقتی گوشی روی characteristic چراغ چیزی می‌نویسد
class LedCallbacks : public BLECharacteristicCallbacks {
  void onWrite(BLECharacteristic* c) override {
    String v = c->getValue();               // در core 3.x نوعش String است
    v.trim();
    v.toLowerCase();
    Serial.printf("LED write: [%s]\n", v.c_str());
    if (v == "on" || v == "1") {
      digitalWrite(LED_PIN, HIGH);
      c->setValue("on");
    } else if (v == "off" || v == "0") {
      digitalWrite(LED_PIN, LOW);
      c->setValue("off");
    }
  }
};

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);

  BLEDevice::init("ESP32-BLE-LED");                 // اسم در لیست اسکن
  pServer = BLEDevice::createServer();
  pServer->setCallbacks(new ServerCallbacks());

  BLEService* service = pServer->createService(SERVICE_UUID);

  pLedChar = service->createCharacteristic(
      LED_CHAR_UUID,
      BLECharacteristic::PROPERTY_READ | BLECharacteristic::PROPERTY_WRITE);
  pLedChar->setCallbacks(new LedCallbacks());
  pLedChar->setValue("off");

  pCounterChar = service->createCharacteristic(
      COUNTER_CHAR_UUID,
      BLECharacteristic::PROPERTY_READ | BLECharacteristic::PROPERTY_NOTIFY);
  pCounterChar->addDescriptor(new BLE2902());       // کلید روشن/خاموش notify برای گوشی

  service->start();

  BLEAdvertising* adv = BLEDevice::getAdvertising();
  adv->addServiceUUID(SERVICE_UUID);
  adv->setScanResponse(true);
  BLEDevice::startAdvertising();
  Serial.println("Advertising as ESP32-BLE-LED ...");
}

void loop() {
  unsigned long now = millis();

  // ۳) هر ۲ ثانیه یک عدد تازه برای گوشی بفرست
  if (deviceConnected && now - lastNotify >= 2000) {
    lastNotify = now;
    counter++;
    String msg = "count=" + String(counter);
    pCounterChar->setValue(msg);
    pCounterChar->notify();
    Serial.println("notify: " + msg);
  }

  // ۴) گوشی رفت؟ دوباره آگهی بده تا بقیه پیدایمان کنند
  if (!deviceConnected && wasConnected) {
    delay(500);                                     // فرصت به پشته بلوتوث
    pServer->startAdvertising();
    Serial.println("Advertising again");
    wasConnected = false;
  }
  if (deviceConnected && !wasConnected) {
    wasConnected = true;
  }
}
  1. چهار فایل کتابخانه BLE داخلی. BLEDevice (خود دستگاه)، BLEServer (سرور GATT)، BLEUtils (ابزارها) و BLE2902 (descriptor مخصوص notify). همه این‌ها بخشی از کتابخانه BLE داخلی پکیج ESP32 هستند؛ نصب جداگانه لازم نیست. همین کد روی ESP32، C3، S3 و C6 کار می‌کند.
  2. سه UUID. یکی برای سرویس و دو تا برای دو characteristic. #define متن را جایگزین می‌کند. UUIDها باید در ESP32 و در اپ گوشی یکی باشند؛ گذاشتن آن‌ها بالای برنامه، پیدا و مقایسه کردنشان را آسان می‌کند.
  3. متغیرهای سراسری. اشاره‌گر (pointer) به سرور و دو characteristic تا در loop هم به آن‌ها دسترسی داشته باشیم. deviceConnected با volatile چون از Task بلوتوث عوض می‌شود. counter عددی است که هر ۲ ثانیه می‌فرستیم. علامت * یعنی «آدرس یک شیء» نه خود شیء؛ کتابخانه BLE اشیا را خودش می‌سازد و فقط آدرسشان را به ما می‌دهد. nullptr یعنی «هنوز به جایی اشاره نمی‌کند». دلیل volatile همان است که در درس ۴.۱ برای رویدادهای Wi-Fi دیدی.
  4. کلاس callback سرور. یک کلاس که از BLEServerCallbacks ارث می‌برد و دو تابع onConnect و onDisconnect آن را بازنویسی می‌کند (override). کتابخانه هنگام وصل و قطع شدن گوشی این‌ها را صدا می‌زند. این همان ایده «زنگ در» درس ۴.۱ است، فقط به شکل کلاس C++. override به کامپایلر می‌گوید «مطمئن شو واقعا تابعی از کلاس پدر را بازنویسی می‌کنم»؛ اگر اسم یا ورودی را اشتباه بنویسی، به جای سکوت و کار نکردن، خطای کامپایل می‌گیری. مثل رویدادهای Wi-Fi، اینجا فقط یک متغیر را عوض می‌کنیم و کار سنگین را به loop می‌سپاریم.
  5. callback نوشتن: onWrite. هر بار که گوشی روی characteristic چراغ چیزی بنویسد، این تابع صدا زده می‌شود. c->getValue() مقدار نوشته‌شده را می‌دهد. علامت -> یعنی «از طریق این اشاره‌گر، این تابع را صدا بزن». در core 3.x، getValue() یک String آردوینویی برمی‌گرداند (پایین‌تر درباره تفاوت با 2.x می‌خوانی).
  6. تمیز کردن و اجرا. دوباره trim و toLowerCase. اگر «on» یا «1» بود LED روشن، اگر «off» یا «0» بود خاموش. بعد با c->setValue مقدار characteristic را به شکل استاندارد («on» یا «off») درمی‌آوریم. پذیرفتن «1» و «0» کار را برای اپ‌هایی که عدد می‌فرستند راحت می‌کند. به‌روز کردن مقدار باعث می‌شود اگر گوشی بعدا این characteristic را «بخواند»، وضعیت واقعی LED را ببیند، نه متنی که کاربر تایپ کرده. ورودی ناشناخته هیچ کاری نمی‌کند؛ ایمن‌ترین پیش‌فرض.
  7. راه‌اندازی دستگاه و سرور. BLEDevice::init پشته BLE را با یک اسم روشن می‌کند. createServer سرور GATT را می‌سازد و setCallbacks کلاس زنگ در را به آن معرفی می‌کند. :: یعنی «تابعی که مال خود کلاس است، نه یک شیء خاص»؛ چون فقط یک دستگاه BLE داریم. new یک شیء callback می‌سازد که تا آخر عمر برنامه زنده می‌ماند.
  8. ساختن سرویس. «قفسه» ما با UUID خودش. همه characteristicها باید داخل یک سرویس باشند؛ characteristic بی‌سرویس وجود ندارد.
  9. characteristic چراغ. با مجوز PROPERTY_READ | PROPERTY_WRITE ساخته می‌شود؛ علامت | یعنی «هر دو». callback نوشتن به آن وصل می‌شود و مقدار اولیه «off» است. فقط مجوزهایی را بده که لازم است: این کشو notify ندارد چون LED خودش تغییر نمی‌کند؛ فقط ما عوضش می‌کنیم. مقدار اولیه یعنی اگر گوشی قبل از هر نوشتنی بخواند، جواب درست بگیرد.
  10. characteristic شمارنده و descriptor 0x2902. مجوز READ | NOTIFY. سپس addDescriptor(new BLE2902()) descriptor استاندارد CCCD را اضافه می‌کند. طبق استاندارد بلوتوث، گوشی notify را با نوشتن روی همین descriptor روشن می‌کند (وقتی در nRF Connect آیکون سه‌فلش را می‌زنی). در پشته Bluedroid (پیش‌فرض ESP32 معمولی در آردوینو) اگر آن را اضافه نکنی، گوشی نمی‌تواند مشترک شود و هیچ notifyی نمی‌رسد. در پشته NimBLE خودکار اضافه می‌شود ولی نوشتنش ضرری ندارد.
  11. service->start(). سرویس را فعال می‌کند. تا start نشود، گوشی حتی بعد از اتصال هم آن را در فهرست نمی‌بیند. همه characteristicها باید قبل از این خط ساخته شوند.
  12. آگهی دادن (Advertising). UUID سرویس را به آگهی اضافه می‌کنیم، پاسخ اسکن (Scan Response) را روشن می‌کنیم و آگهی را شروع می‌کنیم. بسته آگهی BLE خیلی کوچک است (۳۱ بایت). UUID ۱۲۸ بیتی ۱۶ بایت آن را می‌گیرد؛ Scan Response یک بسته دوم است که اسم دستگاه در آن جا می‌شود. نتیجه: گوشی هم اسم را می‌بیند و هم می‌تواند بر اساس سرویس فیلتر کند.
  13. notify هر ۲ ثانیه، بدون delay. اگر گوشی وصل است و ۲۰۰۰ میلی‌ثانیه گذشته، شمارنده را زیاد کن، متنی مثل count=7 بساز، با setValue در characteristic بگذار و با notify() بفرست. متن به جای عدد خام باینری فرستادیم چون nRF Connect متن را مستقیم نشان می‌دهد و تو بدون تبدیل هگز آن را می‌خوانی. در پروژه واقعی، به جای شمارنده، مقدار سنسور (مثلا دمای DHT22) را می‌فرستی. وقتی کسی وصل نیست، notify نمی‌فرستیم؛ فرستادن به هیچ‌کس فقط انرژی هدر می‌دهد.
  14. آگهی دوباره بعد از قطع. اگر الان وصل نیست ولی قبلا بود، یعنی گوشی تازه رفته: ۵۰۰ میلی‌ثانیه صبر، بعد startAdvertising(). مهم‌ترین دام BLE برای مبتدی‌ها: در این کتابخانه، وقتی گوشی وصل می‌شود آگهی متوقف می‌شود و بعد از قطع شدن خودبه‌خود دوباره شروع نمی‌شود. بدون این بخش، ESP32 بعد از اولین قطع شدن برای همیشه نامرئی می‌شود تا ریستش کنی. (هسته ۳ یک میان‌بر هم دارد: pServer->advertiseOnDisconnect(true); در setup؛ پیش‌فرض آن خاموش است. ما نسخه دستی را نوشتیم تا ببینی پشت پرده چه می‌گذرد.) ۵۰۰ میلی‌ثانیه به پشته بلوتوث فرصت می‌دهد اتصال قبلی را کامل ببندد. این delay کوتاه فقط یک بار بعد از هر قطع اتفاق می‌افتد.
  15. ثبت لحظه اتصال. وقتی تازه وصل شده، wasConnected را true کن. این دو متغیر با هم «لبه» را تشخیص می‌دهند: لحظه تغییر از قطع به وصل یا برعکس. همان ایده تشخیص لحظه فشار دکمه در درس ۳.۱.
دقت کن: تفاوت core 3.x با 2.x در BLE

در core 2.x تابع getValue() یک std::string (رشته استاندارد C++) برمی‌گرداند و تقریبا همه آموزش‌های قدیمی این را دارند: std::string value = pCharacteristic->getValue();. در core 3.x این تابع String آردوینو برمی‌گرداند و آن خط دیگر کامپایل نمی‌شود (خطایی شبیه conversion from 'String' to non-scalar type 'std::string' requested). راه حل: بنویس String value = .... اگر واقعا std::string لازم داری: std::string v = c->getValue().c_str();. در core 3.x همچنین setValue یک String می‌پذیرد. جزئیات در راهنمای مهاجرت 2.x به 3.0.

جایگزین سبک‌تر: NimBLE-Arduino

کتابخانه BLE داخلی روی پشته Bluedroid ساخته شده که حجم زیادی از فلش و RAM می‌گیرد. کتابخانه NimBLE-Arduino (از Library Manager) همین کار را با حافظه خیلی کمتر انجام می‌دهد و در پروژه‌هایی که Wi-Fi و BLE را با هم دارند محبوب است. اسم کلاس‌ها شبیه است (NimBLEDevice، NimBLEServer…) ولی امضای بعضی callbackها فرق دارد؛ پس کد را خط به خط کپی نکن و مثال‌های خود کتابخانه را ببین.

آزمایش با nRF Connect (قدم به قدم)

  1. آپلود کن و Serial Monitor را باز کن: Advertising as ESP32-BLE-LED .... توجه: برای BLE لازم نیست از تنظیمات بلوتوث گوشی Pair کنی؛ همه کار داخل اپ است. در اندروید اگر اپ اجازه «مکان» یا «دستگاه‌های نزدیک» خواست، بده (اسکن BLE بدون آن کار نمی‌کند).
  2. اسکن: nRF Connect را باز کن. در تب SCANNER روی SCAN بزن. ESP32-BLE-LED را در فهرست پیدا کن و روی CONNECT کنارش بزن.
  3. سرویس را باز کن: صفحه جدیدی با چند سرویس باز می‌شود. دو تای اول (Generic Access و Generic Attribute) استاندارد هستند. روی Unknown Service با UUID 0582d484-… بزن تا باز شود. دو Unknown Characteristic می‌بینی.
  4. نوشتن روی چراغ: کنار characteristic 851c0eca-… (Properties: READ, WRITE) روی آیکون فلش رو به بالا بزن. در پنجره باز شده، نوع داده را از فهرست کشویی روی TEXT (یا UTF-8) بگذار، on را تایپ کن و SEND را بزن. LED روشن می‌شود. 🎉
  5. خواندن: آیکون فلش رو به پایین همان characteristic را بزن؛ مقدار "on" را می‌بینی. حالا off بفرست و دوباره بخوان.
  6. مشترک شدن در notify: کنار characteristic e8f00efd-… (READ, NOTIFY) روی آیکون چند فلش رو به پایین بزن. هر ۲ ثانیه مقدار عوض می‌شود: count=1، count=2… (اپ مقدار را هم به صورت هگز و هم متن نشان می‌دهد).
  7. قطع و وصل: در بالای صفحه DISCONNECT را بزن. در Serial Monitor Advertising again را می‌بینی و دوباره می‌توانی وصل شوی. این یعنی بخش «آگهی دوباره» درست کار می‌کند.

در آیفون

nRF Connect برای iOS هم هست و مراحل تقریبا یکی است؛ فقط ظاهر آیکون‌ها فرق دارد. آیفون گاهی اسم دستگاه را در حافظه خودش نگه می‌دارد؛ اگر اسم را در کد عوض کردی و آیفون هنوز اسم قدیمی را نشان داد، بلوتوث گوشی را یک بار خاموش و روشن کن.

امنیت: چه کسی می‌تواند وصل شود؟

هر دو برنامه این درس بدون قفل هستند. در بخش الف، ESP32 از روش «Just Works» استفاده می‌کند: هر گوشی در برد حدود ۱۰ متری می‌تواند بدون رمز جفت شود. در بخش ب، هر کس nRF Connect داشته باشد می‌تواند وصل شود و روی characteristic چراغ بنویسد. برای LED آموزشی مشکلی نیست؛ برای قفل در، هرگز.

  • جفت شدن امن (Pairing / Bonding): BLE می‌تواند اتصال را رمزگذاری کند و قبل از اولین اتصال یک رمز ۶ رقمی (Passkey) بخواهد. کتابخانه BLE کلاس BLESecurity را برای این کار دارد (در کتابخانه‌های ESP32 و NimBLE مثال‌های «Secure» یا «Passkey» را ببین). رمز ثابت در کد هم باز بهتر از هیچ است.
  • قاعده پیش‌فرض ایمن: مثل درس ۴.۲، فرمان نامفهوم هیچ کاری نکند و خروجی خطرناک پیش‌فرض خاموش باشد.
  • بعد از کار: در بخش الف، اگر نمی‌خواهی دستگاه همیشه قابل جفت شدن باشد، بعد از کار بلوتوث را با SerialBT.end() خاموش کن.

ویدیوی کمکی

  • این ویدیوی حدود ۳۸ دقیقه‌ای هر دو بخش این درس را پوشش می‌دهد: اول بلوتوث کلاسیک با ترمینال سریال، بعد سرور و کلاینت BLE.
  • در بخش Classic ببین مدرس گوشی را چطور جفت می‌کند و در اپ ترمینال به کدام گزینه وصل می‌شود؛ با مراحل بخش الف ما مقایسه کن.
  • در بخش BLE دقت کن سرویس و characteristic را چطور توضیح می‌دهد و آن را با مثال «کمد کشودار» این درس تطبیق بده.
  • ویدیو قبل از core 3.x ضبط شده؛ اگر در کد آن std::string value = ...getValue() دیدی، طبق هشدار بالا آن را String بنویس.

حرف مربی

BLE اولش گیج‌کننده است چون هیچ «پیامی» نمی‌بینی، فقط جدول مقدار. اشتباه رایج این است که مبتدی هنوز در ذهنش «فرستادن پیام» را تصور می‌کند و وقتی کار نکرد، کد را از پنج آموزش مختلف قاطی می‌کند. این کار را نکن. اول با nRF Connect، بدون هیچ اپ خودت، ثابت کن سرور درست است: سرویس دیده می‌شود، نوشتن کار می‌کند، notify می‌رسد. فقط بعد از آن سراغ ساختن اپ یا وصل کردن سنسور برو. در هر سیستمی که دو طرف دارد، همیشه یک طرف را با ابزاری که مطمئنی درست است آزمایش کن. و یادت باشد: قطع شدن گوشی یک اتفاق عادی است، نه استثنا؛ برنامه‌ای که بعد از اولین قطع شدن نامرئی می‌شود، خراب است.

آزمون این درس

دوستت یک ESP32-C3 دارد و برنامه BluetoothSerial را آپلود می‌کند. چه اتفاقی می‌افتد؟

  1. کار می‌کند ولی فقط با اندروید
  2. کار می‌کند ولی کندتر
  3. کامپایل نمی‌شود، چون ESP32-C3 فقط BLE دارد و بلوتوث کلاسیک (SPP) ندارد
  4. کامپایل می‌شود ولی چون C3 اصلا بلوتوث ندارد، هیچ اتفاقی نمی‌افتد
فقط ESP32 معمولی بلوتوث کلاسیک دارد. C3، S3 و C6 فقط BLE دارند و S2 اصلا بلوتوث ندارد.

در nRF Connect روی characteristic شمارنده، بدون زدن آیکون اشتراک، مقدار هیچ‌وقت عوض نمی‌شود. چرا؟

  1. چون notify فقط به گوشی‌ای فرستاده می‌شود که با نوشتن روی descriptor 0x2902 مشترک شده باشد
  2. چون ESP32 فقط وقتی اپ باز است می‌شمارد
  3. چون مجوز READ کافی نیست و باید WRITE هم اضافه شود
  4. چون اندروید notify را پشتیبانی نمی‌کند
اشتراک یعنی گوشی به ESP32 می‌گوید «از این به بعد تغییرات را برایم بفرست». این کار با CCCD (همان 0x2902) انجام می‌شود.

اگر خط pServer->startAdvertising(); را از loop حذف کنی، چه می‌شود؟

  1. ESP32 اصلا پیدا نمی‌شود
  2. notify کار نمی‌کند
  3. LED روشن نمی‌شود
  4. بار اول وصل می‌شوی، ولی بعد از قطع شدن، ESP32 دیگر در اسکن دیده نمی‌شود تا ریست شود
با اتصال، آگهی متوقف می‌شود و بعد از قطع، خودکار شروع نمی‌شود. آگهی دوباره را خودت باید شروع کنی.

کد قدیمی std::string value = c->getValue(); در core 3.x کامپایل نمی‌شود. درست‌ترین تغییر کدام است؟

  1. core را به 2.x برگردان
  2. ‏String value = c->getValue();
  3. ‏char value = c->getValue();
  4. ‏int value = c->getValue();
در core 3.x، getValue یک String آردوینو برمی‌گرداند. متدهای trim و toLowerCase هم روی همین String کار می‌کنند.

چرا در بخش الف، قبل از مقایسه فرمان، trim() را صدا می‌زنیم؟

  1. تا حروف بزرگ کوچک شوند
  2. تا فرمان‌های طولانی کوتاه شوند
  3. چون اپ‌ها در پایان پیام کاراکترهای نامرئی \r و \n یا فاصله می‌فرستند و بدون trim، "on\r" با "on" برابر نیست
  4. تا حافظه ESP32 پر نشود
ورودی کاربر را همیشه قبل از مقایسه تمیز کن. این ساده‌ترین شکل «پردازش مقاوم ورودی» است.

تمرین‌ها

تمرین ۱: فرمان blink

به برنامه بلوتوث کلاسیک فرمان blink اضافه کن که LED را ۵ بار (هر بار ۲۰۰ میلی‌ثانیه روشن و ۲۰۰ خاموش) چشمک بزند و در پایان به حالت قبلی برگردد. فرمان help هم فهرست همه فرمان‌ها را بفرستد.

راهنمایی

ساده‌ترین نسخه یک حلقه for با delay داخل handleCommand است (۲ ثانیه). نسخه حرفه‌ای (بدون delay): یک متغیر blinksLeft = 10 تنظیم کن و در loop با الگوی millis() هر ۲۰۰ میلی‌ثانیه LED را برعکس کن و یکی از blinksLeft کم کن. کدام را انتخاب کردی و چرا؟

تمرین ۲: notify پتانسیومتر

در برنامه BLE، به جای شمارنده، مقدار یک پتانسیومتر روی GPIO34 (مثل درس ۴.۲) را هر ۵۰۰ میلی‌ثانیه notify کن؛ ولی فقط وقتی مقدار بیش از ۲۰ واحد تغییر کرده.

راهنمایی

یک متغیر int lastSent = -100; نگه دار. در loop: int v = analogRead(34); if (abs(v - lastSent) > 20) { ... notify ...; lastSent = v; }. چرا شرط ۲۰ واحد؟ چون ADC کمی نویز دارد و بدون آن، حتی وقتی به پتانسیومتر دست نمی‌زنی، مدام پیام می‌رود.

جواب 
const int POT_PIN = 34;                     // ADC1
int lastSent = -100;                        // طوری که اولین بار حتما بفرستد

void loop() {
  unsigned long now = millis();
  if (deviceConnected && now - lastNotify >= 500) {
    lastNotify = now;
    int v = analogRead(POT_PIN);            // 0 تا 4095
    if (abs(v - lastSent) > 20) {           // فقط تغییر واقعی، نه نویز
      String msg = "pot=" + String(v);
      pCounterChar->setValue(msg);
      pCounterChar->notify();
      lastSent = v;
    }
  }
  // ... بخش «آگهی دوباره» مثل قبل ...
}
  1. پین و آخرین مقدار فرستاده‌شده. این دو خط را بالای برنامه، کنار بقیه متغیرهای سراسری بگذار. -100 عمدا از هر عدد ممکن ADC دور است. فاصله -100 تا هر عدد ۰ تا ۴۰۹۵ بیش از ۲۰ است، پس اولین خواندن حتما فرستاده می‌شود و گوشی از همان اول مقدار واقعی را می‌بیند.
  2. نگهبان زمان. همان الگوی millis برنامه اصلی، این بار هر ۵۰۰ms؛ فقط وقتی گوشی وصل است پتانسیومتر را می‌خوانیم. متغیرهای deviceConnected و lastNotify از برنامه اصلی می‌آیند؛ این loop جایگزین loop قبلی است، نه اضافه بر آن (دو تابع loop کامپایل نمی‌شود).
  3. فقط تغییر واقعی. اگر اختلاف با آخرین مقدار فرستاده‌شده بیش از ۲۰ بود، متن pot=... را notify کن و lastSent را به‌روز کن. مقایسه با «آخرین فرستاده‌شده» (نه آخرین خوانده‌شده) باعث می‌شود تغییرهای آهسته هم بالاخره جمع شوند و فرستاده شوند؛ همان منطقه مرده درس ۳.۲. ما از همان characteristic شمارنده استفاده کردیم تا UUID جدید لازم نباشد.
  4. آگهی دوباره را فراموش نکن. چهار خط انتهای loop برنامه اصلی را همین‌جا نگه دار. بدون آن، بعد از اولین قطع شدن، ESP32 نامرئی می‌شود.
تمرین ۳: فکر کن (بدون کد)

می‌خواهی یک سنسور دمای باتری‌خور برای اتاق بسازی که دمایش را روی گوشی ببینی. بلوتوث کلاسیک، BLE یا Wi-Fi با وب سرور (درس ۴.۲)؟ برای هر کدام یک مزیت و یک عیب بنویس و انتخابت را با دلیل توضیح بده. اگر بخواهی دما را از محل کار هم ببینی، جوابت عوض می‌شود؟

خلاصه درس در سه خط

بلوتوث کلاسیک یک لوله پیوسته است (با BluetoothSerial مثل Serial بی‌سیم، فقط روی ESP32 معمولی و فقط با اندروید) و BLE یک جدول مقدار کم‌مصرف است که روی ESP32، C3، S3 و C6 و با آیفون هم کار می‌کند. در BLE سرور سرویس‌هایی دارد که characteristicهایی با UUID و مجوز Read/Write/Notify دارند؛ notify بدون descriptor 0x2902 و اشتراک گوشی نمی‌رسد و بعد از هر قطع شدن باید آگهی را دوباره شروع کنی. ورودی را با trim و toLowerCase تمیز کن، در core 3.x getValue() یک String است، و بدون Pairing هر کسی در برد می‌تواند وصل شود.
