هوش مصنوعی می‌تواند در چند ثانیه صد خط کد ESP32 بنویسد. مشکل این است که آن کد را با همان اعتماد به نفس می‌نویسد، چه درست باشد چه غلط. در این درس یاد می‌گیری چطور از Claude، ChatGPT و ابزارهای مشابه مثل یک دستیار کاربلد استفاده کنی، چطور از آن‌ها سؤال درست بپرسی، و مهم‌تر از همه، چطور جوابشان را قبل از وصل کردن به برد واقعی بازبینی کنی.

  • هر کد تولیدشده را با یک چک‌لیست ۱۰ مرحله‌ای بازبینی کنی

🧰 پیش‌نیاز و وسایل

  • همه فصل‌های قبل؛ به‌خصوص ۱.۳ (پین‌ها)، ۳.۲ (PWM) و ۴.۱ (Wi-Fi)

فلسفه: دستیار، نه جایگزین

ممکن است بپرسی: «اگر هوش مصنوعی کد می‌نویسد، چرا این همه فصل را خواندیم؟» جواب کوتاه: چون تو باید قاضی باشی. هوش مصنوعی متن را طوری می‌سازد که «محتمل و درست به نظر برسد». بیشتر وقت‌ها واقعا درست است، ولی گاهی چیزی می‌سازد که وجود ندارد یا برای برد تو غلط است، و لحنش در هر دو حالت یکسان مطمئن است. به این پدیده توهم (Hallucination) می‌گویند.

قالب پرسش برای پروژه‌های امبدد

کیفیت جواب هوش مصنوعی مستقیما به کیفیت پرسش تو بستگی دارد. در برنامه‌نویسی کامپیوتر، «یک برنامه برای جمع دو عدد بنویس» تقریبا کافی است. ولی در امبدد، کد به سخت‌افزار واقعی وصل است: کدام برد؟ کدام پین؟ کدام نسخه کتابخانه؟ اگر این‌ها را نگویی، هوش مصنوعی حدس می‌زند، و حدس‌هایش همان اشتباه‌های جدول بالاست.

این قالب را ذخیره کن و هر بار پر کن. آن را به انگلیسی نوشته‌ایم چون نام‌های فنی، پین‌ها و کد انگلیسی‌اند و کپی کردنش راحت است؛ ولی می‌توانی همین ساختار را به فارسی هم بنویسی. مدل‌های امروزی فارسی را خوب می‌فهمند؛ فقط نام پین‌ها، توابع و پیام‌های خطا را همان‌طور انگلیسی بگذار.

ROLE: You are an experienced embedded engineer helping a beginner.

HARDWARE
- Board: ESP32 DevKitC V4 (ESP32-WROOM-32E module)
- Core: Arduino-ESP32 core 3.x (exact: 3.x.x) in Arduino IDE 2
- Parts and wiring:
  * DHT22: DATA -> GPIO13, VCC -> 3V3, GND -> GND (10k pull-up present)
  * OLED SSD1306 I2C 128x64: SDA -> GPIO21, SCL -> GPIO22, address 0x3C

LIBRARIES (installed)
- DHT sensor library (Adafruit) 1.4.x
- Adafruit SSD1306 2.5.x + Adafruit GFX

GOAL
Read temperature and humidity every 2 s and show them on the OLED.

CONSTRAINTS
- No delay() in loop(); use millis() scheduling.
- Use only core 3.x APIs (e.g. ledcAttach, not ledcSetup).
- If a sensor read fails (NaN), show "ERR" instead of a number.
- Do not put real Wi-Fi passwords or API keys in the code; use placeholders.

OUTPUT I WANT
1) Complete, compilable sketch with short comments.
2) A wiring table (part pin -> ESP32 pin) so I can check it.
3) A step-by-step test plan (what to test first, in isolation).
4) If you are unsure about anything, say so and state your assumption.
  1. نقش (ROLE). به مدل می‌گوید از چه زاویه‌ای جواب بدهد: مهندس باتجربه‌ای که به یک مبتدی کمک می‌کند. این جمله باعث می‌شود جواب‌ها توضیح بیشتری داشته باشند و مدل فرض نکند تو همه چیز را می‌دانی. اثرش معجزه نیست، ولی لحن و عمق جواب را بهتر می‌کند.
  2. برد و نسخه هسته. نام دقیق برد و نسخه دقیق هسته آردوینو را بنویس. نسخه را از Tools › Board › Boards Manager ببین. این مهم‌ترین خط کل قالب است. «ESP32» به تنهایی ده‌ها برد و دو نسخه API کاملا متفاوت را شامل می‌شود. نوشتن «core 3.x» جلوی بخش بزرگی از اشتباه‌های API قدیمی را می‌گیرد.
  3. سیم‌کشی واقعی تو. هر قطعه، هر پایه، به کدام پین ESP32؛ به‌علاوه آدرس I2C و مقاومت‌ها. اگر نگویی DHT22 روی GPIO13 است، مدل یک پین «معمول» انتخاب می‌کند که ممکن است با سیم‌کشی تو فرق کند، یا حتی یک پین نامناسب باشد. تو سیم‌کشی را تعیین کن، نه مدل.
  4. کتابخانه‌ها و نسخه‌ها. دقیقا کدام کتابخانه را نصب کرده‌ای. برای یک سنسور چند کتابخانه با اسم مشابه وجود دارد که توابعشان فرق دارد. بدون این خط، مدل ممکن است کدی برای کتابخانه‌ای بنویسد که نداری و خطای «not declared» بگیری.
  5. هدف (GOAL). یک یا دو جمله روشن: چه چیزی، هر چند وقت، کجا نمایش داده شود. هدف مبهم مثل «یک ایستگاه هواشناسی بساز» باعث می‌شود مدل ده ویژگی اضافه کند که نخواسته‌ای (وب سرور، Wi-Fi، کارت SD) و کد سه برابر بزرگ‌تر و پرخطرتر شود.
  6. محدودیت‌ها (CONSTRAINTS). قواعدی که کد باید رعایت کند: بدون delay، فقط API هسته ۳.x، رفتار در خطای سنسور، بدون رمز واقعی. این‌ها همان درس‌هایی هستند که در این دوره یاد گرفتی. با نوشتنشان، دانش خودت را به مدل «تزریق» می‌کنی. مدل بدون این‌ها معمولا ساده‌ترین (و نه بهترین) راه را انتخاب می‌کند.
  7. خروجی مورد انتظار. کد کامل، جدول سیم‌کشی، برنامه آزمایش، و اعتراف به عدم قطعیت. جدول سیم‌کشی را می‌خواهی تا با سیم‌کشی خودت مقایسه کنی: اگر مدل پین دیگری نوشت، یعنی پرسش را درست نخوانده. برنامه آزمایش تو را وادار می‌کند قدم به قدم جلو بروی. خط آخر، مدل را تشویق می‌کند به جای حدس زدن مطمئن‌نما، بگوید کجا مطمئن نیست.

مثال ۱: تولید کد (پرسش بد در برابر پرسش خوب)

توجه: این مثال‌ها ساختگی و آموزشی‌اند

متن‌ها و کدهای این بخش را ما برای آموزش ساخته‌ایم تا نوع تفاوت‌ها را نشان دهیم؛ رونوشت واقعی گفتگو با هیچ مدل خاصی نیستند. جواب واقعی هر مدل، هر بار ممکن است فرق کند.

پرسش بد: «یک کد بنویس که با ESP32 دما رو بخونه و یه فن رو کنترل کنه.»

این پرسش چه چیزهایی را نگفته؟ کدام سنسور (DHT11؟ DHT22؟ DS18B20؟)، کدام پین‌ها، فن چطور وصل است (مستقیم؟ با ترانزیستور؟ با رله؟)، کنترل روشن و خاموش یا سرعت با PWM، کدام نسخه هسته. مدل باید همه این‌ها را حدس بزند. نتیجه ممکن است چیزی شبیه این باشد:

// نمونه ساختگی: جوابی که یک پرسش مبهم ممکن است بگیرد (اشکال دارد!)
#include <WiFi.h>
#include "DHT.h"

#define DHTPIN 2
DHT dht(DHTPIN, DHT11);
const char* ssid = "MyHomeWiFi";
const char* password = "12345678";

void setup() {
  Serial.begin(9600);
  WiFi.begin(ssid, password);
  while (WiFi.status() != WL_CONNECTED) delay(500);
  dht.begin();
  ledcSetup(0, 25000, 8);
  ledcAttachPin(35, 0);
}

void loop() {
  float t = dht.readTemperature();
  if (t > 30) ledcWrite(0, 255);
  else ledcWrite(0, 0);
  delay(5000);
}
  1. Wi-Fi و رمز که کسی نخواسته بود. مدل Wi-Fi اضافه کرده و یک رمز نمونه را مستقیم در کد گذاشته. پرسش حرفی از اینترنت نزده بود. کد اضافه یعنی خطای اضافه. و عادت گذاشتن رمز در کد، روزی باعث می‌شود رمز واقعی‌ات را در گیت‌هاب یا در یک گفتگو منتشر کنی.
  2. حدس سنسور و پین. DHT11 روی GPIO2. اگر سنسور تو DHT22 باشد، عددها غلط یا NaN می‌شوند. GPIO2 یک پین Strapping است و روی بسیاری از بردها LED هم دارد؛ برای سنسور انتخاب خوبی نیست.
  3. سرعت سریال غیرمعمول و انتظار بی‌پایان. 9600 به جای 115200؛ و حلقه‌ای که اگر Wi-Fi وصل نشود تا ابد می‌چرخد. 9600 غلط نیست ولی با تنظیم Serial Monitor تو (که در این دوره همیشه 115200 بود) حروف درهم می‌بینی. حلقه بدون حد زمانی یعنی اگر مودم خاموش باشد، فن هم هرگز کنترل نمی‌شود.
  4. API قدیمی و پین فقط‌ورودی. ledcSetup و ledcAttachPin در هسته ۳.x وجود ندارند؛ و GPIO35 فقط ورودی است و اصلا نمی‌تواند PWM بدهد. این دو خط، دو اشتباه کاملا متفاوت‌اند: اولی خطای کامپایل می‌دهد (خوب است؛ زود می‌فهمی). دومی حتی اگر کامپایل شود، هیچ‌وقت کار نمی‌کند و ساعت‌ها وقتت را می‌گیرد.
  5. NaN نادیده، delay طولانی. اگر خواندن شکست بخورد، t برابر NaN است و مقایسه‌اش همیشه false است؛ فن بی‌صدا خاموش می‌ماند. delay(5000) هم برنامه را قفل می‌کند. کدی که در شرایط خطا «بی‌صدا» رفتار اشتباه می‌کند، خطرناک‌ترین نوع کد است. و خود فن: یک فن ۱۲ ولتی را نمی‌شود مستقیم به پین ESP32 وصل کرد؛ ترانزیستور یا ماسفت لازم است (درس ۳.۴). مدل درباره سخت‌افزار هیچ هشداری نداده!

پرسش خوب همان قالب بالاست با این تغییرات: «DHT22 روی GPIO13؛ فن ۱۲ ولت DC دو سیم، از طریق ماسفت منطق‌سطح (logic-level) که گیتش به GPIO26 وصل است و دیود هرزگرد دارد؛ کنترل سرعت با PWM ۲۵ کیلوهرتز؛ زیر ۲۸ درجه خاموش، بالای ۳۵ درجه حداکثر، بین این دو خطی؛ هسته ۳.x.» حالا مدل دیگر چیزی برای حدس زدن ندارد. در جواب چنین پرسشی معمولا باید این‌ها را ببینی (و اگر ندیدی، بپرس): ledcAttach(26, 25000, 8)، ledcWrite(26, duty)، بررسی isnan، زمان‌بندی با millis()، و جدول سیم‌کشی که با گفته تو یکی است.

  2. خطای کامل و کد کامل. متن خطا را کامل کپی کن (در Arduino IDE دکمه Copy error messages هست). خلاصه کردن خطا («یه ارور LEDC میده») اطلاعات حیاتی مثل شماره خط و متن دقیق را حذف می‌کند.
  3. کارهایی که کردی و حدس تو. این کار مدل را از پیشنهادهای بی‌فایده («اسم را درست بنویس») نجات می‌دهد و مهم‌تر: تو را وادار می‌کند قبل از پرسیدن فکر کنی. اگر مدل حدس تو را رد کرد، باید دلیلش را بپرسی، نه این که فورا قبول کنی.
  4. درخواست مشخص. تأیید یا رد با دلیل، بازنویسی فقط بخش مربوط، و فهرست بقیه خطرها. «فقط بخش LEDC» جلوی بازنویسی کل برنامه را می‌گیرد که ممکن است باگ‌های جدیدی بیاورد. بند ۳ تو را برای خطای بعدی آماده می‌کند.

جواب درست (که باید بتوانی خودت هم با راهنمای مهاجرت رسمی ۲.x به ۳.۰ تأییدش کنی): در هسته ۳.x، مفهوم «کانال» از API اصلی حذف شد و همه چیز با شماره پین کار می‌کند. کد قدیمی و جدید را کنار هم ببین:

// هسته 2.x (قدیمی) — در 3.x کامپایل نمی‌شود
const int FAN_PIN = 26;
const int CH = 0;

void setup() {
  ledcSetup(CH, 5000, 8);        // کانال 0، فرکانس 5kHz، دقت 8 بیت
  ledcAttachPin(FAN_PIN, CH);    // پین را به کانال وصل کن
}

void loop() {
  ledcWrite(CH, 128);            // در 2.x: عدد اول = کانال
}
  1. دو مرحله در ۲.x. اول یک کانال PWM تنظیم می‌شد، بعد پین به آن کانال وصل می‌شد. این روش انعطاف داشت ولی برای مبتدی گیج‌کننده بود: دو شماره (کانال و پین) که باید با هم هماهنگ نگه داشته می‌شدند.
  2. ledcWrite با کانال. عدد اول کانال بود. این خط در ۳.x هم کامپایل می‌شود، ولی معنایش عوض شده: حالا یعنی «پین ۰». چون پین ۰ به LEDC وصل نشده، تابع بی‌صدا false برمی‌گرداند و هیچ اتفاقی نمی‌افتد. دام بی‌صدا؛ ادامه را ببین.
// هسته 3.x (فعلی)
const int FAN_PIN = 26;

void setup() {
  ledcAttach(FAN_PIN, 5000, 8);  // پین، فرکانس، دقت؛ کانال خودکار انتخاب می‌شود
}

void loop() {
  ledcWrite(FAN_PIN, 128);       // در 3.x: عدد اول = پین
}
  1. ledcAttach. یک خط به جای دو خط: پین، فرکانس و دقت بیت. هسته خودش یک کانال آزاد پیدا می‌کند. کمتر شماره، کمتر اشتباه.
  2. ledcWrite با پین. حالا عدد اول شماره پین است. اگر فقط ledcSetup را درست کنی ولی ledcWrite(0, 128) قدیمی را نگه داری، کد بدون هیچ خطایی کامپایل می‌شود و فن هیچ‌وقت کار نمی‌کند. برای همین در پرسش عیب‌یابی بند ۳ را گذاشتیم: «چه چیز دیگری ۲.x است؟»
نسخه هسته‌ات را از خود برد بپرس

اگر مطمئن نیستی کدام نسخه نصب است، این برنامه کوچک را اجرا کن. عددی که چاپ می‌کند را در پرسش‌هایت بنویس:

void setup() {

  delay(500);
  Serial.printf("Arduino-ESP32 core %d.%d.%d\n",
                ESP_ARDUINO_VERSION_MAJOR,

  1. ماکروهای نسخه. ESP_ARDUINO_VERSION_MAJOR و دو ماکرو بعدی، شماره نسخه هسته‌ای را که کد با آن کامپایل شده نگه می‌دارند. این عدد از خود کامپایل می‌آید، پس دیگر حدس نیست. می‌توانی با #if ESP_ARDUINO_VERSION_MAJOR >= 3 حتی کدی بنویسی که با هر دو نسخه کامپایل شود.

مثال ۳: توضیح کد ناآشنا، خط به خط

یکی از بهترین کاربردهای هوش مصنوعی، «معلم خصوصی» است: کدی را که در اینترنت پیدا کرده‌ای و نمی‌فهمی، بدهی و بخواهی خط به خط توضیح دهد. پرسش پیشنهادی:

I am a beginner (Arduino-ESP32 core 3.x). Explain this code line by line:
what each line does, WHY it is needed, and what would break if I removed it.
Mark clearly anything you are not sure about.
Then give me 3 small experiments to verify your explanation on a real board.

[paste code here]
  1. چه، چرا، و اگر حذف کنم؟ سه سؤال برای هر خط. «چه» را اغلب خودت هم حدس می‌زنی. «چرا» و «اگر حذف کنم» فهم عمیق می‌سازند؛ همان ساختاری که کارت‌های توضیح این دوره دارند.
  2. آزمایش برای راستی‌آزمایی. توضیح هوش مصنوعی هم می‌تواند غلط باشد. آزمایش روی برد، داور نهایی است؛ نه اعتماد به نفس متن.

برای نمونه، این کد شمارش پالس (مثلا از یک سنسور جریان آب یا یک دکمه) را در نظر بگیر. پایین‌تر خودمان همان توضیحی را نوشته‌ایم که از یک جواب خوب انتظار داری؛ با آن می‌توانی کیفیت جواب هوش مصنوعی را بسنجی:

volatile uint32_t pulses = 0;
portMUX_TYPE mux = portMUX_INITIALIZER_UNLOCKED;

void IRAM_ATTR onPulse() {
  portENTER_CRITICAL_ISR(&mux);
  pulses++;
  portEXIT_CRITICAL_ISR(&mux);
}

void setup() {
  Serial.begin(115200);
  pinMode(27, INPUT_PULLUP);
  attachInterrupt(digitalPinToInterrupt(27), onPulse, FALLING);
}

void loop() {
  static uint32_t last = 0;
  if (millis() - last >= 1000) {
    last = millis();
    portENTER_CRITICAL(&mux);
    uint32_t n = pulses;
    pulses = 0;
    portEXIT_CRITICAL(&mux);
    Serial.printf("pulses/s: %lu\n", n);
  }
}
  1. volatile. به کامپایلر می‌گوید این متغیر ممکن است «از بیرون» (در وقفه) عوض شود؛ هر بار از حافظه بخوانش. بدون volatile، کامپایلر ممکن است برای سرعت، مقدار را در یک رجیستر نگه دارد و loop هرگز تغییرات وقفه را نبیند. اگر حذفش کنی: گاهی کار می‌کند، گاهی نه؛ بدترین نوع باگ.
  2. قفل (mux). یک قفل کوچک برای این که وقفه و loop هم‌زمان به pulses دست نزنند. ESP32 دو هسته دارد و خواندن و صفر کردن یک متغیر دو عمل جداست. بدون قفل، ممکن است پالسی دقیقا بین خواندن و صفر کردن بیاید و گم شود.
  3. تابع وقفه (ISR). IRAM_ATTR تابع را در RAM سریع داخلی می‌گذارد. داخلش فقط یک کار کوتاه: شمارنده را زیاد کن. وقفه باید در چند میکروثانیه تمام شود. Serial.print یا delay داخل ISR ممنوع است. _ISR در نام ماکروها یعنی نسخه مخصوص داخل وقفه.
  4. راه‌اندازی وقفه. GPIO27 ورودی با بالاکش؛ هر لبه پایین‌رونده (FALLING، یعنی از HIGH به LOW) تابع onPulse را صدا می‌زند. با بالاکش داخلی، یک دکمه یا خروجی open-collector سنسور بین پین و GND کافی است. دکمه مکانیکی لرزش (Bounce) دارد و یک فشار ممکن است چند پالس بشمارد؛ برای دکمه باید Debounce اضافه کنی.
  5. زمان‌بندی بدون delay. هر ۱۰۰۰ میلی‌ثانیه یک بار. static یعنی مقدار last بین دورهای loop حفظ شود، بدون متغیر سراسری. تفریق millis() - last حتی وقتی millis بعد از حدود ۴۹ روز سرریز کند درست کار می‌کند.
  6. برداشتن امن و چاپ. زیر قفل، مقدار را کپی و صفر می‌کنیم؛ بعد از باز کردن قفل چاپ می‌کنیم. کار زیر قفل باید حداقل باشد؛ Serial.printf کند است و نباید زیر قفل باشد. نتیجه: تعداد پالس در هر ثانیه.

حالا خودت آزمایش کن: volatile را حذف کن، یا چاپ را داخل ISR ببر. چه اتفاقی می‌افتد؟ آیا با پیش‌بینی هوش مصنوعی یکی بود؟

یک دکمه بین GPIO27 و GND. هر بار دکمه را بزن و ببین در ثانیه چند پالس شمرده می‌شود. به احتمال زیاد گاهی برای یک فشار بیش از یک پالس می‌بینی، چون Wokwi لرزش دکمه را هم شبیه‌سازی می‌کند؛ این همان Bounce است.

چک‌لیست بازبینی هر کد تولیدشده برای ESP32

این چک‌لیست را چاپ کن و کنار میزت بچسبان. هر کدی که هوش مصنوعی (یا هر آموزش اینترنتی) به تو داد، قبل از اجرا روی برد واقعی از این ده مرحله بگذرد:

  1. هر خط را می‌فهمم. اگر نه، اول بپرس. کد نفهمیده اجرا نمی‌شود.
  2. پین‌ها. هر پین را با صفحه Pinout چک کن: GPIO6 تا 11 نه؛ خروجی روی 34 تا 39 نه؛ ADC2 با Wi-Fi نه؛ پین‌های Strapping (0، 2، 5، 12، 15) با احتیاط.
  3. با سیم‌کشی من یکی است. جدول سیم‌کشی جواب را با مدار واقعی‌ات، سیم به سیم، مقایسه کن.
  4. ولتاژ و جریان. هیچ سیگنال ۵ ولتی مستقیم به پین ESP32 نرود. هیچ بار سنگین (موتور، فن، رله، نوار LED) مستقیم از پین تغذیه نشود. پین حداکثر ده‌ها میلی‌آمپر می‌دهد.
  5. نسخه API. دنبال نشانه‌های ۲.x بگرد: ledcSetup، ledcAttachPin، امضای قدیمی callback در ESP-NOW. شک داری؟ راهنمای مهاجرت را ببین.
  6. کتابخانه‌ها واقعی‌اند. هر #include را در Library Manager یا گیت‌هاب پیدا کن. تابع‌هایی که صدا زده شده در مستندات همان کتابخانه هستند؟
  7. بدون انتظار بی‌پایان. delay طولانی در loop؟ while بدون حد زمانی؟ اگر Wi-Fi یا سنسور نبود چه می‌شود؟
  8. مدیریت خطا. NaN سنسور، قطع Wi-Fi، شکست MQTT، نبودن نمایشگر؛ هر کدام چه رفتاری دارند؟
  9. امنیت. رمز یا کلید واقعی در کد نیست؛ topic عمومی MQTT برای کنترل وسایل مهم خانه استفاده نشده.
  10. اول Wokwi، بعد برد. کد را اول در Wokwi یا دست‌کم با کامپایل در Arduino IDE آزمایش کن؛ بعد روی برد واقعی، بخش به بخش (اول سنسور، بعد نمایشگر، بعد شبکه).

حریم خصوصی و امنیت: چه چیزی را هرگز نچسبان

هر چیزی که در یک گفتگوی هوش مصنوعی می‌نویسی، به سرورهای یک شرکت دیگر می‌رود و ممکن است ذخیره شود. پس:

  • هرگز رمز Wi-Fi واقعی، کلید API (مثلا AIO Key در Adafruit IO)، توکن ربات تلگرام، یا رمز حساب‌ها را در پرسش نچسبان.
  • قبل از چسباندن کد، این مقدارها را با جای خالی مثل "YOUR_WIFI_PASSWORD" عوض کن.
  • اطلاعات شخصی دیگران (آدرس، شماره تلفن) در کد یا لاگ‌ها نباشد.
  • کد محرمانه کارفرما را بدون اجازه در سرویس‌های عمومی نچسبان.

بهترین عادت: رمزها را از همان اول در یک فایل جدا نگه دار که هیچ‌وقت آن را به اشتراک نمی‌گذاری. در Arduino IDE یک تب جدید به اسم secrets.h بساز:

// secrets.h — این فایل را با کسی به اشتراک نگذار و در گیت‌هاب نگذار
#pragma once
#define WIFI_SSID  "MyHome"
#define WIFI_PASS  "put-your-real-password-here"
  1. #pragma once. اگر این فایل چند بار include شود، فقط یک بار خوانده می‌شود. جلوی خطای «تعریف تکراری» را در پروژه‌های چندفایلی می‌گیرد.
  2. تعریف رمزها. دو ماکرو برای نام و رمز شبکه. حالا فایل اصلی .ino فقط #include "secrets.h" و WiFi.begin(WIFI_SSID, WIFI_PASS) دارد. آن فایل را با خیال راحت به هوش مصنوعی یا دوستت نشان می‌دهی. اگر از گیت استفاده می‌کنی، secrets.h را به .gitignore اضافه کن.

ویدیوی کمکی

  • این ویدیو مال اوایل ۲۰۲۳ است؛ مدل‌ها از آن زمان خیلی بهتر شده‌اند. آن را برای روش کار ببین، نه برای کیفیت جواب‌ها.
  • دقت کن مدرس پرسش‌هایش را چقدر دقیق می‌نویسد و کجا جزئیات سخت‌افزار را می‌گوید یا نمی‌گوید.
  • هر جا کدی تولید شد، خودت چک‌لیست همین درس را رویش اجرا کن: پین‌ها، API (در آن زمان هسته ۲.x رایج بود)، delay و مدیریت خطا.
  • ببین آیا مدرس کد را قبل از اجرا می‌خواند و می‌فهمد یا نه.

کد بلند و پیچیده‌ای گرفتی که نمی‌فهمیخواسته بزرگ و مبهمکار را به گام‌های کوچک بشکن (مثل درس ۶.۳؛ روش کامل «از ایده تا دستگاه» در ۶.۴): اول فقط سنسور، بعد نمایشگر، بعد شبکه. هر گام را جدا بپرس و آزمایش کن.
حرف مربی

هوش مصنوعی تو را سریع‌تر می‌کند، به شرطی که خودت بلد باشی. اگر بلد نباشی، فقط سریع‌تر اشتباه می‌کنی. قانون من برای شاگردانم ساده است: هر کدی که از هوش مصنوعی گرفتی، باید بتوانی بدون نگاه کردن به جواب، به یک نفر دیگر توضیحش بدهی. نمی‌توانی؟ پس هنوز کد تو نیست، کد اوست. و یک هشدار جدی: مسئولیت مدار سوخته، باتری داغ‌شده یا رمز لورفته با توست، نه با هوش مصنوعی.

آزمون این درس

مهم‌ترین اطلاعاتی که در پرسش برنامه‌نویسی ESP32 باید بنویسی کدام است؟

  1. «لطفا» و «ممنون»
  2. این که پرسش حتما انگلیسی باشد
  3. نام دقیق برد، نسخه هسته، و سیم‌کشی دقیق قطعه‌ها
  4. این که پرسش خیلی طولانی باشد
بدون برد، نسخه هسته و سیم‌کشی، مدل مجبور است حدس بزند؛ و حدس‌هایش اغلب پین غلط و API قدیمی است.

هوش مصنوعی کدی داده که ledcWrite(0, 128); دارد و تو با هسته ۳.x کامپایلش کردی. بدون خطا کامپایل شد. چه مشکلی ممکن است باشد؟

  1. هیچ مشکلی؛ کامپایل شد یعنی درست است
  2. در ۳.x عدد اول «پین» است؛ این خط سراغ پین ۰ می‌رود (نه کانال ۰) و چون پین ۰ به LEDC وصل نشده، بی‌صدا کاری نمی‌کند
  3. عدد ۱۲۸ برای PWM مجاز نیست
  4. ledcWrite در ۳.x حذف شده
این دام بی‌صداست: همان اسم تابع، معنای متفاوت. کامپایل موفق یعنی «از نظر زبان درست»، نه «از نظر منطق درست».

برای عیب‌یابی یک خطای کامپایل با هوش مصنوعی، کدام پرسش بهتر است؟

  1. «کدم کار نمی‌کنه، درستش کن»
  2. «یه ارور LEDC می‌ده»
  3. فقط کد کامل را بچسبانی
  4. نسخه هسته + متن کامل خطا + کد + کارهایی که امتحان کرده‌ای و حدست
هر چه اطلاعات دقیق‌تر، جواب دقیق‌تر. و حدس خودت تو را وادار می‌کند فکر کنی.

هوش مصنوعی پیشنهاد کرده خروجی ECHO سنسور HC-SR04 (که با ۵ ولت کار می‌کند) را مستقیم به GPIO18 وصل کنی. چه می‌کنی؟

  1. قبول نمی‌کنم؛ با تقسیم‌کننده ولتاژ یا مبدل سطح ولتاژ را به ۳٫۳ ولت می‌رسانم
  2. قبول می‌کنم چون هوش مصنوعی گفته
  3. فقط پین را به GPIO19 عوض می‌کنم
  4. مقاومت بالاکش داخلی را فعال می‌کنم
پین‌های ESP32 برای ۳٫۳ ولت طراحی شده‌اند (روش‌های تبدیل سطح در درس ۱.۴). این دقیقا جایی است که دانش پایه تو از هوش مصنوعی جلوتر است.

کدام کار در گفتگو با یک دستیار هوش مصنوعی درست است؟

  1. چسباندن کد کامل همراه با رمز Wi-Fi واقعی تا مدل بتواند آن را تست کند
  2. چسباندن کلید API برای این که مدل اتصال را درست کند
  3. جایگزین کردن رمزها با متن جای خالی و نگه داشتن رمز واقعی در فایل جدا
  4. دادن آدرس IP مودم و رمز پنل مدیریت برای عیب‌یابی شبکه
اطلاعات حساس هیچ‌وقت در گفتگو نمی‌رود. فایل secrets.h جدا این کار را آسان می‌کند.

تمرین‌ها

تمرین ۱: توسعه یک پروژه قبلی با هوش مصنوعی و بازبینی آن

یکی از پروژه‌های قبلی را انتخاب کن (مثلا دیتالاگر باتری‌خور درس ۶.۱ یا نمایشگر DHT22 درس ۳.۳). با قالب پرسش، از هوش مصنوعی بخواه یک ویژگی به آن اضافه کند؛ مثلا «اگر رطوبت بالای ۷۰ درصد بود، LED روی GPIO4 چشمک بزند، بدون delay». بعد:

  1. پرسش کاملت را یادداشت کن.
  2. چک‌لیست ده مرحله‌ای را روی جواب اجرا کن و برای هر مرحله بنویس «قبول» یا «رد» و چرا.
  3. حداقل یک پرسش پیگیری بپرس («این کد در کدام شرایط کار نمی‌کند؟»).
  4. کد را اول در Wokwi اجرا کن، بعد روی برد.
راهنمایی

کد فعلی پروژه را کامل در پرسش بگذار و صریح بگو «فقط این ویژگی را اضافه کن و بقیه کد را تغییر نده». بعد تغییرها را خط به خط با کد قبلی مقایسه کن. اگر مدل چیزهایی را که نخواسته بودی عوض کرده (مثلا پین‌ها یا زمان خواب)، این خودش یک یافته مهم بازبینی است.

چه باید ببینی؟

این تمرین دو نتیجه دارد: بازبینی نوشته‌شده تو، و برنامه‌ای که واقعا کار می‌کند.

بازبینی‌ات خوب است اگر برای هر ده مرحله «قبول» یا «رد» همراه با دلیل نوشته باشی (نه فقط یک تیک)؛ کد جدید را خط به خط با کد قبلی مقایسه کرده باشی؛ و جواب سوال پیگیری‌ات را خودت امتحان کرده باشی، نه این که فقط باورش کنی.

برنامه درست (نمایشگر DHT22 درس ۳.۳ به‌علاوه LED روی GPIO4)، هر ۲ ثانیه در Serial Monitor. در Wokwi سنسور DHT22 با ۲۴٫۵ درجه و ۴۰ درصد شروع می‌کند؛ این‌جا لغزنده رطوبت اول روی ۸۰ و بعد روی ۶۰ رفته:

T=24.5 C  H=40.0 %  LED off
T=24.5 C  H=40.0 %  LED off
T=24.5 C  H=80.0 %  LED blinking
T=24.5 C  H=80.0 %  LED blinking
T=24.5 C  H=60.0 %  LED off
  • رطوبت بالای ۷۰: LED ثانیه‌ای دو بار چشمک می‌زند (۲۵۰ میلی‌ثانیه روشن، ۲۵۰ خاموش) و یکنواخت؛ نه هر ۲ ثانیه یک تغییر.
  • رطوبت برگشت زیر ۷۰: LED ظرف ۲ ثانیه خاموش می‌شود و خاموش می‌ماند. هیچ‌وقت روشن گیر نمی‌کند.
  • سیم داده DHT22 را بکش: «DHT22 read error!» روی نمایشگر و LED خاموش.
  • OLED در حالی که LED چشمک می‌زند، هر ۲ ثانیه به‌روز می‌شود.
جواب کامل با توضیح

جواب هوش مصنوعی تو هر بار فرق می‌کند؛ پس این‌جا یک بازبینی نمونه برای یک جواب معمولی آمده (نوشته خود ما، مثل بقیه مثال‌های این درس). پرسش همان قالب بود، با کد کامل Weather_OLED درس ۳.۳ و این درخواست: «اگر رطوبت بالای ۷۰ درصد بود، LED روی GPIO4 (با ۲۲۰ اهم به GND) بدون delay چشمک بزند؛ فقط همین ویژگی را اضافه کن و بقیه کد را تغییر نده». جواب:

// مثال ساختگی: جواب AI (همان Weather_OLED درس ۳.۳ + قابلیت جدید)
#include <Wire.h>
#include <Adafruit_GFX.h>
#include <Adafruit_SSD1306.h>
#include <DHT.h>

Adafruit_SSD1306 display(128, 64, &Wire, -1);
DHT dht(13, DHT22);

unsigned long lastRead = 0;
const int LED_PIN = 4;                  // جدید
bool ledState = false;                  // جدید
unsigned long lastBlink = 0;            // جدید

void showMessage(const char *msg) {
  display.clearDisplay();
  display.setTextSize(1);
  display.setCursor(0, 0);
  display.println(msg);
  display.display();
}

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);             // جدید
  Wire.begin(21, 22);
  if (!display.begin(SSD1306_SWITCHCAPVCC, 0x3C)) {
    Serial.println("OLED not found!");
    while (true) delay(1000);
  }
  display.setTextColor(SSD1306_WHITE);
  dht.begin();
  showMessage("Waiting for DHT22...");
}

void loop() {
  if (millis() - lastRead < 2000) return;   // هنوز ۲ ثانیه نشده
  lastRead = millis();

  float t = dht.readTemperature();
  float h = dht.readHumidity();
  if (isnan(t) || isnan(h)) {
    showMessage("DHT22 read error!");
    Serial.println("DHT22 read error");
    return;
  }

  display.clearDisplay();
  display.setTextSize(1);
  display.setCursor(0, 0);
  display.println("Temperature");
  display.setTextSize(2);
  display.setCursor(0, 12);
  display.printf("%.1f C", t);
  display.setTextSize(1);
  display.setCursor(0, 36);
  display.println("Humidity");
  display.setTextSize(2);
  display.setCursor(0, 48);
  display.printf("%.1f %%", h);
  display.display();

  Serial.printf("T=%.1f C  H=%.1f %%\n", t, h);

  if (h > 70) {                         // جدید: چشمک بدون delay
    if (millis() - lastBlink >= 250) {
      lastBlink = millis();
      ledState = !ledState;
      digitalWrite(LED_PIN, ledState);
    }
  }
}

بدون حتی یک هشدار کامپایل می‌شود. حالا چک‌لیست، مرحله به مرحله:

#مرحلهنتیجهچرا
۱همه خط‌ها را می‌فهمم❌ ردloop را خط به خط دنبال کن: خط اولش اگر ۲ ثانیه نگذشته باشد از loop بیرون می‌رود. پس کد چشمک جدید در انتها فقط هر ۲ ثانیه یک بار اجرا می‌شود و LED هر ۲ ثانیه وضعیت عوض می‌کند، نه هر ۲۵۰ میلی‌ثانیه. «بدون delay» در عمل رعایت نشده، با این که کلمه delay آن‌جا نیست.
۲پین‌ها✅ قبولGPIO4 خروجی امن است، ۱۳ برای DHT22، ۲۱ و ۲۲ برای I2C. هیچ‌کدام ۶ تا ۱۱، پین فقط‌ورودی (۳۴ تا ۳۹) یا Strapping نیست.
۳با سیم‌کشی من یکی است✅ قبولهمان پین‌های بردبورد دوره. در مقایسه خط به خط، فقط خط‌هایی که «جدید» خورده‌اند تازه‌اند؛ مدل چیز دیگری را عوض نکرده.
۴ولتاژ و جریان✅ قبولLED با ۲۲۰ اهم: (۳٫۳ − ۲٫۰) ÷ ۲۲۰ ≈ ۶ میلی‌آمپر، خیلی کمتر از توان یک پین.
۵نسخه API✅ قبولهیچ چیزی از هسته 2.x نیست؛ اصلا LEDC ندارد.
۶کتابخانه‌ها واقعی‌اند✅ قبولهمان سه کتابخانه درس ۳.۳؛ digitalWrite و millis مال خود هسته‌اند.
۷انتظار بی‌پایان نیست✅ قبولنه delay در loop هست و نه while بی‌حد. (while (true) برای نبودن نمایشگر از قبل در ۳.۳ بود و آن‌جا عمدی است.)
۸مدیریت خطا❌ رددو سوراخ: (الف) وقتی رطوبت دوباره زیر ۷۰ می‌آید، هیچ چیزی LED را خاموش نمی‌کند و ممکن است برای همیشه روشن بماند؛ (ب) در خطای سنسور، loop قبل از کد چشمک برمی‌گردد و LED در هر وضعیتی بود یخ می‌زند.
۹امنیت✅ قبولنه Wi-Fi دارد نه رمز.
۱۰اول Wokwi، بعد برد❌ رد (در شبیه‌ساز دیده شد)رطوبت روی ۸۰: LED فقط هر ۲ ثانیه یک بار عوض می‌شود. برگشت به ۵۰: LED گاهی روشن می‌ماند.

سوال پیگیری. «در چه شرایطی این کد درست کار نمی‌کند؟» یک جواب خوب حداقل چشمک کند و گیر کردن LED را نام می‌برد. اگر هوش مصنوعی‌ات گفت «در همه حالت‌ها کار می‌کند»، همین خودش زنگ خطر است: تو همین الان سه حالت پیدا کردی که کار نمی‌کند.

کد اصلاح‌شده. منطق LED به یک تابع جدا می‌رود که در هر دور loop، قبل از نگهبان ۲ ثانیه‌ای اجرا می‌شود؛ رطوبت در یک متغیر سراسری می‌ماند تا آن تابع ببیندش. هر چیزی که در کارت‌ها نیامده، همان کد درس ۳.۳ است.

// ایستگاه هواشناسی کوچک (۳.۳) + LED هشدار رطوبت روی GPIO4، بازبینی و اصلاح‌شده
#include <Wire.h>
#include <Adafruit_GFX.h>
#include <Adafruit_SSD1306.h>
#include <DHT.h>

Adafruit_SSD1306 display(128, 64, &Wire, -1);
DHT dht(13, DHT22);

unsigned long lastRead = 0;
const int LED_PIN = 4;
const float HUM_LIMIT = 70.0;           // بالاتر از این: چشمک
float hum = NAN;                        // آخرین رطوبت، مشترک با updateLed()
bool ledOn = false;
unsigned long lastBlink = 0;

void showMessage(const char *msg) {
  display.clearDisplay();
  display.setTextSize(1);
  display.setCursor(0, 0);
  display.println(msg);
  display.display();
}

void updateLed() {
  if (!isnan(hum) && hum > HUM_LIMIT) {
    if (millis() - lastBlink >= 250) {  // عوض کردن هر ۲۵۰ میلی‌ثانیه = ۲ چشمک در ثانیه
      lastBlink = millis();
      ledOn = !ledOn;
      digitalWrite(LED_PIN, ledOn);
    }
  } else if (ledOn) {                   // رطوبت عادی یا خطای سنسور: LED خاموش
    ledOn = false;
    digitalWrite(LED_PIN, LOW);
  }
}

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  Wire.begin(21, 22);
  if (!display.begin(SSD1306_SWITCHCAPVCC, 0x3C)) {
    Serial.println("OLED not found!");
    while (true) delay(1000);
  }
  display.setTextColor(SSD1306_WHITE);
  dht.begin();
  showMessage("Waiting for DHT22...");
}

void loop() {
  updateLed();                              // در «هر» دور، قبل از نگهبان پایین
  if (millis() - lastRead < 2000) return;   // هنوز ۲ ثانیه نشده
  lastRead = millis();

  float t = dht.readTemperature();
  float h = dht.readHumidity();
  if (isnan(t) || isnan(h)) {
    hum = NAN;                              // رطوبت نامعلوم: LED خاموش می‌شود
    showMessage("DHT22 read error!");
    Serial.println("DHT22 read error");
    return;
  }
  hum = h;

  display.clearDisplay();
  display.setTextSize(1);
  display.setCursor(0, 0);
  display.println("Temperature");
  display.setTextSize(2);
  display.setCursor(0, 12);
  display.printf("%.1f C", t);
  display.setTextSize(1);
  display.setCursor(0, 36);
  display.println("Humidity");
  display.setTextSize(2);
  display.setCursor(0, 48);
  display.printf("%.1f %%", h);
  display.display();

  Serial.printf("T=%.1f C  H=%.1f %%  LED %s\n", t, h, h > HUM_LIMIT ? "blinking" : "off");
}
  1. متغیرهای جدید. پین LED، حد ۷۰ درصد به صورت ثابت نام‌دار، آخرین رطوبت (تا اولین خواندن درست NaN)، وضعیت LED و زمان آخرین تغییر. hum حالا باید سراسری باشد: در loop نوشته می‌شود و در updateLed خوانده. شروع با NaN یعنی «نامعلوم»، پس LED تا یک خواندن واقعی خاموش می‌ماند.
  2. updateLed(): چشمک فقط وقتی رطوبت زیاد است. هر ۲۵۰ میلی‌ثانیه LED برعکس می‌شود؛ در هر حالت دیگر (رطوبت عادی یا نامعلوم) یک بار خاموش می‌شود. شاخه else if (ledOn) هر دو سوراخ مرحله ۸ را می‌بندد: LED دیگر نمی‌تواند تصادفی روشن بماند. فقط وقتی چیزی عوض می‌شود روی پین می‌نویسد.
  3. اول از همه، در هر دور صدا زده می‌شود. قبل از خطی که اگر ۲ ثانیه نگذشته باشد از loop بیرون می‌رود. این خود اصلاح مرحله ۱ است. loop هزاران بار در ثانیه اجرا می‌شود، پس بررسی ۲۵۰ میلی‌ثانیه دقیق است. قاعده: کارهای سریع قبل از «نگهبان دم در»، کارهای کند بعد از آن.
  4. رطوبت را به‌روز نگه دار. در خطا NaN می‌شود و در موفقیت مقدار تازه را می‌گیرد. سنسور مرده نباید LED را روی یک عدد قدیمی در حال چشمک نگه دارد.
  5. یک کلمه اضافه در خط سریال. «LED blinking» یا «LED off». منطق را می‌توانی در Serial Monitor چک کنی، بدون این که به LED خیره شوی.

در Wokwi کتابخانه‌های Adafruit SSD1306 و DHT sensor library را از زبانه Library Manager اضافه کن. روی DHT22 کلیک کن و لغزنده رطوبت را بالا و پایین ۷۰ ببر.

تمرین ۲: شکار باگ

کد ساختگی «پرسش بد» در مثال ۱ را دوباره بخوان. بدون نگاه کردن به کارت‌های توضیح، همه اشکال‌هایش را فهرست کن (حداقل ۷ مورد). بعد نسخه درست را با قالب پرسش از هوش مصنوعی بخواه و مقایسه کن.

بخش ۲. حالا یک جواب ساختگی دوم را با چک‌لیست ده‌مرحله‌ای نمره بده. درخواست این بود: «نور LED را با پتانسیومتر کم و زیاد کن و تا وقتی دکمه نگه داشته شده خاموشش کن؛ LED روی GPIO4، پتانسیومتر روی GPIO34، دکمه روی GPIO27 به GND». حداقل ۴ اشکال پیدا کن و برای هر کدام بگو کدام مرحله چک‌لیست آن را می‌گیرد.

// جواب ساختگی AI: «نور LED را با پتانسیومتر کم و زیاد کن؛ دکمه خاموشش کند»
#include <WiFi.h>

const int LED = 34;
const int POT = 4;
const int BTN = 27;

void setup() {
  Serial.begin(115200);
  WiFi.begin("MyHome", "sunflower2024");
  pinMode(BTN, INPUT);
  ledcAttach(LED, 5000, 8);
}

void loop() {
  int v = analogRead(POT);
  if (digitalRead(BTN) == LOW) ledcWrite(LED, 0);
  else ledcWrite(LED, v);
  delay(10);
}

بخش ۱، معیار قبولی: قبولی اگر فهرستت حداقل ۷ مورد از ۱۱ اشکال جواب را داشته باشد، از جمله دو موردی که بی‌صدا خراب می‌کنند یا به سخت‌افزار آسیب می‌زنند: PWM روی GPIO35 (فقط ورودی) و فن مستقیم روی پین. نسخه درستی که با قالب از هوش مصنوعی می‌گیری باید ledcAttach(26, 25000, 8)، ledcWrite(26, duty)، بررسی isnan، زمان‌بندی با millis() داشته باشد و Wi-Fi نداشته باشد.

بخش ۱: اشکال‌های کد «پرسش بد»، با مرحله‌ای از چک‌لیست که هر کدام را می‌گیرد:

  1. Wi-Fi ناخواسته (مرحله ۱: هر خط اضافه، خطی است که باید بفهمی و به آن اعتماد کنی).
  2. رمز در کد (مرحله ۹).
  3. DHT11 به جای سنسوری که مشخص نشده بود (مرحله ۳).
  4. GPIO2 برای سنسور، که Strapping است (مرحله ۲).
  5. انتظار بی‌پایان برای Wi-Fi (مرحله ۷).
  6. ledcSetup/ledcAttachPin در 3.x وجود ندارند (مرحله ۵).
  7. GPIO35 فقط ورودی است و هیچ‌وقت نمی‌تواند PWM بدهد (مرحله ۲).
  8. NaN بررسی نمی‌شود (مرحله ۸).
  9. delay(5000) (مرحله ۷).
  10. فن مستقیم به پین، بدون ترانزیستور یا ماسفت (مرحله ۴).
  11. سرعت سریال 9600 که با عادت دوره نمی‌خواند (اشکال کوچک).

یک نسخه درست، نوشته‌شده از روی «پرسش خوب» (DHT22 روی GPIO13، گیت ماسفت logic-level روی GPIO26، PWM با ۲۵ کیلوهرتز، زیر ۲۸ درجه خاموش، بالای ۳۵ درجه تمام سرعت، بینشان خطی، هسته 3.x). روی برد واقعی گیت ماسفت با حدود ۱۰۰ اهم به GPIO26 می‌رود، یک مقاومت ۱۰ کیلواهمی از گیت به GND فن را هنگام بوت خاموش نگه می‌دارد، فن بین منبع ۱۲ ولت و درین است و یک دیود هرزگرد دو سر فن قرار می‌گیرد (درس ۳.۴).

// فن کنترل‌شده با دما: DHT22 روی GPIO13، گیت ماسفت روی GPIO26، PWM با ۲۵ کیلوهرتز
#include <DHT.h>

const int PIN_DHT = 13;
const int PIN_FAN = 26;                 // گیت یک ماسفت logic-level، هرگز خود فن
const float T_OFF  = 28.0;              // برابر یا پایین‌تر: فن خاموش
const float T_FULL = 35.0;              // برابر یا بالاتر: تمام سرعت
DHT dht(PIN_DHT, DHT22);
unsigned long lastRead = 0;

int dutyFor(float t) {                  // ۲۸ درجه ← 0 ... ۳۵ درجه ← 255، یک خط راست
  if (t <= T_OFF)  return 0;
  if (t >= T_FULL) return 255;
  return (int)((t - T_OFF) * 255.0 / (T_FULL - T_OFF));
}

void setup() {
  Serial.begin(115200);
  dht.begin();
  ledcAttach(PIN_FAN, 25000, 8);        // هسته 3.x: پین، ۲۵ کیلوهرتز (بی‌صدا)، ۸ بیت
  ledcWrite(PIN_FAN, 0);                // شروع با فن خاموش
}

void loop() {
  if (millis() - lastRead < 2000) return;   // DHT22 بین دو خواندن ۲ ثانیه لازم دارد
  lastRead = millis();
  float t = dht.readTemperature();
  if (isnan(t)) {
    ledcWrite(PIN_FAN, 255);            // سنسور از دست رفت: تمام سرعت انتخاب امن است
    Serial.println("DHT22 error -> fan at full speed");
    return;
  }
  int duty = dutyFor(t);
  ledcWrite(PIN_FAN, duty);             // در 3.x عدد اول «پین» است
  Serial.printf("T=%.1f C  fan duty=%d/255\n", t, duty);
}
  1. پین‌ها و دو حد دما، همه با اسم. هر عددی که در پرسش آمده بود، بالای برنامه اسم دارد. GPIO26 فقط گیت ماسفت را می‌راند؛ جریان فن هیچ‌وقت از ESP32 نمی‌گذرد (اصلاح اشکال ۱۰).
  2. dutyFor(): از دما به سرعت. ۲۸ درجه یا کمتر ← 0، ۳۵ درجه یا بیشتر ← 255، و بینشان یک خط راست. یک تابع کوچک که با ماشین‌حساب چکش می‌کنی: ۳۱٫۵ درجه وسط راه است، پس ۱۲۷. جمع کردن کل قاعده در یک تابع، تستش را آسان می‌کند.
  3. setup بدون Wi-Fi، با 115200 و API هسته 3.x. ledcAttach(pin, 25000, 8) و فن خاموش شروع می‌کند. ۲۵ کیلوهرتز بالاتر از محدوده شنوایی است، پس فن سوت نمی‌کشد. همین یک خط جای دو خط 2.x را می‌گیرد (اصلاح اشکال‌های ۱، ۲، ۵، ۶، ۷ و ۱۱).
  4. هر ۲ ثانیه یک خواندن، بدون متوقف کردن برنامه. جای delay(5000) را می‌گیرد؛ DHT22 که سریع‌تر از این داده تازه نمی‌دهد.
  5. خواندن ناموفق فن را تمام سرعت می‌کند. در یک سیستم خنک‌کننده، «دمای نامعلوم» باید یعنی «خنک کن»، نه «خاموش». سکوت، خطرناک‌ترین رفتار کد بد بود (اشکال ۸).
  6. دیوتی را روی پین بنویس و چاپش کن. در 3.x آرگومان اول ledcWrite پین است. عدد چاپ‌شده اجازه می‌دهد فرمول را با جدول «چه باید ببینی؟» مقایسه کنی.

در Wokwi کتابخانه DHT sensor library را اضافه کن. یک LED آبی روی GPIO26 جای ماسفت و فن را گرفته: نورش همان دیوتی را نشان می‌دهد. روی DHT22 کلیک کن و دما را بین ۲۵ و ۳۶ جابه‌جا کن.

// دیمر، اصلاح‌شده: پتانسیومتر روی GPIO34 نور LED روی GPIO4 را تنظیم می‌کند؛ دکمه GPIO27 خاموشش می‌کند
const int LED = 4;                      // یک پین خروجی واقعی
const int POT = 34;                     // ADC1 و فقط‌ورودی: عالی برای پتانسیومتر
const int BTN = 27;                     // دکمه به GND

void setup() {
  Serial.begin(115200);
  pinMode(BTN, INPUT_PULLUP);           // پین معلق نماند
  ledcAttach(LED, 5000, 8);             // ۸ بیت: دیوتی 0..255
}

void loop() {
  int v = analogRead(POT);              // 0..4095
  int duty = v >> 4;                    // 0..255، همان بازه‌ای که ۸ بیت می‌فهمد
  if (digitalRead(BTN) == LOW) duty = 0;
  ledcWrite(LED, duty);
  delay(10);
}
  1. پین‌های خود درخواست. LED روی ۴، پتانسیومتر روی ۳۴ (ADC1)، دکمه روی ۲۷. سیم‌کشی را درخواست تعیین می‌کند، نه مدل. بدون Wi-Fi حتی پین ADC2 هم کار می‌کرد، ولی ADC1 اگر بعدا Wi-Fi اضافه شود هم درست می‌ماند.
  2. بالاکش برای دکمه، PWM هشت‌بیتی برای LED. INPUT_PULLUP پین را در حالت رها بودن دکمه HIGH نگه می‌دارد، پس هیچ‌وقت معلق نمی‌ماند.
  3. بخوان، مقیاس کن، بنویس. v >> 4 یعنی تقسیم بر ۱۶: بازه ۰ تا ۴۰۹۵ می‌شود ۰ تا ۲۵۵. همان ترفند PortableDemo در درس ۶.۴: حالا کل مسیر پیچ روی کل بازه نور می‌نشیند.

پتانسیومتر را بچرخان: نور LED نرم کم و زیاد می‌شود. دکمه را نگه دار: LED خاموش می‌شود.

تمرین ۳: معلم خصوصی

کد شمارنده پالس (مثال ۳) را بدون توضیح‌های ما به یک دستیار هوش مصنوعی بده و با «پرسش توضیحی» بخواه خط به خط توضیح دهد. جوابش را با کارت‌های توضیح همین صفحه مقایسه کن. کجا یکی بودند؟ کجا چیزی گفت که ما نگفتیم؟ آیا جایی اشتباه کرد؟ یکی از سه آزمایشی را که پیشنهاد داد، روی Wokwi اجرا کن.

چه باید ببینی؟

جواب درست یکتایی از هوش مصنوعی وجود ندارد، ولی یک جواب خوب این شش نکته را پوشش می‌دهد. در توضیح هوش مصنوعی‌ات تیکشان بزن:

  • volatile: مقدار باید هر بار از حافظه خوانده شود چون وقفه آن را عوض می‌کند. (امتیاز اضافه اگر بگوید volatile به تنهایی pulses++ را امن نمی‌کند؛ آن کار قفل است.)
  • قفل (mux): وقفه و loop هیچ‌وقت هم‌زمان به pulses دست نمی‌زنند، پس «بخوان و بعد صفر کن» مثل یک قدم عمل می‌کند.
  • IRAM_ATTR و ISR کوتاه: داخلش نه Serial نه delay.
  • INPUT_PULLUP + FALLING: لبه‌های HIGH به LOW را می‌شمارد؛ دکمه مکانیکی لرزش (bounce) دارد.
  • زمان‌بندی با millis() هر یک ثانیه، static، و تفریقی که از سرریز ۴۹ روزه جان سالم به در می‌برد.
  • چاپ بعد از آزاد شدن قفل، هرگز داخل آن.

زنگ‌های خطر (هوش مصنوعی اشتباه می‌کند یا حدس می‌زند): «volatile متغیر را thread-safe» یا «اتمیک» می‌کند؛ «millis() - last بعد از ۴۹ روز خراب می‌شود»؛ «چاپ داخل ISR اگر کوتاه باشد اشکالی ندارد».

آزمایش‌های رایج واقعا چه نشان می‌دهند:

  • در Wokwi یک بار دکمه را بزن: معمولا pulses/s: 1، گاهی ۲ یا ۳. این لرزش دکمه است، نه باگ شمارنده.
  • volatile را بردار: به احتمال زیاد در این اسکچ هیچ تغییر دیدنی‌ای نمی‌بینی، چون صدا زدن قفل دور خواندن، خودش خواندن تازه از حافظه را اجباری می‌کند. این ثابت نمی‌کند volatile بی‌فایده است؛ در کدی بدون قفل، باگ می‌تواند ظاهر شود. هوش مصنوعی‌ای که پیش‌بینی کند «شمارنده همیشه صفر می‌ماند» بیش از حد مطمئن است.
  • یک Serial.printf داخل ISR بگذار: معمولا کمی بعد از اولین فشار کرش و ریبوت (یک Guru Meditation یا پیام «assert failed»)؛ گاهی مدتی به نظر کار می‌کند. در هر دو حالت ممنوع است.
  • آزمایش فرکانس معلوم در جواب: یک pulses/s: 100 ثابت، گاهی ۹۹ یا ۱۰۱.

مقایسه، قدم به قدم.

  1. توضیح هوش مصنوعی را کنار شش کارت توضیح زیر مثال ۳ بگذار. برای هر کارت علامت بزن: «همان را گفت»، «بیشتر گفت»، «کمتر گفت» یا «چیز دیگری گفت».
  2. هر چیزی که «چیز دیگری» خورده، در یکی از دو دسته می‌رود: (الف) یک جزئیات تازه و درست (در مستندات رسمی چکش کن، مثلا صفحه‌های GPIO و وقفه Arduino-ESP32)، یا (ب) یک اشتباه. زنگ‌های خطر «چه باید ببینی؟» رایج‌ترین اشتباه‌ها هستند.
  3. برای هر کدام از سه آزمایش هوش مصنوعی، پیش‌بینی‌اش را قبل از اجرا یادداشت کن. بعد اجرا و مقایسه کن. آزمایشی که نتیجه‌اش هوش مصنوعی را غافلگیر کرد، باارزش‌ترین یافته کل تمرین است.

یک آزمایش محکم که خودت اضافه کنی: یک فرکانس معلوم به شمارنده بده. با دکمه نمی‌شود دقیق بودن شمارنده را ثابت کرد، چون نمی‌توانی تعداد معلومی فشار بدهی. ESP32 می‌تواند پالس‌های خودش را بسازد: LEDC یک موج مربعی ۱۰۰ هرتز روی GPIO26 می‌دهد و یک سیم جامپر آن را به GPIO27 می‌برد. روی برد واقعی یک جامپر از GPIO26 به GPIO27 وصل کن و در این تست دکمه GPIO27 را فشار نده (خروجی را به GND اتصال کوتاه می‌کند).

// آزمایش: یک فرکانس معلوم به شمارنده پالس بده (سیم جامپر از GPIO26 به GPIO27)
volatile uint32_t pulses = 0;
portMUX_TYPE mux = portMUX_INITIALIZER_UNLOCKED;

void IRAM_ATTR onPulse() {
  portENTER_CRITICAL_ISR(&mux);
  pulses++;
  portEXIT_CRITICAL_ISR(&mux);
}

void setup() {
  Serial.begin(115200);
  pinMode(27, INPUT_PULLUP);
  attachInterrupt(digitalPinToInterrupt(27), onPulse, FALLING);
  ledcAttach(26, 100, 10);              // موج مربعی ۱۰۰ هرتز روی GPIO26
  ledcWrite(26, 512);                   // 512 از 1024 = دیوتی ۵۰ درصد
}

void loop() {
  static uint32_t last = 0;
  if (millis() - last >= 1000) {
    last = millis();
    portENTER_CRITICAL(&mux);
    uint32_t n = pulses;
    pulses = 0;
    portEXIT_CRITICAL(&mux);
    Serial.printf("pulses/s: %lu\n", n);
  }
}
  1. شمارنده پالس مثال ۳ بدون تغییر، به‌علاوه دو خط. ledcAttach(26, 100, 10) یک سیگنال ۱۰۰ هرتز روی GPIO26 می‌سازد؛ ledcWrite(26, 512) آن را ۵۰ درصد می‌کند (۵۱۲ از ۱۰۲۴ پله‌ای که ۱۰ بیت می‌دهد). موج مربعی در هر دوره دقیقا یک لبه پایین‌رونده دارد، پس ۱۰۰ هرتز یعنی دقیقا ۱۰۰ شمارش در ثانیه. دقت ۱۰ بیتی انتخاب شده چون فرکانس‌های خیلی پایین برای تقسیم‌کننده ساعت LEDC بیت کافی لازم دارند.
  2. همان گزارش ثانیه‌ای. دیدن ۱۰۰ پشت سر هم، وقفه، قفل و زمان‌بندی را با هم ثابت می‌کند. ۹۹ یا ۱۰۱ گاه‌به‌گاه طبیعی است: پنجره یک ثانیه‌ای و سیگنال هم‌گام نیستند، پس یک لبه ممکن است درست قبل یا بعد از مرز بیفتد.

هوش مصنوعی دستیار است، نه جایگزین؛ چون با اطمینان کامل هم کد درست می‌نویسد هم کد غلط (پین نامناسب، API هسته ۲.x، ولتاژ ۵ ولت). با قالب پرسش (برد، نسخه هسته، سیم‌کشی، کتابخانه، هدف، محدودیت، خروجی) جواب بهتر بگیر و برای عیب‌یابی خطای کامل و کد کامل بده. هر کد را با چک‌لیست ده مرحله‌ای بازبینی کن، اول در Wokwi اجرا کن، و هرگز رمز یا کلید واقعی را در گفتگو نچسبان.
