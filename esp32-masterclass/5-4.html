بخش ۱: FreeRTOS، چند کار هم‌زمان بدون قاطی شدن

مشکل: loop() تنها، زود شلوغ می‌شود

فرض کن دستگاهی می‌خواهی که: یک LED را هر ۲۵۰ میلی‌ثانیه چشمک بزند، یک LED دیگر را هر ۱ ثانیه، هر ۲۰۰ میلی‌ثانیه پتانسیومتر را بخواند، هر ۱۰ دقیقه هوای تهران را از اینترنت بگیرد، و همیشه به صفحه وب جواب بدهد. با delay() غیرممکن است، چون هر delay همه کارهای دیگر را متوقف می‌کند. با millis() (درس ۳.۱) شدنی است، ولی loop پر از if (millis() - lastX >= ...) می‌شود. بدتر از همه: گرفتن هوا از اینترنت ممکن است ۲ تا ۵ ثانیه طول بکشد و در این مدت LEDها و صفحه وب هم منتظر می‌مانند.

راه حل حرفه‌ای این است که هر کار را جدا بنویسی، انگار هر کدام برنامه کوچک خودش را دارد، و یک «مدیر» تصمیم بگیرد هر لحظه نوبت کیست. این مدیر FreeRTOS است: یک سیستم‌عامل بی‌درنگ (Real-Time Operating System) کوچک که همیشه روی ESP32 در حال اجراست، حتی وقتی تو خبر نداری.

مثال از زندگی روزمره: آشپزخانه رستوران

یک رستوران را تصور کن. اگر فقط یک آشپز داشته باشد (این همان loop تنهاست)، باید برنج را بگذارد، بدود کباب را برگرداند، بدود سالاد درست کند، و اگر پای تلفن سفارش‌ها گیر کند، کباب می‌سوزد. رستوران واقعی چند آشپز دارد (هر کدام یک Task): یکی مسئول برنج، یکی کباب، یکی سالاد. سرآشپز (زمان‌بند FreeRTOS یا Scheduler) تصمیم می‌گیرد چه کسی از اجاق استفاده کند. ESP32 دو اجاق دارد (دو هسته)، پس دو آشپز می‌توانند دقیقا هم‌زمان بپزند.

آشپزها با هم حرف نمی‌زنند که کار هم را خراب نکنند؛ سفارش را روی پیشخوان می‌گذارند (این Queue یا صف است). و فقط یک چاقوی بزرگ هست؛ هر کس برش داشت، بقیه صبر می‌کنند تا سر جایش بگذارد (این Mutex است).

اولین Taskها: دو LED با دو سرعت

مدار: دو LED، هر کدام با مقاومت ۲۲۰ اهم خودش، روی GPIO4 و GPIO5. پتانسیومتر روی GPIO34 را هم همین حالا وصل کن چون در مثال بعدی لازم است.

دقت کن: GPIO5 یک Strapping Pin است

GPIO5 هنگام روشن شدن نقش کوچکی در تنظیم بوت دارد. یک LED با مقاومت ۲۲۰ اهم مشکلی ایجاد نمی‌کند، ولی اگر برد تو موقع روشن شدن رفتار عجیبی داشت، LED دوم را به GPIO18 ببر و عدد را در کد عوض کن (درس ۱.۳).

// دو LED با دو سرعت مختلف، هر کدام در Task خودش
const int LED_FAST = 4;   // LED سریع
const int LED_SLOW = 5;   // LED کند

void blinkFast(void *param) {          // تابع Task اول
  pinMode(LED_FAST, OUTPUT);
  bool on = false;
  for (;;) {                           // Task هرگز نباید تمام شود
    on = !on;
    digitalWrite(LED_FAST, on);
    vTaskDelay(pdMS_TO_TICKS(250));    // ۲۵۰ میلی‌ثانیه کنار برو
  }
}

void blinkSlow(void *param) {          // تابع Task دوم
  pinMode(LED_SLOW, OUTPUT);
  bool on = false;
  for (;;) {
    on = !on;
    digitalWrite(LED_SLOW, on);
    vTaskDelay(pdMS_TO_TICKS(1000));   // ۱ ثانیه
  }
}

void setup() {
  Serial.begin(115200);
  xTaskCreatePinnedToCore(
    blinkFast,     // کدام تابع
    "blinkFast",   // اسم Task (فقط برای عیب‌یابی)
    2048,          // اندازه Stack به «بایت»
    NULL,          // پارامتر ورودی (نداریم)
    1,             // اولویت
    NULL,          // دستگیره Task (لازم نداریم)
    1);            // هسته ۱
  xTaskCreatePinnedToCore(blinkSlow, "blinkSlow", 2048, NULL, 1, NULL, 1);
  Serial.printf("setup() runs on core %d\n", xPortGetCoreID());
}

void loop() {                          // loop خودش هم یک Task است
  Serial.printf("loop() alive on core %d, millis=%lu\n",
                xPortGetCoreID(), millis());
  delay(2000);
}
  1. تابع Task. هر Task یک تابع معمولی با این شکل دقیق است: void اسم(void *param). ورودی param یک «اشاره‌گر به هر چیزی» است که موقع ساختن Task می‌توانی به آن بدهی. FreeRTOS برای همه Taskها یک شکل ثابت می‌خواهد تا بتواند با همه یکسان رفتار کند. اگر شکل تابع فرق کند، کامپایلر خطا می‌دهد.
  2. کار یک‌باره اول Task. مثل یک setup کوچک مخصوص همین Task: پین را خروجی می‌کند و یک متغیر محلی برای وضعیت LED می‌سازد. متغیر on داخل Task است و روی Stack همین Task زندگی می‌کند. هر Task Stack جدای خودش را دارد، پس دو Task با متغیرهای هم‌نام قاطی نمی‌شوند.
  3. حلقه بی‌پایان for (;;). Task باید تا ابد در یک حلقه بماند. این همان نقش loop() است. اگر تابع Task به } آخر برسد و return کند، ESP32 با خطا (abort) ریست می‌شود. اگر واقعا کار Task تمام شد، باید خودش را با vTaskDelete(NULL); پاک کند.
  4. vTaskDelay و pdMS_TO_TICKS. vTaskDelay به زمان‌بند می‌گوید «من فعلا کاری ندارم، اجاق را به دیگران بده». واحد آن «تیک» است؛ pdMS_TO_TICKS(250) میلی‌ثانیه را به تیک تبدیل می‌کند. روی ESP32 آردوینو هر تیک ۱ میلی‌ثانیه است (CONFIG_FREERTOS_HZ=1000)، پس تبدیل عدد را عوض نمی‌کند؛ ولی اگر روزی کد را روی سیستمی با تیک ۱۰ میلی‌ثانیه ببری، بدون این ماکرو زمان‌ها ۱۰ برابر می‌شوند. عادت درست را از اول بساز.
  5. Task دوم. دقیقا همان الگو، فقط با پین و زمان دیگر. ببین چقدر ساده شد: هر Task فقط به کار خودش فکر می‌کند. هیچ if (millis() - last ...) درهمی نیست.
  6. xTaskCreatePinnedToCore با هفت ورودی. به ترتیب: تابع، اسم، اندازه Stack، پارامتر، اولویت، دستگیره (Handle)، شماره هسته. «PinnedToCore» یعنی «به این هسته سنجاقش کن». اگر هسته را مشخص نکنی (تابع xTaskCreate)، Task می‌تواند روی هر دو هسته اجرا شود؛ برای شروع، سنجاق کردن رفتار را قابل پیش‌بینی‌تر می‌کند.
  7. 2048 یعنی ۲۰۴۸ بایت. این مهم‌ترین نکته ESP32 است: در FreeRTOS نسخه ESP-IDF اندازه Stack به بایت است. در FreeRTOS استاندارد (مثلا روی STM32) همین عدد به «word» است و هر word چهار بایت؛ یعنی 2048 آنجا ۸ کیلوبایت می‌شد. اگر کدی از اینترنت برداشتی که Stack را 512 گذاشته، روی ESP32 فقط ۵۱۲ بایت می‌گیری و احتمالا برد کرش می‌کند. برای Task ساده ۲۰۴۸، برای Task با Serial.printf حدود ۳۰۰۰ تا ۴۰۹۶، و برای Task با HTTPS دست‌کم ۸ تا ۱۲ کیلوبایت بگذار.
  8. اولویت (Priority). عددی از 0 تا 24؛ بزرگ‌تر یعنی مهم‌تر. وقتی دو Task آماده اجرا هستند، زمان‌بند همیشه اولویت بالاتر را انتخاب می‌کند. Taskهای هم‌اولویت به نوبت (هر تیک) اجرا می‌شوند. ۱ همان اولویت loop است. برای شروع همه را ۱ یا ۲ بگذار. اولویت بالا به Taskی بده که زود باید جواب بدهد و کوتاه کار می‌کند؛ Task طولانی با اولویت بالا بقیه را گرسنه نگه می‌دارد.
  9. Task دوم در یک خط. همان هفت ورودی، بدون توضیح. بعد از این خط سه Task روی هسته ۱ داریم: loopTask و دو چشمک‌زن؛ به‌علاوه Taskهای خود سیستم روی هسته ۰.
  10. loop هم کار خودش را می‌کند. هر ۲ ثانیه یک پیام چاپ می‌کند؛ xPortGetCoreID() شماره هسته فعلی را برمی‌گرداند. نکته مهم: در ESP32 آردوینو delay() در واقع همان vTaskDelay است (در core تعریف شده vTaskDelay(ms / portTICK_PERIOD_MS))، پس delay در loop هم CPU را به Taskهای دیگر می‌دهد و چشمک‌ها قطع نمی‌شوند. ولی delayMicroseconds() و حلقه‌های خالی مثل while(...) {} واقعا CPU را قفل می‌کنند.

و روی برد: LED قرمز ۲ بار در ثانیه و LED سبز هر ۲ ثانیه یک بار (۱ ثانیه روشن، ۱ ثانیه خاموش) چشمک می‌زند، کاملا مستقل از هم.

پس vTaskDelay با delay چه فرقی دارد؟

در ESP32 آردوینو از نظر رفتار تقریبا هیچ؛ هر دو Task فعلی را می‌خوابانند و CPU آزاد می‌شود. تفاوت در واحد است: delay(ms) میلی‌ثانیه می‌گیرد و vTaskDelay(ticks) تیک. داخل Taskها از vTaskDelay(pdMS_TO_TICKS(...)) استفاده می‌کنیم چون زبان خود FreeRTOS است و روی هر سیستمی درست کار می‌کند. اگر می‌خواهی کاری دقیقا هر ۱۰۰ میلی‌ثانیه تکرار شود (بدون این که زمان اجرای خود کار به آن اضافه شود)، از vTaskDelayUntil استفاده کن.

انتقال امن داده: صف (Queue)

حالا مسئله واقعی: یک Task سنسور را می‌خواند و Task دیگری باید آن را نمایش بدهد. اولین فکر: «یک متغیر سراسری بگذارم، یکی بنویسد و دیگری بخواند». برای یک int ساده معمولا کار می‌کند، ولی برای داده بزرگ‌تر (مثلا یک struct با دما و رطوبت و زمان) ممکن است Task نمایش وسط نوشتن آن را بخواند: دمای جدید با رطوبت قدیمی! به این باگ «Race Condition» (مسابقه) می‌گویند و بدترین نوع باگ است، چون هر هزار بار یک بار رخ می‌دهد.

صف راه حل رسمی FreeRTOS است. صف یک لوله با تعداد خانه مشخص است: یک Task از یک سر کپی داده را می‌گذارد و Task دیگر از سر دیگر برمی‌دارد، به همان ترتیب (اول وارد، اول خارج). FreeRTOS تضمین می‌کند که هیچ‌وقت داده نصفه جابه‌جا نشود.

// Task حسگر ← صف (Queue) ← Task نمایش، به‌علاوه قفل Serial
const int POT_PIN = 34;          // پتانسیومتر (ADC1، فقط ورودی)
const int LED_PIN = 4;           // LED با روشنایی متغیر (PWM)

QueueHandle_t potQueue;          // صف بین دو Task
SemaphoreHandle_t serialMutex;   // قفل Serial Monitor
TaskHandle_t sensorHandle = NULL;
TaskHandle_t displayHandle = NULL;

void sensorTask(void *param) {
  for (;;) {
    int raw = analogRead(POT_PIN);                  // 0 تا 4095
    if (xQueueSend(potQueue, &raw, 0) != pdPASS) {  // صبر نکن
      // صف پر است: این نمونه را دور بریز
    }
    vTaskDelay(pdMS_TO_TICKS(200));                 // ۵ بار در ثانیه
  }
}

void displayTask(void *param) {
  int value;
  for (;;) {
    // تا ۱ ثانیه منتظر داده بمان؛ در این مدت CPU آزاد است
    if (xQueueReceive(potQueue, &value, pdMS_TO_TICKS(1000)) == pdPASS) {
      ledcWrite(LED_PIN, value / 16);               // 0..4095 → 0..255
      if (xSemaphoreTake(serialMutex, pdMS_TO_TICKS(100)) == pdTRUE) {
        Serial.printf("pot=%4d  led=%3d\n", value, value / 16);
        xSemaphoreGive(serialMutex);                // قفل را پس بده
      }
    }
  }
}

void setup() {
  Serial.begin(115200);
  ledcAttach(LED_PIN, 5000, 8);                     // 5kHz، ۸ بیت
  potQueue = xQueueCreate(10, sizeof(int));         // ۱۰ خانه، هر کدام یک int
  serialMutex = xSemaphoreCreateMutex();
  if (potQueue == NULL || serialMutex == NULL) {
    Serial.println("Out of memory!");
    while (true) delay(1000);
  }
  xTaskCreatePinnedToCore(sensorTask, "sensor", 3072, NULL, 2, &sensorHandle, 1);
  xTaskCreatePinnedToCore(displayTask, "display", 4096, NULL, 1, &displayHandle, 1);
}

void loop() {
  delay(5000);
  if (xSemaphoreTake(serialMutex, portMAX_DELAY) == pdTRUE) {
    Serial.printf("[stack] sensor free=%u B, display free=%u B, heap=%u B\n",
                  (unsigned)uxTaskGetStackHighWaterMark(sensorHandle),
                  (unsigned)uxTaskGetStackHighWaterMark(displayHandle),
                  (unsigned)ESP.getFreeHeap());
    xSemaphoreGive(serialMutex);
  }
}
  1. دستگیره‌ها (Handle). QueueHandle_t و SemaphoreHandle_t و TaskHandle_t مثل «شماره تلفن» صف، قفل و Taskها هستند؛ خود شیء را FreeRTOS در حافظه می‌سازد و ما فقط شماره‌اش را نگه می‌داریم. سراسری هستند تا همه Taskها به آن‌ها دسترسی داشته باشند. خود دستگیره بعد از ساخته شدن عوض نمی‌شود، پس سراسری بودنش خطری ندارد.
  2. خواندن و فرستادن. xQueueSend(صف، آدرس داده، زمان صبر) محتوای raw را کپی می‌کند و در صف می‌گذارد. علامت & یعنی «آدرس این متغیر». چون کپی می‌شود، بعد از این خط raw می‌تواند عوض شود بدون این که داده داخل صف خراب شود. زمان صبر 0 یعنی «اگر صف پر است منتظر نمان»؛ Task سنسور نباید به خاطر کندی نمایش عقب بیفتد.
  3. اگر صف پر بود. xQueueSend مقدار errQUEUE_FULL برمی‌گرداند و ما عمدا کاری نمی‌کنیم: این نمونه دور ریخته می‌شود. در دستگاه واقعی باید تصمیم بگیری: «داده جدید مهم‌تر است یا قدیمی؟». برای نمایش، تازه‌ترین داده مهم است؛ برای لاگ، همه داده‌ها. این تصمیم را آگاهانه بگیر، نه تصادفی.
  4. xQueueReceive با زمان صبر. Task نمایش تا ۱ ثانیه منتظر می‌ماند تا چیزی به صف برسد. در این مدت واقعا می‌خوابد و صفر درصد CPU مصرف می‌کند. این زیباترین بخش صف است: Task نمایش نیازی به vTaskDelay ندارد، چون خود انتظار برای صف، CPU را آزاد می‌کند. به محض رسیدن داده، FreeRTOS بیدارش می‌کند.
  5. روشنایی LED. عدد ۱۲ بیتی ADC (۰ تا ۴۰۹۵) تقسیم بر ۱۶ می‌شود ۰ تا ۲۵۵، یعنی بازه PWM هشت بیتی. همان ledcWrite درس ۳.۲ با API نسخه ۳. در core 2.x باید از ledcSetup و ledcAttachPin با شماره کانال استفاده می‌کردی.
  6. Mutex دور Serial. xSemaphoreTake چاقو را برمی‌دارد (تا ۱۰۰ میلی‌ثانیه صبر می‌کند اگر دست کس دیگری است)، چاپ می‌کند و xSemaphoreGive آن را پس می‌دهد. بدون قفل، اگر loop و Task نمایش هم‌زمان چاپ کنند، خط‌ها وسط هم می‌افتند: pot=12[stack] sens34 led=.... هر منبع مشترکی (Serial، I2C، یک فایل، یک متغیر بزرگ) را که بیش از یک Task از آن استفاده می‌کنند، با Mutex محافظت کن. قانون طلایی: هر Take یک Give دارد، وگرنه بقیه تا ابد منتظر می‌مانند.
  7. ساختن صف و قفل و بررسی موفقیت. xQueueCreate(10, sizeof(int)) صفی با ۱۰ خانه می‌سازد که هر خانه اندازه یک int است (۴ بایت). صف و قفل از Heap حافظه گرفته می‌شوند. اگر حافظه تمام باشد NULL برمی‌گردد، و استفاده از NULL یعنی کرش. همیشه بررسی کن. صف و قفل باید قبل از ساختن Taskها ساخته شوند، چون Taskها بلافاصله شروع به استفاده می‌کنند.
  8. اولویت‌ها و دستگیره‌ها. Task حسگر اولویت ۲ دارد و Task نمایش ۱. این بار دستگیره (&sensorHandle) را می‌گیریم. خواندن سنسور کوتاه و حساس به زمان است، پس اولویت بالاتر. دستگیره را لازم داریم تا بعدا از بیرون درباره Task سؤال کنیم (مثلا چقدر Stack مصرف کرده).
  9. uxTaskGetStackHighWaterMark. «علامت بالاترین سطح آب» یعنی کمترین مقدار Stack آزادی که این Task تا حالا داشته، در ESP-IDF به بایت. این عدد ابزار تنظیم Stack است: اگر برای Task ۴۰۹۶ بایت گذاشتی و این عدد ۲۸۰۰ است، یعنی حداکثر حدود ۱۳۰۰ بایت مصرف شده؛ می‌توانی Stack را کم کنی و RAM آزاد کنی. اگر زیر ۵۰۰ بایت شد، Stack را بیشتر کن. ESP.getFreeHeap هم کل RAM آزاد را نشان می‌دهد.

(عددهای Stack و Heap روی برد تو کمی فرق می‌کنند؛ مهم این است که بدانی چطور بخوانی‌شان.)

در Wokwi امتحان کن: پتانسیومتر را بچرخان و ببین روشنایی LED و عددها در Serial Monitor عوض می‌شوند. FreeRTOS در Wokwi کامل شبیه‌سازی می‌شود، پس Taskها، صف و Mutex دقیقا مثل برد واقعی رفتار می‌کنند. کتابخانه اضافه‌ای لازم نیست.

وقتی Stack کم می‌آید (Stack Overflow)

هر Task یک جعبه حافظه به اندازه‌ای که گفتی دارد. متغیرهای محلی، آرایه‌ها و هر تابعی که صدا می‌زنی در این جعبه جا می‌گیرند. Serial.printf خودش چند صد بایت می‌خواهد و یک اتصال HTTPS چند کیلوبایت. اگر جعبه لبریز شود، داده روی حافظه همسایه ریخته می‌شود. خوشبختانه ESP32 مراقب است و قبل از خرابی کامل، این را چاپ و برد را ریست می‌کند:

***ERROR*** A stack overflow in task display has been detected. Backtrace: 0x40081f2e:0x3ffb5f40 0x40086d15:0x3ffb5f60 ... Rebooting...

علامت‌های رایج Stack کم: همین پیام، یا Guru Meditation Error: Core 1 panic'ed (LoadProhibited)، یا ریست‌های تصادفی وقتی Task کار سنگین‌تری می‌کند (مثلا اولین اتصال HTTPS). درمان: عدد Stack را در xTaskCreatePinnedToCore دو برابر کن، بعد با uxTaskGetStackHighWaterMark ببین واقعا چقدر لازم است. آرایه بزرگ (مثلا char buf[4000]) را هم داخل Task محلی تعریف نکن؛ سراسری یا static کن تا از Stack بیرون برود.

نگهبان Task (Task Watchdog): چرا برد خودش ریست می‌شود؟

ESP32 یک «نگهبان» دارد که هر چند وقت یک بار سر می‌زند ببیند Taskهای مهم زنده‌اند. در core آردوینو این نگهبان Task بیکار هسته ۰ (IDLE0) را زیر نظر دارد، با مهلت ۵ ثانیه (CONFIG_ESP_TASK_WDT_TIMEOUT_S=5). Task بیکار فقط وقتی اجرا می‌شود که هیچ Task دیگری روی آن هسته کار نداشته باشد. پس اگر یک Task روی هسته ۰ پنج ثانیه بدون وقفه کار کند، IDLE0 هیچ‌وقت نوبت نمی‌گیرد و نگهبان نتیجه می‌گیرد «سیستم قفل شده» و برد را ریست می‌کند.

مثال از زندگی روزمره

نگهبان شب یک ساختمان هر ساعت باید دکمه‌ای را در لابی بزند تا سیستم بفهمد بیدار است. اگر کسی جلوی لابی را با یک کار بی‌پایان بسته باشد و نگهبان نتواند به دکمه برسد، زنگ خطر به صدا درمی‌آید. vTaskDelay همان «راه دادن» به نگهبان است.

// ❌ نمونه عمدا غلط: Task حریص بدون استراحت روی هسته ۰
volatile unsigned long counter = 0;

void greedyTask(void *param) {
  for (;;) {
    counter++;              // بی‌وقفه کار می‌کند و هرگز کنار نمی‌رود
    // vTaskDelay(1);       // ✅ درمان: این خط را از حالت توضیح دربیاور
  }
}

void setup() {
  Serial.begin(115200);
  xTaskCreatePinnedToCore(greedyTask, "greedy", 2048, NULL, 1, NULL, 0);
}

void loop() {
  Serial.println(counter);
  delay(1000);
}
  1. Task حریص. یک حلقه بی‌پایان که فقط عدد را زیاد می‌کند و هیچ‌وقت vTaskDelay صدا نمی‌زند. این Task آماده اجراست و اولویتش (۱) از IDLE0 (۰) بیشتر است؛ پس زمان‌بند همیشه او را انتخاب می‌کند و IDLE0 گرسنه می‌ماند.
  2. روی هسته ۰. آخرین ورودی 0 است. اگر همین Task را روی هسته ۱ بگذاری، در تنظیمات پیش‌فرض ریست نمی‌شود (IDLE1 زیر نظر نیست) ولی loop و Taskهای هم‌اولویت هسته ۱ کند می‌شوند. «ریست نمی‌شود» یعنی «مشکل پنهان است»، نه «درست است».
  3. درمان. یک vTaskDelay(1) (حتی ۱ میلی‌ثانیه) در حلقه کافی است تا IDLE0 نوبت بگیرد. قانون: هر حلقه بی‌پایان در هر Task باید جایی بخوابد یا منتظر چیزی بماند (vTaskDelay، xQueueReceive، xSemaphoreTake با زمان صبر). حلقه‌های انتظار مثل while (!ready) {} دشمن شماره یک هستند.

حدود ۵ ثانیه بعد از روشن شدن چیزی شبیه این می‌بینی و برد ریست می‌شود:

E (5316) task_wdt: Task watchdog got triggered. The following tasks/users did not reset the watchdog in time: E (5316) task_wdt: - IDLE0 (CPU 0) E (5316) task_wdt: Tasks currently running: E (5316) task_wdt: CPU 0: greedy E (5316) task_wdt: CPU 1: IDLE1 E (5316) task_wdt: Aborting. abort() was called at PC 0x400d8c5f on core 0 ... Rebooting...

خط CPU 0: greedy مجرم را لو می‌دهد: اسمی که به Task دادی. برای همین اسم Taskها را معنادار انتخاب کن.

راه غلط: خاموش کردن نگهبان

در انجمن‌ها کدهایی مثل disableCore0WDT() می‌بینی. این کار پیام را قطع می‌کند ولی مشکل سر جایش است: Taskهای سیستم (مثل Wi-Fi) روی هسته ۰ گرسنه می‌مانند و اتصال شبکه عجیب قطع می‌شود. نگهبان دشمن تو نیست؛ دوستی است که می‌گوید کدت یک جا گیر کرده.

Task یا millis()؟ کدام را انتخاب کنم؟

برای دو سه کار سبک و سریع، millis() در loop ساده‌تر است و باگ‌های هم‌زمانی ندارد. Task را وقتی بیاور که: ۱) یک کار کند و مسدودکننده داری (HTTPS، خواندن کند سنسور، نوشتن روی SD) که نباید بقیه را منتظر بگذارد؛ ۲) کارها زمان‌بندی کاملا متفاوت دارند؛ ۳) می‌خواهی از هسته دوم استفاده کنی. هر Task جدید یعنی Stack جدا، و هر داده مشترک یعنی صف یا Mutex. بی‌دلیل Task نساز.

بخش ۲: آپدیت بی‌سیم (OTA)، برنامه‌ریزی بدون کابل

دستگاهت را داخل سقف کاذب نصب کرده‌ای تا چراغ‌ها را کنترل کند. یک هفته بعد یک باگ پیدا می‌کنی. بدون OTA باید نردبان بیاوری، سقف را باز کنی، لپ‌تاپ را با کابل USB بالا ببری. با OTA (Over-The-Air، «از راه هوا») برنامه جدید را از پشت میزت، از طریق همان Wi-Fi، روی برد می‌ریزی.

OTA پشت صحنه چطور کار می‌کند؟ (پارتیشن‌ها)

حافظه فلش ۴ مگابایتی ESP32 مثل یک هارد دیسک به چند «پارتیشن» تقسیم شده است. نقشه این تقسیم را در منوی Tools › Partition Scheme انتخاب می‌کنی. نکته کلیدی OTA این است: برای آپدیت امن باید دو جای برنامه (app0 و app1) وجود داشته باشد. برنامه جدید در جای خالی نوشته می‌شود، در حالی که برنامه فعلی هنوز در حال اجراست. فقط وقتی دانلود کامل و سالم تمام شد، یک «یادداشت» کوچک (پارتیشن otadata) عوض می‌شود که «از دفعه بعد از جای دیگر بوت کن». اگر وسط آپدیت برق برود، برنامه قدیمی دست‌نخورده باقی است.

دام رایج: Huge APP و OTA

وقتی برنامه بزرگ می‌شود (Wi-Fi + بلوتوث + HTTPS)، خطای Sketch too big می‌گیری و بسیاری از آموزش‌ها می‌گویند «Huge APP را انتخاب کن». آن کار خطا را برطرف می‌کند ولی OTA را برای همیشه می‌کشد، چون فقط یک جای برنامه دارد. برای دستگاهی که OTA لازم دارد، Minimal SPIFFS را انتخاب کن: برنامه تا ۱٫۹ مگابایت و OTA سالم. فقط فضای فایل به ۱۲۸ کیلوبایت کم می‌شود که برای یک صفحه تنظیمات کافی است. یادت باشد تغییر Partition Scheme فقط با آپلود USB اعمال می‌شود.

روش اول: ArduinoOTA، آپلود از خود Arduino IDE

کتابخانه ArduinoOTA داخل core است. برد را روی شبکه «اعلام» می‌کند (با mDNS، همان درس ۴.۲) و روی پورت 3232 منتظر برنامه جدید می‌ماند. اول فایل secrets.h درس ۴.۱ را کامل‌تر کن؛ این نسخه همه رمزهای این درس را دارد:

#pragma once
#define WIFI_SSID "MyHomeWiFi"
#define WIFI_PASS "my-strong-password"
#define OTA_PASS  "ota-pass-2026"      // رمز آپدیت بی‌سیم
#define WEB_USER  "admin"              // نام کاربری صفحه آپدیت وب
#define WEB_PASS  "change-me-now"      // رمز صفحه آپدیت وب
#define NTFY_TOPIC "home-alert-7f3k9q" // اسم Topic ی ntfy: حدس‌ناپذیر
  1. رمز Wi-Fi. همان دو خط درس ۴.۱. یک فایل رمز برای همه برنامه‌های این درس؛ هر برنامه فقط خط‌هایی را که لازم دارد استفاده می‌کند.
  2. رمز OTA. کسی که این رمز را نداند نمی‌تواند برنامه برد را عوض کند. OTA بدون رمز یعنی هر کسی که به Wi-Fi تو وصل است (مهمان، همسایه‌ای که رمز را دارد، یک گوشی آلوده) می‌تواند هر برنامه‌ای روی دستگاهت بریزد.
  3. نام کاربری و رمز صفحه آپدیت وب. برای روش دوم همین بخش. جدا از رمز OTA، تا اگر یکی لو رفت دیگری امن بماند.
  4. اسم Topic ی ntfy. برای بخش هشدار به گوشی (بخش ۴). در ntfy.sh اسم Topic خودش حکم رمز را دارد؛ پس جای آن هم در secrets.h است.
#include <WiFi.h>
#include <ArduinoOTA.h>
#include "secrets.h"             // WIFI_SSID، WIFI_PASS، OTA_PASS
#ifndef OTA_PASS                 // اگر در secrets.h نبود، هشدار بده
#warning "OTA_PASS is not defined in secrets.h"
#define OTA_PASS "change-me"
#endif

const int LED_PIN = 4;

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  WiFi.mode(WIFI_STA);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) {   // برای سادگی؛ نسخه پایدار در درس ۴.۱
    delay(500);
    Serial.print(".");
  }
  Serial.printf("\nIP: %s\n", WiFi.localIP().toString().c_str());

  ArduinoOTA.setHostname("esp32-kitchen");  // اسم در منوی Port
  ArduinoOTA.setPassword(OTA_PASS);         // بدون رمز، هر کسی می‌تواند فلش کند
  ArduinoOTA
    .onStart([]() { Serial.println("OTA start"); })
    .onEnd([]() { Serial.println("\nOTA done, rebooting"); })
    .onProgress([](unsigned int done, unsigned int total) {
      Serial.printf("OTA %u%%\r", done * 100 / total);
    })
    .onError([](ota_error_t err) { Serial.printf("OTA error %u\n", err); });
  ArduinoOTA.begin();                       // از اینجا به بعد منتظر آپدیت است
  Serial.println("OTA ready");
}

void loop() {
  ArduinoOTA.handle();                      // هر دور: «آپدیت نیامده؟»
  static unsigned long last = 0;            // چشمک بدون delay (درس ۳.۱)
  static bool on = false;
  if (millis() - last >= 500) {
    last = millis();
    on = !on;
    digitalWrite(LED_PIN, on);
  }
}
  1. کتابخانه ArduinoOTA. جزو core است، نصب لازم ندارد. WiFi.h را هم لازم داریم چون OTA روی شبکه کار می‌کند.
  2. محافظ #ifndef. اگر در secrets.h خط OTA_PASS را ننوشته باشی، کامپایلر یک هشدار نارنجی نشان می‌دهد و رمز موقت change-me گذاشته می‌شود. برنامه با secrets.h قدیمی درس ۴.۱ هم کامپایل می‌شود، ولی هشدار یادت می‌اندازد که رمز واقعی بگذاری. هشدارهای کامپایلر را هرگز نادیده نگیر.
  3. وصل شدن به Wi-Fi. نسخه ساده برای کوتاه ماندن مثال. در دستگاه واقعی از نسخه پایدار درس ۴.۱ با سقف زمان و اتصال دوباره خودکار استفاده کن. OTA بدون Wi-Fi کار نمی‌کند.
  4. setHostname. اسم برد روی شبکه؛ همان چیزی که در منوی Port می‌بینی. اگر اسم ندهی، چیزی مثل esp32-a0b1c2d3e4f5 (بر اساس MAC) می‌گیرد. وقتی سه دستگاه در خانه داری، «esp32-kitchen» خیلی بهتر است. فقط از حروف کوچک انگلیسی، عدد و خط تیره استفاده کن.
  5. setPassword. رمز OTA. Arduino IDE موقع آپلود آن را از تو می‌پرسد. در core 3.3 احراز هویت OTA با SHA-256 است (نسخه‌های قدیمی MD5 داشتند که دیگر امن حساب نمی‌شود). اگر نمی‌خواهی رمز خام در برنامه باشد، از setPasswordHash با هش SHA-256 رمز استفاده کن.
  6. رویدادها (Callback). چهار تابع کوچک برای شروع، پایان، پیشرفت و خطا. []() { ... } یک «تابع بی‌نام» (lambda) در C++ است. در onStart در پروژه واقعی موتورها و رله‌ها را خاموش کن و فایل‌ها را ببند؛ چند ثانیه بعد برد ریست می‌شود و نباید چیزی نیمه‌کاره بماند.
  7. ArduinoOTA.begin. از اینجا به بعد برد روی شبکه اعلام حضور می‌کند و منتظر آپدیت است. باید بعد از وصل شدن Wi-Fi صدا زده شود.
  8. ArduinoOTA.handle در هر دور loop. بررسی می‌کند آیا کسی می‌خواهد آپدیت بفرستد. اگر loop جایی با delay طولانی یا حلقه انتظار گیر کند، OTA جواب نمی‌دهد و IDE خطای «No response from device» می‌گیرد. برای همین چشمک LED را با millis() نوشتیم، نه delay.

قدم‌به‌قدم: اولین آپدیت بی‌سیم

  1. بار اول حتما با کابل USB. برد هنوز کد OTA را ندارد، پس نمی‌تواند برنامه را از هوا بگیرد. برنامه بالا را مثل همیشه با USB آپلود کن. (Partition Scheme باید OTA داشته باشد؛ Default کافی است.)
  2. Serial Monitor را ببین. باید IP و OTA ready را ببینی.
  3. کامپیوتر و برد روی یک شبکه. لپ‌تاپ باید به همان مودم وصل باشد (نه اینترنت گوشی، نه شبکه مهمان مودم که دستگاه‌ها را از هم جدا می‌کند).
  4. پورت شبکه را انتخاب کن. کابل USB را جدا کن (یا بگذار بماند) و منوی Tools › Port را باز کن. زیر عنوان Network ports چیزی مثل esp32-kitchen at 192.168.1.50 ظاهر می‌شود. اگر نیست، ۳۰ ثانیه صبر کن و منو را دوباره باز کن؛ IDE هر چند ثانیه شبکه را می‌گردد.
  5. یک تغییر کوچک بده (مثلا 500 را 100 کن تا LED سریع‌تر چشمک بزند) و دکمه Upload را بزن. IDE رمز را می‌پرسد: همان OTA_PASS.
  6. نتیجه. نوار پیشرفت Uploading: [==== ] 45% را می‌بینی. بعد برد خودش ریست می‌شود و LED با سرعت جدید چشمک می‌زند. Serial Monitor شبکه‌ای وجود ندارد؛ برای دیدن پیام‌ها هنوز کابل لازم است (یا لاگ را از طریق وب یا MQTT بفرست).
مهم: هر برنامه جدید هم باید کد OTA داشته باشد

اگر برنامه‌ای را از هوا بریزی که ArduinoOTA.begin و handle ندارد (یا در setup گیر می‌کند، یا Wi-Fi اشتباه دارد)، این آخرین آپدیت بی‌سیم تو بود! دفعه بعد باید نردبان و کابل بیاوری. عادت کن: کد OTA را اول از همه در هر برنامه بگذار و قبل از فرستادن به دستگاه سقفی، آن را روی یک برد روی میز تست کن.

روش دوم: صفحه آپدیت در مرورگر (Update + WebServer)

ArduinoOTA فقط از داخل Arduino IDE و در همان شبکه کار می‌کند. گاهی می‌خواهی فایل برنامه را به کس دیگری بدهی (مثلا به مشتری) تا بدون نصب Arduino IDE آپدیت کند. راه حل: یک صفحه وب روی خود ESP32 که فایل .bin را می‌گیرد. کتابخانه Update (داخل core) نوشتن در پارتیشن دوم را انجام می‌دهد.

ساختن فایل .bin

  1. در Arduino IDE منوی Sketch › Export Compiled Binary را بزن (میان‌بر Alt+Ctrl+S).
  2. بعد از کامپایل، در پوشه پروژه یک پوشه build ساخته می‌شود و داخل آن پوشه‌ای با اسم برد (مثلا esp32.esp32.esp32). با Sketch › Show Sketch Folder بازش کن.
  3. چند فایل .bin می‌بینی. فایل درست همان است که اسمش فقط اسم‌پروژه.ino.bin است. فایل‌های .bootloader.bin، .partitions.bin و .merged.bin را برای OTA نفرست؛ آن‌ها برای فلش کامل با کابل هستند.
#include <WiFi.h>
#include <WebServer.h>
#include <Update.h>
#include "secrets.h"
#ifndef WEB_USER
#warning "WEB_USER/WEB_PASS are not defined in secrets.h"
#define WEB_USER "admin"
#define WEB_PASS "change-me"
#endif

WebServer server(80);

const char UPDATE_PAGE[] PROGMEM = R"HTML(
<!doctype html><meta charset="utf-8">
<h3>Firmware update</h3>
<form method="POST" action="/update" enctype="multipart/form-data">
  <input type="file" name="firmware" accept=".bin">
  <button>Upload</button>
</form>)HTML";

void handlePage() {
  if (!server.authenticate(WEB_USER, WEB_PASS)) {
    return server.requestAuthentication();          // پنجره نام کاربری و رمز
  }
  server.send(200, "text/html", UPDATE_PAGE);
}

void handleUploadDone() {                           // بعد از تمام شدن آپلود
  if (!server.authenticate(WEB_USER, WEB_PASS)) {
    return server.requestAuthentication();
  }
  bool ok = !Update.hasError();
  server.send(200, "text/plain", ok ? "OK, rebooting..." : Update.errorString());
  if (ok) {
    delay(500);
    ESP.restart();                                  // با برنامه جدید بالا بیا
  }
}

void handleUploadChunk() {                          // برای هر تکه از فایل
  if (!server.authenticate(WEB_USER, WEB_PASS)) return;
  HTTPUpload &up = server.upload();
  if (up.status == UPLOAD_FILE_START) {
    Serial.printf("Update: %s\n", up.filename.c_str());
    if (!Update.begin(UPDATE_SIZE_UNKNOWN)) Update.printError(Serial);
  } else if (up.status == UPLOAD_FILE_WRITE) {
    if (Update.write(up.buf, up.currentSize) != up.currentSize) {
      Update.printError(Serial);
    }
  } else if (up.status == UPLOAD_FILE_END) {
    if (Update.end(true)) Serial.printf("Done: %u bytes\n", up.totalSize);
    else Update.printError(Serial);
  }
}

void setup() {
  Serial.begin(115200);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) delay(500);
  Serial.printf("Open http://%s/\n", WiFi.localIP().toString().c_str());
  server.on("/", HTTP_GET, handlePage);
  server.on("/update", HTTP_POST, handleUploadDone, handleUploadChunk);
  server.begin();
}

void loop() {
  server.handleClient();
}
  1. کتابخانه Update. رابط ساده برای نوشتن برنامه جدید در پارتیشن OTA خالی. خود ArduinoOTA هم در پشت صحنه از همین کتابخانه استفاده می‌کند. ما فقط راه رسیدن فایل را (به جای IDE، مرورگر) عوض کرده‌ایم.
  2. صفحه HTML با فرم آپلود. enctype="multipart/form-data" یعنی «این فرم فایل می‌فرستد». R"HTML( ... )HTML" همان رشته خام درس ۴.۲ است. بدون enctype مرورگر فقط اسم فایل را می‌فرستد، نه محتوای آن را. accept=".bin" فقط پنجره انتخاب فایل را به فایل‌های bin محدود می‌کند (امنیت نیست، راحتی است).
  3. صفحه اصلی با رمز. server.authenticate نام کاربری و رمز را بررسی می‌کند؛ اگر غلط بود، requestAuthentication پنجره ورود مرورگر را باز می‌کند. صفحه آپدیت بدون رمز یعنی هر کسی در شبکه می‌تواند دستگاهت را صاحب شود. این احراز هویت ساده (Basic/Digest) روی HTTP رمزنگاری نشده است، پس فقط در شبکه خانگی مورد اعتماد استفاده کن و هرگز این صفحه را با Port Forwarding روی اینترنت باز نکن.
  4. server.on با دو تابع. برای آپلود فایل، WebServer دو تابع می‌خواهد: handleUploadChunk که برای هر تکه از فایل صدا زده می‌شود، و handleUploadDone که بعد از تمام شدن کل آپلود جواب را به مرورگر می‌فرستد. فایل bin حدود یک مگابایت است و RAM آزاد ESP32 حدود ۳۰۰ کیلوبایت. پس نمی‌شود کل فایل را اول در RAM گرفت؛ باید آن را تکه‌تکه (هر بار چند کیلوبایت) گرفت و فورا در فلش نوشت.
  5. شروع: Update.begin. در اولین تکه، پارتیشن OTA خالی آماده (پاک) می‌شود. UPDATE_SIZE_UNKNOWN یعنی «اندازه را نمی‌دانم، تا جای خالی هست بنویس». اگر پارتیشن OTA وجود نداشته باشد (Huge APP)، همین‌جا خطا می‌گیری و Update.printError علتش را در Serial چاپ می‌کند.
  6. نوشتن هر تکه. Update.write تکه را در فلش می‌نویسد و تعداد بایت نوشته‌شده را برمی‌گرداند. اگر عدد با اندازه تکه یکی نبود، یعنی نوشتن خراب شد. بررسی کن، حدس نزن.
  7. پایان: Update.end(true). بررسی می‌کند فایل کامل و سالم است (سربرگ و checksum برنامه) و اگر بود، otadata را عوض می‌کند تا دفعه بعد از برنامه جدید بوت شود. اگر فایل اشتباهی (مثلا یک عکس یا فایل merged) فرستاده باشی، همین‌جا رد می‌شود و برنامه قبلی سالم می‌ماند. این همان امنیت دو پارتیشن است.
  8. جواب و ریست. اگر خطایی نبود، «OK» را برای مرورگر می‌فرستد، نیم ثانیه صبر می‌کند تا پیام برسد، و ESP.restart(). برنامه جدید فقط بعد از ریست اجرا می‌شود. بدون delay، ممکن است برد قبل از رسیدن جواب به مرورگر ریست شود و تو فکر کنی آپدیت شکست خورده.

استفاده: آدرس IP برد را در مرورگر باز کن، نام کاربری و رمز را بزن، فایل .ino.bin را انتخاب و Upload کن. حدود ۱۰ تا ۲۰ ثانیه بعد «OK, rebooting...» را می‌بینی.

میان‌بر: کتابخانه آماده HTTPUpdateServer

core 3.x یک کتابخانه به اسم HTTPUpdateServer هم دارد که همین صفحه را با دو خط به WebServer تو اضافه می‌کند. ما عمدا نسخه دستی را نوشتیم تا بفهمی پشت صحنه چه می‌گذرد. در آموزش‌های اینترنتی کتابخانه‌هایی مثل ElegantOTA را هم می‌بینی؛ نسخه‌های قدیمی آن (AsyncElegantOTA) منسوخ شده‌اند.

برگشت خودکار (Rollback): اگر برنامه جدید خراب بود چه؟

فرض کن برنامه جدید باگی دارد که باعث می‌شود به Wi-Fi وصل نشود. حالا دیگر OTA هم کار نمی‌کند! ESP-IDF برای این حالت «برگشت خودکار» دارد و در core آردوینو ۳ هم روشن است (CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y). ایده: برنامه جدید بعد از اولین بوت «در حال آزمایش» است. اگر خودش اعلام کند «من سالمم»، ماندگار می‌شود؛ اگر قبل از آن ریست شود یا خودش بگوید «خرابم»، bootloader به برنامه قبلی برمی‌گردد.

به طور پیش‌فرض core آردوینو برنامه جدید را بلافاصله در شروع کار «سالم» اعلام می‌کند. برای این که خودت تصمیم بگیری:

#include <WiFi.h>
#include "esp_ota_ops.h"
#include "secrets.h"

// به core می‌گوییم: «تأیید برنامه جدید را خودم انجام می‌دهم»
extern "C" bool verifyRollbackLater() {
  return true;
}

void setup() {
  Serial.begin(115200);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  unsigned long t0 = millis();
  while (WiFi.status() != WL_CONNECTED && millis() - t0 < 30000) delay(500);

  if (WiFi.status() == WL_CONNECTED) {
    esp_ota_mark_app_valid_cancel_rollback();   // «این نسخه سالم است»
    Serial.println("New firmware confirmed");
  } else {
    Serial.println("No Wi-Fi: rolling back");
    esp_ota_mark_app_invalid_rollback_and_reboot();  // برگرد به نسخه قبلی
  }
}

void loop() {
  delay(1000);
}
  1. verifyRollbackLater. core این تابع را به شکل «ضعیف» (weak) تعریف کرده که false برمی‌گرداند. وقتی خودت آن را با true بنویسی، نسخه تو جایگزین می‌شود و core تأیید خودکار را انجام نمی‌دهد. extern "C" ضروری است: تابع core در یک فایل C تعریف شده و بدون آن، کامپایلر C++ اسم تابع تو را تغییر می‌دهد (name mangling)؛ برنامه بدون هیچ خطایی کامپایل می‌شود ولی نسخه تو هرگز صدا زده نمی‌شود. این الگوی «تابع weak» در core آردوینو زیاد است: راهی برای تغییر رفتار داخلی بدون دست زدن به فایل‌های core.
  2. تأیید. اگر Wi-Fi در ۳۰ ثانیه وصل شد، esp_ota_mark_app_valid_cancel_rollback() می‌گوید «این نسخه ماندگار است». معیار سلامت را خودت انتخاب کن: وصل شدن به Wi-Fi، جواب دادن سرور MQTT، یا هر چیزی که برای ادامه OTA لازم است.
  3. رد کردن. esp_ota_mark_app_invalid_rollback_and_reboot() برد را ریست می‌کند و bootloader نسخه قبلی را اجرا می‌کند. اگر برنامه با کابل USB ریخته شده باشد، نسخه قبلی معتبری نیست و این تابع فقط خطا برمی‌گرداند؛ پس روی میز با آن کاری نمی‌شود. این مکانیزم فقط بعد از یک آپدیت OTA معنا دارد.
امنیت OTA را جدی بگیر

OTA یعنی «راهی برای عوض کردن مغز دستگاه از راه دور». اگر این راه باز باشد، مهاجم هم می‌تواند از آن استفاده کند. حداقل‌ها: ۱) همیشه رمز بگذار؛ ۲) پورت 3232 و صفحه آپدیت را هرگز با Port Forwarding روی اینترنت باز نکن؛ ۳) برای دستگاهی که به دیگران می‌فروشی، OTA امضاشده (Signed OTA، مثال SignedOTA در کتابخانه ArduinoOTA) و Secure Boot را مطالعه کن تا فقط برنامه امضاشده با کلید خصوصی خودت پذیرفته شود.

OTA و آپلود فایل LittleFS در Wokwi شبیه‌سازی نمی‌شوند (Wokwi برنامه را مستقیم در حافظه شبیه‌ساز می‌گذارد و پورت شبکه‌ای برای IDE ندارد). این دو را روی برد واقعی تمرین کن.

بخش ۳: LittleFS، یک فلش‌مموری کوچک داخل ESP32

در درس ۴.۲ صفحه وب را به شکل یک رشته بزرگ داخل کد C++ نوشتیم. کار می‌کرد، ولی هر تغییر کوچک در رنگ یک دکمه یعنی کامپایل و آپلود دوباره کل برنامه. و اگر بخواهی تنظیمات (مثلا شهر انتخابی کاربر) یا لاگ چند روزه را نگه داری، متغیرها با ریست پاک می‌شوند. LittleFS یک «سیستم فایل» است: بخشی از حافظه فلش (همان پارتیشن spiffs در شکل بالا) را مثل یک فلش‌مموری کوچک با پوشه و فایل در اختیارت می‌گذارد. فایل‌ها با خاموش شدن برق و حتی با آپلود برنامه جدید (با USB یا OTA) باقی می‌مانند.

مثال از زندگی روزمره

برنامه تو مثل آشپز است و RAM مثل میز کارش: سریع ولی با تعطیلی رستوران (قطع برق) پاک می‌شود. LittleFS مثل قفسه دفترها در آشپزخانه است: دستور غذاها (صفحه وب) و دفتر حساب (لاگ) آنجا می‌ماند، حتی اگر آشپز عوض شود (برنامه جدید).

چرا LittleFS و نه SPIFFS؟

SPIFFS سیستم فایل قدیمی‌تر ESP32 است که پوشه واقعی ندارد و با قطع برق وسط نوشتن آسیب‌پذیرتر است؛ Espressif آن را دیگر توسعه نمی‌دهد. LittleFS برای میکروکنترلر طراحی شده: در برابر قطع برق مقاوم است (Power-loss resilient) و نوشتن را روی کل حافظه پخش می‌کند تا یک نقطه از فلش زود فرسوده نشود (Wear leveling). اسم پارتیشن هنوز «spiffs» است ولی LittleFS به راحتی از همان استفاده می‌کند.

نوشتن، اضافه کردن، خواندن و فهرست فایل‌ها

#include <LittleFS.h>

void listFiles(const char *dir) {
  File root = LittleFS.open(dir);
  File f = root.openNextFile();
  while (f) {
    Serial.printf("  %-20s %6u bytes\n", f.name(), (unsigned)f.size());
    f = root.openNextFile();
  }
}

void setup() {
  Serial.begin(115200);
  delay(500);
  if (!LittleFS.begin(true)) {               // true = اگر خراب بود، فرمت کن
    Serial.println("LittleFS mount failed");
    return;
  }
  Serial.printf("FS: %u of %u bytes used\n",
                (unsigned)LittleFS.usedBytes(), (unsigned)LittleFS.totalBytes());

  File f = LittleFS.open("/note.txt", "w");  // w = بساز یا از اول بنویس
  f.println("Hello from ESP32!");
  f.close();                                 // بستن = ذخیره قطعی

  f = LittleFS.open("/log.txt", "a");        // a = به آخر فایل اضافه کن
  f.printf("boot at %lu ms\n", millis());
  f.close();

  f = LittleFS.open("/log.txt", "r");        // r = فقط خواندن
  Serial.println("--- log.txt ---");
  while (f.available()) {
    Serial.write(f.read());
  }
  f.close();

  Serial.println("--- files ---");
  listFiles("/");
}

void loop() {}
  1. کتابخانه LittleFS. داخل core است. نصب جدا لازم نیست. کتابخانه‌های قدیمی مثل «LITTLEFS by lorol» را نصب نکن؛ آن‌ها مال core 1.x بودند و با core 3 تداخل دارند.
  2. LittleFS.begin(true). سیستم فایل را «سوار» (mount) می‌کند. ورودی true یعنی «اگر نتوانستی سوار کنی (مثلا بار اول که هنوز فرمت نشده)، فرمت کن». بار اولی که روی برد نو اجرا می‌کنی، پارتیشن خالی و فرمت‌نشده است و بدون true همیشه «mount failed» می‌گیری. ولی دقت کن: اگر فایل‌ها واقعا خراب شده باشند، true همه را پاک می‌کند. برای دستگاهی با داده ارزشمند، اول با false امتحان کن و فرمت را آگاهانه انجام بده.
  3. فضای کل و مصرف‌شده. totalBytes و usedBytes. با Partition Scheme پیش‌فرض حدود ۱٫۳ تا ۱٫۴ مگابایت می‌بینی؛ با Minimal SPIFFS فقط ۱۲۸ کیلوبایت. قبل از ذخیره لاگ طولانی، همیشه جای خالی را بدان.
  4. حالت "w": نوشتن از اول. فایل را می‌سازد؛ اگر از قبل بود، محتوایش را پاک می‌کند. بعد مثل Serial با println و printf در آن می‌نویسی. اسم فایل همیشه با / شروع می‌شود (مسیر کامل). close() را فراموش نکن: تا فایل بسته نشود، ممکن است آخرین تکه داده هنوز در RAM باشد و با قطع برق از بین برود.
  5. حالت "a": اضافه کردن. به انتهای فایل اضافه می‌کند و قبلی‌ها را نگه می‌دارد. برای لاگ همیشه "a". با هر بار ریست، یک خط boot at ... اضافه می‌شود. دکمه EN را چند بار بزن و ببین فایل بلندتر می‌شود؛ این ثابت می‌کند داده بعد از ریست مانده است.
  6. حالت "r": خواندن. available() می‌گوید چند بایت دیگر مانده و read() یک بایت برمی‌گرداند. خواندن بایت به بایت برای فایل‌های کوچک ساده و کم‌حافظه است. برای فایل بزرگ، f.readStringUntil('\n') خط به خط می‌خواند.
  7. فهرست فایل‌ها. پوشه را باز می‌کنیم و با openNextFile() یکی‌یکی جلو می‌رویم تا فایل خالی (false) برگردد. ابزار عیب‌یابی عالی: وقتی صفحه وب پیدا نمی‌شود، اول ببین فایل واقعا روی برد هست و اسمش دقیقا چیست (حروف بزرگ و کوچک فرق دارند).

  1. ظاهر صفحه در فایل جدا. فونت، عرض حداکثر ۴۸۰ پیکسل (برای گوشی) و رنگ آبی تیتر. فایل CSS را مرورگر جدا درخواست می‌کند (/style.css)، پس برنامه ESP32 باید برای این آدرس هم جواب داشته باشد؛ خط ۱۹ برنامه پایین همین کار را می‌کند.
#include <WiFi.h>
#include <WebServer.h>
#include <LittleFS.h>
#include "secrets.h"

WebServer server(80);

void setup() {
  Serial.begin(115200);
  if (!LittleFS.begin(true)) {
    Serial.println("LittleFS mount failed");
  }
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) delay(500);
  Serial.printf("Open http://%s/\n", WiFi.localIP().toString().c_str());

  // فایل‌های ثابت مستقیم از LittleFS (بعد از LittleFS.begin)
  server.serveStatic("/", LittleFS, "/index.html");
  server.serveStatic("/style.css", LittleFS, "/style.css", "max-age=3600");

  // داده زنده از کد
  server.on("/api/temp", []() {
    float t = temperatureRead();               // دمای داخلی تراشه (تقریبی)
    server.send(200, "application/json", "{\"t\":" + String(t, 1) + "}");
  });
  server.onNotFound([]() { server.send(404, "text/plain", "Not found"); });
  server.begin();
}

void loop() {
  server.handleClient();
}
  1. سوار کردن LittleFS قبل از هر چیز. serveStatic در لحظه تعریف بررسی می‌کند که مسیر یک فایل است یا پوشه؛ اگر LittleFS هنوز سوار نشده باشد، اشتباه تشخیص می‌دهد.
  2. serveStatic برای صفحه اصلی. «هر کس آدرس / را خواست، فایل /index.html را از LittleFS بفرست». نوع محتوا (text/html) را از پسوند فایل حدس می‌زند. یک خط به جای یک تابع کامل. نکته ریز: اگر به جای فایل یک پوشه بدهی (مثلا serveStatic("/", LittleFS, "/"))، کتابخانه برای آدرس / دنبال index.htm (بدون l) می‌گردد، نه index.html. ما برای جلوگیری از این دام، مسیر فایل را دقیق دادیم.
  3. فایل CSS با Cache. ورودی چهارم "max-age=3600" به مرورگر می‌گوید «این فایل را تا یک ساعت دوباره نخواه». ESP32 یک سرور ضعیف است؛ هر درخواست کمتر یعنی جواب سریع‌تر به بقیه. برای index.html کش نگذاشتیم تا تغییراتت فورا دیده شود.
  4. مسیر داده زنده. temperatureRead() دمای داخلی تراشه را می‌دهد (دقیق نیست، فقط برای نمایش) و به شکل JSON فرستاده می‌شود. در پروژه واقعی به جای آن دمای DHT22 یا هر سنسور دیگر را بگذار.

آپلود پوشه data روی برد (Arduino IDE 2)

Arduino IDE 2 برای ریختن پوشه data روی LittleFS یک افزونه لازم دارد: arduino-littlefs-upload از Earle Philhower (سازنده core ی RP2040). از Arduino IDE نسخه 2.2.1 به بعد کار می‌کند.

  1. دانلود. به صفحه Releases برو و آخرین فایل arduino-littlefs-upload-x.y.z.vsix را دانلود کن (از حالت zip خارجش نکن).
  2. پوشه plugins. در ویندوز به C:\Users\اسم‌کاربر\.arduinoIDE\ برو و اگر پوشه plugins نیست، بسازش. در مک و لینوکس: ~/.arduinoIDE/plugins/. دقت کن اسم پوشه با نقطه شروع می‌شود (.arduinoIDE) و در ویندوز ممکن است پنهان باشد.
  3. کپی و راه‌اندازی دوباره. فایل vsix را در پوشه plugins بگذار و Arduino IDE را کامل ببند و باز کن.
  4. Serial Monitor را ببند. اگر باز باشد، آپلود با خطای «port doesn't exist» شکست می‌خورد.
  5. اجرا. Ctrl+Shift+P (در مک ⌘+Shift+P) را بزن و فرمان Upload LittleFS to Pico/ESP8266/ESP32 را انتخاب کن. افزونه از روی Partition Scheme انتخابی تو، اندازه و محل پارتیشن را می‌فهمد، یک تصویر LittleFS از پوشه data می‌سازد و با کابل USB روی برد می‌ریزد.
  6. حالا برنامه را آپلود کن (یا قبلش؛ ترتیب مهم نیست). این دو آپلود جدا از هم هستند: آپلود برنامه فایل‌ها را پاک نمی‌کند و آپلود LittleFS برنامه را.
دو دام رایج

۱) Partition Scheme موقع آپلود LittleFS و موقع آپلود برنامه باید یکی باشد؛ اگر اولی را با Default و دومی را با Minimal SPIFFS بریزی، برنامه پارتیشن را جای دیگری می‌بیند و «mount failed» یا فایل‌های گم‌شده می‌گیری. ۲) آپلود LittleFS کل پارتیشن را بازنویسی می‌کند؛ لاگ‌ها و تنظیماتی که برنامه روی برد ساخته بود پاک می‌شوند. همین افزونه در Wokwi کار نمی‌کند؛ در Wokwi فایل‌ها را باید با کد بسازی (مثل برنامه LittleFS_Basics).

بخش ۴: فراخوانی API اینترنتی (HTTPS و JSON)

تا حالا ESP32 سرور بود (دیگران از او چیزی می‌خواستند). حالا برعکس: ESP32 مشتری (Client) می‌شود و از یک سرویس اینترنتی چیزی می‌پرسد. به آدرسی که یک سرویس برای جواب دادن به برنامه‌ها (نه انسان‌ها) آماده کرده API می‌گویند. جواب معمولا JSON است، همان قالبی که در درس ۵.۱ دیدی.

هوای تهران از Open-Meteo

Open-Meteo یک سرویس هواشناسی رایگان است که برای استفاده غیرتجاری کلید (API Key) و ثبت‌نام نمی‌خواهد. قبل از هر کدی، آدرس زیر را در مرورگر کامپیوترت باز کن تا ببینی جواب چه شکلی است؛ این عادت حرفه‌ای‌هاست:

https://api.open-meteo.com/v1/forecast?latitude=35.69&longitude=51.39&current=temperature_2m,wind_speed_10m

آدرس سه بخش دارد: latitude و longitude (عرض و طول جغرافیایی تهران)، و current (کدام مقدارهای «همین الان» را می‌خواهی: دمای ۲ متری زمین و سرعت باد در ارتفاع ۱۰ متری). جواب چیزی شبیه این است (کوتاه‌شده):

کتابخانه لازم: ArduinoJson 7

  1. Arduino IDE → Tools › Manage Libraries (آیکون کتاب).
  2. عبارت ArduinoJson را جست‌وجو کن و ArduinoJson by Benoit Blanchon را نصب کن؛ مطمئن شو نسخه 7.x است. وابستگی ندارد.
#include <WiFi.h>
#include <WiFiClientSecure.h>
#include <HTTPClient.h>
#include <ArduinoJson.h>
#include "secrets.h"

const char *URL =
  "https://api.open-meteo.com/v1/forecast"
  "?latitude=35.69&longitude=51.39"
  "&current=temperature_2m,wind_speed_10m";

bool fetchWeather(float &temp, float &wind) {
  WiFiClientSecure client;
  client.setInsecure();              // فقط برای یادگیری! پایین‌تر روش درست را ببین
  HTTPClient http;
  http.setConnectTimeout(5000);      // حداکثر ۵ ثانیه برای وصل شدن
  http.setTimeout(5000);             // حداکثر ۵ ثانیه برای جواب
  http.useHTTP10(true);              // بدون chunked، برای خواندن جریانی
  if (!http.begin(client, URL)) return false;

  int code = http.GET();
  if (code != HTTP_CODE_OK) {
    Serial.printf("HTTP error: %d %s\n", code, http.errorToString(code).c_str());
    http.end();
    return false;
  }

  JsonDocument filter;               // فقط همین دو عدد را نگه دار
  filter["current"]["temperature_2m"] = true;
  filter["current"]["wind_speed_10m"] = true;

  JsonDocument doc;
  DeserializationError err = deserializeJson(doc, http.getStream(),
                               DeserializationOption::Filter(filter));
  http.end();
  if (err) {
    Serial.printf("JSON error: %s\n", err.c_str());
    return false;
  }
  temp = doc["current"]["temperature_2m"] | NAN;   // اگر نبود: NAN
  wind = doc["current"]["wind_speed_10m"] | NAN;
  return !isnan(temp);
}

void setup() {
  Serial.begin(115200);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) delay(500);
  Serial.println("Wi-Fi OK");
}

void loop() {
  float t, w;
  if (fetchWeather(t, w)) {
    Serial.printf("Tehran: %.1f C, wind %.1f km/h\n", t, w);
  }
  delay(10UL * 60 * 1000);           // هر ۱۰ دقیقه، نه هر ثانیه
}
  1. سه کتابخانه. WiFiClientSecure برای اتصال رمزنگاری‌شده (HTTPS)، HTTPClient برای ساختن درخواست و خواندن جواب HTTP، و ArduinoJson برای تجزیه JSON. در core 3.x اسم اصلی کلاس NetworkClientSecure است و WiFiClientSecure یک اسم مستعار سازگار با قبل است؛ هر دو یکی‌اند. ما اسم آشناتر را نگه داشتیم.
  2. آدرس API. رشته‌های کنار هم در C++ خودشان به هم می‌چسبند؛ آدرس را برای خوانایی در سه خط شکستیم. پارامترها را با & از هم جدا کن و فاصله نگذار. یک حرف اشتباه (مثلا temperature_2) باعث جواب خطای 400 می‌شود.
  3. setInsecure: رمزنگاری بدون بررسی هویت. اتصال رمز می‌شود ولی ESP32 بررسی نمی‌کند که طرف مقابل واقعا open-meteo.com است. حقیقت صادقانه (مثل درس ۵.۱): برای گرفتن دمای عمومی که رازی نیست، خطرش کم است؛ بدترین حالت این است که کسی دمای دروغ به تو بدهد. ولی برای هر چیزی که رمز یا فرمان جابه‌جا می‌کند، هرگز setInsecure نگذار. روش درست (useBuiltinCACertBundle) را در مثال بعدی می‌بینی.
  4. سقف زمان. setConnectTimeout برای وصل شدن و setTimeout برای انتظار جواب، هر دو به میلی‌ثانیه. بدون سقف زمان، اگر اینترنت کند یا سرور شلوغ باشد، برنامه ممکن است مدت زیادی منتظر بماند. دستگاه واقعی هیچ‌وقت نباید بی‌نهایت منتظر چیزی بماند.
  5. useHTTP10. درخواست را با HTTP نسخه 1.0 می‌فرستد. در HTTP/1.1 سرور ممکن است جواب را «تکه‌تکه» (chunked) بفرستد و بین تکه‌ها عددهای اندازه بگذارد. چون ما جواب را مستقیم از جریان شبکه (getStream) به ArduinoJson می‌دهیم، آن عددها JSON را خراب می‌کنند. HTTP/1.0 تکه‌تکه ندارد. این توصیه رسمی مستندات ArduinoJson است.
  6. GET و بررسی کد جواب. HTTP_CODE_OK یعنی 200. عدد منفی یعنی اصلا به سرور نرسیدیم؛ errorToString آن را به متن تبدیل می‌کند (مثلا connection refused یا read Timeout). کدهای مهم: 200 موفق، 400 آدرس غلط، 429 «زیادی درخواست دادی» (Rate limit)، 5xx خطای سرور. همیشه قبل از خواندن جواب، کد را بررسی کن و http.end() را در هر مسیری فراموش نکن تا حافظه آزاد شود.
  7. فیلتر JSON. یک سند کوچک که شکلش می‌گوید «از جواب فقط این دو فیلد را نگه دار». جواب کامل چند صد بایت است و در APIهای دیگر (مثلا پیش‌بینی ۷ روزه ساعتی) ده‌ها کیلوبایت. با فیلتر، ArduinoJson بقیه را هنگام خواندن دور می‌ریزد و RAM کمی مصرف می‌شود.
  8. deserializeJson مستقیم از شبکه. جواب بدون ذخیره در یک String بزرگ، مستقیم از جریان شبکه خوانده می‌شود. اگر JSON ناقص یا خراب بود، err مقدار دارد و err.c_str() علت را می‌گوید (مثلا IncompleteInput یا NoMemory). در نسخه ۷ فقط JsonDocument داریم که اندازه‌اش را خودش تنظیم می‌کند. در نسخه ۶ باید StaticJsonDocument<512> یا DynamicJsonDocument با اندازه دستی می‌نوشتی؛ کدهای قدیمی اینترنت با نسخه ۷ هشدار یا خطا می‌دهند.
  9. عملگر | برای مقدار پیش‌فرض. «اگر این فیلد بود مقدارش را بده، وگرنه NAN (نه‌عدد)». اگر سرویس روزی اسم فیلد را عوض کند، به جای صفر دروغین (که شبیه دمای واقعی است!) NAN می‌گیری و می‌فهمی مشکلی هست.
  10. هر ۱۰ دقیقه. 10UL * 60 * 1000 میلی‌ثانیه؛ UL یعنی عدد بزرگ بدون علامت تا ضرب سرریز نکند. هشدار به گوشی: POST با JSON به ntfy

حالا برعکس: ESP32 خبری را ارسال می‌کند. ntfy.sh یک سرویس اعلان رایگان و بدون ثبت‌نام است: اپ ntfy را روی گوشی (اندروید یا iOS) نصب می‌کنی، یک «Topic» با اسم دلخواه را Subscribe می‌کنی، و هر پیامی که به آن Topic فرستاده شود، به شکل نوتیفیکیشن روی گوشی‌ات ظاهر می‌شود.

اسم Topic همان رمز است

در ntfy.sh ثبت‌نامی نیست، پس هر کس اسم Topic تو را بداند می‌تواند پیام‌هایت را بخواند و برایت پیام جعلی بفرستد. اسمی مثل test یا ali انتخاب نکن؛ یک اسم طولانی و تصادفی مثل home-alert-7f3k9q بگذار و آن را در secrets.h نگه دار. محدودیت ntfy.sh رایگان: حدود ۲۵۰ پیام در روز و هر پیام حداکثر ۴۰۹۶ بایت.

مدار: یک دکمه فشاری بین GPIO15 و GND (مقاومت Pull-up داخلی را روشن می‌کنیم؛ درس ۳.۱).

#include <WiFi.h>
#include <WiFiClientSecure.h>
#include <HTTPClient.h>
#include <ArduinoJson.h>
#include "secrets.h"
#ifndef NTFY_TOPIC
#warning "NTFY_TOPIC is not defined in secrets.h"
#define NTFY_TOPIC "change-me-to-a-random-name"
#endif

const int BUTTON_PIN = 15;          // دکمه بین GPIO15 و GND

bool sendAlert(const char *title, const char *message) {
  WiFiClientSecure client;
  client.useBuiltinCACertBundle();  // بررسی واقعی هویت سرور
  HTTPClient http;
  http.setTimeout(5000);
  if (!http.begin(client, "https://ntfy.sh/")) return false;
  http.addHeader("Content-Type", "application/json");

  JsonDocument msg;                 // {"topic":..,"title":..,"message":..}
  msg["topic"] = NTFY_TOPIC;
  msg["title"] = title;
  msg["message"] = message;
  msg["priority"] = 4;              // ۱ تا ۵؛ ۴ یعنی «مهم»
  msg["tags"].add("warning");
  String body;
  serializeJson(msg, body);

  int code = http.POST(body);
  http.end();
  Serial.printf("ntfy -> %d\n", code);
  return code == 200;
}

void setup() {
  Serial.begin(115200);
  pinMode(BUTTON_PIN, INPUT_PULLUP);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  while (WiFi.status() != WL_CONNECTED) delay(500);
  Serial.println("Press the button to send an alert");
}

void loop() {
  static unsigned long lastSent = 0;
  if (digitalRead(BUTTON_PIN) == LOW && millis() - lastSent > 30000) {
    lastSent = millis();            // حداکثر هر ۳۰ ثانیه یک هشدار
    sendAlert("Door", "Front door opened!");
  }
  delay(20);
}
  1. useBuiltinCACertBundle. این بار هویت سرور ntfy.sh واقعا بررسی می‌شود. این پیام به گوشی تو می‌رود و ممکن است روزی «در باز شد» یا «نشت گاز» باشد؛ نمی‌خواهی کسی وسط راه آن را عوض کند.
  2. آدرس ریشه و نوع محتوا. برای فرستادن JSON باید به آدرس ریشه https://ntfy.sh/ POST کنی (نه https://ntfy.sh/topic) و بگویی بدنه JSON است. طبق مستندات ntfy، JSON فقط در آدرس ریشه پذیرفته می‌شود و اسم Topic داخل خود JSON می‌آید. روش ساده‌تر هم هست: POST متن خام به https://ntfy.sh/اسم-topic که کل متن می‌شود پیام.
  3. ساختن JSON. این بار برعکس deserialize: سند را پر می‌کنیم و serializeJson آن را به متن تبدیل می‌کند. msg["tags"].add("warning") یک آرایه می‌سازد که ntfy آن را به ایموجی ⚠️ تبدیل می‌کند. هرگز JSON را با چسباندن رشته‌ها دستی نساز ("{\"title\":\"" + ...)؛ اگر متن پیام یک " داشته باشد، JSON خراب می‌شود. ArduinoJson علامت‌های خاص را خودش درست می‌کند.
  4. اولویت ۱ تا ۵. ۳ پیش‌فرض است، ۴ «بالا» با لرزش طولانی، ۵ «فوری». برای هشدار واقعی ۴ یا ۵؛ برای گزارش روزانه ۲ که بی‌صدا در لیست اعلان‌ها می‌نشیند. اگر همه چیز فوری باشد، دیگر هیچ چیز فوری نیست.
  5. POST و کد جواب. ntfy در صورت موفقیت 200 برمی‌گرداند. اگر 429 دیدی، یعنی از سقف درخواست عبور کرده‌ای؛ اگر عدد منفی، مشکل از شبکه یا گواهی است.
  6. محدودیت ارسال. بعد از هر هشدار تا ۳۰ ثانیه هشدار دیگری فرستاده نمی‌شود، حتی اگر دکمه نگه داشته شود. بدون این، نگه داشتن دکمه برای ۲ ثانیه یعنی ده‌ها درخواست و ده‌ها نوتیفیکیشن، و چند دقیقه بعد سرویس تو را مسدود می‌کند. هر دستگاهی که به سرویس بیرونی پیام می‌دهد باید «ترمز» داشته باشد (Rate limiting).

بخش ۵: چک‌لیست دستگاهی که ماه‌ها روشن می‌ماند

برنامه‌ای که ۱۰ دقیقه روی میز کار می‌کند با برنامه‌ای که ۶ ماه بدون دخالت کار می‌کند فرق دارد. مشکلاتی که در ۱۰ دقیقه دیده نمی‌شوند: حافظه‌ای که ذره‌ذره تکه‌تکه می‌شود، Wi-Fi ای که ساعت ۳ صبح قطع می‌شود، برقی که وسط نوشتن فایل می‌رود. قانون مهندسی: فرض کن هر چیزی که ممکن است خراب شود، بالاخره خراب می‌شود، و دستگاه باید خودش را جمع کند.

خطرعلامتدرمان

مثال از زندگی روزمره: جعبه سیاه هواپیما

هواپیما بعد از هر حادثه می‌گوید چه شد، چون جعبه سیاه دارد. دستگاه تو هم باید «جعبه سیاه» داشته باشد: هر بار که روشن می‌شود بگوید چرا ریست شده و تا حالا چند بار کرش کرده. بدون این، عیب‌یابی دستگاهی که در سقف است یعنی حدس زدن.

#include <Preferences.h>
#include "esp_system.h"
#include "esp_task_wdt.h"

Preferences prefs;

const char *resetReasonText(esp_reset_reason_t r) {
  switch (r) {
    case ESP_RST_POWERON:   return "power on";
    case ESP_RST_SW:        return "software (ESP.restart)";
    case ESP_RST_PANIC:     return "PANIC (crash / Guru Meditation)";
    case ESP_RST_INT_WDT:   return "interrupt watchdog";
    case ESP_RST_TASK_WDT:  return "TASK WATCHDOG";
    case ESP_RST_WDT:       return "other watchdog";
    case ESP_RST_DEEPSLEEP: return "wake from deep sleep";
    case ESP_RST_BROWNOUT:  return "BROWNOUT (weak power)";
    default:                return "other/unknown";
  }
}

void workerTask(void *param) {
  esp_task_wdt_add(NULL);                      // این Task را به نگهبان معرفی کن
  for (;;) {
    // ... کار اصلی Task اینجاست ...
    esp_task_wdt_reset();                      // «من زنده‌ام»
    vTaskDelay(pdMS_TO_TICKS(1000));
  }
}

void setup() {
  Serial.begin(115200);
  delay(500);
  esp_reset_reason_t why = esp_reset_reason();

  prefs.begin("sys", false);                   // فضای نام "sys" در NVS
  uint32_t boots = prefs.getUInt("boots", 0) + 1;
  prefs.putUInt("boots", boots);
  if (why == ESP_RST_PANIC || why == ESP_RST_TASK_WDT || why == ESP_RST_BROWNOUT) {
    prefs.putUInt("crashes", prefs.getUInt("crashes", 0) + 1);
  }
  Serial.printf("Boot #%lu, reason: %s, crashes so far: %lu\n",
                (unsigned long)boots, resetReasonText(why),
                (unsigned long)prefs.getUInt("crashes", 0));
  prefs.end();

  enableLoopWDT();                             // اگر loop بیش از ۵ ثانیه گیر کرد: ریست
  xTaskCreatePinnedToCore(workerTask, "worker", 3072, NULL, 1, NULL, 1);
}

String line;                                   // سراسری، یک بار رزرو شده

void loop() {
  line.reserve(64);                            // بعد از اولین بار کاری نمی‌کند
  line = "uptime=";
  line += millis() / 1000;
  line += "s heap=";
  line += ESP.getFreeHeap();
  Serial.println(line);
  delay(2000);                                 // اگر این را 6000 کنی، WDT ریست می‌کند
}
  1. ترجمه علت ریست به متن. esp_reset_reason() یک عدد از نوع esp_reset_reason_t برمی‌گرداند و ما مهم‌ترین‌ها را به متن خوانا تبدیل می‌کنیم. سه علت که همیشه باید نگرانت کنند: PANIC (کرش، مثل Guru Meditation یا Stack overflow)، TASK_WDT (یک Task گیر کرده)، و BROWNOUT (برق ضعیف). POWERON یعنی برق وصل شد و SW یعنی خود برنامه ESP.restart() زده (مثلا بعد از OTA). نکته: فشار دادن دکمه EN روی ESP32 معمولا به شکل POWERON گزارش می‌شود.
  2. معرفی یک Task به نگهبان. esp_task_wdt_add(NULL) یعنی «Task فعلی را زیر نظر بگیر» و esp_task_wdt_reset() یعنی «من زنده‌ام». از این لحظه اگر این Task بیش از ۵ ثانیه reset نکند، برد ریست می‌شود. reset را در جایی بگذار که فقط وقتی کار واقعا جلو می‌رود اجرا شود، نه در یک Task جداگانه که همیشه زنده است (آن وقت نگهبان را فریب داده‌ای). Taskی که کار طولانی مثل HTTPS دارد را با دقت اضافه کن، چون یک درخواست کند ممکن است از ۵ ثانیه بیشتر شود.
  3. شمارنده‌ها در Preferences. تعداد کل روشن شدن‌ها و تعداد ریست‌های «بد» در NVS ذخیره می‌شوند و با قطع برق پاک نمی‌شوند. اگر بعد از یک هفته دیدی crashes عدد ۴۰ است، می‌دانی مشکلی هست، حتی اگر دستگاه «ظاهرا کار می‌کند». فقط در بوت می‌نویسیم، نه در loop، تا فلش فرسوده نشود. در پروژه واقعی این عددها را در صفحه وب یا با MQTT گزارش کن.
  4. enableLoopWDT. تابع آماده core که loopTask را به نگهبان معرفی می‌کند. خود core قبل از هر دور loop() نگهبان را reset می‌کند. پس اگر یک دور loop بیش از ۵ ثانیه طول بکشد (مثلا در یک while منتظر سنسوری که قطع شده گیر کند)، برد خودش ریست می‌شود و کار از نو شروع می‌شود. ریست بهتر از یخ زدن همیشگی است.
  5. String با reserve. متغیر سراسری line یک بار ۶۴ بایت جا می‌گیرد و هر دور همان جا دوباره پر می‌شود. هر بار که یک String بزرگ‌تر می‌شود، ممکن است جای جدیدی در Heap بگیرد و جای قبلی را خالی بگذارد. بعد از هزاران بار، Heap مثل پنیر سوراخ‌سوراخ می‌شود: جمع فضای آزاد زیاد است ولی هیچ تکه بزرگ پیوسته‌ای نمانده (و HTTPS یک تکه پیوسته چند ده کیلوبایتی لازم دارد). reserve جا را یک بار و از اول می‌گیرد. برای رشته‌های ثابت هم char buf[64] با snprintf امن‌ترین است. برای دیدن مشکل، علاوه بر ESP.getFreeHeap() عدد ESP.getMaxAllocHeap() (بزرگ‌ترین تکه آزاد) را هم چاپ کن.
  6. آزمایش نگهبان. اگر delay را به 6000 تغییر دهی، هر دور loop بیش از ۵ ثانیه می‌شود و برد ریست می‌شود؛ بعد از ریست، پیام reason: TASK WATCHDOG را می‌بینی. هر مکانیزم ایمنی را یک بار عمدا تحریک کن تا مطمئن شوی واقعا کار می‌کند. نگهبانی که هرگز تست نشده، نگهبان نیست.

#include <WiFi.h>
#include <WebServer.h>
#include <ArduinoOTA.h>
#include <LittleFS.h>
#include <WiFiClientSecure.h>
#include <HTTPClient.h>
#include <ArduinoJson.h>
#include <Wire.h>
#include <Adafruit_GFX.h>
#include <Adafruit_SSD1306.h>
#include "secrets.h"
#ifndef OTA_PASS
#warning "OTA_PASS is not defined in secrets.h"
#define OTA_PASS "change-me"
#endif

struct Weather { float temp; float wind; unsigned long at; };
struct Config  { float lat; float lon; };

WebServer server(80);
Adafruit_SSD1306 display(128, 64, &Wire, -1);
QueueHandle_t weatherBox;          // صندوق یک‌خانه‌ای: همیشه آخرین هوا
SemaphoreHandle_t cfgMutex;        // قفل تنظیمات مشترک
TaskHandle_t weatherHandle = NULL;
Config cfg = {35.69, 51.39};       // پیش‌فرض: تهران

// ---------- LittleFS: خواندن و ذخیره امن تنظیمات ----------
void loadConfig() {
  File f = LittleFS.open("/config.json", "r");
  if (!f) return;                                  // هنوز ذخیره نشده
  JsonDocument doc;
  if (!deserializeJson(doc, f)) {
    cfg.lat = doc["lat"] | cfg.lat;
    cfg.lon = doc["lon"] | cfg.lon;
  }
  f.close();
}

bool saveConfig(const Config &c) {
  JsonDocument doc;
  doc["lat"] = c.lat;
  doc["lon"] = c.lon;
  File f = LittleFS.open("/config.tmp", "w");      // اول در فایل موقت
  if (!f) return false;
  bool ok = serializeJson(doc, f) > 0;
  f.close();
  if (!ok) return false;
  LittleFS.remove("/config.json");
  return LittleFS.rename("/config.tmp", "/config.json");  // بعد جابه‌جا
}

// ---------- Task هوا: هر ۱۰ دقیقه یا وقتی تنظیمات عوض شد ----------
bool fetchWeather(float lat, float lon, Weather &w) {
  char url[160];
  snprintf(url, sizeof(url),
           "https://api.open-meteo.com/v1/forecast?latitude=%.2f&longitude=%.2f"
           "&current=temperature_2m,wind_speed_10m", lat, lon);
  WiFiClientSecure client;
  client.useBuiltinCACertBundle();
  HTTPClient http;
  http.setConnectTimeout(5000);
  http.setTimeout(5000);
  http.useHTTP10(true);
  if (!http.begin(client, url)) return false;
  int code = http.GET();
  bool ok = false;
  if (code == HTTP_CODE_OK) {
    JsonDocument filter;
    filter["current"]["temperature_2m"] = true;
    filter["current"]["wind_speed_10m"] = true;
    JsonDocument doc;
    if (!deserializeJson(doc, http.getStream(), DeserializationOption::Filter(filter))) {
      w.temp = doc["current"]["temperature_2m"] | NAN;
      w.wind = doc["current"]["wind_speed_10m"] | NAN;
      w.at = millis();
      ok = !isnan(w.temp);
    }
  }
  http.end();
  return ok;
}

void weatherTask(void *param) {
  for (;;) {
    if (WiFi.status() == WL_CONNECTED) {
      xSemaphoreTake(cfgMutex, portMAX_DELAY);
      Config c = cfg;                              // کپی، بعد قفل را پس بده
      xSemaphoreGive(cfgMutex);
      Weather w;
      if (fetchWeather(c.lat, c.lon, w)) {
        xQueueOverwrite(weatherBox, &w);           // جای مقدار قبلی
      }
    }
    // ۱۰ دقیقه بخواب، مگر این که کسی زودتر بیدارمان کند
    ulTaskNotifyTake(pdTRUE, pdMS_TO_TICKS(10UL * 60 * 1000));
  }
}

// ---------- Task نمایش: هر ۲ ثانیه آخرین هوا روی OLED ----------
void displayTask(void *param) {
  Weather w;
  for (;;) {
    display.clearDisplay();
    display.setCursor(0, 0);
    display.println(WiFi.localIP());
    if (xQueuePeek(weatherBox, &w, 0) == pdPASS) {  // نگاه کن، برندار
      display.setTextSize(2);
      display.printf("%.1f C\n", w.temp);
      display.setTextSize(1);
      display.printf("wind %.1f km/h\n", w.wind);
      display.printf("%lu min ago", (millis() - w.at) / 60000);
    } else {
      display.println("waiting for data...");
    }
    display.display();
    vTaskDelay(pdMS_TO_TICKS(2000));
  }
}

// ---------- وب: صفحه از LittleFS، داده از کد ----------
void handleState() {
  Weather w = {NAN, NAN, 0};
  xQueuePeek(weatherBox, &w, 0);
  JsonDocument doc;
  xSemaphoreTake(cfgMutex, portMAX_DELAY);
  doc["lat"] = cfg.lat;
  doc["lon"] = cfg.lon;
  xSemaphoreGive(cfgMutex);
  doc["temp"] = w.temp;
  doc["wind"] = w.wind;
  String out;
  serializeJson(doc, out);
  server.send(200, "application/json", out);
}

void handleSave() {
  Config c = {server.arg("lat").toFloat(), server.arg("lon").toFloat()};
  if (c.lat < -90 || c.lat > 90 || c.lon < -180 || c.lon > 180) {
    return server.send(400, "text/plain", "bad lat/lon");
  }
  xSemaphoreTake(cfgMutex, portMAX_DELAY);
  cfg = c;
  xSemaphoreGive(cfgMutex);
  saveConfig(c);
  xTaskNotifyGive(weatherHandle);                  // «همین الان دوباره بگیر»
  server.sendHeader("Location", "/");
  server.send(303);
}

void setup() {
  Serial.begin(115200);
  LittleFS.begin(true);
  loadConfig();
  weatherBox = xQueueCreate(1, sizeof(Weather));
  cfgMutex = xSemaphoreCreateMutex();

  Wire.begin(21, 22);
  display.begin(SSD1306_SWITCHCAPVCC, 0x3C);
  display.setTextColor(SSD1306_WHITE);

  WiFi.mode(WIFI_STA);
  WiFi.setAutoReconnect(true);
  WiFi.begin(WIFI_SSID, WIFI_PASS);
  unsigned long t0 = millis();
  while (WiFi.status() != WL_CONNECTED && millis() - t0 < 20000) delay(250);

  ArduinoOTA.setHostname("weather-station");
  ArduinoOTA.setPassword(OTA_PASS);
  ArduinoOTA.begin();

  server.serveStatic("/", LittleFS, "/index.html");
  server.on("/api/state", HTTP_GET, handleState);
  server.on("/api/config", HTTP_POST, handleSave);
  server.begin();

  xTaskCreatePinnedToCore(weatherTask, "weather", 12288, NULL, 1, &weatherHandle, 1);
  xTaskCreatePinnedToCore(displayTask, "display", 4096, NULL, 1, NULL, 1);
}

void loop() {
  ArduinoOTA.handle();
  server.handleClient();
  delay(2);
}
  1. دو struct. Weather یک بسته از دما، باد و زمان گرفتن است؛ Config مختصات. بسته‌بندی داده‌های مرتبط در یک struct باعث می‌شود با یک xQueueOverwrite همه را با هم و یک‌جا جابه‌جا کنیم؛ هیچ‌وقت دمای جدید با زمان قدیمی قاطی نمی‌شود.
  2. صف یک‌خانه‌ای به عنوان «صندوق نامه» (Mailbox). صفی با طول ۱ که با xQueueOverwrite پر می‌شود و با xQueuePeek خوانده می‌شود. در صف معمولی (بخش ۱) هر داده یک بار خوانده و برداشته می‌شد. این‌جا دو خواننده داریم (OLED و وب) و هر دو فقط «آخرین هوا» را می‌خواهند؛ Peek نگاه می‌کند و برنمی‌دارد، Overwrite همیشه جای قبلی را می‌گیرد و هرگز «صف پر» نمی‌شود.
  3. خواندن تنظیمات در بوت. اگر فایل نبود یا JSON خراب بود، مقدار پیش‌فرض تهران (خط ۲۵) می‌ماند. همان اصل بخش ۵: دستگاه همیشه باید با تنظیمات ناقص هم بالا بیاید.
  4. ذخیره امن. اول config.tmp، بعد پاک کردن قبلی و تغییر نام. اگر برق وسط serializeJson برود، config.json قبلی سالم است. serializeJson(doc, f) مستقیم در فایل می‌نویسد و تعداد بایت‌ها را برمی‌گرداند؛ صفر یعنی شکست.
  5. fetchWeather. همان کد بخش ۴، با دو تفاوت: آدرس با snprintf از مختصات ساخته می‌شود، و این بار useBuiltinCACertBundle داریم. snprintf در یک آرایه ثابت ۱۶۰ بایتی می‌نویسد و هرگز از آن بیرون نمی‌زند؛ هیچ String موقتی در Heap ساخته نمی‌شود. این Task ماه‌ها هر ۱۰ دقیقه اجرا می‌شود، پس دقیقا جایی است که تکه‌تکه شدن حافظه مهم است.
  6. weatherTask. تنظیمات را زیر قفل کپی می‌کند، قفل را فورا پس می‌دهد، بعد درخواست کند HTTPS را انجام می‌دهد و نتیجه را در صندوق می‌گذارد. هرگز قفل را در طول یک کار کند (چند ثانیه HTTPS) نگه ندار، وگرنه صفحه وب هم که cfg را می‌خواهد همان‌قدر منتظر می‌ماند. «کپی کن، رها کن، بعد کار کن».
  7. ulTaskNotifyTake با سقف ۱۰ دقیقه. Task می‌خوابد تا یا ۱۰ دقیقه بگذرد، یا کسی با xTaskNotifyGive بیدارش کند. «اعلان Task» (Task Notification) سبک‌ترین ابزار FreeRTOS برای «هی، بیدار شو» است. با vTaskDelay ی ساده، بعد از تغییر شهر باید تا ۱۰ دقیقه منتظر هوای جدید می‌ماندی.
  8. displayTask. هر ۲ ثانیه صفحه را از نو می‌کشد: IP، دما با حروف درشت، باد، و این که داده چند دقیقه پیش گرفته شده. فقط همین Task به OLED (و I2C) دست می‌زند، پس برای نمایشگر Mutex لازم نیست. قانون ساده‌تر از قفل: هر سخت‌افزار یک صاحب. نمایش «چند دقیقه پیش» مهم است: اگر اینترنت یک روز قطع باشد، کاربر دمای دیروز را به جای امروز باور نمی‌کند.
  9. /api/state. آخرین هوا را از صندوق Peek می‌کند و تنظیمات را زیر قفل می‌خواند و همه را به شکل JSON برمی‌گرداند. این تابع در loopTask اجرا می‌شود (داخل server.handleClient)، در حالی که weatherTask ممکن است هم‌زمان cfg را بخواند یا عوض شدنش را منتظر باشد؛ برای همین قفل لازم است.
  10. /api/config. ورودی را اعتبارسنجی می‌کند، در cfg و فایل ذخیره می‌کند، weatherTask را بیدار می‌کند و مرورگر را با کد 303 به صفحه اصلی برمی‌گرداند. هرگز به ورودی کاربر اعتماد نکن: toFloat() برای متن نامعتبر صفر برمی‌گرداند و عرض جغرافیایی ۵۰۰ معنی ندارد. 303 باعث می‌شود رفرش صفحه فرم را دوباره نفرستد.
  11. setup به ترتیب درست. LittleFS و تنظیمات، بعد صف و قفل (قبل از هر Task)، OLED، Wi-Fi با سقف ۲۰ ثانیه، OTA، وب سرور، و در آخر Taskها. اگر Wi-Fi در ۲۰ ثانیه وصل نشد، دستگاه متوقف نمی‌شود: setAutoReconnect بعدا وصلش می‌کند و weatherTask تا وصل شدن فقط منتظر می‌ماند. Stack ی weatherTask عمدا ۱۲ کیلوبایت است چون HTTPS سنگین است؛ بعد از چند روز با uxTaskGetStackHighWaterMark مقدار واقعی را اندازه بگیر.
  12. loop کوچک. فقط OTA و وب سرور، با یک delay(2). چون کار کند در Task جداست، loop همیشه در چند میلی‌ثانیه می‌چرخد و OTA و صفحه وب همیشه سریع جواب می‌دهند، حتی وسط یک درخواست HTTPS کند. این همان مشکلی بود که درس را با آن شروع کردیم.
در Wokwi چه چیزی را می‌توانی امتحان کنی؟

Wokwi Wi-Fi (با Wokwi-GUEST)، HTTPS، OLED و FreeRTOS را شبیه‌سازی می‌کند، پس بخش هوا و نمایش کار می‌کند. ولی OTA و آپلود پوشه data در Wokwi وجود ندارند؛ بدون فایل index.html، صفحه اصلی خالی است ولی /api/state جواب می‌دهد. پروژه کامل را روی برد واقعی بساز.

ویدیوی کمکی

  • قسمت دوم از مجموعه مشهور «Introduction to RTOS» شرکت DigiKey (مدرس: Shawn Hymel) که دقیقا با ESP32 و Arduino IDE کار می‌کند.
  • دنبال همان هفت ورودی xTaskCreatePinnedToCore بگرد و آن‌ها را با جدول این درس مقایسه کن. دقت کن مدرس درباره واحد اندازه Stack در ESP32 چه می‌گوید.
  • ویدیو با core قدیمی‌تر ضبط شده؛ اگر جایی با core 3.x فرق داشت، ملاک این درس است.
  • قسمت پنجم همان مجموعه، درباره صف (Queue). بعد از دیدن آن، مثال پتانسیومتر این درس را دوباره بخوان.
  • به این نکته توجه کن که داده کپی می‌شود، نه اشاره‌گرش؛ و به زمان صبر (timeout) در ارسال و دریافت.
  • این مجموعه تمرین‌های خوبی در انتهای هر قسمت دارد؛ اگر وقت داری، تمرین قسمت ۵ را روی برد خودت انجام بده.

حرف مربی

این درس ابزارهای قدرتمندی به تو داد و قدرت خطرناک است. سه قانون من: یک، هر Task، هر صف و هر قفل جدید باید دلیل داشته باشد؛ اگر نمی‌توانی در یک جمله بگویی چرا این کار Task جدا می‌خواهد، نمی‌خواهد. دو، هیچ‌وقت برنامه‌ای را با OTA روی دستگاهی که به آن دسترسی نداری نفرست که قبلا همان برنامه را روی یک برد روی میز، با قطع و وصل Wi-Fi و قطع برق، تست نکرده‌ای. من دستگاه‌هایی دیده‌ام که به خاطر یک خط اشتباه در setup، مجبور شدند آن‌ها را از پشت‌بام پایین بیاورند. سه، دستگاهی که علت ریست‌هایش را ثبت نمی‌کند، دستگاه حرفه‌ای نیست. از امروز در هر پروژه‌ای که بیش از یک روز روشن می‌ماند، کد «جعبه سیاه» بخش ۵ را بگذار. بعد از یک هفته که شمارنده کرش صفر ماند، آن وقت می‌توانی بگویی «کار می‌کند».

آزمون این درس

در ESP32، خط xTaskCreatePinnedToCore(f, "t", 2048, NULL, 1, NULL, 1); چقدر Stack به Task می‌دهد؟

  1. ۲۰۴۸ word یعنی ۸ کیلوبایت
  2. ۲۰۴۸ بایت یعنی ۲ کیلوبایت
  3. همیشه ۸ کیلوبایت، مثل loopTask
  4. بستگی به اولویت دارد
در FreeRTOS ی ESP-IDF اندازه Stack به بایت است. کدهای کپی‌شده از پلتفرم‌های دیگر با عدد کوچک مثل 512 روی ESP32 کرش می‌کنند.

Task ای روی هسته ۰ داری که در یک حلقه for(;;) بدون هیچ vTaskDelay عددی را زیاد می‌کند. حدود ۵ ثانیه بعد چه می‌شود؟

  1. هیچ اتفاقی نمی‌افتد
  2. Stack overflow رخ می‌دهد
  3. Task Watchdog فعال می‌شود چون IDLE0 نوبت اجرا نگرفته، و برد ریست می‌شود
  4. Brownout detector برد را ریست می‌کند
نگهبان Task در core آردوینو IDLE0 را با مهلت ۵ ثانیه زیر نظر دارد. درمان: یک vTaskDelay کوتاه در حلقه.

Task حسگر هر ۲۰۰ میلی‌ثانیه عددی می‌خواند و Task نمایش باید آن را نشان دهد. امن‌ترین و تمیزترین راه انتقال چیست؟

  1. یک صف (Queue) با xQueueSend و xQueueReceive
  2. یک متغیر سراسری معمولی
  3. فقط یک Mutex بدون متغیر
  4. نوشتن در Serial و خواندن از آن
صف داده را کپی می‌کند، نصفه جابه‌جا نمی‌کند، و Task گیرنده را تا رسیدن داده می‌خواباند.

برنامه‌ات «Sketch too big» می‌دهد و دستگاه باید OTA داشته باشد. کدام Partition Scheme را انتخاب می‌کنی؟

  1. Huge APP (3MB No OTA/1MB SPIFFS)
  2. No OTA (2MB APP/2MB SPIFFS)
  3. Default 4MB with spiffs
  4. Minimal SPIFFS (1.9MB APP with OTA/128KB SPIFFS)
Minimal SPIFFS دو جای برنامه ۱٫۹ مگابایتی دارد: هم برنامه بزرگ‌تر جا می‌شود هم OTA می‌ماند. فقط فضای فایل ۱۲۸ کیلوبایت می‌شود.

چرا در مثال هوا قبل از deserializeJson(doc, http.getStream(), ...) خط http.useHTTP10(true) را گذاشتیم؟

  1. چون HTTP 1.0 سریع‌تر است
  2. تا سرور جواب را chunked (تکه‌تکه با عددهای اندازه) نفرستد و JSON خوانده‌شده از جریان خراب نشود
  3. چون HTTPS فقط با HTTP 1.0 کار می‌کند
  4. تا گواهی سرور بررسی نشود
وقتی مستقیم از getStream() می‌خوانی، HTTPClient تکه‌ها را سرهم نمی‌کند. HTTP/1.0 این مشکل را از ریشه حذف می‌کند.

دستگاهت در سقف است. بعد از یک آپدیت OTA دیگر در منوی Port دیده نمی‌شود و Wi-Fi هم وصل نیست. کدام کار از قبل می‌توانست جلوی این را بگیرد؟

  1. برداشتن رمز OTA
  2. انتخاب Huge APP
  3. تست برنامه جدید روی یک برد روی میز، و استفاده از Rollback که فقط بعد از وصل شدن Wi-Fi نسخه جدید را تأیید می‌کند
  4. خاموش کردن Watchdog
با verifyRollbackLater() و تأیید دستی بعد از وصل شدن Wi-Fi، نسخه خراب خودبه‌خود به نسخه قبلی برمی‌گردد. و هیچ چیز جای تست روی میز را نمی‌گیرد.

تمرین‌ها

تمرین ۱: سه آشپز

برنامه صف (پتانسیومتر و LED) را گسترش بده: یک Task سوم بساز که LED دوم روی GPIO5 را چشمک بزند، و سرعت چشمکش به عدد پتانسیومتر بستگی داشته باشد (عدد ۰ یعنی هر ۱۰۰۰ میلی‌ثانیه و ۴۰۹۵ یعنی هر ۱۰۰ میلی‌ثانیه). Task نمایش باید عدد را برای Task سوم هم بفرستد. Stack هر سه Task را هر ۵ ثانیه چاپ کن و Stackها را تا جای ممکن کم کن، با حداقل ۵۰۰ بایت حاشیه.

راهنمایی

یک صف دوم بساز. Task چشمک‌زن می‌تواند با xQueueReceive(q2, &v, 0) بدون صبر بپرسد «عدد جدید داری؟» و اگر نبود با عدد قبلی ادامه دهد. برای تبدیل عدد از map(v, 0, 4095, 1000, 100) استفاده کن.

تمرین ۲: هشدار گرما

برنامه هوا و ntfy را ترکیب کن: اگر دمای تهران از ۳۵ درجه بیشتر شد، یک هشدار ntfy بفرست، ولی فقط یک بار تا وقتی دما دوباره زیر ۳۳ درجه نیامده. وضعیت «هشدار فرستاده شده» باید بعد از ریست هم یادش بماند.

راهنمایی

فاصله ۳۵ و ۳۳ همان «هیسترزیس» است تا دمای ۳۵ و ۳۴٫۹ پشت سر هم ده‌ها هشدار نسازد. برای به یاد ماندن بعد از ریست، یک bool در Preferences کافی است؛ فقط وقتی مقدارش عوض شد بنویس.

جواب (بخش کلیدی) 
prefs.begin("alert", false);
bool sent = prefs.getBool("sent", false);
if (!sent && t > 35.0) {
  if (sendAlert("Heat", "Tehran above 35 C")) {
    prefs.putBool("sent", true);   // فقط وقتی واقعا فرستاده شد
  }
} else if (sent && t < 33.0) {
  prefs.putBool("sent", false);    // آماده برای هشدار بعدی
}
prefs.end();
تمرین ۳: جعبه سیاه در صفحه وب

«جعبه سیاه» بخش ۵ را به پروژه ایستگاه هوا اضافه کن: علت آخرین ریست، تعداد بوت‌ها و تعداد کرش‌ها را در /api/state برگردان و در index.html نشان بده. سپس با تغییر عمدی (مثلا یک حلقه بی‌پایان در loop بعد از ۱ دقیقه با enableLoopWDT) یک ریست نگهبان بساز و ببین در صفحه ثبت می‌شود. در آخر نسخه سالم را با OTA بفرست.

راهنمایی

علت ریست را یک بار در setup بخوان و در یک متغیر سراسری const char * نگه دار؛ در handleState فقط آن را در JSON بگذار. برای تست OTA، مطمئن شو نسخه خراب هم هنوز ArduinoOTA.handle() را در ۱ دقیقه اول صدا می‌زند، وگرنه باید با کابل درستش کنی. (همین تجربه، حرف مربی را برایت واقعی می‌کند.)

خلاصه درس در سه خط

FreeRTOS کارهای کند را در Taskهای جدا اجرا می‌کند؛ داده را با صف و منبع مشترک را با Mutex جابه‌جا کن، Stack را به بایت بده و هر حلقه را جایی بخوابان تا نگهبان ریست نکند. OTA با دو پارتیشن برنامه (Default یا Minimal SPIFFS) و رمز، دستگاه را از راه دور به‌روز نگه می‌دارد و LittleFS فایل‌ها و تنظیمات را جدا از برنامه نگه می‌دارد. APIها را با HTTPS، سقف زمان، فیلتر JSON و فاصله منطقی صدا بزن، و با ثبت علت ریست، Watchdog و ذخیره امن، دستگاهی بساز که ماه‌ها بدون تو کار کند.
