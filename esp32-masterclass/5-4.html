تا اینجا برنامه‌هایی نوشتی که روی میز کار می‌کنند: برد کنار لپ‌تاپ است، کابل USB وصل است و اگر گیر کرد دکمه EN را می‌زنی. ولی دستگاه واقعی جای دیگری زندگی می‌کند: داخل سقف، پشت کمد، روی پشت‌بام. آنجا کسی دکمه ریست نمی‌زند و کابل USB نیست. این درس اولین درس از سه درسی است که فاصله «اسکچ سرگرمی» تا «دستگاه واقعی» را پر می‌کنند. اینجا FreeRTOS را یاد می‌گیری: چطور چند کار را هم‌زمان اجرا کنی، هر کدام در Task خودش، بدون این که کار هم را خراب کنند. داده را با صف بین Taskها جابه‌جا می‌کنی، از منابع مشترک با Mutex محافظت می‌کنی، یک Task را با اعلان (Notification) یا وقفه دکمه فورا بیدار می‌کنی، و می‌فهمی چرا نگهبان (Watchdog) گاهی برد را ریست می‌کند. درس ۵.۵ آپدیت بی‌سیم (OTA) و فایل (LittleFS) را اضافه می‌کند و درس ۵.۶ فراخوانی API اینترنتی، چک‌لیست پایداری و یک پروژه ترکیبی را.

FreeRTOS: چند کار هم‌زمان بدون قاطی شدن

مشکل: loop() تنها، زود شلوغ می‌شود

فرض کن دستگاهی می‌خواهی که: یک LED را هر ۲۵۰ میلی‌ثانیه چشمک بزند، یک LED دیگر را هر ۱ ثانیه، هر ۲۰۰ میلی‌ثانیه پتانسیومتر را بخواند، هر ۱۰ دقیقه وضع هوا را از اینترنت بگیرد، و همیشه به صفحه وب جواب بدهد. با delay() غیرممکن است، چون هر delay همه کارهای دیگر را متوقف می‌کند. با millis() (درس ۳.۱) شدنی است، ولی loop پر از if (millis() - lastX >= ...) می‌شود. بدتر از همه: گرفتن هوا از اینترنت ممکن است ۲ تا ۵ ثانیه طول بکشد و در این مدت LEDها و صفحه وب هم منتظر می‌مانند.

راه حل حرفه‌ای این است که هر کار را جدا بنویسی، انگار هر کدام برنامه کوچک خودش را دارد، و یک «مدیر» تصمیم بگیرد هر لحظه نوبت کیست. این مدیر FreeRTOS است: یک سیستم‌عامل بی‌درنگ (Real-Time Operating System) کوچک که همیشه روی ESP32 در حال اجراست، حتی وقتی تو خبر نداری.

مثال از زندگی روزمره: آشپزخانه رستوران

یک رستوران را تصور کن. اگر فقط یک آشپز داشته باشد (این همان loop تنهاست)، باید برنج را بگذارد، بدود کباب را برگرداند، بدود سالاد درست کند، و اگر پای تلفن سفارش‌ها گیر کند، کباب می‌سوزد. رستوران واقعی چند آشپز دارد (هر کدام یک Task): یکی مسئول برنج، یکی کباب، یکی سالاد. سرآشپز (زمان‌بند FreeRTOS یا Scheduler) تصمیم می‌گیرد چه کسی از اجاق استفاده کند. ESP32 دو اجاق دارد (دو هسته)، پس دو آشپز می‌توانند دقیقا هم‌زمان بپزند.

آشپزها با هم حرف نمی‌زنند که کار هم را خراب نکنند؛ سفارش را روی پیشخوان می‌گذارند (این Queue یا صف است). و فقط یک چاقوی بزرگ هست؛ هر کس برش داشت، بقیه صبر می‌کنند تا سر جایش بگذارد (این Mutex است).

اولین Taskها: دو LED با دو سرعت

مدار: دو LED، هر کدام با مقاومت ۲۲۰ اهم خودش، روی GPIO4 و GPIO26. پتانسیومتر روی GPIO34 را هم همین حالا وصل کن چون در مثال بعدی لازم است.

// دو LED با دو سرعت مختلف، هر کدام در Task خودش
const int LED_FAST = 4;   // LED سریع
const int LED_SLOW = 26;  // LED کند

void blinkFast(void *param) {          // تابع Task اول
  pinMode(LED_FAST, OUTPUT);
  bool on = false;
  for (;;) {                           // Task هرگز نباید تمام شود
    on = !on;
    digitalWrite(LED_FAST, on);
    vTaskDelay(pdMS_TO_TICKS(250));    // ۲۵۰ میلی‌ثانیه کنار برو
  }
}

void blinkSlow(void *param) {          // تابع Task دوم
  pinMode(LED_SLOW, OUTPUT);
  bool on = false;
  for (;;) {
    on = !on;
    digitalWrite(LED_SLOW, on);
    vTaskDelay(pdMS_TO_TICKS(1000));   // ۱ ثانیه
  }
}

void setup() {
  Serial.begin(115200);
  xTaskCreatePinnedToCore(
    blinkFast,     // کدام تابع
    "blinkFast",   // اسم Task (فقط برای عیب‌یابی)
    2048,          // اندازه Stack به «بایت»
    NULL,          // پارامتر ورودی (نداریم)
    1,             // اولویت
    NULL,          // دستگیره Task (لازم نداریم)
    1);            // هسته ۱
  xTaskCreatePinnedToCore(blinkSlow, "blinkSlow", 2048, NULL, 1, NULL, 1);
  Serial.printf("setup() runs on core %d\n", xPortGetCoreID());
}

void loop() {                          // loop خودش هم یک Task است
  Serial.printf("loop() alive on core %d, millis=%lu\n",
                xPortGetCoreID(), millis());
  delay(2000);
}
  1. تابع Task. هر Task یک تابع معمولی با این شکل دقیق است: void اسم(void *param). ورودی param یک «اشاره‌گر به هر چیزی» است که موقع ساختن Task می‌توانی به آن بدهی. FreeRTOS برای همه Taskها یک شکل ثابت می‌خواهد تا بتواند با همه یکسان رفتار کند. اگر شکل تابع فرق کند، کامپایلر خطا می‌دهد.
  2. کار یک‌باره اول Task. مثل یک setup کوچک مخصوص همین Task: پین را خروجی می‌کند و یک متغیر محلی برای وضعیت LED می‌سازد. متغیر on داخل Task است و روی Stack همین Task زندگی می‌کند. هر Task Stack جدای خودش را دارد، پس دو Task با متغیرهای هم‌نام قاطی نمی‌شوند.
  3. حلقه بی‌پایان for (;;). Task باید تا ابد در یک حلقه بماند. این همان نقش loop() است. اگر تابع Task به } آخر برسد و return کند، ESP32 با خطا (abort) ریست می‌شود. اگر واقعا کار Task تمام شد، باید خودش را با vTaskDelete(NULL); پاک کند.
  4. vTaskDelay و pdMS_TO_TICKS. vTaskDelay به زمان‌بند می‌گوید «من فعلا کاری ندارم، اجاق را به دیگران بده». واحد آن «تیک» است؛ pdMS_TO_TICKS(250) میلی‌ثانیه را به تیک تبدیل می‌کند. روی ESP32 آردوینو هر تیک ۱ میلی‌ثانیه است (CONFIG_FREERTOS_HZ=1000)، پس تبدیل عدد را عوض نمی‌کند؛ ولی اگر روزی کد را روی سیستمی با تیک ۱۰ میلی‌ثانیه ببری، بدون این ماکرو زمان‌ها ۱۰ برابر می‌شوند. عادت درست را از اول بساز.
  5. Task دوم. دقیقا همان الگو، فقط با پین و زمان دیگر. ببین چقدر ساده شد: هر Task فقط به کار خودش فکر می‌کند. هیچ if (millis() - last ...) درهمی نیست.
  6. xTaskCreatePinnedToCore با هفت ورودی. به ترتیب: تابع، اسم، اندازه Stack، پارامتر، اولویت، دستگیره (Handle)، شماره هسته. «PinnedToCore» یعنی «به این هسته سنجاقش کن». اگر هسته را مشخص نکنی (تابع xTaskCreate)، Task می‌تواند روی هر دو هسته اجرا شود؛ برای شروع، سنجاق کردن رفتار را قابل پیش‌بینی‌تر می‌کند.
  7. 2048 یعنی ۲۰۴۸ بایت. این مهم‌ترین نکته ESP32 است: در FreeRTOS نسخه ESP-IDF اندازه Stack به بایت است. در FreeRTOS استاندارد (مثلا روی STM32) همین عدد به «word» است و هر word چهار بایت؛ یعنی 2048 آنجا ۸ کیلوبایت می‌شد. اگر کدی از اینترنت برداشتی که Stack را 512 گذاشته، روی ESP32 فقط ۵۱۲ بایت می‌گیری و احتمالا برد کرش می‌کند. برای Task ساده ۲۰۴۸، برای Task با Serial.printf حدود ۳۰۰۰ تا ۴۰۹۶، و برای Task با HTTPS دست‌کم ۸ تا ۱۲ کیلوبایت بگذار.
  8. اولویت (Priority). عددی از 0 تا 24؛ بزرگ‌تر یعنی مهم‌تر. وقتی دو Task آماده اجرا هستند، زمان‌بند همیشه اولویت بالاتر را انتخاب می‌کند. Taskهای هم‌اولویت به نوبت (هر تیک) اجرا می‌شوند. ۱ همان اولویت loop است. برای شروع همه را ۱ یا ۲ بگذار. اولویت بالا به Taskی بده که زود باید جواب بدهد و کوتاه کار می‌کند؛ Task طولانی با اولویت بالا بقیه را گرسنه نگه می‌دارد.
  9. Task دوم در یک خط. همان هفت ورودی، بدون توضیح. بعد از این خط سه Task روی هسته ۱ داریم: loopTask و دو چشمک‌زن؛ به‌علاوه Taskهای خود سیستم روی هسته ۰.
  10. loop هم کار خودش را می‌کند. هر ۲ ثانیه یک پیام چاپ می‌کند؛ xPortGetCoreID() شماره هسته فعلی را برمی‌گرداند. نکته مهم: در ESP32 آردوینو delay() در واقع همان vTaskDelay است (در core تعریف شده vTaskDelay(ms / portTICK_PERIOD_MS))، پس delay در loop هم CPU را به Taskهای دیگر می‌دهد و چشمک‌ها قطع نمی‌شوند. ولی delayMicroseconds() و حلقه‌های خالی مثل while(...) {} واقعا CPU را قفل می‌کنند.
setup() runs on core 1 loop() alive on core 1, millis=312 loop() alive on core 1, millis=2312 loop() alive on core 1, millis=4312

و روی برد: LED قرمز ۲ بار در ثانیه و LED سبز هر ۲ ثانیه یک بار (۱ ثانیه روشن، ۱ ثانیه خاموش) چشمک می‌زند، کاملا مستقل از هم.

پس vTaskDelay با delay چه فرقی دارد؟

در ESP32 آردوینو از نظر رفتار تقریبا هیچ؛ هر دو Task فعلی را می‌خوابانند و CPU آزاد می‌شود. تفاوت در واحد است: delay(ms) میلی‌ثانیه می‌گیرد و vTaskDelay(ticks) تیک. داخل Taskها از vTaskDelay(pdMS_TO_TICKS(...)) استفاده می‌کنیم چون زبان خود FreeRTOS است و روی هر سیستمی درست کار می‌کند. اگر می‌خواهی کاری دقیقا هر ۱۰۰ میلی‌ثانیه تکرار شود (بدون این که زمان اجرای خود کار به آن اضافه شود)، از vTaskDelayUntil استفاده کن.

گوشه C++: void *، & و لامبدا

کد FreeRTOS (و کتابخانه‌های ESP32 در درس‌های ۵.۵ و ۵.۶) پر از سه علامت C++ است که اولش ترسناک به نظر می‌رسند. هر کدام یک ایده ساده است:

مثال روزمره: بسته، نشانی و اسم خودمانی

اشاره‌گر (*) مثل نشانی خانه روی یک کاغذ است: کاغذ خود خانه نیست، ولی با آن خانه را پیدا می‌کنی. void * کاغذ نشانی‌ای است که رویش ننوشته آن ساختمان چه نوعی است؛ کسی که آن را می‌گیرد باید خودش بداند. ارجاع (& در پارامتر) مثل اسم خودمانی است: «علی» و «علیرضا» یک نفرند، پس اگر موهای علی را کوتاه کنی، موهای علیرضا هم کوتاه شده. لامبدا یادداشتی است که دستورش را همان‌جا می‌نویسی و مستقیم به دست کسی می‌دهی، به جای یک دستور پخت اسم‌دار در کتاب آشپزی.

هر سه در یک اسکچ کوچک (همان مدار: LEDها روی GPIO4 و GPIO26):

// void*، & و لامبدا: سه علامت C++ در کد FreeRTOS
int fastPin = 4;                             // سراسری: تا آخر برنامه زنده است
int slowPin = 26;

void blinkTask(void *param) {                // یک تابع، برای دو Task
  int pin = *(int *)param;                   // void* را int* کن، بعد عدد را بخوان
  int ms = (pin == fastPin) ? 250 : 1000;
  pinMode(pin, OUTPUT);
  bool on = false;
  for (;;) {
    on = !on;
    digitalWrite(pin, on);
    vTaskDelay(pdMS_TO_TICKS(ms));
  }
}

void addOne(int &n) {                        // & در پارامتر: ارجاع
  n = n + 1;                                 // متغیر خود صدازننده را عوض می‌کند
}

void setup() {
  Serial.begin(115200);
  xTaskCreatePinnedToCore(blinkTask, "fast", 2048, &fastPin, 1, NULL, 1);
  xTaskCreatePinnedToCore(blinkTask, "slow", 2048, &slowPin, 1, NULL, 1);
  xTaskCreatePinnedToCore(                   // یک Task به شکل لامبدا
    [](void *param) {
      int count = 0;
      for (;;) {
        addOne(count);                       // count واقعا یکی زیاد می‌شود
        Serial.printf("lambda task: count = %d\n", count);
        vTaskDelay(pdMS_TO_TICKS(1000));
      }
    },
    "counter", 3072, NULL, 1, NULL, 1);
}

void loop() {
  delay(1000);                               // loop این‌جا کاری ندارد
}
  1. & جلوی متغیر: «نشانیِ». &fastPin عدد ۴ نیست؛ نشانی جایی از حافظه است که عدد ۴ آنجا نگه‌داری می‌شود. همین نشانی به عنوان param به Task می‌رسد. حالا یک تابع می‌تواند برای دو Task کار کند، هر کدام با پین خودش. متغیرها عمدا سراسری‌اند: متغیر محلیِ setup() با تمام شدن setup از بین می‌رود و Task نشانی‌ای را می‌خواند که آشغال در آن است.
  2. void *: «اشاره‌گر به هر چیزی». FreeRTOS نمی‌داند تو چه چیزی می‌فرستی، پس پارامتر نوع ندارد. (int *)param می‌گوید «این نشانی به یک int اشاره می‌کند» و * اولش همان int را می‌خواند. این همان یک شکل ثابتی است که FreeRTOS برای همه توابع Task می‌خواهد. (void *param) را در همه Taskهای این دوره می‌بینی، معمولا بدون استفاده (NULL فرستاده می‌شود).
  3. & در پارامتر: ارجاع (Reference). int &n یعنی «n فقط اسم دیگری برای متغیر صدازننده است». addOne(count) واقعا count را عوض می‌کند. بدون &، تابع یک کپی می‌گرفت و فقط کپی را عوض می‌کرد. در درس ۵.۶، fetchWeather(float &temp, float &wind) دقیقا با همین روش دو عدد را هم‌زمان «برمی‌گرداند».
  4. لامبدا: تابع بی‌اسم. [](void *param) { ... } درست همان‌جا که لازم است نوشته می‌شود. [] خالی یعنی از متغیرهای محلی اطرافش استفاده نمی‌کند. لامبدا را همه جا به شکل «Callback» می‌بینی، یعنی تابع کوچکی که به یک کتابخانه می‌دهی تا بعدا صدایش بزند: ArduinoOTA.onStart([]() { ... }) و server.on("/api/temp", []() { ... }) در درس ۵.۵. برای Taskی که بیشتر از چند خط است، تابع معمولی اسم‌دار خواناتر است.

انتقال امن داده: صف (Queue)

حالا مسئله واقعی: یک Task سنسور را می‌خواند و Task دیگری باید آن را نمایش بدهد. اولین فکر: «یک متغیر سراسری بگذارم، یکی بنویسد و دیگری بخواند». برای یک int ساده معمولا کار می‌کند، ولی برای داده بزرگ‌تر (مثلا یک struct با دما و رطوبت و زمان) ممکن است Task نمایش وسط نوشتن آن را بخواند: دمای جدید با رطوبت قدیمی! به این باگ «Race Condition» (مسابقه) می‌گویند و بدترین نوع باگ است، چون هر هزار بار یک بار رخ می‌دهد.

صف راه حل رسمی FreeRTOS است. صف یک لوله با تعداد خانه مشخص است: یک Task از یک سر کپی داده را می‌گذارد و Task دیگر از سر دیگر برمی‌دارد، به همان ترتیب (اول وارد، اول خارج). FreeRTOS تضمین می‌کند که هیچ‌وقت داده نصفه جابه‌جا نشود.

// Task حسگر ← صف (Queue) ← Task نمایش، به‌علاوه قفل Serial
const int POT_PIN = 34;          // پتانسیومتر (ADC1، فقط ورودی)
const int LED_PIN = 4;           // LED با روشنایی متغیر (PWM)

QueueHandle_t potQueue;          // صف بین دو Task
SemaphoreHandle_t serialMutex;   // قفل Serial Monitor
TaskHandle_t sensorHandle = NULL;
TaskHandle_t displayHandle = NULL;

void sensorTask(void *param) {
  for (;;) {
    int raw = analogRead(POT_PIN);                  // 0 تا 4095
    if (xQueueSend(potQueue, &raw, 0) != pdPASS) {  // صبر نکن
      // صف پر است: این نمونه را دور بریز
    }
    vTaskDelay(pdMS_TO_TICKS(200));                 // ۵ بار در ثانیه
  }
}

void displayTask(void *param) {
  int value;
  for (;;) {
    // تا ۱ ثانیه منتظر داده بمان؛ در این مدت CPU آزاد است
    if (xQueueReceive(potQueue, &value, pdMS_TO_TICKS(1000)) == pdPASS) {
      ledcWrite(LED_PIN, value / 16);               // 0..4095 → 0..255
      if (xSemaphoreTake(serialMutex, pdMS_TO_TICKS(100)) == pdTRUE) {
        Serial.printf("pot=%4d  led=%3d\n", value, value / 16);
        xSemaphoreGive(serialMutex);                // قفل را پس بده
      }
    }
  }
}

void setup() {
  Serial.begin(115200);
  ledcAttach(LED_PIN, 5000, 8);                     // 5kHz، ۸ بیت
  potQueue = xQueueCreate(10, sizeof(int));         // ۱۰ خانه، هر کدام یک int
  serialMutex = xSemaphoreCreateMutex();
  if (potQueue == NULL || serialMutex == NULL) {
    Serial.println("Out of memory!");
    while (true) delay(1000);
  }
  xTaskCreatePinnedToCore(sensorTask, "sensor", 3072, NULL, 2, &sensorHandle, 1);
  xTaskCreatePinnedToCore(displayTask, "display", 4096, NULL, 1, &displayHandle, 1);
}

void loop() {
  delay(5000);
  if (xSemaphoreTake(serialMutex, portMAX_DELAY) == pdTRUE) {
    Serial.printf("[stack] sensor free=%u B, display free=%u B, heap=%u B\n",
                  (unsigned)uxTaskGetStackHighWaterMark(sensorHandle),
                  (unsigned)uxTaskGetStackHighWaterMark(displayHandle),
                  (unsigned)ESP.getFreeHeap());
    xSemaphoreGive(serialMutex);
  }
}
  1. دستگیره‌ها (Handle). QueueHandle_t و SemaphoreHandle_t و TaskHandle_t مثل «شماره تلفن» صف، قفل و Taskها هستند؛ خود شیء را FreeRTOS در حافظه می‌سازد و ما فقط شماره‌اش را نگه می‌داریم. سراسری هستند تا همه Taskها به آن‌ها دسترسی داشته باشند. خود دستگیره بعد از ساخته شدن عوض نمی‌شود، پس سراسری بودنش خطری ندارد.
  2. خواندن و فرستادن. xQueueSend(صف، آدرس داده، زمان صبر) محتوای raw را کپی می‌کند و در صف می‌گذارد. علامت & یعنی «آدرس این متغیر». چون کپی می‌شود، بعد از این خط raw می‌تواند عوض شود بدون این که داده داخل صف خراب شود. زمان صبر 0 یعنی «اگر صف پر است منتظر نمان»؛ Task سنسور نباید به خاطر کندی نمایش عقب بیفتد.
  3. اگر صف پر بود. xQueueSend مقدار errQUEUE_FULL برمی‌گرداند و ما عمدا کاری نمی‌کنیم: این نمونه دور ریخته می‌شود. در دستگاه واقعی باید تصمیم بگیری: «داده جدید مهم‌تر است یا قدیمی؟». برای نمایش، تازه‌ترین داده مهم است؛ برای لاگ، همه داده‌ها. این تصمیم را آگاهانه بگیر، نه تصادفی.
  4. xQueueReceive با زمان صبر. Task نمایش تا ۱ ثانیه منتظر می‌ماند تا چیزی به صف برسد. در این مدت واقعا می‌خوابد و صفر درصد CPU مصرف می‌کند. این زیباترین بخش صف است: Task نمایش نیازی به vTaskDelay ندارد، چون خود انتظار برای صف، CPU را آزاد می‌کند. به محض رسیدن داده، FreeRTOS بیدارش می‌کند.
  5. روشنایی LED. عدد ۱۲ بیتی ADC (۰ تا ۴۰۹۵) تقسیم بر ۱۶ می‌شود ۰ تا ۲۵۵، یعنی بازه PWM هشت بیتی. همان ledcWrite درس ۳.۲ با API نسخه ۳. در core 2.x باید از ledcSetup و ledcAttachPin با شماره کانال استفاده می‌کردی.
  6. Mutex دور Serial. xSemaphoreTake چاقو را برمی‌دارد (تا ۱۰۰ میلی‌ثانیه صبر می‌کند اگر دست کس دیگری است)، چاپ می‌کند و xSemaphoreGive آن را پس می‌دهد. بدون قفل، اگر loop و Task نمایش هم‌زمان چاپ کنند، خط‌ها وسط هم می‌افتند: pot=12[stack] sens34 led=.... هر منبع مشترکی (Serial، I2C، یک فایل، یک متغیر بزرگ) را که بیش از یک Task از آن استفاده می‌کنند، با Mutex محافظت کن. قانون طلایی: هر Take یک Give دارد، وگرنه بقیه تا ابد منتظر می‌مانند.
  7. ساختن صف و قفل و بررسی موفقیت. xQueueCreate(10, sizeof(int)) صفی با ۱۰ خانه می‌سازد که هر خانه اندازه یک int است (۴ بایت). صف و قفل از Heap حافظه گرفته می‌شوند. اگر حافظه تمام باشد NULL برمی‌گردد، و استفاده از NULL یعنی کرش. همیشه بررسی کن. صف و قفل باید قبل از ساختن Taskها ساخته شوند، چون Taskها بلافاصله شروع به استفاده می‌کنند.
  8. اولویت‌ها و دستگیره‌ها. Task حسگر اولویت ۲ دارد و Task نمایش ۱. این بار دستگیره (&sensorHandle) را می‌گیریم. خواندن سنسور کوتاه و حساس به زمان است، پس اولویت بالاتر. دستگیره را لازم داریم تا بعدا از بیرون درباره Task سؤال کنیم (مثلا چقدر Stack مصرف کرده).
  9. uxTaskGetStackHighWaterMark. «علامت بالاترین سطح آب» یعنی کمترین مقدار Stack آزادی که این Task تا حالا داشته، در ESP-IDF به بایت. این عدد ابزار تنظیم Stack است: اگر برای Task ۴۰۹۶ بایت گذاشتی و این عدد ۲۸۰۰ است، یعنی حداکثر حدود ۱۳۰۰ بایت مصرف شده؛ می‌توانی Stack را کم کنی و RAM آزاد کنی. اگر زیر ۵۰۰ بایت شد، Stack را بیشتر کن. ESP.getFreeHeap هم کل RAM آزاد را نشان می‌دهد.
pot=2048 led=128 pot=2051 led=128 pot=4095 led=255 [stack] sensor free=1964 B, display free=2312 B, heap=289140 B pot=4095 led=255

(عددهای Stack و Heap روی برد تو کمی فرق می‌کنند؛ مهم این است که بدانی چطور بخوانی‌شان.)

در Wokwi امتحان کن: پتانسیومتر را بچرخان و ببین روشنایی LED و عددها در Serial Monitor عوض می‌شوند. FreeRTOS در Wokwi کامل شبیه‌سازی می‌شود، پس Taskها، صف و Mutex دقیقا مثل برد واقعی رفتار می‌کنند. کتابخانه اضافه‌ای لازم نیست.

اعلان Task: سبک‌ترین زنگ

صف داده حمل می‌کند. ولی گاهی اصلا داده‌ای برای فرستادن نیست، فقط یک پیام: «بیدار شو، کار داری». برای این کار هر Task در FreeRTOS یک زنگ داخلی دارد به اسم اعلان Task (Task Notification). یک Task (یا loop) با xTaskNotifyGive(handle) زنگ را می‌زند؛ Task منتظر در ulTaskNotifyTake(...) می‌خوابد تا زنگ بخورد یا مهلتش تمام شود. لازم نیست چیزی بسازی، تقریبا هیچ حافظه‌ای نمی‌گیرد و از صف سریع‌تر است.

مثال روزمره: زنگ آشپزخانه

در رستوران ما، صف همان پیشخوانی است که بشقاب غذا رویش گذاشته می‌شود. اعلان، زنگ کوچک روی پیشخوان است: «دینگ» غذایی حمل نمی‌کند، فقط یعنی «الان بیا». آشپزی که صدایش را می‌شنود می‌داند چه کند.

مدار: LED روی GPIO4 را نگه دار و یک دکمه فشاری بین GPIO27 و GND اضافه کن، دقیقا مثل درس ۳.۱ (از مقاومت Pull-up داخلی استفاده می‌کنیم).

// Task گزارش: هر ۱۰ ثانیه، یا فورا با فشار دکمه بیدار می‌شود
const int BUTTON_PIN = 27;           // دکمه بین GPIO27 و GND
const int LED_PIN = 4;               // LED وضعیت

TaskHandle_t reportHandle = NULL;    // «شماره تلفن» Task گزارش

void reportTask(void *param) {
  pinMode(LED_PIN, OUTPUT);
  for (;;) {
    // بخواب تا زنگ بخورد، یا حداکثر ۱۰ ثانیه
    uint32_t rings = ulTaskNotifyTake(pdTRUE, pdMS_TO_TICKS(10000));
    if (rings > 0) {
      Serial.printf("Woken by the button (rings: %lu)\n", (unsigned long)rings);
    } else {
      Serial.println("10 s passed: routine report");
    }
    digitalWrite(LED_PIN, HIGH);     // یک چشمک کوتاه: «کارم را کردم»
    vTaskDelay(pdMS_TO_TICKS(100));
    digitalWrite(LED_PIN, LOW);
  }
}

void setup() {
  Serial.begin(115200);
  pinMode(BUTTON_PIN, INPUT_PULLUP);
  xTaskCreatePinnedToCore(reportTask, "report", 3072, NULL, 1, &reportHandle, 1);
}

void loop() {
  static bool wasPressed = false;
  bool pressed = (digitalRead(BUTTON_PIN) == LOW);
  if (pressed && !wasPressed) {      // فقط لحظه فشار دادن (لبه)
    xTaskNotifyGive(reportHandle);   // زنگ را بزن
  }
  wasPressed = pressed;
  delay(30);                         // حذف لرزش ساده و استراحت CPU
}
  1. Handle ی Task. برای زدن زنگ یک Task به «شماره تلفن» آن نیاز داری، پس این بار &reportHandle را به xTaskCreatePinnedToCore می‌دهیم تا آن را پر کند. اگر فراموشش کنی، Handle همان NULL می‌ماند و xTaskNotifyGive(NULL) برد را کرش می‌دهد. Task را قبل از این که کسی بخواهد به آن اعلان بدهد بساز.
  2. ulTaskNotifyTake: منتظر زنگ. Task می‌خوابد (صفر درصد CPU) تا کسی xTaskNotifyGive را صدا بزند، یا ۱۰ ثانیه بگذرد. pdTRUE یعنی «بعد از بیدار شدن، شمارش زنگ‌ها را صفر کن». یک خط، دو چیز با هم: یک زمان‌سنج منظم (هر ۱۰ ثانیه) و بیدار شدن فوری. با یک vTaskDelay(10000) ساده، فشار دکمه باید تا ۱۰ ثانیه صبر می‌کرد. اگر به جایش pdFALSE بگذاری، هر فراخوانی فقط یکی از شمارش کم می‌کند؛ برای شمردن رویدادها یکی‌یکی به درد می‌خورد.
  3. چرا بیدار شدم؟ مقدار برگشتی تعداد زنگ‌هایی است که منتظر مانده بودند. صفر یعنی مهلت تمام شده. اگر وقتی Task مشغول چشمک زدن است دو بار دکمه را بزنی، زنگ‌ها جمع می‌شوند و فراخوانی بعدی ۲ برمی‌گرداند. چیزی گم نمی‌شود و Task فقط یک بار بیدار می‌شود.
  4. زدن زنگ با فشار دکمه. loop لحظه‌ای را که دکمه از «رها» به «فشرده» می‌رود تشخیص می‌دهد (لبه، مثل درس ۳.۱) و xTaskNotifyGive را صدا می‌زند. نگه داشتن دکمه فقط یک زنگ می‌زند. دقت کن loop هیچ چیزی چاپ نمی‌کند: فقط Task گزارش از Serial استفاده می‌کند، پس Mutex لازم نیست. «هر منبع یک صاحب» اغلب از قفل ساده‌تر است.
  5. delay(30). حدود ۳۰ بار در ثانیه بررسی دکمه کاملا کافی است و لرزش کنتاکت را هم حذف می‌کند. این delay پردازنده را هم به Taskهای دیگر می‌دهد. loop بدون هیچ delay یک‌سره می‌چرخد و انرژی هدر می‌دهد.

دقت کن بعد از بیدار شدن با دکمه، شمارش ۱۰ ثانیه از صفر شروع می‌شود، چون هر فراخوانی ulTaskNotifyTake یک انتظار تازه است. پروژه ایستگاه هوا در درس ۵.۶ دقیقا از همین الگو استفاده می‌کند: «هر ۱۰ دقیقه، یا همین الان اگر تنظیمات عوض شد».

در Wokwi امتحان کن: ۱۰ ثانیه صبر کن تا گزارش معمولی بیاید، بعد روی دکمه سبز کلیک کن و ببین گزارش فورا می‌رسد و LED یک چشمک کوتاه می‌زند.

از وقفه به Task: xQueueSendFromISR

در درس ۳.۱ با وقفه آشنا شدی: با attachInterrupt یک تابع کوچک (ISR) درست در لحظه تغییر پین اجرا می‌شود، مثل زنگ در. ISR باید خیلی کوتاه باشد: نه Serial، نه delay، نه هیچ نوع انتظاری. توابع معمولی FreeRTOS مثل xQueueSend و xTaskNotifyGive داخل ISR مجاز نیستند، چون ممکن است صبر کنند یا Task را طوری عوض کنند که وقفه از پسش برنمی‌آید. هر کدام یک همزاد مخصوص ISR دارد که آخر اسمش FromISR است. الگوی حرفه‌ای: ISR فقط رویداد را یادداشت می‌کند و به یک Task می‌سپارد؛ کار کند را Task انجام می‌دهد.

مثال روزمره

زنگ در فقط زنگ می‌زند؛ در را باز نمی‌کند و برای مهمان چای نمی‌ریزد. کسی داخل خانه (Task) صدای زنگ را می‌شنود و کار اصلی را انجام می‌دهد. اگر خود زنگ می‌خواست چای بریزد، تا آماده شدن چای کل خانه می‌ایستاد.

// وقفه دکمه ← صف ← Task: ISR فقط زمان را ثبت می‌کند
const int BUTTON_PIN = 27;                 // دکمه بین GPIO27 و GND

QueueHandle_t pressQueue;                  // زمان فشارها، از ISR به Task

void IRAM_ATTR onPress() {                 // ISR: کوچک و سریع
  uint32_t now = millis();
  BaseType_t wokeHigher = pdFALSE;
  xQueueSendFromISR(pressQueue, &now, &wokeHigher);
  portYIELD_FROM_ISR(wokeHigher);          // فورا به Task بیدارشده برو
}

void pressTask(void *param) {
  uint32_t t;
  int count = 0;
  for (;;) {
    xQueueReceive(pressQueue, &t, portMAX_DELAY);  // بخواب تا لبه‌ای برسد
    vTaskDelay(pdMS_TO_TICKS(30));         // بگذار لرزش کنتاکت تمام شود
    xQueueReset(pressQueue);               // لبه‌های لرزش را دور بریز
    if (digitalRead(BUTTON_PIN) != LOW) continue;  // نگه داشته نشده: رها کردن بود
    count++;
    Serial.printf("Press #%d at %lu ms\n", count, (unsigned long)t);
  }
}

void setup() {
  Serial.begin(115200);
  pinMode(BUTTON_PIN, INPUT_PULLUP);
  pressQueue = xQueueCreate(20, sizeof(uint32_t));
  if (pressQueue == NULL) {
    Serial.println("Out of memory!");
    while (true) delay(1000);
  }
  xTaskCreatePinnedToCore(pressTask, "press", 3072, NULL, 2, NULL, 1);
  attachInterrupt(digitalPinToInterrupt(BUTTON_PIN), onPress, FALLING);
}

void loop() {
  delay(1000);                             // loop این‌جا کاری ندارد
}
  1. ISR با IRAM_ATTR. همان نوع تابعی که در درس ۳.۱ دیدی: با هر لبه پایین‌رونده (HIGH به LOW) در GPIO27 اجرا می‌شود. IRAM_ATTR ISR را در RAM داخلی سریع نگه می‌دارد تا حتی وقتی حافظه فلش مشغول است بتواند اجرا شود. بدون آن، وقفه‌ای در لحظه بد می‌تواند برد را کرش دهد.
  2. xQueueSendFromISR. یک کپی از زمان فشار را در صف می‌گذارد، بدون هیچ انتظاری. اگر صف پر باشد، این فشار دور ریخته می‌شود. ورودی سوم، &wokeHigher، یک گزارش کوچک برگشتی است: «آیا این کار Taskی مهم‌تر از Task قطع‌شده را بیدار کرد؟» این همزاد امن xQueueSend برای وقفه است. قانون ساده است: داخل ISR فقط توابعی از FreeRTOS را صدا بزن که اسمشان با FromISR تمام می‌شود. بقیه را هم بعدا می‌بینی: vTaskNotifyGiveFromISR و xSemaphoreGiveFromISR.
  3. portYIELD_FROM_ISR. اگر wokeHigher درست (true) شده باشد، زمان‌بند درست بعد از تمام شدن ISR به آن Task می‌رود، نه در تیک بعدی. این‌جا pressTask اولویت ۲ دارد، بالاتر از اولویت ۱ ی loop، پس فشار دکمه در چند میکروثانیه رسیدگی می‌شود. بدون این خط هم کار می‌کند، فقط تا ۱ میلی‌ثانیه دیرتر.
  4. Task تا ابد منتظر فشار می‌ماند. portMAX_DELAY یعنی «بدون مهلت». بین فشارها Task صفر درصد CPU مصرف می‌کند. این همان صفی است که برای پتانسیومتر استفاده کردی؛ فقط فرستنده عوض شده. زیبایی صف همین است: گیرنده برایش مهم نیست داده را چه کسی فرستاده.
  5. حذف لرزش در Task، نه در ISR. دکمه مکانیکی «می‌لرزد» و با هر فشار چند لبه می‌سازد. Task ۳۰ میلی‌ثانیه صبر می‌کند، لبه‌های اضافه را با xQueueReset دور می‌ریزد و بعد بررسی می‌کند دکمه واقعا هنوز فشرده است. صبر کردن در ISR ممنوع است ولی در Task کاملا مجاز. بررسی آخر لرزشِ رها کردن دکمه را هم حذف می‌کند، که آن هم می‌تواند یک لبه پایین‌رونده بسازد.
  6. کار کند: چاپ. Serial در Task اجرا می‌شود، هرگز در ISR. Serial.printf ممکن است چند میلی‌ثانیه طول بکشد و داخلش قفل دارد؛ در ISR می‌تواند برد را قفل یا کرش کند. ISR در چند میکروثانیه تمام می‌شود و Task بقیه کار را با آرامش انجام می‌دهد.
  7. ترتیب درست در setup. اول صف، بعد Task، و فقط آخر سر attachInterrupt. اگر وقفه اول روشن می‌شد، یک فشار (یا یک لرزش موقع روشن شدن) می‌توانست ISR را وقتی pressQueue هنوز NULL است صدا بزند و برد کرش می‌کرد.

این را هم بدان: تایمرهای نرم‌افزاری

برای «این کار کوچک را هر ۵۰۰ میلی‌ثانیه انجام بده»، FreeRTOS تایمر نرم‌افزاری (Software Timer) هم دارد: یک تابع و یک دوره به آن می‌دهی و یک Task داخلی تایمر، تابع تو را سر وقت صدا می‌زند. تابع باید کوتاه باشد و هرگز صبر نکند (نه delay، نه درخواست طولانی HTTPS)، چون همه تایمرها همان یک Task را شریکی استفاده می‌کنند. برای هر کار کند، تایمر می‌تواند فقط به یک Task اعلان بدهد.

void onTick(TimerHandle_t t) {           // در Task تایمر اجرا می‌شود: کوتاه نگهش دار
  static bool on = false;
  on = !on;
  digitalWrite(4, on);                   // LED وضعیت خودبه‌خود چشمک می‌زند
}

// داخل setup()، بعد از pinMode(4, OUTPUT):
TimerHandle_t tick = xTimerCreate("tick", pdMS_TO_TICKS(500), pdTRUE, NULL, onTick);
xTimerStart(tick, 0);                    // pdTRUE بالا = تکرار برای همیشه

وقتی Stack کم می‌آید (Stack Overflow)

هر Task یک جعبه حافظه به اندازه‌ای که گفتی دارد. متغیرهای محلی، آرایه‌ها و هر تابعی که صدا می‌زنی در این جعبه جا می‌گیرند. Serial.printf خودش چند صد بایت می‌خواهد و یک اتصال HTTPS چند کیلوبایت. اگر جعبه لبریز شود، داده روی حافظه همسایه ریخته می‌شود. خوشبختانه ESP32 مراقب است و قبل از خرابی کامل، این را چاپ و برد را ریست می‌کند:

***ERROR*** A stack overflow in task display has been detected. Backtrace: 0x40081f2e:0x3ffb5f40 0x40086d15:0x3ffb5f60 ... Rebooting...

علامت‌های رایج Stack کم: همین پیام، یا Guru Meditation Error: Core 1 panic'ed (LoadProhibited)، یا ریست‌های تصادفی وقتی Task کار سنگین‌تری می‌کند (مثلا اولین اتصال HTTPS). درمان: عدد Stack را در xTaskCreatePinnedToCore دو برابر کن، بعد با uxTaskGetStackHighWaterMark ببین واقعا چقدر لازم است. آرایه بزرگ (مثلا char buf[4000]) را هم داخل Task محلی تعریف نکن؛ سراسری یا static کن تا از Stack بیرون برود.

نگهبان Task (Task Watchdog): چرا برد خودش ریست می‌شود؟

ESP32 یک «نگهبان» دارد که هر چند وقت یک بار سر می‌زند ببیند Taskهای مهم زنده‌اند. در core آردوینو این نگهبان Task بیکار هسته ۰ (IDLE0) را زیر نظر دارد، با مهلت ۵ ثانیه (CONFIG_ESP_TASK_WDT_TIMEOUT_S=5). Task بیکار فقط وقتی اجرا می‌شود که هیچ Task دیگری روی آن هسته کار نداشته باشد. پس اگر یک Task روی هسته ۰ پنج ثانیه بدون وقفه کار کند، IDLE0 هیچ‌وقت نوبت نمی‌گیرد و نگهبان نتیجه می‌گیرد «سیستم قفل شده» و برد را ریست می‌کند.

مثال از زندگی روزمره

نگهبان شب یک ساختمان هر ساعت باید دکمه‌ای را در لابی بزند تا سیستم بفهمد بیدار است. اگر کسی جلوی لابی را با یک کار بی‌پایان بسته باشد و نگهبان نتواند به دکمه برسد، زنگ خطر به صدا درمی‌آید. vTaskDelay همان «راه دادن» به نگهبان است.

// ❌ نمونه عمدا غلط: Task حریص بدون استراحت روی هسته ۰
volatile unsigned long counter = 0;

void greedyTask(void *param) {
  for (;;) {
    counter++;              // بی‌وقفه کار می‌کند و هرگز کنار نمی‌رود
    // vTaskDelay(1);       // ✅ درمان: این خط را از حالت توضیح دربیاور
  }
}

void setup() {
  Serial.begin(115200);
  xTaskCreatePinnedToCore(greedyTask, "greedy", 2048, NULL, 1, NULL, 0);
}

void loop() {
  Serial.println(counter);
  delay(1000);
}
  1. Task حریص. یک حلقه بی‌پایان که فقط عدد را زیاد می‌کند و هیچ‌وقت vTaskDelay صدا نمی‌زند. این Task آماده اجراست و اولویتش (۱) از IDLE0 (۰) بیشتر است؛ پس زمان‌بند همیشه او را انتخاب می‌کند و IDLE0 گرسنه می‌ماند.
  2. روی هسته ۰. آخرین ورودی 0 است. اگر همین Task را روی هسته ۱ بگذاری، در تنظیمات پیش‌فرض ریست نمی‌شود (IDLE1 زیر نظر نیست) ولی loop و Taskهای هم‌اولویت هسته ۱ کند می‌شوند. «ریست نمی‌شود» یعنی «مشکل پنهان است»، نه «درست است».
  3. درمان. یک vTaskDelay(1) (حتی ۱ میلی‌ثانیه) در حلقه کافی است تا IDLE0 نوبت بگیرد. قانون: هر حلقه بی‌پایان در هر Task باید جایی بخوابد یا منتظر چیزی بماند (vTaskDelay، xQueueReceive، xSemaphoreTake با زمان صبر). حلقه‌های انتظار مثل while (!ready) {} دشمن شماره یک هستند.

حدود ۵ ثانیه بعد از روشن شدن چیزی شبیه این می‌بینی و برد ریست می‌شود:

E (5316) task_wdt: Task watchdog got triggered. The following tasks/users did not reset the watchdog in time: E (5316) task_wdt: - IDLE0 (CPU 0) E (5316) task_wdt: Tasks currently running: E (5316) task_wdt: CPU 0: greedy E (5316) task_wdt: CPU 1: IDLE1 E (5316) task_wdt: Aborting. abort() was called at PC 0x400d8c5f on core 0 ... Rebooting...

خط CPU 0: greedy مجرم را لو می‌دهد: اسمی که به Task دادی. برای همین اسم Taskها را معنادار انتخاب کن.

راه غلط: خاموش کردن نگهبان

در انجمن‌ها کدهایی مثل disableCore0WDT() می‌بینی. این کار پیام را قطع می‌کند ولی مشکل سر جایش است: Taskهای سیستم (مثل Wi-Fi) روی هسته ۰ گرسنه می‌مانند و اتصال شبکه عجیب قطع می‌شود. نگهبان دشمن تو نیست؛ دوستی است که می‌گوید کدت یک جا گیر کرده.

Task یا millis()؟ کدام را انتخاب کنم؟

برای دو سه کار سبک و سریع، millis() در loop ساده‌تر است و باگ‌های هم‌زمانی ندارد. Task را وقتی بیاور که: ۱) یک کار کند و مسدودکننده داری (HTTPS، خواندن کند سنسور، نوشتن روی SD) که نباید بقیه را منتظر بگذارد؛ ۲) کارها زمان‌بندی کاملا متفاوت دارند؛ ۳) می‌خواهی از هسته دوم استفاده کنی. هر Task جدید یعنی Stack جدا، و هر داده مشترک یعنی صف یا Mutex. بی‌دلیل Task نساز.

حرف مربی

FreeRTOS ابزار قدرتمندی است و قدرت خطرناک است. سه قانون من: یک، هر Task، هر صف و هر قفل جدید باید دلیل داشته باشد؛ اگر نمی‌توانی در یک جمله بگویی چرا این کار Task جدا می‌خواهد، نمی‌خواهد. دو، هر حلقه بی‌پایان در هر Task باید جایی صبر کند؛ همین که for (;;) را تایپ کردی، فکر بعدی‌ات باید این باشد: «کجا می‌خوابد؟». سه، وقفه‌ها را کوچک نگه دار: ISR ی که چاپ می‌کند یا صبر می‌کند دیر یا زود کرش می‌کند، معمولا در بدترین لحظه. قبل از رفتن به درس بعد، بدون نگاه کردن فرق صف، Mutex و اعلان را برای یک دوست توضیح بده. اگر توانستی، برای درس ۵.۵ آماده‌ای.

آزمون این درس

در ESP32، خط xTaskCreatePinnedToCore(f, "t", 2048, NULL, 1, NULL, 1); چقدر Stack به Task می‌دهد؟

  1. ۲۰۴۸ word یعنی ۸ کیلوبایت
  2. ۲۰۴۸ بایت یعنی ۲ کیلوبایت
  3. همیشه ۸ کیلوبایت، مثل loopTask
  4. بستگی به اولویت دارد
در FreeRTOS ی ESP-IDF اندازه Stack به بایت است. کدهای کپی‌شده از پلتفرم‌های دیگر با عدد کوچک مثل 512 روی ESP32 کرش می‌کنند.

Task ای روی هسته ۰ داری که در یک حلقه for(;;) بدون هیچ vTaskDelay عددی را زیاد می‌کند. حدود ۵ ثانیه بعد چه می‌شود؟

  1. هیچ اتفاقی نمی‌افتد
  2. Stack overflow رخ می‌دهد
  3. Task Watchdog فعال می‌شود چون IDLE0 نوبت اجرا نگرفته، و برد ریست می‌شود
  4. Brownout detector برد را ریست می‌کند
نگهبان Task در core آردوینو IDLE0 را با مهلت ۵ ثانیه زیر نظر دارد. درمان: یک vTaskDelay کوتاه در حلقه.

Task حسگر هر ۲۰۰ میلی‌ثانیه عددی می‌خواند و Task نمایش باید آن را نشان دهد. امن‌ترین و تمیزترین راه انتقال چیست؟

  1. یک صف (Queue) با xQueueSend و xQueueReceive
  2. یک متغیر سراسری معمولی
  3. فقط یک Mutex بدون متغیر
  4. نوشتن در Serial و خواندن از آن
صف داده را کپی می‌کند، نصفه جابه‌جا نمی‌کند، و Task گیرنده را تا رسیدن داده می‌خواباند.

داخل یک تابع وقفه (ISR) می‌خواهی زمان فشار دکمه را از طریق یک صف به یک Task بفرستی. کدام خط درست است؟

  1. xQueueSend(q, &t, portMAX_DELAY);
  2. xQueueSendFromISR(q, &t, &wokeHigher);
  3. Serial.println(t); و Task از Serial بخواند
  4. delay(50); و بعد xQueueSend(q, &t, 0);
داخل ISR فقط توابع FromISR مجازند؛ آن‌ها هرگز صبر نمی‌کنند. wokeHigher می‌گوید آیا باید با portYIELD_FROM_ISR فورا به Task بیدارشده رفت.

یک Task بین دو کار ۱۰ دقیقه می‌خوابد. وقتی کاربر دکمه را می‌زند، می‌خواهی فورا کارش را انجام دهد. لازم نیست داده‌ای فرستاده شود. سبک‌ترین ابزار چیست؟

  1. یک Mutex
  2. Task را پاک کن و دوباره بساز
  3. اعلان Task: xTaskNotifyGive در یک طرف و ulTaskNotifyTake با مهلت ۱۰ دقیقه در طرف دیگر
  4. ۱۰ دقیقه را به vTaskDelay(1) تغییر بده
اعلان زنگ داخلی FreeRTOS است: چیزی برای ساختن ندارد، تقریبا حافظه نمی‌گیرد، و Task منتظر یا با زنگ بیدار می‌شود یا با تمام شدن مهلتش.

const int LED_PIN = 4;           // LED با نور متغیر (PWM)
const int LED2_PIN = 26;         // ★ LED دوم: سرعت چشمک از پتانسیومتر

QueueHandle_t potQueue;          // سنسور -> نمایش
QueueHandle_t blinkQueue;        // ★ نمایش -> چشمک‌زن
SemaphoreHandle_t serialMutex;   // قفل Serial Monitor
TaskHandle_t sensorHandle = NULL;
TaskHandle_t displayHandle = NULL;
TaskHandle_t blinkHandle = NULL;

void sensorTask(void *param) {
  for (;;) {
    int raw = analogRead(POT_PIN);                  // ۰ تا ۴۰۹۵
    xQueueSend(potQueue, &raw, 0);                  // صف پر است؟ این نمونه را دور بریز
    vTaskDelay(pdMS_TO_TICKS(200));                 // ۵ بار در ثانیه
  }
}

void displayTask(void *param) {
  int value;
  for (;;) {
    if (xQueueReceive(potQueue, &value, pdMS_TO_TICKS(1000)) == pdPASS) {
      ledcWrite(LED_PIN, value / 16);               // 0..4095 -> 0..255
      xQueueSend(blinkQueue, &value, 0);            // ★ به بعدی بده، هرگز صبر نکن
      if (xSemaphoreTake(serialMutex, pdMS_TO_TICKS(100)) == pdTRUE) {
        Serial.printf("pot=%4d  led=%3d\n", value, value / 16);
        xSemaphoreGive(serialMutex);
      }
    }
  }
}

void blinkTask(void *param) {                       // ★ آشپز سوم
  pinMode(LED2_PIN, OUTPUT);
  int period = 1000;                                // تا وقتی اولین عدد برسد
  int v;
  bool on = false;
  for (;;) {
    while (xQueueReceive(blinkQueue, &v, 0) == pdPASS) {  // صف را خالی کن، بدون انتظار
      period = map(v, 0, 4095, 1000, 100);               // تازه‌ترین عدد برنده است
    }
    on = !on;
    digitalWrite(LED2_PIN, on);
    vTaskDelay(pdMS_TO_TICKS(period));
  }
}

void setup() {
  Serial.begin(115200);
  ledcAttach(LED_PIN, 5000, 8);                     // ۵ کیلوهرتز، ۸ بیت
  potQueue = xQueueCreate(10, sizeof(int));
  blinkQueue = xQueueCreate(10, sizeof(int));
  serialMutex = xSemaphoreCreateMutex();
  if (potQueue == NULL || blinkQueue == NULL || serialMutex == NULL) {
    Serial.println("Out of memory!");
    while (true) delay(1000);
  }
  // استک‌ها بعد از اندازه‌گیری کوچک شدند (قبلا 3072 و 4096)
  xTaskCreatePinnedToCore(sensorTask, "sensor", 2048, NULL, 2, &sensorHandle, 1);
  xTaskCreatePinnedToCore(displayTask, "display", 3072, NULL, 1, &displayHandle, 1);
  xTaskCreatePinnedToCore(blinkTask, "blink", 2048, NULL, 1, &blinkHandle, 1);
}

void loop() {
  delay(5000);
  if (xSemaphoreTake(serialMutex, portMAX_DELAY) == pdTRUE) {
    Serial.printf("[stack free] sensor=%u B, display=%u B, blink=%u B, heap=%u B\n",
                  (unsigned)uxTaskGetStackHighWaterMark(sensorHandle),
                  (unsigned)uxTaskGetStackHighWaterMark(displayHandle),
                  (unsigned)uxTaskGetStackHighWaterMark(blinkHandle),
                  (unsigned)ESP.getFreeHeap());
    xSemaphoreGive(serialMutex);
  }
}
  1. یک پایه، یک صف و یک handle بیشتر. GPIO26 برای LED دوم، blinkQueue بین تسک نمایش و تسک چشمک، و blinkHandle برای گزارش استک. هر جفت آشپز صف خودش را دارد. یک صف دقیقا یک کار دارد (بردن عدد از A به B) و این برنامه را راحت‌فهم نگه می‌دارد.
  2. تسک سنسور، بدون تغییر. پتانسیومتر را ۵ بار در ثانیه می‌خواند و اگر صف پر باشد نمونه را دور می‌ریزد. کارش عوض نشده؛ فقط استکش حالا کوچک‌تر است (setup را ببین).
  3. تسک نمایش عدد را به بعدی می‌دهد. بلافاصله بعد از تنظیم LED قرمز، همان عدد را با زمان انتظار ۰ در blinkQueue می‌گذارد. تسک نمایش هرگز نباید به خاطر کند بودن چشمک‌زن گیر کند. با ۰، اگر صف روزی پر باشد، عدد فقط دور ریخته می‌شود؛ عدد تازه‌تر ۲۰۰ میلی‌ثانیه بعد می‌رسد.
  4. خالی کردن صف بدون انتظار. while هر عددی را که رسیده برمی‌دارد؛ فقط آخری (تازه‌ترین) period را تعیین می‌کند. اگر چیزی نرسیده، دوره قبلی می‌ماند. در هر ثانیه حدود ۵ عدد می‌رسد، ولی با سرعت کند تسک فقط ثانیه‌ای یک بار سر می‌زند. اگر هر دور فقط یک عدد برمی‌داشت، مدام عددهای کهنه را پردازش می‌کرد و چند ثانیه از پیچ عقب می‌ماند. map بازه ۰..۴۰۹۵ را به ۱۰۰۰..۱۰۰ تبدیل می‌کند: map(2048, 0, 4095, 1000, 100) = 550.
  5. چشمک، بعد خواب. LED را برعکس کن و period میلی‌ثانیه با vTaskDelay صبر کن. vTaskDelay در مدت انتظار CPU را برای بقیه تسک‌ها آزاد می‌کند. برای همین هم سرعت تازه فقط بعد از تمام شدن انتظار فعلی شروع می‌شود.
  6. ساختن صف دوم و بررسی آن. هر سه شیء قبل از شروع هر تسکی از نظر NULL بررسی می‌شوند. تسکی که از صف ساخته‌نشده استفاده کند برد را کرش می‌دهد. اول ساختن همه چیز و بعد تسک‌ها، جلوی این را می‌گیرد.
  7. استک‌های کوچک‌تر. در درس برای تسک سنسور حدود ۱۹۶۴ بایت آزاد از ۳۰۷۲ اندازه‌گیری شد (یعنی حدود ۱۱۰۰ مصرف) و برای تسک نمایش ۲۳۱۲ آزاد از ۴۰۹۶ (حدود ۱۸۰۰ مصرف). پس ۲۰۴۸ حدود ۹۴۰ و ۳۰۷۲ حدود ۱۲۹۰ بایت آزاد باقی می‌گذارند، هر دو بالای حاشیه ۵۰۰ بایتی. تسک چشمک کار کمتری دارد و ۲۰۴۸ می‌گیرد. اندازه استک = مصرف واقعی تسک + حاشیه اطمینان. دقیقا تا ۵۰۰ کم نکن: یک مسیر نادر (پیام خطا، یک printf بلندتر) می‌تواند بیشتر از هر چیزی که اندازه گرفته‌ای مصرف کند.
  8. گزارش برای سه تسک. برای هر handle یک uxTaskGetStackHighWaterMark، داخل mutex. high-water mark کمترین استک آزادی است که تا حالا دیده شده، پس قبل از اعتماد به عددها بگذار برنامه مدتی کار کند و پیچ را بچرخان.

در Wokwi امتحانش کن: پتانسیومتر را از یک سر تا سر دیگر بچرخان و ببین سرعت LED سبز و نور LED قرمز با هم عوض می‌شوند. کتابخانه اضافه‌ای لازم نیست.

تمرین ۲: شمارنده فشار با ضربان قلب

دو مثال آخر را ترکیب کن. ISR فشارها را مثل ButtonISR از طریق صف به pressTask می‌فرستد. بعد از هر ۵ فشار، pressTask به یک Task دوم اعلان می‌دهد که LED روی GPIO26 را ۵ بار سریع چشمک بزند. Task چشمک‌زن باید خودش هم هر ۱۰ ثانیه یک بار LED را چشمک بزند، به عنوان «ضربان قلب»، حتی اگر کسی دکمه نزند.

راهنمایی

در Task چشمک‌زن از ulTaskNotifyTake(pdTRUE, pdMS_TO_TICKS(10000)) استفاده کن: مقدار برگشتی ۰ یعنی ۱۰ ثانیه تمام شده (ضربان: یک چشمک)، و بیشتر از ۰ یعنی زنگ خورده (پنج چشمک). Handle ی Task چشمک‌زن را در یک متغیر سراسری نگه دار و هر دو Task را قبل از attachInterrupt بساز.

جواب کامل با توضیح

برنامه کامل: ButtonISR به اضافه یک تسک چشمک‌زن که منتظر notification می‌ماند، مثل تسک گزارش در NotifyDemo.

// وقفه دکمه -> صف -> pressTask -> هر ۵ فشار -> blinkTask
const int BUTTON_PIN = 27;                 // دکمه بین GPIO27 و GND
const int LED2_PIN = 26;                   // LED دوم (+۲۲۰ اهم)

QueueHandle_t pressQueue;                  // زمان فشارها، از ISR به pressTask
TaskHandle_t blinkHandle = NULL;           // «شماره تلفن» blinkTask

void IRAM_ATTR onPress() {                 // ISR: کوچک و سریع
  uint32_t now = millis();
  BaseType_t wokeHigher = pdFALSE;
  xQueueSendFromISR(pressQueue, &now, &wokeHigher);
  portYIELD_FROM_ISR(wokeHigher);
}

void blink(int times, int ms) {            // روشن و خاموش، به تعداد times
  for (int i = 0; i < times; i++) {
    digitalWrite(LED2_PIN, HIGH);
    vTaskDelay(pdMS_TO_TICKS(ms));
    digitalWrite(LED2_PIN, LOW);
    vTaskDelay(pdMS_TO_TICKS(ms));
  }
}

void blinkTask(void *param) {
  pinMode(LED2_PIN, OUTPUT);
  for (;;) {
    // بخواب تا زنگ بخورد، یا حداکثر ۱۰ ثانیه
    uint32_t rings = ulTaskNotifyTake(pdTRUE, pdMS_TO_TICKS(10000));
    if (rings > 0) {
      blink(5, 100);                       // ۵ فشار: پنج چشمک سریع
    } else {
      blink(1, 100);                       // ۱۰ ثانیه سکوت: یک ضربان
    }
  }
}

void pressTask(void *param) {
  uint32_t t;
  int count = 0;
  for (;;) {
    xQueueReceive(pressQueue, &t, portMAX_DELAY);  // بخواب تا یک لبه برسد
    vTaskDelay(pdMS_TO_TICKS(30));         // صبر کن لرزش کنتاکت تمام شود
    xQueueReset(pressQueue);               // لبه‌های لرزش را دور بریز
    if (digitalRead(BUTTON_PIN) != LOW) continue;  // نگه داشته نشده: رها کردن بود
    count++;
    Serial.printf("Press #%d at %lu ms\n", count, (unsigned long)t);
    if (count % 5 == 0) {                  // هر پنجمین فشار
      Serial.println("  5 presses: ringing blinkTask");
      xTaskNotifyGive(blinkHandle);        // زنگ را بزن
    }
  }
}

void setup() {
  Serial.begin(115200);
  pinMode(BUTTON_PIN, INPUT_PULLUP);
  pressQueue = xQueueCreate(20, sizeof(uint32_t));
  if (pressQueue == NULL) {
    Serial.println("Out of memory!");
    while (true) delay(1000);
  }
  xTaskCreatePinnedToCore(blinkTask, "blink", 2048, NULL, 1, &blinkHandle, 1);
  xTaskCreatePinnedToCore(pressTask, "press", 3072, NULL, 2, NULL, 1);
  attachInterrupt(digitalPinToInterrupt(BUTTON_PIN), onPress, FALLING);  // در آخر!
}

void loop() {
  delay(1000);                             // loop اینجا کاری ندارد
}
  1. یک صف و یک handle. صف زمان فشارها را از ISR به pressTask می‌برد؛ handle سراسری به pressTask اجازه می‌دهد زنگ blinkTask را بزند. داده (یک زمان) از صف می‌رود؛ یک «بیدار شو» ساده از notification، که به چیزی جز handle نیاز ندارد.
  2. ISR، بدون تغییر. فقط زمان را ثبت می‌کند و با تابع FromISR به صف می‌دهد. ISR باید خیلی کوچک باشد؛ شمردن و چشمک زدن کار تسک‌هاست.
  3. یک تابع کمکی کوچک برای چشمک. روشن و خاموش، به تعدادی که خواسته شده، با vTaskDelay برای انتظارها. یک تابع هم به کار ضربان می‌آید هم به جشن. vTaskDelay (نه انتظار مشغول) باعث می‌شود تسک فشار در حین چشمک زدن همچنان بشمارد.
  4. یک انتظار، دو معنی. ulTaskNotifyTake می‌خوابد تا زنگ بخورد یا ۱۰ ثانیه بگذرد. ۰ یعنی «وقت تمام شد»: یک ضربان؛ بیشتر از ۰ یعنی «زنگ خورد»: پنج چشمک سریع. مقدار برگشتی دو حالت را از هم جدا می‌کند، پس یک تسک بدون تایمر و متغیر اضافه هر دو کار را انجام می‌دهد. pdTRUE شمارش را صفر می‌کند، پس چند زنگ در حین چشمک فقط یک دور دیگر می‌سازند، نه یک صف طولانی.
  5. شمردن، مثل ButtonISR. منتظر لبه بمان، بگذار لرزش بخوابد، صف را خالی کن، بررسی کن دکمه هنوز پایین است، بشمار. همین باعث می‌شود هر فشار دقیقا یک بار شمرده شود، پس «هر پنجمین فشار» واقعا یعنی پنج فشار.
  6. هر پنجمین فشار زنگ را می‌زند. count % 5 == 0 در ۵، ۱۰، ۱۵ و... درست است. % باقی‌مانده تقسیم را می‌دهد؛ دقیقا در مضرب‌های ۵ صفر است، پس شمارنده دومی لازم نیست که صفرش کنیم.
  7. اول تسک‌ها، آخر از همه وقفه. blinkTask اول ساخته می‌شود تا blinkHandle قبل از اینکه کسی زنگش را بزند مقدار داشته باشد؛ attachInterrupt در آخر می‌آید. فشاری که در حین setup اتفاق بیفتد نباید به صف یا handle‌ای برسد که هنوز وجود ندارد. pressTask اولویت بالاتری (۲) دارد تا فشار حتی وسط یک چشمک فورا رسیدگی شود.

در Wokwi امتحانش کن: منتظر یک ضربان بمان، بعد پنج بار روی دکمه سبز کلیک کن. کتابخانه اضافه‌ای لازم نیست.

پروژه تمرینی: چراغ گذرگاه عابر پیاده با Taskها

داری چراغ راهنمایی یک گذرگاه عابر پیاده را برنامه‌ریزی می‌کنی. ماشین‌ها سبز دارند تا وقتی کسی دکمه «عبور» را فشار دهد؛ بعد چراغ به راننده‌ها هشدار می‌دهد، قرمز می‌شود و ۶ ثانیه به عابرها وقت می‌دهد. گذرگاه‌های واقعی قانونی دارند که تو هم رعایتش می‌کنی: ماشین‌ها همیشه یک حداقل زمان سبز دارند، تا فشار دادن پشت‌سرهم دکمه نتواند خیابان را قفل کند. هر کار در Task خودش در FreeRTOS زندگی می‌کند، دکمه از طریق یک وقفه و یک صف به Task خودش می‌رسد، و همه Taskها در یک دفتر گزارش مشترک می‌نویسند بدون اینکه هیچ خطی قاطی شود.

نیازمندی‌ها

  1. همه خروجی Serial از یک تابع logf() می‌گذرد که با یک Mutex محافظت شده و هر خط را با زمان به میلی‌ثانیه شروع می‌کند؛ مثلا [ 2041] Button #1: request sent. هیچ دو خطی هرگز قاطی نمی‌شوند.
  2. یک Task چراغ صاحب هر دو LED است. به طور پیش‌فرض ماشین‌ها سبز دارند: LED سبز (GPIO26) روشن، LED قرمز (GPIO4) خاموش، با ثبت Cars: GREEN.
  3. دکمه روی GPIO27 از وقفه‌ای استفاده می‌کند که فقط زمان فشار را در یک صف می‌گذارد. یک Task دکمه لرزش را حذف می‌کند (مثل مثال ButtonISR درس) و فشارهای واقعی را می‌شمارد.
  4. بعد از یک درخواست، ماشین‌ها روی هم دست‌کم ۵ ثانیه سبز دارند (از لحظه شروع سبز)؛ اگر درخواست زودتر برسد، چراغ بقیه‌اش را صبر می‌کند و ثبت می‌کند چقدر.
  5. تغییر: LED سبز به عنوان هشدار ۳ بار چشمک می‌زند (۲۵۰ میلی‌ثانیه خاموش، ۲۵۰ روشن)، بعد قرمز ۶ ثانیه روشن است («عبور»)، بعد دوباره سبز.
  6. فشارهایی که وقتی یک عبور از قبل درخواست شده یا در حال اجراست بیایند، «نادیده گرفته شد» ثبت می‌شوند و هرگز باعث عبور دوم نمی‌شوند.
  7. هیچ Taskی درجا منتظر نمی‌ماند (busy-wait): هر انتظاری یک صف، یک Notification یا vTaskDelay است. loop() هر ۱۰ ثانیه فضای آزاد Stack هر دو Task را ثبت می‌کند، و برد ۵ دقیقه فشار دادن دکمه را بدون ریست Watchdog تحمل می‌کند.

قطعه‌ها

  • ESP32 DevKitC، برد بورد، سیم جامپر
  • LED قرمز + ۲۲۰ اهم روی GPIO4، LED سبز + ۲۲۰ اهم روی GPIO26 (دو LED همین درس)
  • دکمه فشاری روی GPIO27. پتانسیومتر روی GPIO34 می‌تواند بماند؛ استفاده نمی‌شود.

راهنمایی ۱

Task چراغ داخل for (;;) یک داستان سرراست از بالا به پایین است: سبز، صبر برای درخواست، شاید صبر برای حداقل سبز، چشمک، قرمز، صبر، برگشت به بالا. چون Task است، می‌توانی آن را با vTaskDelay به ترتیب ساده بنویسی، بدون هیچ حساب‌وکتاب millis().

راهنمایی ۲

وقتی سبز شروع می‌شود، millis() را در یک متغیر محلی ذخیره کن. بعد از برگشتن ulTaskNotifyTake، millis() - greenSince می‌گوید سبز چقدر طول کشیده. اگر کمتر از ۵۰۰۰ بود، vTaskDelay(pdMS_TO_TICKS(5000 - greenFor)).

راهنمایی ۳

درست بعد از اینکه Task چراغ درخواستی را پذیرفت busy = true کن، و آخر زمان عبور دوباره false. درست قبل از آن، ulTaskNotifyTake(pdTRUE, 0) (با صفر تیک صبر) هر Notificationی را که در این فاصله رسیده دور می‌ریزد، تا یک فشار اضافه نتواند عبور دومی شروع کند.

const int RED_LED = 4;            // ماشین‌ها بایستند، عابرها بروند
const int GREEN_LED = 26;         // ماشین‌ها بروند
const int BUTTON_PIN = 27;        // دکمه «عبور» بین GPIO27 و GND
const unsigned long MIN_GREEN_MS = 5000;   // ماشین‌ها همیشه دست‌کم ۵ ثانیه سبز دارند
const unsigned long WALK_MS = 6000;        // زمان عبور عابرها

QueueHandle_t pressQueue;         // ISR به buttonTask (زمان فشارها)
SemaphoreHandle_t logMutex;       // هر لحظه فقط یک نویسنده روی Serial
TaskHandle_t lightHandle = NULL;
TaskHandle_t buttonHandle = NULL;
volatile bool busy = false;       // یک عبور در انتظار یا در حال اجراست

void logf(const char *fmt, ...) { // به سبک printf، امن از هر Task
  char buf[96];
  va_list args;
  va_start(args, fmt);
  vsnprintf(buf, sizeof(buf), fmt, args);
  va_end(args);
  if (xSemaphoreTake(logMutex, pdMS_TO_TICKS(100)) == pdTRUE) {
    Serial.printf("[%6lu] %s\n", millis(), buf);
    xSemaphoreGive(logMutex);
  }
}

void IRAM_ATTR onPress() {        // ISR: فقط زمان را ثبت می‌کند
  uint32_t now = millis();
  BaseType_t wokeHigher = pdFALSE;
  xQueueSendFromISR(pressQueue, &now, &wokeHigher);
  portYIELD_FROM_ISR(wokeHigher);
}

void buttonTask(void *param) {
  uint32_t t;
  int count = 0;
  for (;;) {
    xQueueReceive(pressQueue, &t, portMAX_DELAY);  // بخواب تا یک لبه برسد
    vTaskDelay(pdMS_TO_TICKS(30));                 // بگذار لرزش تمام شود
    xQueueReset(pressQueue);                       // لبه‌های لرزش را دور بریز
    if (digitalRead(BUTTON_PIN) != LOW) continue;  // رها شده: فشار نیست
    count++;
    if (busy) {
      logf("Button #%d: crossing already on its way, ignored", count);
    } else {
      logf("Button #%d: request sent", count);
      xTaskNotifyGive(lightHandle);                // زنگ Task چراغ را بزن
    }
  }
}

void lightTask(void *param) {
  pinMode(RED_LED, OUTPUT);
  pinMode(GREEN_LED, OUTPUT);
  for (;;) {
    digitalWrite(RED_LED, LOW);
    digitalWrite(GREEN_LED, HIGH);
    unsigned long greenSince = millis();
    logf("Cars: GREEN");
    ulTaskNotifyTake(pdTRUE, portMAX_DELAY);       // بخواب تا کسی درخواست کند
    busy = true;
    unsigned long greenFor = millis() - greenSince;
    if (greenFor < MIN_GREEN_MS) {
      logf("Request: cars keep green %lu ms more", MIN_GREEN_MS - greenFor);
      vTaskDelay(pdMS_TO_TICKS(MIN_GREEN_MS - greenFor));
    }
    logf("Cars: green blinking (warning)");
    for (int i = 0; i < 3; i++) {
      digitalWrite(GREEN_LED, LOW);
      vTaskDelay(pdMS_TO_TICKS(250));
      digitalWrite(GREEN_LED, HIGH);
      vTaskDelay(pdMS_TO_TICKS(250));
    }
    digitalWrite(GREEN_LED, LOW);
    digitalWrite(RED_LED, HIGH);
    logf("Cars: RED, people: WALK for %lu s", WALK_MS / 1000);
    vTaskDelay(pdMS_TO_TICKS(WALK_MS));
    ulTaskNotifyTake(pdTRUE, 0);                   // زنگ‌های اضافه را فراموش کن
    busy = false;
  }
}

  1. پایه‌ها و زمان‌ها. قرمز روی GPIO4، سبز روی GPIO26، دکمه روی GPIO27؛ ۵ ثانیه حداقل سبز و ۶ ثانیه برای عبور. ثابت‌های اسم‌دار قانون‌های گذرگاه را خوانا و قابل تغییر در یک جا می‌کنند.
  2. اشیای مشترک. صف، زمان فشارها را از ISR می‌آورد، Mutex از Serial محافظت می‌کند، handleها اجازه می‌دهند به یک Task خبر بدهیم و Stackش را اندازه بگیریم، و busy به Task دکمه می‌گوید عبوری در راه است یا نه. busy برابر volatile است چون یک Task آن را می‌نویسد و دیگری می‌خواند. یک bool تکی است، پس خواندنش بدون قفل امن است.
  3. یک printf مال خودت. ... در فهرست ورودی‌ها یعنی «هر تعداد ورودی اضافه». va_list، va_start و va_end آن‌ها را جمع می‌کنند و vsnprintf دقیقا مثل snprintf آن‌ها را در buf قالب‌بندی می‌کند. این C++ تازه است، ولی می‌توانی مثل یک دستور پخت از آن استفاده کنی: به هر Task اجازه می‌دهد logf("x=%d", x) را دقیقا مثل Serial.printf صدا بزند. قالب‌بندی قبل از گرفتن قفل انجام می‌شود، پس قفل فقط برای چاپ کوتاه نگه داشته می‌شود.
  4. چاپ قفل‌دار. Mutex را بگیر (حداکثر ۱۰۰ میلی‌ثانیه صبر)، یک خط کامل با زمان چاپ کن، Mutex را پس بده. بدون قفل، دو Task که هم‌زمان چاپ می‌کنند ممکن است حروفشان را در هم ببافند. با محدودیت زمانی به جای portMAX_DELAY، یک Task گیرکرده هرگز نمی‌تواند چاپگر را برای همه قفل کند.
  5. ISR. بدون تغییر نسبت به درس. فقط زمان را ثبت می‌کند و Task دکمه را بیدار می‌کند؛ نه Serial، نه delay.
  6. حذف لرزش در Task دکمه. بخواب تا یک لبه برسد، ۳۰ میلی‌ثانیه صبر کن، بقیه لبه‌های لرزش را دور بریز، و فقط اگر پایه هنوز LOW است فشار را بشمار. این همان الگوی ButtonISR درس است: هر فشار واقعی دقیقا یک شمارش می‌شود، و رها کردن (که آن هم لرزش دارد) نادیده گرفته می‌شود.
  7. درخواست یا نادیده گرفتن. اگر عبوری از قبل در راه است، «نادیده گرفته شد» ثبت کن؛ وگرنه ثبت کن و زنگ Task چراغ را با xTaskNotifyGive بزن. Notification هیچ داده‌ای نمی‌برد، فقط «بیدار شو»، که دقیقا همان معنی درخواست عبور است. از یک صف دوم سبک‌تر است.
  8. سبز، بعد خواب. LEDها را تنظیم کن، زمان شروع سبز را به خاطر بسپار، ثبت کن، و بدون محدودیت زمانی در ulTaskNotifyTake بخواب. در زمان خواب، Task هیچ پردازنده‌ای مصرف نمی‌کند؛ Task بیکاری (idle) اجرا می‌شود و Watchdog راضی می‌ماند.
  9. حداقل سبز. عبور را busy علامت بزن، بعد اگر سبز کمتر از ۵ ثانیه طول کشیده، بقیه‌اش را بخواب. busy قبل از این انتظار تنظیم می‌شود، پس فشارهای وسط آن هم نادیده گرفته می‌شوند. MIN_GREEN_MS - greenFor منفی نمی‌شود، چون فقط وقتی تفریق می‌کنیم که greenFor کوچک‌تر است.
  10. چشمک هشدار. سه بار خاموش و روشن، هر کدام ۲۵۰ میلی‌ثانیه. در یک Task، یک رشته اتفاق در زمان فقط چند خط پشت‌سرهم با vTaskDelay بینشان است. مقایسه کن که همین کار در یک loop() تنها با millis() چقدر حساب‌وکتاب لازم داشت.
  11. قرمز: عابرها عبور می‌کنند. سبز خاموش، قرمز روشن، ۶ ثانیه. فقط همین Task به LEDها دست می‌زند، پس هرگز قفل لازم ندارند: «هر سخت‌افزار یک صاحب دارد».
  12. زنگ‌های اضافه را فراموش کن، بعد گذرگاه را آزاد کن. ulTaskNotifyTake(pdTRUE, 0) بدون صبر هر Notificationی را پاک می‌کند؛ بعد busy به false برمی‌گردد. فشاری که در لحظه کوتاه بین پذیرفتن درخواست و تنظیم busy بیاید هنوز می‌توانست زنگ بزند. پاک کردنش اینجا تضمین می‌کند: یک درخواست، یک عبور.
  13. setup به ترتیب امن. اول صف و Mutex (و بررسی اینکه ساخته شده‌اند)، بعد Taskها، و وقفه در آخر. اگر وقفه اول وصل می‌شد، یک فشار زودهنگام xQueueSendFromISR را روی صفی صدا می‌زد که هنوز وجود ندارد و برنامه کرش می‌کرد. Task دکمه اولویت ۲ می‌گیرد تا سریع واکنش نشان دهد؛ کارش خیلی کوتاه است.
  14. loop به عنوان گزارش سلامت. هر ۱۰ ثانیه کمترین فضای آزاد Stackی را که هر Task تا حالا داشته ثبت می‌کند. delay در loop مشکلی ندارد: همان vTaskDelay در لباس مبدل است و به بقیه Taskها اجازه اجرا می‌دهد. اگر عدد Stack آزاد روزی به سمت صفر رفت، ۳۰۷۲ بایت آن Task را قبل از سرریز بیشتر کن.

خلاصه درس در سه خط

FreeRTOS هر کار را در Task خودش اجرا می‌کند: اندازه Stack را به بایت بده، اولویت‌ها را منطقی انتخاب کن و هر حلقه را جایی بخوابان یا منتظر بگذار تا نگهبان برد را ریست نکند. داده را با صف جابه‌جا کن، از منابع مشترک با Mutex محافظت کن، Task را با اعلان بیدار کن و از داخل وقفه فقط توابع FromISR را صدا بزن. فقط وقتی دلیل داری Task بساز: یک کار کند و مسدودکننده، یا زمان‌بندی کاملا متفاوت.

در درس بعد (۵.۵) دستگاهت یاد می‌گیرد از طریق Wi-Fi خودش را به‌روز کند (OTA) و فایل‌ها را در حافظه فلش خودش نگه دارد (LittleFS). Task، صف، Mutex و اعلانی که این‌جا یاد گرفتی همه در درس ۵.۶ برمی‌گردند، جایی که یک ایستگاه هوا سه Task را کنار هم اجرا می‌کند.
