تا حالا برنامه‌ای نوشته‌ای که با -O0 درست کار کند و با -O2 عجیب رفتار کند؟ یا روی کامپیوتر خودت جواب بدهد و روی STM32 نه؟ معمولا مقصر «باگ کامپایلر» نیست؛ مقصر یک قرارداد است که خبر نداشتی امضایش کرده‌ای. در این درس آن قرارداد را می‌خوانی: چه کارهایی در C «رفتار تعریف‌نشده» است، چرا کامپایلر از آن‌ها برای سریع‌کردن برنامه استفاده می‌کند، و چطور با هشدار و ابزار پیدایشان کنی.

🎯 بعد از این درس می‌توانی

  • فرق «تعریف‌نشده»، «مشخص‌نشده» و «تعریف‌شده توسط پیاده‌ساز» را بگویی
  • توضیح بدهی چرا -O2 می‌تواند نتیجهٔ برنامه را عوض کند
  • رایج‌ترین رفتارهای تعریف‌نشده را بشناسی و اصلاحشان کنی
  • تله‌های uint8_t، char، sizeof و ماکرو را ببینی و دور بزنی
  • با -fsanitize=undefined,address باگ پنهان را روی PC شکار کنی

🧰 پیش‌نیاز و وسایل

  • درس ۲.۲ (انواع داده و سرریز) و ۳.۲ (اشاره‌گر)
  • درس ۳.۳ (آرایه و اشاره‌گر) و ۳.۶ (volatile)
  • درس ۶.۱ (دیباگ) خوب است ولی لازم نیست
  • gcc یا clang روی PC (نسخه‌های اخیر sanitizer را دارند)؛ سخت‌افزار لازم نیست

ایده اصلی: قراردادی با بندهای ریز

فرض کن با یک پیمانکار قرارداد بسته‌ای: «من نقشهٔ ساختمان را می‌دهم، تو بساز». در قرارداد نوشته شده: «مشتری قول می‌دهد نقشه هرگز دیوار باربر را حذف نکند». پیمانکار هم بر همین اساس، بدون هیچ بازبینی اضافه‌ای، ستون‌ها را کم می‌کند تا ساختمان ارزان‌تر شود. اگر نقشهٔ تو واقعا دیوار باربر را حذف کرده باشد، پیمانکار مقصر نیست؛ تو قولت را شکسته‌ای. ساختمان ممکن است فرو بریزد، یا سال‌ها سالم بماند و روز اول زلزله بریزد.

مثال از زندگی روزمره

C همین پیمانکار است. استاندارد زبان فهرستی از کارها دارد که برنامه‌نویس «قول می‌دهد» انجام ندهد: مثلا دو عدد int را جمع نکند جوری که نتیجه از محدوده بیرون بزند. کامپایلر فرض می‌کند قولت را نگه داشته‌ای و کد ماشین را بر پایهٔ این فرض کوتاه و سریع می‌سازد. اگر قول را بشکنی، استاندارد چیزی برایت تضمین نمی‌کند: نه خطا، نه هشدار، نه نتیجهٔ ثابت.

به آن کارها می‌گویند رفتار تعریف‌نشده (Undefined Behavior، به‌اختصار UB). دو رفتار دیگر هم هستند که با UB اشتباه گرفته می‌شوند ولی خطرشان خیلی کمتر است:

نوعمعنی سادهمثالخطر
تعریف‌شدهاستاندارد یک جواب دقیق می‌دهدسرریز بی‌علامت، 5 / 2 == 2ندارد
تعریف‌شده توسط پیاده‌سازهر کامپایلر یک جواب انتخاب می‌کند و باید بنویسد کدامعلامت char، اندازهٔ int، شیفت راست عدد منفیکم؛ فقط کد قابل‌حمل نیست
مشخص‌نشدهیکی از چند جواب مجاز؛ لازم نیست همیشه همان باشدترتیب ارزیابی آرگومان‌های تابعمتوسط؛ خروجی بین کامپایلرها فرق می‌کند
تعریف‌نشدهاستاندارد هیچ‌چیز نمی‌گویدسرریز int، دسترسی خارج از آرایه، NULL را خواندنزیاد؛ کامپایلر از آن استفاده می‌کند

چرا کامپایلر از UB استفاده می‌کند؟

کامپایلر فقط ترجمه نمی‌کند؛ بهینه هم می‌کند. یکی از مهم‌ترین ابزارهایش همین فرض است: «برنامه‌نویس هرگز UB نمی‌سازد». بیا با یک مثال ببینیمش. روی رایانهٔ خودم با gcc و clang هر دو را اجرا کردم و نتیجه را همین‌جا می‌بینی. volatile را (از درس ۳.۶) فقط برای این آوردم که کامپایلر در زمان کامپایل نتواند حدس بزند v چند است.

#include <stdio.h>
#include <limits.h>

int main(void)
{
    volatile int v = INT_MAX;   // volatile: مقدار در زمان کامپایل معلوم نشود
    int a = v;
    int b = a + 1;              // سرریز علامت‌دار: رفتار تعریف‌نشده
    if (b > a)
        printf("b > a : the world is normal\n");
    else
        printf("b <= a : wrapped around\n");
    return 0;
}
  1. هدرها. stdio.h برای printf و limits.h برای INT_MAX (بزرگ‌ترین int؛ روی STM32 و ESP32 برابر ۲۱۴۷۴۸۳۶۴۷).
  2. تابع main. نقطهٔ شروع برنامه.
  3. مقدار بزرگ. v را برابر بزرگ‌ترین int می‌گذاریم. volatile یعنی «هر بار واقعا از حافظه بخوان». کامپایلر دیگر نمی‌تواند بگوید «v همان INT_MAX است» و کل محاسبه را از قبل انجام بدهد.
  4. کپی در a. a یک متغیر معمولی است و مقدارش INT_MAX.
  5. جمع خطرناک. a + 1 در int جا نمی‌شود. برای عددهای علامت‌دار این UB است. برای عددهای بی‌علامت چرخش کاملا قانونی است (درس ۲.۲). ولی برای علامت‌دار استاندارد گفته: «چنین چیزی نمی‌شود».
  6. مقایسه. اگر عدد نچرخیده باشد، b از a بزرگ‌تر است. اگر چرخیده باشد، نه. این مقایسه راهی است که ببینیم کامپایلر واقعا جمع را انجام داده یا فرض کرده «سرریز نمی‌شود».
  7. پایان موفق. return 0 یعنی برنامه سالم تمام شد.
$ gcc -std=c11 -Wall -Wextra -O2 -o ovf ovf.c
$ ./ovf
b > a : the world is normal

حالا همین فایل را با سطح بهینه‌سازی صفر (-O0، یعنی بدون بهینه‌سازی) بساز:

$ gcc -std=c11 -Wall -Wextra -O0 -o ovf ovf.c
$ ./ovf
b <= a : wrapped around

یک برنامه، دو کامپایل، دو جواب متضاد و هیچ هشداری در هیچ‌کدام. gcc و clang هر دو همین رفتار را دارند. چرا؟

می‌خواهی ببینی؟ نمونهٔ اسمبلی main با -O2 (که با gcc -O2 -S روی همین فایل گرفتم؛ خط‌های راهنمای .cfi را برای کوتاه‌شدن نیاوردم):

main:
    subq    $24, %rsp
    leaq    .LC0(%rip), %rsi
    movl    $2, %edi
    movl    $2147483647, 12(%rsp)
    movl    12(%rsp), %eax
    xorl    %eax, %eax
    call    __printf_chk@PLT
    xorl    %eax, %eax
    addq    $24, %rsp
    ret
  1. نوشتن و خواندن v. volatile را کامپایلر رعایت کرد: ۲۱۴۷۴۸۳۶۴۷ را در حافظه می‌نویسد و دوباره می‌خواند.
  2. فقط یک printf. هیچ addی نیست، هیچ cmp و پرشی هم نیست. رشتهٔ اول (.LC0) مستقیم چاپ می‌شود. شاخهٔ «wrapped around» اصلا در فایل خروجی وجود ندارد؛ کامپایلر آن را «کد مرده» فرض کرد.
«ولی روی سخت‌افزار که جمع می‌چرخد!»

درست است: پردازندهٔ ARM و x86 هر دو جمع را با مکمل ۲ انجام می‌دهند و می‌چرخند. اما کامپایلر با پردازنده کار ندارد؛ با استاندارد C کار دارد. تا وقتی کدت UB دارد، رفتار نهایی حاصل ضرب «کامپایلر × نسخه × پرچم بهینه‌سازی × کد اطراف» است. با تغییر یکی از این‌ها، نتیجه عوض می‌شود.

وقتی کامپایلر وارسی‌ات را دور می‌ریزد

این یکی از خطرناک‌ترین الگوهاست چون کد «محتاطانه» به‌نظر می‌رسد: اول از اشاره‌گر می‌خوانی، بعد وارسی می‌کنی که NULL نباشد.

#include <stdio.h>

int read_first(int *p)
{
    int value = *p;         // اول از p می‌خوانیم...
    if (p == NULL)          // ...بعد وارسی می‌کنیم؟!
        return -1;
    return value;
}

int main(void)
{
    int x = 42;
    printf("%d\n", read_first(&x));
    return 0;
}
  1. تابع read_first. یک اشاره‌گر به int می‌گیرد و مقدارش را برمی‌گرداند.
  2. خواندن *p. اگر p برابر NULL باشد، این خط UB است. پس کامپایلر از این خط نتیجه می‌گیرد: «حتما p صفر نیست، وگرنه برنامه قرارداد را شکسته».
  3. وارسی دیرهنگام. کامپایلر با همان نتیجه‌گیری این if را «همیشه نادرست» می‌بیند و حذفش می‌کند. این وارسی هیچ کاری نمی‌کرد؛ وقتی به آن می‌رسیم که خواندن انجام شده. جای درست وارسی قبل از استفاده است.
  4. برگرداندن مقدار. نتیجهٔ خواندن برگردانده می‌شود.
  5. main. فقط یک فراخوانی سالم با آدرس یک متغیر معتبر.
$ gcc -std=c11 -Wall -Wextra -O2 -o nullchk nullchk.c
$ ./nullchk
42

خروجی سالم است، ولی داخل تابع چه خبر است؟ همین تابع را با کامپایلر ARM (بدون printf) به اسمبلی ترجمه کردم؛ سمت چپ -O0، سمت راست -O2:

@ -O2 : کل تابع
read_first:
    ldr     r0, [r0]
    bx      lr

@ -O0 : وارسی هنوز هست
read_first:
    ...
    ldr     r3, [r3]        @ خواندن *p
    str     r3, [r7, #12]
    ldr     r3, [r7, #4]
    cmp     r3, #0          @ وارسی p == 0
    bne     .L2
    mov     r3, #-1
    b       .L3
  1. با -O2. فقط دو دستور: مقدار را از آدرس r0 بخوان و برگرد. نه cmp هست نه -1. این همان تابع است که وارسی NULL دارد؛ کامپایلر آن را حذف کرده.
  2. با -O0. کامپایلر کد را همان‌طور که نوشتی ترجمه کرده: بعد از خواندن، cmp r3, #0 و پرش. پس تست‌کردن با -O0 (مثلا داخل IDE در حالت Debug) این باگ را پنهان می‌کند.
در STM32 و ESP32 چه می‌شود؟

خواندن *NULL روی PC معمولا برنامه را می‌کشد (خطای segmentation fault). روی میکروکنترلر این‌طور نیست. در STM32F411 آدرس صفر معمولا آینه‌ای از Flash (شروع جدول وقفه) است، پس خواندن *NULL بی‌صدا یک عدد می‌دهد و باگ سال‌ها پنهان می‌ماند. در ESP32 آدرس صفر نگاشت‌نشده است و معمولا خطای LoadProhibited می‌گیری؛ در درس ۶.۱ با decode آن آشنا شدی. نتیجه: روی MCU نمی‌توانی به «کرش‌کردن» تکیه کنی؛ باید خودت وارسی را قبل از استفاده بگذاری.

خارج از آرایه: باگ همسایه

در درس ۲.۷ دیدی که ایندکس معتبر برای آرایهٔ ۴تایی ۰ تا ۳ است. اگر ایندکس ۴ بزنی چه می‌شود؟ کامپایلر بررسی نمی‌کند؛ به همان آدرس می‌رود، که «خانهٔ بعد از آرایه» است. آن خانه مال چه کسی است؟ معمولا متغیر دیگری.

ببین وقتی حلقه به‌جای < از <= استفاده می‌کند چه می‌شود. با «بعدی» قدم‌به‌قدم برو:

#include <stdio.h>

int main(void)
{
    int table[4] = {10, 20, 30, 40};
    int sum = 0;

    for (int i = 0; i <= 4; i++)     // خطا: i تا ۴ می‌رود، ولی آخرین ایندکس ۳ است
        sum += table[i];

    printf("sum = %d\n", sum);
    return 0;
}
  1. آرایهٔ ۴تایی. ایندکس‌های معتبر: ۰، ۱، ۲، ۳.
  2. جمع‌کننده. صفر شروع می‌شود.
  3. حلقهٔ خراب. شرط <= باعث می‌شود i برابر ۴ هم بشود؛ در دور آخر table[4] خوانده می‌شود، که بیرون آرایه است. این باگ «یکی-بیشتر» (off-by-one) پرتکرارترین خطای حلقه است. با < و طول آرایه (sizeof) امنش کن.
  4. چاپ. عددی که چاپ می‌شود شامل یک «آشغال» از حافظهٔ بیرون آرایه است.
$ gcc -std=c11 -Wall -Wextra -O0 -o oob oob.c
$ ./oob
sum = 2040923060
$ ./oob
sum = -303649820

هر بار اجرا عدد دیگری: بدترین نوع باگ! کامپایلر در -O0 حتی یک هشدار هم نداد. حالا همان برنامه را با sanitizer بساز؛ این ابزار کنار هر دسترسی به حافظه یک وارسی پنهان می‌گذارد. چند خط اول را می‌بینی (مسیرها و ادرس‌ها را کوتاه کرده‌ام؛ اجرای خودت کمی فرق می‌کند):

تله ارتقای صحیح: uint8_t همیشه ۸ بیتی حساب نمی‌شود

در درس ۲.۲ با ارتقای صحیح آشنا شدی: در C هر عبارتی که نوعش کوچک‌تر از int باشد، پیش از محاسبه به int تبدیل می‌شود. تله‌های زیر همه از همین‌جا می‌آیند و در کد رجیستر و پروتکل‌ها بسیار زیادند.

#include <stdio.h>
#include <stdint.h>

int main(void)
{
    uint8_t a = 0x0F;
    if (~a == 0xF0)                       // فکر می‌کنی درست است؟
        printf("~a == 0xF0\n");
    else
        printf("~a != 0xF0\n");
    printf("~a = 0x%X\n", (unsigned)~a);

    uint8_t hi = 0xAB;
    uint32_t word = (uint32_t)hi << 24;   // اول به 32 بیت بی‌علامت برسان، بعد شیفت بده
    printf("word = 0x%08X\n", (unsigned)word);

    uint8_t b = 200, c = 100;
    uint8_t sum = b + c;                  // محاسبه با int انجام می‌شود، ذخیره در 8 بیت
    printf("sum = %u\n", sum);
    return 0;
}
  1. وارونه کردن و مقایسه. a ابتدا به int می‌رود (0x0000000F)، بعد ~ اعمال می‌شود (0xFFFFFFF0) و با 0xF0 مقایسه می‌شود. در ذهن ما «~a یک بایت است». ولی زبان C هیچ محاسبهٔ ۸ بیتی ندارد؛ کوچک‌ترین محاسبه int است.
  2. نتیجه. مقایسه نادرست است، پس شاخهٔ else چاپ می‌شود.
  3. چاپ خود ~a. 0xFFFFFFF0 را می‌بینی، نه 0xF0. راه درست: (uint8_t)~a یا ~a & 0xFF یا مقایسه را در uint8_t انجام بده.
  4. شیفت امن. hi اول به uint32_t تبدیل می‌شود و بعد به چپ می‌رود؛ همه‌چیز در نوع بی‌علامت و تعریف‌شده می‌ماند. بدون cast، hi << 24 در نوع int (علامت‌دار) انجام می‌شد؛ در ادامه می‌بینیم چرا خطرناک است.
  5. جمع ۸ بیتی. ۲۰۰ + ۱۰۰ = ۳۰۰ در int حساب می‌شود؛ هنگام ذخیره در uint8_t باقی‌مانده بر ۲۵۶ می‌ماند: ۴۴. این برش قانونی است (تعریف‌شده)، فقط باید بدانی. اگر ۴۴ نمی‌خواهی، نتیجه را در نوع بزرگ‌تر نگه دار.
$ gcc -std=c11 -Wall -Wextra -o promo promo.c
promo.c:7:12: warning: comparison of promoted bitwise complement of an unsigned value with constant [-Wsign-compare]

$ ./promo
~a != 0xF0
~a = 0xFFFFFFF0
word = 0xAB000000
sum = 44

خوشبختانه gcc این مقایسه را هشدار می‌دهد (خط دوم). حالا نسخهٔ خراب همین کد را ببین. این بار x * x و hi << 24 را بدون cast نوشته‌ایم:

#include <stdio.h>
#include <stdint.h>

int main(void)
{
    volatile uint16_t x = 0xFFFF;
    volatile uint8_t hi = 0xAB;
    uint32_t sq = x * x;             // uint16_t به int تبدیل می‌شود: 65535*65535 در int جا نمی‌شود
    uint32_t word = hi << 24;        // 0xAB به int می‌رود؛ شیفت به بیت 31 علامت را خراب می‌کند
    printf("sq = %u, word = 0x%08X\n", (unsigned)sq, (unsigned)word);
    return 0;
}
  1. دو متغیر کوچک. بیشینهٔ uint16_t و مقداری با بیت ۷ روشن. volatile فقط برای این است که کامپایلر ثابت‌بودن را حدس نزند.
  2. ضرب. هر دو عامل به int (علامت‌دار، ۳۲ بیتی) ارتقا می‌یابند. حاصل ۴۲۹۴۸۳۶۲۲۵ از بیشینهٔ int بزرگ‌تر است: سرریز علامت‌دار، یعنی UB. حاصل در uint32_t جا می‌شد؛ ولی ضرب قبل از انتساب و در int انجام می‌شود، نه در نوع سمت چپ =.
  3. شیفت. عدد ۱۷۱ در int به چپ ۲۴ بیت می‌رود و به بیت علامت می‌رسد؛ طبق C11 این هم UB است. در MCU رایج است: (buf[0] << 24) | buf[1] << 16 ... برای ساختن کلمهٔ ۳۲ بیتی. تا وقتی بایت اول کمتر از 0x80 است کار می‌کند و ناگهان بایت اول 0x80 به بالا می‌شود.
  4. چاپ. روی gcc با -O0 جواب «درست» می‌دهد؛ ولی UB است و ضمانتی نیست.
$ gcc -std=c11 -Wall -Wextra -o promo_bad promo_bad.c
$ ./promo_bad
sq = 4294836225, word = 0xAB000000

برنامه «درست» چاپ کرد و اگر فقط به خروجی نگاه کنی، خیالت راحت است. ولی UBSan حقیقت را نشان می‌دهد:

$ gcc -std=c11 -g -fsanitize=undefined -o promo_bad_u promo_bad.c
$ ./promo_bad_u
promo_bad.c:8:21: runtime error: signed integer overflow: 65535 * 65535 cannot be represented in type 'int'
promo_bad.c:9:24: runtime error: left shift of 171 by 24 places cannot be represented in type 'int'
sq = 4294836225, word = 0xAB000000

راه اصلاح ساده است: قبل از عمل، یکی از عامل‌ها را به نوع بی‌علامت بزرگ بکن. (uint32_t)x * x و (uint32_t)hi << 24. قاعده: هر جا شیفت یا ضرب روی نوع کوچک می‌زنی، اول cast به uint32_t.

علامت char در ARM و x86 فرق دارد

استاندارد C نگفته char علامت‌دار است یا بی‌علامت (علامت char). هر پردازنده و کامپایلر خودش انتخاب می‌کند (رفتار تعریف‌شده توسط پیاده‌ساز). در gcc روی x86 پیش‌فرض علامت‌دار است ولی در arm-none-eabi-gcc پیش‌فرض بی‌علامت است؛ ESP32 (Xtensa) هم بی‌علامت است. یعنی کدی که روی PC تست کردی، روی MCU متفاوت رفتار می‌کند.

#include <stdio.h>

int main(void)
{
    char c = (char)200;               // بایت 0xC8
    printf("(int)c = %d\n", (int)c);
    if (c > 100)
        printf("c > 100\n");
    else
        printf("c <= 100\n");
    return 0;
}
  1. ساخت بایت. عدد ۲۰۰ (باینری 11001000) را در یک char می‌گذاریم. cast صریح است تا هشدار ندهد.
  2. چاپ عددی. اگر char علامت‌دار باشد ۵۶- و اگر بی‌علامت باشد ۲۰۰ می‌شود.
  3. مقایسه. نتیجه به همان علامت‌داری وابسته است. در کد واقعی این خط مثل «بایت دریافتی UART از ۱۰۰ بزرگ‌تر است؟» است؛ نتیجه روی PC و روی MCU فرق می‌کند.
$ gcc -std=c11 -Wall -Wextra -o chr chr.c
$ ./chr
(int)c = -56
c <= 100

برای شبیه‌سازی رفتار ARM روی PC، پرچم -funsigned-char را بگذار:

$ gcc -std=c11 -Wall -Wextra -funsigned-char -o chr chr.c
$ ./chr
(int)c = 200
c > 100

راه‌حل حرفه‌ای: برای «بایت خام» همیشه uint8_t بنویس و از char فقط برای متن استفاده کن. اگر مجبوری عدد داخل char بگذاری، signed char یا unsigned char را صریح بنویس.

اشاره‌گر به نوع دیگر: aliasing و ناهم‌ترازی

در درس ۳.۳ شنیدی که strict aliasing وجود دارد: کامپایلر فرض می‌کند دو اشاره‌گر از نوع‌های بی‌ارتباط (مثلا int* و float*) هرگز به یک حافظه اشاره نمی‌کنند. اگر بکنند UB است. ببین این فرض چه می‌کند. هر دو اشاره‌گر را عمدا به یک جا می‌فرستیم:

#include <stdio.h>
#include <string.h>

static int poke(int *i, float *f)
{
    *i = 1;
    *f = 2.0f;          // کامپایلر فرض می‌کند f و i یک جا نیستند
    return *i;          // پس شاید همان 1 را برگرداند
}

int main(void)
{
    int box = 0;
    int r = poke(&box, (float *)&box);      // عمدا هر دو به یک جا اشاره می‌کنند
    printf("returned %d\n", r);
    return 0;
}
  1. تابع poke. دو اشاره‌گر با دو نوع متفاوت می‌گیرد.
  2. نوشتن ۱ در i. عدد صحیح ۱ در حافظه.
  3. نوشتن ۲٫۰ در f. اگر f و i واقعا یکی باشند، الگوی بیت‌های ۲٫۰ جای ۱ را می‌گیرد. قانون aliasing به کامپایلر اجازه می‌دهد بگوید: نوشتن در float نمی‌تواند int را عوض کند.
  4. خواندن i. کامپایلر با -O2 خواندن را جا می‌اندازد و مستقیم ۱ را برمی‌گرداند.
  5. فراخوانی با آدرس یکسان. عمدا قانون را می‌شکنیم. cast (float *) پنهانش می‌کند و gcc هشداری نمی‌دهد.
$ gcc -std=c11 -Wall -Wextra -O2 -o alias2 alias2.c
$ ./alias2
returned 1

$ gcc -std=c11 -Wall -Wextra -O0 -o alias2 alias2.c
$ ./alias2
returned 1073741824

در -O0 نتیجه ۱۰۷۳۷۴۱۸۲۴ (همان 0x40000000، الگوی بیتی ۲٫۰ به‌صورت float) است و با -O2 عدد ۱. اگر بخواهی بیت‌های float را بخوانی، راه امن این است که با memcpy کپی کنی؛ کامپایلرهای خوب memcpy کوچک را به یک دستور تبدیل می‌کنند و هزینه‌ای نمی‌دهی:

uint32_t bits;
memcpy(&bits, &value_f, sizeof bits);   // درست، بدون UB
  1. کپی بایتی. memcpy بایت‌ها را از یک شیء به شیء دیگر کپی می‌کند و نوع‌ها را قاطی نمی‌کند. استاندارد اجازه‌ی دسترسی به هر شیء را از راه char* و memcpy می‌دهد. union هم در C11 معمولا مجاز است.

ناهم‌ترازی

مشکل هم‌خانواده، دسترسی ناهم‌تراز: تبدیل اشاره‌گر uint8_t* به uint32_t* وقتی آدرس مضرب ۴ نیست. بسته‌های شبکه و UART پر از این حالت‌اند (سرآیند یک بایت و بعد یک عدد ۳۲ بیتی). روی x86 «کار می‌کند»؛ در ARM Cortex-M0 خطای HardFault می‌دهد؛ در Cortex-M3/M4 بیشتر دستورهای خواندن مجازند ولی همه نه، و کامپایلر ممکن است از دستور چندکلمه‌ای استفاده کند. استاندارد هم در هر حالت آن را UB می‌داند.

#include <stdio.h>
#include <stdint.h>
#include <string.h>

int main(void)
{
    uint8_t packet[8] = {0x01, 0x78, 0x56, 0x34, 0x12, 0, 0, 0};

    uint32_t *p = (uint32_t *)&packet[1];     // آدرس فرد: ناهم‌تراز برای 32 بیتی
    printf("cast   : 0x%08X\n", (unsigned)*p);

    uint32_t v;
    memcpy(&v, &packet[1], sizeof v);         // روش امن
    printf("memcpy : 0x%08X\n", (unsigned)v);
    return 0;
}
  1. بستهٔ نمونه. بایت اول سرآیند است و چهار بایت بعد یک عدد ۳۲ بیتی little-endian: 0x12345678.
  2. cast خطرناک. آدرس &packet[1] فرد است ولی uint32_t انتظار مضرب ۴ دارد. روی PC جواب می‌دهد و UB است. کامپایلر ممکن است بر اساس فرض «هم‌ترازی» کد سریع‌تری بسازد (مثلا خواندن ۱۶ بایت با یک دستور)، و آن کد روی آدرس فرد خراب می‌شود.
  3. memcpy امن. چهار بایت را به متغیر ۳۲ بیتی کپی می‌کند؛ هم‌ترازی مهم نیست.
$ ./misal
cast   : 0x12345678
memcpy : 0x12345678

$ gcc -std=c11 -g -fsanitize=undefined -o misal_u misal.c
$ ./misal_u
misal.c:10:5: runtime error: load of misaligned address 0x7ffc1d482141 for type 'uint32_t', which requires 4 byte alignment

باقی UB های مهم، یک‌جا

این‌ها را هم باید بشناسی. برای هرکدام پیام واقعی کامپایلر یا ابزار را می‌بینی.

متغیر بدون مقدار

#include <stdio.h>

int main(void)
{
    int count;
    for (int i = 0; i < 3; i++)
        count += i;
    printf("count = %d\n", count);
    return 0;
}
  1. count بدون مقدار. قفسه‌ای پر از آشغال (درس ۲.۱).
  2. جمع‌کردن روی آشغال. count += i یعنی count = count + i؛ اولین خواندن count UB است. در C نوشته‌ایم «متغیر با مقدار نامعین» و استفاده‌اش رفتار غیرقابل‌پیش‌بینی است، نه فقط «عدد تصادفی».
  3. چاپ. خروجی هر بار فرق می‌کند.
$ gcc -std=c11 -Wall -Wextra -O0 -o uninit uninit.c
$ ./uninit
count = 1675686891
$ ./uninit
count = 1842385979

$ gcc -std=c11 -Wall -Wextra -O2 -o uninit uninit.c
uninit.c:7:15: warning: 'count' is used uninitialized [-Wuninitialized]
$ ./uninit
count = 3

دقت کن: با -O0 هشدار نمی‌آید (تحلیل جریان داده فقط با بهینه‌سازی روشن انجام می‌شود) و عدد اجرای اول و دوم فرق دارد. با -O2 هشدار می‌آید و کامپایلر اتفاقا جوابی «قشنگ» (۳) می‌دهد که تصادفی است. یک تنظیم دائمی برای کار حرفه‌ای: هم -O0 هم -O2 را با -Wall -Wextra امتحان کن؛ هشدارهای مختلف در سطح‌های مختلف فعال می‌شوند.

تابعی که return ندارد

#include <stdio.h>

static int sign_of(int x)
{
    if (x > 0)
        return 1;
    if (x < 0)
        return -1;
}                               // اگر x == 0 باشد، چیزی برنمی‌گردد!

int main(void)
{
    printf("%d\n", sign_of(5));
    return 0;
}
  1. مسیر بدون return. برای x == 0 هیچ شاخه‌ای return نمی‌کند و اجرا به آکولاد پایانی می‌رسد. استفاده از مقدار این فراخوانی UB است. کامپایلر می‌تواند فرض کند «x صفر نمی‌شود» و کد ماشین بعد از تابع را روی هم بریزد.
  2. main. فقط با ۵ صدا می‌زند؛ ولی خطا در خود تابع است.
noret.c: In function 'sign_of':
noret.c:9:1: error: control reaches end of non-void function [-Werror=return-type]

به‌طور پیش‌فرض این فقط هشدار (با -Wall) است؛ اینجا با -Werror=return-type به خطا تبدیل شد. در پروژه‌های جدی -Werror را روشن نگه می‌دارند تا هشدار جدید نتواند وارد کد شود (درس ۶.۳).

آدرس متغیر محلی و رشتهٔ ثابت

در درس ۳.۵ دیدی که متغیر محلی بعد از خروج از تابع می‌میرد. آدرسش را برگرداندن، اشاره‌گر آویزان می‌سازد. gcc این را هشدار می‌دهد:

#include <stdio.h>

static int *make_counter(void)
{
    int counter = 5;
    return &counter;            // آدرس متغیر محلی: بعد از return دیگر معتبر نیست
}

int main(void)
{
    int *p = make_counter();
    printf("%d\n", *p);
    return 0;
}
  1. تابع بد. counter روی پشته است و با پایان تابع آزاد می‌شود؛ ولی آدرسش را بیرون می‌دهیم.
  2. استفاده. *p به حافظه‌ای می‌رود که دیگر مال ما نیست. این خط ممکن است ۵ چاپ کند، عدد دیگری بدهد یا برنامه را بکشد. فرقی هم بین اجرا و اجرا دارد.
dangle.c: In function 'make_counter':
dangle.c:6:12: error: function returns address of local variable [-Werror=return-local-addr]

یک اشتباه هم‌خانواده، تغییر رشتهٔ ثابت است. "hello" در بخش فقط‌خواندنی (روی MCU: Flash) نگه‌داری می‌شود:

#include <stdio.h>

int main(void)
{
    char *msg = "hello";        // رشتهٔ ثابت: در بخش فقط‌خواندنی (Flash)
    printf("before: %s\n", msg);
    msg[0] = 'H';               // نوشتن در حافظهٔ فقط‌خواندنی
    printf("after : %s\n", msg);
    return 0;
}
  1. اشاره‌گر به رشتهٔ ثابت. msg به بایت‌های "hello" که در .rodata هستند اشاره می‌کند. در C نوع رشتهٔ ثابت char[] است ولی نوشتن در آن UB است. بهتر است const char *msg بنویسی تا کامپایلر جلوی خط ۷ را بگیرد.
  2. نوشتن در آن. روی PC حافظهٔ فقط‌خواندنی است و سیستم‌عامل برنامه را می‌کشد؛ روی MCU ممکن است HardFault شود یا بی‌صدا هیچ نشود (Flash نوشتنی نیست).
$ ./lit
before: hello
Segmentation fault (core dumped)

راه درست: اگر باید تغییرش بدهی، آرایه بساز: char msg[] = "hello";. اگر نباید تغییرش بدهی، const char *msg بنویس.

تقسیم بر صفر و شیفت

روی PC تقسیم int بر صفر معمولا برنامه را می‌کشد و روی Cortex-M4 به‌طور پیش‌فرض صفر برمی‌گرداند (مگر بیت DIV_0_TRP روشن شود). شیفت به اندازهٔ عرض نوع یا بیشتر، و شیفت چپ عدد منفی، هم UB است. UBSan همه را با پیام روشن اعلام می‌کند:

$ ./div_u
div.c:7:23: runtime error: division by zero
$ ./sh_u
sh.c:7:22: runtime error: shift exponent 32 is too large for 32-bit type 'int'
sh.c:8:24: runtime error: left shift of negative value -8

راه اصلاح: قبل از تقسیم مقسوم‌علیه را با if وارسی کن؛ مقدار شیفت را با < 32 محدود کن؛ برای شیفت از نوع بی‌علامت (1u << n) استفاده کن (درس ۳.۱).

ترتیب ارزیابی: «مشخص‌نشده»

در f(next(), next()) استاندارد نگفته کدام آرگومان اول حساب شود. اجرای واقعی روی gcc و clang:

#include <stdio.h>

static int next(void)
{
    static int n = 0;
    return ++n;
}

int main(void)
{
    // ترتیب ارزیابی آرگومان‌ها مشخص‌نشده (unspecified) است
    printf("%d %d\n", next(), next());
    return 0;
}
  1. تابع next. هر بار یکی بیشتر برمی‌گرداند: ۱ و بعد ۲ و ... static داخل تابع یعنی n بین فراخوانی‌ها می‌ماند (درس ۳.۵).
  2. دو فراخوانی در یک عبارت. کدام اول اجرا شود؟ استاندارد نمی‌گوید. این UB نیست ولی برنامه را «وابسته به کامپایلر» می‌کند. تابع‌های دارای اثر جانبی را در خط‌های جدا صدا بزن.
$ gcc -std=c11 -Wall -Wextra -o order order.c
$ ./order
2 1

$ clang -std=c11 -Wall -Wextra -o order order.c
$ ./order
1 2

حالا i = i++ + i و شبیه‌هایش: در یک عبارت دوبار به یک متغیر می‌نویسی یا هم می‌نویسی هم می‌خوانی، بدون نقطهٔ ترتیب (sequence point)؛ این UB است. gcc با -Wall می‌گوید: warning: operation on 'i' may be undefined [-Wsequence-point]. جوابی هم که بر اساس آن حدس بزنی، معتبر نیست.

sizeof روی پارامتر آرایه

یادت هست در درس ۲.۷ گفتیم آرایه را به تابع که بدهی، فقط آدرس شروع می‌رود؟ پس داخل تابع sizeof اندازهٔ اشاره‌گر را می‌دهد، نه آرایه:

#include <stdio.h>
#include <stddef.h>

static size_t count_bad(int values[4])
{
    return sizeof(values) / sizeof(values[0]);   // اینجا values اشاره‌گر است، نه آرایه
}

int main(void)
{
    int data[4] = {1, 2, 3, 4};
    printf("in main : %zu elements\n", sizeof(data) / sizeof(data[0]));
    printf("in func : %zu elements\n", count_bad(data));
    return 0;
}
  1. تابع فریبنده. با اینکه نوشته‌ایم int values[4]، کامپایلر آن را به int *values تبدیل می‌کند و ۴ فقط یک توضیح است. در C آرایه هرگز کپی نمی‌شود؛ فقط آدرسش می‌رود («decay»، درس ۳.۳).
  2. در main. data واقعا آرایه است: ۱۶ بایت ÷ ۴ = ۴.
  3. در تابع. sizeof(values) = اندازهٔ اشاره‌گر (۸ بایت روی PC ۶۴ بیتی)، پس ۸ ÷ ۴ = ۲. روی STM32 و ESP32 اشاره‌گر ۴ بایت است و نتیجه ۱ می‌شود. به این هم اعتماد نکن؛ طول را جدا به تابع بفرست.
$ gcc -std=c11 -Wall -Wextra -o szarr szarr.c
szarr.c:6:18: warning: 'sizeof' on array function parameter 'values' will return size of 'int *' [-Wsizeof-array-argument]

$ ./szarr
in main : 4 elements
in func : 2 elements

ماکرو و دستورهای خوش‌ظاهر

این‌ها UB نیستند ولی همان سطح خطرناکند: کد «درست به‌نظر می‌رسد» و کار دیگری می‌کند. چهار تله را یک‌جا داخل یک برنامه گذاشتم و هشدارهای واقعی gcc را زیرش می‌بینی.

#include <stdio.h>

#define SQUARE(x) x * x
#define SQUARE_OK(x) ((x) * (x))

static void state_name(int s)
{
    switch (s) {
    case 0:
        printf("[IDLE]");
    case 1:
        printf("[RUN]");
        break;
    default:
        printf("[?]");
    }
    printf("\n");
}

int main(void)
{
    int n = 3;
    printf("SQUARE(n + 1)    = %d\n", SQUARE(n + 1));
    printf("SQUARE_OK(n + 1) = %d\n", SQUARE_OK(n + 1));

    if (n > 5);                 // نقطه‌ویرگول اضافه: بدنهٔ if خالی است
        printf("n is big\n");

    state_name(0);              // break فراموش شده: از case 0 به case 1 می‌ریزد
    return 0;
}
  1. ماکروی بدون پرانتز. ماکرو فقط جایگزینی متن است: SQUARE(n + 1) می‌شود n + 1 * n + 1، یعنی ۳ + ۳ + ۱ = ۷. ضرب قبل از جمع است. جزئیات ماکرو در درس ۴.۱.
  2. نسخهٔ درست. هر پارامتر و کل عبارت پرانتز دارد: ((n + 1) * (n + 1)) = ۱۶.
  3. تابع با switch. در case 0 بعد از چاپ [IDLE] break نیست، پس اجرا به case 1 می‌ریزد. به این می‌گویند fallthrough (درس ۲.۴). گاهی عمدی است ولی باید با کامنت یا __attribute__((fallthrough)) اعلام شود.
  4. مقایسهٔ دو ماکرو. نتیجهٔ این دو خط ۷ و ۱۶ است.
  5. نقطه‌ویرگول اضافه. if (n > 5); یعنی «اگر n بزرگ است، هیچ کاری نکن». خط بعدی فارغ از شرط اجرا می‌شود و تورفتگی فریب می‌دهد. همین یک ; در پروژه‌های واقعی باعث خاموش‌شدن حفاظت‌ها شده است. برای همین همیشه آکولاد بگذار.
  6. فراخوانی. با ۰ صدا می‌زنیم و دو برچسب پشت هم چاپ می‌شود.

  2. دو if تو در تو. بدون آکولاد.

و رقابت داده (data race)؟

اگر متغیری هم در ISR و هم در main تغییر کند و volatile/محافظت نداشته باشد، برای کامپایلر این «دسترسی هم‌زمان» نیست، چون در C خالص وقفه‌ای وجود ندارد. نتیجه: خواندن ناقص، شمارندهٔ خراب یا حلقه‌ای که هرگز تمام نمی‌شود. مثال کامل و راه‌حل (volatile، بخش حساس، نوشتن یک‌بایتی) را در درس ۵.۳ و ۳.۶ دیدی. اینجا فقط به‌خاطر بسپار که این هم یک UB است و sanitizer معمولی روی MCU آن را نمی‌بیند.

زیر کاپوت: چرا اصلا UB وجود دارد؟

اگر استاندارد می‌گفت «سرریز = چرخش» یا «ایندکس بد = خطا»، کامپایلر باید برای هر جمع و هر آرایه کد بازرسی می‌گذاشت و C روی پردازنده‌های مختلف کند می‌شد. C ۱۹۷۰ برای این ساخته شد که «سریع و نزدیک سخت‌افزار» باشد و بار مسئولیت را به برنامه‌نویس داد. UB یعنی «مسئولیت با توست». بعدها کامپایلرها هوشمند شدند و از همین آزادی برای بهینه‌سازی سنگین استفاده کردند. برای همین کد قدیمی که «همیشه کار می‌کرد» با کامپایلر جدید ناگهان خراب می‌شود.

قاعدهٔ طلایی برای کد embedded
  • عددها را uint32_t و شیفت را روی نوع بی‌علامت بزن؛ قبل از ضرب یا شیفت نوع کوچک را cast کن.
  • هر اشاره‌گر را قبل از استفاده وارسی کن، نه بعد.
  • بایت خام = uint8_t؛ خواندن عدد چندبایتی از بافر = شیفت یا memcpy.
  • هر بار -Wall -Wextra را با -O0 و -O2 اجرا کن؛ هشدار جدید را همان روز رفع کن.
  • منطق را روی PC با -fsanitize=undefined,address آزمون کن.

آزمون این درس

کدام جمله دربارهٔ «رفتار تعریف‌نشده» درست است؟

  1. همیشه برنامه را متوقف می‌کند و پیام خطا می‌دهد
  2. کامپایلر حتما هنگام کامپایل آن را هشدار می‌دهد
  3. کامپایلر می‌تواند فرض کند هرگز اتفاق نمی‌افتد و بر آن اساس کد را بهینه کند
  4. هر کامپایلر باید همیشه یک نتیجهٔ ثابت بدهد
UB یعنی استاندارد هیچ تضمینی نمی‌دهد. کامپایلر فرض می‌کند رخ نمی‌دهد و بر همین اساس کد را ساده می‌کند؛ نتیجه‌اش گاهی خطای پنهان است.

با uint8_t a = 0x0F;، شرط if (~a == 0xF0) چه می‌شود؟

  1. نادرست است، چون ~a بعد از ارتقا به int برابر 0xFFFFFFF0 می‌شود
  2. درست است، چون ~ فقط هشت بیت را وارونه می‌کند
  3. برنامه کامپایل نمی‌شود
  4. رفتار تعریف‌نشده است و هر چیزی ممکن است
ارتقای صحیح: a ابتدا به int می‌رود و بعد ~ اعمال می‌شود. راه درست: (uint8_t)~a == 0xF0.

در کدام مورد رفتار برنامه تعریف‌نشده است (فرض کن int ۳۲ بیتی است)؟

  1. uint8_t x = 255; x++;
  2. ۷ / ۲ که جواب ۳ می‌دهد
  3. صدا زدن f(g(), h()) که ترتیب ارزیابی g و h نامعلوم است
  4. int m = INT_MAX; m = m + 1;
فقط سرریز علامت‌دار UB است. چرخش بی‌علامت تعریف‌شده و ترتیب ارزیابی آرگومان‌ها «مشخص‌نشده» (بی‌ضررتر) است.

روی STM32 (arm-none-eabi-gcc) این کد چه می‌کند؟
char c = (char)200; if (c > 100) ...

  1. شرط نادرست است، چون c برابر ۵۶- می‌شود
  2. شرط درست است، چون char روی ARM پیش‌فرض بی‌علامت است و c برابر ۲۰۰ می‌شود
  3. برنامه کامپایل نمی‌شود چون ۲۰۰ در char جا نمی‌شود
  4. نتیجه تصادفی است و هر بار فرق می‌کند
علامت char تعریف‌شده توسط پیاده‌ساز است. برای بایت خام uint8_t بنویس تا روی همه‌جا یکسان باشد.

تابعی روی STM32 با پارامتر int v[4] می‌نویسد sizeof(v) / sizeof(v[0]). چه عددی می‌گیرد؟

  1. ۴
  2. ۲
  3. ۱، چون v اشاره‌گر ۴ بایتی است و ۴ ÷ ۴ = ۱
  4. برنامه کامپایل نمی‌شود
پارامتر آرایه در C همان اشاره‌گر است. طول را همیشه جداگانه به تابع بده.

چرا این تابع خطرناک است؟
int f(int *p) { int v = *p; if (p == NULL) return -1; return v; }

  1. خواندن *p قبل از وارسی است؛ کامپایلر با -O2 وارسی را حذف می‌کند
  2. چون int *p نمی‌تواند پارامتر باشد
  3. چون اشاره‌گر را نمی‌شود با NULL مقایسه کرد
  4. چون volatile ندارد
اول وارسی کن، بعد بخوان. کد باید if (p == NULL) return -1; را قبل از *p بگذارد.

تمرین ۱: کوچک‌ها چرخ می‌کنند، بزرگ‌ها پنهان می‌شوند

می‌خواهیم رفتار سرریز با نوع‌های ۸ بیتی را بشناسیم. a = 250 و b = 10 از نوع uint8_t هستند.

  1. پیش‌بینی: مقدار (uint8_t)(a + b) چند است؟ مقدار a + b بدون cast چند است؟
  2. حل: برنامه‌ای بنویس که هر دو را چاپ کند. سپس با int8_t و مقدارهای ۱۲۰ و ۱۰ همین را تکرار کن.

راهنمایی

جمع همیشه در int انجام می‌شود (۲۶۰ و ۱۳۰ در int جا می‌شوند، پس سرریزی نیست). فقط وقتی نتیجه را ذخیره می‌کنی، به ۸ بیت بریده می‌شود. برای بی‌علامت باقی‌مانده بر ۲۵۶ است؛ برای علامت‌دار نتیجه به پیاده‌ساز-تعریف است (در gcc مثل چرخش).

#include <stdio.h>
#include <stdint.h>

int main(void)
{
    uint8_t a = 250;
    uint8_t b = 10;
    uint8_t sum8 = (uint8_t)(a + b);   // برش به 8 بیت: قانونی و تعریف‌شده
    int sum_int = a + b;               // محاسبه در int: 260
    printf("sum8 = %u\n", sum8);
    printf("sum_int = %d\n", sum_int);

    int8_t s = 120;
    int8_t t = (int8_t)(s + 10);       // 130 در int8_t جا نمی‌شود

  2. برش قانونی. جمع در int = ۲۶۰؛ cast آن را به ۸ بیت می‌برد: ۲۶۰ mod ۲۵۶ = ۴. تبدیل به نوع بی‌علامت همیشه مدول است. استاندارد صریحا می‌گوید.
  3. بدون برش. ۲۶۰ سالم می‌ماند، چون int است.
  4. علامت‌دار ۸ بیتی. جمع در int = ۱۳۰ (سرریز ندارد). cast به int8_t مقدار خارج از محدوده است؛ نتیجه پیاده‌ساز-تعریف است و gcc ۱۲۶- می‌دهد. این با INT_MAX + 1 فرق دارد: آن‌جا خود عمل جمع روی نوع علامت‌دار سرریز می‌کند (UB)؛ این‌جا فقط نتیجه در نوع کوچک‌تر جا نمی‌شود.

تابع میانگین زیر سه خطای جدی دارد. همه‌شان را در این درس دیده‌ای.

static int average(const int *v, int n)
{

  2. پیدا کن: خطای حلقه (یکی-بیشتر) را نشان بده و بگو چرا خارج آرایه می‌خواند.
  3. پیدا کن و اصلاح کن: آرگومان دوم average چه اشتباهی دارد؟ برنامه را درست کن و اجرا کن.
راهنمایی

الف: int sum; بدون مقدار. ب: <= در حلقه. پ: sizeof(readings) تعداد بایت‌ها است، نه تعداد عنصرها. باید بر sizeof(readings[0]) تقسیم شود.

جواب کامل با توضیح 
#include <stdio.h>

static int average(const int *v, int n)
{
    int sum = 0;                        // 1: مقدار اولیه
    for (int i = 0; i < n; i++)         // 2: < نه <=
        sum += v[i];
    return sum / n;
}

int main(void)
{
    int readings[4] = {20, 22, 21, 23};
    int count = (int)(sizeof(readings) / sizeof(readings[0]));   // 3: تعداد عنصر
    printf("%d\n", average(readings, count));
    return 0;
}
  1. صفر کردن جمع. جمع از صفر شروع می‌شود. بدون آن اولین += از آشغال می‌خواند (UB) و نتیجه هر بار فرق می‌کند.
  2. شرط درست. i < n یعنی ایندکس ۰ تا n-1. با <= عنصر v[n] هم خوانده می‌شد که مال آرایه نیست.
  3. جمع و میانگین. تقسیم صحیح. اگر n صفر شود، تقسیم بر صفر است، پس بهتر است در برنامهٔ واقعی n > 0 را وارسی کنی.
  4. تعداد عنصر. اندازهٔ کل آرایه (۱۶ بایت) تقسیم بر اندازهٔ یک عنصر (۴ بایت) = ۴. این کار باید در همان جایی انجام شود که آرایه تعریف شده است، نه داخل تابع دیگر.

تمرین ۳: خواندن عدد ۳۲ بیتی از بستهٔ سنسور

یک سنسور، دمای خود را به‌صورت عدد ۳۲ بیتی big-endian (بایت مهم اول) در یک بستهٔ ۶ بایتی می‌فرستد. عدد از ایندکس ۱ شروع می‌شود. می‌خواهی روی STM32 آن را بخوانی.

  1. پیش‌بینی: چرا *(uint32_t *)&frame[1] بد است؟ (دو دلیل: ناهم‌ترازی و ترتیب بایت‌ها.)
  2. حل: تابع read_be32(const uint8_t *p) را با شیفت بنویس که روی هر پردازنده‌ای درست کار کند.
  3. چالش: بایت اول بسته را 0x80 بگذار. با نسخهٔ بدون (uint32_t) cast و -fsanitize=undefined چه پیامی می‌گیری؟
راهنمایی

هر بایت را ابتدا به uint32_t تبدیل کن و بعد شیفت بده: ((uint32_t)p[0] << 24) | .... شیفت و OR بایت‌ها را در ترتیب درست کنار هم می‌گذارد، صرف‌نظر از little-endian بودن CPU.

چه باید ببینی؟ 
$ ./be32
value = 0x80000102

و با نسخهٔ بدون cast و بایت اول 0x80، UBSan می‌گوید: left shift of 128 by 24 places cannot be represented in type 'int'.

جواب کامل با توضیح 
#include <stdio.h>
#include <stdint.h>

static uint32_t read_be32(const uint8_t *p)
{
    return ((uint32_t)p[0] << 24) | ((uint32_t)p[1] << 16)
         | ((uint32_t)p[2] << 8)  |  (uint32_t)p[3];
}

int main(void)
{
    const uint8_t frame[6] = {0xFF, 0x80, 0x00, 0x01, 0x02, 0xFF};
    printf("value = 0x%08X\n", (unsigned)read_be32(&frame[1]));
    return 0;
}
  1. تابع. یک اشاره‌گر به بایت‌ها می‌گیرد. هیچ فرضی درباره‌ی هم‌ترازی آدرس ندارد.
  2. ساختن کلمه. هر بایت اول به uint32_t می‌رود (cast) و بعد به جای درست شیفت می‌خورد؛ p[0] بالاترین بایت. اگر cast نبود، p[0] << 24 در int علامت‌دار انجام می‌شد و برای 0x80 به بعد UB بود. همین خطا باعث می‌شود کد روزها درست کار کند و یک روز خراب شود.
  3. استفاده. بسته را با آدرس &frame[1] می‌دهیم که بایت‌هایش 0x80 0x00 0x01 0x02 است.
$ gcc -std=c11 -Wall -Wextra -o be32 be32.c

حرف مربی

تقریبا همه در این درس دو جا گیر می‌کنند. اول: «اما روی سیستم من که کار می‌کند!». UB یعنی «کار می‌کند تا روزی که نکند»: کامپایلر جدید، پرچم جدید یا کدِ کنارش عوض شود. دوم: «هشدار را بی‌خیال، چون کد اجرا می‌شود». هشدارهای -Wall -Wextra اغلب نشانهٔ UB هستند؛ بی‌توجهی به آن‌ها گران تمام می‌شود. روی MCU وضع بدتر است چون «کرش» اغلب اتفاق نمی‌افتد و باگ بی‌صدا می‌ماند. پس سه عادت: هشدار را جدی بگیر، با -O0 و -O2 هر دو بساز، و منطقت را روی PC با sanitizer آزمون کن.

خلاصه یک‌دقیقه‌ای

  • UB: استاندارد هیچ نتیجه‌ای تضمین نمی‌کند. کامپایلر فرض می‌کند رخ نمی‌دهد و کد را بر آن اساس بهینه می‌کند؛ پس -O0 و -O2 ممکن است جواب متفاوت بدهند.
  • مثال‌ها: سرریز علامت‌دار، خارج از آرایه، *NULL، متغیر مقداردهی‌نشده، شیفت زیاد، ناهم‌ترازی، aliasing، نوشتن در رشتهٔ ثابت، اشاره‌گر آویزان.
  • «مشخص‌نشده» (ترتیب ارزیابی) و «پیاده‌ساز-تعریف» (علامت char) کم‌خطرترند ولی کد را غیرقابل‌حمل می‌کنند.
  • تله‌های ARM/MCU: ارتقای صحیح (~a، x * x، hi << 24)، char بی‌علامت، sizeof پارامتر آرایه.
  • ماکرو بدون پرانتز، ; اضافه، break فراموش‌شده، dangling else: با آکولاد و پرانتز و هشدار.
  • ابزار: -Wall -Wextra در دو سطح بهینه‌سازی، -fsanitize=undefined,address روی PC، تست با gcc و clang.
