در دیباگ (درس ۶.۱) باگ را بعد از خراب‌شدن پیدا می‌کنی؛ ولی بهترین باگ، باگی است که هرگز اجرا نشود. کامپایلر و چند ابزار رایگان می‌توانند کدت را «بخوانند» و قبل از اینکه حتی برد را روشن کنی بگویند «این خط مشکوک است». در این درس یاد می‌گیری چطور آن‌ها را جدی کار بگیری، قانون‌نامه‌های معروف (MISRA، CERT و ده قانون ناسا) چه می‌گویند، و چطور کدی بنویسی که حتی ورودی بد هم آن را خراب نکند.

ایدهٔ اصلی: بازرس ساختمان قبل از افتتاح

ساختمانی را تصور کن که قرار است صدها نفر در آن زندگی کنند. سازنده «حس می‌کند» همه‌چیز درست است. ولی قبل از افتتاح، بازرس‌ها می‌آیند: یکی با متر و ترازو (خطاهای ساده)، یکی با نقشهٔ برق و لوله (خطاهای پنهان)، یکی با کتاب آیین‌نامه (قاعده‌های ساخت)، و آخر سر یک نفر با یک زلزلهٔ آزمایشی (تست واقعی). هیچ‌کدام تنها کافی نیست، اما هرکدام چیزی را می‌بیند که بقیه نمی‌بینند.

مثال از زندگی روزمره

خلبان‌ها قبل از هر پرواز «چک‌لیست» را از رو می‌خوانند، حتی اگر ده هزار ساعت پرواز کرده باشند. نه چون احمق‌اند؛ چون انسان خسته می‌شود و یک مورد را جا می‌اندازد. ابزارهای این درس همان چک‌لیست خودکارند: خسته نمی‌شوند و هر بار همهٔ موارد را نگاه می‌کنند.

چرا در میکروکنترلر این‌قدر مهم است؟ چون باگ روی دستگاهی که در دیوار نصب شده یا داخل یک بسته‌بندی است، شاید ماه‌ها بعد فقط یک‌بار ظاهر شود و هیچ‌کس هم printf جلوی چشمش نداشته باشد. پیدا کردن باگ قبل از اجرا ارزان‌ترین راه است.

قدم ۱: کامپایلر را به حرف بیاور

در درس‌های قبل همیشه با -Wall -Wextra کامپایل کردیم. این‌ها فقط بخشی از هشدارهای gcc را روشن می‌کنند (اسم «all» گول‌زننده است!). چند پرچم مهم دیگر برای کد embedded هست. اول جدولشان را ببین:

پرچمچه چیزی را می‌گیرد؟چرا در embedded مهم است؟
-Wconversionتبدیل نوع که ممکن است مقدار را ببُرد (مثل int به uint8_t)رجیسترها و بایت‌ها کوچک‌اند؛ برش بی‌صدای عدد یعنی باگ بی‌صدا
-Wshadowمتغیر محلی که اسمش را از یک متغیر بیرونی «قرض گرفته»فکر می‌کنی level سراسری را عوض می‌کنی، ولی یک نسخهٔ محلی را عوض کرده‌ای
-Wstrict-prototypesتابعی که با () نوشته شده، به‌جای (void)در C خالی‌بودن پرانتز یعنی «پارامترها را چک نکن»
-Wcast-alignتبدیل اشاره‌گر به نوعی که تراز بیشتری می‌خواهدبعضی هسته‌های ARM با دسترسی ناهم‌تراز HardFault می‌دهند (پایین‌تر ببین)
-Wswitch (در -Wall)switch روی enum که یک مقدار را فراموش کردهاگر حالت جدید به FSM اضافه کنی، کامپایلر یادت می‌اندازد کجاها را به‌روز کنی
-Wdouble-promotionfloat که بی‌صدا به double ارتقا می‌یابد (مثل printf یا ضرب در 2.0)Cortex-M4F فقط float را سخت‌افزاری حساب می‌کند؛ double نرم‌افزاری و کند است (درس ۴.۷)
-Wundefاستفاده از ماکرویی که هرگز تعریف نشده در #if (بی‌صدا صفر حساب می‌شود)غلط تایپی در نام ماکروی پیکربندی، یک قابلیت را بی‌خبر خاموش می‌کند (درس ۴.۱)
-Werrorهر هشدار را به خطا تبدیل می‌کندهشدارِ نادیده‌گرفته‌شده هیچ فایده‌ای ندارد؛ خطا را نمی‌شود نادیده گرفت

ببین کدی که با -Wall -Wextra هیچ صدایی ندارد، با این پرچم‌ها چه می‌گوید. این کد را ننویس و اجرا نکن؛ فقط بخوان و ببین چند مشکل در آن است:

#include <stdint.h>
#include <stdio.h>

static uint8_t level;

void set_level(int raw)
{
    level = raw * 2;            // int در uint8_t
}

int clamp(int value)
{
    int level = value;          // هم‌نام متغیر سراسری
    if (level > 100) {
        level = 100;
    }
    return level;
}

int read_sensor()               // بدون void
{
    return 42;
}

int main(void)
{
    set_level(read_sensor());
    printf("%d %d\n", level, clamp(250));
    return 0;
}
  1. متغیر سراسری کوچک. level فقط یک بایت است (۰ تا ۲۵۵). اندازهٔ کوچک، مثل رجیستر ۸ بیتی، دقیقا جایی است که برش عدد اتفاق می‌افتد.
  2. مشکل اول: برش بی‌صدا. raw * 2 از نوع int است (۳۲ بیت). گذاشتنش در یک بایت، اگر بزرگ‌تر از ۲۵۵ باشد بی‌هیچ صدایی بریده می‌شود. قانون درس ۲.۲: تبدیل به نوع کوچک‌تر، مقدار را «باقی‌مانده به ۲۵۶» می‌کند. مثلا ۳۰۰ می‌شود ۴۴.
  3. مشکل دوم: سایه‌زدن. در clamp یک level محلی ساخته‌ایم که level سراسری خط ۴ را «سایه» می‌کند. تا آخر تابع هر جا level بنویسی، منظورت نسخهٔ محلی است. اگر روزی کسی در این تابع بخواهد متغیر سراسری را عوض کند، بدون هشدار نسخهٔ محلی را عوض می‌کند. هم‌نام‌بودن دو چیز مثل دو همکار هم‌نام در یک دفتر است.
  4. مشکل سوم: پرانتز خالی. int read_sensor() در C یعنی «تعداد و نوع پارامترها اعلام نشده»، نه «بدون پارامتر». برای «بدون پارامتر» باید (void) بنویسی. با پرانتز خالی می‌توانی read_sensor(1, 2, 3) بنویسی و کامپایلر اعتراض نمی‌کند. (void) این در را می‌بندد.
  5. برنامهٔ اصلی. سنسور را می‌خواند، دو برابرش را در level می‌گذارد و چاپ می‌کند. روی کاغذ درست کار می‌کند (۴۲ × ۲ = ۸۴)، ولی سه سوراخ بالا را دارد.
$ gcc -std=c11 -Wall -Wextra -o risky risky.c
(هیچ خروجی. کامپایلر راضی است.)

حالا همان فایل با پرچم‌های سخت‌گیرانه‌تر:

$ gcc -std=c11 -Wall -Wextra -Wconversion -Wshadow -Wstrict-prototypes -Wcast-align -Werror -o risky risky.c
risky.c: In function 'set_level':
risky.c:8:13: error: conversion from 'int' to 'uint8_t' {aka 'unsigned char'} may change value [-Werror=conversion]
risky.c: In function 'clamp':
risky.c:13:9: error: declaration of 'level' shadows a global declaration [-Werror=shadow]
risky.c: At top level:
risky.c:20:5: error: function declaration isn't a prototype [-Werror=strict-prototypes]

هر سه مشکل پیدا شد. نگاه کن که -Werror اسم هر هشدار را آخر خط گذاشته (مثل [-Werror=shadow]). اگر بخواهی یک هشدار خاص را موقتا خاموش کنی، از همین اسم استفاده می‌کنی: -Wno-shadow. ولی اول سعی کن کد را درست کنی، نه ساکت کنی.

نسخهٔ اصلاح‌شده

حالا همان برنامه، بدون هیچ‌کدام از سه مشکل. این را با همان پرچم‌های سخت‌گیر و -Werror هم می‌سازیم:

#include <stdint.h>
#include <stdio.h>

static uint8_t level;

/* ۰ = موفق، -۱ = ورودی خارج از محدوده */
static int set_level(int raw)
{
    if ((raw < 0) || (raw > 127)) {
        return -1;                      // جلوی سرریز را همین‌جا می‌گیریم
    }
    level = (uint8_t)(raw * 2);         // حالا می‌دانیم جا می‌شود
    return 0;
}

static int clamp(int value)
{
    int limited = value;                // اسم تازه؛ level را سایه نمی‌زند
    if (limited > 100) {
        limited = 100;
    }
    return limited;
}

static int read_sensor(void)            // void = بدون پارامتر
{
    return 42;
}

int main(void)
{
    if (set_level(read_sensor()) != 0) {
        printf("out of range\n");
        return 1;
    }
    printf("%d %d\n", level, clamp(250));
    return 0;
}
  1. تابعی که قبل از کار، ورودی را می‌سنجد. اگر raw بیرون از ۰ تا ۱۲۷ باشد، -1 برمی‌گرداند و level را دست نمی‌زند. وقتی از قبل مطمئنی raw * 2 بین ۰ تا ۲۵۴ است، «برش» تبدیل به یک cast آگاهانه می‌شود، نه یک اتفاق ناخواسته.
  2. cast صریح. (uint8_t) به کامپایلر می‌گوید «می‌دانم چه می‌کنم». هشدار -Wconversion با همین cast ساکت می‌شود. cast فقط وقتی امن است که قبلش ثابت کرده باشی مقدار جا می‌شود (خطوط ۹ تا ۱۱). cast بدون آن، فقط هشدار را دفن می‌کند نه باگ را.
  3. نام غیرتکراری. متغیر محلی limited شد و دیگر با level قاطی نمی‌شود.
  4. (void) در تعریف. حالا اگر کسی read_sensor(5) بنویسد، کامپایلر خطا می‌دهد.
  5. مصرف‌کننده کد وضعیت را چک می‌کند. نتیجهٔ set_level نادیده گرفته نمی‌شود. تابعی که خطا برمی‌گرداند، اگر کسی نگاهش نکند بی‌فایده است. بخش «برنامه‌نویسی دفاعی» پایین‌تر همین را ادامه می‌دهد.
$ gcc -std=c11 -Wall -Wextra -Wconversion -Wshadow -Wstrict-prototypes -Wcast-align -Werror -o safe_level safe_level.c
$ ./safe_level
84 100
-Werror را کجا بگذاریم؟

-Werror برای کد خودت عالی است. ولی کتابخانه‌های بیرونی (مثل هدرهای HAL شرکت ST یا ESP-IDF) هشدار زیاد دارند و مال تو نیستند که درستشان کنی. راه رایج: مسیر آن‌ها را با -isystem به‌جای -I بده؛ gcc هشدارهای فایل‌های «سیستمی» را نشان نمی‌دهد. و در CMake ESP-IDF، پرچم را فقط برای کامپوننت خودت بگذار (پایین‌تر).

چرا -Wconversion؟ ببین چه می‌شود

با این ابزارک نوع را روی uint8_t بگذار و عدد را از ۲۵۵ بالاتر ببر. همان چیزی را می‌بینی که خط ۸ risky.c بی‌صدا انجام می‌داد:

پرچمی که فقط روی ARM حرف می‌زند

-Wcast-align جالب است: روی رایانهٔ x86 تقریبا هرگز چیزی نمی‌گوید، ولی روی ARM (هم Cortex-M0 و هم Cortex-M4 با arm-none-eabi-gcc) می‌گوید؛ gcc بر اساس «تراز اجباری» هدف تصمیم می‌گیرد. کد زیر یک «بایت‌آرایه» را به «کلمهٔ ۳۲ بیتی» تبدیل می‌کند (الگوی رایج در پارس‌کردن بسته‌های شبکه):

#include <stdint.h>

uint32_t first_word(uint8_t *p)
{
    return *(uint32_t *)p;      // p ممکن است آدرس فرد باشد!
}
  1. تفسیر بایت‌ها به‌عنوان uint32_t. اگر p مثلا 0x20000001 باشد، این چهار بایت روی مرز چهار بایتی نیستند. هستهٔ Cortex-M0 و M0+ خواندن ناهم‌تراز را با HardFault پاسخ می‌دهد. Cortex-M4 برای بعضی دستورها تحمل می‌کند ولی برای بعضی نه؛ و آن‌ها که تحمل می‌کنند کندترند. راه امن: memcpy بایت‌ها را به یک uint32_t محلی کپی کن (درس ۳.۴).
$ gcc -Wcast-align -c cast_align.c
(روی x86: ساکت)
$ arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -Wcast-align -c cast_align.c
cast_align.c: In function 'first_word':
cast_align.c:5:13: warning: cast increases required alignment of target type [-Wcast-align]

(اگر روی PC هم می‌خواهی این هشدار را ببینی، -Wcast-align=strict را بگذار: در حالت strict، gcc حتی روی x86 هشدار می‌دهد.) این یک مثال خوب است از اینکه چرا «روی PC کار می‌کند» دلیل درستی نیست. همان پرچم را حتما روی کامپایلر خود میکروکنترلر هم روشن کن.

هدیهٔ رایگان: switch کامل

یادت هست ماشین حالت (درس ۴.۶) با enum و switch نوشته شد؟ اگر یک مقدار جدید به enum اضافه کنی و فراموش کنی در switch جایش را بدهی، -Wall (پرچم -Wswitch) تو را می‌گیرد. این هشدار فقط وقتی کار می‌کند که default نگذاشته باشی. (چرا؟ چون default یعنی «هر چه هست را گرفته‌ام» و کامپایلر دیگر شکایت نمی‌کند.)

#include <stdio.h>

typedef enum { MODE_IDLE, MODE_RUN, MODE_SLEEP } run_mode_t;

static const char *name(run_mode_t m)
{
    switch (m) {
    case MODE_IDLE: return "idle";
    case MODE_RUN:  return "run";
    }
    return "?";
}

int main(void)
{
    printf("%s\n", name(MODE_SLEEP));
    return 0;
}
  1. سه حالت. MODE_SLEEP تازه اضافه شده است.
  2. switch بدون default و بدون MODE_SLEEP. برنامه‌نویس یادش رفته این حالت را بنویسد. اگر default داشتیم، این باگ ساکت می‌ماند و برای MODE_SLEEP همیشه یک نتیجهٔ کلی می‌گرفتیم. سبک بی‌default روی enum یعنی «کامپایلر را نگهبان کن».
  3. مقدار پیش‌فرض بعد از switch. برای وقتی که مقدار خارج از فهرست باشد (مثلا رجیستر خراب).
enum_switch.c: In function 'name':
enum_switch.c:7:5: error: enumeration value 'MODE_SLEEP' not handled in switch [-Werror=switch]
MISRA برعکس می‌گوید

قاعدهٔ MISRA این است که هر switch یک default داشته باشد. دو فلسفه با هم درگیر می‌شوند: «کامپایلر نگهبان باشد» یا «هیچ مسیری بدون پاسخ نماند». راه میانه که بسیاری از تیم‌ها می‌روند: default بگذار ولی ابزار دیگری (مثل -Wswitch-enum یا cppcheck) را برای کامل‌بودن حالت‌ها فعال نگه دار. مهم این است که تیم تصمیم بگیرد و یکنواخت رفتار کند.

قدم ۲: تحلیل ایستا

تحلیل ایستا یعنی خواندن کد بدون اجرایش. کامپایلر هم در حد خودش این کار را می‌کند، ولی ابزارهای تخصصی عمیق‌تر می‌روند: مسیرهای ممکن اجرا را در ذهنشان می‌سازند (اگر if درست باشد چه می‌شود؟ اگر malloc شکست بخورد؟) و دنبال باگ می‌گردند. سه ابزار را امتحان می‌کنیم: cppcheck، clang-tidy و تحلیلگر داخلی gcc.

مثال از زندگی روزمره

غلط‌گیر املایی Word را در نظر بگیر: زیر واژه‌های مشکوک خط قرمز می‌کشد. گاهی درست است، گاهی نه («نام خاص است!»). ابزارهای تحلیل ایستا هم همین‌طورند: پیشنهاد می‌دهند، و تصمیم نهایی با توست. پیشنهاد اشتباهشان را هشدار کاذب (false positive) می‌نامند.

فایلی پر از باگ

این فایل چهار باگ دارد. مهم: این را اجرا نکن، فقط تحلیلش کن (اجرایش رفتار تعریف‌نشده دارد). ببین خودت چند تا را پیدا می‌کنی:

#include <stdio.h>
#include <stdlib.h>
#include <string.h>

#define N 8

static int table[N];

int fill(int count)
{
    for (int i = 0; i <= N; i++) {       // یک خانه بیشتر
        table[i] = i * count;
    }
    return table[0];
}

char *make_name(const char *src)
{
    char *buf = malloc(8);
    strcpy(buf, src);                   // بدون بررسی اندازه و NULL
    return buf;
}

int average(const int *v, int n)
{
    int sum;                            // مقدار اولیه ندارد
    for (int i = 0; i < n; i++) {
        sum += v[i];
    }
    return sum / n;
}

void cleanup(void)
{
    char *p = malloc(16);
    if (p == NULL) {
        return;
    }
    p[0] = 'x';                         // free فراموش شده
}

int main(void)
{
    int v[3] = { 1, 2, 3 };
    printf("%d\n", average(v, 3));
    printf("%d\n", fill(2));
    free(make_name("abc"));
    cleanup();
    return 0;
}
  1. آرایهٔ ۸ خانه‌ای. خانه‌ها از ۰ تا ۷ شماره‌گذاری می‌شوند؛ خانهٔ ۸ وجود ندارد.
  2. باگ ۱: یکی زیادی. شرط i <= N یعنی i تا ۸ می‌رود و table[8] بیرون آرایه را می‌نویسد. این معروف‌ترین باگ C است (off-by-one). اگر آن خانه به یک رجیستر یا متغیر دیگر بخورد، دیباگ‌کردنش جهنم است.
  3. باگ ۲: کپی بی‌کنترل. malloc ممکن است NULL برگرداند و strcpy نمی‌داند طول src چقدر است (بیشتر از ۸ بایت؟). در MCU که حافظه کم است، malloc بیشتر از PC شکست می‌خورد (درس ۴.۴).
  4. باگ ۳: متغیر بدون مقدار. sum بدون مقدار اولیه شروع می‌شود و به آشغال اضافه می‌شود. تازه اگر n صفر باشد، sum / n تقسیم بر صفر است. این همان «مقدار آشغال» درس ۲.۱ است، در لباس یک حلقه.
  5. باگ ۴: نشت حافظه. حافظه گرفته می‌شود ولی هیچ‌وقت free نمی‌شود. در دستگاهی که ماه‌ها روشن می‌ماند، هر بار نشت کوچک هم‌جمع می‌شود تا حافظه تمام شود.
  6. main. همهٔ توابع را صدا می‌زند تا «کد مرده» نباشند.

ابزار اول: خود gcc، ولی با بهینه‌سازی

کامپایلر برای فهمیدن «این متغیر مقدار ندارد» باید جریان داده را تحلیل کند، و این تحلیل فقط وقتی انجام می‌شود که بهینه‌سازی روشن باشد. یک نکتهٔ کم‌دانسته:

ابزار سوم: clang-tidy

نسخه‌ها: خروجی‌های این درس با gcc 13.3، cppcheck 2.13.0 و clang-tidy 18.1.3 گرفته شده؛ نام و متن پیام بررسی‌ها (مثلاً legacyUninitvar یا cert-err33-c) بین نسخه‌ها فرق می‌کند. فایل‌های buggy.c، tidy_demo.c و cast_align.c در پوشهٔ code/6-3 هست و کامپایل‌شدنشان وارسی می‌شود؛ ولی خروجی خودِ cppcheck/clang-tidy را فقط دستی با همان نسخه‌ها تطبیق داده‌ام.

clang-tidy از کامپایلر clang استفاده می‌کند؛ پس بعد از فایل، دو خط تیره -- و بعد پرچم‌های کامپایل را می‌دهی. با --checks فهرست بررسی‌ها را انتخاب می‌کنی (* یعنی «همهٔ آن خانواده»؛ - جلوی اسم یعنی «این یکی را نه»). ما سه خانواده را روشن کردیم: clang-analyzer-* (مسیرشناسی عمیق)، bugprone-* (الگوهای باگ‌خیز) و cert-* (قواعد CERT).

(خروجی کامل پر از خط‌های «note» است که مسیر رسیدن به باگ را قدم‌به‌قدم می‌گوید؛ اینجا فقط خط‌های warning را نگه داشتیم. خودت یک بار کامل اجرا کن؛ آموزنده است.) این بار strcpy پیدا شد، ولی اندیس ۸ آرایه را نگرفت.

ابزار چهارم: تحلیلگر داخلی gcc

نسخه‌های تازهٔ gcc (از ۱۰ به بعد) گزینهٔ -fanalyzer دارند. برای C کار می‌کند و مثل clang-analyzer مسیرها را دنبال می‌کند. روی همین فایل: -fanalyzer نشت (-Wanalyzer-malloc-leak)، استفاده از مقدار بی‌مقدار (-Wanalyzer-use-of-uninitialized-value) و «ممکن است malloc صفر برگرداند» (-Wanalyzer-possible-null-argument) را گفت؛ ولی اندیس ۸ را نه. اجراها با gcc 13.3 بود؛ در نسخهٔ دیگر ممکن است فرق کند. (روی C این تحلیلگر هنوز نسبت به clang-analyzer جوان‌تر است.)

یک مثال دیگر از clang-tidy: عادت‌های بد

این فایل کوچک‌تر است و روی «سبک» و «قاعده‌های CERT» تمرکز دارد. یک پیش‌بینی بکن: چند مشکل می‌بینی؟

#include <stdint.h>
#include <stdio.h>
#include <string.h>

#define SQUARE(x) x * x
#define TIMEOUT_MS 100

static uint8_t buf[16];

int scale(int a)
{
    return SQUARE(a + 1);
}

void copy_in(const uint8_t *src, size_t n)
{
    memcpy(buf, src, sizeof(buf));
    if (n > sizeof(buf))
        n = sizeof(buf);
    for (size_t i = 0; i < n; i++)
        buf[i] = src[i];
}

int main(void)
{
    uint8_t data[4] = { 1, 2, 3, 4 };
    int32_t big = 70000;
    uint16_t small = big;
    copy_in(data, sizeof(data));
    printf("%d %u\n", scale(2), small);
    fputs("done\n", stdout);
    return TIMEOUT_MS;
}
  1. ماکروی بدون پرانتز. SQUARE(a + 1) به a + 1 * a + 1 باز می‌شود، نه (a+1)*(a+1). پیش‌پردازنده فقط متن را جایگزین می‌کند و به اولویت عملگرها کاری ندارد (درس ۴.۱). برای a = 2 نتیجه ۵ می‌شود، نه ۹.
  2. کپی با اندازهٔ بافر مقصد. خط ۱۷ همیشه ۱۶ بایت را از src می‌خواند، حتی وقتی src فقط ۴ بایت است. خط‌های ۱۸ تا ۲۱ همان کار را درست‌تر (با n) انجام می‌دهند. خواندن ۱۶ بایت از آرایهٔ ۴ بایتی یعنی خواندن بیرون از آرایه (رفتار تعریف‌نشده، درس ۶.۲).
  3. if و for بدون آکولاد. کد درست کار می‌کند، ولی اگر بعدا کسی یک خط به بدنه اضافه کند، فقط خط اول داخل آن می‌ماند. (معروف به باگ «goto fail» اپل.)
  4. تبدیل ۳۲ به ۱۶ بیت. عدد ۷۰۰۰۰ در uint16_t نمی‌گنجد و می‌شود ۴۴۶۴.
  5. مقدار برگشتی نادیده. fputs خطا را با مقدار برگشتی خبر می‌دهد و ما نگاهش نمی‌کنیم.

درس صادقانه: ابزار همه‌چیز را نمی‌گیرد

دو ابزار همراه هم روی این فایل هیچ هشداری دربارهٔ ماکروی بدون پرانتز ندادند و خواندن ۱۶ بایت از آرایهٔ ۴ بایتی را هم (با پرچم‌هایی که ما گذاشتیم) نگرفتند. این‌ها را فقط یک انسان در بازبینی می‌بیند. نتیجه: تحلیل ایستا جای فکر کردن را نمی‌گیرد؛ فقط کار کسل‌کننده را از دوشت برمی‌دارد. و «گزارش تمیز» یعنی «این ابزار چیزی ندید»، نه «باگ ندارد».

هشدار کاذب: با آن چه کنیم؟

گاهی ابزار اشتباه می‌کند، یا تو آگاهانه کاری می‌کنی که ابزار دوست ندارد. دو قانون:

  1. اول کد را درست کن. اگر می‌شود کد را جوری نوشت که هشدار نیاید (و خواناتر هم بشود)، همین را بکن.
  2. اگر واقعا هشدار کاذب است، فقط همان یک خط را ساکت کن و دلیلش را کنارش بنویس. ساکت‌کردن کل ابزار یا کل فایل، یعنی خودت را کور کردن.
/* نیازمند: cppcheck --inline-suppr */
int main(void)
{
    // cppcheck-suppress unreadVariable   // این متغیر برای دیباگر است
    int marker = 5;
    fputs("hi\n", stdout);   // NOLINT(cert-err33-c)  // خروجی دیباگ است؛ خطایش مهم نیست
    return 0;
}
  1. تنظیم لازم. کامنت‌های cppcheck-suppress فقط با گزینهٔ --inline-suppr فعال می‌شوند.
  2. ساکت‌کردن cppcheck. کامنت را قبل از خط می‌گذاری و شناسهٔ هشدار (unreadVariable) را می‌نویسی. فقط همان هشدار روی همان خط ساکت می‌شود.
  3. ساکت‌کردن clang-tidy. NOLINT(نام‌بررسی) در انتهای همان خط. اگر نام را ننویسی همهٔ بررسی‌ها ساکت می‌شوند؛ نام را بنویس. کامنت دلیل دار به بازبین بعدی (که شش ماه بعد خودت هستی) می‌گوید ابزار را عمدی ساکت کرده‌ای.

و یک فایل تنظیمات برای اینکه هر بار پرچم‌ها را تایپ نکنی. clang-tidy فایل .clang-tidy را از پوشهٔ پروژه می‌خواند:

Checks: 'clang-analyzer-*,bugprone-*,cert-*,readability-braces-around-statements,-bugprone-easily-swappable-parameters'
WarningsAsErrors: 'clang-analyzer-*,cert-*'
HeaderFilterRegex: '^(src|include)/'
  1. چه بررسی‌هایی. همان فهرستی که در ترمینال می‌دادیم.
  2. کدام‌ها خطا باشند. نتیجهٔ این دو خانواده، خطا حساب می‌شود و ساخت را قرمز می‌کند.
  3. فقط کد خودت. هدرهای داخل src و include بررسی می‌شوند؛ هدرهای HAL و کتابخانه‌ها نه.

قدم ۳: قانون‌نامه‌ها

ابزار می‌گوید «این خط مشکوک است». ولی «چه چیزی مجاز است و چه چیزی نه» را یک استاندارد کدنویسی تعیین می‌کند: فهرستی از قاعده‌ها که تیم قبول کرده رعایت کند. مثل آیین‌نامهٔ رانندگی: لازم نیست هر راننده از اول اختراعش کند.

سه قانون‌نامهٔ معروف را می‌شناسی (با زبان خودمان می‌گوییم؛ متن رسمی MISRA حق نشر دارد و باید از خودِ سازمان تهیه شود):

MISRA C

MISRA C را انجمنی از صنعت خودرو (در بریتانیا) نوشته و امروز در خودرو، هوافضا، پزشکی و راه‌آهن رایج است. نسخهٔ بسیار پرکاربرد آن «MISRA C:2012» است؛ ویرایش‌های تازه‌تر (MISRA C:2023 و ویرایش جدیدتر MISRA C:2025) هم منتشر شده‌اند و تیم‌ها کم‌کم به آن‌ها می‌روند. به سایت رسمی MISRA ببین کدام نسخه برای پروژهٔ تو لازم است. ایده‌اش: از قسمت‌های خطرناک و مبهم C دوری کن تا کد قابل‌پیش‌بینی بماند. اجزای آن:

  • دستورالعمل (Directive): کلی و گاهی نیازمند قضاوت انسان (مثل «کد را باید ردیابی کرد»).
  • قاعده (Rule): دقیق‌تر، و معمولا یک ابزار می‌تواند خودکار بررسی‌اش کند.
  • هر مورد یکی از سه دسته را دارد. دسته‌ها در شکل پایین.
  • انحراف (deviation): اگر مجبوری از یک قاعدهٔ «لازم» تخطی کنی، باید با دلیل و مستند انجامش بدهی (ننوشته و پنهانی نه).

چند نمونه از «روح» قاعده‌ها، با کلمات خودمان (شمارهٔ دقیق و متن رسمی را در سند خودِ MISRA ببین؛ شماره‌ها در نسخه‌های مختلف ممکن است فرق کنند):

ده قانون ناسا

در سال ۲۰۰۶ مهندس Gerard Holzmann از آزمایشگاه «نرم‌افزار قابل‌اعتماد» در JPL ناسا مقاله‌ای کوتاه با نام The Power of 10: Rules for Developing Safety-Critical Code منتشر کرد. ایده: به‌جای صدها قاعده، ده قاعده که همهٔ برنامه‌نویس‌ها بتوانند به‌خاطر بسپارند و ابزار بتواند کنترلشان کند. این‌ها را «ده قانون» می‌نامند (Power of 10). این فهرست به قلم خودم (خلاصهٔ دقیق نه ترجمهٔ کلمه‌به‌کلمه):

#قاعده (خلاصه)چرا؟در MCU یعنی
۱ساختار کنترلی ساده: goto، setjmp/longjmp و بازگشت (مستقیم یا غیرمستقیم) ممنوعگراف اجرا ساده می‌ماند و ابزار می‌تواند تحلیلش کندپشتهٔ قابل‌محاسبه؛ بدون HardFault ناشی از سرریز پشته

قانون ۹ و اشاره‌گر تابع: تناقض؟

در درس‌های قبل (مثلا ۴.۳ و بخش callback) اشاره‌گر تابع را خودمان به‌کار بردیم. قانون ۹ ناسا آن را ممنوع می‌کند، چون تحلیل‌گر نمی‌تواند بفهمد کدام تابع صدا زده می‌شود. حقیقت این است که ناسا نرم‌افزار پرواز می‌نویسد و ما اکثرا برنامهٔ کاربردی. «قانون» برای موقعیت است، نه برای همه. مهم این است که هرجا از قانون تخطی می‌کنی، آگاهانه و با دلیل باشد (در درس ۶.۴ از همین اشاره‌گر تابع برای mock استفاده می‌کنیم).

ببین قانون ۲ در دنیای MCU چطور به‌نظر می‌رسد. این حلقه‌ای است که بسیاری از مبتدی‌ها می‌نویسند:

#define UART_SR   (*(volatile uint32_t *)0x40004400U)   /* نمونه */
#define TXE_BIT   (1U << 7)

void uart_send(uint8_t byte)
{
    while ((UART_SR & TXE_BIT) == 0U) {
        /* منتظر آماده‌شدن */
    }
    /* ... نوشتن byte در رجیستر داده ... */
}
  1. رجیستر و بیت. آدرس نمونه (شکل کار درس ۳.۶)؛ بیت ۷ در رجیستر وضعیت معمولا «فرستنده خالی است» (TXE) است.
  2. انتظار بی‌سقف. اگر سخت‌افزار خراب باشد یا کلاک UART روشن نشده باشد، بیت هرگز یک نمی‌شود و این حلقه تا ابد می‌چرخد. قانون ۲ می‌گوید حلقه سقف ثابت داشته باشد. در تمرین ۳ همین را درست می‌کنی.

برنامه‌نویسی دفاعی

برنامه‌نویسی دفاعی یعنی فرض کن هر ورودی می‌تواند بد باشد: پارامتر از یک تابع دیگر، بایت رسیده از UART، مقدار خوانده‌شده از سنسور. مثل رانندهٔ دفاعی که فرض می‌کند بقیهٔ ماشین‌ها ممکن است اشتباه کنند.

این برنامه یک متن مثل "42" را به عدد ۰ تا ۱۰۰ (درصد) تبدیل می‌کند. ورودی‌هایی مثل NULL، رشتهٔ خالی، حرف غلط و عدد بزرگ را هم می‌شناسد. توجه کن که از هر سه ایدهٔ بالا استفاده کرده است:

#include <assert.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>

#define MAX_DIGITS 3U

typedef enum {
    PARSE_OK = 0,
    PARSE_NULL,
    PARSE_EMPTY,
    PARSE_BAD_CHAR,
    PARSE_RANGE
} parse_status_t;

static const char *status_name(parse_status_t s)
{
    switch (s) {
    case PARSE_OK:       return "OK";
    case PARSE_NULL:     return "NULL";
    case PARSE_EMPTY:    return "EMPTY";
    case PARSE_BAD_CHAR: return "BAD_CHAR";
    case PARSE_RANGE:    return "RANGE";
    default:             return "?";
    }
}

/* متن «۰ تا ۱۰۰» را به عدد تبدیل می‌کند؛ در هر حالت خطا *out دست‌نخورده می‌ماند */
static parse_status_t parse_percent(const char *text, uint8_t *out)
{
    if ((text == NULL) || (out == NULL)) {
        return PARSE_NULL;
    }
    if (text[0] == '\0') {
        return PARSE_EMPTY;
    }

    uint32_t value = 0U;
    size_t i = 0U;
    while (text[i] != '\0') {
        if (i >= MAX_DIGITS) {
            return PARSE_RANGE;             /* خیلی بلند است */
        }
        if ((text[i] < '0') || (text[i] > '9')) {
            return PARSE_BAD_CHAR;
        }
        value = (value * 10U) + (uint32_t)(text[i] - '0');
        i++;
    }
    assert(value <= 999U);                  /* ناوردا: حداکثر سه رقم */
    if (value > 100U) {
        return PARSE_RANGE;
    }
    *out = (uint8_t)value;
    return PARSE_OK;
}

int main(void)
{
    const char *inputs[] = { "42", "100", "101", "", "4x2", "1234", NULL };
    uint8_t pct = 0U;

    for (size_t k = 0U; k < (sizeof(inputs) / sizeof(inputs[0])); k++) {
        parse_status_t st = parse_percent(inputs[k], &pct);
        printf("%-6s -> %-8s (pct=%u)\n",
               (inputs[k] != NULL) ? inputs[k] : "(null)", status_name(st), (unsigned)pct);
    }
    return 0;
}
  1. سقف ثابت. بیش از سه رقم را اصلا قبول نمی‌کنیم. هم اندازهٔ «طولانی‌ترین ورودی» را مشخص می‌کند، هم مانع سرریز value می‌شود؛ ۹۹۹ بسیار کمتر از ۳۲ بیت است.
  2. وضعیت‌های صریح. به‌جای -1 و -2 مرموز، هر خطا یک اسم دارد. قانون ۷ ناسا: خطا باید قابل‌تشخیص و قابل‌چک باشد. اسم‌ها به کد خودتوضیح‌گر می‌دهند.
  3. تبدیل وضعیت به رشته، با switch کامل. همهٔ مقدارها را دارد و یک default (قاعدهٔ MISRA).
  4. قرارداد در کامنت. «در حالت خطا *out دست‌نخورده می‌ماند». مصرف‌کننده می‌تواند روی این قول حساب کند.
  5. دروازه. اشاره‌گر NULL و رشتهٔ خالی، قبل از هر کاری رد می‌شوند. این‌ها همان EXP34-C (خواندن NULL) هستند. یک تابع که مطمئن نیست تماس‌گیرنده درست می‌فرستد، اول می‌سنجد.
  6. حلقه با سقف. حلقه از روی رشته می‌رود، ولی خط ۴۱ آن را به سه رقم محدود می‌کند. رشتهٔ بی‌پایان هم بی‌گمان تمام می‌شود. قانون ۲ ناسا: حلقه‌ای که ابزار بتواند ثابت کند تمام می‌شود.
  7. رقم‌بودن را بسنج. هر کاراکتر باید بین '0' و '9' باشد؛ وگرنه PARSE_BAD_CHAR.
  8. تبدیل رقم به عدد. کاراکتر '7' عدد ۵۵ (در ASCII) است؛ با کم‌کردن '0' می‌شود ۷. cast به uint32_t صریح است تا -Wconversion ساکت باشد. در بازهٔ '0'..'9' نتیجه همیشه ۰ تا ۹ است، پس cast بی‌خطر است (چون خط ۴۴ آن را تضمین کرده).
  9. assert برای فرض داخلی. اگر آخر حلقه value بیشتر از ۹۹۹ باشد، منطق خود ما خراب است. فرق مهم: ورودی بد با کد وضعیت رسیدگی می‌شود (چون پیش می‌آید)، ولی فرض‌های داخلی با assert (چون نباید هرگز پیش بیاید و اگر آمد یعنی باگ داریم).
  10. تنها در موفقیت می‌نویسیم. بعد از بررسی نهایی، مقدار در *out می‌رود.
  11. آزمایش. هفت ورودی مختلف، از جمله رشتهٔ خالی، حرف و NULL. توجه کن که pct پس از اولین موفقیت (۱۰۰) تا آخر همان می‌ماند؛ یعنی خطاها به آن دست نزدند.
$ gcc -std=c11 -Wall -Wextra -Wconversion -Wshadow -Wstrict-prototypes -Wcast-align -Werror -o parse parse.c
$ ./parse
42     -> OK       (pct=42)
100    -> OK       (pct=100)
101    -> RANGE    (pct=100)
       -> EMPTY    (pct=100)
4x2    -> BAD_CHAR (pct=100)
1234   -> RANGE    (pct=100)
(null) -> NULL     (pct=100)
assert در محصول نهایی؟

ماکروی assert اگر NDEBUG تعریف شده باشد (ساخت release)، کاملا حذف می‌شود. یعنی هرچه داخل آن بنویسی (مثلا assert(x++ > 0)) دیگر اجرا نمی‌شود؛ پس هیچ‌وقت عارضهٔ جانبی داخل assert نگذار. در MCU هم assert استاندارد به printf و abort تکیه دارد که شاید نداشته باشی؛ اغلب تیم‌ها یک ماکروی ASSERT اختصاصی می‌نویسند که در خطا، مثلا LED را روشن کرده و منتظر watchdog می‌ماند (درس ۶.۱).

const-correctness: قول به تماس‌گیرنده

به این عادت const-correctness می‌گویند. یادت هست const قفل است. در پارامتر اشاره‌گر، const char *text به تماس‌گیرنده قول می‌دهد که «من فقط می‌خوانم». دو فایده: اگر اشتباهی بنویسی text[0] = 'x'، کامپایلر خطا می‌دهد؛ و می‌توانی رشتهٔ ثابت (که در Flash است) را به تابع بدهی. قاعده: هرچه را تغییر نمی‌دهی، const کن؛ حتی cppcheck در خروجی بالا پیشنهاد const برای v داد.

دو فایل تنظیم برای تیم

یک نکتهٔ عملی: هرچه ابزار به‌صورت خودکار و در هر بار ساخت اجرا شود، بیشتر فایده دارد. در درس بعد (۶.۴) همین‌ها را در CI می‌گذاریم. اینجا دو فایل کوچک:

جر و بحث دربارهٔ جای آکولاد یا تعداد فاصله، اتلاف وقت است. clang-format کد را طبق یک فایل تنظیمات خودکار مرتب می‌کند و بحث را می‌بندد:

پرچم‌ها در پروژهٔ واقعی

روی STM32 با Makefile، پرچم‌ها را در CFLAGS می‌گذاری. روی ESP32 با ESP-IDF، پرچم را برای کامپوننت خودت در CMakeLists.txt می‌افزایی (نه برای کل پروژه، که کد ESP-IDF هشدار می‌دهد). ساختار فایل و نام‌ها مطابق ESP-IDF v5.x است؛ ولی جزئیات دقیقش را در راهنمای رسمی Espressif ببین.

# سخت‌گیر برای کد خودمان
WARN = -Wall -Wextra -Wconversion -Wshadow -Wstrict-prototypes -Wcast-align -Werror
# HAL شرکت سازنده: با -isystem تا هشدارهایش دیده نشود
CFLAGS = -std=c11 $(WARN) -isystem vendor/hal/include -Iinclude
  1. یک متغیر برای هشدارها. جای واحد برای تغییر؛ CI هم از همین استفاده می‌کند.
  2. -isystem برای کد دیگران. هدرهای آن پوشه «سیستمی» حساب می‌شوند و gcc هشدارهایشان را نشان نمی‌دهد. -Iinclude برای هدرهای خودت است که هشدارشان دیده می‌شود.
idf_component_register(SRCS "sensor.c" "main.c"
                       INCLUDE_DIRS ".")

target_compile_options(${COMPONENT_LIB} PRIVATE
    -Wconversion -Wshadow -Wstrict-prototypes)
  1. ثبت کامپوننت. فایل‌های منبع و پوشهٔ هدر.
  2. پرچم فقط برای این کامپوننت. PRIVATE یعنی فقط همین کامپوننت با این پرچم‌ها ساخته می‌شود. -Werror را وقتی اضافه کن که کدت تمیز شد.

چک‌لیست بازبینی کد

وقتی دو نفر یک کد را نگاه می‌کنند، باگ‌هایی را می‌بینند که ابزار نمی‌بیند (مثل ماکروی SQUARE بالا). بازبینی (code review) بدون چک‌لیست، به سلیقه می‌رسد؛ با چک‌لیست، به عادت. این را در تیم‌ات به‌کار ببر:

بخشبپرس
ورودی و خروجیهر پارامتر اشاره‌گر NULL یا خارج از محدوده بررسی شده؟ مقدار برگشتی چک می‌شود؟
حلقه‌هاسقف تکرار دارند؟ انتظار سخت‌افزار timeout دارد؟ شرط <= و < درست انتخاب شده؟
نوع‌هااز stdint.h استفاده شده؟ تبدیل نوع صریح و پس از بررسی محدوده است؟ مخلوط علامت‌دار/بی‌علامت نیست؟
حافظههیچ malloc بعد از راه‌اندازی نیست؟ آرایه‌ها اندازهٔ ثابت دارند؟ عمق پشته کنترل شده؟
هم‌زمانیمتغیر مشترک با ISR volatile است؟ دسترسی چندبایتی به دادهٔ مشترک، بخش بحرانی دارد؟

در STM32 و ESP32 یعنی چه؟

  • همان ابزارها روی هر دو. پرچم‌های gcc برای arm-none-eabi-gcc (STM32) و کامپایلر Xtensa/RISC-V ESP-IDF یکی هستند. همان‌طور که دیدی، برخی (مثل -Wcast-align) فقط روی کامپایلر مقصد معنی می‌دهند.
  • کد سخت‌افزاری و تحلیلگر. ابزارهای PC معمولا volatile uint32_t * با آدرس ثابت را می‌شناسند، ولی ممکن است در هدرهای ST یا ESP-IDF (ماکرو-سنگین) هشدار کاذب بدهند. برای همین HeaderFilterRegex و -isystem را داشتیم.
  • MISRA در دنیای واقعی. اگر شرکت‌ت خودرو یا پزشکی است، MISRA را خواهی دید. برای پروژهٔ شخصی، ترکیب «-Wall -Wextra -Wconversion + cppcheck + clang-tidy با cert-*» ۹۰٪ فایدهٔ آن را بدون هزینه می‌دهد.
  • گران‌ترین باگ‌ها روی سخت‌افزار پیدا می‌شوند. حلقهٔ بی‌پایان روی دستگاه در دیوار، یعنی کسی باید برود و آن را ریست کند. یک watchdog (تایمری که اگر به موقع «تغذیه» نشود دستگاه را ریست می‌کند) آخرین پناه است، ولی پیش از آن باید قانون ۲ را رعایت کنی.

  2. کد ممکن است هنوز مشکل داشته باشد؛ پرچم‌های دیگر (مثل -Wconversion) و ابزارهای تحلیل ایستا هم لازم‌اند
  3. پرچم -Wall کار نمی‌کند
  4. باید با -O0 کامپایل کنیم تا هشدار بیشتری بگیریم
-Wall و -Wextra فقط بخشی از هشدارها هستند. -Wconversion، -Wshadow و -Wstrict-prototypes را جدا روشن می‌کنیم و -O2 هم بعضی تحلیل‌ها را ممکن می‌کند.

خروجی این برنامه چیست؟ (به تابع parse_percent همین درس ورودی "4x2" می‌دهیم.)

  1. PARSE_OK با مقدار ۴۲
  2. PARSE_RANGE
  3. PARSE_BAD_CHAR، و *out دست‌نخورده می‌ماند
  4. برنامه با assert متوقف می‌شود
رقم اول ('4') قبول است، ولی 'x' بین '0' و '9' نیست، پس PARSE_BAD_CHAR برمی‌گردد. در حالت خطا تابع هیچ چیز را در *out نمی‌نویسد.

کدام حلقه قانون ۲ ناسا («سقف ثابت برای هر حلقه») را می‌شکند؟

  1. while ((UART_SR & TXE_BIT) == 0U) { }
  2. for (int i = 0; i < 10; i++) { ... }
  3. حلقه‌ای که با شمارندهٔ n < 1000 منتظر پرچم می‌ماند
  4. حلقه‌ای که روی همهٔ ۸ عضو یک آرایهٔ ثابت می‌گردد
اولی می‌تواند برای همیشه بچرخد اگر بیت هرگز ۱ نشود. سه گزینهٔ دیگر تعداد تکرار مشخصی دارند. راه درست: شمارندهٔ timeout اضافه کن (تمرین ۳).

چرا -Wcast-align روی ARM (مثلا Cortex-M0) هشدار می‌دهد و روی x86 معمولا ساکت است؟

  1. چون x86 سریع‌تر است
  2. چون ARM حافظهٔ کمتری دارد
  3. چون int روی ARM چهار بایت است
  4. چون بعضی هسته‌های ARM خواندن ناهم‌تراز را با HardFault پاسخ می‌دهند، ولی x86 آن را تحمل می‌کند
تراز (alignment) قاعده‌ای سخت‌افزاری است: در Cortex-M0 خواندن ۴ بایتی از آدرس فرد یک خطای جدی است. x86 کند می‌شود ولی از کار نمی‌افتد. پس کد «روی PC کار می‌کند» ممکن است روی MCU بترکد.

cppcheck روی فایل شما هیچ هشداری نداد. چه نتیجه‌ای بگیریم؟

  1. فایل بدون باگ است
  2. ابزار چیزی ندید؛ هنوز بازبینی انسانی، ابزارهای دیگر و تست لازم است
  3. cppcheck خراب است
  4. باید --enable=all بگذاریم تا حتما یک هشدار بدهد
تحلیل ایستا فقط بخشی از باگ‌ها را می‌گیرد؛ «هشدار ندارد» معنی «باگ ندارد» نمی‌دهد. سه لایه (کامپایلر، تحلیل، بازبینی) و تست را با هم بگذار.

کدام رفتار درست‌ترین واکنش به یک هشدار کاذب clang-tidy است؟

  1. کل clang-tidy را از پروژه حذف کنیم
  2. هشدار را نادیده می‌گیریم و بدون توضیح می‌گذاریم بماند
  3. اگر واقعا کاذب است، فقط همان خط را با NOLINT(نام‌بررسی) و یک دلیل کوتاه ساکت می‌کنیم
  4. -Werror را از Makefile برمی‌داریم
اول ببین کد را می‌شود واضح‌تر کرد؛ اگر نه، فقط همان خط و همان بررسی را ساکت کن و دلیلش را بنویس تا بازبین بعدی بفهمد.

تمرین ۱: سه هشدار را رفع کن

این فایل با -Wall -Wextra فقط یک هشدار می‌دهد (-Wunused-variable برای total سراسری؛ ردپای همان مشکل ۱). با -Wconversion -Wshadow -Wstrict-prototypes -Werror چهار پیام می‌گیری: سه مشکل اصلی (شماره‌دار) و همان هشدار «total استفاده نشده». رفع مشکل ۱ آن هشدار چهارم را هم برمی‌دارد.

#include <stdint.h>
#include <stdio.h>

static uint16_t total;

void add_sample(uint8_t sample)
{
    uint8_t total = sample;         // (۱)
    (void)total;
}

uint8_t half(int value)
{
    return value / 2;               // (۲)
}

int get_count()                     // (۳)
{
    return 3;
}
  1. پیش‌بینی: هر سه مورد را با کلمه شرح بده: چه هشدارهایی و روی کدام خط‌ها؟
  2. حل: فایل را درست کن. برای half باید ورودی را بسنجی و در صورت مشکل خطا بدهی (پارامتر uint8_t *out).
  3. چالش: در add_sample قصد اصلی این بوده که به total سراسری اضافه شود. آن را با uint16_t امن بنویس؛ اگر سرریز شود چه کنی؟
راهنمایی

مورد ۱: -Wshadow. مورد ۲: -Wconversion (int به uint8_t). مورد ۳: -Wstrict-prototypes. مورد چهارم (unused-variable) با رفع مورد ۱ از بین می‌رود. برای چالش، قبل از جمع‌کردن ببین total + sample از UINT16_MAX بیشتر می‌شود یا نه.

total = 65535 (saturated)

نکته: خط دوم مقدار قبلی (۵) را نگه داشته چون در حالت خطا *out دست‌نخورده می‌ماند.

جواب کامل با توضیح 
#include <stdint.h>
#include <stdio.h>

static uint16_t total;

/* اضافه می‌کند؛ اگر از حد بگذرد روی حداکثر می‌ماند (اشباع) */
static void add_sample(uint8_t sample)
{
    if (total > (uint16_t)(UINT16_MAX - sample)) {
        total = UINT16_MAX;
    } else {
        total = (uint16_t)(total + sample);
    }
}

static int half(int value, uint8_t *out)
{
    if ((out == NULL) || (value < 0) || (value > 510)) {
        return -1;
    }
    *out = (uint8_t)(value / 2);
    return 0;
}

static int get_count(void)
{
    return 3;
}

int main(void)
{
    uint8_t h = 5U;
    int st = half(10, &h);
    printf("half(10) = %u (status %d)\n", (unsigned)h, st);
    st = half(-4, &h);
    printf("half(-4) = %u (status %d)\n", (unsigned)h, st);

    for (int i = 0; i < get_count() * 100000; i++) {
        add_sample(255U);
        if (total == UINT16_MAX) {
            break;
        }
    }
    printf("total = %u (saturated)\n", (unsigned)total);
    return 0;
}
  1. مشکل ۱ رفع شد. متغیر محلی حذف شد؛ فقط یک total داریم.
  2. اشباع (saturation). اگر جمع از سقف بگذرد، عدد روی سقف می‌ماند، نه اینکه به صفر برگردد. شرط را قبل از جمع می‌سنجیم: total + sample > MAX را به شکل total > MAX - sample می‌نویسیم تا خودِ شرط سرریز نکند. اگر اول جمع کنی و بعد بسنجی، برای بی‌علامت‌ها «دور زدن» رخ داده و دیگر نمی‌توانی تشخیص بدهی. (درس ۴.۷)
  3. مشکل ۲ رفع شد. ورودی را می‌سنجد (۰ تا ۵۱۰)، تا value / 2 در ۸ بیت بگنجد؛ و وضعیت را برمی‌گرداند. cast صریح بعد از اثبات محدوده.
  4. مشکل ۳ رفع شد. (void) داخل پرانتز.
  5. آزمایش. ورودی درست، ورودی منفی و پرکردن با اشباع.

تمرین ۲: باگ‌یاب با ابزار

فایل stats.c مثل یک مبتدی نوشته شده. بدون اجرا کردنش، فقط با ابزار بگرد.

#include <stdint.h>
#include <stdio.h>

#define COUNT 5U

static const int readings[COUNT] = { 10, 20, 30, 40, 50 };

int max_of(void)
{

    for (unsigned i = 0U; i <= COUNT; i++) {
        if (readings[i] > best) {
            best = readings[i];
        }

    return best;
}

{
    if (x = 0) {
        return 1;

    return 0;

    return 0;

#include <stdint.h>
#include <stdio.h>

#define COUNT 5U

_Static_assert(COUNT > 0U, "COUNT must be positive");

static const int readings[COUNT] = { 10, 20, 30, 40, 50 };

static int max_of(void)
{
    int best = readings[0];             // مقدار اولیهٔ معتبر
    for (unsigned i = 1U; i < COUNT; i++) {
        if (readings[i] > best) {
            best = readings[i];
        }
    }
    return best;
}

static int is_zero(int x)
{
    if (x == 0) {                       // مقایسه، نه انتساب
        return 1;
    }
    return 0;
}

{

تمرین ۳: انتظار با timeout (سخت‌افزار)

حلقهٔ uart_send همین درس (بخش «ده قانون ناسا») بی‌پایان می‌شود. آن را به تابعی تبدیل کن که با تعداد تکرار محدود صبر کند و TX_TIMEOUT برگرداند. رجیستر را در این تمرین با یک متغیر ساختگی شبیه‌سازی می‌کنیم، تا روی PC هم اجرا شود.

  1. پیش‌بینی: اگر بیت TXE هرگز یک نشود، حلقهٔ اصلی چه می‌شود؟ و حلقهٔ تو؟
  2. حل: تابع wait_txe(volatile uint32_t *sr, uint32_t limit) بنویس که TX_OK یا TX_TIMEOUT برگرداند.
  3. چالش: عدد limit را چطور انتخاب می‌کنی؟ (فکر کن: کلاک، سرعت باود، بدترین حالت.) و این رجیستر چرا باید volatile باشد؟
راهنمایی

شمارندهٔ n از صفر تا limit؛ در هر دور بیت را بخوان، اگر یک بود TX_OK برگردان. بعد از حلقه یعنی هیچ دوری موفق نشد: TX_TIMEOUT.

چه باید ببینی؟ 
$ ./ex3
sr=0x00 -> TX_TIMEOUT
sr=0x80 -> TX_OK
جواب کامل با توضیح 
#include <stdint.h>
#include <stdio.h>

#define TXE_BIT     (1U << 7)
#define WAIT_LIMIT  1000U

typedef enum { TX_OK = 0, TX_TIMEOUT } tx_status_t;

static volatile uint32_t fake_sr;       // رجیستر ساختگی (روی MCU: آدرس واقعی)

static tx_status_t wait_txe(volatile uint32_t *sr, uint32_t limit)
{
    for (uint32_t n = 0U; n < limit; n++) {
        if ((*sr & TXE_BIT) != 0U) {
            return TX_OK;
        }
    }
    return TX_TIMEOUT;
}

static const char *name(tx_status_t s)
{
    return (s == TX_OK) ? "TX_OK" : "TX_TIMEOUT";
}

int main(void)
{
    fake_sr = 0U;
    printf("sr=0x%02X -> %s\n", (unsigned)fake_sr, name(wait_txe(&fake_sr, WAIT_LIMIT)));
    fake_sr = TXE_BIT;
    printf("sr=0x%02X -> %s\n", (unsigned)fake_sr, name(wait_txe(&fake_sr, WAIT_LIMIT)));
    return 0;
}
  1. ثابت‌های نام‌دار. بیت ۷ و سقف تکرار جدا از منطق. عدد جادویی (magic number) در وسط کد یعنی بازبین نمی‌داند چرا ۱۰۰۰. اسم به آن معنی می‌دهد.
  2. رجیستر ساختگی. روی PC یک متغیر معمولی است ولی volatile؛ روی MCU جایش یک آدرس ثابت می‌آید.
  3. حلقه با سقف. حداکثر limit بار می‌خواند. اگر بیت بیاید TX_OK، وگرنه TX_TIMEOUT. اگر sr volatile نبود، کامپایلر مقدار را یک‌بار می‌خواند و تصور می‌کرد تغییر نمی‌کند (درس ۳.۶): حلقه یا بی‌پایان یا حذف می‌شد.
  4. تبدیل وضعیت به متن. برای چاپ.
  5. دو آزمایش. اول رجیستر صفر (زمان سنجی می‌گذرد)، بعد بیت ۷ روشن.
$ ./ex3
sr=0x00 -> TX_TIMEOUT
sr=0x80 -> TX_OK

روی MCU مقدار limit را از بدترین حالت محاسبه می‌کنی: مثلا ارسال یک بایت در ۱۱۵۲۰۰ باود حدود ۸۷ میکروثانیه است؛ اگر هر دور حلقه چند چرخه بگیرد، تعداد تکرار لازم را حساب کن و ضریب اطمینان بده. یا از SysTick (درس ۵.۴) زمان‌سنج واقعی استفاده کن.

حرف مربی

معمولا سه جا گیر می‌کنند. اول: ابزار را یک‌بار اجرا می‌کنند و فراموشش می‌کنند. ارزش این ابزارها در «هر بار ساخت» است، نه یک‌بار. دوم: وقتی ۲۰۰ هشدار می‌آید، ناامید می‌شوند و همه را خاموش می‌کنند. راه درست: روی پروژهٔ نو از روز اول شروع کن (قانون ۱۰ ناسا)؛ روی پروژهٔ قدیمی، فقط ماژول‌های جدید را سخت‌گیر کن و رفته‌رفته گسترش بده. سوم: MISRA را با «ایمنی مطلق» اشتباه می‌گیرند. هیچ استانداردی باگ را حذف نمی‌کند؛ فقط احتمالش را کم می‌کند. امروز اگر فقط یک کار بکنی: -Wconversion -Wshadow -O2 را در ساخت خودت بگذار و هشدارها را یکی‌یکی صفر کن. حس می‌کنی چیزی را یاد گرفته‌ای که کتاب‌ها فقط اشاره‌اش می‌کنند.

خلاصه یک‌دقیقه‌ای

  • سه توری: کامپایلر با پرچم‌ها، تحلیلگر ایستا، بازبینی و استاندارد؛ بعدش تست (درس ۶.۴). هیچ‌کدام تنها کافی نیست.
  • پرچم‌ها: -Wall -Wextra + -Wconversion -Wshadow -Wstrict-prototypes -Wcast-align + -Werror (برای کد خودت) و -O2 برای تحلیل جریان داده. -isystem برای هدرهای دیگران.
  • ابزارها: cppcheck و clang-tidy رایگان‌اند، هرکدام چیزهای متفاوتی می‌گیرند؛ «گزارش تمیز» یعنی «ابزار چیزی ندید».
  • هشدار کاذب: اول کد را درست کن؛ اگر نشد فقط همان خط را با NOLINT/cppcheck-suppress و دلیل ساکت کن.
  • MISRA (ایمنی، پولی، سه دستهٔ قاعده)، CERT C (امنیت، رایگان، شناسه‌هایی مثل INT32-C) و ده قانون ناسا (سادگی: بدون بازگشت، حلقهٔ سقف‌دار، بدون حافظهٔ پویا پس از راه‌اندازی، اشاره‌گر محدود، ...).
  • دفاعی بنویس: ورودی را در دروازه بسنج؛ خطا را زود و بی‌اثر برگردان؛ وضعیت صریح بده؛ فرض‌های داخلی با assert؛ هر انتظار سخت‌افزاری timeout دارد.
  • بعدی: ۶.۴ تست واحد روی PC، تا رفتار کد را هم خودکار وارسی کنیم.
