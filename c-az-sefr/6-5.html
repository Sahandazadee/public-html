برنامه‌ات درست کار می‌کند، ولی Flash دارد پر می‌شود یا حلقه‌ای آن‌قدر کند است که وقفه‌ها را از دست می‌دهی. اولین غریزهٔ بیشتر ما این است که «کد را دستی ریز‌ریز کنم». استادها اول اندازه می‌گیرند، بعد یک چیز را عوض می‌کنند و دوباره اندازه می‌گیرند. در این درس با ابزارهای واقعی (arm-none-eabi-size، nm، فایل map، -S و شمارندهٔ چرخهٔ DWT) و عددهای واقعی یاد می‌گیری کامپایلر چه کارهایی برایت می‌کند و کجا باید خودت دخالت کنی.

🎯 بعد از این درس می‌توانی

  • با arm-none-eabi-size بگویی برنامه چقدر Flash و چقدر RAM می‌گیرد
  • فرق -O0، -Og، -O1، -O2، -O3 و -Os را با عدد بگویی
  • اسمبلی تولیدشده را با -S ببینی و سه کار اصلی کامپایلر (ثابت‌گذاری، حذف کد مرده، inline) را تشخیص بدهی
  • با --gc-sections و فایل map پیدا کنی چه چیزی جا خورده و چه چیزی دور ریخته شده
  • هزینهٔ float، double و تقسیم را روی Cortex-M4 و Cortex-M0 بشناسی
  • زمان اجرا را با شمارندهٔ چرخهٔ DWT اندازه بگیری و بدانی چرا «زودرس بهینه نکن»

🧰 پیش‌نیاز و وسایل

  • درس ۵.۱ (بخش‌های .text، .data، .bss و اسکریپت لینکر)
  • درس ۳.۶ (volatile) و ۴.۷ (سرریز و عدد ثابت)
  • ابزار arm-none-eabi-gcc و binutils (درس ۱.۳)
  • برد لازم نیست؛ همهٔ اندازه‌ها از کامپایل واقعی روی PC آمده. فقط بخش زمان‌سنجی روی برد معنا دارد

ایدهٔ اصلی: بستن چمدان

فرض کن قرار است به سفر بروی و چمدانت فقط ۲۰ کیلو جا دارد. چند راه داری: لباس‌ها را تا کنی، چیزهای غیرضروری را نبری، یا یک چمدان بزرگ‌تر بخری. ولی اگر ندانی چمدان الان چند کیلو است، هیچ‌کدام از این‌ها را نمی‌توانی درست انجام دهی. بعضی‌ها ساعت‌ها لباس تا می‌کنند و بعد می‌بینند آنچه سنگین بود کفش‌ها بودند.

مثال از زندگی روزمره

کامپایلر مثل یک چمدان‌بند حرفه‌ای است. اگر بگویی «فقط سریع ببند» (-O0)، همه‌چیز را همان‌طور که هست می‌ریزد داخل، بدون فکر. اگر بگویی «کوچک‌ترین حجم» (-Os)، همه‌چیز را تا می‌کند و بعضی چیزهای اضافه را دور می‌گذارد. ولی ترازو را باید خودت بیاوری: size، فایل map و شمارندهٔ چرخه. بدون ترازو، بهینه‌سازی فقط حدس است.

در میکروکنترلر «بهینه» یعنی چه؟ سه چیز داریم و معمولا نمی‌شود هر سه را با هم کامل داشت:

  • اندازه: چقدر Flash (برای کد و ثابت‌ها) و چقدر RAM (برای متغیرها و پشته) می‌گیریم؟
  • سرعت: یک کار چند چرخهٔ ساعت طول می‌کشد؟ (چرخه = یک تیک کلاک CPU. با کلاک ۱۶ مگاهرتز، هر چرخه ۶۲٫۵ نانوثانیه است.)
  • خوانایی و دیباگ‌پذیری: آیا می‌توانی با GDB خط به خط جلو بروی و مقدار متغیرها را ببینی؟

هر بار که یکی را بهتر می‌کنی، معمولا یکی از دو تای دیگر بدتر می‌شود. به همین دلیل اول باید بدانی کدام محدودیت را داری: Flash تنگ است؟ CPU دیر می‌رسد؟ یا فقط دلت می‌خواهد «سریع‌تر» باشد؟ اگر هیچ محدودیتی نداری، بهترین بهینه‌سازی این است که کاری نکنی.

اول ترازو: کد ما چقدر جا می‌گیرد؟

برای اندازه‌گیری یک برنامهٔ کوچک ولی واقعی روی STM32F411 می‌سازیم: یک حلقهٔ بی‌پایان که هر بار یک نمونه از «سنسور» می‌خواند، میانگین ۸ نمونهٔ آخر را حساب می‌کند، به میلی‌ولت تبدیل می‌کند، از یک جدول ثابت مقدار خروجی برمی‌دارد و یک CRC از پنجره در تاریخچه می‌ریزد. (در این درس GPIOA_IDR نقش سنسور و GPIOA_ODR نقش خروجی را دارد؛ فقط برای اینکه دسترسی‌ها volatile و واقعی باشند.)

پروژه سه فایل دارد. دو تای اول را در درس ۵.۱ دیده‌ای؛ اینجا فقط برای کامل‌بودن می‌آیند.

#include <stdint.h>

extern uint32_t _estack, _sidata, _sdata, _edata, _sbss, _ebss;
int main(void);
void Reset_Handler(void);

__attribute__((section(".isr_vector"), used))
void (*const vector_table[])(void) = {
    (void (*)(void))&_estack,   // مقدار اولیهٔ SP
    Reset_Handler,              // نقطهٔ شروع
};

void Reset_Handler(void)
{
    uint32_t *src = &_sidata;
    for (uint32_t *dst = &_sdata; dst < &_edata; ) {
        *dst++ = *src++;        // کپی .data از Flash به RAM
    }
    for (uint32_t *dst = &_sbss; dst < &_ebss; ) {
        *dst++ = 0u;            // صفر کردن .bss
    }
    main();
    for (;;) {
    }
}
  1. جدول وقفه. کلمهٔ اول مقدار اولیهٔ پشته و کلمهٔ دوم آدرس Reset_Handler است. دلیل: CPU بعد از ریست همین دو کلمهٔ ابتدای Flash را می‌خواند (درس ۵.۱).
  2. کپی .data. مقدار اولیهٔ متغیرهای غیرصفر در Flash خوابیده و باید به RAM بیاید. دلیل: calls = 5 فقط وقتی در RAM هم ۵ است که این حلقه اجرا شده باشد.
  3. صفر کردن .bss. همهٔ متغیرهای سراسری بدون مقدار اولیه صفر می‌شوند.
  4. صدا زدن main. اگر برگشت، در یک حلقهٔ بی‌پایان می‌مانیم.
ENTRY(Reset_Handler)
_estack = ORIGIN(RAM) + LENGTH(RAM);

MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 512K
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 128K
}

SECTIONS
{
    .isr_vector : { . = ALIGN(4); KEEP(*(.isr_vector)) . = ALIGN(4); } > FLASH
    .text       : { . = ALIGN(4); *(.text*) . = ALIGN(4); } > FLASH
    .rodata     : { . = ALIGN(4); *(.rodata*) . = ALIGN(4); } > FLASH
    _sidata = LOADADDR(.data);
    .data : { . = ALIGN(4); _sdata = .; *(.data*) . = ALIGN(4); _edata = .; } > RAM AT > FLASH
    .bss  : { . = ALIGN(4); _sbss = .; *(.bss*) *(COMMON) . = ALIGN(4); _ebss = .; } > RAM
    /DISCARD/ : { *(.ARM.exidx*) *(.comment) }
}
  1. ورود و بالای پشته. _estack انتهای RAM است؛ پشته از آنجا به سمت پایین رشد می‌کند.
  2. دو ناحیهٔ حافظه. Flash نیم مگابایت از 0x08000000 و RAM ۱۲۸ کیلوبایت از 0x20000000. دلیل: بعدا --print-memory-usage درصد پر بودن همین دو ناحیه را نشان می‌دهد.
  3. کد و ثابت‌ها در Flash. جدول وقفه اول می‌آید (KEEP یعنی حتی اگر کسی صدایش نزد نگهش دار)، بعد .text و .rodata.
  4. داده‌ها در RAM. .data در RAM زندگی می‌کند ولی تصویر اولیه‌اش در Flash است (AT > FLASH). .bss فقط RAM می‌گیرد.
  5. دور ریختنی‌ها. اطلاعات اضافی که در حافظه لازم نیستند.
#include <stdint.h>
#include <stddef.h>

#define SENSOR_REG (*(volatile uint32_t *)0x40020010u)  /* GPIOA_IDR؛ اینجا نقش سنسور */
#define OUT_REG    (*(volatile uint32_t *)0x40020014u)  /* GPIOA_ODR؛ اینجا نقش خروجی */

static const uint16_t curve[16] = {         /* جدول ثابت: می‌رود Flash */
    0, 12, 40, 90, 160, 250, 360, 490, 640, 810, 1000, 1210, 1440, 1690, 1960, 2250
};
uint8_t history[64];                        /* بافر تاریخچه: می‌رود .bss */
static uint16_t win[8];                     /* پنجرهٔ میانگین: آن هم .bss */
uint32_t calls = 5;                         /* مقدار اولیهٔ غیرصفر: می‌رود .data */

static uint32_t scale_mv(uint32_t raw)      /* عدد ۱۲ بیتی به میلی‌ولت */
{
    return raw * 3300u / 4095u;
}

static uint32_t average(const uint16_t *a, size_t n)
{
    uint32_t sum = 0;
    for (size_t i = 0; i < n; i++) {
        sum += a[i];
    }
    return sum / n;
}

static uint8_t crc8(const uint8_t *d, size_t n)
{
    uint8_t crc = 0;
    for (size_t i = 0; i < n; i++) {
        crc ^= d[i];
        for (int b = 0; b < 8; b++) {
            crc = (crc & 0x80u) ? (uint8_t)((crc << 1) ^ 0x07u) : (uint8_t)(crc << 1);
        }
    }
    return crc;
}

uint32_t diag_dump(void)                    /* هیچ‌کس صدایش نمی‌زند */
{
    uint32_t s = 0;
    for (size_t i = 0; i < 16; i++) {
        s += curve[i] * (uint32_t)(i + 1u);
    }
    return s;
}

int main(void)
{
    uint32_t k = 0;

    for (;;) {
        win[k & 7u] = (uint16_t)SENSOR_REG;
        k++;
        uint32_t mv = scale_mv(average(win, 8));
        OUT_REG = curve[(mv >> 8) & 15u];
        history[k & 63u] = crc8((const uint8_t *)win, sizeof win);
        calls++;
    }
}
  1. دو «رجیستر» ساختگی. آدرس‌های GPIOA_IDR و GPIOA_ODR با volatile. دلیل: بدون volatile کامپایلر خواندن سنسور را حذف یا ادغام می‌کرد و مقایسهٔ ما بی‌معنی می‌شد.
  2. جدول ثابت. static const یعنی فقط‌خواندنی؛ کامپایلر آن را در .rodata یعنی Flash می‌گذارد.
  3. داده‌های صفر. history و win مقدار اولیه ندارند و در .bss می‌روند: ۶۴ + ۱۶ = ۸۰ بایت RAM.
  4. داده با مقدار اولیه. calls = 5 در .data می‌رود: ۴ بایت RAM و ۴ بایت تصویر در Flash.
  5. تبدیل به میلی‌ولت. ضرب و تقسیم صحیح. دلیل: تقسیم بر ۴۰۹۵ (نه توان ۲) روی Cortex-M0 گران است؛ در بخش تقسیم می‌بینی.
  6. میانگین. جمع همهٔ خانه‌ها و تقسیم بر n. در main همیشه با n = 8 صدا زده می‌شود.
  7. CRC-8. یک حلقهٔ تودرتو (بایت‌ها و ۸ بیت هر بایت) که در درس‌های قبل دیده‌ای.
  8. تابع بی‌مشتری. diag_dump خارجی (بدون static) است ولی در main صدایش نمی‌زنیم؛ مهمان بخش gc-sections است.
  9. حلقهٔ اصلی. نمونه را در پنجره می‌ریزد (اندیس k & 7 دور می‌زند)، میانگین و mv را حساب می‌کند، خروجی را می‌نویسد و CRC را ذخیره می‌کند.

ستون‌ها را بخوان، چون همین یک جدول نصف بحث این درس است:

ستونچیست؟کجا می‌نشیند؟
textکد ماشین + .rodata (ثابت‌ها) + جدول وقفهFlash
dataمتغیرهای با مقدار اولیهٔ غیرصفرRAM، و یک کپی تصویر در Flash
bssمتغیرهای سراسری/ایستا با مقدار صفرفقط RAM (در Flash جا نمی‌گیرد)
dec، hexجمع سه ستون بالا، ده‌دهی و هگزعدد کلی بی‌معنی‌تر از تفکیک است

Flash مصرفی = text + data (چون تصویر .data هم در Flash است) و RAM مصرفی = data + bss (پشته را جداگانه حساب کن؛ بعدا می‌بینی). برای -Os: Flash = ۲۹۶ + ۴ = ۳۰۰ بایت و RAM = ۴ + ۸۰ = ۸۴ بایت. لینکر خودش هم همین را می‌گوید، اگر -Wl,--print-memory-usage بدهی:

شش سطح بهینه‌سازی، با عدد

گزینهٔ -O (حرف بزرگ O، نه صفر) که به آن سطح بهینه‌سازی می‌گویند، به کامپایلر می‌گوید چقدر برای بهتر کردن کد تلاش کند. تعریف رسمی هر سطح در مستندات GCC هست؛ خلاصهٔ کاربردی:

سطحهدفFlash (text) در برنامهٔ ماکجا به کار می‌آید
-O0بدون بهینه‌سازی؛ هر متغیر یک خانهٔ RAM، هر خط یک تکه کد۵۶۰ بایتپیش‌فرض GCC؛ دیباگ خط به خط
-Ogبهینه‌سازی‌هایی که دیباگ را خراب نمی‌کنند۳۲۴ بایتتوسعهٔ روزمره با دیباگر
-O1بهینه‌سازی‌های پایه۳۳۶ بایتکم‌کاربرد؛ حد وسط
-O2بیشتر بهینه‌سازی‌ها، بدون عوض‌کردن سرعت با حجم زیاد۳۲۸ بایتانتخاب رایج برای سرعت
-O3تهاجمی‌تر: باز کردن حلقه، inline بیشتر۴۷۶ بایتفقط وقتی اندازه گرفتی که می‌ارزد
-Osمثل -O2 ولی کارهایی که کد را بزرگ می‌کنند ممنوع۲۹۶ بایتانتخاب رایج در MCU با Flash کم
این جدول قانون کلی نیست

این اعداد فقط برای همین برنامهٔ ۶۰ خطی و این نسخهٔ کامپایلر (arm-none-eabi-gcc نسخهٔ ۱۳٫۲) است. در برنامهٔ تو ممکن است -O2 از -Os کوچک‌تر شود یا -O3 واقعا سریع‌تر باشد. تنها راه فهمیدن: سطح‌ها را روی برنامهٔ خودت بساز و اندازه بگیر. برای سرعت هم باید زمان‌سنجی کنی (بخش «زمان» را ببین).

توصیهٔ عملی
  • توسعه و دیباگ: -Og یا -O0 (با GDB متغیرها «بهینه‌شده و ناپدید» نمی‌شوند).
  • محصول نهایی: معمولا -Os یا -O2؛ همان سطحی را که می‌فرستی تست کن. رفتار برنامه با -O0 و -O2 باید یکی باشد؛ اگر نیست، احتمالا رفتار تعریف‌نشده یا یک volatile فراموش‌شده داری (درس‌های ۶.۲ و ۳.۶).

کامپایلر واقعا چه کار می‌کند؟ اسمبلی را ببین

گزینهٔ -S کامپایلر را بعد از تولید اسمبلی متوقف می‌کند و متن دستورهای CPU را می‌دهد. لازم نیست اسمبلی بنویسی؛ فقط باید بتوانی بخوانی که کامپایلر با کدت چه کرده. (در درس ۱.۴ فایل .s را دیده بودی.) سه کار اصلی کامپایلر را با سه مثال کوچک می‌بینیم.

کار ۱: ثابت‌گذاری (محاسبه در زمان کامپایل)

اگر همهٔ عددهای یک عبارت معلوم باشند، لازم نیست CPU هر بار آن را حساب کند؛ کامپایلر خودش یک‌بار حساب می‌کند و فقط جواب را می‌گذارد. به این کار می‌گویند ثابت‌گذاری (constant folding).

#include <stdint.h>

#define VREF_MV 3300u
#define ADC_MAX 4095u

uint32_t full_scale_uv(void)
{
    uint32_t mv = VREF_MV * 1000u / ADC_MAX * 2u;
    return mv + 0u * 12345u;
}
  1. ثابت‌های نام‌دار. ولتاژ مرجع و بیشینهٔ ADC با #define. دلیل: نام‌دار بودن خوانایی می‌دهد و هزینه‌ای ندارد؛ کامپایلر همه را با عدد جایگزین می‌کند.
  2. عبارتی که همه‌اش عدد است. ۳۳۰۰ × ۱۰۰۰ ÷ ۴۰۹۵ × ۲ = ۱۶۱۰ (تقسیم صحیح: ۸۰۵ و بعد ضرب در ۲).
  3. جمع با صفر. 0 * 12345 صفر است و اضافه‌کردنش اثری ندارد.

حتی در -O0 کامپایلر عدد 1610 را حساب کرده و هیچ تقسیمی در برنامه نیست (ثابت‌گذاری تقریبا همیشه فعال است). فرق -O0 با -O2 اینجاست که -O0 جواب را اول در پشته (str r3, [r7, #4]) می‌نویسد و دوباره می‌خواند، یعنی ۱۱ دستور؛ -O2 فقط ۲ دستور: مقدار را در r0 بگذار و برگرد.

نتیجهٔ عملی برای تو

لازم نیست 3300u * 1000u / 4095u را خودت با ماشین‌حساب بزنی و عدد 805 را «جادویی» در کد بگذاری. عبارت خوانا را بنویس و به کامپایلر اعتماد کن. فقط مطمئن شو همهٔ اجزا ثابت زمان کامپایل هستند (#define، enum، const عددی در بیشتر موارد).

کار ۲: حذف کد مرده و inline

کدی که هیچ‌وقت اجرا نمی‌شود یا نتیجه‌اش هیچ‌جا استفاده نمی‌شود، کد مرده (dead code) است. کامپایلر آن را دور می‌ریزد. کار دیگر کامپایلر inline است: به‌جای صدا زدن تابع کوچک، بدنهٔ آن را مستقیم در جای صدا می‌گذارد.

#include <stdint.h>

#define DEBUG 0

static uint32_t helper(uint32_t x)
{
    return x * 3u + 1u;
}

uint32_t run(uint32_t x)
{
    uint32_t y = helper(x);
    if (DEBUG) {
        y = y * 7u;
    }
    return y;
}
  1. کلید خاموش. DEBUG صفر است، پس شرط if (DEBUG) هیچ‌وقت درست نمی‌شود.
  2. تابع کوچک و ایستا. static یعنی فقط همین فایل می‌بیندش؛ کامپایلر می‌داند همهٔ صدازننده‌ها را دیده است.
  3. تابع اصلی. helper را صدا می‌زند و شاخهٔ مرده را دارد.
$ arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -std=gnu11 -ffreestanding -O2 -S -o - dead.c
run:
    add     r0, r0, r0, lsl #1
    adds    r0, r0, #1
    bx      lr

با -O2 کل تابع سه دستور است: x + (x << 1) یعنی 3x، بعد +1. سه اتفاق افتاد: (۱) شاخهٔ if (DEBUG) حذف شد، (۲) helper در جای صدا گذاشته شد (inline) و بدون فراخوانی bl جمع شد، (۳) خود تابع helper هم از خروجی رفت چون static بود و دیگر کسی نیاز نداشت. ضرب در ۳ هم با یک جمع و شیفت انجام شد.

همین است که در -O0 برنامه دو تابع جدا دارد (helper و run) با ذخیره و بازیابی r7 و sp، ولی در -O2 فقط یک تابع سه‌خطی می‌ماند.

کار ۳: نگه داشتن متغیرها در رجیستر

بزرگ‌ترین فرق -O0 با بقیه اینجاست. کد C ساده را ببین: جمع یک آرایه.

#include <stdint.h>
#include <stddef.h>

uint32_t sum(const uint16_t *a, size_t n)
{
    uint32_t s = 0;
    for (size_t i = 0; i < n; i++) {
        s += a[i];
    }
    return s;
}
  1. ورودی‌ها. آدرس آرایه و تعداد عناصر. CPU آن‌ها را در r0 و r1 می‌گیرد (قرارداد فراخوانی ARM).
  2. حلقه. s و i دو متغیر محلی هستند. در -O0 هر کدام یک خانهٔ پشته می‌شوند؛ در -O2 فقط رجیستر.
  3. برگرداندن نتیجه. جواب باید در r0 باشد.
sum:                            @ خروجی -O0
    push    {r7}
    sub     sp, sp, #20
    add     r7, sp, #0
    str     r0, [r7, #4]        @ a را در پشته ذخیره کن
    str     r1, [r7]            @ n را در پشته ذخیره کن
    movs    r3, #0
    str     r3, [r7, #12]       @ s = 0 (در پشته)
    movs    r3, #0
    str     r3, [r7, #8]        @ i = 0 (در پشته)
    b       .L2
.L3:
    ldr     r3, [r7, #8]        @ i را بخوان
    lsls    r3, r3, #1          @ i * 2 (اندازهٔ هر عنصر)
    ldr     r2, [r7, #4]        @ a را بخوان
    add     r3, r3, r2          @ آدرس a[i]
    ldrh    r3, [r3]            @ a[i] را بخوان
    mov     r2, r3
    ldr     r3, [r7, #12]       @ s را بخوان
    add     r3, r3, r2          @ s += a[i]
    str     r3, [r7, #12]       @ s را برگردان به پشته
    ldr     r3, [r7, #8]
    adds    r3, r3, #1          @ i++
    str     r3, [r7, #8]
.L2:
    ldr     r2, [r7, #8]
    ldr     r3, [r7]
    cmp     r2, r3              @ i < n ؟
    bcc     .L3
    ldr     r3, [r7, #12]
    mov     r0, r3
    adds    r7, r7, #20
    mov     sp, r7
    pop     {r7}
    bx      lr
  1. ذخیرهٔ پارامترها. حتی ورودی‌ها اول در پشته می‌روند. دلیل: در -O0 قانون این است که «هر متغیر یک خانهٔ RAM دارد». دیباگر می‌تواند هر متغیر را بخواند، چون همیشه در حافظه است.
  2. مقدار اولیه. s و i در پشته صفر می‌شوند.
  3. بدنهٔ حلقه. برای هر دور: خواندن i، خواندن a، خواندن s، نوشتن s، خواندن i، نوشتن i. دلیل: هر عملیات از حافظه بخواند و در حافظه بنویسد؛ هر ldr/str به RAM حداقل یک چرخه و معمولا بیشتر می‌برد.
  4. شرط حلقه. دوباره i و n از پشته خوانده و مقایسه می‌شوند.
sum:                            @ خروجی -O2
    cbz     r1, .L4             @ اگر n == 0 برو به .L4
    subs    r3, r0, #2          @ r3 = آدرس عنصر قبل از اولی
    add     r1, r3, r1, lsl #1  @ r1 = آدرس پایان حلقه
    movs    r0, #0              @ s = 0 (مستقیم در r0)
.L3:
    ldrh    r2, [r3, #2]!       @ عنصر بعدی را بخوان و اشاره‌گر را جلو ببر
    cmp     r3, r1              @ به پایان رسیدیم؟
    add     r0, r0, r2          @ s += a[i]
    bne     .L3
    bx      lr
.L4:
    mov     r0, r1              @ جواب صفر
    bx      lr
  1. مراقبت از حالت n = 0. اگر آرایه خالی باشد، حلقه اصلا اجرا نمی‌شود.
  2. آماده‌سازی. کامپایلر i را حذف کرد و به‌جایش با اشاره‌گر جلو می‌رود؛ r1 نشان‌دهندهٔ پایان است. s مستقیم در r0 می‌ماند، همان‌جایی که جواب باید باشد.
  3. حلقهٔ چهاردستوری. یک خواندن از حافظه (خود آرایه)، یک مقایسه، یک جمع و یک پرش. هیچ متغیری به پشته نمی‌رود. دلیل: رجیسترها داخل CPU هستند و دسترسی به آن‌ها رایگان است؛ RAM دورتر است.

مقایسهٔ یک دور حلقه: در -O0 ۱۶ دستور و ۹ دسترسی به RAM؛ در -O2 فقط ۴ دستور و ۱ دسترسی (خواندن خود عنصر). شمارش را از فهرست‌ها خودت هم می‌توانی انجام بدهی: در .L3 و .L2 بالا هر ldr/str/ldrh که به [r7, ...] یا [r3] اشاره دارد را بشمار.

بهینه‌سازی و volatile: دوستی که فراموشش می‌کنی

کامپایلر فرض می‌کند «اگر من متغیری را ننوشتم، مقدارش عوض نمی‌شود». برای حافظهٔ معمولی درست است، برای رجیستر سخت‌افزار یا متغیری که ISR عوضش می‌کند، غلط. درس ۳.۶ را یادت هست؟ حالا ببین -O2 با یک انتظار ساده چه می‌کند:

#include <stdint.h>

static uint32_t ready;                 /* بدون volatile */

void wait_ready(void)
{
    while (ready == 0u) {
    }
}
  1. پرچم. فرض کن یک وقفه یا DMA بعدا آن را ۱ می‌کند. ما volatile نگذاشتیم.
  2. انتظار. تا وقتی پرچم صفر است می‌چرخد. دلیل: در این فایل هیچ کدی ready را عوض نمی‌کند، پس کامپایلر نتیجه می‌گیرد که مقدارش هیچ‌وقت عوض نخواهد شد.
$ arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -std=gnu11 -ffreestanding -O2 -S -o - vol.c
wait_ready:
.L2:
    b       .L2

نتیجه یک پرش بی‌پایان به خودش است: کامپایلر دید ready صفر است و هرگز در این فایل نوشته نمی‌شود، پس خواندنش را کلا حذف کرد. در -O0 همین کد درست کار می‌کند (هر بار ldr از RAM). یعنی برنامه‌ای که با -O0 «کار می‌کرد» با -O2 خراب می‌شود. راه‌حل: static volatile uint32_t ready;

هشدار: «بهینه‌سازی باگ نمی‌سازد، باگ پنهان را رو می‌کند»

اگر برنامه‌ات با -O0 درست و با -O2 غلط بود، کامپایلر را مقصر ندان. تقریبا همیشه مشکل از یکی از این‌هاست: volatile فراموش‌شده، رفتار تعریف‌نشده (درس ۶.۲)، متغیر بدون مقدار اولیه یا ترتیب دسترسی به حافظه بین ISR و برنامه (درس ۵.۳).

inline و restrict: دو قول به کامپایلر

static inline: برای تابع‌های خیلی کوچک (مثل خواندن یک رجیستر) static inline در هدر می‌گذاری. inline فقط پیشنهاد است و کامپایلر تصمیم نهایی را می‌گیرد؛ static جلوی خطای «تعریف تکراری» در چند فایل را می‌گیرد. برخلاف ماکرو، نوع دارد و آرگومان را دوبار ارزیابی نمی‌کند (درس ۴.۱).

restrict: اگر دو اشاره‌گر ممکن است به یک جا اشاره کنند، کامپایلر مجبور است بعد از هر نوشتن، مقدار خوانده‌شده را دوباره بخواند. با restrict قول می‌دهی «این دو اشاره‌گر هیچ‌وقت همپوشانی ندارند» و کامپایلر می‌تواند خواندن‌ها را کم کند:

#include <stdint.h>

void twice(uint32_t *a, const uint32_t *b)
{
    *a += *b;
    *a += *b;
}

void twice_r(uint32_t *restrict a, const uint32_t *restrict b)
{
    *a += *b;
    *a += *b;
}
  1. نسخهٔ معمولی. اگر a و b یکی باشند، خط اول *b را هم عوض می‌کند. پس کامپایلر باید *b را برای خط دوم دوباره بخواند.
  2. نسخهٔ restrict. با قول عدم همپوشانی، *b فقط یک‌بار خوانده می‌شود. دلیل: اگر قولت را بشکنی (اشاره‌گرها همپوشانی داشته باشند)، رفتار برنامه تعریف‌نشده است؛ کامپایلر هیچ هشداری نمی‌دهد.
$ arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -std=gnu11 -ffreestanding -O2 -S -o - restr.c
twice:
    ldr     r2, [r1]
    ldr     r3, [r0]
    add     r3, r3, r2
    str     r3, [r0]
    ldr     r2, [r1]            @ دوباره *b را می‌خواند!
    add     r3, r3, r2
    str     r3, [r0]
    bx      lr
twice_r:
    ldr     r3, [r0]
    ldr     r2, [r1]
    add     r3, r3, r2, lsl #1  @ یک‌جا دو بار اضافه کرد
    str     r3, [r0]
    bx      lr

نسخهٔ معمولی سه خواندن و دو نوشتن دارد؛ نسخهٔ restrict دو خواندن و یک نوشتن. restrict ابزار حرفه‌ای است و اشتباهش سخت پیدا می‌شود؛ فقط وقتی اندازه‌گیری نشان داد لازم است و ۱۰۰٪ مطمئنی همپوشانی ندارند، از آن استفاده کن.

ثابت‌ها را در Flash نگه دار

یک جدول (مثل جدول curve بالا) اگر const نباشد، باید در RAM زندگی کند: مقدار اولیه‌اش در Flash است و هنگام بوت به RAM کپی می‌شود (همان حلقهٔ Reset_Handler). یعنی دو برابر جا: یک کپی در Flash و یک کپی در RAM.

#include <stdint.h>

#ifdef TABLE_CONST
const
#endif
uint16_t curve[16] = {
    0, 12, 40, 90, 160, 250, 360, 490, 640, 810, 1000, 1210, 1440, 1690, 1960, 2250
};

uint16_t lookup(uint32_t i)
{
    return curve[i & 15u];
}
  1. const اختیاری. با -DTABLE_CONST کلمهٔ const اضافه می‌شود.
  2. جدول سراسری. ۱۶ عدد ۱۶ بیتی = ۳۲ بایت.
  3. استفاده. با & 15 اندیس را در محدوده نگه می‌دارد.
$ arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -std=gnu11 -ffreestanding -Os -c tab.c -o tab_ram.o
$ arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -std=gnu11 -ffreestanding -Os -DTABLE_CONST -c tab.c -o tab_flash.o
$ arm-none-eabi-size tab_ram.o tab_flash.o
   text	   data	    bss	    dec	    hex	filename
     16	     32	      0	     48	     30	tab_ram.o
     48	      0	      0	     48	     30	tab_flash.o

بدون const: ۳۲ بایت data (یعنی ۳۲ بایت RAM و ۳۲ بایت تصویر در Flash). با const: ۳۲ بایت فقط در Flash و RAM صفر. برای جدول‌های بزرگ (فونت، سینوس، پیام‌ها) این تفاوت هزاران بایت RAM است. ESP32 فرق دارد

در ESP32 حافظهٔ Flash بیرون از تراشه است و از راه یک کش خوانده می‌شود. ثابت‌ها در Flash می‌مانند ولی اولین دسترسی به یک ثابت (وقتی در کش نیست) کندتر است. جزئیات را در بخش «ESP32 و IRAM» پایین‌تر می‌بینی.

هزینهٔ float، double و تقسیم

در PC نوشتن double و تقسیم بی‌دردسر است. در میکروکنترلر این‌ها قیمت دارند و قیمتشان به ساختار CPU بستگی دارد. سه واقعیت را ببین:

  1. STM32F411 (Cortex-M4F): یک واحد ممیز شناور (FPU) تک‌دقتی دارد. یعنی float (۳۲ بیتی) با یک دستور سخت‌افزاری انجام می‌شود، ولی double (۶۴ بیتی) نه.
  2. Cortex-M0 و M0+: نه FPU دارند و نه دستور تقسیم سخت‌افزاری.
  3. هرچه سخت‌افزار ندارد، نرم‌افزار جبران می‌کند: کتابخانهٔ کامپایلر (libgcc) تابع‌هایی مثل __aeabi_dmul و __aeabi_uidiv دارد که با ده‌ها یا صدها دستور همان کار را می‌کنند (به این می‌گویند ممیز شناور نرم‌افزاری).
#include <stdint.h>

volatile uint32_t in_raw;
volatile uint32_t out_val;

int main(void)
{
    for (;;) {
#if defined(USE_DOUBLE)
        double t = (double)in_raw * 3.3 / 4095.0;
        out_val = (uint32_t)(t * 1000.0);
#elif defined(USE_FLOAT)
        float t = (float)in_raw * 3.3f / 4095.0f;
        out_val = (uint32_t)(t * 1000.0f);
#else
        out_val = in_raw * 3300u / 4095u;
#endif
    }
}
  1. ورودی و خروجی volatile. تا کامپایلر محاسبه را حذف نکند.
  2. نسخهٔ double. ثابت 3.3 بدون f از نوع double است. دلیل: در C، عدد اعشاری بدون پسوند double حساب می‌شود؛ یک 3.3 فراموش‌شده کل عبارت را double می‌کند.
  3. نسخهٔ float. با پسوند f همه‌چیز تک‌دقتی می‌ماند.
  4. نسخهٔ صحیح. همان تبدیل با عدد صحیح و بدون اعشار (ضرب، بعد تقسیم).

همان برنامه را چهار جور می‌سازیم: صحیح، float با FPU سخت‌افزاری، float بدون FPU (نرم‌افزاری) و double. همه با -Os و کتابخانهٔ libgcc:

و printf با %f؟

در newlib (کتابخانهٔ C پیش‌فرض arm-none-eabi-gcc) گزینهٔ --specs=nano.specs نسخهٔ کوچک‌شدهٔ کتابخانه (newlib-nano) را انتخاب می‌کند که printf و malloc بسیار سبک‌تر دارد. در همین نسخه، چاپ float با %f به‌طور پیش‌فرض کار نمی‌کند؛ باید صریحا -u _printf_float به لینکر بدهی و این کار هزینهٔ زیادی در Flash دارد. در محیط ساخت این درس کتابخانهٔ newlib نصب نبود، پس عدد قابل‌تکرار برایش نمی‌نویسم؛ در پروژهٔ خودت با size اندازه بگیر. راه ارزان‌تر: عدد را صحیح نگه دار (مثلا دما به‌صورت صدم درجه، درس ۴.۷) و نقطهٔ اعشار را خودت در متن بگذار.

شمارندهٔ چرخه (DWT)

در Cortex-M3/M4 (و M7، با یک قید که پایین‌تر می‌آید) بلوکی به نام DWT هست که یک شمارندهٔ چرخه ۳۲ بیتی دارد که در هر چرخهٔ ساعت CPU یکی زیاد می‌شود. سه رجیستر (آدرس‌ها از مستندات ARM برای معماری ARMv7-M): DEMCR در 0xE000EDFC که بیت ۲۴ آن (TRCENA) کل بلوک‌های DWT و ITM را روشن می‌کند؛ DWT_CTRL در 0xE0001000 که بیت ۰ آن (CYCCNTENA) شمارنده را روشن می‌کند؛ و DWT_CYCCNT در 0xE0001004 که خود شمارنده است. با ابزارک این دو بیت را روشن کن (مثل درس ۵.۲):

#include <stdint.h>

#define DEMCR       (*(volatile uint32_t *)0xE000EDFCu)
#define DWT_CTRL    (*(volatile uint32_t *)0xE0001000u)
#define DWT_CYCCNT  (*(volatile uint32_t *)0xE0001004u)

#define DEMCR_TRCENA        (1u << 24)
#define DWT_CTRL_CYCCNTENA  (1u << 0)

void cyc_init(void)
{
    DEMCR |= DEMCR_TRCENA;              /* روشن کردن DWT */
    DWT_CYCCNT = 0u;                    /* شمارنده از صفر */
    DWT_CTRL |= DWT_CTRL_CYCCNTENA;     /* شروع شمردن */
}

static inline uint32_t cyc_now(void)
{
    return DWT_CYCCNT;
}

volatile uint32_t n_in = 1000u;         /* ورودی: کامپایلر نباید مقدارش را بداند */
volatile uint32_t sink;                 /* نتیجه: کامپایلر نباید بتواند حذفش کند */

static uint32_t work(uint32_t n)
{
    uint32_t x = 0;
    for (uint32_t i = 0; i < n; i++) {
        x += i * i;
    }
    return x;
}

uint32_t measure(void)
{
    uint32_t t0 = cyc_now();
    sink = work(n_in);
    uint32_t t1 = cyc_now();
    return t1 - t0;                     /* بدون علامت: سرریز شمارنده هم درست حساب می‌شود */
}

uint32_t measure_overhead(void)
{
    uint32_t t0 = cyc_now();
    uint32_t t1 = cyc_now();
    return t1 - t0;                     /* هزینهٔ خود اندازه‌گیری */
}
  1. سه رجیستر. همان الگوی volatile + آدرس ثابت که از درس ۳.۶ می‌شناسی.
  2. ماسک بیت‌ها. TRCENA بیت ۲۴ و CYCCNTENA بیت ۰. دلیل: با |= فقط همان بیت را روشن می‌کنیم و بقیهٔ بیت‌های رجیستر دست‌نخورده می‌مانند.
  3. راه‌اندازی. اول بلوک DWT را روشن می‌کنیم، بعد شمارنده را صفر و بعد فعالش می‌کنیم. دلیل: اگر TRCENA خاموش باشد، نوشتن در رجیسترهای DWT اثری ندارد.
  4. خواندن شمارنده. یک تابع static inline کوچک؛ کامپایلر آن را به یک ldr تبدیل می‌کند.
  5. دو volatile برای صداقت اندازه‌گیری. اگر ورودی ثابت باشد، کامپایلر کل حلقه را در زمان کامپایل حساب می‌کند (در تمرین ۲ می‌بینی). اگر نتیجه استفاده نشود، حذفش می‌کند.
  6. کاری که می‌خواهیم زمانش را بدانیم. جمع مربع‌ها.
  7. اندازه‌گیری. شمارنده قبل و بعد خوانده می‌شود و t1 - t0 تعداد چرخه‌هاست. دلیل: تفریق بدون علامت ۳۲ بیتی حتی اگر شمارنده بین دو خواندن از 0xFFFFFFFF به صفر سرریز کند، جواب درست می‌دهد (درس ۴.۷).
  8. هزینهٔ اندازه‌گیری. دو خواندن پشت سر هم چند چرخه طول می‌کشد. این عدد را از نتیجهٔ بالا کم کن.
روی Cortex-M7 یک قدم بیشتر لازم است

در بسیاری از تراشه‌های Cortex-M7 (مثل STM32F7 و H7) پیش از نوشتن در رجیسترهای DWT باید قفل را باز کنی: مقدار 0xC5ACCE55 را در DWT_LAR (آدرس 0xE0001FB0) بنویس؛ وگرنه CYCCNT صفر می‌ماند. این درس فقط STM32F411 (Cortex-M4) را هدف دارد و کد بالا همان‌جا درست است؛ برای M7 به مستندات تراشه‌ات نگاه کن (CMSIS هم برای آن ماکرو دارد).

دو تله در زمان‌سنجی
  • سرریز: شمارنده ۳۲ بیتی است. با ۱۶ مگاهرتز (HSI) هر ۲۶۸٫۴ ثانیه و با ۱۰۰ مگاهرتز (بیشینهٔ STM32F411) هر ۴۲٫۹ ثانیه به صفر برمی‌گردد. برای اندازه‌گیری‌های بلندتر از این، از تایمر استفاده کن.
  • ISR: اگر وسط اندازه‌گیری وقفه بیاید، زمان ISR هم شمرده می‌شود. برای اندازهٔ خالص، وقفه‌ها را (موقتا) غیرفعال کن یا چند بار اندازه بگیر و کمینه را بردار.

راه دوم: یک پایه و اسیلوسکوپ

وقتی DWT نداری (Cortex-M0) یا می‌خواهی با چشم ببینی، یک پایه را قبل از کار روشن و بعد از آن خاموش کن. پهنای پالس روی اسیلوسکوپ یا تحلیلگر منطقی (درس ۶.۱) همان زمان اجراست. اینجا PA5 (LED روی Nucleo) با رجیستر BSRR (بیت‌های ۰ تا ۱۵ = ۱ کن، بیت‌های ۱۶ تا ۳۱ = صفر کن؛ درس ۵.۲):

#include <stdint.h>

#define GPIOA_BSRR (*(volatile uint32_t *)0x40020018u)
#define PIN_SET    (1u << 5)            /* PA5 = 1 */
#define PIN_CLR    (1u << (5 + 16))     /* PA5 = 0 */

extern void work_under_test(void);

void bench_pin(void)
{
    GPIOA_BSRR = PIN_SET;
    work_under_test();
    GPIOA_BSRR = PIN_CLR;
}
  1. تنظیم و پاک‌کردن با یک نوشتن. BSRR فقط بیت‌های ۱ را اثر می‌دهد، پس بدون خواندن-تغییر-نوشتن پایه عوض می‌شود. دلیل: سریع است (یک نوشتن) و اگر وسط کار وقفه بیاید، بقیهٔ پایه‌های پورت خراب نمی‌شوند.
  2. کار مورد آزمایش. در فایل دیگری تعریف می‌شود؛ extern یعنی «جای دیگر است».
  3. قاب پالس. پایه بالا ← کار ← پایه پایین.

انتخاب الگوریتم از پرچم مهم‌تر است

از یک چیز در بهینه‌سازی نباید غافل شد: سطح -O معمولاً چند برابر سریع‌تر می‌کند (ضریب دقیق به کد بستگی دارد و باید اندازه بگیری؛ در این درس فقط اندازهٔ کد را اندازه گرفتیم)، ولی عوض کردن روش گاهی ده‌ها برابر می‌کند. مثال: شمردن بیت‌های ۱ در یک عدد ۱۶ بیتی (بیت‌شماری، popcount که در درس ۳.۱ دیده‌ای) با سه روش، برای همهٔ ۶۵۵۳۶ مقدار ممکن. شمارنده‌ای می‌گذاریم که «تعداد قدم‌های انجام‌شده» را بشمارد. این عدد از کامپایلر و سطح -O مستقل و همیشه یکسان است:

#include <stdio.h>
#include <stdint.h>

static unsigned steps;                      /* شمارندهٔ «کار» انجام‌شده */
static uint8_t table[256];                  /* جدول تعداد بیت‌های هر بایت */

static uint8_t pop_loop(uint16_t x)         /* راه ۱: هر ۱۶ بیت را بررسی کن */
{
    uint8_t n = 0;
    for (int i = 0; i < 16; i++) {
        steps++;
        n += (uint8_t)((x >> i) & 1u);
    }
    return n;
}

static uint8_t pop_kern(uint16_t x)         /* راه ۲: فقط به تعداد بیت‌های ۱ دور بزن */
{
    uint8_t n = 0;
    while (x != 0u) {
        steps++;
        x = (uint16_t)(x & (x - 1u));       /* پایین‌ترین بیت ۱ را پاک می‌کند */
        n++;
    }
    return n;
}

static uint8_t pop_table(uint16_t x)        /* راه ۳: دو بار در جدول نگاه کن */
{
    steps += 2u;
    return (uint8_t)(table[x & 0xFFu] + table[x >> 8]);
}

int main(void)
{
    for (unsigned v = 0; v < 256u; v++) {   /* پر کردن جدول (یک‌بار، مثلا در بوت) */
        table[v] = (uint8_t)((v & 1u) + table[v >> 1]);
    }

    unsigned total1 = 0, total2 = 0, total3 = 0;
    unsigned s1, s2, s3;

    steps = 0;
    for (unsigned v = 0; v < 65536u; v++) total1 += pop_loop((uint16_t)v);
    s1 = steps;
    steps = 0;
    for (unsigned v = 0; v < 65536u; v++) total2 += pop_kern((uint16_t)v);
    s2 = steps;
    steps = 0;
    for (unsigned v = 0; v < 65536u; v++) total3 += pop_table((uint16_t)v);
    s3 = steps;

    printf("results equal: %s\n", (total1 == total2 && total2 == total3) ? "yes" : "NO");
    printf("loop : %u steps\n", s1);
    printf("kern : %u steps\n", s2);
    printf("table: %u steps\n", s3);
    return 0;
}
  1. شمارنده و جدول. steps تعداد قدم‌ها را جمع می‌زند؛ table برای راه سوم.
  2. راه ۱: همهٔ بیت‌ها. همیشه ۱۶ دور، مهم نیست چند بیت ۱ باشد.
  3. راه ۲: ترفند Kernighan. x & (x - 1) پایین‌ترین بیت ۱ را پاک می‌کند؛ پس فقط به تعداد بیت‌های ۱ دور می‌زند. دلیل: از ۰b10110000 کم‌کردن ۱ می‌شود ۰b10101111؛ AND این دو ۰b10100000 است، یعنی همان یک بیت پاک شد.
  4. راه ۳: جدول. تعداد بیت‌های ۱ هر بایت از پیش حساب شده؛ دو نگاه (بایت پایین و بالا) کافی است.
  5. ساختن جدول. table[v] = (v & 1) + table[v >> 1]: تعداد بیت‌های ۱ برابر است با بیت آخر + تعداد بیت‌های ۱ بقیه.
  6. اجرا برای همهٔ ۶۵۵۳۶ مقدار. هر راه یک بار.
  7. چاپ. اول اطمینان از برابری نتیجه‌ها (بدون این، سرعت بی‌معناست) و بعد شمار قدم‌ها.

راه سوم هشت برابر کمتر از راه اول قدم دارد، بدون هیچ پرچمی. ولی هزینه هم دارد: ۲۵۶ بایت جدول (در Flash، با const، کافی است). هر بهینه‌سازی یک «مبادله» است: اینجا Flash را با سرعت معاوضه کردیم. بعد از همهٔ این‌ها بازهم باید برنامهٔ خودت را روی سخت‌افزار اندازه بگیری؛ Cortex-M4 دستور popcount ندارد؛ __builtin_popcount روی آن به صدا زدن تابعی از libgcc (__popcountsi2) ختم می‌شود که خودش کد و چرخهٔ اضافه می‌خواهد. روی هسته‌هایی که دستورش را دارند ممکن است یک دستور بشود. پس بنچ‌مارک روی همان تراشهٔ مقصد تصمیم می‌گیرد که جدول بهتر است یا نه.

زیر کاپوت: «زودرس بهینه نکن»

دونالد کنوث (Donald Knuth) جمله‌ای معروف دارد که می‌گوید بهینه‌سازی زودرس «ریشهٔ بسیاری از بدی‌هاست». معنی‌اش این نیست که کد کند بنویسی. معنی‌اش این است که قبل از اندازه‌گیری کد را تیره و پیچیده نکنی. معمولا بخش کوچکی از برنامه (اغلب چند حلقه) بیشتر زمان را می‌خورد و فقط همان‌جا ارزش تلاش دارد. اول درست بنویس، بعد اندازه بگیر، بعد فقط نقطهٔ داغ را عوض کن، و دوباره اندازه بگیر.

در ESP32 چه فرق می‌کند؟

ابزارها فرق دارند، ولی اصل همان است: اندازه بگیر.

  • سطح بهینه‌سازی: در ESP-IDF از idf.py menuconfig، بخش تنظیمات کامپایلر (Compiler options)، سطح را انتخاب می‌کنی. چند گزینه هست (مثل «Debug» با -Og، «Optimize for size» با -Os و «Optimize for performance» با -O2)؛ نام دقیق و پیش‌فرض را در نسخهٔ خودت ببین («در مستندات رسمی ESP-IDF بخش Build System»).
  • اندازه: idf.py size خلاصهٔ مصرف Flash و RAM را می‌دهد؛ idf.py size-components و idf.py size-files آن را به تفکیک کامپوننت و فایل نشان می‌دهند (هم‌ارز nm --size-sort و map). فایل map هم در پوشهٔ build ساخته می‌شود.
  • Flash بیرونی و کش: کد و ثابت‌های ESP32 در Flash بیرونی هستند و از راه یک کش خوانده می‌شوند. هنگام نوشتن روی Flash (مثلا ذخیرهٔ تنظیمات) کش برای مدت کوتاهی غیرفعال است و کدی که در Flash است نمی‌تواند اجرا شود.
  • IRAM_ATTR: تابعی را که باید همیشه (حتی وقتی کش خاموش است) و با کمترین تأخیر اجرا شود، مثل بعضی ISR ها، با این ویژگی علامت می‌زنی تا در حافظهٔ داخلی (IRAM) بماند. داده‌ای که آن ISR می‌خواند باید در RAM داخلی باشد (DRAM_ATTR اگر لازم شد). جزئیات را در «مستندات رسمی ESP-IDF، بخش Memory types و Interrupt allocation» ببین.
  • زمان: esp_timer_get_time() زمان را با دقت میکروثانیه برمی‌گرداند و برای اندازه‌گیری‌های معمولی کافی است.
#include "esp_attr.h"
#include "esp_log.h"
#include "esp_timer.h"
#include "driver/gpio.h"

static const char *TAG = "opt";
static volatile uint32_t edge_count;

static void IRAM_ATTR button_isr(void *arg)   /* در IRAM می‌ماند */
{
    (void)arg;
    edge_count++;                             /* کوتاه و بدون منتظر ماندن */
}

void app_main(void)
{
    gpio_config_t io = {
        .pin_bit_mask = 1ULL << GPIO_NUM_0,
        .mode = GPIO_MODE_INPUT,
        .pull_up_en = GPIO_PULLUP_ENABLE,
        .intr_type = GPIO_INTR_NEGEDGE,
    };
    gpio_config(&io);
    gpio_install_isr_service(0);
    gpio_isr_handler_add(GPIO_NUM_0, button_isr, NULL);

    int64_t t0 = esp_timer_get_time();        /* میکروثانیه */
    /* ... کار مورد آزمایش ... */
    int64_t dt = esp_timer_get_time() - t0;
    ESP_LOGI(TAG, "work took %lld us", (long long)dt);
}
  1. هدرها. esp_attr.h ماکروی IRAM_ATTR را می‌دهد؛ esp_timer.h زمان؛ driver/gpio.h پایه‌ها.
  2. ISR در IRAM. ویژگی IRAM_ATTR جلوی تابع؛ بدنه فقط یک شمارنده را زیاد می‌کند. دلیل: ISR باید کوتاه باشد و نباید به چیزی در Flash وابسته باشد که ممکن است در آن لحظه در دسترس نباشد.
  3. پیکربندی پایه. ورودی با pull-up و وقفه روی لبهٔ پایین‌رونده (دکمهٔ BOOT معمولا روی GPIO0).
  4. ثبت ISR. اول سرویس وقفه نصب می‌شود، بعد تابع به پایه وصل می‌شود.
  5. زمان‌سنجی. اختلاف دو خواندن esp_timer_get_time(). لاگ با %lld و تبدیل صریح به long long که روی هر معماری درست باشد.

خروجی arm-none-eabi-size برای برنامه‌ای این است: text = 296، data = 4، bss = 80. چقدر RAM (بدون پشته) می‌گیرد؟

  2. ۸۴ بایت

  4. ۴ بایت

تابع wait_ready() با while (ready == 0u) {} و متغیر معمولی ready در -O0 درست کار می‌کند و در -O2 برای همیشه گیر می‌کند. علت چیست؟

  1. باگ کامپایلر -O2 است
  2. نوع uint32_t برای پرچم کوچک است
  3. حلقهٔ خالی در C ممنوع است
  4. کامپایلر دید ready در این فایل هیچ‌وقت نوشته نمی‌شود و خواندنش را حذف کرد؛ باید volatile باشد
بدون volatile کامپایلر فرض می‌کند متغیر تغییر نمی‌کند و شرط را یک بار می‌سنجد. نتیجه b .L2 است؛ پرش بی‌پایان به خودش.

در آزمایش ما با -O3 اندازهٔ text ۴۷۶ و با -O2 ۳۲۸ بایت شد. کدام نتیجه درست است؟

  1. سطح بالاتر همیشه کد کوچک‌تر نمی‌دهد؛ -O3 ممکن است کد را بزرگ کند و باید هر سطح را اندازه بگیری
  2. سطح بالاتر یعنی همیشه Flash کمتر
  3. اندازه‌گیری اشتباه بوده است
  4. استفاده از -Os برای Cortex-M ممنوع است
هر سطح مجموعه‌ای از مبادله‌هاست. -O3 با باز کردن حلقه و inline بیشتر، کد را بزرگ‌تر کرد. حکم کلی وجود ندارد؛ روی برنامهٔ خودت اندازه بگیر.

برنامه‌ای روی Cortex-M0 دارد در هر دور یک حلقهٔ داغ y = x / n; (متغیر n) اجرا می‌کند و کند است. کدام اقدام اول منطقی‌تر است؟

  1. تبدیل همه‌چیز به float
  2. همهٔ متغیرها را volatile کردن
  3. اندازه بگیری تقسیم واقعا گلوگاه است؛ اگر بود، مقسوم‌علیه را توان ۲ کنی (شیفت) یا تقسیم را از حلقه بیرون ببری
  4. کل حلقه را به اسمبلی بنویسی
M0 دستور تقسیم ندارد و __aeabi_uidiv را صدا می‌زند. ولی اول باید اندازه بگیری؛ بعد ساده‌ترین راه (توان ۲ یا بیرون بردن از حلقه) را امتحان کنی.

کدام خط در برنامه‌ای برای STM32F411 بی‌سروصدا بخش بزرگی از Flash و سرعت را می‌خورد؟

  1. ‏uint32_t mv = raw * 3300u / 4095u;
  2. ‏double v = raw * 3.3 / 4095.0;
  3. ‏float v = raw * 3.3f / 4095.0f;
  4. ‏uint32_t half = raw >> 1;
STM32F411 فقط FPU تک‌دقتی دارد. double نرم‌افزاری است و در آزمایش ما اندازهٔ برنامه را از ۱۰۰ به ۲۷۷۶ بایت رساند. 3.3 بدون f از نوع double است.

برای اندازه‌گیری زمان یک تابع با شمارندهٔ DWT نوشته‌ای t1 - t0 با نوع uint32_t. شمارنده بین دو خواندن از 0xFFFFFFFE به 0x00000003 رسید. نتیجه چیست؟

  1. ۵ چرخه؛ چون تفریق بدون علامت ۳۲ بیتی مدولار است و سرریز را درست جبران می‌کند
  2. عدد منفی؛ باید int32_t بگیری
  3. حدود ۴ میلیارد چرخه
  4. رفتار تعریف‌نشده
3 − 0xFFFFFFFE در حساب مدولار ۲³² برابر ۵ است (دو چرخه تا صفر و سه چرخهٔ دیگر تا 3). همین ویژگی است که اندازه‌گیری‌های کوتاه با شمارندهٔ سرریزشونده را امن می‌کند.

تمرین ۲: بنچمارکی که هیچ‌چیز را اندازه نمی‌گرفت (پیدا کردن باگ)

دوستت برای اندازه‌گیری زمان work(1000) این تابع را نوشته و می‌گوید «با -O2 صفر چرخه شد، عجب سرعتی!».

#include <stdint.h>

uint32_t work(uint32_t n)
{
    uint32_t x = 0;
    for (uint32_t i = 0; i < n; i++) {
        x += i * i;
    }
    return x;
}

void bench_bug(void)
{
    work(1000u);                /* نتیجه را هیچ‌جا نمی‌گذاریم */
}
  1. تشخیص: با -O2 -S اسمبلی bench_bug را نگاه کن. چند دستور است؟ چرا؟
  2. تلاش اول: نتیجه را در یک متغیر volatile uint32_t sink بریز (sink = work(1000u);). آیا حلقه در اسمبلی برگشت؟ چرا؟
  3. حل واقعی: ورودی را هم volatile کن و دوباره نگاه کن. توضیح بده هر دو volatile برای چیست.
راهنمایی

کامپایلر می‌تواند تابعی را که فقط عدد حساب می‌کند و نتیجه‌اش استفاده نمی‌شود کلا حذف کند. و اگر ورودی‌ها همه ثابت باشند، خود حلقه را در زمان کامپایل حل می‌کند (مثل fold.c).

چه باید ببینی؟

در اسمبلی bench_bug فقط یک دستور است: برگرد. کل کار حذف شده. (خروجی کامل -S تابع work: را هم دارد، چون static نیست؛ فقط برچسب bench_bug: را نگاه کن. همین برای bench_fix هم صدق می‌کند.)

جواب کامل با توضیح

الف) bench_bug فقط bx lr است، چون work هیچ اثر جانبی ندارد و نتیجه‌اش دور ریخته می‌شود؛ کامپایلر کل فراخوانی را حذف کرد. ب) با sink = work(1000u) فراخوانی می‌ماند، ولی چون 1000 ثابت است، خود حلقه هم در زمان کامپایل حل می‌شود و فقط یک عدد در sink نوشته می‌شود (یک str با ثابت). پ) با ورودی volatile کامپایلر مقدار را نمی‌داند و باید حلقه را واقعا اجرا کند. حالا زمان اندازه‌گیری‌شده واقعی است.

#include <stdint.h>

volatile uint32_t n_in = 1000u;         /* ورودی «مرموز» برای کامپایلر */
volatile uint32_t sink;                 /* مقصد «واقعی» نتیجه */

uint32_t work(uint32_t n)
{
    uint32_t x = 0;
    for (uint32_t i = 0; i < n; i++) {
        x += i * i;
    }
    return x;
}

void bench_fix(void)
{
    sink = work(n_in);                  /* ورودی را نمی‌داند و نتیجه را باید بنویسد */
}
  1. ورودی volatile. هر بار از حافظه خوانده می‌شود و کامپایلر مقدارش را نمی‌داند.
  2. خروجی volatile. نوشتن در آن یک اثر جانبی قابل‌مشاهده است و نباید حذف شود.
  3. تابع بنچمارک. ورودی از n_in می‌آید و نتیجه در sink می‌رود.

تمرین ۳: چرخه به میکروثانیه

با DWT تعداد چرخهٔ یک کار را گرفته‌ای؛ حالا باید به زمان تبدیل کنی. کلاک پیش‌فرض STM32F411 (HSI) ۱۶ مگاهرتز است و بیشینه‌اش ۱۰۰ مگاهرتز.

  1. حساب دستی: ۱۶۰۰ چرخه با ۱۶ مگاهرتز چند میکروثانیه است؟ ۳۲۰۰ چرخه با ۱۰۰ مگاهرتز؟
  2. تابع: uint32_t cycles_to_us(uint32_t cycles, uint32_t hz) بنویس. مراقب باش cycles * 1000000 در ۳۲ بیت سرریز نکند.
  3. چالش سخت‌افزاری: شمارندهٔ ۳۲ بیتی DWT با ۱۶ و با ۱۰۰ مگاهرتز بعد از چند ثانیه سرریز می‌کند؟ این چه محدودیتی برای اندازه‌گیری می‌گذارد؟
راهنمایی

زمان = چرخه ÷ فرکانس. برای اینکه ضرب سرریز نکند، قبل از ضرب به uint64_t تبدیل کن (درس ۴.۷).

چه باید ببینی؟

جواب کامل با توضیح 
#include <stdio.h>
#include <stdint.h>

static uint32_t cycles_to_us_bad(uint32_t cycles, uint32_t hz)
{
    return cycles * 1000000u / hz;          /* ضرب ۳۲ بیتی: ممکن است سرریز کند */
}

static uint32_t cycles_to_us(uint32_t cycles, uint32_t hz)
{
    return (uint32_t)((uint64_t)cycles * 1000000u / hz);   /* ضرب ۶۴ بیتی: امن */
}

int main(void)
{
    printf("1600 cycles @ 16 MHz  : good %u us, bad %u us\n",
           (unsigned)cycles_to_us(1600u, 16000000u), (unsigned)cycles_to_us_bad(1600u, 16000000u));
    printf("5000 cycles @ 16 MHz  : good %u us, bad %u us\n",
           (unsigned)cycles_to_us(5000u, 16000000u), (unsigned)cycles_to_us_bad(5000u, 16000000u));
    printf("3200 cycles @ 100 MHz : good %u us\n", (unsigned)cycles_to_us(3200u, 100000000u));
    printf("counter wraps after %.1f s @ 16 MHz\n", 4294967296.0 / 16000000.0);
    printf("counter wraps after %.1f s @ 100 MHz\n", 4294967296.0 / 100000000.0);
    return 0;
}
  1. نسخهٔ خراب. cycles * 1000000u با ۳۲ بیت حساب می‌شود. دلیل: ۵۰۰۰ × ۱۰۰۰۰۰۰ = ۵ میلیارد و بزرگ‌تر از ۴٫۲۹ میلیارد (حد uint32_t) است؛ نتیجه مدولار می‌شود و جواب بی‌معنی (۴۴ به‌جای ۳۱۲) برمی‌گردد.
  2. نسخهٔ درست. اول به uint64_t تبدیل می‌کنیم و بعد ضرب و تقسیم؛ جای (uint64_t) مهم است. دلیل: اگر بنویسی (uint64_t)(cycles * 1000000u)، ضرب همچنان ۳۲ بیتی است و بعد از سرریز تبدیل می‌شود.
  3. مقایسه. برای ۱۶۰۰ چرخه هر دو درست‌اند، ولی برای ۵۰۰۰ چرخه نسخهٔ خراب اشتباه می‌کند.
  4. زمان سرریز. ۲³² چرخه تقسیم بر فرکانس: ۲۶۸٫۴ ثانیه با ۱۶ مگاهرتز و ۴۲٫۹ ثانیه با ۱۰۰ مگاهرتز. برای اندازه‌گیری طولانی‌تر باید سرریز را بشماری یا از تایمر ۳۲ بیتی/۶۴ بیتی استفاده کنی.

حرف مربی

تقریبا همه در این درس سه جا گیر می‌کنند. اول: بهینه‌سازی را با «ریز‌ریز کردن کد» اشتباه می‌گیرند. اول size و map را نگاه کن؛ معمولا یک کتابخانهٔ بزرگ یا یک جدول const نشده مقصر است، نه کدی که ساعت‌ها صرفش کرده‌ای. دوم: برنامه‌ای که فقط با -O0 کار می‌کند «برنامه‌ای که کار می‌کند» نیست؛ آن را با همان سطحی که می‌فرستی تست کن. سوم: بنچمارک (benchmark) بد (نتیجه‌ای که کامپایلر حذفش می‌کند) عدد دروغ می‌دهد و از هیچ عددی بدتر است. هر بار که عدد عجیب خوب دیدی (صفر چرخه!)، اسمبلی را نگاه کن.

خلاصه یک‌دقیقه‌ای

  • اول اندازه بگیر: arm-none-eabi-size (Flash = text + data؛ RAM = data + bss)، nm --size-sort، فایل map و --print-memory-usage.
  • -O0 برای دیباگ، -Og برای توسعه، -Os/-O2 برای محصول؛ -O3 لزوما بهتر نیست. در برنامهٔ ما: ۵۶۰ (-O0) ← ۲۹۶ (-Os) بایت.
  • کامپایلر ثابت‌ها را حساب می‌کند، کد مرده را دور می‌ریزد، توابع کوچک را inline می‌کند و متغیرها را در رجیستر نگه می‌دارد (۱۶ دستور ← ۴ دستور برای یک دور حلقه).
  • volatile را فراموش کنی، -O2 حلقهٔ انتظارت را به b .L2 تبدیل می‌کند.
  • -ffunction-sections -fdata-sections -Wl,--gc-sections تابع‌های بی‌مصرف را دور می‌ریزد؛ جدول‌ها را const کن تا در Flash بمانند.
  • double روی M4F نرم‌افزاری است (۱۰۰ ← ۲۷۷۶ بایت)؛ M0 تقسیم سخت‌افزاری ندارد.
  • زمان را با DWT (DEMCR بیت ۲۴، DWT_CTRL بیت ۰، DWT_CYCCNT) یا پایه و اسیلوسکوپ اندازه بگیر؛ بنچمارک را از حذف‌شدن توسط کامپایلر نجات بده.
  • الگوریتم بهتر (۱۰۴۸۵۷۶ ← ۱۳۱۰۷۲ قدم) از هر پرچمی مهم‌تر است؛ ولی همیشه «اندازه بگیر، یک تغییر بده، دوباره اندازه بگیر».
