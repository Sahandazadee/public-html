تا اینجا هر چه نوشتی، مستقیم به کامپایلر رسید. ولی پیش از کامپایلر یک ایستگاه کوچک هست که فقط با متن کار می‌کند: کپی می‌کند، جایگزین می‌کند و بعضی تکه‌ها را دور می‌اندازد. تقریبا هر پروژهٔ واقعی برای STM32 و ESP32 از آن برای پیکربندی برد، نام‌گذاری رجیسترها و روشن‌کردن لاگ استفاده می‌کند. در این درس یاد می‌گیری این ایستگاه چه می‌کند و چرا یک جفت پرانتز جا افتاده می‌تواند ساعت‌ها وقتت را بگیرد.

🎯 بعد از این درس می‌توانی

  • بگویی پیش‌پردازنده چه می‌کند و چه نمی‌کند، و نتیجه‌اش را با gcc -E ببینی
  • ثابت را با #define، const و enum بسازی و فرقشان را بدانی
  • ماکروی تابع‌مانند را درست (با پرانتز و do { } while (0)) بنویسی
  • کد را برای چند برد با #if، #ifdef و -D شرطی کامپایل کنی
  • include guard بنویسی و خطای «redefinition» را رفع کنی
  • ماکروهای رجیستر (BIT، REG32) بخوانی و بنویسی

🧰 پیش‌نیاز و وسایل

  • درس ۱.۴ (چهار مرحلهٔ ساخت و #include)
  • درس ۲.۶ (تابع) و ۳.۱ (عملگر بیتی و ماسک)
  • درس ۳.۶ (رجیستر و volatile) برای بخش آخر
  • فقط gcc روی رایانه؛ سخت‌افزار لازم نیست

ایده اصلی: «پیدا کن و جایگزین کن» پیش از چاپ

فرض کن پایان‌نامه‌ای نوشته‌ای و اسم استاد راهنما را ۴۰ بار تایپ کرده‌ای. روز آخر معلوم می‌شود اسمش را غلط نوشته‌ای. راهش این نیست که ۴۰ جا را دستی درست کنی؛ در ویرایشگر «پیدا کن و جایگزین کن» را می‌زنی. ویرایشگر معنی جمله را نمی‌فهمد؛ فقط متن را عوض می‌کند.

مثال از زندگی روزمره

یک کارمند چاپخانه را تصور کن که پیش از چاپ، پایان‌نامه را با یک برگهٔ دستور می‌خواند: «هر جا نوشته نام‌استاد، بنویس دکتر احمدی»؛ «این فصل را فقط در نسخهٔ رنگی بگذار»؛ «پیوست ۲ را از فایل دیگر بیاور و همین‌جا بچسبان». او هیچ‌چیز از محتوای علمی نمی‌فهمد. فقط دستورهای متنی را اجرا می‌کند و بعد نسخهٔ تمیز را به چاپگر می‌دهد. پیش‌پردازنده (preprocessor) در C همین کارمند است و چاپگر همان کامپایلر.

خط‌هایی که با # شروع می‌شوند (#include، #define، #if و...) دستور این کارمندند و به آن‌ها دستورهای پیش‌پردازنده می‌گوییم. کامپایلر هرگز آن‌ها را نمی‌بیند؛ چون پیش‌پردازنده اول همه را اجرا و پاک می‌کند.

زیر کاپوت: «فقط متن» یعنی چه؟

پیش‌پردازنده نمی‌داند int چیست، تابع چیست یا حتی MAX_TEMP عدد است یا اسم. فقط «تکه‌های متن» (به اصطلاح توکن‌ها) را می‌بیند و طبق دستورهایش جابه‌جا می‌کند. به همین دلیل خطاهایی که در ماکروها می‌بینی عجیب‌اند: خطا را کامپایلر روی متنِ جایگزین‌شده می‌گیرد، نه روی چیزی که تو نوشتی.

#include: چسباندن یک فایل

دستور #include ساده‌ترین دستور است: کل محتوای یک فایل را به‌جای همین خط می‌چسباند. در درس‌های قبل همیشه #include <stdio.h> را نوشتی. یعنی متن فایل stdio.h (اعلان printf و دوستانش) عینا اینجا کپی می‌شود.

#define: نام‌گذاری یک تکه متن

ساده‌ترین شکل #define یعنی: «از این به بعد هر جا این اسم را دیدی، این متن را جایش بگذار». به چنین اسمی ماکرو (macro) می‌گویند.

#include <stdio.h>

#define MAX_TEMP   80          // ثابت عددی
#define LED_COUNT  4
#define GREETING   "hello"     // ثابت رشته‌ای

int main(void)
{
    int limit = MAX_TEMP;
    int leds[LED_COUNT] = {0};
    printf("%s: limit=%d, leds=%zu\n", GREETING, limit, sizeof(leds) / sizeof(leds[0]));
    return 0;
}
  1. سه ماکرو. بعد از #define اول اسم می‌آید، بعد فاصله، بعد متنی که باید جایش بنشیند تا آخر خط. نقطه‌ویرگول لازم نیست (خودش جزو متن می‌شود!). اسم ماکرو را حروف بزرگ می‌نویسند تا در نگاه اول معلوم باشد «این ثابت است، متغیر نیست».
  2. مصرف ماکرو. پیش‌پردازنده MAX_TEMP را با 80 عوض می‌کند. کامپایلر فقط int limit = 80; را می‌بیند. هیچ قفسه‌ای در RAM برای MAX_TEMP ساخته نمی‌شود؛ عدد ۸۰ مستقیم داخل دستور ماشین می‌نشیند.
  3. اندازهٔ آرایه از ماکرو. اندازهٔ آرایه باید ثابت باشد و LED_COUNT همین‌جا به ۴ تبدیل می‌شود. اگر روزی ۶ LED شد، فقط خط ۴ عوض می‌شود.
  4. چاپ. GREETING به رشتهٔ "hello" تبدیل می‌شود. عبارت sizeof(leds) / sizeof(leds[0]) تعداد عنصرها را می‌دهد (درس ۲.۷).

تلهٔ اول: نقطه‌ویرگول آخر ماکرو

چون ماکرو «هر چیزی تا آخر خط» را جایگزین می‌کند، نقطه‌ویرگول هم جزو جایگزین می‌شود. این باگ مبتدی‌ها را ببین:

#include <stdio.h>

#define MAX_TEMP 80;            // اشتباه: ; جزو ماکرو می‌شود

int main(void)
{
    int t = 90;
    if (t > MAX_TEMP) {
        printf("too hot\n");
    }
    return 0;
}
  1. ماکروی خراب. متن جایگزین 80; است، با نقطه‌ویرگول. پیش‌پردازنده نمی‌فهمد ; «پایان دستور» است؛ برایش فقط یک نویسه است.
  2. مصرف در شرط. بعد از جایگزینی می‌شود if (t > 80;) و کامپایلر پرانتز ناقص می‌بیند. خطا در خط ۸ گزارش می‌شود، ولی علتش خط ۳ است. برای همین یک note اضافه می‌آید که می‌گوید «in expansion of macro».
semi.c: In function 'main':
semi.c:3:20: error: expected ')' before ';' token
semi.c:8:13: note: in expansion of macro 'MAX_TEMP'

قاعده: پیام خطا به ماکرو اشاره کرد، تعریف ماکرو را بخوان. و #define را هرگز با ; تمام نکن.

ماکروی تابع‌مانند و چهار تله‌اش

ماکرو می‌تواند پارامتر هم بگیرد و شبیه تابع رفتار کند. مثلا «بزرگ‌ترِ دو عدد»:

#define MAX(a, b)  ((a) > (b) ? (a) : (b))

اما فرق بزرگی با تابع دارد: تابع مقدار را کپی می‌کند، ماکرو متن را کپی می‌کند. هر جا a بود، دقیقا همان متنی می‌نشیند که به ماکرو دادی. تفاوت به‌نظر کوچک است ولی سه چهار تله از آن می‌آید.

تلهٔ ۱: پرانتز فراموش‌شده

#include <stdio.h>

#define SQUARE_BAD(x)  x * x
#define SQUARE(x)      ((x) * (x))

int main(void)
{
    int n = 3;
    printf("bad : %d\n", SQUARE_BAD(n + 1));
    printf("good: %d\n", SQUARE(n + 1));
    return 0;
}
  1. نسخهٔ بی‌پرانتز. متن جایگزین فقط x * x است. پس SQUARE_BAD(n + 1) می‌شود n + 1 * n + 1. ضرب قبل از جمع اجرا می‌شود (درس ۲.۳، تقدم عملگرها). یعنی n + (1 * n) + 1 = ۳ + ۳ + ۱ = ۷، نه ۱۶.
  2. نسخهٔ درست. پرانتز دور هر پارامتر و دور کل عبارت می‌نشیند. حالا می‌شود ((n + 1) * (n + 1)). پرانتز دور پارامتر جلوی تقدم عملگر را می‌گیرد؛ پرانتز دور کل عبارت جلوی وقتی را که ماکرو داخل عبارت بزرگ‌تری می‌نشیند (مثلا 10 / SQUARE(2)).
  3. دو چاپ. همان ورودی، دو جواب متفاوت.
$ ./square
bad : 7
good: 16

تلهٔ ۲: آرگومان چند بار حساب می‌شود

در ماکرو، متنِ آرگومان هر بار که پارامتر ظاهر می‌شود دوباره اجرا می‌شود. اگر آرگومان اثر جانبی (side effect) داشته باشد، یعنی چیزی را عوض کند (مثل y++)، دو بار عوض می‌شود.

#include <stdio.h>

#define MAX(a, b)  ((a) > (b) ? (a) : (b))

int main(void)
{
    int x = 5;
    int y = 5;
    int m = MAX(x, y++);     // y++ دو جا کپی می‌شود!
    printf("m=%d y=%d\n", m, y);
    return 0;
}
  1. MAX با پرانتز درست. پارامتر b دو بار در متن آمده: یک بار در مقایسه و یک بار در شاخهٔ جواب.
  2. مصرف با اثر جانبی. بعد از جایگزینی می‌شود ((x) > (y++) ? (x) : (y++)). مقایسه یک y++ اجرا می‌کند و چون ۵ > ۵ نادرست است، شاخهٔ دوم هم y++ را دوباره اجرا می‌کند. با تابع، y++ یک‌بار حساب می‌شد و y می‌شد ۶. اینجا ۷ شد. انتظار داشتی m ۵ باشد؛ شد ۶.
  3. چاپ. نتیجه را ببین.
$ ./maxdouble
m=6 y=7

}

تلهٔ ۳: ماکرو با چند دستور و if

گاهی ماکرو باید چند دستور را با هم اجرا کند (مثلا جابه‌جا کردن دو مقدار). اگر ساده بنویسی، وسط if می‌شکند:

#include <stdio.h>

#define SWAP_BAD(a, b)  tmp = a; a = b; b = tmp;

int main(void)
{
    int x = 2, y = 1, tmp;
    if (x > y)
        SWAP_BAD(x, y)
    else
        printf("already ordered\n");
    printf("%d %d\n", x, y);
    return 0;
}
  1. ماکرو با سه دستور. متنش سه دستور جدا با ; است.
  2. مصرف بدون آکولاد. if بدون آکولاد فقط یک دستور بعدی را کنترل می‌کند. پس فقط tmp = x; زیر if است و دو دستور دیگر بیرونش می‌افتند. بعد else جفت ندارد. قاعدهٔ ۲.۴ را یادت هست؟ «همیشه آکولاد». اینجا مشکل از ماکرو است، ولی آکولاد فراموش‌شده آن را پنهان کرده. حتی کامپایلر هشدار می‌دهد که «macro expands to multiple statements».
swap_bad.c: In function 'main':
swap_bad.c:10:5: error: 'else' without a previous 'if'

راه‌حل استاندارد، پیچیدن دستورها در do { ... } while (0) است. این حلقه دقیقا یک بار اجرا می‌شود (شرطش صفر است) و از بیرون مثل «یک دستور» رفتار می‌کند که با ; تمام می‌شود:

#include <stdio.h>

#define SWAP_INT(a, b)  do { int tmp_ = (a); (a) = (b); (b) = tmp_; } while (0)

int main(void)
{
    int x = 2, y = 1;
    if (x > y)
        SWAP_INT(x, y);
    else
        printf("already ordered\n");
    printf("%d %d\n", x, y);
    return 0;
}
  1. do-while صفر. بدنه یک بلوک است (پس می‌تواند متغیر محلی tmp_ داشته باشد و اسمش با متغیرهای بیرون تداخل نمی‌کند) و while (0) آن را دقیقا یک‌بار اجرا می‌کند. در انتها ; نگذاشتیم. آن نقطه‌ویرگول را کاربر ماکرو (خط ۹) می‌نویسد. اگر خود ماکرو هم ; داشت، if ... else باز می‌شکست.
  2. بدون شکستن else. حالا SWAP_INT(x, y); در نگاه if فقط یک دستور است و else جفت درست دارد.
$ ./swap_good
1 2
تلهٔ ۴: ماکرو نوع ندارد و دیباگ‌پذیر نیست

ماکرو با int و float یکسان رفتار می‌کند و کامپایلر نوع را قبل از جایگزینی نمی‌سنجد. در ماکرو نمی‌شود قدم‌به‌قدم (step) رفت، و اسمش در دیباگر معمولا دیده نمی‌شود. برای همین اگر می‌توانی، تابع static inline بنویس (درس ۲.۶). ماکرو را برای کارهایی نگه دار که تابع نمی‌تواند: ساختن اسم، شرطی‌کردن کد، و ثابت‌های زمان کامپایل.

تلهٔ ۴ب: ماکرو نوع‌ها را «قاطی» می‌کند

در MAX(-1, u) که u بی‌علامت است، قاعدهٔ تبدیل حسابی C (درس ۲.۲) -1 را به unsigned تبدیل می‌کند و می‌شود ۴۲۹۴۹۶۷۲۹۵. پس ماکرو «-1 بزرگ‌تر است» را می‌بیند و همان را برمی‌گرداند. ماکرو خودش نوع نمی‌سنجد؛ فقط کامپایلر هشدار -Wsign-compare می‌دهد (پس هشدارها را جدی بگیر).

#include <stdio.h>

#define MAX(a, b)  ((a) > (b) ? (a) : (b))

int main(void)
{
    unsigned int u = 1u;
    printf("%u\n", MAX(-1, u));
    printf("%d\n", MAX(-1, 1));
    return 0;
}
  1. نوع‌های مختلط. یک طرف int منفی و طرف دیگر unsigned؛ -1 به ۴۲۹۴۹۶۷۲۹۵ تبدیل می‌شود و از ۱ بزرگ‌تر به حساب می‌آید. نتیجهٔ ماکرو هم از نوع unsigned است. بازهٔ هر دو نوع یکی نیست؛ پایتون چنین مشکلی ندارد چون عدد صحیحش بی‌کران و بدون نوع ثابت است.
  2. هر دو int. با دو int نتیجه همان ۱ درست است.

کامپایل شرطی: یک کد، چند برد

این کار را کامپایل شرطی (conditional compilation) می‌گویند. فرض کن پروژه‌ات باید روی Nucleo-F411RE (LED روی PA5) و روی ESP32 DevKit (LED معمولا روی GPIO2) کار کند. دو کپی از کد نمی‌سازی، چون هر اصلاح باید دو بار انجام شود. راه بهتر: یک کد بنویس و به پیش‌پردازنده بگو «اگر برد اول بود این تکه را نگه دار، اگر دوم بود آن یکی را».

چرا این «#if» است و «if» معمولی نیست؟

در if (BOARD == 1) معمولی هر دو شاخه در فایل ماشین می‌مانند (کامپایلر ممکن است شاخهٔ مرده را حذف کند، ولی هر دو شاخه باید معتبر باشند و کامپایل شوند). در #if شاخهٔ رد‌شده حتی نباید وجود داشته باشد. برای کدی که از نظر سخت‌افزار روی برد دیگر نمی‌شود کامپایل شود (مثلا نام رجیستری که فقط روی یک تراشه هست) فقط #if جواب می‌دهد. برای رفتار متفاوت در زمان اجرا (مثلا کاربر حالت را عوض می‌کند) if معمولی.

لاگ با چند آرگومان: ماکروی متغیر (__VA_ARGS__)

LOG() بدون هیچ آرگومان خطا می‌دهد؛ ##__VA_ARGS__ (افزونهٔ GNU) این حالت‌ها را شل می‌کند.

include guard: جلوگیری از دوبار چسباندن

فرض کن main.c دو هدر را وارد می‌کند: point.h و shape.h. ولی shape.h خودش هم point.h را وارد می‌کند. نتیجه: point.h دو بار در یک فایل می‌نشیند و struct point دو بار تعریف می‌شود. این ماجرا در پروژه‌های بزرگ دائم پیش می‌آید، چون هدرها هدر دیگر را می‌خوانند. اول بدون محافظ:

struct point {
    int x;
    int y;
};

#include "point.h"

struct segment {
    struct point a;
    struct point b;
};

#include <stdio.h>
#include "point.h"
#include "shape.h"

int main(void)
{
    struct segment s = { {0, 0}, {3, 4} };
    printf("%d\n", s.b.x + s.b.y);
    return 0;
}
  1. دو هدر. اول point.h چسبانده می‌شود (تعریف اول). بعد shape.h که داخلش دوباره point.h است (تعریف دوم!). هر چند به‌نظر کار عاقلانه‌ای کرده‌ایم (هر فایل هدرهای مورد نیازش را می‌آورد)، ولی نتیجهٔ چسباندن دو تعریف یکسان است و C تعریف مجدد یک struct را نمی‌پذیرد.
point.h:1:8: error: redefinition of 'struct point'

راهش include guard (نگهبان include) است: هر هدر را در یک #ifndef می‌پیچیم که فقط بار اول اجازهٔ ورود بدهد.

#ifndef POINT_H
#define POINT_H

struct point {
    int x;
    int y;
};

#endif /* POINT_H */

#ifndef SHAPE_H
#define SHAPE_H

#include "point.h"

struct segment {
    struct point a;
    struct point b;
};

#endif /* SHAPE_H */

#include <stdio.h>
#include "point.h"
#include "shape.h"

int main(void)
{
    struct segment s = { {0, 0}, {3, 4} };
    printf("%d\n", s.b.x + s.b.y);
    return 0;
}
  1. اگر هنوز نیامده... #ifndef POINT_H می‌پرسد «ماکروی POINT_H تعریف شده؟». بار اول نه؛ پس وارد می‌شود و بلافاصله POINT_H را تعریف می‌کند (پرچم «من آمدم»).
  2. محتوای هدر. فقط بار اول کپی می‌شود.
  3. پایان. #endif بلوک را می‌بندد. کامنت کنارش فقط برای خواندن راحت‌تر است. بار دوم که همین هدر چسبانده شود، POINT_H تعریف شده است، پس تمام محتوا تا #endif دور انداخته می‌شود.
$ gcc -std=c11 -Wall -Wextra -o guard_demo main.c
$ ./guard_demo
7
اسم guard و #pragma once
  • اسم guard باید در کل پروژه یکتا باشد. قاعدهٔ رایج: نام فایل با حرف بزرگ و _H: UART_H، SENSOR_CONFIG_H. دو هدر با اسم guard یکسان یکی را از کار می‌اندازد و پیدا کردنش دردسر دارد.
  • راه کوتاه‌تر #pragma once است. تقریبا همهٔ کامپایلرهای رایج (GCC، Clang، IAR، Keil) می‌فهمند، ولی جزو استاندارد C نیست. در پروژه‌ای که ممکن است کامپایلر عوض شود، #ifndef امن‌تر است و همه‌جا کار می‌کند.
  • هر .h که خودت می‌نویسی از اول guard داشته باشد. این یک عادت بی‌هزینه است.

چند ابزار دیگر پیش‌پردازنده

# و ## داخل ماکرو

داخل تعریف ماکرو دو عملگر ویژه هست:

  • #x (stringify): متن آرگومان را به رشته تبدیل می‌کند. SHOW(a * b) می‌تواند خود عبارت را هم چاپ کند.
  • a##b (چسباندن توکن): دو تکه را به هم می‌چسباند و اسم تازه می‌سازد. reg_##name با moder می‌شود reg_moder.

نکتهٔ ریز: #x و ## آرگومان را پیش از گسترش ماکروها به رشته یا اسم تبدیل می‌کنند. اگر #define LED_PIN 5 داشته باشی، SHOW(LED_PIN) متن «LED_PIN» را می‌سازد نه «5». برای گسترش اول، از دو ماکرو استفاده می‌کنند: #define XSTR(x) STR(x) که STR(x) همان #x است.

و کامپایلر چند ماکروی آماده هم دارد: __FILE__ (نام فایل)، __LINE__ (شمارهٔ خط) و __STDC_VERSION__ (نسخهٔ استاندارد). __func__ هم نام تابع جاری را می‌دهد؛ این یکی در واقع ماکرو نیست، بلکه اسمی است که خود کامپایلر می‌سازد ولی مصرفش مشابه است.

#include <stdio.h>

#define SHOW(expr)  printf(#expr " = %d\n", (expr))
#define REG(name)   reg_##name

int reg_moder = 1;
int reg_odr = 32;

int main(void)
{
    int a = 6;
    int b = 7;
    SHOW(a * b);
    SHOW(a + b);
    printf("%d %d\n", REG(moder), REG(odr));
    printf("file=%s line=%d func=%s\n", __FILE__, __LINE__, __func__);
    printf("std=%ld\n", __STDC_VERSION__);
    return 0;
}
  1. نمایش عبارت و مقدارش. #expr متن آرگومان را در گیومه می‌گذارد؛ دو رشتهٔ کنار هم در C به‌هم می‌چسبند ("a * b" " = %d\n"). خود (expr) مقدار را حساب می‌کند. این کار با تابع ممکن نیست؛ تابع فقط مقدار عبارت را می‌بیند و متنِ آن را نه. در دیباگ لاگ، این ترفند خیلی کاربرد دارد.
  2. ساختن اسم. REG(moder) به reg_moder تبدیل می‌شود، یعنی اسم متغیر از تکه‌ها ساخته می‌شود.
  3. دو بار SHOW. هر کدام عبارت خودش را چاپ می‌کند.
  4. چاپ دو متغیر با REG. بعد از جایگزینی می‌شود reg_moder و reg_odr.
  5. ماکروهای آماده. فایل، شماره خط، نام تابع، و نسخهٔ استاندارد (201112 یعنی C11). در لاگ خطا، نام فایل و شمارهٔ خط ارزش بالایی دارد. بدون اینکه دستی بنویسی، همیشه درست است.
$ ./stringify
a * b = 42
a + b = 13
1 32
file=stringify.c line=16 func=main
std=201112

ماکرو با ماکرو: ترفند X-macro

گاهی یک فهرست را باید در دو جا داشته باشی؛ مثلا نام حالت‌های ماشین حالت هم به‌شکل enum هم به‌شکل رشته برای لاگ. اگر دو فهرست جدا بنویسی، روزی یکی را عوض می‌کنی و دیگری یادت می‌رود. راه‌حل X-macro (X-macro) است: فهرست را فقط یک‌بار بنویس و به ماکرو بگو هر ردیف را چطور بسازد.

#include <stdio.h>

#define STATE_LIST(X) \
    X(IDLE)           \
    X(SAMPLING)       \
    X(ALARM)

#define AS_ENUM(name)   STATE_##name,
#define AS_TEXT(name)   #name,

enum state { STATE_LIST(AS_ENUM) STATE_COUNT };

static const char *const state_name[] = { STATE_LIST(AS_TEXT) };

int main(void)
{
    for (int s = 0; s < STATE_COUNT; s++) {
        printf("%d = %s\n", s, state_name[s]);
    }
    return 0;
}
  1. فهرست یکتا. STATE_LIST ماکرویی است که یک ماکروی دیگر (X) را می‌گیرد و برای هر حالت صدایش می‌زند. آخر خط‌ها \ یعنی «ادامهٔ همین خط در خط بعد». فهرست حالت‌ها فقط همین‌جاست. حالت جدید بخواهی، فقط یک خط اضافه می‌کنی.
  2. دو دستور کار. AS_ENUM از هر نام، STATE_نام, می‌سازد. AS_TEXT از هر نام، رشتهٔ "نام", می‌سازد.
  3. استفاده دو بار. یک بار فهرست را با AS_ENUM باز می‌کنیم و می‌شود STATE_IDLE, STATE_SAMPLING, STATE_ALARM, و یک بار با AS_TEXT و می‌شود "IDLE", "SAMPLING", "ALARM",. آخرین عضو STATE_COUNT تعداد حالت‌ها را می‌دهد. اندیس آرایهٔ اسم‌ها و مقدار enum همیشه هم‌ترتیب‌اند، چون از یک فهرست ساخته شده‌اند. در درس ۴.۶ (ماشین حالت) از همین ترفند استفاده می‌کنیم.
  4. چاپ. حلقه از صفر تا تعداد حالت‌ها می‌رود و اسم هر حالت را چاپ می‌کند.
$ ./xmacro
0 = IDLE
1 = SAMPLING
2 = ALARM

_Static_assert: بررسی شرط هنگام کامپایل

_Static_assert(شرط, "پیام") در C11 شرطی را در زمان کامپایل می‌سنجد. اگر نادرست بود، ساخت متوقف می‌شود. از ماکرو نیست، ولی همان‌جا استفاده می‌شود که ماکروها: اطمینان از فرضیات سخت‌افزاری قبل از اینکه کد روی برد برود. مثلا «این ساختار باید ۵ بایت باشد چون پروتکل ۵ بایتی است»:

#include <stdint.h>
#include <stdio.h>

struct packet {
    uint8_t  id;
    uint32_t value;
};

_Static_assert(sizeof(uint32_t) == 4, "uint32_t must be 4 bytes");
_Static_assert(sizeof(struct packet) == 5, "packet must be 5 bytes");

int main(void)
{
    printf("ok\n");
    return 0;
}
  1. ساختار با padding. یک بایت id و ۴ بایت value. ولی از درس ۳.۴ می‌دانی کامپایلر بعد از id سه بایت خالی (padding) می‌گذارد تا value هم‌تراز شود؛ پس اندازه ۸ است، نه ۵.
  2. شرط درست. uint32_t روی همهٔ بردهای این دوره دقیقا ۳۲ بیت (۴ بایت) است؛ این خط بی‌صدا رد می‌شود.
  3. شرط نادرست. sizeof(struct packet) برابر ۸ است. ساخت با پیام خودمان می‌ایستد. اگر این بررسی نبود، پروتکل با بایت‌های اضافی می‌فرستادی و دنبال باگ ارتباط می‌گشتی. حالا کامپایلر همان لحظه می‌گوید.
sa.c:10:1: error: static assertion failed: "packet must be 5 bytes"
زیر کاپوت: ماکرو در مقابل کامپایلر، چه کسی زودتر است؟

ترتیب کار: ۱) پیش‌پردازنده (ماکروها، #if، #include)، ۲) کامپایلر (نوع، sizeof، _Static_assert)، ۳) لینکر. در #if نمی‌توانی sizeof(int) بنویسی، چون در مرحلهٔ ۱ هنوز کسی نوع‌ها را نمی‌شناسد. برای همین _Static_assert که در مرحلهٔ ۲ است، جای درست برای بررسی اندازهٔ نوع‌هاست.

ماکرو در دنیای embedded بسیار پرکاربرد است، به‌خصوص برای سه کار:

  1. اسم دادن به آدرس‌ها و بیت‌ها. به‌جای *(volatile uint32_t *)0x40020018 = 0x20 می‌نویسی GPIOA_BSRR = BIT(LED_PIN).
  2. پیکربندی برد. پایه‌ها، کلاک، اندازهٔ بافر‌ها یک‌جا در یک هدر board.h.
  3. لاگ و دیباگ شرطی. در نسخهٔ نهایی هیچ کدی تولید نمی‌کنند.

این‌جا نمونهٔ اولی را می‌بینی: همان LED درس ۳.۶ (PA5 روی Nucleo-F411RE) با ماکروهای خوانا. هر خط را با آدرس‌های درس ۳.۶ مقایسه کن؛ چیز تازه‌ای نیست، فقط اسم‌گذاری شده است.

#include <stdint.h>

#define BIT(n)          (1UL << (n))
#define REG32(addr)     (*(volatile uint32_t *)(addr))

#define RCC_AHB1ENR     REG32(0x40023830UL)
#define GPIOA_BASE      0x40020000UL
#define GPIOA_MODER     REG32(GPIOA_BASE + 0x00UL)
#define GPIOA_BSRR      REG32(GPIOA_BASE + 0x18UL)

#define LED_PIN         5U
#define LED_ON()        (GPIOA_BSRR = BIT(LED_PIN))
#define LED_OFF()       (GPIOA_BSRR = BIT(LED_PIN + 16U))

void led_init(void)
{
    RCC_AHB1ENR |= BIT(0);
    GPIOA_MODER &= ~(3UL << (LED_PIN * 2U));
    GPIOA_MODER |= (1UL << (LED_PIN * 2U));
}

void led_blink_once(void)
{
    LED_ON();
    LED_OFF();
}
  1. BIT(n). عدد یک را n خانه به چپ می‌برد، یعنی فقط بیت شمارهٔ n روشن است (درس ۳.۱). 1UL یعنی عدد بی‌علامت از نوع unsigned long، یعنی «حداقل ۳۲ بیت»: روی Cortex-M و ESP32 دقیقا ۳۲ بیت است ولی روی PCِ ۶۴ بیتی لینوکس ۶۴ بیت (۸ بایت). با 1 ساده و n = 31 رفتار تعریف‌نشده می‌گرفتی. (اگر عرض دقیق ۳۲ بیت می‌خواهی، UINT32_C(1) یا 1u روی این بردها؛ در درس‌های ۳.۱ و ۳.۶ 1u نوشتیم و روی MCU با 1UL یکی است.) پرانتز دور n و دور کل عبارت؛ همان قاعدهٔ تلهٔ ۱.
  2. REG32(addr). عدد addr را به اشاره‌گر به volatile uint32_t تبدیل و بلافاصله * می‌زند: یعنی «خودِ رجیستر در آن آدرس» (درس ۳.۶). چون ماکرو است، هم می‌شود در آن نوشت (= ...) و هم خواند.
  3. اسم‌های رجیستر. RCC_AHB1ENR در آدرس 0x40023830 (پایهٔ RCC 0x40023800 + آفست 0x30). GPIOA_MODER آفست ۰ و GPIOA_BSRR آفست 0x18 از پایهٔ 0x40020000 است.
  4. LED_PIN و ماکروهای روشن/خاموش. نوشتن بیت ۵ در BSRR پایه را ۱ می‌کند. بیت ۲۱ (۵ + ۱۶) آن را صفر می‌کند. چون خودش به‌شکل «تابع بدون پارامتر» نوشته شده (LED_ON())، در کد خوانا است، و اگر بعدا خواستی به تابع واقعی تبدیل کنی، جای فراخوانی‌ها عوض نمی‌شود.
  5. راه‌اندازی. ساعت GPIOA را روشن می‌کند (بیت ۰ RCC_AHB1ENR) و بیت‌های ۱۰ و ۱۱ MODER را طوری می‌گذارد که 01 (خروجی) شود.
  6. یک چشمک. خوانایی کد نسبت به آدرس‌های خام قابل مقایسه نیست.

خودت با رجیستر بازی کن. روی بیت‌ها بزن و ببین BIT(5) چه عددی می‌دهد:

در ESP32 (ESP-IDF) رجیستر را مستقیم نمی‌نویسی و از تابع‌های درایور استفاده می‌کنی. اما ماکرو همان‌جا هم هست: پیکربندی تراشه و برد با ماکروهایی که سیستم ساخت (menuconfig) از تنظیمات تو می‌سازد، به شکل CONFIG_... و در ادامهٔ هدرها. نمونه: انتخاب پایهٔ LED بسته به تراشه.

#include "driver/gpio.h"

#if CONFIG_IDF_TARGET_ESP32
#define BLINK_GPIO  GPIO_NUM_2
#else
#error "Set BLINK_GPIO for this chip"
#endif

static void led_init(void)
{
    gpio_reset_pin(BLINK_GPIO);
    gpio_set_direction(BLINK_GPIO, GPIO_MODE_OUTPUT);
}
  1. انتخاب پایه بر اساس تراشه. CONFIG_IDF_TARGET_ESP32 را سیستم ساخت ESP-IDF برای ESP32 کلاسیک تعریف می‌کند. برای تراشه‌های دیگر خطای واضح می‌دهیم تا پایه اشتباه نماند. این نمونه فقط برای نمایش الگو است و در محیط این درس کامپایل نمی‌شود؛ جزئیات در مستندات رسمی ESP-IDF و درس ۵.۶.
  2. استفاده. بقیهٔ کد فقط BLINK_GPIO را می‌شناسد و به تراشه کاری ندارد.

عدد جادویی و ماکرو

عدد «جادویی» (magic number) عددی است که در کد ظاهر می‌شود و معنایش معلوم نیست. مثلا if (adc > 3722). شش ماه بعد کسی نمی‌داند ۳۷۲۲ چیست. با #define ADC_ALARM_LEVEL 3722 اسم و یک مکان برای تغییر داری. هر عدد مهم را یک‌جا و با اسم معنی‌دار (و واحد، مثل درس ۲.۱) بنویس.

خطا در ماکروی سخت‌افزار: ثابت‌ها را UL بنویس

در #define GPIOA_BASE 0x40020000 عدد به‌عنوان int یا unsigned int یا long تفسیر می‌شود که به کامپایلر بستگی دارد. با پسوند UL صریح می‌گویی «بی‌علامت و حداقل ۳۲ بیت» (روی MCU‌های این دوره دقیقا ۳۲ بیت؛ روی PC ۶۴ بیتی ۶۴ بیت، پس ~BIT(n) روی PC و MCU عرض متفاوت دارد؛ برای ماسک‌های دقیق ۳۲ بیتی uint32_t یا UINT32_C بهتر است). در محاسبهٔ آدرس و بیت، ابهام نوع باگ‌های پنهان می‌سازد (درس ۲.۲).

آزمون این درس

با #define SQUARE_BAD(x) x * x و int n = 3; عبارت SQUARE_BAD(n + 1) چه عددی می‌دهد؟

  1. ۱۶
  2. ۷
  3. ۹
  4. خطای کامپایل می‌دهد
متن می‌شود n + 1 * n + 1. ضرب قبل از جمع است: ۳ + (۱×۳) + ۱ = ۷. برای همین پرانتز دور هر پارامتر لازم است.

پیش‌پردازنده دقیقا چه کاری با کد انجام می‌دهد؟

  1. نوع متغیرها را می‌سنجد و خطای نوع را پیدا می‌کند
  2. کد C را به کد ماشین تبدیل می‌کند
  3. فقط متن برنامه را با #include، #define و #if ویرایش می‌کند و به کامپایلر می‌دهد
  4. فایل‌های شیء را به هم وصل می‌کند
پیش‌پردازنده فقط متن را عوض می‌کند: چسباندن، جایگزینی، حذف. هر چیز دیگری (نوع، ترجمه، اتصال) مرحلهٔ بعد است.

کدام خط باعث خطا در if (t > LIMIT) می‌شود؟

  1. #define LIMIT 100;
  2. #define LIMIT 100
  3. #define LIMIT (100)
  4. #define LIMIT 100U
نقطه‌ویرگول جزو متن جایگزین می‌شود: if (t > 100;) که معتبر نیست. در ماکروی ثابت هرگز ; نگذار.

include guard برای چه کاری است؟

  1. تا هدر سریع‌تر خوانده شود
  2. تا هدر در حافظهٔ میکروکنترلر جا نگیرد
  3. تا فایل دیگران نتوانند هدر را ببینند
  4. تا اگر هدر چند بار وارد شد، محتوایش فقط یک بار در فایل بنشیند
بار اول ماکروی guard تعریف می‌شود؛ بار بعد #ifndef نادرست است و کل محتوا پرش می‌شود. اگر نبود، struct دو بار تعریف می‌شد و کامپایلر خطای redefinition می‌داد.

در پروژه‌ای برای دو برد، #ifdef DEBUG با یک LOG(...) نوشته‌ای. اگر DEBUG تعریف نشود، نسخهٔ نهایی روی برد چه می‌شود؟

  1. کد لاگ در Flash هست ولی اجرا نمی‌شود
  2. کامپایل با خطا تمام می‌شود
  3. کد لاگ اصلا در فایل ماشین نیست و هیچ حجمی نمی‌گیرد
  4. لاگ چاپ می‌شود ولی کندتر
شاخهٔ غیرفعال پیش از کامپایلر پاک می‌شود. پس روی MCU با Flash کوچک، لاگ‌های debug در نسخهٔ نهایی هیچ هزینه‌ای ندارند.

با ماکروی MAX(a, b) ((a) > (b) ? (a) : (b)) و مقدارهای x = 5، y = 5، بعد از int m = MAX(x, y++); مقدارِ y چند است؟

  1. ۶
  2. ۷
  3. ۵
  4. ۸
y++ در مقایسه و در شاخهٔ دوم هر دو اجرا می‌شود: y از ۵ به ۶ و بعد ۷ می‌رسد و m برابر ۶ می‌ماند. برای همین اثر جانبی داخل آرگومان ماکرو ممنوع است.

تمرین‌ها

تمرین ۱: ماکروهای MIN، MAX و CLAMP

می‌خواهیم ماکروهای MIN، MAX و CLAMP(v, lo, hi) را بنویسیم که مقدار را در بازهٔ [lo, hi] نگه می‌دارد. سپس با یک ماکروی ناقص مقایسه می‌کنیم.

  1. پیش‌بینی: با #define DOUBLE_BAD(x) x * 2، عبارت DOUBLE_BAD(3 + 1) چه عددی می‌دهد؟ (اول حدس بزن.)
  2. حل: DOUBLE درست را با پرانتز بنویس و هر دو را چاپ کن.
  3. چالش: CLAMP را با ترکیب MIN و MAX بنویس و با سه ورودی -5، 50، 250 و بازهٔ [0, 100] امتحان کن.
راهنمایی

برای CLAMP اول MAX(v, lo) را بگیر (پایین‌تر از lo نشود) و نتیجه را با MIN(..., hi) کوچک‌تر کن. پرانتز دور همه چیز.

چه باید ببینی؟ 
$ ./ex1
bad    = 5
good   = 8
clamp  = 0 50 100

جواب قسمت الف: 3 + 1 * 2 = ۵، نه ۸.

جواب کامل با توضیح 
#include <stdio.h>

#define MIN(a, b)         ((a) < (b) ? (a) : (b))
#define MAX(a, b)         ((a) > (b) ? (a) : (b))
#define CLAMP(v, lo, hi)  MIN(MAX((v), (lo)), (hi))
#define DOUBLE_BAD(x)     x * 2
#define DOUBLE(x)         ((x) * 2)

int main(void)
{
    printf("bad    = %d\n", DOUBLE_BAD(3 + 1));
    printf("good   = %d\n", DOUBLE(3 + 1));
    printf("clamp  = %d %d %d\n", CLAMP(-5, 0, 100), CLAMP(50, 0, 100), CLAMP(250, 0, 100));
    return 0;
}
  1. MIN و MAX. پرانتز دور هر پارامتر و دور کل عبارت.
  2. CLAMP از ترکیب. اول با MAX از پایین محدود می‌شود و بعد با MIN از بالا. هر کدام از پارامترها با پرانتز پوشیده شده‌اند. هر پارامتر (v، lo، hi) فقط یک بار در ماکروی بیرونی می‌آید، ولی در MAX و MIN هر کدام دو بار کپی می‌شود. پس آرگومان‌ها را بدون اثر جانبی بده.
  3. DOUBLE. نسخهٔ بد 3 + 1 * 2 می‌شود و نسخهٔ خوب ((3 + 1) * 2).
  4. چاپ. عدد ۵ و ۸ و سه نتیجه از CLAMP.
$ ./ex1
bad    = 5
good   = 8
clamp  = 0 50 100
تمرین ۲: باگ را در ماکروها پیدا کن

این هدر چهار مشکل دارد. هر کدام را پیدا کن و نسخهٔ درست را بنویس:

#define BUFFER_SIZE 64;
#define AVG(a, b) a + b / 2
#define STOP_MOTOR() motor_off(); led_off();

struct config { int id; };
  1. مشکل BUFFER_SIZE چیست و آرایهٔ uint8_t buf[BUFFER_SIZE]; چه می‌شود؟
  2. چرا AVG(4, 8) عدد ۶ نمی‌دهد؟ (عددی که می‌دهد چیست؟)
  3. در if (fault) STOP_MOTOR(); چه چیزی درست کار نمی‌کند؟ و برای هدر، چه چیزی جا افتاده است که اگر این فایل از دو جا وارد شود خطا می‌دهد؟
راهنمایی

مورد اول: تلهٔ نقطه‌ویرگول. دوم: پرانتز دور پارامتر و کل. سوم: do { } while (0). و برای struct: include guard.

چه باید ببینی؟ 
$ ./ex2
avg=6
motor_off led_off
buf=64

با نسخهٔ خراب: AVG(4, 8) برابر 4 + 8 / 2 یعنی ۸ می‌شود؛ و led_off() حتی وقتی fault نیست هم اجرا می‌شود.

جواب کامل با توضیح
بخشمشکلاصلاح
الفنقطه‌ویرگول جزو ماکرو شده؛ uint8_t buf[64;]; خطای نوشتاری می‌دهد#define BUFFER_SIZE 64
بپرانتز ندارد: 4 + 8 / 2 = ۸#define AVG(a, b) (((a) + (b)) / 2)
پدو دستور بدون بلوک؛ led_off() از if بیرون می‌افتد. هدر هم guard نداردdo { ... } while (0) و #ifndef CONFIG_H ... #endif
#include <stdio.h>

#define BUFFER_SIZE 64
#define AVG(a, b) (((a) + (b)) / 2)

static void motor_off(void) { printf("motor_off "); }
static void led_off(void) { printf("led_off\n"); }

#define STOP_MOTOR() do { motor_off(); led_off(); } while (0)

int main(void)
{
    int fault = 1;
    unsigned char buf[BUFFER_SIZE];

    printf("avg=%d\n", AVG(4, 8));
    if (fault)
        STOP_MOTOR();
    else
        printf("running\n");
    printf("buf=%zu\n", sizeof(buf));
    return 0;
}
  1. ثابت بدون ;. unsigned char buf[64] می‌شود.
  2. AVG با پرانتز. حالا (((4) + (8)) / 2) = ۶.
  3. دو تابع کمکی. برای نمایش اینکه هر کدام اجرا شد.
  4. STOP_MOTOR درست. هر دو دستور داخل یک بلوک و ماکرو مثل یک دستور رفتار می‌کند. شرط if (fault) حالا هر دو تابع را کنترل می‌کند و else جفت دارد.
  5. مصرف‌ها. ورودی fault = 1 است پس هر دو تابع اجرا می‌شود.
$ ./ex2
avg=6
motor_off led_off
buf=64
تمرین ۳: ماکروهای بیت برای رجیستر شبیه‌سازی‌شده

روی PC رجیستر واقعی نداریم؛ پس یک متغیر uint32_t fake_odr را شبیهٔ رجیستر GPIOA_ODR می‌گیریم. ماکروهایی بساز که بیت را روشن/خاموش/برعکس کند.

  1. پیش‌بینی: اگر رجیستر صفر باشد و SET_BIT(fake_odr, 5) بزنیم، مقدارش (به hex) چیست؟ (کمک: درس ۳.۱)
  2. حل: ماکروهای SET_BIT، CLR_BIT، TOGGLE_BIT و TEST_BIT را با کمک BIT(n) بنویس و نتیجه را چاپ کن.
  3. ارتباط با سخت‌افزار: عددی که باید در BSRR بنویسی تا پایه ۵ خاموش شود چیست؟ (BSRR: بیت‌های ۱۶ تا ۳۱ باعث reset می‌شوند.) چاپ کن.
راهنمایی

ماسک را با BIT(n) بساز. روشن: |=. خاموش: &= ~. برعکس: ^=. آزمون: شیفت به راست و & 1. برای BSRR: BIT(5 + 16).

چه باید ببینی؟ 
$ ./ex3
after set    : 0x0020
after toggle : 0x0000
final        : 0x0020, led=1
BSRR off     : 0x00200000
جواب کامل با توضیح 
#include <stdint.h>
#include <stdio.h>

#define BIT(n)            (1UL << (n))
#define SET_BIT(r, n)     ((r) |= BIT(n))
#define CLR_BIT(r, n)     ((r) &= ~BIT(n))
#define TOGGLE_BIT(r, n)  ((r) ^= BIT(n))
#define TEST_BIT(r, n)    (((r) >> (n)) & 1UL)

#define LED_PIN 5U

static uint32_t fake_odr = 0;

int main(void)
{
    SET_BIT(fake_odr, LED_PIN);
    printf("after set    : 0x%04lX\n", (unsigned long)fake_odr);
    TOGGLE_BIT(fake_odr, LED_PIN);
    printf("after toggle : 0x%04lX\n", (unsigned long)fake_odr);
    SET_BIT(fake_odr, 0);
    SET_BIT(fake_odr, LED_PIN);
    CLR_BIT(fake_odr, 0);
    printf("final        : 0x%04lX, led=%lu\n", (unsigned long)fake_odr, TEST_BIT(fake_odr, LED_PIN));
    printf("BSRR off     : 0x%08lX\n", BIT(LED_PIN + 16U));
    return 0;
}
  1. پنج ماکرو. هر کدام فقط BIT(n) را به‌کار می‌برد. r و n هر دو در پرانتزند. آرگومان r در این ماکروها فقط یک‌بار در متن می‌آید، پس SET_BIT(reg++, 1) نامعتبر است ولی SET_BIT(reg, i) امن است.
  2. پایه LED. شمارهٔ پایه یک‌جا و با اسم.
  3. رجیستر ساختگی. یک متغیر ۳۲ بیتی است؛ روی MCU همین ماکروها روی رجیستر volatile کار می‌کنند.
  4. روشن و برعکس. 0x0020 = بیت ۵. بعد از toggle دوباره صفر.
  5. ترکیب و آزمون. بیت ۰ را روشن و خاموش می‌کنیم و بیت ۵ را دوباره روشن؛ در نهایت فقط بیت ۵ است.
  6. مقدار BSRR برای خاموش. BIT(5 + 16) = 0x00200000. نوشتن این عدد در BSRR پایه ۵ را صفر می‌کند.
$ ./ex3
after set    : 0x0020
after toggle : 0x0000
final        : 0x0020, led=1
BSRR off     : 0x00200000
حرف مربی

ماکرو وسوسه‌انگیز است، چون کوتاه و سریع می‌نویسی و «هر جا کار می‌کند». مبتدی‌ها معمولا دو جا گیر می‌کنند: اول پرانتزها (ماکرو بدون پرانتز درست کار می‌کند تا روزی که یک عبارت مرکب را به آن بدهی) و دوم پیام خطای ماکرو که به خط مصرف اشاره می‌کند، نه تعریف. یادت باشد gcc -E را بزنی و خروجی را ببینی. یک قاعدهٔ ساده: اگر تابع static inline کار را انجام می‌دهد، تابع بنویس. ماکرو را برای کارهایی نگه دار که فقط ماکرو می‌تواند: ثابت زمان کامپایل، کامپایل شرطی و ساختن اسم.

خلاصه یک‌دقیقه‌ای

  • پیش‌پردازنده اولین ایستگاه ساخت است و فقط متن را ویرایش می‌کند: #include می‌چسباند، #define جایگزین می‌کند، #if تکه‌ای را نگه می‌دارد یا دور می‌اندازد. نتیجه را با gcc -E ببین.
  • ثابت‌های ماکرو بدون ; و بدون نوع‌اند. ثابت با نوع را با const بساز و حالت‌ها را با enum.
  • ماکروی تابع‌مانند: پرانتز دور هر پارامتر و دور کل؛ آرگومان با اثر جانبی (x++) ممنوع؛ چند دستور را در do { } while (0) بپیچ؛ اگر می‌شود static inline بنویس.
  • کامپایل شرطی: #if، #ifdef، #elif، #error و -D. یک کد برای چند برد، و لاگ debug که در نسخهٔ نهایی هیچ حجمی نمی‌گیرد.
  • هر .h باید include guard داشته باشد.
  • # رشته می‌سازد، ## اسم می‌چسباند، X-macro یک فهرست را دو جا می‌کارد، _Static_assert فرضیات را هنگام کامپایل می‌سنجد.
  • در MCU: ماکرو برای BIT(n)، REG32(addr)، اسم رجیستر و پیکربندی برد. ثابت‌های سخت‌افزار را با UL بنویس.

درس بعد: ۴.۲ پروژهٔ چندفایلی: header، extern و build.
