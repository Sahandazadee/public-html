تا اینجا هر داده یک متغیر جدا بود: id، temp، ok. ولی دنیای واقعی «بسته» است: یک خوانش سنسور همزمان شناسه دارد، دما دارد و وضعیت. یک رجیستر GPIO ده‌ها فیلد پشت سر هم دارد. یک پکت شبکه هدر و بدنه دارد. C برای همین چند ابزار دارد: struct (بسته‌ای از چند مقدار)، union (یک حافظه با چند «عینک»)، enum (اسم برای عددهای حالت) و typedef (اسم کوتاه برای یک نوع). و یک نکته پنهان که هر برنامه‌نویس embedded باید بداند: کامپایلر لابه‌لای فیلدها بایت خالی می‌گذارد.

🎯 بعد از این درس می‌توانی

  • ساختار (struct) تعریف کنی، مقدار اولیه بدهی و با . و -> به فیلدها برسی
  • آرایه‌ای از struct بسازی و struct را با اشاره‌گر به تابع بدهی
  • با sizeof و offsetof بفهمی هر فیلد کجا نشسته و چرا بایت خالی (padding) هست
  • فرق union، bit-field و ماسک را بگویی و union را برای دیدن بایت‌ها به‌کار ببری
  • enum برای حالت‌ها بنویسی و از کامپایلر بخواهی حالت فراموش‌شده را به تو نشان دهد
  • بفهمی چرا GPIOA->ODR کار می‌کند (struct روی آدرس رجیستر)

🧰 پیش‌نیاز و وسایل

  • درس ۳.۲ و ۳.۳ (اشاره‌گر، آدرس، تراز، const)
  • درس ۲.۷ (آرایه) و ۲.۲ (uint8_t و هم‌خانواده‌ها)
  • درس ۳.۱ (ماسک و شیفت) برای بخش bit-field
  • یک کامپایلر روی رایانه؛ کدهای STM32 فقط کامپایل می‌شوند و سخت‌افزار لازم نیست

ایده اصلی: پرونده به‌جای برگه‌های پراکنده

فرض کن برای هر دانش‌آموز مدرسه سه برگه جدا داری: یکی فقط شماره دانش‌آموزی، یکی نمره، یکی وضعیت حضور. برای پیدا کردن اطلاعات علی باید سه جا را بگردی و مطمئن باشی برگه‌ها را قاطی نکرده‌ای. بهتر است برای هر نفر یک پرونده داشته باشی که هر سه برگه در آن است. آن‌وقت می‌گویی «پرونده علی» و همه با هم جابه‌جا می‌شوند.

مثال از زندگی روزمره

فرم ثبت‌نام را ببین: چند خانه دارد (نام، سن، شماره). ساختار فرم ثابت است، اما هر نفر آن را با مقدارهای خودش پر می‌کند. در C «قالب فرم» را با struct می‌نویسی و «فرم پرشده» یک متغیر از آن نوع است. هر خانه فرم اسم دارد و اندازه‌اش را فرم تعیین می‌کند. یک تفاوت مهم با فرم کاغذی: کامپایلر ممکن است بین دو خانه جای خالی بگذارد تا خواندن سریع‌تر شود؛ یک بخش کامل همین درس درباره آن است.

struct: بسته‌ای از چند مقدار

ساختار (struct) نوعی است که خودت می‌سازی و از چند متغیر (به اسم فیلد یا عضو) تشکیل می‌شود. اول قالب را تعریف می‌کنی، بعد از روی قالب متغیر می‌سازی. فیلدهای struct در حافظه به ترتیب نوشتن پشت سر هم می‌نشینند (با یک شرط که در بخش padding می‌بینی).

اگر از Python/JS می‌آیی: s2 = s1 کپی است، نه نام دوم

در Python s2 = s1 برای یک شیء (dict یا کلاس) یعنی دو اسم برای یک شیء؛ تغییر از یکی در دیگری دیده می‌شود. در C با struct برعکس است: s2 = s1 تمام فیلدها را در قفسه‌های جدا کپی می‌کند؛ بعدش دو شیء مستقل‌اند (همان رفتار کپی یک int). اگر خواستی دو اسم برای یک شیء داشته باشی، اشاره‌گر بگیر: sensor_t *p = &s1; (بخش بعد). یک چیز دیگر: struct در C فقط داده دارد، «متد» ندارد؛ ارتباط رفتار با داده را با اشاره‌گر تابع در درس ۴.۳ می‌بینی.

#include <stdio.h>

struct sensor {
    int id;
    int temp_c;
    int ok;
};

int main(void)
{
    struct sensor s1 = {1, 25, 1};
    struct sensor s2 = s1;          // کپی کل بسته
    s2.temp_c = 40;                 // فقط s2 عوض می‌شود

    printf("s1: id=%d temp=%d ok=%d\n", s1.id, s1.temp_c, s1.ok);
    printf("s2: id=%d temp=%d ok=%d\n", s2.id, s2.temp_c, s2.ok);
    printf("sizeof(struct sensor) = %zu\n", sizeof(struct sensor));
    return 0;
}
  1. قالب. struct sensor یک نوع جدید است با سه فیلد int. این فقط طرح فرم است؛ تا اینجا هیچ حافظه‌ای مصرف نشده. نقطه‌ویرگول بعد از } اجباری است. فراموشش کنی، خطای کامپایل عجیبی در خط بعد می‌گیری.
  2. main. نقطه شروع.
  3. ساختن و پر کردن. s1 یک متغیر از نوع struct sensor است. مقدارهای داخل آکولاد به ترتیب فیلدها می‌روند: id=1، temp_c=25، ok=1. اگر ترتیب فیلدها را جابه‌جا کنی، مقدارها جابه‌جا می‌روند بدون هیچ هشداری. در بخش بعد راه امن‌تری را می‌بینی.
  4. کپی کل بسته. s2 = s1 همه فیلدها را یکجا کپی می‌کند. بعد از آن دو بسته مستقل‌اند (مثل کپی int در درس ۲.۱). این با آرایه فرق دارد: آرایه را نمی‌شود با = کپی کرد ولی struct را می‌شود، حتی اگر آرایه داخلش باشد.
  5. دسترسی به فیلد با نقطه. s2.temp_c یعنی «فیلد temp_c از بسته s2». فقط همین فیلد تغییر می‌کند.
  6. چاپ. نشان می‌دهد s1 دست‌نخورده است.
  7. اندازه. ۱۲ بایت: سه int چهار بایتی.
$ gcc -std=c11 -Wall -Wextra -o struct_basic struct_basic.c
$ ./struct_basic
s1: id=1 temp=25 ok=1
s2: id=1 temp=40 ok=1
sizeof(struct sensor) = 12

typedef: اسم کوتاه برای یک نوع

نوشتن struct sensor در هر جا خسته‌کننده است. typedef اسم دیگری برای یک نوع می‌سازد؛ مثل اینکه به «جمهوری اسلامی ایران» بگویی «ایران». چیزی ساخته نمی‌شود، فقط یک لقب دیگر. الگوی رایج در کد embedded:

typedef struct {
    int id;
    int temp_c;
} sensor_t;        /* حالا می‌شود نوشت: sensor_t s1; */

قرارداد: اسم نوع‌ها با _t تمام می‌شود (مثل uint8_t و size_t؛ خود uint8_t هم یک typedef است). روی نوع‌های ساده هم می‌شود لقب داد: typedef uint16_t millivolt_t; خوانایی را بالا می‌برد. فقط بدان که کامپایلر millivolt_t و uint16_t را یکی می‌داند و اگر قاطی‌شان کنی خطایی نمی‌دهد.

یک هشدار برای بعد: struct بدون اسم (مثل typedef struct {...} sensor_t;) نمی‌تواند داخل خودش به همان نوع اشاره کند، چون اسمش هنوز ساخته نشده. لیست پیوندی و درخت (درس ۴.۵) struct node *next; می‌خواهند، پس برای آن‌ها اسم (tag) بنویس: typedef struct node {... struct node *next;} node_t;.

مقداردهی با نام و آرایه‌ای از struct

مقداردهی با ترتیب (مثل {1, 25, 1}) شکننده است: اگر یک فیلد در وسط struct اضافه شود، همه مقدارها به فیلد بعدی سر می‌خورند. راه بهتر که در C99 آمد: مقداردهی نامزد با نام فیلد: {.id = 3, .temp_x10 = 235}. فیلدهایی که ننویسی صفر می‌شوند (نه آشغال، برخلاف متغیر معمولی؛ یک استثنای مهربان).

#include <stdint.h>
#include <stdio.h>

typedef struct {
    uint8_t id;
    int16_t temp_x10;               // دما ضرب در ۱۰
    uint8_t flags;
} reading_t;

int main(void)
{
    reading_t r = {.id = 3, .temp_x10 = 235};
    reading_t table[3] = {
        {.id = 1, .temp_x10 = 200},
        {.id = 2, .temp_x10 = 310},
        {.id = 3, .temp_x10 = 150},
    };
    int hottest = 0;

    printf("r: id=%u temp=%d flags=%u\n", (unsigned)r.id, (int)r.temp_x10, (unsigned)r.flags);
    for (int i = 1; i < 3; i++) {
        if (table[i].temp_x10 > table[hottest].temp_x10) {
            hottest = i;
        }
    }
    printf("hottest: id=%u temp=%d\n", (unsigned)table[hottest].id, (int)table[hottest].temp_x10);
    return 0;
}
  1. تعریف نوع با typedef. سه فیلد با اندازه‌های ثابت (درس ۲.۲). دما را ضرب در ۱۰ نگه می‌داریم: ۲۳٫۵ درجه می‌شود ۲۳۵. بدون float و بدون هزینه اعشار. این ترفند در میکروکنترلرها رایج است (درس ۴.۷ عمیق‌ترش می‌کند). int16_t یعنی دو بایت علامت‌دار.
  2. main.
  3. مقداردهی نامزد. فقط id و temp_x10 را داده‌ایم. flags ننوشته ماند، پس صفر می‌شود. استاندارد C می‌گوید فیلدهای جاافتاده در مقداردهی با آکولاد صفر می‌شوند. برای همین {0} راه رایج «همه چیز را صفر کن» است.
  4. آرایه‌ای از struct. سه خوانش پشت هم. هر عنصر با آکولاد خودش پر می‌شود. کامای آخر مجاز است و افزودن عنصر جدید را ساده می‌کند.
  5. اندیس بهترین. hottest اندیس داغ‌ترین عنصر است؛ اول عنصر ۰.
  6. چاپ. %u برای عدد بی‌علامت و %d برای علامت‌دار؛ چون uint8_t روی چاپ به int ارتقا می‌یابد، با cast صریح می‌نویسیم تا هشدار نگیریم.
  7. جست‌وجو. table[i].temp_x10 یعنی «عنصر i ام آرایه، فیلد temp_x10». اول اندیس، بعد نقطه.
  8. چاپ نتیجه. عنصر شماره ۱ (شناسه ۲) با ۳۱٫۰ داغ‌ترین است.
$ ./designated
r: id=3 temp=235 flags=0
hottest: id=2 temp=310

enum: اسم برای عددهای حالت

فرض کن یک دستگاه سه حالت دارد. اگر بنویسی state = 2، شش ماه بعد کسی نمی‌داند ۲ یعنی چه. enum (از enumeration، شمارش) به عددها اسم می‌دهد: STATE_IDLE می‌شود ۰، بعدی ۱ و همین‌طور. اسم‌ها ثابت‌های int هستند و کامپایلر می‌تواند کمک کند تا حالتی را فراموش نکنی.

#include <stdio.h>

typedef enum {
    STATE_IDLE,
    STATE_RUN,
    STATE_ERROR,
    STATE_COUNT                     // تعداد حالت‌ها؛ حالت واقعی نیست
} state_t;

static const char *const state_names[STATE_COUNT] = {
    [STATE_IDLE]  = "IDLE",
    [STATE_RUN]   = "RUN",
    [STATE_ERROR] = "ERROR",
};

int main(void)
{
    for (int s = 0; s < STATE_COUNT; s++) {
        printf("%d = %s\n", s, state_names[s]);
    }
    printf("STATE_COUNT = %d\n", (int)STATE_COUNT);
    return 0;
}
  1. تعریف enum. اسم‌ها از ۰ شروع می‌شوند و یکی‌یکی زیاد می‌شوند: IDLE=0، RUN=1، ERROR=2. آخرین اسم STATE_COUNT یعنی ۳ = تعداد حالت‌های واقعی. ترفند «COUNT در آخر»: اگر بعدا حالت جدیدی قبل از COUNT اضافه کنی، شمارش خودکار درست می‌شود و آرایه‌ها و حلقه‌هایی که به آن تکیه دارند نمی‌شکنند.
  2. جدول اسم‌ها. آرایه ثابتی از متن‌ها که با خود enum ایندکس می‌شود: [STATE_RUN] = "RUN". اندازه‌اش STATE_COUNT است. این‌طور اسم چاپی هر حالت کنار تعریفش می‌ماند و ترتیب اشتباه نمی‌شود. const جدول را فقط‌خواندنی می‌کند و روی MCU در Flash می‌ماند.
  3. حلقه روی همه حالت‌ها. از ۰ تا قبل از COUNT.
  4. چاپ COUNT. یک enum معمولی همان int است، پس cast صریح می‌کنیم.
$ ./enum_state
0 = IDLE
1 = RUN
2 = ERROR
STATE_COUNT = 3

مزیت بزرگ دیگر: وقتی روی یک enum switch می‌نویسی و یکی از حالت‌ها را جا بیندازی، کامپایلر می‌تواند اعتراض کند (با -Wall هشدار -Wswitch فعال است). این‌جا هشدار را به خطا تبدیل کرده‌ایم:

#include <stdio.h>

typedef enum {
    STATE_IDLE,
    STATE_RUN,
    STATE_ERROR
} state_t;

int main(void)
{
    state_t s = STATE_RUN;
    switch (s) {
    case STATE_IDLE:
        printf("idle\n");
        break;
    case STATE_RUN:
        printf("run\n");
        break;
    }
    return 0;
}
  1. سه حالت. IDLE و RUN و ERROR.
  2. switch ناقص. فقط دو حالت پوشش داده شده و STATE_ERROR نه. اگر روزی حالت ERROR پیش بیاید، هیچ‌چیز اتفاق نمی‌افتد. در ماشین حالت (درس ۴.۶) فراموش کردن یک حالت باگ سخت‌یاب است. اگر default: ننویسی، کامپایلر خودش یادآوری می‌کند؛ با default این هشدار خاموش می‌شود.
enum_switch.c: In function 'main':
enum_switch.c:12:5: error: enumeration value 'STATE_ERROR' not handled in switch [-Werror=switch]

ولی یک طرف دیگر هم هست. بدون default، اگر مقدار enum خراب باشد (حافظهٔ خراب‌شده یا (state_t)42)، switch بی‌صدا رد می‌شود. راه‌حل: برای هر حالت case بنویس، default نگذار تا هشدار کار کند، و بعد از switch یک مسیر دفاعی بگذار که فقط برای مقدار نامعتبر اجرا می‌شود:

#include <stdio.h>

typedef enum { STATE_IDLE, STATE_RUN, STATE_ERROR } state_t;

static const char *describe(state_t s)
{
    switch (s) {
    case STATE_IDLE:  return "idle";
    case STATE_RUN:   return "run";
    case STATE_ERROR: return "error";
    }
    return "INVALID";   // مسیر دفاعی: حالت خراب
}

int main(void)
{
    printf("%s\n", describe(STATE_RUN));
    printf("%s\n", describe((state_t)42));
    return 0;
}
  1. switch کامل + مسیر دفاعی. هر سه حالت return می‌کنند، پس فقط مقدار خراب به خط return "INVALID" می‌رسد. هم هشدار -Wswitch برای حالت فراموش‌شده را نگه می‌داریم، هم حالت خراب بی‌صدا رد نمی‌شود. در برنامهٔ واقعی به‌جای متن یک تابع خطا یا ریست صدا بزن.
  2. مقدار خراب. (state_t)42 هیچ حالت مجازی نیست و به مسیر دفاعی می‌رسد.
$ ./state_ok
run
INVALID
دو نکته درباره enum در C

(۱) اسم‌های enum ثابت‌های int هستند و کامپایلر نمی‌گذارد اشتباه بودن مقدار را ببیند: state_t s = 42; بدون خطا کامپایل می‌شود. (۲) اندازهٔ خودِ نوع enum را استاندارد C تعیین نمی‌کند؛ به پیاده‌سازی (کامپایلر و ABI) بستگی دارد. در ادامه می‌بینی که روی PC چهار بایت است ولی روی arm-none-eabi-gcc فقط یک بایت.

اندازهٔ enum: روی PC یک عدد، روی Cortex-M عددی دیگر

کامپایلر مجاز است کوچک‌ترین نوع صحیحی را انتخاب کند که همهٔ مقدارها در آن جا شود. gcc برای ARM (ABI به اسم EABI) پیش‌فرضش همین است: سوئیچ -fshort-enums به‌طور پیش‌فرض روشن است، پس enum سه‌حالتی یک بایت می‌شود. روی PC (x86-64) و معمولا در ESP32 همان int یعنی چهار بایت است. این را خودمان اندازه بگیریم:

#include <stdio.h>

typedef enum { STATE_IDLE, STATE_RUN, STATE_ERROR } state_t;

int main(void)
{
    printf("sizeof(state_t) = %zu\n", sizeof(state_t));
    return 0;
}
  1. یک enum سه‌حالتی. مقدارها ۰ تا ۲؛ در یک بایت جا می‌شوند.
  2. اندازهٔ نوع. روی PC چهار بایت چاپ می‌شود. اگر همین برنامه را برای Cortex-M4 بسازی، ۱ می‌شود. تست واحد روی PC و برنامه روی برد، اندازهٔ ساختارهایی که enum دارند را متفاوت می‌بینند.
$ ./enum_size
sizeof(state_t) = 4

روی هدف واقعی این ادعا را ثابت می‌کنیم. این فایل با arm-none-eabi-gcc بدون خطا ساخته می‌شود چون اندازه واقعا ۱ است:

typedef enum { STATE_IDLE, STATE_RUN, STATE_ERROR } state_t;

// روی arm-none-eabi-gcc (پیش‌فرض -fshort-enums) اندازه ۱ است
_Static_assert(sizeof(state_t) == 1, "short enum on arm-none-eabi");
  1. همان enum. هیچ مقداردهی خاصی نیست.
  2. ادعای زمان کامپایل. _Static_assert اندازه را برابر ۱ می‌خواهد. اگر همین فایل را روی PC یا با -fno-short-enums بسازی، ادعا شکست می‌خورد و کامپایل متوقف می‌شود (خودم با -fno-short-enums امتحان کردم). یعنی کد به یک تنظیم کامپایلر وابسته است؛ خودش را نشان می‌دهد، نه اینکه بی‌صدا غلط شود.
قاعدهٔ عملی: روی «سیم» (پکت، ثبات، فایل) enum نگذار

هر چیزی که بین دو برنامه یا دو پردازنده رد و بدل می‌شود (پکت UART، رکورد ذخیره‌شده در Flash، ثبات سخت‌افزار) باید اندازه و چیدمان ثابت داشته باشد. پس فیلد را با نوع با پهنای ثابت بنویس (uint8_t، uint16_t، ...) و مقدار enum را با cast داخلش بریز: pkt.state = (uint8_t)STATE_RUN;. enum را فقط برای منطق داخل برنامه نگه دار. (گزینهٔ -fno-short-enums هم هست، ولی تمام فایل‌ها و کتابخانه‌های پروژه باید با یک تنظیم ساخته شوند؛ لینکر با ترکیب دو جور فایل هشدار ناسازگاری ABI می‌دهد.)

(۱) در C نوع enum عملا یک int است و کامپایلر نمی‌گذارد اشتباه بودن مقدار را ببیند: state_t s = 42; بدون خطا کامپایل می‌شود. (۲) اندازه یک enum معمولا ۴ بایت است. برای پکت‌هایی که باید یک بایت باشند، فیلد را uint8_t بگیر و مقدار enum را داخلش بریز.

struct و اشاره‌گر: نقطه یا پیکان؟

در درس ۲.۶ دیدی پارامتر تابع کپی است. برای struct هم همین است: اگر struct بزرگ (مثلا ۱۰۰ بایت) را by value بدهی، همه‌اش کپی می‌شود، هم کند است و هم تابع نمی‌تواند نسخه اصلی را تغییر دهد. راه حل همان اشاره‌گر درس ۳.۲ است. برای رسیدن به فیلد از راه اشاره‌گر پیکان -> داریم: p->x یعنی (*p).x ( «برو به جایی که p می‌گوید، بعد فیلد x»).

#include <stdio.h>

typedef struct {
    int x;
    int y;
} point_t;

typedef struct {
    point_t top_left;
    int w;
    int h;
} rect_t;

static void move_by_value(point_t p)
{
    p.x += 10;                      // فقط کپی عوض می‌شود
}

static void move_by_ptr(point_t *p)
{
    p->x += 10;                     // خود شیء اصلی عوض می‌شود
}

static int area(const rect_t *r)
{
    return r->w * r->h;
}

int main(void)
{
    point_t a = {1, 2};
    rect_t box = {.top_left = {0, 0}, .w = 4, .h = 3};

    move_by_value(a);
    printf("after by value: x=%d\n", a.x);
    move_by_ptr(&a);
    printf("after by pointer: x=%d\n", a.x);
    printf("area=%d, corner x=%d\n", area(&box), box.top_left.x);
    return 0;
}
  1. نوع نقطه. نوع point_t با دو فیلد.
  2. struct تودرتو. یک مستطیل، خودش یک point_t را به‌عنوان فیلد دارد. به فیلدها با زنجیره نقطه می‌رسی: box.top_left.x. داخل حافظه هم فیلد تودرتو مستقیما داخل بسته بیرونی می‌نشیند، نه جای دیگر. همه‌چیز یک تکه پیوسته است.
  3. by value. p کپی است، پس p.x += 10 فقط کپی را عوض می‌کند و در main اثری ندارد.
  4. با اشاره‌گر. p->x به خود شیء اصلی می‌رسد و ۱۰ تا اضافه می‌کند. پیکان چون اشاره‌گر است. اگر به‌جایش نقطه بنویسی (p.x)، کامپایلر خطا می‌دهد؛ نمونه‌اش در تمرین ۲ است.
  5. const برای خواندن. area فقط می‌خواند، پس const rect_t * می‌گیرد (درس ۳.۳). ساختار بزرگ را by value نمی‌دهیم و با const قول می‌دهیم آن را عوض نکنیم.
  6. مقداردهی تودرتو. فیلد مستطیل هم با نام مقدار می‌گیرد.
  7. by value. بعد از صدا زدن، a.x هنوز ۱ است.
  8. با آدرس. &a آدرس بسته را می‌دهد؛ حالا a.x شد ۱۱.
  9. مساحت. ۴×۳ = ۱۲ و گوشه x=0.
$ ./ptr_arrow

after by pointer: x=11
area=12, corner x=0

اندازه واقعی struct و بایت‌های خالی

سه فیلد uint8_t، uint32_t و uint8_t روی هم ۱ + ۴ + ۱ = ۶ بایت‌اند. فکر می‌کنی sizeof چه بشود؟ ۶؟ جواب ۱۲ است! دلیلش همان تراز است که در درس ۳.۳ دیدی: uint32_t باید در آدرسی بنشیند که مضرب ۴ است. پس کامپایلر بعد از فیلد اول ۳ بایت خالی می‌گذارد. به این بایت‌های خالی padding می‌گویند.

قاعده‌ها (روی ARM و ESP32 و PC معمول است):

  1. هر فیلد در آدرسی شروع می‌شود که بر تراز خودش (معمولا اندازه‌اش) بخش‌پذیر باشد.
  2. ترتیب فیلدها ثابت است. کامپایلر فیلدها را جابه‌جا نمی‌کند؛ فقط لابه‌لایشان بایت خالی می‌گذارد.
  3. کل struct هم مضربی از بزرگ‌ترین تراز فیلدهایش می‌شود (بایت خالی در انتها)، تا در یک آرایه از struct همه عنصرها هم‌تراز بمانند.
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>

struct wasteful {
    uint8_t a;
    uint32_t b;
    uint8_t c;
};

struct sorted {
    uint32_t b;
    uint8_t a;
    uint8_t c;
};

struct __attribute__((packed)) tight {
    uint8_t a;
    uint32_t b;
    uint8_t c;
};

int main(void)
{
    printf("wasteful: size=%zu, offset of b=%zu, offset of c=%zu\n",
           sizeof(struct wasteful), offsetof(struct wasteful, b), offsetof(struct wasteful, c));
    printf("sorted:   size=%zu\n", sizeof(struct sorted));
    printf("tight:    size=%zu, offset of b=%zu\n", sizeof(struct tight), offsetof(struct tight, b));
    return 0;
}
  1. ترتیب بد. یک بایت، بعد عدد چهاربایتی، بعد یک بایت دیگر. فیلد b فقط در آفست ۴ می‌تواند بنشیند (۳ بایت خالی بعد از a). فیلد c در آفست ۸ می‌نشیند و آخر هم ۳ بایت خالی تا ۱۲ می‌رسد.
  2. ترتیب مرتب. همان فیلدها، ولی بزرگ‌ترین اول. حالا a و c کنار هم می‌نشینند و فقط ۲ بایت خالی در انتها می‌ماند: ۸ بایت. قاعده سرانگشتی: فیلدها را از بزرگ به کوچک بنویس. اگر لازم نیست ترتیب معنایی خاصی داشته باشند، ۳۳٪ RAM را نجات می‌دهد (از ۱۲ به ۸).
  3. حالت packed. __attribute__((packed)) افزونه gcc/clang است و padding را حذف می‌کند: ۶ بایت. توضیح خطرش پایین‌تر است.
  4. offsetof. ماکرو استاندارد در stddef.h: فاصله فیلد از ابتدای struct بر حسب بایت. اینجا نشان می‌دهد b در ۴ و c در ۸ است. به‌جای حدس زدن، از خود کامپایلر بپرس. در ساختار پروتکل و رجیستر، همین ماکرو راه اثبات درستی است.
  5. اندازه‌ها. ۱۲ و ۸ و ۶.

sorted:   size=8
tight:    size=6, offset of b=1

بایت‌های خالی «آشغال» دارند: قبل از ارسال یا مقایسه

مقدار بایت‌های padding نامعین است. سه نتیجه: (۱) memcmp روی دو struct ممکن است «نابرابر» بگوید با اینکه همهٔ فیلدها برابرند. (۲) اگر کل struct را به UART یا فایل بفرستی، بایت‌های قدیمی حافظه (مثلا بخشی از یک رمز) هم بیرون می‌روند و CRC هم هر بار فرق می‌کند. (۳) sensor_t s = {0}; فیلدها را صفر می‌کند ولی صفر شدن padding را تضمین نمی‌کند؛ فقط memset(&s, 0, sizeof s) این تضمین را می‌دهد. پس: یا پیش از ساخت memset بزن، یا فیلد به فیلد بفرست.

روی میکروکنترلر این عددها را می‌شود قبل از اجرا اثبات کرد. اگر برنامه‌ات به اندازه یا آفست خاصی تکیه دارد (مثلا مدل رجیستر)، آن را با _Static_assert بنویس؛ اگر عدد غلط باشد برنامه اصلا ساخته نمی‌شود. این‌جا برای ARM Cortex-M4 کامپایل می‌شود، یعنی ثابت می‌کند روی هدف واقعی هم همین ۱۲ و ۸ است:

#include <stddef.h>
#include <stdint.h>

struct wasteful {
    uint8_t a;
    uint32_t b;
    uint8_t c;
};

struct sorted {
    uint32_t b;
    uint8_t a;
    uint8_t c;
};

// اگر عددها درست نباشند، همین‌جا کامپایل می‌شکند
_Static_assert(sizeof(struct wasteful) == 12, "wasteful must be 12 bytes");
_Static_assert(offsetof(struct wasteful, b) == 4, "b at offset 4");
_Static_assert(sizeof(struct sorted) == 8, "sorted must be 8 bytes");
  1. هدرها. stddef.h برای offsetof و stdint.h برای اندازه‌های ثابت.
  2. دو چیدمان. همان دو struct قبلی.
  3. ادعای زمان کامپایل. _Static_assert(شرط, "پیام") در C11: اگر شرط نادرست باشد کامپایل شکست می‌خورد. سه ادعا: اندازه ۱۲، آفست b برابر ۴، اندازه دیگری ۸. بدون سخت‌افزار و بدون اجرا ثابت می‌شود که روی این پردازنده پیش‌بینی درست بوده است. اگر کسی فیلدی وسط struct اضافه کند، همین‌جا اعتراض می‌کند.
زیر کاپوت: packed چه می‌کند و چرا خطرناک است

packed به کامپایلر می‌گوید «هیچ بایت خالی نگذار». اندازه کمتر می‌شود و ساختار پکت روی سیم دقیقا با آنچه دو طرف قرار گذاشته‌اند یکی می‌شود. اما هزینه دارد: فیلد b حالا در آفست ۱ است، یعنی ناهم‌تراز. کامپایلر برای هر دسترسی باید کد بیشتر بسازد (مثلا بایت‌به‌بایت بخواند). روی Cortex-M0 بدون این کدِ اضافه خطای سخت‌افزاری می‌داد. اگر آدرس فیلد packed را بگیری و به uint32_t * بدهی، کامپایلر دیگر نمی‌داند ناهم‌تراز است و خطا می‌شود؛ gcc در این حالت هشدار -Waddress-of-packed-member می‌دهد. قاعده: packed را فقط برای تعریف پکت خارجی به‌کار ببر و فیلدها را با نام بخوان، نه با اشاره‌گر. برای رجیسترهای سخت‌افزار اصلا لازم نیست (آنها خودشان هم‌ترازند).

bit-field یا ماسک؟

گاهی یک فیلد فقط چند بیت لازم دارد: یک پرچم ۱ بیتی، یک حالت ۳ بیتی. C اجازه می‌دهد بعد از اسم فیلد : تعداد_بیت بنویسی. به این bit-field می‌گویند. نوشتنش راحت است، اما بسیاری از جزئیاتش را استاندارد C به پیاده‌ساز واگذار کرده: بیت‌ها از ابتدا پر می‌شوند یا از انتها؟ فیلدها در چه اندازه واحد ذخیره می‌شوند؟ آیا از مرز واحد رد می‌شوند؟ پس همان struct ممکن است روی دو کامپایلر مختلف چیدمان متفاوت داشته باشد. دو راه را کنار هم ببین:

#include <stdint.h>
#include <stdio.h>

struct status_bits {
    unsigned ready : 1;
    unsigned error : 1;
    unsigned mode  : 3;
};

#define ST_READY  (1u << 0)
#define ST_ERROR  (1u << 1)
#define ST_MODE_SHIFT 2u
#define ST_MODE_MASK  (0x7u << ST_MODE_SHIFT)

int main(void)
{
    struct status_bits s = {.ready = 1, .mode = 5};
    uint8_t reg = 0;

    reg |= ST_READY;
    reg |= (uint8_t)(5u << ST_MODE_SHIFT);

    printf("sizeof(bit-field struct) = %zu\n", sizeof s);
    printf("bit-field: ready=%u error=%u mode=%u\n", s.ready, s.error, s.mode);
    printf("mask:      ready=%u error=%u mode=%u\n",
           (unsigned)(reg & ST_READY),
           (unsigned)((reg & ST_ERROR) != 0u),
           (unsigned)((reg & ST_MODE_MASK) >> ST_MODE_SHIFT));
    return 0;
}
  1. bit-field. ready یک بیت، error یک بیت و mode سه بیت. روی هم ۵ بیت که داخل یک واحد unsigned (۴ بایت) جا می‌شوند. اندازه ۴ است نه ۱؛ چون واحد ذخیره unsigned است. چیدمان بیت‌ها به کامپایلر بستگی دارد (در gcc روی این پردازنده‌ها از بیت صفر شروع می‌شود، ولی تضمین استاندارد نیست).
  2. راه ماسک. هر پرچم یک ثابت با شیفت است؛ فیلد چندبیتی با ماسک و مقدار شیفت. این همان روش درس ۳.۱ است. در این راه هر بیت را خودت تعیین می‌کنی و تضمین می‌دهی روی هر کامپایلر یکسان باشد. مستندات رجیستر هم بیت‌ها را همین‌طور می‌گوید.
  3. bit-field با نام. مقداردهی نامزد: .ready = 1 و .mode = 5.
  4. راه ماسک. همان مقدارها را به صورت یک بایت می‌سازد: بیت ۰ برای ready، بیت‌های ۲ تا ۴ برای mode.
  5. چاپ اول. اندازه و مقدارها با نام.
  6. چاپ دوم. با ماسک: تست هر پرچم با & و بیرون کشیدن فیلد با ماسک و شیفت به راست.

توصیه برای کد سخت‌افزار

برای رجیسترها و پکت‌ها ماسک و شیفت را ترجیح بده. bit-field فقط وقتی مناسب است که چیدمان برایت مهم نباشد (مثلا صرفه‌جویی RAM در داخل خود برنامه). یک دلیل قوی‌تر هم دارد: کامپایلر برای خواندن یا نوشتن bit-field روی رجیستر محیطی آزاد است دسترسی بایتی یا نیم‌کلمه‌ای تولید کند، در حالی که بعضی رجیسترها فقط دسترسی ۳۲ بیتی کامل را درست می‌پذیرند. کتابخانه‌های ST و ESP-IDF هم برای بیت‌های ثبات‌ها معمولا از ثابت‌های ماسک استفاده می‌کنند، هر چند بعضی ساختارهای سیستمی bit-field دارند.

union: یک حافظه، چند عینک

union شبیه struct نوشته می‌شود، ولی فیلدها پشت سر هم نمی‌نشینند؛ همه از یک آدرس شروع می‌شوند و روی هم می‌افتند. اندازه union برابر بزرگ‌ترین فیلد است. مثل یک تکه حافظه که می‌توانی از سه عینک مختلف نگاهش کنی: یک بار به‌عنوان یک عدد ۳۲ بیتی، یک بار دو عدد ۱۶ بیتی، یک بار چهار بایت.

#include <stdint.h>
#include <stdio.h>

typedef union {
    uint32_t word;
    uint16_t half[2];
    uint8_t byte[4];
} view32_t;

int main(void)
{
    view32_t v;
    v.word = 0x12345678u;
    printf("sizeof = %zu\n", sizeof(view32_t));
    printf("half[0] = 0x%04X, half[1] = 0x%04X\n", (unsigned)v.half[0], (unsigned)v.half[1]);
    printf("byte[0] = 0x%02X, byte[3] = 0x%02X\n", (unsigned)v.byte[0], (unsigned)v.byte[3]);
    v.byte[0] = 0xFF;
    printf("word now = 0x%08X\n", (unsigned)v.word);
    return 0;
}
  1. تعریف. سه دید روی همان ۴ بایت: word (یک عدد)، half[2] (دو عدد ۱۶ بیتی)، byte[4] (چهار بایت). در C، خواندن فیلدی که آخرین بار روی آن ننوشته‌ای، بایت‌های حافظه را با نوع جدید تفسیر می‌کند و مجاز است (در C++ این‌طور نیست). ولی نتیجه به ترتیب بایت‌ها بستگی دارد.
  2. نوشتن با یک دید. کل چهار بایت با یک عدد پر می‌شود.
  3. اندازه. ۴ بایت و نه ۸: فیلدها روی هم افتاده‌اند.
  4. دید ۱۶ بیتی. half[0] نیمه پایین (0x5678) است. چون little-endian است، نیمه کم‌ارزش در آدرس پایین‌تر می‌نشیند.
  5. دید بایتی. byte[0] کم‌ارزش‌ترین بایت (0x78) و byte[3] پرارزش‌ترین (0x12) است.
  6. نوشتن با دید دیگر. فقط بایت اول را عوض می‌کنیم و word خودکار تغییر می‌کند: 0x123456FF. هیچ کپی در کار نیست؛ همه دیدها همان یک حافظه‌اند.

union برچسب‌دار

کاربرد دیگر union: یک «جعبه» که یا یک int دارد یا یک float، و برای اینکه بدانی الان کدام است، یک فیلد kind (از جنس enum) کنارش می‌گذاری. به این الگو union برچسب‌دار (tagged union) می‌گویند و پایه پیام‌ها و رویدادهای مختلف در سیستم‌های embedded است.

#include <stdio.h>

typedef enum {
    VAL_INT,
    VAL_FLOAT
} val_kind_t;

typedef struct {
    val_kind_t kind;
    union {
        int i;
        float f;
    } as;
} value_t;

static void print_value(const value_t *v)
{
    if (v->kind == VAL_INT) {
        printf("int %d\n", v->as.i);
    } else {
        printf("float %.2f\n", (double)v->as.f);
    }
}

int main(void)
{
    value_t a = {.kind = VAL_INT, .as.i = 42};
    value_t b = {.kind = VAL_FLOAT, .as.f = 3.5f};
    print_value(&a);
    print_value(&b);
    printf("sizeof(value_t) = %zu\n", sizeof(value_t));
    return 0;
}
  1. برچسب. enum می‌گوید داخل جعبه چه چیزی است.

۱. ثبات‌های سخت‌افزار = یک struct روی آدرس ثابت

یک پورت GPIO در STM32F4 ده‌ها ثبات ۳۲ بیتی پشت سر هم دارد (MODER در آفست 0x00، ODR در 0x14، BSRR در 0x18 و …؛ جدولش در RM0383). اگر فیلدهای struct را به همان ترتیب و همه از نوع uint32_t بنویسی، هیچ padding‌ای نمی‌ماند و آفست هر فیلد دقیقا آدرس ثبات می‌شود. بعد کافی است آدرس پایه پورت را به اشاره‌گر struct تبدیل کنی. همان چیزی که در فایل‌های stm32f4xx.h ST به اسم GPIO_TypeDef و GPIOA می‌بینی.

#include <stddef.h>
#include <stdint.h>

typedef struct {
    volatile uint32_t MODER;        // +0x00
    volatile uint32_t OTYPER;       // +0x04
    volatile uint32_t OSPEEDR;      // +0x08
    volatile uint32_t PUPDR;        // +0x0C
    volatile uint32_t IDR;          // +0x10
    volatile uint32_t ODR;          // +0x14
    volatile uint32_t BSRR;         // +0x18
    volatile uint32_t LCKR;         // +0x1C
    volatile uint32_t AFR[2];       // +0x20
} gpio_regs_t;

_Static_assert(offsetof(gpio_regs_t, ODR) == 0x14, "ODR offset");
_Static_assert(offsetof(gpio_regs_t, BSRR) == 0x18, "BSRR offset");
_Static_assert(sizeof(gpio_regs_t) == 0x28, "gpio size");

#define GPIOA ((gpio_regs_t *)0x40020000u)

void led_toggle(void)
{
    GPIOA->ODR ^= (1u << 5);        // PA5 = LD2
}
  1. نقشه ثبات‌ها. هر خط یک ثبات ۳۲ بیتی است؛ کامنت‌ها آفست را می‌گویند. AFR[2] دو ثبات پشت هم (AFRL و AFRH) است. کلمه volatile به کامپایلر می‌گوید این حافظه را سخت‌افزار هم عوض می‌کند و هیچ خواندن یا نوشتنی را حذف نکند. دلیل کامل و مثال در درس ۳.۶ است؛ فعلا آن را همراه هر ثبات ببین.
  2. اثبات نقشه. سه ادعا زمان کامپایل: آفست ODR برابر 0x14، آفست BSRR برابر 0x18 و اندازه کل 0x28. این ادعاها همان عددهای مستندات‌اند. اگر اشتباها فیلدی جا بیفتد یا اضافه شود، کامپایل می‌شکند، پیش از اینکه LED روی برد اشتباه کار کند.
  3. آدرس پایه به اشاره‌گر. پورت GPIOA در STM32F411 از 0x40020000 شروع می‌شود. cast آن را «اشاره‌گر به struct» می‌کند تا GPIOA->ODR مثل هر struct دیگری کار کند.
  4. یک خط کار. GPIOA->ODR ^= (1u << 5) بیت ۵ ثبات خروجی را برعکس می‌کند. پایه PA5 روی برد Nucleo به LED کاربر LD2 وصل است. این تابع کامپایل می‌شود ولی نه روی PC اجرا می‌شود (آدرس 0x40020000 در PC وجود ندارد). در درس ۵.۲ همین را روی برد اجرا می‌کنیم.
پیش از لمس GPIOA: کلاک پورت را روشن کن

در STM32F4 کلاک هر پریفرال پس از ریست خاموش است. تا بیت ۰ رجیستر RCC_AHB1ENR (یعنی GPIOAEN، آدرس 0x40023830) را روشن نکنی، نوشتن در GPIOA->MODER یا ODR اثری ندارد و خواندن هم مقدار قابل‌اتکایی نمی‌دهد. در CMSIS ساختار RCC هم دقیقا مثل همین struct ساخته شده (RCC->AHB1ENR |= 1u;). پس led_toggle بالا بدون این مرحله روی برد چیزی را چشمک نمی‌زند؛ این کار و تنظیم MODER در درس ۳.۶ و ۵.۲ کامل می‌آید.

یک نکتهٔ دیگر دربارهٔ همین نقشه: BSRR فقط‌نوشتنی است و خواندنش صفر می‌دهد. پس GPIOA->BSRR |= ... (که اول می‌خواند) منطقی نیست؛ همیشه با = در آن بنویس. جزئیاتش در درس ۳.۶ است.

همین ایده را می‌توانی روی PC هم بازی کنی. به‌جای آدرس سخت‌افزار، یک تکه RAM معمولی می‌گذاریم و همان نوشتن‌ها را می‌کنیم. این نمونه اجرا می‌شود و offsetof عددهای مستندات را نشان می‌دهد:

#include <stddef.h>
#include <stdint.h>
#include <stdio.h>

typedef struct {
    volatile uint32_t MODER;
    volatile uint32_t OTYPER;
    volatile uint32_t OSPEEDR;
    volatile uint32_t PUPDR;
    volatile uint32_t IDR;
    volatile uint32_t ODR;
    volatile uint32_t BSRR;
} gpio_sim_t;

static gpio_sim_t fake_gpioa;           // قطعه‌ای از RAM به‌جای سخت‌افزار
#define GPIOA (&fake_gpioa)

int main(void)
{
    GPIOA->ODR |= (1u << 5);
    printf("ODR after set   = 0x%08X\n", (unsigned)GPIOA->ODR);
    GPIOA->ODR ^= (1u << 5);
    printf("ODR after toggle = 0x%08X\n", (unsigned)GPIOA->ODR);
    printf("offset of ODR = 0x%zX, BSRR = 0x%zX\n", offsetof(gpio_sim_t, ODR), offsetof(gpio_sim_t, BSRR));
    return 0;
}
  1. نقشه ناقص. فقط هفت ثبات اول.
  2. جای‌گزین سخت‌افزار. یک متغیر سراسری از همان نوع؛ ماکرو GPIOA آدرسش را می‌دهد. بقیه کد می‌تواند عین کد واقعی باشد. این کاری است که در تست واحد روی PC می‌کنند: سخت‌افزار را با یک struct معمولی جایگزین می‌کنی (درس ۶.۴).
  3. Set. بیت ۵ را روشن می‌کند: 0x20.
  4. Toggle. همان بیت را برعکس می‌کند و به ۰ برمی‌گردد.
  5. آفست‌ها. 0x14 و 0x18: عینا همان عددهای مستندات.

۳. ESP32

در ESP-IDF تقریبا همه چیز struct است: پیکربندی GPIO یک struct به اسم gpio_config_t است که با مقداردهی نامزد پر می‌کنی (.pin_bit_mask، .mode و …) و به gpio_config() می‌دهی. حالت‌های سیستم و کدهای خطا هم enum هستند (مثل esp_err_t که در ۵.۶ می‌آید). این کد همان الگوی این درس را نشان می‌دهد؛ اسم فیلدها از ESP-IDF v5.x است و در مستندات رسمی آن را ببین:

#include "driver/gpio.h"

{

        .pin_bit_mask = 1ULL << 2,       // GPIO2
        .mode = GPIO_MODE_OUTPUT,

  2. ماسک پین. 1ULL << 2 بیت شماره ۲ در یک عدد ۶۴ بیتی. ULL یعنی unsigned long long تا شیفت در ۶۴ بیت انجام شود.

#include <stddef.h>
#include <stdio.h>

typedef struct {
    const char *name;
    int temp_c;
} room_t;

static const room_t *find_hottest(const room_t *rooms, size_t n)
{
    const room_t *best = &rooms[0];
    for (size_t i = 1; i < n; i++) {
        if (rooms[i].temp_c > best->temp_c) {
            best = &rooms[i];
        }
    }
    return best;
}

int main(void)
{
    const room_t rooms[] = {
        {"kitchen", 27},
        {"bedroom", 21},
        {"garage", 15},
        {"lab", 31},
    };
    size_t n = sizeof rooms / sizeof rooms[0];
    const room_t *hot = find_hottest(rooms, n);
    int sum = 0;

    for (size_t i = 0; i < n; i++) {
        sum += rooms[i].temp_c;
    }
    printf("hottest: %s (%d C)\n", hot->name, hot->temp_c);
    printf("average: %d C\n", sum / (int)n);
    return 0;
}

  2. مقایسه فیلد به فیلد. دو اشاره‌گر const می‌گیرد و هر دو فیلد را چک می‌کند. && یعنی هر دو باید برابر باشند. نمی‌توانیم از memcmp کل struct استفاده کنیم چون بایت‌های padding مقدار مشخصی ندارند و دو struct با فیلد یکسان ممکن است با memcmp برابر درنیایند.
  3. پیکان. p->x به‌جای p.x.
  4. مقایسه. point_equal(&a, &b) عدد ۱ (درست) برمی‌گرداند.

تمرین ۳: شبیه‌سازی GPIO روی PC (کار با سخت‌افزار)

می‌خواهیم منطق روشن و خاموش کردن LED را قبل از رسیدن برد، روی PC آزمایش کنیم. به‌جای 0x40020000 یک struct معمولی می‌گذاریم.

  1. پیش‌نمایش: اگر هفت ثبات ۳۲ بیتی از MODER تا BSRR پشت هم باشند، آفست ODR و BSRR چند است؟ (هر ثبات ۴ بایت است و ODR ششمین است.)
  2. حل: struct را تعریف کن، یک نمونه سراسری بساز، بیت ۵ ODR را روشن کن، چاپ کن، برعکس کن و دوباره چاپ کن.
  3. ادعا: با _Static_assert ثابت کن آفست ODR برابر 0x14 است.
راهنمایی

ثبات‌ها را از MODER تا BSRR به همین ترتیب بنویس. بیت ۵ یعنی (1u << 5). روشن کردن با |= و برعکس کردن با ^= (درس ۳.۱). offsetof در stddef.h است.

چه باید ببینی؟ 
$ ./gpio_sim
ODR after set   = 0x00000020
ODR after toggle = 0x00000000
offset of ODR = 0x14, BSRR = 0x18

جواب الف: ODR ششمین است و هر کدام ۴ بایت، پس 5 × 4 = 20 = 0x14. BSRR هفتمین است: 0x18.

جواب کامل با توضیح

کد همان نمونه بخش «در STM32 و ESP32 یعنی چه؟» است؛ فقط _Static_assert را هم اضافه کن. نسخه کامل:

#include <stddef.h>
#include <stdint.h>
#include <stdio.h>

typedef struct {
    volatile uint32_t MODER;
    volatile uint32_t OTYPER;
    volatile uint32_t OSPEEDR;
    volatile uint32_t PUPDR;
    volatile uint32_t IDR;
    volatile uint32_t ODR;
    volatile uint32_t BSRR;
} gpio_sim_t;

_Static_assert(offsetof(gpio_sim_t, ODR) == 0x14, "ODR must be at 0x14");

static gpio_sim_t fake_gpioa;
#define GPIOA (&fake_gpioa)

int main(void)
{
    GPIOA->ODR |= (1u << 5);
    printf("ODR after set    = 0x%08X\n", (unsigned)GPIOA->ODR);
    GPIOA->ODR ^= (1u << 5);
    printf("ODR after toggle = 0x%08X\n", (unsigned)GPIOA->ODR);
    return 0;
}
  1. نقشه ثبات‌ها. ترتیب فیلدها ترتیب آفست‌هاست؛ همه uint32_t‌اند، پس padding نیست.
  2. اثبات آفست. اگر کسی ترتیب را بهم بریزد، کامپایل نمی‌شود. بهتر است این دفاع را بلافاصله کنار تعریف struct ثبات بنویسی، نه جای دیگر.
  3. جای‌گزین ثبات‌ها. متغیر سراسری از همان نوع (سراسری‌ها صفر شروع می‌شوند)، و ماکرو که آدرسش را می‌دهد.
  4. Set و Toggle. با GPIOA->ODR مثل کد واقعی. فردا که برد رسید، فقط تعریف GPIOA عوض می‌شود؛ بقیه منطق دست‌نخورده می‌ماند.
$ ./gpio_sim2
ODR after set    = 0x00000020
ODR after toggle = 0x00000000
حرف مربی

معمولا سه جا گیر می‌کنند. اول padding: «چرا sizeof از جمع فیلدها بیشتر است؟» جواب همیشه تراز است؛ با offsetof ببین. دوم نقطه یا پیکان: یک قاعده یک‌خطی؛ اگر جلوی حرف p ستاره هست یا خودش اشاره‌گر است، پیکان. سوم وسوسه packed: وقتی RAM کم است، سریع دست به packed می‌بری؛ اول ترتیب فیلدها را از بزرگ به کوچک بچین. ۹۰٪ وقت‌ها همان کافی است و ناهم‌ترازی هم نمی‌آید. و یک عادت طلایی: هر struct مهم (رجیستر، پکت) را کنارش با _Static_assert قفل کن.

خلاصه یک‌دقیقه‌ای

  • struct: چند فیلد پشت هم در یک تکه حافظه. a.x روی شیء، p->x روی اشاره‌گر. = کل struct را کپی می‌کند.
  • مقداردهی نامزد {.x = 1} امن‌تر از ترتیبی است؛ فیلدهای جاافتاده صفر می‌شوند.
  • typedef فقط اسم دیگری برای یک نوع می‌سازد؛ قرارداد _t.
  • enum به عددهای حالت اسم می‌دهد؛ ترفند COUNT در آخر. در switch بدون default کامپایلر حالت فراموش‌شده را نشان می‌دهد.
  • padding از تراز می‌آید: هر فیلد در مضرب تراز خودش می‌نشیند و اندازه کل مضرب بزرگ‌ترین تراز است. فیلدها را از بزرگ به کوچک بنویس؛ با sizeof، offsetof و _Static_assert ثابت کن.
  • packed padding را برمی‌دارد ولی ناهم‌ترازی می‌آورد؛ فقط برای پکت خارجی. bit-field به پیاده‌ساز وابسته است؛ برای رجیستر ماسک بهتر است.
  • union: یک حافظه با چند دید، اندازه برابر بزرگ‌ترین فیلد. با برچسب enum می‌شود یک «جعبه چندنوعی» ساخت.
  • رجیستر سخت‌افزار = struct از uint32_t روی آدرس پایه: GPIOA->ODR.

درس بعد: ۳.۵ نقشه حافظه و طول عمر متغیر؛ ببین متغیرهایت واقعا کجا زندگی می‌کنند.
