تا اینجا فقط دربارهٔ C حرف زدیم. حالا وقتش است که یک برنامه بنویسی، اجرایش کنی و ببینی روی صفحه چیزی ظاهر می‌شود. ولی این درس فقط «سلام دنیا» نیست: می‌خواهیم بفهمی بین فایل متنی‌ای که تایپ می‌کنی و برنامه‌ای که پردازنده اجرا می‌کند دقیقا چه اتفاقی می‌افتد. کسی که این مسیر را بفهمد، پیام‌های خطا را هم می‌فهمد و برای میکروکنترلر هم همین راه را می‌رود.

🎯 بعد از این درس می‌توانی

  • اولین برنامهٔ C را بنویسی، کامپایل و اجرا کنی و هر خطش را توضیح بدهی
  • چهار مرحلهٔ ساخت (پیش‌پردازش، کامپایل، اسمبل، لینک) را با دستور واقعی و فایل‌های میانی ببینی
  • فرق فایل‌های .c .h .o .elf .bin .hex را بگویی
  • بگویی چرا برای میکروکنترلر «کامپایلر متقاطع» لازم است و چرا آنجا main تمام نمی‌شود
  • پیام خطای کامپایلر را بخوانی: اولین خطا اول، فرق «خطا» و «هشدار»، معنی پرچم‌های -Wall -Wextra

🧰 پیش‌نیاز و وسایل

  • درس ۱.۳: باید کامپایلر gcc روی رایانه‌ات نصب باشد (یا یک کامپایلر آنلاین آماده‌شده)
  • درس ۱.۱: فهمیدن اینکه برنامه = دستورهایی در حافظهٔ Flash که پردازنده یکی‌یکی اجرا می‌کند
  • هیچ سخت‌افزاری لازم نیست. بخش آخر فقط پیش‌نمایش است

ایدهٔ اصلی: دستور پخت و آشپز

یک دستور پخت را تصور کن که به زبان فارسی نوشته شده. آشپز فقط ترکی می‌فهمد. پس یک مترجم لازم داری. مترجم متن فارسی را می‌خواند و همان دستور را به ترکی می‌نویسد. آشپز از روی نسخهٔ ترکی کار می‌کند و از فارسی چیزی نمی‌داند.

مثال از زندگی روزمره

دستور پخت فارسی = برنامهٔ C که تو می‌نویسی (متنی که آدم می‌فهمد). مترجم = کامپایلر. نسخهٔ ترکی = کد ماشین، یعنی فقط عددهایی که پردازنده می‌فهمد. آشپز = پردازنده. اگر آشپز به‌جای رایانه، «ریزآشپز» بود که زبانش فرق دارد، به مترجم دیگری نیاز داشتی. میکروکنترلر همان ریزآشپز است.

پس دو نوع «نوشته» داریم:

  • کد منبع (source code): متنی که تو با ویرایشگر تایپ می‌کنی. فایل معمولی است؛ با ویندوز Notepad هم می‌شود بازش کرد.
  • کد ماشین (machine code): فقط عدد. پردازنده فقط همین را اجرا می‌کند و آدم نمی‌تواند راحت بخواندش.

کار ما این است که اول کد منبع بنویسیم و بعد ابزارها آن را به کد ماشین تبدیل کنند. بیا با کوچک‌ترین برنامهٔ واقعی شروع کنیم.

اولین برنامه: سلام دنیا

این برنامه فقط یک جمله روی صفحه می‌نویسد. در پوشهٔ c-course (که در درس ۱.۳، بخش ترمینال ساختی) فایلی به اسم hello.c بساز (پسوند .c یعنی «این فایل کد C است»)، دقیقا این را در آن بنویس و ذخیره کن:

یادآوری سی‌ثانیه‌ای ترمینال (اگر ۱.۳ را نخواندی، همین‌جا بخوان)

ترمینال را باز کن (ویندوز: کلید Windows و تایپ PowerShell؛ مک: Cmd + Space و Terminal؛ لینوکس: Ctrl + Alt + T؛ در WSL برنامهٔ Ubuntu). بعد:

$ mkdir c-course
$ cd c-course
$ pwd
$ ls

اولی پوشه می‌سازد (اگر قبلا ساخته‌ای، می‌گوید وجود دارد؛ مهم نیست)، دومی واردش می‌شود، pwd نشان می‌دهد کجایی و ls فایل‌های همین‌جا را فهرست می‌کند (بعد از ساختن فایل باید hello.c را ببینی). اگر بعدا ترمینال تازه باز کردی، دوباره cd ~/c-course (در PowerShell: cd ~\c-course) بزن. فایل را با VS Code یا nano hello.c بساز؛ در ویندوز مراقب باش hello.c.txt نشود. اگر برنامه‌ای گیر کرد و تمام نشد: Ctrl + C.

#include <stdio.h>

// اولین برنامه من
int main(void)
{
    printf("Hello, C!\n");
    return 0;
}
  1. کتابخانهٔ ورودی/خروجی. #include <stdio.h> یعنی «محتوای فایل stdio.h را همین‌جا بگذار». در آن فایل اعلام شده که چیزی به اسم printf وجود دارد. stdio یعنی standard input/output، ورودی و خروجی استاندارد. C عمدا کوچک است و هیچ چیز را خودکار نمی‌آورد. اگر این خط نباشد، کامپایلر printf را نمی‌شناسد (پایین‌تر این خطا را می‌بینی).
  2. کامنت (توضیح). هرچه بعد از // تا آخر خط بیاید، برای آدم‌هاست و کامپایلر نادیده‌اش می‌گیرد. کد را یک بار می‌نویسی و صدبار می‌خوانی. کامنت به آدم بعدی (که شاید خودت باشی) می‌گوید «چرا».
  3. تابع main. main یعنی «اصلی». اجرای هر برنامهٔ C از اینجا شروع می‌شود. هر چیزی بین { و } جزو بدنهٔ این تابع است و از بالا به پایین یکی‌یکی اجرا می‌شود. int یعنی «در پایان یک عدد صحیح برمی‌گرداند» (این عدد برای کسی است که برنامه را اجرا کرده؛ در بخش «کد خروج» می‌بینی) و (void) یعنی «ورودی نمی‌گیرد». «تابع» یعنی یک بستهٔ دستور که اسم دارد، مثل «دستور پخت املت» در دفتر آشپزی. در درس ۲.۶ کامل می‌شناسیمش. فعلا بدان که هر برنامه دقیقا یک main دارد چون پردازنده باید بداند از کجا شروع کند. روی میکروکنترلر کسی نیست که عدد برگشتی را بخواند، ولی زبان C همین شکل int main را می‌خواهد و همه از آن پیروی می‌کنند.
  4. چاپ. printf (مخفف print formatted) متن داخل گیومه را روی صفحه می‌نویسد. \n یعنی «برو خط بعد» (مثل زدن Enter). پایان دستور با ; است. بدون \n، خروجی برنامه به خط فرمان می‌چسبد و مرتب دیده نمی‌شود. ; مثل نقطهٔ آخر جمله به کامپایلر می‌گوید «این دستور تمام شد».
  5. پایان با کد صفر. return 0; یعنی «main تمام شد و عدد ۰ را به عنوان نتیجه پس می‌دهم». صفر یعنی «همه چیز خوب بود». در بخش «کد خروج» می‌بینی کجا خوانده می‌شود. هر برنامه باید به کسی که اجرایش کرده بگوید موفق بود یا نه. قرارداد جهانی: ۰ = موفق، هر عدد دیگر = مشکل.

حالا در همان ترمینال و همان پوشهٔ c-course (با pwd و ls مطمئن شو hello.c کنارت است) دو دستور بزن. دستور اول برنامه را می‌سازد، دستور دوم اجرایش می‌کند:

$ gcc -std=c11 -Wall -Wextra -o hello hello.c
$ ./hello
Hello, C!

اگر همین را دیدی، تبریک: اولین برنامه‌ات را نوشتی و اجرا کردی. (در WSL و MSYS2 همین ./hello را بزن؛ در PowerShell ویندوز با gcc بومی، .\hello.) اگر No such file or directory دیدی، یعنی در پوشهٔ اشتباهی هستی: pwd و ls بزن و با cd به c-course برو. برای خطای دیگر نگران نباش؛ بخش «خواندن پیام خطا» همین پایین است.

اشتباه‌های همیشگی روز اول
  • بزرگ و کوچک بودن حروف مهم است: Printf و printf دو اسم جدا هستند. Main هم main نیست.
  • گیومه‌ها باید ASCII باشند: " درست است؛ گیومهٔ هوشمند وُرد “ غلط است. ویرایشگر کد این مشکل را ندارد؛ برای همین در Word یا تلگرام کد ننویس.
  • فراموش‌کردن ; رایج‌ترین خطای مبتدی‌هاست.

از فایل متنی تا برنامه: چهار ایستگاه

وقتی نوشتی gcc ... hello.c، ظاهرا یک دستور اجرا شد. اما پشت پرده gcc چهار ابزار را پشت سر هم صدا زد. مثل کارخانهٔ نان‌پزی که خمیر می‌گیرد، شکل می‌دهد، می‌پزد و بسته‌بندی می‌کند.

ایستگاه ۱: پیش‌پردازنده

پیش‌پردازنده (preprocessor) هنوز C را «نمی‌فهمد». فقط ویرایش متنی می‌کند، مثل کسی که با خودکار روی کاغذ خط می‌کشد و تکه‌ای را می‌چسباند. خط‌هایی که با # شروع می‌شوند فرمان‌های او هستند: #include یعنی «تمام متن آن فایل را همین‌جا بچسبان»، و کامنت‌ها را هم دور می‌ریزد. با -E می‌توانیم نتیجه را ببینیم:

$ gcc -E hello.c | wc -l
821
$ gcc -E hello.c | tail -6
# 4 "hello.c"
int main(void)
{
    printf("Hello, C!\n");
    return 0;
}

برنامهٔ ما ۸ خط بود، ولی بعد از پیش‌پردازش حدود ۸۰۰ خط شد. چون محتوای stdio.h چسبیده شد. (عدد دقیق روی رایانهٔ تو فرق می‌کند.) دو نکتهٔ مهم: خط کامنت // اولین برنامه من ناپدید شده، و خط # 4 "hello.c" فقط یک یادداشت برای خطایاب است که بگوید این تکه از کجا آمده.

یک مثال کوچک‌تر از کار پیش‌پردازنده با #define (تعریف یک نام جایگزین). فایل mini.c را ببین:

#define LIMIT 10

// کامنت
int main(void)
{
    return LIMIT;
}
  1. تعریف جایگزینی. #define LIMIT 10 یعنی «هرجا دیدی LIMIT بنویسی، عدد ۱۰ بگذار». این فقط جایگزینی متنی است. اسم LIMIT معنی می‌دهد، ولی پردازنده هیچ‌وقت آن را نمی‌بیند. در درس ۴.۱ قدرت و تله‌هایش را می‌بینیم.
  2. کامنت. پیش‌پردازنده حذفش می‌کند.
  3. برنامه. فقط یک عدد به‌عنوان نتیجه برمی‌گرداند. هیچ چاپی ندارد.
$ gcc -E mini.c | tail -4
int main(void)
{
    return 10;
}

ببین LIMIT رفت و ۱۰ جایش آمد و کامنت هم حذف شد. تا اینجا هنوز «ترجمه‌ای» انجام نشده.

ایستگاه ۲: کامپایلر

حالا نوبت کامپایلر اصلی است. او C خالص را می‌خواند، غلط‌های نوشتاری را پیدا می‌کند (اگر داشته باشی، همین‌جا پیام خطا می‌دهد) و متن اسمبلی (assembly) می‌سازد. اسمبلی هم یک متن است ولی با دستورهای خود پردازنده، یکی‌یکی و با اسم‌های کوتاه مثل mov (جابه‌جا کن) و ret (برگرد). با -S می‌توانی ببینی:

برای کنجکاوها: متن اسمبلی hello.c را ببین (دانستنش لازم نیست؛ می‌توانی رد شوی) 
main:
    endbr64
    pushq   %rbp
    movq    %rsp, %rbp
    leaq    .LC0(%rip), %rax
    movq    %rax, %rdi
    call    puts@PLT
    movl    $0, %eax
    popq    %rbp
    ret
  1. برچسب main. نام تابع ما. جایی که پردازنده باید بپرد.
  2. مقدمه و پایان. پردازنده جای مهم خودش را نگه می‌دارد و آخر کار دوباره برمی‌گرداند. جزئیات برای الان لازم نیست. فقط ببین که یک خط C به چند دستور ریز تبدیل می‌شود.
  3. چاپ. نشانی متن را آماده می‌کند و تابعی به اسم puts را صدا می‌زند. puts رشته‌ای را همراه رفتن به خط بعد چاپ می‌کند. جالب است: ما printf نوشتیم ولی کامپایلر دید متن ساده است و همان کار را با puts سریع‌تر انجام داد. کامپایلر فقط ترجمه نمی‌کند، بهبود هم می‌دهد.
  4. return 0. عدد ۰ را در جایی می‌گذارد که سیستم‌عامل نتیجه را از آنجا بخواند و برمی‌گردد.
این اسمبلی مال رایانهٔ من است، نه میکروکنترلر

متن بالا برای پردازندهٔ رایانه‌های معمولی (x86-64) است. نسخهٔ گرفته‌شده روی رایانهٔ تو، بسته به کامپایلر و سیستم‌عاملت، کمی فرق می‌کند. (چند خط کمکی هم که با نقطه شروع می‌شوند حذف کرده‌ام.) پایین‌تر همان کد را برای پردازندهٔ میکروکنترلر می‌بینیم.

ایستگاه ۳: اسمبلر

اسمبلر (assembler) متن اسمبلی را به کد ماشین، یعنی عدد، تبدیل می‌کند. این کار ساده و مکانیکی است؛ هر اسم دستور یک عدد مشخص دارد. خروجی، فایل .o (فایل شیء یا object file) است. این فایل دیگر متن نیست و با ویرایشگر معمولی خوانده نمی‌شود.

$ gcc -c hello.c
$ file hello.o
hello.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV), not stripped

خروجی file چند کلمهٔ فنی دارد که فقط برای تماشاست: ELF نام قالب فایل برنامه است (مثل «PDF» برای اسناد)، 64-bit و x86-64 نوع پردازندهٔ هدف را می‌گویند، و «شیء» در «فایل شیء» یعنی «تکهٔ ساخته‌شده‌ای که هنوز برنامهٔ کامل نیست» (نه جسم فیزیکی). در خروجی file کلمهٔ relocatable یعنی «تکه‌ای که هنوز جای نهایی‌اش در حافظه معلوم نیست». چرا؟ چون هنوز نمی‌داند puts کجاست. آن را ایستگاه آخر پیدا می‌کند.

ایستگاه ۴: لینکر

لینکر (linker، «پیوندزننده») تکه‌ها را به هم می‌چسباند: فایل‌های .o خودت و کد آمادهٔ printf/puts که در کتابخانهٔ استاندارد است. اسم‌ها را به آدرس‌ها وصل می‌کند و یک برنامهٔ کامل می‌سازد. بدون لینکر، فایل hello.o نمی‌داند puts کجاست.

$ gcc -o hello hello.o
$ ./hello
Hello, C!
این چهار مرحله را حتما یادت بماند

هر خطای کامپایل، از یکی از این ایستگاه‌ها می‌آید. خطاهای نوشتاری از ایستگاه ۲. خطای «تعریف پیدا نشد» (undefined reference) از ایستگاه ۴. وقتی بدانی خطا از کدام ایستگاه است، علتش را سریع‌تر پیدا می‌کنی. در بخش «خواندن پیام خطا» یک نمونهٔ واقعی می‌بینیم.

این همه فایل با پسوندهای مختلف

در پروژهٔ میکروکنترلری اسم این فایل‌ها را زیاد می‌شنوی. جدول زیر همه را کنار هم می‌گذارد:

پسوندچیست؟کی ساخته می‌شود؟آدم می‌تواند بخواند؟
.cکد منبع C (تو می‌نویسی)توبله
.hفایل هدر: فهرست اعلان‌ها (چه چیزهایی وجود دارد). مثل stdio.hتو یا کتابخانهبله
.iنتیجهٔ پیش‌پردازشgcc -Eبله (طولانی)
.sمتن اسمبلیgcc -Sسخت، ولی بله
.oکد ماشینِ یک فایل، هنوز لینک‌نشدهgcc -cخیر
.elfبرنامهٔ نهایی میکروکنترلر همراه اطلاعات دیباگ (اسم تابع‌ها، شماره خط‌ها). روی لینوکس برنامهٔ اجرایی هم همین قالب را داردلینکرخیر
.binفقط بایت‌های خام برنامه. چیزی که واقعا در Flash نوشته می‌شودobjcopy از روی .elfخیر
.hexهمان بایت‌ها به‌صورت متنی، هر خط همراه آدرس و کد کنترل خطا (قالب Intel HEX). بعضی برنامه‌های فلش‌کردن فقط این را می‌فهمندobjcopy از روی .elfمتن است ولی معنی‌دار نیست
.exeبرنامهٔ اجرایی ویندوزلینکر (روی ویندوز)خیر

برای میکروکنترلر آخرین دستورها این‌ها هستند (در درس ۵.۱ آن‌ها را با پروژهٔ واقعی می‌سازیم):

$ arm-none-eabi-objcopy -O binary app.elf app.bin
$ arm-none-eabi-objcopy -O ihex app.elf app.hex
چرا اصلا .elf و .bin هر دو را داریم؟

.elf مثل کتابی است که فهرست و توضیحات حاشیه دارد؛ دیباگر (ابزار پیداکردن خطا در حین اجرا) از این توضیحات برای نشان‌دادن اسم تابع‌ها استفاده می‌کند. .bin مثل متن خالص کتاب است بدون حاشیه: کوچک‌تر و همان چیزی که در حافظهٔ میکروکنترلر می‌نشیند.

کامپایلر برای میکروکنترلر: همان C، زبانی دیگر

در دستور پخت ما، مترجم به زبان آشپز ترجمه می‌کرد. آشپزهای مختلف زبان‌های مختلفی دارند. پردازندهٔ رایانهٔ تو (x86-64 یا Apple Silicon) با پردازندهٔ داخل STM32 (ARM Cortex-M) و ESP32 (Xtensa) زبان ماشین متفاوتی دارند. پس باید هر بار مترجم درستِ همان پردازنده را صدا بزنیم.

وقتی رایانه‌ای با پردازندهٔ A کدی می‌سازد که برای پردازندهٔ B است، به این کار کامپایل متقاطع (cross-compile) می‌گویند. کامپایلرش را «cross-compiler» می‌نامند. اسم arm-none-eabi-gcc هم بی‌دلیل نیست: arm = برای پردازندهٔ ARM، none = بدون سیستم‌عامل، eabi = قرارداد پایهٔ ARM برای توابع و داده.

یک تابع خیلی کوچک را با هر دو کامپایلر ترجمه کردم. تابع add_one عددی می‌گیرد و یکی بیشتر برمی‌گرداند (توابع را در درس ۲.۶ کامل می‌آموزیم؛ الان فقط تماشا کن):

int add_one(int x)
{
    return x + 1;
}
  1. تابع add_one. یک ورودی صحیح به اسم x می‌گیرد و یک عدد صحیح پس می‌دهد.
  2. نتیجه. ورودی را یکی بیشتر می‌کند و همان را برمی‌گرداند.

حالا ببین برای میکروکنترلر ARM دقیقا چه عددهایی ساخته می‌شود. این دستورها را روی خود رایانه‌ات اجرا می‌کنی؛ هیچ برد سخت‌افزاری لازم نیست:

$ arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -O1 -c add.c
$ arm-none-eabi-objdump -d add.o

add.o:     file format elf32-littlearm

Disassembly of section .text:

00000000 <add_one>:
   0:	3001      	adds	r0, #1

سه ستون دارد: آدرس (۰ و ۲)، کد ماشین (3001 و 4770، که به‌صورت هگز نوشته شده) و متن اسمبلی برای آدم. یعنی کل تابع فقط ۴ بایت است: دو دستور ۱۶ بیتی. این عددها دقیقا همان چیزی‌اند که در Flash میکروکنترلر می‌نشینند و پردازنده می‌خواند. (اگر با نمایش هگز آشنا نیستی، درس ۱.۲ را ببین. objdump -d کد ماشین را برمی‌گرداند به متن اسمبلی تا بتوانیم بخوانیم.)

پرچم‌های -mcpu=cortex-m4 -mthumb می‌گویند «هدف: پردازندهٔ Cortex-M4 (STM32F4)، با مجموعه‌دستور Thumb». بدون آن‌ها، arm-none-eabi-gcc نمی‌داند دقیقا برای کدام ARM بسازد.

زیر کاپوت: ESP32 چه؟

پردازندهٔ ESP32 معمولی از خانوادهٔ Xtensa است، نه ARM. ابزار ساختش xtensa-esp32-elf-gcc نام دارد که با ESP-IDF نصب می‌شود و معمولا مستقیم صدایش نمی‌زنی؛ idf.py build این کار را برایت می‌کند. مدل‌های جدیدتر ESP32 (مثل C3 و C6) پردازندهٔ RISC-V دارند و ابزارشان فرق می‌کند. نکتهٔ اصلی این است: برای هر پردازنده یک کامپایلر هدف‌دار لازم است.

روی میکروکنترلر، main هرگز تمام نمی‌شود

روی رایانه، وقتی main به return 0; برسد، برنامه تمام می‌شود و سیستم‌عامل (ویندوز یا لینوکس) دوباره کنترل را می‌گیرد. شبیه اجارهٔ ماشین: ماشین را برمی‌گردانی و شرکت تحویل می‌گیرد.

در میکروکنترلر سیستم‌عاملی نیست که بعد از تمام‌شدن برنامه به او برگردیم. کسی آنجا نیست که ماشین را تحویل بگیرد. علاوه بر این، دستگاه باید تا وقتی برق دارد کارش را بکند: ترموستات باید مدام دما را بخواند، نه یک بار. پس برنامهٔ MCU تقریبا همیشه شکل زیر را دارد. به آن حلقهٔ بی‌پایان اصلی (super loop) می‌گویند:

پس اگر main تمام شود چه می‌شود؟

در STM32 معمولا کد آغازین بعد از main در یک حلقهٔ خالی گیر می‌کند (یا ریست می‌شود؛ بسته به پروژه). در ESP-IDF تابع app_main می‌تواند برگردد و فقط همان «کار» حذف می‌شود؛ بقیهٔ سیستم زنده می‌ماند. در هر دو حالت، برنامهٔ تو دیگر کاری نمی‌کند. برای همین «کار دائمی» را خودت در حلقه می‌نویسی.

خواندن پیام خطا

خطا کردن بخشی از کار است. حتی برنامه‌نویسان بیست‌ساله هر روز خطای کامپایل می‌گیرند؛ تفاوتشان این است که پیام را می‌خوانند. بیا یک خطا را عمدا بسازیم. دقت کن این‌بار ; بعد از printf را برداشتیم:

#include <stdio.h>

int main(void)
{
    printf("Hello, C!\n")
    return 0;
}
  1. نقطه‌ویرگول گم‌شده. کامپایلر بعد از printf(...) منتظر ; بود ولی return را دید. کامپایلر نمی‌داند دستور اول کجا تمام شده بود. تنها وقتی به return می‌رسد که بفهمد اشتباه است و همان‌جا گزارش می‌دهد.
  2. جایی که کامپایلر گیر کرد. پیام اشاره می‌کند «قبل از return»، ولی مشکل واقعی در خط بالاتر است.
semi.c: In function 'main':
semi.c:5:26: error: expected ';' before 'return'

پیام را قسمت‌قسمت بخوان:

تکهمعنی

قانون اول: از اولین خطا شروع کن

یک خطا می‌تواند پشت سرش چند خطای دیگر بسازد، مثل یک دومینو که فقط اولین تکه‌اش را خودت انداخته‌ای. گیومهٔ بستهٔ رشته را فراموش کن تا ببینی:

$ gcc -std=c11 -Wall -Wextra -o q q.c

q.c:5:12: warning: missing terminating " character

یک اشتباه ("Hello, C!\n بدون گیومهٔ بسته)، چهار پیام! خطای دوم و سوم فقط پیامدند. اول خط ۵ را درست کن، دوباره کامپایل کن؛ بقیه خودبه‌خود ناپدید می‌شوند. برنامه‌نویسان با تجربه هیچ‌وقت از ته لیست شروع نمی‌کنند.

پیام note (یادداشت) خودش راه حل را می‌گوید. کلمهٔ داخل کروشه (-Wimplicit-function-declaration) اسم همان هشدار است و اگر دنبالش در وب بگردی، توضیح کامل پیدا می‌کنی. حواست باشد: نسخه‌های جدیدتر gcc (از ۱۴ به بعد) این را دیگر هشدار نمی‌دانند و خطا می‌گیرند. هرچه است، راه‌حل یکی است: #include <stdio.h> را اضافه کن.

یک خطای ایستگاه ۴

یک بار هم اسم را غلط بنویس: pritnf به‌جای printf. با gcc نسخهٔ ۱۳ و قدیمی‌تر، نتیجه جالب است: هم هشدار دارد هم خطا، و خطای آخرش از لینکر می‌آید. (با gcc ۱۴ به بعد، clang یا macOS، همان‌جا که کامپایلر pritnf را نمی‌شناسد خطا می‌دهد و کار تمام می‌شود؛ لینکر اصلا به کار نمی‌رسد. برای همین بعد از این بخش یک نمونهٔ مستقل از نسخه هم هست.)

#include <stdio.h>

int main(void)
{
    pritnf("Hello, C!\n");
    return 0;
}
  1. اسم اشتباه. pritnf در هیچ هدری وجود ندارد. کامپایلر (ایستگاه ۲) هشدار می‌دهد که اسم را نمی‌شناسد و پیشنهاد هم می‌دهد. لینکر (ایستگاه ۴) هم وقتی دنبال تعریفش می‌گردد و پیدایش نمی‌کند، خطا می‌دهد.
typo.c: In function 'main':
typo.c:5:5: warning: implicit declaration of function 'pritnf'; did you mean 'printf'? [-Wimplicit-function-declaration]
collect2: error: ld returned 1 exit status

خطای undefined reference to `pritnf' (به‌معنی «تعریفی برای این اسم پیدا نشد») از ld می‌آید، همان لینکر. ببین کامپایلر چطور جلوی چشمت پیشنهاد داد: did you mean 'printf'? همیشه پیشنهادهای کامپایلر را بخوان. جزئیات خطاهای لینک در درس ۴.۲ است.

خطای لینکر، مستقل از نسخهٔ gcc

برای اینکه خطای ایستگاه ۴ را حتما ببینی، چیزی لازم داریم که کامپایلر به آن اعتراضی نکند: تابعی را «اعلام» کنیم (بگوییم وجود دارد) ولی هرگز «تعریف» نکنیم (بدنه‌اش را ننویسیم). کامپایلر به قولت اعتماد می‌کند؛ لینکر وقتی دنبال بدنه‌اش می‌گردد، پیدایش نمی‌کند:

int f(void);

int main(void)
{
    return f();
}
  1. اعلام بدون تعریف. «تابعی به اسم f هست که چیزی نمی‌گیرد و عدد برمی‌گرداند.» بدنه‌ای ننوشتیم. اعلام فقط یک قول است. کامپایلر هر فایل را جدا می‌بیند و فرض می‌کند بدنهٔ f جای دیگری (فایل دیگر یا کتابخانه) هست.
  2. صدا زدن f. main تابع f را صدا می‌زند و نتیجه‌اش را برمی‌گرداند. کامپایل خوب پیش می‌رود؛ مشکل تا ایستگاه لینکر پنهان می‌ماند.
collect2: error: ld returned 1 exit status

بالای این خط، ld می‌نویسد undefined reference to `f' (یعنی «برای f تعریفی پیدا نشد»). ظاهر دقیق پیام‌های لینکر (مسیرها و آفست‌ها) از سیستمی به سیستم دیگر فرق می‌کند، ولی عبارت undefined reference همه‌جا هست. نتیجه: خطای undefined reference یعنی اسمی را وعده دادی ولی بدنه‌اش را هیچ‌جا نساخته‌ای یا به لینکر نشان نداده‌ای (درس ۴.۲).

پرچم‌هایی که همیشه می‌گذاریم

در دستور gcc -std=c11 -Wall -Wextra -o hello hello.c هر تکه یک معنی دارد:

گزینهمعنیچرا؟
-std=c11از نسخهٔ C11 زبان استفاده کنزبان C چند نسخه دارد. اینجا قرار دادیم که رفتار روی همهٔ رایانه‌ها یکی باشد.
-Wallبیشتر هشدارهای مهم را روشن کننام‌اش «همه» است ولی کامل نیست. با این گزینه بسیاری از باگ‌ها را همان لحظه می‌گیری.

کد خروج

در return 0; قبلا گفتیم عدد ۰ نتیجهٔ برنامه است. این عدد گم نمی‌شود؛ کسی که برنامه را اجرا کرده می‌تواند بخواندش. به آن کد خروج (exit code) می‌گویند. با یک برنامهٔ کوچک ببین:

int main(void)
{
    return 3;
}
  1. برنامه‌ای که فقط عدد ۳ برمی‌گرداند. هیچ چاپی ندارد. برای همین نیازی به stdio.h نیست. هر چیزی که استفاده می‌کنی باید اعلام شده باشد. چون printf صدا نزدیم، فایل هدر لازم نیست.
$ gcc -std=c11 -Wall -Wextra -o exit exit.c
$ ./exit
$ echo $?
3

$? در ترمینال لینوکس و macOS یعنی «کد خروج آخرین برنامه». (در WSL و مک همین است. در ویندوز: PowerShell با $LASTEXITCODE و CMD با echo %ERRORLEVEL%؛ در PowerShell فقط $? نمی‌نویسی، چون آنجا فقط «درست/غلط» نشان می‌دهد.) اسکریپت‌ها و ابزارهای ساخت (مثل make) از همین می‌فهمند مرحله موفق بوده یا نه. قرارداد: ۰ = موفق، هر عدد دیگر = خطا. این روی MCU کاربردی ندارد (کسی آنجا نیست که بخواند)، ولی وقتی روی رایانه تست می‌نویسی (درس ۶.۴)، کاربرد فراوانی دارد.

پیش‌نمایش: «سلام دنیا»ی میکروکنترلر

روی میکروکنترلر صفحه‌ای برای printf نیست. «سلام دنیا»ی آن دنیا این است: یک LED را چشمک بزن. تنها هدف این بخش این است که شکل برنامهٔ میکروکنترلر را ببینی: همان اجزایی که یاد گرفتی (#include، main، حلقهٔ بی‌پایان) + چند چیز جدید که هر کدام درسی دارد. نگران فهمیدن همه‌اش نباش؛ فقط بخوان.

STM32 (Nucleo-F411RE)، بدون هیچ کتابخانه‌ای

روی برد Nucleo-F411RE یک LED کاربر به اسم LD2 وجود دارد که به پایهٔ PA5 وصل است. برای روشن‌کردنش باید با چند «رجیستر» (سلول‌های ویژهٔ حافظه که مستقیم سخت‌افزار را کنترل می‌کنند) کار کنیم. آدرس‌ها از مستند رسمی RM0383 گرفته شده:

#include <stdint.h>

#define RCC_AHB1ENR (*(volatile uint32_t *)0x40023830u)
#define GPIOA_MODER (*(volatile uint32_t *)0x40020000u)
#define GPIOA_ODR   (*(volatile uint32_t *)0x40020014u)

int main(void)
{
    RCC_AHB1ENR |= 1u;                                   // ساعت GPIOA روشن
    GPIOA_MODER = (GPIOA_MODER & ~(3u << 10)) | (1u << 10); // PA5 خروجی

    for (;;)
    {
        GPIOA_ODR ^= (1u << 5);                        // وضعیت LED برعکس شود
        for (volatile uint32_t i = 0; i < 400000u; i++) { }   // کمی صبر
    }
}
  1. نوع‌های اندازه‌ثابت. stdint.h نوع uint32_t (عدد ۳۲ بیتی بدون علامت) را می‌دهد. در درس ۲.۲ کامل می‌شود. در سخت‌افزار باید بدانی عددت دقیقا چند بیت است.
  2. اسم دادن به آدرس‌ها. هر #define یک آدرس ثابت حافظه را به یک اسم قابل‌فهم وصل می‌کند. volatile به کامپایلر می‌گوید «این سلول با سخت‌افزار در ارتباط است؛ خواندن و نوشتنش را حذف نکن». کامپایلر باهوش است و ممکن است دو نوشتن پشت‌سرهم به یک آدرس را یکی کند. ولی روی رجیستر هر نوشتن، یک فرمان جداست. جزئیات در درس ۳.۶.
  3. تابع main. نقطهٔ شروع، مثل hello.c. (روی MCU کد آغازین، قبل از آن پایه‌ها را آماده و main را صدا می‌زند؛ درس ۵.۱.)
  4. روشن‌کردن ساعت پورت A. بخش‌های سخت‌افزاری برای صرفه‌جویی در برق بدون ساعت خاموش‌اند. بیت ۰ ثبات RCC_AHB1ENR یعنی «ساعت GPIOA روشن». اگر این را فراموش کنی، پایه‌ها هیچ واکنشی نشان نمی‌دهند و ساعت‌ها دنبال باگ می‌گردی؛ یکی از شایع‌ترین مشکل‌های مبتدی‌هاست.
  5. PA5 خروجی شود. برای هر پایه ۲ بیت در MODER داریم؛ برای PA5 بیت‌های ۱۱ و ۱۰. مقدار 01 یعنی «خروجی». اول آن دو بیت را صفر می‌کنیم، بعد ۱ را می‌گذاریم. فقط دو بیت را دست می‌زنیم و بقیهٔ پایه‌ها دست‌نخورده می‌مانند. عملگرهای & | ~ << را در درس ۳.۱ می‌آموزی.
  6. حلقهٔ بی‌پایان. همان for (;;) که دیدی. اگر حلقه نبود، بعد از یک بار روشن‌شدن برنامه تمام می‌شد.
  7. برعکس‌کردن LED. بیت ۵ خروجی را با ^= (xor) برعکس می‌کند: روشن ← خاموش ← روشن.
  8. صبر. یک حلقهٔ خالی که فقط ۴۰۰ هزار بار می‌شمارد تا LED با چشم دیده شود. زمان دقیق‌اش به کامپایلر و کلاک بستگی دارد. volatile روی خود i هم عمدی است: بدون آن کامپایلر می‌بیند حلقهٔ خالی هیچ اثری ندارد و آن را کلا حذف می‌کند، یعنی هیچ صبری نمی‌ماند و LED آن‌قدر سریع برعکس می‌شود که چشمک دیده نمی‌شود. این روش بدترین راه صبرکردن است (پردازنده کاری نمی‌کند ولی مشغول است). در درس ۵.۴ تایمر واقعی را می‌آموزیم.
در ۱.۱ با BSRR بود، اینجا با ODR؟

هر دو درستند و هر دو را بعدا کامل می‌شناسی. در ۱.۱ برای روشن و خاموش‌کردن صریح از BSRR استفاده کردیم (یک بیت برای «روشن»، یک بیت برای «خاموش»). اینجا می‌خواهیم LED را برعکس کنیم، پس رجیستر ODR (وضعیت فعلی خروجی‌ها) را می‌خوانیم، بیت ۵ را با ^= برعکس می‌کنیم و برمی‌گردانیم. دو ابزار برای دو کار؛ ۳.۱ و ۳.۶ توضیح کامل دارند.

ما این کد را فقط با کامپایلر arm-none-eabi-gcc ساخته‌ایم (بدون هیچ هشدار). برای اجرا روی برد به فایل راه‌اندازی و اسکریپت لینکر نیاز است که در درس‌های ۵.۱ و ۵.۲ می‌سازیم.

ESP32 (ESP-IDF)

در ESP32 کارهای سخت‌افزاری را کتابخانهٔ رسمی (ESP-IDF) با توابع آماده انجام می‌دهد. کد نوعی این است:

#include "freertos/FreeRTOS.h"
#include "freertos/task.h"
#include "driver/gpio.h"

#define LED_GPIO GPIO_NUM_2

void app_main(void)
{
    gpio_reset_pin(LED_GPIO);
    gpio_set_direction(LED_GPIO, GPIO_MODE_OUTPUT);
    int level = 0;

    while (1)
    {
        level = !level;
        gpio_set_level(LED_GPIO, level);
        vTaskDelay(pdMS_TO_TICKS(500));
    }
}
  1. هدرهای ESP-IDF. اعلام توابع FreeRTOS (سیستم‌عامل ساده‌ای که ESP-IDF زیر برنامهٔ تو دارد) و درایور GPIO.
  2. شماره پایهٔ LED. در بسیاری از بردهای DevKit ارزان LED روی GPIO2 است؛ ولی برد تو ممکن است فرق کند. حتما برگهٔ برد خودت را ببین.
  3. app_main. در ESP-IDF نقطهٔ شروع برنامهٔ تو app_main است، نه main. خود ESP-IDF قبلش سیستم را آماده می‌کند.
  4. آماده‌سازی پایه. پایه را به حالت اولیه برمی‌گرداند و سپس خروجی می‌کند.
  5. وضعیت فعلی. ۰ = خاموش، ۱ = روشن.
  6. حلقهٔ بی‌پایان. while (1) یعنی «تا وقتی ۱ (درست) است تکرار کن»؛ چون ۱ همیشه درست است، هرگز تمام نمی‌شود.
  7. برعکس و نوشتن. وضعیت را برعکس می‌کند (! یعنی «نقیض») و روی پایه می‌نویسد.
  8. صبر ۵۰۰ میلی‌ثانیه. vTaskDelay این «کار» را به خواب می‌برد و پردازنده به کارهای دیگر می‌رسد. این خیلی بهتر از حلقهٔ شمارشی STM32 است چون پردازنده مشغول نمی‌ماند. در درس ۵.۶ کامل می‌شود.

این قطعه در این محیط کامپایل نشده (ESP-IDF لازم دارد)، پس برچسب «نمونهٔ تقریبی» دارد. برای ساخت واقعی در درس ۵.۶ با idf.py build flash monitor کار می‌کنیم.

دو برنامه، یک الگو

هر دو: «یک‌بار آماده‌سازی، بعد حلقهٔ بی‌پایان». تفاوت اصلی در این است که در STM32 مستقیم با رجیستر حرف زدیم و در ESP32 کتابخانه واسطه شد. هر دو راه را در دوره یاد می‌گیریم.

آزمون این درس

ترتیب درست ایستگاه‌های ساخت برنامهٔ C کدام است؟

  1. لینکر ← کامپایلر ← اسمبلر ← پیش‌پردازنده
  2. پیش‌پردازنده ← کامپایلر ← اسمبلر ← لینکر
  3. کامپایلر ← پیش‌پردازنده ← اسمبلر ← لینکر
  4. پیش‌پردازنده ← اسمبلر ← کامپایلر ← لینکر
متن ← (پیش‌پردازش) ← C خالص ← (کامپایل) ← اسمبلی ← (اسمبل) ← فایل شیء ← (لینک) ← برنامه.

خط #include <stdio.h> را چه کسی، و در کدام ایستگاه، اجرا می‌کند؟

  1. لینکر، در آخر
  2. اسمبلر، به‌صورت عددی
  3. کامپایلر، هنگام ترجمه
  4. پیش‌پردازنده، در ایستگاه اول: محتوای فایل را همان‌جا می‌چسباند
خط‌های شروع‌شده با # فرمان‌های پیش‌پردازنده‌اند. او فقط متن را ویرایش می‌کند. نتیجه را با gcc -E می‌بینی.

کامپایلر می‌گوید file.c:8:5: error: expected ';' before 'return'. مشکل احتمالا کجاست؟

  1. در دستور خط قبل از return، جایی که ; فراموش شده
  2. در خود خط return، که غلط نوشته شده
  3. مشکلی نیست؛ نادیده بگیر چون فقط یک پیام است
  4. gcc درست نصب نشده
کامپایلر وقتی به return رسید فهمید دستور قبلی تمام نشده. پس علت معمولا یک خط بالاتر است. «قبل از X» یعنی نگاه کن به چیزی که قبل از X است.

در ترمینال لینوکس (یا مک یا WSL) برنامه‌ای که با return 7; تمام می‌شود را اجرا می‌کنی و بلافاصله echo $? می‌زنی. چه چاپ می‌شود؟ (در PowerShell ویندوز همان عدد را $LASTEXITCODE نشان می‌دهد.)

  1. ۰
  2. هرچه برنامه با printf چاپ کرده بود
  3. ۷
  4. پیام خطا، چون ۷ موفقیت نیست
$? کد خروج آخرین برنامه را نشان می‌دهد؛ اینجا ۷.

با arm-none-eabi-gcc یک فایل اجرایی ساخته‌ای. آیا می‌شود آن را مستقیم روی لپ‌تاپ اجرا کرد؟

  1. بله، همه‌ی برنامه‌های C همه‌جا اجرا می‌شوند
  2. خیر؛ آن کد برای پردازندهٔ ARM Cortex-M ساخته شده و باید در Flash میکروکنترلر باشد
  3. بله، اگر پسوند را به .exe تغییر بدهی
  4. خیر، چون لینکر آن را خراب کرده
کد ماشین وابسته به پردازنده است. پردازنده‌ای که آن دستورها را نمی‌شناسد، نمی‌تواند اجرایشان کند. برای همین به کامپایلر «متقاطع» نیاز داریم.

چرا برنامهٔ نوعی یک میکروکنترلر داخل یک حلقهٔ بی‌پایان (for (;;)) کار می‌کند؟

  1. تا برنامه سریع‌تر شود
  2. تا RAM کمتری مصرف شود
  3. چون کامپایلر بدون آن خطا می‌دهد
  4. چون سیستم‌عاملی نیست که بعد از پایان main به آن برگردیم، و دستگاه باید تا وقتی برق دارد کار کند
روی MCU «کار دائمی» را باید خودت بنویسی. اگر main تمام شود، دیگر هیچ دستوری اجرا نمی‌شود.

تمرین‌ها

تمرین ۱: برنامهٔ خودت را بنویس

می‌خواهیم برنامهٔ سلام را کمی شخصی کنیم.

  1. پیش‌بینی: اگر در برنامهٔ hello دو خط printf پشت هم داشته باشیم، هر کدام با \n پایان یابد، خروجی چند خط است؟
  2. حل: برنامه‌ای بنویس که دو خط چاپ کند: Hello, C! و I am learning C.
  3. آزمایش: در برنامهٔ خودت return 0; را به return 7; تغییر بده. بعد از اجرا echo $? (در PowerShell: $LASTEXITCODE) چه چیزی نشان می‌دهد؟
راهنمایی

هر printf یک دستور جدا است و ; خودش را می‌خواهد. متن هر کدام را داخل گیومه بگذار.

چه باید ببینی؟ 
$ ./two_lines
Hello, C!
I am learning C.

با return 7; بعد از اجرا، echo $? عدد ۷ را نشان می‌دهد. (پاسخ الف: دو خط.)

جواب کامل با توضیح 
#include <stdio.h>

int main(void)
{
    printf("Hello, C!\n");
    printf("I am learning C.\n");

  1. هدر. هر دو printf به آن نیاز دارند، یک include کافی است.
  2. دو چاپ. اجرا از بالا به پایین است، پس اول خط اول چاپ می‌شود. اگر \n نبود، دو متن به هم می‌چسبیدند: Hello, C!I am learning C.
  3. کد خروج. برای آزمایش قسمت پ این عدد را عوض کن.

تمرین ۲: باگ‌ها را با چشم پیدا کن

هرکدام از این سه برنامه یک مشکل دارد. قبل از کامپایل حدس بزن مشکل چیست و در کدام ایستگاه گزارش می‌شود.

// الف
int main(void)
{
    printf("Hi\n");
    return 0;
}

// ب
#include <stdio.h>
int main(void)
{
    Printf("Hi\n");
    return 0;
}

// پ
#include <stdio.h>
int main(void)
{
    printf("Hi\n";
    return 0;
}
  1. برنامهٔ الف: چه چیزی کم دارد؟
  2. برنامهٔ ب: مشکل چیست؟ در کدام ایستگاه گزارش می‌شود؟ (بسته به نسخهٔ gcc ممکن است از کامپایلر بیاید یا از لینکر؛ هر دو حالت را بگو.)
  3. برنامهٔ پ: مشکل چیست؟ پیام را حدس بزن.
راهنمایی

الف: printf را کجا معرفی کردیم؟ ب: بزرگ و کوچک بودن حروف. پ: پرانتز ( را ببین که کجا بسته می‌شود.

چه باید ببینی؟

الف: هشدار (در gcc جدید: خطا) دربارهٔ implicit declaration of function 'printf'. ب: هشدار برای Printf و بعد یک خطای undefined reference از لینکر (در gcc ۱۴ به بعد: همان‌جا خطای implicit declaration از کامپایلر). پ: خطای expected ')' before ';' token و معمولا یک خطای دوم expected ';' before '}' token که فقط پیامد اولی است.

جواب کامل با توضیح
الففراموشی #include <stdio.h>؛ اصلاح: خط اول را اضافه کن.
بPrintf با P بزرگ وجود ندارد. با gcc قدیمی‌تر کامپایلر هشدار می‌دهد و لینکر (ایستگاه ۴) تعریفش را پیدا نمی‌کند؛ با gcc ۱۴ به بعد کامپایلر (ایستگاه ۲) همان‌جا خطا می‌دهد. اصلاح: printf.
پپرانتز بسته نشده؛ پیام اول expected ')' before ';' token است و پیام دوم (expected ';' before '}' token) فقط پیامد آن. یادت هست؟ از اولین خطا شروع کن. اصلاح: printf("Hi\n");
#include <stdio.h>

int main(void)
{
    Printf("Hi\n");
    return 0;
}
  1. حرف اول بزرگ. در C «Printf» و «printf» دو اسم کاملا جدا هستند. C به بزرگی و کوچکی حروف حساس است. کامپایلر پیشنهاد did you mean 'printf'? هم می‌دهد.
printf_case.c: In function 'main':
printf_case.c:5:5: warning: implicit declaration of function 'Printf'; did you mean 'printf'? [-Wimplicit-function-declaration]
collect2: error: ld returned 1 exit status
تمرین ۳: چشمک با سرعت دیگر

به برنامه‌های چشمک بخش آخر نگاه کن.

  1. پیش‌بینی: در برنامهٔ STM32 عدد 400000u را به 800000u تغییر بدهیم، LED سریع‌تر چشمک می‌زند یا کندتر؟
  2. سخت‌افزار: در همان برنامه، کدام خط PA5 را خروجی می‌کند؟ اگر آن را حذف کنیم و ساعت GPIOA را هم روشن نکنیم چه می‌شود؟
  3. حل: نسخهٔ جدید با 800000u را با arm-none-eabi-gcc بساز و بدون هشدار ببین. برای ESP32 هم بنویس عدد ۵۰۰ را به چه چیزی تغییر می‌دهی تا سرعت دو برابر شود.
راهنمایی

حلقهٔ صبر هرچه بیشتر بشمارد، بیشتر طول می‌کشد. دو برابر سرعت یعنی نصف زمان صبر.

چه باید ببینی؟

ساخت بدون هیچ پیام و هشدار، و فایل .o ساخته می‌شود. (پاسخ‌ها: الف کندتر. ب خط GPIOA_MODER = ...؛ اگر حذف شود پایه خروجی نمی‌شود و LED تغییر نمی‌کند. پ ESP32: ۲۵۰.)

جواب کامل با توضیح 
#include <stdint.h>

#define RCC_AHB1ENR (*(volatile uint32_t *)0x40023830u)
#define GPIOA_MODER (*(volatile uint32_t *)0x40020000u)
#define GPIOA_ODR   (*(volatile uint32_t *)0x40020014u)

int main(void)
{
    RCC_AHB1ENR |= 1u;
    GPIOA_MODER = (GPIOA_MODER & ~(3u << 10)) | (1u << 10);

    for (;;)
    {
        GPIOA_ODR ^= (1u << 5);
        for (volatile uint32_t i = 0; i < 800000u; i++) { }
    }
}
  1. ساعت GPIOA. بدون این خط، نوشتن روی رجیسترهای GPIOA اثر ندارد.
  2. PA5 خروجی. اگر حذف شود، پایه در حالت پیش‌فرض (ورودی) می‌ماند و خروجی روی LED نمی‌رود.
  3. چشمک. عدد ۸۰۰۰۰۰ صبر را دو برابر می‌کند، پس LED کندتر می‌شود. این حلقه فقط تعداد شمارش‌ها را عوض می‌کند. ساعت واقعی را در درس ۵.۴ می‌سازیم.
حرف مربی

جدی می‌گویم: اولین هفته‌ای که C می‌نویسی، بیشتر وقت‌ت صرف خطاهای ;، گیومه و حروف بزرگ و کوچک می‌شود. عادی است، حتی برنامه‌نویس ده‌ساله هم می‌کند. سه عادت که کمک می‌کند: (۱) همیشه از اولین خطا شروع کن، (۲) خط قبل از شمارهٔ خط پیام را هم نگاه کن، (۳) بعد از هر چند خط کامپایل کن، نه بعد از صد خط. و اگر در بخش پیش‌نمایش میکروکنترلر چیزی را نفهمیدی، اصلا مهم نیست؛ هر تکه‌اش درس جدا دارد و دوباره به آن برمی‌گردیم.

خلاصه یک‌دقیقه‌ای

  • برنامهٔ C یک فایل متنی است؛ ابزارها آن را به کد ماشین تبدیل می‌کنند. ساده‌ترین برنامه: #include + main + دستور + return 0;.
  • چهار ایستگاه: پیش‌پردازنده (متن) ← کامپایلر (اسمبلی) ← اسمبلر (فایل .o) ← لینکر (برنامهٔ کامل). با gcc -E / -S / -c فایل‌های میانی را می‌بینی.
  • پسوندها: .c منبع، .h هدر، .o ناتمام، .elf نهایی با اطلاعات دیباگ، .bin/.hex چیزی که در Flash نوشته می‌شود.
  • برای MCU کامپایلر «متقاطع» لازم است (arm-none-eabi-gcc، xtensa-esp32-elf-gcc)؛ همان C، زبان ماشین دیگر.
  • روی MCU سیستم‌عامل نیست و main تمام نمی‌شود: یک‌بار آماده‌سازی + حلقهٔ بی‌پایان.
  • خطا را بخوان: فایل:خط:ستون، اول از اولین خطا، مشکل معمولا خط بالاتر است. error = ساخته نمی‌شود، warning = مشکوک ولی جدی بگیر. همیشه با -std=c11 -Wall -Wextra.
  • کد خروج: return برنامه؛ ۰ یعنی موفق.
