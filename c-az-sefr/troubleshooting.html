عیب‌یابی: رمزگشای خطاها

وقتی کامپایلر می‌نویسد error، آدم‌ها اولین‌بار فکر می‌کنند «کامپیوتر با من قهر کرده». در واقع پیام خطا یک گزارش دقیق است، به زبان خشک ولی قابل‌فهم. این صفحه رمزگشایش است: هر پیام با متن واقعی که خودمان با gcc 13.3 و arm-none-eabi-gcc 13.2 ساختیم، علت و راه‌حل. برای علائم بی‌پیام (مثل «LED چشمک نمی‌زند») هم بخش جدا هست.

چطور از این صفحه استفاده کنم؟

پیامت را کپی کن و با Ctrl+F یک تکهٔ ثابتش (مثل undefined reference) را اینجا بگرد؛ یا از جدول «فهرست سریع» زیر برو. دو نکته: (۱) نمونه‌های این صفحه با LC_ALL=C گرفته شده‌اند و گیومه‌ها ساده ('x') هستند؛ ولی gcc در ترمینال با زبان UTF-8 (پیش‌فرض اوبونتو، مک و WSL) گیومه‌های خمیده می‌نویسد، مثلاً expected ‘;’ before ‘return’. پس برای Ctrl+F فقط بخش بدون گیومه را بگرد، یا برای دیدن همان متن صفحه LC_ALL=C gcc ... اجرا کن. (۲) فقط بخشی از خروجی‌ها خودکار با کامپایلر وارسی می‌شوند: خطاهای کامپایل که واقعاً خطا هستند و کدهای زمان اجرا؛ هشدارها و خروجی لینکر دومرحله‌ای و ARM را یک‌بار با gcc 13.3 و arm-none-eabi-gcc 13.2 دستی گرفته و تطبیق داده‌ایم و ممکن است با نسخهٔ تو کمی فرق کنند. اگر متن دقیقا یکی نبود ولی شبیه بود، خوب است: اسم متغیر، شماره خط و نام فایل هر بار فرق می‌کنند، ولی ساختار پیام همان است.

چطور یک پیام خطا را بخوانیم

قبل از دیدن نمونه‌ها، دو مهارت: بدانیم پیام از کدام ایستگاه ساخت آمده، و اجزای پیام را بشناسیم. ایستگاه‌ها را در درس ۱.۴ دیده‌ای.

دو قانون که نصف مشکل‌ها را حل می‌کند

۱. فقط اولین خطا (از بالا) را حل کن و دوباره کامپایل کن؛ بقیه اغلب زنجیرهٔ همان‌اند. ۲. جای واقعی اشتباه اغلب همان خط یا یکی دو خط بالاتر است، نه لزوما خطی که گزارش شده. و هشدار (warning) را هم مثل خطا حل کن؛ با -Wall -Wextra هر کدامشان یک باگ احتمالی است.

۱. خطاهای کامپایلر (gcc)

قبل از ساخت فایل شیء رخ می‌دهند. هر پیام فایل:خط:ستون: error/warning دارد.

expected ';' before ...

#include <stdio.h>

int main(void)
{
    int x = 5;
    x++
    return 0;
}

$ gcc -std=c11 -Wall -Wextra -c e17.c
e17.c: In function 'main':
e17.c:6:8: error: expected ';' before 'return'
    6 |     x++
      |        ^
      |        ;
    7 |     return 0;
      |     ~~~~~~

چرا؟ کامپایلر می‌بیند دستور x++ تمام نشده و کلمهٔ بعدی (return) شروع شده است. برای همین خطا را در خط بعدی (خط ۶) و روی کلمهٔ بعدی نشان می‌دهد، ولی جای غلط، آخر خط ۵ است. کامپایلر حتی جای ; را با یک علامت کوچک زیر خط نشان داده است.

چه کنم؟ وقتی خطای «expected ';'» را دیدی، به خط بالاتر از خط گزارش‌شده نگاه کن و ; را آخرش بگذار. همین‌طور اگر ) یا } بسته‌نشده باشد، پیام مشابهی می‌آید.

expected ',' or ';' before ...

#include <stdio.h>

int main(void)
{
    int count = 3
    printf("%d\n", count);
    return 0;
}

$ gcc -std=c11 -Wall -Wextra -c e1.c
e1.c: In function 'main':
e1.c:6:5: error: expected ',' or ';' before 'printf'
    6 |     printf("%d\n", count);
      |     ^~~~~~
e1.c:5:9: warning: unused variable 'count' [-Wunused-variable]
    5 |     int count = 3
      |         ^~~~~

چرا؟ این بار سمت چپِ ; یک تعریف متغیر با مقدار اولیه است (int count = 3). کامپایلر بعد از 3 انتظار , (برای متغیر بعدی) یا ; داشت. دقت کن هشدار دوم (unused variable) نتیجهٔ همین خطاست: چون دستور نیمه‌کاره ماند، کامپایلر نفهمید count جایی استفاده شده.

چه کنم؟ ; را اضافه کن. قانون طلایی: فقط اولین خطا را درست کن و دوباره کامپایل کن. خطاهای بعدی اغلب اثر همان یکی هستند.

چرا؟ اسمی نوشته‌ای که کامپایلر تا آن خط ندیده است. اینجا totl غلط املایی total است. gcc حتی حدس می‌زند («did you mean»). جمله «each undeclared identifier is reported only once» فقط یعنی برای هر اسم ناشناخته، خطا را یک بار می‌نویسد.

چه کنم؟ متغیر را قبل از حلقه تعریف کن، اگر بعد از حلقه هم لازمش داری: int i; for (i = 0; ...).

implicit declaration of function

int main(void)
{
    int x = 1;
    int y = square(x);
    return y;
}

$ gcc -std=c11 -Wall -Wextra -c e3.c
e3.c: In function 'main':
e3.c:4:13: warning: implicit declaration of function 'square' [-Wimplicit-function-declaration]
    4 |     int y = square(x);
      |             ^~~~~~

چرا؟ تابعی صدا زده‌ای که کامپایلر پیش از آن خط ندیده است: نه تعریفش را، نه پروتوتایپش را. در C قدیمی کامپایلر «حدس می‌زد» تابع int برمی‌گرداند. در gcc 13 این فقط هشدار است. استاندارد C99 این قابلیت را حذف کرد و gcc 14 آن را به‌طور پیش‌فرض خطا کرده و هیچ کد جدیدی نباید به آن تکیه کند. اگر آن تابع اصلا وجود نداشته باشد، بعدش خطای لینک هم می‌گیری (مثال «Blink» در بخش لینکر).

چه کنم؟ یا #include درست را بگذار (مثلا <stdio.h> برای printf)، یا پروتوتایپ تابع را بالای فایل بنویس (درس ۲.۶).

توجه

نسخهٔ کامپایلر همین صفحه: gcc 13.3 (Ubuntu 24.04). با نسخهٔ جدیدتر ممکن است warning به error تبدیل شود؛ متن بقیهٔ پیام یکسان است.

passing argument … from incompatible pointer type

#include <stdint.h>

static void store(uint8_t *dst) { *dst = 1; }

int main(void)
{
    uint32_t value = 0;
    store(&value);
    return (int)value;
}

$ gcc -std=c11 -Wall -Wextra -c e4.c
e4.c: In function 'main':
e4.c:8:11: warning: passing argument 1 of 'store' from incompatible pointer type [-Wincompatible-pointer-types]
    8 |     store(&value);
      |           ^~~~~~
      |           |
      |           uint32_t * {aka unsigned int *}
e4.c:3:28: note: expected 'uint8_t *' {aka 'unsigned char *'} but argument is of type 'uint32_t *' {aka 'unsigned int *'}
    3 | static void store(uint8_t *dst) { *dst = 1; }
      |                   ~~~~~~~~~^~~

چرا؟ تابع store اشاره‌گر به uint8_t می‌خواهد ولی اشاره‌گر به uint32_t فرستاده‌ای. اشاره‌گرها فقط وقتی سازگارند که «به چه نوعی اشاره می‌کنند» یکی باشد. اینجا خطر واقعی است: تابع فقط یک بایت از چهار بایت متغیر را می‌نویسد. پیام note زیر هشدار هر دو نوع را کنار هم می‌گذارد؛ {aka ...} یعنی «نام واقعی‌تر همین نوع».

چه کنم؟ نوع پارامتر را با نوع متغیر یکی کن، یا اگر واقعا بایت‌بایت کار داری، عمدی و با (uint8_t *) تبدیل کن و دلیلش را بنویس. این هشدار را هرگز نادیده نگیر: از gcc 14 به بعد به‌صورت پیش‌فرض خطاست.

توجه: gcc 14

در gcc 13 هشدار است؛ gcc 14 آن را به خطا تبدیل کرده است. چهار هشدار معروفی که در gcc 14 به‌طور پیش‌فرض خطا شده‌اند: -Wimplicit-function-declaration، -Wincompatible-pointer-types، -Wint-conversion و -Wimplicit-int. همین «makes integer from pointer without a cast» (پایین‌تر) هم در gcc 14 خطاست.

assignment of read-only variable

int main(void)
{
    const int limit = 10;
    limit = 20;
    return limit;
}

$ gcc -std=c11 -Wall -Wextra -c e5.c
e5.c: In function 'main':
e5.c:4:11: error: assignment of read-only variable 'limit'
    4 |     limit = 20;
      |           ^

چرا؟ متغیری که با const ساخته شده مقدارش بعد از تعریف عوض نمی‌شود، و کامپایلر جلوی نوشتن روی آن را می‌گیرد (درس ۲.۱). این خطا همان چیزی است که const قرار است به تو بدهد.

چه کنم؟ اگر مقدار باید عوض شود، const را بردار. اگر نباید عوض شود، برنامه‌ات جایی اشتباه فکر کرده است. هرگز با تبدیل نوع (cast) دور زدنش نکن.

format '%d' expects argument of type 'int', but argument 2 has type ...

#include <stdio.h>

int main(void)
{
    long big = 5000000000L;
    printf("%d\n", big);
    return 0;
}

$ gcc -std=c11 -Wall -Wextra -c e6.c
e6.c: In function 'main':
e6.c:6:14: warning: format '%d' expects argument of type 'int', but argument 2 has type 'long int' [-Wformat=]
    6 |     printf("%d\n", big);
      |             ~^     ~~~
      |              |     |
      |              int   long int
      |             %ld

چرا؟ مشخصهٔ فرمت printf با نوع واقعی آرگومان نمی‌خواند. %d برای int است و big از نوع long. gcc پیشنهاد هم می‌دهد (%ld). اگر هشدار را نبینی، چاپ عدد اشتباه یا حتی خرابی برنامه می‌شود. جدولش را در برگهٔ خلاصه ببین.

چه کنم؟ مشخصه را با نوع بخوان: %ld برای long، %u برای unsigned، %zu برای size_t. برای انواع stdint.h از ماکروهای PRIu32 و مشابهش در inttypes.h استفاده می‌شود.

control reaches end of non-void function

int sign(int v)
{
    if (v > 0) {
        return 1;
    } else if (v < 0) {
        return -1;
    }
}

int main(void) { return sign(3); }

$ gcc -std=c11 -Wall -Wextra -c e7.c
e7.c: In function 'sign':
e7.c:8:1: warning: control reaches end of non-void function [-Wreturn-type]
    8 | }
      | ^

چرا؟ تابعی که باید int برگرداند، یک مسیر دارد که به return نمی‌رسد (اینجا وقتی v == 0). در C استفادهٔ نتیجه از چنین مسیری رفتار تعریف‌نشده است (درس ۶.۲).

چه کنم؟ همهٔ مسیرها را با return ببند، مثلا یک return 0; در آخر. این هشدار را جدی بگیر؛ در -O2 کامپایلر گاهی کد بعد از آن را خراب می‌کند.

چرا؟ تعداد آرگومان‌ها با تعریف تابع نمی‌خواند. پیام note: declared here نشانت می‌دهد تابع کجا و با چه پارامترهایی تعریف شده. برعکسش هم too many arguments است.

چه کنم؟ آرگومان‌ها را با امضای تابع تطبیق بده (تعداد، ترتیب و نوع).

چرا؟ کامپایلر فایلی به اسم sensor.h پیدا نمی‌کند. fatal یعنی کامپایل همان‌جا متوقف شد (پس خطای دیگری نمی‌بینی). #include "..." اول کنار فایل جاری می‌گردد و بعد در مسیرهای -I و سپس مسیرهای سیستم؛ <...> مستقیم سراغ مسیرهای -I و بعد مسیرهای سیستم می‌رود (فقط «پوشهٔ فایل جاری» مخصوص شکل "..." است).

چرا؟ اشاره‌گر (char *) را داخل عدد (int) ریخته‌ای. روی MCU 32 بیتی حتی اندازه‌ها برابرند و «ظاهرا» کار می‌کند، ولی روی سیستم 64 بیتی بخشی از آدرس از بین می‌رود.

چه کنم؟ معمولا یعنی نوع متغیر یا * جا افتاده است: char *n = msg; یا با *msg اولین حرف را بخوان. اگر واقعا آدرس را می‌خواهی، از uintptr_t استفاده کن.

    .text : { *(.text*) *(.rodata*) . = ALIGN(4); _etext = .; } > FLASH
    .data : { _sdata = .; *(.data*) . = ALIGN(4); _edata = .; } > RAM AT > FLASH
    _sidata = LOADADDR(.data);
    .bss : { _sbss = .; *(.bss*) *(COMMON) . = ALIGN(4); _ebss = .; } > RAM
    _estack = ORIGIN(RAM) + LENGTH(RAM);
}

HardFault روی Cortex-M: فهرست علت‌ها

HardFault یعنی پردازنده کاری دید که ممنوع است و راه‌حلی برایش ندارد. مثل آژیر ساختمان: می‌گوید «مشکلی هست»، نه «مشکل کجاست». خوب‌ترین کارت نوشتن یک HardFault_Handler است که ثبات‌های ذخیره‌شده را نشان بدهد. اطلاعات همه در ثبات‌های وضعیت خطا هستند:

ثباتآدرسچه می‌گوید
CFSR0xE000ED28سه بخش: MMFSR (بیت ۰ تا ۷)، BFSR (۸ تا ۱۵)، UFSR (۱۶ تا ۳۱). نوع دقیق خطا اینجاست.
HFSR0xE000ED2Cبیت ۳۰ (FORCED): یک خطای دیگر به HardFault ارتقا یافته است. بیت ۱ (VECTTBL): خواندن جدول وقفه شکست خورد.
MMFAR0xE000ED34آدرس دسترسی وقتی MMARVALID (بیت ۷ CFSR) برقرار است.
BFAR0xE000ED38آدرس دسترسی خطادار وقتی BFARVALID (بیت ۱۵ CFSR) برقرار است.

و این‌ها بیت‌های پرتکرار CFSR هستند (شمارهٔ بیت در خود ثبات 32 بیتی). یادآوری: بیت‌های UsageFault/BusFault/MemManage فقط وقتی «خودشان» دیده می‌شوند که همین CFSR را بخوانی؛ اگر handler جدا فعال نباشد، خطا به HardFault می‌رسد و در HFSR بیت FORCED روشن می‌شود، ولی علت واقعی همچنان در CFSR می‌ماند. پس UsageFault «همان HardFault» نیست، علتِ آن است:

بیتناممعنی ساده
۱DACCVIOLدسترسی به داده در ناحیهٔ ممنوع (فقط با MPU)
۸IBUSERRخطای گذرگاه هنگام واکشی دستور (پرش به آدرس بی‌معنی)
۹PRECISERRخطای گذرگاه دقیق؛ BFAR آدرس را دارد و PC ذخیره‌شده همان دستور خطاست
۱۰IMPRECISERRخطای گذرگاه نادقیق؛ نوشتن بافر شده و خطا بعد از چند دستور اعلام شد (PC دقیق نیست)
۱۱ و ۱۲UNSTKERR، STKERRخطا هنگام برداشتن یا ذخیرهٔ ثبات‌ها روی پشته: پشته خراب یا خیلی پر است
۰IACCVIOLواکشی دستور از ناحیهٔ ممنوع (MemManage؛ فقط با MPU)
۳ و ۴MUNSTKERR، MSTKERRمثل UNSTKERR/STKERR ولی از نوع MemManage (فقط با MPU)
۱۶UNDEFINSTRدستور تعریف‌نشده؛ معمولا پرش به داده یا حافظهٔ خراب
۱۷INVSTATEتلاش برای رفتن به حالت ARM؛ مثلا اشاره‌گر تابعی که بیت صفرش ۰ است
۱۸INVPCمقدار نامعتبر EXC_RETURN هنگام بازگشت از وقفه
۱۹NOCPاستفاده از واحد اعشاری (FPU) که روشن نشده
۲۴UNALIGNEDدسترسی ناهم‌تراز از نوعی که مجاز نیست (مثل LDM/LDRD، یا هر دسترسی ناهم‌تراز وقتی UNALIGN_TRP روشن باشد)
۲۵DIVBYZEROتقسیم بر صفر (فقط اگر تلهٔ آن روشن شده باشد)

حالا فهرست علت‌های واقعی، به ترتیب شیوع در پروژه‌های مبتدی:

  1. اشاره‌گر خراب یا نامقداردهی‌شده. اشاره‌گر به آدرسی که هیچ حافظه‌ای پشتش نیست (منطقهٔ رزرو) PRECISERR می‌دهد. نکته: روی STM32 وقتی از Flash بوت می‌کنی (پین‌های BOOT در حالت پیش‌فرض برد Nucleo) آدرس 0 حافظهٔ معتبر (آینهٔ Flash) است و خواندن NULL خطا نمی‌دهد! (با بوت از SRAM یا System memory آدرس ۰ چیز دیگری را نشان می‌دهد؛ جزئیات در درس ۶.۲.) پس باگ می‌ماند و بی‌صدا مقدار غلط برمی‌گردد. برای همین پیش از استفاده باید اشاره‌گر را خودت بسنجی.
  2. پرش به اشاره‌گر تابع نامعتبر. اشاره‌گر تابع NULL یا مقداردهی‌نشده: INVSTATE (چون بیت صفر ۰ است) یا IBUSERR. فراموش‌شدن ثبت callback (درس ۴.۳) کلاسیک است.
  3. سرریز پشته (stack overflow). آرایهٔ محلی بزرگ یا بازگشت عمیق پشته را به داده‌های دیگر می‌رساند. آدرس‌های بازگشت خراب می‌شوند و تابع به جای بی‌معنی برمی‌گردد. علامت: HardFault در جاهای «غیرممکن» و متغیرهای سراسری که خودبه‌خود عوض می‌شوند.
  4. استفاده از FPU بدون روشن‌کردن آن. اگر با -mfloat-abi=hard ساخته‌ای، ثبات CPACR (آدرس 0xE000ED88) باید بیت‌های ۲۰ تا ۲۳ را ۱ کند. کد راه‌انداز (SystemInit در CMSIS) این کار را می‌کند؛ در پروژهٔ دست‌نویس فراموش می‌شود و اولین عملیات float NOCP می‌دهد.
  5. خطای وقفه‌ها. ISR با نام غلط (به Default_Handler می‌رود، که معمولا حلقهٔ بی‌نهایت است، نه HardFault)، یا بازگشت اشتباه از ISR. اگر جدول وقفه درست چیده نشده باشد، HFSR.VECTTBL را می‌بینی (درس ۵.۱ و ۵.۳).
  6. دسترسی ناهم‌تراز. تبدیل اشاره‌گر بایت به uint32_t * روی آدرس فرد. روی Cortex-M4 LDR/STR ساده معمولا مجاز است ولی دستورهایی مثل LDM/LDRD ناهم‌تراز خطا می‌دهند، و کامپایلر هم ممکن است آن‌ها را بسازد. راه امن: memcpy (درس ۳.۴).
  7. تقسیم بر صفر با تله روشن: DIVBYZERO. بدون تله، نتیجه صفر می‌شود و اصلا خطایی نمی‌بینی.
  8. پیکربندی غلط یا فراموش‌شدهٔ پریفرال. دسترسی به رجیستر پریفرالی که کلاکش روشن نشده روی خانواده‌های مختلف رفتار متفاوت دارد؛ بسیار وقت‌ها فقط «کار نمی‌کند» و گاهی خطای گذرگاه می‌دهد. Reference Manual تراشه‌ات را ببین.
  9. حافظهٔ پویای خراب: free دوباره، نوشتن بعد از free، سرریز بافر malloc. علامت‌ها در زمان‌های تصادفی و دور از علت (درس ۴.۴).

یک HardFault_Handler که PC را نشان می‌دهد

وقتی خطا رخ می‌دهد، پردازنده ۸ ثبات را روی پشته می‌ریزد: R0 R1 R2 R3 R12 LR PC xPSR. پس اگر frame اشاره‌گر به ابتدای آن‌ها باشد، frame[6] همان PC در لحظهٔ خطاست. آدرس PC را با arm-none-eabi-addr2line -e firmware.elf 0x08001234 به خط کد تبدیل می‌کنی. کد زیر با arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -Wall -Wextra -ffreestanding -c کامپایل شد.

#include <stdint.h>

void hardfault_c(uint32_t *frame)
{
    volatile uint32_t stacked_pc = frame[6];
    volatile uint32_t cfsr = *(volatile uint32_t *)0xE000ED28u;
    (void)stacked_pc;
    (void)cfsr;
    for (;;) { }
}

__attribute__((naked)) void HardFault_Handler(void)
{
    __asm volatile(
        "tst lr, #4      \n"
        "ite eq          \n"
        "mrseq r0, msp   \n"
        "mrsne r0, psp   \n"
        "b hardfault_c   \n"
    );
}
  1. تابع C که فریم را می‌خواند. ورودی: اشاره‌گر به ثبات‌های ذخیره‌شده. frame[6] همان PC است و CFSR را از آدرس ثبات می‌خوانیم. دلیل: volatile تا کامپایلر متغیرها را در -O2 حذف نکند و در دیباگر ببینی؛ حلقهٔ بی‌نهایت هم برنامه را همان‌جا نگه می‌دارد تا دیباگر وصل شود.
  2. ورودی naked به زبان اسمبلی. ما نمی‌دانیم پشتهٔ فعال MSP بود یا PSP (اگر RTOS داری، PSP). بیت ۲ ثبات LR در ورود به استثنا این را می‌گوید: ۰ یعنی MSP و ۱ یعنی PSP. سپس اشاره‌گر درست را در R0 می‌گذاریم (اولین آرگومان تابع) و به تابع C می‌پریم. دلیل naked: پیش‌درآمد تابع معمولی پشته را دست می‌زند و SP را جابه‌جا می‌کند، پیش از آنکه بخوانیمش.
راه سریع‌تر با دیباگر

اگر به GDB وصل هستی، بعد از ایستادن در HardFault_Handler این‌ها را بزن: x/8wx $sp (هشت ثبات ذخیره‌شده) و x/wx 0xE000ED28 (CFSR). شرط: قاب روی MSP باشد (بیت ۲ از EXC_RETURN صفر) و دقیقاً در ورودی HardFault_Handler بایستی، پیش از آنکه پیش‌درآمد تابع چیزی در پشته بریزد؛ اگر قاب روی PSP است (مثلاً با RTOS) بزن x/8wx $psp، و اگر داخل hardfault_c ایستاده‌ای از آرگومان frame استفاده کن. روش کامل در درس ۶.۱ است.

علائم بی‌پیام روی میکروکنترلر

گاهی هیچ پیامی نیست: برنامه ساخته می‌شود ولی برد «کار نمی‌کند». در این جدول از علامت شروع کن. هر ردیف به ترتیب شیوع نوشته شده.

علامتمحتمل‌ترین علت‌هاچه وارسی کنم
LED (یا خروجی) هیچ‌وقت روشن نمی‌شودکلاک پورت روشن نشده؛ پایه خروجی نشده؛ پایهٔ اشتباه (LED روی برد شما PA5 نیست)؛ LED فعال-پایین استترتیب: کلاک ← MODER ← ODR/BSRR (درس ۵.۲). دیاگرام برد. با مولتی‌متر ولتاژ پایه را بسنج.
با -O0 کار می‌کند، با -O2 نهناتمام‌بودن volatile؛ رفتار تعریف‌نشده؛ حلقهٔ انتظار که کامپایلر حذفش کردمتغیرهای مشترک با ISR و رجیسترها volatile باشند (درس ۳.۶). با -fsanitize=undefined روی PC تست کن.
پرچم ISR عوض می‌شود ولی حلقهٔ اصلی نمی‌فهمدمتغیر volatile نیست؛ ISR با نام غلط؛ وقفه در NVIC فعال نشدهنام ISR را با فایل startup مقایسه کن (درس ۵.۳).
برنامه ریست می‌شود و از نو شروع می‌کندWatchDog؛ سرریز پشته؛ افت ولتاژ (brownout)؛ HardFault که ریست می‌کندعلت آخرین ریست را از ثبات وضعیت ریست بخوان؛ پشته را بزرگ‌تر کن؛ منبع تغذیه را بسنج.

صادقانه دربارهٔ این بخش

ما این پیام‌ها را روی سخت‌افزار واقعی بازتولید نکردیم (ابزار ESP-IDF در محیط نوشتن این صفحه نبود). متن‌ها بر پایهٔ قالب مستندات ESP-IDF نسخهٔ ۵ نوشته شده‌اند؛ عبارت دقیق و شماره‌ها بین نسخه‌ها فرق می‌کند. اگر متن برد تو کمی فرق داشت، ساختار را تطبیق بده و صفحهٔ «Fatal Errors» در راهنمای ESP-IDF را ببین.

روش کلی: وقتی هیچ‌کدام از این‌ها نبود

  1. بازتولید کن. بدون تکرار قابل‌اعتماد، رفع‌کردن حدس است. مسئله را کوچک کن تا تنها چند خط بماند.
  2. ببین آخرین چه چیزی عوض شد. با git بین دو نسخه (کارا و ناکارا) فرق بگیر (git diff، git bisect).
  3. دو نیمه کن. نیمی از برنامه را غیرفعال کن؛ مشکل هست یا نه؟ همین‌طور ادامه بده.
  4. قبل از سخت‌افزار، PC. منطق را (بدون رجیستر) با sanitizer و تست واحد (درس ۶.۴) وارسی کن.
  5. ببین، حدس نزن. یک چاپ، یک پایهٔ توگل‌شونده با اسیلوسکوپ یا تحلیلگر منطقی، یا یک breakpoint. ابزارها را در جعبه‌ابزار ببین.
  6. مشکل را با یک آدم (یا اردک لاستیکی) توضیح بده. بلندبلند توضیح‌دادن اغلب خودش جواب را می‌دهد.
حرف مربی

آدم‌ها به‌جای خواندن پیام، فقط عصبانی می‌شوند و کد را دست‌کاری می‌کنند تا «چیزی عوض شود». این تنها راهی است که کارت را طولانی می‌کند. عادت کن پیام را از اول تا آخر بخوانی، اولین خطا را ببینی، و فقط یک چیز را در هر بار عوض کنی. در بیشتر موارد جواب توی پیام است.

خلاصهٔ یک‌دقیقه‌ای

  • اول ایستگاه پیام را بشناس: پیش‌پردازنده، کامپایلر، لینکر یا اجرا.
  • فقط اولین خطا را رفع کن؛ جایش اغلب خط بالاتر است.
  • هشدارها را رفع کن؛ implicit declaration، incompatible pointer و control reaches end باگ‌های واقعی‌اند.
  • خطای لینکر: تعریف نیست (undefined) یا دوتاست (multiple)؛ شمارهٔ خط ندارد.
  • region overflowed یعنی RAM/Flash پر است؛ اندازهٔ حافظه‌ها را بسنج.
  • HardFault: CFSR و PC ذخیره‌شده را بخوان و با addr2line به خط کد ببر.
