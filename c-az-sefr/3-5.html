تا حالا گفتیم «متغیر یک قفسه در حافظه است». ولی حافظهٔ میکروکنترلر یک اتاق بزرگ و یکدست نیست؛ چند منطقه با قانون‌های متفاوت دارد. بعضی متغیرها با خاموشی می‌مانند، بعضی با هر تابع ساخته و خراب می‌شوند، و بعضی هرگز در RAM نمی‌نشینند. در این درس نقشهٔ کامل را می‌کشیم تا هر بار متغیری می‌نویسی، بدانی کجا زندگی می‌کند، چه زمانی متولد می‌شود و کی می‌میرد.

🎯 بعد از این درس می‌توانی

  • نقشهٔ Flash و RAM در STM32F411 را بکشی و بگویی هر بخش چه چیزی نگه می‌دارد
  • برای هر متغیر بگویی در .text، .rodata، .data، .bss یا پشته است
  • فرق «دیده‌شدن» (scope) و «زنده‌بودن» (lifetime) را توضیح بدهی
  • با static محلی، متغیری بسازی که بین صدا زدن‌ها زنده بماند
  • با arm-none-eabi-size و nm مصرف حافظهٔ برنامه‌ات را اندازه بگیری
  • بفهمی چرا سرریز پشته در میکروکنترلر بی‌صدا خرابکاری می‌کند و چرا هرگز آدرس متغیر محلی را برنمی‌گردانیم

ایدهٔ اصلی: آشپزخانهٔ یک رستوران

یک آشپزخانهٔ شلوغ را در نظر بگیر. همه‌چیز یک‌جا نیست، هر چیزی جای خودش را دارد:

مثال از زندگی روزمره
  • دفتر دستور پخت (چاپ‌شده): با خاموش‌شدن برق هم می‌ماند و هیچ‌کس در آن خط نمی‌زند. این «برنامه» است.
  • منوی چاپی روی دیوار: قیمت‌ها و اسم غذاها. فقط خواندنی. این «ثابت‌ها» هستند.
  • تختهٔ سفید با اعداد اولیه: هر صبح مدیر عددهای شروع (موجودی برنج = ۵۰) را از روی یک کاغذ چاپی رویش می‌نویسد. بعد کارکنان مدام پاک و بازنویسی می‌کنند. این «متغیرهای سراسری با مقدار اولیه» است.
  • تختهٔ سفید تمیز: هر صبح کامل پاک می‌شود و همه‌چیز صفر است. این «متغیرهای سراسری بدون مقدار» است.
  • سینی کارهای در جریان: آشپز هر کار تازه را روی سینی می‌گذارد و تمام که شد برمی‌دارد. آخرین کاری که آمده اولین کاری است که تمام می‌شود. این «پشته» است.
  • انبار: هر وقت خواستی یک جعبه می‌گیری و خودت باید پس بدهی. این «heap» است (درس ۴.۴).

حافظهٔ میکروکنترلر دقیقا همین‌طور تقسیم شده. هر متغیری که می‌نویسی، کامپایلر یکی از این جاها را برایش انتخاب می‌کند. اگر ندانی کدام، دو جا غافلگیر می‌شوی: اول وقتی RAM بی‌دلیل پر می‌شود، و دوم وقتی مقدار یک متغیر ناگهان «آشغال» می‌شود.

نقشهٔ حافظهٔ STM32F411

یادت هست میکروکنترلر دو حافظهٔ اصلی دارد (درس ۲.۱): Flash که با خاموشی می‌ماند و RAM که پاک می‌شود. هر دو یک فضای آدرس مشترک دارند؛ یعنی هر بایت یک شماره دارد و CPU با شماره صدایش می‌کند. در STM32F411 (برد Nucleo-F411RE):

  • Flash از 0x08000000 شروع می‌شود و ۵۱۲ کیلوبایت است.
  • RAM از 0x20000000 شروع می‌شود و ۱۲۸ کیلوبایت است.

«SP اولیه» یعنی جایی که پشته از آن شروع می‌شود: خانهٔ بعد از آخرین بایت RAM. یادت باشد پشته از بالاترین آدرس RAM شروع می‌شود و به سمت آدرس‌های کمتر می‌آید (در شکل بالا: از ته شکل به سمت بالا). این را کمی بعد در بخش پشته می‌بینی، و در درس ۵.۱ می‌بینی که چطور این عدد به CPU داده می‌شود.

شش بخش، شش قانون

کامپایلر خروجی‌اش را در «تکه‌هایی» به اسم بخش (section) می‌ریزد. اسم‌ها از قدیم مانده و باید حفظ شوند، چون در هر پروژهٔ embedded و در فایل linker script می‌بینی‌شان:

بخشچه چیزی داخلش است؟کجا؟مثال
.textدستورهای ماشین (کد توابع)Flashبدنهٔ main
.rodataداده‌های فقط‌خواندنیFlashconst سراسری، رشتهٔ "hello"
.dataسراسری و static با مقدار اولیهٔ غیرصفرRAM (و یک نسخه در Flash)int g = 5;

اسم عجیب .bss از کجاست؟

اسمش از یک اسمبلر قدیمی می‌آید (Block Started by Symbol). لازم نیست معنی اسمش را بدانی؛ فقط بدان «متغیرهای سراسری که با صفر شروع می‌شوند». مهم‌ترین نکته: چون قرار است همه صفر باشند، لازم نیست در Flash نسخه‌ای از صفرها نگه داشت، فقط اندازه‌شان ثبت می‌شود. برنامه‌ای با آرایهٔ سراسری ۱۰۰۰ بایتی و بدون مقدار، Flash را ۱۰۰۰ بایت بزرگ‌تر نمی‌کند.

حالا با یک برنامهٔ کوچک ببینیم کدام متغیر به کدام بخش می‌رود. این فایل را برای Cortex-M4 (پردازندهٔ STM32F411) کامپایل می‌کنیم:

#include <stdint.h>

int g_counter = 5;              // سراسری با مقدار اولیه
int g_total;                    // سراسری بدون مقدار
const int g_limit = 100;        // سراسری const
static uint8_t s_buf[64];       // سراسری خصوصی فایل، بدون مقدار

int bump(void)
{
    static int calls = 0;       // static محلی
    int step = 2;               // محلی معمولی
    calls = calls + 1;
    g_total = g_total + step;
    s_buf[0] = (uint8_t)calls;
    return g_counter + g_limit + calls;
}
  1. سراسری با مقدار. g_counter بیرون هر تابع تعریف شده و مقدار اولیه‌اش ۵ است (غیرصفر). می‌رود به .data. ماشین باید بداند «۵» کجا نوشته شده: پس یک نسخه از آن در Flash می‌ماند و هنگام بوت به RAM کپی می‌شود.
  2. سراسری بدون مقدار. می‌رود به .bss. C تضمین می‌کند مقدار اولیهٔ هر متغیر سراسری، صفر است. پس نیازی به ذخیرهٔ مقدار نیست؛ کد بوت کل این ناحیه را با صفر پر می‌کند.
  3. const سراسری. می‌رود به .rodata در Flash و اصلا RAM مصرف نمی‌کند. چون هرگز عوض نمی‌شود، لازم نیست کپی قابل‌تغییری در RAM داشته باشد. برای همین در میکروکنترلر جدول‌های بزرگ را const می‌کنیم.
  4. سراسری static. ۶۴ بایت، بدون مقدار: .bss. static فقط این را می‌گوید که نامش برای فایل‌های دیگر دیده نشود، جایش را عوض نمی‌کند.
  5. خود تابع. دستورهای bump در .text (Flash) هستند، نه RAM.
  6. static محلی. اسمش فقط داخل تابع دیده می‌شود، ولی خودش مثل سراسری در RAM ثابت می‌ماند (اینجا صفر است: .bss). پس با برگشتن از تابع نمی‌میرد. بخش بعد دقیق‌تر می‌گوید.
  7. محلی معمولی. step روی پشته (یا حتی در یک رجیستر CPU) است و با برگشتن از تابع از بین می‌رود. در هیچ‌یک از بخش‌های بالا نیست.
  8. استفاده. خواندن و نوشتن سراسری‌ها از RAM (.data/.bss) انجام می‌شود.

حالا از خود ابزارها بپرس. nm فهرست نمادها (اسم‌ها) را می‌دهد و حرف وسط نوع بخش را نشان می‌دهد؛ size -A اندازهٔ هر بخش را:

دستور size روی فایل کامل

وقتی پروژهٔ کامل لینک شد (درس ۵.۱)، arm-none-eabi-size firmware.elf سه عدد می‌دهد: text (کد + ثابت‌ها؛ در Flash)، data و bss. مصرف Flash تقریبا text + data است و مصرف RAM ایستا data + bss. (در فایل تنها با -c مثل بالا، ستون text شامل .rodata هم می‌شود و ۸۸ = ۸۴ + ۴ را نشان می‌دهد.) این سه عدد اولین چیزی است که یک مهندس حرفه‌ای بعد از هر ساخت نگاه می‌کند.

قبل از main چه می‌گذرد؟

وقتی برق وصل می‌شود، RAM پر از آشغال است (مثل تختهٔ سفید نانوشته‌ای که کسی رویش خط‌خطی کرده). ولی ما قول داده‌ایم g_counter برابر ۵ و g_total برابر ۰ باشد. کی این قول عملی می‌شود؟ قبل از main، توسط تکه‌کدی به اسم «کد استارت‌آپ» که با هر reset اول از همه اجرا می‌شود.

ببین همین کار چقدر ساده است. این نسخهٔ کوچک‌شده از کد استارت‌آپ واقعی است (نسخهٔ کامل و تنظیم آدرس‌ها در درس ۵.۱ می‌آید):

#include <stdint.h>

extern uint32_t _sidata;        // شروع مقدارهای اولیه در Flash
extern uint32_t _sdata;         // شروع .data در RAM
extern uint32_t _edata;         // پایان .data در RAM
extern uint32_t _sbss;          // شروع .bss
extern uint32_t _ebss;          // پایان .bss

int main(void);

void Reset_Handler(void)
{
    uint32_t *src = &_sidata;
    uint32_t *dst = &_sdata;
    while (dst < &_edata) {
        *dst++ = *src++;        // کپی از Flash به RAM
    }
    for (dst = &_sbss; dst < &_ebss; dst++) {
        *dst = 0;               // صفر کردن .bss
    }
    main();
    for (;;) { }
}
  1. نمادهای مرزی. extern یعنی «این نام جای دیگری تعریف شده» (جزئیاتش در درس ۴.۲). اینجا این پنج نام را برنامه‌ات تعریف نمی‌کند؛ لینکر (linker script) می‌سازد و آدرس‌های شروع و پایان بخش‌ها را در آنها می‌گذارد. فقط لینکر می‌داند بعد از چیدن همهٔ فایل‌ها، .data دقیقا کجای RAM افتاده. پس خودش نشانه‌گذاری می‌کند و کد ما با & (آدرسِ) این نشانه‌ها کار می‌کند، نه با مقدارشان.
  2. پروتوتایپ main. تا کامپایلر بداند main چیست (درس ۲.۶).
  3. اولین تابع برنامه. پس از reset، CPU مستقیم اینجا می‌آید (نه به main). چرا و چطور، در درس ۵.۱.
  4. دو اشاره‌گر. src جایی در Flash که مقدارهای اولیه‌اند؛ dst جایی در RAM که باید کپی شوند (اشاره‌گر: درس ۳.۲).
  5. حلقهٔ کپی. تا وقتی dst به پایان .data نرسیده: یک کلمهٔ ۳۲ بیتی کپی کن (*dst++ = *src++: «مقدار src را در خانهٔ dst بگذار، بعد هر دو را یک خانه جلو ببر»). بعد از این حلقه g_counter واقعا ۵ است. بدون آن، مقدار اولیه‌ای که در کدت نوشتی هرگز به RAM نمی‌رسید.
  6. حلقهٔ صفر کردن. از ابتدا تا انتهای .bss صفر می‌نویسد. به همین دلیل «سراسری بدون مقدار = صفر» تضمین می‌شود. این ضمانت مفت به دست نمی‌آید؛ کسی باید RAM را پاک کند و آن کس، همین کد استارت‌آپ است. (در برنامه‌های خیلی بزرگ، این صفر کردن چند میکروثانیه زمان می‌برد.)
  7. حالا برنامهٔ تو. main صدا زده می‌شود و می‌داند همهٔ سراسری‌ها آماده‌اند.
  8. اگر main برگشت. روی میکروکنترلر جایی برای برگشتن نیست (سیستم‌عاملی نیست)؛ پس اینجا برای همیشه می‌چرخد (درس ۱.۴).

دیده‌شدن و زنده‌بودن، دو سؤال جدا

دربارهٔ هر متغیر دو سؤال کاملا جدا داریم:

  • کجا دیده می‌شود؟ (scope، یعنی «حوزه»): از کدام خط‌ها می‌توانی اسمش را بنویسی؟
  • کی زنده است؟ (lifetime، یعنی «طول عمر»): چه مدت قفسه‌اش در RAM وجود دارد و مقدارش حفظ می‌شود؟
مثال از زندگی روزمره

هتل را ببین. شمارهٔ اتاق فقط برای مهمانِ همان اتاق معنی دارد (دیده‌شدن محدود). ولی اتاق هست چه مهمان در آن باشد چه نباشد (زنده‌بودن). حالا فرض کن اتاقی فقط وقتی ساخته می‌شود که مهمان می‌رسد و وقتی می‌رود خراب می‌شود: این «متغیر محلی» است. اتاقی که همیشه هست ولی کلیدش فقط دست مهمان است: «static محلی». و لابی که همه می‌بینند: «سراسری».

نوع متغیرکجا تعریف می‌شوددیده می‌شودزنده استجا
محلی (پیش‌فرض)داخل تابع یا بلوک { }فقط همان بلوکاز ورود تا خروجپشته (یا رجیستر CPU)
پارامتر تابعسر تابعفقط همان تابعاز صدا زدن تا برگشتپشته (یا رجیستر)
static محلیداخل تابعفقط همان تابعکل برنامه.data یا .bss
سراسریبیرون هر تابعکل پروژه (با extern، درس ۴.۲)کل برنامه.data، .bss، یا .rodata اگر const
static سراسریبیرون هر تابعفقط همین فایلکل برنامهمثل سراسری

کلمهٔ static در C دو معنی دارد که به هم شبیه‌اند ولی یکی نیستند. این جدول را با دقت بخوان:

  • static بیرون تابع: فقط «دیده‌شدن» را محدود می‌کند (فقط در همین فایل). طول عمرش از قبل هم کل برنامه بود.
  • static داخل تابع: «طول عمر» را عوض می‌کند: متغیر از محلی معمولی به «زنده تا آخر برنامه» می‌رود. دیده‌شدنش همان تابع می‌ماند.

static محلی: حافظه‌ای که تابع دارد

گاهی تابع باید چیزی را از یک بار صدا شدن به بار بعد یادش بماند: شمارندهٔ فراخوانی، مقدار قبلی سنسور، شمارهٔ بستهٔ بعدی. دو راه داری: یک متغیر سراسری (که همه‌جا دیده می‌شود و ممکن است کسی خرابش کند)، یا یک static محلی (که فقط خود تابع می‌بیند). دومی تمیزتر است. مقایسه:

#include <stdio.h>

static int next_id(void)
{
    static int last = 100;      // فقط یک بار ساخته می‌شود
    last = last + 1;
    return last;
}

static int next_local(void)
{
    int last = 100;             // هر بار از نو
    last = last + 1;
    return last;
}

int main(void)
{
    for (int i = 0; i < 3; i++) {
        int a = next_id();
        int b = next_local();
        printf("call %d: static=%d local=%d\n", i + 1, a, b);
    }
    return 0;
}
  1. تابع با حافظه. static int last = 100; فقط یک بار مقدار می‌گیرد: نه هر بار که تابع صدا زده می‌شود، بلکه یک بار برای همیشه، قبل از اجرای برنامه (در .data). صدا زدن‌های بعدی از این خط رد می‌شوند. تصور غلط رایج: «خط static int last = 100; هر بار اجرا می‌شود و مقدار را ۱۰۰ می‌کند». نه! مقدار ۱۰۰ قبل از main در قفسه گذاشته شده و بعدا فقط last = last + 1 عوضش می‌کند.
  2. نسخهٔ معمولی. last محلی است. هر بار که تابع صدا زده می‌شود، قفسهٔ تازه روی پشته ساخته و با ۱۰۰ پر می‌شود، ۱ اضافه می‌شود و تابع که تمام شد، قفسه از بین می‌رود.
  3. سه بار صدا زدن. هر دو تابع را سه بار صدا می‌زنیم و هر بار جواب هر دو را می‌گیریم و چاپ می‌کنیم. (هر تابع را در یک خط جدا صدا زدیم تا ترتیب اجرایشان معلوم باشد.) اگر هر دو را داخل یک printf می‌نوشتی، C ترتیب ارزیابی آرگومان‌ها را تضمین نمی‌کند (درس ۲.۳)؛ برای مثالی که اثر static را نشان می‌دهد، ترتیب مهم است.
$ gcc -std=c11 -Wall -Wextra -o life life.c
$ ./life
call 1: static=101 local=101
call 2: static=102 local=101
call 3: static=103 local=101

ستون static بالا می‌رود (۱۰۱، ۱۰۲، ۱۰۳): تابع «یادش می‌ماند». ستون local همیشه ۱۰۱ است: هر بار قفسهٔ تازه.

دو خطر static محلی
  • تابع دیگر «خالص» نیست. با ورودی یکسان خروجی متفاوت می‌دهد و تست‌کردنش سخت‌تر است. برای شمارنده یا آخرین مقدار خوب است، برای منطق اصلی نه.
  • ایمنی در برابر وقفه و چند وظیفه. اگر هم main و هم یک ISR (درس ۵.۳) یا دو task (درس ۵.۶) همان تابع را صدا بزنند، یک قفسه بین آنها مشترک می‌شود. بدون محافظت، خراب می‌شود. متغیر محلی معمولی این خطر را ندارد چون هر بار قفسهٔ خودش را دارد.

مقدار اولیه: سراسری صفر، محلی آشغال

در درس ۲.۱ دیدی متغیر محلی بدون مقدار، «آشغال» دارد. حالا دلیلش را می‌فهمی و می‌بینی سراسری‌ها فرق دارند:

متغیرمقدار اولیه اگر ننویسیچرا؟
سراسری و static (محلی یا سراسری)صفر (تضمین‌شده توسط استاندارد C)کد استارت‌آپ .bss را صفر می‌کند
محلی معمولیآشغال (هر چه قبلا روی آن خانه‌ها بوده)پشته هر لحظه دوباره استفاده می‌شود و پاک نمی‌شود، چون پاک کردن زمان می‌برد
حافظهٔ mallocآشغالcalloc صفر می‌کند (درس ۴.۴)
#include <stdio.h>

int g_count;                    // سراسری بدون مقدار
static int s_flag;              // static بدون مقدار
int g_table[4];                 // آرایهٔ سراسری بدون مقدار

int main(void)
{
    static int calls;           // static محلی بدون مقدار
    printf("g_count=%d s_flag=%d calls=%d\n", g_count, s_flag, calls);
    printf("table: %d %d %d %d\n", g_table[0], g_table[1], g_table[2], g_table[3]);
    return 0;
}
  1. سه سراسری بدون مقدار. هیچ‌کدام مقدار اولیه ندارند. آرایه هم همین‌طور: همهٔ خانه‌هایش صفر می‌شود. اگر مقدار نمی‌دهی هم به‌خاطر خوانایی = 0 بنویس؛ برای کامپایلر تفاوتی ندارد (باز هم .bss) ولی خواننده مطمئن می‌شود عمدی است.
  2. static محلی بدون مقدار. مثل سراسری صفر است، نه آشغال.
  3. چاپ. همه صفر چاپ می‌شوند، بدون اینکه ما چیزی نوشته باشیم.
$ gcc -std=c11 -Wall -Wextra -o zero zero.c
$ ./zero
g_count=0 s_flag=0 calls=0
table: 0 0 0 0
در میکروکنترلر: «صفر تضمینی» به کد استارت‌آپ وابسته است

این ضمانت را استاندارد C می‌دهد، ولی کد استارت‌آپ عملی‌اش می‌کند. اگر خودت یک استارت‌آپ ناقص بنویسی (یا در یک پروژهٔ خاص حافظه‌ای را عمدا پاک نکنی)، سراسری‌ها آشغال می‌شوند. در پروژه‌های معمولی STM32 و ESP32 کد استارت‌آپ آماده است و کار می‌کند؛ لازم نیست نگرانش باشی، فقط بدانی از کجا می‌آید.

پشته: سینی کارهای در جریان

در درس ۲.۶ دیدی هر تابع، هنگام صدا زدن، یک فریم روی پشتهٔ فراخوانی می‌گیرد. حالا آن را روی نقشهٔ حافظه ببین. پشته یک ناحیهٔ ثابت از RAM است که از بالاترین آدرس شروع می‌شود و به سمت آدرس‌های کمتر رشد می‌کند. ثباتی به اسم SP (Stack Pointer، اشاره‌گر پشته) همیشه به آخرین فریم اشاره می‌کند.

سرریز پشته: خطری که بی‌صدا می‌آید

اندازهٔ پشته در PC چندین مگابایت است و اگر پر شود، سیستم‌عامل برنامه را می‌کُشد (پیام segmentation fault). در میکروکنترلر این‌طور نیست. پشته یک ناحیهٔ کوچک است (معمولا از چند صد بایت تا چند کیلوبایت که خودت در پروژه تعیین می‌کنی) و هیچ نگهبانی اطرافش نیست: حافظهٔ زیر پشته یا داده‌های دیگر است (سراسری‌ها، heap) یا حافظهٔ بی‌مصرف. پس سرریز پشته (stack overflow) یعنی پشته بی‌سروصدا روی متغیرهای دیگر می‌نویسد.

مثال از زندگی روزمره

سینی کارهای آشپزخانه فقط ده جا دارد. آشپز یازدهمین ظرف را می‌گذارد؛ ظرف روی میز کناری، جایی که مواد اولیهٔ فردا بود، می‌افتد و همه را می‌ریزد. هیچ آلارمی نمی‌زند؛ فردا مواد خراب‌اند و کسی نمی‌داند چرا. علائم در میکروکنترلر همین است: متغیر سراسری که «خودبه‌خود» عوض شد، برنامه‌ای که گاهی هنگ می‌کند، یا HardFault (خطای سخت CPU، درس ۶.۱).

پشته با چه چیزهایی پر می‌شود؟ سه عامل اصلی:

  1. آرایهٔ بزرگ محلی. char buf[1024] داخل یک تابع یعنی هر بار که تابع صدا زده شود، ۱۰۲۴ بایت از پشته می‌رود.
  2. بازگشت عمیق. هر مرحله یک فریم (درس ۲.۶).
  3. زنجیرهٔ عمیق توابع و ISRها که بالای پشته نشسته‌اند.

می‌شود پیش از اجرا، مصرف پشتهٔ هر تابع را از کامپایلر پرسید. گزینهٔ -fstack-usage یک فایل .su می‌سازد. این دو تابع را ببین:

#include <stdint.h>

extern void send(const uint8_t *data, uint32_t len);

void log_small(void)
{
    uint8_t line[16];
    for (uint32_t i = 0; i < 16; i++) line[i] = (uint8_t)i;
    send(line, 16);
}

void log_big(void)
{
    uint8_t line[1024];
    for (uint32_t i = 0; i < 1024; i++) line[i] = (uint8_t)i;
    send(line, 1024);
}
  1. تابع بیرونی. send جای دیگر تعریف می‌شود؛ فقط لازم داریم چیزی باشد که آرایه را «مصرف» کند تا کامپایلر آن را حذف نکند.
  2. آرایهٔ ۱۶ بایتی محلی. روی پشته: کوچک و بی‌خطر.
  3. آرایهٔ ۱۰۲۴ بایتی محلی. هر بار صدا زدن ۱ کیلوبایت پشته می‌گیرد. در یک MCU با پشتهٔ ۲ کیلوبایتی، دو بار صدا زدن تو در تو (یا یک ISR وسط آن) کافی است تا پشته سرریز شود.
$ arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -std=gnu11 -Wall -Wextra -ffreestanding -fstack-usage -c stack.c
$ cat stack.su
stack.c:5:6:log_small	32	static
stack.c:12:6:log_big	1040	static

ستون دوم بایت‌های پشته است: ۳۲ و ۱۰۴۰ (بیشتر از خود آرایه، چون آدرس برگشت و رجیسترهای ذخیره‌شده هم روی فریم می‌روند). static در ستون سوم یعنی اندازه در زمان کامپایل ثابت است.

چطور بفهمیم پشته سرریز شده؟

سه راه عملی: (۱) پیش از اجرا، ناحیهٔ پشته را با یک الگوی شناخته‌شده مثل 0xDEADBEEF پر کن و بعد از مدتی اجرا ببین تا کجا پاک شده (حد بالای مصرف واقعی)؛ (۲) گزینهٔ -fstack-protector در gcc بعضی سرریزهای بافر محلی را موقع برگشت از تابع شناسایی می‌کند (روی MCU به پشتیبانی کتابخانه نیاز دارد)؛ (۳) در FreeRTOS و ESP-IDF تابع uxTaskGetStackHighWaterMark کمترین فضای خالی پشتهٔ یک تسک را برمی‌گرداند.

چه کنیم؟
  • بافر بزرگ را static کن (می‌رود .bss؛ اندازه‌اش را size نشان می‌دهد و در زمان ساخت می‌فهمی جا می‌شود یا نه) یا سراسری بگذار.
  • بازگشت را در MCU جدی محدود کن یا حذف کن (درس ۲.۶).
  • در ISR فقط متغیرهای کوچک بگذار (درس ۵.۳).
  • اندازهٔ پشته را از روی -fstack-usage و آزمایش واقعی بگذار، با حاشیهٔ ایمنی. در FreeRTOS/ESP-IDF هر task پشتهٔ جدا و اندازهٔ جداگانه دارد (درس ۵.۶).

هرگز آدرس متغیر محلی را برنگردان

حالا که فهمیدی محلی‌ها با برگشتن از تابع می‌میرند، خطرناک‌ترین اشتباه اشاره‌گر را بفهم. تابع می‌خواهد یک عدد بسازد و آدرسش را بدهد:

#include <stdio.h>

int *make_number(void)
{
    int n = 42;                 // محلی: با برگشتن تابع می‌میرد
    return &n;                  // آدرس چیزی که دارد می‌میرد!
}

int main(void)
{
    int *p = make_number();
    printf("%d\n", *p);
    return 0;
}
  1. تابع اشتباه. n روی پشته و در فریم make_number است. return &n آدرس همان خانه را به بیرون می‌دهد. لحظهٔ برگشت، فریم رها می‌شود. آن خانه‌ها به‌زودی برای تابع بعدی به کار می‌روند و n هیچ‌جا نیست.
  2. استفادهٔ آویزان. p به خانه‌ای اشاره دارد که دیگر مال ما نیست (dangling pointer، اشاره‌گر آویزان؛ درس ۳.۲). خواندن آن نتیجهٔ نامعلوم دارد: ممکن است ۴۲ بدهد (اگر هنوز پاک نشده)، ممکن است آشغال یا crash.
dangling.c: In function 'make_number':
dangling.c:6:12: error: function returns address of local variable [-Werror=return-local-addr]

خوشبختانه gcc این خطا را می‌بیند (همین هشدار به‌طور پیش‌فرض با -Wall هست؛ ما با -Werror= به خطا تبدیلش کردیم تا کامپایل متوقف شود). ولی همیشه هشدار نمی‌دهد: اگر آدرس را در یک اشاره‌گر سراسری بریزی یا از چند تابع رد کنی، کامپایلر ممکن است ندبیند. یک قانون ساده: هر چه در تابع ساخته‌ای، با برگشتن می‌میرد؛ پس آدرسش را نده. سه راه درست:

#include <stdio.h>

static int *counter_ptr(void)
{
    static int n = 42;          // static: تا آخر برنامه زنده است
    return &n;
}

static void fill_number(int *out)
{
    *out = 42;                  // نتیجه در قفسهٔ صدازننده نوشته می‌شود
}

int main(void)
{
    int *p = counter_ptr();
    int mine;
    fill_number(&mine);
    printf("%d %d\n", *p, mine);
    return 0;
}
  1. راه ۱: static. n در .data می‌نشیند و می‌ماند؛ آدرسش همیشه معتبر است. هزینه‌اش: یک قفسهٔ مشترک بین همهٔ صدا زدن‌ها. اگر دو نفر همزمان از آن استفاده کنند به هم می‌ریزد.
  2. راه ۲: صدازننده قفسه را می‌دهد. out اشاره‌گر به قفسه‌ای در main است. تابع فقط داخلش می‌نویسد. این رایج‌ترین الگو در کد embedded است: تابع خروجی را در جایی که تو می‌دهی می‌ریزد.
  3. استفاده. هر دو خروجی معتبرند.
$ ./safe_number
42 42

راه سوم malloc است که در درس ۴.۴ می‌آید و در میکروکنترلر با احتیاط استفاده می‌شود.

Flash یا RAM؟ قدرت const

یک جدول ۳۲ عددی سینوس را در نظر بگیر که برای تولید صدا لازم است. دو راه برای نوشتنش هست و تفاوتشان فقط یک کلمه است:

#include <stdint.h>

const uint8_t sine_flash[32] = {
    128, 152, 176, 198, 218, 234, 245, 253,
    255, 253, 245, 234, 218, 198, 176, 152,
    128, 103,  79,  57,  37,  21,  10,   2,
      0,   2,  10,  21,  37,  57,  79, 103
};

uint8_t sine_ram[32] = {
    128, 152, 176, 198, 218, 234, 245, 253,
    255, 253, 245, 234, 218, 198, 176, 152,
    128, 103,  79,  57,  37,  21,  10,   2,
      0,   2,  10,  21,  37,  57,  79, 103
};
  1. با const. جدول فقط‌خواندنی است، پس می‌رود .rodata در Flash. RAM هیچ‌چیز نمی‌گیرد.
  2. بدون const. جدول ممکن است عوض شود؛ پس باید در RAM باشد و برای مقدارهای اولیه‌اش یک نسخه هم در Flash نگه داشته شود (.data). یعنی ۳۲ بایت Flash و ۳۲ بایت RAM. دو برابر! در جدول‌های بزرگ‌تر (فونت صفحه‌نمایش، جدول CRC، نقشهٔ رنگ) این تفاوت تعیین‌کننده است. RAM میکروکنترلر گران‌ترین منبع است.
$ arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -std=gnu11 -Wall -Wextra -ffreestanding -c tables.c
$ arm-none-eabi-size -A tables.o | head -6
tables.o  :
section           size   addr
.text                0      0
.data               32      0
.bss                 0      0
.rodata             32      0
$ arm-none-eabi-nm tables.o
00000000 R sine_flash
00000000 D sine_ram

sine_flash با حرف R در .rodata و sine_ram با D در .data. هر کدام ۳۲ بایت، ولی اولی فقط Flash می‌گیرد و دومی هر دو.

سه نکتهٔ ریز دربارهٔ const و Flash
  • فقط const سراسری (یا static const) به Flash می‌رود. یک const int x = 5; داخل تابع فقط یک متغیر محلی است که نباید عوض شود؛ روی پشته می‌نشیند.
  • رشتهٔ literal مثل "hello" در .rodata است (درس ۲.۸). ولی char s[] = "hello" داخل تابع یک کپی روی پشته می‌سازد.
  • در پردازنده‌های ۸ بیتی AVR (Arduino Uno) Flash و RAM آدرس‌گذاری جدا دارند و برای خواندن از Flash باید ابزار مخصوص (PROGMEM) به کار ببری. در Cortex-M و ESP32 این‌طور نیست؛ Flash در همان فضای آدرس دیده می‌شود و const کافی است (در ESP32 از راه کش).

در ESP32 یک جزئیات خاص هست که در ESP-IDF زیاد به آن می‌خوری: تابعی که در ISR اجرا می‌شود یا نباید منتظر Flash بماند، باید در RAM باشد. برای همین برچسب IRAM_ATTR را جلوی تابع می‌گذاری تا در IRAM (RAM اجرایی) قرار بگیرد، نه در Flash کش‌شده (درس ۵.۳). جزئیات دقیق انواع حافظه و اندازه‌ها در «Memory Types» مستندات ESP-IDF است؛ آنجا ببین، چون بین نسخه‌های تراشه (ESP32، S2، S3، C3) فرق می‌کند. یک نمونه برای دیدن مقدار heap آزاد (ESP-IDF v5.x):

#include "esp_log.h"
#include "esp_system.h"

static const char *TAG = "mem";

int g_boot_count = 3;           // .data
int g_flags;                    // .bss

void app_main(void)
{
    int local = 7;              // پشتهٔ task اصلی
    ESP_LOGI(TAG, "local=%d boot=%d flags=%d", local, g_boot_count, g_flags);
    ESP_LOGI(TAG, "free heap = %lu bytes", (unsigned long)esp_get_free_heap_size());
}
  1. سرصفحه‌ها. esp_log.h برای لاگ و esp_system.h برای esp_get_free_heap_size.
  2. برچسب لاگ. رشتهٔ ثابت، در .rodata.
  3. سراسری‌ها. یکی در .data و یکی در .bss، دقیقا مثل STM32.
  4. app_main. نقطهٔ شروع برنامه در ESP-IDF (به‌جای main دستی، درس ۵.۶). local روی پشتهٔ همین task است.
  5. heap آزاد. تعداد بایت‌های آزاد heap را برمی‌گرداند؛ با (unsigned long) و %lu چاپ می‌کنیم تا روی هر پلتفرم درست کار کند. اندازهٔ دقیق نوع برگشتی در نسخه‌های مختلف فرق می‌کند؛ تبدیل صریح مشکل قالب printf را از بین می‌برد.
زیر کاپوت: چرا «نقشه» تا این حد مهم است؟

در PC سیستم‌عامل به هر برنامه یک حافظهٔ مجازی می‌دهد: ناحیه‌های جدا، محافظت‌شده، با پشتهٔ بزرگ. اگر برنامه بیرون از حدش بنویسد، سیستم‌عامل قطعش می‌کند. در میکروکنترلر (به‌ویژه Cortex-M4 در STM32F411 که واحد محافظت حافظهٔ MPU را دارد ولی به‌طور پیش‌فرض خاموش است و باید خودت آن را تنظیم و روشن کنی) هیچ‌چیز ناحیه‌ها را محافظت نمی‌کند. برنامه‌نویس خودش «شهردار» است: باید بداند هر متغیر کجاست و هر ناحیه چقدر بزرگ است. همین آگاهی، فرق «کد که روی PC کار می‌کند» با «کد که سال‌ها روی دستگاه بی‌خطا می‌چرخد» است.

آزمون این درس

متغیر uint8_t table[100] = {0}; در سطح فایل (بیرون هر تابع) را بدون const نوشته‌ای. معمولا در کدام بخش می‌رود؟

  1. پشته (stack)
  2. .bss (RAM، با صفر پر می‌شود)
  3. .rodata (Flash)
  4. .text (Flash)
سراسری بدون const با مقدار صفر (یا بدون مقدار) در .bss است. مقدار صفر لازم نیست در Flash ذخیره شود؛ کد استارت‌آپ آن را پاک می‌کند.

تابع زیر را سه بار پشت هم صدا زده‌ایم. مجموع سه مقدار برگشتی چند می‌شود؟
int f(void) { static int n = 0; n++; return n; }

  1. ۳ (هر بار ۱)
  2. ۱
  3. ۶ (یعنی ۱ + ۲ + ۳)
  4. برنامه کامپایل نمی‌شود
مقدارها ۱، ۲، ۳ هستند چون n یک بار ساخته می‌شود و با هر صدا زدن یکی بالا می‌رود. مجموعشان ۶ است.

کدام گزینه باگ دارد؟

  1. char *get_name(void) { char name[8] = "ADC"; return name; }
  2. ‎const char *get_name(void) { return "ADC"; }
  3. ‎char *get_name(void) { static char name[8] = "ADC"; return name; }
  4. ‎void get_name(char *out) { out[0] = 'A'; out[1] = 0; }
در گزینهٔ اول name محلی است و با برگشتن تابع می‌میرد؛ اشاره‌گر برگشتی آویزان است. سه گزینهٔ دیگر یا در .rodata، یا static، یا در قفسهٔ صدازننده می‌نویسند.

چرا در STM32 نوشتن char buf[4096]; داخل یک تابع معمولی معمولا فکر خوبی نیست؟

  1. چون مقدارش آشغال است
  2. چون کامپایل نمی‌شود
  3. چون Flash را پر می‌کند
  4. چون ۴ کیلوبایت از پشتهٔ کوچک را می‌گیرد و ممکن است پشته سرریز شود و متغیرهای دیگر را بی‌صدا خراب کند
پشته در MCU کوچک است و محافظت ندارد. بافر بزرگ را static یا سراسری کن تا در زمان ساخت (با size) بفهمی جا می‌شود.

چه کسی قبل از main مقدار اولیهٔ int g = 5; را در RAM می‌گذارد؟

  1. خود تابع main در اولین خط
  2. کد استارت‌آپ (Reset_Handler)، با کپی از Flash به RAM
  3. خود RAM آن را از قبل نگه داشته
  4. کامپایلر هنگام کامپایل مستقیم در RAM می‌نویسد
کامپایلر مقدار ۵ را در Flash می‌گذارد و کد استارت‌آپ هر بار که میکروکنترلر reset می‌شود آن را به RAM کپی می‌کند.

خروجی arm-none-eabi-size -A برای فایلی نشان می‌دهد: .data 8، .bss 400، .rodata 64. این فایل در RAM چند بایت متغیر ایستا (سراسری و static) اشغال می‌کند؟

  1. ۴۰۰
  2. ۴۷۲
  3. ۴۰۸
  4. ۸
RAM ایستا = .data + .bss = ۸ + ۴۰۰ = ۴۰۸. .rodata (۶۴) در Flash است. پشته و heap جدا حساب می‌شوند.

#include <stdint.h>

uint32_t g_ticks;

const char g_name[] = "LOGGER";
static uint16_t s_samples[100];
const uint16_t g_limits[4] = {10, 20, 30, 40};

uint32_t work(void)
{
    static uint32_t runs;
    uint32_t local_sum = 0;
    runs++;
    for (uint32_t i = 0; i < 4; i++) {
        local_sum += g_limits[i];
    }
    return local_sum + runs + s_samples[0] + g_ticks + g_boot_count + (uint32_t)g_name[0];
}

  3. g_name. const سراسری: .rodata. رشتهٔ «LOGGER» ۶ حرف + '\0' = ۷ بایت.
  4. s_samples. ۱۰۰ عنصر ۲ بایتی = ۲۰۰ بایت، بدون مقدار: .bss.
  5. g_limits. ۴ عنصر ۲ بایتی = ۸ بایت: .rodata.
  6. runs. static محلی بدون مقدار: .bss (۴ بایت).
  7. local_sum. محلی معمولی: پشته یا رجیستر. در هیچ بخشی ثبت نمی‌شود.

حرف مربی

معمولا در این درس سه جا گیر می‌کنند. اول: فکر می‌کنند static داخل تابع هر بار مقدار اولیه می‌گیرد؛ نه، فقط یک بار. دوم: یادشان می‌رود Flash و RAM دو انبارند؛ برای همین جدول را const نمی‌کنند و RAM را هدر می‌دهند. سوم و خطرناک‌تر: بافر بزرگ محلی که فقط در آزمایش‌های بلند و گاهی کار می‌کند و اسمش در گزارش باگ «هنگ‌کردن تصادفی» می‌ماند. عادت‌های حرفه‌ای: بعد از هر ساخت، عددهای size را نگاه کن، مصرف پشته را از -fstack-usage بپرس، و هرگز آدرس یک متغیر محلی را برنگردان. اگر این سه عادت را الان بگیری، ماه‌ها زمان اشکال‌زدایی را صرفه‌جویی می‌کنی.

خلاصه یک‌دقیقه‌ای

  • Flash: .text (کد)، .rodata (ثابت‌ها)، نسخهٔ اولیهٔ .data. RAM: .data، .bss، heap، پشته.
  • سراسری با مقدار غیرصفر: .data. سراسری بدون مقدار یا صفر: .bss (صفر تضمینی). محلی: پشته (آشغال، مگر مقدار بدهی).
  • کد استارت‌آپ، قبل از main، .data را از Flash کپی و .bss را صفر می‌کند.
  • دیده‌شدن (scope) با طول عمر (lifetime) فرق دارد. static محلی: فقط تابع می‌بیند، ولی تا آخر برنامه زنده است.
  • پشته از بالاترین آدرس RAM شروع می‌شود و به سمت آدرس‌های کمتر رشد می‌کند؛ در MCU محافظت ندارد و سرریزش بی‌صدا خرابکاری می‌کند. بافر بزرگ محلی نساز.
  • آدرس متغیر محلی را برنگردان؛ با برگشتن تابع می‌میرد.
  • const سراسری در Flash می‌ماند و RAM نمی‌گیرد. با size، nm و -fstack-usage اندازه بگیر.
  • درس بعد: ۳.۶ رجیستر و volatile، جایی که آدرس‌ها به سخت‌افزار وصل می‌شوند.
