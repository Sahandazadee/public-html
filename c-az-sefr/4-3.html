تا اینجا هر کاری که در C کردی، روی داده بود: عدد، آرایه، ساختار. ولی یک سؤال عجیب هست: خود تابع هم جایی در حافظه نشسته است؛ پس آدرس هم دارد. آیا می‌شود آدرس یک تابع را در یک متغیر نگه داشت و بعدا گفت «هر چه در این متغیر است را اجرا کن»؟ جواب «بله» است و همین ترفند ساده پشت وقفه‌ها، درایورها، جدول فرمان‌ها و task های FreeRTOS است. در این درس یاد می‌گیری اشاره‌گر به تابع را بنویسی، بخوانی و درست به کار ببری.

🎯 بعد از این درس می‌توانی

  • اشاره‌گر به تابع را اعلان کنی و اعلان‌های عجیبش را «از داخل به بیرون» بخوانی
  • با typedef برایش یک اسم خوانا بسازی
  • تابعی بنویسی که تابع دیگری را به‌عنوان آرگومان می‌گیرد (callback)
  • جدول فرمان (dispatch table) و ساختار «عملیات درایور» بسازی
  • با qsort مرتب‌سازی سفارشی انجام بدهی
  • توضیح بدهی چرا vector table میکروکنترلر «آرایه‌ای از اشاره‌گر به تابع» است

🧰 پیش‌نیاز و وسایل

ایدهٔ اصلی: «شمارهٔ تلفن» به‌جای «خود کار»

فرض کن مدیر رستوران هستی و می‌خواهی وقتی غذای مشتری آماده شد، یکی خبرش کند. دو راه داری. راه اول: خودت کنار پنجرهٔ آشپزخانه بایستی و مدام نگاه کنی (کار دیگری نمی‌کنی). راه دوم: به آشپز یک شمارهٔ تلفن بدهی و بگویی «آماده شد، به این شماره زنگ بزن». آشپز نمی‌داند پشت آن شماره چه کسی است؛ فقط زنگ می‌زند. فردا می‌توانی شماره را عوض کنی و آشپز بدون هیچ تغییری کارش را ادامه می‌دهد.

مثال از زندگی روزمره

تابع = یک آدم با یک کار مشخص. آدرس تابع = شمارهٔ تلفن او. اشاره‌گر به تابع = یک دفترچه‌ای که یک شماره در آن نوشته‌اند. کسی که دفترچه را دارد، لازم نیست بداند طرف مقابل کیست؛ فقط «زنگ می‌زند». تنها چیزی که لازم است بداند این است که طرف مقابل چه ورودی می‌گیرد و چه چیزی برمی‌گرداند (مثل اینکه بدانی طرف فارسی حرف می‌زند). این شرط را در C «امضای تابع» می‌نامند.

در C این ایده دقیقا همین است. وقتی برنامه کامپایل شود، بدنهٔ هر تابع به چند دستور ماشین تبدیل می‌شود و آن دستورها در Flash (درس ۳.۵) از یک آدرس مشخص شروع می‌شوند. آن آدرس، «شمارهٔ تلفن» تابع است. اشاره‌گر به تابع متغیری است که همین آدرس را در RAM نگه می‌دارد.

اعلان: اولین اشاره‌گر به تابع

سخت‌ترین بخش این درس فقط شکل نوشتن است. اعلان اشاره‌گر به تابع اولش عجیب به‌نظر می‌رسد. ولی قاعدهٔ ساده‌ای دارد: اعلان را مثل خودِ تابع بنویس، فقط اسم را با (*اسم) عوض کن. اگر تابع این‌طور نوشته می‌شود:

int  add(int a, int b);        // یک تابع
int (*op)(int, int);           // اشاره‌گر به تابعی با همین امضا

پرانتز دور *op حیاتی است. بدونش، int *op(int, int) یعنی «تابعی به اسم op که یک اشاره‌گر به int برمی‌گرداند»؛ چیز کاملا متفاوتی. علت: در C پرانتز ( ) تقدم بالاتری از * دارد. پرانتز به کامپایلر می‌گوید «اول *op را ببین».

حالا اولین برنامه. دو تابع ساده داریم و یک اشاره‌گر که هر بار به یکی‌شان اشاره می‌کند.

#include <stdio.h>

static int add(int a, int b) { return a + b; }
static int sub(int a, int b) { return a - b; }

int main(void)
{
    int (*op)(int, int);        // اشاره‌گر به تابع (هنوز مقدار ندارد)

    op = add;                   // آدرس add را بگذار
    printf("op = add: %d\n", op(7, 3));

    op = sub;                   // حالا آدرس sub
    printf("op = sub: %d\n", op(7, 3));

    printf("op == add ? %d\n", op == add);
    return 0;
}
  1. دو تابع با امضای یکسان. هر دو دو int می‌گیرند و یک int برمی‌گردانند. static یعنی فقط داخل همین فایل دیده می‌شوند (درس ۴.۲). امضای یکسان شرط لازم است. اشاره‌گر فقط به تابعی اشاره می‌کند که ورودی و خروجی‌اش با اعلان اشاره‌گر بخواند.
  2. اعلان اشاره‌گر. op ساخته می‌شود ولی هنوز مقدار معتبر ندارد؛ مثل هر متغیر مقدارنداده (درس ۲.۱) آشغال دارد. در کد واقعی همان لحظهٔ ساخت مقدار بده (یا NULL). فراخوانی اشاره‌گر بدون مقدار، برنامه را به جایی تصادفی می‌پراند.
  3. مقدار دادن. نام تابع بدون پرانتز، یعنی «آدرس تابع». پس op = add آدرس add را در op می‌گذارد. (نوشتن &add هم یکی است.) اگر بنویسی add(1, 2) تابع اجرا می‌شود و نتیجه‌اش (عدد ۳) داده می‌شود. پرانتز یعنی «زنگ بزن»؛ بدون پرانتز یعنی «فقط شماره را بده».
  4. فراخوانی از راه اشاره‌گر. op(7, 3) همان تابعی را اجرا می‌کند که آدرسش در op است. (شکل رسمی‌تر: (*op)(7, 3)؛ نتیجه یکی است.) C هر دو شکل را می‌پذیرد. شکل کوتاه‌تر خواناتر است و در کد حرفه‌ای رایج‌تر.
  5. عوض کردن مقصد. همان op(7, 3)، این بار sub را اجرا می‌کند. خطِ صدا زدن تغییری نکرده؛ فقط «شماره» عوض شده. قدرت اشاره‌گر به تابع همین است: رفتار را می‌شود در زمان اجرا عوض کرد، بدون دست‌زدن به کدی که صدا می‌زند.
  6. مقایسه. دو اشاره‌گر به تابع با == مقایسه می‌شوند. الان op به sub اشاره می‌کند، پس جواب 0 است.
$ gcc -std=c11 -Wall -Wextra -o fp_basic fp_basic.c
$ ./fp_basic
op = add: 10
op = sub: 4
op == add ? 0

اسم خوانا با typedef

اگر بخواهی پارامتر تابع یا عضو struct را «اشاره‌گر به تابع» کنی، نوشتنِ int (*)(int, int) هر بار خسته‌کننده و پر از خطاست. راه‌حل استاندارد: با typedef (درس ۳.۴) یک بار برایش اسم بساز. قالب: اعلانِ متغیر را بنویس و جلویش typedef بگذار؛ اسمِ متغیر تبدیل به اسم نوع می‌شود.

int (*op)(int, int);                  // op یک متغیر است
typedef int (*binop_t)(int, int);     // binop_t یک نوع است
binop_t op;                           // همان اعلان بالا، ولی خوانا

پسوند _t رسم رایج برای اسم نوع‌هاست. از این به بعد در این درس همیشه با typedef کار می‌کنیم.

تابعی که تابع می‌گیرد: callback

حالا مثال رستوران را به کد ببریم. callback (به معنی «تماس برگشتی») تابعی است که تو می‌نویسی ولی دیگری صدایش می‌زند، هر وقت خودش لازم دید. تو فقط شمارهٔ تلفن را (آدرس تابع) به او می‌دهی.

ساده‌ترین نمونه: تابعی به اسم for_each که روی همهٔ عضوهای آرایه می‌گردد، ولی «با هر عضو چه کنم؟» را نمی‌داند و از بیرون می‌گیرد.

#include <stdio.h>

typedef void (*visit_fn)(int value);    // نوع: تابعی که int می‌گیرد و چیزی برنمی‌گرداند

static void print_value(int value)  { printf("[%d] ", value); }
static void print_double(int value) { printf("[%d] ", value * 2); }

static void for_each(const int *items, int count, visit_fn fn)
{
    for (int i = 0; i < count; i++) {
        fn(items[i]);               // callback: هر عضو را به fn بده
    }
}

int main(void)
{
    const int data[4] = {3, 8, 1, 6};

    for_each(data, 4, print_value);
    printf("\n");
    for_each(data, 4, print_double);
    printf("\n");
    return 0;
}
  1. نوع callback. visit_fn یعنی «تابعی که یک int می‌گیرد و چیزی برنمی‌گرداند». با این اسم، امضای مورد انتظار یک‌جا نوشته شده. اگر فردا بخواهی پارامتر دومی اضافه کنی، فقط همین یک خط عوض می‌شود و کامپایلر بقیهٔ جاهای ناسازگار را نشانت می‌دهد.
  2. دو رفتار مختلف. هر دو با visit_fn سازگارند: print_value عدد را چاپ می‌کند، print_double دو برابرش را.
  3. for_each. آرایه، تعداد و یک callback می‌گیرد. برای هر عضو fn(items[i]) را صدا می‌زند. خودش نمی‌داند fn چه می‌کند. این جداسازی «پیمایش» از «کار روی هر عضو» است. یک بار پیمایش را می‌نویسی و با callback های مختلف بارها استفاده می‌کنی.
  4. داده. آرایهٔ const: for_each فقط می‌خواند، پس const int * می‌گیرد (درس ۳.۳).
  5. دادن شماره. فقط نام تابع، بدون پرانتز. اگر print_value(...) بنویسی، تابع همین‌جا اجرا می‌شود و نتیجه‌اش (که void است) به for_each می‌رسد؛ کامپایل نمی‌شود.
$ gcc -std=c11 -Wall -Wextra -o callback callback.c
$ ./callback
[3] [8] [1] [6]
[6] [16] [2] [12]

callback بدون سراسری: پارامتر context

یک مشکل: print_value فقط با ورودی‌اش کار می‌کند. اگر callback بخواهد چیزی را «به یاد بسپارد» (مثلا جمع را)، کجا نگه دارد؟ راه بد: متغیر سراسری. راه خوب: یک اشاره‌گر void * به‌عنوان پارامتر اضافه (اغلب context یا user_data نامیده می‌شود). for_each فقط آن را عیناً به callback برمی‌گرداند و خودش نمی‌داند داخلش چیست.

#include <stdio.h>

typedef void (*visit_fn)(int value, void *ctx);

typedef struct {
    int sum;
    int max;
} stats_t;

static void update_stats(int value, void *ctx)
{
    stats_t *s = ctx;               // برگرداندن void * به نوع واقعی
    s->sum += value;
    if (value > s->max) {
        s->max = value;
    }
}

static void for_each(const int *items, int count, visit_fn fn, void *ctx)
{
    for (int i = 0; i < count; i++) {
        fn(items[i], ctx);
    }
}

int main(void)
{
    const int data[5] = {3, 8, 1, 6, 4};
    stats_t stats = {0, data[0]};

    for_each(data, 5, update_stats, &stats);
    printf("sum=%d max=%d\n", stats.sum, stats.max);
    return 0;
}
  1. امضای جدید. callback حالا دو ورودی دارد: مقدار عضو، و void *ctx که «جعبهٔ دلخواه» تو است. هر تابعی با void * می‌تواند اشاره‌گر به هر نوعی را نگه دارد (درس ۳.۳)؛ پس یک for_each با همهٔ کاربردها کار می‌کند.
  2. جعبهٔ آمار. ساختاری که جمع و بیشینه را نگه می‌دارد.
  3. callback. اول ctx را به stats_t * برمی‌گرداند، بعد جمع و بیشینه را به‌روز می‌کند. برگرداندن void * به اشاره‌گر واقعی در C بدون cast مجاز است. مسئولیت درست‌بودن نوع با توست؛ کامپایلر نمی‌تواند بررسی کند.
  4. for_each. ctx را بدون دست‌زدن رد می‌کند.
  5. جعبه را بساز و بده. &stats آدرس جعبه است. stats مقدار اولیهٔ بیشینه را عضو اول می‌گیرد تا مقایسه درست باشد. هیچ متغیر سراسری لازم نشد. هر فراخوانی جعبهٔ مخصوص خودش را دارد؛ پس امن‌تر و قابل‌تست‌تر است.
$ ./context
sum=22 max=8

جدول فرمان: dispatch table

فرض کن دستگاهت از UART متن می‌گیرد: on، off یا status. ساده‌ترین راه یک زنجیرهٔ طولانی if (strcmp(...)) ... else if (...) است. هر فرمان جدید یعنی یک else if دیگر و کد کم‌کم به هم می‌ریزد. راه بهتر: یک جدول بساز که هر ردیفش «اسم فرمان + تابعی که اجرایش می‌کند» است، و برای پیدا کردن فرمان فقط جدول را بگردی. به این کار dispatch (یعنی «توزیع کردن به تابع مناسب») می‌گویند.

#include <stdio.h>
#include <string.h>

static void cmd_led_on(void)  { printf("LED is now ON\n"); }
static void cmd_led_off(void) { printf("LED is now OFF\n"); }
static void cmd_status(void)  { printf("status: all good\n"); }

typedef struct {
    const char *name;           // اسم فرمان
    void (*run)(void);          // تابعی که اجرایش می‌کند
} command_t;

static const command_t commands[] = {
    { "on",     cmd_led_on  },
    { "off",    cmd_led_off },
    { "status", cmd_status  },
};

#define COMMAND_COUNT (sizeof(commands) / sizeof(commands[0]))

static void dispatch(const char *word)
{
    for (size_t i = 0; i < COMMAND_COUNT; i++) {
        if (strcmp(word, commands[i].name) == 0) {
            commands[i].run();
            return;
        }
    }
    printf("unknown command: %s\n", word);
}

int main(void)
{
    const char *input[] = { "on", "status", "blink", "off" };

    for (size_t i = 0; i < sizeof(input) / sizeof(input[0]); i++) {
        dispatch(input[i]);
    }
    return 0;
}
  1. سه کار. هر فرمان یک تابع کوچک با امضای یکسان void f(void).
  2. ردیف جدول. یک struct با دو عضو: اسم و اشاره‌گر به تابع. اعلان اشاره‌گر داخل struct دقیقا همان شکل قبلی است. عضو struct را می‌شود به‌صورت typedef هم نوشت؛ اینجا یک‌بار مصرف است و مستقیم نوشتنش خواناتر است.
  3. خود جدول. آرایهٔ static const؛ هر ردیف با { اسم, تابع } پر شده. اسم تابع بدون پرانتز. const باعث می‌شود جدول روی میکروکنترلر در Flash بماند و RAM را اشغال نکند (درس ۳.۵). اشاره‌گر داخل جدول عوض‌شدنی نیست و این عیب نیست؛ مزیت است.
  4. تعداد ردیف‌ها. ماکرو، اندازهٔ کل آرایه را بر اندازهٔ یک عضو تقسیم می‌کند (درس ۲.۷). با اضافه‌کردن ردیف، خودش به‌روز می‌شود.
  5. dispatch. ردیف‌ها را می‌گردد، اسم را با strcmp مقایسه می‌کند و وقتی پیدا شد، commands[i].run() را صدا می‌زند. اگر هیچ ردیفی نخورد، پیام «ناشناخته» می‌دهد. فراموش‌شدن حالت «پیدا نشد» یکی از رایج‌ترین باگ‌هاست. کاربر همیشه چیزی می‌نویسد که تو انتظارش را نداری.
  6. تست. چهار ورودی؛ سومی (blink) در جدول نیست.
$ ./cmd_table
LED is now ON
status: all good
unknown command: blink
LED is now OFF

مرتب‌سازی سفارشی با qsort

کتابخانهٔ استاندارد C خودش یک تابع مرتب‌سازی دارد: qsort در stdlib.h. مشکل: qsort نمی‌داند عضوها چه نوعی‌اند (int؟ struct؟ رشته؟) و نمی‌داند «کوچک‌تر» یعنی چه. پس تابع مقایسه را از تو می‌گیرد؛ یک callback. امضایش ثابت است: دو اشاره‌گر const void * می‌گیرد و int برمی‌گرداند: منفی اگر اولی باید جلوتر باشد، صفر اگر برابرند، مثبت اگر دومی جلوتر باشد.

#include <stdio.h>
#include <stdlib.h>

typedef struct {
    const char *name;
    int mv;
} reading_t;

static int cmp_int(const void *a, const void *b)
{
    int x = *(const int *)a;
    int y = *(const int *)b;
    return (x > y) - (x < y);
}

static int cmp_reading_desc(const void *a, const void *b)
{
    const reading_t *x = a;
    const reading_t *y = b;
    return (y->mv > x->mv) - (y->mv < x->mv);
}

int main(void)
{
    int v[6] = {42, 7, 19, 3, 25, 11};
    reading_t r[4] = {{"ch0", 3120}, {"ch1", 2980}, {"ch2", 3300}, {"ch3", 3050}};

    qsort(v, 6, sizeof v[0], cmp_int);
    for (int i = 0; i < 6; i++) {
        printf("%d ", v[i]);
    }
    printf("\n");

    qsort(r, 4, sizeof r[0], cmp_reading_desc);
    for (int i = 0; i < 4; i++) {
        printf("%s=%d ", r[i].name, r[i].mv);
    }
    printf("\n");
    return 0;
}
  1. مقایسهٔ عددها. qsort آدرس دو عضو را به‌صورت const void * می‌دهد. اول به const int * تبدیل می‌کنیم، بعد با * مقدار را برمی‌داریم. عبارت (x > y) - (x < y) می‌شود -1، 0 یا 1. نوشتن return x - y; وسوسه‌انگیز است ولی اگر x خیلی بزرگ و y خیلی منفی باشد، سرریز int می‌شود (رفتار تعریف‌نشده، درس ۲.۲). این فرمول همیشه امن است.
  2. مقایسهٔ struct ها، نزولی. همان الگو ولی y و x جابه‌جا شده‌اند تا بزرگ‌ترین اول بیاید. const reading_t *x = a; بدون cast نوشته می‌شود چون void * در C خودکار تبدیل می‌شود.
  3. صدا زدن qsort. آرایه، تعداد عضو، اندازهٔ هر عضو (با sizeof v[0]) و شمارهٔ تابع مقایسه. خود qsort هر جا لازم دید مقایسه را صدا می‌زند. اندازهٔ هر عضو لازم است چون qsort نوع را نمی‌شناسد و فقط بایت جابه‌جا می‌کند.
  4. مرتب‌سازی struct ها. همان qsort، فقط با تابع مقایسهٔ دیگر. qsort هیچ تغییری نکرده است.
$ ./sort

ch2=3300 ch0=3120 ch3=3050 ch1=2980
در میکروکنترلر

qsort روی MCU هم کار می‌کند ولی کد کتابخانه فضا می‌گیرد، و اگر آرایه خیلی کوچک است (مثلا ۸ نمونهٔ سنسور) یک مرتب‌سازی ساده خودت کافی است. اهمیت این مثال الگوی آن است: الگوریتم ثابت، رفتار از بیرون.

ساختار عملیات درایور: شبه vtable

اگر چند اشاره‌گر به تابع را در یک struct جمع کنی، به چیزی می‌رسی که یک «واسط» (interface) را نشان می‌دهد: مجموعه‌ای از کارها که هر پیاده‌سازی باید بلد باشد. مثلا یک LED چیزی است که init و set دارد؛ اینکه واقعا روی پایهٔ GPIO باشد یا فقط یک چاپ روی صفحه، برای کسی که آن را استفاده می‌کند مهم نیست.

وقتی می‌خواهی کدت را روی PC تست کنی (درس ۶.۴) یا یک برنامه را روی دو میکروکنترلر مختلف ببری، همین الگو نجاتت می‌دهد: منطق برنامه فقط با «واسط» حرف می‌زند و پشتش هر پیاده‌سازی را می‌شود گذاشت. در زبان‌های شیءگرا به اسم virtual table شناخته می‌شود؛ در C خودت با دست می‌سازی.

#include <stdio.h>

typedef struct {
    void (*init)(void);
    void (*set)(int on);
} led_ops_t;

static void console_init(void)  { printf("console: ready\n"); }
static void console_set(int on) { printf("console: LED %s\n", on ? "ON" : "OFF"); }

static void quiet_init(void)    { }
static void quiet_set(int on)   { (void)on; }

static const led_ops_t console_ops = { console_init, console_set };
static const led_ops_t quiet_ops   = { quiet_init,   quiet_set };

static void blink_twice(const led_ops_t *ops)
{
    ops->init();
    for (int i = 0; i < 2; i++) {
        ops->set(1);
        ops->set(0);
    }
}

int main(void)
{
    blink_twice(&console_ops);
    blink_twice(&quiet_ops);
    printf("done\n");
    return 0;
}
  1. واسط. هر «LED» باید init و set داشته باشد. این struct فقط دو اشاره‌گر است، پس روی MCU هشت بایت جا می‌گیرد.
  2. پیاده‌سازی اول. به‌جای LED واقعی، روی صفحه می‌نویسد. برای تست روی PC ایده‌آل است.
  3. پیاده‌سازی دوم. هیچ کاری نمی‌کند (مثل یک «LED خاموش»). گاهی برای غیرفعال کردن یک قابلیت لازم می‌شود. (void)on; به کامپایلر می‌گوید «پارامتر را عمدا استفاده نکردم»؛ بدون آن -Wextra هشدار می‌دهد.
  4. دو شیء ثابت. هر کدام یک بستهٔ آدرس‌ها. چون const هستند، روی MCU در Flash می‌مانند.
  5. منطق برنامه. blink_twice نمی‌داند LED چیست؛ فقط از بستهٔ ops استفاده می‌کند. هر پیاده‌سازی جدید (مثلا GPIO واقعی) بدون دست‌زدن به blink_twice اضافه می‌شود. این ایده در درس ۵.۷ (لایهٔ HAL) کامل می‌شود.
  6. استفاده. یک بار با console_ops، یک بار با quiet_ops.
$ ./led_ops
console: ready
console: LED ON
console: LED OFF
console: LED ON
console: LED OFF
done

اگر خراب شد چه می‌شود؟ سه تلهٔ اصلی

تله ۱: امضای ناسازگار

اگر اشاره‌گری که برای int f(int) ساخته‌ای، به تابعی با امضای دیگر اشاره کند، کامپایلر باید هشدار بدهد. ببین:

#include <stdio.h>

static int add(int a, int b) { return a + b; }

int main(void)
{
    int (*op)(int) = add;       // op یک ورودی می‌گیرد، add دو ورودی
    printf("%d\n", op(1));
    return 0;
}

sig_mismatch.c: In function 'main':
sig_mismatch.c:7:22: error: initialization of 'int (*)(int)' from incompatible pointer type 'int (*)(int,  int)' [-Werror=incompatible-pointer-types]

ما هشدار را به‌عمد به خطا تبدیل کردیم (-Werror=incompatible-pointer-types)؛ بدون آن، بسته به نسخهٔ gcc فقط هشدار می‌گیری و برنامه ساخته می‌شود. پیام می‌گوید «اشاره‌گر int (*)(int) را از نوع ناسازگار int (*)(int, int) مقداردهی کردی». (فاصلهٔ اضافه در پیام از خود gcc است.)

با cast ساکتش نکن

اگر از سر تنبلی بنویسی op = (int (*)(int))add;، هشدار ساکت می‌شود ولی مشکل سر جایش است: op(1) تابعی را صدا می‌زند که دو ورودی انتظار دارد و ورودی دوم را از جای خالی می‌خواند. این «رفتار تعریف‌نشده» است (درس ۶.۲): ممکن است هزار بار درست کار کند و روز تحویل پروژه خراب شود. هر cast روی اشاره‌گر به تابع باید دلیل مشخص داشته باشد.

تله ۲: صدا زدن اشاره‌گر NULL یا مقدارنداده

اگر اشاره‌گر به تابع NULL باشد و صدایش بزنی، پردازنده به آدرس ۰ می‌پرد. روی PC برنامه با Segmentation fault می‌میرد. روی میکروکنترلر Cortex-M آدرس ۰ معمولا محتوای معتبری دارد (جدول وقفه یا Flash) و برنامه خودش را بی‌صدا خراب می‌کند یا به HardFault می‌رود؛ پیدا کردنش سخت است. راه‌حل: قبل از صدا زدنِ callback اختیاری، NULL بودنش را بررسی کن.

#include <stdio.h>

typedef void (*button_cb_t)(int pin);

static button_cb_t on_press = NULL;     // در ابتدا هیچ‌کس ثبت‌نام نکرده

static void button_register(button_cb_t cb)
{
    on_press = cb;
}

static void button_event(int pin)
{
    if (on_press != NULL) {
        on_press(pin);
    } else {
        printf("no handler for pin %d\n", pin);
    }
}

static void my_handler(int pin)
{
    printf("pressed: pin %d\n", pin);
}

int main(void)
{
    button_event(13);
    button_register(my_handler);
    button_event(13);
    return 0;
}
  1. نوع callback دکمه. تابعی که شمارهٔ پایه را می‌گیرد.
  2. ثبت‌نام‌شده‌ای وجود ندارد. اشاره‌گر سراسری‌ایستا با مقدار اولیهٔ NULL. صریح NULL نوشتن نشان می‌دهد «خالی بودن» یک حالت مجاز طراحی است، نه فراموشی. (سراسری‌ها به‌هر حال صفر می‌شوند؛ درس ۳.۵.)
  3. ثبت‌نام. فقط آدرس تابع کاربر را ذخیره می‌کند. همین الگو در HAL و درایورها هست: «هر وقت اتفاقی افتاد، این را صدا بزن».
  4. رویداد. اول بررسی می‌کند کسی ثبت‌نام کرده یا نه. فقط اگر کرده، صدایش می‌زند. بدون if فراخوانیِ NULL رخ می‌دهد و برنامه خراب می‌شود. هزینهٔ این if چند سیکل است؛ هزینهٔ حذفش یک ساعت دیباگ.
  5. دو بار رویداد. بار اول هیچ‌کس گوش نمی‌دهد؛ بار دوم my_handler اجرا می‌شود.
$ ./button_cb
no handler for pin 13
pressed: pin 13

تله ۳: callback را ثبت کردی، ولی جعبه‌اش مرد

در بخش context دیدی که یک void * می‌فرستیم. اگر callback فقط همان لحظه صدا زده شود (مثل for_each)، اشکالی ندارد که context یک متغیر محلی باشد. ولی اگر callback را ثبت کنی تا بعدا صدا زده شود (دکمه، تایمر، UART)، آدرسی که می‌دهی باید تا آن زمان زنده بماند. اگر آدرس متغیر محلیِ تابعی را بدهی که تمام شده، اشاره‌گر «آویزان» می‌شود (درس ۳.۲ و ۳.۵). برای callback های ثبت‌شده، context را static یا سراسری یا از یک ساختار بلندعمر بساز.

اشاره‌گر به تابع در قلب میکروکنترلر: vector table

تا اینجا هر چه دیدی روی PC هم کار می‌کرد. ولی جالب اینجاست که همین ایده، ستون فقرات هر میکروکنترلر ARM Cortex-M است. وقتی پردازنده روشن می‌شود یا یک وقفه می‌رسد (مثلا «دکمه فشرده شد»)، باید بداند به کدام تابع بپرد. جواب در vector table است: آرایه‌ای از آدرس‌ها که در ابتدای Flash قرار دارد. یعنی دقیقا «آرایه‌ای از اشاره‌گر به تابع».

پردازنده هنگام Reset دو کار ساده انجام می‌دهد: کلمهٔ اول را در SP (اشاره‌گر پشته) می‌گذارد و به آدرس کلمهٔ دوم می‌پرد. هنگام وقفه هم شمارهٔ وقفه را به عنوان اندیس در همین جدول به کار می‌برد و به آدرس آن ردیف می‌پرد. کسی «صدایش نمی‌زند»؛ خود سخت‌افزار جدول را می‌خواند و می‌پرد. جزئیات ساختن کامل این جدول در درس ۵.۱، و وقفه‌ها در ۵.۳ می‌آید. اینجا فقط ببین چقدر شبیه دانسته‌هایت است:

#include <stdint.h>

typedef void (*isr_t)(void);

extern uint32_t _estack;                // آدرس پایان RAM؛ linker script می‌سازد

void Reset_Handler(void);
void Default_Handler(void);
void NMI_Handler(void)       __attribute__((weak, alias("Default_Handler")));
void HardFault_Handler(void) __attribute__((weak, alias("Default_Handler")));

__attribute__((section(".isr_vector"), used))
const isr_t vector_table[] = {
    (isr_t)(uintptr_t)&_estack,         // کلمهٔ ۰: SP اولیه
    Reset_Handler,                      // کلمهٔ ۱
    NMI_Handler,                        // کلمهٔ ۲
    HardFault_Handler,                  // کلمهٔ ۳
};

void Default_Handler(void)
{
    for (;;) { }                        // وقفهٔ بی‌صاحب: همین‌جا بمان
}
  1. نوع ISR. هر تابع وقفه void f(void) است؛ ISR یعنی «تابع سرویس وقفه» (درس ۵.۳).
  2. نماد از بیرون. _estack را linker script (درس ۵.۱) تعریف می‌کند؛ ما فقط آدرسش را می‌خواهیم، با &.
  3. تابع‌ها و اسم مستعار ضعیف. Reset_Handler را خودمان جایی می‌نویسیم. NMI_Handler و HardFault_Handler «ضعیف» و مستعار Default_Handler هستند: اگر کسی تابع همنامی بنویسد، آن جایگزین می‌شود؛ وگرنه Default_Handler اجرا می‌شود. این‌طوری وقفه‌ای که هنوز برایش تابعی ننوشته‌ای، به جای پرش به آدرس تصادفی به یک حلقهٔ امن می‌رود. جزئیات weak در بخش بعد.
  4. مکان جدول. section(".isr_vector") به لینکر می‌گوید این آرایه را در ابتدای Flash بگذار. const یعنی در Flash بماند. used یعنی «حذفش نکن، حتی اگر کسی صدایش نزند». لینکر فقط چیزی را نگه می‌دارد که کسی به آن ارجاع بدهد. جدول وقفه را هیچ تابعی ارجاع نمی‌دهد؛ سخت‌افزار می‌خواندش. بدون used ممکن است بهینه‌ساز آن را دور بیندازد.
  5. خود جدول. یک آرایهٔ isr_t؛ همان الگوی جدول فرمان. کلمهٔ اول یک آدرس داده (SP) است؛ برای اینکه در آرایهٔ اشاره‌گر به تابع بنشیند، از uintptr_t (درس ۲.۲) عبور داده و cast شده. این cast به‌صورت مشخص لازم است چون در سخت‌افزار همهٔ کلمه‌ها یک جنس (۳۲ بیت) هستند، ولی C بین آدرس داده و آدرس تابع فرق می‌گذارد.
  6. تابع پیش‌فرض. یک حلقهٔ بی‌نهایت خالی. اگر برنامه اینجا گیر کرد، دیباگر می‌بینی کدام وقفه فراموش شده.
زیر کاپوت: چرا آدرس‌ها فرد هستند؟

Cortex-M4 فقط دستورهای Thumb را اجرا می‌کند. در آدرسی که برای پرش می‌دهی، کمترین بیت (بیت ۰) نشان می‌دهد «حالت Thumb». اگر ۰ باشد، پردازنده فکر می‌کند حالت ARM قدیمی است که در Cortex-M وجود ندارد و HardFault می‌دهد. خوشبختانه لینکر خودش بیت ۰ را برای تابع‌های Thumb روشن می‌کند؛ برای همین در جدول آدرس‌های فرد می‌بینی (مثل 0x08000201). در درس ۵.۱ این را عمل می‌کنیم.

تابع «ضعیف»: callback های آمادهٔ HAL

کتابخانهٔ HAL شرکت ST را دیده‌ای که تابع‌هایی مثل HAL_GPIO_EXTI_Callback(uint16_t GPIO_Pin) دارد؟ کاربر بدون دست‌زدن به کد HAL، همین تابع را در برنامهٔ خودش دوباره می‌نویسد و لینکر نسخهٔ او را انتخاب می‌کند. مکانیزمش weak (ضعیف) است: تابعی که با __attribute__((weak)) علامت خورده، یعنی «من نسخهٔ پیش‌فرض‌ام؛ اگر کسی نسخهٔ جدی‌تری بسازد، او را ترجیح بده». ببین روی PC (gcc/Linux) هم کار می‌کند:

#ifndef HAL_H
#define HAL_H

void hal_button_callback(int pin);      // callback: کاربر می‌تواند جایگزین کند
void hal_irq(int pin);                  // از سخت‌افزار (ISR) صدا زده می‌شود

#endif

#include <stdio.h>
#include "hal.h"

__attribute__((weak)) void hal_button_callback(int pin)
{
    printf("default: pin %d ignored\n", pin);
}

void hal_irq(int pin)
{
    hal_button_callback(pin);
}

#include <stdio.h>
#include "hal.h"

void hal_button_callback(int pin)       // نسخهٔ کاربر
{
    printf("user: pin %d handled\n", pin);
}

int main(void)
{
    hal_irq(13);
    return 0;
}
  1. نسخهٔ ضعیف. پیش‌فرضِ بی‌اثر؛ فقط چیزی چاپ می‌کند.
  2. کد HAL. هر وقت رویدادی رسید، hal_button_callback را با نامش صدا می‌زند. HAL نمی‌داند کدام نسخه اجرا می‌شود؛ لینکر تصمیم می‌گیرد.
  1. نسخهٔ قوی. تابعی هم‌نام و هم‌امضا بدون weak. لینکر این را ترجیح می‌دهد. اگر دو تعریف «قوی» هم‌نام وجود داشته باشد، لینکر multiple definition می‌دهد (درس ۴.۲). «ضعیف» فقط در برابر «قوی» کوتاه می‌آید.
  2. صدا زدن HAL. تابع کاربر اجرا می‌شود، نه پیش‌فرض.
$ gcc -std=c11 -Wall -Wextra -o app main.c hal.c
$ ./app
user: pin 13 handled

اگر main.c فقط hal_irq(13) را صدا می‌زد و نسخهٔ خودش را نمی‌نوشت، خروجی default: pin 13 ignored می‌شد.

قاعدهٔ اسم‌گذاری

در STM32 HAL تقریبا همهٔ callback ها HAL_..._Callback نام دارند و __weak هستند (__weak در ARM همان __attribute__((weak)) است). اگر اسم را دقیقا مثل هدر ننویسی (یک حرف اشتباه)، کامپایلر اعتراض نمی‌کند و تابع تو هیچ‌وقت صدا زده نمی‌شود، چون نسخهٔ ضعیف جایش را می‌گیرد. اولین جایی که باید نگاه کنی: املای اسم.

یک نمونهٔ ESP32 که نشان می‌دهد task در FreeRTOS فقط یک تابع با امضای void f(void *) است و آدرسش را به xTaskCreate می‌دهی. (این قطعه در محیط ما ساخته نمی‌شود؛ مطابق ESP-IDF نسخهٔ ۵ نوشته شده است.)

#include "freertos/FreeRTOS.h"
#include "freertos/task.h"
#include "driver/gpio.h"

#define LED_GPIO GPIO_NUM_2

static void blink_task(void *arg)
{
    (void)arg;                                  // این task پارامتر نمی‌خواهد
    gpio_set_direction(LED_GPIO, GPIO_MODE_OUTPUT);
    int level = 0;

    for (;;) {                                  // task هرگز تمام نمی‌شود
        level = !level;
        gpio_set_level(LED_GPIO, level);
        vTaskDelay(pdMS_TO_TICKS(500));         // نیم ثانیه صبر
    }
}

void app_main(void)
{
    xTaskCreate(blink_task, "blink", 2048, NULL, 5, NULL);
}
  1. امضای task. در FreeRTOS هر task یک تابع با شکل void f(void *) است. پارامتر همان «context» این درس است.
  2. راه‌اندازی. پایهٔ LED را خروجی می‌کند. (روی بسیاری از بردهای DevKit ارزان LED به GPIO2 وصل است؛ برد تو ممکن است فرق کند.)
  3. حلقهٔ بی‌پایان. هر ۵۰۰ میلی‌ثانیه LED را برعکس می‌کند. vTaskDelay به زمان‌بند اجازه می‌دهد تا وقتی این task منتظر است، task های دیگر اجرا شوند. task نباید return کند؛ حلقهٔ for (;;) همان «super loop» درس ۱.۴ است.
  4. ساخت task. اولین آرگومان، اسم تابع بدون پرانتز است؛ یعنی «شمارهٔ تلفن». بعد نام (برای دیباگ)، اندازهٔ پشته (بایت)، پارامتر (NULL)، اولویت و دستگیره (که اینجا نمی‌خواهیم).

آزمون این درس

فرق op = add; و op = add(1, 2); (با فرض اینکه op اشاره‌گر به تابع است) چیست؟

  1. هیچ فرقی ندارند؛ هر دو آدرس add را می‌گذارند
  2. اولی آدرس تابع را می‌گذارد؛ دومی تابع را اجرا می‌کند و نتیجه (یک عدد) را می‌خواهد بگذارد که با نوع op نمی‌خواند
  3. اولی تابع را اجرا می‌کند و دومی فقط آدرس را می‌گیرد
  4. هر دو خطای کامپایل می‌دهند
پرانتز یعنی «زنگ بزن». add(1, 2) یک int است (عدد ۳)، نه آدرس؛ گذاشتن عدد در اشاره‌گر به تابع هشدار یا خطا می‌دهد.

کدام اعلان، f را «اشاره‌گر به تابعی که یک int می‌گیرد و int برمی‌گرداند» می‌کند؟

  1. int *f(int);
  2. int (*f) int;
  3. int (*f)(int);
  4. (int *f)(int);
پرانتز دور *f نشان می‌دهد «ابتدا f اشاره‌گر است»؛ بعدش (int) می‌گوید به تابعی با یک ورودی int و نوع برگشتی سمت چپ (int).

خروجی این کد چیست؟
int (*p)(int) = twice; int (*q)(int) = p; p = thrice; printf("%d", q(5));
(twice(x) برابر 2x و thrice(x) برابر 3x است.)

  1. ۱۵
  2. ۵
  3. کامپایل نمی‌شود
  4. ۱۰
مثل متغیرهای int (درس ۲.۱)، q = p فقط یک‌بار آدرس فعلی را کپی می‌کند. q هنوز به twice اشاره می‌کند: 2×5 = 10.

کدام کد در زمان اجرا خطرناک است (حتی اگر بی‌هشدار کامپایل شود)؟

  1. void (*cb)(int); و بعد بلافاصله cb(3);
  2. void (*cb)(int) = handler; و بعد cb(3);
  3. if (cb != NULL) { cb(3); }
  4. void (*cb)(int) = NULL;
اشاره‌گر بدون مقدار اولیه آشغال دارد؛ فراخوانی‌اش پردازنده را به آدرس تصادفی می‌پراند. همیشه مقدار اولیه بده (تابع معتبر یا NULL) و قبل از صدا زدنِ callback اختیاری، NULL را بررسی کن.

در Cortex-M هنگام Reset، پردازنده با «کلمهٔ اول» و «کلمهٔ دوم» vector table چه می‌کند؟

  1. به هر دو کلمه می‌پرد، اول و بعد دوم
  2. هر دو کلمه را با مقدار تازه بازنویسی می‌کند
  3. کلمهٔ اول را در SP می‌گذارد و به آدرسی که در کلمهٔ دوم است می‌پرد (Reset_Handler)
  4. مستقیم به main می‌پرد
کلمهٔ ۰ = SP اولیه، کلمهٔ ۱ = آدرس Reset_Handler. این تابع (که در درس ۵.۱ می‌نویسیم) آماده‌سازی‌ها را انجام می‌دهد و بعد main را صدا می‌زند.

تابعی در کتابخانهٔ HAL با __weak اعلان شده و تو نسخهٔ خودت را با همان اسم در main.c نوشته‌ای. چه می‌شود؟

  1. لینکر multiple definition می‌دهد
  2. لینکر نسخهٔ قوی (تو) را نگه می‌دارد و نسخهٔ ضعیف را کنار می‌گذارد
  3. هر کدام زودتر لینک شد برنده است
  4. هر دو نسخه یکی‌یکی اجرا می‌شوند
«ضعیف» یعنی «پیش‌فرض». لینکر نسخهٔ قوی را ترجیح می‌دهد. همین مکانیزم اجازه می‌دهد callback های HAL را بدون تغییر دادن کد کتابخانه جایگزین کنی.

تمرین‌ها

تمرین ۱: ماشین‌حساب با جدول اشاره‌گر

یک تابع find_op می‌خواهیم که یک نماد ('+'، '-'، '*'، '/') بگیرد و اشاره‌گر به تابع مناسب را برگرداند؛ برای نماد ناشناخته NULL.

  1. پیش‌بینی: برای ورودی‌های + - * / % با 8 و 2 چه خروجی‌ای انتظار داری؟ (% پشتیبانی نمی‌شود.)
  2. حل: چهار تابع add، sub، mul، divide با یک typedef مشترک بنویس. divide اگر مقسوم‌علیه صفر بود، 0 برگرداند.
  3. تغییر: اگر find_op نتیجه را NULL برگرداند و بدون بررسی صدایش بزنی چه می‌شود؟ کد را طوری بنویس که این اتفاق نیفتد.
راهنمایی

از switch استفاده کن که به‌جای عدد، اشاره‌گر return می‌کند. اعلان نوع برگشتی را با binop_t بنویس تا خوانا بماند.

چه باید ببینی؟ 
$ ./calc

8 * 2 = 16
8 / 2 = 4

جواب کامل با توضیح 
#include <stdio.h>

typedef int (*binop_t)(int, int);

static int add(int a, int b)    { return a + b; }
static int sub(int a, int b)    { return a - b; }
static int mul(int a, int b)    { return a * b; }
static int divide(int a, int b) { return b == 0 ? 0 : a / b; }

static binop_t find_op(char symbol)
{
    switch (symbol) {
    case '+': return add;
    case '-': return sub;
    case '*': return mul;
    case '/': return divide;
    default:  return NULL;
    }
}

int main(void)
{
    const char symbols[] = {'+', '-', '*', '/', '%'};

    for (int i = 0; i < 5; i++) {
        binop_t op = find_op(symbols[i]);
        if (op == NULL) {
            printf("8 %c 2 : unsupported\n", symbols[i]);
        } else {
            printf("8 %c 2 = %d\n", symbols[i], op(8, 2));
        }
    }
    return 0;
}
  1. نوع مشترک. همهٔ عمل‌ها این امضا را دارند.
  2. چهار تابع. divide اسمش عمدا div نیست، چون div در stdlib.h تعریف شده و تداخل ایجاد می‌کند. اسم کوتاه و عمومی برای تابع بگذاری، با کتابخانهٔ استاندارد یا درایور دیگران برخورد می‌کند. اگر divide هم هنوز مشکل داشت، پیشوند ماژول بگذار (calc_divide).
  3. find_op. نوع برگشتی binop_t است. هر case اشاره‌گر را برمی‌گرداند. default یعنی «نماد ناشناخته»: NULL.
  4. بررسی NULL. فقط اگر اشاره‌گر معتبر بود صدایش می‌زنیم. در برنامهٔ واقعی نمادها را کاربر می‌دهد. فرض کردن اینکه همیشه معتبر است، همان باگی است که در تله ۲ دیدی.

int *fp(int) = square;

  2. int (*fp)(int) = square(3);
  3. int r = *fp(5); (فرض: fp به‌درستی تعریف شده است)

الف: پرانتز را کجا گذاشته‌اند؟ ب: «پرانتز یعنی زنگ بزن». پ: * و ( ) کدام تقدم بیشتری دارد؟

تمرین ۳: جدول وقفهٔ شبیه‌سازی‌شده روی PC

می‌خواهیم رفتار vector table را روی PC شبیه‌سازی کنیم. آرایه‌ای از ۴ اشاره‌گر به تابع بساز: ردیف ۱ = button_handler، ردیف ۲ = timer_handler؛ ردیف‌های ۰ و ۳ را پر نکن (NULL می‌مانند). تابع irq_fire(unsigned n) باید ردیف n را صدا بزند، ولی اگر ردیف NULL بود یا n خارج از جدول بود، default_handler را صدا بزند.

  1. پیش‌بینی: برای دنبالهٔ 1, 2, 1, 3, 7 چه چاپ می‌شود؟
  2. حل: برنامه را با مقداردهی نامزد (designated initializer، مثل [1] = ...) بنویس.
  3. سخت‌افزار: روی یک STM32 واقعی، چرا جدول const است و چرا نباید ردیف NULL بماند؟ به‌جای NULL چه بگذاریم؟
راهنمایی

الف: هر 1 شمارنده را زیاد می‌کند. ب: مقداردهی نامزد را در درس ۲.۷ دیدی. پ: به «پرش به آدرس ۰» در تله ۲ فکر کن.

چه باید ببینی؟

button pressed (2)

جواب کامل با توضیح 
#include <stdio.h>

#define IRQ_COUNT 4u

typedef void (*handler_t)(void);

static int button_count = 0;

static void default_handler(void) { printf("unexpected interrupt\n"); }
static void timer_handler(void)   { printf("timer tick\n"); }
static void button_handler(void)
{
    button_count++;
    printf("button pressed (%d)\n", button_count);
}

static const handler_t vector_table[IRQ_COUNT] = {
    [1] = button_handler,
    [2] = timer_handler,
};

static void irq_fire(unsigned n)
{
    handler_t h = default_handler;

    if (n < IRQ_COUNT && vector_table[n] != NULL) {
        h = vector_table[n];
    }
    h();
}

int main(void)
{
    const unsigned events[] = {1, 2, 1, 3, 7};

    for (unsigned i = 0; i < sizeof(events) / sizeof(events[0]); i++) {
        irq_fire(events[i]);
    }
    return 0;
}
  1. اندازه و نوع. ۴ ردیف؛ 4u بی‌علامت است تا با n از یک جنس مقایسه شود (درس ۲.۲).
  2. شمارندهٔ دکمه. فقط برای اینکه ببینیم handler حالت نگه می‌دارد.
  3. جدول. فقط ردیف‌های ۱ و ۲ پر شده‌اند؛ بقیه به‌صورت خودکار صفر (NULL) می‌شوند. اگر ردیف‌ها را با مقداردهی نامزد پر کنی، ردیف‌های نانوشته صفر می‌شوند (درس ۲.۷). در MCU واقعی «صفر» یعنی پرش به آدرس ۰؛ پس باید Default_Handler بگذاری.
  4. irq_fire. اول h را به default_handler می‌گذارد؛ فقط اگر n در محدوده بود و ردیف خالی نبود، جایگزین می‌شود. ترتیب شرط مهم است: اول بازه، بعد دسترسی به آرایه. عملگر && اگر سمت چپ نادرست باشد، سمت راست را اجرا نمی‌کند (short-circuit، درس ۲.۳). پس برای n = 7 هرگز به vector_table[7] نمی‌رسد که خارج آرایه است.
$ ./irq_sim
button pressed (1)
timer tick
button pressed (2)
unexpected interrupt
unexpected interrupt

جواب قسمت پ: جدول const است تا در Flash بماند و RAM نگیرد و کسی (باگ) رویش ننویسد. ردیف NULL یعنی اگر آن وقفه فعال شود، پردازنده به آدرس ۰ می‌پرد و برنامه خراب می‌شود. به‌جای NULL باید Default_Handler بگذاری (مثل بخش vector table). در C استاندارد const برای vector_table با مقداردهی نامزد و NULL هیچ مشکلی ندارد؛ فقط تصمیم طراحی است.

حرف مربی

تقریبا همه در همین درس دو جا گیر می‌کنند: نوشتن اعلان (پرانتز دور *name را فراموش می‌کنند) و فرق «نام تابع» با «صدا زدن تابع» (پرانتز). اگر اعلان‌ها را خسته‌کننده یافتی، از typedef استفاده کن و هیچ‌وقت شرمنده نباش؛ متخصص‌ها هم همین را می‌کنند. اگر می‌خواهی مطمئن شوی درس را فهمیده‌ای، ببین می‌توانی برای دوستت توضیح بدهی «چرا vector table فقط یک آرایه است». اگر توانستی، بقیهٔ فصل ۵ برایت روان می‌شود.

خلاصه یک‌دقیقه‌ای

  • تابع در Flash آدرس دارد. اشاره‌گر به تابع این آدرس را در RAM نگه می‌دارد (روی MCU: ۴ بایت).
  • اعلان: int (*op)(int, int);. پرانتز دور *op ضروری است. با typedef خوانا کن.
  • نام تابع بدون پرانتز = آدرس؛ با پرانتز = اجرا. فراخوانی: op(7, 3).
  • callback: تابعی که تو می‌نویسی و دیگری صدایش می‌زند. برای حالت نگه‌داشتن از پارامتر void *ctx استفاده کن.
  • الگوهای رایج: جدول فرمان (ردیف = اسم + تابع)، ساختار عملیات درایور (شبه‌vtable)، qsort.
  • تله‌ها: امضای ناسازگار (با cast ساکتش نکن)، صدا زدن NULL یا مقدارنداده، آویزان‌شدن context ثبت‌شده.
  • vector table در Cortex-M آرایه‌ای از آدرس‌هاست: کلمهٔ ۰ = SP اولیه، کلمهٔ ۱ = Reset_Handler. تابع weak را نسخهٔ قوی‌تر جایگزین می‌کند (callback های HAL).
  • در FreeRTOS هر task یک تابع void f(void *) است و آدرسش را به xTaskCreate می‌دهی.
