تا حالا هر بار کدی نوشتی، برد را فلش کرده‌ای و با چشم نگاه کرده‌ای «درست کار می‌کند؟». این روش برای پنج خط کد خوب است، ولی برای هزار خط، مثل چک‌کردن پل با راه‌رفتن روی آن است. در این درس یاد می‌گیری کد میکروکنترلر را روی رایانهٔ خودت، در چند میلی‌ثانیه و بدون هیچ سخت‌افزاری تست کنی: یک فریم‌ورک کوچک می‌نویسیم، بافر حلقوی و ماشین حالت درس‌های قبل را با آن می‌آزماییم، سخت‌افزار را با «مانکن آزمایش تصادف» (mock) جایگزین می‌کنیم و در آخر می‌بینیم تست‌ها چقدر از کد را دیده‌اند.

🎯 بعد از این درس می‌توانی

  • بگویی چرا بیشتر منطق برنامهٔ MCU را باید روی PC تست کرد و چه چیزهایی را نمی‌شود
  • یک هدر تست به سبک Unity بنویسی و بفهمی TEST_ASSERT_... و RUN_TEST زیر کاپوت چه می‌کنند
  • تست را با الگوی «آماده‌کن ← اجرا کن ← بسنج» (AAA) و با اسم‌های گویا بنویسی
  • با روش TDD یک تابع کوچک را «قرمز ← سبز ← مرتب» بسازی
  • بافر حلقوی و ماشین حالت debounce را تست کنی، از جمله مرزها و سرریز شمارنده
  • وابستگی سخت‌افزاری را با اشاره‌گر تابع یا پیوند جایگزین کنی (fake، stub، mock)
  • با gcov پوشش تست را بخوانی و یک فایل CI ساده بنویسی

🧰 پیش‌نیاز و وسایل

  • درس‌های ۴.۵ (بافر حلقوی) و ۴.۶ (ماشین حالت): همان کدها را اینجا تست می‌کنیم
  • درس ۴.۳ (اشاره‌گر به تابع) و ۴.۲ (پروژهٔ چندفایلی و make)
  • درس ۶.۳ (پرچم‌های هشدار) و ۶.۲ (رفتار تعریف‌نشده)؛ ASan/UBSan در ۶.۱
  • gcc، make و gcov روی PC (Linux، macOS، یا WSL/MSYS2 روی Windows)
  • سخت‌افزار لازم نیست

ایدهٔ اصلی: قطعه را روی میز آزمایش امتحان کن

سازندهٔ ماشین قبل از سوار کردن ترمز روی ماشین، آن را روی یک میز آزمایش می‌گذارد: فشار می‌دهد، گرم می‌کند، ده هزار بار می‌فشارد. اگر ترمز خراب باشد، اینجا می‌فهمد و لازم نیست ماشین را در جاده بشکند. حتی حالت‌هایی را که در جاده خطرناک است (روغن تمام شده) روی میز به‌راحتی می‌سازد.

مثال از زندگی روزمره

در آزمایش تصادف، به‌جای آدم واقعی یک مانکن پشت فرمان می‌نشانند که همه‌جا سنسور دارد. مانکن را می‌شود صدها بار برخورد داد و «اعداد» را خواند. در تست نرم‌افزار هم به‌جای سخت‌افزار واقعی (سنسور، UART) یک مانکن نرم‌افزاری می‌گذاریم که هر جوابی که ما بخواهیم بدهد و ثبت کند چه چیزی از آن خواسته شده است.

تست واحد (unit test) یعنی همین: یک «واحد» کوچک کد (یک تابع یا یک ماژول مثل بافر حلقوی) را جدا از بقیه، با ورودی‌های مشخص اجرا می‌کنیم و خروجی را با جواب درست مقایسه می‌کنیم. هر بار که کد را عوض کنی، همهٔ تست‌ها دوباره در چند ثانیه اجرا می‌شوند و اگر چیزی که قبلا درست کار می‌کرد خراب شود (به این می‌گویند رگرسیون)، همان لحظه می‌فهمی.

چرا روی PC؟ و چه چیزی را نمی‌شود روی PC تست کرد؟

کد MCU را روی خودِ برد هم می‌شود تست کرد، ولی هر بار باید کامپایل، فلش، ریست، و خروجی را از UART خواند: دقیقه‌ها. روی PC همان کار چند میلی‌ثانیه است. مزیت‌ها:

  • سرعت: صدها تست در یک ثانیه؛ پس هر بار که ذخیره می‌کنی اجرایشان می‌کنی.
  • ابزار بهتر: gdb، ASan و UBSan (درس‌های ۶.۱ و ۶.۲)، gcov و valgrind روی PC هست؛ روی MCU ندارید یا سخت است.
  • حالت‌های خطا: سنسور خراب، UART که پر شده، بایت ناقص: روی PC یک خط کد است، روی میز کار پیدا کردنش سخت.
  • خودکار: بدون سخت‌افزار می‌شود در سرور (CI) هم اجرا کرد، بارها و بی‌خسته.
تست روی PC چه چیزی را نمی‌بیند؟

PC یک MCU دیگر است: int و اشاره‌گر ۶۴ بیتی، long روی Linux و macOS ۶۴ بیت (روی Windows ۳۲ بیت) (درس ۲.۲)، کامپایلر و بهینه‌ساز متفاوت، حافظهٔ فراوان. تست PC نمی‌تواند اثبات کند که رجیستر درست تنظیم شده، زمان‌بندی کافی است، یا وقفه سر وقت می‌آید. راه حل: منطق را از سخت‌افزار جدا کن (درس‌های ۵.۷ و ۴.۳)، منطق را روی PC تست کن، و برای لایهٔ سخت‌افزاری چند تست روی برد نگه دار (بخش آخر). تست PC «کافی» نیست، ولی «لازم» است.

قدم صفر: بدون هیچ فریم‌ورکی

ساده‌ترین تست چیست؟ یک main که تابع را صدا می‌زند و با if نتیجه را چک می‌کند. تابعی می‌خواهیم که دو عدد ۸ بیتی را جمع کند و اگر از ۲۵۵ گذشت روی ۲۵۵ بماند (جمع اشباع‌شده، درس ۴.۷). این نسخهٔ اول ساده‌لوحانه است:

#include <stdio.h>
#include <stdint.h>

/* نسخهٔ اول: ساده‌لوحانه */
static uint8_t sat_add_u8(uint8_t a, uint8_t b)
{
    return (uint8_t)(a + b);
}

int main(void)
{
    int failures = 0;
    if (sat_add_u8(10, 20) != 30) { printf("FAIL 1\n"); failures++; }
    if (sat_add_u8(200, 100) != 255) { printf("FAIL 2\n"); failures++; }
    printf("%d failures\n", failures);
    return failures;
}
  1. تابع تحت‌آزمون. جمع را در uint8_t برمی‌گرداند. ۲۰۰ + ۱۰۰ = ۳۰۰ اما در یک بایت جا نمی‌شود و «دور می‌زند». این باگ عمدی است تا ببینیم تست آن را می‌گیرد.
  2. دو بررسی دستی. اگر نتیجه با انتظار نخواند، پیام چاپ می‌کنیم و شمارندهٔ شکست را زیاد می‌کنیم. این کار ساده است ولی هر بررسی چهار خط تکراری می‌خواهد و پیام‌ها فقط می‌گویند «FAIL 2»؛ نمی‌گویند چه عددی انتظار داشتیم و چه عددی گرفتیم.
  3. کد خروج. برنامه failures را برمی‌گرداند: صفر یعنی همه‌چیز خوب. سرور CI فقط همین را نگاه می‌کند. قرارداد پایه‌ای همهٔ تست‌ها: «کد خروج ۰ = موفق، غیرصفر = شکست» (درس ۱.۴).
$ gcc -std=c11 -Wall -Wextra -o manual manual.c
$ ./manual
FAIL 2
1 failures

(کد خروج برنامه ۱ است؛ echo $? آن را نشان می‌دهد.) کار می‌کند، ولی ناراحت‌کننده است: فقط شمارهٔ بررسی را می‌گوید و اگر ۵۰ بررسی داشتیم، باید خودمان بشماریم. یک فریم‌ورک باید این کارها را بکند: اسم بدهد به هر تست، اولین شکست را با «انتظار / نتیجه» گزارش کند، و بقیهٔ تست‌ها را ادامه بدهد.

فریم‌ورک کوچک: minitest.h

فریم‌ورک‌های واقعی برای C زیادند. معروف‌ترین آن‌ها Unity از پروژهٔ ThrowTheSwitch است: فقط چند فایل کوچک (unity.c و unity.h و unity_internals.h)، بدون وابستگی، و روی خودِ MCU هم اجرا می‌شود؛ همراهش Ceedling (سیستم ساخت که تست‌ها را پیدا می‌کند و برنامهٔ اصلی‌شان را خودش می‌سازد) و CMock (که از روی فایل هدر شما mock تولید می‌کند) می‌آیند. دیگران: CppUTest، cmocka، Check و Google Test (مخصوص C++). سایت رسمی Unity: throwtheswitch.org.

برای اینکه «جادو» نباشد، در این درس خودمان یک هدر بسیار کوچک به همان سبک می‌نویسیم. اسم ماکروها را عمدا مثل Unity گذاشته‌ایم (TEST_ASSERT_EQUAL_INT، RUN_TEST، setUp، tearDown) تا وقتی روزی Unity واقعی را برداشتی، همه‌چیز آشنا باشد. ایدهٔ اصلی: هر تست یک تابع void f(void) است؛ اگر یک TEST_ASSERT شکست بخورد، پیام را چاپ می‌کند و با longjmp از همان تست بیرون می‌پرد؛ بقیهٔ تست‌ها ادامه می‌یابند.

setjmp و longjmp چیست؟

setjmp(env) یک «نشانگر کتاب» در کد می‌گذارد (اولین بار صفر برمی‌گرداند). longjmp(env, 1) از هر عمق تودرتوی توابع به همان نشانگر می‌پرد و این بار setjmp عدد ۱ برمی‌گرداند. برای فریم‌ورک تست عالی است، چون assert می‌تواند داخل تابع کمکی یا حتی داخل mock باشد و باز هم تست جاری فوری تمام شود. در کد محصول (MCU) از آن دوری کن: قانون ۱ ناسا (درس ۶.۳) آن را ممنوع می‌کند.

#ifndef MINITEST_H
#define MINITEST_H

#include <setjmp.h>
#include <stdarg.h>
#include <stdio.h>
#include <string.h>

/* فریم‌ورک کوچک به سبک Unity. هر فایل test_*.c یک برنامهٔ مستقل است. */
typedef struct {
    const char *name;       /* تست جاری */
    unsigned    run;        /* چند تست اجرا شد */
    unsigned    failed;     /* چند تست رد شد */
    int         failed_now; /* تست جاری رد شده؟ */
    jmp_buf     env;        /* نقطهٔ بازگشت بعد از شکست */
} mt_state_t;

static mt_state_t mt;

void setUp(void);           /* تست‌نویس تعریفشان می‌کند (مثل Unity) */
void tearDown(void);

static inline _Noreturn void mt_fail(const char *file, int line, const char *fmt, ...)
{
    va_list ap;
    printf("%s:%d:%s:FAIL: ", file, line, mt.name);
    va_start(ap, fmt);
    vprintf(fmt, ap);
    va_end(ap);
    printf("\n");
    mt.failed_now = 1;
    longjmp(mt.env, 1);     /* بقیهٔ همین تست اجرا نمی‌شود */
}

static inline void mt_run(const char *file, int line, const char *name, void (*fn)(void))
{
    mt.name = name;
    mt.run++;
    mt.failed_now = 0;
    if (setjmp(mt.env) == 0) {
        setUp();
        fn();
    }
    tearDown();
    if (mt.failed_now) {
        mt.failed++;
    } else {
        printf("%s:%d:%s:PASS\n", file, line, name);
    }
}

static inline int mt_end(void)
{
    printf("-----------------------\n%u Tests %u Failures\n%s\n",
           mt.run, mt.failed, (mt.failed == 0U) ? "OK" : "FAIL");
    return (mt.failed == 0U) ? 0 : 1;
}

#define TEST_BEGIN()   ((void)0)
#define RUN_TEST(fn)   mt_run(__FILE__, __LINE__, #fn, (fn))
#define TEST_END()     mt_end()

#define TEST_ASSERT_TRUE(c) \
    do { if (!(c)) { mt_fail(__FILE__, __LINE__, "Expected TRUE: %s", #c); } } while (0)
#define TEST_ASSERT_FALSE(c) \
    do { if (c) { mt_fail(__FILE__, __LINE__, "Expected FALSE: %s", #c); } } while (0)
#define TEST_ASSERT_NULL(p) \
    do { if ((p) != NULL) { mt_fail(__FILE__, __LINE__, "Expected NULL: %s", #p); } } while (0)
#define TEST_ASSERT_NOT_NULL(p) \
    do { if ((p) == NULL) { mt_fail(__FILE__, __LINE__, "Expected not NULL: %s", #p); } } while (0)

#define TEST_ASSERT_EQUAL_INT(exp, act) \
    do { long long e_ = (long long)(exp), a_ = (long long)(act); \
         if (e_ != a_) { mt_fail(__FILE__, __LINE__, "Expected %lld Was %lld", e_, a_); } } while (0)
#define TEST_ASSERT_EQUAL_HEX(exp, act) \
    do { unsigned long long e_ = (unsigned long long)(exp), a_ = (unsigned long long)(act); \
         if (e_ != a_) { mt_fail(__FILE__, __LINE__, "Expected 0x%llX Was 0x%llX", e_, a_); } } while (0)
#define TEST_ASSERT_EQUAL_STRING(exp, act) \
    do { const char *e_ = (exp), *a_ = (act); \
         if (strcmp(e_, a_) != 0) { mt_fail(__FILE__, __LINE__, "Expected \"%s\" Was \"%s\"", e_, a_); } } while (0)
#define TEST_ASSERT_EQUAL_MEMORY(exp, act, n) \
    do { if (memcmp((exp), (act), (n)) != 0) { mt_fail(__FILE__, __LINE__, "Memory differs (%s)", #act); } } while (0)
#define TEST_FAIL_MESSAGE(msg) mt_fail(__FILE__, __LINE__, "%s", (msg))

#endif /* MINITEST_H */
  1. نگهبان include. مثل هر هدر (درس ۴.۲).
  2. هدرهای لازم. setjmp.h برای پرش، stdarg.h برای تابعی با آرگومان متغیر (مثل printf)، string.h برای strcmp و memcmp.
  3. وضعیت فریم‌ورک. اسم تست جاری، شمارندهٔ اجراشده‌ها و ردشده‌ها، و env: همان نشانگر کتاب setjmp. هر فایل test_*.c برنامهٔ مستقل است، پس یک نمونهٔ static کافی است.
  4. setUp و tearDown. فقط اعلان شده‌اند؛ نویسندهٔ تست تعریفشان می‌کند. setUp قبل از هر تست اجرا می‌شود (صحنه‌چینی) و tearDown بعد از آن. اگر صحنه را هر بار از نو نچینی، تست‌ها به هم گره می‌خورند (تمرین ۲).
  5. گزارش شکست. «فایل:خط:اسم‌تست:FAIL: پیام» را چاپ می‌کند (قالبی که ویرایشگرها می‌فهمند)، علامت می‌زند که تست رد شد و با longjmp بیرون می‌پرد. _Noreturn (C11) یعنی این تابع برنمی‌گردد. static inline یعنی اگر تستی از این تابع استفاده نکرد، هشدار «تابع بلااستفاده» نمی‌آید و -Werror نمی‌شکند (درس ۶.۳).
  6. اجرای یک تست. اسم را ثبت می‌کند، setjmp می‌گذارد و داخل آن setUp و بعد تست را اجرا می‌کند (پس assert داخل setUp هم مجاز است و longjmp به یک jmp_buf معتبر می‌پرد). بعد از شکست، اجرا از همان setjmp (این بار با مقدار ۱) به tearDown می‌رسد. آخر: PASS یا شمارش ردشده. tearDown حتی بعد از شکست اجرا می‌شود؛ پس منابع گم نمی‌شوند.
  7. جمع‌بندی و ماکروهای اجرا. mt_end شمار تست‌ها را چاپ می‌کند و کد خروج ۰ یا ۱ می‌دهد؛ همان قرارداد CI. RUN_TEST(fn) اسم تابع را با #fn به رشته تبدیل می‌کند (درس ۴.۱) و شمارهٔ خط را هم می‌فرستد.
  8. بررسی درست/غلط و NULL. هر ماکرو شرط را داخل do { } while (0) می‌پیچد (ماکروی امن) و متن شرط را با #c در پیام می‌آورد.
  9. مقایسهٔ عدد. هر دو طرف یک بار حساب و در long long (یا بی‌علامت) ریخته می‌شوند؛ پیام «Expected … Was …» می‌گوید انتظار چه بود و چه شد. اگر مستقیم (exp) != (act) می‌نوشتیم، ماکرو آرگومان‌ها را دوبار ارزیابی می‌کرد و TEST_ASSERT_EQUAL_INT(1, next()) دوبار next() را صدا می‌زد (تلهٔ ماکرو، درس ۴.۱).
  10. رشته، حافظه و شکست دستی. strcmp و memcmp محتوا را مقایسه می‌کنند (نه آدرس را!). TEST_FAIL_MESSAGE برای وقتی که شرط را خودت جداگانه بررسی کرده‌ای.

حالا فریم‌ورک را روی همان تابع جمع اشباع‌شده امتحان می‌کنیم. این‌بار هر تست یک رفتار با اسم روشن است. ابتدا هدر کوچک و بعد فایل تست:

#ifndef SATMATH_H
#define SATMATH_H

#include <stdint.h>

/* جمع اشباع‌شده: اگر از ۲۵۵ بگذرد روی ۲۵۵ می‌ماند (دور نمی‌زند) */
uint8_t sat_add_u8(uint8_t a, uint8_t b);

#endif /* SATMATH_H */

#include "minitest.h"
#include "satmath.h"

void setUp(void) {}
void tearDown(void) {}

static void test_small_values_add_normally(void)
{
    TEST_ASSERT_EQUAL_INT(30, sat_add_u8(10, 20));
}

static void test_zero_is_neutral(void)
{
    TEST_ASSERT_EQUAL_INT(200, sat_add_u8(200, 0));
}

static void test_result_saturates_at_255(void)
{
    TEST_ASSERT_EQUAL_INT(255, sat_add_u8(200, 100));
}

static void test_exactly_255_is_not_clipped(void)
{
    TEST_ASSERT_EQUAL_INT(255, sat_add_u8(250, 5));
}

int main(void)
{
    TEST_BEGIN();
    RUN_TEST(test_small_values_add_normally);
    RUN_TEST(test_zero_is_neutral);
    RUN_TEST(test_result_saturates_at_255);
    RUN_TEST(test_exactly_255_is_not_clipped);
    return TEST_END();
}
  1. هدر فریم‌ورک و ماژول تحت‌آزمون.
  2. setUp و tearDown خالی. این تابع‌ها حالت ندارند و لازم نیست چیزی آماده کنند؛ ولی باید تعریف شوند تا لینک شود.
  3. چهار تست، هر کدام یک ادعا. اسم‌ها جمله‌اند («جمع اشباع در ۲۵۵ می‌ماند»)، نه test1. وقتی یکی رد شد، فقط از اسمش می‌فهمی چه چیزی خراب است. چهارمی (۲۵۰ + ۵ = ۲۵۵) مرز را تست می‌کند: دقیقا رسیدن به سقف نباید «اشباع» حساب شود. باگ‌ها در مرزها لانه می‌کنند (قانون off-by-one).
  4. main = فهرست تست‌ها. هر تست با RUN_TEST ثبت می‌شود و کد خروج فریم‌ورک برمی‌گردد.

الگوی AAA و اسم تست

یک تست خوب سه بخش دارد؛ به آن AAA می‌گویند:

  1. Arrange (آماده‌کن): صحنه را بچین: متغیرها، ورودی‌ها، mock. setUp بخشی از این کار را برای همه می‌کند.
  2. Act (اجرا کن): یک کار را انجام بده؛ معمولا یک تابع را صدا بزن.
  3. Assert (بسنج): نتیجه را با انتظار مقایسه کن.

و پنج ویژگی تست خوب را به‌خاطر بسپار (به آن FIRST می‌گویند): سریع (Fast)، مستقل از تست‌های دیگر (Independent)، تکرارپذیر با هر بار همان نتیجه (Repeatable)، خودبسنده در گزارش یعنی فقط PASS/FAIL و نه «نگاه کن و خودت تشخیص بده» (Self-validating)، و به‌موقع یعنی همراه یا قبل از کد نوشته شود (Timely).

اسم تست، مستند کد است

اسم را مثل جمله بنویس: «چه چیزی، تحت چه شرطی، چه نتیجه‌ای». test_full_buffer_rejects_new_byte بهتر از test_put_2 است. اسم خوب یعنی وقتی CI قرمز شد، بدون باز کردن فایل می‌فهمی چه رفتاری شکسته است. و یک تست، یک دلیل برای شکستن: اگر یک تست ده ASSERT دربارهٔ چند رفتار دارد، وقتی رد شد نمی‌دانی مشکل کجاست.

TDD: اول تست، بعد کد

TDD (توسعهٔ تست‌محور) یک عادت است: اول تستی می‌نویسی که رد می‌شود، بعد کمترین کد را می‌نویسی که آن را قبول کند، بعد مرتب می‌کنی (تست‌ها ضامن‌اند که چیزی خراب نشود). به آن چرخهٔ «قرمز، سبز، مرتب» می‌گویند.

ببین با همان جمع اشباع‌شده چه شد. اول تست‌ها را نوشتیم (همان چهار تست بالا) و نسخهٔ ساده‌لوحانهٔ (uint8_t)(a + b) را زیرشان گذاشتیم. این خروجی اجرای واقعی است:

TDD همیشه لازم نیست

TDD برای توابع «حسابی» و ماژول‌های منطقی (پارسر، بافر، FSM، ریاضی) عالی است. برای کد ورود و خروج سخت‌افزار (تنظیم رجیستر) سخت‌تر است. اهمیت اصلی‌اش این است که کد را قابل‌تست طراحی می‌کند: تابعی که هم‌زمان رجیستر می‌خواند و منطق دارد، تست نمی‌شود؛ پس ناچار آن‌ها را جدا می‌کنی، و طراحی بهتر می‌شود.

تست واقعی ۱: بافر حلقوی

از همان بافر حلقوی درس ۴.۵ استفاده می‌کنیم؛ کد را بدون هیچ تغییری آورده‌ایم (اگر یادت رفته، بازش کن):

ringbuf.h و ringbuf.c (بدون تغییر از درس ۴.۵) 
#ifndef RINGBUF_H
#define RINGBUF_H

#include <stdbool.h>
#include <stdint.h>

#ifndef RB_SIZE
#define RB_SIZE 8U              /* ظرفیت بافر؛ باید توان ۲ باشد */
#endif
#define RB_MASK (RB_SIZE - 1U)

_Static_assert((RB_SIZE & RB_MASK) == 0U && RB_SIZE <= 32768U,
               "RB_SIZE must be a power of two, at most 32768");

typedef struct {
    volatile uint8_t  data[RB_SIZE];
    volatile uint16_t head;     /* شمارندهٔ نوشتن: فقط تولیدکننده عوضش می‌کند */
    volatile uint16_t tail;     /* شمارندهٔ خواندن: فقط مصرف‌کننده عوضش می‌کند */
} ringbuf_t;

void     rb_init(ringbuf_t *rb);
uint16_t rb_count(const ringbuf_t *rb);
bool     rb_is_empty(const ringbuf_t *rb);
bool     rb_is_full(const ringbuf_t *rb);
bool     rb_put(ringbuf_t *rb, uint8_t byte);
bool     rb_get(ringbuf_t *rb, uint8_t *out);

#endif /* RINGBUF_H */

#include "ringbuf.h"

void rb_init(ringbuf_t *rb)
{
    rb->head = 0;
    rb->tail = 0;
}

uint16_t rb_count(const ringbuf_t *rb)
{
    return (uint16_t)(rb->head - rb->tail);
}

bool rb_is_empty(const ringbuf_t *rb)
{
    return rb->head == rb->tail;
}

bool rb_is_full(const ringbuf_t *rb)
{
    return rb_count(rb) == RB_SIZE;
}

bool rb_put(ringbuf_t *rb, uint8_t byte)
{
    if (rb_is_full(rb)) {
        return false;                       // جا نیست؛ بایت جدید را نمی‌پذیریم
    }
    rb->data[rb->head & RB_MASK] = byte;    // اول داده را بنویس
    rb->head++;                             // بعد اعلام کن که تازه چیزی آمده
    return true;
}

bool rb_get(ringbuf_t *rb, uint8_t *out)
{
    if (rb_is_empty(rb)) {
        return false;
    }
    *out = rb->data[rb->tail & RB_MASK];    // اول داده را بردار
    rb->tail++;                             // بعد جا را آزاد اعلام کن
    return true;
}

چه چیزهایی را باید تست کرد؟ یک فهرست خوب از «مرزها» می‌سازیم: بافر خالی، بافر پر، رسیدن به انتهای آرایه و برگشتن به اول (wrap)، و چیزی که در درس ۴.۵ فقط اشاره شد: شمارندهٔ ۱۶ بیتی که از ۶۵۵۳۵ به ۰ برمی‌گردد. آن را فقط بعد از هزاران عملیات می‌بینی؛ روی برد شاید هفته‌ها بعد، ولی روی PC یک حلقه‌ی ۷۰۰۰۰ تایی، چند میلی‌ثانیه است:

#include "minitest.h"
#include "ringbuf.h"

static ringbuf_t rb;

void setUp(void)
{
    rb_init(&rb);               // هر تست با یک بافر تازه شروع می‌کند
}

void tearDown(void) {}

/* کمکی: n بایت با مقدار first, first+1, ... می‌گذارد */
static void fill(uint8_t first, unsigned n)
{
    for (unsigned i = 0; i < n; i++) {
        TEST_ASSERT_TRUE(rb_put(&rb, (uint8_t)(first + i)));
    }
}

static void test_new_buffer_is_empty(void)
{
    TEST_ASSERT_TRUE(rb_is_empty(&rb));
    TEST_ASSERT_FALSE(rb_is_full(&rb));
    TEST_ASSERT_EQUAL_INT(0, rb_count(&rb));
}

static void test_bytes_come_out_in_same_order(void)
{
    uint8_t out = 0;
    fill(10, 3);
    TEST_ASSERT_EQUAL_INT(3, rb_count(&rb));
    TEST_ASSERT_TRUE(rb_get(&rb, &out));
    TEST_ASSERT_EQUAL_INT(10, out);
    TEST_ASSERT_TRUE(rb_get(&rb, &out));
    TEST_ASSERT_EQUAL_INT(11, out);
    TEST_ASSERT_TRUE(rb_get(&rb, &out));
    TEST_ASSERT_EQUAL_INT(12, out);
    TEST_ASSERT_TRUE(rb_is_empty(&rb));
}

static void test_full_buffer_rejects_new_byte(void)
{
    fill(0, RB_SIZE);
    TEST_ASSERT_TRUE(rb_is_full(&rb));
    TEST_ASSERT_FALSE(rb_put(&rb, 99));
    TEST_ASSERT_EQUAL_INT(RB_SIZE, rb_count(&rb));      // چیزی عوض نشد
}

static void test_get_on_empty_leaves_output_untouched(void)
{
    uint8_t out = 0x5A;
    TEST_ASSERT_FALSE(rb_get(&rb, &out));
    TEST_ASSERT_EQUAL_HEX(0x5A, out);
}

static void test_wraps_around_the_end_of_storage(void)
{
    uint8_t out = 0;
    fill(0, RB_SIZE);                       // پر
    for (unsigned i = 0; i < 3; i++) {      // سه‌تا خالی می‌کنیم
        TEST_ASSERT_TRUE(rb_get(&rb, &out));
    }
    fill(100, 3);                           // این سه‌تا از ابتدای آرایه شروع می‌شوند
    TEST_ASSERT_TRUE(rb_is_full(&rb));
    for (unsigned i = 3; i < RB_SIZE; i++) {
        TEST_ASSERT_TRUE(rb_get(&rb, &out));
        TEST_ASSERT_EQUAL_INT(i, out);
    }
    for (uint8_t v = 100; v < 103; v++) {
        TEST_ASSERT_TRUE(rb_get(&rb, &out));
        TEST_ASSERT_EQUAL_INT(v, out);
    }
    TEST_ASSERT_TRUE(rb_is_empty(&rb));
}

static void test_counters_survive_16_bit_wrap(void)
{
    uint8_t out = 0;
    for (uint32_t i = 0; i < 70000U; i++) { // بیش از ۶۵۵۳۶ عملیات
        TEST_ASSERT_TRUE(rb_put(&rb, (uint8_t)i));
        TEST_ASSERT_TRUE(rb_get(&rb, &out));
        TEST_ASSERT_EQUAL_INT((uint8_t)i, out);
    }
    TEST_ASSERT_TRUE(rb_is_empty(&rb));
    fill(1, RB_SIZE);                       // هنوز ظرفیت کامل دارد
    TEST_ASSERT_TRUE(rb_is_full(&rb));
}

int main(void)
{

    RUN_TEST(test_new_buffer_is_empty);
    RUN_TEST(test_bytes_come_out_in_same_order);
    RUN_TEST(test_full_buffer_rejects_new_byte);
    RUN_TEST(test_get_on_empty_leaves_output_untouched);
    RUN_TEST(test_wraps_around_the_end_of_storage);
    RUN_TEST(test_counters_survive_16_bit_wrap);

}

  2. تابع کمکی. fill چند بایت پشت‌سرهم می‌گذارد و هر بار می‌سنجد که rb_put موفق بوده.
  3. حالت آغازین و ترتیب FIFO. بافر نو خالی است؛ بایت‌ها به همان ترتیبی که رفتند بیرون می‌آیند.
  4. بافر پر. RB_SIZE بایت می‌گیرد؛ بایت بعدی رد می‌شود و شمارنده هنوز ۸ است.
  5. خواندن از بافر خالی. rb_get false برمی‌گرداند و *out دست‌نخورده می‌ماند (۰x5A همان می‌ماند). این یک «قرارداد» است که تست می‌کند؛ تماس‌گیرنده روی آن حساب می‌کند (درس ۶.۳).
  6. چرخش در انتهای آرایه. پر می‌کنیم، ۳ تا برمی‌داریم، ۳ تا دیگر می‌گذاریم: این سه بایت به ابتدای آرایه می‌روند و بافر دوباره پر می‌شود. اینجا ماسک & RB_MASK کار می‌کند. اگر فراموشش کنیم، این تست (و UBSan) می‌گیرد؛ در «تست را تست کن» می‌بینی.
  7. دور زدن شمارنده‌ها. ۷۰۰۰۰ بار یک بایت می‌گذاریم و برمی‌داریم؛ head و tail (۱۶ بیتی) از ۶۵۵۳۵ عبور می‌کنند و همه‌چیز باید درست بماند. قاعدهٔ CERT به نام INT30-C (درس ۶.۳): دور زدن بی‌علامت باید آگاهانه باشد. این تست ثابت می‌کند تفریق head - tail با دور زدن هم درست کار می‌کند.
  8. main. شش تست ثبت می‌شوند.

تست واقعی ۲: ماشین حالت debounce

ماشین‌های حالت فوق‌العاده تست‌پذیرند: ورودی‌ها یک دنباله‌اند و خروجی‌ها رویدادهایی که می‌شود شمرد. کد debounce دکمهٔ درس ۴.۶ را برمی‌داریم (بدون تغییر):

button.h و button.c (بدون تغییر از درس ۴.۶) 
#ifndef BUTTON_H
#define BUTTON_H

#include <stdbool.h>

#ifndef BTN_STABLE_TICKS
#define BTN_STABLE_TICKS 3U     /* چند tick پشت‌سرهم یکسان بماند تا معتبر باشد */
#endif

typedef enum {
    BTN_RELEASED,           /* رها و پایدار */
    BTN_PRESS_CANDIDATE,    /* تازه پایین دیده شد؛ منتظر تأیید */
    BTN_PRESSED,            /* پایین و پایدار */
    BTN_RELEASE_CANDIDATE   /* تازه بالا دیده شد؛ منتظر تأیید */
} btn_state_t;

typedef enum {
    BTN_EV_NONE,
    BTN_EV_PRESS,           /* یک بار، لحظهٔ فشرده شدن معتبر */
    BTN_EV_RELEASE          /* یک بار، لحظهٔ رها شدن معتبر */
} btn_event_t;

typedef struct {
    btn_state_t state;
    unsigned count;         /* چند نمونهٔ یکسان پشت‌سرهم دیده‌ایم */
} button_t;

void button_init(button_t *b);
btn_event_t button_step(button_t *b, bool raw_pressed);   /* هر tick یک بار */
const char *button_state_name(btn_state_t s);

#endif /* BUTTON_H */

#include "button.h"

void button_init(button_t *b)
{
    b->state = BTN_RELEASED;
    b->count = 0;
}

btn_event_t button_step(button_t *b, bool raw_pressed)
{
    btn_event_t ev = BTN_EV_NONE;

    switch (b->state) {
    case BTN_RELEASED:
        if (raw_pressed) {
            b->state = BTN_PRESS_CANDIDATE;
            b->count = 1;
        }
        break;

    case BTN_PRESS_CANDIDATE:
        if (!raw_pressed) {
            b->state = BTN_RELEASED;            // فقط نویز بود
        } else if (++b->count >= BTN_STABLE_TICKS) {
            b->state = BTN_PRESSED;
            ev = BTN_EV_PRESS;                  // معتبر شد
        }
        break;

    case BTN_PRESSED:
        if (!raw_pressed) {
            b->state = BTN_RELEASE_CANDIDATE;
            b->count = 1;
        }
        break;

    case BTN_RELEASE_CANDIDATE:
        if (raw_pressed) {
            b->state = BTN_PRESSED;             // پرش دکمه، هنوز پایین است
        } else if (++b->count >= BTN_STABLE_TICKS) {
            b->state = BTN_RELEASED;
            ev = BTN_EV_RELEASE;
        }
        break;
    }
    return ev;
}

const char *button_state_name(btn_state_t s)
{
    static const char *const names[] = {
        "RELEASED", "PRESS_CANDIDATE", "PRESSED", "RELEASE_CANDIDATE"
    };
    return names[s];
}

ایدهٔ کار: یک تابع کمکی به‌نام feed رشته‌ای از صفر و یک ("0111000": یک=دکمه پایین) را tick به tick به ماشین می‌دهد و رویدادها را می‌شمارد. تست‌ها همه به شکل «این دنباله را بده؛ اینقدر PRESS و اینقدر RELEASE بگیر» می‌شوند. نتیجه خیلی خواناست:

#include "minitest.h"
#include "button.h"

static button_t btn;
static unsigned presses;
static unsigned releases;

void setUp(void)
{
    button_init(&btn);
    presses = 0;
    releases = 0;
}

void tearDown(void) {}

/* کمکی: رشتهٔ '0'/'1' را tick به tick به دکمه می‌دهد و رویدادها را می‌شمارد */
static void feed(const char *pattern)
{
    for (unsigned i = 0; pattern[i] != '\0'; i++) {
        btn_event_t ev = button_step(&btn, pattern[i] == '1');
        if (ev == BTN_EV_PRESS) {
            presses++;
        } else if (ev == BTN_EV_RELEASE) {
            releases++;
        }
    }
}

static void test_starts_released_without_events(void)
{
    TEST_ASSERT_EQUAL_INT(BTN_RELEASED, btn.state);
    feed("0000");
    TEST_ASSERT_EQUAL_INT(0, presses + releases);
}

static void test_short_noise_is_ignored(void)
{
    feed("01010100");
    TEST_ASSERT_EQUAL_INT(0, presses);
    TEST_ASSERT_EQUAL_INT(BTN_RELEASED, btn.state);
}

static void test_press_needs_exactly_the_stable_count(void)
{
    for (unsigned i = 0; i < BTN_STABLE_TICKS - 1U; i++) {
        feed("1");
    }
    TEST_ASSERT_EQUAL_INT(0, presses);          // یکی کم است
    feed("1");
    TEST_ASSERT_EQUAL_INT(1, presses);          // همین‌جا معتبر شد
    TEST_ASSERT_EQUAL_INT(BTN_PRESSED, btn.state);
}

static void test_holding_does_not_repeat_the_event(void)
{
    feed("0");
    for (unsigned i = 0; i < 50; i++) {
        feed("1");
    }
    TEST_ASSERT_EQUAL_INT(1, presses);
    TEST_ASSERT_EQUAL_INT(0, releases);
}

static void test_bounce_while_pressed_is_not_a_release(void)
{
    feed("111");
    feed("0110");                                // پرش کوتاه وسط فشار
    TEST_ASSERT_EQUAL_INT(1, presses);
    TEST_ASSERT_EQUAL_INT(0, releases);
}

static void test_full_cycle_twice(void)
{

    feed("0111000");

    TEST_ASSERT_EQUAL_INT(2, releases);
    TEST_ASSERT_EQUAL_INT(BTN_RELEASED, btn.state);

typedef struct {
    const char *pattern;
    unsigned    presses;
    unsigned    releases;
} scenario_t;

static void test_table_of_scenarios(void)
{
    static const scenario_t rows[] = {
        { "",            0, 0 },
        { "1",           0, 0 },
        { "111",         1, 0 },
        { "1101110",     1, 0 },
        { "111000",      1, 1 },
        { "11100100",    1, 0 },

  1. وضعیت مشترک و setUp. دکمه و دو شمارنده هر بار صفر می‌شوند.
  2. تابع feed. رشته را کاراکتر به کاراکتر ورودی خام می‌کند و رویدادها را می‌شمارد. این یک «زبان کوچک تست» است: feed("0111000") از هر شرح فارسی گویاتر است.
  3. شروع و نویز. بی‌ورودی بی‌رویداد؛ پرش‌های تک‌تیکی هیچ رویدادی نمی‌سازند. کل هدف debounce همین است.
  4. مرز دقیق. با BTN_STABLE_TICKS - 1 نمونهٔ پایین هنوز رویدادی نیست؛ با یکی بیشتر، PRESS. از ثابت خود هدر استفاده کرده‌ایم، نه عدد ۳؛ اگر ثابت را ۵ کنی، تست درست می‌ماند.
  5. نگه‌داشتن و پرش. ۵۰ tick پایین‌ماندن فقط یک رویداد می‌دهد؛ یک لحظه صفر شدن وسط فشار، رها شدن حساب نمی‌شود.
  6. دو چرخهٔ کامل و اسم حالت‌ها. ماشین به حالت اول برمی‌گردد. تست اسم حالت‌ها برای بخش «پوشش» است.
  7. تست جدولی. هر سطر یک سناریو (دنباله + نتیجه) است. اگر سطری شکست خورد، شمارهٔ سطر و رشته را در پیام می‌آوریم. افزودن سناریو یعنی افزودن یک خط، نه یک تابع. بیشتر تست‌های ماشین حالت و پارسر همین‌طورند.
  8. main. هشت تست ثبت می‌شود.

وابستگی سخت‌افزاری: mock و seam

ماژول‌های بالا خالص بودند و به هیچ سخت‌افزاری نیاز نداشتند. ولی درایور یک سنسور روی I2C چطور؟ روی PC که I2C نداریم! راه حل: در نقطه‌ای که کد به سخت‌افزار می‌رسد یک درز (seam) بگذار، جایی که بتوانی بدون عوض‌کردن کد اصلی، چیز دیگری را وارد کنی. مثل پریز برق: دستگاه فقط به «پریز» وصل است و برایش مهم نیست پشت دیوار شبکهٔ شهری است یا یک ژنراتور.

مثال: دوبلور

در فیلم، صحنهٔ خطرناک را «دوبلور» (stunt double) انجام می‌دهد؛ بازیگر اصلی سالم می‌ماند و کارگردان همان صحنه را می‌گیرد. به همین دلیل اسم عمومی این چیزها test double است. چند نوع دارد و بین آدم‌ها اسم‌ها کمی قاطی می‌شود:

نوعچه می‌کندمثال
dummyفقط برای پرکردن پارامتر؛ هیچ‌وقت استفاده نمی‌شودNULL یا اشاره‌گر بی‌مصرف
stubجواب‌های حاضرآماده می‌دهد تا کد ما را به مسیر دلخواه ببرد«خواندن رجیستر همیشه ۰x58 برمی‌گرداند»
spyثبت می‌کند چه‌کسی با چه آرگومانی صدایش زدشمارندهٔ calls و last_reg
mockمثل spy ولی انتظارها را خودش می‌داند و ناسازگاری را اعلام می‌کند (ابزار CMock/cmocka)«انتظار دارم دقیقا یک بار با آدرس ۰x76 صدا زده شود»
fakeنسخهٔ ساده ولی واقعا کارکنیک EEPROM ساختگی با آرایهٔ RAM که هم می‌نویسد و هم می‌خواند

در عمل نام «mock» را برای همهٔ این‌ها به‌کار می‌برند؛ آنچه ما می‌نویسیم ترکیب stub و spy است. مهم فهمیدن کار است، نه اسم.

سه راه برای ساختن درز داریم:

  1. اشاره‌گر تابع (زمان اجرا): ماژول به‌جای صدا زدن مستقیم I2C، از یک struct از اشاره‌گر تابع (bus_ops_t) استفاده می‌کند؛ درس ۴.۳ و ۵.۷. برد یکی می‌دهد، تست یکی دیگر. بهترین انتخاب برای درایورها.
  2. جایگزینی هنگام لینک: تابعی را فقط اعلان می‌کنی (hal_delay_ms) و فایل پیاده‌سازی را برای تست نمی‌سازی؛ فایل تست تعریف دیگری از همان نام می‌دهد. GNU ld گزینهٔ --wrap و نمادهای weak (درس ۵.۱) هم دارد.
  3. پیش‌پردازنده: #ifdef UNIT_TEST داخل کد اصلی. آخرین انتخاب؛ چون کدی که تست می‌کنی با کدی که ارسال می‌شود فرق می‌کند.

حالا مثال واقعی: درایور سنسور با یک تابع sensor_probe. کارش این است که رجیستر شناسهٔ تراشه (آدرس ۰xD0 روی آدرس I2C ۰x76) را بخواند و ببیند مقدارش ۰x60 است (شناسهٔ BME280 در برگهٔ داده) یا نه؛ اگر گذرگاه خطا داد، تا سه بار با ۲ میلی‌ثانیه صبر تلاش کند. اول هدرها:

hal.h: اعلان تابع تأخیر 
#ifndef HAL_H
#define HAL_H

#include <stdint.h>

/* روی برد واقعی در hal_stm32.c پیاده می‌شود؛ روی PC، فایل تست تعریفش می‌کند */
void hal_delay_ms(uint32_t ms);

#endif /* HAL_H */

#ifndef SENSOR_H
#define SENSOR_H

#include <stdint.h>

#define SENSOR_ADDR            0x76U    /* آدرس I2C */
#define SENSOR_REG_ID          0xD0U    /* رجیستر شناسهٔ تراشه */
#define SENSOR_CHIP_ID         0x60U    /* مقداری که باید در آن رجیستر باشد */
#define SENSOR_RETRIES         3U
#define SENSOR_RETRY_DELAY_MS  2U

/* لایهٔ انتقال: هر برد یک نسخه از این تابع می‌دهد (I2C واقعی یا mock) */
typedef struct {
    int   (*read_reg)(void *ctx, uint8_t dev, uint8_t reg, uint8_t *value);  /* ۰ = موفق */
    void   *ctx;
} bus_ops_t;

typedef enum {
    SENSOR_OK = 0,
    SENSOR_ERR_ARG,     /* اشاره‌گر NULL */
    SENSOR_ERR_BUS,     /* خطای ارتباط پس از چند بار تلاش */
    SENSOR_ERR_ID       /* تراشه جواب داد ولی شناسه اشتباه است */
} sensor_status_t;

sensor_status_t sensor_probe(const bus_ops_t *bus);

#endif /* SENSOR_H */
  1. ثابت‌های نام‌دار. آدرس، رجیستر، شناسه، تعداد تلاش و مکث. تست هم از همین‌ها استفاده می‌کند.
  2. درز ۱: bus_ops_t. یک تابع read_reg که با 0 موفقیت را اعلام می‌کند و یک ctx (اشاره‌گر void* به هر داده‌ای که پیاده‌ساز لازم دارد). روی برد واقعی ctx اشاره‌گر به دستگیرهٔ I2C است؛ در تست به mock. پارامتر ctx باعث می‌شود mock بدون متغیر سراسری کار کند: هر نمونه وضعیت خودش را دارد (این همان «دستگیرهٔ مات» درس ۵.۷ است).
  3. وضعیت‌های صریح. به‌جای -1: اشاره‌گر خالی، خطای گذرگاه، شناسهٔ اشتباه. سه چیزی که باید جدا تشخیص داد.
#include "sensor.h"
#include "hal.h"
#include <stddef.h>

sensor_status_t sensor_probe(const bus_ops_t *bus)
{
    if ((bus == NULL) || (bus->read_reg == NULL)) {
        return SENSOR_ERR_ARG;
    }
    for (unsigned attempt = 0U; attempt < SENSOR_RETRIES; attempt++) {
        uint8_t id = 0U;
        if (bus->read_reg(bus->ctx, SENSOR_ADDR, SENSOR_REG_ID, &id) == 0) {
            return (id == SENSOR_CHIP_ID) ? SENSOR_OK : SENSOR_ERR_ID;
        }
        if ((attempt + 1U) < SENSOR_RETRIES) {
            hal_delay_ms(SENSOR_RETRY_DELAY_MS);    // قبل از تلاش بعدی کمی صبر
        }
    }
    return SENSOR_ERR_BUS;
}
  1. دروازه. اشاره‌گر NULL رد می‌شود (برنامه‌نویسی دفاعی، درس ۶.۳).
  2. تلاش با سقف. حداکثر SENSOR_RETRIES بار. اگر گذرگاه موفق بود، همان‌جا شناسه را می‌سنجد و برمی‌گردد. برای شناسهٔ اشتباه دوباره تلاش نمی‌کنیم؛ چون تراشه جواب داده و جواب اشتباه است. حلقهٔ سقف‌دار، قانون ۲ ناسا.
  3. درز ۲: مکث. بین تلاش‌ها hal_delay_ms را صدا می‌زند؛ بعد از آخرین تلاش لازم نیست صبر کند.
  4. خطای گذرگاه. همهٔ تلاش‌ها شکست خوردند.

حالا فایل تست. در آن هر دو درز را پر می‌کنیم: hal_delay_ms را خودمان تعریف می‌کنیم (نه پیاده‌سازی برد) و برای bus_ops_t یک mock می‌سازیم که جواب‌ها را از یک سناریوی از پیش نوشته‌شده می‌خواند:

#include "minitest.h"
#include "sensor.h"
#include "hal.h"

/* ---- درگاه پیوندی (link seam): جایگزین hal_delay_ms واقعی ---- */
static uint32_t total_delay_ms;
void hal_delay_ms(uint32_t ms)
{
    total_delay_ms += ms;               // صبر واقعی نمی‌کنیم؛ فقط ثبت می‌کنیم
}

/* ---- ماکِ گذرگاه: جواب‌ها از یک سناریوی از پیش نوشته‌شده می‌آیند ---- */
#define MAX_CALLS 8U
typedef struct {
    int      result[MAX_CALLS];         /* هر فراخوانی چه کد برگرداند */
    uint8_t  value[MAX_CALLS];          /* و چه مقداری در *value بگذارد */
    unsigned calls;                     /* چند بار صدا زده شد */
    uint8_t  last_dev;                  /* آخرین آرگومان‌ها (جاسوس) */
    uint8_t  last_reg;
} mock_bus_t;

static mock_bus_t mock;
static bus_ops_t  bus;

static int mock_read_reg(void *ctx, uint8_t dev, uint8_t reg, uint8_t *value)
{
    mock_bus_t *m = ctx;
    if (m->calls >= MAX_CALLS) {
        TEST_FAIL_MESSAGE("unexpected extra bus call");
    }
    m->last_dev = dev;
    m->last_reg = reg;
    *value = m->value[m->calls];
    return m->result[m->calls++];
}

void setUp(void)
{
    memset(&mock, 0, sizeof(mock));
    bus.read_reg = mock_read_reg;
    bus.ctx = &mock;
    total_delay_ms = 0;
}

void tearDown(void) {}

static void test_correct_chip_id_gives_ok(void)
{
    mock.value[0] = 0x60;
    TEST_ASSERT_EQUAL_INT(SENSOR_OK, sensor_probe(&bus));
    TEST_ASSERT_EQUAL_INT(1, mock.calls);
    TEST_ASSERT_EQUAL_HEX(0x76, mock.last_dev);     // آدرس درست صدا زده شد؟
    TEST_ASSERT_EQUAL_HEX(0xD0, mock.last_reg);     // رجیستر درست خوانده شد؟
    TEST_ASSERT_EQUAL_INT(0, total_delay_ms);
}

static void test_wrong_chip_id_is_reported(void)
{
    mock.value[0] = 0x58;                           // شناسهٔ تراشهٔ دیگری
    TEST_ASSERT_EQUAL_INT(SENSOR_ERR_ID, sensor_probe(&bus));
    TEST_ASSERT_EQUAL_INT(1, mock.calls);           // برای شناسهٔ غلط تلاش مجدد نمی‌کنیم
}

static void test_retries_after_bus_errors(void)
{
    mock.result[0] = -1;
    mock.result[1] = -1;
    mock.value[2]  = 0x60;                          // بار سوم جواب می‌دهد
    TEST_ASSERT_EQUAL_INT(SENSOR_OK, sensor_probe(&bus));
    TEST_ASSERT_EQUAL_INT(3, mock.calls);
    TEST_ASSERT_EQUAL_INT(2 * SENSOR_RETRY_DELAY_MS, total_delay_ms);
}

static void test_gives_up_after_all_retries_fail(void)
{
    for (unsigned i = 0; i < MAX_CALLS; i++) {
        mock.result[i] = -1;
    }
    TEST_ASSERT_EQUAL_INT(SENSOR_ERR_BUS, sensor_probe(&bus));
    TEST_ASSERT_EQUAL_INT(SENSOR_RETRIES, mock.calls);
    TEST_ASSERT_EQUAL_INT(2 * SENSOR_RETRY_DELAY_MS, total_delay_ms);   // بعد از آخری صبر نمی‌کند
}

static void test_null_arguments_are_rejected(void)
{
    bus_ops_t empty = { NULL, NULL };
    TEST_ASSERT_EQUAL_INT(SENSOR_ERR_ARG, sensor_probe(NULL));
    TEST_ASSERT_EQUAL_INT(SENSOR_ERR_ARG, sensor_probe(&empty));
    TEST_ASSERT_EQUAL_INT(0, mock.calls);
}

int main(void)
{
    TEST_BEGIN();
    RUN_TEST(test_correct_chip_id_gives_ok);
    RUN_TEST(test_wrong_chip_id_is_reported);
    RUN_TEST(test_retries_after_bus_errors);
    RUN_TEST(test_gives_up_after_all_retries_fail);
    RUN_TEST(test_null_arguments_are_rejected);
    return TEST_END();
}
  1. درز پیوندی. تعریف hal_delay_ms در فایل تست است؛ به‌جای صبر واقعی فقط مجموع میلی‌ثانیه‌ها را ثبت می‌کند. اگر واقعا صبر می‌کردیم، تست‌ها کند می‌شدند.
  2. ساختار mock. آرایهٔ کدهای برگشتی و مقدارها (سناریو)، شمارندهٔ فراخوانی و آخرین آرگومان‌ها (جاسوس).
  3. تابع mock. آرگومان‌ها را ثبت می‌کند و جواب بعدی سناریو را می‌دهد؛ اگر بیش از انتظار صدا زده شود، همان‌جا تست را رد می‌کند. TEST_FAIL_MESSAGE از داخل mock هم کار می‌کند، چون longjmp از هر عمقی برمی‌گردد.
  4. setUp. mock را صفر می‌کند و به bus وصل می‌کند؛ مکث ثبت‌شده هم صفر می‌شود.
  5. مسیر خوشحال و شناسهٔ اشتباه. ۰x60 یعنی OK؛ علاوه بر نتیجه، بررسی می‌کنیم درست صدا زده شده باشد (آدرس ۰x76، رجیستر ۰xD0): «بررسی رفتار» فقط با spy ممکن است. ۰x58 (شناسهٔ تراشهٔ مشابه BMP280) رد می‌شود و تلاش دوباره نمی‌کند.
  6. تلاش مجدد و تسلیم. دو خطا و بعد موفقیت: سه فراخوانی و دو مکث. همهٔ تلاش‌ها خطا: SENSOR_ERR_BUS بعد از SENSOR_RETRIES فراخوانی و فقط ۲ مکث. این‌ها سخت‌ترین مسیرها روی سخت‌افزار واقعی‌اند (باید کابل را قطع کنی!) ولی اینجا چند خط.
  7. ورودی‌های NULL. هم اشاره‌گر خالی و هم struct بدون تابع، بدون دست‌زدن به گذرگاه.
  8. main. پنج تست.
mock بیش‌ازحد سخت‌گیر، تست شکننده می‌سازد

اگر تست را طوری بنویسی که «دقیقا این ترتیب از این فراخوانی‌ها»، با هر تغییر بی‌ضرر در پیاده‌سازی رد شود، تست‌ها را دور می‌ریزی. قاعده: رفتار قابل‌مشاهده را بسنج (چه برگشت، چه چیزی به گذرگاه فرستاده شد)، نه جزئیات درونی. و mock را برای کد خودت بساز؛ به‌جای mock کردن کتابخانه‌های بیرونی (مثل HAL شرکت ST)، یک لایهٔ نازک خودت بین آن‌ها بگذار و آن را mock کن.

همه با یک دستور: Makefile

تا اینجا پنج برنامهٔ تست داریم و اگر بخواهیم هر کدام را جدا بسازیم و اجرا کنیم، خسته‌کننده است. یک Makefile (درس ۴.۲) می‌نویسیم که خودش هر فایل test_*.c را پیدا کند؛ افزودن تست جدید فقط ساختن یک فایل است. روش: کدهای اصلی (غیر از تست‌ها) را در یک کتابخانهٔ ایستا (libsrc.a) جمع می‌کنیم؛ هر تست فقط با همان بخش از آن که لازم دارد لینک می‌شود. مثلا test_ringbuf اصلا sensor.o را نمی‌کشد؛ و test_sensor تعریف hal_delay_ms را از فایل خودش می‌گیرد.

CC     = gcc
WARN   = -Wall -Wextra -Wconversion -Wshadow -Wstrict-prototypes -Werror
CFLAGS = -std=c11 $(WARN) -O0 -g --coverage -fsanitize=address,undefined
BUILD  = build

SRCS  := $(filter-out test_%.c,$(wildcard *.c))
OBJS  := $(SRCS:%.c=$(BUILD)/%.o)
TESTS := $(patsubst test_%.c,$(BUILD)/test_%,$(wildcard test_*.c))

all: test coverage

$(BUILD):
	mkdir -p $(BUILD)

$(BUILD)/%.o: %.c $(wildcard *.h) | $(BUILD)
	$(CC) $(CFLAGS) -c $< -o $@

$(BUILD)/libsrc.a: $(OBJS)
	ar rcs $@ $^

$(BUILD)/test_%: test_%.c $(BUILD)/libsrc.a $(wildcard *.h)
	$(CC) $(CFLAGS) $< -L$(BUILD) -lsrc -o $@

test: $(TESTS)
	@fail=0; for t in $(TESTS); do echo "=== $$t"; ./$$t || fail=1; done; exit $$fail

coverage: test
	@echo "=== coverage"
	@gcov -n -o $(BUILD) $(SRCS)

clean:
	rm -rf $(BUILD) *.gcov

.PHONY: all test coverage clean
  1. متغیرها. پرچم‌های سخت‌گیر درس ۶.۳ با -Werror؛ بدون بهینه‌سازی و با اطلاعات دیباگ (-O0 -g)؛ --coverage برای gcov (بخش بعد)؛ و -fsanitize=address,undefined برای ASan و UBSan (درس‌های ۶.۱ و ۶.۲). هر تست، بدون هزینهٔ اضافه، زیر ذره‌بین دو sanitizer اجرا می‌شود؛ روی PC می‌توانی، روی MCU نه.
  2. پیدا کردن فایل‌ها. wildcard فایل‌های .c را می‌گیرد؛ آن‌هایی که با test_ شروع می‌شوند تست‌اند و بقیه «کد اصلی».
  3. هدف پیش‌فرض. make بی‌آرگومان، هم تست می‌کند هم پوشش را می‌گیرد.
  4. پوشهٔ ساخت و قاعدهٔ .o. همهٔ خروجی‌ها در build/ می‌روند تا پوشهٔ اصلی تمیز بماند. اگر هر هدری عوض شود، همه دوباره ساخته می‌شوند (ساده ولی درست).
  5. کتابخانهٔ ایستا. ar فایل‌های .o را در یک آرشیو می‌گذارد.
  6. ساخت هر تست. test_X.c را با آرشیو لینک می‌کند. لینکر از آرشیو فقط فایل‌هایی را برمی‌دارد که نمادی از آن‌ها لازم است.
  7. اجرای همه. هر تست اجرا می‌شود؛ اگر یکی شکست بخورد، ادامه می‌دهیم ولی در آخر با کد غیرصفر خارج می‌شویم. چون یک شکست نباید تست‌های دیگر را پنهان کند؛ ولی CI باید قرمز شود.
  8. پوشش. gcov روی فایل‌های اصلی (نه تست‌ها) اجرا می‌شود. -n یعنی فقط خلاصه بنویس.
  9. پاک‌سازی و اسم‌های ساختگی. .PHONY یعنی all، test و ... اسم فایل نیستند.

پوشش با gcov

«تست‌هایم چقدر از کد را دیده‌اند؟» را پوشش کد (code coverage) جواب می‌دهد. ابزار gcov همراه gcc است و مثل مأمور آمارگیری عمل می‌کند: هنگام اجرا برای هر خط شماره می‌زند چند بار اجرا شد. سه مرحله:

  1. کامپایل با --coverage. کامپایلر کد شمارنده اضافه می‌کند و فایل .gcno (نقشهٔ بلوک‌ها) می‌سازد. مقایسه دقیق خط‌ها به -O0 نیاز دارد.

  3. گزارش. gcov file.c فایل file.c.gcov می‌سازد: هر خط، شمارهٔ اجرا؛ خط ناپیموده با #####.

CI: هر بار push، تست خودکار

CI (یکپارچه‌سازی پیوسته، continuous integration) یعنی یک سرور، هر بار که کدی را در مخزن می‌گذاری، پروژه را از نو می‌سازد، تست می‌زند و نتیجه را می‌گوید. مثل بازرسی که هر بار کارگاه را بازدید می‌کند، حتی اگر تو یادت رفته باشد تست بزنی. برای اینکه CI بتواند کار کند، تست باید با یک دستور و بدون دخالت انسان اجرا شود و با کد خروج جواب بدهد؛ همان‌طور که ساختیم. این نمونهٔ یک فایل برای GitHub Actions است (نام و ساختار مطابق مستندات فعلی GitHub است؛ نسخه‌ها را در مستندات رسمی وارسی کن). فرض کرده‌ایم فایل‌های پروژهٔ این درس (همان‌هایی که با Makefile بالا ساختی؛ نه manual.c «قدم صفر») در پوشهٔ unit/ مخزن هستند. اگر manual.c را کنار آن‌ها بگذاری، هم make آن را جزو کد اصلی می‌شمارد (و پوشش پایین می‌آید) و هم cppcheck شرط‌های همیشه‌درست/غلط آن را گزارش می‌کند؛ پس «قدم صفر» را در پوشهٔ جدا (مثلاً step0/) بساز. نسخهٔ actions/checkout و actions/upload-artifact زود به‌روز می‌شود؛ شمارهٔ نسخه را از مستندات GitHub بگیر:

name: unit-tests
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: unit
    steps:
      - uses: actions/checkout@v4

      - name: Install cppcheck
        run: sudo apt-get update && sudo apt-get install -y cppcheck

      - name: Static analysis
        run: cppcheck -q --error-exitcode=1 --enable=warning,style --inline-suppr .

      - name: Unit tests and coverage
        run: make

      - name: Coverage report
        run: gcov -o build $(ls *.c | grep -v '^test_') > coverage.txt

      - uses: actions/upload-artifact@v4
        with:
          name: coverage
          path: unit/coverage.txt
  1. چه موقع. با هر push و هر pull_request.
  2. یک کار روی Ubuntu. همهٔ دستورها داخل پوشهٔ unit اجرا می‌شوند.
  3. گرفتن کد. مخزن را روی ماشین CI می‌آورد.
  4. تحلیل ایستا. cppcheck (درس ۶.۳) با --error-exitcode=1: اگر هشداری بدهد، مرحله قرمز می‌شود. هشداری که کسی ندیده، وجود ندارد. CI آن را جلوی چشم همه می‌گذارد.
  5. تست و پوشش. همان make که خودت اجرا می‌کنی. اگر تستی رد شود، کد خروج غیرصفر است و کل کار قرمز می‌شود.
  6. ذخیرهٔ گزارش. گزارش پوشش را به‌عنوان فایل پیوست نگه می‌دارد تا بعدا بخوانی.

نکته: اگر CI روی سرور make را با -Werror و ASan اجرا کند، دقیقا همان چیزی است که روی رایانهٔ خودت اجرا کردی؛ «روی سیستم من کار می‌کرد» (که بهانهٔ معروف است) کمتر پیش می‌آید. این‌جا فقط ساختن روی PC را داریم؛ ساختن «فرم واقعی» (با arm-none-eabi-gcc) هم در همین CI می‌تواند یک مرحلهٔ دیگر باشد تا بدانی برای مقصد هم کامپایل می‌شود.

فراتر از PC: روی برد، شبیه‌ساز و HIL

تست PC همه‌چیز نیست. جدول زیر گزینه‌ها را کنار هم می‌گذارد:

روشکجا اجرا می‌شودچه چیزی را می‌گیردهزینه
تست PCرایانهٔ توسعه یا CIمنطق، حالت‌های خطا، مرزهاخیلی کم
شبیه‌ساز (QEMU، Renode)CPU مجازی مقصداندازهٔ int، ترتیب بایت، کد کامپایل‌شدهٔ مقصد؛ بخشی از پریفرال‌هاکم تا متوسط
تست روی خود MCUبرد واقعی؛ نتیجه با UART یا semihosting به PC می‌رسدرجیستر، وقفه، زمان‌بندی واقعی، کامپایلر مقصدمتوسط
HIL (hardware-in-the-loop)برد واقعی وصل به یک دستگاه که ورودی‌ها را می‌سازدکل سیستم: ADC واقعی، موتور، حسگرگران

Unity طوری نوشته شده که روی خود MCU هم اجرا شود (فقط باید خروجی‌اش را به یک UART بفرستی). ESP-IDF خودش کامپوننت Unity را همراه دارد؛ برای راه‌اندازی، به بخش «Unit Testing» مستندات ESP-IDF نگاه کن. برای STM32 معمولا منطق را در فایل‌های مستقل از HAL نگه می‌دارند و روی PC تست می‌کنند؛ لایهٔ پریفرال را روی برد یا با شبیه‌ساز.

قانون کاربردی

منطق را در فایل‌هایی بنویس که هیچ #include ای از HAL یا رجیستر نداشته باشند (مثل ringbuf.c). این فایل‌ها هم روی PC و هم روی MCU کامپایل می‌شوند و تست PC آن‌ها را کاملا می‌سنجد. سخت‌افزار در فایل‌های جدا و نازک بماند.

در STM32 و ESP32 یعنی چه؟

  • همان کد، دو دنیا. ringbuf.c، button.c و sensor.c بدون هیچ تغییر روی STM32 (با arm-none-eabi-gcc) و ESP32 (با ESP-IDF) هم کامپایل می‌شوند؛ چون فقط به stdint.h و stdbool.h تکیه دارند و سخت‌افزار را از راه bus_ops_t می‌گیرند.
  • پیاده‌سازی واقعی bus_ops_t. روی STM32 تابعی با HAL/رجیستر I2C و روی ESP32 تابعی با i2c ESP-IDF؛ هر دو همان امضای read_reg را دارند. تست PC آن را نمی‌بیند، ولی بقیهٔ منطق (تلاش مجدد، بررسی شناسه) کاملا تست شده است.
  • تفاوت‌های PC و MCU. روی PC، int ۳۲ بیتی است و اشاره‌گر ۶۴ بیتی؛ یک تست که sizeof(void*) را فرض کند ممکن است روی MCU فرق کند. همیشه از stdint.h استفاده کن (درس ۲.۲) و یک بار هم کد را با کامپایلر مقصد بساز.
  • وقفه‌ها. تست تک‌رشته‌ای رقابت (race) را نمی‌بیند. می‌توانی «توالی رخداد» را دستی شبیه‌سازی کنی (تابع «ISR» را وسط عملیات صدا بزنی)، ولی برای ثابت‌کردن SPSC بودن بافر باید طراحی (درس ۴.۵) و بازبینی را هم داشته باشی.

آزمون این درس

کدام مورد را نمی‌شود با تست واحد روی PC ثابت کرد؟

  1. بافر حلقوی بایت‌ها را به ترتیب برمی‌گرداند
  2. اگر گذرگاه I2C خطا بدهد، درایور سه بار تلاش می‌کند
  3. رجیستر MODER واقعی برد مقدار درست گرفته و پایه PA5 واقعا LED را روشن می‌کند
  4. دکمه با ۳ نمونهٔ پایدار «فشرده» حساب می‌شود
PC سخت‌افزار برد را ندارد؛ آنچه به رجیستر و پایهٔ واقعی مربوط است باید روی برد، شبیه‌ساز یا HIL دیده شود. منطق را روی PC تست کن و لایهٔ سخت‌افزاری را نازک نگه دار.

این تست چه ایرادی دارد؟

static void test_put(void)
{
    rb_put(&rb, 5);
    uint8_t out;
    rb_get(&rb, &out);
}
  1. هیچ TEST_ASSERT ندارد؛ همیشه «PASS» می‌شود و چیزی را ثابت نمی‌کند
  2. تابع تست نباید static باشد
  3. پارامتر void ندارد
  4. متغیر out مقدار اولیه ندارد
تستی که چیزی را نمی‌سنجد، فقط پوشش می‌دهد و اطمینان کاذب می‌سازد. اولین سؤال درباره هر تست: «اگر کد خراب شود، این تست قرمز می‌شود؟» (این‌جا: نه.)

تابع sensor_probe از bus->read_reg(...) استفاده می‌کند و مستقیم I2C را صدا نمی‌زند. این چه فایده‌ای برای تست دارد؟

  1. برنامه روی برد سریع‌تر می‌شود
  2. در تست، می‌شود یک تابع ساختگی (mock) وصل کرد که جواب‌های دلخواه بدهد و آرگومان‌ها را ثبت کند
  3. دیگر به ASan نیازی نیست
  4. خطای گذرگاه هیچ‌وقت پیش نمی‌آید
این «درز» (seam) است: نقطه‌ای که می‌توانی بدون تغییر کد اصلی، چیز دیگری را جایگزین کنی. با آن مسیر خطا را هم به‌سادگی می‌سازی.

خروجی gcov می‌گوید Lines executed:100.00% ولی در برنامه باگ پیدا می‌شود. چرا؟

  1. gcov خراب است
  2. تست‌ها باید اجرا نشده باشند
  3. پوشش فقط می‌گوید هر خط اجرا شده؛ اگر تست چیزی را نسنجد یا ورودی مرزی نداشته باشد، باگ می‌ماند
  4. چون از -O0 استفاده کرده‌ایم
پوشش می‌گوید «کجا را ندیده‌ایم»، نه «همه‌چیز درست است». کیفیت به assertها و انتخاب ورودی‌های مرزی بستگی دارد. برای همین «جهش» (خراب‌کردن عمدی کد) را هم امتحان کن.

دو تست را جدا اجرا می‌کنی و هر دو سبزند، ولی با هم یکی قرمز می‌شود. مشکل معمولا چیست؟

  1. کامپایلر تست‌ها را قاطی می‌کند
  2. تست‌ها به هم وابسته‌اند: وضعیت مشترک (مثلا بافر static) بین تست‌ها ریست نمی‌شود
  3. تعداد تست‌ها بیش از حد است
  4. تست‌ها خیلی سریع‌اند
قانون «مستقل بودن»: هر تست باید در setUp صحنه را از نو بچیند. تمرین ۲ همین باگ را دارد.

تمرین ۳: mock برای UART (سخت‌افزار)

روی سخت‌افزار واقعی، تابع نوشتن UART ممکن است فقط بخشی از بایت‌ها را بپذیرد (FIFO پر است) یا خطا بدهد. تابع log_line زیر یک خط لاگ را با \r\n می‌فرستد و در صورت ارسال ناقص، ادامه می‌دهد.

#ifndef LOGGER_H
#define LOGGER_H

#include <stddef.h>
#include <stdint.h>

#define LOG_MAX_TEXT 62U            /* حداکثر طول متن (بدون \r\n) */

/* لایهٔ انتقال (مثلا UART): تعداد بایت‌های واقعا فرستاده‌شده را برمی‌گرداند؛ منفی = خطا */
typedef struct {
    int   (*write)(void *ctx, const uint8_t *data, size_t n);
    void   *ctx;
} tx_ops_t;

typedef enum {
    LOG_OK = 0,
    LOG_ERR_ARG = -1,
    LOG_ERR_TOO_LONG = -2,
    LOG_ERR_IO = -3
} log_status_t;

/* متن را همراه با "\r\n" می‌فرستد و ارسال ناقص را ادامه می‌دهد */
log_status_t log_line(const tx_ops_t *tx, const char *text);

#endif /* LOGGER_H */

#include "logger.h"
#include <string.h>

log_status_t log_line(const tx_ops_t *tx, const char *text)
{
    uint8_t buf[LOG_MAX_TEXT + 2U];
    size_t  len;
    size_t  sent = 0U;

    if ((tx == NULL) || (tx->write == NULL) || (text == NULL)) {
        return LOG_ERR_ARG;
    }
    len = strlen(text);
    if (len > LOG_MAX_TEXT) {
        return LOG_ERR_TOO_LONG;
    }
    memcpy(buf, text, len);
    buf[len] = (uint8_t)'\r';
    buf[len + 1U] = (uint8_t)'\n';
    len += 2U;

    while (sent < len) {                        // هر دور لااقل یک بایت پیش می‌رود
        int n = tx->write(tx->ctx, &buf[sent], len - sent);
        if (n <= 0) {
            return LOG_ERR_IO;
        }
        sent += (size_t)n;
    }
    return LOG_OK;
}
  1. دروازه. اشاره‌گر خالی رد می‌شود.

  3. ارسال با ادامه. هر دور write را صدا می‌زند؛ اگر n <= 0 خطا؛ وگرنه sent جلو می‌رود. چون هر دور یک بایت یا بیشتر پیش می‌رود (وگرنه خروج با خطا)، حلقه حتما تمام می‌شود؛ قانون ۲ ناسا.

/* ماک UART: در هر فراخوانی حداکثر max_chunk بایت می‌پذیرد و همه را ضبط می‌کند */
typedef struct {
    uint8_t  sent[128];
    size_t   total;
    size_t   max_chunk;         /* سقف بایت در هر فراخوانی (شبیه FIFO پر) */
    unsigned calls;
    int      fail_on_call;      /* شمارهٔ فراخوانی‌ای که خطا بدهد؛ ۰ = هرگز */
} mock_tx_t;

static mock_tx_t uart;
static tx_ops_t  tx;

static int mock_write(void *ctx, const uint8_t *data, size_t n)
{
    mock_tx_t *m = ctx;
    m->calls++;
    if ((int)m->calls == m->fail_on_call) {
        return -1;
    }
    if (n > m->max_chunk) {
        n = m->max_chunk;
    }
    memcpy(&m->sent[m->total], data, n);
    m->total += n;
    return (int)n;
}

حرف مربی

معمولا سه جا گیر می‌کنند. اول: «تست ننوشتم چون وقت نداشتم». درست است که نوشتن تست وقت می‌برد؛ ولی هر ساعتی که برای دیباگ روی برد می‌گذارد را ده برابر می‌کند. با ماژول‌های کوچک منطقی شروع کن (بافر، CRC، پارسر)؛ آن‌ها ارزان‌ترین و پرسودترین تست‌اند. دوم: کدی می‌نویسند که تست‌پذیر نیست (تابعی که هم رجیستر می‌خواند، هم تصمیم می‌گیرد، هم printf می‌کند). راه درست: تصمیم را در یک تابع خالص بگذار و سخت‌افزار را از راه یک اشاره‌گر تابع بده. سوم: پوشش را هدف می‌کنند. تیمی که «۹۰٪ پوشش» می‌خواهد و بعد تست بی‌assert می‌نویسد، خودش را گول می‌زند. یک پیشنهاد عملی برای امروز: بافر حلقوی خودت را با make این درس تست کن، بعد یک باگ عمدی بگذار و ببین تست می‌گیرد. وقتی اولین‌بار یک تست باگی را گرفت که خودت فراموش کرده بودی، دیگر بدون آن نمی‌نویسی.

خلاصه یک‌دقیقه‌ای

  • چرا PC؟ سریع، ابزار عالی (gdb، ASan، gcov)، حالت‌های خطا آسان، و قابل‌اجرا در CI. ولی جای برد واقعی را نمی‌گیرد؛ منطق را جدا کن و روی PC تست کن.
  • فریم‌ورک: هر تست یک تابع؛ TEST_ASSERT_... در شکست پیام «انتظار/نتیجه» چاپ می‌کند و با longjmp از تست خارج می‌شود؛ setUp/tearDown صحنه را می‌چینند؛ کد خروج ۰ یا ۱ برای CI.   • تست خوب: AAA، یک ادعا در هر تست، اسم گویا، مرزها (خالی، پر، چرخش، دور زدن شمارنده)، و FIRST (سریع، مستقل، تکرارپذیر، خودبسنده، به‌موقع).
  • TDD: قرمز ← سبز ← مرتب. تستی که هرگز قرمز ندیده‌ای معتبر نیست؛ گاهی خود تست غلط است.

  • پوشش: --coverage -O0، اجرا، gcov؛ ##### = ندیده‌ایم. ۱۰۰٪ یعنی «اجرا شد»، نه «درست است». برای اطمینان از تست‌ها: باگ عمدی بگذار.
