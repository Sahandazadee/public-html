دوره تمام شد، ولی یادگیری نه. C که یاد گرفتی، ابزاری است که در دست تو بماند؛ حالا باید بدانی به کجا می‌شود رفت: کدام موضوع‌ها را بعدا یاد بگیری، از کدام کتاب‌ها، چه‌طور مستندات سخت‌افزار را بخوانی و سؤال‌های مصاحبه چه هستند. این درس نقشهٔ راه بعد از دوره است.

ایدهٔ اصلی: بعد از یاد گرفتن رانندگی

وقتی گواهینامه می‌گیری، هنوز راننده‌ای حرفه‌ای نیستی. ولی حالا می‌توانی به جاده بروی، و از آن به بعد هر کیلومتر تو را بهتر می‌کند. C برای میکروکنترلر هم همین است: پایه‌ها را داری (نوع، بیت، اشاره‌گر، حافظه، رجیستر، وقفه، ساخت پروژه). آنچه مانده، عمق و گستره است.

مثال از زندگی روزمره

دورهٔ تو مثل یادگرفتن آشپزی پایه است: برنج، خورش، سرخ‌کردن. از اینجا می‌شود به سمت شیرینی‌پزی رفت (RTOS: هماهنگی چند کار)، یا آشپزی حرفه‌ای رستورانی (بوت‌لودر و OTA: کار در مقیاس محصول)، یا آشپزی سالم (امنیت و کم‌مصرف). لازم نیست همه را یک‌جا؛ یکی را انتخاب کن که پروژهٔ بعدی‌ات لازمش دارد.

RTOS: وقتی super loop کافی نیست

تا اینجا برنامه‌ات یک حلقهٔ بی‌نهایت بود که کارها را یکی‌یکی انجام می‌داد و وقفه‌ها کارهای فوری را (super loop، درس ۵.۳ و ۵.۴). وقتی کارها زیاد و ناهمگن شوند (خواندن حسگر، Wi-Fi، نمایشگر، پروتکل) هماهنگ‌کردنشان با پرچم و ماشین حالت پیچیده می‌شود. اینجا RTOS کمک می‌کند: هر کار را به‌صورت یک وظیفه (task) جدا می‌نویسی و زمان‌بند (scheduler) بین‌شان جابه‌جا می‌شود.

FreeRTOS رایج‌ترین است و ESP-IDF از پیش با آن ساخته شده (درس ۵.۶: xTaskCreate، vTaskDelay). روی STM32 هم می‌شود آن را اضافه کرد. Zephyr یک RTOS بزرگ‌تر و کامل‌تر با پشتیبانی از بردهای زیاد است (سیستم ساخت و توضیح دستگاه‌های خودش را دارد). یادگیری هر دو بعد از دانستن اشاره‌گر و ISR راحت است. اصل مهم: RTOS داده‌ها را خودکار امن نمی‌کند؛ هنوز مشکل «دو وظیفه یک متغیر را می‌نویسند» را باید با mutex یا صف حل کنی.

قاعدهٔ ISR در RTOS

در ISR فقط از نسخه‌های مخصوص ISR توابع RTOS استفاده کن (در FreeRTOS نام‌هایی که به FromISR ختم می‌شوند) و ISR را کوتاه نگه دار؛ کار سنگین را به یک وظیفه بسپار.

گواهی و مدرک: لازم است؟

در کار نرم‌افزار نهفته هیچ گواهی واحد و اجباری‌ای وجود ندارد که در همهٔ شرکت‌ها شرط استخدام باشد. چیزی که معمولاً بیشتر از مدرک وزن دارد، نمونه‌کار است: پروژه‌ای مثل ۷.۱ با مخزن مرتب، تست‌های خودکار، توضیح معماری و اندازهٔ Flash/RAM، که بشود در مصاحبه روی آن حرف زد. گواهی‌ها در دو حالت به کار می‌آیند: (۱) دوره‌ها و آزمون‌هایی که خود سازندگان تراشه یا آموزشگاه‌ها می‌دهند، برای نشان‌دادن آشنایی با یک خانواده؛ (۲) در صنایع ایمنی‌محور (خودرو، پزشکی، هوافضا) که شرکت‌ها آشنایی با استانداردهایی مثل MISRA C (درس ۶.۳) یا ISO 26262 را می‌خواهند و گاهی دورهٔ مربوط را از کارمند می‌طلبند. اگر هدفت صنعت خاصی است، آگهی‌های استخدام همان صنعت را بخوان و ببین چه چیزی نوشته‌اند؛ از روی همان تصمیم بگیر.

چطور datasheet و Reference Manual بخوانیم

هر PDF چند صد صفحه است و هیچ‌کس همه‌اش را نمی‌خواند. کار درست این است که سؤال بپرسی و سند درست را باز کنی:

چک‌لیست خواندن یک بخش از Reference Manual (مثلا GPIO یا USART):

  1. اول نمودار بلوکی و توضیح کلی. ببین بخش چه اجزایی دارد (ثبات‌ها، کلاک، وقفه‌ها) و به چه پایه‌هایی وصل است.
  2. کلاک و فعال‌سازی. کدام ثبات RCC کلاکش را روشن می‌کند؟ بدون این، رجیسترها جواب نمی‌دهند.
  3. پایه‌ها و حالت‌های جایگزین. در Datasheet جدول Alternate Function: پایهٔ موردنظر برای این پریفرال کدام AF است؟
  4. فهرست رجیسترها. آفست هر ثبات از آدرس پایه، اندازه، مقدار پس از ریست، و دسترسی هر بیت (خواندنی/نوشتنی/فقط با نوشتن ۱ پاک می‌شود).
  5. توالی راه‌اندازی. ترتیب لازم: کلاک ← پیکربندی ← فعال‌سازی ← داده. اغلب یک بخش «Programming sequence» یا مثال دارد.
  6. محدودیت‌ها و یادداشت‌ها. پاورقی‌ها و «Note» را بخوان؛ بسیاری از دام‌ها آنجاست (مثلا نوشتن روی بیت‌های رزرو).
  7. Errata. اگر همهٔ مراحل درست است ولی کار نمی‌کند، اینجا را ببین.

سؤال‌های مصاحبه و جواب‌های سنجیده

این‌ها سؤال‌هایی‌اند که در مصاحبهٔ نرم‌افزار نهفته بارها می‌آیند. حفظ‌کردن جواب کافی نیست؛ دلیل را بگو.

۱. volatile یعنی چه؟

یعنی «هر بار از حافظه بخوان و بنویس؛ کامپایلر حق ندارد مقدار را در ثبات نگه دارد یا دسترسی را حذف کند». لازم است برای رجیسترهای سخت‌افزاری و متغیرهایی که ISR و برنامهٔ اصلی مشترکا استفاده می‌کنند (درس ۳.۶). نمی‌دهد: اتمی‌بودن، ترتیب بین هسته‌ها. یک نمونهٔ الگوی پرچم ISR:

#include <stdint.h>

static volatile uint8_t tick_flag;

void SysTick_Handler(void)
{
    tick_flag = 1u;
}

int main(void)
{
    for (;;) {
        if (tick_flag != 0u) {
            tick_flag = 0u;
            /* کار دورهای اینجا */
        }
    }
}
  1. پرچم مشترک. بین ISR و main مشترک است. اگر volatile نبود، کامپایلر در -O2 می‌توانست بخواند که main هرگز آن را عوض نمی‌کند و شرط را برای همیشه «غلط» بگیرد یا حلقه را حذف کند.
  2. ISR کوتاه. فقط پرچم را ۱ می‌کند و برمی‌گردد. دلیل: ISR باید سریع باشد؛ کار سنگین را main می‌کند (درس ۵.۳).
  3. حلقهٔ اصلی. پرچم را می‌خواند، پاک می‌کند و کار را انجام می‌دهد. توجه: اگر بین تست و پاک‌کردن ISR دوباره اجرا شود، یک رویداد گم می‌شود. برای شمارش دقیق از شمارنده یا بافر حلقوی استفاده کن.

۲. چه چیزهایی را در ISR انجام نمی‌دهیم؟

کار طولانی، انتظار فعال، printf، malloc و توابع مسدودکننده. دلیل: ISR وقفه‌های هم‌رده یا پایین‌تر را نگه می‌دارد، و توابعی مثل malloc و printf reentrant نیستند یا زمان نامعلوم دارند. کار را با پرچم، بافر حلقوی یا صف به main یا یک وظیفه بسپار (درس ۴.۵).

۳. padding و ترتیب اعضای struct

کامپایلر برای تراز حافظه بین اعضا بایت خالی می‌گذارد (درس ۳.۴). ترتیب اعضا اندازه را عوض می‌کند:

#include <stdio.h>
#include <stdint.h>

struct loose { uint8_t flag; uint32_t value; uint8_t mode; };
struct tight { uint32_t value; uint8_t flag; uint8_t mode; };

int main(void)
{
    printf("loose: %zu\n", sizeof(struct loose));
    printf("tight: %zu\n", sizeof(struct tight));
    return 0;
}
  1. ترتیب بد. ۱ بایت، سه بایت padding تا value به مرز ۴ برسد، ۴ بایت، ۱ بایت و ۳ بایت padding آخر تا کل struct مضرب ۴ شود. دلیل padding آخر: اگر آرایه‌ای از این struct بسازی، هر عنصر باید تراز بماند.
  2. ترتیب خوب. اعضای بزرگ‌تر اول: ۴ + ۱ + ۱ و ۲ بایت padding.
  3. اندازه‌ها را چاپ می‌کند. با %zu چون sizeof از نوع size_t است.
$ gcc -std=c11 -Wall -Wextra -o pad pad.c
$ ./pad
loose: 12
tight: 8

روی MCU حافظه گران است؛ اعضا را از بزرگ به کوچک بچین. ولی اگر struct را روی پروتکل یا رجیستر منطبق می‌کنی، بهتر است به‌جای packed بایت‌ها را صریحا بسازی (پرهیز از دسترسی ناهم‌تراز).

۴. بافر حلقوی چرا و چگونه؟

برای تحویل دادهٔ ISR به برنامهٔ اصلی بدون قفل: ISR فقط سر (head) را جلو می‌برد و برنامهٔ اصلی فقط دم (tail) را. چون هر شاخص را فقط یک طرف می‌نویسد، در حالت تولیدکنندهٔ واحد و مصرف‌کنندهٔ واحد بدون قفل کار می‌کند (به شرط volatile یا سد حافظه مناسب و اندازهٔ توان ۲ برای ماسک). توجه: ring_push در پروژهٔ ۷.۱ با سیاست «قدیمی‌ترین را دور بریز» tail را هم تغییر می‌دهد؛ پس آن بافر تولیدکنندهٔ واحد/مصرف‌کنندهٔ واحد بدون قفل نیست و برای تحویل از ISR باید طراحی دیگری داشته باشد. تمایز «پر» و «خالی»: یک خانه را خالی می‌گذاریم یا شمارنده جدا نگه می‌داریم (درس ۴.۵).

۵. تابع reentrant چیست؟

تابعی که اگر وسط اجرا قطع شود و دوباره (از ISR یا وظیفهٔ دیگر) صدا زده شود، درست کار کند. یعنی reentrant است اگر فقط از پارامتر و متغیرهای محلی استفاده کند و متغیر static یا سراسری قابل‌تغییرِ مشترک نداشته باشد (خواندن داده‌های ثابت مثل جدول static const اشکالی ندارد؛ همین کار را hex_ok پایین می‌کند). توجه: «thread-safe» با «reentrant» یکی نیست؛ تابعی که با قفل ایمن شده، در ISR که قفل را نمی‌تواند بگیرد باز هم مشکل دارد. نمونهٔ خراب و درست:

#include <stdint.h>
#include <stdio.h>

static const char digits[] = "0123456789abcdef";

static char *hex_bad(uint8_t v)
{
    static char buf[3];
    buf[0] = digits[v >> 4];
    buf[1] = digits[v & 0xFu];
    buf[2] = '\0';
    return buf;
}

static void hex_ok(uint8_t v, char out[3])
{
    out[0] = digits[v >> 4];
    out[1] = digits[v & 0xFu];
    out[2] = '\0';
}

int main(void)
{
    char *a = hex_bad(0x0A);
    char *b = hex_bad(0xFF);
    printf("%s %s\n", a, b);

    char x[3];
    char y[3];
    hex_ok(0x0A, x);
    hex_ok(0xFF, y);
    printf("%s %s\n", x, y);
    return 0;
}
  1. نسخهٔ ناایمن. بافر static یکی است و بین همهٔ فراخوانی‌ها مشترک. خروجی آدرس همان بافر است؛ فراخوانی دوم محتوای اولی را رونویسی می‌کند. در وقفه یا دو وظیفه اوضاع بدتر می‌شود.
  2. نسخهٔ ایمن. بافر را صدا زننده می‌دهد. هر فراخوانی حافظهٔ خودش را دارد؛ هیچ حالت مشترک نیست.
  3. نتیجهٔ باگ. a و b هر دو به همان بافر اشاره می‌کنند و هر دو «ff» چاپ می‌شوند.
  4. نتیجهٔ درست. دو بافر جدا، دو نتیجهٔ درست.
$ gcc -std=c11 -Wall -Wextra -o reent reent.c
$ ./reent
ff ff
0a ff

خودارزیابی نهایی

صادقانه به هر جمله جواب بده. اگر «نه» بود، درس مربوطه را دوباره بخوان (شمارهٔ درس کنارش است).

و در پایان: پروژهٔ ۷.۱ را ساخته‌ای؟ اگر آری، تبریک: تو اکنون کسی هستی که می‌تواند C را برای میکروکنترلر بنویسد و یاد بگیرد. اگر مطالب ESP32 را عمیق‌تر می‌خواهی (Wi-Fi، MQTT و بقیهٔ اکوسیستم)، دورهٔ همراه ESP32 Masterclass را ببین.

آزمون این درس

کدام مشکل را RTOS خودکار حل نمی‌کند؟

  1. اجرای چند کار به‌نوبت روی یک هسته
  2. دو وظیفه که هم‌زمان یک متغیر مشترک را می‌نویسند
  3. منتظر ماندن یک وظیفه بدون مصرف CPU
  4. تصمیم‌گیری دربارهٔ اینکه چه وظیفه‌ای اکنون اجرا شود
دادهٔ مشترک را باید خودت با mutex، صف یا semaphore محافظت کنی. RTOS ابزار می‌دهد، محافظت را به‌جایت انجام نمی‌دهد.

خروجی sizeof(struct { uint8_t a; uint32_t b; uint8_t c; }) روی ARM Cortex-M (تراز ۴ بایتی) چند است؟

  1. ۶
  2. ۸
  3. ۱۲
  4. ۱۶
a یک بایت، سه بایت padding، b چهار بایت، c یک بایت و سه بایت padding آخر: ۱۲. با ترتیب b، a، c فقط ۸ بایت می‌شود.

برای فهمیدن «فلان بیت ثبات GPIO چه می‌کند» کدام سند را باز می‌کنی؟

  1. Reference Manual تراشه
  2. Datasheet
  3. Errata
  4. نقشهٔ برد (Schematic)
Reference Manual (مثلا RM0383 برای STM32F411) ثبات‌ها و بیت‌ها را شرح می‌دهد.

کدام گزینه یک تابع reentrant را خراب می‌کند؟

  1. استفاده از متغیر محلی
  2. استفاده از پارامترهای ورودی
  3. نوشتن نتیجه در بافری که صدا زننده می‌دهد
  4. برگرداندن آدرس یک متغیر static داخل تابع
متغیر static بین فراخوانی‌ها مشترک است و اگر تابع وسط کار قطع شود، محتوایش خراب می‌شود.

در مصاحبه می‌پرسند «چرا در ISR از printf استفاده نمی‌کنیم؟» بهترین جواب کدام است؟

  1. چون در C ممنوع است
  2. چون کند و با زمان نامعلوم است و ممکن است reentrant نباشد؛ ISR باید کوتاه باشد
  3. چون ISR به Flash دسترسی ندارد
  4. چون ISR نمی‌تواند رشته چاپ کند
ISR باید سریع و قابل‌پیش‌بینی باشد. printf زمان‌بر و اغلب غیر reentrant است؛ داده را به main بسپار و آنجا چاپ کن.

تمرین‌ها

تمرین ۱: نقشهٔ راه شخصی

بدون کد؛ برای خودت برنامه بنویس.

  1. هدف: یک پروژهٔ واقعی که می‌خواهی در سه ماه بعد بسازی بنویس (مثلا «ایستگاه هواشناسی با ESP32»).
  2. موضوع: از شکل نقشهٔ راه، دو شاخهٔ لازم برای آن پروژه را انتخاب کن و بگو چرا.
  3. منبع: برای هر شاخه یک کتاب یا سند رسمی از این درس یا صفحهٔ منابع انتخاب کن و هر هفته چند ساعت برایش بگذار.
راهنمایی

پروژه‌ای انتخاب کن که کوچک باشد و یک چیز تازه داشته باشد. اگر همه‌چیز تازه باشد، گیر می‌کنی.

نمونه پاسخ

هدف: ثبت دما و ارسال آن. شاخه‌ها: پروتکل‌ها (Wi-Fi/MQTT در ESP32) و سیستم (کم‌مصرف). منبع: راهنمای ESP-IDF برای Wi-Fi و بخش خواب عمیق. برنامه: ۳ ساعت در هفته، هر دو هفته یک نمونهٔ کوچک.

تمرین ۲: کوچک‌کردن struct (یافتن باگ حافظه)

این struct روی یک MCU ۳۲ بیتی ۱۲ بایت جا می‌گیرد و ۱۰۰۰ نمونه از آن در RAM داری.

struct sample { uint8_t id; uint16_t value; uint8_t flags; uint32_t time; };
  1. پیش‌بینی: بدون اجرا، جای padding را پیدا کن و بگو sizeof چند است.
  2. حل: ترتیب اعضا را طوری عوض کن که اندازه کمترین شود؛ با sizeof ثابت کن.
  3. چالش: با ۱۰۰۰ نمونه چند بایت RAM ذخیره کردی؟
راهنمایی

اعضا را از بزرگ به کوچک بچین: uint32_t اول.

چه باید ببینی؟ 
$ ./sample
old: 12
new: 8
جواب کامل با توضیح 
#include <stdint.h>
#include <stdio.h>

struct sample_old { uint8_t id; uint16_t value; uint8_t flags; uint32_t time; };
struct sample_new { uint32_t time; uint16_t value; uint8_t id; uint8_t flags; };

int main(void)
{
    printf("old: %zu\n", sizeof(struct sample_old));
    printf("new: %zu\n", sizeof(struct sample_new));
    return 0;
}
  1. ترتیب قدیم. ۱ بایت، ۱ padding، ۲ بایت، ۱ بایت، ۳ padding، ۴ بایت: جمعا ۱۲.
  2. ترتیب جدید. ۴ + ۲ + ۱ + ۱ = ۸، بدون padding. اعضا به ترتیب اندازه چیده شدند و هر کدام روی مرز طبیعی خودش می‌نشیند.
  3. چاپ اندازه‌ها. ۱۲ در برابر ۸؛ برای ۱۰۰۰ نمونه ۴۰۰۰ بایت ذخیره می‌شود.
$ gcc -std=c11 -Wall -Wextra -o sample sample.c
$ ./sample
old: 12
new: 8
تمرین ۳: خواندن Reference Manual

Reference Manual تراشه‌ات (مثلا RM0383 برای STM32F411) را باز کن؛ بدون هیچ حدسی از حافظه.

  1. در بخش GPIO، آفست ثبات‌های MODER و BSRR را از فهرست رجیسترها پیدا کن.
  2. پیدا کن کدام ثبات RCC کلاک GPIOA را روشن می‌کند و کدام بیت.
  3. در توضیح BSRR ببین بیت‌های ۰ تا ۱۵ و ۱۶ تا ۳۱ چه می‌کنند و اگر هر دو ۱ باشند کدام برنده است.
راهنمایی

در فهرست مطالب دنبال «GPIO register map» و «RCC AHB1 peripheral clock enable register» بگرد. پاسخ‌ها با آنچه در درس ۵.۲ نوشتیم باید یکی باشد؛ اگر نبود، مرجع رسمی برنده است.

جواب

باید ببینی MODER آفست 0x00 و BSRR آفست 0x18 است؛ کلاک GPIOA با بیت ۰ ثبات RCC_AHB1ENR؛ و در BSRR بیت‌های ۰ تا ۱۵ پایه را ۱ می‌کنند (set) و ۱۶ تا ۳۱ صفر می‌کنند (reset). طبق توضیح مرجع اگر هر دو برای یک پایه ۱ باشند، set اولویت دارد؛ این را از متن رسمی وارسی کن، نه از حافظهٔ ما.

حرف مربی

بزرگ‌ترین خطای بعد از این نقطه «دنبال دورهٔ بعدی گشتن» است. دورهٔ بعدی تو یک پروژهٔ واقعی است؛ کوچک، با یک هدف روشن، که در آن چیزی بشکند و مجبور شوی دیباگ کنی. هر باگی که خودت حل کنی از ده ساعت ویدیو ارزشمندتر است. و وقتی گیر کردی، ابتدا سند رسمی و بعد این دوره را دوباره بخوان؛ بعضی جمله‌ها بعد از تجربه معنی تازه‌ای پیدا می‌کنند.

خلاصهٔ یک‌دقیقه‌ای

  • RTOS برای چند کار هم‌زمان؛ داده‌های مشترک را هنوز خودت محافظت می‌کنی.
  • C++ و Rust جایگزین فهم C نیستند؛ اسمبلی را بخوان (نه لزوما بنویس).
  • موضوع‌های بعدی: DMA، کم‌مصرف، CAN/USB/BLE، بوت‌لودر و OTA، بوت امن. هر یک با یک پروژهٔ کوچک.
  • مستندات: پرسش را بشناس و سند درست را باز کن (Datasheet، Reference Manual، Programming Manual، Errata، Schematic).
  • در ISR: کوتاه، بدون printf و malloc؛ متغیر مشترک volatile؛ تابع reentrant بدون static/سراسری قابل‌تغییر مشترک.
  • ترتیب اعضای struct روی اندازه اثر می‌گذارد؛ بزرگ به کوچک.
