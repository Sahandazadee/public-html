تا اینجا همیشه با main شروع کرده‌ایم، انگار برنامه از همان‌جا متولد می‌شود. ولی وقتی برق میکروکنترلر وصل می‌شود، main خیلی دیر به صحنه می‌رسد: قبلش باید پشته آماده شود، متغیرهای سراسری مقدار بگیرند و حافظه پاک شود. در این درس همهٔ آن «پشت صحنه» را می‌نویسیم: یک جدول وقفه، یک کد استارت‌آپ و یک اسکریپت لینکر کامل برای STM32F411. آخرش یک فایل ELF واقعی می‌سازیم و درونش را با ابزار می‌خوانیم.

🎯 بعد از این درس می‌توانی

  • توضیح بدهی بعد از reset، CPU دقیقا چه می‌خواند و کجا می‌رود
  • یک جدول وقفهٔ Cortex-M در C بنویسی و بدانی چرا آدرس Reset_Handler فرد است
  • کد Reset_Handler را بنویسی که .data را کپی و .bss را صفر کند
  • یک اسکریپت لینکر بخوانی و بنویسی (MEMORY، SECTIONS، AT >)
  • ELF ساخته‌شده را با objdump، size و nm بخوانی
  • وقفه‌های weak را با تعریف خودت جایگزین کنی
  • زنجیرهٔ بوت ESP32 را در حد مفهوم بگویی

🧰 پیش‌نیاز و وسایل

  • درس ۳.۵ (بخش‌های .data و .bss، نقشهٔ حافظه)
  • درس ۳.۶ (رجیستر و volatile) و ۳.۲ (اشاره‌گر)
  • درس ۴.۲ (لینک، extern، چند فایل) و ۴.۱

ایدهٔ اصلی: باز کردن مغازه

صبح یک مغازه را تصور کن. مشتری (برنامهٔ تو، یعنی main) ساعت ۹ می‌رسد. ولی قبل از او یک کارمند باید:

  1. برق را وصل کند و بداند لیست کارهای صبح کجاست (SP و آدرس شروع).
  2. قفسه‌ها را بچیند: جنس‌هایی که از انبار (Flash) باید در مغازه (RAM) باشند را ببرد (کپی .data).
  3. پیشخوان را پاک کند: جای بقیهٔ اجناس را تمیز و خالی کند (صفر کردن .bss).
  4. در را باز کند. (صدا زدن main)
مثال از زندگی روزمره

در کامپیوتر معمولی سیستم‌عامل این کارمند است. روی میکروکنترلر سیستم‌عاملی نیست، پس کارمند خودِ تو هستی: همان کد کوچکی که به آن «استارت‌آپ» (startup) می‌گویند. خوشبختانه فقط چند خط C است.

برای اینکه این کارمند کار کند، سه چیز باید درست کنار هم بنشینند:

قطعهکارشکجا نوشته می‌شود
جدول وقفه (vector table)به CPU می‌گوید SP چه باشد و از کجا شروع کندvectors.c
استارت‌آپ (Reset_Handler)حافظه را آماده و main را صدا می‌زندstartup.c
اسکریپت لینکرتصمیم می‌گیرد هر تکه از برنامه کجای Flash و RAM بنشیندstm32f411.ld

روشن شدن: CPU چه می‌کند؟

وقتی reset تمام می‌شود (برق وصل شده یا دکمهٔ reset رها شده)، CPU هنوز هیچ دستور C ای اجرا نکرده. سخت‌افزار Cortex-M خودش دو کار ثابت انجام می‌دهد:

  1. یک کلمهٔ ۳۲ بیتی از آدرس 0x00000000 می‌خواند و در SP (اشاره‌گر پشته) می‌گذارد.
  2. کلمهٔ بعدی، از آدرس 0x00000004، را می‌خواند و در PC (شمارندهٔ برنامه؛ آدرس دستور بعدی) می‌گذارد. CPU از همان‌جا شروع به اجرا می‌کند.

یعنی هیچ‌چیز جادویی نیست: دو عدد اول حافظه به CPU می‌گویند «پشته این‌جاست» و «کد از آن‌جا شروع می‌شود». این دو عدد ابتدای جدول وقفه هستند.

پس چرا آدرس صفر؟ ما Flash را در 0x08000000 گذاشتیم

در STM32F4 وقتی پایهٔ BOOT0 صفر است (حالت پیش‌فرض روی Nucleo)، حافظهٔ Flash اصلی در آدرس 0x00000000 هم آینه (alias) می‌شود. یعنی کلمهٔ اول جدول که در 0x08000000 نوشته‌ایم، CPU در 0x00000000 هم می‌بیند. اگر BOOT0 یک باشد (و BOOT1 صفر)، به‌جای Flash خود ST یک bootloader داخلی اجرا می‌شود؛ همین است که برنامه‌ریزی از راه USB/UART ممکن می‌کند (جزئیات: بخش بوت در RM0383).

ابزارک زیر همین دو قدم را نشان می‌دهد. مقدارها از همین درس‌اند (بعدا می‌بینی از کجا آمده‌اند):

زیر کاپوت: بیت Thumb

Cortex-M4 فقط دستورهای Thumb (فشرده، ۱۶ یا ۳۲ بیتی) را اجرا می‌کند. قرارداد ARM این است که آدرس‌های تابع Thumb با بیت ۰ برابر ۱ نوشته می‌شوند (آدرس واقعی همیشه زوج است). اگر در جدول وقفه آدرسی با بیت ۰ برابر صفر بگذاری، CPU می‌فهمد می‌خواهد به حالت ARM برود که در Cortex-M وجود ندارد و خطا (fault) می‌دهد. لینکر این بیت را خودش برای توابع Thumb می‌گذارد، پس در C کاری نداری.

جدول وقفه: یک آرایه از اشاره‌گر تابع

در درس ۴.۳ یاد می‌گیری «اشاره‌گر به تابع» چیست. جدول وقفه یعنی دقیقا یک آرایهٔ ثابت از اشاره‌گر تابع که ابتدای Flash می‌نشیند. ورودی صفر آدرس پشته است (که به‌شکل عدد در جدول می‌آید) و بقیه آدرس تابع‌ها.

ورودیناموقتی چه می‌شود
۰مقدار اولیهٔ SP(عدد است نه تابع)
۱Reset_Handlerبعد از reset
۲NMI_Handlerوقفهٔ غیرقابل‌ماسک (خطای سخت‌افزاری مثل خرابی کلاک)
۳HardFault_Handlerخطای جدی CPU (دسترسی ممنوع به حافظه و ...). در درس ۶.۱
۴، ۵، ۶MemManage، BusFault، UsageFaultخطاهای ریزتر (به HardFault ارتقا می‌یابند مگر فعال شوند)
۱۱SVC_Handlerدستور svc (سیستم‌عامل‌های بلادرنگ)
۱۴PendSV_Handlerتعویض task در RTOS
۱۵SysTick_Handlerتایمر سیستم (درس ۵.۴)
۱۶ به بعدوقفه‌های تراشه (WWDG، EXTI0، ...)هر پریفرال وقفهٔ خودش را دارد (درس ۵.۳)

ما جدول را در فایل vectors.c می‌نویسیم. برای اینکه این کد تمام پروژه را بسازد، سه فایل (به‌علاوه اسکریپت لینکر) دور هم کار می‌کنند. اول جدول:

#include <stdint.h>

extern uint32_t _estack;            /* ساخته‌شده توسط اسکریپت لینکر */

typedef void (*isr_t)(void);

void Reset_Handler(void);
void Default_Handler(void);

/* هر وقفه‌ای که خودت ننویسی، به Default_Handler می‌رسد */
void NMI_Handler(void)          __attribute__((weak, alias("Default_Handler")));
void HardFault_Handler(void)    __attribute__((weak, alias("Default_Handler")));
void MemManage_Handler(void)    __attribute__((weak, alias("Default_Handler")));
void BusFault_Handler(void)     __attribute__((weak, alias("Default_Handler")));
void UsageFault_Handler(void)   __attribute__((weak, alias("Default_Handler")));
void SVC_Handler(void)          __attribute__((weak, alias("Default_Handler")));
void DebugMon_Handler(void)     __attribute__((weak, alias("Default_Handler")));
void PendSV_Handler(void)       __attribute__((weak, alias("Default_Handler")));
void SysTick_Handler(void)      __attribute__((weak, alias("Default_Handler")));
void EXTI15_10_IRQHandler(void) __attribute__((weak, alias("Default_Handler")));

/* جدول وقفه: ۱۶ ورودی هسته + ۴۱ وقفهٔ اول تراشه (تا EXTI15_10) */
__attribute__((section(".isr_vector"), used))
const isr_t g_vectors[57] = {
    (isr_t)&_estack,                 /* 0: مقدار اولیهٔ SP */
    Reset_Handler,                   /* 1: کجا شروع کنم؟ */
    NMI_Handler,                     /* 2 */
    HardFault_Handler,               /* 3 */
    MemManage_Handler,               /* 4 */
    BusFault_Handler,                /* 5 */
    UsageFault_Handler,              /* 6 */
    0, 0, 0, 0,                      /* 7..10: رزرو */
    SVC_Handler,                     /* 11 */
    DebugMon_Handler,                /* 12 */
    0,                               /* 13: رزرو */
    PendSV_Handler,                  /* 14 */
    SysTick_Handler,                 /* 15 */
    [16 ... 55] = Default_Handler,   /* وقفه‌های 0 تا 39 تراشه */
    [56] = EXTI15_10_IRQHandler,     /* وقفهٔ 40 */
};

void Default_Handler(void)
{
    for (;;) { }                     /* وقفهٔ پیش‌بینی‌نشده: همین‌جا می‌ایستیم */
}
  1. نماد _estack. این نام را اسکریپت لینکر می‌سازد و آدرس بالای RAM است. اینجا فقط اعلانش می‌کنیم. در درس ۳.۵ دیدی _sdata و _edata هم همین‌طورند: نمادهایی که «آدرس» مهم‌شان است، نه مقدار داخلشان.
  2. نوع isr_t. «اشاره‌گر به تابعی بدون ورودی و بدون خروجی». هر handler وقفه همین امضا را دارد.
  3. اعلان دو تابع. Reset_Handler در startup.c تعریف می‌شود. Default_Handler پایین همین فایل.
  4. weak alias. هر handler را به‌عنوان «نام دیگر برای Default_Handler» اعلان می‌کنیم، ولی ضعیف (weak). اگر خودت در جایی تابعی به اسم SysTick_Handler بنویسی، لینکر نسخهٔ تو (قوی) را به‌جای نسخهٔ weak می‌گذارد. اگر ننویسی، همان alias می‌ماند و به Default_Handler می‌رسد. پس هیچ ورودی جدول خالی یا نامعتبر نمی‌ماند.
  5. تعریف جدول. آرایهٔ ۵۷ عضوی از isr_t. section(".isr_vector") آن را در بخشی با همین نام می‌گذارد تا اسکریپت لینکر بتواند اول Flash بچیندش. used یعنی «حتی اگر کسی صدایش نمی‌زند، دورش نینداز». هیچ کدی جدول را «صدا» نمی‌زند؛ سخت‌افزار آن را می‌خواند. بدون used و KEEP (در اسکریپت لینکر) ممکن است کامپایلر یا لینکر آن را حذف کنند چون هیچ‌کس ازش استفاده نمی‌کند.
  6. ورودی ۰: SP. آدرس _estack را به‌شکل عدد در جدول می‌گذاریم (تبدیل به isr_t فقط برای اینکه در آرایه جا شود). جدول عملا «آرایهٔ کلمه» است. ورودی صفر تابع نیست ولی هم‌اندازهٔ اشاره‌گر تابع است (۳۲ بیت روی ARM).
  7. ورودی ۱: Reset_Handler. جایی که CPU شروع می‌کند.
  8. ورودی‌های هسته. NMI و خطاها و SVC و PendSV و SysTick را با نام‌های استاندارد می‌نویسیم.
  9. رزرو. ورودی‌های ۷ تا ۱۰ و ۱۳ در Cortex-M4 استفاده نمی‌شوند. صفر می‌گذاریم تا جای بقیه درست بماند. هر ورودی دقیقا ۴ بایت است. اگر یکی را جا بیندازی، همهٔ ورودی‌های بعدی یک خانه جابه‌جا می‌شوند و SysTick به‌جای PendSV صدا زده می‌شود!
  10. وقفه‌های تراشه. ‏[16 ... 55] = Default_Handler یعنی «ورودی‌های ۱۶ تا ۵۵ همه Default_Handler». (این نحو، «بازهٔ دسته‌بندی‌شده»، افزونهٔ GNU است؛ فقط با -std=gnu11 کار می‌کند.) ورودی ۵۶ یعنی وقفهٔ شمارهٔ ۴۰ (EXTI15_10، خط‌های ۱۰ تا ۱۵ وقفهٔ خارجی که دکمهٔ PC13 هم داخلشان است). جدول کامل STM32F411 بلندتر است. ما تا وقفه‌ای که در درس ۵.۳ لازم داریم پیش رفته‌ایم؛ فایل رسمی ST همه را دارد. وقفه‌ای که فعال نکنی هرگز صدا زده نمی‌شود، پس جدول کوتاه‌تر بی‌خطر است.
  11. Default_Handler. یک حلقهٔ بی‌نهایت. اگر وقفه‌ای رخ دهد که handler نداشته باشد، برنامه همین‌جا می‌ایستد. ایستادن بهتر از اجرای بی‌هدف است. وقتی دیباگر وصل کنی و ببینی PC داخل Default_Handler است، می‌فهمی وقفهٔ فراموش‌شده‌ای داری.
ترتیب ورودی‌ها مقدس است

موقعیت هر ورودی را سخت‌افزار تعیین می‌کند، نه تو. اگر Reset_Handler را جای دیگری بگذاری، CPU کلمهٔ دوم جدول را به‌عنوان آدرس شروع می‌خواند و به جای اشتباه می‌پرد، معمولا با HardFault. همیشه از فایل رسمی ST یا CMSIS کپی و مقایسه کن.

اسکریپت لینکر: نقشهٔ چیدمان

در درس‌های ۱.۴ و ۴.۲ دیدی لینکر فایل‌های .o را به هم می‌چسباند. اما لینکر از کجا بفهمد «کد باید از 0x08000000 شروع شود»؟ یا «متغیرها در 0x20000000 بنشینند»؟ این‌ها را تو در یک فایل متنی می‌گویی: اسکریپت لینکر (پسوند .ld).

مثال از زندگی روزمره

تصور کن یک اسباب‌کش هستی که باید همهٔ وسایل خانه را در کامیون و انبار جدید بچیند. «نقشهٔ چیدمان» می‌گوید: یخچال کنار در، کتاب‌ها بالا، فرش پایین. اسکریپت لینکر هم همین نقشه است: .text در Flash، .data در RAM، و ...

/* اسکریپت لینکر مینیمال برای STM32F411RE */
ENTRY(Reset_Handler)

/* بالای RAM: SP اولیه. پشته به سمت پایین رشد می‌کند */
_estack = ORIGIN(RAM) + LENGTH(RAM);

MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 512K
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 128K
}

SECTIONS
{
    /* جدول وقفه باید اولین چیز در Flash باشد */
    .isr_vector :
    {
        . = ALIGN(4);
        KEEP(*(.isr_vector))
        . = ALIGN(4);
    } > FLASH

    .text :
    {
        . = ALIGN(4);
        *(.text*)
        . = ALIGN(4);
    } > FLASH

    .rodata :
    {
        . = ALIGN(4);
        *(.rodata*)
        . = ALIGN(4);
    } > FLASH

    /* آدرس ذخیرهٔ مقدارهای اولیهٔ .data در Flash */
    _sidata = LOADADDR(.data);

    /* .data در RAM زندگی می‌کند ولی تصویرش در Flash است */
    .data :
    {
        . = ALIGN(4);
        _sdata = .;
        *(.data*)
        . = ALIGN(4);
        _edata = .;
    } > RAM AT > FLASH

    .bss :
    {
        . = ALIGN(4);
        _sbss = .;
        *(.bss*)
        *(COMMON)
        . = ALIGN(4);
        _ebss = .;
    } > RAM

    /DISCARD/ : { *(.ARM.exidx*) *(.comment) }

    /* بررسی زمان لینک: حداقل ۱ کیلوبایت RAM برای پشته بماند */
    ASSERT(_ebss + 0x400 <= _estack, "RAM is too full: less than 1 KiB left for the stack")
}
  1. نقطهٔ ورود. ‏ENTRY(Reset_Handler) به لینکر می‌گوید نماد ورود برنامه چیست (در فایل ELF ثبت می‌شود). روی میکروکنترلر CPU نقطهٔ ورود ELF را نمی‌خواند؛ جدول وقفه را می‌خواند. ولی ابزارها (مثل دیباگر) از ELF می‌فهمند برنامه از کجا شروع می‌شود.
  2. نماد _estack. بالای RAM: ORIGIN(RAM) + LENGTH(RAM) = 0x20000000 + 128K = 0x20020000. پشته به سمت آدرس‌های کمتر رشد می‌کند. پس از بالاترین آدرس RAM شروع می‌کنیم تا حداکثر فضا برایش بماند.
  3. MEMORY. دو منطقهٔ حافظهٔ واقعی تراشه: FLASH از 0x08000000 با ۵۱۲ کیلوبایت و RAM از 0x20000000 با ۱۲۸ کیلوبایت. حروف داخل پرانتز مجوزهاست: r خواندن، w نوشتن، x اجرا. این اعداد از reference manual (RM0383) و datasheet تراشه می‌آیند. اگر اندازه را بیشتر از واقعی بنویسی، لینکر بدون خطا می‌سازد ولی برنامه روی تراشه کار نمی‌کند. اگر کمتر بنویسی، لینکر زودتر از موعد «پر شد» می‌گوید.
  4. SECTIONS. اینجا می‌گوییم چه بخش‌هایی، به چه ترتیبی، در کدام منطقه بنشینند.
  5. .isr_vector اول. بخش .isr_vector از همهٔ فایل‌ها را در ابتدای FLASH می‌گذارد. ALIGN(4) ابتدا و انتها را ۴ بایتی تراز می‌کند. KEEP یعنی حتی با --gc-sections حذفش نکن. چون CPU جدول را در 0x0 (و آینه‌اش 0x08000000) می‌خواند، باید دقیقا اول Flash بنشیند. اگر .text جلوتر بیاید، CPU کد را به‌جای SP می‌خواند.
  6. .text. همهٔ کد (*(.text*) یعنی هر بخش با نامی که با .text شروع شود از هر فایل) در Flash.
  7. .rodata. ثابت‌های const و رشته‌های ثابت (درس ۳.۵). آن‌ها هم فقط در Flash می‌مانند.
  8. نماد _sidata. ‏LOADADDR(.data) «آدرس بارگذاری» بخش .data است: یعنی جایی از Flash که مقدارهای اولیه ذخیره می‌شوند. این همان مبدأ کپی است که Reset_Handler لازم دارد.
  9. .data: RAM ولی AT Flash. نمادهای _sdata و _edata ابتدا و انتها را علامت می‌زنند. سطر آخر > RAM AT > FLASH می‌گوید: «این بخش وقتی برنامه اجرا می‌شود در RAM است (VMA)، ولی محتوایش را در Flash ذخیره کن (LMA)». RAM با قطع برق پاک می‌شود. مقدار اولیهٔ g_counter = 5 باید جایی زنده بماند؛ پس در Flash می‌نشیند و استارت‌آپ آن را کپی می‌کند.
  10. .bss. فقط در RAM. هیچ محتوایی در Flash ندارد (مقدارش صفر است و لازم نیست ذخیره شود). *(COMMON) برای متغیرهای «common» قدیمی است (قدیمی، ولی بعضی کدها هنوز می‌سازند). این‌که .bss در فایل خروجی جا نمی‌گیرد یعنی برنامهٔ تو با ۱۰۰۰ بایت آرایهٔ سراسری صفر، در Flash ۱۰۰۰ بایت بیشتر نمی‌شود.
  11. دور ریختن. بخش‌هایی که به کارمان نمی‌آیند (اطلاعات استثنا و رشتهٔ نسخهٔ کامپایلر).
  12. بررسی زمان لینک. ASSERT شرط را موقع لینک می‌سنجد: انتهای .bss به‌اضافهٔ ۱ کیلوبایت باید از _estack کمتر باشد. وگرنه لینک متوقف و پیام چاپ می‌شود. پشته و متغیرهای سراسری از دو سوی RAM به هم نزدیک می‌شوند. این بررسی خیلی زود می‌گوید جایی برای پشته نمانده، به‌جای اینکه ماه‌ها بعد برنامه بی‌دلیل خراب شود.
VMA و LMA در یک جمله

VMA = «آدرسی که برنامه هنگام اجرا برای آن بخش می‌بیند»؛ LMA = «جایی که محتوای بخش در فایل/Flash ذخیره است». برای .text و .rodata یکی‌اند. فقط برای .data با هم فرق دارند، و همین فرق دلیل وجود کد کپی در استارت‌آپ است.

Reset_Handler: کارمند صبح

حالا خود کارمند. این کار در تابعی به نام Reset_Handler انجام می‌شود و اصلا پیچیده نیست:

#include <stdint.h>

extern uint32_t _sidata;            /* شروع تصویر .data در Flash */
extern uint32_t _sdata, _edata;     /* ابتدا و انتهای .data در RAM */
extern uint32_t _sbss, _ebss;       /* ابتدا و انتهای .bss در RAM */

int main(void);

static void system_init(void)
{
#if defined(__VFP_FP__) && !defined(__SOFTFP__)
    /* CPACR: دسترسی کامل به FPU (CP10 و CP11) */
    *(volatile uint32_t *)0xE000ED88u |= (0xFu << 20);
    __asm volatile ("dsb\n\tisb");
#endif
}

void Reset_Handler(void)
{
    uint32_t *src = &_sidata;
    uint32_t *dst = &_sdata;

    while (dst < &_edata) {
        *dst++ = *src++;            /* .data: از Flash به RAM */
    }
    for (dst = &_sbss; dst < &_ebss; dst++) {
        *dst = 0;                   /* .bss: صفر */
    }

    system_init();
    main();
    for (;;) { }                    /* اگر main برگشت: بایست */
}
  1. نمادهای مرزی. ابتدا و انتهای .data و .bss، و آدرس تصویر .data در Flash. همه از اسکریپت لینکر می‌آیند. فقط لینکر می‌داند بعد از چیدن همهٔ فایل‌ها هر بخش دقیقا کجا افتاده. پس خودش نشانه‌گذاری می‌کند و ما با & «آدرسِ» نشانه‌ها کار می‌کنیم (درس ۳.۵).
  2. پروتوتایپ main. تا کامپایلر بداند main چیست.
  3. راه‌اندازی اولیهٔ سیستم. تابعی که کارهای سخت‌افزاری قبل از main را می‌کند. در Cortex-M4 اگر با -mfloat-abi=hard ساخته شود، دسترسی به واحد اعشاری (FPU) را باز می‌کند. در درس ۴.۷ گفتیم FPU بعد از reset خاموش است؛ نوشتن در CPACR (آدرس 0xE000ED88) بیت‌های ۲۰ تا ۲۳ آن را روشن می‌کند. dsb و isb اطمینان می‌دهند نوشتن تمام شده و خط لولهٔ CPU پاک شده باشد. با ساخت پیش‌فرض ما (بدون FPU) این #if کامپایل نمی‌شود.
  4. تابع اصلی. ‏Reset_Handler اولین تابع C برنامه است. ورودی و خروجی ندارد (کسی نیست که صدایش بزند یا نتیجه‌اش را بگیرد).
  5. دو اشاره‌گر. ‏src از تصویر Flash شروع می‌کند و dst از ابتدای .data در RAM.
  6. حلقهٔ کپی. تا وقتی dst به انتهای .data نرسیده، یک کلمهٔ ۳۲ بیتی از Flash به RAM ببر و هر دو اشاره‌گر را یک کلمه جلو ببر. کلمه به کلمه سریع‌تر از بایت‌به‌بایت است. به همین دلیل اسکریپت لینکر ابتدا و انتها را با ALIGN(4) ۴ بایتی کرده.
  7. صفر کردن bss. از _sbss تا _ebss صفر بنویس. قانون C می‌گوید سراسری‌های بدون مقدار اولیه صفرند (درس ۳.۵). این کد آن را «واقعی» می‌کند. بدون آن g_total آشغال داشت.
  8. راه‌اندازی سیستم. صدا زدن system_init. (در پروژه‌های ST اینجا SystemInit و تنظیم کلاک است.)
  9. main و بعد بی‌نهایت. برنامهٔ تو اجرا می‌شود. اگر روزی برگشت، در حلقهٔ بی‌نهایت می‌مانیم. جایی برای بازگشت نیست؛ هیچ سیستم‌عاملی نمی‌گوید «بعدش چی؟». اگر این حلقه نباشد، CPU دستورهای بعد از تابع (آشغال) را اجرا می‌کند.
در Reset_Handler به متغیر سراسری تکیه نکن

قبل از اتمام حلقه‌ها، .data و .bss هنوز آماده نیستند. اگر در Reset_Handler از یک متغیر سراسری استفاده کنی، مقدارش آشغال است. حتی تابعی که از متغیر سراسری «مقدار اولیه‌دار» استفاده می‌کند (مثلا یک SystemCoreClock که مقدار پیش‌فرض دارد) باید بعد از کپی صدا زده شود. به همین دلیل system_init را بعد از هر دو حلقه گذاشتیم.

همین حلقه‌ها را روی PC ببین

لازم نیست به برد چیزی وصل کنی تا نتیجه را ببینی. این برنامهٔ PC یک «تراشهٔ اسباب‌بازی» می‌سازد: یک آرایه نقش Flash و یک آرایه نقش RAM را دارد. دقیقا همان دو حلقه را روی آن‌ها اجرا می‌کنیم:

#include <stdio.h>
#include <stdint.h>

/* «تراشهٔ اسباب‌بازی»: آرایه‌ها نقش Flash و RAM را بازی می‌کنند */
static const uint32_t flash_image[3] = { 5, 7, 9 };   /* مقدارهای اولیهٔ .data */
static uint32_t ram[8];      /* کلمهٔ 0..2: .data ، 3..5: .bss ، 6..7: آزاد */

static void dump(const char *title)
{
    printf("%-12s", title);
    for (int i = 0; i < 8; i++) {
        printf(" %08lX", (unsigned long)ram[i]);
    }
    printf("\n");
}

int main(void)
{
    uint32_t *sdata = &ram[0];
    uint32_t *edata = &ram[3];
    uint32_t *sbss  = &ram[3];
    uint32_t *ebss  = &ram[6];

    printf(".data = %ld words, .bss = %ld words\n",
           (long)(edata - sdata), (long)(ebss - sbss));

    for (int i = 0; i < 8; i++) {
        ram[i] = 0xDEADBEEFu;               /* برق وصل شد: آشغال */
    }
    dump("power on:");

    const uint32_t *src = flash_image;
    uint32_t *dst = sdata;
    while (dst < edata) {
        *dst++ = *src++;                    /* کپی .data */
    }
    dump("after copy:");

    for (dst = sbss; dst < ebss; dst++) {
        *dst = 0;                           /* صفر کردن .bss */
    }
    dump("after zero:");
    return 0;
}
  1. Flash و RAM ساختگی. تصویر .data سه کلمه است: ۵ و ۷ و ۹. RAM هشت کلمه دارد. آرایهٔ const شبیه Flash است (فقط‌خواندنی)؛ آرایهٔ معمولی شبیه RAM.
  2. چاپ RAM. هشت کلمهٔ RAM را با هگز چاپ می‌کند.
  3. چهار نشانگر. همان کاری که نمادهای لینکر می‌کنند: کلمه‌های ۰ تا ۲ برای .data، ۳ تا ۵ برای .bss.
  4. اندازه‌ها. تفاضل دو اشاره‌گر تعداد کلمه‌ها را می‌دهد (درس ۳.۳: حساب اشاره‌گر با مقیاس نوع).
  5. برق وصل شد. RAM را با 0xDEADBEEF پر می‌کنیم تا «آشغال» دیده شود.
  6. کپی. همان حلقه.
  7. صفر. همان حلقه.

برنامهٔ کوچک ما

اسکریپت و استارت‌آپ آماده‌اند. یک main کوچک می‌نویسیم که هر بخش را یک بار پر کند تا بعدا در فایل خروجی ببینیم:

#include <stdint.h>

uint32_t g_counter = 5;                         /* .data: مقدار اولیه دارد */
uint32_t g_total;                               /* .bss: صفر */
const uint32_t g_table[4] = { 1, 2, 4, 8 };     /* .rodata: فقط در Flash */
volatile uint32_t g_ticks;                      /* .bss */

/* تعریف «قوی»: جای نسخهٔ weak استارت‌آپ می‌نشیند */
void SysTick_Handler(void)
{
    g_ticks++;
}

int main(void)
{
    for (;;) {
        g_total += g_table[g_counter & 3u];
        g_counter++;
    }
}
  1. .data. سراسری با مقدار اولیهٔ غیرصفر. ۴ بایت در RAM و ۴ بایت در Flash (تصویر).
  2. .bss. سراسری بدون مقدار اولیه: فقط ۴ بایت در RAM.
  3. .rodata. آرایهٔ ثابت: ۱۶ بایت، فقط در Flash.
  4. یک شمارنده. متغیر volatile که در وقفه تغییر می‌کند (درس ۳.۶). در .bss می‌نشیند.
  5. تعریف SysTick_Handler. یک تابع معمولی با همان نامی که در vectors.c به‌صورت weak اعلان شده بود. لینکر می‌بیند دو تعریف با یک نام دارد: یکی weak، یکی قوی. قوی برنده می‌شود. پس ورودی ۱۵ جدول به تابع ما اشاره خواهد کرد، نه Default_Handler. (در درس ۵.۴ واقعا SysTick را روشن می‌کنیم؛ اینجا هرگز صدا زده نمی‌شود.)
  6. حلقهٔ اصلی. ‏main هرگز تمام نمی‌شود (super loop، درس ۱.۴). هر دور یک عنصر از جدول را با شمارنده جمع می‌کند. این حلقه فقط برای استفادهٔ هر سه بخش است تا لینکر هیچ‌کدام را دور نیندازد.

ساخت و کالبدشکافی ELF

یک دستور، هر سه فایل و اسکریپت را به یک فایل ELF (فایل اجرایی همراه با اطلاعات بخش‌ها و نمادها) تبدیل می‌کند:

$ arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -std=gnu11 -Wall -Wextra -ffreestanding -nostdlib -T stm32f411.ld -o out.elf vectors.c startup.c main.c

اگر همه‌چیز درست باشد، هیچ خروجی و هیچ هشداری نمی‌بینی و out.elf ساخته می‌شود.

  1. -mcpu=cortex-m4 -mthumb کد برای هستهٔ M4 با دستورهای Thumb.
  2. -ffreestanding «محیط ما کتابخانهٔ C استاندارد و سیستم‌عامل ندارد».
  3. -nostdlib فایل‌های آمادهٔ استارت‌آپ و کتابخانهٔ C را به لینک اضافه نکن (ما همه‌چیز خودمان نوشته‌ایم).
  4. -T stm32f411.ld از این اسکریپت لینکر استفاده کن.

پنج کلمهٔ آخر ثابت‌های literal pool هستند: 0x080001C0 (_sidata)، 0x20000000 (_sdata)، 0x20000004 (_edata)، دوباره 0x20000004 (_sbss) و 0x2000000C (_ebss). لینکر بعد از تعیین چیدمان، همین‌ها را در کد پر می‌کند. یعنی نمادهای اسکریپت لینکر، مستقیم به عدد داخل کد تبدیل می‌شوند؛ وقتی اسکریپت را عوض کنی، همین اعداد عوض می‌شوند و کدِ C لازم نیست تغییر کند.

وقفهٔ weak: نام‌های آماده برای جایگزینی

یک تجربهٔ عملی: وقفه‌ای را که می‌خواهی، فقط با نوشتن یک تابع هم‌نام جایگزین کن. بدون تغییر در vectors.c. مثلا در درس ۵.۳ دکمهٔ آبی روی PC13 با EXTI15_10_IRQHandler کار می‌کند. همین الآن هم می‌توانیم نشان بدهیم لینکر آن را جایگزین می‌کند:

#include <stdint.h>

volatile uint32_t g_button_events;

/* تعریف قوی: جای نسخهٔ weak را می‌گیرد (پاک کردن پرچم EXTI در درس 5-3) */
void EXTI15_10_IRQHandler(void)
{
    g_button_events++;
}

int main(void)
{
    for (;;) { }
}
  1. شمارندهٔ رویداد. ‏volatile چون بعدا وقفه و main هر دو به آن دست می‌زنند (درس ۳.۶).
  2. تعریف قوی. همان نام handler که در جدول آمده. در وقفهٔ واقعی باید پرچم pending را پاک کنی (درس ۵.۳). اگر اسم را یک حرف اشتباه بنویسی (EXTI15_10_IRQhandler)، هیچ خطایی نمی‌گیری. لینکر یک تابع اضافه‌ی بی‌ربط می‌بیند و جدول همچنان به Default_Handler اشاره می‌کند. اگر وقفهٔ تو «کار نمی‌کند» و برنامه در Default_Handler گیر کرده، اول املای نام را بررسی کن.
  3. main خالی. فقط برای اینکه لینک کامل شود.

این فایل را (جای main.c) با همان vectors.c و startup.c و اسکریپت لینک کن (خروجی را ex3.elf بنام) و ببین:

$ arm-none-eabi-nm -n ex3.elf | grep -i 'Default\|EXTI'

0800015c T EXTI15_10_IRQHandler

$ arm-none-eabi-objdump -s -j .isr_vector ex3.elf | tail -2

حالا EXTI15_10_IRQHandler نوع T و آدرس خودش را دارد (0x0800015C)، و آخرین کلمهٔ جدول (ورودی ۵۶ در 0x080000E0) برابر 0x0800015D شده. ورودی قبلی که همه 0x080000E5 بود.

تله‌ها: چیزهایی که این‌جا خراب می‌شوند

۱. بهینه‌سازی حلقهٔ کپی را به memcpy تبدیل می‌کند

وقتی بدون -ffreestanding با -O2 بسازی، GCC حلقهٔ کپی را می‌شناسد و به‌جایش memcpy/memset صدا می‌زند. ولی چون -nostdlib کتابخانه را نیاورده، لینک شکست می‌خورد:

۳. جدول حذف می‌شود

اگر -Wl,--gc-sections (برای کوچک‌کردن برنامه؛ درس ۶.۵) بزنی و در اسکریپت KEEP را فراموش کنی، لینکر جدول را «بلااستفاده» می‌بیند و دور می‌ریزد. برنامه‌ات لینک می‌شود ولی روی برد هرگز اجرا نمی‌شود. KEEP و used برای همین‌اند.

۴. جدول اول Flash نیست

اگر در اسکریپت .text را قبل از .isr_vector بنویسی، اولین کلمهٔ Flash دستور خواهد بود، نه SP. CPU آن دستور را به‌عنوان آدرس پشته می‌خواند و برنامه بی‌دلیل خراب می‌شود. بعد از ساخت همیشه objdump -h را نگاه کن که .isr_vector در 0x08000000 باشد.

زیر کاپوت: استارت‌آپ رسمی ST

در پروژه‌های واقعی معمولا از فایل startup_stm32f411xe.s شرکت ST استفاده می‌کنی (اسمبلی، نه C) که همین کارها را می‌کند و کارهای اضافه هم دارد: صدا زدن SystemInit (تنظیم FPU و ...)، و صدا زدن __libc_init_array که سازنده‌های ایستا و ابتدایی‌سازی کتابخانهٔ C را اجرا می‌کند. اگر کتابخانهٔ C (printf، malloc) می‌خواهی، به‌جای -nostdlib از -nostartfiles استفاده می‌کنی تا فقط فایل‌های استارت‌آپ حذف شوند و خود کتابخانه بماند. جدول وقفهٔ کامل همان فایل ده‌ها ورودی بیشتر از جدول ما دارد. ایدهٔ همهٔ این‌ها همان چیزی است که این‌جا نوشتیم.

جدول را هم می‌شود جابه‌جا کرد: رجیستر SCB->VTOR (آدرس 0xE000ED08) آدرس شروع جدول را عوض می‌کند. bootloaderها و برنامه‌های چندتصویری از همین استفاده می‌کنند.

ESP32: همین داستان، با یک مقدمهٔ بیشتر

ESP32 هم «پیش از app_main» کارهایی می‌کند، ولی قطعه‌های زنجیره فرق دارند. تفاوت اصلی: کد برنامه روی Flash بیرونی است (و از طریق کش خوانده می‌شود)، و یک برنامهٔ دیگر به نام bootloader مسئول بوت است. زنجیره چنین است (ESP32 کلاسیک، ESP-IDF v5):

  1. کد ROM. بعد از reset، پردازنده اول کدی را اجرا می‌کند که در خود تراشه ثبت شده و عوض نمی‌شود. این کد بر پایهٔ پایه‌های strapping (مثلا GPIO0) تصمیم می‌گیرد آیا وارد حالت دانلود شود یا از Flash بوت کند.
  2. bootloader مرحلهٔ دوم. ROM آن را از Flash (آفست 0x1000 برای ESP32) در RAM بار می‌کند. bootloader جدول پارتیشن را (آفست 0x8000) می‌خواند تا بفهمد برنامه کجاست، تصویر را وارسی می‌کند و بخش‌های آن را در جای درستشان بار می‌کند.
  3. شروع برنامه. کد راه‌اندازی ESP-IDF: heap، FreeRTOS، و بعد شروع scheduler.
  4. app_main(). در یک task به نام «main» اجرا می‌شود. app_main مثل main در STM32 نیست: می‌تواند برگردد و task تمام شود. (درس ۵.۶)

می‌بینی؟ نقش‌ها یکی است: «چیزی باید قبل از برنامهٔ تو، حافظه را آماده کند». فرق این است که در ESP-IDF این کدها آماده‌اند و تو معمولا لازم نیست خودت بنویسی‌شان. اسکریپت لینکر و جدول پارتیشن هم در menuconfig (بخش Partition Table) قابل تغییرند.

آزمون این درس

بعد از reset در Cortex-M4، CPU چه چیزی را از دو کلمهٔ اول جدول وقفه می‌خواند؟

  1. آدرس main و اندازهٔ پشته
  2. اندازهٔ Flash و تعداد وقفه‌ها
  3. مقدار اولیهٔ SP و آدرس Reset_Handler
  4. آدرس .data و آدرس .bss
کلمهٔ اول → SP، کلمهٔ دوم → PC (آدرس Reset_Handler). بقیه را نرم‌افزار استارت‌آپ انجام می‌دهد.

چرا آدرس Reset_Handler در جدول 0x080000F9 است، در حالی که خود تابع در 0x080000F8 قرار دارد؟

  1. بیت ۰ برابر ۱ نشان می‌دهد تابع از نوع Thumb است (قرارداد Cortex-M)
  2. لینکر یک بایت فاصله بین جدول و کد می‌گذارد
  3. چون تابع باید فرد تراز شود
  4. اشتباه اسکریپت لینکر است و باید اصلاح شود
آدرس‌های Thumb در Cortex-M با بیت ۰ = ۱ نوشته می‌شوند. CPU بیت ۰ را حذف می‌کند و از آدرس زوج اجرا می‌کند. اگر ۰ باشد fault می‌دهد.

در C می‌نویسیم uint32_t g_total; (سراسری، بدون مقدار اولیه). چه چیزی تضمین می‌کند که در ابتدای main صفر باشد؟

  1. سخت‌افزار RAM را هنگام روشن‌شدن صفر می‌کند
  2. کامپایلر هنگام ترجمه صفر را در متغیر می‌گذارد
  3. لینکر موقع لینک، RAM را صفر می‌کند
  4. حلقهٔ صفر کردن .bss در Reset_Handler
قانون C «سراسری = صفر» توسط استارت‌آپ اجرا می‌شود. اگر استارت‌آپ نداشته باشی، g_total آشغال دارد.

کدام خط استارت‌آپ باگ دارد؟
uint32_t *src = &_sdata;
uint32_t *dst = &_sdata;
while (dst < &_edata) { *dst++ = *src++; }

  1. شرط dst < &_edata
  2. مبدأ src که باید &_sidata (تصویر در Flash) باشد
  3. کپی *dst++ = *src++
  4. نوع اشاره‌گرها
اگر src = &_sdata باشد، حلقه RAM را روی خودش کپی می‌کند و مقدارهای اولیه (مثل g_counter = 5) هرگز از Flash نمی‌آیند: مقدار آشغال می‌ماند.

در vectors.c نوشته‌ایم void SysTick_Handler(void) __attribute__((weak, alias("Default_Handler"))); و در main.c یک تابع void SysTick_Handler(void) { ... } تعریف کرده‌ایم. جدول به کدام اشاره می‌کند؟

  1. به تابع main.c (تعریف قوی، جای weak را می‌گیرد)
  2. به Default_Handler (چون weak زودتر آمده)
  3. لینک با خطای «multiple definition» شکست می‌خورد
  4. به آدرس نامعتبر
قانون: تعریف قوی بر weak برنده می‌شود. nm هم همین را نشان داد: SysTick_Handler در 0x0800015C با نوع T.

در ESP32 کلاسیک، اولین کدی که بعد از reset اجرا می‌شود چیست؟

  1. تابع app_main تو
  2. bootloader مرحلهٔ دوم
  3. کد ROM داخل تراشه
  4. جدول وقفه در آدرس 0x08000000
اول کد ROM (تغییرناپذیر)، بعد bootloader مرحلهٔ دوم از Flash، بعد برنامه، و آخر app_main داخل یک task.

تمرین‌ها

تمرین ۱: Flash و RAM چقدر شد؟

خروجی size برنامهٔ ما این بود: text=448 data=4 bss=8. حالا یک آرایهٔ ۱۰۰۰ بایتی سراسری به پروژه اضافه می‌کنیم. در دو حالت: بدون مقدار اولیه (uint8_t g_rx_buf[1000];) و با مقدار اولیه (uint8_t g_rx_buf[1000] = { 1 };).

  1. پیش‌بینی: در هر حالت، text و data و bss چقدر می‌شود؟ (Flash مصرفی = text + data.)
  2. حل: هر دو را با همان دستور بساز و size را بگیر.
  3. سؤال: چرا حالت دوم Flash را ۱۰۰۰ بایت بیشتر می‌کند ولی اولی نه؟
راهنمایی

بخش .bss فقط RAM می‌گیرد. بخش .data هم RAM می‌گیرد هم یک تصویر در Flash دارد. مقدار اولیهٔ { 1 } بقیهٔ عنصرها را صفر می‌کند، ولی آرایه هنوز جزو .data است، چون یک عنصر غیرصفر دارد.

چه باید ببینی؟ 
$ arm-none-eabi-size buf_bss.elf buf_data.elf
   text	   data	    bss	    dec	    hex	filename
    448	      4	   1008	   1460	    5b4	buf_bss.elf
    448	   1004	      8	   1460	    5b4	buf_data.elf

Flash مصرفی: 448 + 4 = 452 در حالت اول (تغییری نکرد)، و 448 + 1004 = 1452 در حالت دوم. RAM مصرفی هر دو 1012 بایت (حالت اول: ۴+۱۰۰۸، حالت دوم: ۱۰۰۴+۸).

جواب کامل با توضیح

uint8_t g_rx_buf[1000] = { 1 };     // حالت دوم: .data

سؤال ج: آرایهٔ بدون مقدار اولیه به .bss می‌رود. مقدارش صفر است و لازم نیست در Flash ذخیره شود؛ استارت‌آپ صفرش می‌کند. آرایهٔ با { 1 } عنصر اولش ۱ است، پس .data است و کل ۱۰۰۰ بایتش (با صفرها!) در Flash ذخیره می‌شود تا استارت‌آپ کپی کند.

درس کاربردی: بافرهای بزرگ را با مقدار اولیهٔ غیرصفر نساز. اگر لازم است مقدار بدهی، در تابع init بده.

#include <stdint.h>

uint8_t g_rx_buf[1000] = { 1 };     /* سراسری با مقدار اولیه */
  1. آرایهٔ ۱۰۰۰ بایتی. تنها یک عنصر غیرصفر ({ 1 }) کافی است تا کل آرایه در .data باشد. کامپایلر باید بتواند «مقدار اولیه» را از Flash کپی کند؛ بنابراین تصویر کامل ۱۰۰۰ بایت ذخیره می‌شود.
تمرین ۲: باگ در استارت‌آپ

دوستت استارت‌آپ را با همان «تراشهٔ اسباب‌بازی» PC امتحان کرده و نتیجه عجیب است: .data همان مقدار ۵ شده و .bss هنوز آشغال دارد. دو باگ در حلقه‌ها هست.

#include <stdio.h>
#include <stdint.h>

/* «تراشهٔ اسباب‌بازی»: آرایه‌ها نقش Flash و RAM را بازی می‌کنند */
static const uint32_t flash_image[3] = { 5, 7, 9 };   /* مقدارهای اولیهٔ .data */
static uint32_t ram[8];      /* کلمهٔ 0..2: .data ، 3..5: .bss ، 6..7: آزاد */

static void dump(const char *title)
{
    printf("%-12s", title);
    for (int i = 0; i < 8; i++) {
        printf(" %08lX", (unsigned long)ram[i]);
    }
    printf("\n");
}

int main(void)
{
    uint32_t *sdata = &ram[0];
    uint32_t *edata = &ram[3];
    uint32_t *sbss  = &ram[3];
    uint32_t *ebss  = &ram[6];

    printf(".data = %ld words, .bss = %ld words\n",
           (long)(edata - sdata), (long)(ebss - sbss));

    for (int i = 0; i < 8; i++) {
        ram[i] = 0xDEADBEEFu;               /* برق وصل شد: آشغال */
    }
    dump("power on:");

    const uint32_t *src = flash_image;
    uint32_t *dst = sdata;
    while (dst < edata) {
        *dst++ = *src;                      /* کپی .data */
    }
    dump("after copy:");

    for (dst = sbss; dst < edata; dst++) {
        *dst = 0;                           /* صفر کردن .bss */
    }
    dump("after zero:");
    return 0;
}
  1. پیش‌بینی: بدون اجرا، با نگاه به دو حلقه حدس بزن چه چاپ می‌شود.
  2. حل: هر دو باگ را پیدا کن و اصلاح کن.
  3. فکر کن: اگر این باگ‌ها روی برد واقعی بودند، برنامه با چه نشانه‌ای خراب می‌شد؟
راهنمایی

حلقهٔ اول را با دقت بخوان: اشاره‌گر src چه می‌شود؟ حلقهٔ دوم: تا کجا صفر می‌نویسد؟ (سه نشانگر edata، sbss و ebss را مقایسه کن.)

جواب کامل با توضیح
  1. باگ ۱: در حلقهٔ کپی *dst++ = *src; نوشته‌ای: src جلو نمی‌رود، پس همهٔ کلمه‌ها ۵ (اولین مقدار تصویر) می‌شوند. باید *src++ باشد.
  2. باگ ۲: شرط حلقهٔ صفر dst < edata است. چون edata همان sbss است (شروع bss)، حلقه یک دور هم اجرا نمی‌شود. باید dst < ebss باشد.

روی برد واقعی: باگ ۱ باعث می‌شود متغیرهای .data مقدار اولیهٔ اشتباه بگیرند (مثلا همهٔ ثابت‌های پیکربندی برابر اولین‌شان)، و باگ ۲ باعث می‌شود متغیرهای سراسری «بدون مقدار» آشغال باشند. علامتش: هر بار که برد را reset می‌کنی رفتار فرق می‌کند، چون آشغال RAM تصادفی است. همین را «باگ گاهی‌اتفاق‌می‌افتد» می‌گویند و پیدا کردنش سخت است.

#include <stdio.h>
#include <stdint.h>

/* «تراشهٔ اسباب‌بازی»: آرایه‌ها نقش Flash و RAM را بازی می‌کنند */
static const uint32_t flash_image[3] = { 5, 7, 9 };   /* مقدارهای اولیهٔ .data */
static uint32_t ram[8];      /* کلمهٔ 0..2: .data ، 3..5: .bss ، 6..7: آزاد */

static void dump(const char *title)
{
    printf("%-12s", title);
    for (int i = 0; i < 8; i++) {
        printf(" %08lX", (unsigned long)ram[i]);
    }
    printf("\n");
}

int main(void)
{
    uint32_t *sdata = &ram[0];
    uint32_t *edata = &ram[3];
    uint32_t *sbss  = &ram[3];
    uint32_t *ebss  = &ram[6];

    printf(".data = %ld words, .bss = %ld words\n",
           (long)(edata - sdata), (long)(ebss - sbss));

    for (int i = 0; i < 8; i++) {
        ram[i] = 0xDEADBEEFu;               /* برق وصل شد: آشغال */
    }
    dump("power on:");

    const uint32_t *src = flash_image;
    uint32_t *dst = sdata;
    while (dst < edata) {
        *dst++ = *src++;                    /* کپی .data */
    }
    dump("after copy:");

    for (dst = sbss; dst < ebss; dst++) {
        *dst = 0;                           /* صفر کردن .bss */
    }
    dump("after zero:");
    return 0;
}
  1. حلقهٔ کپی درست. src++ و dst++ با هم.
  2. حلقهٔ صفر درست. از sbss تا ebss. در نمونهٔ اسباب‌بازی، مقدار ebss را با چاپ اندازهٔ bss (خط ۲۴) هم بررسی می‌کنیم: سه کلمه.

چه باید ببینی؟

آخرین کلمه 0x0800015D است که همان EXTI15_10_IRQHandler (0x0800015C) با بیت Thumb است. ورودی قبل‌ترها هنوز 0x080000E5 (Default_Handler) هستند.

جواب کامل با توضیح
  1. الف) بایت‌های 5d 01 00 08 در little-endian یعنی کلمهٔ 0x0800015D. آدرس تابع 0x0800015C است (بیت ۰ = پرچم Thumb). طبق nm این آدرس EXTI15_10_IRQHandler است.
  2. ب) شمارهٔ ورودی = ۵۶. آدرس = 0x08000000 + 4 × 56 = 0x08000000 + 224 = 0x080000E0 ✓ (۲۲۴ = 0xE0).
  3. پ) شمارهٔ ورودی = 16 + 40 = 56. جدول باید حداقل ۵۷ ورودی (شماره‌های ۰ تا ۵۶) باشد تا این وقفه داخلش باشد؛ برای همین ۵۷ گذاشتیم. اگر وقفه‌ای با شمارهٔ بزرگ‌تر فعال کنی، باید جدول را بلندتر کنی؛ وگرنه CPU از بیرون جدول می‌خواند و به آدرس آشغال می‌پرد.

حرف مربی

بیشتر برنامه‌نویس‌های embedded عمر خود را با استارت‌آپ آمادهٔ سازنده می‌گذرانند و اسکریپت لینکر را هرگز باز نمی‌کنند... تا روزی که برنامه بی‌دلیل خراب شود: متغیر سراسری مقدار غلط می‌گیرد، RAM پر می‌شود، یا وقفه‌ای به‌جای handler خودش به Default_Handler می‌رود. کسی که این درس را فهمیده، آن روز اول size و nm و objdump -h را باز می‌کند و در پنج دقیقه علت را می‌بیند. این ابزارها بعد از هر تغییر بزرگ ۵ ثانیه وقت می‌گیرند؛ عادتشان کن. اگر جایی گیج شدی، به نگاره‌های درس برگرد: جدول اول Flash، .data دو آدرس دارد، و Reset_Handler قبل از main می‌آید.

خلاصه یک‌دقیقه‌ای

  • بعد از reset، Cortex-M دو کلمه می‌خواند: SP (آدرس 0x0، آینهٔ Flash) و PC = Reset_Handler (آدرس 0x4). بیت ۰ در آدرس تابع = Thumb.
  • جدول وقفه = آرایهٔ اشاره‌گر تابع در ابتدای Flash (.isr_vector). ورودی n در 0x08000000 + 4n؛ وقفهٔ n ام تراشه ورودی n + ۱۶.
  • اسکریپت لینکر: MEMORY (منطقه‌ها)، SECTIONS (چیدمان)، .data > RAM AT > FLASH و نمادهای _sidata _sdata _edata _sbss _ebss _estack.
  • Reset_Handler: کپی .data از Flash، صفر کردن .bss، راه‌اندازی سیستم، main، و حلقهٔ بی‌نهایت. قبل از این حلقه‌ها به سراسری‌ها تکیه نکن.
  • وقفه‌های weak با alias به Default_Handler؛ تعریف هم‌نام قوی جایش را می‌گیرد.
  • ابزارها: objdump -h (بخش‌ها، VMA/LMA)، size (Flash = text + data؛ RAM = data + bss)، nm -n (نمادها)، objdump -s (بایت‌ها).
  • ESP32: کد ROM ← bootloader مرحلهٔ دوم (Flash 0x1000) ← جدول پارتیشن (0x8000) ← برنامه ← app_main در یک task.
