تا اینجا هر متغیری که ساختی، اندازه‌اش را همان لحظهٔ نوشتن کد می‌دانستی: int a[10] یعنی دقیقا ده عدد. ولی گاهی اندازه را فقط وقتی برنامه در حال اجراست می‌فهمی: کاربر چند نمونه سنسور خواست؟ فایل چند بایت است؟ C برای این حالت یک «انبار» دارد که هر وقت خواستی از آن جعبه می‌گیری و خودت باید پس بدهی. این انبار جادویی به نظر می‌رسد و در برنامه‌های PC بی‌دردسر است؛ اما در میکروکنترلر، که ماه‌ها بدون خاموش‌شدن کار می‌کند و فقط چند کیلوبایت RAM دارد، همین انبار منبع باگ‌های سخت و «گاهی خراب می‌شود» است. در این درس هم راه‌استفاده را یاد می‌گیری، هم دلیل احتیاط را می‌بینی، هم جایگزین‌های امن را.

🎯 بعد از این درس می‌توانی

  • با malloc، calloc، realloc و free درست کار کنی و همیشه NULL را بررسی کنی
  • چهار باگ کلاسیک را بشناسی: نشتی، استفادهٔ بعد از free، free دوباره، سرریز بلوک
  • با -fsanitize=address روی PC این باگ‌ها را پیدا کنی
  • توضیح بدهی fragmentation چیست و چرا کلِ فضای آزاد گاهی کافی نیست
  • بدانی چرا کد ایمن و MISRA malloc را کنار می‌گذارد و به‌جایش چه می‌گذارند (تخصیص ایستا و memory pool)

🧰 پیش‌نیاز و وسایل

  • درس ۳.۲ و ۳.۳: اشاره‌گر، NULL، آویزان‌بودن، حساب اشاره‌گر
  • درس ۳.۵: نقشهٔ حافظه (heap و stack)
  • درس ۳.۴: struct و padding
  • کامپایلر gcc روی PC (برای sanitizer). هیچ سخت‌افزاری لازم نیست

ایدهٔ اصلی: کمد امانات فرودگاه

تا حالا حافظه را مثل اتاق خودت استفاده می‌کردی: وسایلی که از اول در برنامه نوشته‌ای، خودکار جا می‌گیرند و وقتی تابع تمام شد خودکار جمع می‌شوند (متغیر محلی روی پشته بود؛ درس ۳.۵). حالا فرض کن به فرودگاه رفته‌ای و می‌خواهی چمدانت را تا شب جایی بگذاری. می‌روی سراغ کمدهای امانات: به دستگاه می‌گویی «یک کمد به این اندازه بده»، دستگاه یک شماره و کلید می‌دهد، تو هر وقت خواستی برمی‌گردی و کمد را باز می‌کنی. ولی خودت باید یادت بماند کمد را پس بدهی. اگر کلید را گم کنی، کمد تا ابد اشغال می‌ماند.

مثال از زندگی روزمره

دستگاه کمد امانات = malloc. شماره و کلید = اشاره‌گری که برمی‌گرداند. پس‌دادن کمد = free. اگر کمدها تمام شده باشند، دستگاه «موجود نیست» می‌گوید = malloc مقدار NULL برمی‌گرداند. اگر کلید را گم کنی = نشتی حافظه (memory leak). اگر کمد را پس بدهی ولی بعدا با همان کلید بروی و در بزنی، ممکن است چمدان یک غریبه را باز کنی = استفاده بعد از free.

در C این کار را تخصیص پویا می‌گویند و «کمدهای امانات» در ناحیه‌ای از RAM به اسم heap (انبار) هستند. تابع‌های لازم در stdlib.h اعلان شده‌اند:

تابعکاردر صورت شکست
malloc(n)یک بلوک n بایتی می‌دهد؛ محتویاتش آشغال استNULL
calloc(count, size)بلوک count × size بایتی، همه صفرNULL
realloc(p, n)بلوک p را به اندازهٔ n بزرگ/کوچک می‌کند (ممکن است جابه‌جا شود)NULL (و بلوک قدیمی سالم می‌ماند)
free(p)بلوک را پس می‌دهد—

اولین تخصیص

الگوی درست همیشه چهار قدم دارد: بگیر ← بررسی کن ← استفاده کن ← پس بده. اندازه را با sizeof *اشاره‌گر بنویس، نه عدد جادویی.

#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int count = 5;
    int *values = malloc(count * sizeof *values);   // بگیر
    if (values == NULL) {                           // بررسی کن
        printf("out of memory\n");
        return 1;
    }

    for (int i = 0; i < count; i++) {
        values[i] = (i + 1) * 10;                   // استفاده کن
    }
    int sum = 0;
    for (int i = 0; i < count; i++) {
        sum += values[i];
    }
    printf("sum = %d (used %zu bytes)\n", sum, count * sizeof *values);

    free(values);                                   // پس بده
    values = NULL;                                  // دیگر آویزان نیست
    return 0;
}
  1. سرآیندها. stdlib.h اعلان malloc و free را دارد.
  2. گرفتن. count * sizeof *values یعنی «پنج تا از هر چه values به آن اشاره می‌کند». malloc آدرس اولین بایت را برمی‌گرداند و به‌صورت void * در values می‌نشیند. نوشتن sizeof *values به‌جای sizeof(int) یعنی اگر فردا نوع را عوض کنی، اندازه خودکار درست می‌ماند. malloc فقط «بایت» می‌شناسد؛ ضرب در اندازهٔ هر عضو با خودت است.
  3. بررسی NULL. اگر انبار پر بود، malloc NULL می‌دهد. اینجا خطا را گزارش می‌دهیم و برمی‌گردیم. فراموشی این if یعنی اولین بار که حافظه تمام شود، به NULL[0] می‌نویسی و برنامه خراب می‌شود. روی PC معمولا «هرگز» پیش نمی‌آید و همین باعث می‌شود بررسی را فراموش کنند؛ روی میکروکنترلر خیلی زود پیش می‌آید.
  4. استفاده. یک بلوک malloc مثل آرایه است؛ values[i] کار می‌کند (درس ۳.۳: a[i] یعنی *(a+i)). محتویات بلوک تازه آشغال است. اینجا قبل از خواندن، خودمان همه را نوشته‌ایم.
  5. چاپ. %zu برای size_t. ۵ عدد × ۴ بایت = ۲۰ بایت.
  6. پس‌دادن و پاک کردن اشاره‌گر. free(values) بلوک را به انبار برمی‌گرداند؛ ولی متغیر values هنوز همان آدرس را دارد. با NULL کردنش، استفادهٔ اشتباه بعدی زود و واضح خراب می‌شود، نه بی‌صدا. آدرسِ بلوکِ پس‌داده‌شده «آویزان» است (درس ۳.۲). free(NULL) در C کاملا بی‌خطر است و کاری نمی‌کند؛ پس NULL کردن اجازه می‌دهد اگر اشتباها دوباره free شد، اتفاقی نیفتد.
$ gcc -std=c11 -Wall -Wextra -o malloc_basic malloc_basic.c
$ ./malloc_basic
sum = 150 (used 20 bytes)

calloc و realloc: صفر و بزرگ‌کردن

calloc(count, size) دو کار می‌کند: بلوک را می‌گیرد و همه را صفر می‌کند. علاوه بر این، خودش ضرب count × size را بررسی می‌کند که سرریز نکند (اگر سرریز کند NULL می‌دهد)؛ در حالی که malloc(count * size) ضرب را بی‌مراقبت انجام می‌دهد و ممکن است یک عدد کوچکِ اشتباه بسازد. پس برای آرایه‌ها calloc امن‌تر است.

realloc(p, n) برای «بلوک را بزرگ‌تر کن» است: اگر جای کافی پشت بلوک نباشد، بلوک تازه می‌گیرد، محتوا را کپی می‌کند و بلوک قدیمی را خودش آزاد می‌کند. پس آدرس ممکن است عوض شود. تلهٔ مشهور: نوشتن p = realloc(p, n)؛ اگر شکست بخورد، NULL در p می‌نشیند و آدرس بلوک قدیمی (که هنوز سالم است) برای همیشه گم می‌شود. راه درست: یک متغیر موقت.

#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    size_t capacity = 2;
    size_t length = 0;
    int *items = malloc(capacity * sizeof *items);
    if (items == NULL) {
        return 1;
    }

    for (int v = 1; v <= 5; v++) {
        if (length == capacity) {                   // پر شد؛ دو برابر کن
            size_t new_capacity = capacity * 2;
            int *bigger = realloc(items, new_capacity * sizeof *bigger);
            if (bigger == NULL) {
                free(items);                        // قدیمی هنوز سالم است
                return 1;
            }
            items = bigger;
            capacity = new_capacity;
            printf("grew to %zu\n", capacity);
        }
        items[length] = v * v;
        length++;
    }

    printf("items:");
    for (size_t i = 0; i < length; i++) {
        printf(" %d", items[i]);
    }
    printf("\nlength=%zu capacity=%zu\n", length, capacity);

    free(items);
    return 0;
}
  1. ظرفیت و طول. capacity یعنی «جا برای چند عضو گرفته‌ام»؛ length یعنی «چند عضو واقعا پر است». جداکردن این دو، الگوی همهٔ آرایه‌های پویاست (مثل vector در C++ یا list در Python). هر بار که پر شد، ظرفیت را دو برابر می‌کنند تا تعداد realloc ها کم بماند.
  2. وقتی پر شد. ظرفیت جدید را حساب می‌کند و نتیجهٔ realloc را در متغیر موقت bigger می‌گیرد. اگر مستقیم به items می‌دادیم و realloc شکست می‌خورد، items می‌شد NULL و بلوک قدیمی گم می‌شد (نشتی).
  3. شکست. بلوک قدیمی هنوز مال ماست؛ پس آزادش می‌کنیم و خارج می‌شویم.
  4. موفقیت. حالا items را به بلوک تازه می‌بریم. آدرس قدیمی items دیگر معتبر نیست (realloc آن را آزاد کرده). هر اشاره‌گر دیگری هم که به داخل بلوک قدیمی داشتی آویزان شده است.
  5. افزودن عضو. همان items[length] معمولی.
$ ./grow
grew to 4
grew to 8
items: 1 4 9 16 25
length=5 capacity=8

چهار باگ کلاسیک heap

هر کدام از این‌ها روی PC ممکن است «بی‌صدا» کار کند و روی میکروکنترلر یک ماه بعد خودش را نشان بدهد. اول توضیح، بعد ابزاری که پیدایشان می‌کند.

۱. نشتی حافظه (memory leak)

نشتی یعنی بلوک را گرفته‌ای ولی آدرسش را از دست داده‌ای و نمی‌توانی free کنی. بلوک تا پایان برنامه اشغال می‌ماند. روی PC با پایان برنامه سیستم‌عامل همه چیز را جمع می‌کند؛ ولی روی میکروکنترلر برنامه هرگز تمام نمی‌شود. اگر در هر دور حلقهٔ اصلی ۱۶ بایت نشت کند و ۱۰ بار در ثانیه اجرا شود، RAM ۱۲۸ کیلوبایتی طی چند ساعت تمام است.

#include <stdlib.h>

int main(void)
{
    int *p = malloc(10 * sizeof *p);
    if (p == NULL) {
        return 1;
    }
    p[0] = 42;
    return 0;                       // free فراموش شد!
}
  1. گرفتن ۴۰ بایت. ده int چهار بایتی.
  2. خروج بدون free. برنامه تمام می‌شود و بلوک ۴۰ بایتی هرگز پس داده نمی‌شود. روی PC سیستم‌عامل بعد از خروج همهٔ حافظهٔ برنامه را پس می‌گیرد؛ پس اثری نمی‌بینی. ولی وقتی این کد داخل یک تابع باشد که هزار بار صدا زده شود، هزار بلوک نشت می‌کند.

بدون sanitizer این برنامه کاملا بی‌صدا تمام می‌شود و هیچ نشانه‌ای از خطا نمی‌بینی. ولی sanitizer (ابزاری که به کد دستورهای اضافه برای شکار باگ حافظه می‌دهد) با -fsanitize=address همه‌چیز را زیر نظر می‌گیرد و در پایان برنامه گزارش می‌دهد؛ برنامه با کد خروج ۱ (یعنی «خطا») تمام می‌شود:

$ ./leak

۲. استفاده بعد از free و free دوباره

بلوک را پس داده‌ای، ولی هنوز آدرسش در یک اشاره‌گر است. اگر بخوانی/بنویسی، به حافظه‌ای دست می‌زنی که ممکن است همین حالا مال کس دیگری باشد. دو حالت مشهور:

  • use-after-free: خواندن یا نوشتن از طریق اشاره‌گر آویزان.
  • double free: دوبار free کردن همان آدرس. مدیریت داخلی heap را خراب می‌کند و ممکن است ماه‌ها بعد، در یک malloc کاملا بی‌ربط، برنامه را زمین بزند.
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *p = malloc(sizeof *p);
    if (p == NULL) {
        return 1;
    }
    *p = 7;
    free(p);
    printf("%d\n", *p);             // باگ: p آویزان است
    return 0;
}
  1. پس دادن. بلوک دیگر مال ما نیست.
  2. خواندن آویزان. *p از حافظه‌ای می‌خواند که آزاد شده. ممکن است ۷ بخوانی، ممکن است آشغال؛ رفتار تعریف‌نشده است. بعد از free، مدیریت heap ممکن است بلوک را فورا به درخواست بعدی malloc بدهد؛ آن‌وقت دو بخش از برنامه به یک بلوک می‌نویسند و همدیگر را خراب می‌کنند. باگی که فقط «گاهی» رخ می‌دهد.

۳. نوشتن بیرون از بلوک

بلوکت ۴ عضو دارد ولی حلقه تا ایندکس ۴ (پنجمین) می‌رود؛ همان off-by-one آشنای درس ۲.۵ و ۲.۷. اینجا هیچ چیز «آرایه» نیست که کامپایلر بشناسد؛ فقط یک آدرس است.

#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *v = malloc(4 * sizeof *v);
    if (v == NULL) {
        return 1;
    }
    for (int i = 0; i <= 4; i++) {          // باگ: باید i < 4
        v[i] = i;
    }
    printf("done\n");
    free(v);
    return 0;
}
  1. ۴ عضو، یعنی ایندکس ۰ تا ۳.
  2. حلقهٔ یکی‌زیاد. <= باعث می‌شود v[4] هم نوشته شود؛ ۴ بایت بعد از پایان بلوک. آن چهار بایت شاید بخشی از هدر بلوک بعدی یا فضای پُرکنندهٔ heap باشد. روی PC اغلب چیزی نمی‌شود و برنامه «done» چاپ می‌کند؛ ولی هدر heap ممکن است خراب شده باشد و free بعدی از کار بیفتد.

۴. اندازهٔ اشتباه

شکل نامرئی: fragmentation

فرض کن پارکینگی با ۱۶ جا داری. پنج ماشین سه‌جایی (اتوبوس کوچک) پشت‌سرهم پارک کرده‌اند. سپس ماشین دوم و چهارم می‌روند. الان ۷ جای خالی داری، ولی یک ماشین پنج‌جایی که بیاید، جا ندارد: جاهای خالی پراکنده‌اند و هیچ کدام به‌تنهایی ۵ تایی نیست. در heap هم دقیقا همین است و اسمش fragmentation (تکه‌تکه‌شدگی) است.

این را با یک heap اسباب‌بازی شبیه‌سازی می‌کنیم: ۱۶ واحد، تخصیص «اولین جای خالیِ به‌اندازهٔ کافی» (first-fit). برنامه هر بار وضعیت را چاپ می‌کند. (این heap واقعی نیست؛ فقط برای دیدن پدیده است.)

#include <stdio.h>

#define UNITS 16                    // ۱۶ واحد

static char owner[UNITS];           // '.' یعنی آزاد؛ حرف یعنی مال کدام بلوک

static void show(const char *label)
{
    printf("%-12s |%.*s|\n", label, UNITS, owner);
}

// اولین جای خالیِ پشت‌سرهمِ به طول n را پیدا کن؛ نبود: -1
static int toy_alloc(int n, char id)
{
    for (int start = 0; start + n <= UNITS; start++) {
        int ok = 1;
        for (int i = 0; i < n; i++) {
            if (owner[start + i] != '.') {
                ok = 0;
                break;
            }
        }
        if (ok) {
            for (int i = 0; i < n; i++) {
                owner[start + i] = id;
            }
            return start;
        }
    }
    return -1;
}

static void toy_free(char id)
{
    for (int i = 0; i < UNITS; i++) {
        if (owner[i] == id) {
            owner[i] = '.';
        }
    }
}

static int free_total(void)
{
    int n = 0;
    for (int i = 0; i < UNITS; i++) {
        n += (owner[i] == '.');
    }
    return n;
}

int main(void)
{
    for (int i = 0; i < UNITS; i++) {
        owner[i] = '.';
    }

    toy_alloc(3, 'A');
    toy_alloc(3, 'B');
    toy_alloc(3, 'C');
    toy_alloc(3, 'D');
    toy_alloc(3, 'E');
    show("5 allocs");

    toy_free('B');
    toy_free('D');
    show("free B, D");
    printf("free units: %d\n", free_total());

    int r = toy_alloc(5, 'F');
    printf("alloc 5 units: %s\n", r < 0 ? "FAILED" : "ok");
    return 0;
}
  1. نقشهٔ heap. یک حرف برای هر واحد: . یعنی آزاد، حرف یعنی «مال بلوک این حرف».
  2. نمایش. نقشه را در یک خط چاپ می‌کند. %.*s یعنی «رشته را با طول داده‌شده چاپ کن» (درس ۲.۸)؛ چون owner پایان '\0' ندارد لازم است.
  3. تخصیص first-fit. از ابتدای heap می‌گردد و اولین جایی را که n واحد آزادِ پشت‌سرهم باشد می‌گیرد. اگر نبود -1. کلمهٔ «پشت‌سرهم» کلید ماجراست. بلوک باید یک تکهٔ پیوسته باشد؛ نمی‌شود سه واحد از این‌جا و دو واحد از آن‌جا جمع کرد.
  4. آزاد کردن. همهٔ واحدهای یک بلوک را دوباره . می‌کند.
  5. مجموع آزادها. فقط تعداد . ها را می‌شمارد.
  6. پنج بلوک سه‌واحدی. ۱۵ واحد پر، یک واحد خالی.
  7. آزاد کردن ب و د. ۷ واحد آزاد ولی در سه تکه (۳، ۳ و ۱).
  8. درخواست ۵ واحد. toy_alloc(5) هیچ تکهٔ پیوستهٔ ۵ تایی پیدا نمی‌کند و شکست می‌خورد.
$ ./toy_heap
5 allocs     |AAABBBCCCDDDEEE.|
free B, D    |AAA...CCC...EEE.|
free units: 7
alloc 5 units: FAILED

نکتهٔ ترسناک: هیچ نشتی‌ای رخ نداده و هیچ باگی در کد نیست؛ فقط ترتیب تخصیص و آزادسازی باعث شد. در دستگاهی که ماه‌ها روشن است، تخصیص‌ها و آزادسازی‌های با اندازه‌های مختلف، heap را کم‌کم مثل پنیر سوراخ‌سوراخ می‌کنند و یک روز malloc شکست می‌خورد، هرچند «کلی» جا آزاد است. این را با تست چند دقیقه‌ای پیدا نمی‌کنی.

چرا در میکروکنترلر احتیاط می‌کنیم؟

خلاصهٔ دلایل، به ترتیب اهمیت:

  1. هیچ‌کس نیست که جمع کند. برنامهٔ PC تمام می‌شود و سیستم‌عامل همه چیز را پس می‌گیرد. میکروکنترلر هرگز «تمام نمی‌شود»؛ هر نشتی و هر تکه‌تکه‌شدگی انباشته می‌شود.
  2. RAM بسیار کم است. ۱۲۸ کیلوبایت در STM32F411 (و برای بعضی مدل‌ها حتی چند کیلوبایت). یک نشتی کوچک هم آخرش RAM را می‌بلعد. و در STM32 heap و پشته در یک RAM هستند و به هم نزدیک می‌شوند (شکل درس ۳.۵)؛ heap پرشده یعنی پشته هم جا ندارد.
  3. زمان اجرا قابل‌پیش‌بینی نیست. malloc باید جای مناسب را بگردد؛ زمانش به وضعیت heap بستگی دارد. در سیستمی که باید هر ۱ میلی‌ثانیه پاسخ بدهد (درس ۵.۴) این عدم‌قطعیت بد است. در ISR هم که اصلا نباید malloc صدا زد.
  4. شکست را نمی‌شود پنهان کرد. اگر malloc در وسط کنترل موتور شکست بخورد، چه کنی؟ روی PC می‌گویی «حافظه کم است، خروج». روی دستگاه واقعی راه خوبی وجود ندارد.
  5. ابزار سخت‌تر است. sanitizer ها معمولا روی خود MCU نیستند؛ باگ‌ها را باید با دیباگر و دقت پیدا کنی.

به همین دلیل استانداردهای کد ایمن صراحتا موضوع را گفته‌اند: MISRA C:2012 قانون ۲۱.۳ استفاده از توابع تخصیص حافظهٔ stdlib.h را ممنوع می‌کند، و قاعدهٔ معروف «Power of 10» (نوشتهٔ Gerard Holzmann از JPL) می‌گوید بعد از راه‌اندازی، تخصیص پویا نکن. (درس ۶.۳ این استانداردها را بیشتر باز می‌کند.)

«هرگز» نیست؛ «حساب‌شده» است

این به معنای ممنوعیت مطلق نیست. برنامه‌های ESP32 با Wi-Fi و TLS خودشان مدام از heap استفاده می‌کنند (خود ESP-IDF این‌طور طراحی شده). قاعده این است: اگر لازم شد، فقط یک‌بار در شروع برنامه (قبل از حلقهٔ اصلی) بگیر و تا پایان نگه دار؛ همیشه NULL را چک کن؛ و برای داده‌های تکراری از جایگزین‌های زیر استفاده کن.

جایگزین‌ها: ایستا و memory pool

راه اول: تخصیص ایستا

ساده‌ترین جایگزین: بدترین حالت را حدس بزن و آرایهٔ ثابت بساز. static uint8_t rx_buf[64]; در زمان کامپایل جا می‌گیرد (بخش .bss؛ درس ۳.۵)، هرگز تمام نمی‌شود، هرگز تکه‌تکه نمی‌شود و مصرف RAM را همان‌جا در فایل map می‌بینی. اگر ۱۰ بسته لازم داری، ۱۰ تا بگذار؛ اگر ۱۱ ام رسید، تصمیم طراحی است: رد کن، بنویس روی قدیمی‌ترین (بافر حلقوی، درس ۴.۵) یا گزارش خطا بده.

راه دوم: memory pool

گاهی تعداد بلوک‌ها معلوم نیست ولی همهٔ بلوک‌ها هم‌اندازه‌اند (مثلا «پیام UART»). آن‌وقت یک memory pool (استخر حافظه) می‌سازی: آرایه‌ای از N بلوک هم‌اندازه، از قبل در RAM و فهرستی از بلوک‌های آزاد. گرفتن = برداشتن یکی از فهرست، پس‌دادن = برگرداندن به فهرست. هر دو در زمان ثابت انجام می‌شوند و چون همه هم‌اندازه‌اند، هرگز fragmentation ندارند.

#include <stdio.h>
#include <stdint.h>
#include <stddef.h>

#define BLOCK_COUNT 4

typedef struct {
    uint16_t id;
    int16_t  value;
} packet_t;

static packet_t storage[BLOCK_COUNT];       // همهٔ بلوک‌ها از قبل در RAM هستند
static packet_t *free_list[BLOCK_COUNT];    // آدرس بلوک‌های آزاد
static int free_count;

static void pool_init(void)
{
    for (int i = 0; i < BLOCK_COUNT; i++) {
        free_list[i] = &storage[BLOCK_COUNT - 1 - i];
    }
    free_count = BLOCK_COUNT;
}

static packet_t *pool_alloc(void)
{
    if (free_count == 0) {
        return NULL;                        // پر است؛ تصمیمش با صدا زننده
    }
    free_count--;
    return free_list[free_count];
}

static void pool_free(packet_t *p)
{
    if (p == NULL) {
        return;
    }
    free_list[free_count] = p;
    free_count++;
}

static int index_of(const packet_t *p)
{
    return (int)(p - storage);
}

int main(void)
{
    pool_init();

    packet_t *a = pool_alloc();
    packet_t *b = pool_alloc();
    packet_t *c = pool_alloc();
    packet_t *d = pool_alloc();
    packet_t *e = pool_alloc();
    printf("a=%d b=%d c=%d d=%d e=%s\n", index_of(a), index_of(b), index_of(c), index_of(d), e == NULL ? "NULL" : "?");

    pool_free(b);
    packet_t *f = pool_alloc();
    printf("after free(b): f=%d, free=%d\n", index_of(f), free_count);
    return 0;
}
  1. نوع بلوک. یک بستهٔ کوچک. همهٔ بلوک‌های استخر از همین نوع‌اند؛ پس هم‌اندازه.
  2. حافظهٔ ثابت. storage آرایهٔ چهار بسته است که از قبل جا دارد؛ free_list آدرس بلوک‌های آزاد است. هر دو static اند؛ در .bss قرار می‌گیرند و در فایل map قابل‌مشاهده‌اند. هیچ mallocای در کار نیست.
  3. مقداردهی. اول همهٔ بلوک‌ها آزادند. (به‌صورت معکوس می‌چینیم تا اولین گرفتن، بلوک صفر باشد.)
  4. گرفتن. اگر آزادی نیست، NULL؛ وگرنه آخرین آدرس فهرست را بیرون می‌آورد. هزینه‌اش چند دستور ثابت است، مستقل از اینکه چند بلوک گرفته شده باشند. برای همین در حلقه‌های حساس زمانی هم قابل‌استفاده است.
  5. پس دادن. آدرس را دوباره در فهرست می‌گذارد. این نسخه از double free محافظت نمی‌کند (اگر دوبار pool_free(b) شود، فهرست خراب می‌شود). نسخهٔ حرفه‌ای‌تر یک پرچم «در استفاده» در هر بلوک یا بررسی اندازه دارد؛ تمرین ۳ همین فکر را دنبال می‌کند.
  6. شمارهٔ بلوک. تفریق دو اشاره‌گر به عضو‌های یک آرایه، اندیس را می‌دهد (درس ۳.۳).
  7. پنج درخواست از چهار بلوک. پنجمی NULL می‌گیرد؛ این تصمیم طراحی توست که چه شود.
  8. پس دادن و دوباره گرفتن. بلوکی که پس داده شد، دقیقا همان بلوک دوباره داده می‌شود.
$ ./pool
a=0 b=1 c=2 d=3 e=NULL
after free(b): f=1, free=0

یک نمونهٔ ESP32 برای دیدن مقدار heap آزاد. (این قطعه در این محیط ساخته نمی‌شود؛ مطابق ESP-IDF نسخهٔ ۵.)

#include "esp_log.h"
#include "esp_system.h"

static const char *TAG = "heap";

void app_main(void)
{
    ESP_LOGI(TAG, "free heap: %u bytes", (unsigned)esp_get_free_heap_size());
    ESP_LOGI(TAG, "lowest ever: %u bytes", (unsigned)esp_get_minimum_free_heap_size());
}
  1. سرآیندها. لاگ و تابع‌های اطلاعات سیستم.
  2. مقدار فعلی. چند بایت heap الان آزاد است. unsigned تا با %u جور شود.
  3. حداقل تاریخی. کمترین مقدار آزادی که از شروع برنامه دیده شده. این عدد مهم‌تر است: نشان می‌دهد در بدترین لحظه چقدر به لبهٔ پرتگاه نزدیک بوده‌ای. اگر این عدد در طول روزها کم‌کم کم شود، نشتی داری.

ابزار: پیدا کردن باگ‌های heap

  • روی PC: gcc -g -fsanitize=address (نشتی، استفاده بعد از free، سرریز، double free). یک ابزار دیگر در لینوکس valgrind است. بهترین کار: منطق برنامه‌ات را روی PC بنویس و تست کن (درس ۶.۴)، با sanitizer.
  • روی MCU: خودت heap را کنترل می‌کنی: شمارنده‌ی تخصیص و آزادسازی، پر کردن بلوک آزاد با الگوی مشخص (مثلا 0xDD) تا استفادهٔ آویزان زود دیده شود، و نگه‌داشتن آمار «حداقل آزاد».
  • آنالیز ایستا: ابزارهایی مثل cppcheck بعضی نشتی‌ها را بدون اجرا پیدا می‌کنند (درس ۶.۳).

آزمون این درس

اگر انبار پر باشد، malloc چه برمی‌گرداند و تو چه باید بکنی؟

  1. برنامه را خودکار متوقف می‌کند
  2. NULL؛ باید قبل از استفاده بررسی‌اش کنی
  3. یک آدرس تصادفی که می‌شود استفاده کرد
  4. عدد ۰ به‌عنوان int که باید با if (x == 0) بررسی شود
نتیجهٔ NULL یعنی «جایی نبود». بدون بررسی، نوشتن در آن آدرس ۰ رفتار تعریف‌نشده است و برنامه در بهترین حالت با HardFault می‌میرد.

بعد از این کد، کدام جمله درست است؟
int *p = malloc(sizeof *p); int *q = p; *p = 5; free(p);

  1. q بلوک جداگانهٔ خودش را دارد و *q برابر ۵ است
  2. هر دو p و q خودکار NULL می‌شوند
  3. کد کامپایل نمی‌شود
  4. هر دو p و q آویزان هستند؛ خواندن یا نوشتن از هر کدام رفتار تعریف‌نشده است
free بلوک را پس می‌دهد ولی آدرسی را که در p و q است دست نمی‌زند. هر دو حالا به حافظهٔ آزادشده اشاره می‌کنند. برای همین بعد از free اشاره‌گر را NULL می‌کنیم (اشاره‌گر «کپی‌ها» را نمی‌شود ردیابی کرد).

اگر v از نوع int * باشد، کدام خط برای گرفتن ۱۰ عدد int اشتباه است؟

  1. v = malloc(10 * sizeof *v);
  2. v = malloc(10 * sizeof(int));
  3. v = malloc(10 * sizeof(v));
  4. v = malloc(10 * sizeof v[0]);
sizeof(v) اندازهٔ خود متغیر v (یک اشاره‌گر، ۴ بایت روی MCU) است، نه چیزی که به آن اشاره می‌کند. اینجا اتفاقی برابر است ولی برای double یا struct کمبود می‌آورد.

اصلی‌ترین دلیل اینکه firmware ای که ماه‌ها روشن است از malloc پرهیز می‌کند چیست؟

  1. نشتی و تکه‌تکه‌شدگی انباشته می‌شوند، زمان malloc قابل‌پیش‌بینی نیست و شکستش راه خوبی ندارد
  2. malloc روی میکروکنترلر اصلا وجود ندارد
  3. malloc بلوک‌ها را در Flash می‌سازد که کند است
  4. malloc همیشه در بار اول خراب می‌شود
مشکل بیشتر «طول عمر و شکست» است تا اجرای اولین malloc. برنامه‌ای که هر روز چند ساعت کار می‌کند و بعد ناگهان بی‌دلیل خراب می‌شود، معمولا همین است.

در مثال heap اسباب‌بازی، ۷ واحد آزاد داشتیم ولی درخواست ۵ واحدی شکست خورد. علتش چیست؟

  1. نشتی حافظه
  2. double free
  3. سرریز پشته
  4. fragmentation: جاهای خالی پراکنده‌اند و هیچ‌کدام به‌تنهایی پیوستهٔ ۵ واحد نیست
بلوک باید یک تکهٔ پیوسته باشد. مجموع آزادها (۷) بیشتر از درخواست است، ولی بزرگ‌ترین تکه ۳ است.

چرا نوشتن p = realloc(p, new_size); خطرناک است؟

  1. چون محتوای قدیمی را همیشه پاک می‌کند
  2. چون اگر شکست بخورد، NULL در p می‌نشیند و آدرس بلوک قدیمی (که هنوز سالم بود) گم و نشتی می‌شود
  3. چون آدرس را هرگز عوض نمی‌کند
  4. چون کامپایل نمی‌شود
راه درست: نتیجه را در یک اشاره‌گر موقت بگیر، اگر NULL نبود در p بگذار؛ اگر NULL بود، هنوز p سالم است و می‌توانی آزادش کنی یا ادامه بدهی.

تمرین‌ها

تمرین ۱: آرایهٔ مربع‌ها با calloc

برنامه‌ای بنویس که تعداد n = 6 را بگیرد، آرایه‌ای با calloc بسازد، مربع‌های ۱ تا ۶ را در آن بگذارد، آن‌ها و جمعشان را چاپ کند و در پایان free کند.

  1. پیش‌بینی: با ماشین‌حساب بگو مربع‌ها و جمع چند است.
  2. حل: برنامه را با بررسی NULL و free بنویس.
  3. فکر کن: چرا calloc(n, sizeof *sq) از malloc(n * sizeof *sq) امن‌تر است؟ (دو دلیل.)
راهنمایی

الگوی چهارقدمی: بگیر، بررسی کن، استفاده کن، پس بده. برای n از size_t استفاده کن تا با calloc هماهنگ باشد.

چه باید ببینی؟ 
$ ./squares
squares: 1 4 9 16 25 36
sum = 91
جواب کامل با توضیح 
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    size_t n = 6;
    int *sq = calloc(n, sizeof *sq);
    if (sq == NULL) {
        printf("out of memory\n");
        return 1;
    }

    int sum = 0;
    printf("squares:");
    for (size_t i = 0; i < n; i++) {
        sq[i] = (int)((i + 1) * (i + 1));
        sum += sq[i];
        printf(" %d", sq[i]);
    }
    printf("\nsum = %d\n", sum);

    free(sq);
    return 0;
}
  1. گرفتن و بررسی. calloc دو آرگومان دارد: تعداد و اندازهٔ هر عضو.
  2. حلقه. اندیس i از size_t است؛ حاصل (i+1)*(i+1) هم size_t می‌شود و با یک cast صریح به int می‌رود. cast صریح به کامپایلر و خواننده می‌گوید «می‌دانم چه می‌کنم». بدون آن -Wextra در بعضی تنظیمات دربارهٔ تبدیل هشدار می‌دهد.
  3. پس‌دادن. هر calloc یک free دارد.
$ ./squares
squares: 1 4 9 16 25 36
sum = 91

جواب قسمت پ: (۱) بلوک را صفر می‌کند؛ پس اگر عضوی را فراموش کنی پر کنی، آشغال نمی‌خوانی. (۲) خودش ضرب n × size را روی سرریز بررسی می‌کند؛ اگر n از ورودی کاربر باشد، malloc(n * size) می‌تواند با سرریز یک بلوک خیلی کوچک بدهد و بعد حلقه بیرون از آن بنویسد.

تمرین ۲: باگ‌ها را پیدا کن

هر کدام از این سه قطعه یک باگ heap دارد. باگ را نام ببر و اصلاحش کن.

char *copy = malloc(strlen(name));      // الف
strcpy(copy, name);

int *v = malloc(10);                    // ب
v[5] = 1;

int *p = malloc(sizeof *p);             // پ
*p = 3;
free(p);
printf("%d\n", *p);
  1. قطعهٔ الف (کپی یک رشته)
  2. قطعهٔ ب (می‌خواهیم ۱۰ عدد int داشته باشیم)
  3. قطعهٔ پ (چاپ بعد از free)
راهنمایی

الف: رشتهٔ C چه چیزی در انتها دارد؟ ب: malloc بر حسب چه چیزی است؟ پ: بعد از free اشاره‌گر چه وضعیتی دارد؟

چه باید ببینی؟ 
$ ./fixed
copy: sensor
v[5] = 1, count = 10
p was 3
جواب کامل با توضیح
قطعهباگاصلاح
الفجای '\0' در نظر گرفته نشده؛ strcpy یک بایت بیرون بلوک می‌نویسد (heap overflow)malloc(strlen(name) + 1)
بmalloc(10) ۱۰ بایت است، یعنی جای ۲ عدد int؛ v[5] بیرون بلوک استmalloc(10 * sizeof *v)
پاستفاده بعد از freeاول چاپ کن، بعد free کن
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

int main(void)
{
    const char *name = "sensor";
    char *copy = malloc(strlen(name) + 1);
    int *v = malloc(10 * sizeof *v);
    int *p = malloc(sizeof *p);
    if (copy == NULL || v == NULL || p == NULL) {
        free(copy);
        free(v);
        free(p);
        return 1;
    }

    strcpy(copy, name);
    printf("copy: %s\n", copy);

    v[5] = 1;
    printf("v[5] = %d, count = %d\n", v[5], 10);

    *p = 3;
    printf("p was %d\n", *p);

    free(copy);
    free(v);
    free(p);
    return 0;
}
  1. +۱ برای پایان رشته. رشتهٔ «sensor» شش حرف است و به هفت بایت نیاز دارد.
  2. ضرب در sizeof. ده عضو، هر کدام به‌اندازهٔ *v.
  3. یک بررسی برای هر سه. اگر هر کدام NULL بود، آن‌هایی را که گرفته شده‌اند آزاد می‌کنیم. free(NULL) بی‌خطر است. اگر فقط یکی شکست بخورد و بقیه را آزاد نکنیم، نشتی می‌سازیم. بی‌خطر بودن free(NULL) این کد را ساده می‌کند.
  4. آزادسازی در آخر. بعد از آخرین استفاده. ترتیب free بین اشاره‌گرهای مستقل مهم نیست.

تمرین ۳: ثبت‌کنندهٔ ایستا، بدون heap

در یک ثبت‌کنندهٔ داده روی STM32، هر نمونه یک زمان (uint32_t) و یک مقدار (int16_t) دارد. می‌خواهیم آخرین ۸ نمونه را نگه داریم و بدون malloc.

  1. حساب: هر نمونه چند بایت جا می‌گیرد؟ (به padding فکر کن؛ درس ۳.۴.) و ۸ نمونه چند بایت؟
  2. حل: یک آرایهٔ static ۸ عضوی و تابع log_add بنویس که وقتی پر شد، قدیمی‌ترین را بازنویسی کند. ۱۰ نمونه (100 تا 109) بفرست و ۸ آخر را از قدیمی به جدید چاپ کن.
  3. سخت‌افزار: اگر همین ثبت‌کننده با malloc برای هر نمونه ساخته می‌شد و ماه‌ها کار می‌کرد، چه مشکلاتی پیش می‌آمد؟ (سه مورد.)
راهنمایی

برای جای بعدی از یک شمارنده و باقیمانده (%) استفاده کن: بعد از خانهٔ ۷ برمی‌گردی به ۰. اندیس شروع چاپ = (next + LOG_SIZE - count) % LOG_SIZE.

چه باید ببینی؟ 
$ ./logger
entry = 8 bytes, total = 64 bytes
102 103 104 105 106 107 108 109
جواب کامل با توضیح 
#include <stdio.h>
#include <stdint.h>

#define LOG_SIZE 8u

typedef struct {
    uint32_t time_ms;
    int16_t  value;
} entry_t;

static entry_t entries[LOG_SIZE];
static unsigned next_slot = 0;
static unsigned count = 0;

static void log_add(uint32_t time_ms, int16_t value)
{
    entries[next_slot].time_ms = time_ms;
    entries[next_slot].value = value;
    next_slot = (next_slot + 1u) % LOG_SIZE;
    if (count < LOG_SIZE) {
        count++;
    }
}

int main(void)
{
    printf("entry = %zu bytes, total = %zu bytes\n", sizeof(entry_t), sizeof entries);

    for (int i = 0; i < 10; i++) {
        log_add((uint32_t)(i * 10), (int16_t)(100 + i));
    }

    unsigned start = (next_slot + LOG_SIZE - count) % LOG_SIZE;
    for (unsigned i = 0; i < count; i++) {
        printf("%d%s", entries[(start + i) % LOG_SIZE].value, i + 1 < count ? " " : "\n");
    }
    return 0;
}
  1. نوع نمونه. ۴ بایت زمان + ۲ بایت مقدار = ۶، ولی برای اینکه عضو بعدی (اگر آرایه) تراز بماند، کامپایلر ۲ بایت padding اضافه می‌کند: کل ۸ بایت.
  2. حافظهٔ ثابت. ۸ × ۸ = ۶۴ بایت، از لحظهٔ کامپایل معلوم است و هرگز کم و زیاد نمی‌شود.
  3. افزودن. در خانهٔ next_slot می‌نویسد، اندیس را یکی جلو می‌برد (با % که بعد از ۷ به ۰ برمی‌گردد) و تعداد را تا سقف ۸ زیاد می‌کند. وقتی پر شد، خانهٔ جدید روی قدیمی‌ترین می‌نشیند: «بازنویسی قدیمی». این همان ایدهٔ بافر حلقوی است (درس ۴.۵).
  4. چاپ از قدیمی به جدید. اگر بافر پر است، قدیمی‌ترین خانه همان next_slot است؛ فرمول (next + size - count) % size این را هم برای حالت پر و هم نیمه‌پر درست می‌دهد.
$ ./logger
entry = 8 bytes, total = 64 bytes
102 103 104 105 106 107 108 109

جواب قسمت پ: (۱) با هر نمونه یک malloc و هر دور یک free heap را تکه‌تکه می‌کند. (۲) هر بلوک هدر پنهان دارد؛ ۶ بایت داده با هدر و padding چند برابر می‌شود و RAM هدر می‌رود. (۳) روزی که malloc شکست بخورد، ثبت‌کننده باید تصمیم بگیرد داده را از دست بدهد یا خراب شود؛ در نسخهٔ ایستا چنین لحظه‌ای وجود ندارد.

حرف مربی

گیر اصلی این درس دو چیز است. اول: «چرا کامپایلر ایراد نگرفت؟» چون باگ‌های heap همه در زمان اجرا هستند و کامپایلر فقط بخشی را می‌بیند. عادت خوب: هر برنامه‌ای را که malloc دارد، یک بار با -fsanitize=address اجرا کن. دوم: وسوسهٔ راحتی. در برنامه‌های PC malloc همه جا هست و اشکال ندارد؛ فقط یادت باشد میکروکنترلر دنیای دیگری است: اول آرایهٔ ثابت و pool، و فقط با دلیل قوی heap. اگر دستگاهی را دیدی که «بعد از سه هفته هنگ می‌کند»، اولین مظنونش heap است.

خلاصه یک‌دقیقه‌ای

  • malloc بلوکی از heap می‌دهد (آشغال)، calloc صفر‌شده، realloc تغییر اندازه، free پس‌دادن. همیشه: بگیر ← NULL را بررسی کن ← استفاده کن ← free.
  • اندازه را n * sizeof *p بنویس. برای رشته strlen + 1.
  • چهار باگ: نشتی، استفاده بعد از free، double free، نوشتن بیرون بلوک. با -fsanitize=address روی PC پیدایشان کن.
  • p = realloc(p, n) ممنوع؛ از متغیر موقت استفاده کن.
  • Fragmentation: فضای آزاد پراکنده است، پس درخواست پیوستهٔ بزرگ شکست می‌خورد، بی‌آنکه نشتی باشد.
  • روی MCU احتیاط: هیچ‌کس جمع نمی‌کند، RAM کم است، زمان ثابت نیست. MISRA 21.3 ممنوعش می‌کند.
  • جایگزین‌ها: آرایهٔ ایستا با بدترین حالت، و memory pool برای بلوک‌های هم‌اندازه (زمان ثابت، بدون fragmentation).
