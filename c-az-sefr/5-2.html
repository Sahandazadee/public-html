تا حالا هر کاری که با تراشه کردی، از میان یک «واسطه» رد شده است: کتابخانه، سیستم‌عامل، یا تابعی که کس دیگری نوشته. در این درس واسطه را کنار می‌گذاریم. سه رجیستر را خودت می‌نویسی و چراغ سبز روی برد Nucleo شروع به چشمک‌زدن می‌کند. بعد یک دکمه را می‌خوانی. وقتی این دو کار را بدون هیچ کتابخانه‌ای انجام بدهی، هر کتابخانهٔ سازنده (HAL) برایت شفاف می‌شود.

🎯 بعد از این درس می‌توانی

  • LED روی برد (LD2 روی PA5) را فقط با رجیستر، بدون HAL، چشمک بزنی
  • سه قدم «ساعت، حالت، کار» را برای هر پریفرال بگویی و بنویسی
  • دکمهٔ آبی (PC13) را با polling بخوانی و بدانی چرا «فشرده = صفر» است
  • یک هدر رجیستر کوچک شبیه CMSIS بنویسی و آدرس‌هایش را با _Static_assert بسنجی
  • پروژه را با Makefile و arm-none-eabi-gcc بسازی و روی برد بریزی
  • همین برنامه را با HAL و LL مقایسه کنی و بدانی هرکدام کی به‌کار می‌آید

ایدهٔ اصلی: رفتن سراغ جعبه‌فیوز

در ساختمانی لامپ راهرو خراب شده است. دو راه داری. راه اول: به سرایدار زنگ بزنی و بگویی «لطفا لامپ را عوض کن». سرایدار همهٔ کارها را می‌داند و تو چیزی از جزئیات نمی‌فهمی. راه دوم: خودت سراغ جعبه‌فیوز بروی، کلید درست را پیدا کنی و بزنی.

مثال از زندگی روزمره

سرایدار همان HAL است، کتابخانه‌ای که سازندهٔ تراشه نوشته. جعبه‌فیوز همان رجیسترهاست. کار bare-metal (به فارسی «روی فلز خالی») یعنی بدون سیستم‌عامل و بدون واسطه، مستقیم با رجیستر حرف زدن. سرایدار بد نیست؛ ولی اگر جعبه‌فیوز را ندیده باشی، وقتی سرایدار نیامد یا اشتباه کرد، هیچ کاری از دستت برنمی‌آید.

خبر خوب: هر پریفرال STM32 (GPIO، تایمر، UART و…) با همان سه قدم راه می‌افتد. این سه قدم را حفظ کن، چون تا آخر دوره تکرار می‌شوند:

  1. ساعت (clock). پریفرال‌ها برای صرفه‌جویی در برق پیش‌فرض بی‌ساعت‌اند. ساعت را در RCC روشن کن.
  2. حالت (mode). به پریفرال بگو چه کاری بکند. برای GPIO: این پایه ورودی است یا خروجی؟
  3. کار. حالا واقعا فرمان بده: بنویس، بخوان، صبر کن.

مسیر یک فرمان: از CPU تا LED

شکل زیر مسیر همین سه قدم برای LD2 را نشان می‌دهد. روی برد Nucleo-F411RE، پایهٔ PA5 (پایهٔ ۵ پورت A) از راه یک مقاومت به LED سبز وصل است. پس اگر PA5 را «بالا» کنیم، LED روشن می‌شود.

هر یک از این سه نوشتن، یک str (ذخیره) به یک آدرس ثابت است. آدرس‌ها از RM0383 (مرجع رسمی STM32F411) می‌آیند. برای پروژهٔ امروز فقط این پنج آدرس لازم است:

قدم ۱ در ابزارک: ساعت

در ابزارک زیر رجیستر RCC_AHB1ENR (فقط ۸ بیت پایین) را می‌بینی. بیت ۰ را یک کن: ساعت GPIOA روشن می‌شود. بیت ۲ مال GPIOC است (برای دکمه، کمی بعد). در STM32F411 بیت‌های ۵ و ۶ استفاده نمی‌شوند.

ساعت خاموش = نوشتن بی‌اثر و بی‌صدا

وقتی ساعت یک پریفرال خاموش است، نوشتن روی رجیسترهایش خطا نمی‌دهد؛ فقط اثر ندارد (و خواندنشان معمولا صفر برمی‌گرداند). برای همین «LED چشمک نمی‌زند» بیشتر از هر علتی به فراموشیِ همین قدم برمی‌گردد. قدم ۱ را همیشه اول بنویس.

هدر کوچک خودمان: stm32f4.h

در درس ۳.۶ دیدی که می‌شود رجیسترهای یک بخش را با یک struct روکش کرد. حالا همان را جدی می‌کنیم و یک هدر می‌نویسیم که فقط چیزهای لازم این درس را دارد. کار ST در فایل stm32f4xx.h (بخشی از CMSIS) هم همین است، ولی برای همهٔ رجیسترهای همهٔ تراشه‌ها. بعد از نوشتن هدر خودت، خواندن آن فایل بزرگ دیگر ترسناک نیست.

#ifndef STM32F4_H
#define STM32F4_H

#include <stdint.h>
#include <stddef.h>

typedef struct {
    volatile uint32_t MODER;    // +0x00
    volatile uint32_t OTYPER;   // +0x04
    volatile uint32_t OSPEEDR;  // +0x08
    volatile uint32_t PUPDR;    // +0x0C
    volatile uint32_t IDR;      // +0x10
    volatile uint32_t ODR;      // +0x14
    volatile uint32_t BSRR;     // +0x18
    volatile uint32_t LCKR;     // +0x1C
    volatile uint32_t AFR[2];   // +0x20, +0x24
} GPIO_TypeDef;

typedef struct {
    volatile uint32_t CR;       // +0x00
    volatile uint32_t PLLCFGR;  // +0x04
    volatile uint32_t CFGR;     // +0x08
    volatile uint32_t CIR;      // +0x0C
    volatile uint32_t AHB1RSTR; // +0x10
    volatile uint32_t AHB2RSTR; // +0x14
    uint32_t RESERVED0[2];      // +0x18, +0x1C
    volatile uint32_t APB1RSTR; // +0x20
    volatile uint32_t APB2RSTR; // +0x24
    uint32_t RESERVED1[2];      // +0x28, +0x2C
    volatile uint32_t AHB1ENR;  // +0x30
} RCC_TypeDef;

#define RCC   ((RCC_TypeDef *)0x40023800u)
#define GPIOA ((GPIO_TypeDef *)0x40020000u)
#define GPIOC ((GPIO_TypeDef *)0x40020800u)

#define RCC_AHB1ENR_GPIOAEN (1u << 0)
#define RCC_AHB1ENR_GPIOCEN (1u << 2)

_Static_assert(offsetof(GPIO_TypeDef, IDR) == 0x10, "IDR offset");
_Static_assert(offsetof(GPIO_TypeDef, BSRR) == 0x18, "BSRR offset");
_Static_assert(offsetof(RCC_TypeDef, AHB1ENR) == 0x30, "AHB1ENR offset");

#endif /* STM32F4_H */
  1. نگهبان include. اگر این هدر دو بار وارد شود (مثلا از دو فایل)، بار دوم نادیده گرفته می‌شود. بدون آن، typedef ها دو بار تعریف می‌شوند و کامپایلر خطا می‌دهد. جزئیات در درس ۴.۲.
  2. دو هدر استاندارد. stdint.h برای uint32_t و stddef.h برای offsetof. هر دو در حالت freestanding هم وجود دارند. این‌ها فقط تعریف نوع و ماکرو هستند و به کتابخانهٔ زمان اجرا نیاز ندارند؛ پس روی تراشه بدون سیستم‌عامل هم مشکلی نیست.
  3. روکش GPIO. هر فیلد یک رجیستر ۳۲ بیتی است و ترتیب فیلدها دقیقا ترتیب آدرس‌هاست: MODER در +0x00، IDR در +0x10. کامپایلر فیلدها را پشت هم می‌چیند و چون همه ۴ بایتی‌اند، padding نمی‌آید. volatile روی همهٔ فیلدها حیاتی است: بدون آن کامپایلر می‌تواند خواندن‌های تکراری را حذف کند (درس ۳.۶).
  4. BSRR. رجیستر فقط‌نوشتنی: بیت‌های ۰ تا ۱۵ = روشن‌کردن پایه‌ها، بیت‌های ۱۶ تا ۳۱ = خاموش‌کردن.
  5. قفل و توابع جایگزین. LCKR برای قفل‌کردن پیکربندی و AFR[2] (دو رجیستر) برای انتخاب عملکرد جایگزین پایه (در درس‌های ۵.۴ و ۵.۵ لازم می‌شود). امروز به آن‌ها دست نمی‌زنیم، ولی باید در چیدمان باشند تا آدرس بعدی‌ها جابه‌جا نشود.
  6. روکش RCC. همان ایده برای مدیر ساعت‌ها. فقط تا AHB1ENR را نوشته‌ایم؛ بقیه را هر وقت لازم شد اضافه می‌کنیم.
  7. فضاهای رزرو. بین رجیسترهای واقعی، آدرس‌هایی هست که ST چیزی در آن‌ها نگذاشته. این آرایه‌ها جای خالی را پر می‌کنند تا AHB1ENR دقیقا روی +0x30 بنشیند. اگر یکی را جا بیندازی، همهٔ فیلدهای بعدی چند بایت جابه‌جا می‌شوند و روی رجیستر اشتباه می‌نویسی. باگی که دیدنش سخت است؛ برای همین _Static_assert پایین‌تر را داریم.
  8. دو رجیستر ریست. APB1RSTR و APB2RSTR. امروز استفاده نمی‌شوند ولی جایشان را نگه می‌داریم.
  9. AHB1ENR. رجیستر ساعت پورت‌های GPIO (و DMA). رجیستر مقصد قدم ۱.
  10. اشاره‌گر به آدرس ثابت. عدد 0x40020000u را به «اشاره‌گر به GPIO_TypeDef» تبدیل می‌کنیم. بعد GPIOA->BSRR یعنی «فیلد BSRR از ساختاری که روی آدرس 0x40020000 نشسته». پورت C به‌اندازهٔ 0x800 بعد از A است. کل رجیسترهای یک پورت در یک بلوک ۴۰۰ (هگز) بایتی است و پورت‌ها پشت هم می‌آیند: B = +0x400، C = +0x800.
  11. نام برای بیت‌ها. RCC_AHB1ENR_GPIOAEN از همان الگوی نام‌گذاری ST پیروی می‌کند. (1u << 0) بهتر از عدد جادویی 1 خوانده می‌شود.
  12. بازرس آفست. _Static_assert در زمان کامپایل بررسی می‌کند فاصلهٔ فیلد از ابتدای struct همان عددی است که در RM0383 نوشته. اگر نباشد، برنامه کامپایل نمی‌شود. هزینه‌اش صفر است (هیچ کدی روی تراشه نمی‌رود) ولی جلوی یک باگ سخت را می‌گیرد. در بخش بعد ببین چطور کار می‌کند.

ببین اگر یک فیلد جا بیفتد چه می‌شود. همان ساختار ولی بدون OSPEEDR:

#include <stdint.h>
#include <stddef.h>

typedef struct {
    volatile uint32_t MODER;
    volatile uint32_t OTYPER;
    volatile uint32_t PUPDR;    // OSPEEDR جا افتاده!
    volatile uint32_t IDR;
    volatile uint32_t ODR;
    volatile uint32_t BSRR;
} GPIO_TypeDef;

_Static_assert(offsetof(GPIO_TypeDef, BSRR) == 0x18, "BSRR offset");

int main(void)
{
    return 0;
}
  1. فیلد جا افتاده. OSPEEDR نیست، پس PUPDR به‌جای آفست 0x0C در 0x08 می‌نشیند.
  2. همه بعدی‌ها جابه‌جا. BSRR حالا در 0x14 است، نه 0x18.
  3. بازرس. می‌گوید BSRR باید در 0x18 باشد. نیست؛ پس خطا. بدون این خط، برنامه کامپایل می‌شد و LED به‌جای BSRR روی ODR می‌نوشت؛ نتیجه‌اش رفتاری عجیب بود که ساعت‌ها طول می‌کشید تا پیدا شود.

شروع و پایان: startup و linker script

برد بعد از روشن‌شدن نمی‌داند main کجاست. چیزی باید قبل از main اجرا شود: کدی که حافظه را آماده کند. اسم این کد startup است و همراهش یک فایل ساختِ حافظه به اسم linker script. درس ۵.۱ این دو را کامل توضیح می‌دهد. برای اینکه این درس خودش تنها بایستد، نسخهٔ کوچک کارآمد آن‌ها را اینجا می‌آوریم. اگر ۵.۱ را نخوانده‌ای، فعلا با این دو فایل مثل یک «جعبهٔ سیاه مطمئن» رفتار کن.

#include <stdint.h>

extern uint32_t _estack, _sidata, _sdata, _edata, _sbss, _ebss;
int main(void);

void Reset_Handler(void);
void Default_Handler(void);
void NMI_Handler(void)       __attribute__((weak, alias("Default_Handler")));
void HardFault_Handler(void) __attribute__((weak, alias("Default_Handler")));

__attribute__((section(".isr_vector"), used))
void (*const vector_table[])(void) = {
    (void (*)(void))&_estack,   // کلمهٔ ۰: مقدار اولیهٔ SP
    Reset_Handler,              // کلمهٔ ۱: نقطهٔ شروع
    NMI_Handler,                // کلمهٔ ۲
    HardFault_Handler,          // کلمهٔ ۳
};

void Reset_Handler(void)
{
    uint32_t *src = &_sidata;
    for (uint32_t *dst = &_sdata; dst < &_edata; ) {
        *dst++ = *src++;
    }
    for (uint32_t *dst = &_sbss; dst < &_ebss; ) {
        *dst++ = 0u;
    }
    main();
    for (;;) {
    }
}

void Default_Handler(void)
{
    for (;;) {
    }
}
  1. نمادهای linker script. _estack، _sdata، _edata، _sidata، _sbss، _ebss متغیر واقعی نیستند؛ مرزهای حافظه‌اند که linker می‌سازد. فقط آدرسشان به‌کار می‌آید (&_sdata).
  2. اعلان‌ها. main، Reset_Handler (اولین کد بعد از روشن‌شدن) و Default_Handler (جایگزین وقفه‌هایی که کسی ننوشته).
  3. نام‌های ضعیف. weak, alias یعنی «اگر کسی NMI_Handler را جدی تعریف نکرد، همین Default_Handler را بردار». تعریف واقعی همیشه برنده است. در درس ۵.۳ فقط با نوشتن تابعی همنام، ISR را جایگزین می‌کنیم.
  4. جدول برداری در Flash. آرایهٔ const از اشاره‌گر تابع، با section(".isr_vector") که linker آن را اول Flash (0x08000000) می‌گذارد. used یعنی «حذفش نکن». سخت‌افزار Cortex-M بعد از ریست این جدول را از ابتدای Flash می‌خواند؛ کسی «صدایش نمی‌زند».
  5. دو کلمهٔ اول. کلمهٔ ۰: مقدار اولیهٔ SP (آخرین آدرس RAM؛ پشته به پایین رشد می‌کند). کلمهٔ ۱: آدرس Reset_Handler، جایی که CPU می‌پرد.
  6. استثناهای ۲ و ۳. NMI و HardFault؛ فعلا هر دو به حلقهٔ بی‌نهایت می‌روند.
  7. Reset_Handler. اولین تابعی که CPU اجرا می‌کند.
  8. کپی مقدار اولیهٔ .data. مقدار اولیهٔ سراسری‌های مقداردار در Flash است؛ اینجا به RAM کپی می‌شود. RAM بعد از روشن‌شدن آشغال است؛ بدون این کپی int x = 5; سراسری ۵ نمی‌بود (درس ۳.۵). امروز چنین متغیری نداریم ولی کد باید آماده باشد.
  9. صفر کردن .bss. سراسری‌های بی‌مقدار باید صفر باشند؛ قانون C.
  10. صدا زدن main. حالا حافظه آماده است. اگر main برگشت در حلقه می‌مانیم: روی MCU سیستم‌عاملی نیست که منتظرش باشد.
  11. Default_Handler. جای امن برای وقفه‌های ناخواسته: در حلقه می‌ماند تا با دیباگر ببینی کجا افتاده‌ای.
ENTRY(Reset_Handler)

MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 512K
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 128K
}

_estack = ORIGIN(RAM) + LENGTH(RAM);

SECTIONS
{
    .isr_vector : {
        KEEP(*(.isr_vector))
    } > FLASH

    .text : {
        *(.text*)
        *(.rodata*)
        . = ALIGN(4);
    } > FLASH

    _sidata = LOADADDR(.data);

    .data : {
        _sdata = .;
        *(.data*)
        . = ALIGN(4);
        _edata = .;
    } > RAM AT > FLASH

    .bss : {
        _sbss = .;
        *(.bss*)
        *(COMMON)
        . = ALIGN(4);
        _ebss = .;
    } > RAM
}
  1. نقطهٔ ورود. برنامه از Reset_Handler شروع می‌شود (برای دیباگر و ابزارها).
  2. نقشهٔ حافظه. Flash از 0x08000000 با ۵۱۲ کیلوبایت و RAM از 0x20000000 با ۱۲۸ کیلوبایت (مشخصات STM32F411).
  3. سر پشته. _estack = ابتدای RAM + اندازهٔ آن = 0x20020000، یک بعد از آخرین بایت. پشته با هر push اول یکی پایین می‌آید و بعد می‌نویسد؛ پس شروع از «یک بعد از انتها» درست است.
  4. SECTIONS. هر بخش خروجی از چه ورودی‌هایی ساخته شود و کجا برود.
  5. جدول برداری اول. .isr_vector اول Flash می‌رود؛ KEEP از حذف‌شدنش جلوگیری می‌کند.
  6. کد و ثابت‌ها. .text و .rodata بعد از جدول، در Flash.
  7. مبدأ کپی .data. _sidata = آدرس «انبار» مقدارهای اولیه در Flash.
  8. .data. > RAM AT > FLASH: در زمان اجرا در RAM زندگی می‌کند ولی محتوایش در Flash ذخیره می‌شود. Reset_Handler کپی می‌کند.
  9. .bss. فقط در RAM جا می‌گیرد؛ فقط مرزهایش را می‌گذاریم تا startup صفرش کند.

فایل‌های startup رسمی ST معمولا با اسمبلی نوشته شده‌اند، ولی همین کار در C هم شدنی است، به‌شرطی که تا وقتی حافظه آماده نشده، فقط از متغیرهای محلی استفاده کنیم. در Reset_Handler ما متغیر سراسری نخوانده و ننوشته‌ایم. نکتهٔ ظریف دیگر: اگر با -O2 کامپایل کنی، ممکن است gcc حلقه‌ای را که صفر می‌نویسد به تابع memset تبدیل کند، و چون -nostdlib داری، لینک خطای undefined reference to memset بدهد. ما با -Og ساختیم و مشکلی نداشتیم؛ راه‌حل حرفه‌ای در ۵.۱ می‌آید.

اولین برنامهٔ واقعی: چشمک LD2

حالا همهٔ قطعات آماده‌اند. برنامه‌ای که فقط خودش را به هدر و startup تکیه می‌دهد:

#include "stm32f4.h"

#define LED_PIN 5u

static void delay(volatile uint32_t n)
{
    while (n--) {
    }
}

int main(void)
{
    RCC->AHB1ENR |= RCC_AHB1ENR_GPIOAEN;
    (void)RCC->AHB1ENR;
    GPIOA->MODER = (GPIOA->MODER & ~(3u << (LED_PIN * 2u)))
                 | (1u << (LED_PIN * 2u));

    for (;;) {
        GPIOA->BSRR = 1u << LED_PIN;
        delay(400000u);
        GPIOA->BSRR = 1u << (LED_PIN + 16u);
        delay(400000u);
    }
}
  1. هدر خودمان. با گیومه ("") چون در پوشهٔ پروژه است (درس ۴.۱).
  2. شمارهٔ پایه. LD2 روی PA5 است. اسم دادن به عدد ۵ کمک می‌کند بعدا اگر LED را عوض کردی فقط یک جا را عوض کنی.
  3. تأخیر خام. تا صفر می‌شمارد. پارامتر n عمدا volatile است تا کامپایلر حلقهٔ «بی‌کار» را حذف نکند. راه بدی است ولی ساده‌ترین. مشکلش: CPU در این مدت کاری جز شمردن نمی‌کند و زمانش به بهینه‌سازی وابسته است. درس ۵.۴ زمان‌بندی درست را می‌آورد.
  4. main. اولین کدی که ما نوشتیم و startup صدایش می‌زند.
  5. قدم ۱: ساعت. فقط بیت ۰ را یک می‌کنیم (|=) تا ساعت بقیهٔ پورت‌ها دست نخورد.
  6. خواندن بی‌مصرف. یک بار رجیستر را می‌خوانیم و دور می‌ریزیم. چون volatile است، حذف نمی‌شود. اثرش: چند چرخه تأخیر تا ساعت پورت واقعا برقرار شود. ST در errata/مستندات بعضی تراشه‌ها همین کار را توصیه می‌کند. هزینه‌اش ناچیز است و از باگ‌های نادر جلوگیری می‌کند.
  7. قدم ۲: حالت. اول دو بیت مربوط به پایهٔ ۵ (بیت‌های ۱۰ و ۱۱) را پاک می‌کنیم، بعد 01 (خروجی) می‌نویسیم. LED_PIN * 2u چون هر پایه دو بیت دارد. اگر فقط MODER = 1u << 10 می‌نوشتی، حالت همهٔ پایه‌های دیگر (از جمله SWD دیباگر) هم صفر می‌شد. الگوی «پاک کن، بگذار» از درس ۳.۱.
  8. حلقهٔ بی‌نهایت. برنامهٔ MCU هرگز تمام نمی‌شود (super loop، درس ۱.۴).
  9. قدم ۳: روشن. بیت ۵ در BSRR = «پایهٔ ۵ را بالا ببر».
  10. خاموش. بیت 5 + 16 = ۲۱ = «پایهٔ ۵ را پایین بیاور». این یک نوشتن واحد است؛ برخلاف ODR |= … که سه مرحله دارد (بخوان، تغییر بده، بنویس) و اگر وقفه‌ای وسط بیاید خراب می‌شود. (درس ۳.۶)
  11. صبر. ۴۰۰ هزار دور شمارش بین دو تغییر.
چرا LED با «۱» روشن می‌شود؟

در Nucleo-64 پایهٔ PA5 از راه مقاومت به LED و بعد زمین وصل است. پس بالا رفتن پایه (۳٫۳ ولت) جریان می‌دهد و LED روشن می‌شود. روی برد دیگری ممکن است LED به ۳٫۳ ولت وصل باشد و با «صفر» روشن شود. همیشه شماتیک برد را ببین (درس ۱.۳: datasheet و مستند برد).

ساختن: Makefile واقعی

دستور بلند arm-none-eabi-gcc … را نمی‌خواهیم هر بار دستی بنویسیم. طبق درس ۴.۲ یک Makefile می‌نویسیم که سه برنامهٔ این درس (blink، button، toggle) را بسازد. نکته: جلوی دستورها یک نویسهٔ Tab است، نه فاصله.

CC      = arm-none-eabi-gcc
CFLAGS  = -mcpu=cortex-m4 -mthumb -std=gnu11 -Wall -Wextra -ffreestanding -Og
LDFLAGS = -nostdlib -T link.ld
PROGS   = blink button toggle

all: $(PROGS:=.bin)

%.elf: %.o startup.o link.ld
	$(CC) $(CFLAGS) $(LDFLAGS) -o $@ $(filter %.o,$^)

%.bin: %.elf
	arm-none-eabi-objcopy -O binary $< $@

%.o: %.c stm32f4.h
	$(CC) $(CFLAGS) -c -o $@ $<

.PRECIOUS: %.o %.elf

clean:
	rm -f *.o *.elf *.bin
  1. متغیرها. کامپایلر و پرچم‌ها یک‌جا. -mcpu=cortex-m4 -mthumb = هدف: Cortex-M4 با دستورهای Thumb. -ffreestanding = «کتابخانه‌ای در کار نیست». -Og = بهینه‌سازی سبک و دیباگ‌پذیر. در خط ۳: -nostdlib = کتابخانهٔ استاندارد را لینک نکن، -T link.ld = این linker script. بدون -nostdlib، linker دنبال startup و libc استاندارد رایانه‌ات می‌گردد که برای این تراشه وجود ندارد.
  2. فهرست برنامه‌ها. سه برنامه؛ اگر چهارمی اضافه کنی فقط همین خط عوض می‌شود.
  3. هدف پیش‌فرض. $(PROGS:=.bin) یعنی به هر اسم .bin بچسبان: blink.bin button.bin toggle.bin. با نوشتن make همهٔ این‌ها ساخته می‌شوند.
  4. قانون لینک. هر X.elf از X.o به‌اضافهٔ startup.o ساخته می‌شود. $@ = خود هدف، $(filter %.o,$^) = فقط فایل‌های .o از پیش‌نیازها (تا link.ld به‌عنوان ورودی کامپایلر نرود). پیش‌نیاز بودن link.ld باعث می‌شود اگر آن را عوض کردی، دوباره لینک شود.
  5. ELF به BIN. objcopy -O binary فقط بایت‌هایی را که باید در Flash بروند بیرون می‌کشد (بدون اطلاعات دیباگ).
  6. کامپایل هر فایل. هر X.c به X.o. اگر stm32f4.h عوض شود همهٔ .o ها دوباره ساخته می‌شوند. $< = اولین پیش‌نیاز (خود .c).
  7. فایل‌های میانی را نگه دار. make پیش‌فرض فایل‌های میانی زنجیره‌ای (.o و .elf) را پاک می‌کند. .PRECIOUS این را خاموش می‌کند تا blink.elf برای دیدن با objdump بماند.
  8. پاک‌سازی. make clean همهٔ خروجی‌ها را حذف می‌کند.

شبیه‌ساز: بدون برد هم می‌شود؟

بله، تا حدی. Renode یک شبیه‌ساز متن‌باز برای سیستم‌های embedded است که برای خانوادهٔ STM32F4 بردهای نمونه دارد (فهرست دقیقش را در مستندات خودش ببین؛ ما وجود Nucleo-F411RE را در آن تضمین نمی‌کنیم). ما در این دوره از آن فقط به‌عنوان «راهی برای اجرای همین ELFها بدون سخت‌افزار» یاد می‌کنیم؛ کار با آن را وارد نمی‌شویم. برنامه‌های این درس را روی برد واقعی امتحان کن.

خواندن دکمهٔ آبی: PC13

تا اینجا فقط «نوشتیم». حالا «بخوانیم». دکمهٔ آبی B1 روی Nucleo به پایهٔ PC13 وصل است. برای خواندن آن باید سه چیز را بدانی.

مثال: آب در لوله

لوله‌ای را تصور کن که همیشه از بالا آب دارد (این مقاومت بالاکش است، یعنی pull-up). تا کسی چیزی را باز نکند، سر لوله «آب هست» (=۱). دکمه شیری است که لوله را به چاه (زمین) وصل می‌کند: وقتی فشار می‌دهی آب تخلیه می‌شود و سر لوله «آب نیست» (=۰). پس: رها = ۱، فشرده = ۰. این را فعال-پایین (active-low) می‌گویند.

  1. ساعت پورت C را روشن کن (RCC_AHB1ENR بیت ۲).
  2. پایه را ورودی کن. در GPIOC_MODER دو بیت پایهٔ ۱۳ (بیت‌های ۲۷ و ۲۶) را 00 کن. (پس از ریست معمولا همین‌اند، ولی نوشتنِ صریح خوانا و مطمئن است.)
  3. سطح پایه را از GPIOC_IDR بخوان. بیت ۱۳ آن سطح PC13 است.

در ابزارک زیر GPIOC_IDR را می‌بینی (۱۶ بیت پایین). حالت «رها» یعنی بیت ۱۳ یک است. با کلیک روی بیت ۱۳ «فشردن» را شبیه‌سازی کن:

حالا برنامه: LED فقط تا وقتی دکمه فشرده است روشن باشد.

#include "stm32f4.h"

#define LED_PIN    5u
#define BUTTON_PIN 13u

static int button_pressed(void)
{
    return (GPIOC->IDR & (1u << BUTTON_PIN)) == 0u;
}

int main(void)
{
    RCC->AHB1ENR |= RCC_AHB1ENR_GPIOAEN | RCC_AHB1ENR_GPIOCEN;
    (void)RCC->AHB1ENR;

    GPIOA->MODER = (GPIOA->MODER & ~(3u << (LED_PIN * 2u)))
                 | (1u << (LED_PIN * 2u));
    GPIOC->MODER &= ~(3u << (BUTTON_PIN * 2u));
    GPIOC->PUPDR = (GPIOC->PUPDR & ~(3u << (BUTTON_PIN * 2u)))
                 | (1u << (BUTTON_PIN * 2u));

    for (;;) {
        if (button_pressed()) {
            GPIOA->BSRR = 1u << LED_PIN;
        } else {
            GPIOA->BSRR = 1u << (LED_PIN + 16u);
        }
    }
}
  1. دو شمارهٔ پایه. LED روی PA5، دکمه روی PC13.
  2. تابع «فشرده است؟». بیت ۱۳ را جدا می‌کند (& (1u << 13)) و می‌پرسد صفر است یا نه. صفر = فشرده. نتیجه ۱ (درست) یا ۰. پرانتز دور (1u << 13) لازم نیست، ولی پرانتزِ (IDR & ماسک) لازم است: == تقدم بالاتری از & دارد و بدون پرانتز کل شرط همیشه نادرست می‌شود (درس ۳.۱).
  3. main. اینجا شروع.
  4. قدم ۱: ساعت دو پورت. A (LED) و C (دکمه) با یک |. بعد یک خواندن بی‌مصرف.
  5. قدم ۲ برای LED. همان که در blink.c دیدی: PA5 خروجی.
  6. قدم ۲ برای دکمه. بیت‌های ۲۷ و ۲۶ را صفر می‌کنیم: 00 = ورودی. 3u << 26 = دو بیت یک.
  7. بالاکش. در PUPDR مقدار 01 یعنی «بالاکش فعال». روی Nucleo دکمه از قبل مقاومت بالاکش خارجی دارد، پس این خط معمولا فقط اطمینان است؛ ولی الگوی درستی است که برای هر دکمهٔ دیگری هم کار می‌کند. پایهٔ ورودی‌ای که به هیچ‌چیز وصل نیست «شناور» است و مقدارش تصادفی می‌شود؛ بالاکش آن را روی ۱ نگه می‌دارد.
  8. حلقهٔ بی‌نهایت. پولینگ: مدام بپرس.
  9. LED دنبال دکمه. فشرده: BSRR بیت ۵ (روشن). رها: بیت ۲۱ (خاموش). چون فقط یک نوشتن است، هر چقدر هم بپرسد ضرر ندارد. این «سطح» را می‌خواند، نه «رویداد» را. ببین در بخش بعد چرا فرق دارد.
اشتباه رایج: کجا برای IDR بنویسیم؟

IDR فقط‌خواندنی است. نوشتن روی آن بی‌اثر است و به‌جای آن باید ODR یا BSRR را بنویسی. هرگز برای خواندن ورودی به ODR نگاه نکن: ODR «آنچه خودت نوشتی» را نگه می‌دارد، نه ولتاژ واقعی پایه.

لبه، پرش و «یک بار» بودن

برنامهٔ قبل LED را با دکمه روشن نگه می‌دارد. حالا می‌خواهیم مثل چراغ خواب: هر بار که دکمه فشرده شد، LED عوض شود (روشن↔خاموش). این «هر بار» یعنی یک رویداد (فشردن)، نه یک وضعیت (فشرده‌بودن). دکمه ممکن است ده‌ها میلی‌ثانیه پایین بماند و برنامه در این مدت میلیون‌ها بار می‌پرسد. اگر در هر پرسش عوض کنیم، LED تند می‌پرد. باید لحظهٔ تغییر از ۱ به ۰ را بگیریم: لبهٔ پایین‌رونده (falling edge). راه ساده: وضعیت قبلی را نگه دار و فقط وقتی «قبلا رها بود و حالا فشرده است» عوض کن.

همین منطق را با toggle.c روی برد می‌گذاریم. به دو فرق نسبت به button.c دقت کن: دو متغیر وضعیت، و یک تأخیر کوتاه بعد از تشخیص:

#include "stm32f4.h"

#define LED_PIN    5u
#define BUTTON_PIN 13u

static void delay(volatile uint32_t n)
{
    while (n--) {
    }
}

static int button_pressed(void)
{
    return (GPIOC->IDR & (1u << BUTTON_PIN)) == 0u;
}

int main(void)
{
    RCC->AHB1ENR |= RCC_AHB1ENR_GPIOAEN | RCC_AHB1ENR_GPIOCEN;
    (void)RCC->AHB1ENR;

    GPIOA->MODER = (GPIOA->MODER & ~(3u << (LED_PIN * 2u)))
                 | (1u << (LED_PIN * 2u));
    GPIOC->MODER &= ~(3u << (BUTTON_PIN * 2u));
    GPIOC->PUPDR = (GPIOC->PUPDR & ~(3u << (BUTTON_PIN * 2u)))
                 | (1u << (BUTTON_PIN * 2u));

    int was_pressed = 0;
    int led_on = 0;

    for (;;) {
        int now = button_pressed();
        if (now && !was_pressed) {
            led_on = !led_on;
            if (led_on) {
                GPIOA->BSRR = 1u << LED_PIN;
            } else {
                GPIOA->BSRR = 1u << (LED_PIN + 16u);
            }
            delay(30000u);
        }
        was_pressed = now;
    }
}
  1. delay. همان تأخیر volatile. اینجا برای «خنثی‌کردن پرش» استفاده می‌شود.
  2. فشرده است؟ مثل قبل: بیت ۱۳ صفر است.
  3. حافظهٔ برنامه. was_pressed = وضعیت دور قبل؛ led_on = LED الان روشن است؟ دو متغیر محلی که در main می‌مانند (main هرگز تمام نمی‌شود).
  4. حلقه. پولینگ.
  5. وضعیت کنونی. یک بار می‌خوانیم و در متغیر می‌گذاریم تا در این دور یک مقدار ثابت داشته باشیم.
  6. لبهٔ فشردن. «الان فشرده و قبلا رها»: فقط همین لحظه درست است.
  7. عوض‌کردن LED. led_on برعکس می‌شود و با یک نوشتن BSRR روی پایه اعمال.
  8. تأخیر ضد پرش. حدود ۱۵ میلی‌ثانیه (۳۰ هزار دور، هر دور تقریبا ۸ چرخه، روی ۱۶ مگاهرتز)، تا پرش‌های تماس فلزی (شکل بعد) گذشته باشد. این روش ساده است و همین‌جا کار می‌کند؛ ولی در این مدت CPU هیچ کار دیگری نمی‌کند. ماشین حالت و SysTick (درس‌های ۴.۶ و ۵.۴) راه حرفه‌ای‌اند.
  9. به‌خاطر سپردن. وضعیت این دور می‌شود «وضعیت قبلی» برای دور بعد.

چرا یک فشردن، چند رویداد است؟

دکمه مکانیکی است: دو تیغهٔ فلزی که برخورد می‌کنند. لحظهٔ برخورد، تیغه چند بار به هم می‌خورد و جدا می‌شود؛ مثل توپ که روی زمین می‌جهد. این را پرش تماس (bounce) می‌گویند. سرعت CPU میلیون‌ها بار در ثانیه است، پس هر پرش را «یک فشردن» می‌بیند.

ببین سه راه شمارش روی یک دنبالهٔ نمونه‌های دکمه چه می‌دهند. این برنامه روی PC اجرا می‌شود (همان منطق را بدون سخت‌افزار امتحان می‌کنیم). هر عدد در آرایه یک بار پرسیدن PC13 است: ۱ = رها، ۰ = فشرده. دنباله شبیه شکل بالاست: پرش هنگام فشردن، نگه‌داشتن، رها کردن با پرش. فقط یک فشردن واقعی داریم.

#include <stdio.h>

int main(void)
{
    /* هر عدد یک بار پرسیدن PC13 است: 1 = رها، 0 = فشرده (یک فشردن واقعی با پرش‌ها) */
    const int s[] = {1,1,0,1,0,1,0,0,0,0,0,0,1,0,1,0,1,1,1};
    const int n = (int)(sizeof s / sizeof s[0]);

    int level = 0;                  /* هر نمونهٔ صفر را بشمار */
    int edge = 0;                   /* هر رفتن از ۱ به ۰ را بشمار */
    int stable = 0;                 /* فقط وقتی ۴ صفر پشت‌سرهم دیدی بشمار */
    int prev = 1, run0 = 0, armed = 1;

    for (int i = 0; i < n; i++) {
        if (s[i] == 0) {
            level++;
            run0++;
        } else {
            run0 = 0;
            armed = 1;
        }
        if (prev == 1 && s[i] == 0) {
            edge++;
        }
        if (run0 == 4 && armed) {
            stable++;
            armed = 0;
        }
        prev = s[i];
    }
    printf("level counting : %d\n", level);
    printf("edge counting  : %d\n", edge);
    printf("debounced (4)  : %d\n", stable);
    return 0;
}
  1. نمونه‌ها. ۱۹ بار پرسیدن. پرش هنگام فشردن، چند نمونهٔ پایدار صفر، سپس پرش هنگام رها کردن. n تعداد نمونه‌هاست (طول آرایه را sizeof حساب می‌کند).
  2. سه شمارنده. هر روش یک عدد جدا: «سطح» (هر نمونهٔ ۰)، «لبه» (هر رفتن از ۱ به ۰)، «پایدار» (فقط وقتی ۴ نمونهٔ پشت هم ۰).
  3. حالت کمکی. prev نمونهٔ قبل، run0 طول رشتهٔ صفرها، armed یعنی «اجازه داریم دوباره بشماریم».
  4. به‌روزرسانی رشتهٔ صفر. هر صفر: سطح و طول رشته زیاد می‌شود. هر یک: رشته قطع و دوباره مجاز می‌شویم.
  5. شمارش لبه. قبلا ۱ و الان ۰.
  6. شمارش پایدار. فقط وقتی ۴ صفر پشت‌سرهم دیدیم و از آخرین ۱ بعد هنوز نشمرده‌ایم. armed = 0 جلوی شمارش دوباره در همان رشته را می‌گیرد. این همان ایدهٔ «نمونه‌برداری پایدار» (debounce) است: تغییر را فقط وقتی قبول کن که چند نمونه پشت هم تأییدش کنند.
  7. به‌روز کردن prev. نمونهٔ این دور می‌شود «قبلی» دور بعد.
  8. چاپ. سه عدد.
$ gcc -std=c11 -Wall -Wextra -o bounce bounce.c
$ ./bounce
level counting : 10
edge counting  : 5
debounced (4)  : 1

شمارش «سطح» عدد ۱۰ می‌دهد (هر نمونهٔ صفر). شمارش «لبه» عدد ۵: دقیقا همان پنج دایره در شکل. فقط روش «پایدار» عدد درست، یعنی ۱، را می‌دهد. یک تفاوت را ببین: پرش‌های هنگام رها کردن (شمارهٔ ۴ و ۵) بدون محافظت «دو فشردن جعلی» می‌سازند. درس تکراری ولی مهم: از روی یک لبهٔ تنها نمی‌شود «فشردن واقعی» را تشخیص داد؛ باید زمان یا تکرار را به کمک بگیری.

همین برنامه با HAL و LL

حالا که زیر کاپوت را دیدی، ببین ST همین کار را چطور برایت بسته‌بندی کرده. سه سطح وجود دارد:

سطحچه شکلی؟هزینه و مزیت
رجیستر خام (این درس)GPIOA->BSRR = 1u << 5;کمترین کد و کاملا شفاف. باید مرجع (RM0383) را بخوانی
CMSIS (stm32f4xx.h)همان، ولی با نام‌های آماده مثل RCC_AHB1ENR_GPIOAENهدر رسمی؛ همان رجیستر خام با نام استاندارد. هیچ هزینهٔ زمان اجرا ندارد
LL (Low-Layer)توابع static inline نازک، مثل LL_GPIO_TogglePinتقریبا هم‌سرعت رجیستر، ولی نام‌ها خواناترند
HALHAL_GPIO_Init() با struct پیکربندیقابل‌حمل بین تراشه‌های ST؛ کد و RAM بیشتر و کندتر، اما سریع‌ترین راه شروع

در سطح CMSIS، همین سه خط ما با هدر رسمی stm32f4xx.h (بستهٔ CMSIS device) نوشته می‌شود: RCC->AHB1ENR |= RCC_AHB1ENR_GPIOAEN; و بقیه دقیقا مثل ما. تنها فرق این است که ST هدر را نوشته و تست کرده. برای نام ماسک هر بیت، فایل stm32f411xe.h همان بسته را ببین؛ نام‌ها در نسخه‌های مختلف بسته ممکن است کمی فرق کنند.

و در سطح HAL، برنامهٔ کامل چشمک (بدون تنظیم ساعت سیستم که CubeMX می‌سازد) این شکلی است. این کد در این محیط کامپایل نمی‌شود چون به بستهٔ HAL نیاز دارد؛ ولی نام‌ها از مستندات رسمی STM32CubeF4 HAL هستند:

#include "main.h"                       // هدر ساخته‌شده با STM32CubeMX

int main(void)
{
    HAL_Init();                         // آماده‌سازی HAL و SysTick
    /* ساعت سیستم: SystemClock_Config() که CubeMX می‌سازد */

    __HAL_RCC_GPIOA_CLK_ENABLE();       // قدم ۱: ساعت

    GPIO_InitTypeDef gpio = {0};
    gpio.Pin   = GPIO_PIN_5;            // قدم ۲: حالت
    gpio.Mode  = GPIO_MODE_OUTPUT_PP;
    gpio.Pull  = GPIO_NOPULL;
    gpio.Speed = GPIO_SPEED_FREQ_LOW;
    HAL_GPIO_Init(GPIOA, &gpio);

    while (1) {
        HAL_GPIO_TogglePin(GPIOA, GPIO_PIN_5);   // قدم ۳: کار
        HAL_Delay(500);                 // نیم ثانیه
    }
}
  1. main.h. CubeMX این فایل را برای پروژه می‌سازد؛ HAL و اسم‌هایی مثل LD2_Pin را وارد می‌کند.
  2. HAL_Init. تنظیمات پایه و راه‌اندازی SysTick (برای HAL_Delay). ما در درس ۵.۴ خودمان همین را می‌سازیم.
  3. قدم ۱. ماکرویی که همان RCC->AHB1ENR |= … را می‌نویسد.
  4. قدم ۲. یک struct پر می‌کنی و به تابع می‌دهی. تابع همان کار MODER، OTYPER، PUPDR و OSPEEDR را انجام می‌دهد. این چند رجیستر را با یک تابع تنظیم می‌کند؛ ولی هزینه‌اش این است که کارش را با بررسی‌ها و شاخه‌های زیاد انجام می‌دهد (کدش صدها بایت است، نه ده‌ها).
  5. قدم ۳. HAL_GPIO_TogglePin وضعیت پایه را برعکس می‌کند و HAL_Delay بر پایهٔ SysTick صبر می‌کند (بدون شمارش خام).
پس کدام را انتخاب کنم؟

برای پروژهٔ حرفه‌ای معمولا ترکیب: HAL برای بخش‌های پیچیده و کم‌زمان‌حساس (USB، فایل‌سیستم)، رجیستر/LL برای مسیرهای سریع و ساده. مهم‌تر: چون رجیستر را فهمیده‌ای، وقتی HAL درست کار نکرد یا مستنداتش کم بود، می‌توانی خودت درون آن را ببینی. اصل آموزش امروز همین است.

اگر LED چشمک نمی‌زند: فهرست وارسی

در عمل بیشتر خرابی‌ها از فهرست کوتاه زیر می‌آیند. از بالا به پایین وارسی کن:

نشانهعلت رایجراه دیدن / اصلاح
هیچ اتفاقی نمی‌افتدساعت GPIOA روشن نشدهبیت ۰ RCC_AHB1ENR را یک کن. در دیباگر رجیستر را ببین
LED همیشه خاموش/روشنMODER پایه ۵ خروجی نشده، یا دیگران را هم پاک کردیبا الگوی «پاک کن، بگذار»؛ مقدار MODER را بعد از اجرا بخوان
LED فقط روشن می‌شودبرای خاموش کردن هم بیت ۵ نوشته‌ایخاموش‌کردن = بیت 5 + 16 = 21
LED «نیمه‌روشن» دائمیحلقهٔ تأخیر حذف شده (بدون volatile)؛ LED با فرکانس بالا می‌پردشمارنده را volatile کن (تمرین ۲)
پس از ریختن، دیباگر وصل نمی‌شودMODER را کامل بازنویسی کردی و پایه‌های SWD (PA13/PA14) را ورودی کردیریست سخت (دکمهٔ RESET را نگه دار و دوباره وصل کن)، سپس کد را اصلاح کن
برنامه اجرا نمی‌شود، LED دست‌نخوردهstartup یا link.ld اشتباه: جدول برداری در آدرس نادرستبا objdump -s -j .isr_vector ببین اولین کلمه 0x20020000 باشد
فایل کامپایل شد ولی نمی‌ریزدفایل اشتباه (مثلا .o) یا آدرس Flash غلط.bin را در 0x08000000 بریز؛ ELF آدرس‌ها را خودش دارد

آزمون این درس

برای اینکه نوشتن روی GPIOA->MODER واقعا اثر کند، اول باید چه کاری انجام شود؟

  1. نوشتن در BSRR
  2. روشن‌کردن ساعت GPIOA با RCC->AHB1ENR |= RCC_AHB1ENR_GPIOAEN
  3. نوشتن در ODR
  4. فعال‌کردن وقفه در NVIC
هر پریفرال STM32 به‌طور پیش‌فرض بی‌ساعت است. بدون آن نوشتن بی‌خطا ولی بی‌اثر است. قدم اول همیشه ساعت است.

دستور GPIOA->BSRR = 1u << 21; چه می‌کند؟

  1. پایهٔ PA21 را روشن می‌کند
  2. PA5 را روشن می‌کند
  3. همهٔ پایه‌های پورت A را خاموش می‌کند
  4. فقط PA5 را خاموش می‌کند و بقیه پایه‌ها را دست‌نخورده می‌گذارد
بیت ۵+۱۶ = ۲۱ در نیمهٔ «Reset» است. نوشتن صفر در بیت‌های دیگر هیچ اثری ندارد، پس بقیهٔ پایه‌ها دست‌نخورده می‌مانند.

این شرط برای «آیا دکمه فشرده است؟» نوشته شده ولی هیچ‌وقت درست نمی‌شود. چرا؟
if (GPIOC->IDR & (1u << 13) == 0u)

  1. چون == تقدم بالاتری از & دارد؛ اول (1u << 13) == 0u حساب می‌شود که ۰ است و بعد IDR & 0 همیشه صفر (نادرست) است
  2. چون IDR را نمی‌شود خواند
  3. چون پرانتز دور 1u << 13 اضافه است
  4. چون باید ۱۴ می‌نوشتیم نه ۱۳
راه درست: if ((GPIOC->IDR & (1u << 13)) == 0u). قانون: همیشه ماسک‌گذاری را در پرانتز جدا کن (درس ۳.۱).

روی Nucleo-F411RE دکمهٔ آبی رها است. بیت ۱۳ از GPIOC->IDR چند می‌خواند؟

  1. ۰، چون پایه ورودی است و ورودی همیشه صفر می‌خواند
  2. ۰، چون هیچ‌کس پایه را بالا نبرده
  3. ۱، چون بالاکش پایه را بالا نگه می‌دارد (فعال-پایین)
  4. مقدار تصادفی، چون پایه شناور است
رها = ۱، فشرده = ۰. این «فعال-پایین» است و به‌خاطر مقاومت بالاکش.

حلقهٔ for (uint32_t i = 0; i < 400000u; i++) {} با -O2 چه می‌شود؟

  1. دقیقا ۴۰۰ هزار دور اجرا می‌شود و حدود ۰٫۲ ثانیه طول می‌کشد
  2. کامپایلر آن را حذف می‌کند، چون بدنه‌ای ندارد و i جای دیگری استفاده نمی‌شود (مگر i را volatile کنی)
  3. حلقه کندتر می‌شود چون -O2 کد را بزرگ‌تر می‌کند
  4. خطای کامپایل می‌دهد
خروجی واقعی اسمبلی در تمرین ۲ همین را نشان می‌دهد: از حلقه اثری نمانده. برای تأخیر خام همیشه شمارنده را volatile کن.

آدرس GPIOC_IDR در STM32F411 کدام است؟

  1. 0x40020010
  2. 0x40020814
  3. 0x40023810
  4. 0x40020810
GPIOC در 0x40020800 شروع می‌شود و IDR آفست 0x10 دارد: 0x40020810.

تمرین‌ها

تمرین ۱: الگوی «دو چشمک و مکث»

می‌خواهیم LED دو چشمک کوتاه بزند، بعد مکث طولانی داشته باشد و همین را تکرار کند (مثل ضربان قلب).

  1. پیش‌بینی: در یک دورهٔ کامل، چند بار در BSRR می‌نویسی؟ (روشن و خاموش را جدا بشمار.)
  2. حل: یک تابع flash_once() بنویس که یک چشمک بزند و آن را دوبار صدا بزن، بعد مکث بلند.
  3. تغییر: تعداد چشمک‌ها را به سه تغییر بده. برای این باید چه چیزی را در کد عوض کنی؟
راهنمایی

همان قدم‌های blink.c؛ فقط بدنهٔ روشن-صبر-خاموش-صبر را در یک تابع static void بگذار و آن را از داخل حلقه صدا بزن. مکث بلند = یک delay با عدد بزرگ‌تر.

چه باید ببینی؟

روی برد: LD2 دو بار می‌زند (هرکدام حدود ۰٫۰۷ ثانیه روشن و ۰٫۰۷ خاموش) و بعد حدود ۰٫۶ ثانیه خاموش می‌ماند؛ دوباره از اول. (زمان‌ها تخمینی‌اند؛ مثل بخش تأخیر.) پاسخ الف: چهار بار در هر دوره.

تمرین ۳: چشمک تند وقتی دکمه فشرده است (چالش سخت‌افزاری)

LED مدام چشمک بزند: آرام (هر نیم‌دوره حدود ۰٫۲ ثانیه) وقتی دکمهٔ آبی رها است، و تند (حدود یک‌هشتم آن) وقتی فشرده است.

  1. طرح: کدام رجیسترها و چه ساعتی لازم است؟ (پورت‌ها و بیت‌ها را فهرست کن.)
  2. حل: برنامه را بنویس. تأخیر را از روی وضعیت دکمه انتخاب کن.
  3. فکر کن: اگر دکمه را وسط یک تأخیر بلند بزنی، LED کِی تند می‌شود؟ چرا؟ راه‌حلش کجای دورهٔ ماست؟
راهنمایی

هر دور حلقه، اول دکمه را بخوان و طول تأخیر را بر اساس آن بگذار: pressed ? کوتاه : بلند. سپس همان چشمک قبلی را با این طول تأخیر بزن.

چه باید ببینی؟

روی برد: LD2 آرام می‌زند. با فشردن و نگه‌داشتن B1، در چشمک بعدی سریع می‌زند و با رها کردن دوباره آرام. پاسخ ج: تا پایان تأخیر جاری صبر باید کرد؛ چون CPU سرگرم شمارش است و دکمه را نمی‌بیند.

#include <stdint.h>

#define RCC_AHB1ENR (*(volatile uint32_t *)0x40023830u)
#define GPIOA_MODER (*(volatile uint32_t *)0x40020000u)
#define GPIOA_BSRR  (*(volatile uint32_t *)0x40020018u)
#define GPIOC_PUPDR (*(volatile uint32_t *)0x4002080Cu)
#define GPIOC_IDR   (*(volatile uint32_t *)0x40020810u)

static void delay(volatile uint32_t n)
{
    while (n--) {
    }
}

int main(void)
{
    RCC_AHB1ENR |= (1u << 0) | (1u << 2);
    (void)RCC_AHB1ENR;
    GPIOA_MODER = (GPIOA_MODER & ~(3u << 10)) | (1u << 10);
    GPIOC_PUPDR = (GPIOC_PUPDR & ~(3u << 26)) | (1u << 26);

    for (;;) {
        uint32_t pressed = (GPIOC_IDR & (1u << 13)) == 0u;
        uint32_t wait = pressed ? 50000u : 400000u;

        GPIOA_BSRR = 1u << 5;
        delay(wait);
        GPIOA_BSRR = 1u << 21;
        delay(wait);
    }
}

  2. تأخیر. volatile.
  3. main.
  4. ساعت دو پورت. بیت ۰ (A) و بیت ۲ (C) با هم؛ سپس یک خواندن بی‌مصرف.
  5. PA5 خروجی.
  6. بالاکش برای PC13. بیت‌های ۲۷..۲۶ = 01. (حالت MODER پس از ریست ورودی است.)
  7. حلقه.
  8. دکمه. ۱ اگر فشرده (بیت ۱۳ صفر).
  9. انتخاب تأخیر. ۵۰ هزار دور (تند) یا ۴۰۰ هزار (آرام). نسبت ۸ به ۱.
  10. چشمک با تأخیر انتخاب‌شده.

نکتهٔ پاسخ ج: دکمه فقط در لحظهٔ شروع هر چشمک خوانده می‌شود. این ضعف پولینگ است: تو فقط وقتی می‌فهمی که «خودت نگاه کنی». راه‌حل: وقفه (درس ۵.۳). آنجا سخت‌افزار خودش تو را صدا می‌زند.

حرف مربی

تقریبا هرکسی روی STM32 bare-metal دو بار گیر می‌کند: «چرا هیچ اتفاقی نمی‌افتد؟» (ساعت پریفرال را فراموش کرده‌ای) و «چرا بعد از فلش، دیباگر وصل نمی‌شود؟» (MODER را بازنویسی و SWD را ورودی کرده‌ای). هر دو با فهرست وارسی همین درس در یک دقیقه حل می‌شوند. عادت امروز: قبل از فرض «سخت‌افزار خراب است»، ساعت، حالت و بیت را بشمار. LED خودش اولین ابزار دیباگ توست.

تقریبا هر کسی که برای اولین بار روی STM32 bare-metal کار می‌کند، دو بار گیر می‌کند: یکی «چرا هیچ اتفاقی نمی‌افتد؟» که ۹۰٪ وقت ساعت پریفرال را فراموش کرده‌ای، و دیگری «چرا بعد از یک بار فلش، دیباگر وصل نمی‌شود؟» که MODER را بازنویسی کرده‌ای و SWD را کشته‌ای. خبر خوب: هر دو با فهرست وارسی همین درس در یک دقیقه حل می‌شوند. عادتی که از امروز با خودت ببر: قبل از فرض «سخت‌افزار خراب است»، ساعت، حالت و بیت را بشمار. و اگر کمکی از دیباگر نداری، LED خودش بهترین ابزار دیباگ اول توست.

خلاصه یک‌دقیقه‌ای

  • bare-metal یعنی مستقیم با رجیستر؛ HAL و LL فقط بسته‌بندی همان‌اند.
  • هر پریفرال: ساعت (RCC)، حالت (مثلا MODER)، کار (مثلا BSRR/IDR). ساعت خاموش = نوشتن بی‌اثر.
  • چشمک LD2: RCC_AHB1ENR بیت ۰؛ MODER بیت‌های ۱۱..۱۰ = ۰۱؛ BSRR بیت ۵ (روشن) و ۲۱ (خاموش).
  • دکمهٔ آبی PC13 فعال-پایین است (رها = ۱، فشرده = ۰). برای «یک بار» باید لبه را بگیری و پرش تماس را مهار کنی.
  • MODER را همیشه با «پاک کن، بگذار» بنویس؛ با = ساده SWD خودت را می‌کُشی.
  • پروژه: stm32f4.h + startup + linker script + Makefile؛ ساختش با arm-none-eabi-gcc، ریختنش با drag-and-drop یا OpenOCD.
  • تأخیر با شمارش، بد است و پولینگ ضعف دارد. درس‌های بعد: وقفه و تایمر.
