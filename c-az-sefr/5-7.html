تا اینجا هر برنامه‌ای که نوشتیم مستقیم با رجیستر یک تراشهٔ مشخص حرف می‌زد. حالا فرض کن مشتری بگوید «همین دستگاه را روی ESP32 هم می‌خواهیم». اگر کدت مثل یک تکهٔ چسب‌خورده به STM32 باشد، باید از صفر بنویسی‌اش. در این درس یاد می‌گیری کد را لایه‌لایه بچینی تا فقط یک لایهٔ کوچک به تراشه بچسبد و بقیه، حتی روی PC و بدون هیچ بردی، آزمایش شود.

🎯 بعد از این درس می‌توانی

  • لایه‌های یک برنامهٔ embedded (برنامه، درایور، HAL، backend) را بشناسی و بگویی هر لایه چه کسی را می‌شناسد
  • قرارداد HAL را با struct از اشاره‌گر تابع بنویسی
  • درایور LED را طوری بنویسی که به هیچ تراشه‌ای وابسته نباشد
  • دو backend بسازی: تقلبی (mock) روی PC و رجیستر خام STM32
  • خطا را با کد وضعیت (enum) از لایه‌ها عبور بدهی و حالت را سازگار نگه داری
  • همین معماری را در ESP-IDF و STM32Cube HAL بشناسی

🧰 پیش‌نیاز و وسایل

  • درس ۴.۳ (اشاره‌گر به تابع و شبه‌vtable) و ۴.۲ (پروژهٔ چندفایلی و Makefile)
  • درس ۵.۲ (GPIO با رجیستر: RCC، MODER، BSRR) و ۵.۵ (لایهٔ انتقال و mock)
  • gcc و make روی PC؛ برای وارسی بخش STM32 هم arm-none-eabi-gcc
  • برد لازم نیست: بخش بزرگ درس روی PC اجرا می‌شود

ایدهٔ اصلی: سوکت و دوشاخه

کتری برقی‌ات را در نظر بگیر. کتری نمی‌داند برق از کدام نیروگاه می‌آید؛ زغال‌سنگ، آب یا خورشید برایش فرقی ندارد. فقط یک قرارداد را می‌شناسد: دوشاخه با دو پایهٔ مشخص. هر خانه‌ای که سوکت استاندارد داشته باشد، کتری در آن کار می‌کند و اگر نیروگاه عوض شود، کتری را دور نمی‌ریزی.

مثال از زندگی روزمره

در نرم‌افزار، «کتری» درایور LED است، «سوکت» یک struct از توابع است (به آن جدول عملیات می‌گوییم) و «نیروگاه» سخت‌افزار زیرین است: رجیسترهای STM32، درایور ESP32، یا حتی یک شبیه‌ساز ساده روی PC. تا وقتی سوکت همان است، هر سه نیروگاه به کتری برق می‌دهند.

به این کار می‌گویند معماری لایه‌ای (layered architecture). ایده ساده است: کد را به چند لایه بشکن؛ هر لایه یک کار دارد و فقط با لایهٔ درست زیر خودش حرف می‌زند. هر چه به تراشه مربوط است در پایین‌ترین لایه جمع می‌شود.

بدون لایه‌بندی: کدی که به تراشه چسبیده است

یک بار ببین برنامهٔ «چشمک LED» درس ۵.۲ اگر همه‌چیز را در main بریزیم چه شکلی می‌شود:

#include <stdint.h>

#define RCC_AHB1ENR (*(volatile uint32_t *)0x40023830u)
#define GPIOA_MODER (*(volatile uint32_t *)0x40020000u)
#define GPIOA_BSRR  (*(volatile uint32_t *)0x40020018u)

static int g_led_on;

int main(void)
{
    RCC_AHB1ENR |= 1u;
    GPIOA_MODER = (GPIOA_MODER & ~(3u << 10)) | (1u << 10);

    for (;;) {
        g_led_on = !g_led_on;
        GPIOA_BSRR = g_led_on ? (1u << 5) : (1u << 21);
        for (volatile uint32_t i = 0; i < 400000u; i++) {
        }
    }
}
  1. آدرس‌های خام. سه رجیستر STM32F411 با عدد نوشته شده‌اند. این سه خط فقط روی این خانواده از تراشه معنی دارند؛ روی ESP32 یا حتی روی PC، خواندن این آدرس‌ها یا خطا می‌دهد یا برنامه را می‌ترکاند.
  2. حالت LED. یک متغیر که می‌گوید LED روشن است یا خاموش.
  3. راه‌اندازی. ساعت GPIOA را روشن می‌کند و پین ۵ را خروجی می‌کند (بیت‌های ۱۱:۱۰ برابر 01). عدد 10 و 5 «عدد جادویی» هستند: خواننده باید حدس بزند یعنی پین ۵.
  4. حلقهٔ اصلی. حالت را برعکس می‌کند، به BSRR می‌نویسد و صبر می‌کند.

این برنامه روی برد کار می‌کند، ولی سه مشکل جدی دارد:

  • قابل‌حمل نیست. برای ESP32 هیچ خطش به دردت نمی‌خورد.
  • قابل‌آزمایش نیست. نمی‌توانی روی PC بفهمی «اگر LED از نوع فعال-پایین باشد چه می‌شود؟». همیشه برد لازم است.
  • قابل‌استفادهٔ دوباره نیست. اگر LED دوم روی PB0 بگذاری، باید همه‌چیز را کپی و دستکاری کنی؛ و اگر یک عدد را اشتباه کپی کنی، پین دیگری خراب می‌شود.

این دردها را از درس‌های قبل می‌شناسی: در درس ۴.۲ ماژول‌های جدا دیدیم و در ۵.۵ لایهٔ انتقال. حالا همان فکر را برای کل برنامه به کار می‌بریم.

قاعدهٔ طلایی: وابستگی فقط رو به پایین

لایهٔ بالا لایهٔ پایین را می‌شناسد (include می‌کند)، ولی لایهٔ پایین هیچ‌وقت بالایی را نمی‌شناسد. اگر led.c بگوید #include "main.h" یا hal_gpio_stm32.c بگوید #include "led.h"، رشتهٔ وابستگی حلقه می‌شود و دیگر نمی‌توانی یک لایه را جدا آزمایش کنی. هر وقت خواستی از پایین به بالا خبر بدهی، از callback استفاده کن (درس ۴.۳).

چرا درایور به «قرارداد» وابسته می‌شود، نه به تراشه؟

ساده‌ترین لایه‌بندی این است که led.c مستقیم HAL_GPIO_WritePin (تابع کتابخانهٔ ST) را صدا بزند. لایه‌ها هست ولی درایور هنوز به ST چسبیده است. راه بهتر: قرارداد را خودمان بنویسیم و هر backend آن را پیروی کند. به این کار وارونگی وابستگی (dependency inversion) می‌گویند: به‌جای اینکه درایور به تراشه وابسته باشد، تراشه است که خودش را با قراردادِ درایور وفق می‌دهد.

قرارداد: hal_gpio.h

قرارداد یک فایل هدر است: نوع‌ها و یک struct از اشاره‌گر تابع. هیچ کدی (پیاده‌سازی) در آن نیست. این فایل را لایهٔ بالا مالک است، نه backend ها.

#ifndef HAL_GPIO_H
#define HAL_GPIO_H

#include <stdint.h>

/* شمارهٔ پایه = حرف پورت × ۱۶ + شمارهٔ پین؛ PA5 → 5، PC13 → 45 */
#define HAL_PIN(port, n) ((uint8_t)((((port) - 'A') * 16) + (n)))

typedef enum {
    HAL_OK = 0,
    HAL_ERR_PARAM,
    HAL_ERR_IO
} hal_status_t;

typedef enum {
    HAL_LOW = 0,
    HAL_HIGH = 1
} hal_level_t;

/* قرارداد: هر backend این سه تابع را می‌دهد */
typedef struct {
    hal_status_t (*init_output)(uint8_t pin);
    hal_status_t (*write)(uint8_t pin, hal_level_t level);
    hal_status_t (*read)(uint8_t pin, hal_level_t *level);
} hal_gpio_ops_t;

#endif
  1. Include guard. جلوی وارد شدن دوبارهٔ هدر را می‌گیرد (درس ۴.۲).
  2. شمارهٔ پایه. یک عدد ۸ بیتی: حرف پورت × ۱۶ + شمارهٔ پین. پس PA5 می‌شود ۵، PB0 می‌شود ۱۶ و PC13 می‌شود ۴۵. یک عدد ساده روی هر تراشه‌ای معنی دارد. هر backend خودش می‌داند این عدد را چطور به پورت و پین ترجمه کند. ماکرو فقط برای خوانایی است: HAL_PIN('A', 5) از «۵» روشن‌تر است.
  3. کد وضعیت. هر تابع HAL یکی از سه حالت را برمی‌گرداند: موفق، پارامتر اشتباه (پایهٔ ناموجود) یا خطای سخت‌افزار. صفر = موفق، همان قرارداد پروژه (درس ۱.۴). چون enum است، مقایسه با HAL_ERR_IO از «۲» خواناتر است.
  4. سطح منطقی. HAL_LOW و HAL_HIGH: ولتاژ پایین و بالا، نه «روشن» و «خاموش»؛ چون LED فعال-پایین هم هست.
  5. جدول عملیات. سه اشاره‌گر تابع: خروجی‌کردن یک پایه، نوشتن سطح و خواندن سطح. هر backend یک نمونه از این struct می‌سازد. این همان «سوکت» مثال ابتدای درس است. اگر یک backend تابعی با امضای متفاوت بگذارد، کامپایلر همان‌جا خطا می‌دهد (پایین‌تر می‌بینی).

درایور LED: فقط «قرارداد» را می‌شناسد

حالا درایور. یک struct پیکربندی داریم (config struct) که می‌گوید LED به کدام پایه وصل است و فعال-بالاست یا فعال-پایین. یک struct هم برای حالت درایور داریم (به آن دستگیره یا handle می‌گویند). هیچ متغیر سراسری‌ای وجود ندارد؛ پس می‌توانی هر تعداد LED بسازی.

#ifndef LED_H
#define LED_H

#include <stdbool.h>
#include <stdint.h>
#include "hal_gpio.h"

typedef enum {
    LED_OK = 0,
    LED_ERR_ARG,
    LED_ERR_HW
} led_status_t;

typedef struct {
    uint8_t pin;
    bool active_low;        /* true: سطح LOW یعنی روشن */
} led_config_t;

typedef struct {
    const hal_gpio_ops_t *gpio;     /* خصوصی: مستقیم دست نزن */
    led_config_t cfg;
    bool on;
} led_t;

led_status_t led_init(led_t *led, const hal_gpio_ops_t *gpio,
                      const led_config_t *cfg);
led_status_t led_on(led_t *led);
led_status_t led_off(led_t *led);
led_status_t led_toggle(led_t *led);
bool led_is_on(const led_t *led);

#endif
  1. Include guard.
  2. وابستگی‌ها. فقط hal_gpio.h (قرارداد) آمده. نه هدر ST، نه هدر ESP. این سه خط تعیین می‌کنند درایور به چه چیزی وابسته است. اگر یک روز stm32f4xx.h اینجا ظاهر شد، لایه‌بندی شکسته است.
  3. کد وضعیت خود درایور. لایه‌ها کد خطای خودشان را دارند و کد خطای لایهٔ پایین را «ترجمه» می‌کنند. کاربر led نباید مجبور باشد معنی HAL_ERR_IO را بداند.
  4. پیکربندی. شمارهٔ پایه و قطبیت. active_low برای LED هایی است که با پایین کشیدن پایه روشن می‌شوند (وصل به +V از راه مقاومت). قطبیت یک ویژگی بردِ توست، نه منطق برنامه. پس در پیکربندی می‌آید، نه در دل کد.
  5. حالت درایور. اشاره‌گر به جدول عملیات، نسخه‌ای از پیکربندی و وضعیت فعلی LED. این struct را کاربر می‌سازد (حافظهٔ ایستا؛ بدون malloc) ولی نباید فیلدها را دست بزند. نگه‌داشتن on در خود درایور یعنی برای toggle لازم نیست دوباره از سخت‌افزار بخوانیم.
  6. API عمومی. پنج تابع با پیشوند led_ (درس ۲.۶: نام‌گذاری ماژولی). اولین پارامتر هر کدام همان دستگیره است.
#include "led.h"

#include <stddef.h>

static led_status_t from_hal(hal_status_t st)
{
    if (st == HAL_OK) {
        return LED_OK;
    }
    return (st == HAL_ERR_PARAM) ? LED_ERR_ARG : LED_ERR_HW;
}

static led_status_t led_apply(led_t *led, bool on)
{
    bool high = (on != led->cfg.active_low);
    hal_status_t st = led->gpio->write(led->cfg.pin, high ? HAL_HIGH : HAL_LOW);

    if (st != HAL_OK) {
        return from_hal(st);
    }
    led->on = on;
    return LED_OK;
}

led_status_t led_init(led_t *led, const hal_gpio_ops_t *gpio,
                      const led_config_t *cfg)
{
    if (led == NULL || gpio == NULL || cfg == NULL ||
        gpio->init_output == NULL || gpio->write == NULL) {
        return LED_ERR_ARG;
    }
    led->gpio = gpio;
    led->cfg = *cfg;
    led->on = false;

    hal_status_t st = gpio->init_output(cfg->pin);
    if (st != HAL_OK) {
        return from_hal(st);
    }
    return led_apply(led, false);
}

led_status_t led_on(led_t *led)     { return led_apply(led, true); }
led_status_t led_off(led_t *led)    { return led_apply(led, false); }
led_status_t led_toggle(led_t *led) { return led_apply(led, !led->on); }
bool led_is_on(const led_t *led)    { return led->on; }
  1. include ها. باز هم هیچ هدر تراشه‌ای نیست.
  2. ترجمهٔ خطا. HAL_ERR_PARAM (پایهٔ نامعتبر) را به LED_ERR_ARG ترجمه می‌کند و بقیه را به LED_ERR_HW. اگر کد پایین را عینا رد کنیم، لایهٔ برنامه باید HAL را هم بشناسد و مرز لایه‌ها می‌ریزد. ترجمه یعنی هر لایه فقط دو همسایه‌اش را می‌بیند.
  3. تابع مرکزی. اول سطح ولتاژ را با قطبیت حساب می‌کند. on != active_low یعنی: LED فعال-بالا و روشن ← HIGH؛ فعال-پایین و روشن ← LOW. فقط بعد از موفقیت حالت on عوض می‌شود. اگر نوشتن شکست بخورد، حالت درایور با آنچه واقعا روی پایه است همخوان می‌ماند؛ وگرنه toggle بعدی جهت اشتباه می‌رود.
  4. تنها فراخوانی سخت‌افزار. led->gpio->write(...): صدا زدن تابع از راه اشاره‌گر. درایور نمی‌داند این تابع در STM32 است، در ESP32 یا در mock.
  5. راه‌اندازی. ورودی‌ها را بررسی می‌کند (NULL و اشاره‌گر تابع‌های ضروری)، پیکربندی را کپی می‌کند، پایه را خروجی می‌کند و LED را خاموش می‌گذارد. کپی‌کردن *cfg (نه نگه‌داشتن اشاره‌گر به آن) یعنی کاربر می‌تواند struct پیکربندی را بعد از led_init دور بریزد (مثلا متغیر محلی باشد) بدون خطر آویزان‌شدن اشاره‌گر (درس ۳.۲).
  6. چهار تابع کوچک. همه فقط led_apply را با آرگومان مناسب صدا می‌زنند؛ toggle با !led->on.

backend اول: تقلبی روی PC

حالا اولین «نیروگاه»: پیاده‌سازی تقلبی (mock) که هیچ سخت‌افزاری ندارد؛ فقط یک آرایه در RAM است که سطح هر پایه را نگه می‌دارد و هر کار را چاپ می‌کند. علاوه بر سه تابع قرارداد، چند «دریچهٔ آزمون» هم دارد که فقط تست‌ها استفاده می‌کنند: خواندن سطح واقعی، شمارش نوشتن‌ها و شکست‌دادن عمدی نوشتن (تزریق خطا).

#ifndef HAL_GPIO_MOCK_H
#define HAL_GPIO_MOCK_H

#include "hal_gpio.h"

extern const hal_gpio_ops_t hal_gpio_mock_ops;

/* دریچه‌های آزمون: فقط برای تست‌ها */
hal_level_t hal_gpio_mock_level(uint8_t pin);
unsigned hal_gpio_mock_write_count(void);
void hal_gpio_mock_fail_writes(int enable);

#endif
  1. تنها نمونهٔ عمومی. فقط جدول عملیات از بیرون دیده می‌شود؛ خود توابع static اند (پنهان). هر backend یک شیء برای صدا زدن دارد و همین. کاربر نباید mock_write را مستقیم صدا بزند؛ همیشه از راه قرارداد.
  2. دریچه‌های آزمون. این‌ها در قرارداد HAL نیستند؛ چون فقط mock می‌تواند «سطح واقعی پایه» را گزارش کند. روی برد چنین چیزی نداریم (به جز خواندن IDR).
#include "hal_gpio_mock.h"

#include <stdio.h>

#define MOCK_PINS 80u                   /* پورت‌های A تا E */

static hal_level_t s_level[MOCK_PINS];
static uint8_t s_is_output[MOCK_PINS];
static unsigned s_writes;
static int s_fail;

static char port_of(uint8_t pin) { return (char)('A' + pin / 16u); }

static hal_status_t mock_init_output(uint8_t pin)
{
    if (pin >= MOCK_PINS) {
        return HAL_ERR_PARAM;
    }
    s_is_output[pin] = 1u;
    s_level[pin] = HAL_LOW;
    printf("[mock] P%c%u = output\n", port_of(pin), (unsigned)(pin % 16u));
    return HAL_OK;
}

static hal_status_t mock_write(uint8_t pin, hal_level_t level)
{
    if (pin >= MOCK_PINS || !s_is_output[pin]) {
        return HAL_ERR_PARAM;
    }
    if (s_fail) {
        return HAL_ERR_IO;
    }
    s_level[pin] = level;
    s_writes++;
    printf("[mock] P%c%u <- %s\n", port_of(pin), (unsigned)(pin % 16u),
           level == HAL_HIGH ? "HIGH" : "LOW");
    return HAL_OK;
}

static hal_status_t mock_read(uint8_t pin, hal_level_t *level)
{
    if (pin >= MOCK_PINS || level == NULL) {
        return HAL_ERR_PARAM;
    }
    *level = s_level[pin];
    return HAL_OK;
}

const hal_gpio_ops_t hal_gpio_mock_ops = {
    .init_output = mock_init_output,
    .write = mock_write,
    .read = mock_read,
};

hal_level_t hal_gpio_mock_level(uint8_t pin) { return s_level[pin]; }
unsigned hal_gpio_mock_write_count(void)     { return s_writes; }
void hal_gpio_mock_fail_writes(int enable)   { s_fail = enable; }
  1. تعداد پایه‌ها. ۸۰ = پنج پورت (A تا E) × ۱۶، مطابق فرمول HAL_PIN.
  2. حالت داخلی. آرایهٔ سطح‌ها، آرایهٔ «آیا خروجی شده؟»، شمارندهٔ نوشتن و پرچم خطا. همه static: فقط این فایل آن‌ها را می‌بیند (درس ۳.۵).
  3. حرف پورت. برای چاپ زیبا: پایهٔ ۵ می‌شود PA5.
  4. خروجی‌کردن. پایه‌ای که وجود ندارد خطای پارامتر می‌گیرد؛ وگرنه علامت «خروجی است» می‌خورد و سطحش صفر می‌شود.
  5. نوشتن. سه بررسی: پایه معتبر است؟ خروجی شده؟ خطا تزریق شده؟ فقط اگر همه درست بود، سطح ذخیره و چاپ می‌شود. بررسی «خروجی شده؟» باگ رایج «فراموش کردم init بزنم» را روی PC پیدا می‌کند. روی برد، نوشتن به پایهٔ خروجی‌نشده بی‌سروصدا هیچ اتفاقی نمی‌اندازد و ساعت‌ها دنبال باگ می‌گردی.
  6. خواندن. ساده: سطح ذخیره‌شده را برمی‌گرداند.
  7. جدول عملیات. با «مقداردهی نامزد» (درس ۳.۴): اسم هر عضو آمده، پس ترتیب مهم نیست و ناخوانا نمی‌شود. const یعنی این جدول تغییر نمی‌کند.
  8. دریچه‌ها. سه تابع یک‌خطی برای تست‌ها.

backend دوم: رجیستر خام STM32

حالا «نیروگاه» واقعی. همان سه تابع قرارداد، این بار با رجیستر STM32F411 (همان‌هایی که در درس ۵.۲ دیدی): RCC_AHB1ENR برای روشن‌کردن ساعت پورت، MODER برای خروجی‌کردن و BSRR برای نوشتن بی‌خطر (بدون خواندن-تغییر-نوشتن). چون شمارهٔ پایه را پورت×۱۶+پین تعریف کردیم، هر تابع پورت و پین را با / و % بیرون می‌کشد. پورت‌ها هر کدام 0x400 بایت آن‌طرف‌تر هستند: GPIOA در 0x40020000، GPIOB در 0x40020400 و…

این بلاک‌ها یک پروژهٔ جدا هستند و با کامپایلر ARM بررسی می‌شوند. دو هدر اول (hal_gpio.h و led.h) عینا همان فایل‌های بالا هستند و فقط برای اینکه این پروژه مستقل کامپایل شود در اینجا تکرار شده‌اند:

#include "hal_gpio_stm32.h"

#include <stddef.h>

#define REG32(addr)      (*(volatile uint32_t *)(addr))
#define RCC_AHB1ENR      REG32(0x40023830u)
#define GPIO_BASE(port)  (0x40020000u + 0x400u * (port))
#define GPIO_MODER(port) REG32(GPIO_BASE(port) + 0x00u)
#define GPIO_IDR(port)   REG32(GPIO_BASE(port) + 0x10u)
#define GPIO_BSRR(port)  REG32(GPIO_BASE(port) + 0x18u)

#define MAX_PORT 4u                     /* GPIOA تا GPIOE */

static hal_status_t stm32_init_output(uint8_t pin)
{
    uint32_t port = pin / 16u;
    uint32_t n = pin % 16u;

    if (port > MAX_PORT) {
        return HAL_ERR_PARAM;
    }
    RCC_AHB1ENR |= (1u << port);            /* ساعت پورت را روشن کن */
    (void)RCC_AHB1ENR;                      /* خواندن ساختگی: تأخیر کوتاه */
    GPIO_MODER(port) = (GPIO_MODER(port) & ~(3u << (2u * n)))
                     | (1u << (2u * n));    /* 01 = خروجی */
    return HAL_OK;
}

static hal_status_t stm32_write(uint8_t pin, hal_level_t level)
{
    uint32_t port = pin / 16u;
    uint32_t n = pin % 16u;

    if (port > MAX_PORT) {
        return HAL_ERR_PARAM;
    }
    GPIO_BSRR(port) = (level == HAL_HIGH) ? (1u << n) : (1u << (n + 16u));
    return HAL_OK;
}

static hal_status_t stm32_read(uint8_t pin, hal_level_t *level)
{
    uint32_t port = pin / 16u;

    if (port > MAX_PORT || level == NULL) {
        return HAL_ERR_PARAM;
    }
    *level = ((GPIO_IDR(port) >> (pin % 16u)) & 1u) ? HAL_HIGH : HAL_LOW;
    return HAL_OK;
}

const hal_gpio_ops_t hal_gpio_stm32_ops = {
    .init_output = stm32_init_output,
    .write = stm32_write,
    .read = stm32_read,
};
  1. ماکروی رجیستر. آدرس را به اشاره‌گر volatile تبدیل می‌کند و * می‌گذارد؛ پس می‌توان آن را مثل متغیر نوشت و خواند (درس ۳.۶).
  2. رجیستر ساعت. RCC_AHB1ENR آفست 0x30 از 0x40023800 است؛ بیت n ساعت پورت n را روشن می‌کند (بیت ۰ = GPIOA).
  3. آدرس محاسبه‌شده. پایهٔ هر پورت = 0x40020000 + 0x400 × شمارهٔ پورت. سه رجیستر لازم: MODER (+0x00)، IDR (+0x10)، BSRR (+0x18). ماکرو با آرگومان است تا بشود هر پورت را انتخاب کرد؛ ولی چون آرگومان یک بار ارزیابی می‌شود و عبارت ساده است، خطر «ارزیابی دوباره» (درس ۴.۱) وجود ندارد.
  4. پورت‌های معتبر. A تا E (۰ تا ۴). GPIOH هم روی F411 هست ولی در طراحی ساده‌مان نمی‌گذاریم؛ در تمرین ۳ فکرش را می‌کنی.
  5. خروجی‌کردن. پورت و پین را جدا می‌کند، ساعت را روشن می‌کند، یک بار همان رجیستر را می‌خواند (تأخیر کوتاه تا ساعت پایدار شود) و دو بیت MODER پین را روی 01 (خروجی) می‌گذارد. اول دو بیت را با ماسک صفر می‌کند (~(3u << 2n)) و بعد 01 می‌نویسد. اگر ماسک نباشد، بیت‌های قبلی پین ممکن است بمانند و حالت اشتباه شود (درس ۳.۱).
  6. نوشتن با BSRR. برای HIGH بیت n و برای LOW بیت n+16 را یک می‌کند. بیت‌های صفر هیچ اثری ندارند. BSRR نوشتنی است و «اتمی» عمل می‌کند؛ یعنی خواندن-تغییر-نوشتن لازم نیست و وقفه وسط کار هیچ پینِ دیگری را خراب نمی‌کند (درس ۳.۶ و ۵.۳).
  7. خواندن. IDR را می‌خواند و بیت پین را جدا می‌کند.
  8. جدول عملیات. سه تابع static و یک جدول عمومی. هیچ کد دیگر در پروژه نام stm32_write را نمی‌بیند.

بیت ۵ را یک کن: 0x00000020 = «PA5 را بالا ببر». بیت ۲۱ (۵+۱۶) را یک کن: 0x00200000 = «PA5 را پایین بیاور». هر دو را با هم یک کنی، بنا به RM0383 «Set» برنده است. برای همین backend فقط یکی را می‌نویسد.

backend سوم: ESP32

برای ESP32 هیچ خط دیگری عوض نمی‌شود: نه led.c، نه main (جز یک خط انتخاب backend). فقط یک فایل جدید می‌نویسیم که قرارداد را با درایور GPIO فریم‌ورک ESP-IDF پر می‌کند (توابع gpio_set_direction، gpio_set_level و gpio_get_level؛ مستندات در docs.espressif.com). برای ESP32 شمارهٔ پایه همان شمارهٔ GPIO است:

#include "driver/gpio.h"
#include "hal_gpio.h"

#define ESP_MAX_GPIO 39

static hal_status_t esp_init_output(uint8_t pin)
{
    if (pin > ESP_MAX_GPIO) {
        return HAL_ERR_PARAM;
    }
    return (gpio_set_direction((gpio_num_t)pin, GPIO_MODE_OUTPUT) == ESP_OK)
               ? HAL_OK : HAL_ERR_PARAM;
}

static hal_status_t esp_write(uint8_t pin, hal_level_t level)
{
    if (pin > ESP_MAX_GPIO) {
        return HAL_ERR_PARAM;
    }
    return (gpio_set_level((gpio_num_t)pin, (uint32_t)level) == ESP_OK)
               ? HAL_OK : HAL_ERR_IO;
}

static hal_status_t esp_read(uint8_t pin, hal_level_t *level)
{
    if (pin > ESP_MAX_GPIO || level == NULL) {
        return HAL_ERR_PARAM;
    }
    *level = gpio_get_level((gpio_num_t)pin) ? HAL_HIGH : HAL_LOW;
    return HAL_OK;
}

const hal_gpio_ops_t hal_gpio_esp32_ops = {
    .init_output = esp_init_output,
    .write = esp_write,
    .read = esp_read,
};
  1. دو هدر. درایور GPIO فریم‌ورک و قرارداد خودمان. این تنها فایلی است که driver/gpio.h را می‌بیند.
  2. حد پایه‌ها. ESP32 کلاسیک GPIO0 تا GPIO39 دارد (بعضی فقط ورودی‌اند). شمارهٔ ورودی را پیش از تبدیل به gpio_num_t بررسی می‌کنیم؛ تا مقدار بی‌معنی به فریم‌ورک نرسد.
  3. خروجی‌کردن. gpio_set_direction یک esp_err_t برمی‌گرداند (ESP_OK یعنی موفق؛ درس ۵.۶). آن را به کد وضعیت HAL ترجمه می‌کنیم: پایهٔ فقط‌ورودی خطا می‌دهد و ما آن را «پارامتر اشتباه» می‌دانیم.
  4. نوشتن. gpio_set_level با عدد ۰ یا ۱. چون HAL_LOW و HAL_HIGH دقیقا ۰ و ۱ هستند، تبدیل ساده است.
  5. خواندن. gpio_get_level عدد صحیح برمی‌گرداند.
  6. جدول عملیات. همان شکل mock و STM32.

قرارداد را کامپایلر نگه می‌دارد

اگر یک backend تابعی با امضای متفاوت بگذارد (مثلا write که void برگرداند)، کامپایلر خطا می‌دهد؛ نه بعد از فلش، نه هنگام اجرا:

#include <stdint.h>

typedef struct {
    int (*write)(uint8_t pin, int level);
} gpio_ops_t;

static void my_write(uint8_t pin, int level)
{
    (void)pin;
    (void)level;
}

static const gpio_ops_t ops = { .write = my_write };

int main(void)
{
    return ops.write == 0;
}
  1. قرارداد. write باید int برگرداند.
  2. تابع اشتباه. نتیجه void است. فراموش‌کردن «برگرداندن کد خطا» رایج‌ترین اشتباه هنگام نوشتن backend است. اگر کامپایلر جلویش را نگیرد، درایور جواب بی‌معنی می‌گیرد.
  3. پر کردن جدول. این‌جا کامپایلر اعتراض می‌کند.
bad_sig.c:13:42: error: initialization of 'int (*)(uint8_t,  int)' {aka 'int (*)(unsigned char,  int)'} from incompatible pointer type 'void (*)(uint8_t,  int)' {aka 'void (*)(unsigned char,  int)'} [-Werror=incompatible-pointer-types]

پیام می‌گوید «مقداردهی اشاره‌گر int (*)(...) با void (*)(...) ناسازگار است». بدون -Werror=incompatible-pointer-types نسخه‌های قدیمی‌تر gcc فقط هشدار می‌دادند؛ به همین دلیل همیشه با -Wall -Wextra کامپایل کن و هشدارها را جدی بگیر.

جدول عملیات کجا می‌نشیند؟

یادت هست در درس ۳.۵ گفتیم متغیر سراسری const به Flash می‌رود و متغیر عادیِ مقدار‌دار در RAM جا می‌گیرد؟ جدول عملیات هم همین‌طور است. بررسی خروجی واقعی کامپایلر:

$ arm-none-eabi-objdump -t hal_gpio_stm32.o | grep ops
00000000 g     O .rodata	0000000c hal_gpio_stm32_ops

خط را بخوان: جدول در بخش .rodata (فقط‌خواندنی، در Flash) نشسته و ۱۲ بایت است: سه اشاره‌گر × ۴ بایت. اگر const را بردارید، به بخش .data می‌رود و هم در Flash هم در RAM یک کپی می‌گیرد؛ ۱۲ بایت RAM هدر می‌رود و بدتر، یک باگ می‌تواند اشاره‌گر تابع را عوض کند و برنامه را به جای اشتباه بپراند. هر جدول عملیات را const بگیر.

لایه‌بندی هزینه دارد: کد بیشتر، یک پرش غیرمستقیم برای هر فراخوانی (چند چرخهٔ CPU) و فایل‌های بیشتر که باید آن‌ها را نگه داشت. برای یک آزمایش ۲۰ خطی روی میز، «LED را با یک خط BSRR روشن کن» کافی است. لایه‌بندی وقتی می‌ارزد که (۱) قرار است روی دو تراشه اجرا شود، (۲) می‌خواهی روی PC تست کنی، یا (۳) کد چند ماه عمر دارد و چند نفر روی آن کار می‌کنند. از هر انتزاع بپرس: «کدام مشکل را حل می‌کند؟»

دو راه برای «انتخاب backend»

ما backend را با یک اشاره‌گر در زمان اجرا انتخاب کردیم (led_init(&ld2, &hal_gpio_stm32_ops, ...)). راه دیگری هم هست: انتخاب در زمان لینک. HAL فقط توابع ساده را اعلان می‌کند (مثلا hal_gpio_write(pin, level)) و هر backend آن را با همان اسم پیاده می‌کند. Makefile تصمیم می‌گیرد کدام فایل .c در برنامه لینک شود.

اشاره‌گر در زمان اجراانتخاب در زمان لینک
هزینهیک پرش غیرمستقیم + ۱۲ بایت جدولهیچ؛ فراخوانی مستقیم (و قابل inline)
هم‌زمان چند backendبله (مثلا GPIO داخلی و GPIO expander)خیر؛ هر برنامه یکی
تست با mockساده: پارامتر می‌دهیباید mock را جای backend اصلی لینک کنی
نمونهٔ واقعیلایهٔ VFS، درایورهای شبه‌vtable لینوکسبیشتر CMSIS و درایورهای تک‌تراشه

هیچ‌کدام «درست‌تر» نیست. اگر backend دوم هرگز در یک برنامه نیست، لینک‌شده ساده‌تر و ارزان‌تر است. اگر چند دستگاه مشابه با راه‌های متفاوت داری (چند سنسور روی I2C و SPI)، جدول اشاره‌گر بهتر است. در تمرین ۳ همین را عملی حس می‌کنی.

در دنیای واقعی: STM32 و ESP32 خودشان همین‌اند

  • STM32Cube: لایه‌ای که ST می‌دهد همین معماری است. HAL_GPIO_WritePin یک تابع HAL است؛ زیرش «LL» یا رجیستر مستقیم؛ بالایش درایور تو. «CMSIS» هم لایهٔ اسم‌گذاری رجیستر است (درس ۳.۶). برای جزئیات، مستندات رسمی روی st.com را ببین.
  • ESP-IDF: درایور gpio یک API یکسان برای همهٔ تراشه‌های ESP دارد. چیزی که در ESP32-S3 یا ESP32-C3 هم کار می‌کند، مثل gpio_set_level، نتیجهٔ همین لایه‌بندی است. راهنمای رسمی: docs.espressif.com. برای آشنایی با خود ESP32 از دورهٔ ESP32 Masterclass هم می‌توانی کمک بگیری.
  • پروژه‌های سازمانی: بیشتر شرکت‌ها روی این معماری استاندارد دارند: «پوشهٔ drivers، پوشهٔ hal، پوشهٔ bsp» و مجموعهٔ تست روی PC. درس ۶.۴ نشان می‌دهد چطور با mock ها تست واحد بنویسی و پروژهٔ پایانی (درس ۷.۱) از همین شکل استفاده می‌کند.

بازی کن: عدد ۴۵ همان HAL_PIN('C', 13) (دکمهٔ آبی) است. در مبنای ۱۶ می‌شود 0x2D: نیمهٔ بالا 2 یعنی پورت C و نیمهٔ پایین D = ۱۳ یعنی پین ۱۳. چون ۱۶ = ۲۴، ضرب در ۱۶ فقط یک هگزیت جابه‌جا می‌کند و / و % روی ۱۶ فقط «بالا» و «پایین» را جدا می‌کنند. همین حسابِ ساده است که backend STM32 استفاده می‌کند.

آزمون این درس

چرا led.c به‌جای صدا زدن مستقیم رجیستر، از راه led->gpio->write(...) پایه را می‌نویسد؟

  1. چون سریع‌تر است
  2. چون درایور نباید بداند زیرش کدام سخت‌افزار (STM32، ESP32 یا mock) است؛ همان کد در همه جا کار می‌کند
  3. چون RAM کمتری مصرف می‌کند
  4. چون C اجازهٔ دسترسی مستقیم به رجیستر را نمی‌دهد
وارونگی وابستگی: درایور فقط به «قرارداد» وابسته است و هر backend خودش را با آن وفق می‌دهد.

LED فعال-پایین روی PB0 است (active_low = true). بعد از led_on()، mock چه چیزی چاپ می‌کند؟

  1. [mock] PB0 <- HIGH
  2. هیچ چیز
  3. [mock] PB0 <- LOW
  4. [mock] PB0 <- ON
high = (on != active_low) برای on = true و active_low = true نادرست می‌شود، پس سطح LOW نوشته می‌شود.

کدام خط لایه‌بندی را می‌شکند؟

  1. داخل led.c: #include "hal_gpio_stm32.h"
  2. داخل main.c: #include "hal_gpio_mock.h"
  3. داخل hal_gpio_stm32.h: #include "hal_gpio.h"
  4. داخل led.h: #include "hal_gpio.h"
درایور نباید backend مشخصی را بشناسد. اگر led.c فایل hal_gpio_stm32.h را include کند، دیگر روی PC یا ESP32 ساخته نمی‌شود.

جدول const hal_gpio_ops_t hal_gpio_stm32_ops = {...} در حافظهٔ STM32 کجا قرار می‌گیرد؟

  1. در RAM، بخش .bss
  2. در RAM، بخش .data با کپی از Flash
  3. روی stack
  4. در Flash، بخش .rodata
سراسری‌های const در .rodata می‌مانند (اگر const نبود، به .data می‌رفت و ۱۲ بایت RAM می‌گرفت). objdump همین را نشان داد.

هنگام led_off سخت‌افزار خطای HAL_ERR_IO می‌دهد. درایور باید با فیلد on چه کند؟

  1. آن را false کند تا کاربر فکر کند LED خاموش است
  2. دست نزند و کد خطا را به بالا برگرداند؛ حالت با سخت‌افزار همخوان می‌ماند
  3. برنامه را متوقف کند (حلقهٔ بی‌پایان)
  4. خطا را نادیده بگیرد و on را عوض کند
حالت فقط بعد از موفقیت عوض می‌شود. لایهٔ بالا با دیدن کد خطا تصمیم می‌گیرد چه کند (دوباره تلاش، اعلان، توقف).

کدام کار با mock روی PC (بدون برد) امکان‌پذیر است؟

  1. سنجش روشنایی واقعی LED
  2. تأیید اینکه ساعت GPIOA واقعا روشن شده است
  3. آزمودن منطق درایور: قطبیت، ترتیب toggle و رفتار هنگام خطا
  4. پیدا کردن مقاومت اشتباه روی برد
mock منطق نرم‌افزار را آزمایش می‌کند، نه فیزیک. به همین دلیل بعد از تست روی PC هنوز به یک بار آزمایش روی برد نیاز داری، ولی بسیار کمتر و با اطمینان بیشتر.

تمرین‌ها

تمرین ۱: backend سوم؛ شمارنده

بدون دست‌زدن به «درایور»، یک backend تازه بساز که فقط تعداد دفعات نوشتن را می‌شمارد، و آن را کنار backend «لاگ» قرار بده. برای سادگی همه‌چیز در یک فایل است، ولی ساختار لایه‌ای است: blink_n نقش درایور را دارد.

  1. پیش‌بینی: blink_n(&count_ops, 5, 3) چند بار write را صدا می‌زند؟ (هر دور دو نوشتن.)
  2. حل: برنامه را بنویس یا کامل کن که ابتدا با backend لاگ ۲ دور بزند و سپس با backend شمارنده ۳ دور، و تعداد را چاپ کند.
  3. فکر کن: چرا blink_n هیچ تغییری نکرد؟ این خاصیت در تست خودکار چه کمکی می‌کند؟
راهنمایی

هر backend فقط یک تابع با امضای void (*)(int, int) است. برای شمارنده، یک متغیر static unsigned بساز و در تابعش یکی اضافه کن. پارامترهایی که استفاده نمی‌شوند را با (void)pin; ساکت کن تا -Wextra هشدار ندهد.

چه باید ببینی؟ 
$ ./count_backend

pin 5 <- 0
pin 5 <- 1
pin 5 <- 0
count backend saw 6 writes

جواب الف: ۶ بار (۳ دور × ۲).

جواب کامل با توضیح 
#include <stdio.h>

typedef struct {
    void (*write)(int pin, int level);
} gpio_ops_t;

static unsigned s_calls;

static void count_write(int pin, int level)
{
    (void)pin;
    (void)level;
    s_calls++;
}

static void log_write(int pin, int level)
{
    printf("pin %d <- %d\n", pin, level);
}

static const gpio_ops_t count_ops = { count_write };
static const gpio_ops_t log_ops = { log_write };

static void blink_n(const gpio_ops_t *gpio, int pin, int times)
{
    for (int i = 0; i < times; i++) {
        gpio->write(pin, 1);
        gpio->write(pin, 0);
    }
}

int main(void)
{
    blink_n(&log_ops, 5, 2);
    blink_n(&count_ops, 5, 3);
    printf("count backend saw %u writes\n", s_calls);
    return 0;
}
  1. قرارداد. فقط یک تابع write؛ ساده‌شدهٔ hal_gpio_ops_t.
  2. backend شمارنده. پایه و سطح را نادیده می‌گیرد و شمارنده را زیاد می‌کند. (void)pin; به کامپایلر می‌گوید «این پارامتر را عمدا استفاده نمی‌کنم»؛ بدون آن، -Wextra هشدار «unused parameter» می‌دهد.
  3. backend لاگ. فقط چاپ می‌کند.
  4. دو جدول ثابت. هر backend یک نمونه.
  5. «درایور». blink_n فقط از راه اشاره‌گر می‌نویسد؛ نمی‌داند کدام backend است.
  6. استفاده. همان تابع با دو backend.
$ ./count_backend
pin 5 <- 1
pin 5 <- 0
pin 5 <- 1
pin 5 <- 0
count backend saw 6 writes

بخش پ: چون blink_n ثابت ماند، هر تغییری در نتیجه فقط از backend می‌آید. در تست خودکار همین‌طور «مشاهده‌گر» می‌گذاری: تعداد نوشتن، ترتیب و مقدارها را می‌شمارد و اگر با انتظار نخواند، تست شکست می‌خورد.

تمرین ۲: باگ قطبیت را پیدا کن

برنامهٔ زیر یک LED فعال-پایین را روشن می‌کند، ولی سطح پایه اشتباه است. (s_level آرایهٔ ساختگیِ سطح پایه‌هاست.)

#include <stdbool.h>
#include <stdio.h>

static int s_level[16];                 /* سطح پایه‌های ساختگی */

static void gpio_write(int pin, int level)
{
    s_level[pin] = level;
}

typedef struct {
    int pin;
    bool active_low;
    bool on;
} led_t;

static void led_set(led_t *led, bool on)
{
    led->on = on;
    gpio_write(led->pin, on ? 1 : 0);
}

int main(void)
{
    led_t led = { .pin = 3, .active_low = true, .on = false };

    led_set(&led, true);
    printf("led on=%d, pin level=%d\n", led.on, s_level[led.pin]);
    return 0;
}

  1. ببین: برای LED فعال-پایین، سطح پایه بعد از «روشن» باید چند باشد؟ برنامه چه چیزی چاپ می‌کند؟
  2. بیاب: کدام خط باگ دارد و چرا؟ درستش کن.
  3. تست: یک تابع check بنویس که هر چهار ترکیب (فعال-بالا/پایین × روشن/خاموش) را وارسی کند و PASS/FAIL چاپ کند.
راهنمایی

جواب کامل با توضیح 
#include <stdbool.h>
#include <stdio.h>

static int s_level[16];

static void gpio_write(int pin, int level)
{
    s_level[pin] = level;
}

typedef struct {
    int pin;
    bool active_low;
    bool on;
} led_t;

static void led_set(led_t *led, bool on)
{
    led->on = on;
    gpio_write(led->pin, (on != led->active_low) ? 1 : 0);
}

static int check(bool active_low, bool on, int want_level)
{
    led_t led = { .pin = 3, .active_low = active_low, .on = false };

    led_set(&led, on);
    int ok = (s_level[3] == want_level);
    printf("active_low=%d on=%d -> level %d %s\n",
           active_low, on, s_level[3], ok ? "PASS" : "FAIL");
    return ok;
}

int main(void)
{
    int ok = 1;

    ok &= check(false, true, 1);
    ok &= check(false, false, 0);
    ok &= check(true, true, 0);
    ok &= check(true, false, 1);
    return ok ? 0 : 1;
}
  1. اصلاح. (on != led->active_low) ? 1 : 0 به‌جای on ? 1 : 0. اگر active_low صفر باشد، سطح همان on است؛ اگر یک باشد، برعکس می‌شود. باگ اصلی این بود که فیلد پیکربندی خوانده نمی‌شد. کامپایلر نمی‌تواند این را بگیرد؛ چون برنامه معنی‌دار و بی‌هشدار است. فقط تست آن را می‌گیرد.
  2. تابع تست. یک حالت را می‌سازد، اجرا می‌کند و سطح مورد انتظار را با سطح واقعی می‌سنجد.
  3. چهار حالت. هر ترکیب یک بار. ok &= نتیجه را جمع می‌کند و کد خروج main صفر (موفق) یا ۱ (شکست) است. کد خروج ۰/۱ همان چیزی است که سیستم‌های CI (درس ۶.۴) می‌فهمند.

تمرین ۳: حساب پورت و رجیستر (ارتباط با سخت‌افزار)

backend STM32 برای هر شمارهٔ پایه، پورت، آدرس پایه و بیت‌های MODER و BSRR را حساب می‌کند. اول با دست، بعد با برنامه.

  1. با دست: برای HAL_PIN('C', 13) (دکمهٔ آبی) شمارهٔ پایه، پورت، آدرس پایهٔ GPIOC، بیت‌های MODER و مقدار BSRR برای «set» و «reset» را بنویس. (پایهٔ پورت: 0x40020000 + 0x400 × پورت.)
  2. با برنامه: تابع describe(pin) بنویس و برای PA5، PB0، PC13، PE3 و PH1 چاپش کن. با جواب دستی‌ات مقایسه کن.
  3. چالش: در backend ما MAX_PORT برابر ۴ بود و PH1 (پورت ۷) خطای پارامتر می‌گیرد. اگر بخواهی GPIOH را هم پشتیبانی کنی، دو چیز باید عوض شود: کدام‌ها؟ (راهنمایی: بیت ساعت GPIOH در RCC_AHB1ENR؛ و پورت‌های F و G که روی F411 وجود ندارند.)
راهنمایی

پورت = پایه / 16؛ پین = پایه % 16. MODER هر پین ۲ بیت دارد: بیت‌های 2n+1 و 2n. BSRR: set = 1 << n، reset = 1 << (n+16).

جواب کامل با توضیح 
#include <stdint.h>
#include <stdio.h>

#define HAL_PIN(port, n) ((uint8_t)((((port) - 'A') * 16) + (n)))

static void describe(uint8_t pin)
{
    uint32_t port = pin / 16u;
    uint32_t n = pin % 16u;
    uint32_t base = 0x40020000u + 0x400u * port;

    printf("pin %3u = GPIO%c%-2u base=0x%08X MODER bits %2u:%-2u BSRR set=0x%08X reset=0x%08X\n",
           (unsigned)pin, (char)('A' + port), (unsigned)n, (unsigned)base,
           (unsigned)(2u * n + 1u), (unsigned)(2u * n),
           (unsigned)(1u << n), (unsigned)(1u << (n + 16u)));
}

int main(void)
{
    describe(HAL_PIN('A', 5));
    describe(HAL_PIN('B', 0));
    describe(HAL_PIN('C', 13));
    describe(HAL_PIN('E', 3));
    describe(HAL_PIN('H', 1));
    return 0;
}
  1. همان ماکرو. HAL_PIN عینا از hal_gpio.h.
  2. تقسیم پایه. پورت با /16، پین با %16؛ آدرس پایه با ضرب 0x400. هر پورت GPIO در F411 یک بلوک ۱KB (0x400) است و به‌ترتیب کنار هم‌اند؛ برای همین فرمول خطی جواب می‌دهد. GPIOH چون سومین بلوک پس از E نیست و در RM0383 روی 0x40021C00 است، همان فرمول با شمارهٔ ۷ برایش درست از آب درمی‌آید.
  3. چاپ. بیت‌های MODER: 2n+1 تا 2n؛ BSRR set و reset با شیفت.
  4. پنج پایه. نمونه‌هایی از پورت‌های مختلف.

جواب ب و پ: PC13: پایه ۴۵، پورت ۲، آدرس 0x40020800، بیت‌های MODER ۲۷:۲۶، set = 0x2000 و reset = 0x20000000. برای پشتیبانی از GPIOH: (۱) شرط پورت را به «A تا E یا H» تغییر بده، مثلا port <= 4u || port == 7u؛ (۲) بیت ساعت GPIOH در RCC_AHB1ENR بیت ۷ است، که با 1u << port برای پورت ۷ خودش درست می‌شود (اگر بخواهی، در مستندات RM0383 بررسی کن). تنها چیز اضافه، رد کردن پورت‌های ۵ و ۶ (F و G) است که روی F411 وجود ندارند.

حرف مربی

معمولا در این درس دو جا گیر می‌کنند. اول: «چرا این‌همه فایل برای یک LED؟» حق داری؛ برای یک LED واقعا زیاد است. مقصود آموختن الگو است؛ وقتی به سنسور، UART و ۱۰ ماژول برسی، فایل‌ها ارزان‌تر از باگ‌ها هستند. دوم: وسوسهٔ «فقط یک بار» include کردن هدر تراشه در درایور. یک #include که رو به پایین است، فردا در ESP32 ساخته نمی‌شود. اگر یک خط این درس را با خودت ببری: «هر #include را بپرس: این لایه چرا آن یکی را می‌شناسد؟» و یک عادت: هر کدی که با سخت‌افزار حرف می‌زند، اول یک نسخهٔ mock داشته باشد؛ تا آزمایشش روی PC ممکن شود.

خلاصهٔ یک‌دقیقه‌ای

  • لایه‌ها: برنامه ← درایور ← HAL (قرارداد) ← backend ← سخت‌افزار؛ وابستگی فقط رو به پایین. BSP می‌گوید هر LED به کدام پین وصل است.
  • قرارداد = struct از اشاره‌گر تابع (hal_gpio_ops_t) که لایهٔ بالا مالک آن است؛ backend ها آن را پر می‌کنند (وارونگی وابستگی).
  • درایور با config و handle کار می‌کند: بدون متغیر سراسری، با ورودی‌های اعتبارسنجی‌شده، و کد وضعیت خودش که خطای لایهٔ پایین را ترجمه می‌کند.
  • حالت فقط بعد از موفقیت عوض می‌شود تا با سخت‌افزار همخوان بماند.
  • backend تقلبی (mock) اجازه می‌دهد کل منطق را روی PC و بدون برد آزمایش کنی؛ backend STM32 همان قرارداد را با BSRR و MODER پر می‌کند و backend ESP32 با gpio_set_level.
  • جدول عملیات را const بگیر: در Flash (.rodata) می‌ماند.
  • لایه‌بندی هزینه دارد. برای کد کوتاه‌عمر و تک‌برد لازم نیست؛ برای کد چندبرده و قابل‌تست، بله.

درس بعد: فصل ۶ با دیباگ شروع می‌شود؛ ابزارهایی که کمکت می‌کنند وقتی همین کدهای لایه‌ای رفتار عجیب نشان دادند، ریشه را پیدا کنی.
