هر برنامه‌نویسی باگ می‌نویسد؛ فرق حرفه‌ای‌ها با مبتدی‌ها در این است که حرفه‌ای‌ها حدس نمی‌زنند، اندازه می‌گیرند. روی PC می‌توانی هر لحظه برنامه را متوقف کنی و درونش را ببینی. روی میکروکنترلر همین کار ممکن است، ولی باید راهش را بدانی: چطور با یک سیم SWD داخل تراشه را ببینی، وقتی برنامه به HardFault می‌افتد چه چیزی را بخوانی، و چطور خودت به تراشه «حس» بدهی. این درس جعبه‌ابزار کارآگاه توست.

🎯 بعد از این درس می‌توانی

  • باگ را با روش «تکرار، کوچک‌کردن، نصف‌کردن» پیدا کنی
  • لاگ با سطح‌بندی و assert بنویسی و بدانی کجا خطرناک است
  • با GDB روی PC نقطهٔ توقف، ناظر و پشتهٔ فراخوانی را ببینی
  • مسیر ST-LINK، OpenOCD و arm-none-eabi-gdb را توضیح بدهی
  • HardFault را بخوانی: PC ذخیره‌شده، ثبات CFSR و خط منبع
  • با یک پایهٔ دیباگ و تحلیلگر منطقی زمان اجرا را اندازه بگیری

🧰 پیش‌نیاز و وسایل

  • درس ۳.۶ (ثبات و volatile) و ۵.۳ (وقفه)
  • درس ۶.۲ (رفتار تعریف‌نشده) مکمل این درس است
  • PC با gcc و gdb؛ بخش‌های سخت‌افزاری برد Nucleo-F411RE می‌خواهند ولی اجرای کدها بدون برد هم ممکن است
  • تحلیلگر منطقی ارزان (اختیاری؛ در ۱.۳ معرفی شد)

ایده اصلی: کارآگاه، نه فالگیر

فرض کن ماشینت روشن نمی‌شود. فالگیر می‌گوید «حتما باتری است» و باتری نو می‌خرد. کارآگاه اول امتحان می‌کند: چراغ‌ها روشن می‌شوند؟ استارت صدا می‌دهد؟ بنزین هست؟ با هر امتحان یک احتمال حذف می‌شود تا علت بماند. باگ‌یابی هم همین است: هر تغییر بی‌دلیل در کد، «فال» است؛ هر اندازه‌گیری، «مدرک».

مثال از زندگی روزمره

لوله‌کش را ببین: نشتی در دیوار است، ولی او دیوار را نمی‌شکند. شیر اصلی را می‌بندد، نیمی از لوله‌ها را جدا می‌کند و فشار می‌سنجد؛ اگر نشتی ماند، نیمهٔ دیگر را بررسی می‌کند. با چهار پنج اندازه‌گیری به یک متر لوله می‌رسد. کد هم همین است. هزاران خط، ولی با «نصف کردن» در حدود ده قدم به خط مقصر می‌رسی.

روش: پنج قدم و نصف‌کردن

  1. تکرار کن. باگی که هر بار نیست، قابل‌ رفع نیست. اول یک راه مطمئن برای ساختنش پیدا کن (ورودی ثابت، تعداد دور مشخص).
  2. کوچکش کن. هرچه را که به باگ ربطی ندارد بردار: ماژول‌ها، سنسورها، وقفه‌های غیرضروری. کد کمینه‌ای بساز که هنوز خراب باشد. اغلب خودِ همین کار علت را نشان می‌دهد.
  3. حدس بزن و بنویس. «فکر می‌کنم sum بعد از دور سوم بزرگ می‌شود.» حدس باید قابل‌آزمایش باشد.
  4. اندازه بگیر. با لاگ، assert، دیباگر یا پایهٔ دیباگ حدس را بیازما. اگر غلط بود، حدس بعدی.
  5. رفع کن و تست بنویس. باگ را که رفع کردی، یک آزمون بگذار که اگر برگشت، فوری بفهمی (درس ۶.۴).

لاگ (printf) با سطح‌بندی

ساده‌ترین بازرسی: چاپ یک مقدار. اما اگر همه‌جا printf بگذاری، بعد از رفع باگ باید همه را پاک کنی و شش ماه بعد برای باگ بعدی دوباره بنویسی. راه حرفه‌ای‌ها: لاگ با سطح. هر پیام یک سطح دارد (خطا، اطلاع، ردیابی) و با یک پرچم کامپایل، پیام‌های غیرضروری حذف می‌شوند. ESP-IDF هم همین را با ESP_LOGE، ESP_LOGI و ESP_LOGD می‌دهد؛ اینجا نسخهٔ خودمان را با ماکرو (درس ۴.۱) می‌سازیم:

#include <stdio.h>

#define LOG_ERROR 1
#define LOG_INFO  2
#define LOG_DEBUG 3

#ifndef LOG_LEVEL
#define LOG_LEVEL LOG_INFO      // سطح پیش‌فرض
#endif

#define LOG_AT(lvl, tag, ...)                                   \
    do {                                                        \
        if ((lvl) <= LOG_LEVEL) {                               \
            printf("[%s] %s:%d: ", (tag), __FILE__, __LINE__);  \
            printf(__VA_ARGS__);                                \
            printf("\n");                                       \
        }                                                       \
    } while (0)

#define LOGE(...) LOG_AT(LOG_ERROR, "E", __VA_ARGS__)
#define LOGI(...) LOG_AT(LOG_INFO,  "I", __VA_ARGS__)
#define LOGD(...) LOG_AT(LOG_DEBUG, "D", __VA_ARGS__)

int main(void)
{
    int temp = 42;
    LOGE("sensor timeout after %d ms", 500);
    LOGI("temp = %d", temp);
    LOGD("raw adc = %d", 1234);
    return 0;
}
  1. سه سطح. عدد کمتر = مهم‌تر: خطا ۱، اطلاع ۲، ردیابی ۳.
  2. سطح پیش‌فرض. اگر موقع کامپایل -DLOG_LEVEL=3 ندهی، سطح «اطلاع» است. #ifndef یعنی «اگر قبلا تعریف نشده». با یک پرچم کامپایل، همهٔ لاگ‌های ردیابی را بدون دست‌زدن به کد روشن یا خاموش می‌کنی.
  3. ماکروی اصلی. فقط اگر سطح پیام از سطح مجاز کمتر یا برابر باشد چاپ می‌کند. __FILE__ و __LINE__ نام فایل و شمارهٔ خط همین جا را می‌دهند و __VA_ARGS__ بقیهٔ آرگومان‌ها را عبور می‌دهد. فایل و خط را خودکار می‌گیری و لازم نیست دستی بنویسی؛ اشتباه هم نمی‌شود. do { ... } while (0) ماکرو را مثل یک دستور رفتار می‌دهد (درس ۴.۱).
  4. میان‌بُرها. سه ماکروی کوتاه برای هر سطح.
  5. استفاده. سه پیام با سه سطح. با سطح پیش‌فرض فقط دو پیام اول چاپ می‌شود.
$ gcc -std=c11 -Wall -Wextra -o log log.c
$ ./log
[E] log.c:27: sensor timeout after 500 ms
[I] log.c:28: temp = 42

printf روی میکروکنترلر گران است
  • زمان: ارسال یک خط ۳۰ کاراکتری با UART در ۱۱۵۲۰۰ باود حدود ۲٫۶ میلی‌ثانیه طول می‌کشد (۱۰ بیت برای هر کاراکتر). اگر در ISR یا حلقهٔ سریع باشد، زمان‌بندی را عوض می‌کنی و باگ زمانی گم می‌شود یا ظاهر می‌شود («اثر هایزنبرگ» دیباگ).
  • حافظه: printf با اعشار در کتابخانهٔ newlib ده‌ها کیلوبایت Flash می‌گیرد (درس ۲.۸).
  • داخل ISR هرگز: printf ممکن است قفل بگیرد یا طولانی باشد (درس ۵.۳). به‌جایش یک پرچم بگذار و در main چاپ کن.
  • در ESP-IDF لاگ از طریق تابع‌های صف‌دار کار می‌کند و این مشکلات کمتر است، ولی هنوز هزینه دارد.

assert: قرارداد را در خود کد بنویس

لاگ برای «ببینم چه شد» است؛ assert برای «این نباید هرگز اتفاق بیفتد» است. هر جا فرضی داری (ایندکس معتبر است، اشاره‌گر NULL نیست)، آن را با assert بنویس. اگر فرض شکست، برنامه همان لحظه و با نام فایل و خط می‌ایستد، نه ده تابع بعد که علامتش گم شده.

#include <assert.h>
#include <stdio.h>

#define N 4
static int table[N] = {1, 2, 3, 4};

static int get(int idx)
{
    assert(idx >= 0 && idx < N);    // قرارداد: ایندکس باید معتبر باشد
    return table[idx];
}

int main(void)
{
    printf("get(2) = %d\n", get(2));
    fflush(stdout);
    printf("get(7) = %d\n", get(7));
    return 0;
}
  1. هدر assert. ماکروی assert از اینجا می‌آید.
  2. تابع get. قبل از خواندن جدول، درست‌بودن ایندکس را «ادعا» می‌کند. اگر شرط نادرست باشد، assert پیام خطا با فایل، خط و متن شرط چاپ می‌کند و برنامه را با abort() می‌کشد.
  3. فراخوانی درست. ایندکس ۲ معتبر است. fflush خروجی را فوری می‌فرستد. چون بعدش برنامه با abort کشته می‌شود و بافر stdout خالی نمی‌شود؛ بدون fflush این خط را نمی‌دیدی.
  4. فراخوانی غلط. ایندکس ۷ نامعتبر است و assert جلوی خواندن خارج از آرایه (UB) را می‌گیرد.
$ gcc -std=c11 -Wall -Wextra -o assert assert.c
$ ./assert

$ ./assert     # پیام assert روی stderr می‌آید (نمونه؛ نام برنامه فرق می‌کند)

Aborted (core dumped)
$ echo $?

کد خروج ۱۳۴ یعنی ۱۲۸ + ۶ (سیگنال SIGABRT). حالا دو نکتهٔ بسیار مهم:

دو تله
  • با -DNDEBUG همهٔ assert ها حذف می‌شوند. پس داخل assert هرگز کاری با اثر جانبی نگذار: assert(i++ < 5) در نسخهٔ نهایی i را زیاد نمی‌کند و رفتار برنامه عوض می‌شود.
  • assert برای ورودی کاربر نیست. ورودی نامعتبر باید با if و کد خطا مدیریت شود. assert فقط برای «اشتباه برنامه‌نویس» است (نباید هرگز رخ بدهد).

روی میکروکنترلر abort() استاندارد به کار نمی‌آید: کسی پیام را نمی‌بیند. پس assert خودت را می‌نویسی که فایل و خط را در یک متغیر ذخیره کند، LED خطا را روشن کند و بایستد یا ریست کند. نسخهٔ PC آن را ببین (همان الگو با exit):

#include <stdio.h>
#include <stdlib.h>

/* روی MCU: اینجا LED خطا را روشن می‌کنند، فایل و خط را ذخیره می‌کنند و می‌ایستند */
static void assert_failed(const char *file, int line)
{
    printf("ASSERT FAILED at %s:%d\n", file, line);
    exit(3);
}

#define ASSERT(cond) \
    do { if (!(cond)) assert_failed(__FILE__, __LINE__); } while (0)

static void set_duty(int percent)
{
    ASSERT(percent >= 0 && percent <= 100);
    printf("duty = %d%%\n", percent);
}

int main(void)
{
    set_duty(40);
    set_duty(140);      // اشتباه در جای دیگر برنامه
    return 0;
}
  1. تابع شکست. در نسخهٔ MCU به‌جای printf و exit: ذخیرهٔ file و line در متغیر volatile، روشن‌کردن LED و for (;;). در این حالت می‌توانی دیباگر را وصل کنی و همان متغیرها را بخوانی؛ اینجا نقطهٔ توقف طبیعی توست.
  2. ماکروی ASSERT. نام فایل و خط را خودکار می‌فرستد.
  3. تابع با قرارداد. درصد باید بین ۰ و ۱۰۰ باشد. شکست یعنی فراخواننده اشتباه کرده.
  4. استفاده. فراخوانی اول درست و دوم غلط است.
$ ./my_assert

دیباگر GDB روی PC

لاگ یعنی «چند سؤال را از قبل بپرس». دیباگر یعنی «برنامه را نگه دار، هر سؤالی خواستی بپرس». GDB دیباگر استاندارد خانوادهٔ GNU است و همین ابزار (با نام arm-none-eabi-gdb) روی STM32 هم کار می‌کند؛ پس تمرین امروزت روی PC مستقیم به MCU منتقل می‌شود.

برنامهٔ زیر باید میانگین پنج خوانش سنسور را بدهد. یکی از خوانش‌ها پارازیت (۹۹۹۹) است. میانگین «معقول» باید حدود ۲۱۱ باشد. ببین چه چاپ می‌کند:

#include <stdio.h>
#include <stdint.h>

#define N 5

static int32_t readings[N] = {210, 215, 9999, 212, 208};   // 9999 = پارازیت سنسور

static int32_t average(const int32_t *v, int n)
{
    int32_t sum = 0;
    for (int i = 0; i < n; i++)
        sum += v[i];
    return sum / n;
}

int main(void)
{
    int32_t avg = average(readings, N);
    printf("average = %d\n", (int)avg);
    return 0;
}
  1. داده. پنج خوانش؛ سومی غیرعادی است.
  2. تابع average. اشاره‌گر به داده و تعداد را می‌گیرد.
  3. جمع‌کننده. از صفر شروع می‌شود.
  4. حلقه. همهٔ عنصرها را جمع می‌کند، حتی پارازیت را.
  5. میانگین. تقسیم صحیح بر تعداد.
  6. main. میانگین را می‌گیرد و چاپ می‌کند.
$ gcc -std=c11 -Wall -Wextra -o avg_dbg avg_dbg.c
$ ./avg_dbg
average = 2168

۲۱۶۸ به‌جای ۲۱۱! کدام خوانش این‌قدر خراب کرد؟ کد را دوباره با -g بساز (اطلاعات دیباگ: نام متغیرها و خط‌ها را در فایل می‌گذارد) و با -O0 (بدون بهینه‌سازی؛ با بهینه‌سازی بسیاری از متغیرها <optimized out> می‌شوند):

$ gcc -std=c11 -Wall -Wextra -g -O0 -o avg_dbg avg_dbg.c
$ gdb ./avg_dbg

نکته: -Og و -g

همیشه با -g بساز. برای دیباگ -O0 یا -Og (بهینه‌سازی سبک، مخصوص دیباگ) بهتر از -O2 است چون کد ترتیب‌شده و متغیرها سر جایشان می‌مانند. ولی یادت باشد که رفتار برنامه با -O2 ممکن است فرق کند (درس ۶.۲): بعد از رفع باگ در حالت -O0، برنامه را با تنظیمات نهایی هم بیازما.

Sanitizer: کامپایلر خودش باگ‌یاب می‌شود

گاهی باگ آن‌قدر پنهان است که نمی‌دانی کجا را نگاه کنی. sanitizer ها (با -fsanitize=address,undefined) کنار هر دسترسی به حافظه یک بازرسی پنهان می‌گذارند و هنگام اجرا فوری گزارش می‌دهند. در درس ۶.۲ بیشتر می‌بینی؛ اینجا یک باگ کلاسیک: strcpy در بافر کوچک.

#include <stdio.h>
#include <string.h>

int main(void)
{
    char name[8];
    strcpy(name, "temperature");     // 11 حرف + '\0' در 8 بایت جا نمی‌شود
    printf("%s\n", name);
    return 0;
}
  1. بافر ۸ بایتی. جای ۷ حرف و پایان رشته.
  2. کپی طولانی. ۱۲ بایت (۱۱ حرف و '\0') روی ۸ بایت نوشته می‌شود؛ ۴ بایت روی چیزی بعد از بافر می‌افتد. بایت‌های اضافی روی داده‌های همسایه (و حتی آدرس برگشت) می‌نویسند. اسمش «سرریز بافر» است (درس ۲.۸).
  3. چاپ. اگر برنامه تا اینجا برسد.

gcc اینجا هشدار هم می‌دهد: writing 12 bytes into a region of size 8 overflows the destination. اگر هشدار را نبینی و برنامه را بسازی، در Ubuntu (که محافظ پشته روشن است) اجرا با یک «canary» (نگهبان) گیر می‌افتد:

$ gcc -std=c11 -Wall -Wextra -O0 -o name_bug name_bug.c
$ ./name_bug
*** stack smashing detected ***: terminated
Aborted (core dumped)

و با sanitizer دقیقا می‌گوید کجا و چند بایت (چند خط اول، کوتاه‌شده):

$ gcc -std=c11 -g -fsanitize=address -o name_bug_s name_bug.c
$ ./name_bug_s
==5441==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x7f4757d00028 ...
WRITE of size 12 at 0x7f4757d00028 thread T0
    #0 0x7f475a2fb302 in memcpy ...
    #1 0x5571b121a2ca in main name_bug.c:7
    ...
    [32, 40) 'name' (line 6) <== Memory access at offset 40 overflows this variable
SUMMARY: AddressSanitizer: stack-buffer-overflow ... in memcpy

«WRITE of size 12» و «'name' ... overflows this variable»: بافر name بود و ۱۲ بایت نوشته شد. روی MCU sanitizer معمولی در دسترس نیست (حافظه و کتابخانه‌اش سنگین است)، پس منطق را روی PC تست کن (درس ۶.۴). ولی خود ایدهٔ canary روی MCU هم کاربرد دارد؛ در بخش پشته می‌بینی.

دیباگ سخت‌افزاری: SWD و OpenOCD

روی PC، GDB خود برنامه را اجرا می‌کند. روی میکروکنترلر برنامه روی تراشه است و GDB روی رایانه؛ باید پلی بینشان باشد. این پل چند تکه دارد:

SWD (Serial Wire Debug) پروتکل دو‌سیمهٔ دیباگ ARM است. بخش دیباگ داخل هسته (DAP) بدون دخالت CPU به حافظه و ثبات‌ها دسترسی دارد؛ پس می‌شود هسته را نگه داشت، RAM را خواند و Flash را برنامه‌ریزی کرد. پروتکل قدیمی‌تر و پرسیم‌تر JTAG همین کار را با چهار یا پنج سیم می‌کند و در بسیاری از تراشه‌ها (از جمله ESP32 با پروب مناسب) موجود است. ST-LINK و OpenOCD را در درس ۵.۲ دیدی؛ اینجا روند کامل:

# ترمینال ۱: OpenOCD را روشن بگذار
openocd -f interface/stlink.cfg -f target/stm32f4x.cfg

# ترمینال ۲: GDB را روی فایل ELF (با -g ساخته‌شده) باز کن
arm-none-eabi-gdb build/firmware.elf
  1. OpenOCD. دو فایل پیکربندی می‌گیرد: یکی برای پروب (stlink.cfg)، یکی برای تراشه (stm32f4x.cfg). بعد به SWD وصل می‌شود و روی پورت ۳۳۳۳ منتظر GDB می‌ماند. هر پروب و هر تراشه فایل خودش را دارد؛ برای تراشهٔ دیگر فقط این دو فایل عوض می‌شود.
  2. GDB مخصوص ARM. firmware.elf نقشهٔ بین آدرس‌ها و خط‌های کد را دارد؛ بدون آن فقط آدرس می‌بینی.
target extended-remote localhost:3333
monitor reset halt
load
break main
continue
  1. وصل شدن. به OpenOCD روی پورت ۳۳۳۳ وصل می‌شود.
  2. ریست و توقف. monitor یعنی «فرمان را مستقیم به OpenOCD بده». reset halt تراشه را ریست می‌کند و روی اولین دستور نگه می‌دارد.
  3. برنامه‌ریزی. load کد ELF را در Flash می‌نویسد. همان کاری که «Flash» در IDE می‌کند؛ ولی حالا فرمانش دست توست.
  4. اجرا تا main. نقطهٔ توقف روی main می‌گذارد و می‌گذارد برنامه تا آن‌جا برود.
$ openocd -f interface/stlink.cfg -f target/stm32f4x.cfg
Open On-Chip Debugger ...
Info : Listening on port 3333 for gdb connections

خروجی بالا فقط سرنخ است؛ متن دقیق روی هر نسخه و برد فرق می‌کند (ما اینجا برد واقعی نداریم و بخش‌های سخت‌افزاری نمونه هستند). ولی همین حالا می‌توانی همهٔ فرمان‌های جدول GDB را روی تراشه بزنی: break، watch، x/8xw 0x40020000 (خواندن ثبات‌های GPIOA!)، print/x روی هر متغیر.

با بهینه‌سازی و وقفه مراقب باش

وقتی هسته را با halt نگه می‌داری، پریفرال‌ها هنوز کار می‌کنند (تایمرها می‌شمارند، UART داده می‌گیرد؛ در STM32 با تنظیم DBGMCU می‌توان تایمرها را هم متوقف کرد). پس بعد از ادامه، ممکن است ISR ها یک‌جا پشت هم اجرا شوند. نقطهٔ توقف در ISR های زمان‌حساس کد را نامعتبر می‌کند؛ برای آن‌ها از پایهٔ دیباگ (بخش پایه و تحلیلگر منطقی) استفاده کن.

گاهی دیباگر کافی نیست و می‌خواهی برنامه در حال اجرا «حرف بزند». چند راه هست؛ هرکدام هزینه و مزیتی دارد:

راهسخت‌افزار لازمسرعت و هزینهنکته

پایهٔ دیباگ و تحلیلگر منطقی

سریع‌ترین و کم‌مزاحمت‌ترین «چاپ»، روشن و خاموش‌کردن یک پایه است. یک GPIO (مثلا PA6) را اول تابع بالا ببر و آخرش پایین بیاور. یک تحلیلگر منطقی ارزان (۱۰ تا ۲۰ دلار؛ معرفی‌اش در درس ۱.۳) یا اسیلوسکوپ، عرض پالس را دقیق نشان می‌دهد. دو دستور BSRR (درس ۳.۶) حدود چند چرخهٔ ساعت طول می‌کشد، پس مزاحمت ناچیز است.

#include <stdint.h>

#define RCC_AHB1ENR (*(volatile uint32_t *)0x40023830u)
#define GPIOA_MODER (*(volatile uint32_t *)0x40020000u)
#define GPIOA_BSRR  (*(volatile uint32_t *)0x40020018u)

#define DBG_HIGH() (GPIOA_BSRR = (1u << 6))         // PA6 = 1
#define DBG_LOW()  (GPIOA_BSRR = (1u << (6 + 16)))  // PA6 = 0

extern void process_sample(void);   // تابعی که می‌خواهیم زمانش را بسنجیم

void dbg_pin_init(void)
{
    RCC_AHB1ENR |= 1u << 0;                             // ساعت GPIOA
    GPIOA_MODER = (GPIOA_MODER & ~(3u << 12)) | (1u << 12); // PA6 خروجی
}

void measured_step(void)
{
    DBG_HIGH();
    process_sample();
    DBG_LOW();
}
  1. آدرس ثبات‌ها. RCC_AHB1ENR (آفست 0x30 از پایهٔ RCC) و GPIOA_MODER و GPIOA_BSRR مطابق RM0383.
  2. ماکروها. بیت ۶ از BSRR پایهٔ PA6 را یک می‌کند و بیت ۲۲ (۶ + ۱۶) آن را صفر. BSRR فقط با نوشتن ۱ اثر دارد، پس بدون خواندن-تغییر-نوشتن و بدون خطر قطع‌شدن به‌وسیلهٔ ISR کار می‌کند (درس ۳.۶).
  3. تابع هدف. extern: در فایل دیگری تعریف شده.
  4. راه‌اندازی پایه. ساعت GPIOA را روشن می‌کند و دو بیت ۱۳:۱۲ از MODER را ۰۱ (خروجی) می‌گذارد. پایه‌ها ۲ بیت دارند: PA6 بیت‌های ۱۳ و ۱۲. همان الگوی ماسک درس ۳.۱: اول پاک، بعد نوشتن.
  5. بازرسی. پایه قبل از تابع بالا می‌رود و بعد از آن پایین. مدت بالا بودن = زمان اجرا.

ببین چقدر کم‌هزینه بود و بدون هیچ printf: عرض پالس = زمان اجرا؛ فاصله‌ها = بیکاری؛ تغییر عرض بین دورها = تغییر زمان اجرا (مثلا وقتی ISR وسط بپرد). روی ESP32 همین کار را با gpio_set_level می‌کنی؛ مفهوم یکی است.

HardFault: وقتی پردازنده جیغ می‌زند

روی PC، اشتباه در حافظه به خطای segmentation fault می‌رسد. روی Cortex-M، کار خطاست و این خطاها با یک وقفهٔ ویژه اعلام می‌شوند: HardFault. اگر برنامه‌ات «خودش ریست می‌شود» یا در یک حلقهٔ بی‌نهایت گیر می‌کند، معمولا اینجاست. تلهٔ واقعی این است که HardFault_Handler پیش‌فرض (در فایل startup، درس ۵.۱) یک حلقهٔ while(1) است؛ هیچ سرنخی نمی‌دهد. کار ما این است که handler را طوری بنویسیم که سرنخ بدهد.

علت رایجمثال در Cثبات وضعیت
خواندن/نوشتن آدرس نامعتبراشاره‌گر خراب، *(uint32_t*)0xA0000000BusFault (PRECISERR)
پرش به آدرس نامعتبر یا بیت۰ = ۰اشاره‌گر تابع NULL یا خراب (درس ۴.۳)UsageFault (INVSTATE)
تقسیم بر صفر (اگر فعال شده باشد)a / b با b == 0UsageFault (DIVBYZERO)
دستور نامعتبرکد Flash خراب یا پرش وسط دادهUsageFault (UNDEFINSTR)
دسترسی ناهم‌تراز به چندکلمه‌ایcast اشاره‌گر بایتی به uint32_t* (درس ۶.۲)UsageFault (UNALIGNED)
سرریز پشتهبازگشتی عمیق، آرایهٔ محلی بزرگ (درس ۳.۵)معمولا BusFault یا MemManage
استفاده از FPU بدون روشن‌کردنشfloat در Cortex-M4F بدون فعال‌سازیUsageFault (NOCP)

وقتی خطا می‌آید، CPU برای اینکه بتواند بعدا برگردد، هشت ثبات را روی پشته می‌ریزد. ترتیبشان ثابت است و مهم‌ترین‌شان ثبات PC است: آدرس دستوری که خطا داد.

اکنون حاضری handler بنویسی. چالش این است که handler باید بداند قاب روی کدام پشته است: پشتهٔ اصلی (MSP) یا پشتهٔ پردازه (PSP، اگر RTOS داری). بیت ۲ ثبات LR (که در این لحظه مقدار ویژه EXC_RETURN دارد) جواب را می‌دهد:

#include <stdint.h>

/* ثبات‌های SCB: وضعیت خطاها */
#define SCB_CFSR (*(volatile uint32_t *)0xE000ED28u)
#define SCB_BFAR (*(volatile uint32_t *)0xE000ED38u)

/* volatile تا دیباگر (و کامپایلر) آن‌ها را حذف نکند */
volatile uint32_t fault_pc;
volatile uint32_t fault_lr;
volatile uint32_t fault_cfsr;
volatile uint32_t fault_bfar;

/* frame: هشت کلمه‌ای که CPU هنگام خطا روی پشته ریخته: R0 R1 R2 R3 R12 LR PC xPSR */
void hardfault_c(const uint32_t *frame)
{
    fault_lr   = frame[5];
    fault_pc   = frame[6];
    fault_cfsr = SCB_CFSR;
    fault_bfar = SCB_BFAR;
    for (;;) {
        /* اینجا می‌ایستیم تا دیباگر وصل شود */
    }
}

/* naked: بدون prologue، تا SP دست‌نخورده بماند */
__attribute__((naked)) void HardFault_Handler(void)
{
    __asm volatile (
        "tst lr, #4      \n"
        "ite eq          \n"
        "mrseq r0, msp   \n"
        "mrsne r0, psp   \n"
        "b hardfault_c   \n"
    );
}

/* برای آزمایش: خواندن از آدرسی که هیچ‌چیز آنجا نیست */
uint32_t read_missing(void)
{
    return *(volatile uint32_t *)0xA0000000u;
}

int main(void)
{
    return (int)read_missing();
}
  1. ثبات‌های SCB. CFSR (آدرس 0xE000ED28) علت خطا را می‌گوید و BFAR (0xE000ED38) آدرس بدی را که باس خطا داد. این‌ها ثبات‌های خود هستهٔ Cortex-M هستند (در منوال ARM)، نه ثبات ST؛ پس روی هر Cortex-M4 یکسان‌اند.
  2. متغیرهای خروجی. خودِ handler چیزی چاپ نمی‌کند؛ مقدارها را در RAM می‌گذارد تا با دیباگر بخوانی. بدون volatile کامپایلر می‌بیند هیچ‌کس این متغیرها را نمی‌خواند و نوشتنشان را حذف می‌کند (درس ۳.۶).
  3. تابع C. اشاره‌گر به قاب را می‌گیرد.
  4. LR و PC ذخیره‌شده. کلمهٔ ششم و هفتم قاب. PC ذخیره‌شده آدرس دستور خطادار است. با addr2line به خط منبع تبدیلش می‌کنیم.
  5. وضعیت خطا. CFSR و BFAR را کپی می‌کند.
  6. توقف. حلقهٔ بی‌نهایت تا دیباگر وصل شود و متغیرها را بخواند. در محصول واقعی می‌توانی به‌جایش اطلاعات را در حافظهٔ غیرفرار ذخیره کنی و ریست کنی (بعد از ثبت خطا).
  7. handler برهنه. naked یعنی کامپایلر هیچ کد مقدمه (ذخیرهٔ ثبات‌ها) نمی‌گذارد. اگر کامپایلر خودش چیزی در پشته می‌ریخت، SP جابه‌جا می‌شد و دیگر به ابتدای قاب اشاره نمی‌کرد.
  8. کدام پشته؟ tst lr, #4 بیت ۲ از EXC_RETURN را می‌سنجد.
  9. انتخاب SP. اگر بیت ۰ است، قاب روی MSP است؛ اگر ۱ است، روی PSP. نتیجه در r0 می‌رود که اولین آرگومان تابع C است.
  10. پرش به تابع C. با b (نه bl) تا LR خراب نشود.
  11. تابع آزمایشی. از آدرس 0xA0000000 می‌خواند که در STM32F411 هیچ حافظه‌ای آنجا نیست: BusFault دقیق و بعد HardFault.
  12. main. فقط تابع آزمایشی را صدا می‌زند.

این فایل با arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -Wall -Wextra -ffreestanding -c بدون هشدار کامپایل می‌شود. بعد از وصل‌شدن دیباگر و رسیدن به حلقهٔ بی‌نهایت، متغیرها را می‌خوانی. این یک نمونهٔ نمایشی است؛ مقدارها را از روی مستندات ARM برای این آزمایش محاسبه کرده‌ام و روی برد تو باید همین را ببینی:

(gdb) print/x fault_pc
$1 = 0x8000064
(gdb) print/x fault_cfsr
$2 = 0x8200
(gdb) print/x fault_bfar
$3 = 0xa0000000

0x8200 یعنی چه؟ بیت‌های CFSR را در ابزارک روشن کن. مقدار همین لحظه را گذاشته‌ام: دو بیت روشن است.

بیت ۹ (PRECISERR) یعنی «خطای باس دقیق: دستور مقصر همین است که PC نشان می‌دهد» و بیت ۱۵ (BFARVALID) می‌گوید BFAR آدرس بد را دارد: 0xA0000000. تشخیص کامل شد: خواندن از 0xA0000000 در دستوری که PC نشان می‌دهد. بقیهٔ بیت‌ها را هم از جدول می‌شود خواند؛ برای اینکه دست خودت با آن‌ها راحت شود، این رمزگشا (روی PC اجرا می‌شود و همان منطق را نشان می‌دهد):

#include <stdio.h>
#include <stdint.h>

struct bit_name {
    uint8_t bit;
    const char *name;
};

static const struct bit_name cfsr_bits[] = {
    { 0, "IACCVIOL"},  { 1, "DACCVIOL"},  { 7, "MMARVALID"},
    { 8, "IBUSERR"},   { 9, "PRECISERR"}, {10, "IMPRECISERR"}, {15, "BFARVALID"},
    {16, "UNDEFINSTR"},{17, "INVSTATE"},  {18, "INVPC"},  {19, "NOCP"},
    {24, "UNALIGNED"}, {25, "DIVBYZERO"},
};

static void decode_cfsr(uint32_t cfsr)
{
    printf("CFSR = 0x%08X:", (unsigned)cfsr);
    for (unsigned i = 0; i < sizeof cfsr_bits / sizeof cfsr_bits[0]; i++) {
        if (cfsr & (1u << cfsr_bits[i].bit))
            printf(" %s", cfsr_bits[i].name);
    }
    printf("\n");
}

int main(void)
{
    decode_cfsr(0x00008200u);   // خواندن از آدرس نامعتبر
    decode_cfsr(0x02000000u);   // تقسیم بر صفر
    decode_cfsr(0x00020000u);   // پرش به آدرسی با بیت0 = 0
    return 0;
}
  1. ردیف جدول. شمارهٔ بیت و نامش.
  2. جدول بیت‌ها. هر ردیف یک پرچم CFSR است: خطاهای MemManage (بیت‌های ۰ تا ۷)، BusFault (۸ تا ۱۵) و UsageFault (۱۶ تا ۳۱). جدول به‌جای زنجیرهٔ if کد را کوتاه می‌کند و افزودن بیت جدید فقط یک ردیف است.
  3. رمزگشا. برای هر ردیف، بیت را با 1u << bit می‌سنجد و اگر روشن بود نامش را چاپ می‌کند. 1u بی‌علامت است تا شیفت به بیت‌های بالا (۳۱) UB نباشد (درس ۶.۲).
  4. سه نمونهٔ واقعی. 0x8200 همان خطای بالا؛ 0x02000000 تقسیم بر صفر؛ 0x00020000 حالت نامعتبر (مثلا اشاره‌گر تابعی با بیت صفر).

مرحلهٔ آخر: از آدرس PC به خط کد. ابزار addr2line از فایل ELF، که با -g ساخته‌ای، آدرس را به نام تابع و شمارهٔ خط تبدیل می‌کند. برای همین برنامه (که خودم لینک کردم و ELF داشتم) نتیجه واقعی است؛ مسیر پوشه را کوتاه کرده‌ام:

خط ۴۰ همان return *(volatile uint32_t *)0xA0000000u; است. هم‌چنین با LR می‌توانی بفهمی چه کسی این تابع را صدا زده. برای فهمیدن «چرا به اینجا رسیدیم» از bt در GDB (اگر پشته سالم باشد) یا LR کمک بگیر. اگر پشته خودش خراب است، نتیجهٔ bt قابل‌اعتماد نیست؛ باید دستی از روی مقادیر روی پشته جست‌وجو کنی.

خطاهای دقیق‌تر: فعال‌کردن handler های جدا

به‌طور پیش‌فرض فقط HardFault فعال است و همهٔ خطاها به آن ارتقا (escalate) می‌یابند؛ بیت FORCED در HFSR این را نشان می‌دهد. با روشن‌کردن بیت‌های ۱۶ تا ۱۸ از SCB_SHCSR، MemManage، BusFault و UsageFault دست‌های جدا می‌گیرند. با بیت‌های ۴ (DIV_0_TRP) و ۳ (UNALIGN_TRP) از SCB_CCR تقسیم بر صفر و دسترسی ناهم‌تراز هم خطا می‌شوند. این را در تمرین ۳ می‌نویسی.

در ESP32 چه خبر است؟

ESP32 (Xtensa) HardFault ندارد ولی ایده یکی است. وقتی برنامه به خطای جدی می‌خورد (مثلا خواندن از NULL)، ESP-IDF متنی به‌نام «Guru Meditation Error» چاپ می‌کند: نوع استثنا، مقدار ثبات‌ها (از جمله PC) و یک backtrace: فهرست آدرس‌های برگشت. نمونهٔ زیر برای نشان‌دادن قالب است؛ آدرس‌ها را من ساخته‌ام (نه خروجی برد واقعی):

مصرف پشته: رنگ‌آمیزی و نگهبان

سرریز پشته بی‌صدا حافظهٔ دیگر را خراب می‌کند و اغلب به HardFault ختم می‌شود (درس ۳.۵). راهی ساده برای دیدن آن: رنگ‌آمیزی. قبل از شروع، کل ناحیهٔ پشته را با یک الگوی شناخته‌شده (مثلا 0xA5A5A5A5) پر می‌کنی. بعد از مدتی اجرا، از ته پشته می‌شماری چند کلمه هنوز دست‌نخورده است. تعداد کلمه‌های دست‌نخورده = «حاشیهٔ امن»؛ و پایین‌ترین جایی که به آن رسیده‌ای = علامت آب (high-water mark). آخرین کلمهٔ ناحیه را هم یک canary (قناری معدن؛ نگهبانی که اول می‌میرد) می‌گذاری: اگر عوض شد یعنی پشته تا ته رسیده است.

#include <stdio.h>
#include <stdint.h>

#define STACK_WORDS 64
#define PAINT       0xA5A5A5A5u
#define CANARY      0xDEADBEEFu

static uint32_t stack_area[STACK_WORDS];    // شبیه‌سازی یک پشته (رشد از بالا به پایین)

static void stack_init(void)
{
    for (int i = 0; i < STACK_WORDS; i++)
        stack_area[i] = PAINT;
    stack_area[0] = CANARY;                 // نگهبان در انتهای پشته
}

static void fake_calls(int depth)           // مصرف پشته را شبیه‌سازی می‌کند
{
    for (int k = 0; k < depth; k++)
        stack_area[STACK_WORDS - 1 - k] = 0x1000u + (uint32_t)k;
}

static int stack_free_words(void)
{
    int n = 1;                              // خانهٔ 0 نگهبان است
    while (n < STACK_WORDS && stack_area[n] == PAINT)
        n++;
    return n - 1;
}

int main(void)
{
    stack_init();
    fake_calls(20);
    int free_w = stack_free_words();
    printf("used = %d words, free = %d words\n", STACK_WORDS - 1 - free_w, free_w);
    printf("canary %s\n", stack_area[0] == CANARY ? "intact" : "SMASHED");
    fake_calls(64);
    printf("canary %s\n", stack_area[0] == CANARY ? "intact" : "SMASHED");
    return 0;
}
  1. الگوها. رنگ (PAINT) و نگهبان (CANARY) دو عدد شناخته‌شده و نامحتمل‌اند.
  2. ناحیهٔ پشته. در پروژهٔ واقعی این همان ناحیهٔ stack در linker script (درس ۵.۱) است.
  3. رنگ‌آمیزی. همهٔ خانه‌ها را با PAINT پر می‌کند و نگهبان را در خانهٔ ۰ می‌گذارد. روی MCU این کار را اول از همه، در startup انجام می‌دهی. پشتهٔ Cortex-M از آدرس بالا به پایین رشد می‌کند؛ پس خانهٔ ۰ (آدرس کم) آخرین خانه‌ای است که مصرف می‌شود.
  4. مصرف شبیه‌سازی‌شده. از بالا به پایین depth کلمه را با مقدار غیر از رنگ می‌نویسد.
  5. شمردن کلمه‌های دست‌نخورده. از پایین شروع می‌کند و تا اولین کلمه‌ای که رنگ نیست می‌شمارد. این روش «علامت آب» را بدون هیچ کد اضافه در برنامه می‌دهد؛ فقط باید هر از گاهی تابع را صدا بزنی.
  6. آزمایش. اول ۲۰ کلمه مصرف می‌شود و نگهبان سالم است. بعد ۶۴ کلمه (کل ناحیه) که نگهبان را خراب می‌کند.
$ gcc -std=c11 -Wall -Wextra -o stackpaint stackpaint.c
$ ./stackpaint
used = 20 words, free = 43 words
canary intact
canary SMASHED

روی MCU می‌توانی نگهبان را در تایمر ۱ میلی‌ثانیه‌ای یا در حلقهٔ اصلی وارسی کنی و در صورت خراب‌شدن، اطلاعات را ثبت و ریست کنی. اگر با arm-none-eabi-gcc و -fstack-protector کار کنی، خود کامپایلر canary می‌گذارد ولی باید نمادهای پشتیبان (__stack_chk_guard و __stack_chk_fail) را خودت تعریف کنی؛ جزئیات را در مستندات GCC ببین. در FreeRTOS هم ویژگی مشابهی برای پشتهٔ تسک‌ها هست (درس ۵.۶).

زیر کاپوت: چرا bt گاهی دروغ می‌گوید؟

GDB پشتهٔ فراخوانی را با خواندن آدرس‌های برگشت و اطلاعات unwind درون ELF می‌سازد. اگر پشته خراب شده باشد (سرریز، اشاره‌گر خراب)، آدرس‌های برگشت هم خراب‌اند و bt چیز بی‌معنی نشان می‌دهد. به همین دلیل «PC ذخیره‌شده» که CPU خودش ذخیره کرده معتبرتر از bt است. ولی دقت کن که PC ذخیره‌شده آدرس دستور خطادار است، نه لزوما علت اصلی: اگر اشاره‌گر را چند خط قبل خراب کرده‌ای، فقط اینجا انفجار دیده می‌شود. برای پیدا‌کردن علت واقعی، حدس بزن چه چیزی مقدار بد را ساخت و watch بگذار.

آزمون این درس

اولین کار درست هنگام باگی که «گاهی» رخ می‌دهد چیست؟

  1. اول چند خط را بی‌دلیل عوض کنیم و ببینیم درست می‌شود
  2. راهی برای تکرار مطمئن آن پیدا کنیم (ورودی ثابت، شمارهٔ دور مشخص)
  3. بلافاصله printf در همهٔ توابع بگذاریم
  4. فقط آن را ریست خودکار کنیم
باگ قابل‌تکرار نیمی از راه حل است: بعد از آن می‌توان مشکل را کوچک و نصف کرد.

کد assert(count++ < 10); در نسخهٔ ساخته‌شده با -DNDEBUG چه می‌شود؟

  1. شرط اجرا می‌شود ولی خطا نمی‌دهد
  2. برنامه کامپایل نمی‌شود
  3. count دوبار زیاد می‌شود
  4. کل دستور حذف می‌شود و count دیگر زیاد نمی‌شود؛ رفتار برنامه عوض می‌شود
با NDEBUG ماکرو assert به «هیچ» تبدیل می‌شود. پس شرط assert نباید اثر جانبی داشته باشد.

در GDB می‌خواهی هر بار مقدار متغیر sum عوض شد برنامه بایستد. کدام فرمان؟

  1. watch sum
  2. ‌break sum
  3. ‌finish sum
  4. ‌print sum
watch یک ناظر می‌گذارد که با هر تغییر متغیر برنامه را نگه می‌دارد و مقدار قدیم و جدید را نشان می‌دهد.

در handler HardFault، اشاره‌گر frame به هشت کلمهٔ ذخیره‌شده روی پشته اشاره می‌کند. آدرس دستور خطادار کدام است؟

  1. ‌frame[0]
  2. ‌frame[5]
  3. frame[6]
  4. ‌frame[7]
ترتیب: R0, R1, R2, R3, R12, LR, PC, xPSR؛ پس PC هفتمین کلمه یعنی frame[6] است.

تابعی در ISR هر ۵۰ میکروثانیه اجرا می‌شود و می‌خواهی زمان اجرایش را بسنجی. کدام روش مناسب‌تر است؟

  1. داخل ISR یک printf با زمان بگذاریم
  2. نقطهٔ توقف در ISR بگذاریم و زمان را با ساعت خودمان بگیریم
  3. با semihosting در ISR بنویسیم
  4. ابتدای ISR یک پایه را بالا و آخرش پایین ببریم و با تحلیلگر منطقی عرض پالس را ببینیم
پایهٔ دیباگ یکی دو دستور BSRR است و مزاحمت ناچیز دارد؛ عرض پالس زمان واقعی است.

علامت آب (high-water mark) پشته چیست؟

  1. بیشترین عمقی که پشته تا حالا مصرف شده است (کمترین کلمهٔ دست‌نخورده)
  2. اندازهٔ کل ناحیهٔ پشته در linker script
  3. آدرس فعلی SP
  4. تعداد وقفه‌هایی که تا حالا اجرا شده‌اند
با رنگ‌آمیزی پشته و شمردن کلمه‌های دست‌نخورده، عمیق‌ترین نقطهٔ رسیده‌شده را می‌فهمی. حاشیهٔ امن = کلمه‌های دست‌نخورده.

تمرین ۱: میانگین با پارازیت

برنامهٔ avg_dbg.c این درس، پارازیت ۹۹۹۹ را هم جمع می‌کند و ۲۱۶۸ چاپ می‌کند. می‌خواهیم اصلاحش کنیم.

  1. پیش‌بینی: بدون اجرا، میانگین چهار خوانش سالم (۲۱۰، ۲۱۵، ۲۱۲، ۲۰۸) با تقسیم صحیح چند می‌شود؟
  2. حل: تابع average را طوری تغییر بده که خوانش‌های بزرگ‌تر از ۱۰۰۰ را نادیده بگیرد و فقط روی خوانش‌های معتبر میانگین بگیرد (تعدادشان را بشمار).
  3. دیباگ: برنامه را با -g -O0 بساز و در GDB watch used بگذار. چند بار می‌ایستد؟ چرا؟
راهنمایی

یک شمارندهٔ used بگذار. داخل حلقه اگر v[i] > MAX_OK، از continue استفاده کن تا جمع نشود و شمارنده هم بالا نرود. تقسیم را بر used بزن (و اگر صفر بود، جواب صفر بده تا تقسیم بر صفر نشود).

چه باید ببینی؟ 
$ ./avg_fix
average = 211

مجموع ۸۴۵ بر ۴ = ۲۱۱٫۲۵ که با تقسیم صحیح ۲۱۱ می‌شود. watch used چهار بار می‌ایستد، یک بار برای هر خوانش سالم.

جواب کامل با توضیح 
#include <stdio.h>
#include <stdint.h>

#define N      5
#define MAX_OK 1000

static int32_t readings[N] = {210, 215, 9999, 212, 208};

static int32_t average(const int32_t *v, int n)
{
    int32_t sum = 0;
    int used = 0;
    for (int i = 0; i < n; i++) {
        if (v[i] > MAX_OK)
            continue;               // پارازیت را رد کن
        sum += v[i];
        used++;
    }
    return used > 0 ? sum / used : 0;
}

int main(void)
{
    printf("average = %d\n", (int)average(readings, N));
    return 0;
}
  1. ثابت‌ها. تعداد خوانش‌ها و حد بالای منطقی. عدد جادویی ۱۰۰۰ را به‌جای متن پخش‌شده نام‌گذاری کن (درس ۴.۱).
  2. دو شمارنده. جمع و تعداد خوانش‌های معتبر.
  3. رد پارازیت. continue بقیهٔ بدنهٔ حلقه را می‌پرد.
  4. جمع معتبرها. فقط خوانش‌های سالم.
  5. تقسیم امن. اگر هیچ خوانش سالمی نبود، صفر برمی‌گرداند. در MCU تقسیم بر صفر می‌تواند خطا بدهد یا بی‌صدا صفر بدهد؛ در هر دو حالت باید وارسی کنی.
$ gcc -std=c11 -Wall -Wextra -o avg_fix avg_fix.c
$ ./avg_fix
average = 211
تمرین ۲: رمزگشای HFSR

در درس، decode_cfsr را دیدی. ثبات HFSR (آدرس 0xE000ED2C) هم علت HardFault را می‌گوید: بیت ۱ = VECTTBL (خطا هنگام خواندن جدول وقفه)، بیت ۳۰ = FORCED (یک خطای دیگر ارتقا یافته)، بیت ۳۱ = DEBUGEVT.

  1. پیش‌بینی: اگر HFSR = 0x40000000 باشد، چه بیتی روشن است؟ برای نمونهٔ درس (خواندن از 0xA0000000) این مقدار منطقی است؟ چرا؟
  2. حل: رمزگشا را تعمیم بده: یک تابع decode(const char *reg, uint32_t v, ...) که برای هر دو ثبات کار کند و برای 0x40000000 بنویسد HFSR = 0x40000000: FORCED.
  3. فکر کن: اگر FORCED روشن باشد، باید بعدش کدام ثبات را بخوانی؟
راهنمایی

یک ساختار bit_name و یک جدول برای HFSR بساز و تابع را طوری بنویس که جدول و طولش را بگیرد. برای ب بخش پ: FORCED یعنی خطا ارتقا یافته؛ علتش در CFSR است.

چه باید ببینی؟ 
$ ./hfsr
HFSR = 0x40000000: FORCED
CFSR = 0x00008200: PRECISERR BFARVALID

جواب الف: بیت ۳۰. بله؛ چون BusFault جدا فعال نیست، به HardFault ارتقا می‌یابد و FORCED روشن می‌شود. جواب پ: CFSR (و بعد BFAR/MMFAR).

جواب کامل با توضیح 
#include <stdio.h>
#include <stdint.h>

struct bit_name {
    uint8_t bit;
    const char *name;
};

static const struct bit_name hfsr_bits[] = {
    {1, "VECTTBL"}, {30, "FORCED"}, {31, "DEBUGEVT"},
};

static const struct bit_name cfsr_bits[] = {
    {8, "IBUSERR"}, {9, "PRECISERR"}, {15, "BFARVALID"}, {25, "DIVBYZERO"},
};

static void decode(const char *reg, uint32_t v, const struct bit_name *t, unsigned n)
{
    printf("%s = 0x%08X:", reg, (unsigned)v);
    for (unsigned i = 0; i < n; i++) {
        if (v & (1u << t[i].bit))
            printf(" %s", t[i].name);
    }
    printf("\n");
}

int main(void)
{
    decode("HFSR", 0x40000000u, hfsr_bits, sizeof hfsr_bits / sizeof hfsr_bits[0]);
    decode("CFSR", 0x00008200u, cfsr_bits, sizeof cfsr_bits / sizeof cfsr_bits[0]);
    return 0;
}
  1. ساختار ردیف. همان قالب جدول درس.
  2. دو جدول. یکی برای HFSR و یکی (کوتاه‌شده) برای CFSR.
  3. تابع عمومی. نام ثبات، مقدار، جدول و تعداد ردیف را می‌گیرد. طول جدول جدا فرستاده می‌شود چون آرایه در پارامتر تابع به اشاره‌گر تبدیل می‌شود و sizeof داخل تابع غلط می‌شود (درس ۶.۲).
  4. استفاده. sizeof در جایی که آرایه تعریف شده حساب می‌شود، نه داخل تابع.

تمرین ۳: هر خطا handler خودش را داشته باشد

می‌خواهیم علاوه بر HardFault، خطاهای BusFault، UsageFault و MemManage هم handler جدا بگیرند و تقسیم بر صفر و دسترسی ناهم‌تراز به‌جای خاموشی بی‌صدا، خطا بدهند.

  1. پیش‌بینی: بیت‌های SCB_SHCSR (آدرس 0xE000ED24) برای فعال‌کردن این سه: MEMFAULTENA بیت ۱۶، BUSFAULTENA بیت ۱۷، USGFAULTENA بیت ۱۸. مقدار OR آن‌ها چند است؟
  2. حل: تابع enable_fault_traps را بنویس که این سه بیت را روشن کند و در SCB_CCR (آدرس 0xE000ED14) بیت ۴ (DIV_0_TRP) و بیت ۳ (UNALIGN_TRP) را روشن کند. سه handler خالی (for (;;)) هم بگذار.
  3. سخت‌افزار: چرا این کار کمک می‌کند؟ (راهنمایی: به‌جای همه چیز در HardFault، UsageFault فقط برای خطای ابزار می‌آید.)
راهنمایی

هر ثبات را با |= عوض کن؛ اگر می‌خواهی دقیق باشی، پیش از نوشتن مقدار فعلی را بخوان (چون بعضی بیت‌ها ممکن است قبلا روشن باشند). نام handler ها باید دقیقا BusFault_Handler و UsageFault_Handler و MemManage_Handler باشد تا با جدول وقفهٔ startup بخوانند.

چه باید ببینی؟

این کد فقط کامپایل می‌شود و اجرای مستقلی ندارد؛ باید بدون هشدار با arm-none-eabi-gcc -mcpu=cortex-m4 -mthumb -Wall -Wextra -ffreestanding -c کامپایل شود. جواب الف: (1u<<16) | (1u<<17) | (1u<<18) = 0x00070000.

جواب کامل با توضیح 
#include <stdint.h>

#define SCB_CCR   (*(volatile uint32_t *)0xE000ED14u)
#define SCB_SHCSR (*(volatile uint32_t *)0xE000ED24u)

void enable_fault_traps(void)
{
    SCB_SHCSR |= (1u << 16) | (1u << 17) | (1u << 18);   // MemManage، BusFault، UsageFault فعال
    SCB_CCR   |= (1u << 4) | (1u << 3);                   // تقسیم بر صفر و ناهم‌ترازی هم خطا بدهند
}

void BusFault_Handler(void)   { for (;;) { } }
void UsageFault_Handler(void) { for (;;) { } }
void MemManage_Handler(void)  { for (;;) { } }
  1. ثبات‌های SCB. CCR تنظیمات هسته و SHCSR فعال‌سازی handler های سیستم است.
  2. فعال‌سازی. بیت‌های ۱۶ تا ۱۸ سه خطای جدا را روشن می‌کنند. بدون این‌ها هر خطا به HardFault ارتقا می‌یابد و FORCED روشن می‌شود؛ با آن‌ها می‌فهمی نوع دقیق خطا از همان ورودی است.
  3. تله‌های اضافه. DIV_0_TRP تقسیم بر صفر و UNALIGN_TRP دسترسی ناهم‌تراز را به UsageFault تبدیل می‌کند. پیش‌فرض این‌ها خاموش است و بی‌صدا صفر یا مقدار غلط می‌دهد؛ فعال‌کردنشان باگ را همان لحظه آشکار می‌کند.
  4. handler ها. در جدول وقفهٔ startup (درس ۵.۱) با همین نام‌ها صدا زده می‌شوند. اینجا فقط می‌ایستند تا دیباگر ببیند.
حرف مربی

تقریبا همه در دو جای این درس گیر می‌کنند. اول: «بی‌خیال ابزار؛ printf می‌زنم!» برای باگ ساده خوب است، ولی روی MCU بیشتر باگ‌ها زمان‌بندی یا حافظه‌اند و printf آن‌ها را عوض می‌کند. یک ساعت یادگیری GDB و SWD سال‌ها وقت را نجات می‌دهد. دوم: «HardFault یعنی تراشه خراب شده»؛ تقریبا هیچ‌وقت. تراشه دارد با تو حرف می‌زند: PC می‌گوید کجا، CFSR می‌گوید چه، BFAR می‌گوید کدام آدرس. اگر یک کار بکنی، همان handler درس را در هر پروژهٔ Cortex-M از روز اول بگذار. و یادت باشد: باگی که رفع کردی، یک تست می‌خواهد.

خلاصه یک‌دقیقه‌ای

  • روش: تکرار، کوچک‌کردن، حدس قابل‌آزمایش، اندازه‌گیری، رفع و تست. نصف‌کردن جای مشکوک سریع‌ترین راه است.
  • لاگ سطح‌بندی‌شده با ماکرو؛ روی MCU printf گران است و در ISR ممنوع.
  • assert برای «نباید هرگز رخ دهد»؛ با NDEBUG حذف می‌شود، پس بدون اثر جانبی.
  • GDB: break (شرطی)، watch، bt، x، print؛ با -g -O0 بساز. sanitizer روی PC باگ حافظه را می‌گیرد.
  • مسیر سخت‌افزاری: arm-none-eabi-gdb ← OpenOCD ← ST-LINK ← SWD ← Cortex-M. راه‌های خروجی: UART، semihosting، SWO/ITM، RTT.
  • پایهٔ دیباگ با BSRR و تحلیلگر منطقی، زمان اجرا را بدون مزاحمت می‌سنجد.
  • HardFault: قاب پشته (frame[6] = PC)، CFSR/BFAR، addr2line؛ ESP32: backtrace و idf.py monitor. رنگ‌آمیزی پشته و canary سرریز پشته را نشان می‌دهد.
