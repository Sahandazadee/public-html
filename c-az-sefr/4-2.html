تا حالا هر برنامه‌ات در یک فایل جا می‌شد. پروژهٔ واقعی روی STM32 یا ESP32 ده‌ها فایل دارد: درایور UART، درایور سنسور، فیلتر، ماشین حالت. اگر همه در یک فایل ۵۰۰۰ خطی بودند، هیچ‌کس نمی‌توانست چیزی را پیدا کند یا بخشی را به پروژهٔ دیگر ببرد. در این درس یاد می‌گیری چطور کد را بین فایل‌ها تقسیم کنی، فایل‌ها چطور همدیگر را می‌شناسند، و چطور یک دستور make کل پروژه را می‌سازد. همین‌جا هم می‌فهمی پیام‌های ترسناک لینکر (undefined reference) واقعا یعنی چه.

ایده اصلی: منو و آشپزخانه

یک رستوران را در نظر بگیر. مشتری روی منو می‌بیند چه غذاهایی هست و اسم و قیمتشان چیست. او نمی‌داند و لازم هم نیست بداند غذا چطور پخته می‌شود. طرز پخت در آشپزخانه است. اگر آشپز طرز پخت را عوض کند، منو همان می‌ماند و مشتری چیزی نمی‌فهمد.

مثال از زندگی روزمره

در C همین تقسیم را داریم. فایل هدر (header، پسوند .h) منوست: فقط می‌گوید چه تابع‌هایی هست و ورودی و خروجیشان چیست. فایل منبع (پسوند .c) آشپزخانه است: طرز کار واقعی. فایل‌های دیگر فقط منو را می‌خوانند (با #include) و سفارش می‌دهند (تابع را صدا می‌زنند).

به هر مجموعه از یک .h و یک .c که یک کار مشخص را انجام می‌دهد، ماژول (module) می‌گوییم: مثلا ماژول uart برای فرستادن بایت، یا ماژول filter برای میانگین‌گیری. پروژه یعنی چند ماژول به‌اضافهٔ یک main.c که آن‌ها را کنار هم می‌گذارد.

اعلان و تعریف: دو کار متفاوت

این مهم‌ترین مفهوم درس است. در C دو چیز کاملا جدا داریم:

به اعلان تابع قبلا «پروتوتایپ» گفتیم (درس ۲.۶). اعلان متغیر با کلمهٔ extern (از external یعنی «بیرونی») نوشته می‌شود و به کامپایلر می‌گوید: «این قفسه جای دیگری ساخته شده؛ من فقط اسم و نوعش را می‌دانم».

چرا «فقط یک بار»؟

اگر دو فایل هر کدام یک قفسه به نام counter بسازند، لینکر نمی‌داند کدام را وصل کند و خطا می‌دهد. اگر هدری که تعریف دارد در دو فایل #include شود، همین اتفاق می‌افتد، چون #include فقط متن را کپی می‌کند (درس ۴.۱). پس در هدر فقط اعلان بگذار، تعریف را در .c بنویس.

اگر از پایتون می‌آیی

import در پایتون ماژول را یک‌بار می‌خواند و یک شیء می‌سازد. #include فقط متن فایل را کپی می‌کند، پس اگر دو فایل .c یک هدر را بگیرند، هر کدام نسخهٔ خودش را دارد. بنابراین هدر باید فقط اعلان باشد و خودِ «ماژول» همان فایل .c است که جداگانه کامپایل و بعدا لینک می‌شود.

اولین پروژهٔ چندفایلی: دماسنج با فیلتر

برنامه‌ای می‌سازیم که دما را «می‌خواند» و میانگین سه خوانش اخیر را نشان می‌دهد. سه بخش دارد: ماژول سنسور (تولید خوانش شبیه‌سازی‌شده)، ماژول فیلتر (میانگین) و main.c. دما را بر حسب دهم درجه نگه می‌داریم: ۲۳۵ یعنی ۲۳٫۵ درجه (بدون اعشار، مثل درس ۲.۳).

این نکته مهم است: وقتی کامپایلر main.c را می‌خواند، هیچ‌چیز از محتوای sensor.c نمی‌داند. فقط از روی هدر می‌داند که تابعی به اسم sensor_read_dc هست که int16_t برمی‌گرداند. بقیه‌اش را لینکر پر می‌کند.

ماژول سنسور

#ifndef SENSOR_H
#define SENSOR_H

#include <stdint.h>

/* دمای شبیه‌سازی‌شده بر حسب دهم درجه: 235 یعنی 23.5 درجه */
int16_t sensor_read_dc(void);

#endif /* SENSOR_H */
  1. include guard. همان الگوی درس ۴.۱: اگر این هدر دو بار وارد شد، بار دوم پرش می‌خورد. هر هدر خودت از اولین روز guard داشته باشد؛ چون نمی‌دانی چه فایلی روزی آن را از دو راه می‌آورد.
  2. هدرهای مورد نیاز خودش. چون در اعلان int16_t آمده، خود هدر باید stdint.h را بیاورد. اگر نیاورد، هر کسی که sensor.h را وارد کند باید یادش باشد قبلش stdint.h را هم وارد کند. هدر خوب «خودکفاست».
  3. اعلان تابع. فقط سر تابع و ;. بدنه‌ای در کار نیست.
#include "sensor.h"

static const int16_t samples[] = { 231, 236, 229, 240, 233 };
static unsigned next_index = 0;

int16_t sensor_read_dc(void)
{
    int16_t value = samples[next_index];
    next_index = (next_index + 1U) % (sizeof(samples) / sizeof(samples[0]));
    return value;
}
  1. هدر خودش را include می‌کند. با این کار کامپایلر می‌تواند تعریف را با اعلان مقایسه کند. اگر اعلان در هدر int16_t باشد و در .c تعریف را با int بنویسی، همین‌جا خطا می‌گیری، نه در لینک یا (بدتر) هنگام اجرا. پایین‌تر خطایش را می‌بینی.
  2. داده‌های خصوصی. جدول نمونه‌ها و اندیس فعلی static هستند: یعنی فقط برای همین فایل‌اند. const جدول را فقط‌خواندنی و جای‌گیرنده در Flash می‌کند (درس ۲.۷). هیچ فایل دیگری نباید بتواند next_index را دست‌کاری کند. این «دیوار آشپزخانه» است.
  3. تعریف تابع. مقدار فعلی را بگیر، اندیس را یکی جلو ببر و اگر به انتها رسید به صفر برگرد (با باقیمانده %). sizeof(samples) / sizeof(samples[0]) تعداد عنصرهاست (درس ۲.۷).

ماژول فیلتر

#ifndef FILTER_H
#define FILTER_H

#include <stdint.h>

void filter_reset(void);
void filter_add(int16_t value);
int16_t filter_average(void);

#endif /* FILTER_H */

#include "filter.h"

#define WINDOW 3U

static int16_t window[WINDOW];
static unsigned count = 0;
static unsigned head = 0;

void filter_reset(void)
{
    count = 0;
    head = 0;
}

void filter_add(int16_t value)
{
    window[head] = value;
    head = (head + 1U) % WINDOW;
    if (count < WINDOW) {
        count++;
    }
}

int16_t filter_average(void)
{
    int32_t sum = 0;
    if (count == 0) {
        return 0;
    }
    for (unsigned i = 0; i < count; i++) {
        sum += window[i];
    }
    return (int16_t)(sum / (int32_t)count);
}
  1. اندازهٔ پنجره. ماکرو (درس ۴.۱) با U برای بی‌علامت.
  2. وضعیت داخلی. آرایهٔ سه‌تایی از آخرین خوانش‌ها، تعداد پرشده و اندیس نوشتن بعدی. همه static. فیلتر «حافظه» دارد (آخرین مقدارها)، ولی این حافظه پنهان است و بیرون فقط از راه توابع ماژول به آن دسترسی داری.
  3. صفر کردن. شروع دوباره.
  4. افزودن نمونه. در خانهٔ head بنویس، head را چرخشی جلو ببر (به کمک %) و تا وقتی پنجره پر نشده count را زیاد کن. این هستهٔ همان «بافر حلقوی» است که در درس ۴.۵ کامل می‌سازیم.
  5. میانگین. جمع را در int32_t نگه می‌داریم تا سرریز نکند (چون int16_t برای جمع چند دما ممکن است کوچک باشد؛ درس ۲.۲). اگر هنوز نمونه‌ای نیست ۰ برگردان. تقسیم بر صفر رفتار تعریف‌نشده است؛ پس حالت count == 0 باید جدا بررسی شود.

فایل main.c

#include <stdio.h>
#include "sensor.h"
#include "filter.h"

int main(void)
{
    filter_reset();
    for (int i = 0; i < 5; i++) {
        int16_t raw = sensor_read_dc();
        filter_add(raw);
        int16_t avg = filter_average();
        printf("raw=%d.%d avg=%d.%d\n", raw / 10, raw % 10, avg / 10, avg % 10);
    }
    return 0;
}
  1. سه include. <stdio.h> با <> چون سیستمی است. هدرهای پروژه با "". در main.c فقط هدر لازم را وارد می‌کنیم؛ نه sensor.c. هرگز #include "sensor.c" ننویس: کد دو بار کامپایل می‌شود و multiple definition می‌گیری.
  2. آغاز. فیلتر را خالی می‌کنیم.
  3. حلقهٔ ۵ بار. هر بار یک خوانش می‌گیرد، به فیلتر می‌دهد و میانگین را می‌پرسد. raw / 10 بخش صحیح دما و raw % 10 رقم اعشار است. این ترفند بدون float اعشار نمایش می‌دهد. درس ۲.۸ گفتیم روی MCU چاپ float پرهزینه است.

ساخت دستی: هر فایل جدا، لینک همه با هم

کاری که make برایمان می‌کند را اول دستی انجام می‌دهیم تا سر از کارش دربیاوریم. مرحلهٔ اول: هر .c را جدا به فایل شیء (object file) کامپایل می‌کنیم. پرچم -c یعنی «فقط کامپایل، لینک نکن». مرحلهٔ دوم: لینکر (linker) همه را وصل می‌کند.

$ gcc -std=c11 -Wall -Wextra -c main.c
$ gcc -std=c11 -Wall -Wextra -c sensor.c
$ gcc -std=c11 -Wall -Wextra -c filter.c
$ gcc main.o sensor.o filter.o -o thermo

لینکر چطور می‌فهمد main.o باید sensor_read_dc را از کجا بگیرد؟ هر فایل شیء یک جدول نام‌ها دارد. دستور nm این جدول را چاپ می‌کند:

$ nm sensor.o
0000000000000000 b next_index
0000000000000000 r samples
0000000000000000 T sensor_read_dc
$ nm main.o
                 U filter_add
                 U filter_average
                 U filter_reset
0000000000000000 T main
                 U sensor_read_dc

حرفمعنیمثال بالا

وقتی لینک خراب می‌شود: سه خطای معروف

خطاهای لینکر برای مبتدی‌ها ترسناک‌اند، چون به شماره خط اشاره نمی‌کنند و پیام‌شان طولانی است. ولی فقط سه مدل اصلی دارند. با هر کدام از نزدیک آشنا شو.

خطای ۱: undefined reference

هدر را داری و تابع را صدا می‌زنی، ولی sensor.c را کامپایل و لینک نکرده‌ای. کامپایلر راضی است (اعلان را دیده). لینکر می‌گوید «تعریف کجاست؟»:

#ifndef SENSOR_H
#define SENSOR_H

#include <stdint.h>

int16_t sensor_read_dc(void);

#endif /* SENSOR_H */

#include <stdio.h>
#include "sensor.h"

int main(void)
{
    printf("%d\n", sensor_read_dc());
    return 0;
}
  1. فقط هدر. اعلان کافی است تا کامپایلر main.c را بپذیرد.
  2. صدا زدن. در main.o این می‌شود یک «U»: منتظر تعریف. هیچ فایل .c دیگری در فرمان ساخت نیست، پس هیچ «T»ی برای sensor_read_dc نیست.
$ gcc -std=c11 -Wall -Wextra -o prog main.c
main.c:(.text+0x9): undefined reference to `sensor_read_dc'
collect2: error: ld returned 1 exit status

خط اول (که با /usr/bin/ld: شروع می‌شود و نام فایل موقت دارد) کوتاه شده است. مهم‌ترین قسمت undefined reference to `نام' است: نام همان تابع یا متغیری است که لینکر تعریفش را پیدا نکرد. آخرین خط (collect2) فقط می‌گوید لینکر شکست خورد.

چک‌لیست undefined reference
  1. آیا فایل .c را کامپایل کرده‌ام؟ در Makefile یا لیست منبع‌ها اضافه‌اش کن.
  2. آیا اسم را درست نوشته‌ام؟ sensor_read_dc با sensor_readdc دو تابع جدا هستند.
  3. آیا تابع static شده؟ تابع static از فایل دیگر دیده نمی‌شود.
  4. در C++ هستی؟ برای فایل C در پروژه C++ به extern "C" نیاز داری (فعلا لازم نیست).

خطای ۲: multiple definition

یک متغیر را در هدر تعریف کرده‌ای (نه اعلان). هر فایلی که هدر را وارد کند، قفسهٔ خودش را می‌سازد:

#ifndef COUNTER_H
#define COUNTER_H

int counter = 0;       // تعریف در هدر: اشتباه!

#endif /* COUNTER_H */

#include "counter.h"

void bump(void)
{
    counter++;
}

#include <stdio.h>
#include "counter.h"

void bump(void);

int main(void)
{
    bump();
    printf("%d\n", counter);
    return 0;
}
  1. تعریف در هدر. int counter = 0; یک قفسهٔ واقعی می‌سازد. include guard جلوی دوبار ورود در یک فایل را می‌گیرد، ولی هر .c جدا، هدر را دوباره و از نو می‌خواند. قفل guard «برای هر فایل ترجمه» از نو شروع می‌شود؛ پس دو فایل .c دو قفسه به نام counter می‌سازند: یکی در other.o و یکی در main.o.
$ gcc -std=c11 -Wall -Wextra -o prog main.c other.c
multiple definition of `counter'
collect2: error: ld returned 1 exit status

پیام کامل وقتی که فایل‌ها را جدا کامپایل کرده باشی (مثل make) نام فایل‌های شیء را نشان می‌دهد و خیلی کمک می‌کند:

$ gcc -std=c11 -c main.c
$ gcc -std=c11 -c other.c
$ gcc main.o other.o -o prog
/usr/bin/ld: other.o:(.bss+0x0): multiple definition of `counter'; main.o:(.bss+0x0): first defined here
collect2: error: ld returned 1 exit status

در این پیام نام هر دو فایلی که تعریف را دارند آمده است. راه‌حل استاندارد: اعلان را با extern در هدر بگذار و تعریف را فقط در یک .c. در بخش بعد می‌بینی.

«روی کامپیوتر دوستم لینک شد!»

اگر در هدر بنویسی int counter; (بدون = 0)، این یک «تعریف آزمایشی» (tentative definition) است. gcc نسخه‌های ۹ و قدیمی‌تر به‌طور پیش‌فرض با -fcommon چنین متغیرهایی را در فایل‌های مختلف بی‌صدا یکی می‌کرد و لینک می‌شد؛ gcc نسخهٔ ۱۰ به بعد پیش‌فرضش -fno-common است و خطای multiple definition می‌دهد. پس کدی که روی یک کامپیوتر «کار می‌کرد» روی کامپیوتر دیگر نمی‌ساخت. راه درست یکی است: در هدر extern، در دقیقا یک .c تعریف.

خطای ۳: conflicting types

این خطا لینکر نیست، کامپایلر است؛ ولی اینجا می‌آید چون از دورشدن اعلان و تعریف می‌آید. اگر در sensor.c هدر را #include کرده باشی و تعریف را با نوع دیگری بنویسی:

#ifndef SENSOR_H
#define SENSOR_H

#include <stdint.h>

int16_t sensor_read_dc(void);

#endif /* SENSOR_H */

#include "sensor.h"

int sensor_read_dc(void)
{
    return 231;
}

#include <stdio.h>
#include "sensor.h"

int main(void)
{
    printf("%d\n", sensor_read_dc());
    return 0;
}
  1. هدر خودش. کامپایلر اعلان را می‌بیند.
  2. تعریف با نوع دیگر. int با int16_t یکی نیست. اگر sensor.c هدر خودش را include نمی‌کرد، این خطا دیده نمی‌شد و main.c فکر می‌کرد تابع int16_t می‌دهد ولی sensor.c چیز دیگری می‌ساخت. روی بعضی سخت‌افزارها (اندازهٔ ثبات‌ها یا قرارداد فراخوانی متفاوت) فقط دادهٔ اشتباه می‌گرفتی. include کردن هدر خود ماژول در فایل خودش یک شبکهٔ ایمنی رایگان است.
sensor.c:3:5: error: conflicting types for 'sensor_read_dc'; have 'int(void)'
sensor.h:6:9: note: previous declaration of 'sensor_read_dc' with type 'int16_t(void)' {aka 'short int(void)'}

extern: متغیر مشترک بین فایل‌ها

گاهی واقعا یک متغیر باید بین دو فایل مشترک باشد؛ مثل شمارندهٔ تیک زمان یا پرچمی که وقفه می‌گذارد و main می‌خواند (درس ۵.۳). الگوی درست سه قدم دارد:

  1. تعریف در یک .c: int g_tick_count = 0; (قفسه اینجا ساخته می‌شود).
  2. اعلان در هدر: extern int g_tick_count; (به همه می‌گوید چنین قفسه‌ای هست).
  3. هر فایلی که لازم دارد، هدر را وارد می‌کند.
#ifndef CONFIG_H
#define CONFIG_H

extern int g_tick_count;      /* اعلان: تعریفش جای دیگری است */
void tick(void);

#endif /* CONFIG_H */

#include "config.h"

int g_tick_count = 0;         /* تعریف: اینجا قفسه ساخته می‌شود */

void tick(void)
{
    g_tick_count++;
}

#include <stdio.h>
#include "config.h"

int main(void)
{
    tick();
    tick();
    g_tick_count += 10;
    printf("ticks = %d\n", g_tick_count);
    return 0;
}
  1. extern. بدون مقدار اولیه و بدون ساختن قفسه؛ فقط «این اسم با این نوع وجود دارد». اگر اینجا = 0 می‌نوشتی، تعریف می‌شد و دوباره به خطای multiple definition می‌رسیدی.
  2. تابع دسترسی. اعلان تابع tick که در config.c تعریف شده.
  1. هدر خودش. تا کامپایلر بررسی کند اعلان و تعریف هم‌نوع‌اند.
  2. تعریف تنها. تنها جایی که قفسهٔ g_tick_count ساخته می‌شود و مقدار اولیه می‌گیرد.
  3. تابع. یکی به شمارنده اضافه می‌کند.
  1. تغییر از دو جا. دو بار tick() (شمارنده می‌شود ۲) و بعد مستقیم ۱۰ تا اضافه می‌کنیم. هر دو یک قفسه را تغییر می‌دهند.
$ gcc -std=c11 -Wall -Wextra -o ext_demo main.c config.c
$ ./ext_demo
ticks = 12

متغیر سراسری مشترک: با احتیاط

هر متغیری که چند فایل به آن دسترسی مستقیم دارند، رد پای باگ را سخت می‌کند: «چه کسی این را عوض کرد؟». قاعده: تا می‌توانی متغیر را static نگه دار و بیرون فقط توابع (tick_get()، tick_reset()) بده. اگر مجبوری متغیر مشترک بدهی (مثلا پرچم بین ISR و main)، آن را با volatile (درس ۳.۶) و پیشوند g_ مشخص کن:

/* button.h */
extern volatile uint8_t g_button_pressed;   /* اعلان */

/* button.c */
volatile uint8_t g_button_pressed = 0;      /* تعریف */

static: دیوار دور فایل

در درس ۲.۶ دیدی static جلوی تابع یعنی «فقط برای همین فایل». حالا دلیل واقعی‌اش را می‌فهمی: به‌طور پیش‌فرض هر تابع و هر متغیر سراسری برای لینکر «T» است و همه‌ی فایل‌ها می‌توانند به آن برسند. به این می‌گویند پیوند بیرونی (external linkage). با static، اسم پیوند درونی (internal linkage) می‌گیرد: فقط در همین فایل ترجمه شناخته می‌شود. دو فایل می‌توانند هر کدام تابع static با اسم یکسان داشته باشند، بدون هیچ برخوردی.

#include <stdio.h>

static void log_line(const char *msg)
{
    printf("[a] %s\n", msg);
}

void a_run(void)
{
    log_line("hello from a");
}

#include <stdio.h>

static void log_line(const char *msg)
{
    printf("[b] %s\n", msg);
}

void b_run(void)
{
    log_line("hello from b");
}

void a_run(void);
void b_run(void);

int main(void)
{
    a_run();
    b_run();
    return 0;
}
  1. تابع خصوصی. log_line با static فقط در a.c دیده می‌شود. در b.c هم یک log_line دیگر با همین اسم داریم و برخوردی نیست. در پروژه‌ای با ۵۰ فایل، تابع‌های کمکی کوچک (clamp، log_line) زیاد تکرار می‌شوند. static جلوی «آلودگی اسم‌ها» را می‌گیرد.
  2. تابع عمومی. a_run بدون static است، پس main.c می‌تواند صدایش بزند.
$ gcc -std=c11 -Wall -Wextra -o static_demo main.c a.c b.c
$ ./static_demo
[a] hello from a
[b] hello from b

اگر static را از هر دو log_line برداری، هر دو «T» می‌شوند و لینکر با خطای آشنا مواجه می‌شویم:

/usr/bin/ld: b.o: in function `log_line':

collect2: error: ld returned 1 exit status

طراحی ماژول: چه چیزی را نشان بدهم؟

ماژول خوب مثل یک دستگاه با چند دکمه است. می‌دانی هر دکمه چه می‌کند، ولی درون دستگاه را نمی‌بینی. هدر واسط کاربری (API، از Application Programming Interface) ماژول است.

قواعد طراحی ماژول
  • یک ماژول، یک مسئولیت. uart فقط با UART کار دارد و فیلتر دما در آن نیست.
  • پیشوند اسم ماژول روی همهٔ توابع عمومی: uart_init، uart_send_byte. در C اسم فضای جدا ندارد؛ پیشوند جلوی برخورد اسم‌ها را می‌گیرد.
  • هدر تا حد ممکن کوچک: فقط آنچه کاربر لازم دارد. هر چیزی که فقط داخل .c لازم است در .c و static بماند.
  • هدر خودکفا: هر هدر باید تنها هم کامپایل شود (هدرهای لازم خودش را بیاورد).
  • در هدر فقط اعلان، ماکرو، typedef/struct/enum و توابع static inline. هرگز تعریف تابع یا متغیر معمولی.

نوع مات: مخفی کردن درون struct

گاهی نمی‌خواهی کاربر فیلدهای یک struct را ببیند (که بعدا نتواند مستقیم دست‌کاری‌شان کند و تغییر ساختار همه‌جا را نشکند). ترفند: در هدر فقط نام struct را می‌نویسی و محتوایش را در .c. به این نوع مات (opaque type) می‌گویند: کاربر فقط اشاره‌گر به آن را دارد، نه درونش را.

#ifndef LED_H
#define LED_H

typedef struct led led_t;      /* نوع مات: فیلدها در led.c هستند */

led_t *led_get(unsigned index);
void led_on(led_t *led);
void led_off(led_t *led);
int led_is_on(const led_t *led);

#endif /* LED_H */

#include "led.h"

struct led {
    int pin;
    int on;
};

static led_t leds[2] = { { 5, 0 }, { 2, 0 } };

led_t *led_get(unsigned index)
{
    if (index >= 2U) {
        return 0;
    }
    return &leds[index];
}

void led_on(led_t *led)  { led->on = 1; }
void led_off(led_t *led) { led->on = 0; }
int led_is_on(const led_t *led) { return led->on; }

#include <stdio.h>
#include "led.h"

int main(void)
{
    led_t *ld2 = led_get(0);
    led_on(ld2);
    printf("led on: %d\n", led_is_on(ld2));
    led_off(ld2);
    printf("led on: %d\n", led_is_on(ld2));
    return 0;
}
  1. نوع ناقص. typedef struct led led_t; فقط می‌گوید «چنین struct ای هست». اندازه و فیلدهایش را کامپایلر main.c نمی‌داند. پس در main.c نمی‌شود led_t x; ساخت (اندازه نامعلوم) و نمی‌شود x->on نوشت. فقط اشاره‌گر led_t * مجاز است، چون اندازهٔ اشاره‌گر ثابت و معلوم است (روی MCUهای این دوره ۴ بایت، روی PC ۶۴ بیتی ۸ بایت).
  2. تابع‌های دسترسی. تمام کارها با اشاره‌گر انجام می‌شود. const led_t * برای تابعی که فقط می‌خواند.
  1. تعریف کامل struct. فقط در led.c که فیلدها را واقعا می‌شناسد.
  2. دو LED خصوصی. آرایهٔ static که پایهٔ ۵ (LD2 روی Nucleo) و ۲ (LED رایج ESP32) را نگه می‌دارد.
  3. تحویل اشاره‌گر. شمارهٔ نامعتبر را با اشاره‌گر 0 (NULL) رد می‌کنیم. در درس ۳.۲ دیدی همیشه باید NULL را چک کرد.
  4. تغییر و خواندن. اینجا فیلدها دیده می‌شوند و می‌شود -> زد.
$ gcc -std=c11 -Wall -Wextra -o opaque_ok main.c led.c
$ ./opaque_ok
led on: 1
led on: 0

اگر کاربر بخواهد دور زدن دیوار را امتحان کند، کامپایلر او را نگه می‌دارد (یک نمونهٔ کوچک با struct ناقص):

{
    struct led *p = 0;
    return p->on;

Makefile: دستور ساخت که یاد می‌گیرد چه چیزی عوض شده

ساخت دستی با چهار دستور برای ۳ فایل قابل تحمل است، ولی برای ۳۰ فایل نه. بدتر: بعد از تغییر یک خط، همه را از نو کامپایل می‌کنی؟ اگر فقط sensor.c عوض شده، چرا main.c را دوباره بسازی؟ ابزار make دقیقا برای همین است. یک فایل به‌نام Makefile می‌نویسی که می‌گوید «چه چیزی از چه چیزی ساخته می‌شود» و make با مقایسهٔ زمان فایل‌ها تصمیم می‌گیرد چه چیزی را از نو بسازد. این ابزار یک سیستم ساخت (build system) است.

مثال از زندگی روزمره

فرض کن فهرست خریدی داری: «برای پخت کیک: تخم‌مرغ + آرد». اگر دیروز کیک را پخته‌ای و امروز فقط آرد جدید خریده‌ای، باید دوباره کیک بپزی. اگر هیچ‌کدام تغییر نکرده‌اند، لازم نیست. make همین منطق «کدام مادهٔ اولیه از پخت جدیدتر است؟» را برای فایل‌ها به‌کار می‌برد.

یک Makefile از قاعده (rule) ساخته شده. هر قاعده سه بخش دارد:

هدف: پیش‌نیازها
	دستور ساخت

«هدف» فایلی است که می‌خواهی بسازی، «پیش‌نیازها» فایل‌هایی که هدف از آن‌ها ساخته می‌شود، و «دستور» چیزی که در ترمینال اجرا می‌شود. حتما جلوی دستور یک نویسهٔ Tab باشد (نه فاصله). این قدیمی‌ترین تله در Makefile است و پیام خطایش missing separator است.

CC      = gcc
CFLAGS  = -std=c11 -Wall -Wextra -Wpedantic -O1 -MMD -MP
TARGET  = thermo
SRCS    = main.c sensor.c filter.c
OBJS    = $(SRCS:.c=.o)
DEPS    = $(OBJS:.o=.d)

all: $(TARGET)

$(TARGET): $(OBJS)
	$(CC) $(OBJS) -o $@

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

-include $(DEPS)

clean:
	rm -f $(OBJS) $(DEPS) $(TARGET)

.PHONY: all clean
  1. متغیرهای ساخت. CC کامپایلر و CFLAGS پرچم‌هاست. برای استفادهٔ بعدی: $(CC). پرچم‌های -Wall -Wextra مثل همیشه؛ -MMD -MP را چند خط بعد توضیح می‌دهم. پرچم‌ها یک‌جا هستند. اگر بخواهی -O2 بگذاری یا برای ARM کراس‌کامپایل کنی، فقط این خط‌ها را عوض می‌کنی.
  2. اسم برنامه و منبع‌ها. برای افزودن فایل تازه فقط SRCS را عوض کن.
  3. جایگزینی پسوند. $(SRCS:.c=.o) یعنی «در فهرست SRCS هر .c را .o کن». می‌شود main.o sensor.o filter.o. مشابه برای .d.
  4. هدف پیش‌فرض. وقتی فقط make می‌زنی، اولین قاعدهٔ فایل ساخته می‌شود. اینجا all که می‌خواهد thermo ساخته شود.
  5. لینک. برنامه از فایل‌های شیء ساخته می‌شود. $@ یعنی «نام هدف» (thermo). اگر هر .o جدیدتر از thermo باشد، این دستور دوباره اجرا می‌شود.
  6. قاعدهٔ عمومی کامپایل. %.o: %.c یعنی «هر X.o از X.c ساخته می‌شود». $< اولین پیش‌نیاز (فایل .c) و $@ هدف (فایل .o).
  7. وابستگی به هدرها. پرچم -MMD به کامپایلر می‌گوید کنار هر .o یک فایل .d بسازد که فهرست هدرهای همان فایل را دارد. -include این فایل‌ها را می‌خواند (اگر هنوز نبودند خطا نمی‌دهد). بدون این، اگر filter.h را عوض کنی، make نمی‌فهمد main.c هم باید دوباره کامپایل شود؛ چون در قاعده‌اش فقط main.c پیش‌نیاز است. نتیجه: باگ‌های عجیبی که فقط با make clean رفع می‌شوند.
  8. پاک‌سازی. فایل‌های ساخته‌شده را حذف می‌کند تا ساخت از نو شروع شود.
  9. .PHONY. به make می‌گوید all و clean اسم فایل نیستند، اسم کارند. اگر روزی فایلی به نام clean در پوشه باشد، بدون این خط make clean فکر می‌کند «فایل clean که هست، کاری ندارم».
$ make
gcc -std=c11 -Wall -Wextra -Wpedantic -O1 -MMD -MP -c main.c -o main.o
gcc -std=c11 -Wall -Wextra -Wpedantic -O1 -MMD -MP -c sensor.c -o sensor.o
gcc -std=c11 -Wall -Wextra -Wpedantic -O1 -MMD -MP -c filter.c -o filter.o
gcc main.o sensor.o filter.o -o thermo
$ ./thermo
raw=23.1 avg=23.1
raw=23.6 avg=23.3
raw=22.9 avg=23.2
raw=24.0 avg=23.5
raw=23.3 avg=23.4

حالا ببین make چطور «هوشمند» رفتار می‌کند. بار دوم که می‌زنی چیزی تغییر نکرده. بعد فقط filter.h را «لمس» می‌کنیم (touch فقط زمان فایل را جدید می‌کند). فقط فایل‌هایی که آن هدر را include کرده‌اند دوباره ساخته می‌شوند (sensor.c هدر filter.h را ندارد و دست‌نخورده می‌ماند):

روی پروژهٔ بزرگ (هزاران فایل) این هوشمندی فرق ۳۰ ثانیه با ۳۰ دقیقه است.

تلهٔ Tab و تلهٔ پرچم‌ها
  • Tab نه فاصله. اگر ویرایشگرت Tab را به چهار فاصله تبدیل کند، make خطای *** missing separator. Stop. می‌دهد. در VS Code برای فایل Makefile حالت «Indent Using Tabs» را روشن کن.
  • Makefile فقط زمان فایل‌ها را نگاه می‌کند، نه پرچم‌ها را. اگر CFLAGS را عوض کنی (مثلا -DBOARD=2)، فایل‌های .o قدیمی جدیدتر از .c هستند و دوباره ساخته نمی‌شوند. بعد از تغییر پرچم‌ها یک بار make clean بزن. در تمرین ۳ این را واقعا می‌بینی.

CMake: نسل بعدی

Makefile روی Linux و macOS عالی است ولی روی Windows و بین IDEها دردسر دارد. CMake (CMake) یک لایه بالاتر است: تو در CMakeLists.txt می‌نویسی «این برنامه از این فایل‌ها ساخته می‌شود» و CMake خودش برای هر سیستم (Makefile، Ninja، Visual Studio) فایل ساخت می‌سازد. ESP-IDF و بسیاری از پروژه‌های STM32 (از جمله خروجی CubeMX نسخه‌های جدید) از CMake استفاده می‌کنند.

cmake_minimum_required(VERSION 3.10)
project(thermo C)

set(CMAKE_C_STANDARD 11)
set(CMAKE_C_STANDARD_REQUIRED ON)

add_executable(thermo main.c sensor.c filter.c)
target_compile_options(thermo PRIVATE -Wall -Wextra -Wpedantic)
  1. حداقل نسخه و پروژه. اسم پروژه thermo و زبانش C.
  2. استاندارد C11. معادل -std=c11 و REQUIRED یعنی «اگر نشد، خطا بده».
  3. تعریف برنامه. اسم خروجی و فهرست منبع‌ها. هدرها را لازم نیست بنویسی؛ CMake وابستگی هدرها را خودش پیدا می‌کند.
  4. پرچم هشدار. فقط برای این برنامه (PRIVATE).

ساخت با CMake دو مرحله دارد: «پیکربندی» (ساخت فایل‌های ساخت در یک پوشهٔ جدا به‌نام build) و «ساخت». من این را روی همین پروژه اجرا کردم:

در STM32 و ESP32 پروژه چه شکلی دارد؟

همین منطق (هدر، منبع، فهرست ساخت) در پروژهٔ واقعی MCU هم هست. فقط چند فایل ویژه اضافه می‌شود. نام‌های زیر نمونهٔ رایج‌اند و بسته به نسخهٔ ابزار ممکن است کمی فرق کنند:

STM32

خروجی CubeMX (یا نمونه‌های آماده) معمولا یک Makefile یا CMakeLists.txt می‌آورد. سه فایل ویژه دارد که در PC نبود: startup (کدی که بعد از روشن‌شدن اجرا می‌شود و main را صدا می‌زند)، linker script (فایل .ld که می‌گوید Flash و RAM کجا هستند و هر بخش کد کجا می‌نشیند) و HAL/CMSIS (هدرهای ثبات‌ها و کتابخانه). هر سه را در درس ۵.۱ از نزدیک می‌سازیم. ساخت برای ARM فقط با تغییر کامپایلر است:

CC      = arm-none-eabi-gcc
CFLAGS  = -mcpu=cortex-m4 -mthumb -std=gnu11 -Wall -Wextra -ffunction-sections -fdata-sections
LDFLAGS = -T STM32F411RETx_FLASH.ld -Wl,--gc-sections

همان قاعدهٔ %.o: %.c، فقط با CC و CFLAGS تازه. برای شروع بهتر است از پروژهٔ نمونهٔ تولیدشده استفاده کنی و بخوانی، نه اینکه از صفر بنویسی. (شرح هر پرچم را در درس ۶.۵ می‌بینی.)

نکتهٔ دیباگ: برای اینکه در GDB/دیباگر بتوانی اسم متغیرها و شمارهٔ خط را ببینی، هنگام ساخت -g را به CFLAGS اضافه کن؛ بدون آن ELF فقط کد ماشین دارد. (-g اندازهٔ Flash را زیاد نمی‌کند؛ اطلاعات دیباگ در خود فایل ELF می‌ماند و روی برد نمی‌رود.)

ESP32 (ESP-IDF)

ESP-IDF از CMake استفاده می‌کند و مفهوم کامپوننت (component) دارد: هر پوشه با CMakeLists.txt خودش، یک ماژول. کامپوننت main همیشه هست و شامل app_main است. کامپوننت‌های خودت را در پوشهٔ components/ می‌گذاری. نمونه (الگوی ESP-IDF v5.x؛ جزئیات دقیق را در مستندات رسمی ESP-IDF Programming Guide ببین):

# CMakeLists.txt در ریشهٔ پروژه
cmake_minimum_required(VERSION 3.16)
include($ENV{IDF_PATH}/tools/cmake/project.cmake)
project(thermo)

# components/sensor/CMakeLists.txt
idf_component_register(SRCS "sensor.c"
                       INCLUDE_DIRS "include")
  1. ثبت کامپوننت. SRCS فایل‌های .c و INCLUDE_DIRS پوشه‌هایی که هدرهای عمومی (API) در آن‌هاست. هر کامپوننتی که sensor.h را بخواهد، این پوشه را در مسیر include می‌بیند. این همان تقسیم «منو و آشپزخانه» است: پوشهٔ include منو و بقیه خصوصی.

برای اینکه کامپوننت main از sensor استفاده کند، در main/CMakeLists.txt آن را با REQUIRES (یا PRIV_REQUIRES) اعلام می‌کنی. سپس idf.py build همه را می‌سازد. پرچم‌ها و تنظیمات را idf.py menuconfig در فایل sdkconfig ذخیره می‌کند (پایهٔ همان ماکروهای CONFIG_... درس ۴.۱).

PlatformIO

PlatformIO افزونه‌ای برای VS Code است (درس ۱.۳) که کامپایلر و کتابخانه را خودش می‌آورد. تنها فایل تنظیم platformio.ini است:

[env:nucleo_f411re]
platform = ststm32
board = nucleo_f411re
framework = cmsis

[env:esp32dev]
platform = espressif32
board = esp32dev
framework = espidf
  1. یک محیط برای STM32. نام محیط، پلتفرم، برد و چارچوب.
  2. یک محیط برای ESP32. با pio run -e esp32dev فقط همین محیط ساخته می‌شود. یک پروژه با دو محیط، دقیقا همان «یک کد، چند برد» درس ۴.۱ است. نام برد و چارچوب‌ها را حتما در مستندات PlatformIO تطبیق بده؛ فهرستشان مرتب عوض می‌شود.

آزمون این درس

کدام خط تعریف است، نه اعلان؟

  1. extern int g_count;
  2. int read_adc(void);
  3. int g_count = 0;
  4. typedef struct led led_t;
تعریف قفسه یا کد را می‌سازد و فقط یک بار در کل برنامه مجاز است. اعلان فقط اسم را معرفی می‌کند.

لینکر می‌گوید undefined reference to `uart_send'. اولین چیزی که باید چک کنی چیست؟

  1. در ماژول uart نقطه‌ویرگول جا افتاده است
  2. آیا فایل uart.c کامپایل و لینک شده و آیا uart_send همان اسم را دارد و static نیست
  3. include guard در uart.h کم است
  4. آرایه‌ها بزرگ‌اند و باید کوچک شوند
کامپایل شدن یعنی اعلان دیده شده است. خطای لینکر یعنی تعریف در فایل‌های لینک‌شده نیست: فایل را فراموش کرده‌ای، اسم را غلط نوشته‌ای یا تابع static است.

هدر state.h شامل int g_state = 0; است و دو فایل .c آن را include می‌کنند. با وجود include guard، لینک چه می‌شود؟

  1. خطای multiple definition of `g_state'؛ چون هر فایل ترجمه، تعریف خودش را ساخته است
  2. بدون خطا؛ include guard جلویش را می‌گیرد
  3. فقط یک هشدار می‌گیرد و برنامه ساخته می‌شود
  4. هر دو فایل .c کامپایل نمی‌شوند
هر .c جدا کامپایل می‌شود و guard برای هر کدام از نو شروع می‌شود. تعریف در هدر یعنی تعریف در همهٔ فایل‌ها. راه‌حل: extern int g_state; در هدر و int g_state = 0; در یک .c.

static جلوی یک تابع در .c چه می‌کند؟

  1. تابع را سریع‌تر می‌کند
  2. متغیرهای محلی تابع را حفظ می‌کند
  3. تابع را برای همهٔ فایل‌ها قابل‌دیدن می‌کند
  4. تابع را فقط برای همان فایل ترجمه قابل‌دیدن می‌کند (پیوند درونی)
در سطح فایل، static یعنی «پیوند درونی»: لینکر این اسم را برای فایل‌های دیگر نمی‌بیند. دو فایل می‌توانند تابع static هم‌نام داشته باشند.

پروژه‌ات با make ساخته می‌شود و CFLAGS را از -DBOARD=1 به -DBOARD=2 عوض کرده‌ای، ولی خروجی همان قبلی است. چرا؟

  1. make پرچم جدید را نمی‌شناسد
  2. کامپایلر خطا داده است ولی دیده نشده
  3. make فقط زمان فایل‌ها را نگاه می‌کند و .o قدیمی هنوز جدیدتر از .c است؛ باید make clean بزنی
  4. Makefile فقط برای یک برد کار می‌کند
Makefile وابستگی به «پرچم‌ها» را نمی‌فهمد؛ فقط زمان فایل‌ها را مقایسه می‌کند. بعد از عوض‌کردن پرچم‌ها، make clean یا حذف .oها لازم است.

در پروژهٔ STM32، ISR یک پرچم را ۱ می‌کند و main می‌خواند. پرچم در فایل button.c تعریف شده است. در button.h چه می‌نویسی؟

  1. volatile uint8_t g_pressed = 0;
  2. extern volatile uint8_t g_pressed;
  3. static volatile uint8_t g_pressed;
  4. volatile uint8_t g_pressed;
اعلان با extern، تعریف در یک .c، و volatile چون ISR مقدار را «پشت سر برنامه» تغییر می‌دهد (درس ۳.۶).

تمرین‌ها

تمرین ۱: تقسیم یک برنامه به ماژول

برنامهٔ زیر همه‌چیز را در یک فایل دارد. آن را به سه فایل conv.h، conv.c و main.c تقسیم کن.

#include <stdio.h>

int celsius_to_f(int c) { return c * 9 / 5 + 32; }
int clamp_int(int v, int lo, int hi)
{
    if (v < lo) return lo;
    if (v > hi) return hi;
    return v;
}

int main(void)
{
    printf("%d C = %d F\n", 25, celsius_to_f(25));
    printf("clamp(150) = %d\n", clamp_int(150, 0, 100));
    return 0;
}
  1. پیش‌بینی: اگر فایل conv.c را در دستور gcc ننویسی (فقط gcc main.c) چه خطایی می‌گیری؟ لینکر یا کامپایلر؟
  2. حل: سه فایل را بنویس (با include guard و هدر خودکفا) و با gcc -std=c11 -Wall -Wextra -o conv main.c conv.c بساز.
  3. چالش: یک Makefile کوتاه برایش بنویس که فقط با make ساخته شود.
راهنمایی

در conv.h فقط دو پروتوتایپ و guard. در conv.c اول #include "conv.h" و بعد بدنهٔ دو تابع. در main.c فقط stdio.h و conv.h. برای Makefile می‌توانی الگوی Makefile درس را کپی و SRCS را عوض کنی.

چه باید ببینی؟ 
$ ./conv
25 C = 77 F
clamp(150) = 100

جواب قسمت الف: خطای لینکر (undefined reference to `celsius_to_f')، چون اگر هدر را نوشته باشی، کامپایلر اعلان را می‌بیند و راضی است، ولی لینکر تعریف را پیدا نمی‌کند.

جواب کامل با توضیح 
#ifndef CONV_H
#define CONV_H

int celsius_to_f(int c);
int clamp_int(int v, int lo, int hi);

#endif /* CONV_H */

#include "conv.h"

int celsius_to_f(int c)
{
    return c * 9 / 5 + 32;
}

int clamp_int(int v, int lo, int hi)
{
    if (v < lo) {
        return lo;
    }
    if (v > hi) {
        return hi;
    }
    return v;
}

#include <stdio.h>
#include "conv.h"

int main(void)
{
    printf("%d C = %d F\n", 25, celsius_to_f(25));
    printf("clamp(150) = %d\n", clamp_int(150, 0, 100));
    return 0;
}
  1. guard. از دوبار ورود جلوگیری می‌کند.
  2. فقط اعلان‌ها. دو پروتوتایپ؛ همان چیزی که main.c لازم دارد.
  1. هدر خودش. برای بررسی سازگاری تعریف با اعلان.
  2. تعریف‌ها. همان بدنه‌های قبلی، با آکولاد کامل.
  1. دو include. استاندارد و هدر پروژه.
  2. استفاده. صدا زدن توابع فقط از روی اعلان.
$ gcc -std=c11 -Wall -Wextra -o conv main.c conv.c
$ ./conv
25 C = 77 F
clamp(150) = 100
تمرین ۲: باگ‌های چندفایلی را پیدا کن

در این سه تکه، هر کدام یک اشتباه ساختاری دارد. بگو چه اتفاقی می‌افتد و چطور درست می‌شود.

/* uart.h */
volatile unsigned char g_rx_flag = 0;
void uart_init(void) { g_rx_flag = 0; }

/* sensor.c  (sensor.h را include نکرده) */
int sensor_read_dc(void) { return 231; }

/* main.c */
static int helper(void);
int main(void) { return helper(); }
  1. uart.h: اگر دو فایل .c آن را include کنند چه می‌شود؟ چطور اصلاحش می‌کنی؟
  2. sensor.c: چه شبکهٔ ایمنی از دست رفته؟ (فکر کن اگر نوع برگشتی در هدر int16_t باشد.)
  3. main.c: helper در فایل دیگری تعریف شده و اینجا static اعلان شده. چه خطایی و چرا؟
راهنمایی

الف: قاعدهٔ «در هدر فقط اعلان». ب: خطای conflicting types را یادت بیاور. پ: static یعنی پیوند درونی.

چه باید ببینی؟

الف: multiple definition of `g_rx_flag' و multiple definition of `uart_init'. ب: هیچ خطایی، و همین خطرناک است. پ: در main.c، کامپایلر هشدار می‌دهد 'helper' used but never defined و لینک خطای خودش را می‌دهد (چون static است، هیچ فایل دیگری هم نمی‌تواند تعریفش کند).

$ ./uart_demo
rx_flag=1 byte=65
جواب کامل با توضیح
بخشمشکلاصلاح
الفپرچم و تابع در هدر تعریف شده‌اند؛ هر .c که include کند یک نسخه می‌سازد → multiple definition؛ guard هم ندارددر uart.h: guard، extern volatile uint8_t g_rx_flag; و پروتوتایپ؛ تعریف‌ها در uart.c
بتعریف بدون include کردن هدر خودش؛ کامپایلر نمی‌تواند با اعلان مقایسه کند و ناسازگاری نوع پنهان می‌ماند#include "sensor.h" در بالای sensor.c
پstatic یعنی تعریف باید در همین فایل باشد؛ فایل دیگر نمی‌تواند آن را تأمین کندیا تعریف را به همین فایل بیاور، یا static را بردار و اعلان را در هدر بگذار

نسخهٔ اصلاح‌شدهٔ ماژول uart (یک شبیه‌سازی روی PC):

#ifndef UART_H
#define UART_H

#include <stdint.h>

extern volatile uint8_t g_rx_flag;

void uart_init(void);
void uart_on_byte(uint8_t byte);
uint8_t uart_last_byte(void);

#endif /* UART_H */

#include "uart.h"

volatile uint8_t g_rx_flag = 0;
static uint8_t last_byte = 0;

void uart_init(void)
{
    g_rx_flag = 0;
    last_byte = 0;
}

void uart_on_byte(uint8_t byte)
{
    last_byte = byte;
    g_rx_flag = 1;
}

uint8_t uart_last_byte(void)
{
    return last_byte;
}

#include <stdio.h>
#include "uart.h"

int main(void)
{
    uart_init();
    uart_on_byte(65);
    if (g_rx_flag) {
        printf("rx_flag=%u byte=%u\n", (unsigned)g_rx_flag, (unsigned)uart_last_byte());
    }
    return 0;
}
  1. اعلان متغیر مشترک. extern volatile؛ بدون مقدار اولیه.
  2. اعلان توابع. فقط واسط: uart_last_byte راه خواندن است، چون last_byte خصوصی می‌ماند.
  1. تعریف پرچم. تنها جایی که قفسه ساخته می‌شود.
  2. داده خصوصی. static است؛ بیرون فقط از راه تابع دیده می‌شود.
  3. توابع ماژول. شبیه‌سازی دریافت یک بایت: ذخیرهٔ آخرین بایت و بلند کردن پرچم (روی MCU این کار را ISR انجام می‌دهد).
$ gcc -std=c11 -Wall -Wextra -o uart_demo main.c uart.c
$ ./uart_demo
rx_flag=1 byte=65
تمرین ۳: یک کد، دو برد، با make

می‌خواهیم پروژهٔ کوچکی بسازیم که نام برد و پایهٔ LED را چاپ کند و برد را با make BOARD=2 انتخاب شود (شبیه -DBOARD درس ۴.۱).

  1. پیش‌بینی: اگر یک‌بار make run بزنی و بعد make BOARD=2 run، به‌نظرت خروجی دوم چیست؟
  2. حل: یک Makefile بنویس با متغیر BOARD ?= 1 (یعنی «اگر از بیرون نیامده، ۱») که -DBOARD=$(BOARD) را به CFLAGS اضافه کند و هدف run و clean داشته باشد.
  3. فکر کن: چرا خروجی بعد از make BOARD=2 run هنوز برد ۱ است؟ چطور درستش می‌کنی؟
راهنمایی

اول make clean بزن و make BOARD=2 run را بزن. فکر کن make چه چیزی را با چه چیزی مقایسه می‌کند: زمان فایل‌ها. پرچم‌ها در هیچ فایلی نیستند.

چه باید ببینی؟ 
$ make run
board=nucleo-f411re led_pin=5
$ make BOARD=2 run
board=nucleo-f411re led_pin=5      # هنوز قدیمی! (چون main.o جدیدتر از main.c است)
$ make clean
$ make BOARD=2 run
board=esp32-devkit led_pin=2
جواب کامل با توضیح 
#ifndef BOARD_H
#define BOARD_H

#ifndef BOARD
#define BOARD 1
#endif

#if BOARD == 1
#define BOARD_NAME "nucleo-f411re"
#define LED_PIN    5
#elif BOARD == 2
#define BOARD_NAME "esp32-devkit"
#define LED_PIN    2
#else
#error "Unknown BOARD"
#endif

#endif /* BOARD_H */

#include <stdio.h>
#include "board.h"

int main(void)
{
    printf("board=%s led_pin=%d\n", BOARD_NAME, LED_PIN);
    return 0;
}

CC      = gcc
BOARD  ?= 1
CFLAGS  = -std=c11 -Wall -Wextra -DBOARD=$(BOARD)
TARGET  = board_demo

all: $(TARGET)

$(TARGET): main.o
	$(CC) main.o -o $@

main.o: main.c board.h
	$(CC) $(CFLAGS) -c main.c -o $@

run: $(TARGET)
	./$(TARGET)

clean:
	rm -f main.o $(TARGET)

.PHONY: all run clean
  1. متغیر برد. ?= فقط وقتی مقدار می‌دهد که BOARD از بیرون (خط فرمان یا محیط) نیامده باشد. make BOARD=2 آن را ۲ می‌کند. پرچم -DBOARD=... به کامپایلر می‌رسد.
  2. لینک. برنامه از main.o.
  3. کامپایل. وابسته به main.c و board.h؛ اگر هر دو (زمان) عوض شوند دوباره ساخته می‌شود. ولی مقدار BOARD در هیچ فایلی نیست. مهم همین است: make نمی‌فهمد -DBOARD عوض شده.
  4. اجرا. run اول board_demo را می‌سازد و بعد اجرا می‌کند.
  5. پاک‌سازی. برای وقتی که پرچم عوض می‌شود.

$ make BOARD=2 run

$ make clean

$ make BOARD=2 run

ابزارهای بزرگ‌تر این مشکل را با نگه‌داشتن پرچم‌های ساخت در یک فایل و مقایسهٔ آن حل می‌کنند (CMake خودش هنگام تغییر گزینه‌ها همه را از نو می‌سازد). در Makefile ساده، عادت «بعد از عوض‌کردن پرچم، make clean» کافی است.

حرف مربی

تقریبا همه در این درس سه جا گیر می‌کنند. اول اعلان و تعریف را قاطی می‌کنند؛ قانون ساده: هر چیزی که حافظه می‌گیرد فقط یک‌بار و در .c باشد. دوم از پیام لینکر می‌ترسند؛ در حالی که فقط دو جمله است: «این اسم را پیدا نکردم» یا «این اسم را دو بار پیدا کردم». سوم Tab در Makefile. برای اینکه مطمئن شوی درس را فهمیده‌ای، یک پروژهٔ کوچک با سه ماژول بساز و عمدا هر سه خطا را تولید کن؛ وقتی خودت بلد باشی خراب کنی، خطاها را در پروژهٔ واقعی ۱۰ ثانیه‌ای پیدا می‌کنی.

خلاصه یک‌دقیقه‌ای

  • ماژول = یک .h (منو: اعلان‌ها) + یک .c (آشپزخانه: تعریف‌ها). هر .c جدا کامپایل می‌شود و لینکر همه را وصل می‌کند.
  • اعلان اسم را معرفی می‌کند و چندبار مجاز است؛ تعریف حافظه می‌گیرد و فقط یک بار. در هدر فقط اعلان (و ماکرو/نوع/static inline).
  • متغیر مشترک: extern در هدر، تعریف در یک .c. تا می‌توانی متغیر را static نگه دار.
  • static در سطح فایل = پیوند درونی: اسم برای بقیه پنهان است.
  • خطاهای لینکر: undefined reference (تعریف نیست: فایل، غلط املایی یا static) و multiple definition (تعریف دو بار: معمولا تعریف در هدر). هر .c باید هدر خودش را include کند تا conflicting types را زود بگیرد.
  • Makefile: قاعده‌های هدف: پیش‌نیاز با Tab؛ -MMD وابستگی هدرها را می‌سازد؛ پرچم‌ها را make نمی‌بیند، پس بعد از تغییرشان make clean.
  • CMake، فایل‌های ساخت را برای هر سیستم می‌سازد. ESP-IDF کامپوننت با idf_component_register دارد؛ PlatformIO با platformio.ini؛ پروژهٔ STM32 علاوه بر منبع‌ها startup و linker script دارد.

درس بعد: ۴.۳ اشاره‌گر به تابع و callback.
